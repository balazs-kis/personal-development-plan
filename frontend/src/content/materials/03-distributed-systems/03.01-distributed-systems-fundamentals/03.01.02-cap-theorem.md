## Introduction

The CAP theorem, proposed by Eric Brewer in 2000 and formally proven by Seth Gilbert and Nancy Lynch in 2002, states that in a distributed data store, it's impossible to simultaneously provide all three of the following guarantees: Consistency, Availability, and Partition tolerance. Understanding CAP is fundamental to choosing the right technologies and making architectural decisions.

## CAP Theorem Explained

### The Three Properties

#### **Consistency (C)**

Every read receives the most recent write or an error. All nodes see the same data at the same time. This is formally called **linearizability**—the strongest form of consistency.

**Formal Definition:** If operation A completes before operation B begins, then B must see the effects of A.

**What This Means in Practice:**
- No stale reads
- All replicas synchronized before acknowledging writes
- Writes block until all nodes agree
- Higher latency but guaranteed correctness

**Example:** After updating a user's email address, every subsequent read must return the new email—never the old one, even if reading from a different node.

```csharp
// Strong consistency requirement
public class StronglyConsistentUserStore
{
    private readonly DbContext _primaryDb;
    private readonly List<DbContext> _replicas;
    
    public async Task UpdateEmailAsync(string userId, string newEmail)
    {
        // Write to primary
        var user = await _primaryDb.Users.FindAsync(userId);
        user.Email = newEmail;
        await _primaryDb.SaveChangesAsync();
        
        // Wait for all replicas to acknowledge
        var replicationTasks = _replicas.Select(async replica =>
        {
            var replicaUser = await replica.Users.FindAsync(userId);
            replicaUser.Email = newEmail;
            await replica.SaveChangesAsync();
        });
        
        // Block until ALL replicas confirm
        await Task.WhenAll(replicationTasks);
        
        // Only now acknowledge success to client
    }
    
    public async Task<User> GetUserAsync(string userId)
    {
        // Always reads from primary database to ensure latest data
        return await _primaryDb.Users
            .AsNoTracking()
            .FirstOrDefaultAsync(u => u.Id == userId);
    }
}
```

**Trade-offs:**
- ✅ Guarantees correctness
- ✅ Simpler reasoning about system behavior
- ❌ Higher write latency (waiting for replication)
- ❌ Reduced availability (fails if replicas unreachable)
- ❌ Doesn't scale writes well

---

#### **Availability (A)**

Every request receives a (non-error) response, without guarantee that it contains the most recent write. The system remains operational and responsive.

**Formal Definition:** Every request to a non-failing node must result in a response (but the response might contain stale data).

**What This Means in Practice:**
- System always responds (no timeouts)
- Can read from any replica
- Writes succeed even if some nodes are unreachable
- May return stale data temporarily

**Example:** The system always responds to requests, even if some nodes are down, though the data might be slightly stale (seconds or minutes old).

```csharp
// Availability priority: read from any replica
public class HighlyAvailableUserStore
{
    private readonly List<DbContext> _readReplicas;
    private int _replicaIndex = 0;
    
    public async Task<User> GetUserAsync(string userId)
    {
        // Round-robin through replicas for load distribution
        var replica = _readReplicas[_replicaIndex++ % _readReplicas.Count];
        
        try
        {
            // Reads from any available replica, might be slightly stale
            return await replica.Users
                .AsNoTracking()
                .FirstOrDefaultAsync(u => u.Id == userId);
        }
        catch
        {
            // Try another replica if this one fails
            var alternateReplica = _readReplicas
                .FirstOrDefault(r => r != replica);
            
            if (alternateReplica != null)
            {
                return await alternateReplica.Users
                    .AsNoTracking()
                    .FirstOrDefaultAsync(u => u.Id == userId);
            }
            
            throw;
        }
    }
    
    public async Task UpdateEmailAsync(string userId, string newEmail)
    {
        // Write to local node, replicate asynchronously
        var localUser = await _readReplicas[0].Users.FindAsync(userId);
        localUser.Email = newEmail;
        
        // Don't wait for replication—return immediately
        await _readReplicas[0].SaveChangesAsync();
        
        // Background replication to other nodes
        _ = Task.Run(async () =>
        {
            foreach (var replica in _readReplicas.Skip(1))
            {
                try
                {
                    var user = await replica.Users.FindAsync(userId);
                    user.Email = newEmail;
                    await replica.SaveChangesAsync();
                }
                catch
                {
                    // Log error but don't fail the write
                }
            }
        });
    }
}
```

**Trade-offs:**
- ✅ Low latency (immediate responses)
- ✅ High throughput
- ✅ Resilient to node failures
- ❌ Possible stale reads
- ❌ Conflict resolution complexity
- ❌ Harder to reason about system state

#### **Partition Tolerance (P)**

The system continues to operate despite arbitrary partitioning due to network failures. Messages between nodes may be lost or delayed indefinitely.

**Formal Definition:** The system continues to function despite an arbitrary number of messages being dropped (or delayed) by the network between nodes.

**Why It's Non-Negotiable:**

In distributed systems, network partitions are not a rare edge case—they're a normal operating condition. Networks fail for many reasons:
- Switch failures
- Router misconfigurations
- Fiber cuts
- Software bugs in network stack
- Overloaded network links
- Firewall misconfigurations

**Reality:** In a distributed system, partitions WILL happen. Network failures are inevitable, so partition tolerance is not optional—you must choose between C and A during a partition.

```csharp
// Detecting network partitions
public class PartitionDetector
{
    private readonly List<Node> _nodes;
    private readonly ILogger _logger;
    
    public async Task<PartitionStatus> DetectPartitionAsync()
    {
        var reachableNodes = new List<Node>();
        var unreachableNodes = new List<Node>();
        
        foreach (var node in _nodes)
        {
            try
            {
                using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
                await node.PingAsync(cts.Token);
                reachableNodes.Add(node);
            }
            catch (Exception ex)
            {
                _logger.LogWarning(
                    "Node {NodeId} unreachable: {Error}",
                    node.Id, ex.Message);
                unreachableNodes.Add(node);
            }
        }
        
        var reachableRatio = reachableNodes.Count / (double)_nodes.Count;
        
        if (reachableRatio == 1.0)
        {
            return PartitionStatus.Healthy;
        }
        else if (reachableRatio >= 0.5)
        {
            // We can reach majority—we're in the majority partition
            return PartitionStatus.MajorityPartition;
        }
        else
        {
            // We can't reach majority—we're in minority partition
            return PartitionStatus.MinorityPartition;
        }
    }
}
```

## The CAP Trade-off: Deep Dive

### Understanding the Proof

Why can't we have all three? Here's the intuitive proof:

**Scenario:**
1. Network partition splits nodes into two groups: A and B
2. Client writes to group A
3. Client reads from group B

**The Dilemma:**
- If we return the new value from B (Consistency): B must have communicated with A, but there's a partition—impossible!
- If we return a response from B without the new value (Availability): We violate consistency
- If we refuse to respond (neither C nor A): We violate both

**Conclusion:** We can maintain partition tolerance (handle the partition), but must choose: respond with potentially stale data (A) or refuse to respond (C).

---

### CA (Consistency + Availability) - No Partition Tolerance

**Reality:** Impossible in distributed systems because partitions happen. This category is largely theoretical.

**Example:** Single-node databases (PostgreSQL, MySQL on one server) are technically CA, but they're not distributed—there are no partitions because there's only one node.

**Why This Doesn't Work in Distribution:**
- If you claim to be "CA", you're actually failing during partitions
- You're prioritizing C and hoping partitions don't happen
- When they do happen, availability drops to zero

```csharp
// "CA" approach (doesn't work in practice for distributed systems)
public class NaiveReplicatedStore
{
    private readonly DbContext _node1;
    private readonly DbContext _node2;
    
    public async Task WriteAsync(string key, string value)
    {
        // Attempt to write to both nodes
        try
        {
            await _node1.Data.AddAsync(new DataItem { Key = key, Value = value });
            await _node1.SaveChangesAsync();
            
            await _node2.Data.AddAsync(new DataItem { Key = key, Value = value });
            await _node2.SaveChangesAsync();
            
            // Success: consistent and available
        }
        catch (Exception ex)
        {
            // Network partition! Now what?
            // - If we proceed with one node: violates consistency
            // - If we fail the request: violates availability
            // We must choose C or A
            
            throw new PartitionException("Cannot guarantee both C and A during partition");
        }
    }
}
```

### CP (Consistency + Partition Tolerance) - Sacrifice Availability

When a partition occurs, the system becomes unavailable (returns errors) to maintain consistency. The minority partition stops accepting writes.

**Philosophy:** "It's better to be unavailable than to be wrong."

**Use Cases:**
- **Banking transactions:** Never allow inconsistent balances
- **Inventory systems:** Overselling is unacceptable
- **Booking systems:** Double-booking is unacceptable
- **Locking systems:** Only one holder at a time
- **Configuration management:** All nodes must have same config

**Examples:**
- MongoDB (in default configuration with majority writes)
- HBase
- Redis Cluster
- Azure Cosmos DB with strong consistency
- etcd
- ZooKeeper
- Google Spanner

**Implementation Pattern:**

```csharp
// CP approach: Fail if we can't guarantee consistency
public class ConsistentPartitionTolerantStore
{
    private readonly List<IDataNode> _nodes;
    private readonly IPartitionDetector _partitionDetector;
    
    public async Task<bool> TransferMoneyAsync(
        string fromAccount, 
        string toAccount, 
        decimal amount)
    {
        // Check if we can achieve consensus
        var partitionStatus = await _partitionDetector.DetectPartitionAsync();
        
        if (partitionStatus == PartitionStatus.MinorityPartition)
        {
            // We're in minority—refuse to serve to maintain consistency
            throw new ServiceUnavailableException(
                "Cannot guarantee consistency during partition");
        }
        
        // We're in majority partition—proceed with quorum writes
        var quorumSize = (_nodes.Count / 2) + 1;
        
        var transaction = new DistributedTransaction
        {
            FromAccount = fromAccount,
            ToAccount = toAccount,
            Amount = amount
        };
        
        var commitTasks = _nodes
            .Take(quorumSize)
            .Select(node => node.CommitTransactionAsync(transaction));
        
        try
        {
            await Task.WhenAll(commitTasks);
            return true;
        }
        catch
        {
            // Couldn't achieve quorum—abort
            await RollbackTransactionAsync(transaction);
            throw new ServiceUnavailableException(
                "Quorum not achieved—transaction aborted");
        }
    }
    
    public async Task<decimal> GetBalanceAsync(string accountId)
    {
        var partitionStatus = await _partitionDetector.DetectPartitionAsync();
        
        if (partitionStatus == PartitionStatus.MinorityPartition)
        {
            // Refuse to serve stale data
            throw new ServiceUnavailableException(
                "Cannot serve read in minority partition");
        }
        
        // Read from majority to ensure consistency
        var quorumSize = (_nodes.Count / 2) + 1;
        var readTasks = _nodes
            .Take(quorumSize)
            .Select(node => node.GetBalanceAsync(accountId));
        
        var balances = await Task.WhenAll(readTasks);
        
        // Use latest version (by timestamp or version number)
        return balances
            .OrderByDescending(b => b.Version)
            .First()
            .Amount;
    }
}
```

**Real-World Example: MongoDB**

```csharp
// MongoDB with majority write concern (CP)
public class MongoDbCPExample
{
    private readonly IMongoCollection<BankAccount> _accounts;
    
    public async Task<bool> TransferAsync(string from, string to, decimal amount)
    {
        var session = await _client.StartSessionAsync();
        session.StartTransaction(new TransactionOptions(
            readConcern: ReadConcern.Majority,
            writeConcern: WriteConcern.WMajority // Wait for majority
        ));
        
        try
        {
            var fromAccount = await _accounts.Find(
                session, 
                a => a.Id == from).FirstOrDefaultAsync();
            
            var toAccount = await _accounts.Find(
                session,
                a => a.Id == to).FirstOrDefaultAsync();
            
            fromAccount.Balance -= amount;
            toAccount.Balance += amount;
            
            await _accounts.ReplaceOneAsync(session, 
                a => a.Id == from, fromAccount);
            await _accounts.ReplaceOneAsync(session,
                a => a.Id == to, toAccount);
            
            // Commits only when majority of nodes acknowledge
            await session.CommitTransactionAsync();
            
            return true;
        }
        catch (MongoException ex) when (ex.Message.Contains("NotMasterError"))
        {
            // Network partition—we're not in majority
            // Transaction fails to maintain consistency
            await session.AbortTransactionAsync();
            throw new ServiceUnavailableException(
                "Cannot complete transaction during partition");
        }
    }
}
```

**Trade-offs:**
- ✅ Data correctness guaranteed
- ✅ No split-brain scenarios
- ✅ Simpler conflict resolution (no conflicts!)
- ❌ Unavailable during partitions
- ❌ Higher latency (quorum writes)
- ❌ Reduced write throughput

### AP (Availability + Partition Tolerance) - Sacrifice Consistency

When a partition occurs, both sides remain available but may have inconsistent data. Consistency is eventually achieved after partition heals.

**Philosophy:** "It's better to give an answer than no answer, even if it might be slightly outdated."

**Use Cases:**
- **Social media feeds:** Slight staleness acceptable
- **Shopping cart contents:** Can be reconciled later
- **Product catalogs:** Minor inconsistencies tolerable
- **User profiles:** Eventual consistency is fine
- **Real-time analytics:** Approximation acceptable
- **DNS:** Availability critical, propagation delays acceptable

**Examples:**
- Cassandra
- DynamoDB
- Couchbase
- Riak
- Azure Cosmos DB with eventual consistency
- CouchDB

**Implementation Pattern:**

```csharp
// AP approach: Always available, eventual consistency
public class AvailablePartitionTolerantStore
{
    private readonly IDataNode _localNode;
    private readonly List<IDataNode> _remoteNodes;
    private readonly IConflictResolver _conflictResolver;
    
    public async Task AddToCartAsync(string userId, CartItem item)
    {
        // Write to local datacenter immediately
        var cart = await GetOrCreateCartAsync(userId);
        cart.Items.Add(item);
        cart.LastModified = DateTime.UtcNow;
        cart.Version++; // Vector clock or version number
        
        // Save locally—always succeeds (availability)
        await _localNode.SaveAsync(cart);
        
        // Asynchronous replication—fire and forget
        _ = Task.Run(async () =>
        {
            foreach (var node in _remoteNodes)
            {
                try
                {
                    await node.ReplicateAsync(cart);
                }
                catch (Exception ex)
                {
                    // Log but don't fail—will sync later
                    _logger.LogWarning(
                        "Replication to {Node} failed: {Error}. Will retry.",
                        node.Id, ex.Message);
                    
                    // Queue for retry
                    await _replicationQueue.EnqueueAsync(
                        new ReplicationTask { Node = node, Cart = cart });
                }
            }
        });
        
        // Return immediately—don't wait for replication
    }
    
    public async Task<ShoppingCart> GetCartAsync(string userId)
    {
        // Read from local node for speed
        var localCart = await _localNode.GetAsync<ShoppingCart>(userId);
        
        // If we detect conflicts (concurrent updates from different partitions),
        // resolve them
        if (localCart.HasConflicts)
        {
            var resolvedCart = await _conflictResolver.ResolveAsync(localCart);
            await _localNode.SaveAsync(resolvedCart);
            return resolvedCart;
        }
        
        return localCart;
    }
}

// Conflict resolution for AP systems
public class LastWriteWinsConflictResolver : IConflictResolver
{
    public async Task<ShoppingCart> ResolveAsync(ShoppingCart conflictedCart)
    {
        // Get all conflicting versions
        var versions = conflictedCart.ConflictingVersions;
        
        // Simple strategy: last write wins
        var winner = versions
            .OrderByDescending(v => v.LastModified)
            .First();
        
        _logger.LogInformation(
            "Resolved cart conflict using LWW. " +
            "Chosen version from {Timestamp}",
            winner.LastModified);
        
        return winner;
    }
}

// Advanced: Merge conflicting shopping carts
public class MergeConflictResolver : IConflictResolver
{
    public async Task<ShoppingCart> ResolveAsync(ShoppingCart conflictedCart)
    {
        var versions = conflictedCart.ConflictingVersions;
        
        // Merge strategy: union of items from all versions
        var mergedCart = new ShoppingCart
        {
            UserId = conflictedCart.UserId,
            Items = new List<CartItem>()
        };
        
        foreach (var version in versions)
        {
            foreach (var item in version.Items)
            {
                // Add if not already present, or take higher quantity
                var existing = mergedCart.Items
                    .FirstOrDefault(i => i.ProductId == item.ProductId);
                
                if (existing == null)
                {
                    mergedCart.Items.Add(item);
                }
                else if (item.Quantity > existing.Quantity)
                {
                    existing.Quantity = item.Quantity;
                }
            }
        }
        
        mergedCart.LastModified = DateTime.UtcNow;
        
        _logger.LogInformation(
            "Merged {Count} conflicting cart versions into single cart",
            versions.Count);
        
        return mergedCart;
    }
}
```

// Cassandra with eventual consistency (AP)
public class CassandraAPExample

- ✅ High throughput
- ✅ Scales well geographically

- ❌ Conflict resolution needed
- ❌ More complex application logic

## Beyond CAP: PACELC

CAP theorem is often oversimplified. Daniel Abadi proposed **PACELC** to provide a more nuanced view that better describes real-world trade-offs:

- **PAC**: If there's a **P**artition, choose between **A**vailability and **C**onsistency
- **ELC**: **E**lse (no partition), choose between **L**atency and **C**onsistency

This better describes real-world trade-offs where you make decisions even when the system is healthy.

### The Latency-Consistency Trade-off

Even without partitions, you face trade-offs:
- Strong consistency requires coordination → higher latency
- Weak consistency allows local reads → lower latency

**Examples of PACELC Classifications:**

| System | P+A or P+C | E+L or E+C | Description |
|--------|-----------|-----------|-------------|
| DynamoDB | PA | EL | Partition → Available; Else → Low Latency |
| MongoDB | PC | EC | Partition → Consistent; Else → Consistent |
| Cassandra | PA | EL | Partition → Available; Else → Low Latency |
| Cosmos DB (tunable) | Configurable | Configurable | Supports all combinations |
| VoltDB | PC | EC | Always prioritizes consistency |

```csharp
// PACELC in practice: Azure Cosmos DB with tunable consistency
public class CosmosDbPACELCExample
{
    private readonly Container _container;
    
    // Strong consistency: PC/EC (both consistency always)
    public async Task<Document> ReadStrongAsync(string id)
    {
        var response = await _container.ReadItemAsync<Document>(
            id,
            new PartitionKey(id),
            new ItemRequestOptions
            {
                ConsistencyLevel = ConsistencyLevel.Strong // E+C: prioritize consistency
            });
        
        // Higher latency, but guaranteed latest data
        return response.Resource;
    }
    
    // Eventual consistency: PA/EL (availability + latency always)
    public async Task<Document> ReadEventualAsync(string id)
    {
        var response = await _container.ReadItemAsync<Document>(
            id,
            new PartitionKey(id),
            new ItemRequestOptions
            {
                ConsistencyLevel = ConsistencyLevel.Eventual // E+L: prioritize latency
            });
        
        // Lower latency, but might be slightly stale
        return response.Resource;
    }
    
    // Session consistency: Balanced approach
    public async Task<Document> ReadSessionAsync(string id, string sessionToken)
    {
        var response = await _container.ReadItemAsync<Document>(
            id,
            new PartitionKey(id),
            new ItemRequestOptions
            {
                ConsistencyLevel = ConsistencyLevel.Session, // Your own writes are consistent
                SessionToken = sessionToken
            });
        
        // Reads your own writes consistently, others eventual
        return response.Resource;
    }
}
```

### Making the Right PACELC Choice

**When to Choose P+A / E+L (Availability + Low Latency):**
- Social media applications
- Content delivery networks
- Shopping carts
- Product catalogs
- Analytics dashboards
- Read-heavy workloads

**When to Choose P+C / E+C (Consistency Always):**
- Financial transactions
- Inventory management
- Booking systems
- User authentication
- Configuration management
- Write-heavy critical systems

**When to Choose P+A / E+C (Available during partition, consistent otherwise):**
- Rare; usually you're consistent or you're not
- Some systems use this for non-critical vs critical operations

**When to Choose P+C / E+L (Consistent during partition, low latency otherwise):**
- Also rare; usually consistency requirements don't change

## Consistency Models Spectrum

CAP's "consistency" is actually "linearizability" (strongest form). In practice, systems offer various consistency levels—a spectrum rather than binary choice:

### 1. Strong/Linearizable Consistency (Strongest)

**Definition:** Operations appear to execute atomically at a single point in time between invocation and response.

**Guarantee:** If write W completes before read R starts, R sees W's effect.

**Use Case:** Banking, inventory, locks

```csharp
public class LinearizableStore
{
    private readonly object _lock = new object();
    private Dictionary<string, (string Value, long Version)> _data = new();
    
    public (string Value, long Version) Read(string key)
    {
        lock (_lock) // Serializes all operations
        {
            return _data.TryGetValue(key, out var value) 
                ? value 
                : (null, 0);
        }
    }
    
    public void Write(string key, string value)
    {
        lock (_lock)
        {
            var (_, version) = _data.TryGetValue(key, out var existing) 
                ? existing 
                : (null, 0L);
            
            _data[key] = (value, version + 1);
        }
    }
}
```

---

### 2. Sequential Consistency

**Definition:** All nodes see operations in the same total order, but not necessarily real-time order.

**Guarantee:** Operations appear to execute in some sequential order, and operations of each process appear in order.

**Difference from Linearizability:** Doesn't preserve real-time ordering between processes.

```csharp
// Sequential consistency allows reordering as long as order is consistent
// Process A: Write X=1, Write Y=2
// Process B: Read Y=2, Read X=?
// 
// Linearizable: Must read X=1 (real-time ordering)
// Sequential: Could read X=0 or X=1 (any consistent order)
```

---

### 3. Causal Consistency

**Definition:** Causally related operations are seen in the same order by all nodes. Concurrent operations may be seen in different orders.

**Guarantee:** If operation A causally precedes operation B, all nodes see A before B.

**Use Case:** Social media (reply after post), collaborative editing

```csharp
public class CausallyConsistentStore
{
    private readonly VectorClock _clock;
    
    public async Task WriteAsync(string key, string value, VectorClock causedBy)
    {
        // This write causally depends on previous operation
        _clock.Merge(causedBy);
        _clock.Increment();
        
        await _store.WriteAsync(new Write
        {
            Key = key,
            Value = value,
            VectorClock = _clock.Clone()
        });
    }
    
    // Example: Post and reply
    // Post A: timestamp [1, 0, 0]
    // Reply B to A: timestamp [1, 1, 0] (causally after A)
    // All nodes must see Post A before Reply B
}
```

### 4. Eventual Consistency

**Definition:** If no new updates are made, all replicas will eventually converge to the same value.

**Guarantee:** Eventually consistent—no guarantee when.

**Use Case:** DNS, cache invalidation, analytics

```csharp
public class EventuallyConsistentCache
{
    private readonly ICache _localCache;
    private readonly IMessageBus _bus;
    
    public async Task UpdateAsync(string key, string value)
    {
        // Update local cache immediately
        _localCache.Set(key, value);
        
        // Propagate to other nodes asynchronously
        await _bus.PublishAsync(new CacheInvalidation
        {
            Key = key,
            Value = value,
            Timestamp = DateTime.UtcNow
        });
        
        // Other caches will update "eventually"
    }
    
    public string Get(string key)
    {
        // Might return stale value
        return _localCache.Get(key);
    }
}
```

### 5. Read-Your-Writes Consistency (Session Consistency)

**Definition:** A client always reads its own writes, but might not see other clients' recent writes.

**Guarantee:** Your session is consistent, others are eventual.

**Use Case:** User profiles, settings, personalization

```csharp
public class SessionConsistentStore
{
    private readonly ICache _cache;
    private readonly IDatabase _database;
    
    public async Task<User> GetUserAsync(string userId, string sessionToken)
    {
        // Check if this session recently wrote this user
        var cacheKey = $"{userId}:{sessionToken}";
        var cachedUser = _cache.Get<User>(cacheKey);
        
        if (cachedUser != null)
        {
            // Return what this session wrote (read-your-writes)
            return cachedUser;
        }
        
        // Otherwise read from database (might be stale from other sessions)
        return await _database.GetUserAsync(userId);
    }
    
    public async Task UpdateUserAsync(User user, string sessionToken)
    {
        await _database.UpdateUserAsync(user);
        
        // Cache for this session (read-your-writes guarantee)
        var cacheKey = $"{user.Id}:{sessionToken}";
        _cache.Set(cacheKey, user, TimeSpan.FromMinutes(5));
    }
}
```

### Consistency Level Comparison Table

| Consistency Model | Guarantees | Use Cases | Performance |
|-------------------|------------|-----------|-------------|
| **Linearizability** | Strongest: real-time order | Finance, inventory | Slowest |
| **Sequential** | Total order (not real-time) | Rare | Slow |
| **Causal** | Causally related ordered | Social apps | Medium |
| **Eventual** | Eventually converges | Caches, analytics | Fast |
| **Session** | Read your own writes | User preferences | Fast |

## Making the Right Choice

### Decision Framework

Ask these questions when choosing consistency model:

**1. What happens if users see stale data?**
- Critical failure (banking) → Strong consistency (CP)
- Minor annoyance (social media) → Eventual consistency (AP)

**2. What's your read/write ratio?**
- Read-heavy → AP with caching
- Write-heavy → CP might be necessary

**3. What's your geographic distribution?**
- Single region → Strong consistency feasible
- Multi-region → Strong consistency = high latency

**4. What's your availability requirement?**
- 99.99% SLA → Probably need AP
- Can tolerate downtime → CP acceptable

### Feature-Level CAP Choices

Different features in the same system can make different CAP trade-offs:

| Feature | Choice | Reason |
|---------|--------|--------|
| User authentication | CP | Security critical |
| Shopping cart | Session | Read-your-writes |
| Product catalog | AP | Staleness tolerable |
| Inventory | CP | Can't oversell |
| Reviews | AP | Delayed visibility OK |

## Key Takeaways

- CAP theorem states you can only guarantee 2 of 3: Consistency, Availability, Partition tolerance
- In distributed systems, partitions are inevitable, so you choose between C and A
- CP systems sacrifice availability to maintain consistency during partitions
- AP systems sacrifice consistency to maintain availability, relying on eventual consistency
- Different features in the same system can make different CAP trade-offs
- PACELC extends CAP to cover trade-offs even when there are no partitions
