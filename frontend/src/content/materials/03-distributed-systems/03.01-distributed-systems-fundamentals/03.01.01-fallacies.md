By the end of this lesson, you will be able to:

## Introduction

In 1994, L. Peter Deutsch and colleagues at Sun Microsystems identified assumptions that programmers new to distributed computing commonly make—assumptions that prove false in practice. These became known as the "Fallacies of Distributed Computing." Understanding these fallacies is the first step in building robust distributed systems.

## The 8 Fallacies Explained

### Fallacy 1: The Network is Reliable

**The Assumption:** "The network will always deliver my messages successfully."

**The Reality:** Networks fail constantly. Packets get dropped, connections timeout, switches crash, cables get unplugged, routers get misconfigured, and data centers lose connectivity.

**Real-World Manifestations:**
- Transient network blips causing packet loss
- Router failures creating temporary outages
- DNS resolution failures
- Firewall rules blocking traffic unexpectedly
- Network interface card (NIC) failures

**Impact on Your System:**

Systems must handle transient failures, implement retries with exponential backoff, and design for eventual consistency. Assume every network call can fail and design accordingly.

**Code Examples:**

```csharp
// ❌ Bad: Assumes network reliability
public async Task<UserProfile> GetUserProfileAsync(string userId)
{
    var result = await httpClient.GetAsync($"/api/users/{userId}");
    var data = await result.Content.ReadAsStringAsync();
    return JsonSerializer.Deserialize<UserProfile>(data);
    // What happens if the network fails? Exception crashes the app
}

// ✅ Good: Handles network failures with retries
public async Task<UserProfile> GetUserProfileAsync(string userId)
{
    var policy = Policy
        .Handle<HttpRequestException>()
        .Or<TaskCanceledException>()
        .WaitAndRetryAsync(
            retryCount: 3,
            sleepDurationProvider: retryAttempt => 
                TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)),
            onRetry: (exception, timespan, retryCount, context) =>
            {
                _logger.LogWarning(
                    "Retry {RetryCount} after {Delay}s due to {Exception}",
                    retryCount, timespan.TotalSeconds, exception.Message);
            });

    var result = await policy.ExecuteAsync(async () =>
    {
        using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(10));
        return await httpClient.GetAsync($"/api/users/{userId}", cts.Token);
    });

    result.EnsureSuccessStatusCode();
    return await result.Content.ReadFromJsonAsync<UserProfile>();
}
```

**Mitigation Strategies:**
- Implement retry logic with exponential backoff and jitter
- Use circuit breakers to fail fast when services are down
- Design idempotent operations so retries are safe
- Add timeouts to prevent hanging indefinitely
- Log network failures for observability

### Fallacy 2: Latency is Zero

**The Assumption:** "Network calls are instantaneous, like in-memory function calls."

**The Reality:** Network calls take time—anywhere from single-digit milliseconds to several seconds, and the duration is unpredictable. Even within the same data center, latency exists. Across regions or continents, latency can be hundreds of milliseconds.

**Real-World Manifestations:**
- Local network: 1-10ms
- Same region (cloud): 5-50ms
- Cross-region: 50-300ms
- Intercontinental: 100-500ms+
- Mobile networks: 50-1000ms+

**Impact on Your System:**

Never make synchronous remote calls on critical paths. Use async patterns, implement caching strategies, add timeouts, and design APIs to minimize round trips.

**Code Examples:**

```csharp
// ❌ Bad: Chatty interface causing latency amplification
public async Task<OrderSummary> GetOrderSummaryAsync(string orderId)
{
    var order = await orderClient.GetOrderAsync(orderId);
    var customer = await customerClient.GetCustomerAsync(order.CustomerId);
    var items = new List<Product>();
    
    foreach (var lineItem in order.LineItems)
    {
        var product = await productClient.GetProductAsync(lineItem.ProductId);
        items.Add(product);
    }
    // If order has 10 items, that's 12+ network calls!
    // At 50ms each = 600ms minimum latency
    
    return new OrderSummary(order, customer, items);
}

// ✅ Good: Batched requests and caching
public async Task<OrderSummary> GetOrderSummaryAsync(string orderId)
{
    // Fetch order and customer in parallel
    var orderTask = orderClient.GetOrderAsync(orderId);
    var customerTask = customerClient.GetCustomerAsync(order.CustomerId);
    
    await Task.WhenAll(orderTask, customerTask);
    
    var order = orderTask.Result;
    var customer = customerTask.Result;
    
    // Batch fetch all products in a single call
    var productIds = order.LineItems.Select(li => li.ProductId).ToList();
    var products = await productClient.GetProductsBatchAsync(productIds);
    
    // Total: 3 network calls instead of 12+
    return new OrderSummary(order, customer, products);
}
```

**Mitigation Strategies:**
- Use async/await everywhere to avoid blocking threads
- Implement aggressive caching with appropriate TTLs
- Design coarse-grained APIs that return all needed data in one call
- Use batching APIs to fetch multiple entities at once
- Consider data denormalization to reduce cross-service calls
- Add request/response compression

### Fallacy 3: Bandwidth is Infinite

**The Assumption:** "I can send as much data as I want over the network."

**The Reality:** Network bandwidth is limited and shared among many services and users. Even modern networks have constraints, and bandwidth contention causes degradation.

**Real-World Manifestations:**
- Bandwidth limits: 1Gbps, 10Gbps, 100Gbps network cards
- Shared bandwidth among multiple services
- Cloud provider bandwidth throttling
- Network congestion during peak times
- Last-mile bandwidth constraints (user connections)

**Impact on Your System:**

Minimize data transfer, use compression, implement pagination, avoid chatty interfaces, and design efficient wire formats.

**Code Examples:**

```csharp
// ❌ Bad: Returns entire dataset without pagination
[HttpGet("users")]
public async Task<ActionResult<List<User>>> GetAllUsers()
{
    var users = await _dbContext.Users
        .Include(u => u.Profile)
        .Include(u => u.Orders)
        .Include(u => u.Addresses)
        .ToListAsync();
    
    // Could return 10,000+ users with all relationships
    // Payload: 50MB+
    return Ok(users);
}

// ✅ Good: Pagination and selective field projection
[HttpGet("users")]
public async Task<ActionResult<PagedResult<UserSummary>>> GetUsers(
    [FromQuery] int page = 1,
    [FromQuery] int pageSize = 20)
{
    pageSize = Math.Min(pageSize, 100); // Cap page size
    
    var query = _dbContext.Users
        .Select(u => new UserSummary
        {
            Id = u.Id,
            Name = u.Name,
            Email = u.Email
            // Only essential fields, not full object graph
        });
    
    var totalCount = await query.CountAsync();
    var users = await query
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .ToListAsync();
    
    return Ok(new PagedResult<UserSummary>
    {
        Items = users,
        Page = page,
        PageSize = pageSize,
        TotalCount = totalCount
    });
}
```

**Mitigation Strategies:**
- Implement pagination on all collection endpoints
- Use field selection/projection (GraphQL-style)
- Enable gzip/brotli compression on HTTP responses
- Use binary protocols (gRPC, MessagePack) instead of JSON where appropriate
- Implement efficient serialization formats
- Monitor network bandwidth usage

### Fallacy 4: The Network is Secure

**The Assumption:** "My network is a safe, trusted environment."

**The Reality:** Networks are hostile environments. Data can be intercepted, modified, replayed, or spoofed. Attackers exist both outside and inside your network perimeter.

**Real-World Manifestations:**
- Man-in-the-middle (MITM) attacks
- Packet sniffing on shared networks
- DNS spoofing
- ARP poisoning
- Insider threats
- Compromised certificates

**Impact on Your System:**

Always use encryption (TLS), authenticate all services, validate all inputs, implement defense in depth, and never trust the network layer.

**Code Examples:**

```csharp
// ❌ Bad: Unencrypted internal communication
public class InsecureHttpClient
{
    private readonly HttpClient _client;
    
    public InsecureHttpClient()
    {
        _client = new HttpClient
        {
            BaseAddress = new Uri("http://internal-service") // HTTP, not HTTPS!
        };
    }
}

// ✅ Good: Mutual TLS and certificate validation
public class SecureServiceClient
{
    private readonly HttpClient _client;
    
    public SecureServiceClient()
    {
        var handler = new HttpClientHandler
        {
            ClientCertificateOptions = ClientCertificateOption.Manual,
            SslProtocols = SslProtocols.Tls13 | SslProtocols.Tls12,
            ServerCertificateCustomValidationCallback = ValidateServerCertificate
        };
        
        // Add client certificate for mutual TLS
        var clientCert = LoadClientCertificate();
        handler.ClientCertificates.Add(clientCert);
        
        _client = new HttpClient(handler)
        {
            BaseAddress = new Uri("https://internal-service") // HTTPS
        };
    }
    
    private bool ValidateServerCertificate(
        HttpRequestMessage request,
        X509Certificate2 cert,
        X509Chain chain,
        SslPolicyErrors errors)
    {
        // Implement certificate pinning or custom validation
        return errors == SslPolicyErrors.None;
    }
}
```

**Mitigation Strategies:**
- Use TLS 1.2+ for all communication, even internal
- Implement mutual TLS (mTLS) for service-to-service communication
- Use API keys, OAuth tokens, or JWTs for authentication
- Validate and sanitize all inputs
- Implement rate limiting and DDoS protection
- Use a service mesh for automatic security policies

### Fallacy 5: Topology Doesn't Change

**The Assumption:** "The network structure and service locations remain constant."

**The Reality:** Services move, scale up and down, fail and get replaced, migrate to different hosts, and change IP addresses constantly—especially in cloud and containerized environments.

**Real-World Manifestations:**
- Auto-scaling adding/removing instances
- Rolling deployments replacing nodes
- Container orchestration moving workloads
- Data center failures triggering failovers
- Load balancer changes
- DNS updates

**Impact on Your System:**

Use service discovery mechanisms, avoid hardcoded endpoints, design for dynamic topology, and implement health checks.

**Code Examples:**

```csharp
// ❌ Bad: Hardcoded service endpoints
public class ServiceClient
{
    private readonly HttpClient _client = new HttpClient
    {
        BaseAddress = new Uri("http://192.168.1.50:8080")
        // What happens when this IP changes?
    };
}

// ✅ Good: Service discovery with Consul
public class DynamicServiceClient
{
    private readonly IConsulClient _consul;
    private readonly HttpClient _client;
    private string _currentServiceAddress;
    
    public DynamicServiceClient(IConsulClient consul, HttpClient client)
    {
        _consul = consul;
        _client = client;
    }
    
    private async Task<string> DiscoverServiceAddressAsync()
    {
        var services = await _consul.Health.Service("order-service", tag: null, passingOnly: true);
        
        if (!services.Response.Any())
        {
            throw new ServiceUnavailableException("No healthy instances of order-service found");
        }
        
        // Pick a random healthy instance
        var service = services.Response[Random.Shared.Next(services.Response.Length)];
        return $"http://{service.Service.Address}:{service.Service.Port}";
    }
    
    public async Task<Order> GetOrderAsync(string orderId)
    {
        var serviceAddress = await DiscoverServiceAddressAsync();
        var response = await _client.GetAsync($"{serviceAddress}/api/orders/{orderId}");
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<Order>();
    }
}
```

**Mitigation Strategies:**
- Use DNS-based service discovery
- Implement client-side load balancing with health checks
- Use service registries (Consul, Eureka, Kubernetes Services)
- Design stateless services that can be easily moved
- Implement graceful shutdown and startup procedures

### Fallacy 6: There is One Administrator

**The Assumption:** "One team or person controls the entire system."

**The Reality:** In distributed systems, multiple teams manage different components, each with different priorities, schedules, and operational practices.

**Real-World Manifestations:**
- Different teams owning different microservices
- Third-party managed services (databases, queues)
- Multi-vendor environments
- Different deployment schedules
- Inconsistent monitoring and logging practices
- Varied change management processes

**Impact on Your System:**

Design for operational independence, establish clear ownership boundaries, implement comprehensive monitoring and logging, and use standardized contracts between services.

**Mitigation Strategies:**
- Define clear service ownership and SLAs
- Implement distributed tracing (OpenTelemetry)
- Use centralized logging and monitoring
- Document APIs and maintain backwards compatibility
- Establish incident response procedures
- Implement chaos engineering to test failure scenarios

### Fallacy 7: Transport Cost is Zero

**The Assumption:** "Network operations are free in terms of time, money, and resources."

**The Reality:** Every network call has costs: serialization overhead, network transit time, deserialization, cloud egress fees, and compute resources.

**Real-World Manifestations:**
- Cloud provider data egress charges
- Serialization/deserialization CPU overhead
- Memory allocation for buffers
- Network card and router processing
- Cross-region data transfer costs

**Impact on Your System:**

Design efficient APIs, batch operations where possible, consider data locality, minimize cross-region calls, and be aware of cloud cost implications.

**Code Examples:**

```csharp
// ❌ Bad: Making individual calls in a loop
public async Task NotifyUsersAsync(List<string> userIds, string message)
{
    foreach (var userId in userIds)
    {
        // Each call costs: serialization + network + deserialization
        await notificationClient.SendAsync(userId, message);
    }
    // For 1,000 users: 1,000 network calls!
}

// ✅ Good: Batching to reduce transport costs
public async Task NotifyUsersAsync(List<string> userIds, string message)
{
    // Batch into groups of 100
    var batches = userIds.Chunk(100);
    
    foreach (var batch in batches)
    {
        // Single call for 100 users
        await notificationClient.SendBatchAsync(batch.ToList(), message);
    }
    // For 1,000 users: 10 network calls
}
```

**Mitigation Strategies:**
- Implement batch APIs for bulk operations
- Use data locality: process data close to where it lives
- Cache frequently accessed data
- Consider data transfer costs in architectural decisions
- Use efficient serialization formats (Protocol Buffers, MessagePack)
- Monitor cloud egress costs

### Fallacy 8: The Network is Homogeneous

**The Assumption:** "All parts of the network use the same protocols, have the same performance, and run compatible software."

**The Reality:** Distributed systems run on heterogeneous infrastructure: different operating systems, programming languages, framework versions, network equipment, and cloud providers.

**Real-World Manifestations:**
- Mixing Windows and Linux servers
- Different versions of the same service running simultaneously
- Various serialization formats (JSON, XML, Protocol Buffers)
- Different character encodings
- Clock skew between systems
- Mixed networking hardware (1Gbps and 10Gbps NICs)

**Impact on Your System:**

Use standard protocols, version your APIs explicitly, design for backward compatibility, handle different data formats gracefully, and test across heterogeneous environments.

**Code Examples:**

```csharp
// ❌ Bad: Assuming specific .NET version features
public record UserDto
{
    public required string Id { get; init; } // C# 11 feature
    public required string Email { get; init; }
}
// Fails if consuming service uses older C# version

// ✅ Good: Use standard, version-agnostic contracts
public class UserDto
{
    [JsonPropertyName("id")]
    [JsonRequired]
    public string Id { get; set; }
    
    [JsonPropertyName("email")]
    [JsonRequired]
    public string Email { get; set; }
    
    // Handles old and new clients gracefully
    [JsonPropertyName("phone")]
    public string Phone { get; set; } // Optional for backward compat
}

// API versioning
[ApiController]
[Route("api/v{version:apiVersion}/users")]
[ApiVersion("1.0")]
[ApiVersion("2.0")]
public class UsersController : ControllerBase
{
    [HttpGet("{id}")]
    [MapToApiVersion("1.0")]
    public async Task<ActionResult<UserDtoV1>> GetUserV1(string id)
    {
        // Version 1 implementation
    }
    
    [HttpGet("{id}")]
    [MapToApiVersion("2.0")]
    public async Task<ActionResult<UserDtoV2>> GetUserV2(string id)
    {
        // Version 2 with additional fields
    }
}
```

**Mitigation Strategies:**
- Use standard protocols (HTTP, gRPC, AMQP)
- Implement explicit API versioning
- Use content negotiation (Accept headers)
- Design for backward and forward compatibility
- Document API contracts with OpenAPI/Swagger
- Test with different client versions

## Real-World Case Studies

### Case Study 1: Amazon DynamoDB and the Network Reliability Fallacy

In 2015, Amazon DynamoDB experienced a major outage caused by metadata service failures. The service assumed network reliability when communicating between metadata servers. When network partitions occurred, the system couldn't handle the cascading failures, leading to hours of downtime.

**Lessons Learned:**
- Implement bulkhead patterns to isolate failures
- Design for graceful degradation
- Never assume internal networks are perfectly reliable

### Case Study 2: Latency at Scale - Google Search

Google discovered that even 100ms of additional latency caused a measurable drop in search queries. This led them to implement:
- Aggressive caching at multiple layers
- Speculative execution (running queries on multiple servers)
- Tail latency optimization techniques
- Geographic distribution of services

**Key Insight:** At scale, latency isn't just a performance issue—it's a business issue.

### Case Study 3: Security Breach via Internal Network

A major retailer suffered a data breach where attackers compromised a vendor's internal network access. They assumed internal networks were secure and used unencrypted communication.

**Lessons Learned:**
- Always use TLS, even for internal communication
- Implement zero-trust security models
- Authenticate and authorize every request

## Patterns for Addressing the Fallacies

### 1. Retry Pattern with Circuit Breaker

Addresses: Fallacy 1 (Network is Reliable), Fallacy 2 (Latency is Zero)

```csharp
public class ResilientServiceClient
{
    private readonly IAsyncPolicy<HttpResponseMessage> _policy;
    
    public ResilientServiceClient()
    {
        var retry = Policy
            .Handle<HttpRequestException>()
            .Or<TimeoutException>()
            .WaitAndRetryAsync(
                retryCount: 3,
                sleepDurationProvider: retryAttempt => 
                    TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)),
                onRetry: (exception, timespan, retryCount, context) =>
                {
                    Log.Warning($"Retry {retryCount} after {timespan.TotalSeconds}s");
                });
        
        var circuitBreaker = Policy
            .Handle<HttpRequestException>()
            .CircuitBreakerAsync(
                handledEventsAllowedBeforeBreaking: 5,
                durationOfBreak: TimeSpan.FromSeconds(30),
                onBreak: (exception, duration) =>
                {
                    Log.Error($"Circuit opened for {duration.TotalSeconds}s");
                },
                onReset: () => Log.Info("Circuit reset"));
        
        // Combine retry and circuit breaker
        _policy = Policy.WrapAsync(retry, circuitBreaker);
    }
    
    public async Task<T> ExecuteAsync<T>(Func<Task<HttpResponseMessage>> operation)
    {
        var response = await _policy.ExecuteAsync(operation);
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<T>();
    }
}
```

### 2. Service Discovery Pattern

Addresses: Fallacy 5 (Topology Doesn't Change)

```csharp
public interface IServiceRegistry
{
    Task<ServiceEndpoint> DiscoverAsync(string serviceName);
    Task RegisterAsync(ServiceEndpoint endpoint);
    Task DeregisterAsync(string serviceId);
}

public class ConsulServiceRegistry : IServiceRegistry
{
    private readonly IConsulClient _consul;
    private readonly IHealthChecker _healthChecker;
    
    public async Task<ServiceEndpoint> DiscoverAsync(string serviceName)
    {
        var services = await _consul.Health.Service(
            serviceName, 
            tag: null, 
            passingOnly: true);
        
        if (!services.Response.Any())
        {
            throw new ServiceNotFoundException(serviceName);
        }
        
        // Load balance: select random healthy instance
        var service = services.Response[Random.Shared.Next(services.Response.Length)];
        
        return new ServiceEndpoint
        {
            Address = service.Service.Address,
            Port = service.Service.Port,
            ServiceId = service.Service.ID
        };
    }
    
    public async Task RegisterAsync(ServiceEndpoint endpoint)
    {
        var registration = new AgentServiceRegistration
        {
            ID = endpoint.ServiceId,
            Name = endpoint.ServiceName,
            Address = endpoint.Address,
            Port = endpoint.Port,
            Check = new AgentServiceCheck
            {
                HTTP = $"http://{endpoint.Address}:{endpoint.Port}/health",
                Interval = TimeSpan.FromSeconds(10),
                Timeout = TimeSpan.FromSeconds(5)
            }
        };
        
        await _consul.Agent.ServiceRegister(registration);
    }
}
```

### 3. Compression and Efficient Serialization

Addresses: Fallacy 3 (Bandwidth is Infinite), Fallacy 7 (Transport Cost is Zero)

```csharp
public class EfficientApiClient
{
    private readonly HttpClient _client;
    
    public EfficientApiClient()
    {
        var handler = new HttpClientHandler
        {
            AutomaticDecompression = DecompressionMethods.GZip | DecompressionMethods.Brotli
        };
        
        _client = new HttpClient(handler);
    }
    
    public async Task<T> PostAsync<T>(string url, object data)
    {
        // Use MessagePack for efficient binary serialization
        var bytes = MessagePackSerializer.Serialize(data);
        
        using var content = new ByteArrayContent(bytes);
        content.Headers.ContentType = new MediaTypeHeaderValue("application/x-msgpack");
        content.Headers.ContentEncoding.Add("gzip");
        
        var response = await _client.PostAsync(url, content);
        response.EnsureSuccessStatusCode();
        
        var responseBytes = await response.Content.ReadAsByteArrayAsync();
        return MessagePackSerializer.Deserialize<T>(responseBytes);
    }
}
```

### 4. API Versioning Strategy

Addresses: Fallacy 8 (Network is Homogeneous)

```csharp
// URL versioning
[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    [MapToApiVersion("1.0")]
    public async Task<ActionResult<OrderV1>> GetV1(string id)
    {
        var order = await _orderService.GetAsync(id);
        return Ok(MapToV1(order));
    }
    
    [HttpGet("{id}")]
    [MapToApiVersion("2.0")]
    public async Task<ActionResult<OrderV2>> GetV2(string id)
    {
        var order = await _orderService.GetAsync(id);
        return Ok(MapToV2(order));
    }
}

// Content negotiation versioning
[HttpGet("{id}")]
public async Task<ActionResult<Order>> Get(
    string id,
    [FromHeader(Name = "Accept")] string acceptHeader)
{
    var order = await _orderService.GetAsync(id);
    
    return acceptHeader switch
    {
        "application/vnd.company.order.v1+json" => Ok(MapToV1(order)),
        "application/vnd.company.order.v2+json" => Ok(MapToV2(order)),
        _ => Ok(order) // Default to latest
    };
}
```

## Architectural Principles Derived from the Fallacies

### Design for Failure

Every component in a distributed system will eventually fail. Design systems that:
- Detect failures quickly
- Isolate failures to prevent cascading
- Recover automatically when possible
- Degrade gracefully when recovery isn't possible

### Embrace Asynchrony

Synchronous communication couples services tightly and amplifies latency. Use:
- Message queues for decoupling
- Event-driven architectures
- Async APIs with callbacks or webhooks
- Eventual consistency where appropriate

### Monitor Everything

In distributed systems, observability is critical:
- Distributed tracing (Jaeger, Zipkin)
- Centralized logging (ELK, Splunk)
- Metrics and dashboards (Prometheus, Grafana)
- Health checks and heartbeats
- Alerting on anomalies

### Security by Default

Never trust the network:
- Encrypt all communication (TLS 1.2+)
- Authenticate every request
- Authorize based on least privilege
- Validate and sanitize all inputs
- Implement rate limiting

## Self-Check Questions

1. **Why is it dangerous to assume "latency is zero" when designing microservices?**
   
   *Answer:* Latency accumulates across service calls. If a request calls 5 services synchronously, each with 50ms latency, the total latency is 250ms minimum. Ignoring latency leads to poor user experience, timeouts, and performance bottlenecks. Solutions include async communication, caching, and minimizing round trips.

2. **How does the fallacy "topology doesn't change" particularly apply to cloud-native applications?**
   
   *Answer:* Cloud environments constantly change: containers start and stop, auto-scaling adjusts instance counts, deployments replace nodes, and orchestrators move workloads. Hardcoded endpoints break immediately. Service discovery, DNS, and dynamic configuration are essential.

3. **What's the relationship between "bandwidth is infinite" and API design?**
   
   *Answer:* Limited bandwidth forces efficient API design: pagination to limit response sizes, field selection to return only needed data, compression to reduce payload size, and coarse-grained APIs to minimize request count. Ignoring bandwidth leads to slow responses and high cloud costs.

4. **How do the fallacies interact with each other? Give an example.**
   
   *Answer:* The fallacies often compound each other. Example: Network unreliability (Fallacy 1) + non-zero latency (Fallacy 2) + limited bandwidth (Fallacy 3) means a retry strategy must account for latency amplification and avoid overwhelming limited bandwidth with large retry payloads. A naive retry policy could make things worse by generating more traffic than the network can handle.

5. **Why must internal services use TLS even though they're "inside" the network?**
   
   *Answer:* Fallacy 4 teaches us networks are never truly secure. Internal networks can be compromised through: lateral movement after initial breach, malicious insiders, misconfigured switches exposing traffic, or compromised vendor access. Zero-trust security and TLS everywhere are essential.

6. **How does the "one administrator" fallacy affect incident response?**
   
   *Answer:* Different teams own different services, making coordination during incidents complex. Teams have different on-call schedules, monitoring tools, and response procedures. This requires: clear ownership (RACI), runbooks, shared incident communication channels, and post-incident reviews involving all affected teams.
