---

## Introduction

**Domain-Driven Design (DDD)** provides another powerful approach to decomposition: using **bounded contexts** as service boundaries. A bounded context is an explicit boundary within which a domain model is consistent and unified. The same term might mean different things in different contexts — and that's okay! Bounded contexts acknowledge this reality and use it to create clear boundaries.

While business capabilities answer "what does the business do?", bounded contexts answer "what are the boundaries of consistency in our domain model?"

## Key Concepts

### What is a Bounded Context?

A **bounded context** is:
> An explicit boundary within which a domain model exists and is valid. Outside this boundary, different models may apply.

**Example: "Customer" in different contexts**

```
Sales Context:
  Customer {
    customerId
    name
    salesHistory
    creditLimit
    accountManager
  }

Support Context:
  Customer {
    customerId
    name
    supportTickets
    serviceLevel (Bronze/Silver/Gold)
    lastContactDate
  }

Shipping Context:
  Customer {
    customerId
    name
    shippingAddresses
    deliveryPreferences
  }
```

Each context has its own "Customer" model optimized for its needs. They don't share a database or class hierarchy.

### Why Bounded Contexts Matter for Microservices

1. **Natural Boundaries**: Bounded contexts provide natural service boundaries
2. **Independence**: Each context can evolve its model independently
3. **Clear Ownership**: Teams can own entire contexts
4. **Reduced Coupling**: Contexts communicate through well-defined interfaces

### Identifying Bounded Contexts

#### Technique 1: Event Storming

**Event Storming** is a workshop technique to discover domain events and boundaries:

1. **Gather Domain Experts**: Include people who know the business
2. **Identify Domain Events**: Things that happen ("Order Placed", "Payment Processed")
3. **Discover Commands**: What triggers events ("Place Order", "Process Payment")
4. **Find Aggregates**: Entities that process commands and produce events
5. **Draw Boundaries**: Group related events, commands, and aggregates

```
Example: E-commerce Event Storming Results

┌─────────────────────────────────────┐
│   Order Management Context          │
│                                      │
│   Events: Order Placed,              │
│           Order Confirmed,           │
│           Order Cancelled            │
│                                      │
│   Aggregates: Order, OrderLine       │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│   Inventory Context                  │
│                                      │
│   Events: Item Reserved,             │
│           Stock Replenished,         │
│           Reservation Expired        │
│                                      │
│   Aggregates: InventoryItem,         │
│               Reservation            │
└─────────────────────────────────────┘
```

#### Technique 2: Language Analysis

Look for terms that mean different things in different parts of the system:

- In **Sales**: "Customer" = someone with a credit limit and payment history
- In **Marketing**: "Customer" = someone with preferences and campaign responses
- In **Logistics**: "Customer" = a delivery address and shipping preferences

These different meanings suggest different bounded contexts.

#### Technique 3: Change Patterns

Things that change together should stay together:

- If changing product pricing always requires changing product display, they might belong together
- If changing inventory rules never affects order processing, they should be separate

### Context Mapping Patterns

When bounded contexts need to interact, use these patterns:

#### 1. Customer-Supplier

```
┌─────────────────┐          ┌─────────────────┐
│   Order         │          │   Shipping      │
│   Management    │──────────▶   Context       │
│   (Upstream)    │ provides │   (Downstream)  │
└─────────────────┘          └─────────────────┘
```

The upstream context defines the API; downstream must adapt.

#### 2. Shared Kernel

```
┌─────────────────┐
│  Shared Models  │ ◀── Use sparingly!
│  (e.g., Money,  │     Creates coupling
│   Currency)     │
└─────────────────┘
       △    △
       │    │
   ┌───┘    └───┐
   │            │
Context A   Context B
```

Two contexts share a common subset of domain model. Changes require coordination.

#### 3. Anti-Corruption Layer (ACL)

```
┌─────────────────┐          ┌─────────────────┐
│   Your Context  │          │   Legacy        │
│                 │   ACL    │   System        │
│                 │◀────────▶│                 │
│   Clean Model   │          │   Messy Model   │
└─────────────────┘          └─────────────────┘
```

Isolate your context from external systems with a translation layer.

#### 4. Separate Ways

```
┌─────────────────┐          ┌─────────────────┐
│   Context A     │          │   Context B     │
│                 │    X     │                 │
│   No coupling   │          │   Independent   │
└─────────────────┘          └─────────────────┘
```

Contexts that don't need to communicate should remain completely independent.

## Bounded Contexts vs Business Capabilities

**When to use which?**

| Aspect | Business Capability | Bounded Context |
|--------|-------------------|-----------------|
| **Focus** | What the business does | Consistency of domain model |
| **Best for** | Organizational alignment | Domain complexity |
| **Granularity** | Usually coarser | Can be finer |
| **When to use** | Business-driven decomposition | Complex domains with rich models |

**Often, they align!** A business capability often corresponds to a bounded context.

Example:
- Business Capability: "Order Management"
- Bounded Context: "Order Context" (with Order aggregate, order events, order rules)

```csharp
public class EventStormingWorkshop

                "Payment",
                "Shipment",

        {

            public List<string> Commands { get; set; }
```

### Context Mapping in Detail

```csharp
// Detailed patterns for context relationships

public class ContextMappingPatterns
{
    // Pattern 1: Partnership (mutual dependence)
    public class Partnership
    {
        // Two contexts with shared success criteria
        // Teams collaborate closely
        
        // Example:
        public class OrderContext
        {
            // Must coordinate with Fulfillment
            // Shared success: Fast order delivery
        }
        
        public class FulfillmentContext
        {
            // Must coordinate with Order
            // Joint planning required
        }
        
        // When to use:
        // - High interdependence
        // - Both contexts evolve together
        // - Same release schedule acceptable
        
        // Risk: Can create coupling
    }
    
    // Pattern 2: Customer-Supplier (power dynamic)
    public class CustomerSupplier
    {
        // Upstream provides API
        // Downstream depends on it
        
        public class UpstreamContext
        {
            // Product Catalog (upstream)
            // Defines product API
            // Can change at own pace (carefully)
        }
        
        public class DownstreamContext
        {
            // Order Service (downstream)
            // Consumes product API
            // Must adapt to upstream changes
        }
        
        // Mitigation: 
        // - Upstream maintains backward compatibility
        // - Downstream uses ACL to protect itself
    }
    
    // Pattern 3: Conformist (follow the leader)
    public class Conformist
    {
        // Downstream conforms to upstream model
        // No negotiation, just adapt
        
        // When to use:
        // - External/legacy system (can't change)
        // - Low strategic value
        // - Simple integration acceptable
        
        public class ExternalPaymentGateway
        {
            // Stripe, PayPal - can't change their API
        }
        
        public class PaymentContext
        {
            // Conforms to external gateway
            // Maps to their model
        }
    }
    
    // Pattern 4: Anti-Corruption Layer (translation)
    public class AntiCorruptionLayerExample
    {
        // Protect your context from external complexity
        
        public interface ILegacySystemACL
        {
            // Clean interface
            Task<Customer> GetCustomerAsync(string id);
        }
        
        public class LegacySystemAdapter : ILegacySystemACL
        {
            private readonly LegacySystemClient _legacy;
            
            public async Task<Customer> GetCustomerAsync(string id)
            {
                // Call messy legacy API
                var legacyCustomer = await _legacy.GetCustomerByIdAsync(
                    int.Parse(id), includeHistory: true, format: "XML");
                
                // Translate to clean domain model
                return new Customer
                {
                    Id = legacyCustomer.CUST_ID.ToString(),
                    Name = $"{legacyCustomer.FNAME} {legacyCustomer.LNAME}",
                    Email = legacyCustomer.EMAIL_ADDR
                };
                // Shields domain from legacy mess
            }
        }
        
        // Benefits:
        // - Domain model stays clean
        // - Easy to replace legacy system later
        // - Testing easier (mock the ACL)
    }
    
    // Pattern 5: Open Host Service
    public class OpenHostService
    {
        // Well-defined API for many consumers
        
        [ApiController]
        [Route("api/products")]
        public class ProductAPI
        {
            // Public API designed for external consumption
            // - Versioned
            // - Well-documented
            // - Stable contracts
            // - Multiple consumers
            
            [HttpGet("{id}")]
            public async Task<ProductDto> GetProduct(string id)
            {
                // Designed for many consumers
                // Can't change lightly
                return await _service.GetProductAsync(id);
            }
        }
    }
    
    // Pattern 6: Published Language
    public class PublishedLanguage
    {
        // Shared format/protocol
        // Examples: JSON Schema, Protobuf, OpenAPI
        
        public class OrderEvent
        {
            // Published event schema
            // All services understand this format
            
            [JsonProperty("order_id")]
            public string OrderId { get; set; }
            
            [JsonProperty("customer_id")]
            public string CustomerId { get; set; }
            
            [JsonProperty("total_amount")]
            public decimal TotalAmount { get; set; }
            
            // Well-defined, versioned schema
            // Documented in schema registry
        }
    }
}
```

### Strategic Design Decisions

```csharp
// How to make strategic decisions about contexts

public class StrategicDesign
{
    // Core Domain: Your competitive advantage
    public class CoreDomain
    {
        // Example: Recommendation Engine for e-commerce
        // - Strategic differentiator
        // - Heavy investment
        // - Best developers
        // - Most attention
        
        // Characteristics:
        // ✓ Business competitive advantage
        // ✓ Complex domain logic
        // ✓ Rapidly evolving
        // ✓ High business value
    }
    
    // Supporting Subdomain: Necessary but not differentiating
    public class SupportingSubdomain
    {
        // Example: Inventory Management
        // - Necessary for business
        // - Not competitive advantage
        // - Standard implementation OK
        
        // Characteristics:
        // ✓ Needed for core domain
        // ✓ Not unique to business
        // ✓ Can use off-the-shelf solutions
    }
    
    // Generic Subdomain: Buy, don't build
    public class GenericSubdomain
    {
        // Example: Authentication, Email
        // - Common to all businesses
        // - Use third-party services
        // - Auth0, SendGrid, etc.
        
        // Characteristics:
        // ✓ Commodity functionality
        // ✓ No customization needed
        // ✓ Mature market solutions exist
    }
    
    // Resource allocation strategy
    public class ResourceAllocation
    {
        // Core Domain: 60% of resources
        // - Senior developers
        // - Most time
        // - Custom implementation
        
        // Supporting: 30% of resources
        // - Mid-level developers
        // - Standard patterns
        // - Some customization
        
        // Generic: 10% of resources
        // - Integration work
        // - Buy or use OSS
        // - Minimal customization
    }
}
```

## Advanced Context Patterns

### Context Integration Strategies

```csharp
// How contexts communicate

public class ContextIntegrationStrategies
{
    // Strategy 1: Shared Events
    public class EventDrivenIntegration
    {
        // Order Context publishes events
        public async Task PublishOrderPlaced(Order order)
        {
            await _eventBus.PublishAsync(new OrderPlacedEvent
            {
                OrderId = order.Id,
                CustomerId = order.CustomerId,
                Items = order.Items,
                TotalAmount = order.Total
            });
        }
        
        // Multiple contexts subscribe
        // - Inventory: Reserve stock
        // - Billing: Create invoice
        // - Shipping: Prepare shipment
        
        // Benefits:
        // ✓ Loose coupling
        // ✓ Temporal decoupling
        // ✓ Easy to add new consumers
    }
    
    // Strategy 2: API Calls (for queries)
    public class APIDrivenIntegration
    {
        // Order Context needs product info
        public async Task<Order> CreateOrderAsync(CreateOrderCommand cmd)
        {
            // Query Product Context
            var product = await _productClient.GetProductAsync(cmd.ProductId);
            
            // Use info in order creation
            var order = new Order
            {
                ProductId = cmd.ProductId,
                ProductName = product.Name,  // Snapshot
                ProductPrice = product.Price // Snapshot at order time
            };
            
            return order;
        }
    }
    
    // Strategy 3: Data Replication
    public class DataReplication
    {
        // Order Context maintains its own product cache
        // Updated via events from Product Context
        
        public class OrderContext
        {
            // Local read model of products
            private readonly IProductReadModel _products;
            
            public async Task HandleProductUpdatedAsync(ProductUpdatedEvent evt)
            {
                // Update local copy
                await _products.UpdateAsync(new ProductSnapshot
                {
                    ProductId = evt.ProductId,
                    Name = evt.Name,
                    Price = evt.Price
                });
            }
            
            public async Task CreateOrderAsync(CreateOrderCommand cmd)
            {
                // Read from local cache - fast!
                var product = await _products.GetAsync(cmd.ProductId);
                
                // No external call needed
            }
        }
    }
}
```

## Practice Exercise

**Scenario**: You're designing a **hospital management system**.

Current features include:
- Patient registration and medical records
- Doctor schedules and appointments
- Lab test orders and results
- Billing and insurance claims
- Pharmacy prescription fulfillment
- Operating room scheduling

**Tasks** (35 minutes):

2. For each context:
   - Name it

### Part 3: Context Mapping (10 min)
1. Draw a context map showing relationships
2. For each relationship, specify the pattern:
   - Partnership / Customer-Supplier / Conformist / ACL / etc.
3. Identify which contexts need Anti-Corruption Layers
4. Mark which are Core / Supporting / Generic domains

**Consider**:
- What terms mean different things in different areas?
- Where do different departments have different concerns?
- What are the transaction boundaries?
- Which contexts could evolve independently?

## Self-Check Questions

1. **What's the difference between a bounded context and a microservice?**
   - A bounded context is a logical boundary in the domain model
   - A microservice is a physical deployment unit
   - Often, one bounded context = one microservice, but not always

2. **When should contexts share a model (Shared Kernel)?**
   - Rarely! Only for truly fundamental, stable concepts
   - When the cost of duplication is higher than the cost of coordination
   - When two teams are willing to coordinate changes

3. **What is an Anti-Corruption Layer and why is it important?**
   - A translation layer that prevents external models from "polluting" your context
   - Protects your domain model from legacy systems or external APIs
   - Allows your model to evolve independently

4. **Can a bounded context span multiple services?**
   - Yes, for very large contexts
   - But generally, start with 1 context = 1 service
   - Only split if truly necessary for scaling or team autonomy

## Key Takeaways

✅ **Bounded contexts** define boundaries of consistency in domain models

✅ Use **event storming** and language analysis to discover contexts

✅ **Context mapping** patterns help manage relationships between contexts

✅ **Anti-corruption layers** protect your model from external systems

✅ Bounded contexts often align with business capabilities

✅ Start with **larger contexts**; you can split them later if needed
