# Lesson 5: Avoiding Distributed Monoliths and Shared Libraries

## Learning Objectives

By the end of this lesson, you will be able to:
- Recognize the symptoms of a distributed monolith
- Identify and avoid common coupling pitfalls in microservices
- Understand the risks of shared libraries with business logic
- Design services for true independence and autonomy

---

## Introduction

A **distributed monolith** is the worst of both worlds: you have all the complexity of microservices (network calls, distributed failures, deployment coordination) but none of the benefits (independent deployment, scaling, team autonomy). This happens when services are tightly coupled despite being physically separated.

This lesson explores how to recognize and avoid creating distributed monoliths.

## Key Concepts

### What is a Distributed Monolith?

A distributed monolith has these characteristics:

```
❌ Can't deploy services independently
❌ Services must be deployed in lock-step
❌ Shared database across multiple services
❌ Synchronous coupling: Service A can't work without Service B
❌ Shared libraries with business logic
❌ Changes ripple across multiple services
❌ Testing requires spinning up many services
```

**Example of a Distributed Monolith:**

```
┌──────────────┐
│  UI Service  │
└──────┬───────┘
       │ (must call in sequence)
       ▼
┌──────────────┐
│Order Service │────────┐
└──────┬───────┘        │
       │                │
       ▼                │
┌──────────────┐        │    ┌──────────────┐
│Inventory Svc │        └───▶│Shared Library│◀────┐
└──────┬───────┘             │(Business     │     │
       │                     │ Logic)       │     │
       ▼                     └──────────────┘     │
┌──────────────┐                  │               │
│Payment Svc   │──────────────────┘               │
└──────┬───────┘                                  │
       │                                          │
       ▼                                          │
┌──────────────┐                                  │
│Shipping Svc  │──────────────────────────────────┘
└──────────────┘

Problems:
- Services call each other synchronously in a chain
- All share the same business logic library
- Deploying one service may break others
- Can't test services in isolation
```

## Anti-Pattern 1: Shared Database

### The Problem

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Service A   │     │  Service B   │     │  Service C   │
│              │     │              │     │              │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │                    │                    │
       └────────────────────┼────────────────────┘
                            │
                     ┌──────▼──────┐
                     │   Shared    │
                     │   Database  │
                     └─────────────┘

Symptoms:
❌ Schema changes affect multiple services
❌ Can't deploy services independently
❌ Database becomes a bottleneck
❌ Unclear data ownership
```

### The Solution

**Database per Service pattern** (covered in Lesson 4):

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Service A   │     │  Service B   │     │  Service C   │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │                    │                    │
   ┌───▼───┐            ┌───▼───┐            ┌───▼───┐
   │ DB A  │            │ DB B  │            │ DB C  │
   └───────┘            └───────┘            └───────┘

Benefits:
✅ Clear data ownership
✅ Independent schema evolution
✅ Independent scaling
✅ Can choose different database technologies
```

## Anti-Pattern 2: Shared Libraries with Business Logic

### The Problem

**Shared library containing business logic:**

```csharp
// SharedBusinessLogic.dll (used by all services)
public class OrderValidator
{
    public bool IsValid(Order order)
    {
        // Complex business rules
        return order.Total > 0 && 
               order.Items.Count > 0 &&
               order.CustomerId != null;
    }
}

public class PricingCalculator
{
    public decimal CalculateTotal(Order order)
    {
        // Pricing logic
        return order.Items.Sum(i => i.Price * i.Quantity);
    }
}
```

**Why this is a problem:**

```
┌────────────────┐         ┌────────────────┐
│ Order Service  │         │Shipping Service│
│ v1.2.0         │         │  v1.2.0        │
└───────┬────────┘         └───────┬────────┘
        │                          │
        └────────┐      ┌──────────┘
                 │      │
          ┌──────▼──────▼──────┐
          │ SharedBusinessLogic│
          │       v1.2.0       │
          └────────────────────┘

Updating SharedBusinessLogic to v1.3.0:
❌ Both services must be updated simultaneously
❌ Can't deploy Order Service independently
❌ Changes in one service's logic affect another
❌ Testing requires coordinating versions
```

### The Solution

**Option 1: Duplicate Business Logic**

```csharp
// In Order Service
public class OrderValidator
{
    public bool IsValid(Order order) { ... }
}

// In Shipping Service  
public class ShipmentValidator
{
    public bool IsValid(Shipment shipment) { ... }
}

Benefits:
✅ Services are independent
✅ Each can evolve at its own pace
✅ Context-specific implementations

Cost:
⚠️ Some code duplication (but that's okay!)
```

**Option 2: Extract to a Service**

If the logic is truly shared and complex:

```
┌────────────────┐         ┌────────────────┐
│ Order Service  │         │Shipping Service│
└───────┬────────┘         └───────┬────────┘
        │                          │
        │    ┌────────────────┐    │
        └───▶│Pricing Service │◀───┘
             │(via API/Events)│
             └────────────────┘

Benefits:
✅ Single source of truth
✅ Independent deployment
✅ Services communicate asynchronously

Cost:
⚠️ Network overhead
⚠️ Another service to manage
```

**What CAN be shared:**

```csharp
✅ Utility libraries (no business logic)
   - Logging
   - HTTP client wrappers
   - Configuration helpers
   - Data structures (DTOs)

✅ Contracts/Interfaces
   - API contracts
   - Event schemas
   - Message formats

❌ Business logic
❌ Domain models
❌ Validation rules
❌ Calculation logic
```

## Anti-Pattern 3: Chatty Service Communication

### The Problem

**Service A needs data from multiple services:**

```
Client Request
      │
      ▼
┌─────────────┐
│ Service A   │
└─────┬───────┘
      │
      ├──▶ Call Service B (wait)
      │         │
      │         ▼
      │    Get data, return
      │
      ├──▶ Call Service C (wait)
      │         │
      │         ▼
      │    Get data, return
      │
      ├──▶ Call Service D (wait)
      │         │
      │         ▼
      │    Get data, return
      │
      └──▶ Aggregate and return

Total latency: latency(B) + latency(C) + latency(D)

Problems:
❌ High latency
❌ Cascading failures
❌ Tight coupling
❌ Difficult to test
```

### The Solution

**Use asynchronous events and caching:**

```
Service A maintains a local cache of needed data:

┌─────────────────────────────┐
│      Service A               │
│                              │
│  ┌────────────────────────┐ │
│  │  Local Cache/Read Model│ │
│  │  - Product Info        │ │
│  │  - Customer Info       │ │
│  │  - Inventory Status    │ │
│  └────────────────────────┘ │
└──────────────┬──────────────┘
               │
               │ subscribes to events
               ▼
        ┌──────────────┐
        │  Event Bus   │
        └──┬─────┬─────┘
           │     │
    ┌──────┘     └──────┐
    │                   │
┌───▼────┐      ┌───────▼───┐
│Product │      │ Inventory │
│Service │      │  Service  │
└────────┘      └───────────┘

Benefits:
✅ Fast reads (from local cache)
✅ No synchronous dependencies
✅ Resilient to other service failures

Trade-off:
⚠️ Eventual consistency
```

## Anti-Pattern 4: Distributed Transactions

### The Problem

**Trying to maintain ACID across services:**

```csharp
// This doesn't work across services!
using (var transaction = new TransactionScope())
{
    orderService.CreateOrder(order);
    inventoryService.ReserveStock(order.Items);
    paymentService.ChargeCustomer(order.Total);
    
    transaction.Complete(); // Can't coordinate across services!
}
```

### The Solution

**Use Saga Pattern (covered in Lesson 4):**

```
Order Saga:
1. Create Order → Success
   ├─▶ Reserve Inventory → Success
   │   ├─▶ Process Payment → Success
   │   │   └─▶ Confirm Order → Success ✓
   │   │
   │   └─▶ Process Payment → Failure
   │       └─▶ Release Inventory (compensate)
   │           └─▶ Cancel Order (compensate)
   │
   └─▶ Reserve Inventory → Failure
       └─▶ Cancel Order (compensate)
```

## Anti-Pattern 5: Overly Fine-Grained Services

### The Problem

**Too many tiny services:**

```
❌ 50+ microservices for a medium-sized application
❌ Services with just one or two operations
❌ More services than developers
❌ Excessive network overhead
❌ Deployment complexity

Example: E-commerce with too many services
- UserRegistrationService
- UserLoginService
- UserProfileService
- UserPreferencesService
- UserAddressService
- UserPaymentMethodService
... (5 user services that should be 1)
```

### The Solution

**Start with larger services, split when needed:**

```
✅ Start with: UserManagementService
   - Registration
   - Login/Auth
   - Profile
   - Preferences
   - Addresses
   - Payment methods

Split only when:
- Service becomes too large (team can't manage it)
- Different scaling needs
- Different deployment cadences
- Clear bounded context emerges
```

**Rule of Thumb**: Prefer larger services initially. It's easier to split than to merge.

## Distributed Monolith Checklist

### Symptoms (Red Flags)

Ask yourself:

**Deployment:**
- □ Do services need to be deployed together?
- □ Does deploying one service break others?
- □ Do you coordinate deployment schedules?

**Development:**
- □ Do changes in one service require changes in others?
- □ Do services share business logic libraries?
- □ Is the shared library updated frequently?

**Runtime:**
- □ If one service is down, do others fail?
- □ Are services calling each other synchronously in chains?
- □ Can you test a service in isolation?

**Data:**
- □ Do multiple services access the same database?
- □ Are foreign keys enforced across service boundaries?
- □ Do services modify each other's data?

If you answered "yes" to many of these, you might have a distributed monolith!

## When Microservices Aren't the Answer

Sometimes a **modular monolith** is better:

```
Modular Monolith:
┌──────────────────────────────────┐
│         Single Application        │
│  ┌─────────┐  ┌─────────┐       │
│  │ Order   │  │ Product │        │
│  │ Module  │  │ Module  │        │
│  └────┬────┘  └────┬────┘        │
│       │            │             │
│       └────────┬───┘             │
│                │                 │
│         ┌──────▼──────┐          │
│         │  Database   │          │
│         └─────────────┘          │
└──────────────────────────────────┘

Better when:
✅ Small team (< 10 people)
✅ Low complexity domain
✅ Tight coupling is acceptable
✅ Simpler deployment/operations preferred
✅ Learning microservices first time
```

**Recommendation**: Start with a modular monolith, evolve to microservices when needed.

### Distributed Monolith Symptoms Checklist

```csharp
// Comprehensive assessment tool

public class DistributedMonolithDiagnostic
{
    public DiagnosticResult Assess(MicroservicesArchitecture system)
    {
        var score = 0;
        var issues = new List<string>();
        
        // Category 1: Deployment Independence (25 points)
        if (RequiresCoordinatedDeployments(system))
        {
            score += 10;

        }
        
        if (HasSharedDeploymentPipeline(system))
        {
            score += 8;
            issues.Add("Single deployment pipeline for multiple services");
        }
        
        if (CannotRollbackIndependently(system))
        {
            score += 7;
            issues.Add("Cannot rollback services independently");
        }
        
        // Category 2: Runtime Coupling (30 points)
        if (HasSynchronousChainingScore = score += 15;
            issues.Add("Synchronous service chains");
        }
        
        if (HasCircularDependencies(system))
        {
            score += 10;
            issues.Add("Circular service dependencies");
        }
        
        if (SharedSessionState(system))
        {
            score += 5;
            issues.Add("Shared session state across services");
        }
        
        // Category 3: Data Coupling (30 points)
        if (HasSharedDatabase(system))
        {
            score += 20;
            issues.Add("Services share database");
        }
        
        if (HasCrossDatabaseForeignKeys(system))
        {
            score += 10;
            issues.Add("Foreign keys across service databases");
        }
        
        // Category 4: Code Coupling (15 points)
        if (HasSharedBusinessLogicLibrary(system))
        {
            score += 10;
            issues.Add("Shared business logic library");
        }
        
        if (HasSharedDomainModels(system))
        {
            score += 5;
            issues.Add("Shared domain models");
        }
        
        return new DiagnosticResult
        {
            Score = score,
            Severity = score switch
            {
                <= 15 => "Healthy microservices",
```

### Measuring Service Independence

```csharp
// Quantitative metrics for service autonomy

public class ServiceIndependenceMetrics
{
    // Metric 1: Deployment Frequency Ratio
    public double CalculateDeploymentIndependence(Service service)
    {
        var totalDeployments = service.Deployments.Count();
        var coordinatedDeployments = service.Deployments
            .Count(d => d.RequiredOtherServices.Any());
        
        // Higher is better (1.0 = fully independent)
        return 1.0 - (coordinatedDeployments / (double)totalDeployments);
    }
    
    // Metric 2: Change Failure Rate Impact
    public double CalculateFailureIsolation(Service service)
    {
        var serviceFailures = service.Incidents.Count();
        var cascadingFailures = service.Incidents
            .Count(i => i.CausedOtherServiceFailures);
        
        // Higher is better (1.0 = failures don't cascade)
        return 1.0 - (cascadingFailures / (double)serviceFailures);
    }
    
    // Metric 3: API Stability
    public double CalculateAPIStability(Service service)
    {
        var totalChanges = service.APIChanges.Count();
        var breakingChanges = service.APIChanges
            .Count(c => c.IsBreaking);
        
        // Higher is better (1.0 = no breaking changes)
        return 1.0 - (breakingChanges / (double)totalChanges);
    }
    
    // Composite score
    public ServiceIndependenceScore CalculateCompositeScore(Service service)
    {
        var deployment = CalculateDeploymentIndependence(service);
        var isolation = CalculateFailureIsolation(service);
        var stability = CalculateAPIStability(service);
        
        var composite = (deployment + isolation + stability) / 3.0;
        
        return new ServiceIndependenceScore
        {
            Deployment = deployment,
            Isolation = isolation,
            Stability = stability,
            Composite = composite,
            Grade = composite switch
            {
                >= 0.9 => "A - Excellent independence",
                >= 0.7 => "B - Good independence",
                >= 0.5 => "C - Moderate coupling",
                >= 0.3 => "D - Significant coupling",
                _ => "F - Distributed monolith"
            }
        };
    }
}
```

## Refactoring Distributed Monoliths

### Step-by-Step Remediation

```csharp
// How to fix a distributed monolith

public class RefactoringStrategy
{
    // Step 1: Eliminate shared database
    public class EliminateSharedDatabase
    {
        public async Task RefactorAsync()
        {
            // Phase 1: Identify data ownership
            var dataOwnership = new Dictionary<string, string>
            {
                ["Orders"] = "OrderService",
                ["Customers"] = "CustomerService",
                ["Products"] = "ProductService"
            };
            
            // Phase 2: Create service-specific databases
            await CreateServiceDatabasesAsync(dataOwnership);
            
            // Phase 3: Migrate data
            await MigrateDataAsync(dataOwnership);
            
            // Phase 4: Dual-write period
            await EnableDualWriteAsync();
            
            // Phase 5: Switch reads to new databases
            await SwitchReadsAsync();
            
            // Phase 6: Remove shared database access
            await RemoveSharedAccessAsync();
        }
    }
    
    // Step 2: Break synchronous chains
    public class BreakSynchronousChains
    {
        // Before: A → B → C → D (synchronous chain)
        // After: A publishes event, B/C/D subscribe
        
        public async Task RefactorAsync()
        {
            // Introduce event bus
            await SetupEventBusAsync();
            
            // Convert chain to events
            // Service A: Publish event instead of calling B
            public class ServiceA
            {
                public async Task ProcessAsync()
                {
                    var result = await DoWorkAsync();
                    
                    // Instead of: await _serviceB.ProcessAsync(result);
                    await _eventBus.PublishAsync(new ACompletedEvent
                    {
                        Data = result
                    });
                }
            }
            
            // Services B, C, D: Subscribe to events
            public class ServiceB
            {
                public async Task HandleACompletedAsync(ACompletedEvent evt)
                {
                    await ProcessAsync(evt.Data);
                    
                    await _eventBus.PublishAsync(new BCompletedEvent
                    {
                        Data = resultFromB
                    });
                }
            }
            
            // Now services are decoupled!
        }
    }
    
    // Step 3: Extract shared business logic
    public class ExtractSharedLogic
    {
        // Option A: Duplicate the logic
        public class DuplicateLogic
        {
            // OrderService gets its own validation
            public class OrderValidator
            {
                public bool Validate(Order order)
                {
                    // Order-specific rules
                    return order.Total > 0 && order.Items.Any();
                }
            }
            
            // ShippingService gets its own validation
            public class ShipmentValidator
            {
                public bool Validate(Shipment shipment)
                {
                    // Shipment-specific rules
                    return shipment.Address != null;
                }
            }
            
            // Some duplication is OK for independence!
        }
        
        // Option B: Create a service
        public class CreateValidationService
        {
            // If truly shared and complex:
            [HttpPost("validate-order")]
            public async Task<ValidationResult> ValidateOrder(Order order)
            {
                // Centralized validation
                // But service must be highly available!
            }
        }
    }
    
    // Step 4: Consolidate over-fragmented services
    public class ConsolidateServices
    {
        // Merge tiny services into larger, cohesive ones
        
        // Before: 6 user-related microservices
        // - UserRegistrationService
        // - UserLoginService
        // - UserProfileService
        // - UserPreferencesService
        // - UserAddressService
        // - UserNotificationService
        
        // After: 2 user-related services
        public class UserManagementService
        {
            // Combined: Registration, Login, Profile, Preferences
            // All core user functionality
        }
        
        public class UserCommunicationService
        {
            // Combined: Addresses, Notifications
            // Communication-related functionality
        }
    }
}
```

### Migration Patterns

```csharp
// Patterns for transitioning away from distributed monolith

public class MigrationPatterns
{
    // Pattern 1: Merge to modular monolith first
    public class MergeToMonolith
    {
        // If distributed monolith has:
        // - < 20 developers
        // - High coupling anyway
        // - Operational burden too high
        
        // Consider: Merge back to modular monolith
        // Then extract properly bounded services later
        
        // Steps:
        // 1. Identify proper module boundaries
        // 2. Merge services into modules
        // 3. Keep module boundaries strict
        // 4. Extract to services when truly needed
    }
    
    // Pattern 2: Reorganize around capabilities
    public class ReorganizeByCapability
    {
        // Current: 15 services with unclear boundaries
        // Target: 5-7 services around business capabilities
        
        // Mergers:
        // UserService + AuthService + ProfileService
        //   → CustomerManagementService
        
        // OrderService + CartService + CheckoutService
        //   → OrderManagementService
        
        // Result: Larger, more cohesive services
    }
    
    // Pattern 3: Introduce API gateway
    public class APIGatewayPattern
    {
        // Add gateway to reduce direct coupling
        
        [HttpGet("order-details/{id}")]
        public async Task<OrderDetails> GetOrderDetails(string id)
        {
            // Gateway orchestrates calls
            var order = await _orderService.GetOrderAsync(id);
            var customer = await _customerService.GetCustomerAsync(order.CustomerId);
            var items = await _productService.GetProductsAsync(order.ItemIds);
            
            // Compose response
            return new OrderDetails
            {
                Order = order,
                Customer = customer,
                Items = items
            };
        }
        
        // Services don't call each other directly
        // Reduces coupling, easier to refactor
    }
}
```

## Alternative Architecture: Modular Monolith

### When Modular Monolith is Better

```csharp
// Detailed modular monolith implementation

public class ModularMonolithArchitecture
{
    // Module structure
    // src/
    //   Modules/
    //     Orders/
    //       Orders.API/
    //       Orders.Domain/
    //       Orders.Infrastructure/
    //     Products/
    //       Products.API/
    //       Products.Domain/
    //       Products.Infrastructure/
    
    // Module communication rules
    public class ModuleCommunicationRules
    {
        // Rule 1: Modules communicate via interfaces
        public interface IOrdersModule
        {
            Task<Order> GetOrderAsync(string id);
            Task<Order> CreateOrderAsync(CreateOrderCommand cmd);
        }
        
        // Rule 2: No direct database access across modules
        // ProductModule cannot query Orders table directly
        
        // Rule 3: Use in-process events
        public class InProcessEventBus
        {
            public async Task PublishAsync<TEvent>(TEvent evt)
            {
                // Publish to handlers in same process
                // Fast, simple, transactional
            }
        }
        
        // Rule 4: Each module has its own database schema
        // Orders → dbo.Orders schema
        // Products → dbo.Products schema
        // Logical separation prepares for future extraction
    }
    
    // Benefits over distributed monolith:
    public class ModularMonolithBenefits
    {
        // ✓ Clear boundaries (like microservices)
        // ✓ Simple deployment (unlike microservices)
        // ✓ ACID transactions (unlike microservices)
        // ✓ Fast in-process calls (unlike microservices)
        // ✓ Easy debugging (unlike microservices)
        // ✓ Lower operational complexity
        // ✓ Can extract to services later if needed
    }
    
    // When to use:
    public class WhenToUseModularMonolith
    {
        // ✓ Team size < 20 developers
        // ✓ Domain boundaries clear but coupling OK
        // ✓ Don't need independent scaling
        // ✓ Don't need polyglot persistence
        // ✓ Want faster development velocity
        // ✓ Limited DevOps maturity
    }
}
```

## Self-Check Questions

1. **What's worse: code duplication or shared business logic libraries?**
   - Shared libraries create tight coupling
   - Some duplication is acceptable for independence
   - DRY is less important than decoupling in microservices

2. **When is it okay to make synchronous calls between services?**
   - For queries (read operations)
   - When you need immediate response
   - When failure of called service should fail the operation
   - But: prefer async for everything else

3. **How do you know if your services are too fine-grained?**
   - More services than team members
   - Services with only 1-2 operations
   - Constant coordination needed
   - Network overhead is significant

4. **What's the difference between a modular monolith and microservices?**
   - Modular monolith: logical separation, single deployment
   - Microservices: physical separation, independent deployments
   - Both can have good boundaries

## Key Takeaways

✅ **Distributed monoliths** have microservices complexity without the benefits

✅ **Avoid shared business logic** in libraries — duplicate or create a service

✅ **Database per service** is non-negotiable for true independence

✅ **Prefer async communication** and caching over synchronous chains

✅ **Start with larger services**, split only when necessary

✅ Sometimes a **modular monolith** is the right choice

✅ **Independence** is more important than avoiding duplication
