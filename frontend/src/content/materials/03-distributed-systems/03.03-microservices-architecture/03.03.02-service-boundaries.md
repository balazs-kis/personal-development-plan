# Lesson 2: Identifying Service Boundaries

## Learning Objectives

By the end of this lesson, you will be able to:
- Identify appropriate service boundaries using Domain-Driven Design
- Apply bounded contexts to define service boundaries
- Recognize high cohesion and low coupling in service design
- Avoid creating distributed monoliths
- Use business capabilities to guide decomposition

---

## Introduction

One of the hardest challenges in microservices is determining where one service ends and another begins. Poor service boundaries lead to distributed monoliths—systems with all the complexity of microservices but none of the benefits. This lesson teaches you how to identify natural boundaries that lead to cohesive, loosely coupled services.

## Domain-Driven Design Fundamentals

### Bounded Contexts

A bounded context is a boundary within which a particular domain model is defined and applicable.

```csharp
// Example: "Customer" means different things in different contexts

// Sales Context
public class Customer
{
    public string Id { get; set; }
    public string Name { get; set; }
    public CreditLimit CreditLimit { get; set; }
    public List<Order> OrderHistory { get; set; }
    // Focused on purchasing behavior
}

// Support Context
public class Customer
{
    public string Id { get; set; }
    public string Name { get; set; }
    public List<SupportTicket> Tickets { get; set; }
    public SupportTier SupportLevel { get; set; }
    // Focused on support interactions
}

// Shipping Context
public class Customer
{
    public string Id { get; set; }
    public string Name { get; set; }
    public List<Address> ShippingAddresses { get; set; }
    // Focused on delivery logistics
}

// Each context has its own model of "Customer"
// This is intentional and correct!
```

### Ubiquitous Language

Each bounded context has its own language.

```csharp
// Inventory Context
public class Product
{
    public string SKU { get; set; }
    public int QuantityOnHand { get; set; }
    public int ReorderPoint { get; set; }
    // Language: SKU, stock, reorder
}

// Catalog Context  
public class Product
{
    public string ProductId { get; set; }
    public string Title { get; set; }
    public string Description { get; set; }
    public List<string> Images { get; set; }
    // Language: title, description, images
}

// Different language = different context = different service
```

## Identifying Service Boundaries

### 1. Business Capabilities Approach

```csharp
// Organize around what the business does, not technical layers

// ❌ BAD: Technical layers as services
// - UserDataService
// - OrderDataService  
// - PaymentDataService
// Just a distributed monolith!

// ✅ GOOD: Business capabilities as services
public class ECommerceSystem
{
    // Order Management - Everything about orders
    public class OrderService
    {
        public Task<Order> CreateOrderAsync(CreateOrderRequest request) { }
        public Task<Order> GetOrderAsync(string id) { }
        public Task CancelOrderAsync(string id) { }
        // Owns: Orders, OrderItems, OrderStatus
    }
    
    // Inventory Management - Everything about stock
    public class InventoryService
    {
        public Task<int> GetAvailableQuantityAsync(string sku) { }
        public Task ReserveInventoryAsync(string sku, int quantity) { }
        public Task ReleaseInventoryAsync(string sku, int quantity) { }
        // Owns: Inventory, Warehouses, StockLevels
    }
    
    // Payment Processing - Everything about money
    public class PaymentService
    {
        public Task<PaymentResult> ProcessPaymentAsync(PaymentRequest request) { }
        public Task RefundAsync(string transactionId) { }
        // Owns: Transactions, PaymentMethods, Refunds
    }
}
```

### 2. Cohesion Analysis

High cohesion: Things that change together, stay together.

```csharp
// ✅ GOOD: High cohesion
public class OrderService
{
    // All order-related operations in one service
    public Task CreateOrder(Order order) { }
    public Task AddItemToOrder(string orderId, OrderItem item) { }
    public Task RemoveItemFromOrder(string orderId, string itemId) { }
    public Task CalculateOrderTotal(string orderId) { }
    
    // When order logic changes, we change one service
}

// ❌ BAD: Low cohesion
public class OrderCreationService { }
public class OrderItemManagementService { }
public class OrderCalculationService { }
// Order logic scattered across multiple services
// Change requires coordinating multiple deployments
```

### 3. Coupling Analysis

Low coupling: Services are independent.

```csharp
// ✅ GOOD: Loose coupling through events
public class OrderService
{
    public async Task CreateOrderAsync(CreateOrderRequest request)
    {
        var order = new Order { /* ... */ };
        await _repository.SaveAsync(order);
        
        // Publish event - don't call other services directly
        await _eventBus.PublishAsync(new OrderCreatedEvent
        {
            OrderId = order.Id,
            CustomerId = request.CustomerId,
            Items = order.Items
        });
    }
}

public class InventoryService
{
    // Listen to event - no compile-time dependency on OrderService
    public async Task HandleOrderCreatedAsync(OrderCreatedEvent evt)
    {
        foreach (var item in evt.Items)
        {
            await ReserveInventoryAsync(item.ProductId, item.Quantity);
        }
    }
}

// ❌ BAD: Tight coupling through shared database
public class OrderService
{
    public async Task CreateOrderAsync(CreateOrderRequest request)
    {
        // Directly update Inventory table
        await _db.ExecuteAsync(
            "UPDATE Inventory SET Available = Available - @Qty WHERE ProductId = @Id",
            request.Items);
        
        // Now OrderService depends on Inventory schema!
    }
}
```

## Practical Decomposition Strategies

### 1. Start with Business Capabilities

```csharp
// E-Commerce Example

// Identify top-level capabilities:
// 1. Product Catalog
// 2. Order Management
// 3. Inventory Management
// 4. Payment Processing
// 5. Shipping & Fulfillment
// 6. Customer Management
// 7. Recommendations

// Each becomes a bounded context / service

public class ProductCatalogService
{
    // Capability: Display products to customers
    // - Search products
    // - View product details
    // - Manage product information
}

public class OrderManagementService
{
    // Capability: Process customer orders
    // - Create orders
    // - Track order status
    // - Handle returns
}
```

### 2. Use Event Storming

```csharp
// Collaborative workshop to identify domain events

// Domain Events discovered:
// - OrderPlaced
// - PaymentProcessed
// - InventoryReserved
// - OrderShipped
// - OrderDelivered

// Events cluster around bounded contexts:

// Order Context:
// - OrderPlaced, OrderCancelled, OrderReturned

// Payment Context:
// - PaymentProcessed, PaymentFailed, RefundIssued
```

### 3. Analyze Data Relationships

```csharp
// Look for aggregate roots and their boundaries

// ✅ GOOD: Clear aggregates
public class Order // Aggregate Root
{
    public string Id { get; set; }
    public List<OrderLine> Lines { get; set; } // Part of Order aggregate
    public Address ShippingAddress { get; set; } // Part of Order aggregate
    
    // Order and OrderLines always change together
    // Keep in same service
}

public class Product // Different Aggregate Root
{
    public string Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    
    // Product changes independently of Order
    // Different service
}

// ❌ BAD: Breaking up aggregates
// OrderService: Has Order entity
// OrderLineService: Has OrderLine entity
// Now you need distributed transactions!
```

## Avoiding Distributed Monoliths

### Anti-Pattern: Chatty Services

```csharp
// ❌ BAD: Service needs multiple calls to other services
public class OrderService
{
    public async Task<OrderDetails> GetOrderDetailsAsync(string orderId)
    {
        var order = await _orderRepo.GetAsync(orderId);
        
        // Call to CustomerService
        var customer = await _customerClient.GetCustomerAsync(order.CustomerId);
        
        // Call to ProductService for EACH item
        foreach (var item in order.Items)
        {
            var product = await _productClient.GetProductAsync(item.ProductId);
            item.ProductName = product.Name;
        }
        
        // Call to InventoryService
        var availability = await _inventoryClient.CheckAvailabilityAsync(
            order.Items.Select(i => i.ProductId));
        
        // Too many network calls!
        // Latency adds up, failure probability increases
        return new OrderDetails { Order = order, Customer = customer };
    }
}

// ✅ GOOD: Service has all data it needs
public class OrderService
{
    public async Task<OrderDetails> GetOrderDetailsAsync(string orderId)
    {
        // Order service keeps denormalized data
        var order = await _orderRepo.GetAsync(orderId);
        
        // Order includes:
        // - Customer name (denormalized)
        // - Product names (denormalized)  
        // - Snapshot of data at order time
        
        // No additional service calls needed
        return new OrderDetails { Order = order };
    }
    
    // Update denormalized data via events
    public async Task HandleCustomerNameChangedAsync(CustomerNameChangedEvent evt)
    {
        await _orderRepo.UpdateCustomerNameAsync(evt.CustomerId, evt.NewName);
    }
}
```

### Anti-Pattern: Shared Database

```csharp
// ❌ BAD: Services share a database
public class SharedDatabaseSystem
{
    // OrderService: Reads/writes Orders table
    // ShippingService: Reads Orders table, writes Shipments table
    // BillingService: Reads Orders table, writes Invoices table
    
    // Problems:
    // 1. Schema changes require coordinating all services
    // 2. Cannot scale databases independently
    // 3. Cannot choose different database types
    // 4. Tight coupling through schema
}

// ✅ GOOD: Database per service
public class DatabasePerServiceSystem
{
    // OrderService: Has OrderDb
    public class OrderService
    {
        private readonly OrderDbContext _db;
        // Full control over Order schema
    }
    
    // ShippingService: Has ShippingDb
    public class ShippingService
    {
        private readonly ShippingDbContext _db;
        // Full control over Shipping schema
        
        // Gets order info via API or events
        public async Task HandleOrderPlacedAsync(OrderPlacedEvent evt)
        {
            var shipment = new Shipment
            {
                OrderId = evt.OrderId,
                // Copy only what shipping needs
                ShippingAddress = evt.ShippingAddress,
                Items = evt.Items
            };
            await _db.Shipments.AddAsync(shipment);
        }
    }
}
```

## Size Guidelines

```csharp
// How big should a microservice be?

// ✅ GOOD: Right-sized service
public class OrderService
{
    // Domain: Order Management
    // Team: 5-8 developers can maintain it
    // Deployment: Can deploy in ~10 minutes
    // Code: ~10,000-50,000 lines of code
    // Scope: One bounded context
}

// ❌ TOO SMALL: Nano-services
public class CreateOrderService { }
public class UpdateOrderService { }
public class DeleteOrderService { }
// Each operation is a service
// Too much overhead, too chatty

// ❌ TOO LARGE: Distributed monolith
public class EverythingService
{
    // Handles orders, inventory, payments, shipping
    // 200,000 lines of code
    // Takes 2 hours to deploy
    // Defeats the purpose of microservices
}

// Rule of thumb: "Two pizza team"
// A service should be maintainable by a team that can be fed with two pizzas (~5-8 people)
```

## Advanced Decomposition Techniques

### Context Mapping

```csharp
// Map relationships between bounded contexts

public enum ContextRelationship
{
    // Partnership: Two teams collaborate closely
    Partnership,
    
    // Shared Kernel: Shared code/database (use sparingly!)
    SharedKernel,
    
    // Customer-Supplier: Downstream depends on upstream
    CustomerSupplier,
    
    // Conformist: Downstream conforms to upstream
    Conformist,
    
    // Anticorruption Layer: Translate between contexts
    AnticorruptionLayer,
    
    // Open Host Service: Well-defined API for many consumers
    OpenHostService,
    
    // Separate Ways: No relationship, duplicate if needed
    SeparateWays
}

// Example: E-Commerce Context Map

public class OrderContext
{
    // Relationship with ProductCatalog: Customer-Supplier
    // Order context depends on product information
    // Uses Anticorruption Layer to protect from catalog changes
    
    public class ProductAnticorruptionLayer
    {
        private readonly IProductCatalogClient _catalogClient;
        
        // Translate catalog model to order model
        public async Task<OrderProduct> GetProductForOrder(string productId)
        {
            var catalogProduct = await _catalogClient.GetProductAsync(productId);
            
            // Transform to order domain model
            return new OrderProduct
            {
                ProductId = catalogProduct.Id,
                Name = catalogProduct.DisplayName, // Different naming
                Price = catalogProduct.CurrentPrice,
                // Only what order needs, shields from catalog changes
            };
        }
    }
}

public class PaymentContext
{
    // Relationship with Order: Customer-Supplier
    // Payment is downstream, order is upstream
    // Payment conforms to order's contract
    
    public async Task HandleOrderPlacedAsync(OrderPlacedEvent evt)
    {
        // Payment adapts to order's event structure
        await ProcessPaymentAsync(evt.OrderId, evt.TotalAmount);
    }
}

public class InventoryContext
{
    // Relationship with Order: Partnership
    // Close collaboration, coordinated releases sometimes needed
    
    // Tight coupling acceptable here due to business criticality
}
```

### Service Interface Design

```csharp
// Design service interfaces for loose coupling

// ❌ BAD: Leaky abstraction
public class LeakyOrderService
{
    [HttpGet("orders/{id}")]
    public async Task<Order> GetOrder(string id)
    {
        // Returns internal database entity
        return await _db.Orders
            .Include(o => o.Customer)
            .Include(o => o.Lines)
            .ThenInclude(l => l.Product)
            .FirstOrDefaultAsync(o => o.Id == id);
        
        // Consumers coupled to:
        // - Database schema
        // - EF Core
        // - Internal entity relationships
    }
}

// ✅ GOOD: Clean contract
public class CleanOrderService
{
    [HttpGet("orders/{id}")]
    public async Task<OrderDto> GetOrder(string id)
    {
        var order = await _db.Orders.FindAsync(id);
        
        // Return DTO, not entity
        return new OrderDto
        {
            OrderId = order.Id,
            Status = order.Status.ToString(),
            OrderDate = order.CreatedAt,
            Items = order.Lines.Select(l => new OrderItemDto
            {
                ProductId = l.ProductId,
                ProductName = l.ProductName, // Denormalized
                Quantity = l.Quantity,
                Price = l.UnitPrice
            }).ToList(),
            // Only expose what consumers need
            // Hide internal implementation
        };
    }
}

// ✅ GOOD: Command-Query Separation
public class OrderCommandApi
{
    // Commands: Change state
    [HttpPost("orders")]
    public async Task<OrderCreatedResponse> CreateOrder(CreateOrderCommand cmd)
    {
        var order = await _commandHandler.HandleAsync(cmd);
        return new OrderCreatedResponse { OrderId = order.Id };
    }
    
    [HttpPost("orders/{id}/cancel")]
    public async Task<IActionResult> CancelOrder(string id)
    {
        await _commandHandler.HandleAsync(new CancelOrderCommand { OrderId = id });
        return NoContent();
    }
}

public class OrderQueryApi
{
    // Queries: Read state (separate, can scale independently)
    [HttpGet("orders/{id}")]
    public async Task<OrderDto> GetOrder(string id)
    {
        return await _queryHandler.HandleAsync(new GetOrderQuery { OrderId = id });
    }
    
    [HttpGet("orders")]
    public async Task<PagedResult<OrderSummaryDto>> SearchOrders(OrderSearchQuery query)
    {
        return await _queryHandler.HandleAsync(query);
    }
}
```

### Handling Cross-Cutting Concerns

```csharp
// Authentication, logging, etc. across services

// Pattern 1: API Gateway handles concerns
public class ApiGateway
{
    public async Task<IActionResult> HandleRequest(HttpRequest request)
    {
        // 1. Authentication (once at gateway)
        var user = await AuthenticateAsync(request);
        if (user == null) return Unauthorized();
        
        // 2. Rate limiting
        if (!await _rateLimiter.AllowRequestAsync(user.Id))
            return TooManyRequests();
        
        // 3. Logging
        _logger.LogInformation("User {UserId} accessing {Path}", 
            user.Id, request.Path);
        
        // 4. Route to service (services trust gateway)
        return await RouteToServiceAsync(request, user);
    }
}

// Pattern 2: Sidecar proxy (Service Mesh)
public class ServiceWithSidecar
{
    // Service code is simple
    [HttpGet("orders/{id}")]
    public async Task<OrderDto> GetOrder(string id)
    {
        // Just business logic
        return await _orderRepository.GetAsync(id);
    }
    
    // Sidecar handles:
    // - mTLS encryption
    // - Retries
    // - Circuit breaking
    // - Distributed tracing
    // - Metrics collection
    
    // Service doesn't need to worry about it!
}

// Pattern 3: Shared library (use carefully!)
public class SharedCrossCuttingLibrary
{
    // OK for:
    // - Logging interfaces
    // - Telemetry standards
    // - Common DTOs for shared events
    
    // NOT OK for:
    // - Business logic
    // - Data access
    // - Service-specific concerns
    
    public interface ILogger
    {
        void LogInformation(string message, params object[] args);
    }
    
    // Each service implements, doesn't share code
}
```

### Versioning Strategies

```csharp
// Handle API evolution

// Strategy 1: URI Versioning
[ApiVersion("1.0")]
[Route("api/v{version:apiVersion}/orders")]
public class OrdersV1Controller : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<OrderV1Dto> GetOrder(string id)
    {
        return await _service.GetOrderV1Async(id);
    }
}

[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/orders")]
public class OrdersV2Controller : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<OrderV2Dto> GetOrder(string id)
    {
        // Enhanced version
        return await _service.GetOrderV2Async(id);
    }
}

// Strategy 2: Header Versioning
public class OrdersController : ControllerBase
{
    [HttpGet("orders/{id}")]
    public async Task<IActionResult> GetOrder(string id)
    {
        var version = Request.Headers["api-version"].FirstOrDefault() ?? "1.0";
        
        return version switch
        {
            "1.0" => Ok(await _service.GetOrderV1Async(id)),
            "2.0" => Ok(await _service.GetOrderV2Async(id)),
            _ => BadRequest("Unsupported API version")
        };
    }
}

// Strategy 3: Expand/Contract
public class ExpandContractVersion
{
    // Phase 1: EXPAND - Add new fields (optional)
    public class OrderDto
    {
        public string Id { get; set; }
        public string Status { get; set; }
        
        // New field (optional, not breaking)
        public DateTime? EstimatedDelivery { get; set; }
    }
    
    // Phase 2: Migrate consumers to use new field
    // Phase 3: CONTRACT - Make field required
    public class OrderDtoV2
    {
        public string Id { get; set; }
        public string Status { get; set; }
        public DateTime EstimatedDelivery { get; set; } // Now required
    }
}
```

## Testing Service Boundaries

### Contract Testing

```csharp
// Ensure services don't break each other

// Consumer (ShippingService) defines expectations
public class OrderServiceContractTests
{
    [Fact]
    public async Task OrderService_ProvidesRequiredFieldsForShipping()
    {
        // Arrange: Consumer expectations
        var requiredFields = new[] { "orderId", "shippingAddress", "items" };
        
        // Act: Call provider
        var response = await _orderClient.GetOrderAsync("123");
        var json = JsonSerializer.Serialize(response);
        var doc = JsonDocument.Parse(json);
        
        // Assert: Provider meets expectations
        foreach (var field in requiredFields)
        {
            Assert.True(doc.RootElement.TryGetProperty(field, out _),
                $"OrderService must provide '{field}' for shipping");
        }
    }
    
    [Fact]
    public async Task OrderService_ShippingAddressHasRequiredFields()
    {
        var order = await _orderClient.GetOrderAsync("123");
        
        Assert.NotNull(order.ShippingAddress);
        Assert.NotNull(order.ShippingAddress.Street);
        Assert.NotNull(order.ShippingAddress.City);
        Assert.NotNull(order.ShippingAddress.PostalCode);
        
        // If OrderService breaks this, ShippingService tests fail
    }
}

// Provider (OrderService) runs consumer tests
public class OrderServicePipeline
{
    public async Task BuildAndTest()
    {
        await RunUnitTests();
        await RunIntegrationTests();
        
        // Run all consumer contract tests
        await RunContractTests("ShippingService");
        await RunContractTests("BillingService");
        
        // If any consumer contract fails, build fails
        // Cannot break consumers!
    }
}
```

## Key Takeaways

- Use Domain-Driven Design to identify natural service boundaries
- Bounded contexts from DDD map well to microservice boundaries
- Organize around business capabilities, not technical layers
- High cohesion: Things that change together stay together
- Low coupling: Services communicate through APIs or events, never shared databases
- Avoid distributed monoliths: chatty services, shared databases, tight coupling
- Size matters: Team should be able to maintain the service (5-8 people)
- Start with larger services, split them later if needed
- Data ownership is clear: each service owns its database
- Denormalize data to avoid excessive inter-service communication
