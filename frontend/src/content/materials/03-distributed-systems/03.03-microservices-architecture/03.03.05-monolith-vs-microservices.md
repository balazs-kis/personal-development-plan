# Lesson 5: Microservices vs Monoliths: Making the Right Choice

## Learning Objectives

By the end of this lesson, you will be able to:
- Compare monoliths and microservices objectively
- Identify when each approach is appropriate
- Understand the modular monolith as a middle ground
- Plan a migration strategy from monolith to microservices
- Avoid premature decomposition and distributed monoliths

---

## Introduction

The choice between monoliths and microservices is not binary—it's a spectrum. Many successful systems start as monoliths and evolve to microservices, while others remain monoliths indefinitely. This lesson helps you make informed decisions about architecture based on your specific context, avoiding dogmatic approaches.

## Objective Comparison

### Monolith Advantages

```csharp
// ✅ Simpler Development
public class MonolithicECommerce
{
    private readonly AppDbContext _db;
    
    public async Task PlaceOrderAsync(Order order)
    {
        // Simple transaction across tables
        using var transaction = _db.Database.BeginTransaction();
        
        // All in same database, same transaction
        await _db.Orders.AddAsync(order);
        await UpdateInventoryAsync(order.Items);
        await ChargeCustomerAsync(order.CustomerId, order.Total);
        
        await _db.SaveChangesAsync();
        await transaction.CommitAsync();
        
        // No distributed transactions!
        // No network calls!
        // Easy to reason about!
    }
}

// ✅ Easier Testing
[Fact]
public async Task PlaceOrder_ReducesInventory()
{
    // Test entire flow in one process
    var order = CreateTestOrder();
    await _orderService.PlaceOrderAsync(order);
    
    var product = await _productService.GetProductAsync(order.Items[0].ProductId);
    Assert.Equal(expectedQuantity, product.QuantityAvailable);
    
    // No need to mock multiple services
}

// ✅ Simpler Deployment
public class MonolithDeployment
{
    // One application to deploy
    // One configuration file
    // One connection string
    // One monitoring dashboard
}

// ✅ Better Performance (No Network Overhead)
public class MonolithPerformance
{
    // In-process calls are ~1000x faster than HTTP
    public Order GetOrderWithCustomer(string orderId)
    {
        var order = _orderRepo.Get(orderId);
        var customer = _customerRepo.Get(order.CustomerId); // Microseconds!
        
        order.Customer = customer;
        return order;
    }
}
```

### Microservices Advantages

```csharp
// ✅ Independent Scaling
public class MicroservicesScaling
{
    // Scale services independently
    // OrderService: 50 instances (Black Friday traffic)
    // UserService: 5 instances (normal traffic)
    
    // Monolith: Must scale entire app even if only orders are busy
}

// ✅ Team Autonomy
public class MicroservicesAutonomy
{
    // Team A: Deploy OrderService 10 times/day
    // Team B: Deploy PaymentService once/week
    // No coordination needed!
    
    // Monolith: All teams must coordinate deployments
}

// ✅ Technology Flexibility
public class MicroservicesPolyglot
{
    // OrderService: C# + SQL Server
    // RecommendationService: Python + TensorFlow
    // SearchService: Node.js + Elasticsearch
    
    // Each team chooses best tool
    
    // Monolith: Entire system in one stack
}

// ✅ Fault Isolation
public class MicroservicesResilience
{
    [HttpGet("product/{id}")]
    public async Task<IActionResult> GetProduct(string id)
    {
        var product = await _productService.GetAsync(id);
        
        try
        {
            // Recommendation service down? No problem!
            var recommendations = await _recommendationService.GetAsync(id);
            product.Recommendations = recommendations;
        }
        catch
        {
            product.Recommendations = new List<Product>();
        }
        
        return Ok(product);
        // Product page still works!
    }
    
    // Monolith: One component fails, entire app may fail
}
```

## The Modular Monolith

A middle ground: monolith with good boundaries.

```csharp
// Modular Monolith Structure

// Solution Structure:
// - Modules/
//   - Orders/
//     - Orders.Api/
//     - Orders.Domain/
//     - Orders.Infrastructure/
//   - Products/
//     - Products.Api/
//     - Products.Domain/
//     - Products.Infrastructure/
//   - Payments/
//     - Payments.Api/
//     - Payments.Domain/
//     - Payments.Infrastructure/

// Each module is self-contained
// Clear boundaries prepare for future extraction

// Orders Module
namespace ECommerce.Modules.Orders
{
    // Public interface (other modules use this)
    public interface IOrderService
    {
        Task<Order> CreateOrderAsync(CreateOrderRequest request);
        Task<Order> GetOrderAsync(string id);
    }
    
    // Internal implementation (hidden from other modules)
    internal class OrderService : IOrderService
    {
        private readonly IOrderRepository _repository;
        
        public async Task<Order> CreateOrderAsync(CreateOrderRequest request)
        {
            // Order-specific logic
            var order = new Order { /* ... */ };
            await _repository.SaveAsync(order);
            
            // Publish event for other modules
            await _eventBus.PublishAsync(new OrderCreatedEvent(order));
            
            return order;
        }
    }
}

// Products Module  
namespace ECommerce.Modules.Products
{
    // Separate, independent module
    // Could extract to microservice later
    
    public interface IProductService
    {
        Task<Product> GetProductAsync(string id);
    }
    
    internal class ProductService : IProductService
    {
        // Product-specific logic
    }
}

// Main Application
public class Startup
{
    public void ConfigureServices(IServiceCollection services)
    {
        // Register modules
        services.AddOrdersModule(Configuration);
        services.AddProductsModule(Configuration);
        services.AddPaymentsModule(Configuration);
        
        // Still one deployment, but modular!
    }
}
```

## Migration Strategies

### Strangler Fig Pattern

Gradually replace monolith with microservices.

```csharp
// Step 1: Identify candidate for extraction
// Choose: Low-risk, well-defined boundary

// Monolith
public class MonolithController : ControllerBase
{
    [HttpGet("recommendations/{userId}")]
    public async Task<IActionResult> GetRecommendations(string userId)
    {
        // Currently in monolith
        var recommendations = await _recommendationEngine.GetAsync(userId);
        return Ok(recommendations);
    }
}

// Step 2: Build new microservice
public class RecommendationMicroservice
{
    [HttpGet("recommendations/{userId}")]
    public async Task<IActionResult> GetRecommendations(string userId)
    {
        // Same functionality, separate service
        var recommendations = await _engine.GetAsync(userId);
        return Ok(recommendations);
    }
}

// Step 3: Route new requests to microservice
public class ApiGateway
{
    public async Task<IActionResult> RouteRequest(HttpRequest request)
    {
        if (request.Path.StartsWith("/recommendations"))
        {
            // Route to new microservice
            return await _recommendationClient.ForwardAsync(request);
        }
        else
        {
            // Route to monolith
            return await _monolithClient.ForwardAsync(request);
        }
    }
}

// Step 4: Remove code from monolith
// Step 5: Repeat for next service

// Result: Gradual, low-risk migration
```

### Branch by Abstraction

```csharp
// Step 1: Create abstraction
public interface IRecommendationService
{
    Task<List<Product>> GetRecommendationsAsync(string userId);
}

// Step 2: Implement with current monolith code
public class MonolithRecommendationService : IRecommendationService
{
    public async Task<List<Product>> GetRecommendationsAsync(string userId)
    {
        // Existing monolith logic
        return await _recommendationEngine.GetAsync(userId);
    }
}

// Step 3: Implement with microservice client
public class MicroserviceRecommendationService : IRecommendationService
{
    private readonly HttpClient _client;
    
    public async Task<List<Product>> GetRecommendationsAsync(string userId)
    {
        // Call new microservice
        var response = await _client.GetAsync($"/recommendations/{userId}");
        return await response.Content.ReadFromJsonAsync<List<Product>>();
    }
}

// Step 4: Use feature flag to switch
public class RecommendationController : ControllerBase
{
    private readonly IRecommendationService _service;
    
    public RecommendationController(
        IFeatureManager features,
        MonolithRecommendationService monolith,
        MicroserviceRecommendationService microservice)
    {
        // Feature flag controls which implementation
        _service = features.IsEnabled("UseMicroservice") 
            ? microservice 
            : monolith;
    }
}

// Step 5: Gradually roll out, monitor, then remove monolith code
```

## Common Mistakes

### ❌ Mistake: Microservices First

```csharp
// BAD: Start new project with microservices
// - Domain boundaries unknown
// - Requirements unclear
// - Will create wrong boundaries

// GOOD: Start with modular monolith
public class WellDesignedStart
{
    // Modular monolith with:
    // - Clear module boundaries
    // - Modules communicate via interfaces/events
    // - Prepare for future extraction
    // - Extract to microservices when needed
}
```

### ❌ Mistake: Distributed Monolith

```csharp
// BAD: Microservices with monolith characteristics
public class DistributedMonolith
{
    // - Shared database
    // - Synchronous coupling
    // - Coordinated deployments
    // - Same technology stack everywhere
    
    // Worst of both worlds:
    // - Complexity of microservices
    // - Inflexibility of monolith
}

// GOOD: True microservices or stay monolith
```

### ❌ Mistake: Too Many Services Too Soon

```csharp
// BAD: 50 services for 10 developers
// - Cannot manage operational complexity
// - Slows development to a crawl

// GOOD: Start with 3-5 services
// - Grow gradually as team grows
// - 1-2 services per team
}
```

## The Cost of Getting It Wrong

### Anti-Pattern: Premature Microservices

```csharp
// Real-world failure story

public class PrematureDecomposition
{
    // Startup scenario: 3 developers, unclear domain
    
    // Day 1: "Let's build microservices from the start!"
    public class Day1
    {
        // Created services:
        // - UserService
        // - OrderService
        // - ProductService
        // - PaymentService
        // - NotificationService
    }
    
    // Month 3: Wrong boundaries discovered
    public class Month3
    {
        // Problem: Orders need products, but created separate services
        // Solution: OrderService now calls ProductService for every order
        
        public async Task<Order> GetOrderAsync(string id)
        {
            var order = await _orderRepo.GetAsync(id);
            
            // N+1 problem across services!
            foreach (var line in order.Lines)
            {
                var product = await _productClient.GetAsync(line.ProductId);
                line.ProductName = product.Name;
            }
            
            // Slow! Fragile!
        }
    }
    
    // Month 6: Redesign required
    public class Month6
    {
        // Realized: Order and Product should be same service
        // Cost: 3 months wasted
        // - Merging services
        // - Refactoring APIs
        // - Updating all clients
        // - Fixing broken contracts
        
        // If started as monolith: 1 week to refactor
    }
    
    // Lesson: Don't decompose until domain is understood!
}
```

### Anti-Pattern: Distributed Monolith

```csharp
// Worst of both worlds

public class DistributedMonolithSymptoms
{
    // Symptom 1: All services deploy together
    public class CoupledDeployments
    {
        // Must deploy in specific order:
        // 1. Deploy UserService first
        // 2. Then OrderService (depends on UserService changes)
        // 3. Then PaymentService (depends on OrderService changes)
        // 4. Then ShippingService (depends on PaymentService changes)
        
        // If any step fails, rollback everything
        // This is a distributed monolith!
    }
    
    // Symptom 2: Shared database
    public class SharedDatabase
    {
        // All services read/write same tables
        // - Cannot change schema without coordinating all services
        // - No service autonomy
        // - Just a monolith split into processes
    }
    
    // Symptom 3: Synchronous coupling chains
    public class CouplingChains
    {
        // OrderService → ProductService → PricingService → PromotionService
        // 4 services in a chain, all must be up
        
        // If PromotionService is down:
        // - PricingService fails
        // - ProductService fails
        // - OrderService fails
        // - Entire order flow broken
        
        // Availability: 99.9% × 99.9% × 99.9% × 99.9% = 99.6%
        // Worse than monolith!
    }
    
    // How to fix:
    // - Break synchronous chains (use async events)
    // - Separate databases
    // - Make services truly independent
    // - Or... consider going back to monolith!
}
```

## Decision Framework Revisited

### The Microservices Decision Tree

```csharp
public class MicroservicesDecisionTree
{
    public string DetermineArchitecture(ProjectContext context)
    {
        // Question 1: Is this a new project?
        if (context.IsNewProject)
        {
            // Start with modular monolith
            return "Modular Monolith";
        }
        
        // Question 2: Team size?
        if (context.TeamSize < 20)
        {
            // Too small for microservices overhead
            return "Modular Monolith";
        }
        
        // Question 3: Domain boundaries clear?
        if (!context.HasClearBoundaries)
        {
            // Will create wrong boundaries
            return "Modular Monolith - discover boundaries first";
        }
        
        // Question 4: DevOps maturity?
        if (!context.HasCICD || !context.HasMonitoring || !context.HasContainers)
        {
            // Not ready for operational complexity
            return "Build DevOps capabilities first, keep monolith";
        }
        
        // Question 5: Performance/scaling problems?
        if (!context.HasScalingProblems && !context.HasTeamBottlenecks)
        {
            // No pain points to solve
            return "Monolith is working, don't fix what isn't broken";
        }
        
        // Question 6: Leadership support?
        if (!context.HasExecutiveBuyIn)
        {
            // Migration takes time and resources
            return "Build business case first";
        }
        
        // All conditions met: Microservices appropriate
        return "Microservices - but migrate gradually!";
    }
}
```

### ROI Calculation

```csharp
// Calculate return on investment

public class MicroservicesROI
{
    public class Costs
    {
        // Infrastructure costs
        public decimal InfrastructureCost = 50_000; // per year
        // - Container orchestration
        // - Service mesh
        // - API gateway
        // - Monitoring/observability tools
        
        // Staffing costs
        public decimal StaffingCost = 400_000; // per year
        // - 2 platform engineers @ $150k
        // - 1 SRE @ $160k
        // Overhead: $400k/year
        
        // Migration costs
        public decimal MigrationCost = 500_000; // one-time
        // - 6 months of development
        // - Training
        // - Tooling setup
        
        // Ongoing development overhead
        public decimal DevelopmentOverhead = 0.20m; // 20% slower
        // Features take longer due to distributed complexity
        
        public decimal TotalFirstYearCost => 
            InfrastructureCost + StaffingCost + MigrationCost;
    }
    
    public class Benefits
    {
        // Team scaling benefits
        public decimal TeamScalingBenefit = 300_000; // per year
        // - 50 developers can work without conflicts
        // - Deployment velocity increases
        // - 30% productivity gain = $300k value
        
        // Infrastructure cost savings
        public decimal InfrastructureSavings = 100_000; // per year
        // - Independent scaling saves resources
        // - At large scale, 20% savings = $100k
        
        // Faster time to market
        public decimal TimeToMarketValue = 200_000; // per year
        // - Features ship 2x faster
        // - Competitive advantage
        // - Estimated value: $200k
        
        public decimal TotalAnnualBenefit => 
            TeamScalingBenefit + InfrastructureSavings + TimeToMarketValue;
    }
    
    public bool IsWorthIt()
    {
        var costs = new Costs();
        var benefits = new Benefits();
        
        // Year 1: High cost (migration)
        var year1Net = benefits.TotalAnnualBenefit - costs.TotalFirstYearCost;
        // = $600k - $950k = -$350k (loss)
        
        // Year 2+: Ongoing
        var year2Net = benefits.TotalAnnualBenefit - 
            (costs.InfrastructureCost + costs.StaffingCost);
        // = $600k - $450k = $150k (profit)
        
        // Break even: ~2.3 years
        
        // Worth it if:
        // - Long-term project (3+ years)
        // - Benefits compound (more teams, more scale)
        
        return year2Net > 0;
    }
}
```

## The Middle Path: Modular Monolith Patterns

### Module Communication Patterns

```csharp
// Best practices for modular monoliths

// Pattern 1: In-process event bus
public class InProcessEventBus
{
    private readonly ConcurrentDictionary<Type, List<Delegate>> _handlers = new();
    
    public void Subscribe<TEvent>(Func<TEvent, Task> handler)
    {
        var eventType = typeof(TEvent);
        var handlers = _handlers.GetOrAdd(eventType, _ => new List<Delegate>());
        handlers.Add(handler);
    }
    
    public async Task PublishAsync<TEvent>(TEvent @event)
    {
        var eventType = typeof(TEvent);
        if (_handlers.TryGetValue(eventType, out var handlers))
        {
            foreach (var handler in handlers.Cast<Func<TEvent, Task>>())
            {
                await handler(@event);
            }
        }
    }
}

// Orders module publishes events
public class OrderModule
{
    public async Task CreateOrderAsync(Order order)
    {
        await _repository.SaveAsync(order);
        
        // Other modules subscribe (loose coupling)
        await _eventBus.PublishAsync(new OrderCreatedEvent
        {
            OrderId = order.Id,
            CustomerId = order.CustomerId
        });
    }
}

// Inventory module subscribes
public class InventoryModule
{
    public void Initialize()
    {
        _eventBus.Subscribe<OrderCreatedEvent>(HandleOrderCreatedAsync);
    }
    
    private async Task HandleOrderCreatedAsync(OrderCreatedEvent evt)
    {
        await ReserveInventoryAsync(evt.Items);
    }
}
```

### Extract to Service Pattern

```csharp
// When to extract from modular monolith

public class ExtractionDecision
{
    public bool ShouldExtractModule(Module module)
    {
        // Extract if module has:
        
        // 1. Different scaling needs
        if (module.RequiresIndependentScaling)
            return true;
        
        // 2. Different technology requirements
        if (module.NeedsDifferentTechStack)
            return true;
        
        // 3. Independent team ownership
        if (module.HasDedicatedTeam && module.Team.WantsAutonomy)
            return true;
        
        // 4. High rate of change
        if (module.DeploysPerWeek > 10 && module.BlocksOtherTeams)
            return true;
        
        // 5. Compliance/security isolation
        if (module.RequiresIsolation)
            return true;
        
        // Otherwise: Keep in monolith!
        return false;
    }
}

// Extraction process
public class ModuleExtraction
{
    public async Task ExtractModuleAsync(string moduleName)
    {
        // Step 1: Create service with same interface
        await CreateServiceAsync(moduleName);
        
        // Step 2: Dual-write pattern
        await EnableDualWrites(moduleName);
        // Both module and service receive writes
        
        // Step 3: Validate service behavior
        await CompareOutputs(moduleName);
        // Ensure service produces same results
        
        // Step 4: Switch reads to service
        await SwitchReadsToService(moduleName);
        
        // Step 5: Stop writes to module
        await DisableModuleWrites(moduleName);
        
        // Step 6: Remove module from monolith
        await RemoveModule(moduleName);
    }
}
```

## Key Takeaways

- Monoliths and microservices both have legitimate use cases
- Start with a monolith (preferably modular) for most projects
- Microservices make sense for large teams with clear domain boundaries
- Modular monoliths provide good boundaries without distributed complexity
- Strangler Fig pattern enables gradual, low-risk migration
- Distributed monoliths have the worst of both worlds
- Technology should serve business needs, not vice versa
- Most successful microservices systems started as monoliths
- Don't decompose until you understand the domain
- Team size and DevOps maturity are key factors
