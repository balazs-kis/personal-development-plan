## Introduction

The **Database per Service pattern** is fundamental to microservices architecture. It states that each microservice should have its own private data store that no other service can access directly. This ensures loose coupling and enables services to evolve independently. However, it introduces challenges around data consistency and cross-service queries that we'll address in this lesson.

## Key Concepts

### The Pattern

**Definition**: Each microservice's persistent data is private to that service and accessible only via its API.

```
❌ ANTI-PATTERN: Shared Database
┌────────────┐  ┌────────────┐  ┌────────────┐
│ Service A  │  │ Service B  │  │ Service C  │
└─────┬──────┘  └─────┬──────┘  └─────┬──────┘
      │               │               │
      └───────────────┼───────────────┘
                      ▼
               ┌──────────────┐
               │    Shared    │
               │   Database   │
               └──────────────┘

✅ CORRECT: Database per Service
┌────────────┐  ┌────────────┐  ┌────────────┐
│ Service A  │  │ Service B  │  │ Service C  │
└─────┬──────┘  └─────┬──────┘  └─────┬──────┘
      │               │               │
  ┌───▼───┐       ┌───▼───┐       ┌───▼───┐
  │ DB A  │       │ DB B  │       │ DB C  │
  └───────┘       └───────┘       └───────┘
```

### Benefits

✅ **Loose Coupling**: Services don't depend on others' schemas  
✅ **Independent Evolution**: Change schema without coordinating  
✅ **Technology Choice**: Use different databases for different needs  
✅ **Independent Scaling**: Scale databases based on service needs  
✅ **Clear Ownership**: One team owns schema and data  
✅ **Fault Isolation**: Database failures don't affect all services

### Challenges

⚠️ **No joins**: Can't join across databases  
⚠️ **Distributed transactions**: ACID doesn't work across services  
⚠️ **Data duplication**: Same data may exist in multiple services  
⚠️ **Referential integrity**: No foreign key constraints across services  
⚠️ **Reporting complexity**: Aggregating data from multiple sources

## Polyglot Persistence

Choose the right database for each service's needs:

```csharp
// Order Service - needs ACID transactions
services.AddDbContext<OrderContext>(options =>
    options.UseNpgsql(connectionString));

// Product Catalog - needs full-text search

{
    options.Configuration = redisConnectionString;
```

## Data Access Patterns

### Pattern 1: API Composition

Query multiple services and combine results:

```csharp
[HttpGet("orders/{id}/details")]
public async Task<OrderDetailsDto> GetOrderDetails(int id)
{
    // Parallel calls
    var orderTask = _orderService.GetOrderAsync(id);
    var customerTask = _customerService.GetCustomerAsync(order.CustomerId);
    var productsTask = _productService.GetProductsAsync(order.ProductIds);

    await Task.WhenAll(orderTask, customerTask, productsTask);

    return new OrderDetailsDto
    {
        Order = await orderTask,
        Customer = await customerTask,
        Products = await productsTask
    };
}
```

**Pros**: Simple, no data duplication  
**Cons**: Multiple network calls, potential inconsistency, higher latency

### Pattern 2: CQRS with Read Model

Maintain denormalized read model:

```csharp
// Write side: Individual services
Order Service → Orders DB
Product Service → Products DB
Customer Service → Customers DB

// Events published
↓
Message Bus
↓
// Read side: Denormalized view
Read Model Builder → Order Details DB (denormalized)

// Query
[HttpGet("orders/{id}/details")]
public async Task<OrderDetailsDto> GetOrderDetails(int id)
{
    // Single query to denormalized database
    return await _readModel.GetOrderDetailsAsync(id);
}
```

**Pros**: Fast queries, single database call  
**Cons**: Eventual consistency, additional complexity

### Pattern 3: Event-Carried State Transfer

Include related data in events:

```csharp
public class OrderPlacedEvent
{
    public Guid OrderId { get; set; }
    
    // Include customer data
    public Guid CustomerId { get; set; }
    public string CustomerName { get; set; }
    public string CustomerEmail { get; set; }
    
    // Include product data
    public List<ProductSnapshot> Products { get; set; }
    public decimal TotalAmount { get; set; }
}
```

**Pros**: Self-contained events, no additional queries  
**Cons**: Larger events, data duplication, consistency of snapshot data

## Handling Foreign Keys

**Traditional (Monolith)**:
```sql
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    CustomerId INT FOREIGN KEY REFERENCES Customers(CustomerId),
    ProductId INT FOREIGN KEY REFERENCES Products(ProductId)
);
```

**Microservices (No FK)**:
```csharp
// Order Service database
public class Order
{
    public int OrderId { get; set; }
    public Guid CustomerId { get; set; }  // Just the ID, no FK
    public List<OrderLine> Lines { get; set; }
}

public class OrderLine
{
    public int ProductId { get; set; }  // Just the ID, no FK
    public int Quantity { get; set; }
    public decimal Price { get; set; }  // Snapshot at order time
}

// Validation via API
public async Task<ValidationResult> ValidateOrder(CreateOrderCommand cmd)
{
    // Check customer exists
    var customerExists = await _customerService.ExistsAsync(cmd.CustomerId);
    if (!customerExists)
        return ValidationResult.Failure("Customer not found");

    // Check products exist
    foreach (var line in cmd.Lines)
    {
        var productExists = await _productService.ExistsAsync(line.ProductId);
        if (!productExists)
            return ValidationResult.Failure($"Product {line.ProductId} not found");
    }

    return ValidationResult.Success();
}
```

## Database Schema Design Across Services

When splitting a monolith, you must redesign schemas to fit service boundaries.

### Before: Monolith Schema

```sql
-- All tables in one database
CREATE TABLE Customers (
    CustomerId INT PRIMARY KEY,
    Name VARCHAR(100),
    Email VARCHAR(100),
    MembershipTier VARCHAR(20)
);

CREATE TABLE Products (
    ProductId INT PRIMARY KEY,
    Name VARCHAR(200),
    Price DECIMAL(10,2),
    StockQuantity INT,
    CategoryId INT FOREIGN KEY REFERENCES Categories(CategoryId)
);

CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    CustomerId INT FOREIGN KEY REFERENCES Customers(CustomerId),
    OrderDate DATETIME,
    Status VARCHAR(20),
    Total DECIMAL(10,2)
);

CREATE TABLE OrderLines (
    OrderLineId INT PRIMARY KEY,
    OrderId INT FOREIGN KEY REFERENCES Orders(OrderId),
    ProductId INT FOREIGN KEY REFERENCES Products(ProductId),
    Quantity INT,
    Price DECIMAL(10,2)
);
```

### After: Distributed Across Services

**Order Service Database:**
```sql
-- No foreign keys to other services
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    CustomerId GUID,  -- Reference only, no FK
    OrderDate DATETIME,
    Status VARCHAR(20),
    Total DECIMAL(10,2),
    
    -- Snapshot data from other services
    CustomerName VARCHAR(100),
    CustomerEmail VARCHAR(100)
);

CREATE TABLE OrderLines (
    OrderLineId INT PRIMARY KEY,
    OrderId INT FOREIGN KEY REFERENCES Orders(OrderId),
    ProductId INT,  -- Reference only, no FK
    Quantity INT,
    Price DECIMAL(10,2),  -- Price at order time
    
    -- Snapshot
    ProductName VARCHAR(200)
);
```

**Product Service Database:**
```sql
CREATE TABLE Products (
    ProductId INT PRIMARY KEY,
    Name VARCHAR(200),
    Description TEXT,
    Price DECIMAL(10,2),
    StockQuantity INT,
    CategoryId INT FOREIGN KEY REFERENCES Categories(CategoryId)
);

-- Category belongs to Product service
CREATE TABLE Categories (
    CategoryId INT PRIMARY KEY,
    Name VARCHAR(100)
);
```

**Customer Service Database:**
```sql
CREATE TABLE Customers (
    CustomerId GUID PRIMARY KEY,
    Name VARCHAR(100),
    Email VARCHAR(100),
    MembershipTier VARCHAR(20),
    
    -- Aggregates from other services (cached)
    TotalOrders INT,
    LifetimeValue DECIMAL(10,2)
);
```

## Data Synchronization Patterns

### Pattern: Cache Aside

Service maintains local cache of data from other services:

```csharp
public class OrderService
{
    private readonly IDistributedCache _cache;
    private readonly ICustomerServiceClient _customerClient;

    public async Task<CustomerInfo> GetCustomerAsync(Guid customerId)
    {
        // Try cache first
        var cached = await _cache.GetStringAsync($"customer:{customerId}");
        if (cached != null)
            return JsonSerializer.Deserialize<CustomerInfo>(cached);

        // Fetch from Customer Service
        var customer = await _customerClient.GetCustomerAsync(customerId);
        
        // Cache with TTL
        await _cache.SetStringAsync(
            $"customer:{customerId}",
            JsonSerializer.Serialize(customer),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            });

        return customer;
    }
}
```

### Pattern: Change Data Capture (CDC)

Replicate data changes to other services:

```csharp
// Product Service publishes price changes
public class ProductService
{
    public async Task UpdatePriceAsync(int productId, decimal newPrice)
    {
        var product = await _repository.GetAsync(productId);
        product.Price = newPrice;
        await _repository.SaveAsync(product);

        // Publish change event
        await _eventBus.PublishAsync(new ProductPriceChangedEvent
        {
            ProductId = product.Id,
            NewPrice = newPrice,
            OldPrice = product.Price,
            Timestamp = DateTime.UtcNow
        });
    }
}

// Order Service maintains product price cache
public class ProductPriceEventHandler : IEventHandler<ProductPriceChangedEvent>
{
    public async Task HandleAsync(ProductPriceChangedEvent evt)
    {
        // Update local cache
        await _cache.SetStringAsync(
            $"product-price:{evt.ProductId}",
            evt.NewPrice.ToString());
    }
}
```

## Handling Distributed Queries

### Anti-Pattern: Database Joins Across Services

```csharp
❌ WRONG: Can't do this!
SELECT o.OrderId, o.Total, c.Name AS CustomerName, p.Name AS ProductName
FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId  -- Different service!
JOIN OrderLines ol ON o.OrderId = ol.OrderId
JOIN Products p ON ol.ProductId = p.ProductId    -- Different service!
WHERE o.OrderDate > '2024-01-01';
```

### Solution 1: API Composition (Immediate Consistency)

```csharp
[HttpGet("orders/{id}/full-details")]
public async Task<OrderFullDetailsDto> GetOrderFullDetails(int orderId)
{
    // Step 1: Get order from Order Service
    var order = await _orderRepository.GetAsync(orderId);
    if (order == null) return null;

    // Step 2: Get customer from Customer Service (parallel)
    var customerTask = _customerClient.GetAsync(order.CustomerId);
    
    // Step 3: Get products from Product Service (parallel)
    var productIds = order.Lines.Select(l => l.ProductId).ToList();
    var productsTask = _productClient.GetByIdsAsync(productIds);

    await Task.WhenAll(customerTask, productsTask);

    // Step 4: Compose result
    return new OrderFullDetailsDto
    {
        OrderId = order.OrderId,
        OrderDate = order.OrderDate,
        Total = order.Total,
        Customer = new CustomerDto
        {
            Name = customerTask.Result.Name,
            Email = customerTask.Result.Email
        },
        Lines = order.Lines.Select(line => new OrderLineDto
        {
            ProductName = productsTask.Result
                .First(p => p.Id == line.ProductId).Name,
            Quantity = line.Quantity,
            Price = line.Price
        }).ToList()
    };
}
```

**Pros:**
- ✅ Always up-to-date
- ✅ No data duplication
- ✅ Simple logic

**Cons:**
- ❌ Multiple network calls (latency)
- ❌ Partial failure handling needed
- ❌ Performance impact at scale

### Solution 2: CQRS with Denormalized Read Model (Eventual Consistency)

```csharp
// Read model database
public class OrderDetailsReadModel
{
    public int OrderId { get; set; }
    public DateTime OrderDate { get; set; }
    public decimal Total { get; set; }
    
    // Denormalized customer data
    public Guid CustomerId { get; set; }
    public string CustomerName { get; set; }
    public string CustomerEmail { get; set; }
    
    // Denormalized product data
    public List<OrderLineReadModel> Lines { get; set; }
}

public class OrderLineReadModel
{
    public int ProductId { get; set; }
    public string ProductName { get; set; }
    public int Quantity { get; set; }
    public decimal Price { get; set; }
}

// Query handler - single database call
[HttpGet("orders/{id}/details")]
public async Task<OrderDetailsReadModel> GetOrderDetails(int orderId)
{
    return await _readModelRepository.GetOrderDetailsAsync(orderId);
}

// Keep read model updated via events
public class OrderDetailsReadModelUpdater :
    IEventHandler<OrderPlacedEvent>,
    IEventHandler<CustomerUpdatedEvent>,
    IEventHandler<ProductUpdatedEvent>
{
    public async Task HandleAsync(OrderPlacedEvent evt)
    {
        var readModel = new OrderDetailsReadModel
        {
            OrderId = evt.OrderId,
            OrderDate = evt.OrderDate,
            Total = evt.Total,
            CustomerId = evt.CustomerId,
            CustomerName = evt.CustomerName,
            CustomerEmail = evt.CustomerEmail,
            Lines = evt.Lines.Select(l => new OrderLineReadModel
            {
                ProductId = l.ProductId,
                ProductName = l.ProductName,
                Quantity = l.Quantity,
                Price = l.Price
            }).ToList()
        };
        
        await _readModelRepository.SaveAsync(readModel);
    }

    public async Task HandleAsync(CustomerUpdatedEvent evt)
    {
        // Update all orders for this customer
        var orders = await _readModelRepository
            .GetOrdersByCustomerAsync(evt.CustomerId);
        
        foreach (var order in orders)
        {
            order.CustomerName = evt.Name;
            order.CustomerEmail = evt.Email;
            await _readModelRepository.SaveAsync(order);
        }
    }

    public async Task HandleAsync(ProductUpdatedEvent evt)
    {
        // Only update future orders, past orders keep historical data
        // (business decision)
    }
}
```

**Pros:**
- ✅ Fast queries (single database call)
- ✅ No cross-service calls
- ✅ Scales independently

**Cons:**
- ❌ Eventual consistency
- ❌ Data duplication
- ❌ Complexity in keeping data synced

## Data Migration Strategies

### Migrating from Shared Database to Database per Service

**Step 1: Identify Data Ownership**

```
Shared Database:
┌─────────────────────────────────────┐
│ Customers, Orders, Products, etc.   │
└─────────────────────────────────────┘

After Analysis:
Customer Service owns: Customers
Order Service owns: Orders, OrderLines
Product Service owns: Products, Categories
```

**Step 2: Duplicate Schema (Both Old and New)**

```csharp
// Phase 1: Dual writes
public class OrderService
{
    public async Task CreateOrderAsync(CreateOrderCommand cmd)
    {
        // Write to OLD shared database
        await _legacyDbContext.Orders.AddAsync(order);
        await _legacyDbContext.SaveChangesAsync();

        // Write to NEW service database
        await _newDbContext.Orders.AddAsync(order);
        await _newDbContext.SaveChangesAsync();
    }
}
```

**Step 3: Migrate Historical Data**

```csharp
// Data migration script
public class OrderDataMigration
{
    public async Task MigrateAsync()
    {
        var pageSize = 1000;
        var page = 0;

        while (true)
        {
            var orders = await _legacyDb.Orders
                .OrderBy(o => o.OrderId)
                .Skip(page * pageSize)
                .Take(pageSize)
                .ToListAsync();

            if (!orders.Any()) break;

            foreach (var order in orders)
            {
                await _newDb.Orders.AddAsync(order);
            }

            await _newDb.SaveChangesAsync();
            page++;
            
            _logger.LogInformation("Migrated page {Page}, total {Total} orders",
                page, page * pageSize);
        }
    }
}
```

**Step 4: Switch Reads to New Database**

```csharp
// Feature flag to control cutover
public class OrderService
{
    public async Task<Order> GetOrderAsync(int orderId)
    {
        if (_featureFlags.IsEnabled("use_new_order_db"))
        {
            return await _newDbContext.Orders.FindAsync(orderId);
        }
        else
        {
            return await _legacyDbContext.Orders.FindAsync(orderId);
        }
    }
}
```

**Step 5: Stop Dual Writes, Remove Old Database Access**

## Common Challenges and Solutions

### Challenge 1: Cross-Service Transactions

**Problem:** Need to update data in multiple services atomically.

**Solution:** Use Saga pattern (covered in next lesson).

```csharp
// Instead of:
using var transaction = new DistributedTransaction();
await _orderService.CreateOrderAsync(order);
await _inventoryService.ReserveStockAsync(items);
await _paymentService.ChargeAsync(payment);
await transaction.CommitAsync();

// Use Saga:
var saga = new OrderSaga(order);
await _sagaOrchestrator.ExecuteAsync(saga);
```

### Challenge 2: Referential Integrity

**Problem:** Can't use foreign keys across databases.

**Solution:** Validate at application layer + eventual consistency checks.

```csharp
public class OrderValidator
{
    public async Task<ValidationResult> ValidateAsync(CreateOrderCommand cmd)
    {
        var errors = new List<string>();

        // Check customer exists (via API)
        if (!await _customerService.ExistsAsync(cmd.CustomerId))
            errors.Add("Customer not found");

        // Check products exist
        foreach (var item in cmd.Items)
        {
            if (!await _productService.ExistsAsync(item.ProductId))
                errors.Add($"Product {item.ProductId} not found");
        }

        // Background job: periodic consistency check
        // (Fix orphaned records if services deleted data)
        
        return errors.Any() 
            ? ValidationResult.Failure(errors) 
            : ValidationResult.Success();
    }
}

// Background consistency checker
public class OrphanedOrderChecker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            var orders = await _db.Orders
                .Where(o => o.CreatedDate > DateTime.UtcNow.AddHours(-1))
                .ToListAsync(ct);

            foreach (var order in orders)
            {
                // Check if customer still exists
                if (!await _customerService.ExistsAsync(order.CustomerId))
                {
                    _logger.LogWarning(
                        "Order {OrderId} has invalid customer {CustomerId}",
                        order.OrderId, order.CustomerId);
                    
                    // Take corrective action
                    await HandleOrphanedOrder(order);
                }
            }

            await Task.Delay(TimeSpan.FromMinutes(15), ct);
        }
    }
}
```

### Challenge 3: Reporting and Analytics

**Problem:** Need to query data across multiple services for reports.

**Solution:** Use dedicated reporting database with ETL.

```csharp
// Reporting service subscribes to events
public class ReportingEventHandler :
    IEventHandler<OrderPlacedEvent>,
    IEventHandler<OrderShippedEvent>,
    IEventHandler<CustomerRegisteredEvent>
{
    public async Task HandleAsync(OrderPlacedEvent evt)
    {
        // Insert into reporting database (denormalized)
        await _reportingDb.OrderFacts.AddAsync(new OrderFact
        {
            OrderId = evt.OrderId,
            OrderDate = evt.OrderDate,
            CustomerId = evt.CustomerId,
            CustomerName = evt.CustomerName,
            Total = evt.Total,
            Status = "Placed"
        });
        await _reportingDb.SaveChangesAsync();
    }

    // Similar handlers for other events...
}

// Run complex reports
[HttpGet("reports/sales-by-month")]
public async Task<SalesReport> GetSalesByMonth([FromQuery] int year)
{
    return await _reportingDb.OrderFacts
        .Where(o => o.OrderDate.Year == year)
        .GroupBy(o => o.OrderDate.Month)
        .Select(g => new MonthlySales
        {
            Month = g.Key,
            TotalOrders = g.Count(),
            TotalRevenue = g.Sum(o => o.Total)
        })
        .ToListAsync();
}
```

## Database Technology Selection Guide

| Service | Typical Choice | Reason |
|---------|----------------|--------|
| **Order Management** | PostgreSQL, SQL Server | ACID transactions, relations, complex queries |
| **Product Catalog** | Elasticsearch, MongoDB | Full-text search, flexible schema |
| **Shopping Cart** | Redis | Fast key-value, TTL support, session data |
| **User Sessions** | Redis, Memcached | Fast access, automatic expiration |
| **Analytics/Events** | MongoDB, Cassandra | Time-series, high write volume |
| **Audit Logs** | Event Store, PostgreSQL | Append-only, immutability |
| **Recommendations** | Neo4j | Graph relationships |
| **Search** | Elasticsearch, Solr | Full-text, faceted search |
| **Cache** | Redis, Memcached | In-memory, fast access |
| **Files/Blobs** | S3, Azure Blob Storage | Object storage |

## Self-Check Questions

1. **Why can't services share a database?**
   - Creates coupling, prevents independent deployment and scaling

2. **How do you enforce referential integrity across services?**
   - Application-level validation via API calls, eventual consistency

3. **What is polyglot persistence?**
   - Using different database technologies for different services based on their needs
   - Example: PostgreSQL for orders, Elasticsearch for search, Redis for caching

4. **When is data duplication acceptable?**
   - When it improves performance, reduces coupling, or provides service autonomy
   - Trade-off: storage cost vs. operational complexity

5. **How do you ensure a customer exists before creating an order?**
   - Call Customer Service API to validate
   - Use circuit breaker to handle Customer Service failures
   - Consider eventual consistency checks

## Real-World Considerations

### Performance Implications

**Single Database (Monolith):**
```sql
-- Fast: single query with joins
SELECT o.*, c.Name, p.Name
FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId
JOIN Products p ON o.ProductId = p.ProductId
WHERE o.OrderId = 123;
-- Execution time: ~5ms
```

**Database Per Service:**
```csharp
// Slower: multiple network calls
var order = await _orderService.GetOrderAsync(123);      // 5ms + 10ms network
var customer = await _customerService.GetAsync(order.CustomerId); // 5ms + 10ms network
var product = await _productService.GetAsync(order.ProductId);    // 5ms + 10ms network
// Total: ~45ms (9x slower)
```

**Mitigation strategies:**
1. Denormalize read models (CQRS)
2. Cache frequently accessed data
3. Batch API calls when possible
4. Use async/parallel requests

### Cost Considerations

**Database costs multiply:**
- 3 services × $200/month = $600/month
- Plus: backup costs, monitoring, maintenance

**Is it worth it?**
- For small apps: probably not
- For teams with different scaling needs: yes
- For independent deployment: yes

### When NOT to Use Database Per Service

❌ **Small applications:** Overhead > benefit  
❌ **Same team, same deployment:** Shared database is simpler  
❌ **Tight coupling needed:** Some domains naturally share data  
❌ **Complex reporting only:** Use read replicas instead  

✅ **Different teams:** Clear ownership  
✅ **Different scaling needs:** Scale databases independently  
✅ **Independent deployment:** No coordination needed  
✅ **Polyglot persistence:** Different tech per service

## Migration Checklist

Planning to split a shared database? Follow this checklist:

- [ ] **Identify service boundaries** (Domain-Driven Design)
- [ ] **Map data ownership** (which service owns what)
- [ ] **Document cross-service relationships** (foreign keys to break)
- [ ] **Choose database technologies** per service
- [ ] **Design API contracts** for cross-service data access
- [ ] **Implement dual writes** (to old and new databases)
- [ ] **Migrate historical data** (with verification)
- [ ] **Update read paths** to new databases
- [ ] **Test thoroughly** (integration, contract, performance)
- [ ] **Monitor performance** (compare to baseline)
- [ ] **Remove old database access** (clean up)

## Key Takeaways

✅ **Each service owns its data** - no shared databases

✅ **Polyglot persistence** - choose the right database for each service

✅ **No foreign keys** across services - use IDs and API validation

✅ **Accept data duplication** when it reduces coupling

✅ **API composition, CQRS, or event-carried state** for cross-service data
