# Lesson 2: Building a Debt Inventory and Tracking System

## Learning Objectives

By the end of this lesson, you will be able to:
- Build a systematic inventory of technical debt across systems
- Measure technical debt using quantitative metrics
- Track debt accumulation and resolution over time
- Use tools and dashboards to monitor debt
- Distinguish technical debt from defects and feature requests

---

## Introduction

You can't manage what you don't measure. Building a technical debt inventory creates visibility into what debt exists, where it's located, and how much it's costing you. Tracking debt over time reveals whether you're winning or losing the battle against accumulation.

A good tracking system makes debt visible to both engineers and stakeholders, enables data-driven prioritization, and demonstrates progress as debt is paid down.

## Key Concepts Summary

### Why Build a Debt Inventory?

**Visibility:** You can't fix what you can't see. An inventory makes debt concrete and measurable.

**Prioritization:** With a complete list, you can prioritize based on impact rather than "whoever yells loudest."

**Progress Tracking:** An inventory lets you demonstrate that debt is being paid down over time.

**Stakeholder Communication:** Numbers and trends speak louder than anecdotes.

**Prevention:** Tracking new debt accumulation reveals where your processes are failing.

### Building the Initial Inventory

#### Step 1: Systematic Discovery

**Code Reviews and Audits:**
- Review critical paths and high-traffic code
- Identify code smells, complexity hotspots, and anti-patterns
- Document areas that consistently cause bugs or slow development

**Team Surveys:**
- Ask engineers: "What part of the codebase frustrates you most?"
- "What change takes longer than it should?"
- "What scares you to touch?"

**System Analysis:**
- Use automated tools (see below) to identify complexity, duplication, coverage gaps
- Review architecture diagrams for circular dependencies and tight coupling
- Check for outdated dependencies and unsupported versions

**Pain Point Tracking:**
- Where do bugs cluster?
- Which features take unexpectedly long to implement?
- What causes production incidents?

#### Step 2: Classification

For each debt item identified, document:

**What:** Description of the debt
- "User authentication logic duplicated across 8 controllers"

**Where:** Location in codebase
- File paths, services, modules

**Type:** What kind of debt is it?
- Code, Architecture, Test, Documentation, etc.

**Impact:** What does this debt cost?
- Slows development by X%
- Causes Y bugs per month
- Blocks feature Z from being implemented

**Source:** How did it happen?
- Business pressure, lack of knowledge, changing requirements, etc.

**Quadrant:** Fowler's classification
- Reckless/Prudent, Deliberate/Inadvertent

#### Step 3: Initial Estimate

For each debt item, estimate:

**Remediation Cost:** How long to fix?
- Hours or story points
- Required expertise

**Interest Cost:** What's the ongoing cost of NOT fixing it?
- Time lost per week/month
- Bugs caused
- Features blocked

### Key Metrics to Track

#### 1. Technical Debt Ratio (TDR)

**Formula:**
```
TDR = (Remediation Cost / Development Cost) × 100%
```

**Target:** < 5%

**What it means:**
- 5% = For every $100 spent on development, $5 of debt is accumulated
- Tools like SonarQube calculate this automatically

**Example:**
- Total development cost: $1M
- Estimated cost to fix all debt: $50K
- TDR = 5%

#### 2. Code Quality Metrics

**Cyclomatic Complexity:**
- Measures the number of independent paths through code
- **Target:** Average < 10
- High complexity (>15) correlates with bugs and maintenance difficulty

**Code Duplication:**
- Percentage of code that's duplicated
- **Target:** < 3%
- Duplication increases maintenance burden linearly

**Code Coverage:**
- Percentage of code executed during automated tests
- **Target:** > 80%
- Low coverage indicates test debt

**Code Smells:**
- Long methods, large classes, feature envy, etc.
- Track count and severity over time

#### 3. DORA Metrics (Delivery Performance)

These four research-backed metrics show how technical debt impacts delivery:

**Deployment Frequency:**
- How often you deploy to production
- **Elite:** Multiple times per day
- **Struggling:** Monthly or less
- High debt slows deployments

**Lead Time for Changes:**
- Time from commit to production
- **Elite:** < 1 hour
- **Struggling:** > 1 month
- Debt increases change lead time

**Change Failure Rate:**
- Percentage of deployments causing incidents
- **Elite:** < 15%
- **Struggling:** > 45%
- High debt increases failure rates

**Mean Time to Recovery (MTTR):**
- Time to recover from production failures
- **Elite:** < 1 hour
- **Struggling:** > 1 week
- Debt makes recovery harder

#### 4. Inventory Metrics

**Total Debt Items:** Count of identified debt

**Debt by Type:** Distribution across architecture, code, test, etc.

**Debt by Severity:** Critical, high, medium, low

**Debt Trend:** Is debt growing or shrinking?
- New debt added per month
- Debt resolved per month
- Net change

**Age of Debt:** How long has debt existed?
- Older debt is often more expensive to fix

### Tools for Tracking Debt

#### Automated Analysis Tools

**SonarQube / SonarCloud:**
- Comprehensive code quality analysis
- Calculates Technical Debt Ratio automatically
- Tracks code smells, bugs, vulnerabilities
- Provides dashboards and trends

**.NET Code Analyzers:**
- Built into Visual Studio
- Roslyn analyzers for code quality
- Code metrics (complexity, maintainability index)
- Custom rules and thresholds

**CodeClimate / Codacy:**
- Automated code review
- Quality metrics and trends
- Integration with CI/CD

**ESLint / RuboCop / etc.:**
- Language-specific linters
- Enforce coding standards
- Detect common issues

#### Manual Tracking Systems

**Issue Tracker (Jira, GitHub Issues, etc.):**
- Label issues as "tech-debt"
- Track in separate backlog or board
- Estimate effort and impact

**Spreadsheets / Databases:**
- For teams without sophisticated tooling
- Track: Description, Location, Type, Impact, Estimate, Status

**Example Structure:**
```
ID | Description | Type | Impact | Effort | Interest/Month | Status | Assigned
1  | Auth duplication | Code | High | 3d | 2d | Open | -
2  | Missing API tests | Test | High | 5d | 1d | In Progress | Alex
3  | Legacy DB schema | Data | Medium | 20d | 4h | Planned | -
```

### Tracking Debt Over Time

**Weekly/Sprint Reviews:**
- How much debt was added?
- How much was resolved?
- Are we making progress?

**Quarterly Reports:**
- Debt trends (growing or shrinking?)
- Impact on velocity and quality
- Comparison to targets (TDR < 5%, coverage > 80%)

**Dashboards:**
- Real-time visibility into metrics
- Trend charts showing progress
- Alerts when metrics exceed thresholds

**Before/After Comparisons:**
- Show improvement after debt paydown
- Demonstrate impact: "Deployment time reduced from 45 min to 5 min"

### Distinguishing Debt from Defects and Features

**Technical Debt:**
- Makes future changes harder or more costly
- Doesn't necessarily cause current bugs
- Example: Duplicated code, poor architecture

**Defects/Bugs:**
- Current broken behavior
- Needs to be fixed regardless of architecture
- Example: Button doesn't work, data corruption

**Features:**
- New functionality requested
- Not about fixing existing code
- Example: Add OAuth2 support

**Key Distinction:** Debt is about code quality and maintainability, not current functionality.

Some items can be multiple categories:
- "Fix bug AND refactor the broken module" = Defect + Debt
- "Add tests for existing feature" = Debt (test debt)

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

Pick a system or codebase you have access to:

1. **Identify 10 Debt Items:** Use code review, team input, or automated tools
2. **Classify Each:** Type, impact, effort to fix, ongoing cost
3. **Calculate Simple TDR:**
   - Estimate total effort to fix all 10 items (in hours)
   - Estimate total development effort on this system in last 3 months
   - TDR = (Fix Effort / Development Effort) × 100%
4. **Create a Tracking System:** Set up a simple spreadsheet or issue tracker with your 10 items

This gives you hands-on experience with debt inventory building.
