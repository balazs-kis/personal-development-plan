# Lesson 3: Identifying System Components

## Learning Objectives

By the end of this lesson, you will be able to:
- Identify the core building blocks of distributed systems
- Map functional requirements to system components
- Create high-level architecture diagrams
- Understand when to use different component types

---

## Introduction

Once you understand requirements and have validated feasibility through capacity estimation, the next step is identifying the components that will make up your system. This lesson covers the standard building blocks you'll use in almost every design: load balancers, caches, databases, message queues, and more.

## Key Concepts Summary

### The Standard Component Toolkit

Every system is built from these fundamental building blocks:

#### 1. Client (Entry Point)
```
What: User interface or API consumer
Types:
- Web browser (HTML/CSS/JavaScript)
- Mobile app (iOS/Android)
- Desktop application
- Other services (API client)

Responsibilities:
- Render UI
- Capture user input
- Make API requests
- Handle responses
```

#### 2. Load Balancer (Traffic Distribution)
```
What: Distributes incoming requests across multiple servers
Why: Prevent single server overload, improve availability

Common Algorithms:
- Round Robin: Distribute requests evenly in sequence
- Least Connections: Send to server with fewest active connections
- IP Hash: Route same client to same server (session affinity)
- Weighted Round Robin: Distribute based on server capacity

Benefits:
- Horizontal scaling
- High availability (if one server fails, route to others)
- Zero-downtime deployments (take servers out of rotation)

Example:
Client → Load Balancer → [Server 1, Server 2, Server 3, ...]
```

#### 3. Application/API Servers (Business Logic)
```
What: Process business logic and handle requests
Responsibilities:
- Validate input
- Execute business logic
- Query databases
- Return responses

Best Practices:
- Keep stateless (no user session data stored)
- Scale horizontally (add more servers)
- Use connection pooling for databases
- Implement caching

Tech Examples:
- Node.js, ASP.NET Core, Spring Boot, Django, Flask
```

#### 4. Databases (Data Storage)
```
Two main types: SQL (Relational) and NoSQL

SQL Databases (Relational):
Examples: PostgreSQL, MySQL, SQL Server
Use When:
- Need ACID transactions
- Complex queries and joins
- Structured, relational data
- Strong consistency required

NoSQL Databases:
Types:
- Document Store (MongoDB, CouchDB): JSON-like documents
- Key-Value Store (Redis, DynamoDB): Simple key-value pairs
- Column-Family (Cassandra, HBase): Wide-column storage
- Graph (Neo4j, Amazon Neptune): Relationships and connections

Use When:
- Need horizontal scalability
- Flexible schema
- High write throughput
- Eventual consistency acceptable
```

#### 5. Cache (Fast Data Access)
```
What: In-memory data store for frequently accessed data
Why: Reduce database load, improve response time

Types:
- In-Memory Cache: Redis, Memcached
- CDN (Content Delivery Network): Cloudflare, Akamai
- Application-Level Cache: In-process cache (IMemoryCache)
- Database Query Cache: Built into DB engines

Common Patterns:
- Cache-Aside: App checks cache, loads from DB if miss
- Write-Through: Write to cache and DB simultaneously
- Write-Behind: Write to cache, async write to DB

What to Cache:
- User sessions
- API responses
- Database query results
- Static assets (images, CSS, JavaScript)
- Computed/aggregated data

Example:
Request → Check Cache → (Hit) Return Cached Data
                      → (Miss) Query Database → Store in Cache → Return Data
```

#### 6. Message Queue (Asynchronous Processing)
```
What: Middleware for async communication between services
Why: Decouple services, handle traffic spikes, reliable delivery

Popular Options:
- RabbitMQ: General-purpose message broker
- Apache Kafka: High-throughput event streaming
- AWS SQS: Managed queue service
- Azure Service Bus: Enterprise messaging

Use Cases:
- Background job processing
- Email/notification sending
- Image/video processing
- Order processing
- Event-driven architecture

Pattern:
Producer → Message Queue → Consumer(s)

Example:
User uploads photo → Queue photo processing job
                   → Worker resizes/optimizes photo
                   → Update database with processed photo URL
```

#### 7. API Gateway (Single Entry Point)
```
What: Single entry point for all client requests
Responsibilities:
- Routing requests to appropriate services
- Authentication and authorization
- Rate limiting and throttling
- Request/response transformation
- API versioning
- Logging and monitoring

Benefits:
- Centralized security
- Simplified client code
- Consistent API interface
- Monitoring and analytics

Example:
Client → API Gateway → [Auth Service, User Service, Order Service, ...]
```

#### 8. CDN (Content Delivery Network)
```
What: Distributed network of servers for static content
Why: Reduce latency by serving content from edge locations

What to Serve via CDN:
- Images, videos
- JavaScript, CSS files
- Fonts
- Static HTML pages

How It Works:
1. User requests image from CDN
2. CDN checks if content is cached at edge location
3. If cached, serve immediately
4. If not cached, fetch from origin server, cache, then serve

Benefits:
- Reduced latency (serve from geographically close location)
- Reduced origin server load
- Better user experience
```

### Mapping Requirements to Components

#### Example 1: URL Shortener

**Functional Requirements:**
- Generate short URLs
- Redirect short URLs to original URLs
- Track click analytics

**Component Mapping:**
```
Client (Web Browser)
    ↓
Load Balancer
    ↓
API Servers (Generate/Redirect)
    ↓
Cache (Redis) ← Frequently accessed URLs
    ↓
Database (PostgreSQL) ← URL mappings, analytics
```

**Why This Design:**
- Load Balancer: Handle high traffic
- Cache: 80% of redirects hit the same 20% of URLs
- Database: Persistent storage for URL mappings

#### Example 2: Social Media Feed

**Functional Requirements:**
- Post updates
- View personalized feed
- Like and comment
- Real-time notifications

**Component Mapping:**
```
Client (Mobile/Web)
    ↓
API Gateway
    ↓
Load Balancer
    ↓
+-- API Servers (Posts, Likes, Comments)
|       ↓
|   Cache (Redis) ← User feeds, hot posts
|       ↓
|   Database (PostgreSQL) ← User data, posts, relationships
|
+-- Message Queue (Kafka) ← Async events
        ↓
    Feed Generator Service
        ↓
    Notification Service
```

**Why This Design:**
- Message Queue: Async processing for feed updates
- Cache: Pre-computed feeds for fast retrieval
- Separate Services: Scale independently

#### Example 3: Video Streaming Platform

**Functional Requirements:**
- Upload videos
- Transcode to multiple resolutions
- Stream videos
- Search videos

**Component Mapping:**
```
Client (Web/Mobile)
    ↓
CDN ← Serve video content
    ↓
Load Balancer
    ↓
API Servers (Metadata, Search)
    ↓
+-- Object Storage (S3) ← Video files
|
+-- Message Queue (RabbitMQ) ← Transcode jobs
|       ↓
|   Transcode Workers
|
+-- Search Engine (Elasticsearch) ← Video metadata
|
+-- Database (PostgreSQL) ← User data, video metadata
```

**Why This Design:**
- CDN: Serve videos from edge locations (low latency)
- Object Storage: Cheap, durable storage for large files
- Message Queue: Async video processing
- Search Engine: Fast full-text search

### High-Level Architecture Diagram Guidelines

When drawing architecture diagrams:

#### 1. Start Simple (Top-Down)
```
Level 1: Client → Server → Database
Level 2: Add load balancer, cache
Level 3: Break server into services
Level 4: Add message queues, CDN
```

#### 2. Use Standard Symbols
```
□  Server/Service
⬡  Load Balancer
⬜  Database
◇  Cache
→  Synchronous call
⇢  Asynchronous call
```

#### 3. Label Everything
```
- What each component does
- What data flows between components
- Key technologies (e.g., "PostgreSQL", "Redis")
```

#### 4. Show Data Flow
```
- Use arrows to show request/response flow
- Number steps if helpful (1, 2, 3...)
- Show both read and write paths if different
```

### Component Selection Criteria

#### When to Use SQL vs. NoSQL

**Choose SQL When:**
- Complex queries with JOINs required
- ACID transactions are critical
- Data has clear relationships
- Data structure is stable

**Choose NoSQL When:**
- Need massive horizontal scalability
- Schema changes frequently
- Simple queries (key-value lookups)
- Eventual consistency is acceptable

#### When to Add a Cache

**Add Cache When:**
- Read-heavy workload (read:write ratio > 10:1)
- Repeated reads of same data
- Database is bottleneck
- Need sub-millisecond latency

**Skip Cache When:**
- Write-heavy workload
- Data changes frequently
- Small dataset (fits in DB cache)

#### When to Add a Message Queue

**Add Message Queue When:**
- Operations take long time (> 1 second)
- Traffic spikes need buffering
- Need reliable delivery
- Multiple consumers for same event

**Skip Message Queue When:**
- Operations are fast (< 100ms)
- Synchronous response needed
- Simple single-consumer scenario

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

**Design Components for an E-Commerce Platform**

**Requirements:**
- Users browse products
- Users add products to cart
- Users checkout and pay
- Users track order status
- Admins manage inventory
- Send email confirmations
- Generate recommendations

**Tasks:**
1. **List the components** you'd use (e.g., load balancer, API servers, etc.)
2. **Draw a high-level architecture diagram** showing how components connect
3. **Justify each component:** Why is it needed? What problem does it solve?

**Example Answer Structure:**
```
Components:
1. Load Balancer - Distribute traffic across API servers
2. API Servers - Handle product browse, cart, checkout
3. PostgreSQL - Store users, products, orders
4. Redis Cache - Cache product catalog, user sessions
5. Message Queue (RabbitMQ) - Queue email sends, recommendation jobs
6. Payment Service - Process payments
7. Email Service - Send confirmations
8. CDN - Serve product images

Diagram:
[Draw showing connections]

Justification:
- Cache: Product catalog is read-heavy (1000:1 read:write)
- Message Queue: Email sending shouldn't block checkout
- Separate Payment Service: PCI compliance, security isolation
```
