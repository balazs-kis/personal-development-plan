# Lesson 1: Functional and Non-Functional Requirements

## Learning Objectives

By the end of this lesson, you will be able to:
- Distinguish between functional and non-functional requirements
- Ask effective clarifying questions during system design discussions
- Identify the key non-functional requirements for different system types
- Document requirements clearly and concisely

---

## Introduction

The first step in any system design is understanding what you're building and why. Requirements gathering separates functional requirements (what the system does) from non-functional requirements (how well it performs). Skipping this step or making assumptions leads to misaligned designs that fail to meet actual needs.

## Key Concepts Summary

### Functional vs. Non-Functional Requirements

#### Functional Requirements (FR)
```
Definition: What the system should do
Question: "What features and capabilities?"
Format: "System shall <action>"

Examples for a Video Streaming Platform:
- Users can upload videos up to 4K resolution
- System transcodes videos to multiple resolutions (240p, 360p, 720p, 1080p)
- Users can search for videos by title, tags, or creator
- Users can like, comment, and subscribe to channels
- System sends notifications for new uploads from subscribed channels
```

#### Non-Functional Requirements (NFR)
```
Definition: How well the system should perform
Question: "What quality attributes matter?"
Format: "System shall achieve <quality metric>"

Examples for a Video Streaming Platform:
- Performance: Video buffering starts within 2 seconds
- Scalability: Support 10 million concurrent viewers
- Availability: 99.9% uptime (less than 8.76 hours downtime/year)
- Reliability: Video playback succeeds 99.99% of the time
- Durability: Zero data loss for uploaded videos
- Cost Efficiency: Storage costs under $X per petabyte
```

### The Seven Core Non-Functional Requirements

When designing systems, always consider these NFRs:

#### 1. Performance
```
Metrics:
- Response time / latency (e.g., API responds in <100ms)
- Throughput (e.g., 10,000 requests per second)
- Time to first byte (e.g., video starts in <2 seconds)

Questions to Ask:
- What's the expected response time?
- How many concurrent users must we support?
- What's acceptable for peak vs. average load?
```

#### 2. Scalability
```
Metrics:
- Maximum concurrent users
- Growth rate (e.g., 20% user growth per year)
- Peak load multiplier (e.g., 10x traffic during events)

Questions to Ask:
- How many users do we have now vs. 1 year from now?
- What's the peak load scenario?
- Do we need to scale horizontally or vertically?
```

#### 3. Availability
```
Metrics:
- Uptime percentage (e.g., 99.9%, 99.99%, 99.999%)
- Planned downtime windows
- Recovery time objective (RTO)

Questions to Ask:
- How much downtime is acceptable per year?
- Are there critical vs. non-critical features?
- What happens during maintenance windows?

Availability Reference:
99.9% = 8.76 hours downtime/year
99.99% = 52.56 minutes downtime/year
99.999% = 5.26 minutes downtime/year
```

#### 4. Reliability / Consistency
```
Metrics:
- Error rate (e.g., <0.01% of requests fail)
- Data consistency guarantees (strong vs. eventual)
- Recovery point objective (RPO)

Questions to Ask:
- How important is data consistency?
- Can we tolerate eventual consistency?
- What's the acceptable error rate?
```

#### 5. Security
```
Considerations:
- Authentication and authorization
- Data encryption (at rest and in transit)
- Compliance requirements (GDPR, HIPAA, etc.)
- Audit logging

Questions to Ask:
- What data needs protection?
- Who has access to what?
- Are there compliance requirements?
```

#### 6. Maintainability
```
Considerations:
- Code quality and documentation
- Deployment frequency
- Rollback capabilities
- Monitoring and observability

Questions to Ask:
- How often do we deploy?
- How quickly can we roll back?
- How do we debug production issues?
```

#### 7. Cost
```
Considerations:
- Infrastructure costs
- Storage and bandwidth costs
- Operational overhead
- Development and maintenance costs

Questions to Ask:
- What's the budget constraint?
- How do we optimize costs?
- What's the acceptable cost per user?
```

### Clarifying Questions Framework

When starting a system design, use this question framework:

#### Scope Questions
```
- What features are in scope vs. out of scope?
- Who are the users (consumers, admins, internal systems)?
- What's the geographic distribution (single region vs. global)?
```

#### Scale Questions
```
- How many users (total, daily active, monthly active)?
- What's the read-to-write ratio?
- What's the expected data volume?
- What's the growth projection?
```

#### Performance Questions
```
- What's the expected latency?
- What throughput is required?
- Are there batch vs. real-time requirements?
```

#### Availability & Reliability Questions
```
- What's the acceptable downtime?
- How critical is data consistency?
- What happens if a component fails?
```

### Documenting Requirements

**Good Requirement Documentation:**
```markdown
## Functional Requirements
1. Users can upload videos (max 10GB, supported formats: MP4, AVI, MOV)
2. System transcodes videos to 240p, 360p, 720p, 1080p within 30 minutes
3. Users can search videos by title (autocomplete), tags, creator name
4. Videos support playback at 0.5x, 1x, 1.5x, 2x speeds

## Non-Functional Requirements
- **Scale:** 100M daily active users, 1M video uploads per day
- **Performance:** Video starts playing within 2 seconds (P95)
- **Availability:** 99.9% uptime
- **Consistency:** Eventual consistency acceptable (video metadata)
- **Security:** HTTPS only, user authentication required
- **Storage:** 10 PB with 3x replication
```

**Bad Requirement Documentation (Too Vague):**
```
- System should be fast
- System should handle lots of users
- System should be reliable
- Videos should work
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

**Requirement Gathering for a URL Shortener**

Imagine you're designing a URL shortening service (like bit.ly). Write down:

1. **5 Functional Requirements**
   - What features must the system provide?

2. **5 Non-Functional Requirements** 
   - Pick specific metrics (e.g., "99.99% availability" not "high availability")

3. **10 Clarifying Questions**
   - What would you ask to better understand the requirements?

**Example Answer Structure:**

```
Functional Requirements:
1. System generates short URLs from long URLs
2. Short URLs redirect to original long URLs
3. Users can customize short URL slugs (if available)
4. System tracks click analytics (count, location, referrer)
5. Short URLs expire after configurable duration

Non-Functional Requirements:
1. Availability: 99.99% uptime
2. Latency: URL redirection in <50ms (P95)
3. Scale: 1 billion URLs, 10M new URLs per day
4. Read/Write Ratio: 100:1 (reads much higher)
5. Data Retention: Short URLs valid for 5 years minimum

Clarifying Questions:
1. How many URLs do we need to support?
2. What's the expected read-to-write ratio?
3. How long should short URLs remain valid?
4. Are custom short URLs allowed?
5. Do we need analytics (clicks, locations)?
6. What's the acceptable latency for redirection?
7. What's the character set for short URLs?
8. How do we handle duplicate long URLs?
9. Is authentication required?
10. What's the target availability?
```
