# Lesson 2: ADR Structure and Templates

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the core components of an ADR (title, status, context, decision, consequences)
- Choose between different ADR template formats (Nygard, MADR, Y-Statement)
- Structure an ADR effectively for your use case
- Write concise, informative ADR titles
- Use metadata and cross-references in ADRs

## Introduction

A good ADR template provides structure without being burdensome. This lesson covers the most popular ADR formats, their components, and how to choose the right template for your team. We'll explore everything from minimal templates to comprehensive formats.

## Key Concepts Summary

### The Core ADR Components

Every ADR, regardless of template, should contain:

```markdown
1. Title
2. Status
3. Context
4. Decision
5. Consequences
```

---

## 1. Title

### Format

```
ADR-{number}: {short title}

Examples:
ADR-001: Use ADRs for Architectural Decisions
ADR-015: Use Redis for Session Storage
ADR-023: Adopt Event-Driven Architecture
ADR-042: Split Monolith into Microservices
```

### Numbering

```
Sequential numbering:
ADR-001, ADR-002, ADR-003, ...

With leading zeros:
ADR-0001, ADR-0002, ADR-0003, ...

Date-based:
20240115-use-redis-for-sessions.md
```

**Best practice:** Use sequential numbers with leading zeros for consistent sorting.

### Title Guidelines

✅ **Good titles:**
- "Use PostgreSQL for Primary Database"
- "Adopt GraphQL for Public API"
- "Implement OAuth2 for Authentication"
- "Deploy to Kubernetes"

❌ **Bad titles:**
- "Database Decision" (too vague)
- "Use the Best Database We Can Find" (not specific)
- "Refactor Everything to Microservices Because They're Cool" (not concise)

**Formula:** `{Verb} {Technology/Pattern} for {Purpose}`

---

## 2. Status

### Common Status Values

```
Proposed  → Under review, not yet decided
Accepted  → Approved and in use
Superseded → Replaced by another ADR
Deprecated → No longer recommended but may still exist in code
Rejected   → Proposed but not accepted
```

### Status Examples

```markdown
## Status

Accepted

---

## Status

Superseded by [ADR-042: Use PostgreSQL Partitioning](0042-postgres-partitioning.md)

---

## Status

Proposed
```

### Status Lifecycle

```
        Proposed
           ↓
    ┌──────┼──────┐
    ↓      ↓      ↓
Accepted Rejected Withdrawn
    ↓
    ├─→ Superseded
    └─→ Deprecated
```

## 3. Context

### What to Include

Context explains **why** a decision is needed:

```markdown
## Context

We currently have session data stored in PostgreSQL, which works
fine for our current user base of 10,000 daily active users.

However, we're planning to scale to 100,000+ users within 6 months.
Load testing shows that database-backed sessions will become a 
bottleneck at that scale:
- Average session query time: 50ms (P95: 200ms)
- Database CPU utilization hits 80% at 50,000 concurrent sessions

Additionally, our current single-database deployment has no 
geographic distribution, causing high latency for users outside 
North America (200-500ms for EU users).

We need a session storage solution that:
1. Scales horizontally
2. Provides sub-10ms latency
3. Supports geographic distribution
4. Maintains session consistency
```

### Context Anti-Patterns

❌ **Too vague:**
```markdown
## Context
We need better session storage.
```

❌ **Too detailed (implementation):**
```markdown
## Context
Redis uses RDB and AOF persistence mechanisms. The RDB creates 
point-in-time snapshots while AOF logs every write operation...
[3 pages of Redis internals]
```

✅ **Just right:**
```markdown
## Context
Current session storage (PostgreSQL) has latency and scalability 
issues. We need sub-10ms access times for 100k+ concurrent users.
```

### Context Template Questions

Ask yourself:
- What problem are we solving?
- What constraints do we have?
- What are our requirements?
- What's the current situation?
- Why is change needed now?

---

## 4. Decision

### Structure

The decision should be:
- **Clear and unambiguous**
- **Actionable**
- **Specific**

```markdown
## Decision

We will use Redis as our session storage solution.

Specifically:
- Redis Cluster for horizontal scalability
- Redis Sentinel for high availability
- Deploy Redis instances in each geographic region (US, EU, APAC)
- Use Redis TTL for automatic session expiration
- Store session data as JSON with 24-hour expiration
```

### Decision Anti-Patterns

❌ **Vague:**
```markdown
## Decision
We'll use something better for sessions.
```

❌ **Multiple unrelated decisions:**
```markdown
## Decision
We'll use Redis for sessions, switch to PostgreSQL for main 
database, adopt microservices, move to Kubernetes, and rewrite 
the frontend in React.
```
(This should be 5 separate ADRs)

✅ **Clear and specific:**
```markdown
## Decision
Use Redis Cluster for distributed session storage with 
geographic deployment in three regions.
```

---

## 5. Consequences

### Structure

Document **both positive and negative** outcomes:

```markdown
## Consequences

### Positive
- Session access latency reduced from 50ms to <5ms
- Horizontal scalability: can handle 1M+ concurrent sessions
- Geographic distribution reduces latency for global users
- TTL-based expiration simplifies session cleanup
- Redis's high availability features prevent session loss

### Negative
- Additional infrastructure to maintain (Redis clusters)
- Requires Redis expertise on team (learning curve)
- Slightly higher infrastructure cost (~$500/month)
- More complex deployment (3 Redis clusters vs 1 database)
- Need to implement Redis monitoring and alerting

### Risks
- Redis cluster split-brain scenarios during network partitions
- Need backup strategy for session data
- Session consistency during failover (may lose recent updates)
```

### Consequences Template

Consider:
- **Performance:** How does this affect speed/latency?
- **Scalability:** How does this affect growth?
- **Complexity:** What new complexity is added?
- **Cost:** What's the financial impact?
- **Team:** What skills are needed?
- **Operations:** What's the operational burden?
- **Security:** Any security implications?
- **Risks:** What could go wrong?

## ADR Template Formats

### 1. Nygard Template (Classic)

The original, minimal template:

```markdown
# Title

## Status
Accepted

## Context
[Describe the forces at play, including technological, political,
social, and project local. These forces are probably in tension,
and should be called out as such.]

## Decision
[Describe our response to these forces. Full sentences with active
voice. "We will ..."]

## Consequences
[Describe the resulting context, after applying the decision. All
consequences should be listed, not just the positive ones.]
```

**Pros:**
- Simple and quick
- Low barrier to entry
- Flexible

**Cons:**
- May be too minimal for complex decisions
- No standard for options considered

**Best for:** Teams starting with ADRs, simple decisions

### 2. MADR Template (Comprehensive)

Markdown Architectural Decision Records with more structure:

```markdown
# {short title, representative of solved problem and found solution}

## Context and Problem Statement
{Describe the context and problem statement, e.g., in free form
using two to three sentences or in the form of an illustrative
story. You may want to articulate the problem in form of a question
and add links to collaboration boards or issue management systems.}

## Decision Drivers
* {decision driver 1, e.g., a force, facing concern, …}
* {decision driver 2, e.g., a force, facing concern, …}

## Considered Options
* {title of option 1}
* {title of option 2}
* {title of option 3}

## Decision Outcome
Chosen option: "{title of option 1}", because {justification.
e.g., only option that satisfies key driver}.

### Consequences
* Good, because {positive consequence, e.g., improvement of one or
  more desired qualities, …}
* Bad, because {negative consequence, e.g., compromising one or
  more desired qualities, …}

### Confirmation
{Describe how the implementation of/compliance with the ADR is
confirmed. E.g., by a review or an ArchUnit test.}

## Pros and Cons of the Options

### {title of option 1}
{example | description | pointer to more information | …}
* Good, because {argument a}
* Good, because {argument b}
* Neutral, because {argument c}
* Bad, because {argument d}

### {title of option 2}
{example | description | pointer to more information | …}
* Good, because {argument a}
* Good, because {argument b}
* Neutral, because {argument c}
* Bad, because {argument d}

### {title of option 3}
{example | description | pointer to more information | …}
* Good, because {argument a}
* Good, because {argument b}
* Neutral, because {argument c}
* Bad, because {argument d}

## More Information
{You might want to provide additional evidence/confidence for the
decision outcome here and/or document the team agreement on the
decision and/or define when/how this decision the decision should
be realized and if/when it should be re-visited.}
```

**Pros:**
- Explicit options analysis
- Structured trade-off documentation
- Confirmation section for validation

**Cons:**
- Longer and more formal
- May feel like overkill for simple decisions

**Best for:** Complex decisions with many options, teams wanting thorough documentation

### 3. Y-Statement (One-Liner)

Ultra-concise format:

```
In the context of {use case/user story},
facing {concern/problem},
we decided for {option},
to achieve {quality/benefit},
accepting {downside/compromise}.
```

**Example:**
```
In the context of scaling to 100k concurrent users,
facing database session storage latency,
we decided for Redis Cluster,
to achieve sub-10ms session access,
accepting increased operational complexity.
```

**Pros:**
- Extremely concise
- Forces clarity
- Quick to write and read

**Cons:**
- May lack detail for complex decisions
- Hard to document multiple options considered

**Best for:** Simple decisions, teams wanting minimal overhead

### 4. Alexandrian Pattern (Forces)

Based on Christopher Alexander's pattern language:

```markdown
# Title

## Status

## Context
[Setting and prerequisites]

## Forces
* {Force 1: tension that needs resolution}
* {Force 2: conflicting requirement}
* {Force 3: constraint that must be satisfied}

## Decision
[How the decision resolves the forces]

## Consequences
[New context and remaining forces]
```

**Example:**
```markdown
## Forces
* Need fast session access (<10ms)
* Must scale to 100k+ concurrent sessions
* Team has limited Redis experience
* Budget constraint of $1000/month infrastructure
* Require high availability (99.9% uptime)
```

**Pros:**
- Explicitly calls out tensions and trade-offs
- Good for decisions with competing concerns

**Cons:**
- "Forces" concept may be unfamiliar
- Can be verbose

**Best for:** Complex decisions with many trade-offs

## Complete ADR Example

Here's a complete ADR using the Nygard template:

```markdown
# ADR-015: Use Redis for Session Storage

## Status

Accepted

Date: 2024-01-15

Supersedes: ADR-003 (Database Session Storage)

## Context

We currently store user sessions in PostgreSQL, which worked well
for our initial user base. However, as we approach 100,000 daily
active users, we're encountering performance issues:

- Database CPU hits 80% during peak hours
- Session queries average 50ms (P95: 200ms)
- No geographic distribution (high latency for non-US users)

Load testing indicates the database will become a critical 
bottleneck at our projected growth rate of 50% quarter-over-quarter.

Requirements:
- Support 100k+ concurrent sessions
- Sub-10ms session access latency
- Geographic distribution (US, EU, APAC)
- 99.9% availability
- Automatic session expiration

## Decision

We will migrate from PostgreSQL to Redis Cluster for session storage.

Implementation details:
- Deploy Redis Cluster in each geographic region (3 regions)
- Use Redis Sentinel for automatic failover
- Store sessions as JSON with 24-hour TTL
- Implement session replication across regions for disaster recovery
- Use existing Redis library for .NET (StackExchange.Redis)

Timeline: 2-week migration with gradual rollout by region.

## Consequences

### Positive

- Session latency reduced from 50ms to <5ms (90% reduction)
- Can scale horizontally to millions of sessions
- Geographic deployment reduces global user latency
- Automatic TTL-based expiration simplifies cleanup
- Redis's pub/sub can enable real-time features later

### Negative

- Additional infrastructure cost: ~$500/month for 3 Redis clusters
- Team needs Redis expertise (1-week learning curve)
- More complex monitoring (Redis + PostgreSQL)
- Need to implement Redis backup strategy
- Potential session loss during Redis cluster failover (rare)

### Risks and Mitigations

- **Risk:** Redis cluster split-brain during network partition
  - *Mitigation:* Use Redis Sentinel with 5-node quorum
- **Risk:** Session data loss during regional outage
  - *Mitigation:* Implement cross-region replication
- **Risk:** Cost overruns if usage exceeds projections
  - *Mitigation:* Set up CloudWatch alarms for cost monitoring

### Next Steps

1. Set up Redis clusters in staging environment (Week 1)
2. Implement session migration code with A/B testing (Week 1)
3. Load test Redis implementation (Week 2)
4. Gradual rollout: 10% → 50% → 100% (Week 2)
5. Document Redis operations runbook (Week 2)

### References

- Load testing results: [link to report]
- Redis Cluster documentation: https://redis.io/topics/cluster-tutorial
- Cost analysis spreadsheet: [link]
```

## Template Selection Guide

| Scenario | Recommended Template |
|----------|---------------------|
| Just starting with ADRs | Nygard (simple) |
| Complex multi-option decision | MADR (comprehensive) |
| Need ultra-quick documentation | Y-Statement |
| Many competing concerns | Alexandrian (forces) |
| Team already uses ADRs | Stick with current template |

**Pro tip:** Pick one template and stick with it. Consistency matters more than perfection.
