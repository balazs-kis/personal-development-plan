# Lesson 3: Mentoring Through Code Review

## Learning Objectives

By the end of this lesson, you will be able to:
- Use code review as an effective mentoring tool for junior developers
- Structure reviews to maximize learning while maintaining quality
- Balance teaching moments with practical code improvements
- Scale mentoring through small-group code reviews

---

## Introduction

Code review is one of the most powerful tools for mentoring junior developers. Unlike abstract training sessions, code reviews provide immediate, contextual feedback on real production code—making lessons relevant and memorable. However, effective mentoring through review requires intentionality: knowing when to teach versus when to simply approve, how to explain concepts without overwhelming, and how to create learning opportunities that stick. This lesson explores how to transform routine code reviews into high-impact mentoring sessions.

## Key Concepts Summary

### Why Code Review is Powerful for Mentoring

**Real-World Learning:**

```markdown
Traditional training:
- Abstract examples
- Removed from context
- Theoretical knowledge
- Forgotten quickly

Code review mentoring:
✅ Real production code
✅ Immediate practical application
✅ Contextualized learning
✅ Memorable lessons

Junior developers learn faster through code review because:
1. Feedback is on their actual work
2. Consequences are clear (production impact)
3. They see expert reasoning in real scenarios
4. Learning is personalized to their skill gaps
```

**Knowledge Transfer That Textbooks Miss:**

```markdown
Domain-specific knowledge difficult to document:
- Team coding conventions and "the way we do things"
- Common gotchas in your specific tech stack
- Business logic quirks
- Performance patterns for your scale
- Security considerations for your domain
- Organizational architecture decisions

Code review naturally transfers this tribal knowledge.
```

### Structuring Mentoring Through Review

**1. Set Clear Expectations**

```markdown
At the start of a mentoring relationship:

✅ Explain review purpose:
"Code reviews are learning opportunities. My goal is to help
you grow as a developer. Questions are encouraged!"

✅ Define scope and criteria:
"I'll focus feedback on: correctness, maintainability, 
team conventions, and testing. Don't expect perfection—
we all improve iteratively."

✅ Establish communication norms:
"I'll use prefixes like [LEARN] for teaching moments,
[BLOCKER] for must-fix items. Feel free to ask 'why'
on any comment!"

✅ Frame feedback positively:
"Code review comments are not judgments of you as a person.
We're all learning, and I make mistakes too. This is
collaborative improvement."
```

**2. Teach Concepts, Not Just Fixes**

```markdown
❌ Just the fix:
"Change this to use LINQ."

```csharp
var activeUsers = users.Where(u => u.IsActive).ToList();
```

✅ Teaching the concept:
"[LEARN] When filtering collections, LINQ is more readable
than foreach loops:

```csharp
// Current approach (imperative)
var activeUsers = new List<User>();
foreach (var user in users)
{
    if (user.IsActive)
        activeUsers.Add(user);
}

// LINQ approach (declarative)
var activeUsers = users.Where(u => u.IsActive).ToList();
```

LINQ is:
- More concise
- Easier to understand intent
- Standard C# idiom
- Chainable for complex filters

This is a pattern we use throughout the codebase.
Questions?"

Key elements:
- Show both approaches
- Explain benefits (not just "do it this way")
- Connect to broader patterns
- Invite questions
```

**3. Use Progressive Complexity**

```markdown
Early PRs (Week 1-2):
✅ Focus on fundamentals
   - Code compiles and runs
   - Basic tests present
   - Obvious bugs caught
✅ Teach one new concept per review
✅ Praise good practices heavily

Mid-stage PRs (Month 1-3):
✅ Raise the bar gradually
   - Edge case handling
   - Error management
   - Code organization
✅ Reference past lessons
   "Remember we discussed LINQ? Same pattern applies here."

Mature PRs (Month 3+):
✅ Treat more like peer review
   - Focus on design decisions
   - Performance considerations
   - Architectural fit
✅ Ask their opinion
   "What do you think about using Strategy pattern here?"
```

### Mentoring Techniques

**1. Explain the "Why" Behind Conventions**

```markdown
❌ Dictating rules:
"Use dependency injection here."
"Follow the Repository pattern."
"Add XML documentation."

✅ Teaching reasoning:
"We use dependency injection because it:
1. Makes code testable (can inject mocks)
2. Allows swapping implementations (dev vs prod)
3. Makes dependencies explicit and clear

In this case, you're using 'new EmailService()' directly.
If we inject IEmailService instead:

```csharp
public class UserController 
{
    private readonly IEmailService _emailService;
    
    public UserController(IEmailService emailService)
    {
        _emailService = emailService;
    }
}
```

Now we can test this without actually sending emails.
Does that make sense?"

This approach:
- Explains principles, not just rules
- Shows concrete benefits
- Demonstrates how to apply it
- Checks for understanding
```

**2. Link to Resources for Deep Dives**

```markdown
✅ Provide learning paths:

"[LEARN] This is a common async/await pitfall. Quick fix
for now, but worth understanding deeply:

For this PR: Remove the `.Result` call and use `await`.

To learn more:
- Microsoft docs on async/await: [link]
- Video on async best practices: [link]
- Our team wiki on common async patterns: [link]

Happy to discuss in our next 1:1 if you have questions!"

Benefits:
- Unblocks immediate work
- Provides learning resources
- Offers to discuss further
- Doesn't overwhelm with information
```

**3. Ask Questions to Guide Discovery**

```markdown
❌ Telling answers:
"This function is too long. Split it into three functions."

✅ Socratic method:
"This function is about 80 lines. What do you think about
its complexity?

[Let them reflect]

I see it's doing three distinct things:
1. Validating input
2. Calling the API
3. Transforming the response

What if we extracted each into its own function? How might
that improve readability and testability?"

Benefits:
- Encourages critical thinking
- Makes them active participants
- Helps them develop intuition
- More likely to stick
```

**4. Highlight Good Practices**

```markdown
✅ Positive reinforcement:

"[NICE] Excellent error handling here! You:
- Caught the specific exception
- Logged with context
- Provided a clear message to the user
- Didn't swallow the exception

This is exactly how we should handle errors. Great job!"

Benefits:
- Reinforces correct patterns
- Builds confidence
- Shows you notice good work
- Motivates continued learning
```

### Small-Group Code Reviews

**Format for Team Learning:**

```markdown
Structure (30-minute session):
- 4 junior developers + 1 facilitator
- 1 PR per person (30 lines, pre-shared)
- Silent review: 4 minutes per person
- Discussion: 3 minutes per person
- Rotation: Different PR author each time

Benefits:
✅ Scales mentoring (1:4 ratio)
✅ Peer learning (juniors learn from each other)
✅ Multiple perspectives
✅ Builds review skills
✅ Creates safe learning environment

Process:
1. Everyone silently reviews code (4 min)
2. Reviewer 1 shares observations (1 min)
3. Reviewer 2 adds new insights (1 min)
4. Reviewer 3 adds new insights (1 min)
5. Author reflects and asks questions (1 min)
6. Facilitator summarizes key lessons (1 min)
```

**Example Small-Group Review:**

```markdown
Author: Junior Dev A shares PR
Facilitator: "Everyone silently review for 4 minutes"

[Silent review period]

Facilitator: "Junior Dev B, what did you notice?"

Dev B: "The SQL query looks correct, but I think there's
a potential SQL injection risk if userId comes from user input."

Facilitator: "Good catch! Dev C, what else?"

Dev C: "I noticed the function returns null on error.
Would an exception be clearer?"

Facilitator: "Interesting point. Dev D?"

Dev D: "The test only covers the happy path. We might
want to test the error cases."

Facilitator: "All excellent observations. Author, thoughts?"

Dev A: "I didn't think about SQL injection since userId
is from the API, but I should use parameters to be safe.
And you're right about testing edge cases."

Facilitator: "Great discussion! Key takeaways:
1. Always parameterize SQL, even if input seems safe
2. Be explicit about error handling (null vs exception)
3. Test both happy and error paths

Everyone learned from Dev A's code. Thanks for sharing!"
```

### Balancing Teaching and Shipping

**When to Teach:**

```markdown
✅ Good teaching moments:
- Introducing new team patterns
- Recurring mistakes worth explaining
- Fundamental concepts (async, LINQ, DI)
- Security or correctness issues
- Opportunities to connect dots

✅ When time allows:
- Non-urgent PRs
- Refactoring work
- Learning-focused tasks
```

**When to Be Pragmatic:**

```markdown
✅ Minimize teaching when:
- Production emergency
- Hard deadline approaching
- Simple hotfix
- Junior is overwhelmed

In these cases:
- Mark issues as [BLOCKER] vs [LEARN]
- "Let's fix this now, discuss why later"
- Schedule follow-up conversation
- Create tickets for future learning
```

### Tracking Growth

**Measure Mentoring Impact:**

```markdown
Quantitative indicators:
📊 Time to first PR merged (decreasing)
📊 Number of review iterations (decreasing)
📊 Test coverage in PRs (increasing)
📊 Bug rate in production (decreasing)
📊 PR size (decreasing = better scoping)

Qualitative indicators:
📈 Junior asks thoughtful questions
📈 Anticipates review feedback
📈 Reviews peers' code effectively
📈 Contributes to architecture discussions
📈 Teaches newer juniors
```

**Celebrate Milestones:**

```markdown
✅ Recognize growth:

"Your last 3 PRs have had minimal feedback! You're:
- Writing tests without being asked
- Following our conventions
- Handling errors properly
- Keeping PRs focused

This is huge progress from Month 1. Great work! 🎉"

Public recognition:
- Team meetings
- Slack channels
- Performance reviews
- Peer feedback
```

## Practice Exercise

After completing the materials (20-30 minutes):

1. **Transform a Review Comment:**
   Take this basic feedback:
   
   "This won't work if the list is null. Add a null check."
   
   Rewrite it as a teaching moment for a junior developer.
   Include: why it matters, how to fix it, general principle.

2. **Create a Teaching Review:**
   Imagine reviewing this code from a junior developer:
   
   ```csharp
   public List<User> GetActiveUsers()
   {
       var users = _db.Users.ToList();
       var active = new List<User>();
       foreach (var u in users)
       {
           if (u.Status == "active")
               active.Add(u);
       }
       return active;
   }
   ```
   
   Write a review comment that:
   - Identifies improvement opportunities
   - Teaches LINQ and query optimization
   - Explains why it matters
   - Provides example code

3. **Plan a Small-Group Review:**
   Design a 30-minute small-group code review session:
   - Define format and timing
   - Create facilitation script
   - List discussion questions
   - Identify key learning goals

4. **Mentoring Roadmap:**
   Create a 3-month mentoring plan through code review:
   - Week 1-2: Focus areas
   - Month 1: Key concepts to teach
   - Month 2: Raising the bar
   - Month 3: Approaching peer review
