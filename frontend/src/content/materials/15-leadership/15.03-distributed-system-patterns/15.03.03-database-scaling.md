## Introduction

As applications grow, single database instances become bottlenecks. Database scaling is essential for handling increased load, improving performance, and ensuring high availability. This lesson covers the fundamental patterns: replication for read scalability and availability, and sharding for write scalability and data distribution.

## Key Concepts Summary

### Scaling Approaches

```
Vertical Scaling (Scale Up):
Database Server
├─ CPU: 4 cores → 16 cores
├─ RAM: 16GB → 128GB
└─ Disk: HDD → SSD

Horizontal Scaling (Scale Out):
1 Database Server → 4 Database Servers
```

**Vertical Scaling:**
- **Pros:** Simple (no code changes), strong consistency
- **Cons:** Hardware limits, expensive, single point of failure
- **When:** Small to medium scale, ACID requirements

**Horizontal Scaling:**
- **Pros:** Nearly unlimited scalability, cost-effective
- **Cons:** Complexity, eventual consistency challenges
- **When:** Web-scale applications, high availability needs

## Database Replication

Replication copies data across multiple database servers to improve read performance and availability.

### 1. Leader-Follower (Primary-Replica) Replication

```
        Writes
          ↓
    Leader (Primary)
         ↓
    Replication
    ↙    ↓    ↘
Follower Follower Follower
(Replica) (Replica) (Replica)
  ↑        ↑        ↑
 Reads    Reads    Reads
```

**How it works:**
1. All writes go to leader
2. Leader replicates changes to followers
3. Reads distributed across followers
4. If leader fails, promote a follower

**Implementation Example:**
```csharp
// Configure read replicas
public class DatabaseConfig
{
    public string LeaderConnectionString { get; set; }
    public List<string> ReplicaConnectionStrings { get; set; }
}

public class DataService
{
    private readonly DbConnection _leader;
    private readonly List<DbConnection> _replicas;
    
    public async Task<User> GetUserAsync(int id)
    {
        // Read from random replica
        var replica = _replicas[Random.Shared.Next(_replicas.Count)];
        return await replica.QueryFirstAsync<User>(
            "SELECT * FROM Users WHERE Id = @id", 
            new { id }
        );
    }
    
    public async Task UpdateUserAsync(User user)
    {
        // Write to leader
        await _leader.ExecuteAsync(
            "UPDATE Users SET Name = @name WHERE Id = @id",
            user
        );
    }
}
```

**Pros:**
- Scales read throughput
- High availability (failover to replicas)
- Backup without affecting primary

**Cons:**
- Replication lag (eventual consistency)
- Writes don't scale (single leader)
- Failover complexity

**Use cases:** Read-heavy applications (90%+ reads)

### 2. Synchronous vs Asynchronous Replication

**Synchronous Replication:**
```
Client → Write → Leader → Wait for replica ACK → Confirm to client
                    ↓
                 Replica
```
- **Pros:** Guaranteed consistency, no data loss
- **Cons:** Higher latency, availability risk (replica failure blocks writes)

**Asynchronous Replication:**
```
Client → Write → Leader → Confirm to client
                    ↓ (async)
                 Replica
```
- **Pros:** Lower latency, higher availability
- **Cons:** Replication lag, potential data loss on leader failure

**Practical approach:** Semi-synchronous (1 synchronous replica, rest async)

### 3. Leader-Leader (Multi-Primary) Replication

```
     Leader 1  ←→  Leader 2
     (US West)     (US East)
        ↕              ↕
    Replicas       Replicas
```

**How it works:**
- Multiple nodes accept writes
- Bi-directional replication
- Conflict resolution required

**Pros:**
- Writes can be distributed
- Geographic distribution
- Better availability (no single leader)

**Cons:**
- Conflict resolution complexity
- Harder to guarantee consistency
- More complex setup

### 4. Conflict Resolution

```csharp
// Last Write Wins (LWW)
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public DateTime LastModified { get; set; }
}

// Keep the most recent write
if (update1.LastModified > update2.LastModified)
    ApplyUpdate(update1);
else
    ApplyUpdate(update2);

// Application-level resolution
public User ResolveConflict(User version1, User version2)
{
    return new User
    {
        Id = version1.Id,
        Name = version1.Name, // Prefer version1 for name
        Email = version2.Email, // Prefer version2 for email
        LastModified = DateTime.UtcNow
    };
}
```

**Strategies:**
- **Last Write Wins (LWW):** Simplest but may lose data
- **Version Vectors:** Track causality, detect true conflicts
- **Application Resolution:** Let application code decide
- **CRDTs:** Conflict-free replicated data types (automatic merging)

## Database Partitioning

Partitioning divides data into smaller, manageable pieces.

### Horizontal Partitioning (Sharding)

Splits rows across multiple tables/databases:

```
Users Table (10M rows)
         ↓
Shard 1: Users 1-3.3M
Shard 2: Users 3.3M-6.6M
Shard 3: Users 6.6M-10M
```

### Vertical Partitioning

Splits columns across tables:

```
Users Table: Id, Name, Email, ProfilePic, Bio, Preferences
         ↓
Users_Core: Id, Name, Email
Users_Profile: Id, ProfilePic, Bio
Users_Settings: Id, Preferences
```

**Use when:**
- Frequently accessed columns separate from rarely accessed
- Large columns (BLOBs) separate from small columns
- Different access patterns for different columns

## Database Sharding

Sharding distributes data across multiple independent databases.

### Sharding Strategies

#### 1. Range-Based Sharding

```
Shard by User ID ranges:
Shard 1: User IDs 1-1,000,000
Shard 2: User IDs 1,000,001-2,000,000
Shard 3: User IDs 2,000,001-3,000,000
```

```csharp
public class RangeShardRouter
{
    public int GetShardId(int userId)
    {
        if (userId <= 1_000_000) return 1;
        if (userId <= 2_000_000) return 2;
        return 3;
    }
}
```

**Pros:**
- Simple to implement
- Range queries efficient within shard

**Cons:**
- Unbalanced load (new users → last shard gets all writes)
- Hotspots possible
- Resharding difficult

**Use when:** Data has natural ranges, even distribution

#### 2. Hash-Based Sharding

```
Shard = Hash(UserID) % NumShards

User 123 → Hash(123) = 7891 → 7891 % 3 = 2 → Shard 2
User 456 → Hash(456) = 3421 → 3421 % 3 = 1 → Shard 1
```

```csharp
public class HashShardRouter
{
    private readonly int _numShards;
    
    public int GetShardId(int userId)
    {
        return Math.Abs(userId.GetHashCode()) % _numShards;
    }
}
```

**Pros:**
- Even distribution
- No hotspots

**Cons:**
- Range queries difficult (data scattered)
- Resharding requires remapping all keys

**Use when:** Even distribution critical, no range queries

#### 3. Consistent Hashing

```
Hash ring (0-360°):
Shard 1: 0°
Shard 2: 120°
Shard 3: 240°

Virtual nodes for better distribution:
Shard 1: 0°, 90°, 180°
Shard 2: 60°, 150°, 270°
Shard 3: 30°, 210°, 330°
```

```csharp
public class ConsistentHashRouter
{
    private readonly SortedDictionary<int, int> _ring = new();
    
    public ConsistentHashRouter(int numShards, int virtualNodes)
    {
        for (int shard = 0; shard < numShards; shard++)
        {
            for (int v = 0; v < virtualNodes; v++)
            {
                var hash = Hash($"shard-{shard}-vnode-{v}");
                _ring[hash] = shard;
            }
        }
    }
    
    public int GetShardId(int userId)
    {
        var hash = Hash(userId.ToString());
        
        // Find first shard >= hash (wrap around)
        foreach (var kvp in _ring)
        {
            if (kvp.Key >= hash)
                return kvp.Value;
        }
        
        return _ring.First().Value; // Wrap to first
    }
}
```

**Pros:**
- Adding/removing shards only affects ~1/n of data
- Better for dynamic scaling

**Cons:**
- More complex
- Still can't do efficient range queries

**Use when:** Need to add/remove shards frequently

#### 4. Geographic Sharding

```
Shard by region:
US Shard: US users
EU Shard: EU users
APAC Shard: APAC users
```

**Pros:**
- Lower latency (data close to users)
- Compliance (GDPR, data residency)

**Cons:**
- Uneven load if user distribution skewed
- Cross-region queries expensive

**Use when:** Global application, data locality requirements

#### 5. Entity-Based Sharding

```
Shard by tenant (multi-tenant SaaS):
Shard 1: Company A's data
Shard 2: Company B's data
Shard 3: Company C's data
```

**Pros:**
- Tenant isolation
- Easy to scale per tenant

**Cons:**
- Uneven shard sizes
- Difficult to move large tenants

**Use when:** Multi-tenant applications, strong isolation needed

## Choosing a Shard Key

The shard key determines data distribution. Poor choice = hotspots and performance issues.

### Good Shard Key Characteristics:

1. **High Cardinality:** Many unique values
2. **Even Distribution:** No hotspots
3. **Queries Hit Single Shard:** Avoid cross-shard queries

### Examples:

| Shard Key | Good/Bad | Reason |
|-----------|----------|--------|
| User ID | ✅ Good | High cardinality, even distribution |
| Timestamp | ❌ Bad | Recent data → hotspot on newest shard |
| Country | ❌ Bad | Uneven (USA has way more users) |
| User ID + Timestamp | ✅ Good | Combines benefits |
| Status (active/inactive) | ❌ Bad | Low cardinality, uneven |

## Challenges with Sharding

### 1. Cross-Shard Queries

```sql
-- Want: All orders over $100
-- Problem: Orders scattered across shards

-- Bad: Query all shards, merge results (slow)
SELECT * FROM orders WHERE amount > 100;

-- Better: Denormalize or use search index (Elasticsearch)
```

**Solutions:**
- Avoid cross-shard queries in design
- Denormalize data
- Use separate search/analytics system

### 2. Cross-Shard Joins

```sql
-- Want: Join users and orders (different shards)
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id;

-- Not possible if sharded differently
```

**Solutions:**
- Shard related data together
- Denormalize
- Application-level joins

### 3. Distributed Transactions

```csharp
// Transfer money between users on different shards
// Needs two-phase commit (2PC) - slow and complex

// Better: Event-driven eventual consistency
public async Task TransferMoney(int fromUserId, int toUserId, decimal amount)
{
    // Deduct from sender
    await Deduct(fromUserId, amount);
    
    // Publish event
    await eventBus.Publish(new MoneyDeducted(fromUserId, toUserId, amount));
    
    // Event handler adds to recipient (different shard)
}
```

### 4. Resharding

```
3 shards → 4 shards
= Migrating 25% of data
= Downtime or complex online migration
```

**Strategies:**
- Plan for growth (start with more shards)
- Use consistent hashing (minimizes data movement)
- Database proxy (routes during migration)

## Real-World Examples

### YouTube (Vitess)
- Shards MySQL horizontally
- Resharding without downtime
- Powers billions of views/day

### Instagram
- Sharded PostgreSQL by user ID
- Consistent hashing for distribution
- Each shard is leader-follower replicated

### Discord
- Sharded by message channel
- Cassandra for message storage
- ScyllaDB for high write throughput
