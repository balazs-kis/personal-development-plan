## Introduction

Load balancers are critical components in distributed systems that distribute incoming traffic across multiple servers. They enable horizontal scaling, improve reliability through redundancy, and optimize resource utilization. Understanding load balancing strategies is fundamental for designing scalable systems.

## Key Concepts Summary

### What is a Load Balancer?

```
Client Requests
      ↓
 Load Balancer
   /    |    \
  ↓     ↓     ↓
Server1 Server2 Server3
```

A load balancer sits between clients and servers, distributing requests to prevent any single server from becoming overwhelmed. It provides:
- **Scalability:** Handle more traffic by adding servers
- **High Availability:** Redundancy through multiple servers
- **Performance:** Better response times through optimal distribution
- **Maintenance:** Update servers without downtime

### Static Load Balancing Algorithms

**1. Round Robin**
```
Request 1 → Server 1
Request 2 → Server 2
Request 3 → Server 3
Request 4 → Server 1 (cycle repeats)
```
- **Pros:** Simple, fair distribution
- **Cons:** Doesn't account for server capacity or current load
- **Use when:** All servers have equal capacity and requests require similar processing

**2. Weighted Round Robin**
```
Server 1: Weight 3 (gets 3 requests)
Server 2: Weight 2 (gets 2 requests)
Server 3: Weight 1 (gets 1 request)
```
- **Pros:** Accounts for different server capacities
- **Cons:** Still doesn't consider real-time load
- **Use when:** Servers have known different capacities

**3. IP Hash / Session Persistence**
```csharp
// Pseudo-code
int serverIndex = Hash(clientIP) % serverCount;
```
- **Pros:** Same client always hits same server (session affinity)
- **Cons:** Uneven distribution if traffic patterns aren't uniform
- **Use when:** Sessions need to be maintained on specific servers

**4. URL Hash**
```csharp
// Route based on URL path
int serverIndex = Hash(request.Path) % serverCount;
```
- **Pros:** Cache efficiency (same URLs hit same servers)
- **Cons:** Uneven load if some URLs more popular
- **Use when:** Caching benefits from routing similar requests together

### Dynamic Load Balancing Algorithms

**1. Least Connections**
```
Server 1: 10 active connections
Server 2: 5 active connections  ← Route here
Server 3: 8 active connections
```
- **Pros:** Adapts to real-time load
- **Cons:** Requires tracking connections
- **Use when:** Requests have varying processing times

**2. Weighted Least Connections**
```
Server 1: 10 connections, weight 3 → ratio: 3.3
Server 2: 5 connections, weight 2 → ratio: 2.5 ← Route here
Server 3: 8 connections, weight 1 → ratio: 8.0
```
- **Pros:** Combines capacity with real-time load
- **Cons:** More complex to implement
- **Use when:** Different server capacities AND varying request times

**3. Least Response Time**
```
Server 1: avg response time 100ms
Server 2: avg response time 50ms  ← Route here
Server 3: avg response time 200ms
```
- **Pros:** Routes to fastest-performing server
- **Cons:** Requires continuous monitoring
- **Use when:** Performance consistency is critical

### Layer 4 vs Layer 7 Load Balancing

**Layer 4 (Transport Layer)**
```
Works at TCP/UDP level
- Faster (less processing)
- Routes based on IP and port
- Can't inspect application data
- Lower latency
```

**Layer 7 (Application Layer)**
```
Works at HTTP/HTTPS level
- Routes based on URL, headers, cookies
- Content-based routing
- SSL termination
- Higher latency but more intelligent
```

**Comparison:**

| Feature | Layer 4 | Layer 7 |
|---------|---------|---------|
| Speed | Faster | Slower |
| Routing | IP/Port only | URL, headers, cookies |
| SSL Termination | No | Yes |
| Content Inspection | No | Yes |
| Use Case | High throughput | Intelligent routing |

### Health Checks and Failover

```csharp
// Health check pattern
public class HealthCheck
{
    public async Task<bool> IsHealthy(Server server)
    {
        try
        {
            var response = await httpClient.GetAsync($"{server.Url}/health");
            return response.IsSuccessStatusCode;
        }
        catch
        {
            return false;
        }
    }
}

// Check every 10 seconds
// If 3 consecutive failures, remove from pool
// When healthy again, add back to pool
```

**Health Check Types:**
- **Passive:** Monitor actual requests, mark server down if errors
- **Active:** Send periodic health check requests
- **Hybrid:** Combine both approaches

### Real-World Examples

**Netflix:**
- Uses multiple layers of load balancing
- Edge load balancers route to regional data centers
- Internal load balancers distribute within data centers
- Zuul API gateway performs intelligent Layer 7 routing

**Amazon:**
- Elastic Load Balancing (ELB) with auto-scaling
- Combines multiple algorithms based on traffic patterns
- Geographic load balancing for global distribution

## Load Balancer Patterns

### 1. DNS Load Balancing
```
DNS Query: example.com
↓
DNS returns different IPs in rotation:
- 1.2.3.4 (40% traffic)
- 5.6.7.8 (40% traffic)
- 9.10.11.12 (20% traffic)
```
- **Pros:** Simple, built into DNS
- **Cons:** Slow to update (DNS caching), no health checks

### 2. Hardware Load Balancers
- Dedicated physical devices
- High performance, expensive
- Examples: F5 BIG-IP, Citrix ADC

### 3. Software Load Balancers
- Run on standard servers
- Flexible, cost-effective
- Examples: HAProxy, NGINX, Envoy

### 4. Cloud Load Balancers
- Managed services from cloud providers
- Auto-scaling, high availability
- Examples: AWS ELB/ALB, Azure Load Balancer, GCP Load Balancing

## System Design Considerations

### When designing with load balancers:

1. **Stateless Services**
   - Design services to be stateless where possible
   - Use session stores (Redis, databases) for shared state
   - Enables any server to handle any request

2. **Sticky Sessions Trade-offs**
   ```
   Pros:
   - Simpler application code
   - In-memory sessions work
   
   Cons:
   - Uneven load distribution
   - Harder to scale down
   - Server failure loses sessions
   ```

3. **Load Balancer as Single Point of Failure**
   - Deploy multiple load balancers
   - Use floating IPs or DNS failover
   - Cloud providers handle this automatically

4. **Cascading Failures**
   - Circuit breaker pattern
   - Graceful degradation
   - Rate limiting per server
