---

## Introduction

Creating indexes isn't enough—you need to verify they're actually being used and helping performance. MongoDB's `explain()` method provides detailed information about how queries execute: which indexes are used, how many documents are examined, execution time, and more. By analyzing explain output, you can diagnose slow queries, identify missing indexes, verify index selectivity, and measure the impact of schema changes. Mastering explain() is essential for maintaining optimal database performance.

## Key Concepts Summary

### Using explain()

**Basic Syntax:**
```javascript
db.collection.find(<query>).explain()
db.collection.find(<query>).explain("<verbosity>")
```

**Verbosity Levels:**

**1. queryPlanner (default):**
```javascript
db.orders.find({ status: "shipped" }).explain()
db.orders.find({ status: "shipped" }).explain("queryPlanner")
```
- Shows which index was selected
- Shows the query plan stages
- Does NOT execute the query
- Fastest, no performance impact

**2. executionStats:**
```javascript
db.orders.find({ status: "shipped" }).explain("executionStats")
```
- Executes the query
- Shows actual execution metrics
- Number of documents examined
- Execution time in milliseconds
- Most commonly used

**3. allPlansExecution:**
```javascript
db.orders.find({ status: "shipped" }).explain("allPlansExecution")
```
- Shows all candidate plans MongoDB considered
- Shows why the winning plan was selected
- Most detailed, slowest

### Key Metrics in explain()

**Critical Metrics:**

**1. executionTimeMillis**
- Total query execution time
- Lower is better
- Goal: < 100ms for most queries

**2. totalDocsExamined**
- Number of documents scanned
- Goal: Close to nReturned

**3. totalKeysExamined**
- Number of index keys scanned
- Should be close to nReturned for selective queries

**4. nReturned**
- Number of documents returned
- Actual result set size

**5. executionStages.stage**
- Indicates how the query executed
- IXSCAN = index scan (good)
- COLLSCAN = collection scan (usually bad)
- FETCH = retrieving documents

### Understanding Query Stages

**COLLSCAN (Collection Scan):**
```javascript
{
  stage: "COLLSCAN",
  direction: "forward",
  docsExamined: 1000000
}
```
- Scans entire collection
- ❌ Usually indicates missing index
- Acceptable for small collections (<1000 docs)
- Acceptable for queries returning large % of collection

**IXSCAN (Index Scan):**
```javascript
{
  stage: "IXSCAN",
  indexName: "status_1_orderDate_-1",
  keysExamined: 42,
  direction: "forward"
}
```
- ✅ Uses an index
- Most efficient for selective queries
- keysExamined shows index selectivity

**FETCH:**
```javascript
{
  stage: "FETCH",
  inputStage: {
    stage: "IXSCAN",
    keysExamined: 42
  },
  docsExamined: 42
}
```
- Retrieves full documents using index results
- Normal for queries returning document fields
- Avoided in covered queries

**SORT:**
```javascript
{
  stage: "SORT",
  sortPattern: { orderDate: -1 },
  memUsage: 512,
  inputStage: { ... }
}
```
- In-memory sort (expensive)
- ❌ Indicates sort not covered by index
- Limited to 32MB by default

**PROJECTION_COVERED:**
```javascript
{
  stage: "PROJECTION_COVERED",
  transformBy: { _id: 0, email: 1 }
}
```
- ✅ Covered query (returns data from index only)
- No FETCH stage
- Optimal performance

### Reading explain() Output

**Example 1: Efficient Query**

```javascript
db.orders.find({ customerId: "cust123" }).explain("executionStats")
```

**Output (simplified):**
```javascript
{
  executionStats: {
    executionSuccess: true,
    nReturned: 15,                    // Returned 15 documents
    executionTimeMillis: 3,           // Fast: 3ms
    totalKeysExamined: 15,            // Examined 15 index keys
    totalDocsExamined: 15,            // Examined 15 documents
    executionStages: {
      stage: "FETCH",
      docsExamined: 15,
      inputStage: {
        stage: "IXSCAN",              // ✅ Using index
        indexName: "customerId_1",
        keysExamined: 15
      }
    }
  }
}
```

**Analysis:**
- ✅ Uses index (IXSCAN)
- ✅ Efficient: keysExamined = nReturned
- ✅ Fast execution time
- ✅ All examined documents were returned

**Example 2: Inefficient Query**

```javascript
db.orders.find({ status: "shipped" }).explain("executionStats")
```

**Output:**
```javascript
{
  executionStats: {
    nReturned: 150,                   // Returned 150
    executionTimeMillis: 1250,        // ❌ Slow: 1.25 seconds
    totalKeysExamined: 0,             // ❌ No index used
    totalDocsExamined: 1000000,       // ❌ Scanned 1M documents
    executionStages: {
      stage: "COLLSCAN",              // ❌ Collection scan
      direction: "forward",
      docsExamined: 1000000
    }
  }
}
```

**Analysis:**
- ❌ No index used (COLLSCAN)
- ❌ Scanned 1,000,000 docs to return 150
- ❌ Very slow (1.25 seconds)
- **Solution:** Create index on `status`

**Example 3: Inefficient Sort**

```javascript
db.orders.find({ status: "shipped" }).sort({ orderDate: -1 }).explain("executionStats")
```

**Output:**
```javascript
{
  executionStats: {
    nReturned: 150,
    executionTimeMillis: 450,         // ❌ Slow
    totalDocsExamined: 150,
    executionStages: {
      stage: "SORT",                  // ❌ In-memory sort
      sortPattern: { orderDate: -1 },
      memUsage: 15360,
      inputStage: {
        stage: "FETCH",
        inputStage: {
          stage: "IXSCAN",            // ✅ Uses index for filter
          indexName: "status_1",
          keysExamined: 150
        }
      }
    }
  }
}
```

**Analysis:**
- ✅ Uses index for filter
- ❌ Sort not covered by index (in-memory sort)
- **Solution:** Compound index `{status: 1, orderDate: -1}`

### Calculating Query Efficiency

**Index Selectivity:**
```javascript
Selectivity = keysExamined / nReturned
```
- **1.0 = Perfect:** Every examined key returned a result
- **< 2.0 = Good:** Index is selective
- **> 10.0 = Poor:** Index not selective, many keys examined per result

**Example:**
```javascript
{
  nReturned: 10,
  totalKeysExamined: 150
}
// Selectivity = 150 / 10 = 15 (Poor)
// Index scanned 15 keys per returned document
```

**Document Examination Ratio:**
```javascript
Ratio = totalDocsExamined / nReturned
```
- **1.0 = Perfect:** Every examined document was returned
- **< 2.0 = Good:** Efficient document examination
- **> 10.0 = Poor:** Too many documents examined

### Covered Query Verification

A covered query returns results from the index without fetching documents.

**Indicators:**
- `totalDocsExamined: 0`
- No FETCH stage
- PROJECTION_COVERED stage present

**Example:**
```javascript
// Create compound index
db.users.createIndex({ country: 1, age: 1, email: 1 })

// Covered query
db.users.find(
  { country: "USA", age: { $gte: 25 } },
  { _id: 0, email: 1 }  // Only project indexed fields
).explain("executionStats")
```

**Output:**
```javascript
{
  executionStats: {
    nReturned: 50,
    totalKeysExamined: 50,
    totalDocsExamined: 0,             // ✅ Covered: No docs examined
    executionStages: {
      stage: "PROJECTION_COVERED",    // ✅ Covered query
      inputStage: {
        stage: "IXSCAN",
        indexName: "country_1_age_1_email_1",
        keysExamined: 50
      }
    }
  }
}
```

### Comparing Index Options

Use explain() to compare different index strategies:

```javascript
// Scenario: Find orders by status, sorted by date

// Option 1: No index
db.orders.find({ status: "shipped" }).sort({ orderDate: -1 })
  .explain("executionStats")
// Result: COLLSCAN + SORT (slow)

// Create index
db.orders.createIndex({ status: 1 })

// Option 2: Single-field index
db.orders.find({ status: "shipped" }).sort({ orderDate: -1 })
  .explain("executionStats")
// Result: IXSCAN + SORT (better, but still in-memory sort)

// Create compound index
db.orders.createIndex({ status: 1, orderDate: -1 })

// Option 3: Compound index
db.orders.find({ status: "shipped" }).sort({ orderDate: -1 })
  .explain("executionStats")
// Result: IXSCAN (best, no sort needed)
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

Given a `products` collection with 100,000 documents:

```javascript
{
  _id: ObjectId("..."),
  name: "Laptop",
  category: "Electronics",
  price: 1200,
  stock: 15,
  rating: 4.5
}
```

**Existing indexes:**
```javascript
{ _id: 1 }
{ category: 1 }
```

**Run explain() on these queries and analyze:**

1. **Query A:**
   ```javascript
   db.products.find({ category: "Electronics", price: { $gt: 500 } })
     .sort({ price: 1 })
     .explain("executionStats")
   ```

2. **Query B:**
   ```javascript
   db.products.find({ price: { $gte: 100, $lte: 1000 } })
     .explain("executionStats")
   ```

3. **Query C:**
   ```javascript
   db.products.find(
     { category: "Electronics" },
     { _id: 0, name: 1, price: 1 }
   ).explain("executionStats")
   ```

**For each query, determine:**
- Is an index being used? Which one?
- What stages are present?
- Is there an in-memory sort?
- What's the keysExamined/nReturned ratio?
- What index would optimize this query?
