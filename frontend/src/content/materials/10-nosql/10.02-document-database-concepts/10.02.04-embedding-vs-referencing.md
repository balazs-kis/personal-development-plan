# Lesson 4: Embedding vs Referencing

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the difference between embedding and referencing data
- Identify when to embed data and when to reference it
- Apply data modeling patterns for different relationship types
- Recognize the trade-offs between embedding and referencing

---

## Introduction

One of the most important decisions in document database modeling is whether to embed related data within a document or reference it in a separate collection. This decision significantly impacts query performance, data consistency, and application complexity. Unlike relational databases where normalization is the default, document databases encourage denormalization through embedding when it makes sense for your access patterns.

## Key Concepts Summary

### The Fundamental Principle

**MongoDB's Golden Rule:**
> Data that is accessed together should be stored together.

Your schema should reflect your application's data access patterns, not abstract data relationships.

### Embedding Data

**Embedding** means storing related data within a single document:

```javascript
// Embedded document example
{
  _id: ObjectId("..."),
  title: "Introduction to MongoDB",
  author: {
    name: "Alice Johnson",
    email: "alice@example.com",
    bio: "Database expert"
  },
  comments: [
    {
      userId: "user123",
      text: "Great article!",
      date: ISODate("2026-01-27")
    },
    {
      userId: "user456",
      text: "Very helpful",
      date: ISODate("2026-01-26")
    }
  ],
  tags: ["mongodb", "database", "tutorial"],
  publishedDate: ISODate("2026-01-15")
}
```

**Advantages of Embedding:**
- **Better read performance:** All data retrieved in one query
- **Atomic updates:** Update all related data in a single operation
- **Simpler queries:** No joins needed
- **Data locality:** Related data stored together on disk

**Disadvantages of Embedding:**
- **Document size limits:** MongoDB has 16MB per document limit
- **Data duplication:** Same data may be embedded in multiple documents
- **Update complexity:** Must update data in multiple places
- **Unbounded growth:** Arrays can grow indefinitely

### Referencing Data

**Referencing** means storing references to documents in other collections:

```javascript
// Referenced documents example

// Posts collection
{
  _id: ObjectId("post123"),
  title: "Introduction to MongoDB",
  authorId: ObjectId("author456"),  // Reference to author
  commentIds: [                      // References to comments
    ObjectId("comment789"),
    ObjectId("comment012")
  ],
  tags: ["mongodb", "database"],
  publishedDate: ISODate("2026-01-15")
}

// Authors collection
{
  _id: ObjectId("author456"),
  name: "Alice Johnson",
  email: "alice@example.com",
  bio: "Database expert"
}

// Comments collection
{
  _id: ObjectId("comment789"),
  postId: ObjectId("post123"),  // Back-reference to post
  userId: "user123",
  text: "Great article!",
  date: ISODate("2026-01-27")
}
```

**Advantages of Referencing:**
- **No duplication:** Single source of truth
- **Smaller documents:** No risk of hitting 16MB limit
- **Easy updates:** Update data in one place
- **Flexibility:** Can query entities independently

**Disadvantages of Referencing:**
- **Multiple queries:** Or use $lookup (like SQL JOIN)
- **No atomicity across documents:** Need transactions for consistency
- **Complexity:** Application must manage references

### When to Embed

**Embed when:**

**1. One-to-Few Relationships:**
```javascript
// User with few addresses (1-3 addresses)
{
  _id: "user123",
  name: "Alice",
  addresses: [
    { type: "home", street: "123 Main St", city: "Springfield" },
    { type: "work", street: "456 Oak Ave", city: "Shelbyville" }
  ]
}
```

**2. Data Accessed Together:**
```javascript
// Blog post always displayed with comments
{
  _id: "post123",
  title: "My Post",
  content: "...",
  comments: [
    { user: "Bob", text: "Nice!" },
    { user: "Charlie", text: "Thanks!" }
  ]
}
```

**3. Child Data Belongs to Parent:**
```javascript
// Order items belong only to that order
{
  _id: "order123",
  customer: "Alice",
  items: [
    { product: "Widget", quantity: 2, price: 9.99 },
    { product: "Gadget", quantity: 1, price: 19.99 }
  ],
  total: 39.97
}
```

**4. Data Changes Together:**
```javascript
// User profile fields updated together
{
  _id: "user123",
  profile: {
    firstName: "Alice",
    lastName: "Johnson",
    avatar: "...",
    bio: "..."
  }
}
```

### When to Reference

**Reference when:**

**1. One-to-Many (Unbounded):**
```javascript
// Publisher with thousands of books
// Publishers collection
{ _id: "pub123", name: "TechBooks Inc" }

// Books collection
{ _id: "book456", title: "MongoDB Guide", publisherId: "pub123" }
{ _id: "book789", title: "Node.js Basics", publisherId: "pub123" }
// ... thousands more
```

**2. Many-to-Many Relationships:**
```javascript
// Students and Courses

// Students collection
{
  _id: "student123",
  name: "Alice",
  enrolledCourses: ["course456", "course789"]
}

// Courses collection
{
  _id: "course456",
  title: "Database Design",
  enrolledStudents: ["student123", "student999"]
}
```

**3. Data Queried Independently:**
```javascript
// Products and Categories
// Often need to list all categories separately

// Categories collection
{ _id: "cat123", name: "Electronics" }

// Products collection
{ _id: "prod456", name: "Laptop", categoryId: "cat123" }
```

**4. Large or Frequently Updated Data:**
```javascript
// User account (small, stable) vs activity log (large, changing)

// Users collection
{ _id: "user123", name: "Alice", email: "alice@example.com" }

// Activity collection
{ _id: "act456", userId: "user123", action: "login", timestamp: ... }
{ _id: "act457", userId: "user123", action: "view_page", timestamp: ... }
// ... thousands of activity records
```

### Hybrid Approach: Subset Pattern

Embed a subset of frequently accessed fields and reference the full data:

```javascript
// Posts collection - embed author summary
{
  _id: "post123",
  title: "Introduction to MongoDB",
  authorSummary: {                    // Embedded subset
    id: ObjectId("author456"),
    name: "Alice Johnson",
    avatar: "avatar-url"
  },
  content: "..."
}

// Authors collection - full author data
{
  _id: ObjectId("author456"),
  name: "Alice Johnson",
  email: "alice@example.com",
  bio: "Long biography...",
  socialLinks: { ... },
  publishedPosts: [...],
  // ... more fields
}
```

### Querying Referenced Data

**Using $lookup (Aggregation Join):**
```javascript
// Find posts with author details
db.posts.aggregate([
  {
    $lookup: {
      from: "authors",           // Collection to join
      localField: "authorId",    // Field in posts
      foreignField: "_id",       // Field in authors
      as: "authorDetails"        // Output array name
    }
  },
  {
    $unwind: "$authorDetails"    // Convert array to object
  }
])
```

**Application-Level Joins:**
```javascript
// Two queries in application code
const post = await db.posts.findOne({ _id: "post123" });
const author = await db.authors.findOne({ _id: post.authorId });

// Combine in application
post.author = author;
```

### Decision Matrix

| Factor | Embed | Reference |
|--------|-------|-----------|
| **Relationship size** | One-to-few | One-to-many (unbounded) |
| **Access pattern** | Always together | Often separate |
| **Update frequency** | Rare | Frequent |
| **Data duplication** | Acceptable | Must avoid |
| **Document size** | Small | Could be large |
| **Atomicity needed** | Yes | No (or use transactions) |
| **Query performance** | Critical | Less critical |

### Real-World Examples

**Example 1: Blog Platform**
```javascript
// EMBED: Comments (assuming limited per post, always shown with post)
{
  _id: "post123",
  title: "My Post",
  comments: [
    { user: "Bob", text: "Nice!", date: ISODate("...") }
  ]
}

// REFERENCE: Author (reused across many posts, updated independently)
{
  _id: "post123",
  title: "My Post",
  authorId: "author456"
}
```

**Example 2: E-Commerce**
```javascript
// EMBED: Order items (belong only to this order, atomic)
{
  _id: "order123",
  items: [
    { productId: "prod456", name: "Widget", price: 9.99, quantity: 2 }
  ]
}

// REFERENCE: Product details (shared across orders, frequently updated)
{
  _id: "order123",
  items: [
    { productId: "prod456", quantity: 2, priceAtPurchase: 9.99 }
  ]
}

// Products collection
{
  _id: "prod456",
  name: "Widget",
  currentPrice: 8.99,  // Price changed after order
  description: "...",
  inventory: 100
}
```

**Example 3: Social Network**
```javascript
// EMBED: User profile fields (accessed together)
{
  _id: "user123",
  profile: {
    name: "Alice",
    bio: "...",
    location: "Springfield"
  }
}

// REFERENCE: Friendships (many-to-many, queried independently)
{
  _id: "friendship123",
  user1: "user123",
  user2: "user456",
  since: ISODate("2024-01-01")
}
```

### Common Patterns

**1. Extended Reference Pattern:**
```javascript
// Cache frequently accessed fields from referenced doc
{
  _id: "order123",
  productId: "prod456",
  productName: "Widget",        // Cached from products
  productPrice: 9.99,           // Cached from products
  quantity: 2
}
```

**2. Bucketing Pattern:**
```javascript
// Group related documents to avoid unbounded arrays
// Time-series data bucketed by hour
{
  _id: "sensor_ABC_2026-01-27-10",
  sensor: "ABC",
  hour: ISODate("2026-01-27T10:00:00Z"),
  readings: [
    { temp: 72, time: "10:00:15" },
    { temp: 73, time: "10:15:22" },
    // ... more readings this hour
  ]
}
```

**3. Computed Pattern:**
```javascript
// Embed computed/aggregated data to avoid recalculation
{
  _id: "movie123",
  title: "Inception",
  averageRating: 4.7,           // Computed from ratings
  totalRatings: 1523,           // Count
  ratings: [                    // Or reference to ratings collection
    { userId: "user456", rating: 5 },
    // ...
  ]
}
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

Design a data model for a library management system:

**Entities:**
- Books (title, ISBN, author(s), publisher, publication date)
- Authors (name, bio, birth date)
- Publishers (name, address, contact)
- Members (name, email, membership date)
- Loans (member, book, checkout date, due date, return date)

**Decide for each relationship:**
1. Should it be embedded or referenced?
2. Why did you choose that approach?
3. What are the trade-offs?

**Hint:** Consider:
- How many authors per book?
- How many books per author?
- Are loans temporary or permanent data?
- What data is queried together?
