## Introduction

Column-family stores (also called wide-column stores) organize data by columns rather than rows. Unlike relational databases where all rows have the same columns, column-family stores allow each row to have different columns. They excel at storing and querying massive datasets across distributed clusters, making them ideal for big data and analytics workloads.

## Key Concepts Summary

### What is a Column-Family Store?

Column-family stores organize data into rows and columns, but unlike relational databases:
- Each row can have different columns
- Columns are grouped into column families
- Data is stored and retrieved by row key
- Optimized for reading and writing columns, not rows

**Conceptual Model:**
```
Row Key: user_123
  ColumnFamily: profile
    - name: "Alice Johnson"
    - email: "alice@example.com"
    - joined: "2024-01-15"
  ColumnFamily: activity
    - last_login: "2026-01-27"
    - login_count: "247"

Row Key: user_456
  ColumnFamily: profile
    - name: "Bob Smith"
    - location: "New York"  // Note: different columns than user_123
  ColumnFamily: activity
    - last_login: "2026-01-26"
```

### Key Characteristics

**Flexible Columns:** Each row can have different columns within a column family. No fixed schema.

**Column-Oriented Storage:** Data is physically stored by column rather than row, enabling efficient compression and fast column scans.

**Distributed Architecture:** Designed from the ground up for horizontal scaling across many nodes.

**Eventual Consistency:** Most column stores prioritize availability and partition tolerance over strong consistency.

**Write-Optimized:** Typically optimized for high write throughput using techniques like log-structured merge trees.

### Apache Cassandra

**Architecture:**
- Peer-to-peer distributed system (no master node)
- Inspired by Amazon Dynamo and Google BigTable
- Uses consistent hashing for data distribution
- Tunable consistency levels

**Key Features:**
- Linear scalability—add nodes to increase capacity
- High availability with no single point of failure
- Multi-datacenter replication
- CQL (Cassandra Query Language) similar to SQL

**Data Model:**
```cql
CREATE TABLE users (
    user_id UUID PRIMARY KEY,
    username TEXT,
    email TEXT,
    created_at TIMESTAMP
);

-- Partition key determines data distribution
CREATE TABLE posts_by_user (
    user_id UUID,
    post_id UUID,
    title TEXT,
    content TEXT,
    created_at TIMESTAMP,
    PRIMARY KEY (user_id, created_at)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

**When to Use Cassandra:**
- High write throughput requirements
- Need for linear scalability
- Multi-datacenter deployment
- Time-series data
- No single point of failure tolerance

### Apache HBase

**Architecture:**
- Built on top of Hadoop HDFS
- Master-slave architecture (not peer-to-peer)
- Strong consistency model
- Part of the Hadoop ecosystem

**Key Features:**
- ACID guarantees at row level
- Strongly consistent reads and writes
- Integration with MapReduce and Spark
- Automatic sharding and load balancing

**Data Model:**
```
Table: users
  Row Key: user_123
    Column Family: profile
      profile:name => "Alice Johnson" [timestamp: 1706371200]
      profile:email => "alice@example.com" [timestamp: 1706371200]
    Column Family: activity
      activity:last_login => "2026-01-27" [timestamp: 1706457600]
```

**When to Use HBase:**
- Already using Hadoop ecosystem
- Need strong consistency
- Large, sparse datasets
- Random, real-time read/write access to big data
- Batch processing with MapReduce/Spark

### Cassandra vs. HBase

| Aspect | Cassandra | HBase |
|--------|-----------|-------|
| **Architecture** | Peer-to-peer | Master-slave |
| **Consistency** | Tunable (eventual by default) | Strong |
| **Write Performance** | Extremely high | High |
| **Read Performance** | High | Very high for consistent reads |
| **Ecosystem** | Standalone | Hadoop/HDFS |
| **Single Point of Failure** | No | Yes (master node) |

### When to Use Column-Family Stores

**Ideal Use Cases:**
- Time-series data (sensor data, logs, metrics)
- Event logging and audit trails
- IoT and telemetry data
- Recommendation engines
- Content management systems
- Messaging and chat applications
- Large-scale analytics

**Not Ideal For:**
- Complex queries with many joins
- Transactions across multiple rows/tables
- Ad-hoc queries (requires predefined access patterns)
- Small datasets (overhead not worth it)

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Design a data model for an IoT temperature monitoring system using Cassandra:

**Requirements:**
- Store temperature readings from thousands of sensors
- Query patterns: Get all readings for a sensor in a time range
- Write-heavy: New readings every 10 seconds per sensor
- Reads: Dashboard showing last 24 hours for selected sensors

Consider:
1. What should be the partition key?
2. What should be the clustering key?
3. How would you optimize for the query pattern?

Sketch out a CQL table definition.
