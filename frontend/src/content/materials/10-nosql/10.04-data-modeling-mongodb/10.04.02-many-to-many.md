# Lesson 2: Many-to-Many Relationships

## Learning Objectives

By the end of this lesson, you will be able to:
- Model many-to-many relationships using array references
- Decide between embedding and referencing for bidirectional relationships
- Apply denormalization strategies for frequently accessed data
- Avoid common pitfalls with unbounded array growth

---

## Introduction

Many-to-many relationships are common in applications: students take multiple courses, products belong to multiple categories, users have multiple roles. Unlike relational databases where you'd use a join table, MongoDB offers flexible strategies using arrays of references or embedded documents. Your choice depends on which side of the relationship is queried most frequently and the cardinality of the relationship.

## Key Concepts Summary

### Pattern 1: Array of References on Both Sides

**Use when both sides need to query the relationship:**

```javascript
// Book document
{
  _id: "book001",
  title: "MongoDB Patterns",
  isbn: "978-1234567890",
  author_ids: ["author123", "author456"]
}

// Author document
{
  _id: "author123",
  name: "Jane Smith",
  book_ids: ["book001", "book002", "book003"]
}
```

**Characteristics:**
- Bidirectional navigation
- Requires two updates when creating/removing relationships
- Risk of data inconsistency (arrays can get out of sync)
- Good when both sides are frequently queried

### Pattern 2: Array of References on One Side Only

**Use when queries predominantly go one direction:**

```javascript
// Student document
{
  _id: "student001",
  name: "Alice Johnson",
  email: "alice@example.com",
  course_ids: ["course101", "course102", "course103"]
}

// Course document (no reference to students)
{
  _id: "course101",
  title: "Introduction to Databases",
  code: "CS-101"
}
```

**Characteristics:**
- Simpler to maintain (single source of truth)
- Queries from the side with references are efficient
- Queries from the other side require lookups (less efficient)
- Choose the side based on your primary access pattern

### Pattern 3: Embedded Documents with Denormalization

**Use when you need quick access to key attributes:**

```javascript
// Book document with embedded author info
{
  _id: "book001",
  title: "Cell Biology",
  authors: [
    { author_id: "author124", name: "Ellie Smith" },
    { author_id: "author381", name: "John Palmer" }
  ]
}

// Full author document (separate collection)
{
  _id: "author124",
  name: "Ellie Smith",
  bio: "Professor of Biology...",
  publications: [...]
}
```

**Characteristics:**
- Fast reads (no joins needed)
- Data duplication (author names stored in multiple places)
- Requires careful update strategy when author names change
- Best when embedded data rarely changes

### Pattern 4: Separate Junction Collection (SQL-like)

**Use for complex many-to-many with relationship metadata:**

```javascript
// Student document
{
  _id: "student001",
  name: "Bob Wilson"
}

// Course document
{
  _id: "course101",
  title: "Advanced Algorithms"
}

// Enrollment junction document
{
  _id: "enrollment001",
  student_id: "student001",
  course_id: "course101",
  enrolled_date: ISODate("2026-01-15"),
  grade: "A",
  status: "completed"
}
```

**Characteristics:**
- Stores metadata about the relationship
- Similar to SQL join table approach
- Requires multiple queries to navigate
- Good when relationship itself has significant attributes

## Decision Framework

**Choose your pattern based on:**

1. **Query Pattern:** Which side do you query most often?
   - Mostly query from students → Store course_ids in students
   - Mostly query from courses → Store student_ids in courses
   - Query equally → Store references on both sides or use junction

2. **Relationship Cardinality:**
   - Bounded small numbers → Array of references is fine
   - One side unbounded → Use references on bounded side only
   - Both sides unbounded → Use junction collection

3. **Need for Relationship Metadata:**
   - Yes → Use junction collection pattern
   - No → Use array references

4. **Read vs Write Performance:**
   - Read-heavy with stable data → Denormalize (embed key fields)
   - Write-heavy or frequently changing → Keep normalized (references only)

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Design a schema for a social media application with the following requirements:

- Users can follow other users (bidirectional queries needed)
- Users can like posts (primarily query: "show all posts liked by user X")
- Posts can have multiple tags, tags can belong to multiple posts
- Track when a user liked a post (relationship metadata)

For each relationship, decide:
1. Which many-to-many pattern to use
2. Where to store references (one side, both sides, or junction)
3. Whether to denormalize any data
