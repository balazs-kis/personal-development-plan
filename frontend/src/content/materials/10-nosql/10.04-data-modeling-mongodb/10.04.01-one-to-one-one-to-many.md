# Lesson 1: One-to-One and One-to-Many Relationships

## Learning Objectives

By the end of this lesson, you will be able to:
- Model one-to-one relationships using embedded documents
- Distinguish between one-to-few, one-to-many, and one-to-squillions patterns
- Choose appropriate strategies for different cardinalities
- Apply embedding and referencing based on access patterns

---

## Introduction

MongoDB's flexible document model allows you to represent relationships differently than relational databases. The key principle is: **data that is accessed together should be stored together**. Understanding relationship cardinality helps you choose between embedding and referencing to optimize both performance and data integrity.

## Key Concepts Summary

### One-to-One Relationships

**Embedded Approach (Preferred):**
```javascript
// Patron document with embedded address
{
  _id: "joe",
  name: "Joe Bookreader",
  address: {
    street: "123 Fake Street",
    city: "Faketon",
    state: "MA",
    zip: "12345"
  }
}
```

**When to use:**
- Related data is always accessed together
- The relationship is truly 1:1 (e.g., user to user profile)
- Document size remains manageable

### One-to-Few (< ~10 items)

**Embed the related documents:**
```javascript
// Person document with addresses
{
  _id: "person123",
  name: "John Smith",
  addresses: [
    { type: "home", street: "123 Main St", city: "Springfield" },
    { type: "work", street: "456 Office Blvd", city: "Capital City" }
  ]
}
```

**Characteristics:**
- Small, bounded number of related items
- Related data accessed with parent document
- Enables atomic updates of parent and children together

### One-to-Many (10-1000 items)

**Use references on the "many" side:**
```javascript
// Product document
{
  _id: "product789",
  name: "Widget",
  description: "A useful widget"
}

// Parts documents (reference the product)
{
  _id: "part001",
  partNumber: "XYZ-123",
  product_id: "product789",
  quantity: 5
}
```

**Why reference instead of embed:**
- Avoids creating large arrays that grow unbounded
- Allows querying the "many" side independently
- Prevents document growth issues

### One-to-Squillions (> 1000 items)

**Use parent reference on the "many" side:**
```javascript
// Host document
{
  _id: "host1.example.com",
  hostname: "host1.example.com",
  ipaddr: "192.168.1.100"
}

// Log entries (millions) reference the host
{
  _id: ObjectId("..."),
  timestamp: ISODate("2026-01-27T10:00:00Z"),
  host_id: "host1.example.com",
  message: "System started"
}
```

**Characteristics:**
- Extremely high cardinality
- Never try to embed or maintain array of references
- Always query from the "many" side to the "one" side

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Model the following scenarios and decide whether to use embedding or referencing:

1. **Blog Post and Comments:** A blog where posts can have 0-500 comments
2. **User and Login History:** A user account with millions of login attempts over time
3. **Order and Line Items:** An e-commerce order with 1-20 product line items
4. **Company and Employees:** A company with 1-10,000 employees

For each scenario, justify your choice based on:
- Expected cardinality
- Access patterns
- Update frequency
- Document size considerations
