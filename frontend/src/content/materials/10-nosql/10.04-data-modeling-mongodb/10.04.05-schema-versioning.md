## Learning Objectives

By the end of this lesson, you will be able to:
- Implement schema versioning to support zero-downtime migrations
- Handle multiple document versions in the same collection
- Design migration strategies for evolving schemas
- Balance the trade-offs between immediate and lazy migration

---

## Introduction

Unlike relational databases that require expensive schema migrations, MongoDB's flexible schema allows different document shapes to coexist in the same collection. This enables zero-downtime deployments where old and new code can run simultaneously, each handling its expected document format. Schema versioning is essential for large-scale applications where migrating millions of documents would cause unacceptable downtime.

## Key Concepts Summary

### The Schema Versioning Pattern

**Core Concept:** Add a `schema_version` field to documents to track their structure version, allowing multiple versions to coexist.

**Basic Implementation:**

```javascript
// Version 1 (original) - no schema_version field
{
  _id: "contact001",
  name: "John Smith",
  home: "555-1234",
  work: "555-5678"
}

// Version 2 (restructured) - with schema_version field
{
  _id: "contact002",
  name: "Jane Doe",
  schema_version: 2,
  contactInfo: {
    home: { type: "phone", number: "555-9999" },
    work: { type: "phone", number: "555-8888" },
    mobile: { type: "phone", number: "555-7777" }
  }
}

// Version 3 (further evolved)
{
  _id: "contact003",
  name: "Bob Wilson",
  schema_version: 3,
  contactInfo: {
    phones: [
      { type: "home", number: "555-1111", primary: true },
      { type: "work", number: "555-2222", primary: false }
    ],
    emails: [
      { type: "personal", address: "bob@example.com" }
    ]
  }
}
```

**Application Code Handles Multiple Versions:**

```javascript
function getPhoneNumbers(contact) {
  // No schema_version means version 1
  if (!contact.schema_version) {
    return {
      home: contact.home,
      work: contact.work
    };
  }
  
  // Version 2
  if (contact.schema_version === 2) {
    return {
      home: contact.contactInfo.home?.number,
      work: contact.contactInfo.work?.number
    };
  }
  
  // Version 3
  if (contact.schema_version === 3) {
    const result = {};
    contact.contactInfo.phones.forEach(phone => {
      result[phone.type] = phone.number;
    });
    return result;
  }
  
  throw new Error(`Unsupported schema version: ${contact.schema_version}`);
}
```

### Migration Strategies

**1. Lazy Migration (Migrate on Write)**

Update documents to the new version only when they're modified:

```javascript
async function updateContact(contactId, updates) {
  const contact = await db.contacts.findOne({ _id: contactId });
  
  // Migrate to latest version if needed
  if (!contact.schema_version || contact.schema_version < 3) {
    const migrated = migrateToV3(contact);
    await db.contacts.replaceOne({ _id: contactId }, migrated);
  }
  
  // Now apply the actual updates
  await db.contacts.updateOne(
    { _id: contactId },
    { $set: updates }
  );
}

function migrateToV3(contact) {
  if (!contact.schema_version) {
    // Migrate from V1 to V3
    return {
      _id: contact._id,
      name: contact.name,
      schema_version: 3,
      contactInfo: {
        phones: [
          { type: "home", number: contact.home, primary: true },
          { type: "work", number: contact.work, primary: false }
        ],
        emails: []
      }
    };
  }
  
  if (contact.schema_version === 2) {
    // Migrate from V2 to V3
    const phones = [];
    if (contact.contactInfo.home) {
      phones.push({
        type: "home",
        number: contact.contactInfo.home.number,
        primary: true
      });
    }
    if (contact.contactInfo.work) {
      phones.push({
        type: "work",
        number: contact.contactInfo.work.number,
        primary: false
      });
    }
    
    return {
      _id: contact._id,
      name: contact.name,
      schema_version: 3,
      contactInfo: {
        phones: phones,
        emails: []
      }
    };
  }
  
  return contact; // Already V3
}
```

**Pros:**
- Zero downtime
- No bulk migration needed
- Documents migrated only if they're accessed
- Gradual, risk-free deployment

**Cons:**
- Old versions persist indefinitely
- Application must handle all versions forever
- Queries may need to check multiple field locations

**2. Background Batch Migration**

Migrate all documents in batches during low-traffic periods:

```javascript
async function migrateBatch(batchSize = 1000) {
  const session = client.startSession();
  
  try {
    await session.withTransaction(async () => {
      // Find documents needing migration
      const docs = await db.contacts.find({
        $or: [
          { schema_version: { $exists: false } },  // V1
          { schema_version: { $lt: 3 } }            // V2
        ]
      })
      .limit(batchSize)
      .toArray();
      
      // Migrate each document
      const bulkOps = docs.map(doc => ({
        replaceOne: {
          filter: { _id: doc._id },
          replacement: migrateToV3(doc)
        }
      }));
      
      if (bulkOps.length > 0) {
        await db.contacts.bulkWrite(bulkOps);
      }
      
      return docs.length;
    });
  } finally {
    await session.endSession();
  }
}

// Run migration job
async function runMigration() {
  let migrated = 0;
  let batchCount;
  
  do {
    batchCount = await migrateBatch(1000);
    migrated += batchCount;
    console.log(`Migrated ${migrated} documents so far...`);
    
    // Pause between batches to avoid overwhelming the database
    await new Promise(resolve => setTimeout(resolve, 100));
  } while (batchCount > 0);
  
  console.log(`Migration complete: ${migrated} documents migrated`);
}
```

**Pros:**
- Eventually all documents use new schema
- Can remove old version handling code later
- Controlled migration pace

**Cons:**
- Still requires zero-downtime handling during migration
- Resource intensive
- May take hours/days for large collections

**3. Dual-Write Strategy**

When adding a new field or structure, write to both old and new formats:

```javascript
// During transition period: write both formats
async function createContact(name, phones) {
  const contact = {
    _id: new ObjectId(),
    name: name,
    
    // OLD format (V1) - for compatibility
    home: phones.find(p => p.type === 'home')?.number || '',
    work: phones.find(p => p.type === 'work')?.number || '',
    
    // NEW format (V3) - going forward
    schema_version: 3,
    contactInfo: {
      phones: phones,
      emails: []
    }
  };
  
  await db.contacts.insertOne(contact);
  return contact;
}
```

**Pros:**
- Read path can use either format
- Gradual migration
- Easy rollback

**Cons:**
- Temporary data duplication
- Increased write cost
- Must keep formats in sync

### Querying Across Versions

**Challenge:** Fields moved between versions require complex queries.

```javascript
// Find all contacts with specific work phone
// Must check all possible locations across versions

db.contacts.find({
  $or: [
    { work: "555-5678" },                          // V1
    { "contactInfo.work.number": "555-5678" },     // V2
    { "contactInfo.phones": {                       // V3
        $elemMatch: {
          type: "work",
          number: "555-5678"
        }
      }
    }
  ]
})
```

**Solution Options:**

1. **Computed field:** Maintain a normalized field for queries
   ```javascript
   {
     _id: "contact001",
     schema_version: 3,
     work_phone: "555-5678",  // Computed field for queries
     contactInfo: { ... }      // Full structured data
   }
   ```

2. **Indexing strategy:** Create indexes on all field locations
   ```javascript
   db.contacts.createIndex({ work: 1 });
   db.contacts.createIndex({ "contactInfo.work.number": 1 });
   db.contacts.createIndex({ "contactInfo.phones.number": 1 });
   ```

3. **Accept migration debt:** Finish background migration to eliminate old versions

### Best Practices

**1. Version Field Conventions:**
- Use `schema_version` or `_schema_version`
- Omit field for version 1 (reduces storage for initial documents)
- Increment version with each breaking change
- Document what changed in each version

**2. Version Lifecycle:**
- Limit supported versions (e.g., current + 2 previous)
- Plan deprecation timeline
- Log usage of old versions to track migration progress

**3. Testing:**
- Test application with all supported versions
- Automated tests should use multiple version documents
- Monitor for documents with unexpected versions

You have a `products` collection with this schema:

```javascript
// Current schema (implicit V1)
{
  _id: "prod123",
  name: "Widget",
  price: 29.99,
  category: "Tools"
}
```

You need to evolve it to support:
- Multiple categories (array instead of string)
- Price history (track price changes over time)
- Localized names (different names per language)

**Tasks:**
1. Design a V2 schema that supports these requirements
2. Write a migration function that converts V1 → V2
3. Write a query function that works with both V1 and V2
4. Decide: lazy migration, background batch, or dual-write?
5. How would you query for products in a specific category across both versions?
