## Introduction

Caching is more than just storing data in Redis—it requires thoughtful strategies for reading, writing, invalidating, and refreshing cached data. Different caching patterns suit different use cases, and choosing the right pattern can dramatically impact application performance, consistency, and complexity.

## Key Concepts Summary

### 1. Cache-Aside (Lazy Loading)

The most common caching pattern where the application manages the cache explicitly.

#### How It Works

```
1. Application requests data
2. Check cache first
3. If HIT: Return cached data
4. If MISS:
   a. Load from database
   b. Store in cache with TTL
   c. Return data
```

#### Implementation Pattern

```csharp
public async Task<Product> GetProductAsync(int productId)
{
    var cacheKey = $"product:{productId}";
    
    // Try to get from cache
    var cachedProduct = await _cache.GetStringAsync(cacheKey);
    
    if (cachedProduct != null)
    {
        // Cache HIT
        _logger.LogInformation("Cache hit for {Key}", cacheKey);
        return JsonSerializer.Deserialize<Product>(cachedProduct);
    }
    
    // Cache MISS - load from database
    _logger.LogInformation("Cache miss for {Key}", cacheKey);
    var product = await _database.Products
        .FirstOrDefaultAsync(p => p.Id == productId);
    
    if (product != null)
    {
        // Store in cache with 5-minute expiration
        var serialized = JsonSerializer.Serialize(product);
        await _cache.SetStringAsync(
            cacheKey,
            serialized,
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            }
        );
    }
    
    return product;
}
```

#### Write Operations

```csharp
public async Task<Product> UpdateProductAsync(Product product)
{
    // Update database
    _database.Products.Update(product);
    await _database.SaveChangesAsync();
    
    // Invalidate cache
    var cacheKey = $"product:{product.Id}";
    await _cache.RemoveAsync(cacheKey);
    
    // Alternative: Update cache immediately
    // var serialized = JsonSerializer.Serialize(product);
    // await _cache.SetStringAsync(cacheKey, serialized, ...);
    
    return product;
}
```

#### Pros and Cons

**Pros:**
- Simple to implement and understand
- Only caches data that's actually requested (efficient memory usage)
- Resilient: Cache failure doesn't prevent database access
- Database is always the source of truth

**Cons:**
- Initial requests always miss cache (cold start)
- Cache misses cause latency spikes (database query + cache write)
- Potential for stale data if updates don't invalidate cache
- Thundering herd problem on popular keys after expiration

### 2. Read-Through

Cache acts as an intermediary that automatically loads data from the database.

#### How It Works

```
1. Application requests data from cache
2. Cache checks if data exists
3. If HIT: Cache returns data
4. If MISS:
   a. Cache loads from database (application doesn't know)
   b. Cache stores data
   c. Cache returns data
```

#### Implementation (Conceptual - requires cache provider support)

```csharp
// The cache provider handles database loading
public async Task<Product> GetProductAsync(int productId)
{
    var cacheKey = $"product:{productId}";
    
    // Cache handles database loading automatically
    var product = await _smartCache.GetAsync(
        cacheKey,
        async () => await _database.Products
            .FirstOrDefaultAsync(p => p.Id == productId)
    );
    
    return product;
}
```

#### Pros and Cons

**Pros:**
- Application code is cleaner (no explicit cache miss handling)
- Consistent caching logic across application
- Database loading logic centralized

**Cons:**
- Requires cache provider support or custom implementation
- Cache becomes more complex
- Harder to debug cache behavior

### 3. Write-Through

Data is written to cache and database synchronously.

#### How It Works

```
1. Application writes data
2. Write to cache
3. Cache writes to database (synchronously)
4. Acknowledge success when both complete
```

#### Implementation Pattern

```csharp
public async Task UpdateProductAsync(Product product)
{
    var cacheKey = $"product:{product.Id}";
    
    // Start transaction or use distributed transaction
    using var transaction = await _database.Database.BeginTransactionAsync();
    
    try
    {
        // Update database
        _database.Products.Update(product);
        await _database.SaveChangesAsync();
        
        // Update cache
        var serialized = JsonSerializer.Serialize(product);
        await _cache.SetStringAsync(cacheKey, serialized);
        
        await transaction.CommitAsync();
    }
    catch
    {
        await transaction.RollbackAsync();
        await _cache.RemoveAsync(cacheKey);
        throw;
    }
}
```

#### Pros and Cons

**Pros:**
- Cache always consistent with database
- No stale data
- Good for read-heavy workloads with occasional writes

**Cons:**
- Write latency (must update both cache and database)
- Increased write complexity
- Potential for partial failures
- Cache contains all data, even rarely accessed

---

### 4. Write-Behind (Write-Back)

Data is written to cache immediately, then asynchronously to database.

#### How It Works

```
1. Application writes to cache
2. Acknowledge success immediately
3. Background process writes to database asynchronously
```

#### Implementation Pattern

```csharp
public async Task UpdateProductAsync(Product product)
{
    var cacheKey = $"product:{product.Id}";
    
    // Write to cache immediately
    var serialized = JsonSerializer.Serialize(product);
    await _cache.SetStringAsync(cacheKey, serialized);
    
    // Queue database write (e.g., using background service)
    await _writeQueue.EnqueueAsync(new DatabaseWrite
    {
        Key = cacheKey,
        Data = product,
        Timestamp = DateTime.UtcNow
    });
    
    // Return immediately
}

// Background worker
public class DatabaseWriteWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var write = await _writeQueue.DequeueAsync(stoppingToken);
            
            try
            {
                // Write to database
                _database.Products.Update(write.Data);
                await _database.SaveChangesAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Failed to write to database");
                // Implement retry logic
            }
        }
    }
}
```

#### Pros and Cons

**Pros:**
- Lowest write latency
- High write throughput
- Batching opportunities (multiple writes can be grouped)

**Cons:**
- Risk of data loss if cache fails before database write
- Complex error handling
- Eventual consistency only
- Requires background processing infrastructure

### 5. Refresh-Ahead (Cache Warming)

Proactively refresh cache before expiration to avoid cache misses.

#### Implementation Pattern

```csharp
public class CacheWarmer : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // Refresh popular/critical data before expiration
            var popularProductIds = await GetPopularProductIds();
            
            foreach (var productId in popularProductIds)
            {
                var cacheKey = $"product:{productId}";
                var ttl = await GetTTL(cacheKey);
                
                // Refresh if TTL < 1 minute
                if (ttl < TimeSpan.FromMinutes(1))
                {
                    var product = await _database.Products
                        .FirstOrDefaultAsync(p => p.Id == productId);
                    
                    var serialized = JsonSerializer.Serialize(product);
                    await _cache.SetStringAsync(
                        cacheKey,
                        serialized,
                        new DistributedCacheEntryOptions
                        {
                            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
                        }
                    );
                }
            }
            
            await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
        }
    }
}
```

## Cache Invalidation Strategies

### 1. Time-Based (TTL)

```csharp
// Fixed expiration
await _cache.SetStringAsync(key, value, new DistributedCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
});

// Sliding expiration (refreshed on each access)
await _cache.SetStringAsync(key, value, new DistributedCacheEntryOptions
{
    SlidingExpiration = TimeSpan.FromMinutes(5)
});
```

### 2. Event-Based

```csharp
// Invalidate on write
public async Task UpdateProductAsync(Product product)
{
    _database.Products.Update(product);
    await _database.SaveChangesAsync();
    
    // Invalidate related caches
    await _cache.RemoveAsync($"product:{product.Id}");
    await _cache.RemoveAsync($"products:category:{product.CategoryId}");
    await _cache.RemoveAsync("products:all");
}
```

### 3. Tag-Based

```csharp
// Cache with tags
public async Task CacheProductWithTagsAsync(Product product)
{
    var cacheKey = $"product:{product.Id}";
    var tags = new[] { "products", $"category:{product.CategoryId}" };
    
    await _cache.SetWithTagsAsync(cacheKey, product, tags);
}

// Invalidate by tag
public async Task InvalidateProductCategoryAsync(int categoryId)
{
    await _cache.InvalidateByTagAsync($"category:{categoryId}");
}
```

## Common Caching Problems and Solutions

### 1. Thundering Herd

**Problem:** Many requests hit cache miss simultaneously, overwhelming database.

**Solution:** Use locking or semaphores:

```csharp
private static readonly SemaphoreSlim _semaphore = new(1, 1);

public async Task<Product> GetProductAsync(int productId)
{
    var cacheKey = $"product:{productId}";
    var cached = await _cache.GetStringAsync(cacheKey);
    
    if (cached != null)
        return JsonSerializer.Deserialize<Product>(cached);
    
    // Only one request loads from database
    await _semaphore.WaitAsync();
    try
    {
        // Double-check cache (another request may have loaded it)
        cached = await _cache.GetStringAsync(cacheKey);
        if (cached != null)
            return JsonSerializer.Deserialize<Product>(cached);
        
        // Load from database
        var product = await _database.Products
            .FirstOrDefaultAsync(p => p.Id == productId);
        
        if (product != null)
        {
            var serialized = JsonSerializer.Serialize(product);
            await _cache.SetStringAsync(cacheKey, serialized);
        }
        
        return product;
    }
    finally
    {
        _semaphore.Release();
    }
}
```

### 2. Cache Stampede

**Problem:** Popular key expires, causing sudden spike in database load.

**Solution:** Probabilistic early expiration:

```csharp
public async Task<Product> GetProductWithSoftTTLAsync(int productId)
{
    var cacheKey = $"product:{productId}";
    var cached = await _cache.GetStringAsync(cacheKey);
    
    if (cached != null)
    {
        var entry = JsonSerializer.Deserialize<CacheEntry<Product>>(cached);
        
        // Refresh probabilistically before expiration
        var age = DateTime.UtcNow - entry.CachedAt;
        var maxAge = TimeSpan.FromMinutes(5);
        var refreshProbability = age.TotalSeconds / maxAge.TotalSeconds;
        
        if (Random.Shared.NextDouble() < refreshProbability)
        {
            // Asynchronously refresh cache
            _ = Task.Run(() => RefreshCacheAsync(productId));
        }
        
        return entry.Value;
    }
    
    // Load and cache
    return await LoadAndCacheProductAsync(productId);
}
```

### 3. Stale Data

**Problem:** Cache contains outdated data.

**Solutions:**
- Set appropriate TTLs
- Invalidate on writes
- Use versioning in cache keys
- Implement pub/sub for distributed invalidation

## Choosing the Right Pattern

| Scenario | Recommended Pattern | Why |
|----------|-------------------|-----|
| General web application | Cache-Aside | Simple, flexible, resilient |
| Read-heavy, infrequent writes | Write-Through | Consistency matters |
| Write-heavy | Write-Behind | Performance matters |
| Critical data consistency | Write-Through | Avoid stale data |
| High-performance APIs | Cache-Aside + Refresh-Ahead | Balance performance and freshness |
| Session management | Cache-Aside with sliding expiration | Natural fit for session timeout |

---

## Best Practices

1. **Always Set TTL:** Prevent unbounded cache growth
2. **Monitor Cache Hit Rate:** Aim for > 80% hit rate
3. **Use Appropriate Keys:** Namespace and version your keys
4. **Handle Failures Gracefully:** Cache should enhance, not break functionality
5. **Measure Performance:** Track cache hit/miss latency
6. **Test Invalidation:** Verify updates reflect correctly
7. **Consider Consistency:** Choose pattern based on staleness tolerance
