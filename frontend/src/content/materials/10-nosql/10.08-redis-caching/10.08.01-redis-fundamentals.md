## Introduction

Redis (Remote Dictionary Server) is an in-memory data structure store that can be used as a database, cache, message broker, and queue. Its speed comes from storing data in memory, and its versatility comes from supporting multiple data structures beyond simple key-value pairs. Understanding these data structures is fundamental to using Redis effectively.

## Key Concepts Summary

### What is Redis?

Redis is an open-source, in-memory data structure store that excels at:
- **Caching:** Store frequently accessed data for fast retrieval
- **Session Management:** Store user session data
- **Real-time Analytics:** Track counters, statistics, and metrics
- **Leaderboards:** Maintain ranked lists with sorted sets
- **Message Queuing:** Implement pub/sub messaging patterns

**Key Characteristics:**
- Data stored in memory (RAM) for sub-millisecond response times
- Optional persistence to disk
- Single-threaded architecture (no race conditions)
- Atomic operations
- Built-in replication and high availability

### Redis Strings

Strings are the most basic Redis data type and can store text, numbers, or binary data.

```bash
# Set and get values
SET user:1:name "John Doe"
GET user:1:name

# Set with expiration (5 seconds)
SET session:abc123 "user_data" EX 5
SETEX session:abc123 5 "user_data"  # Alternative syntax

# Set if not exists
SETNX config:version "1.0"

# Multiple set/get
MSET user:1:name "John" user:1:email "john@example.com"
MGET user:1:name user:1:email

# Check existence
EXISTS user:1:name

# Delete
DEL user:1:name

# Numeric operations
SET counter:views 0
INCR counter:views      # Returns 1
INCRBY counter:views 10 # Returns 11
DECR counter:views      # Returns 10
DECRBY counter:views 5  # Returns 5

# Get and set atomically
GETSET config:version "2.0"  # Returns old value, sets new

# Append to string
APPEND user:1:notes "Additional information"

# Get length
STRLEN user:1:name
```

**Use Cases:**
- Caching serialized objects (JSON, XML)
- Counters and metrics
- Rate limiting
- Feature flags
- Session tokens

### Redis Hashes

Hashes store field-value pairs, perfect for representing objects.

```bash
# Set single field
HSET user:1000 name "Alice"
HSET user:1000 email "alice@example.com"
HSET user:1000 age 30

# Set multiple fields at once
HMSET user:1000 name "Alice" email "alice@example.com" age 30

# Get single field
HGET user:1000 name

# Get multiple fields
HMGET user:1000 name email

# Get all fields and values
HGETALL user:1000

# Get all field names
HKEYS user:1000

# Get all values
HVALS user:1000

# Check if field exists
HEXISTS user:1000 email

# Delete field
HDEL user:1000 age

# Increment numeric field
HINCRBY user:1000 login_count 1
HINCRBYFLOAT user:1000 balance 10.50

# Get number of fields
HLEN user:1000

# Set if field doesn't exist
HSETNX user:1000 created_at "2024-01-01"
```

**Use Cases:**
- User profiles
- Product information
- Configuration settings
- Any object with multiple properties

**Why use hashes instead of multiple strings?**
- More memory efficient
- Atomic operations on the entire object
- Cleaner data model

### Redis Lists

Lists are ordered collections of strings, implemented as linked lists.

```bash
# Push to left (head)
LPUSH tasks "task1"
LPUSH tasks "task2"  # ["task2", "task1"]

# Push to right (tail)
RPUSH tasks "task3"  # ["task2", "task1", "task3"]

# Push multiple
LPUSH tasks "task4" "task5"

# Get range (0-based index, inclusive)
LRANGE tasks 0 -1  # All elements
LRANGE tasks 0 2   # First 3 elements

# Get specific element
LINDEX tasks 0     # First element
LINDEX tasks -1    # Last element

# Get length
LLEN tasks

# Pop from left
LPOP tasks         # Returns and removes first element

# Pop from right
RPOP tasks         # Returns and removes last element

# Blocking pop (wait for element)
BLPOP tasks 5      # Wait up to 5 seconds

# Set element at index
LSET tasks 0 "updated_task"

# Insert before/after element
LINSERT tasks BEFORE "task1" "new_task"

# Remove elements
LREM tasks 1 "task2"  # Remove first occurrence
LREM tasks -1 "task2" # Remove last occurrence
LREM tasks 0 "task2"  # Remove all occurrences

# Trim list to range
LTRIM tasks 0 99      # Keep first 100 elements
```

**Use Cases:**
- Activity feeds
- Message queues
- Recent items (with LTRIM)
- Undo/redo functionality
- Task queues

### Redis Sets

Sets are unordered collections of unique strings.

```bash
# Add members
SADD tags:1 "redis" "database" "cache"

# Add single member
SADD tags:1 "nosql"

# Check membership
SISMEMBER tags:1 "redis"  # Returns 1 (true)

# Get all members
SMEMBERS tags:1

# Get count
SCARD tags:1

# Remove members
SREM tags:1 "cache"

# Pop random member
SPOP tags:1
SPOP tags:1 2  # Pop 2 random members

# Get random member (without removing)
SRANDMEMBER tags:1
SRANDMEMBER tags:1 3  # Get 3 random members

# Set operations
SADD set1 "a" "b" "c"
SADD set2 "b" "c" "d"

SUNION set1 set2      # Union: ["a","b","c","d"]
SINTER set1 set2      # Intersection: ["b","c"]
SDIFF set1 set2       # Difference: ["a"]

# Store result in new set
SUNIONSTORE set3 set1 set2

# Move member between sets
SMOVE set1 set2 "a"
```

**Use Cases:**
- Tags and categories
- Unique visitor tracking
- Social relationships (followers, friends)
- Access control lists
- Real-time analytics (unique page views)

### Redis Sorted Sets (ZSets)

Sorted sets combine sets and hashes: unique members with associated scores for ordering.

```bash
# Add members with scores
ZADD leaderboard 100 "player1"
ZADD leaderboard 85 "player2" 95 "player3"

# Get rank (0-based, low to high)
ZRANK leaderboard "player2"  # Returns 0 (lowest score)

# Get reverse rank (high to low)
ZREVRANK leaderboard "player2"  # Returns 2 (from top)

# Get score
ZSCORE leaderboard "player1"

# Get range by rank (low to high)
ZRANGE leaderboard 0 -1           # All members
ZRANGE leaderboard 0 9 WITHSCORES # Top 10 with scores

# Get range by rank (high to low)
ZREVRANGE leaderboard 0 9 WITHSCORES  # Top 10 highest

# Get range by score
ZRANGEBYSCORE leaderboard 80 100
ZRANGEBYSCORE leaderboard 80 100 WITHSCORES LIMIT 0 10

# Count members in score range
ZCOUNT leaderboard 80 100

# Increment score
ZINCRBY leaderboard 5 "player2"  # Add 5 to player2's score

# Remove members
ZREM leaderboard "player1"

# Remove by rank range
ZREMRANGEBYRANK leaderboard 0 9  # Remove bottom 10

# Remove by score range
ZREMRANGEBYSCORE leaderboard 0 50  # Remove scores 0-50

# Get cardinality (count)
ZCARD leaderboard

# Pop highest scoring member
ZPOPMAX leaderboard
ZPOPMAX leaderboard 3  # Pop top 3

# Pop lowest scoring member
ZPOPMIN leaderboard
```

**Use Cases:**
- Leaderboards and ranking systems
- Priority queues
- Rate limiters (with timestamp scores)
- Time-series data
- Autocomplete suggestions (with lexicographic scores)

## Choosing the Right Data Structure

| Use Case | Data Structure | Why |
|----------|----------------|-----|
| Cache serialized object | String | Simple, fast |
| Store user profile | Hash | Structured data, atomic field updates |
| Activity feed | List | Ordered, efficient head/tail operations |
| Unique visitors | Set | Automatic deduplication |
| Leaderboard | Sorted Set | Ranked by score |
| Session data | Hash or String | Depends on access patterns |
| Counter | String (INCR) | Atomic increment operations |
| Tags | Set | Unique, set operations |
| Recent items | List (LPUSH + LTRIM) | Ordered, size-limited |

---

## Best Practices

1. **Naming Conventions:** Use namespaces with colons: `user:1000:profile`, `cache:product:5`
2. **Avoid Large Keys:** Split large collections into smaller ones
3. **Use Appropriate Data Types:** Don't store JSON in strings when hashes make sense
4. **Consider Memory:** Strings < 100 bytes, hashes with < 100 fields are most efficient
5. **Atomic Operations:** Leverage Redis's single-threaded nature for race-free operations
