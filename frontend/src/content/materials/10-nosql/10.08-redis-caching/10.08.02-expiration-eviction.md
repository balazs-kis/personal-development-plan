## Introduction

Redis provides powerful mechanisms for automatic data cleanup through key expiration (TTL - Time To Live) and eviction policies. Understanding these features is crucial for building efficient caching systems that automatically manage memory and keep data fresh without manual intervention.

## Key Concepts Summary

### Key Expiration (TTL)

Redis allows you to set expiration times on keys, after which they are automatically deleted.

#### Setting Expiration

```bash
# Set key with expiration in seconds
SET session:abc123 "user_data" EX 3600  # Expires in 1 hour
SETEX session:abc123 3600 "user_data"   # Alternative syntax

# Set key with expiration in milliseconds
SET cache:product:5 "data" PX 5000      # Expires in 5 seconds
PSETEX cache:product:5 5000 "data"      # Alternative syntax

# Set expiration on existing key (seconds)
EXPIRE mykey 300

# Set expiration on existing key (milliseconds)
PEXPIRE mykey 300000

# Set expiration at specific Unix timestamp (seconds)
EXPIREAT mykey 1735689600

# Set expiration at specific Unix timestamp (milliseconds)
PEXPIREAT mykey 1735689600000

# Set expiration only if key has no expiration
SET mykey "value" EXAT 1735689600 NX

# Set expiration only if new expiration is greater than current
SET mykey "value" EXAT 1735689600 GT

# Set expiration only if new expiration is less than current
SET mykey "value" EXAT 1735689600 LT
```

#### Checking and Removing Expiration

```bash
# Check remaining time to live (seconds)
TTL mykey
# Returns:
#  -2 if key does not exist
#  -1 if key exists but has no expiration
#  positive number: remaining seconds

# Check remaining time to live (milliseconds)
PTTL mykey

# Remove expiration (make key persistent)
PERSIST mykey

# Get key value and its expiration
GET mykey
TTL mykey
```

#### Expiration Behavior

```bash
# Example: Session management
SET session:user123 "session_data" EX 1800  # 30 minutes

# Renewing expiration on access (sliding expiration)
GET session:user123      # Get data
EXPIRE session:user123 1800  # Reset expiration to 30 minutes

# Or use GETEX (Redis 6.2+)
GETEX session:user123 EX 1800  # Get and reset expiration atomically
```

**Important Notes:**
- Expired keys are deleted lazily (when accessed) or actively (background process)
- Expiration is preserved during RENAME
- Expiration is removed by SET, GETSET, and other commands that modify the key

### Common Expiration Patterns

#### 1. Cache with Fixed TTL

```bash
# Cache API response for 5 minutes
SET cache:api:users:list "json_data" EX 300
```

#### 2. Sliding Window (Session Management)

```bash
# On each user action, reset expiration
GETEX session:user123 EX 1800
```

#### 3. Rate Limiting

```bash
# Allow 100 requests per hour per user
INCR rate:user123:2024-01-28-15
EXPIRE rate:user123:2024-01-28-15 3600
```

#### 4. Temporary Data

```bash
# Email verification code valid for 10 minutes
SET verify:email:abc123 "verification_code" EX 600
```

#### 5. Leaderboard with Time Decay

```bash
# Score decreases over time (manually managed with ZINCRBY and periodic cleanup)
ZADD trending:posts:2024-01-28 100 "post:1"
# Separate job removes old dates
```

### Eviction Policies

When Redis reaches the `maxmemory` limit, it uses an eviction policy to free memory.

#### Available Policies

**1. noeviction (default in some configurations)**
```bash
CONFIG SET maxmemory-policy noeviction
```
- Returns errors when memory limit is reached
- No keys are evicted
- New writes fail with OOM (Out Of Memory) error
- Use when: Data loss is unacceptable

**2. allkeys-lru (Least Recently Used)**
```bash
CONFIG SET maxmemory-policy allkeys-lru
```
- Evicts least recently used keys from all keys
- Use when: All keys are equally important, want automatic cleanup
- Best for: General caching

**3. allkeys-lfu (Least Frequently Used)**
```bash
CONFIG SET maxmemory-policy allkeys-lfu
```
- Evicts least frequently used keys from all keys
- Considers access frequency, not just recency
- Use when: Want to keep "hot" data regardless of access time
- Best for: Long-term caching with varying access patterns

**4. allkeys-random**
```bash
CONFIG SET maxmemory-policy allkeys-random
```
- Evicts random keys from all keys
- Fast but less precise
- Use when: All data is equally important and simple eviction is acceptable

**5. volatile-lru**
```bash
CONFIG SET maxmemory-policy volatile-lru
```
- Evicts least recently used keys from keys with expiration set
- Use when: Some keys should never be evicted
- Best for: Mixed permanent and temporary data

**6. volatile-lfu**
```bash
CONFIG SET maxmemory-policy volatile-lfu
```
- Evicts least frequently used keys from keys with expiration set
- Use when: Want to keep frequently accessed temporary data longer

**7. volatile-random**
```bash
CONFIG SET maxmemory-policy volatile-random
```
- Evicts random keys from keys with expiration set
- Fast, simple approach for temporary data

**8. volatile-ttl**
```bash
CONFIG SET maxmemory-policy volatile-ttl
```
- Evicts keys with shortest TTL first
- Use when: Want to respect expiration intentions
- Best for: Time-sensitive data with varying lifetimes

### Configuring Memory and Eviction

```bash
# Set maximum memory (in bytes)
CONFIG SET maxmemory 100mb

# Set eviction policy
CONFIG SET maxmemory-policy allkeys-lru

# Get current settings
CONFIG GET maxmemory
CONFIG GET maxmemory-policy

# Check current memory usage
INFO memory

# Get memory usage of specific key
MEMORY USAGE mykey
```

#### redis.conf Configuration

```conf
# Maximum memory limit
maxmemory 2gb

# Eviction policy
maxmemory-policy allkeys-lru

# LRU/LFU algorithm precision (higher = more accurate, more CPU)
maxmemory-samples 5

# LFU counter decay time (minutes)
lfu-log-factor 10
lfu-decay-time 1
```

### Choosing the Right Eviction Policy

| Scenario | Recommended Policy | Why |
|----------|-------------------|-----|
| Pure cache (all data can be evicted) | allkeys-lru | Most common, works well |
| Hot data cache | allkeys-lfu | Keeps frequently accessed data |
| Mixed permanent + cache data | volatile-lru or volatile-lfu | Only evicts temporary keys |
| Time-sensitive cache | volatile-ttl | Respects TTL priorities |
| Critical data (no eviction) | noeviction | Data loss unacceptable |
| Simple/fast eviction | allkeys-random | When precision doesn't matter |

---

### LRU vs LFU

**LRU (Least Recently Used):**
- Evicts keys not accessed recently
- Good for: Time-sensitive data, recent trends
- Problem: One-time popular item can stay in cache

**LFU (Least Frequently Used):**
- Evicts keys accessed least often
- Good for: Long-term popular items
- Problem: Old popular items may never be evicted

**Example:**
```bash
# LRU scenario
# Key A: accessed 100 times yesterday, 0 times today
# Key B: accessed 1 time today
# LRU evicts A (older), LFU evicts B (less frequent)

# Set LFU
CONFIG SET maxmemory-policy allkeys-lfu

# Adjust LFU settings for faster decay
CONFIG SET lfu-decay-time 1  # Decay frequency counters faster
```

## Best Practices

1. **Set Appropriate TTLs:**
   - Short TTL for frequently changing data (1-5 minutes)
   - Medium TTL for stable data (30-60 minutes)
   - Long TTL for rarely changing data (hours to days)

2. **Use Expiration for All Cache Keys:**
   - Always set TTL on cache keys to prevent stale data
   - Even with eviction policies, explicit expiration is better

3. **Choose the Right Policy:**
   - Start with `allkeys-lru` for general caching
   - Use `volatile-*` policies when mixing permanent and temporary data
   - Consider `lfu` for long-running caches with stable access patterns

4. **Monitor Memory:**
   - Set up alerts for memory usage > 80%
   - Track eviction rates
   - Adjust maxmemory based on actual usage

5. **Test Eviction Behavior:**
   - Simulate memory pressure in staging
   - Verify critical keys aren't evicted unintentionally
   - Monitor application behavior during eviction

6. **Sliding Expiration:**
   - Use GETEX or GET + EXPIRE for session-like data
   - Implement in application code for automatic renewal

7. **Namespace Keys:**
   - Group keys by type: `cache:*`, `session:*`, `rate:*`
   - Makes it easier to manage different expiration strategies
