# Lesson 5: GitOps Tools: ArgoCD and Flux Overview

## Learning Objectives

By the end of this lesson, you will be able to:
- Compare ArgoCD and Flux CD capabilities and architectures
- Understand the installation and setup process for both tools
- Deploy applications using ArgoCD and Flux
- Choose the appropriate GitOps tool for your use case

---

## Introduction

While the principles of GitOps are tool-agnostic, practical implementation requires choosing a GitOps tool. ArgoCD and Flux are the two most popular CNCF projects for Kubernetes GitOps. This lesson provides a comprehensive overview of both tools, their architectures, and practical usage to help you make informed decisions.

## Key Concepts Summary

### ArgoCD Overview

**What is ArgoCD?**
ArgoCD is a declarative, GitOps continuous delivery tool for Kubernetes. It is a CNCF graduated project known for its powerful UI, multi-cluster support, and extensive configuration options.

**Architecture:**
```
┌─────────────────────────────────────────────┐
│          ArgoCD Architecture                │
│                                             │
│  ┌──────────────┐      ┌───────────────┐  │
│  │  Git Repo    │─────→│ ArgoCD Server │  │
│  └──────────────┘      └───────┬───────┘  │
│                                 │           │
│                        ┌────────▼────────┐ │
│                        │ Application     │ │
│                        │ Controller      │ │
│                        └────────┬────────┘ │
│                                 │           │
│                        ┌────────▼────────┐ │
│                        │   Kubernetes    │ │
│                        │    Cluster      │ │
│                        └─────────────────┘ │
└─────────────────────────────────────────────┘
```

**Key Features:**
- **Web UI:** Intuitive interface for managing applications and viewing sync status
- **Multi-Cluster:** Manage applications across multiple Kubernetes clusters
- **SSO Integration:** OIDC, SAML, LDAP, and other authentication providers
- **RBAC:** Fine-grained access control for teams and projects
- **Health Assessment:** Automatic health status detection for resources
- **Sync Strategies:** Manual, automatic, and selective sync options
- **Rollback:** One-click rollback to previous Git commits
- **Diff Viewer:** Visual diff between desired and actual state
- **Tool Support:** Native support for Helm, Kustomize, Jsonnet, and plain YAML

**Installation:**
```bash
# Create namespace
kubectl create namespace argocd

# Install ArgoCD
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Access ArgoCD UI (port-forward)
kubectl port-forward svc/argocd-server -n argocd 8080:443

# Get admin password
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
```

**Creating an Application:**
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/myapp
    targetRevision: HEAD
    path: k8s/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
    - CreateNamespace=true
```

**ArgoCD CLI:**
```bash
# Login
argocd login localhost:8080

# List applications
argocd app list

# Sync application
argocd app sync my-app

# Get application details
argocd app get my-app

# Delete application
argocd app delete my-app
```

### Flux CD Overview

**What is Flux?**
Flux is a set of continuous and progressive delivery solutions for Kubernetes. It is a CNCF graduated project that pioneered GitOps for Kubernetes and emphasizes a toolkit approach with composable controllers.

**Architecture:**
```
┌─────────────────────────────────────────────┐
│           Flux Architecture                 │
│                                             │
│  ┌──────────────┐    ┌──────────────────┐ │
│  │  Git Repo    │───→│ Source           │ │
│  └──────────────┘    │ Controller       │ │
│                      └────────┬─────────┘ │
│                               │            │
│                      ┌────────▼─────────┐ │
│                      │ Kustomize        │ │
│                      │ Controller       │ │
│                      └────────┬─────────┘ │
│                               │            │
│                      ┌────────▼─────────┐ │
│                      │ Helm             │ │
│                      │ Controller       │ │
│                      └────────┬─────────┘ │
│                               │            │
│                      ┌────────▼─────────┐ │
│                      │   Kubernetes     │ │
│                      │    Cluster       │ │
│                      └──────────────────┘ │
└─────────────────────────────────────────────┘
```

**Key Features:**
- **GitOps Toolkit:** Composable controllers (source, kustomize, helm, notification, image)
- **Multi-Tenancy:** Built-in support for isolating workloads and configurations
- **Helm Support:** Native HelmRelease CRD for Helm chart management
- **Kustomize Support:** Native Kustomization CRD for Kustomize overlays
- **Image Automation:** Automatically update container images in Git
- **Notification System:** Alerts and notifications for events (Slack, Microsoft Teams, etc.)
- **Progressive Delivery:** Integration with Flagger for canary deployments
- **Bootstrap:** Simple cluster bootstrap process
- **CLI-First:** Designed for automation and CLI workflows

**Installation (Bootstrap):**
```bash
# Install Flux CLI
curl -s https://fluxcd.io/install.sh | sudo bash

# Verify prerequisites
flux check --pre

# Bootstrap with GitHub
export GITHUB_TOKEN=<your-token>
export GITHUB_USER=<your-username>

flux bootstrap github \
  --owner=$GITHUB_USER \
  --repository=fleet-infra \
  --branch=main \
  --path=./clusters/production \
  --personal
```

**Creating a GitRepository Source:**
```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: my-app
  namespace: flux-system
spec:
  interval: 5m
  url: https://github.com/myorg/myapp
  ref:
    branch: main
```

**Creating a Kustomization:**
```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: my-app
  namespace: flux-system
spec:
  interval: 10m
  sourceRef:
    kind: GitRepository
    name: my-app
  path: ./k8s/production
  prune: true
  wait: true
  timeout: 2m
```

**Flux CLI:**
```bash
# Check Flux components
flux check

# Get GitRepository sources
flux get sources git

# Get Kustomizations
flux get kustomizations

# Reconcile immediately
flux reconcile kustomization my-app --with-source

# Suspend reconciliation
flux suspend kustomization my-app

# Resume reconciliation
flux resume kustomization my-app
```

### ArgoCD vs Flux Comparison

| Feature | ArgoCD | Flux |
|---------|--------|------|
| **UI** | Rich web UI | No official UI (3rd party available) |
| **Architecture** | Monolithic application | Toolkit of controllers |
| **Primary Interface** | UI + CLI | CLI + CRDs |
| **Multi-Cluster** | Built-in hub model | One Flux per cluster |
| **RBAC** | Built-in project/role system | Kubernetes RBAC |
| **Helm Support** | Native | Native (HelmRelease) |
| **Kustomize Support** | Native | Native (Kustomization) |
| **Image Automation** | External tools needed | Built-in |
| **Progressive Delivery** | Argo Rollouts (separate) | Flagger integration |
| **Notifications** | Basic | Rich (notification-controller) |
| **Maturity** | CNCF Graduated | CNCF Graduated |
| **Learning Curve** | Easier (UI) | Steeper (CLI/CRD-focused) |

### When to Choose Each Tool

**Choose ArgoCD if:**
- You want a comprehensive UI for visualization and operations
- You need to manage multiple clusters from a central control plane
- Your team prefers UI-driven workflows
- You need built-in SSO and RBAC
- You want quick onboarding for less Kubernetes-experienced teams

**Choose Flux if:**
- You prefer a toolkit approach with composable components
- You want GitOps entirely defined as code (CRDs)
- You need advanced image automation
- You're comfortable with CLI and Kubernetes-native workflows
- You want lighter resource footprint
- You prefer decentralized architecture (one Flux per cluster)

**Consider Both if:**
- You have different team preferences (UI vs CLI)
- You want to evaluate both before committing
- Different clusters have different requirements
