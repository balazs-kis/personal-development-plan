## Introduction

Feature flags (also called feature toggles) represent a paradigm shift in how we release software. Instead of tying feature releases to deployments, feature flags let you deploy code to production with new features turned off, then enable them for specific users or gradually roll them out. This decoupling of deployment from release enables safer, more controlled releases and powerful capabilities like A/B testing and progressive delivery.

## Key Concepts Summary

### What Are Feature Flags?

**Definition:** Feature flags are runtime configuration switches that allow you to enable or disable features without deploying new code.

**Simple Example:**
```javascript
// Without feature flags
function renderDashboard() {
  return <NewDashboard />;  // Everyone gets new dashboard
}

// With feature flags
function renderDashboard() {
  if (featureFlags.newDashboard) {
    return <NewDashboard />;
  }
  return <OldDashboard />;  // Safe fallback
}
```

**Basic Implementation:**
```javascript
// Configuration (stored in database, config service, or environment)
const featureFlags = {
  newDashboard: false,
  darkMode: true,
  experimentalSearch: false
};

// Usage in code
if (featureFlags.newDashboard) {
  // New feature code
} else {
  // Old feature code
}
```

### Benefits of Feature Flags

**1. Decouple Deployment from Release**
- Deploy code to production with features turned off
- Enable features when ready, independent of deployment
- No need for complex release branches

**2. Reduce Deployment Risk**
- Test in production with feature off
- Enable for internal users first
- Instant rollback by toggling flag (no redeployment)

**3. Enable Progressive Rollout**
- Start with 1% of users
- Gradually increase to 5%, 25%, 50%, 100%
- Monitor metrics at each stage

**4. A/B Testing**
- Show different features to different user segments
- Measure impact on key metrics
- Make data-driven decisions

**5. Environment-Specific Behavior**
```javascript
const config = {
  debugMode: environment === 'development',
  analyticsEnabled: environment === 'production',
  mockPayments: environment !== 'production'
};
```

**6. Kill Switch**
- Instantly disable problematic features
- No deployment required
- Faster than rollback

### Feature Flag Types

**1. Release Flags (Short-lived)**
```javascript
// Removed after full rollout
if (flags.newCheckoutFlow) {
  return <NewCheckout />;
}
return <OldCheckout />;
```
**Lifecycle:** Created → Gradual rollout → 100% → Flag removed

**2. Operational Flags (Long-lived)**
```javascript
// Permanent toggles for operational control
if (flags.maintenanceMode) {
  return <MaintenancePage />;
}
```

**3. Experiment Flags (Short-lived)**
```javascript
// A/B testing
if (flags.checkoutVariantB) {
  return <CheckoutB />;  // Variant B
}
return <CheckoutA />;  // Control
```

**4. Permission Flags (Long-lived)**
```javascript
// Feature access control
if (user.hasPremiumFeatures && flags.premiumDashboard) {
  return <PremiumDashboard />;
}
```

### Progressive Delivery

**Progressive Delivery** extends continuous delivery with fine-grained control over feature releases, combining deployment strategies with feature flags.

**Canary Deployment with Automated Analysis:**
```
1. Deploy new version to 5% of infrastructure
2. Monitor metrics (error rate, latency, conversion)
3. If metrics healthy → increase to 25%
4. If metrics degraded → automatic rollback
5. Continue until 100% or rollback
```

**Progressive Rollout Strategy:**
```
Phase 1: Internal team (0.1% of traffic)
↓ (24 hours, monitor)
Phase 2: Beta users (1% of traffic)
↓ (48 hours, monitor)
Phase 3: Early adopters (10% of traffic)
↓ (72 hours, monitor)
Phase 4: General availability (100%)
```

### Feature Flag Implementation Patterns

**1. Simple Boolean Flags**
```typescript
interface FeatureFlags {
  newDashboard: boolean;
  darkMode: boolean;
  betaFeatures: boolean;
}

const flags: FeatureFlags = {
  newDashboard: true,
  darkMode: false,
  betaFeatures: false
};
```

**2. Percentage Rollout**
```typescript
interface FeatureFlag {
  enabled: boolean;
  rolloutPercentage: number;  // 0-100
}

function isFeatureEnabled(flag: FeatureFlag, userId: string): boolean {
  if (!flag.enabled) return false;
  
  // Deterministic hash to percentage
  const hash = hashUserId(userId);
  return (hash % 100) < flag.rolloutPercentage;
}

const newFeature: FeatureFlag = {
  enabled: true,
  rolloutPercentage: 25  // 25% of users
};
```

**3. User Segment Targeting**
```typescript
interface FeatureFlag {
  enabled: boolean;
  allowedUsers?: string[];
  allowedGroups?: string[];
  rolloutPercentage?: number;
}

function isFeatureEnabled(
  flag: FeatureFlag,
  user: User
): boolean {
  if (!flag.enabled) return false;
  
  // Explicit allow list
  if (flag.allowedUsers?.includes(user.id)) return true;
  if (flag.allowedGroups?.some(g => user.groups.includes(g))) return true;
  
  // Percentage rollout
  if (flag.rolloutPercentage) {
    return (hashUserId(user.id) % 100) < flag.rolloutPercentage;
  }
  
  return false;
}
```

**4. Multi-Variant Flags**
```typescript
type Variant = 'control' | 'variantA' | 'variantB';

interface ExperimentFlag {
  enabled: boolean;
  variants: {
    [key in Variant]: {
      weight: number;  // Percentage
    }
  };
}

const checkoutExperiment: ExperimentFlag = {
  enabled: true,
  variants: {
    control: { weight: 34 },   // 34%
    variantA: { weight: 33 },  // 33%
    variantB: { weight: 33 }   // 33%
  }
};
```

### Feature Flag Management

**Centralized Feature Flag Service:**
```
┌─────────────────────────────────────┐
│   Feature Flag Service              │
│   (LaunchDarkly, Split.io, etc.)    │
│                                     │
│   Flags: newDashboard: 25%         │
│          darkMode: 100%            │
│          betaSearch: internal-only │
└──────────────┬──────────────────────┘
               │ REST API / SDK
               │
    ┌──────────┼──────────┐
    │          │          │
┌───▼───┐  ┌───▼───┐  ┌───▼───┐
│ Web   │  │ API   │  │Mobile │
│ App   │  │       │  │ App   │
└───────┘  └───────┘  └───────┘
```

**Feature Flag SDK Pattern:**
```typescript
// Initialize SDK
const client = LaunchDarkly.initialize('sdk-key', user);

// Check flag
if (client.variation('new-dashboard', false)) {
  return <NewDashboard />;
}

// Track events
client.track('dashboard-viewed');
```

### Flagger for Automated Progressive Delivery

**Flagger** automates progressive delivery in Kubernetes:

```yaml
apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: myapp
spec:
  # Target deployment
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  
  # Progressive delivery
  progressDeadlineSeconds: 60
  
  service:
    port: 80
    targetPort: 8080
  
  analysis:
    # Check every 1 minute
    interval: 1m
    # Promote after 5 successful checks
    threshold: 5
    # Rollback after 2 failed checks
    maxWeight: 50
    stepWeight: 10
    
    # Success metrics
    metrics:
    - name: request-success-rate
      thresholdRange:
        min: 99
      interval: 1m
    
    - name: request-duration
      thresholdRange:
        max: 500
      interval: 1m
    
    # Webhooks for notifications
    webhooks:
    - name: slack
      url: https://hooks.slack.com/services/YOUR/WEBHOOK
```

**Flagger Rollout Process:**
1. Detects new deployment
2. Creates canary deployment with new version
3. Routes 10% traffic to canary
4. Analyzes metrics
5. If healthy: increase to 20%, 30%, 40%, 50%
6. If unhealthy: automatic rollback
7. On success: promote canary to primary

### Best Practices

**1. Flag Naming Conventions**
```
✅ Good: user_profile_redesign, checkout_flow_v2, payment_provider_stripe
❌ Bad: new_feature, temp_flag, test123
```

**2. Clean Up Old Flags**
- Set expiration dates
- Monitor flag age
- Remove flags after full rollout
- Don't let flags accumulate

**3. Flag Testing**
```javascript
// Test both code paths
describe('Dashboard', () => {
  it('renders new dashboard when flag enabled', () => {
    featureFlags.newDashboard = true;
    // Test new dashboard
  });
  
  it('renders old dashboard when flag disabled', () => {
    featureFlags.newDashboard = false;
    // Test old dashboard
  });
});
```

**4. Default to Safe**
```javascript
// If flag service is down, use safe default
const isNewDashboardEnabled = flags?.newDashboard ?? false;
```

**5. Monitor Flag Usage**
- Track which users see which variants
- Monitor metrics per variant
- Alert on flag service unavailability

**6. Document Flags**
```typescript
/**
 * Feature Flag: new_checkout_flow
 * 
 * Description: New streamlined checkout with one-click purchase
 * Owner: @checkout-team
 * Created: 2026-01-15
 * Expected Removal: 2026-03-15
 * Jira: SHOP-1234
 * 
 * Rollout Plan:
 * - Phase 1: Internal team (2026-01-15)
 * - Phase 2: 10% of users (2026-02-01)
 * - Phase 3: 100% of users (2026-03-01)
 * - Phase 4: Remove flag (2026-03-15)
 */
const NEW_CHECKOUT_FLOW = 'new_checkout_flow';
```

### Anti-Patterns to Avoid

**1. Too Many Nested Flags**
```javascript
// ❌ Flag spaghetti
if (flags.featureA) {
  if (flags.featureB) {
    if (flags.featureC) {
      // Combinatorial explosion
    }
  }
}
```

**2. Using Flags for Configuration**
```javascript
// ❌ This should be config, not a flag
flags.apiTimeout = 5000;
flags.maxRetries = 3;

// ✅ Use environment variables
const apiTimeout = process.env.API_TIMEOUT || 5000;
```

**3. Long-Lived Release Flags**
- Release flags should be temporary
- Set removal dates
- Clean up after rollout
