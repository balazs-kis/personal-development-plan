# Lesson 2: Configuration Management Across Environments

## Learning Objectives

By the end of this lesson, you will be able to:
- Separate configuration from code following 12-Factor App principles
- Manage environment-specific configurations without duplication
- Use environment variables and configuration files effectively
- Implement configuration management in Kubernetes and Docker

---

## Introduction

Every application needs different configuration in different environments—database URLs, API keys, feature toggles, and resource limits all vary between dev, staging, and production. The challenge is managing these differences without creating brittle, environment-specific code branches. This lesson explores best practices for configuration management that keep code DRY while allowing environment-specific behavior.

## Key Concepts Summary

### The 12-Factor App Configuration Principle

**Definition:** Configuration is anything that varies between deploys (environments). This includes:
- Database connection strings
- Credentials for external services
- Per-deploy values like hostnames
- Feature flags and toggles

**The Rule:** Store config in environment variables, never in code.

**Why?**
- Code can be open-sourced without compromising credentials
- Config changes don't require code changes
- Easy to change config without rebuilding
- Language and framework agnostic

### Anti-Pattern: Config Files in Code

```javascript
// ❌ BAD: Environment-specific config files committed to repo
// config/development.js
module.exports = {
  database: 'postgresql://localhost/myapp_dev',
  apiKey: 'dev-key-123',
  debugMode: true
};

// config/production.js
module.exports = {
  database: 'postgresql://prod-db:5432/myapp',
  apiKey: 'prod-key-456',  // Security risk!
  debugMode: false
};

// app.js
const config = require(`./config/${process.env.NODE_ENV}`);
```

**Problems:**
- Credentials in version control
- Need to rebuild/redeploy to change config
- Environment-specific branches or conditional logic

### Correct Pattern: Environment Variables

```javascript
// ✅ GOOD: Read config from environment
// app.js
const config = {
  database: process.env.DATABASE_URL,
  apiKey: process.env.API_KEY,
  debugMode: process.env.DEBUG_MODE === 'true'
};

// No config files committed
// Each environment sets its own variables
```

**Benefits:**
- No secrets in code
- Same code runs everywhere
- Easy to change without redeployment (for certain changes)

### Configuration Layers

Most applications benefit from multiple configuration layers:

**1. Defaults (in code)**
```javascript
const config = {
  port: process.env.PORT || 3000,
  logLevel: process.env.LOG_LEVEL || 'info',
  timeout: process.env.TIMEOUT || 30000
};
```

**2. Environment Files (not committed for secrets)**
```bash
# .env.development (committed)
LOG_LEVEL=debug
PORT=3000

# .env.production (NOT committed, or only non-sensitive values)
LOG_LEVEL=warn
PORT=8080

# .env.local (gitignored, for local secrets)
DATABASE_URL=postgresql://localhost/myapp_dev
API_KEY=local-dev-key
```

**3. Runtime Environment Variables (highest priority)**
```bash
# Override anything when running
PORT=4000 npm start
```

### Docker Compose Configuration

**Directory Structure:**
```
project/
├── docker-compose.yml
├── .env.development
├── .env.staging
├── .env.production
└── .env.local  # gitignored
```

**docker-compose.yml:**
```yaml
services:
  app:
    build: .
    env_file:
      - .env.${ENVIRONMENT:-development}  # Load based on ENVIRONMENT variable
    environment:
      # Can override or add specific variables
      NODE_ENV: ${ENVIRONMENT:-development}
```

**Running:**
```bash
# Development (default)
docker-compose up

# Staging
ENVIRONMENT=staging docker-compose up

# Production
ENVIRONMENT=production docker-compose up
```

### Kubernetes Configuration Management

**Three Approaches:**

**1. Direct Environment Variables:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      containers:
      - name: app
        image: myapp:1.0
        env:
        - name: LOG_LEVEL
          value: "info"
        - name: PORT
          value: "8080"
```

**2. ConfigMaps (non-sensitive config):**
```yaml
# ConfigMap per environment
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config-prod
  namespace: production
data:
  LOG_LEVEL: "warn"
  PORT: "8080"
  FEATURE_X_ENABLED: "true"
---
# Deployment references ConfigMap
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  template:
    spec:
      containers:
      - name: app
        envFrom:
        - configMapRef:
            name: myapp-config-prod
```

**3. Secrets (sensitive config):**
```yaml
# Secret per environment
apiVersion: v1
kind: Secret
metadata:
  name: myapp-secrets-prod
  namespace: production
type: Opaque
stringData:
  DATABASE_URL: "postgresql://prod-db:5432/myapp"
  API_KEY: "prod-key-456"
---
# Deployment references Secret
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  template:
    spec:
      containers:
      - name: app
        envFrom:
        - secretRef:
            name: myapp-secrets-prod
```

### Kubernetes Multi-Environment Structure

**Namespace per Environment:**
```
kubernetes/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
├── overlays/
│   ├── dev/
│   │   ├── configmap.yaml
│   │   ├── secrets.yaml  # or external secrets
│   │   └── kustomization.yaml
│   ├── staging/
│   │   ├── configmap.yaml
│   │   ├── secrets.yaml
│   │   └── kustomization.yaml
│   └── production/
│       ├── configmap.yaml
│       ├── secrets.yaml
│       └── kustomization.yaml
```

**base/deployment.yaml:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 1  # Will be overridden per environment
  template:
    spec:
      containers:
      - name: app
        image: myapp:latest  # Will be overridden
        envFrom:
        - configMapRef:
            name: myapp-config
        - secretRef:
            name: myapp-secrets
```

**overlays/production/kustomization.yaml:**
```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: production

resources:
- ../../base
- configmap.yaml
- secrets.yaml

replicas:
- name: myapp
  count: 10

images:
- name: myapp
  newTag: v1.2.3
```

### Azure DevOps Environments

Azure DevOps provides first-class environment support:

**Environment Definition:**
```yaml
# azure-pipelines.yml
stages:
- stage: Deploy_Dev
  jobs:
  - deployment: DeployWeb
    environment: 
      name: Development
      resourceType: Kubernetes
    strategy:
      runOnce:
        deploy:
          steps:
          - script: kubectl apply -f k8s/dev/

- stage: Deploy_Staging
  dependsOn: Deploy_Dev
  jobs:
  - deployment: DeployWeb
    environment: 
      name: Staging
      resourceType: Kubernetes
    strategy:
      runOnce:
        deploy:
          steps:
          - script: kubectl apply -f k8s/staging/

- stage: Deploy_Production
  dependsOn: Deploy_Staging
  jobs:
  - deployment: DeployWeb
    environment: 
      name: Production
      resourceType: Kubernetes
    strategy:
      runOnce:
        deploy:
          steps:
          - script: kubectl apply -f k8s/production/
```

**Benefits:**
- Deployment history per environment
- Approval gates per environment
- Environment-specific variables
- Resource health monitoring

### Best Practices

1. **Never commit secrets** to version control
2. **Use specific .env files** for different environments
3. **Understand precedence** of configuration sources
4. **Separate sensitive from non-sensitive** config (ConfigMap vs Secret)
5. **Use external secret managers** (Vault, AWS Secrets Manager) for production
6. **Document required variables** in README or example .env file
7. **Validate configuration** on application startup
8. **Use consistent naming** across environments
