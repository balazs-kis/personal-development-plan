## Introduction

Terraform workspaces allow you to manage multiple instances of the same infrastructure configuration with separate state files. While workspaces are useful for simple environment management, understanding their limitations and alternatives is crucial for making informed architectural decisions.

## Key Concepts Summary

### Workspace Basics

Workspaces maintain separate state files for the same configuration:

```bash
# List workspaces (default exists automatically)
terraform workspace list

# Create new workspace
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod

# Switch between workspaces
terraform workspace select dev

# Show current workspace
terraform workspace show

# Delete workspace (must not be current workspace)
terraform workspace delete staging
```

### Workspace-Aware Configuration

**Using the Current Workspace:**

```hcl
# main.tf
resource "aws_instance" "app" {
  ami           = var.ami_id
  instance_type = var.instance_sizes[terraform.workspace]
  
  tags = {
    Name        = "${var.app_name}-${terraform.workspace}"
    Environment = terraform.workspace
  }
}

# variables.tf
variable "instance_sizes" {
  type = map(string)
  default = {
    dev     = "t3.micro"
    staging = "t3.small"
    prod    = "t3.large"
  }
}

variable "app_name" {
  type    = string
  default = "myapp"
}
```

**Environment-Specific Variable Files:**

```bash
# Directory structure
.
├── main.tf
├── variables.tf
├── dev.tfvars
├── staging.tfvars
└── prod.tfvars
```

```hcl
# dev.tfvars
instance_count = 1
enable_monitoring = false
database_size = "db.t3.micro"
```

```hcl
# prod.tfvars
instance_count = 3
enable_monitoring = true
database_size = "db.r5.xlarge"
```

```bash
# Apply with workspace-specific variables
terraform workspace select dev
terraform apply -var-file="dev.tfvars"

terraform workspace select prod
terraform apply -var-file="prod.tfvars"
```

### State File Organization

Workspaces store state in environment-specific paths:

**Local Backend:**
```
terraform.tfstate.d/
├── dev/
│   └── terraform.tfstate
├── staging/
│   └── terraform.tfstate
└── prod/
    └── terraform.tfstate
```

**S3 Backend:**
```hcl
terraform {
  backend "s3" {
    bucket = "my-terraform-state"
    key    = "app/terraform.tfstate"
    region = "us-east-1"
  }
}
```

State paths in S3:
- `default`: `app/terraform.tfstate`
- `dev`: `env:/dev/app/terraform.tfstate`
- `prod`: `env:/prod/app/terraform.tfstate`

## Workspaces vs Directory Structure

### When to Use Workspaces

**✅ Good Use Cases:**

1. **Identical infrastructure across environments:**
```hcl
# Same config, different sizing
resource "aws_instance" "app" {
  instance_type = var.instance_type
  count         = var.instance_count
}
```

2. **Development/testing environments:**
```bash
# Quick environment creation for testing
terraform workspace new feature-branch-test
terraform apply -var-file="dev.tfvars"
```

3. **Short-lived environments:**
```bash
# Create temporary environment
terraform workspace new demo-2024-02-01
# ... use it ...
terraform destroy
terraform workspace select default
terraform workspace delete demo-2024-02-01
```

### When to Use Directory Structure

**✅ Better for:**

1. **Different infrastructure per environment**
2. **Large teams with environment ownership**
3. **Different backends per environment**
4. **Complex environments with unique configurations**

**Directory Structure Pattern:**

```
terraform/
├── modules/
│   ├── networking/
│   ├── compute/
│   └── database/
├── environments/
│   ├── dev/
│   │   ├── main.tf
│   │   ├── backend.tf
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   ├── staging/
│   │   ├── main.tf
│   │   ├── backend.tf
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   └── prod/
│       ├── main.tf
│       ├── backend.tf
│       ├── variables.tf
│       └── terraform.tfvars
```

**Example Environment Configuration:**

```hcl
# environments/prod/main.tf
module "network" {
  source = "../../modules/networking"
  
  vpc_cidr    = "10.0.0.0/16"
  environment = "prod"
}

module "app" {
  source = "../../modules/compute"
  
  vpc_id          = module.network.vpc_id
  instance_count  = 5
  instance_type   = "t3.large"
  environment     = "prod"
}
```

```hcl
# environments/prod/backend.tf
terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-prod"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-prod-locks"
  }
}
```

## Advanced Workspace Patterns

### Conditional Resource Creation

```hcl
resource "aws_cloudwatch_log_group" "app" {
  count = terraform.workspace == "prod" ? 1 : 0
  
  name              = "/aws/app/${var.app_name}"
  retention_in_days = 90
}

resource "aws_backup_plan" "daily" {
  count = contains(["staging", "prod"], terraform.workspace) ? 1 : 0
  
  name = "${var.app_name}-${terraform.workspace}-backup"
  
  rule {
    rule_name         = "daily_backup"
    target_vault_name = aws_backup_vault.main[0].name
    schedule          = "cron(0 5 * * ? *)"
  }
}
```

### Dynamic Naming

```hcl
locals {
  env_config = {
    dev = {
      instance_type = "t3.micro"
      instance_count = 1
      enable_ha = false
    }
    staging = {
      instance_type = "t3.small"
      instance_count = 2
      enable_ha = true
    }
    prod = {
      instance_type = "t3.large"
      instance_count = 3
      enable_ha = true
    }
  }
  
  current_env = local.env_config[terraform.workspace]
}

resource "aws_instance" "app" {
  count = local.current_env.instance_count
  
  ami           = var.ami_id
  instance_type = local.current_env.instance_type
  
  tags = {
    Name        = "${var.app_name}-${terraform.workspace}-${count.index + 1}"
    Environment = terraform.workspace
    HighAvailability = local.current_env.enable_ha
  }
}
```

### Workspace Validation

```hcl
variable "allowed_workspaces" {
  type    = list(string)
  default = ["dev", "staging", "prod"]
}

locals {
  validate_workspace = (
    contains(var.allowed_workspaces, terraform.workspace)
    ? null
    : file("ERROR: Invalid workspace '${terraform.workspace}'. Allowed: ${join(", ", var.allowed_workspaces)}")
  )
}
```

## Best Practices

### 1. Workspace Naming Convention

```
✅ Good:
  - dev, staging, prod
  - feature-auth-service
  - hotfix-payment-bug

❌ Bad:
  - john-test
  - temporary
  - old
```

### 2. Minimize Blast Radius

Keep workspaces focused:

```
✅ Good:
  - One application or service per workspace set
  - Separate networking, compute, and data layers

❌ Bad:
  - Entire infrastructure in one workspace
  - 100+ resources in single state
```

### 3. Document Workspace Usage

```hcl
# README.md
## Workspaces

Available workspaces:
- `dev`: Development environment (single instance)
- `staging`: Staging environment (mirrors prod)
- `prod`: Production environment (multi-AZ, HA)

## Usage

# Switch to dev
terraform workspace select dev
terraform apply -var-file="dev.tfvars"

# Deploy to prod
terraform workspace select prod
terraform apply -var-file="prod.tfvars"
```

### 4. Protect Production

```bash
# Use workspace selection in CI/CD
if [ "$WORKSPACE" == "prod" ]; then
  echo "Deploying to PRODUCTION - manual approval required"
  # Require manual approval
fi
```

## Comparison Table

| Aspect | Workspaces | Directories |
|--------|-----------|-------------|
| **State isolation** | Separate state files | Completely separate |
| **Code reuse** | Same code, different state | Modules provide reuse |
| **Configuration differences** | Variables only | Any configuration can differ |
| **Backend configuration** | Same backend | Can use different backends |
| **Team access control** | Requires Terraform Cloud | Easier with IAM/RBAC |
| **Complexity** | Simple | More files, more explicit |
| **Best for** | Similar environments | Complex/unique environments |
