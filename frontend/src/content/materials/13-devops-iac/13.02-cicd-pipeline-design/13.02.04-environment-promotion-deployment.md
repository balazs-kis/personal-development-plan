## Learning Objectives

By the end of this lesson, you will be able to:
- Design multi-environment promotion workflows
- Implement different deployment strategies (blue-green, canary, rolling)
- Choose the right deployment strategy for your context
- Configure quality gates between environments
- Apply best practices for safe production deployments

---

## Introduction

Environment promotion is the process of moving code and artifacts through increasingly production-like environments—from development to staging to production. Combined with smart deployment strategies, proper promotion workflows enable safe, confident releases while minimizing downtime and risk.

This lesson explores how to design effective promotion workflows and implement deployment strategies that balance speed with safety.

## Key Concepts Summary

### Environment Promotion Workflow

**Standard environment progression:**

```
Developer Workstation
         ↓
    Development (Dev)
         ↓
[Integration Tests]
         ↓
    Staging (UAT)
         ↓
[Acceptance Tests]
[Manual Approval]
         ↓
    Production
         ↓
[Monitoring]
```

Each environment serves a specific purpose:

```csharp
// Example: Environment configuration
public class EnvironmentConfig
{
    public enum EnvironmentType
    {
        Development,   // Rapid iteration, developer testing
        Staging,       // Production-like, QA testing
        Production     // Live customer traffic
    }
    
    public static EnvironmentSettings GetSettings(EnvironmentType env)
    {
        return env switch
        {
            EnvironmentType.Development => new EnvironmentSettings
            {
                LogLevel = "Debug",
                EnableDetailedErrors = true,
                DatabaseReplicas = 0,
                CacheSize = "small",
                AutoDeploy = true,          // Deploy on every commit
                RequireApproval = false
            },
            
            EnvironmentType.Staging => new EnvironmentSettings
            {
                LogLevel = "Information",
                EnableDetailedErrors = true,
                DatabaseReplicas = 1,
                CacheSize = "medium",
                AutoDeploy = true,          // Deploy after tests pass
                RequireApproval = false
            },
            
            EnvironmentType.Production => new EnvironmentSettings
            {
                LogLevel = "Warning",
                EnableDetailedErrors = false,
                DatabaseReplicas = 3,
                CacheSize = "large",
                AutoDeploy = false,         // Manual or scheduled
                RequireApproval = true      // Require human approval
            },
            
            _ => throw new ArgumentException($"Unknown environment: {env}")
        };
    }
}
```

### Environment Parity

**Principle:** Staging should mirror production as closely as possible

**Key similarities:**
- Same infrastructure (scaled down is OK)
- Same configuration structure
- Same dependencies and versions
- Same deployment process
- Same monitoring and logging

```yaml
# Example: Environment parity with different scales
environments:
  staging:
    replicas: 2              # Scaled down
    instance_type: t3.medium
    database: postgres-13
    cache: redis-7
    monitoring: enabled
    ssl: enabled
    
  production:
    replicas: 10             # Full scale
    instance_type: t3.xlarge
    database: postgres-13    # Same version!
    cache: redis-7           # Same version!
    monitoring: enabled      # Same monitoring!
    ssl: enabled             # Same SSL config!
```

**Differences that are acceptable:**
```
Staging              Production
-------              ----------
2 replicas       vs  10 replicas
Smaller instances vs Larger instances
1 database       vs  3 databases (HA)
Sample data      vs  Real data
```

### Deployment Strategies

#### 1. Blue-Green Deployment

**Concept:** Run two identical production environments; switch traffic between them

```
Blue Environment (Current)          Green Environment (New)
├── App v1.0                        ├── App v1.1
├── 100% traffic               →    ├── 0% traffic (testing)
└── Running                         └── Running

                    [Switch]

Blue Environment (Idle)             Green Environment (Current)
├── App v1.0                        ├── App v1.1
├── 0% traffic (rollback ready)     ├── 100% traffic
└── Running                         └── Running
```

**Implementation example:**

```csharp
// Example: Blue-green deployment controller
public class BlueGreenDeployment
{
    public async Task DeployAsync(string newVersion)
    {
        var currentEnv = await GetActiveEnvironmentAsync();  // "blue"
        var targetEnv = currentEnv == "blue" ? "green" : "blue";
        
        _logger.LogInformation(
            "Deploying {Version} to {Target} (current: {Current})",
            newVersion, targetEnv, currentEnv
        );
        
        // 1. Deploy to inactive environment
        await DeployToEnvironmentAsync(targetEnv, newVersion);
        
        // 2. Run health checks
        var healthy = await HealthCheckAsync(targetEnv);
        if (!healthy)
        {
            await RollbackAsync(targetEnv);
            throw new DeploymentException("Health checks failed");
        }
        
        // 3. Run smoke tests
        await RunSmokeTestsAsync(targetEnv);
        
        // 4. Switch traffic (instant cutover)
        await SwitchTrafficAsync(from: currentEnv, to: targetEnv);
        
        // 5. Monitor for errors
        await Task.Delay(TimeSpan.FromMinutes(5));
        var errorRate = await GetErrorRateAsync(targetEnv);
        
        if (errorRate > 0.01)  // More than 1% errors
        {
            // Instant rollback
            await SwitchTrafficAsync(from: targetEnv, to: currentEnv);
            throw new DeploymentException("High error rate detected");
        }
        
        _logger.LogInformation("Deployment successful");
    }
}
```

**Pros:**
- Zero downtime
- Instant rollback (switch back)
- Test in production-identical environment

**Cons:**
- Requires double infrastructure
- Database migrations are complex
- Not suitable for minor changes

**Best for:** Major releases, applications with strict uptime requirements

#### 2. Canary Deployment

**Concept:** Gradually roll out to increasing percentages of users

```
Phase 1: 5% canary
├── v1.0: 95% of users
└── v1.1: 5% of users (canary)
         ↓
Phase 2: 25% canary
├── v1.0: 75% of users
└── v1.1: 25% of users
         ↓
Phase 3: 50% canary
├── v1.0: 50% of users
└── v1.1: 50% of users
         ↓
Phase 4: 100% rollout
└── v1.1: 100% of users
```

**Implementation example:**

```csharp
// Example: Canary deployment with gradual rollout
public class CanaryDeployment
{
    private readonly int[] _rolloutPhases = { 5, 10, 25, 50, 100 };
    
    public async Task DeployAsync(string newVersion)
    {
        foreach (var percentage in _rolloutPhases)
        {
            _logger.LogInformation(
                "Rolling out {Version} to {Percentage}% of users",
                newVersion, percentage
            );
            
            // Update traffic routing
            await SetTrafficPercentageAsync(newVersion, percentage);
            
            // Wait and observe
            await Task.Delay(TimeSpan.FromMinutes(10));
            
            // Check metrics
            var metrics = await GatherMetricsAsync(newVersion);
            
            if (!metrics.IsHealthy)
            {
                _logger.LogError("Metrics unhealthy, rolling back");
                await SetTrafficPercentageAsync(newVersion, 0);
                throw new DeploymentException("Canary failed health checks");
            }
            
            if (metrics.ErrorRate > metrics.BaselineErrorRate * 1.5)
            {
                _logger.LogError("Error rate increased, rolling back");
                await SetTrafficPercentageAsync(newVersion, 0);
                throw new DeploymentException("Error rate too high");
            }
            
            _logger.LogInformation("Phase {Percentage}% successful", percentage);
        }
        
        _logger.LogInformation("Canary deployment complete");
    }
    
    private async Task<CanaryMetrics> GatherMetricsAsync(string version)
    {
        var baseline = await GetBaselineMetricsAsync();
        var canary = await GetVersionMetricsAsync(version);
        
        return new CanaryMetrics
        {
            IsHealthy = canary.ResponseTime < baseline.ResponseTime * 1.2
                     && canary.ErrorRate < 0.01,
            ErrorRate = canary.ErrorRate,
            BaselineErrorRate = baseline.ErrorRate,
            ResponseTime = canary.ResponseTime
        };
    }
}
```

**Pros:**
- Gradual risk exposure
- Early problem detection
- Real user feedback
- Easy to pause or rollback

**Cons:**
- Takes longer to complete
- Requires traffic routing capability
- Need good metrics and monitoring

**Best for:** High-risk changes, user-facing features, gradual rollouts

#### 3. Rolling Deployment

**Concept:** Update servers incrementally while maintaining service

```
Start:
Server 1: v1.0 ✓
Server 2: v1.0 ✓
Server 3: v1.0 ✓
Server 4: v1.0 ✓

Step 1:
Server 1: v1.1 ← (updating)
Server 2: v1.0 ✓
Server 3: v1.0 ✓
Server 4: v1.0 ✓

Step 2:
Server 1: v1.1 ✓
Server 2: v1.1 ← (updating)
Server 3: v1.0 ✓
Server 4: v1.0 ✓

Step 3:
Server 1: v1.1 ✓
Server 2: v1.1 ✓
Server 3: v1.1 ← (updating)
Server 4: v1.0 ✓

Step 4:
Server 1: v1.1 ✓
Server 2: v1.1 ✓
Server 3: v1.1 ✓
Server 4: v1.1 ← (updating)

Complete:
Server 1: v1.1 ✓
Server 2: v1.1 ✓
Server 3: v1.1 ✓
Server 4: v1.1 ✓
```

**Implementation example:**

```csharp
// Example: Rolling deployment
public class RollingDeployment
{
    public async Task DeployAsync(string newVersion, List<Server> servers)
    {
        var batchSize = Math.Max(1, servers.Count / 4);  // Update 25% at a time
        
        for (int i = 0; i < servers.Count; i += batchSize)
        {
            var batch = servers.Skip(i).Take(batchSize).ToList();
            
            _logger.LogInformation(
                "Updating batch {Batch}: servers {Servers}",
                i / batchSize + 1,
                string.Join(", ", batch.Select(s => s.Name))
            );
            
            // Update batch
            foreach (var server in batch)
            {
                // Remove from load balancer
                await _loadBalancer.RemoveServerAsync(server);
                
                // Wait for connections to drain
                await Task.Delay(TimeSpan.FromSeconds(30));
                
                // Deploy new version
                await DeployToServerAsync(server, newVersion);
                
                // Health check
                var healthy = await HealthCheckAsync(server);
                if (!healthy)
                {
                    // Rollback this server
                    await RollbackServerAsync(server);
                    throw new DeploymentException($"Server {server.Name} failed health check");
                }
                
                // Add back to load balancer
                await _loadBalancer.AddServerAsync(server);
            }
            
            // Wait and monitor before next batch
            await Task.Delay(TimeSpan.FromMinutes(2));
            
            var errorRate = await GetErrorRateAsync();
            if (errorRate > 0.01)
            {
                _logger.LogError("High error rate, stopping deployment");
                throw new DeploymentException("Deployment halted due to errors");
            }
        }
        
        _logger.LogInformation("Rolling deployment complete");
    }
}
```

**Pros:**
- No additional infrastructure needed
- Gradual rollout reduces risk
- Can pause/stop if issues occur

**Cons:**
- Takes time to complete
- Both versions run simultaneously
- Rollback is slow (requires another rolling update)

**Best for:** Incremental updates, large server fleets, cost-sensitive environments

### Choosing the Right Strategy

```
Question                           Recommended Strategy
--------                           --------------------
Major breaking changes?            → Blue-Green
High-risk new feature?             → Canary
Many servers to update?            → Rolling
Need instant rollback?             → Blue-Green
Limited infrastructure budget?     → Rolling
Want user feedback during rollout? → Canary
Stateless application?             → Any
Stateful with database changes?    → Blue-Green or Rolling
Microservices architecture?        → Canary per service
```

### Quality Gates Between Environments

```yaml
# Example: Multi-environment promotion with gates
stages:
  - deploy-dev
  - test-dev
  - deploy-staging
  - test-staging
  - manual-approval
  - deploy-production
  - monitor-production

deploy-dev:
  stage: deploy-dev
  script:
    - ./deploy.sh dev
  environment: dev

test-dev:
  stage: test-dev
  script:
    - npm run test:integration
  needs: [deploy-dev]

deploy-staging:
  stage: deploy-staging
  script:
    - ./deploy.sh staging
  environment: staging
  needs: [test-dev]
  only:
    - main  # Only from main branch

test-staging:
  stage: test-staging
  script:
    - npm run test:e2e
    - npm run test:performance
  needs: [deploy-staging]

manual-approval:
  stage: manual-approval
  script:
    - echo "Waiting for approval"
  when: manual
  needs: [test-staging]
  only:
    - main

deploy-production:
  stage: deploy-production
  script:
    - ./deploy.sh production --strategy canary
  environment: production
  needs: [manual-approval]
  only:
    - main

monitor-production:
  stage: monitor-production
  script:
    - ./monitor-deployment.sh
    - sleep 300  # Monitor for 5 minutes
    - ./check-error-rates.sh
  needs: [deploy-production]
```

### Feature Flags for Safe Deployments

**Concept:** Deploy code with features disabled; enable gradually

```csharp
// Example: Feature flag for gradual rollout
public class OrderController : ControllerBase
{
    private readonly IFeatureFlagService _featureFlags;
    
    [HttpPost("orders")]
    public async Task<IActionResult> CreateOrder(OrderRequest request)
    {
        // Check if new payment flow is enabled for this user
        var useNewPaymentFlow = await _featureFlags.IsEnabledAsync(
            "new-payment-flow",
            userId: request.UserId
        );
        
        if (useNewPaymentFlow)
        {
            // New implementation (deployed but not fully enabled)
            return await CreateOrderWithNewPaymentAsync(request);
        }
        else
        {
            // Old implementation (still running for most users)
            return await CreateOrderWithLegacyPaymentAsync(request);
        }
    }
}

// Feature flag configuration
{
  "new-payment-flow": {
    "enabled": true,
    "rollout": {
      "type": "gradual",
      "percentage": 10,  // Start with 10% of users
      "ramp": {
        "day1": 10,
        "day3": 25,
        "day7": 50,
        "day14": 100
      }
    },
    "targeting": {
      "segments": ["beta-users", "internal-users"]
    }
  }
}
```

## Key Takeaways

1. **Environment promotion ensures quality**—progress through dev, staging, and production with increasing confidence at each stage.

2. **Different strategies suit different contexts**—blue-green for instant rollback, canary for gradual risk exposure, rolling for large fleets.

3. **Quality gates protect production**—automated tests and manual approvals ensure only validated code reaches customers.

4. **Feature flags decouple deployment from release**—deploy code anytime, enable features gradually with instant rollback capability.

5. **Staging should mirror production**—consistent environments prevent "works in staging" surprises.
