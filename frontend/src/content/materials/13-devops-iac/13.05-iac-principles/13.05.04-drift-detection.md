## Introduction

Configuration drift occurs when the actual state of your infrastructure deviates from the desired state defined in your Infrastructure as Code. This happens due to manual changes, automated scaling, security patches, or other out-of-band modifications. Detecting and remediating drift is crucial for maintaining consistent, predictable infrastructure.

## Key Concepts Summary

### What is Configuration Drift?

**Configuration drift** occurs when the real-world state of infrastructure deviates from the state defined in Infrastructure as Code.

```hcl
# Your IaC defines this:
resource "aws_instance" "web" {
  instance_type = "t2.micro"
  ami           = "ami-12345678"
}

# But in reality, someone manually changed it to:
# instance_type = "t2.small"  ← DRIFT!
```

**Result:** Your code says `t2.micro`, but the actual instance is `t2.small`.

---

## Common Causes of Drift

### 1. Manual Changes

```bash
# Someone makes a "quick fix" in the console
aws ec2 modify-instance-attribute \
  --instance-id i-1234567890abcdef0 \
  --instance-type t2.medium

# Now there's drift between code and reality
```

### 2. Auto-Scaling and Auto-Healing

```bash
# Auto-scaling group launches instances
# These instances might have different configs than IaC
```

### 3. Security Patches

```bash
# Automated security patching changes instance configurations
# Security group rules added by compliance tools
```

### 4. Multiple Tools Managing Same Resources

```bash
# Terraform creates a security group
# Later, AWS Config auto-remediates and adds rules
# Drift created!
```

### 5. Manual Emergency Fixes

```bash
# Production down at 3 AM
# Engineer makes emergency change via console
# Forgets to update IaC later
```

---

## Why Drift Matters

### 1. Inconsistency Across Environments

```
Development: t2.micro (as per code)
Staging:     t2.micro (as per code)
Production:  t2.large (manual change - drift!)
```

Result: Environments don't match, "works in staging" problems.

### 2. Failed Deployments

```bash
terraform apply
# Error: Security group rule conflicts
# Someone manually added conflicting rules
```

### 3. Security Risks

```bash
# IaC: Security group allows only port 443
# Reality: Someone added port 22 (SSH) for "debugging"
# Security vulnerability introduced!
```

### 4. Compliance Violations

```bash
# IaC: Encryption enabled
# Reality: Someone disabled encryption
# Fails audit!
```

### 5. Unpredictable Disaster Recovery

```bash
# Disaster occurs, you rebuild from IaC
# Result: Different from original (which had drift)
# Applications break!
```

## Three Strategies for Drift Detection

### Strategy 1: Stateful Comparison

**How it works:** Compare the last known good state (state file) with live infrastructure.

```bash
# Terraform approach
terraform plan
# Compares state file to actual infrastructure
# Shows differences

# Output:
# ~ resource "aws_instance" "web" {
#   ~ instance_type = "t2.small" -> "t2.micro" (drift detected)
# }
```

**Advantages:**
- ✅ Very precise
- ✅ Fast (uses state file)
- ✅ Shows exact changes needed

**Disadvantages:**
- ❌ Only works for resources managed by IaC
- ❌ Requires accurate state file
- ❌ Doesn't detect unmanaged resources

**Tools:** Terraform, CloudFormation, Pulumi

### Strategy 2: Stateless Scanning

**How it works:** Periodically scan the live environment against policy definitions.

```python
# Pseudo-code example
def check_all_instances():
    for instance in get_all_ec2_instances():
        if instance.encryption_enabled == False:
            report_drift(f"Instance {instance.id} not encrypted")
        
        if instance.has_public_ip and instance.environment == "prod":
            report_drift(f"Production instance {instance.id} has public IP")
```

**Advantages:**
- ✅ Detects unmanaged resources
- ✅ Works without state files
- ✅ Can enforce policies broadly

**Disadvantages:**
- ❌ Resource-intensive (queries all APIs)
- ❌ Slower
- ❌ Requires defining policies separately

**Tools:** Cloud Custodian, Steampipe, OPA, AWS Config

### Strategy 3: Event-Driven Detection

**How it works:** Cloud provider event streams trigger checks when resources change.

```yaml
# AWS EventBridge rule (pseudo-code)
when:
  event: "EC2 Instance State Change"
  or: "Security Group Modified"
do:
  - trigger_drift_check()
  - compare_with_iac()
  - alert_if_drift_detected()
```

**Advantages:**
- ✅ Real-time detection
- ✅ Low overhead
- ✅ Fast alerting

**Disadvantages:**
- ❌ Complex to set up
- ❌ Event stream coverage may be incomplete
- ❌ Cloud-specific

**Tools:** AWS EventBridge + Lambda, Azure Event Grid, Google Cloud Functions

## Detecting Drift with Terraform

### Basic Drift Detection

```bash
# Check for drift
terraform plan

# Output if no drift:
# No changes. Your infrastructure matches the configuration.

# Output if drift detected:
# Terraform will perform the following actions:
#
#   ~ resource "aws_instance" "web" {
#       ~ instance_type = "t2.small" -> "t2.micro"
#     }
```

### Refresh State First

```bash
# Update state to match reality (doesn't change infrastructure)
terraform apply -refresh-only

# Then check what would need to change to match code
terraform plan
```

### Targeted Drift Detection

```bash
# Check specific resource
terraform plan -target=aws_instance.web

# Check specific module
terraform plan -target=module.networking
```

### Automated Drift Detection (CI/CD)

```yaml
# .github/workflows/drift-detection.yml
name: Drift Detection
on:
  schedule:
    - cron: '0 */6 * * *'  # Every 6 hours

jobs:
  detect-drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
        
      - name: Terraform Init
        run: terraform init
        
      - name: Detect Drift
        run: |
          terraform plan -detailed-exitcode
        continue-on-error: true
        id: plan
        
      - name: Alert on Drift
        if: steps.plan.outputs.exitcode == 2
        run: |
          echo "Drift detected!"
          # Send alert to Slack, email, etc.
```

### HCP Terraform Drift Detection

```hcl
# Enable drift detection in HCP Terraform
terraform {
  cloud {
    organization = "my-org"
    
    workspaces {
      name = "production"
    }
  }
}
```

HCP Terraform (Standard Edition and above) provides:
- Scheduled drift detection
- Automatic drift reports
- Webhooks for notifications
- Health assessments

## Remediating Drift

### Option 1: Update Infrastructure to Match Code

```bash
# Terraform: Apply to restore desired state
terraform apply

# Pulumi: Update to restore desired state
pulumi up

# This OVERWRITES manual changes
```

**When to use:**
- Manual changes were mistakes
- Want to enforce IaC as source of truth
- Drift violates policies or security requirements

### Option 2: Update Code to Match Infrastructure

```bash
# 1. Refresh state to capture manual changes
terraform apply -refresh-only

# 2. Update code to match
# Edit main.tf to reflect the manual changes

# 3. Verify no further drift
terraform plan
# No changes needed
```

**When to use:**
- Manual change was intentional and approved
- Change needs to be preserved
- Want to "adopt" the manual change into IaC

### Option 3: Import Unmanaged Resources

```bash
# Someone created a resource manually
# Import it into Terraform management

# 1. Write the resource configuration
resource "aws_instance" "imported" {
  ami           = "ami-12345678"
  instance_type = "t2.micro"
}

# 2. Import the existing resource
terraform import aws_instance.imported i-1234567890abcdef0

# 3. Verify
terraform plan
# No changes needed
```

## Preventing Drift

### 1. Restrict Manual Changes

```json
// AWS IAM policy - deny console changes
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": [
        "ec2:ModifyInstanceAttribute",
        "ec2:ModifySecurityGroupRules"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:PrincipalArn": "arn:aws:iam::123456789:role/TerraformRole"
        }
      }
    }
  ]
}
```

### 2. Read-Only Console Access

```bash
# Give engineers read-only access
# All changes must go through IaC pipeline
```

### 3. Automated Drift Remediation

```yaml
# Automatically revert drift (use with caution!)
name: Auto-Remediate Drift
on:
  schedule:
    - cron: '0 * * * *'  # Every hour

jobs:
  remediate:
    runs-on: ubuntu-latest
    steps:
      - name: Check and Fix Drift
        run: |
          terraform init
          terraform plan -detailed-exitcode || terraform apply -auto-approve
```

**⚠️ Warning:** Auto-remediation can break things if not carefully designed!

### 4. GitOps Approach

```
┌──────────────┐
│     Git      │ ← Single source of truth
│  Repository  │
└──────┬───────┘
       │
       │ (automated sync)
       │
       ▼
┌──────────────┐
│ Infrastructure│
└──────────────┘

Any drift is automatically reverted
```

### 5. Immutable Infrastructure

```bash
# Instead of modifying instances, replace them
# No drift possible - resources are never changed
terraform destroy -target=aws_instance.web
terraform apply
```

## Continuous Drift Monitoring

### Pattern 1: Scheduled Checks

```yaml
# Run drift detection every 6 hours
schedule:
  - cron: '0 */6 * * *'
```

### Pattern 2: Pre-Deployment Checks

```yaml
# Check for drift before every deployment
steps:
  - name: Drift Check
    run: terraform plan -detailed-exitcode
  
  - name: Deploy
    if: steps.drift-check.outcome == 'success'
    run: terraform apply
```

### Pattern 3: Real-Time Alerts

```python
# AWS Lambda triggered by CloudTrail events
def lambda_handler(event, context):
    if event['eventName'] in ['ModifyInstanceAttribute', 'AuthorizeSecurityGroupIngress']:
        alert_team(f"Manual change detected: {event['eventName']}")
        trigger_drift_detection()
```

## Practice Exercise

After completing the materials (15 minutes max):

1. Create a simple Terraform configuration with one resource
2. Deploy it with `terraform apply`
3. Manually change the resource (e.g., via console or CLI)
4. Detect the drift with `terraform plan`
5. Choose a remediation strategy:
   - Option A: Restore with `terraform apply`
   - Option B: Accept drift with `terraform apply -refresh-only` and update code

Example:
```bash
# 1. Deploy
terraform apply

# 2. Manually change
aws ec2 modify-instance-attribute \
  --instance-id i-xxx \
  --instance-type t2.small

# 3. Detect drift
terraform plan

# 4. Remediate (choose one)
terraform apply  # Restore t2.micro
# OR
terraform apply -refresh-only  # Accept t2.small
```
