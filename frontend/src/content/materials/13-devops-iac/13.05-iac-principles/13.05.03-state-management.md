## Introduction

State management is the backbone of declarative Infrastructure as Code. The state file is the source of truth that maps your infrastructure code to real resources in your cloud provider. Understanding how to properly manage, secure, and synchronize state is crucial for reliable infrastructure automation, especially when working in teams.

## Key Concepts Summary

### What is Infrastructure State?

**State** is a mapping between your infrastructure code and the real resources that exist in your cloud provider.

```hcl
# Your Terraform code
resource "aws_instance" "web" {
  ami           = "ami-12345678"
  instance_type = "t2.micro"
}
```

```json
// Terraform state file (simplified)
{
  "resources": [
    {
      "type": "aws_instance",
      "name": "web",
      "instances": [
        {
          "attributes": {
            "id": "i-0123456789abcdef",
            "ami": "ami-12345678",
            "instance_type": "t2.micro",
            "public_ip": "54.123.45.67"
          }
        }
      ]
    }
  ]
}
```

The state file tells Terraform:
- Which real resources correspond to which code resources
- Current configuration of each resource
- Dependencies between resources
- Metadata like resource IDs and computed attributes

---

## Why State Management Matters

### 1. Mapping Code to Reality

Without state, Terraform can't know which real resources correspond to your code.

```bash
# First run
terraform apply
# Creates instance i-0123456789abcdef

# Without state file, second run would:
# - Not know the instance exists
# - Try to create a duplicate
# - Fail or create unintended resources
```

### 2. Performance Optimization

State allows Terraform to know what exists without querying every resource.

```bash
# With state: Fast - reads from state file
terraform plan
# Completed in 2 seconds

# Without state: Slow - must query all cloud APIs
terraform plan -refresh-only
# Completed in 45 seconds for 100 resources
```

### 3. Tracking Metadata

State stores metadata that isn't in your code:

```json
{
  "id": "i-0123456789abcdef",
  "public_ip": "54.123.45.67",      // Not in code
  "private_ip": "10.0.1.5",         // Not in code
  "arn": "arn:aws:ec2:...",         // Not in code
  "created_at": "2024-01-15T10:30:00Z"
}
```

## Local vs Remote State

### Local State

**Default behavior:** State stored in `terraform.tfstate` file locally.

```bash
my-infrastructure/
├── main.tf
├── terraform.tfstate        # State file here
└── terraform.tfstate.backup
```

**Advantages:**
- ✅ Simple for learning
- ✅ No additional setup required
- ✅ Fast access

**Disadvantages:**
- ❌ Not suitable for teams (conflicts)
- ❌ No locking (concurrent runs corrupt state)
- ❌ State file contains secrets in plain text
- ❌ No versioning/backup
- ❌ Easy to accidentally delete or commit to Git

### Remote State

**Recommended for teams:** State stored in a shared backend (S3, Azure Storage, etc.)

```hcl
# backend.tf
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}
```

**Advantages:**
- ✅ Team collaboration (shared access)
- ✅ State locking prevents conflicts
- ✅ Encryption at rest
- ✅ Versioning and backup
- ✅ Audit logging
- ✅ Access control

**Disadvantages:**
- ⚠️ Requires additional infrastructure
- ⚠️ Dependency on backend availability
- ⚠️ Slightly slower than local

## State Locking

State locking prevents multiple users from running Terraform simultaneously, which would corrupt the state.

### Without Locking (Dangerous!)

```bash
# Developer A starts apply
terraform apply
# Started at 10:00 AM...

# Developer B starts apply (different terminal)
terraform apply
# Started at 10:00 AM...

# Result: State file corrupted! 
# Both processes write conflicting changes
```

### With Locking (Safe)

```bash
# Developer A starts apply
terraform apply
# Acquired state lock ID: abc123...

# Developer B tries to start apply
terraform apply
# Error: Failed to acquire state lock
# Lock Info:
#   ID:        abc123
#   Operation: apply
#   Who:       developer-a@example.com
#   Created:   2024-01-15 10:00:00 UTC
```

### Configuring State Locking

```hcl
# S3 backend with DynamoDB locking
terraform {
  backend "s3" {
    bucket         = "terraform-state"
    key            = "state/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"  # Enables locking
  }
}
```

```hcl
# Azure backend (locking built-in)
terraform {
  backend "azurerm" {
    resource_group_name  = "terraform-state-rg"
    storage_account_name = "tfstate"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
  }
}
```

## Remote State Backend Examples

### AWS S3 + DynamoDB

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/vpc/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
    
    # Optional: workspace-aware paths
    workspace_key_prefix = "workspaces"
  }
}
```

**Setup requirements:**
1. Create S3 bucket with versioning enabled
2. Enable encryption on bucket
3. Create DynamoDB table with primary key `LockID`
4. Configure IAM permissions

### Azure Storage

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "terraform-state-rg"
    storage_account_name = "tfstate20240115"
    container_name       = "tfstate"
    key                  = "production.tfstate"
  }
}
```

### Terraform Cloud

```hcl
terraform {
  cloud {
    organization = "my-org"
    
    workspaces {
      name = "production"
    }
  }
}
```

**Benefits:**
- Built-in state management
- Built-in locking
- Web UI for state viewing
- Remote execution
- Team access control
- Audit logging

### Google Cloud Storage

```hcl
terraform {
  backend "gcs" {
    bucket = "my-terraform-state"
    prefix = "terraform/state"
  }
}
```

## State Management Best Practices

### 1. Never Commit State to Git

```gitignore
# .gitignore
*.tfstate
*.tfstate.*
.terraform/
```

**Why:** State files contain:
- Resource IDs
- IP addresses
- Secrets and sensitive data
- Provider credentials

### 2. Use Remote State for Teams

```hcl
# Always use remote state for production
terraform {
  backend "s3" {
    bucket  = "terraform-state"
    key     = "prod/terraform.tfstate"
    region  = "us-east-1"
    encrypt = true
  }
}
```

### 3. Enable State Versioning

```bash
# S3 bucket versioning
aws s3api put-bucket-versioning \
  --bucket my-terraform-state \
  --versioning-configuration Status=Enabled
```

This allows you to recover from accidental state corruption:

```bash
# List state versions
aws s3api list-object-versions \
  --bucket my-terraform-state \
  --prefix terraform.tfstate

# Restore previous version if needed
aws s3api get-object \
  --bucket my-terraform-state \
  --key terraform.tfstate \
  --version-id <version-id> \
  terraform.tfstate
```

### 4. Encrypt State

```hcl
terraform {
  backend "s3" {
    bucket  = "terraform-state"
    key     = "terraform.tfstate"
    encrypt = true  # Enable encryption
    kms_key_id = "arn:aws:kms:us-east-1:123456789:key/..."
  }
}
```

### 5. Separate State by Environment

```
terraform-states/
├── dev/
│   └── terraform.tfstate
├── staging/
│   └── terraform.tfstate
└── prod/
    └── terraform.tfstate
```

```hcl
# Environment-specific backend configuration
terraform {
  backend "s3" {
    bucket = "terraform-state"
    key    = "${var.environment}/terraform.tfstate"
    region = "us-east-1"
  }
}
```

### 6. Use Workspaces for Environment Isolation

```bash
# Create workspaces
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod

# Switch between workspaces
terraform workspace select prod

# Each workspace has its own state
```

## Handling State Conflicts

### Scenario 1: State Lock Stuck

```bash
# Lock is stuck (previous run crashed)
terraform apply
# Error: state locked

# Force unlock (use with caution!)
terraform force-unlock <lock-id>
```

**⚠️ Warning:** Only use `force-unlock` if you're certain no other process is running!

### Scenario 2: State Drift

```bash
# Someone made manual changes
terraform plan
# Shows unexpected changes

# Refresh state to match reality
terraform apply -refresh-only

# Or restore desired state
terraform apply
```

### Scenario 3: Merge Conflicts (Migration)

```bash
# Moving from local to remote state
terraform init -migrate-state

# Terraform will:
# 1. Read local state
# 2. Write to remote backend
# 3. Delete local state (with confirmation)
```

## State Operations

### View State

```bash
# List resources in state
terraform state list

# Show specific resource
terraform state show aws_instance.web

# View entire state
terraform show
```

### Modify State (Advanced)

```bash
# Remove resource from state (doesn't delete resource)
terraform state rm aws_instance.old_server

# Move resource to new name
terraform state mv aws_instance.web aws_instance.web_server

# Import existing resource
terraform import aws_instance.web i-0123456789abcdef

# Pull state to local file
terraform state pull > terraform.tfstate

# Push state from local file (dangerous!)
terraform state push terraform.tfstate
```

## Team Collaboration Patterns

### Pattern 1: Shared Remote State

```hcl
# All team members use same backend
terraform {
  backend "s3" {
    bucket = "team-terraform-state"
    key    = "app/terraform.tfstate"
    region = "us-east-1"
  }
}
```

### Pattern 2: State Locking for Safety

```bash
# Developer A
terraform apply
# Acquired lock...

# Developer B
terraform apply
# Waiting for lock... (blocked until A completes)
```

### Pattern 3: CI/CD with State

```yaml
# GitHub Actions example
- name: Terraform Apply
  env:
    AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
    AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
  run: |
    terraform init
    terraform apply -auto-approve
  # CI/CD system accesses same remote state
```

## Common Mistakes to Avoid

| Mistake | Problem | Solution |
|---------|---------|----------|
| Committing state to Git | Exposes secrets | Add `*.tfstate*` to `.gitignore` |
| Using local state for teams | Conflicts and overwrites | Use remote state backend |
| No state locking | Concurrent runs corrupt state | Enable locking (DynamoDB, etc.) |
| Not encrypting state | Secrets in plain text | Enable encryption on backend |
| Manual state edits | State corruption | Use `terraform state` commands |
| Ignoring state drift | Inconsistent infrastructure | Regular `terraform plan` checks |
