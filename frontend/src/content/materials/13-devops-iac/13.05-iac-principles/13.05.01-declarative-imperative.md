## Introduction

Infrastructure as Code can be implemented using two fundamentally different approaches: declarative and imperative. Declarative IaC describes *what you want* (the desired end state), while imperative IaC specifies *how to achieve it* (step-by-step instructions). Understanding this distinction is crucial for choosing the right tools and designing maintainable infrastructure code.

## Key Concepts Summary

### Declarative Infrastructure as Code

**What it is:** You describe the *desired end state* of your infrastructure, and the tool determines how to achieve it.

```hcl
# Terraform example - Declarative
resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  
  tags = {
    Name = "web-server"
  }
}

# If you run this multiple times:
# - If instance doesn't exist → creates it
# - If instance exists with same config → does nothing
# - If instance exists with different config → updates it
```

**Characteristics:**
- Focus on "what" not "how"
- Built-in state tracking
- Automatically handles creates, updates, and deletes
- Idempotent by design
- Better at handling configuration drift

**Popular Tools:**
- Terraform
- AWS CloudFormation
- Azure Resource Manager (ARM) / Bicep
- Pulumi (uses imperative languages with declarative behavior)
- Kubernetes manifests

### Imperative Infrastructure as Code

**What it is:** You provide *step-by-step instructions* on how to build the infrastructure.

```yaml
# Ansible example - Imperative
- name: Ensure web server is running
  hosts: web_servers
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
        
    - name: Copy configuration file
      copy:
        src: nginx.conf
        dest: /etc/nginx/nginx.conf
        
    - name: Restart nginx
      service:
        name: nginx
        state: restarted
```

**Characteristics:**
- Focus on "how" to achieve the result
- Explicit sequencing of operations
- More procedural control
- May require manual state management
- Better for configuration management tasks

**Popular Tools:**
- Ansible (primarily imperative, but with idempotent modules)
- Chef
- Puppet
- Shell scripts
- PowerShell DSC

### Key Differences

| Aspect | Declarative | Imperative |
|--------|-------------|------------|
| **Focus** | Desired end state | Step-by-step instructions |
| **State Management** | Built-in state tracking | Manual or no state tracking |
| **Idempotency** | Automatic | Must be explicitly coded |
| **Configuration Drift** | Detects and remediates easily | Difficult to detect |
| **Learning Curve** | Steeper initially | More intuitive for developers |
| **Best For** | Infrastructure provisioning | Configuration management |
| **Re-run Safety** | Safe to run multiple times | May cause errors if re-run |

### Real-World Analogy

**Declarative:** "I want a coffee on my desk at 9 AM"
- The system figures out all the steps needed
- If coffee already exists and is correct, nothing happens
- If coffee is cold, it replaces it

**Imperative:** "Go to the kitchen, fill the kettle with water, turn it on, wait for it to boil, add coffee grounds to the French press, pour the water, wait 4 minutes, press down the plunger, pour into a cup, bring to my desk"
- You control every step
- Running it again would try to repeat all steps

## Benefits of Declarative IaC

### 1. Handling Configuration Drift
Declarative tools excel at detecting when actual infrastructure has drifted from the desired state and can automatically reconcile the difference.

```bash
# Terraform detects drift
$ terraform plan
~ aws_instance.web_server will be updated in-place
  ~ instance_type = "t2.small" -> "t2.micro" (change detected)
```

### 2. Automatic Dependency Resolution
Declarative tools understand resource dependencies and create/destroy in the correct order.

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id  # Automatic dependency
  cidr_block = "10.0.1.0/24"
}
# Terraform knows to create VPC before subnet
```

### 3. Predictable Outcomes
Running the same declarative code multiple times produces identical results.

## When to Use Each Approach

### Use Declarative IaC When:
- Provisioning cloud infrastructure (VMs, networks, storage)
- Managing Kubernetes resources
- Need to detect and remediate drift
- Want to track complete infrastructure state
- Multiple team members need to collaborate
- Infrastructure is relatively static with occasional updates

### Use Imperative IaC When:
- Configuring servers and applications
- Performing complex orchestration with branching logic
- Need fine-grained control over execution order
- Handling one-time migrations or transformations
- Working with legacy systems without APIs
- Need to integrate with existing scripts

### Hybrid Approach (Common in Practice)
Most organizations use both:
1. **Declarative** (Terraform) → Provision infrastructure
2. **Imperative** (Ansible) → Configure servers and applications

```hcl
# Terraform creates the servers
resource "aws_instance" "app_server" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  
  provisioner "local-exec" {
    # Then Ansible configures them
    command = "ansible-playbook -i ${self.public_ip}, configure.yml"
  }
}
```

## Common Mistakes to Avoid

| Mistake | Problem | Solution |
|---------|---------|----------|
| Using imperative scripts for infrastructure | Drift detection impossible, hard to maintain | Use declarative tools like Terraform |
| Mixing manual changes with IaC | State files become inaccurate | All changes through code only |
| Not understanding tool paradigm | Fighting the tool's design | Learn the intended workflow |
| Over-engineering simple tasks | Unnecessary complexity | Use scripts for truly one-off tasks |

## Practice Exercise

After completing the materials (15 minutes max):

1. Compare two approaches to creating a storage bucket:
   - Write a declarative configuration (e.g., Terraform syntax)
   - Write an imperative script (e.g., AWS CLI commands)
2. Consider what happens if you run each twice
3. Identify which approach would better detect if someone manually deleted the bucket

Example starting point:
```hcl
# Declarative (Terraform)
resource "aws_s3_bucket" "data" {
  bucket = "my-data-bucket"
}
```

```bash
# Imperative (AWS CLI)
aws s3 mb s3://my-data-bucket
# What happens if you run this twice?
```
