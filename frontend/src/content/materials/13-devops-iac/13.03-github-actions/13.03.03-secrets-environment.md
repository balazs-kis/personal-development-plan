# Lesson 3: Secrets and Environment Variables

## Learning Objectives

By the end of this lesson, you will be able to:
- Create and manage secrets at repository, environment, and organization levels
- Use secrets securely in workflows without exposing them in logs
- Configure environment variables for workflows, jobs, and steps
- Implement environment-specific configurations
- Apply security best practices for sensitive data
- Use GitHub environments with protection rules

---

## Introduction

Secrets and environment variables enable you to pass configuration and sensitive data to your workflows without hardcoding them. GitHub provides secure secret storage with automatic masking in logs, and environments allow you to configure deployment targets with protection rules and approvals.

## Key Concepts Summary

### Creating and Using Secrets

```yaml
# Secrets are created in GitHub UI:
# Settings > Secrets and variables > Actions > New repository secret

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to production
        env:
          API_KEY: ${{ secrets.API_KEY }}
          DATABASE_PASSWORD: ${{ secrets.DB_PASSWORD }}
        run: |
          # Secrets are automatically masked in logs
          echo "Deploying with API key..."
          # Output: Deploying with API key...
          # (The actual key value is hidden as ***)
          
          deploy.sh --api-key "$API_KEY"
```

### Secret Levels

```yaml
# Repository-level secrets (available to all workflows in repo)
${{ secrets.REPOSITORY_SECRET }}

# Environment-level secrets (only available when deploying to that environment)
jobs:
  deploy:
    environment: production
    steps:
      - name: Use environment secret
        env:
          PROD_API_KEY: ${{ secrets.PROD_API_KEY }}
        run: deploy.sh

# Organization-level secrets (available to selected repos in organization)
${{ secrets.ORG_WIDE_SECRET }}
```

### Environment Variables

```yaml
# Workflow-level environment variables
env:
  BUILD_CONFIGURATION: Release
  NODE_ENV: production

jobs:
  # Job-level environment variables
  build:
    runs-on: ubuntu-latest
    env:
      DOTNET_VERSION: '8.0'
      OUTPUT_DIR: './dist'
    
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      
      # Step-level environment variables
      - name: Build
        env:
          BUILD_FLAGS: '--no-incremental --verbosity minimal'
        run: |
          echo "Configuration: $BUILD_CONFIGURATION"
          echo ".NET Version: $DOTNET_VERSION"
          dotnet build -c $BUILD_CONFIGURATION -o $OUTPUT_DIR $BUILD_FLAGS
      
      # Accessing in different shells
      - name: PowerShell example
        shell: pwsh
        run: |
          Write-Host "Configuration: $env:BUILD_CONFIGURATION"
          Write-Host "Output: $env:OUTPUT_DIR"
```

### Default Environment Variables

```yaml
jobs:
  info:
    runs-on: ubuntu-latest
    steps:
      - name: Print GitHub context
        run: |
          # GitHub provides many default environment variables
          echo "Repository: $GITHUB_REPOSITORY"
          echo "Ref: $GITHUB_REF"
          echo "SHA: $GITHUB_SHA"
          echo "Actor: $GITHUB_ACTOR"
          echo "Workflow: $GITHUB_WORKFLOW"
          echo "Action: $GITHUB_ACTION"
          echo "Event: $GITHUB_EVENT_NAME"
          echo "Runner OS: $RUNNER_OS"
          echo "Runner Temp: $RUNNER_TEMP"
          echo "Workspace: $GITHUB_WORKSPACE"
```

### Environments with Protection Rules

```yaml
# Environment configuration is done in GitHub UI:
# Settings > Environments > New environment

jobs:
  deploy-staging:
    # Reference environment by name
    environment:
      name: staging
      url: https://staging.example.com
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to staging
        env:
          STAGING_API_KEY: ${{ secrets.STAGING_API_KEY }}
        run: deploy.sh staging
  
  deploy-production:
    needs: deploy-staging
    # Production environment with protection rules
    environment:
      name: production
      url: https://example.com
    runs-on: ubuntu-latest
    steps:
      # This job waits for approval if required reviewers are configured
      - name: Deploy to production
        env:
          PROD_API_KEY: ${{ secrets.PROD_API_KEY }}
          PROD_DB_CONNECTION: ${{ secrets.PROD_DB_CONNECTION }}
        run: deploy.sh production
```

### Environment Protection Rules

```yaml
# Environment protection rules (configured in UI):
# - Required reviewers: Up to 6 people/teams must approve
# - Wait timer: Delay deployment by specified minutes
# - Deployment branches: Restrict which branches can deploy

jobs:
  deploy:
    environment:
      name: production
    runs-on: ubuntu-latest
    steps:
      # Workflow pauses here until:
      # 1. Required reviewers approve
      # 2. Wait timer expires
      # 3. Branch is allowed to deploy
      - name: Deploy
        run: echo "Deploying to production"
```

### Setting Outputs and Environment Variables Dynamically

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Set environment variable
        run: |
          # Set env var for subsequent steps in same job
          echo "VERSION=1.2.3" >> $GITHUB_ENV
          echo "BUILD_TIME=$(date -u +'%Y%m%d-%H%M%S')" >> $GITHUB_ENV
      
      - name: Use environment variable
        run: |
          echo "Version: $VERSION"
          echo "Build time: $BUILD_TIME"
      
      - name: Set job output
        id: build-info
        run: |
          # Set output for use in other jobs
          echo "artifact-name=myapp-$VERSION" >> $GITHUB_OUTPUT
          echo "sha-short=$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT
    
    outputs:
      artifact-name: ${{ steps.build-info.outputs.artifact-name }}
      sha: ${{ steps.build-info.outputs.sha-short }}
  
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Deploy artifact
        run: |
          echo "Deploying: ${{ needs.build.outputs.artifact-name }}"
          echo "Git SHA: ${{ needs.build.outputs.sha }}"
```

## Security Best Practices

### Principle of Least Privilege

```yaml
# Restrict GITHUB_TOKEN permissions to minimum required
permissions:
  contents: read              # Read repository contents
  pull-requests: write        # Comment on PRs

jobs:
  test:
    runs-on: ubuntu-latest
    # Can override permissions per job
    permissions:
      contents: read
      checks: write           # Write test results
    steps:
      - uses: actions/checkout@v4
      - run: npm test
```

### Masking Sensitive Values

```yaml
jobs:
  example:
    runs-on: ubuntu-latest
    steps:
      - name: Generate token
        run: |
          # If you generate a secret value, mask it immediately
          TOKEN=$(generate-token.sh)
          echo "::add-mask::$TOKEN"
          echo "TOKEN=$TOKEN" >> $GITHUB_ENV
      
      - name: Use token
        run: |
          # Token value is now masked in logs
          curl -H "Authorization: Bearer $TOKEN" https://api.example.com
```

### Avoiding Structured Data in Secrets

```yaml
# ❌ BAD: Don't store JSON/YAML as a secret
# Secret: API_CONFIG = {"key": "abc123", "endpoint": "https://api.example.com"}
- name: Bad practice
  env:
    CONFIG: ${{ secrets.API_CONFIG }}
  run: |
    # Values inside JSON won't be masked!
    echo $CONFIG

# ✅ GOOD: Store individual values as separate secrets
- name: Good practice
  env:
    API_KEY: ${{ secrets.API_KEY }}
    API_ENDPOINT: ${{ secrets.API_ENDPOINT }}
  run: |
    # Both values are properly masked
    echo "Connecting to $API_ENDPOINT"
```

### Secret Rotation

```yaml
# When a secret is exposed:
# 1. Delete the workflow run containing the exposed secret
# 2. Rotate the secret immediately
# 3. Update the secret value in GitHub

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Check secret age
        run: |
          # Consider implementing secret rotation checks
          if [ "$SECRET_AGE_DAYS" -gt 90 ]; then
            echo "::warning::Secret is older than 90 days, consider rotating"
          fi
```

### Using GitHub CLI for Secrets

```bash
# Create secret via GitHub CLI
gh secret set API_KEY --body "your-secret-value"

# Set from file
gh secret set CERTIFICATE --body @certificate.pem

# List secrets
gh secret list

# Delete secret
gh secret delete API_KEY
```

## Common Patterns

### Multi-Environment Configuration

```yaml
jobs:
  deploy-dev:
    environment: development
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to dev
        env:
          API_URL: ${{ secrets.DEV_API_URL }}
          DB_CONNECTION: ${{ secrets.DEV_DB_CONNECTION }}
        run: deploy.sh
  
  deploy-staging:
    needs: deploy-dev
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to staging
        env:
          API_URL: ${{ secrets.STAGING_API_URL }}
          DB_CONNECTION: ${{ secrets.STAGING_DB_CONNECTION }}
        run: deploy.sh
  
  deploy-prod:
    needs: deploy-staging
    environment: production
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to production
        env:
          API_URL: ${{ secrets.PROD_API_URL }}
          DB_CONNECTION: ${{ secrets.PROD_DB_CONNECTION }}
        run: deploy.sh
```

### Conditional Secrets

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Set environment based on branch
        run: |
          if [ "${{ github.ref }}" == "refs/heads/main" ]; then
            echo "ENV_NAME=production" >> $GITHUB_ENV
          else
            echo "ENV_NAME=staging" >> $GITHUB_ENV
          fi
      
      - name: Deploy with environment-specific config
        env:
          # Choose secrets based on environment
          API_KEY: ${{ github.ref == 'refs/heads/main' && secrets.PROD_API_KEY || secrets.STAGING_API_KEY }}
        run: |
          echo "Deploying to $ENV_NAME"
          deploy.sh --env $ENV_NAME --api-key "$API_KEY"
```

### Docker Login with Secrets

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      # Docker Hub
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      
      # GitHub Container Registry
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: |
            myuser/myapp:latest
            ghcr.io/${{ github.repository }}:latest
```

### Configuration Files from Secrets

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      # Create config file from secret
      - name: Create kubeconfig
        run: |
          mkdir -p ~/.kube
          echo "${{ secrets.KUBECONFIG }}" > ~/.kube/config
          chmod 600 ~/.kube/config
      
      # Create .env file from multiple secrets
      - name: Create .env file
        run: |
          cat > .env << EOF
          DATABASE_URL=${{ secrets.DATABASE_URL }}
          REDIS_URL=${{ secrets.REDIS_URL }}
          API_KEY=${{ secrets.API_KEY }}
          SECRET_KEY=${{ secrets.SECRET_KEY }}
          EOF
          chmod 600 .env
      
      - name: Deploy
        run: kubectl apply -f deployment.yaml
```

## Best Practices Checklist

- ✅ Never store secrets in code or workflow files
- ✅ Use separate secrets for each environment (dev, staging, prod)
- ✅ Rotate secrets regularly (every 90 days recommended)
- ✅ Use environment protection rules for production deployments
- ✅ Grant minimum required permissions to GITHUB_TOKEN
- ✅ Mask any dynamically generated sensitive values with `::add-mask::`
- ✅ Store individual values as separate secrets, not JSON/YAML structures
- ✅ Use required reviewers for sensitive deployments
- ✅ Audit secret usage through workflow logs (values are masked)
- ✅ Delete workflow runs if secrets are accidentally exposed

## When to Use What

| Use Case | Solution |
|----------|----------|
| API keys and passwords | Repository or environment secrets |
| Environment-specific config | Environment secrets |
| Temporary credentials | Generate and mask in workflow |
| Non-sensitive config | Environment variables |
| Organization-wide credentials | Organization secrets |
| Required approvals | Environment protection rules |
| Branch restrictions | Environment deployment branches |
