## Introduction

Slow tests kill productivity. Developers lose focus waiting for feedback. A 30-minute test suite means 30 minutes before you know if your code works. This lesson teaches you proven strategies to reduce test execution time from hours to minutes, or minutes to seconds.

**Key principle:** The value of a test decreases exponentially with feedback time. A 1-minute test suite is infinitely more valuable than a 30-minute one.

## Key Concepts Summary

### The Cost of Slow Tests

```
Impact of Test Duration on Productivity:

1-minute test suite:
- Developer makes change
- Runs tests: 1 minute
- Gets feedback: immediately
- Context preserved: 100%
- Can make 10+ iterations/hour

10-minute test suite:
- Developer makes change
- Runs tests: 10 minutes
- Gets feedback: after context switch
- Context preserved: 50%
- Can make 3-4 iterations/hour

30-minute test suite:
- Developer makes change
- Runs tests: 30 minutes
- Gets feedback: after lunch/meeting
- Context preserved: 10%
- Can make 1-2 iterations/hour
- Often skipped locally (!)

The Goal:
< 1 minute: Unit tests
< 5 minutes: Integration tests
< 15 minutes: Full suite (in CI)
```

### Optimization Strategies Overview

```
1. INTELLIGENT TEST SELECTION
   Run only tests affected by code changes
   Speedup: 70-95% reduction in test time

2. TEST SPLITTING
   Distribute tests optimally across workers
   Speedup: Near-linear with worker count

3. CACHING
   Cache dependencies, build artifacts, test results
   Speedup: 30-70% reduction

4. TEST CATEGORIZATION
   Run fast tests first, slow tests in parallel
   Speedup: Faster failure detection

5. INFRASTRUCTURE OPTIMIZATION
   Use faster hardware, optimize I/O
   Speedup: 20-50% improvement

6. TEST REFACTORING
   Make individual tests faster
   Speedup: Varies greatly
```

### Intelligent Test Selection

```
Traditional Approach:
Code change → Run ALL tests → 30 minutes

Intelligent Selection:
Code change → Analyze dependencies → Run affected tests → 3 minutes

How it works:
1. Build dependency graph of code and tests
2. Track which tests cover which code
3. When code changes, run only affected tests
4. Periodically run full suite (nightly) to catch integration issues

Example dependency graph:
CustomerService.cs
├── CustomerServiceTests.cs ✓ Run
├── OrderServiceTests.cs ✓ Run (uses CustomerService)
└── ProductServiceTests.cs ✗ Skip (no dependency)

Result: 66% of tests skipped!
```

```yaml
# GitHub Actions: Run affected tests only
name: CI

on: [pull_request]

jobs:
  test-affected:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Full history for git diff
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Find Changed Files
        id: changed
        run: |
          # Get changed C# files
          CHANGED_FILES=$(git diff --name-only origin/main...HEAD | grep '\.cs$' || true)
          echo "changed_files<<EOF" >> $GITHUB_OUTPUT
          echo "$CHANGED_FILES" >> $GITHUB_OUTPUT
          echo "EOF" >> $GITHUB_OUTPUT
      
      - name: Determine Affected Test Projects
        id: affected
        run: |
          # Simple heuristic: if file is in src/ProjectA, run tests in tests/ProjectA.Tests
          # In practice, use a dependency analysis tool
          
          AFFECTED_TESTS=""
          if echo "${{ steps.changed.outputs.changed_files }}" | grep -q "src/CustomerService"; then
            AFFECTED_TESTS="$AFFECTED_TESTS tests/CustomerService.Tests/CustomerService.Tests.csproj"
          fi
          
          if echo "${{ steps.changed.outputs.changed_files }}" | grep -q "src/OrderService"; then
            AFFECTED_TESTS="$AFFECTED_TESTS tests/OrderService.Tests/OrderService.Tests.csproj"
          fi
          
          echo "projects=$AFFECTED_TESTS" >> $GITHUB_OUTPUT
      
      - name: Run Affected Tests
        if: steps.affected.outputs.projects != ''
        run: |
          for project in ${{ steps.affected.outputs.projects }}; do
            echo "Running tests in $project"
            dotnet test $project --verbosity normal
          done
      
      - name: No Tests to Run
        if: steps.affected.outputs.projects == ''
        run: echo "No test projects affected by changes"
```

### Test Splitting by Timing Data

```bash
# Generate test timing data
dotnet test --logger "trx" --results-directory ./TestResults

# Parse TRX to extract timing data
# test-times.json format:
# {
#   "CustomerServiceTests.CreateCustomer": 0.523,
#   "CustomerServiceTests.UpdateCustomer": 0.234,
#   "OrderServiceTests.PlaceOrder": 1.456,
#   ...
# }
```

```python
# split-tests.py - Split tests optimally based on timing
import json
import sys

def split_tests_by_time(test_times, num_shards):
    """Split tests into shards with balanced execution time"""
    
    # Sort tests by duration (longest first)
    sorted_tests = sorted(test_times.items(), key=lambda x: x[1], reverse=True)
    
    # Initialize shards
    shards = [[] for _ in range(num_shards)]
    shard_times = [0.0] * num_shards
    
    # Greedy algorithm: assign each test to shard with least total time
    for test_name, duration in sorted_tests:
        min_shard = shard_times.index(min(shard_times))
        shards[min_shard].append(test_name)
        shard_times[min_shard] += duration
    
    return shards, shard_times

# Read timing data
with open('test-times.json') as f:
    test_times = json.load(f)

# Split into 4 shards
shards, shard_times = split_tests_by_time(test_times, 4)

# Output results
for i, (shard, time) in enumerate(zip(shards, shard_times)):
    print(f"Shard {i+1} (estimated {time:.2f}s):")
    for test in shard:
        print(f"  {test}")
    print()
```

```yaml
# GitHub Actions: Use timing-based splitting
name: CI

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Restore Test Timing Data
        uses: actions/cache@v4
        with:
          path: test-times.json
          key: test-times-${{ github.sha }}
          restore-keys: test-times-
      
      - name: Split Tests
        id: split
        run: |
          python scripts/split-tests.py ${{ matrix.shard }} 4 > shard-tests.txt
      
      - name: Run Shard Tests
        run: |
          # Run only tests in this shard
          while IFS= read -r test; do
            dotnet test --filter "FullyQualifiedName~$test"
          done < shard-tests.txt
```

### Caching Strategies

```yaml
# GitHub Actions: Comprehensive caching
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      # Cache NuGet packages
      - name: Cache NuGet packages
        uses: actions/cache@v4
        with:
          path: ~/.nuget/packages
          key: ${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}
          restore-keys: |
            ${{ runner.os }}-nuget-
      
      # Cache build output
      - name: Cache Build Output
        uses: actions/cache@v4
        with:
          path: |
            **/bin
            **/obj
          key: ${{ runner.os }}-build-${{ hashFiles('**/*.cs') }}
          restore-keys: |
            ${{ runner.os }}-build-
      
      # Cache test results for unchanged tests
      - name: Cache Test Results
        uses: actions/cache@v4
        with:
          path: TestResults/
          key: ${{ runner.os }}-tests-${{ hashFiles('**/*.cs') }}
          restore-keys: |
            ${{ runner.os }}-tests-
      
      - name: Restore dependencies
        run: dotnet restore
      
      - name: Build
        run: dotnet build --no-restore
      
      - name: Test
        run: dotnet test --no-build --verbosity normal
```

### xUnit Performance Optimization

```csharp
// xUnit performance tips from Nick Chapsas video

// 1. Use IClassFixture for expensive setup
public class DatabaseFixture : IDisposable
{
    public MyDbContext Context { get; }
    
    public DatabaseFixture()
    {
        // Expensive: create once per test class
        Context = new MyDbContext();
    }
    
    public void Dispose() => Context.Dispose();
}

public class DatabaseTests : IClassFixture<DatabaseFixture>
{
    private readonly DatabaseFixture _fixture;
    
    public DatabaseTests(DatabaseFixture fixture)
    {
        _fixture = fixture;
    }
    
    [Fact]
    public void Test1() { /* uses _fixture.Context */ }
    
    [Fact]
    public void Test2() { /* uses _fixture.Context */ }
}

// 2. Use ICollectionFixture for shared setup across multiple classes
[CollectionDefinition("Database collection")]
public class DatabaseCollection : ICollectionFixture<DatabaseFixture>
{
}

[Collection("Database collection")]
public class CustomerTests
{
    [Fact]
    public void Test1() { }
}

[Collection("Database collection")]
public class OrderTests
{
    [Fact]
    public void Test2() { }
}

// 3. Configure parallel execution
// xunit.runner.json
{
  "parallelizeAssembly": true,
  "parallelizeTestCollections": true,
  "maxParallelThreads": -1  // Use all available cores
}

// 4. Use Assembly-level parallelization
// AssemblyInfo.cs
[assembly: CollectionBehavior(DisableTestParallelization = false, MaxParallelThreads = 8)]
```

### Profiling and Identifying Slow Tests

```yaml
# GitHub Actions: Profile test execution
name: Profile Tests

on: [workflow_dispatch]

jobs:
  profile:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Run Tests with Detailed Timing
        run: |
          dotnet test \
            --logger "trx;LogFileName=results.trx" \
            --logger "console;verbosity=detailed" \
            --results-directory TestResults
      
      - name: Extract Slow Tests
        run: |
          # Parse TRX and find tests over 1 second
          python3 << 'EOF'
          import xml.etree.ElementTree as ET
          
          tree = ET.parse('TestResults/results.trx')
          root = tree.getroot()
          
          ns = {'ns': 'http://microsoft.com/schemas/VisualStudio/TeamTest/2010'}
          
          slow_tests = []
          for test in root.findall('.//ns:UnitTestResult', ns):
              duration = test.get('duration')
              test_name = test.get('testName')
              
              if duration:
                  # Parse duration (format: HH:MM:SS.mmmmmmm)
                  parts = duration.split(':')
                  seconds = float(parts[2]) + float(parts[1]) * 60 + float(parts[0]) * 3600
                  
                  if seconds > 1.0:
                      slow_tests.append((test_name, seconds))
          
          slow_tests.sort(key=lambda x: x[1], reverse=True)
          
          print("## Slow Tests (>1s)")
          for test_name, duration in slow_tests[:20]:
              print(f"- {test_name}: {duration:.2f}s")
          EOF
```

# Track test performance over time
name: CI

jobs:

    runs-on: ubuntu-latest

      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4

          dotnet test --verbosity normal
          END=$(date +%s)

          # Store metric
          echo "{\"commit\":\"${{ github.sha }}\",\"duration\":$DURATION}" \

      - name: Upload Metrics
