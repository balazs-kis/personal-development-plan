# Lesson 4: Contract Versioning and Evolution

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand how Pact handles contract versioning
- Manage contract evolution and breaking changes
- Use consumer version selectors effectively
- Implement backward-compatible API changes
- Handle breaking changes safely in distributed teams

---

## Introduction

Contract versioning is critical when services evolve independently. This lesson covers how to manage contract changes over time, prevent breaking consumers, and safely introduce new features or breaking changes.

## Key Concepts Summary

### What Gets Versioned in Pact?

```
Application Versions
├── Consumer v1.0.0 ──────┐
├── Consumer v1.0.1 ──────┤
└── Consumer v1.1.0 ──────┤
                          │
                          ▼
                   Pact Contracts (content-based versioning)
                   ├── Contract ABC123 (v1.0.0, v1.0.1 both reference)
                   └── Contract DEF456 (v1.1.0 references - new contract)
                          │
                          ▼
                   Provider Versions
                   ├── Provider v2.0.0
                   ├── Provider v2.0.1
                   └── Provider v2.1.0
```

**Three Versioned Resources:**
1. **Consumer Application Version** - Git commit SHA or semantic version
2. **Pact Contract** - Content hash (automatic, internal)
3. **Provider Application Version** - Git commit SHA or semantic version

### Application Version Best Practices

**Good Version Numbers:**
```bash
# ✓ Git SHA (best)
cefbfb4d4e1a53b8044cf399fee21033e603e5fc

# ✓ Semantic version with commit (good)
1.2.456+405b31ec6

# ✓ Build number with commit (good)
2024.02.15.3+abc123def

# ✗ Pure semantic version (risky)
1.2.3

# ✗ Random or sequential (bad)
build-123
version-456
```

**Why Git SHA?**
- Unique per commit
- Maps to specific code state
- Exists on only one branch
- Known at release time
- No race conditions

**Setting Version in CI/CD:**
```yaml
# .github/workflows/contract-tests.yml
- name: Publish Pacts
  run: |
    dotnet test --filter Category=ContractTest
    
    pact-broker publish ./pacts \
      --consumer-app-version ${{ github.sha }} \
      --branch ${{ github.ref_name }} \
      --broker-base-url ${{ secrets.PACT_BROKER_URL }} \
      --broker-token ${{ secrets.PACT_BROKER_TOKEN }}

- name: Verify Provider
  run: |
    dotnet test --filter Category=ProviderTest
    
    # Results published with provider version
    # (done in test code with ProviderVersion(${{ github.sha }}))
```

### Backward Compatible Changes

**Safe Changes (Non-Breaking):**
```csharp
// Original contract
{
    "id": 10,
    "name": "Widget"
}

// ✓ Adding optional field (non-breaking)
{
    "id": 10,
    "name": "Widget",
    "description": "A useful widget"  // New field
}

// ✓ Adding new endpoint (non-breaking)
// GET /api/products/{id}/reviews  // New endpoint

// ✓ Making response field nullable (usually safe)
{
    "id": 10,
    "name": "Widget",
    "description": null  // Now nullable
}

// ✓ Relaxing validation (non-breaking)
// Was: name must be 3-20 chars
// Now: name must be 1-100 chars
```

**Consumer Test for Optional Fields:**
```csharp
[Fact]
public async Task GetProduct_WithOptionalFields_ParsesCorrectly()
{
    _pactBuilder
        .UponReceiving("a product with optional description")
        .WithRequest(HttpMethod.Get, "/api/products/10")
        .WillRespond()
        .WithStatus(HttpStatusCode.OK)
        .WithJsonBody(new
        {
            id = Integer(10),
            name = Type("Widget"),
            // description is optional - consumer doesn't require it
        });

    await _pactBuilder.VerifyAsync(async ctx =>
    {
        var client = new ProductApiClient(_mockServerUri);
        var product = await client.GetProductAsync(10);
        
        Assert.Equal(10, product.Id);
        Assert.NotNull(product.Name);
        // description may or may not be present
    });
}
```

### Breaking Changes

**Breaking Changes (Require Coordination):**
```csharp
// Original
{
    "id": 10,
    "name": "Widget"
}

// ✗ Removing field (breaking)
{
    "id": 10
    // "name" removed - breaks consumers expecting it!
}

// ✗ Renaming field (breaking)
{
    "id": 10,
    "productName": "Widget"  // Was "name"
}

// ✗ Changing type (breaking)
{
    "id": "10",  // Was number, now string!
    "name": "Widget"
}

// ✗ Changing endpoint (breaking)
// Was: GET /api/products/{id}
// Now: GET /api/v2/products/{id}  // Different path

// ✗ Adding required request field (breaking)
// POST /api/products
{
    "name": "Widget",
    "category": "Tools",  // Now required, was optional
    "description": "..."   // New required field - breaks old consumers!
}
```

### Handling Breaking Changes Safely

**Approach 1: Expand-Contract Pattern**

```
Phase 1: EXPAND - Add new field/endpoint while keeping old
┌──────────────────────────────────────┐
│ Provider                             │
│ - GET /api/products/{id}             │
│   Returns: { id, name, description } │ ← Old + New
│ - Supports both "name" and           │
│   "productName" in response          │
└──────────────────────────────────────┘
         ↓
Phase 2: MIGRATE - Consumers update to use new field
┌──────────────────────────────────────┐
│ Consumer A: Updated to "productName" │
│ Consumer B: Updated to "productName" │
│ Consumer C: Still uses "name"        │ ← Straggler
└──────────────────────────────────────┘
         ↓
Phase 3: CONTRACT - Remove old field once all consumers migrated
┌──────────────────────────────────────┐
│ Provider                             │
│ - GET /api/products/{id}             │
│   Returns: { id, productName, desc } │ ← Only new
└──────────────────────────────────────┘
```

**Implementation:**
```csharp
// Phase 1: Return both old and new fields
public class ProductDto
{
    public int Id { get; set; }
    
    [JsonPropertyName("productName")]
    public string ProductName { get; set; }
    
    [JsonPropertyName("name")]
    public string Name => ProductName;  // Deprecated, maps to new field
    
    public string Description { get; set; }
}

// Phase 3: Remove old field after all consumers updated
public class ProductDto
{
    public int Id { get; set; }
    
    [JsonPropertyName("productName")]
    public string ProductName { get; set; }
    
    public string Description { get; set; }
}
```

**Approach 2: API Versioning**

```csharp
// v1 API - Keep for old consumers
[ApiController]
[Route("api/v1/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet("{id}")]
    public ActionResult<ProductV1Dto> GetProduct(int id)
    {
        return new ProductV1Dto
        {
            Id = product.Id,
            Name = product.Name  // Old format
        };
    }
}

// v2 API - New format
[ApiController]
[Route("api/v2/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet("{id}")]
    public ActionResult<ProductV2Dto> GetProduct(int id)
    {
        return new ProductV2Dto
        {
            Id = product.Id,
            ProductName = product.Name,  // New format
            Description = product.Description
        };
    }
}
```

### Consumer Version Selectors

**Selecting Which Pacts to Verify:**
```csharp
new PactVerifier(config)
    .WithPactBrokerSource(new Uri("https://pact-broker.com"), options =>
    {
        options.ConsumerVersionSelectors(
            // Verify pacts from main branch
            new ConsumerVersionSelector { Branch = "main" },
            
            // Verify pacts from currently deployed versions
            new ConsumerVersionSelector { DeployedOrReleased = true },
            
            // Verify pacts from this specific consumer version
            new ConsumerVersionSelector 
            { 
                Consumer = "ProductConsumer",
                Tag = "prod"  // Using tags (older approach)
            }
        );
    })
    .Verify();
```

**Common Selector Patterns:**
```csharp
// Development: Verify main branch
new ConsumerVersionSelector { Branch = "main" }

// Staging: Verify deployed to staging
new ConsumerVersionSelector 
{ 
    Environment = "staging",
    DeployedOrReleased = true 
}

// Production: Verify all production versions
new ConsumerVersionSelector 
{ 
    Environment = "production",
    DeployedOrReleased = true 
}

// Feature Branch: Verify specific feature
new ConsumerVersionSelector 
{ 
    Branch = "feature/new-api",
    FallbackBranch = "main"  // Fallback if no pacts on feature branch
}
```

### Can-I-Deploy Tool

**Checking Deployment Safety:**
```bash
# Before deploying consumer
pact-broker can-i-deploy \
  --pacticipant ProductConsumer \
  --version $GIT_COMMIT \
  --to-environment production \
  --retry-while-unknown 10 \
  --retry-interval 10

# Before deploying provider
pact-broker can-i-deploy \
  --pacticipant ProductAPI \
  --version $GIT_COMMIT \
  --to-environment production
```

**In CI/CD Pipeline:**
```yaml
# .github/workflows/deploy.yml
deploy:
  runs-on: ubuntu-latest
  steps:
    - name: Check if safe to deploy
      run: |
        docker run --rm \
          pactfoundation/pact-cli:latest \
          broker can-i-deploy \
          --pacticipant ProductAPI \
          --version ${{ github.sha }} \
          --to-environment production \
          --broker-base-url ${{ secrets.PACT_BROKER_URL }} \
          --broker-token ${{ secrets.PACT_BROKER_TOKEN }}
    
    - name: Deploy
      if: success()
      run: |
        # Deploy application
        kubectl apply -f deployment.yaml
    
    - name: Record deployment
      run: |
        docker run --rm \
          pactfoundation/pact-cli:latest \
          broker record-deployment \
          --pacticipant ProductAPI \
          --version ${{ github.sha }} \
          --environment production \
          --broker-base-url ${{ secrets.PACT_BROKER_URL }} \
          --broker-token ${{ secrets.PACT_BROKER_TOKEN }}
```

### Coordinating Breaking Changes

**Communication Flow:**
```
1. Provider Team identifies need for breaking change
   │
   ▼
2. Check can-i-deploy to see which consumer versions will break
   │
   ▼
3. Coordinate with consumer teams
   - Share migration guide
   - Provide migration timeline
   │
   ▼
4. Consumers update contracts and deploy
   │
   ▼
5. Provider verifies updated contracts pass
   │
   ▼
6. Provider deploys breaking change
   │
   ▼
7. Remove deprecated code after migration period
```

**Example Migration:**
```csharp
// Consumer updates contract to new format
[Fact]
public async Task GetProduct_WithNewFormat_ParsesCorrectly()
{
    _pactBuilder
        .UponReceiving("a product with new format")
        .WithRequest(HttpMethod.Get, "/api/products/10")
        .WillRespond()
        .WithStatus(HttpStatusCode.OK)
        .WithJsonBody(new
        {
            id = Integer(10),
            productName = Type("Widget"),  // New field name
            description = Type("Description")
        });

    await _pactBuilder.VerifyAsync(async ctx =>
    {
        var client = new ProductApiClient(_mockServerUri);
        var product = await client.GetProductAsync(10);
        
        Assert.Equal(10, product.Id);
        Assert.NotNull(product.ProductName);  // Updated client code
    });
}
```

### Contract Evolution Best Practices

**1. Prefer Additive Changes:**
```csharp
// ✓ Good - Add new optional fields
// ✓ Good - Add new endpoints
// ✗ Avoid - Removing or renaming existing fields
```

**2. Use Semantic Versioning for APIs:**
```
v1.0.0 → v1.1.0  // Added feature (backward compatible)
v1.1.0 → v1.1.1  // Bug fix (backward compatible)
v1.1.1 → v2.0.0  // Breaking change
```

**3. Communicate Changes:**
```markdown
# API Changelog

## v2.0.0 (Breaking)
- **BREAKING:** Renamed `name` to `productName` in Product response
- **BREAKING:** `category` is now required in POST /api/products
- Migration guide: https://docs.example.com/migration/v2

## v1.2.0
- Added optional `description` field to Product response
- Added GET /api/products/{id}/reviews endpoint
```

**4. Monitor Contract Verification:**
```
Set up alerts for:
- Failed contract verifications
- Pacts with no verification for > 24 hours
- Breaking changes detected in contracts
```

## Practice Exercise

After completing the materials (30 minutes max):

1. **Version Setup:** Configure your consumer and provider to use Git commit SHAs as version numbers.

2. **Backward Compatible Change:**
   - Add a new optional field to your API response
   - Update provider to return the new field
   - Verify old consumer contracts still pass
   - Update consumer to use new field

3. **Breaking Change Simulation:**
   - Rename a field in your API
   - See consumer contract verification fail
   - Implement expand-contract pattern
   - Update consumer contract
   - Remove old field after migration

4. **Can-I-Deploy:** Set up can-i-deploy checks in your CI/CD pipeline.
