# Lesson 2: Test Naming Conventions

## Learning Objectives

By the end of this lesson, you will be able to:
- Apply effective test naming conventions
- Choose between different naming styles (UnitOfWork_Scenario_ExpectedResult, plain English, etc.)
- Write test names that clearly communicate intent
- Organize tests to improve discoverability
- Use xUnit DisplayName for human-readable test descriptions

---

## Introduction

A good test name is like a good variable name - it should clearly communicate intent without requiring you to read the implementation. Test names serve as documentation, appear in test reports, and help developers understand what broke when tests fail. Investing in clear naming pays dividends throughout your codebase's lifetime.

## Key Concepts Summary

### Why Test Names Matter

Test names serve multiple purposes:
- **Documentation** - Describe what the system does
- **Test Reports** - Appear in CI/CD output and failed test lists
- **Developer Communication** - Help team members understand intent
- **Debugging** - Guide you to the problem when tests fail

**Bad names:**
```csharp
Test1()
TestMethod()
CheckStuff()
ValidateCorrectBehavior()
```

**Good names:**
```csharp
Add_TwoPositiveNumbers_ReturnsSum()
CreateUser_WithInvalidEmail_ThrowsArgumentException()
CalculateDiscount_PremiumUser_Returns25Percent()
```

### Naming Convention Patterns

#### Pattern 1: UnitOfWork_Scenario_ExpectedResult

**Format:** `MethodName_StateUnderTest_ExpectedBehavior`

This is the most popular convention in the .NET community.

**Examples:**
```csharp
[Fact]
public void Add_TwoPositiveNumbers_ReturnsSum() { }

[Fact]
public void Add_NegativeAndPositive_ReturnsCorrectResult() { }

[Fact]
public void Remove_NonExistentItem_ThrowsNotFoundException() { }

[Fact]
public void GetUser_UserDoesNotExist_ReturnsNull() { }

[Fact]
public void ProcessPayment_InsufficientFunds_ReturnsFalse() { }
```

**Advantages:**
- Clear structure
- Easy to scan and understand
- Consistent across team
- Works well with test explorers

**When to use:** Default choice for most .NET projects

#### Pattern 2: Plain English with Underscores

**Format:** Readable sentences with underscores instead of spaces

**Examples:**
```csharp
[Fact]
public void Returns_empty_list_when_no_items_exist() { }

[Fact]
public void Throws_exception_when_email_is_invalid() { }

[Fact]
public void Sends_confirmation_email_after_successful_registration() { }

[Fact]
public void Applies_25_percent_discount_for_premium_members() { }
```

**Advantages:**
- Very readable
- Focuses on behavior, not implementation
- Natural language flow

**Disadvantages:**
- Less emphasis on what's being tested
- Can be harder to find tests for specific methods

**When to use:** When behavior matters more than implementation details

#### Pattern 3: Given/When/Then (BDD Style)

**Format:** Organize by context (Given), group tests in scenario-specific classes

**Class Example:**
```csharp
public class CalculateDiscount_GivenPremiumUser
{
    [Fact]
    public void Returns25PercentDiscount() { }
    
    [Fact]
    public void DoesNotApplyDiscountToExcludedProducts() { }
}

public class CalculateDiscount_GivenStandardUser
{
    [Fact]
    public void Returns10PercentDiscount() { }
    
    [Fact]
    public void DoesNotApplyDiscountUnderMinimumPurchase() { }
}
```

**Advantages:**
- Groups related scenarios together
- Avoids repetition in test names
- Aligns with BDD thinking
- Excellent test organization

**Disadvantages:**
- More test classes to manage
- Can be harder to find tests for specific methods
- May feel like overkill for simple scenarios

**When to use:** Complex scenarios with multiple contexts, BDD-focused teams

#### Pattern 4: xUnit DisplayName Attribute

**Format:** Use natural language strings with DisplayName attribute

**Examples:**
```csharp
[Fact(DisplayName = "Adding two positive numbers returns their sum")]
public void AddTwoPositiveNumbers() { }

[Fact(DisplayName = "Given a premium user with 5+ years membership, when calculating discount, then returns 25%")]
public void PremiumUserLongMembershipDiscount() { }

[Fact(DisplayName = "User registration fails when email format is invalid")]
public void InvalidEmailRegistration() { }

[Fact(DisplayName = "Shopping cart removes item and updates total correctly")]
public void RemoveItemUpdatesCart() { }
```

**Advantages:**
- Complete sentences with spaces and punctuation
- Very readable in test reports
- Method names can be shorter
- No underscore restrictions

**Disadvantages:**
- Duplication between method name and display name
- Test name not visible in code at a glance
- Requires extra attribute

**When to use:** When test report readability is paramount, integration with BDD tools

### Best Practices

**1. Be Descriptive**

```csharp
// ❌ BAD - Too vague
[Fact]
public void TestAdd() { }

// ❌ BAD - Still vague
[Fact]
public void TestAddMethod() { }

// ✅ GOOD - Clear and specific
[Fact]
public void Add_TwoPositiveIntegers_ReturnsTheirSum() { }
```

**2. Avoid Technical Jargon in Behavior**

```csharp
// ❌ BAD - Too technical
[Fact]
public void Validate_NullReferenceException_ThrownOnNullInput() { }

// ✅ GOOD - Focus on behavior
[Fact]
public void Validate_NullInput_ThrowsArgumentNullException() { }
```

**3. Test One Thing Per Test**

```csharp
// ❌ BAD - Testing multiple things
[Fact]
public void AddAndRemoveAndCalculateTotal_VariousScenarios_WorksCorrectly() { }

// ✅ GOOD - Separate tests
[Fact]
public void Add_SingleItem_IncreasesCountByOne() { }

[Fact]
public void Remove_ExistingItem_DecreasesCountByOne() { }

[Fact]
public void CalculateTotal_MultipleItems_ReturnsSumOfPrices() { }
```

**4. State the Expected Outcome**

```csharp
// ❌ BAD - No expected outcome
[Fact]
public void ProcessPayment_InsufficientFunds() { }

// ✅ GOOD - Clear expected outcome
[Fact]
public void ProcessPayment_InsufficientFunds_ReturnsFalseAndLogsError() { }
```

**5. Use Consistent Vocabulary**

Pick terms and stick to them across your test suite:
- Returns vs. Produces
- Throws vs. Raises (for exceptions)
- Creates vs. Generates
- Validates vs. Checks

**6. Length is OK**

```csharp
// Don't be afraid of long names if they're clear
[Fact]
public void CalculateShippingCost_InternationalDestination_WithExpressShipping_AppliesCorrectRatesAndSurcharges() { }
```

Long test names are far better than unclear ones.

### Real-World Examples

```csharp
public class OrderServiceTests
{
    // Testing method behavior
    [Fact]
    public void CreateOrder_ValidOrderData_SavesOrderToDatabase() { }
    
    [Fact]
    public void CreateOrder_InvalidCustomerId_ThrowsArgumentException() { }
    
    [Fact]
    public void CreateOrder_EmptyItemsList_ThrowsInvalidOperationException() { }
    
    // Testing state
    [Fact]
    public void CalculateTotal_OrderWithMultipleItems_ReturnsSumIncludingTax() { }
    
    [Fact]
    public void CalculateTotal_EmptyOrder_ReturnsZero() { }
    
    // Testing interactions
    [Fact]
    public void ProcessPayment_SuccessfulTransaction_SendsConfirmationEmail() { }
    
    [Fact]
    public void ProcessPayment_FailedTransaction_DoesNotUpdateInventory() { }
    
    // Testing business rules
    [Fact]
    public void ApplyDiscount_OrderOver100Dollars_Applies10PercentDiscount() { }
    
    [Fact]
    public void ApplyDiscount_OrderUnder100Dollars_DoesNotApplyDiscount() { }
}
```

### Organizing Test Classes

**Option 1: One test class per production class**
```csharp
public class Calculator { }
public class CalculatorTests { }

public class OrderService { }
public class OrderServiceTests { }
```

**Option 2: Multiple test classes per production class (grouped by feature)**
```csharp
public class OrderService { }

public class OrderServiceCreationTests { }
public class OrderServicePaymentTests { }
public class OrderServiceNotificationTests { }
```

**Option 3: Nested classes (BDD style)**
```csharp
public class CalculateDiscountTests
{
    public class GivenPremiumUser
    {
        [Fact]
        public void Returns25PercentDiscount() { }
    }
    
    public class GivenStandardUser
    {
        [Fact]
        public void Returns10PercentDiscount() { }
    }
}
```

### Team Agreement is Key

**The most important thing:** Your entire team must agree on and follow the convention.

Inconsistent naming is worse than a "suboptimal" convention consistently applied.
