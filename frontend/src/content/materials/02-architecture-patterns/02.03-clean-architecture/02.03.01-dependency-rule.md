## Learning Objectives

## Introduction

Clean Architecture (also known as Onion or Hexagonal Architecture) organizes code into layers where dependencies point inward toward business logic. This creates systems where core business rules are independent of databases, frameworks, and external concerns.

## Key Concepts Summary

### The Dependency Rule

**Rule:** Source code dependencies must point inward, toward higher-level policies.

```
┌────────────────────────────────────────────┐
│   Frameworks & Drivers (Web, DB, UI)      │  ← External
├────────────────────────────────────────────┤
│   Interface Adapters (Controllers, Gateways)│
├────────────────────────────────────────────┤
│   Application Business Rules (Use Cases)   │
├────────────────────────────────────────────┤
│   Enterprise Business Rules (Entities)     │  ← Core
└────────────────────────────────────────────┘

Dependencies flow inward →
```

**Why this matters:**
- Inner layers have no knowledge of outer layers
- Changes to external concerns (UI, DB) don't affect business logic
- Business rules can be tested independently
- Technology decisions can be deferred or changed
- The system becomes flexible and maintainable

**Dependency Inversion Principle:**
```
❌ Wrong: High-level depends on low-level
OrderService → SqlOrderRepository

✅ Correct: Both depend on abstraction
OrderService → IOrderRepository ← SqlOrderRepository
```

### Layer Structure in .NET
```
Solution/
├── Core/
│   ├── Domain/                    // Entities (innermost)
│   │   ├── Entities/
│   │   ├── ValueObjects/
│   │   ├── Enums/
│   │   └── Exceptions/
│   └── Application/               // Use Cases
│       ├── Interfaces/
│       ├── UseCases/
│       ├── DTOs/
│       └── Behaviors/
├── Infrastructure/                // External concerns
│   ├── Persistence/
│   │   ├── Repositories/
│   │   └── DbContext/
│   ├── Identity/
│   └── Services/
└── Presentation/                  // UI/API
    ├── WebApi/
    │   ├── Controllers/
    │   └── Middleware/
    └── Startup.cs
```

### Domain Layer (Core)
```csharp
// Domain/Entities/Order.cs
// No dependencies on infrastructure or frameworks!
namespace CleanArchitecture.Domain.Entities
{
    public class Order
    {
        public OrderId Id { get; private set; }
        public CustomerId CustomerId { get; private set; }
        private readonly List<OrderLine> _lines = new();
        public IReadOnlyCollection<OrderLine> Lines => _lines.AsReadOnly();
        
        public void AddLine(Product product, int quantity)
        {
            var line = new OrderLine(product.Id, quantity, product.Price);
            _lines.Add(line);
        }
    }
}
```

### Application Layer (Use Cases)
```csharp
// Application/UseCases/Orders/CreateOrder/CreateOrderCommand.cs
public record CreateOrderCommand(
    Guid CustomerId,
    List<OrderLineDto> Lines) : IRequest<OrderDto>;

// Application/UseCases/Orders/CreateOrder/CreateOrderHandler.cs
public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, OrderDto>
{
    // Depend on abstractions, not concrete implementations
    private readonly IOrderRepository _orderRepository;
    private readonly IProductRepository _productRepository;
    
    public CreateOrderHandler(
        IOrderRepository orderRepository,
        IProductRepository productRepository)
    {
        _orderRepository = orderRepository;
        _productRepository = productRepository;
    }
    
    public async Task<OrderDto> Handle(CreateOrderCommand request, CancellationToken cancellationToken)
    {
        var order = Order.Create(new CustomerId(request.CustomerId));
        
        foreach (var lineDto in request.Lines)
        {
            var product = await _productRepository.GetById(new ProductId(lineDto.ProductId));
            order.AddLine(product, lineDto.Quantity);
        }
        
        await _orderRepository.Add(order);
        await _orderRepository.SaveChanges();
        
        return OrderDto.FromEntity(order);
    }
}

// Application/Interfaces/IOrderRepository.cs
// Interface defined in Application, implemented in Infrastructure
public interface IOrderRepository
{
    Task<Order> GetById(OrderId id);
    Task Add(Order order);
    Task SaveChanges();
}
```

### Infrastructure Layer
```csharp
// Infrastructure/Persistence/Repositories/OrderRepository.cs
// Implements interface from Application layer
public class OrderRepository : IOrderRepository
{
    private readonly ApplicationDbContext _context;
    
    public OrderRepository(ApplicationDbContext context)
    {
        _context = context;
    }
    
    public async Task<Order> GetById(OrderId id)
    {
        return await _context.Orders
            .Include(o => o.Lines)
            .FirstOrDefaultAsync(o => o.Id == id);
    }
    
    public async Task Add(Order order)
    {
        await _context.Orders.AddAsync(order);
    }
    
    public async Task SaveChanges()
    {
        await _context.SaveChangesAsync();
    }
}
```

## The Four Layers Explained

### 1. Entities (Enterprise Business Rules)

**Responsibility:** Core business objects and rules that would exist regardless of the application.

**Characteristics:**
- No dependencies on anything
- Pure business logic and validation
- Shared across multiple applications
- Highest level of abstraction
- Changes least frequently

**Example:**
```csharp
namespace CleanArchitecture.Domain.Entities
{
    public class Customer
    {
        public CustomerId Id { get; private set; }
        public string Name { get; private set; }
        public Email Email { get; private set; }
        public CustomerStatus Status { get; private set; }
        private readonly List<Order> _orders = new();
        public IReadOnlyCollection<Order> Orders => _orders.AsReadOnly();
        
        private Customer() { } // For EF
        
        public static Customer Create(string name, Email email)
        {
            if (string.IsNullOrWhiteSpace(name))
                throw new DomainException("Customer name is required");
                
            return new Customer
            {
                Id = CustomerId.New(),
                Name = name,
                Email = email,
                Status = CustomerStatus.Active
            };
        }
        
        public void PlaceOrder(Order order)
        {
            if (Status != CustomerStatus.Active)
                throw new DomainException("Cannot place order for inactive customer");
                
            _orders.Add(order);
        }
        
        public void Deactivate()
        {
            if (_orders.Any(o => o.Status == OrderStatus.Pending))
                throw new DomainException("Cannot deactivate customer with pending orders");
                
            Status = CustomerStatus.Inactive;
        }
    }
}
```

### 2. Use Cases (Application Business Rules)

**Responsibility:** Application-specific business rules and orchestration.

**Characteristics:**
- Contains application logic
- Orchestrates entities
- Defines interfaces for infrastructure
- No dependencies on frameworks or infrastructure implementations
- Changes when requirements change

**Example:**
```csharp
// Application/Features/Customers/Commands/DeactivateCustomer/DeactivateCustomerCommand.cs
public record DeactivateCustomerCommand(Guid CustomerId) : IRequest<Result>;

public class DeactivateCustomerHandler : IRequestHandler<DeactivateCustomerCommand, Result>
{
    private readonly ICustomerRepository _customerRepository;
    private readonly IUnitOfWork _unitOfWork;
    private readonly IEmailService _emailService;
    
    public DeactivateCustomerHandler(
        ICustomerRepository customerRepository,
        IUnitOfWork unitOfWork,
        IEmailService emailService)
    {
        _customerRepository = customerRepository;
        _unitOfWork = unitOfWork;
        _emailService = emailService;
    }
    
    public async Task<Result> Handle(
        DeactivateCustomerCommand request,
        CancellationToken cancellationToken)
    {
        var customer = await _customerRepository.GetById(
            new CustomerId(request.CustomerId));
            
        if (customer == null)
            return Result.Failure("Customer not found");
        
        try
        {
            customer.Deactivate();
            await _unitOfWork.SaveChangesAsync(cancellationToken);
            
            await _emailService.SendDeactivationNotification(customer.Email);
            
            return Result.Success();
        }
        catch (DomainException ex)
        {
            return Result.Failure(ex.Message);
        }
    }
}
```

### 3. Interface Adapters

**Responsibility:** Convert data between use cases and external systems.

**Characteristics:**
- Controllers, presenters, gateways
- Implements interfaces defined in use cases
- Converts between domain models and DTOs
- No business logic

**Example:**
```csharp
// WebApi/Controllers/CustomersController.cs
[ApiController]
[Route("api/[controller]")]
public class CustomersController : ControllerBase
{
    private readonly IMediator _mediator;
    
    public CustomersController(IMediator mediator) => _mediator = mediator;
    
    [HttpPost("{id}/deactivate")]
    [ProducesResponseType(StatusCodes.Status200OK)]
    [ProducesResponseType(typeof(ProblemDetails), StatusCodes.Status400BadRequest)]
    [ProducesResponseType(StatusCodes.Status404NotFound)]
    public async Task<ActionResult> DeactivateCustomer(Guid id)
    {
        var command = new DeactivateCustomerCommand(id);
        var result = await _mediator.Send(command);
        
        return result.IsSuccess 
            ? Ok() 
            : BadRequest(new ProblemDetails { Detail = result.Error });
    }
}
```

### 4. Frameworks & Drivers

**Responsibility:** External tools and frameworks.

**Characteristics:**
- Databases, web frameworks, UI, external APIs
- Implementation details
- Most likely to change
- Concrete implementations

**Example:**
```csharp
// Infrastructure/Persistence/Repositories/CustomerRepository.cs
public class CustomerRepository : ICustomerRepository
{
    private readonly ApplicationDbContext _context;
    
    public CustomerRepository(ApplicationDbContext context) => _context = context;
    
    public async Task<Customer?> GetById(CustomerId id)
    {
        return await _context.Customers
            .Include(c => c.Orders)
            .FirstOrDefaultAsync(c => c.Id == id);
    }
    
    public async Task Add(Customer customer)
    {
        await _context.Customers.AddAsync(customer);
    }
}
```

## Crossing Boundaries

**The Data Transfer Object (DTO) Pattern:**

When crossing boundaries, use simple data structures (DTOs) to avoid coupling:

```csharp
// Application/Features/Customers/Queries/GetCustomer/CustomerDto.cs
public record CustomerDto
{
    public Guid Id { get; init; }
    public string Name { get; init; } = string.Empty;
    public string Email { get; init; } = string.Empty;
    public string Status { get; init; } = string.Empty;
    public int OrderCount { get; init; }
    
    public static CustomerDto FromEntity(Customer customer) => new()
    {
        Id = customer.Id.Value,
        Name = customer.Name,
        Email = customer.Email.Value,
        Status = customer.Status.ToString(),
        OrderCount = customer.Orders.Count
    };
}
```

**Boundary Crossing Rules:**
1. Data crosses boundaries as simple structures (DTOs)
2. Inner layers define interfaces, outer layers implement them
3. Use dependency injection to wire implementations at runtime
4. Keep DTOs in the Application layer (or create separate Contracts project)

## Common Violations and How to Avoid Them

### ❌ Violation 1: Entity Framework Annotations in Domain

```csharp
// WRONG: Domain entity depends on EF Core
public class Order
{
    [Key]
    public Guid Id { get; set; }
    
    [Required]
    [MaxLength(100)]
    public string CustomerName { get; set; }
}
```

```csharp
// CORRECT: Use Fluent API in Infrastructure
// Domain/Entities/Order.cs
public class Order
{
    public OrderId Id { get; private set; }
    public string CustomerName { get; private set; }
}

// Infrastructure/Persistence/Configurations/OrderConfiguration.cs
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> builder)
    {
        builder.HasKey(o => o.Id);
        builder.Property(o => o.CustomerName).IsRequired().HasMaxLength(100);
    }
}
```

### ❌ Violation 2: Using DbContext in Use Cases

```csharp
// WRONG: Use case depends on EF Core
public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, Guid>
{
    private readonly ApplicationDbContext _context;
    
    public async Task<Guid> Handle(CreateOrderCommand request, CancellationToken ct)
    {
        var order = new Order();
        _context.Orders.Add(order);
        await _context.SaveChangesAsync(ct);
        return order.Id;
    }
}
```

```csharp
// CORRECT: Depend on repository interface
public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, Guid>
{
    private readonly IOrderRepository _repository;
    private readonly IUnitOfWork _unitOfWork;
    
    public async Task<Guid> Handle(CreateOrderCommand request, CancellationToken ct)
    {
        var order = Order.Create(/*...*/);
        await _repository.Add(order);
        await _unitOfWork.SaveChangesAsync(ct);
        return order.Id.Value;
    }
}
```

### ❌ Violation 3: HTTP Concerns in Application Layer

```csharp
// WRONG: HTTP request in use case
public class GetCustomerHandler : IRequestHandler<GetCustomerQuery, CustomerDto>
{
    private readonly HttpClient _httpClient;
    
    public async Task<CustomerDto> Handle(GetCustomerQuery request, CancellationToken ct)
    {
        var response = await _httpClient.GetAsync($"api/customers/{request.Id}");
        // ...
    }
}
```

```csharp
// CORRECT: Define interface in Application, implement in Infrastructure
// Application/Interfaces/ICustomerApiClient.cs
public interface ICustomerApiClient
{
    Task<CustomerDto> GetCustomerAsync(Guid id, CancellationToken ct);
}

// Infrastructure/ExternalServices/CustomerApiClient.cs
public class CustomerApiClient : ICustomerApiClient
{
    private readonly HttpClient _httpClient;
    
    public async Task<CustomerDto> GetCustomerAsync(Guid id, CancellationToken ct)
    {
        var response = await _httpClient.GetAsync($"api/customers/{id}", ct);
        // ...
    }
}
```

## Benefits of Clean Architecture

| Benefit | Description | Example |
|---------|-------------|---------|
| **Testability** | Business logic tested without databases or UI | Unit test order creation without EF Core |
| **Framework Independence** | Can change frameworks without rewriting business logic | Migrate from ASP.NET to gRPC |
| **Database Independence** | Can swap databases with minimal changes | Switch from SQL Server to PostgreSQL |
| **UI Independence** | Multiple UIs can use the same business logic | Web API, gRPC, CLI share same use cases |
| **External Agency Independence** | Business rules don't know about external services | Replace SendGrid with Mailgun |
| **Delayed Decisions** | Can defer technology choices | Start with in-memory repos, add DB later |

### Exercise: Build a Blog System with Clean Architecture

Create a "Create Blog Post" feature using Clean Architecture principles:

**1. Domain Layer:**
```csharp
// Domain/Entities/BlogPost.cs
public class BlogPost
{
    public BlogPostId Id { get; private set; }
    public string Title { get; private set; }
    public string Content { get; private set; }
    public AuthorId AuthorId { get; private set; }
    public BlogPostStatus Status { get; private set; }
    public DateTime CreatedAt { get; private set; }
    public DateTime? PublishedAt { get; private set; }
    
    private BlogPost() { }
    
    public static BlogPost Create(string title, string content, AuthorId authorId)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new DomainException("Title is required");
        if (string.IsNullOrWhiteSpace(content))
            throw new DomainException("Content is required");
            
        return new BlogPost
        {
            Id = BlogPostId.New(),
            Title = title,
            Content = content,
            AuthorId = authorId,
            Status = BlogPostStatus.Draft,
            CreatedAt = DateTime.UtcNow
        };
    }
    
    public void Publish()
    {
        if (Status == BlogPostStatus.Published)
            throw new DomainException("Blog post already published");
            
        Status = BlogPostStatus.Published;
        PublishedAt = DateTime.UtcNow;
    }
}

// Domain/ValueObjects/BlogPostId.cs
public record BlogPostId(Guid Value)
{
    public static BlogPostId New() => new(Guid.NewGuid());
    public static BlogPostId From(Guid value) => new(value);
}
```

**2. Application Layer:**
```csharp
// Application/Features/BlogPosts/Commands/CreateBlogPost/CreateBlogPostCommand.cs
public record CreateBlogPostCommand(
    string Title,
    string Content,
    Guid AuthorId) : IRequest<BlogPostDto>;

// Application/Features/BlogPosts/Commands/CreateBlogPost/CreateBlogPostValidator.cs
public class CreateBlogPostCommandValidator : AbstractValidator<CreateBlogPostCommand>
{
    public CreateBlogPostCommandValidator()
    {
        RuleFor(x => x.Title).NotEmpty().MaximumLength(200);
        RuleFor(x => x.Content).NotEmpty().MinimumLength(50);
        RuleFor(x => x.AuthorId).NotEmpty();
    }
}

// Application/Features/BlogPosts/Commands/CreateBlogPost/CreateBlogPostHandler.cs
public class CreateBlogPostHandler : IRequestHandler<CreateBlogPostCommand, BlogPostDto>
{
    private readonly IBlogPostRepository _repository;
    private readonly IUnitOfWork _unitOfWork;
    
    public async Task<BlogPostDto> Handle(
        CreateBlogPostCommand request,
        CancellationToken cancellationToken)
    {
        var blogPost = BlogPost.Create(
            request.Title,
            request.Content,
            new AuthorId(request.AuthorId));
        
        await _repository.Add(blogPost);
        await _unitOfWork.SaveChangesAsync(cancellationToken);
        
        return BlogPostDto.FromEntity(blogPost);
    }
}

// Application/Interfaces/IBlogPostRepository.cs
public interface IBlogPostRepository
{
    Task<BlogPost?> GetById(BlogPostId id);
    Task Add(BlogPost blogPost);
    Task<List<BlogPost>> GetByAuthor(AuthorId authorId);
}
```

**3. Infrastructure Layer:**
```csharp
// Infrastructure/Persistence/Repositories/BlogPostRepository.cs
public class BlogPostRepository : IBlogPostRepository
{
    private readonly ApplicationDbContext _context;
    
    public async Task<BlogPost?> GetById(BlogPostId id) =>
        await _context.BlogPosts.FindAsync(id);
    
    public async Task Add(BlogPost blogPost) =>
        await _context.BlogPosts.AddAsync(blogPost);
    
    public async Task<List<BlogPost>> GetByAuthor(AuthorId authorId) =>
        await _context.BlogPosts
            .Where(b => b.AuthorId == authorId)
            .ToListAsync();
}

// Infrastructure/Persistence/Configurations/BlogPostConfiguration.cs
public class BlogPostConfiguration : IEntityTypeConfiguration<BlogPost>
{
    public void Configure(EntityTypeBuilder<BlogPost> builder)
    {
        builder.HasKey(b => b.Id);
        builder.Property(b => b.Id).HasConversion(
            id => id.Value,
            value => BlogPostId.From(value));
        builder.Property(b => b.Title).IsRequired().HasMaxLength(200);
        builder.Property(b => b.Content).IsRequired();
    }
}
```

**4. Presentation Layer:**

## Self-Check Questions

1. **What is the Dependency Rule?**
   - Answer: Source code dependencies must point inward toward higher-level policies. Outer layers can depend on inner layers, but inner layers cannot depend on outer layers.

2. **Why should business logic not depend on infrastructure?**
   - Answer: To keep business rules testable, framework-independent, and flexible. Infrastructure is a detail that should be easily replaceable without affecting core business logic.

3. **Where are interfaces defined vs. where are they implemented?**
   - Answer: Interfaces are defined in inner layers (Application/Domain), implementations are in outer layers (Infrastructure). This is Dependency Inversion.

4. **How does Clean Architecture improve testability?**
   - Answer: Business logic has no dependencies on databases, frameworks, or external services. You can test it in isolation with simple mocks or in-memory implementations.

5. **What are the four main layers?**
   - Answer: Entities (Domain), Use Cases (Application), Interface Adapters, and Frameworks & Drivers (Infrastructure).

6. **When should you use DTOs?**
   - Answer: When crossing architectural boundaries to prevent coupling between layers and to shape data for specific use cases.

7. **What's the difference between Entities and Use Cases?**
   - Answer: Entities contain enterprise-wide business rules that could exist across applications. Use Cases contain application-specific business rules that orchestrate entities.
