# Lesson 2: Bounded Contexts and Context Mapping

## Learning Objectives

By the end of this lesson, you will be able to:
- Identify and define bounded contexts in a domain
- Map relationships between different contexts
- Understand context integration patterns
- Apply bounded contexts to microservices architecture

---

## Introduction

A Bounded Context is an explicit boundary within which a domain model exists. Within this boundary, terms have specific meanings and rules. The same term may mean different things in different contexts, and that's okay—bounded contexts make these differences explicit.

Bounded contexts solve one of the biggest challenges in large systems: trying to create a single, unified model for everything. In reality, different parts of your organization have different concerns, different vocabularies, and different rules. A "Customer" means one thing to Sales, another to Support, and something entirely different to Billing. Trying to force all these perspectives into a single model creates a "frankenstein" object that satisfies no one.

Instead of fighting this natural organizational structure, bounded contexts embrace it. Each context gets its own model, optimized for its specific needs. The art is in defining where the boundaries lie and how contexts communicate with each other.

Strategic DDD is about identifying these boundaries and designing the relationships between contexts. This is often more important than the tactical patterns (entities, value objects, aggregates) because getting the boundaries wrong creates coupling that spreads throughout your system architecture.

```csharp
namespace ECommerce.Catalog
```

### Context Mapping Patterns

**Shared Kernel**
```csharp
// Shared types between contexts (use sparingly!)
namespace ECommerce.SharedKernel
{
    public record ProductId(Guid Value);
    public record CustomerId(Guid Value);
    public record Money(decimal Amount, string Currency);
}
```

**Customer-Supplier**
```csharp
// Catalog (Upstream) → Orders (Downstream)
// Orders depend on Catalog for product information

// In Orders Context, use anti-corruption layer
public class ProductCatalogService
{
    private readonly ICatalogApi _catalogApi;
    
    public async Task<OrderItemInfo> GetProductInfo(ProductId productId)
    {
        // Translate from Catalog model to Orders model
        var catalogProduct = await _catalogApi.GetProduct(productId);
        
        return new OrderItemInfo(
            catalogProduct.Id,
            catalogProduct.Name,
            catalogProduct.CurrentPrice
        );
    }
}
```

**Conformist**
```csharp
// When you must use upstream model as-is (legacy systems)
// Avoid when possible, but sometimes necessary

public class LegacyInventoryAdapter
{
    private readonly LegacyInventoryService _legacy;
    
    // Forced to use their model
    public async Task<LegacyStockInfo> CheckStock(string sku)
    {
        return await _legacy.GetStockLevel(sku);
    }
}
```

**Anti-Corruption Layer (ACL)**
```csharp
// Protect your domain from external models
public interface IPaymentGateway
{
    Task<PaymentResult> ProcessPayment(PaymentRequest request);
}

// ACL translates between your domain and external service
public class StripePaymentGateway : IPaymentGateway
{
    private readonly Stripe.PaymentIntentService _stripeService;
    
    public async Task<PaymentResult> ProcessPayment(PaymentRequest request)
    {
        // Translate our domain model to Stripe's model
        var stripeRequest = new Stripe.PaymentIntentCreateOptions
        {
            Amount = (long)(request.Amount.Value * 100), // Stripe uses cents
            Currency = request.Amount.Currency.ToLower(),
            PaymentMethod = request.PaymentMethodToken,
            Confirm = true
        };
        
        try
        {
            var paymentIntent = await _stripeService.CreateAsync(stripeRequest);
            
            // Translate Stripe's response to our domain model
            return new PaymentResult(
                Success: paymentIntent.Status == "succeeded",
                TransactionId: paymentIntent.Id,
                ErrorMessage: paymentIntent.Status == "failed" 
                    ? paymentIntent.CancellationReason 
                    : null
            );
        }
        catch (StripeException ex)
        {
            return new PaymentResult(
                Success: false,
                TransactionId: null,
                ErrorMessage: ex.Message
            );
        }
    }
}
```

## Bounded Contexts and Microservices

Bounded contexts are a strategic design pattern from DDD. Microservices are an architectural pattern for system implementation. They align naturally, but are not synonymous.

### The Ideal Alignment

**One Bounded Context = One Microservice**

```
┌────────────────────────────────────────┐
│   Bounded Context: Orders              │
│   ┌──────────────────────────────────┐ │
│   │   Orders Microservice            │ │
│   │   - Order API                    │ │
│   │   - Order Database               │ │
│   │   - Order Domain Model           │ │
│   └──────────────────────────────────┘ │
└────────────────────────────────────────┘

Benefits:
✓ Clear boundaries
✓ Independent deployment
✓ Team ownership
✓ Technology choice
✓ Scalability
```

### Anti-Pattern: Microservices Cutting Across Contexts

```
❌ BAD: One microservice spans multiple contexts

┌────────────────────────────────────────────┐
│   "Commerce Service"                       │
│   ├─ Catalog logic                         │
│   ├─ Orders logic                          │
│   ├─ Inventory logic                       │
│   └─ Shipping logic                        │
└────────────────────────────────────────────┘

Problems:
✗ Mixed responsibilities
✗ Coupled concerns
✗ Large, complex service
✗ Difficult to understand and maintain
```

### Context-to-Service Mapping Strategies

**Strategy 1: One Context, One Service (Ideal)**

```
Catalog Context → Catalog Service
Orders Context → Orders Service
Inventory Context → Inventory Service
Shipping Context → Shipping Service
```

Best when:
- Contexts are well-defined
- Each context has moderate complexity
- Teams can own one service each

**Strategy 2: One Context, Multiple Services (Decomposition)**

When a bounded context is very large or has distinct scalability needs:

```
Catalog Context
├─ Product Service (read-heavy, cacheable)
└─ Pricing Service (write-heavy, complex rules)
```

Use when:
- Context is genuinely large
- Different scalability requirements
- Different data access patterns
- Still maintain context boundary (services coordinate internally)

**Strategy 3: Multiple Contexts, One Service (Starting Small)**

For small startups or teams:

```
Monolithic Service
├─ Catalog Module (namespace/folder)
├─ Orders Module
└─ Inventory Module
```

Use when:
- Team is small
- Premature to split
- Plan migration path to microservices
- Maintain logical boundaries in code

**Important:** Even in a monolith, respect context boundaries via namespaces and module isolation.

### Integration Patterns for Microservices

**Pattern 1: Synchronous HTTP/REST**

```csharp
// Orders Service calls Catalog Service
public class OrderService
{
    private readonly HttpClient _catalogClient;
    
    public async Task AddProduct(OrderId orderId, ProductId productId)
    {
        // Synchronous HTTP call to Catalog Service
        var response = await _catalogClient.GetAsync(
            $"https://catalog-service/api/products/{productId}");
        
        if (!response.IsSuccessStatusCode)
            throw new ProductNotFoundException();
        
        var product = await response.Content.ReadFromJsonAsync<ProductDto>();
        
        var order = await _orderRepo.GetById(orderId);
        order.AddLine(product.Id, product.Name, product.Price);
        
        await _orderRepo.SaveChanges();
    }
}
```

**Pros:**
- Simple, familiar
- Immediate response
- Easy to debug

**Cons:**
- Tight runtime coupling
- Cascading failures
- Latency accumulation

**Use for:** Queries, lookups, when immediate consistency needed

**Pattern 2: Asynchronous Messaging**

```csharp
// Orders Service publishes event
public class Order
{
    public void Confirm()
    {
        Status = OrderStatus.Confirmed;
        _events.Add(new OrderConfirmed(Id, CustomerId, TotalAmount));
    }
}

// Event published to message broker (RabbitMQ, Kafka, etc.)
public class OrderRepository
{
    private readonly IMessageBroker _broker;
    
    public async Task SaveChanges()
    {
        await _dbContext.SaveChangesAsync();
        
        // Publish events after successful save
        foreach (var @event in GetDomainEvents())
        {
            await _broker.Publish(@event);
        }
    }
}

// Inventory Service subscribes to event
namespace Inventory
{
    public class OrderConfirmedHandler : IEventHandler<OrderConfirmed>
    {
        public async Task Handle(OrderConfirmed @event)
        {
            // Reserve inventory asynchronously
            foreach (var line in @event.OrderLines)
            {
                await _inventory.ReserveStock(line.ProductId, line.Quantity);
            }
        }
    }
}
```

**Pros:**
- Loose coupling
- No cascading failures
- Better scalability
- Temporal decoupling

**Cons:**
- Eventual consistency
- More complex debugging
- Need message infrastructure

**Use for:** Commands, notifications, when eventual consistency acceptable

**Pattern 3: API Gateway**

```
Client
  │
  ▼
┌──────────────┐
│ API Gateway  │ (Single entry point)
└──────┬───────┘
       │
   ┌───┴──────┬────────────┬──────────┐
   │          │            │          │
┌──▼───┐  ┌──▼────┐  ┌────▼──┐  ┌────▼────┐
│Catalog│ │Orders │  │Users  │  │Payments │
└───────┘ └───────┘  └───────┘  └─────────┘
```

**Responsibilities:**
- Authentication/Authorization
- Request routing
- Response aggregation
- Rate limiting
- Caching

```csharp
// API Gateway aggregates data from multiple services
public class OrderDetailsController
{
    private readonly ICatalogService _catalog;
    private readonly IOrderService _orders;
    private readonly ICustomerService _customers;
    
    [HttpGet("api/order-details/{orderId}")]
    public async Task<OrderDetailsDto> GetOrderDetails(string orderId)
    {
        // Parallel calls to multiple services
        var orderTask = _orders.GetOrder(orderId);
        var customerTask = _customers.GetCustomer(order.CustomerId);
        var productsTask = GetProductDetails(order.Lines);
        
        await Task.WhenAll(orderTask, customerTask, productsTask);
        
        // Aggregate responses
        return new OrderDetailsDto
        {
            Order = orderTask.Result,
            Customer = customerTask.Result,
            Products = productsTask.Result
        };
    }
}
```

### Data Management in Bounded Contexts

**Rule: Each Context Owns Its Data**

```
❌ BAD: Shared Database
┌───────────────────────────────────────┐
│        Shared Database                │
│   ┌──────────────────────────────┐   │
│   │  Orders | Products | Inventory│   │
│   └──────────────────────────────┘   │
└───────────────────────────────────────┘
         ▲         ▲         ▲
         │         │         │
  ┌──────┴──┐  ┌──┴───┐  ┌──┴────────┐
  │Orders   │  │Catalog│  │Inventory  │
  │Service  │  │Service│  │Service    │
  └─────────┘  └───────┘  └───────────┘

Problems:
✗ Coupling through database
✗ Can't evolve schemas independently
✗ Transactions cross service boundaries
✗ Can't scale databases independently


✓ GOOD: Database Per Service
┌─────────────┐  ┌──────────────┐  ┌───────────────┐
│Orders Service│  │Catalog Service│  │Inventory Service│
├─────────────┤  ├──────────────┤  ├───────────────┤
│Orders DB    │  │Catalog DB    │  │Inventory DB   │
└─────────────┘  └──────────────┘  └───────────────┘

Benefits:
✓ Independent evolution
✓ Technology choice (SQL, NoSQL, etc.)
✓ Independent scaling
✓ Clear ownership
```

**Challenge: Cross-Context Queries**

When you need data from multiple contexts:

```csharp
// Option 1: API Composition (Gateway pattern)
public class OrderDetailsService
{

    {
        var order = await _orderService.GetOrder(id);
        var customer = await _customerService.GetCustomer(order.CustomerId);
        var products = await _catalogService.GetProducts(order.ProductIds);

// Orders Service maintains read model with product data
public class OrderReadModel
{
    public OrderId Id { get; set; }
    public CustomerId CustomerId { get; set; }
    public string CustomerName { get; set; }  // Replicated from Customer context
    public List<OrderLineReadModel> Lines { get; set; }
}

public class OrderLineReadModel
{
    public ProductId ProductId { get; set; }
    public string ProductName { get; set; }  // Replicated from Catalog context
    public Money Price { get; set; }
}

// Event handler keeps read model in sync
public class ProductUpdatedHandler : IEventHandler<ProductUpdated>
{
    public async Task Handle(ProductUpdated @event)
    {
        // Update replicated product data in Orders read model
        await _readModelRepo.UpdateProductInfo(
            @event.ProductId,
            @event.Name,
            @event.Price);
    }
}
```

## Real-World Example: E-Commerce Platform

Let's see how bounded contexts work in a complete e-commerce system.

### Context Identification

**Catalog Context**
- **Responsibility:** Product information, categories, search
- **Team:** Merchandising team
- **Key concepts:** Product, Category, Specification, Image
- **Ubiquitous language:** "SKU", "Product Line", "Category Tree"
- **Change drivers:** New products, seasonal updates, marketing campaigns

**Orders Context**
- **Responsibility:** Order lifecycle, cart to confirmation
- **Team:** Commerce team
- **Key concepts:** Basket, Order, OrderLine, Checkout
- **Ubiquitous language:** "Basket", "Place Order", "Order Confirmation"
- **Change drivers:** Business rules, promotions, payment methods

**Inventory Context**
- **Responsibility:** Stock levels, allocation, replenishment
- **Team:** Operations team
- **Key concepts:** StockItem, Location, Allocation, Replenishment
- **Ubiquitous language:** "On Hand", "Allocated", "Available to Promise"
- **Change drivers:** Warehouse operations, supplier integration

**Shipping Context**
- **Responsibility:** Fulfillment, shipments, tracking
- **Team:** Logistics team
- **Key concepts:** Shipment, Package, Carrier, Tracking
- **Ubiquitous language:** "Pick", "Pack", "Ship", "Track"
- **Change drivers:** Carrier contracts, warehouse processes

**Payments Context**
- **Responsibility:** Payment processing, refunds
- **Team:** Finance/Security team
- **Key concepts:** PaymentTransaction, Refund, PaymentMethod
- **Ubiquitous language:** "Authorize", "Capture", "Settle", "Refund"
- **Change drivers:** Payment gateways, fraud rules, compliance

```csharp
// Catalog Context (Upstream) provides product data
namespace Catalog
{
    public class Product
    {
        public ProductId Id { get; private set; }
        public string Name { get; private set; }
        public Money Price { get; private set; }

    }
}

namespace Orders
{

    {

        {

                product.Name,
                product.Price,
                product.IsAvailable);
        }
    }
    
    // Orders domain model
    public class Order
    {
        public void AddLine(OrderItemInfo product, Quantity quantity)
        {

                product.Id,

// Inventory Context subscribes to Orders events
namespace Inventory
{
    public class OrderConfirmedHandler : IEventHandler<OrderConfirmed>
    {

        {
            foreach (var line in @event.OrderLines)
            {
                await _inventory.AllocateStock(line.ProductId, line.Quantity);
            }
        }
    }
}

// Shipping Context has Partnership with Orders
namespace Shipping
{
    public class ShipmentService
    {
        // Orders publishes events, Shipping subscribes
        public async Task Handle(OrderConfirmed @event)
        {
            var shipment = Shipment.CreateFromOrder(@event);
            await _shipmentRepo.Add(shipment);
        }

    // Shipping publishes events, Orders subscribes
    public class Shipment
    {

namespace Orders
{

        {
            var order = await _orderRepo.GetByOrderId(@event.OrderId);
            order.MarkAsShipped(@event.Tracking);
            await _orderRepo.SaveChanges();

    }
}

        }
    }
}
```

## Identifying Bounded Contexts

The process of identifying bounded contexts is both art and science. Here are practical heuristics and techniques.

**Heuristic 1: Different Ubiquitous Language**

When different teams use different terms for concepts, or the same terms with different meanings, you've found a potential context boundary.

Symptoms:
- "Product" means catalog listing to Marketing, but SKU to Warehouse
- Sales calls them "deals", Finance calls them "invoices"
- Engineering says "deployment", Operations says "release"

**Heuristic 2: Different Team/Department Ownership**

Organizational boundaries often reflect natural domain boundaries.

```
Sales Team owns:
- Lead, Opportunity, Quote, Deal
- Focus: Closing sales, tracking pipeline

Support Team owns:
- Ticket, Issue, Resolution, SLA
- Focus: Customer satisfaction, response times

Engineering Team owns:
- Feature, Bug, Sprint, Release
- Focus: Delivery, technical quality

→ These are likely different bounded contexts
```

**Heuristic 3: Different Change Cadence**

When different areas of the system change at different rates or for different reasons, they should be separate contexts.

```
Product Catalog:
- Changes constantly (new products daily)
- Marketing team makes changes
- High churn, needs flexibility

Order Processing:
- Stable business rules
- Changes require compliance review
- Low churn, needs reliability

→ Separate contexts allow independent evolution
```

**Heuristic 4: Different Data Consistency Requirements**

When different operations have different consistency needs, consider separate contexts.

```
Shopping Basket:
- Eventual consistency is fine
- Can tolerate brief inconsistencies
- Performance critical

Payment Processing:
- Strong consistency required
- Cannot tolerate inconsistencies
- Correctness critical

→ Different consistency models suggest different contexts
```

**Heuristic 5: Different Scalability Requirements**

```
Product Search:
- Heavy read traffic
- Needs caching, replication
- Can use denormalized data

Order Creation:
- Lower write traffic
- Needs transactional guarantees
- Normalized data

→ Different scaling strategies suggest different contexts
```

### Context Identification Workshop

**Step 1: Collect all domain concepts**
- Run Event Storming or similar workshop
- List all entities, events, commands
- Don't worry about grouping yet

**Step 2: Look for clusters**
- Which concepts are frequently used together?
- Which concepts are always discussed together?
- What natural groupings emerge?

**Step 3: Identify seams**
- Where do different teams work?
- Where does language shift?
- Where are natural integration points?

**Step 4: Validate with business capabilities**
- Does each context map to a business capability?
- Can each context deliver value independently?
- Is each context cohesive?

**Example: Banking Domain**

```
Core Banking Context:
- Account, Transaction, Balance, Interest
- Team: Core banking
- Language: Financial domain terms
- Changes: Regulatory driven, slow

Loans Context:
- Loan, Payment Schedule, Collateral, Risk Assessment
- Team: Loan officers
- Language: Lending terminology
- Changes: Product driven, moderate

Fraud Detection Context:
- Transaction (different view!), Pattern, Alert, Investigation
- Team: Security team
- Language: Risk and security terms
- Changes: Threat driven, fast

Customer Identity Context:
- Customer, Profile, Contact Info, Authentication
- Team: Identity management
- Language: User management terms
- Changes: Compliance driven, moderate

→ Four clear bounded contexts with minimal overlap
```

## Context Mapping Patterns in Depth

Context mapping defines the relationships between bounded contexts. Each pattern has different implications for coupling, autonomy, and governance.

### Pattern 1: Partnership

Two contexts in a partnership collaborate closely and coordinate changes. Both teams are committed to joint success.

```
┌─────────────────┐         ┌─────────────────┐
│   Orders        │◄───────►│   Shipping      │
│   Context       │Partnership│   Context      │
└─────────────────┘         └─────────────────┘

Both teams coordinate releases
Shared sprint planning
Joint code reviews
```

**When to use:**
- Teams are co-located or closely collaborate
- Features require coordinated changes
- Both contexts must evolve together
- Trust and communication are strong

**Implementation:**
```csharp
// Both contexts agree on shared contracts
namespace Shared.Contracts
{
    public record OrderShipped(
        OrderId OrderId,
        TrackingNumber TrackingNumber,
        DateTime ShippedAt);
}

// Orders Context publishes
namespace Orders
{
    public class Order
    {
        public void Ship(TrackingNumber trackingNumber)
        {
            Status = OrderStatus.Shipped;
            _events.Add(new OrderShipped(Id, trackingNumber, DateTime.UtcNow));
        }
    }
}

// Shipping Context consumes
namespace Shipping
{
    public class ShipmentCreatedHandler : IEventHandler<OrderShipped>
    {
        public async Task Handle(OrderShipped @event)
        {
            // Create shipment tracking record
        }
    }
}
```

**Pros:**
- Tight collaboration enables complex features
- Shared understanding reduces misalignment
- Fast feedback loops

**Cons:**
- Strong coupling requires coordinated releases
- Both teams must agree on changes
- Can slow down independent evolution

### Pattern 2: Shared Kernel

A subset of the domain model is shared between contexts. This shared code is maintained jointly and changes require agreement from both teams.

```
┌─────────────────────────────┐
│     Shared Kernel           │
│  • Money                    │
│  • CustomerId               │
│  • ProductId                │
└─────────────────────────────┘
         ▲         ▲
         │         │
┌────────┴───┐ ┌──┴──────────┐
│  Orders    │ │  Billing    │
│  Context   │ │  Context    │
└────────────┘ └─────────────┘
```

**When to use:**
- Two contexts share core domain concepts
- Duplication would be costly
- Teams can coordinate on shared changes

**Implementation:**
```csharp
// Shared Kernel - Both contexts depend on this
namespace Company.SharedKernel
{
    public record Money(decimal Amount, Currency Currency)
    {
        public static Money Zero => new(0, Currency.USD);
        
        public static Money operator +(Money left, Money right)
        {
            if (left.Currency != right.Currency)
                throw new CurrencyMismatchException();
            return new Money(left.Amount + right.Amount, left.Currency);
        }
    }
    
    public record CustomerId(Guid Value)
    {
        public static CustomerId Generate() => new(Guid.NewGuid());
    }
    
    public record ProductId(Guid Value);
    
    public enum Currency { USD, EUR, GBP }
}

// Orders Context uses shared kernel
namespace Orders
{
    using Company.SharedKernel;
    
    public class Order
    {
        public Money TotalAmount { get; private set; }
        public CustomerId CustomerId { get; private set; }
    }
}

// Billing Context uses shared kernel
namespace Billing
{
    using Company.SharedKernel;
    
    public class Invoice
    {
        public Money Amount { get; private set; }
        public CustomerId CustomerId { get; private set; }
    }
}
```

**Pros:**
- Avoids duplication of fundamental concepts
- Ensures consistency of core types
- Clear ownership and governance

**Cons:**
- Creates coupling between contexts
- Changes require coordination
- Can become a bottleneck
- Keep it minimal!

**Warning:** Shared Kernel should be small and change infrequently. If it keeps growing, you may have the wrong boundaries.

### Pattern 3: Customer-Supplier

One context (upstream supplier) provides data/functionality to another (downstream customer). Supplier has some obligation to meet customer needs, but supplier plans and priorities drive the relationship.

```
┌─────────────┐
│  Catalog    │ Upstream Supplier
│  (Upstream) │
└──────┬──────┘
       │ Provides product data
       ▼
┌──────────────┐
│  Orders      │ Downstream Customer
│ (Downstream) │
└──────────────┘
```

**When to use:**
- Clear provider/consumer relationship
- Upstream has natural authority
- Downstream depends on upstream data
- Teams can negotiate interface changes

**Implementation:**
```csharp
// Catalog Context (Upstream) - Defines API
namespace Catalog.Api
{
    public interface ICatalogApi
    {
        Task<ProductDetails> GetProduct(ProductId id);
        Task<IEnumerable<ProductDetails>> SearchProducts(string query);
    }
    
    public record ProductDetails(
        ProductId Id,
        string Name,
        string Description,
        Money CurrentPrice,
        bool IsAvailable);
}

// Orders Context (Downstream) - Consumes API
namespace Orders
{
    using Catalog.Api;
    
    public class OrderService
    {
        private readonly ICatalogApi _catalog;
        
        public async Task<Result> AddProductToOrder(
            OrderId orderId, 
            ProductId productId, 
            int quantity)
        {
            // Get product details from upstream
            var product = await _catalog.GetProduct(productId);
            
            if (!product.IsAvailable)
                return Result.Fail("Product not available");
            
            var order = await _orderRepo.GetById(orderId);
            order.AddLine(product.Id, product.Name, product.CurrentPrice, quantity);
            
            await _orderRepo.SaveChanges();
            return Result.Success();
        }
    }
}
```

**Negotiation process:**
1. Downstream team requests new feature/data
2. Upstream team evaluates and prioritizes
3. Teams negotiate timeline and contract
4. Upstream implements and communicates changes
5. Downstream adapts to changes

**Pros:**
- Clear responsibilities
- Supplier maintains quality and stability
- Customer gets needed functionality

**Cons:**
- Downstream is somewhat dependent
- Must negotiate changes
- Supplier priorities may not align with customer needs

### Pattern 4: Conformist

Downstream context conforms entirely to upstream model, even if it's not ideal. Used when you have no influence over the upstream context.

```
┌─────────────┐
│  Legacy     │ External/Legacy
│  System     │ (No influence)
└──────┬──────┘
       │ Must use as-is
       ▼
┌──────────────┐
│  Our System  │ Conformist
│              │ (Adapts to legacy)
└──────────────┘
```

**When to use:**
- Upstream is external/legacy/third-party
- You have no influence over upstream model
- Cost of translation layer is too high
- Relationship is temporary

**Implementation:**
```csharp
// Legacy system has weird model (we can't change it)
namespace Legacy.Inventory
{
    public class StockInfo
    {
        public string PROD_CD { get; set; }  // Product code
        public int QTY_OH { get; set; }  // Quantity on hand
        public string STAT { get; set; }  // Status: "A", "D", "O"
        public decimal? RSRV_QTY { get; set; }  // Reserved quantity (nullable)
    }
}

// Our context conforms to their model (unfortunately)
namespace Orders
{
    using Legacy.Inventory;
    
    public class InventoryService
    {
        private readonly LegacyInventoryClient _legacy;
        
        public async Task<bool> CheckAvailability(string productCode, int quantity)
        {
            // Must use their weird model
            var stock = await _legacy.GetStockInfo(productCode);
            
            // Decode their cryptic status
            if (stock.STAT != "A")  // "A" means active
                return false;
            
            // Handle nullable reserved quantity
            var available = stock.QTY_OH - (stock.RSRV_QTY ?? 0);
            return available >= quantity;
        }
    }
}
```

**Pros:**
- Simple integration (no translation)
- Lower initial development cost
- Fewer moving parts

**Cons:**
- Upstream model pollutes your context
- Ugly or illogical model in your code
- Difficult to test
- Tight coupling to external model

**Mitigation:** Isolate conformist adapter in a specific layer/namespace so it doesn't spread.

### Pattern 5: Anti-Corruption Layer (ACL)

Create a translation layer that protects your domain model from the external model. Essential when integrating with poorly designed or legacy systems.

```
┌─────────────┐
│  External   │
│  System     │
└──────┬──────┘
       │
┌──────▼──────────────┐
│ Anti-Corruption     │ Translation Layer
│ Layer               │
└──────┬──────────────┘
       │
┌──────▼──────┐
│  Our Domain │ Protected
│  Model      │
└─────────────┘
```

**When to use:**
- External model is poorly designed
- External model uses different concepts
- Want to isolate your domain from external changes
- Integration is long-term

**Implementation:**
```csharp
// External payment gateway with ugly model
namespace Stripe.Api
{
    public class PaymentIntentCreateOptions
    {
        public long Amount { get; set; }  // In cents!
        public string Currency { get; set; }  // Lowercase string
        public string PaymentMethod { get; set; }
        public bool Confirm { get; set; }
    }
    
    public class PaymentIntent
    {
        public string Id { get; set; }
        public string Status { get; set; }  // "succeeded", "failed", etc.
        public string CancellationReason { get; set; }
    }
}

// Our domain model (clean)
namespace Orders.Domain
{
    public record PaymentRequest(
        Money Amount,
        PaymentMethodToken Token);
    
    public record PaymentResult(
        bool Success,
        string TransactionId,
        string ErrorMessage);
}

// Anti-Corruption Layer - Translates between models
namespace Orders.Infrastructure
{
    using Orders.Domain;
    using Stripe.Api;
    
    public interface IPaymentGateway
    {
        Task<PaymentResult> ProcessPayment(PaymentRequest request);
    }
    
    public class StripePaymentGateway : IPaymentGateway
    {
        private readonly Stripe.PaymentIntentService _stripe;
        
        public async Task<PaymentResult> ProcessPayment(PaymentRequest request)
        {
            // Translate our clean model to Stripe's model
            var stripeRequest = new PaymentIntentCreateOptions
            {
                Amount = (long)(request.Amount.Value * 100),  // Convert to cents
                Currency = request.Amount.Currency.ToString().ToLower(),
                PaymentMethod = request.Token.Value,
                Confirm = true
            };
            
            try
            {
                var paymentIntent = await _stripe.CreateAsync(stripeRequest);
                
                // Translate Stripe's response to our model
                return new PaymentResult(
                    Success: paymentIntent.Status == "succeeded",
                    TransactionId: paymentIntent.Id,
                    ErrorMessage: paymentIntent.Status != "succeeded" 
                        ? paymentIntent.CancellationReason 
                        : null);
            }
            catch (StripeException ex)
            {
                // Translate exception to our error model
                return new PaymentResult(
                    Success: false,
                    TransactionId: null,
                    ErrorMessage: TranslateStripeError(ex));
            }
        }
        
        private string TranslateStripeError(StripeException ex)
        {
            return ex.StripeError.Code switch
            {
                "card_declined" => "Payment method was declined",
                "insufficient_funds" => "Insufficient funds",
                "expired_card" => "Payment method has expired",
                _ => "Payment processing failed"
            };
        }
    }
}

// Domain service uses clean interface
namespace Orders.Domain
{
    public class OrderService
    {
        private readonly IPaymentGateway _payment;  // ACL interface
        
        public async Task<Result> ConfirmOrder(OrderId orderId)
        {
            var order = await _orderRepo.GetById(orderId);
            
            // Use our clean domain model
            var paymentRequest = new PaymentRequest(
                order.TotalAmount,
                order.PaymentMethodToken);
            
            var result = await _payment.ProcessPayment(paymentRequest);
            
            if (result.Success)
            {
                order.Confirm(result.TransactionId);
                await _orderRepo.SaveChanges();
                return Result.Success();
            }
            
            return Result.Fail(result.ErrorMessage);
        }
    }
}
```

**Pros:**
- Your domain stays clean
- Isolated from external changes
- Easier to test (mock the interface)
- Can switch providers without domain changes

**Cons:**
- Additional layer of code
- More complexity
- Requires maintenance

**Best practice:** Always use ACL when integrating with external systems unless the external model is truly excellent.

### Pattern 6: Open Host Service

Provide a well-documented API for other contexts to consume. Focus on stability and backward compatibility.

```
┌─────────────────┐
│  Catalog        │
│  Context        │
│  (Open Host)    │
└────────┬────────┘
         │ Documented API
   ┌─────┴─────┬──────────┐
   │           │          │
┌──▼───┐  ┌───▼──┐  ┌────▼─────┐
│Orders│  │Search│  │Recommend │
└──────┘  └──────┘  └──────────┘
  Multiple consumers
```

**When to use:**
- Multiple downstream contexts need your data
- Want to decouple from downstream implementations
- API should be stable and versioned

**Implementation:**
```csharp
// Catalog Context exposes Open Host Service
namespace Catalog.Api.V1
{
    // Published Language - Stable contract
    public interface ICatalogApi
    {
        Task<ProductDto> GetProduct(ProductId id);
        Task<PagedResult<ProductDto>> SearchProducts(SearchCriteria criteria);
        Task<IEnumerable<CategoryDto>> GetCategories();
    }
    
    // DTOs form the Published Language
    public record ProductDto(
        string Id,
        string Name,
        string Description,
        decimal Price,
        string Currency,
        bool IsAvailable,
        string[] Categories,
        string[] Images);
    
    public record SearchCriteria(
        string Query,
        string[] Categories,
        decimal? MinPrice,
        decimal? MaxPrice,
        int Page,
        int PageSize);
}

// Implementation (internal to Catalog context)
namespace Catalog.Application
{
    using Catalog.Api.V1;
    using Catalog.Domain;
    
    public class CatalogApiService : ICatalogApi
    {
        private readonly IProductRepository _products;
        
        public async Task<ProductDto> GetProduct(ProductId id)
        {
            var product = await _products.GetById(id);
            
            // Translate domain model to DTO
            return new ProductDto(
                product.Id.Value.ToString(),
                product.Name,
                product.Description,
                product.CurrentPrice.Amount,
                product.CurrentPrice.Currency.ToString(),
                product.IsAvailable,
                product.Categories.Select(c => c.Name).ToArray(),
                product.Images.Select(i => i.Url).ToArray());
        }
    }
}
```

**Versioning strategy:**
```csharp
// Support multiple versions
namespace Catalog.Api.V1 { /* version 1 contracts */ }
namespace Catalog.Api.V2 { /* version 2 contracts */ }

// Route to correct version
app.MapGet("/api/v1/products/{id}", /* v1 handler */);
app.MapGet("/api/v2/products/{id}", /* v2 handler */);
```

**Pros:**
- Decouples provider from consumers
- Multiple consumers can use API independently
- Clear contract and documentation
- Version management

**Cons:**
- Must maintain API stability
- Versioning adds complexity
- Breaking changes are difficult

### Pattern 7: Separate Ways

Sometimes the cost of integration exceeds the benefit. Contexts go their own way with no connection.

```
┌──────────────┐     ┌──────────────┐
│  Marketing   │     │  Engineering │
│  Analytics   │  ╳  │  Metrics     │
└──────────────┘     └──────────────┘
      No integration needed
```

**When to use:**
- Contexts have no meaningful overlap
- Integration cost exceeds benefit
- Duplication is cheaper than coordination

**Example:**
- Marketing analytics tracks campaigns
- Engineering metrics track system performance
- No shared concepts, no need to integrate

**Pros:**
- Maximum autonomy
- No coupling
- Simple

**Cons:**
- Duplication if there is overlap
- Must truly be independent

## Common Mistakes and How to Avoid Them

### Mistake 1: Too Few Contexts (The "Big Ball of Mud")

```csharp
// BAD: Everything in one giant context
namespace Education
{
    public class Course
    {
        // Catalog properties
        public string Title { get; set; }
        public string Description { get; set; }
        public string Syllabus { get; set; }
        
        // Enrollment properties
        public List<Student> EnrolledStudents { get; set; }
        public Money Price { get; set; }
        
        // Learning properties
        public List<Lesson> Lessons { get; set; }
        public Dictionary<Student, Progress> StudentProgress { get; set; }
        
        // Forum properties
        public List<Discussion> Discussions { get; set; }
        
        // Admin properties
        public bool IsPublished { get; set; }
        public CourseAnalytics Analytics { get; set; }
    }
}
```

**Problems:**
- Impossible to understand
- Changes for one concern affect all others
- Can't scale concerns independently
- Can't assign ownership

**Solution:** Identify natural boundaries and split:

```csharp
// Catalog Context
namespace Catalog
{
    public class Course
    {
        public CourseId Id { get; private set; }
        public string Title { get; private set; }
        public string Description { get; private set; }
        public InstructorId InstructorId { get; private set; }
    }
}

// Enrollment Context
namespace Enrollment
{
    public class CourseEnrollment
    {
        public CourseId CourseId { get; private set; }
        public StudentId StudentId { get; private set; }
        public EnrollmentStatus Status { get; private set; }
    }
}

// Learning Context
namespace Learning
{
    public class CourseSession
    {
        public CourseId CourseId { get; private set; }
        public StudentId StudentId { get; private set; }
        public Progress Progress { get; private set; }
    }
}
```

### Mistake 2: Too Many Contexts (Microservice Madness)

```
❌ BAD: Excessive fragmentation

User Service
User-Profile Service
User-Preferences Service
User-Settings Service
User-Avatar Service
User-Notifications Service

... all for "user" concept!
```

**Problems:**
- Excessive network chattiness
- Distributed transactions
- Complex orchestration
- High operational overhead

**Solution:** Group related concepts into cohesive contexts

```
✓ GOOD: Identity Context

Contains:
- User account
- Profile
- Preferences
- Settings
- Avatar
- Notification preferences

All related to user identity, managed together
```

**Rule of thumb:** If two concepts always change together and have strong invariants between them, they should be in the same context.

### Mistake 3: Ignoring Organizational Boundaries

```
Technical view: "Orders and Shipping should be one context"
Organizational reality: Different teams, different priorities, different release cycles

Result: Constant friction, blocked deployments, ownership conflicts
```

**Solution:** Align contexts with team boundaries (Conway's Law)

```
✓ Align with organization:

Orders Context → Commerce Team
Shipping Context → Logistics Team

Separate contexts, clear ownership, independent evolution
```

### Mistake 4: Sharing Domain Models Across Contexts

```csharp
// BAD: Shared domain model assembly
namespace Company.Domain.Shared
```

**Problems:**
- Coupling through shared types
- Changes require coordinating all contexts

## Advanced Topic: Context Refactoring

As your understanding deepens, you may need to split or merge contexts.

### Splitting a Context

**When to split:**
- Context is too large
- Different teams want ownership of different parts
- Different parts have different change rates
- Subdomains are becoming clear

**Example: Splitting "Products" Context**

```
Before:
┌─────────────────────────────┐
│   Products Context          │
│   - Catalog                 │
│   - Inventory               │
│   - Pricing                 │
└─────────────────────────────┘

After discovering different concerns:
┌────────────────┐  ┌────────────────┐  ┌────────────────┐
│  Catalog       │  │  Inventory     │  │  Pricing       │
│  Context       │  │  Context       │  │  Context       │
│  (Marketing)   │  │  (Operations)  │  │  (Finance)     │
└────────────────┘  └────────────────┘  └────────────────┘
```

**Migration approach:**
1. Identify the seam (where to cut)
2. Define interfaces for communication
3. Extract one subdomain at a time
4. Migrate data gradually
5. Remove old code when migration complete

### Merging Contexts

**When to merge:**
- Contexts are too small/trivial
- Excessive coordination needed
- Shared transactional boundaries
- Same team owns both

**Example: Merging "Tax" into "Billing"**

```
Before:
┌────────────┐  ┌────────────┐
│  Billing   │  │  Tax       │

└────────────┘  └────────────┘
    │ Constant coordination needed
    │ Always change together
    │ Same team owns both

After:
┌────────────────────────────┐
│   Billing Context          │
│   - Invoicing              │
│   - Tax Calculation        │
```

## Self-Check Questions

1. **What is a bounded context and why is it important?**
   - A bounded context is an explicit boundary within which a domain model exists
   - Within the boundary, terms have specific, consistent meanings
   - Different contexts can have different models for the same concept
   - Important because it prevents the "unified model" trap and allows independent evolution
   - Aligns with team boundaries and organizational structure

2. **How does the same term (like "Product") mean different things in different contexts?**
   - In Catalog: Product is rich marketing information (descriptions, images, specifications)
   - In Orders: Product is a snapshot at time of purchase (name, price at that moment)
   - In Warehouse: Product is physical inventory (SKU, weight, dimensions, location)
   - Each context optimizes the model for its specific needs
   - This is correct and healthy—not a problem to fix!

3. **What is an Anti-Corruption Layer and when should you use it?**
   - Translation layer that protects your domain from external models
   - Translates between your clean model and external/legacy systems
   - Use when: Integrating with poorly designed systems, external APIs, legacy systems
   - Prevents external model from polluting your domain
   - Makes it possible to swap external dependencies

4. **How do bounded contexts relate to microservices?**
   - Ideal: One bounded context = One microservice
   - Contexts define logical boundaries, services are physical deployment units
   - Contexts help identify service boundaries
   - Each service should represent exactly one context
   - Database per context/service for independence

5. **What are the different context mapping patterns?**
   - Partnership: Teams collaborate closely, coordinate changes
   - Shared Kernel: Small shared model between contexts (use sparingly)
   - Customer-Supplier: Upstream provides to downstream, negotiated changes
   - Conformist: Downstream conforms to upstream (when no influence)
   - Anti-Corruption Layer: Translation layer protects domain
   - Open Host Service: Well-documented API for multiple consumers
   - Separate Ways: No integration when cost exceeds benefit

6. **How do you identify bounded context boundaries?**
   - Different ubiquitous language between areas
   - Different team/department ownership
   - Different change cadence and drivers
   - Different data consistency requirements
   - Different scalability needs
   - Natural organizational seams

## Key Takeaways

1. **Bounded contexts are about boundaries** - They make explicit where one model ends and another begins

2. **Same term, different meanings is OK** - Don't force a unified model; embrace multiple models

3. **Align with organization** - Context boundaries often match team boundaries (Conway's Law)

4. **Integration patterns matter** - Choose the right pattern for each relationship (Partnership, ACL, etc.)

5. **One context = One service (ideally)** - But contexts are logical, services are physical

6. **Database per context** - Don't share databases across contexts; it couples them

7. **Context maps are documentation** - Visualize relationships to make dependencies explicit

8. **Start with fewer contexts** - You can split later; merging is harder

9. **Respect boundaries in code** - Even in monoliths, use namespaces to separate contexts

10. **Refactor as understanding deepens** - Boundaries will evolve as you learn the domain
