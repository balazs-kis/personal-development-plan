# Lesson 1: Common Architectural Anti-Patterns

## Learning Objectives

By the end of this lesson, you will be able to:
- Recognize Big Ball of Mud and other common anti-patterns
- Identify Golden Hammer and Cargo Cult programming in codebases
- Understand root causes and symptoms of anti-patterns
- Apply strategies to avoid and remediate anti-patterns
- Distinguish between acceptable pragmatism and harmful anti-patterns

---

## Introduction

Anti-patterns are common solutions to recurring problems that appear beneficial but ultimately cause more harm than good. Unlike patterns—which are proven solutions to common problems—anti-patterns are tempting approaches that lead to technical debt, maintenance nightmares, and decreased productivity.

Understanding anti-patterns is crucial because:
- **Prevention:** Recognizing them early prevents costly mistakes
- **Remediation:** Identifying them in legacy code enables targeted refactoring
- **Communication:** Naming anti-patterns provides a shared vocabulary for discussing code quality
- **Career Growth:** Senior developers are distinguished by their ability to avoid these traps

The goal isn't to judge code as "good" or "bad," but to recognize when a solution will cause more problems than it solves, and to understand why these patterns emerge so we can address root causes.

## Key Concepts Summary

### 1. Big Ball of Mud

**Description:** A system with no recognizable structure, where everything depends on everything.

**Symptoms:**
```csharp
// Everything in one giant class
public class OrderManager
{
    // Database access
    private SqlConnection _connection;
    
    // Business logic
    public void ProcessOrder(Order order)
    {
        // Validation mixed with data access
        if (string.IsNullOrEmpty(order.CustomerName))
            throw new Exception("Invalid name");
        
        // Direct SQL in business logic
        _connection.Open();
        var cmd = new SqlCommand(
            "INSERT INTO Orders VALUES (@id, @customer, @total)", 
            _connection);
        
        // Email logic mixed in
        SendEmail(order.CustomerEmail, "Order confirmed");
        
        // Payment processing
        ChargeCard(order.CardNumber, order.Total);
        
        // Logging
        File.AppendAllText("orders.log", order.ToString());
    }
    
    // 50 more methods doing everything...
}
```

**Solution: Apply Clean Architecture**

```csharp
// Domain layer
public class Order
{
    public Guid Id { get; }
    public string CustomerName { get; }
    public decimal Total { get; }
    
    public void Validate()
    {
        if (string.IsNullOrEmpty(CustomerName))
            throw new DomainException("Customer name required");
    }
}

// Application layer
public class ProcessOrderHandler : IRequestHandler<ProcessOrderCommand, Guid>
{
    private readonly IOrderRepository _repository;
    private readonly IEmailService _emailService;
    private readonly IPaymentService _paymentService;
    
    public async Task<Guid> Handle(ProcessOrderCommand command, CancellationToken ct)
    {
        var order = new Order(command.CustomerName, command.Total);
        order.Validate();
        
        await _repository.AddAsync(order);
        await _paymentService.ChargeAsync(command.PaymentInfo);
        await _emailService.SendConfirmationAsync(order.Id);
        
        return order.Id;
    }
}

// Infrastructure layer
public class OrderRepository : IOrderRepository
{
    private readonly DbContext _context;
    
    public async Task AddAsync(Order order)
    {
        _context.Orders.Add(order);
        await _context.SaveChangesAsync();
    }
}
```

### 2. Golden Hammer

**Description:** "When you have a hammer, everything looks like a nail." Using the same solution for every problem.

**Example:**

```csharp
// Using inheritance for everything
public abstract class BaseService { }
public class OrderService : BaseService { }
public class UserService : BaseService { }
public class EmailService : BaseService { }
// ... Inheritance everywhere, even when composition is better

// Using microservices for everything (including tiny utilities)
// Service 1: GetCurrentTimeService
// Service 2: AddTwoNumbersService
// Service 3: GenerateRandomNumberService
// Overkill!

// Using Redis for everything
// - Session storage ✓ Good
// - Caching ✓ Good
// - Primary database ✗ Bad choice
// - Message queue ✗ Use proper message broker
```

**Solution: Choose the Right Tool**

```csharp
// Use composition over inheritance when appropriate
public class OrderService
{
    private readonly IRepository _repository;    // Composition
    private readonly IValidator _validator;      // Composition
    private readonly ILogger _logger;            // Composition
}

// Use appropriate data stores
public class DataStoreStrategy
{
    // Relational data → SQL database
    private readonly IOrderRepository _orderRepo;  // PostgreSQL
    
    // Caching → Redis
    private readonly ICacheService _cache;         // Redis
    
    // Full-text search → Elasticsearch
    private readonly ISearchService _search;       // Elasticsearch
    
    // Files → Blob storage
    private readonly IBlobStorage _storage;        // Azure Blob/S3
}
```

### 3. Cargo Cult Programming

**Description:** Copying code patterns without understanding why they exist.

**Example:**

```csharp
// Cargo cult: Repository for everything, even for third-party APIs
public interface IWeatherRepository
{
    Task<Weather> GetWeatherAsync(string city);
}

public class WeatherRepository : IWeatherRepository
{
    private readonly HttpClient _httpClient;
    
    // This is just a thin wrapper, adds no value!
    public async Task<Weather> GetWeatherAsync(string city)
    {
        return await _httpClient.GetFromJsonAsync<Weather>($"api/weather/{city}");
    }
}

// Cargo cult: Interfaces for everything
public interface IEmailSender { }
public interface IEmailValidator { }
public interface IEmailFormatter { }
public interface IEmailLogger { }
// When you only have one implementation, you may not need an interface!
```

**Solution: Understand the Purpose**

```csharp
// Repository pattern makes sense for entities you own
public interface IOrderRepository
{
    Task<Order> GetByIdAsync(Guid id);
    Task AddAsync(Order order);
}

// For third-party APIs, use a service/client directly
public class WeatherService
{
    private readonly HttpClient _httpClient;
    
    public async Task<Weather> GetWeatherAsync(string city)
    {
        var response = await _httpClient.GetAsync($"api/weather/{city}");
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<Weather>();
    }
}

// Only create interfaces when you need abstraction
// - Multiple implementations
// - Testing with mocks
// - Plugin architecture
```

### 4. God Object / God Class

**Description:** A class that knows too much or does too much.

```csharp
// BAD - God class
public class ApplicationManager
{
    public void RegisterUser() { }
    public void SendEmail() { }
    public void ProcessPayment() { }
    public void GenerateReport() { }
    public void BackupDatabase() { }
    public void SendSMS() { }
    public void ValidateInput() { }
    // ... 100+ methods
}
```

**Solution: Single Responsibility Principle**

```csharp
public class UserService
{
    public Task RegisterUserAsync(UserRegistration registration) { }
}

public class EmailService
{
    public Task SendEmailAsync(EmailMessage message) { }
}

public class PaymentService
{
    public Task ProcessPaymentAsync(Payment payment) { }
}

public class ReportService
{
    public Task<Report> GenerateReportAsync(ReportRequest request) { }
}
```

### 5. Lava Flow

**Description:** Dead code and obsolete features that nobody dares to remove.

```csharp
// Code with layers of "just in case" cruft
public class OrderService
{
    // TODO: Remove after migration (added 3 years ago)
    private readonly ILegacyOrderService _legacyService;
    
    // Not used anymore, but keeping just in case
    private readonly IOldPaymentProvider _oldPayment;
    
    public async Task ProcessOrder(Order order)
    {
        // New code
        await _newService.ProcessAsync(order);
        
        // Commented out code from 2019
        // if (useLegacy)
        // {
        //     _legacyService.Process(order);
        // }
    }
}
```

**Solution: Clean Up Regularly**

```csharp
public class OrderService
{
    private readonly IPaymentService _payment;
    
    public async Task ProcessOrder(Order order)
    {
        await _payment.ProcessAsync(order);
    }
}

// Use version control instead of commented code
// Delete unused dependencies
// Remove feature flags after rollout complete
```

### 6. Magic Numbers and Strings

```csharp
// BAD
if (user.Status == 3)
{
    // What does 3 mean?
}

if (order.Type == "express-overnight-priority")
{
    // Typo-prone
}
```

**Solution: Use Constants and Enums**

```csharp
public enum UserStatus
{

    Active = 2,
    Suspended = 3,
    Deleted = 4

if (user.Status == UserStatus.Suspended)
{
    // Clear and type-safe
}

public enum OrderType
{

    Express,
    Overnight
}
```

### 7. Premature Optimization

**Description:** Optimizing code before identifying actual performance problems.

```csharp
// BAD - Optimizing before measuring
public class ProductService
{
    // Using object pooling for simple objects
    private readonly ObjectPool<Product> _pool;
    
    // Caching everything "just in case"
    private readonly Dictionary<string, object> _cache;
    
    // Manual memory management
    private unsafe Product* CreateProduct() { }
    
    // Complex pre-calculation
    private readonly Dictionary<string, ComputedResult> _precomputedResults;
}
```

**Solution: Measure First, Then Optimize**

```csharp
// Start simple and readable
public class ProductService
{
    private readonly IProductRepository _repository;
    
    public Product CreateProduct(string name, decimal price)
    {
        return new Product(name, price);
    }
    
    public async Task<Product> GetProductAsync(Guid id)
    {
        return await _repository.GetByIdAsync(id);
    }
}

// If performance tests show problems, add targeted optimization
public class OptimizedProductService
{
    private readonly IProductRepository _repository;
    private readonly IMemoryCache _cache;
    
    public async Task<Product> GetProductAsync(Guid id)
    {
        // Only cache after measuring and identifying this as a bottleneck
        return await _cache.GetOrCreateAsync(
            $"product:{id}",
            async entry =>
            {
                entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
                return await _repository.GetByIdAsync(id);
            });
    }
}
```

### 8. Spaghetti Code

**Description:** Code with a complex and tangled control structure, making it difficult to follow.

```csharp
// BAD - Tangled logic with goto, nested conditions
public void ProcessTransaction(Transaction tx)
{
    if (tx != null)
    {
        if (tx.Amount > 0)
        {
            if (tx.Status == "pending")
            {
                for (int i = 0; i < tx.Items.Count; i++)
                {
                    if (tx.Items[i].IsValid)
                    {
                        // Process item
                        if (tx.Items[i].RequiresApproval)
                        {
                            // Send for approval
                            if (tx.Items[i].ApprovalLevel > 2)
                            {
                                // Escalate
                                goto Escalate;
                            }
                        }
                    }
                }
            }
        }
    }
    return;
    
Escalate:
    // Escalation logic
    // Hard to understand flow
}
```

**Solution: Clean, Structured Flow**

```csharp
public class TransactionProcessor
{
    public async Task ProcessTransactionAsync(Transaction transaction)
    {
        ValidateTransaction(transaction);
        
        var validItems = GetValidItems(transaction);
        
        foreach (var item in validItems)
        {
            await ProcessItemAsync(item);
        }
    }
    
    private void ValidateTransaction(Transaction transaction)
    {
        if (transaction == null)
            throw new ArgumentNullException(nameof(transaction));
            
        if (transaction.Amount <= 0)
            throw new DomainException("Transaction amount must be positive");
            
        if (transaction.Status != "pending")
            throw new DomainException("Only pending transactions can be processed");
    }
    
    private IEnumerable<TransactionItem> GetValidItems(Transaction transaction)
    {
        return transaction.Items.Where(item => item.IsValid);
    }
    
    private async Task ProcessItemAsync(TransactionItem item)
    {
        if (!item.RequiresApproval)
        {
            await _processor.ProcessAsync(item);
            return;
        }
        
        if (item.ApprovalLevel > 2)
            await _approvalService.EscalateAsync(item);
        else
            await _approvalService.RequestApprovalAsync(item);
    }
}
```

### 9. Copy-Paste Programming

**Description:** Duplicating code rather than abstracting reusable logic.

```csharp
// BAD - Copy-paste everywhere
public class ReportGenerator
{
    public void GenerateSalesReport()
    {
        var data = _db.Sales.ToList();
        var csv = new StringBuilder();
        csv.AppendLine("Date,Amount,Customer");
        foreach (var sale in data)
        {
            csv.AppendLine($"{sale.Date},{sale.Amount},{sale.Customer}");
        }
        File.WriteAllText("sales.csv", csv.ToString());
    }
    
    public void GenerateOrdersReport()
    {
        var data = _db.Orders.ToList();
        var csv = new StringBuilder();
        csv.AppendLine("Date,Amount,Customer");  // Same code!
        foreach (var order in data)
        {
            csv.AppendLine($"{order.Date},{order.Total},{order.Customer}");
        }
        File.WriteAllText("orders.csv", csv.ToString());
    }
    
    public void GenerateInvoicesReport()
    {
        var data = _db.Invoices.ToList();
        var csv = new StringBuilder();
        csv.AppendLine("Date,Amount,Customer");  // Same code again!
        foreach (var invoice in data)
        {
            csv.AppendLine($"{invoice.Date},{invoice.Amount},{invoice.Customer}");
        }
        File.WriteAllText("invoices.csv", csv.ToString());
    }
}
```

**Solution: DRY (Don't Repeat Yourself)**

```csharp
public class ReportGenerator
{
    public void GenerateSalesReport()
    {
        var data = _db.Sales.Select(s => new ReportRow
        {
            Date = s.Date,
            Amount = s.Amount,
            Customer = s.Customer
        });
        
        GenerateCsvReport(data, "sales.csv");
    }
    
    public void GenerateOrdersReport()
    {
        var data = _db.Orders.Select(o => new ReportRow
        {
            Date = o.Date,
            Amount = o.Total,
            Customer = o.Customer
        });
        
        GenerateCsvReport(data, "orders.csv");
    }
    
    private void GenerateCsvReport(IEnumerable<ReportRow> data, string filename)
    {
        var csv = new StringBuilder();
        csv.AppendLine("Date,Amount,Customer");
        
        foreach (var row in data)
        {
            csv.AppendLine($"{row.Date},{row.Amount},{row.Customer}");
        }
        
        File.WriteAllText(filename, csv.ToString());
    }
    
    private record ReportRow(DateTime Date, decimal Amount, string Customer);
}
```

### 10. Not Invented Here (NIH) Syndrome

**Description:** Rejecting existing solutions and reinventing the wheel.

```csharp
// BAD - Building your own when libraries exist
public class CustomJsonParser
{
    // 500 lines of custom JSON parsing
    // Bugs, edge cases not handled
    // Performance issues
}

public class CustomHttpClient
{
    // Reimplementing HTTP client
    // Missing features
    // Security vulnerabilities
}

public class CustomLogger
{
    // Yet another logging framework
    // No ecosystem support
}
```

**Solution: Use Battle-Tested Libraries**

```csharp
// GOOD - Use existing, proven solutions
using System.Text.Json;
using Microsoft.Extensions.Logging;

public class DataProcessor
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<DataProcessor> _logger;
    
    public async Task<MyData> FetchAndProcessAsync(string url)
    {
        _logger.LogInformation("Fetching data from {Url}", url);
        
        var response = await _httpClient.GetAsync(url);
        response.EnsureSuccessStatusCode();
        
        var json = await response.Content.ReadAsStringAsync();
        var data = JsonSerializer.Deserialize<MyData>(json);
        
        return data;
    }
}
```

### Root Causes of Anti-Patterns

Understanding why anti-patterns emerge helps prevent them:

**1. Time Pressure**
```csharp
// Under deadline pressure, taking shortcuts
// "We'll fix it later" (spoiler: we won't)
public void QuickFix(Order order)
{
    // TODO: This needs refactoring after release
    // Added 2019-03-15, still here...
}
```

**2. Lack of Knowledge**
```csharp
// Not knowing better patterns exist
// Learning C# but not LINQ, async/await, etc.
```

**3. Growing Complexity**
```csharp
// Started simple, grew organically without refactoring
// "It's working, don't touch it"
```

**4. Poor Communication**
```csharp
// Team not aligned on architecture
// No code reviews
// No shared standards
```

### Preventing Anti-Patterns

**Strategies for Prevention:**

1. **Code Reviews**
```markdown
Every PR reviewed by at least one other developer
Focus on design, not just syntax
Ask "why" questions
```

2. **Continuous Refactoring**
```csharp
// Boy Scout Rule: Leave code better than you found it
// Small improvements constantly
```

3. **Pair Programming**
```markdown
Two brains catch anti-patterns faster
Knowledge transfer prevents NIH syndrome
```

4. **Architecture Decision Records**
```markdown
# ADR-042: Use Repository Pattern for Data Access

## Status
Accepted

## Context
Need consistent data access patterns across services.

## Decision
Implement repository pattern for all entity data access.

## Consequences
- Consistent interface
- Easier testing
- Clear separation of concerns
```

**Refactored Solution:**

```csharp
// Domain layer - clear responsibilities
public enum OperationType
{
    SaveData = 1,
    SendEmail = 2,
    LogData = 3
}

// Separate concerns into services
public interface IDataService
{
    Task SaveDataAsync(string data);
}

public interface IEmailService
{
    Task SendEmailAsync(string to, string subject, string body);
}

public interface ILoggingService
{
    Task LogAsync(string message);
}

// Implementations
public class DataService : IDataService
{
    private readonly IDbConnection _connection;
    
    public DataService(IDbConnection connection)
    {
        _connection = connection;
    }
    
    public async Task SaveDataAsync(string data)
    {
        // Using parameterized queries to prevent SQL injection
        const string sql = "INSERT INTO Data (Content) VALUES (@data)";
        await _connection.ExecuteAsync(sql, new { data });
    }
}

public class EmailService : IEmailService
{
    private readonly IConfiguration _config;
    private readonly ISmtpClient _smtpClient;
    
    public EmailService(IConfiguration config, ISmtpClient smtpClient)
    {
        _config = config;
        _smtpClient = smtpClient;
    }
    
    public async Task SendEmailAsync(string to, string subject, string body)
    {
        var message = new MailMessage(
            from: _config["Email:From"],
            to: to,
            subject: subject,
            body: body);
            
        await _smtpClient.SendMailAsync(message);
    }
}

public class FileLoggingService : ILoggingService
{
    private readonly ILogger<FileLoggingService> _logger;
    
    public FileLoggingService(ILogger<FileLoggingService> logger)
    {
        _logger = logger;
    }
    
    public Task LogAsync(string message)
    {
        _logger.LogInformation(message);
        return Task.CompletedTask;
    }
}

// Orchestrator - single responsibility
public class OperationHandler
{
    private readonly IDataService _dataService;
    private readonly IEmailService _emailService;
    private readonly ILoggingService _loggingService;
    
    public OperationHandler(
        IDataService dataService,
        IEmailService emailService,
        ILoggingService loggingService)
    {
        _dataService = dataService;
        _emailService = emailService;
        _loggingService = loggingService;
    }
    
    public async Task HandleOperationAsync(string data, OperationType operationType)
    {
        try
        {
            switch (operationType)
            {
                case OperationType.SaveData:
                    await _dataService.SaveDataAsync(data);
                    break;
                    
                case OperationType.SendEmail:
                    await HandleEmailAsync(data);
                    break;
                    
                case OperationType.LogData:
                    await _loggingService.LogAsync(data);
                    break;
                    
                default:
                    throw new ArgumentException($"Unknown operation type: {operationType}");
            }
        }
        catch (Exception ex)
        {
            _loggingService.LogAsync($"Error handling operation: {ex.Message}");
            throw;
        }
    }
    
    private async Task HandleEmailAsync(string data)
    {
        await _emailService.SendEmailAsync("user@example.com", "Subject", data);
        
        // Urgent notification - reusing service, not duplicating code
        if (data.Contains("URGENT", StringComparison.OrdinalIgnoreCase))
        {
            await _emailService.SendEmailAsync("manager@example.com", "URGENT", data);
        }
    }
}

// Configuration (appsettings.json)

    "From": "admin@example.com",
    "SmtpHost": "smtp.gmail.com",
    "SmtpPort": 587
  },
  "ConnectionStrings": {
    "Default": "Data Source=localhost;..."
  }
}
```

## Self-Check Questions

1. **What causes Big Ball of Mud, and how do you prevent it?**
   - Caused by: Lack of planning, time pressure, poor communication, no refactoring
   - Prevention: Clear architecture from start, continuous refactoring, code reviews, enforce separation of concerns

2. **How is Golden Hammer different from design patterns?**
   - Golden Hammer: Using same solution for EVERY problem (anti-pattern)
   - Design Pattern: Using appropriate pattern for specific problem (good practice)
   - Key: Patterns are tools in a toolbox; use the right tool for the job

3. **Why is Cargo Cult programming problematic?**
   - Creates unnecessary complexity without benefits
   - Wastes time maintaining code that adds no value
   - Makes codebase harder to understand
   - Prevents team from learning WHY patterns exist
   - Solution: Understand the purpose before applying a pattern

4. **How do you identify and remove Lava Flow code safely?**
   - Identify: Look for commented code, TODO older than 6 months, unused dependencies, dead branches
   - Safe removal:
     1. Ensure version control is in place (can always recover)
     2. Run tests before and after removal
     3. Use static analysis to find unused code
     4. Remove in small increments, commit frequently
     5. Communicate with team (someone might know why it's there)

5. **When is it acceptable to take on technical debt intentionally?**
   - Time-sensitive launch (MVP, conference demo)
   - Exploring/validating new feature
   - Requirements unclear, need feedback first
   - Must: Document the debt, create tickets, plan repayment

6. **What's the difference between an anti-pattern and a code smell?**
   - Code smell: Hint that something might be wrong (e.g., long method)
   - Anti-pattern: Known problematic solution with a name (e.g., God Object)
   - All anti-patterns are code smells, but not all smells are anti-patterns

## Key Takeaways

- **Anti-patterns are attractive:** They often seem like the quickest solution, which is why they're common
- **Context matters:** Some "anti-patterns" may be acceptable in specific contexts (prototypes, throwaway code)
- **Prevention is easier than cure:** Establishing good practices from the start is easier than refactoring later
- **Naming is powerful:** Giving anti-patterns names helps teams communicate about code quality
- **Balance pragmatism and perfection:** Ship working code, but don't let anti-patterns accumulate indefinitely

**The Golden Rule:** When you're tempted to say "I'll fix it later," remember that later rarely comes. Make it at least a little bit better now.
