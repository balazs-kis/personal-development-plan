## Introduction

systemd is the init system and service manager used by most modern Linux distributions. It initializes the system, starts services in parallel, manages dependencies, and provides centralized logging. Understanding systemd is essential for managing services, troubleshooting boot issues, and automating system tasks.

systemd replaced the traditional SysV init system, offering faster boot times, better dependency management, and more powerful service control.

## Key Concepts Summary

### What is systemd?

**Definition:**
- **System and service manager** for Linux
- **Init system** (PID 1) - first process started by kernel
- **Manages system boot** and service lifecycle
- **Provides logging** through journald
- **Handles system state** (boot, shutdown, targets)

**Why systemd?**
- **Faster boot** - Parallel service startup
- **Better dependencies** - Services start in correct order
- **On-demand activation** - Services start when needed
- **Unified management** - Single tool (systemctl) for all services
- **Better logging** - Centralized journal with journalctl
- **Socket activation** - Services start when connections arrive

**systemd vs SysV Init:**
| Feature | SysV Init | systemd |
|---------|-----------|---------|
| Boot | Sequential | Parallel |
| Service files | Shell scripts | Declarative units |
| Dependencies | Manual ordering | Automatic |
| Logging | Separate logs | Centralized journal |
| Socket activation | No | Yes |
| Resource limits | Limited | Comprehensive (cgroups) |

### systemd Components

**Key daemons and tools:**
```
systemd         - Main system daemon (PID 1)
systemctl       - Control systemd and services
journald        - Logging daemon
journalctl      - Query journal logs
systemd-logind  - User session management
systemd-networkd - Network configuration
systemd-resolved - DNS resolution
systemd-timesyncd - Time synchronization
```

**systemd manages:**
- Services (daemons)
- Sockets (network/IPC)
- Devices (hardware)
- Mounts (filesystems)
- Targets (system states)
- Timers (scheduled tasks)

### systemd Units

**What is a unit?**
- Basic object managed by systemd
- Defined by unit files (.service, .socket, .timer, etc.)
- Has a name, type, and configuration
- Can have dependencies on other units

**Unit types:**
```
.service    - System services (daemons)
.socket     - IPC or network socket
.device     - Device unit (udev)
.mount      - Filesystem mount point
.automount  - Automatic mount point
.swap       - Swap file/partition
.target     - Group of units (like runlevel)
.path       - Path-based activation
.timer      - Timer for scheduled execution
.slice      - Resource management group
.scope      - External processes
```

**Most common: .service units**
```bash
nginx.service
postgresql.service
sshd.service
myapp.service
```

### Unit File Locations

**System unit directories (priority order):**
```bash
/etc/systemd/system/          # Local configuration (highest priority)
/run/systemd/system/          # Runtime units
/usr/lib/systemd/system/      # Distribution packages (lowest priority)
```

**Priority rules:**
1. Files in `/etc/systemd/system/` override all others
2. Use `/etc/systemd/system/` for custom services
3. Never modify files in `/usr/lib/systemd/system/`
4. Use `systemctl edit` to override specific settings

**View unit file paths:**
```bash
# Show unit file location
systemctl show -p FragmentPath nginx.service

# List all unit files
systemctl list-unit-files

# Show unit file content
systemctl cat nginx.service
```

### Basic Unit File Structure

**Three main sections:**
```ini
[Unit]
# General information and dependencies

[Service]
# Service-specific configuration

[Install]
# Installation instructions (enable/disable)
```

**Simple example:**
```ini
[Unit]
Description=My Application
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/myapp
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

### Understanding Targets

**What is a target?**
- Group of units that represent a system state
- Similar to runlevels in SysV init
- Can depend on other targets
- Units can be "wanted by" targets

**Common targets:**
```
default.target      - Default target (usually multi-user or graphical)
multi-user.target   - Multi-user text mode (like runlevel 3)
graphical.target    - Graphical mode (like runlevel 5)
rescue.target       - Single-user rescue mode
emergency.target    - Emergency shell
reboot.target       - System reboot
poweroff.target     - System shutdown
```

**Target relationships:**
```
graphical.target
    └─ multi-user.target
        └─ basic.target
            └─ sysinit.target
```

**View and change targets:**
```bash
# Current target
systemctl get-default

# All available targets
systemctl list-units --type=target

# Change default target
sudo systemctl set-default multi-user.target

# Switch to target immediately
sudo systemctl isolate rescue.target
```

### Dependencies

**Unit dependency types:**
```
Requires=       - Hard dependency (if required unit fails, this fails)
Wants=          - Soft dependency (preferred, doesn't cause failure)
Requisite=      - Must already be running
BindsTo=        - Tightly bound (stops if bound unit stops)
PartOf=         - Stop/restart with other unit
Conflicts=      - Cannot run simultaneously
```

**Ordering dependencies:**
```
Before=         - This unit must start before listed units
After=          - This unit must start after listed units
```

**Example:**
```ini
[Unit]
Description=Web Application
After=network.target postgresql.service
Requires=postgresql.service
```

**Dependency chain example:**
```
myapp.service
    Requires: postgresql.service
    After: network.target, postgresql.service
    
postgresql.service
    Requires: network.target
    After: network.target
```

### systemd Boot Process

**Boot sequence:**
```
1. Kernel starts
     ↓
2. Kernel starts /sbin/init (systemd)
     ↓
3. systemd reads default.target
     ↓
4. systemd activates dependencies
     ↓
5. Units start in parallel (respecting dependencies)
     ↓
6. System reaches default.target
```

**View boot time:**
```bash
# Overall boot time
systemd-analyze

# Per-service boot time
systemd-analyze blame

# Critical path
systemd-analyze critical-chain

# Visualize boot (creates SVG)
systemd-analyze plot > boot.svg
```

### Unit States

**Unit load states:**
```
loaded      - Unit file found and parsed
not-found   - Unit file doesn't exist
bad-setting - Error in unit file
error       - Failed to load
masked      - Unit is masked (disabled)
```

**Unit active states:**
```
active      - Running
inactive    - Stopped
activating  - Starting
deactivating - Stopping
failed      - Failed to start/stopped with error
```

**Sub-states (for .service):**
```
running     - Service is running
exited      - Successfully exited (oneshot)
failed      - Exited with error
dead        - Not running
```

**Check unit state:**
```bash
# Full status
systemctl status nginx.service

# Just active state
systemctl is-active nginx.service

# Check if enabled
systemctl is-enabled nginx.service

# Check if failed
systemctl is-failed nginx.service
```

### Unit File Naming

**Naming convention:**
```
unit-name.unit-type
```

**Examples:**
```
nginx.service
sshd.socket
docker.service
home.mount
backup.timer
```

**Template units:**
```
getty@.service         - Template
getty@tty1.service     - Instance
```

**Special characters:**
```
- (dash)               - Separator in name
@ (at)                 - Template/instance separator
. (dot)                - Extension separator
\ (backslash)          - Escape special chars
```
