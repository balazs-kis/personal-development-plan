## Introduction

Overlay filesystems are union filesystems that combine multiple directories into a single unified view. Docker uses OverlayFS to efficiently manage container images by layering read-only image layers with a writable container layer. Understanding overlay filesystems helps you optimize image building, troubleshoot storage issues, and understand container filesystem performance.

## Key Concepts Summary

### What is OverlayFS?

**Definition:**
- Union filesystem
- Merges multiple directories into single view
- Layers read-only and read-write filesystems
- Copy-on-write (CoW) behavior

**Purpose:**
```
Without overlay:
- Each container needs full filesystem copy
- Wastes disk space
- Slow container creation
- No image reuse

With overlay:
- Containers share image layers
- Only differences stored
- Fast container creation
- Efficient disk usage
```

**History:**
```
2014 - OverlayFS merged into Linux 3.18
2016 - Docker adopts overlay2 driver
2024 - overlay2 considered legacy
2024 - overlayfs snapshotter preferred
```

### How OverlayFS Works

**Basic concept:**
```
Lower dir (read-only)    ─┐
                          ├─→ Merged dir (unified view)
Upper dir (read-write)   ─┘

User sees: Merged directory
Reads: From lower or upper
Writes: Go to upper dir
Deletes: Create whiteout in upper
```

**Layers:**
```
lowerdir  - Read-only base layer(s)
upperdir  - Read-write top layer
merged    - Unified view presented to user
workdir   - Internal working directory
```

**Example:**
```bash
# Create directories
mkdir -p lower upper work merged

# Add file to lower
echo "Base content" > lower/file.txt

# Mount overlay
mount -t overlay overlay \
  -o lowerdir=lower,upperdir=upper,workdir=work \
  merged/

# User sees merged
cat merged/file.txt  # "Base content"

# Modify file
echo "Modified" > merged/file.txt

# Change stored in upper
cat upper/file.txt   # "Modified"
cat lower/file.txt   # "Base content" (unchanged)
```

### Copy-on-Write (CoW)

**How CoW works:**
```
1. File exists in lower layer (read-only)
2. User modifies file
3. OverlayFS copies file to upper layer
4. Modification happens in upper layer
5. Lower layer remains unchanged
6. Merged view shows modified version
```

**Benefits:**
```
- Saves disk space
- Fast writes (only copy modified files)
- Share base images
- Isolate changes per container
```

**CoW operations:**
```
Read:
- File in upper? Read from upper
- File in lower? Read from lower
- File in both? Read from upper (shadows lower)

Write (file exists):
- Copy file from lower to upper
- Modify in upper
- Lower unchanged

Write (new file):
- Create directly in upper
- No copy needed

Delete:
- Create whiteout file in upper
- Lower file hidden
- Actual file not deleted
```

### Docker's Use of OverlayFS

**Image layers:**
```
Image = Stack of read-only layers

Example nginx image:
Layer 1: Base Ubuntu
Layer 2: Install packages
Layer 3: Add nginx
Layer 4: Configure nginx
Layer 5: Add content

All layers are read-only
```

**Container layer:**
```
Container = Image layers + writable layer

nginx:latest (read-only)  ─┐
                           ├─→ Container view
Container layer (writable) ─┘

All changes go to container layer
Base image unchanged
```

**Layer sharing:**
```
Image A:        Image B:
- Layer 1       - Layer 1  (shared with A)
- Layer 2       - Layer 2  (shared with A)
- Layer 3       - Layer 6  (unique)

Container 1 (from Image A)
Container 2 (from Image A)
Both share image layers
Each has own writable layer
```

### Docker Storage Structure

**Directory layout:**
```
/var/lib/docker/overlay2/
├── <layer-id-1>/
│   ├── diff/          # Layer content
│   ├── link           # Short layer ID
│   └── lower          # Parent layers
├── <layer-id-2>/
│   ├── diff/
│   ├── link
│   └── lower
└── <container-id>/
    ├── diff/          # Container changes
    ├── link
    ├── lower          # Image layers
    ├── merged/        # Container's view
    └── work/          # OverlayFS work dir
```

**Key directories:**
```
diff/   - Actual layer content
link    - Short symlink name
lower   - List of lower layers
merged/ - Unified filesystem view (container sees this)
work/   - Internal OverlayFS workspace
```

### Inspecting Overlay Mounts

**View container layers:**
```bash
# Inspect container
docker inspect container_name

# Look for GraphDriver section:
"GraphDriver": {
    "Data": {
        "LowerDir": "/var/lib/docker/overlay2/abc.../diff:/var/lib/docker/overlay2/def.../diff",
        "MergedDir": "/var/lib/docker/overlay2/xyz.../merged",
        "UpperDir": "/var/lib/docker/overlay2/xyz.../diff",
        "WorkDir": "/var/lib/docker/overlay2/xyz.../work"
    },
    "Name": "overlay2"
}
```

**View mounts:**
```bash
# Show overlay mounts
mount | grep overlay

# Or
findmnt -t overlay

# Detailed mount info
cat /proc/mounts | grep overlay
```

**Examine container filesystem:**
```bash
# Get container ID
CONTAINER_ID=$(docker inspect -f '{{.Id}}' container_name)

# View merged directory
sudo ls /var/lib/docker/overlay2/${CONTAINER_ID}/merged/

# View container layer (changes only)
sudo ls /var/lib/docker/overlay2/${CONTAINER_ID}/diff/

# View lower (image) layers
cat /var/lib/docker/overlay2/${CONTAINER_ID}/lower
```

### Whiteout Files

**What are whiteouts?**
- Special files marking deletions
- Created when file deleted in container
- Hides file from lower layers
- Actual lower file unchanged

**Whiteout format:**
```
Character device with 0/0 major/minor
Named: .wh.<filename>

Example:
Delete /file.txt in container
Creates: /upper/.wh.file.txt
Result: /merged/file.txt appears deleted
```

**View whiteouts:**
```bash
# Container deletes file
docker exec container rm /etc/some-file

# Check container layer
sudo ls -la /var/lib/docker/overlay2/xyz.../diff/etc/
# Shows: .wh.some-file

# Verify file hidden in merged view
docker exec container ls /etc/some-file
# File not found
```

### Performance Considerations

**Read performance:**
```
Best: File in upper layer (one lookup)
Good: File in top lower layer
Slower: File in deep lower layer (multiple lookups)

Recommendation:
- Keep frequently modified files in container
- Minimize image layer depth
- Consolidate layers when building images
```

**Write performance:**
```
Fast: New file (create in upper)
Slower: Modify existing file (CoW from lower)
Slowest: Modify large file (full copy to upper)

Recommendations:
- Use volumes for large file I/O
- Avoid modifying large image files
- Write new files when possible
```

**Disk usage:**
```
Efficient:
- Shared image layers
- Only deltas stored

Issues:
- Many layers = more overhead
- Large files in layers = wasted space
- Deleted files still in image

Recommendations:
- Squash layers when building
- Clean up in same layer
- Use .dockerignore
```

### overlay2 vs overlayfs Snapshotter

**overlay2 (legacy):**
```
Storage driver for Docker
Located: /var/lib/docker/overlay2/
Configuration: daemon.json
Direct kernel OverlayFS usage
```

**overlayfs snapshotter (modern):**
```
Containerd native snapshotter
Located: /var/lib/containerd/
Better performance
Enhanced security
Preferred for new installations
```

**Migration:**
```bash
# Check current driver
docker info | grep "Storage Driver"

# Existing containers use old driver
# New containers use new driver
# No automatic migration
```

### Troubleshooting

**Issue: Container disk space**
```bash
# Check container size
docker ps -s

# Show disk usage
docker system df

# Inspect layers
docker history image_name

# Cleanup
docker system prune -a
```

**Issue: Too many layers**
```bash
# Check layer count
docker history image_name | wc -l

# Squash layers during build
docker build --squash -t myimage .

# Or use multi-stage builds
```

**Issue: Read-only filesystem errors**
```bash
# Container filesystem is read-only
# Check mount:
docker inspect container | grep -A 10 GraphDriver

# Run with writable layer:
docker run -it image bash  # Has writable layer

# Mount as read-only explicitly:
docker run --read-only image
```

**Issue: Disk space after deletion**
```bash
# Deleted files still in image layers

# Solution 1: Delete in same layer
RUN apt-get update && \
    apt-get install -y package && \
    rm -rf /var/lib/apt/lists/*

# Solution 2: Use .dockerignore

# Solution 3: Squash image
docker build --squash
```

### Best Practices

**Building images:**
```dockerfile
# 1. Order layers by change frequency
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y \
    package1 package2 package3
# ^ Changes rarely

COPY requirements.txt .
RUN pip install -r requirements.txt
# ^ Changes occasionally

COPY . /app
# ^ Changes frequently

# 2. Combine commands
RUN apt-get update && \
    apt-get install -y package && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*
# ^ All in one layer

# 3. Use multi-stage builds
FROM golang:1.21 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp

FROM alpine:latest
COPY --from=builder /app/myapp /usr/local/bin/
# ^ Only binary in final image
```

**Storage optimization:**
```
- Minimize layers (combine RUN commands)
- Clean up in same layer
- Use .dockerignore
- Use multi-stage builds
- Squash final image if needed
- Use volumes for data
```
