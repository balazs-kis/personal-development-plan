## Introduction

Kafka achieves high availability and fault tolerance through **replication**. Each partition is replicated across multiple brokers, ensuring that data remains available even when brokers fail. Understanding replication is crucial for designing resilient systems that can tolerate hardware failures, network issues, and planned maintenance.

At the heart of Kafka's replication model are three key concepts: **leaders** (handle all reads/writes), **followers** (replicate data), and **in-sync replicas (ISR)** (followers that are caught up with the leader). Together, these mechanisms provide configurable durability guarantees.

## Key Concepts Summary

### Replication Architecture

Each Kafka partition is replicated across multiple brokers. The **replication factor** (RF) determines how many copies exist:

```
Topic: "orders" 
Partitions: 3
Replication Factor: 3

Partition 0:
  Leader: Broker 1
  Followers: Broker 2, Broker 3

Partition 1:
  Leader: Broker 2
  Followers: Broker 1, Broker 3

Partition 2:
  Leader: Broker 3
  Followers: Broker 1, Broker 2
```

**Key characteristics:**
- Each partition has exactly one leader and (RF - 1) followers
- Leaders are distributed across brokers for load balancing
- Clients only read/write to leaders
- Followers passively replicate from the leader

### Leaders and Followers

**Leader responsibilities:**
- Handle all produce requests (writes) for the partition
- Handle all fetch requests (reads) from consumers
- Track which followers are in-sync
- Maintain the high watermark (HW) — highest offset replicated to all ISR

**Follower responsibilities:**
- Continuously fetch new messages from the leader
- Maintain an exact replica of the leader's log
- Send heartbeats to indicate they're alive and caught up
- Can become leader if current leader fails

```csharp
// Producer always writes to the leader
// (Kafka client handles this automatically)
var producer = new ProducerBuilder<string, Order>(config).Build();
await producer.ProduceAsync("orders", message);  // Routed to partition leader

// Consumer reads from the leader by default
// (Can be configured to read from followers for read scalability)
var consumer = new ConsumerBuilder<string, Order>(config).Build();
var result = consumer.Consume();  // Reads from partition leader
```

### In-Sync Replicas (ISR)

The **ISR (In-Sync Replica) set** is the subset of replicas that are caught up with the leader:

```
Partition 0 (RF=3):
  Broker 1 (Leader): Offset 1000    ← ISR
  Broker 2 (Follower): Offset 1000  ← ISR (caught up)
  Broker 3 (Follower): Offset 950   ← NOT in ISR (lagging)
```

**ISR membership criteria:**
- Replica must send fetch requests within `replica.lag.time.max.ms` (default: 10 seconds)
- Replica must be caught up to within `replica.lag.max.messages` (deprecated in newer versions)

**Why ISR matters:**
- Only ISR members are eligible to become leader
- `acks=all` waits for all ISR to acknowledge, not all replicas
- ISR size impacts durability vs availability trade-offs

**ISR dynamics:**

```
Time T0: Partition ISR = [Broker 1, Broker 2, Broker 3]

Time T1: Broker 3 network issues → stops fetching
         ISR shrinks = [Broker 1, Broker 2]

Time T2: Broker 3 recovers → catches up
         ISR expands = [Broker 1, Broker 2, Broker 3]
```

### Replication Configuration

#### 1. Replication Factor (Topic-level)

```bash
# Create topic with replication factor 3
kafka-topics --create \
  --topic orders \
  --partitions 6 \
  --replication-factor 3 \
  --bootstrap-server localhost:9092
```

```csharp
// Using AdminClient in .NET
using var adminClient = new AdminClientBuilder(config).Build();

await adminClient.CreateTopicsAsync(new[]
{
    new TopicSpecification
    {
        Name = "orders",
        NumPartitions = 6,
        ReplicationFactor = 3
    }
});
```

**Guidelines:**
- Minimum: RF=1 (no fault tolerance, use only for development)
- Common: RF=3 (tolerates 1 broker failure)
- High durability: RF=5 (tolerates 2 broker failures)
- RF > number of brokers = topic creation fails

#### 2. Acknowledgment Level (Producer-level)

```csharp
var config = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    Acks = Acks.All  // or Acks.Leader, Acks.None
};
```

**Options:**

- **`acks=0`**: No acknowledgment
  - Fastest, no durability guarantee
  - Data may be lost if leader crashes before replication

- **`acks=1`**: Leader acknowledgment only
  - Balanced performance
  - Data may be lost if leader crashes before followers replicate

- **`acks=all` (or `-1`)**: All in-sync replicas acknowledge
  - Strongest durability guarantee
  - Slower due to waiting for replication
  - Guarantees data is replicated before confirming

```
Example: acks=all with RF=3, ISR=[B1, B2, B3]

Producer → Leader (B1) → Writes to log
              ↓
         Follower B2 ← Replicates → Acknowledges
         Follower B3 ← Replicates → Acknowledges
              ↓
         Leader B1 → Acknowledges to Producer ✓
```

#### 3. Min In-Sync Replicas (Topic/Broker-level)

```bash
# Set at topic level
kafka-configs --alter \
  --topic orders \
  --add-config min.insync.replicas=2 \
  --bootstrap-server localhost:9092
```

```csharp
// Or via AdminClient in .NET
await adminClient.AlterConfigsAsync(new Dictionary<ConfigResource, Config>
{
    [new ConfigResource { Type = ResourceType.Topic, Name = "orders" }] = new Config
    {
        Entries = new Dictionary<string, string>
        {
            ["min.insync.replicas"] = "2"
        }
    }
});
```

**Purpose:** Minimum number of ISR required for `acks=all` to succeed

**Example scenarios:**

```
Topic: RF=3, min.insync.replicas=2

Scenario 1: ISR=[B1, B2, B3] (3 in ISR)
  acks=all → Waits for B1, B2, B3 → Success ✓

Scenario 2: ISR=[B1, B2] (2 in ISR, B3 down)
  acks=all → Waits for B1, B2 → Success ✓

Scenario 3: ISR=[B1] (only leader in ISR, B2 and B3 down)
  acks=all → NotEnoughReplicasException ✗
  Partition becomes unavailable for writes
```

**Best practices:**
- Common: `RF=3, min.insync.replicas=2`
- Tolerates 1 replica failure while maintaining durability
- `min.insync.replicas=RF` = very strict (any replica failure blocks writes)

### Leader Election and Failover

When a leader fails, Kafka automatically elects a new leader from the ISR:

```
Initial state:
  Partition 0: Leader=B1, ISR=[B1, B2, B3]

Broker 1 crashes:
  1. Controller detects leader failure (via ZooKeeper/KRaft)
  2. Selects new leader from ISR (e.g., B2)
  3. Updates metadata: Leader=B2, ISR=[B2, B3]
  4. Clients automatically reconnect to new leader

New state:
  Partition 0: Leader=B2, ISR=[B2, B3]
```

**Election guarantees:**
- Only ISR members can become leader
- No data loss if ISR is properly maintained
- Election typically completes in milliseconds to seconds

#### Unclean Leader Election

**Problem:** What if all ISR members are unavailable?

**Options:**

1. **`unclean.leader.election.enable=false` (default, recommended):**
   - Partition becomes unavailable for writes
   - Waits for ISR member to recover
   - No data loss

2. **`unclean.leader.election.enable=true` (risky):**
   - Allows non-ISR replica to become leader
   - Partition remains available
   - ⚠️ **Data loss**: Non-ISR replica may be missing recent messages

```csharp
// Check if unclean leader election occurred (monitoring)
// This would typically be done via Kafka metrics/logs
// NotLeaderException or other errors may indicate failover events
```

**When to enable unclean election:**
- Availability is more critical than data consistency
- Data loss is acceptable (e.g., telemetry, logs)
- Never for financial data, orders, user state

### Handling Broker Failures

**Single broker failure (RF ≥ 2):**
```
Before: RF=3, ISR=[B1, B2, B3]
Broker 2 fails
After: RF=3, ISR=[B1, B3]

Impact:
  - Automatic failover if B2 was leader
  - Reduced redundancy (now tolerates 0 more failures)
  - Under-replicated partitions (monitoring alert)
  - No data loss
```

**Recovery process:**
1. Broker restarts
2. Followers catch up by fetching missing messages
3. Rejoins ISR once caught up
4. Load rebalances

**Multiple broker failures:**
```
Before: RF=3, ISR=[B1, B2, B3], min.insync.replicas=2

Brokers 2 and 3 fail simultaneously
After: RF=3, ISR=[B1]

Impact:
  - ISR < min.insync.replicas
  - Writes fail with NotEnoughReplicasException
  - Reads still work (leader is available)
  - Partition unavailable until ≥1 broker recovers
```

### Replication Performance Considerations

**Factors affecting replication performance:**

1. **Network bandwidth**: Followers fetch from leader over the network
2. **Disk I/O**: Sequential writes on all replicas
3. **Replication factor**: Higher RF = more replication overhead
4. **Producer `acks` setting**: `acks=all` waits for replication

```csharp
// High-throughput configuration (lower durability)
var highThroughputConfig = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    Acks = Acks.Leader,              // Don't wait for followers
    LingerMs = 10,                   // Batch messages
    CompressionType = CompressionType.Lz4
};

// High-durability configuration (lower throughput)
var highDurabilityConfig = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    Acks = Acks.All,                 // Wait for all ISR
    MaxInFlight = 1,                 // Strict ordering
    EnableIdempotence = true         // Exactly-once
};
```

**Monitoring replication health:**

```csharp
// Monitor under-replicated partitions
// This is typically done via Kafka's JMX metrics:
// kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions

// Check ISR status programmatically
using var adminClient = new AdminClientBuilder(config).Build();
var metadata = adminClient.GetMetadata("orders", TimeSpan.FromSeconds(10));

foreach (var partition in metadata.Topics[0].Partitions)
{
    var inSyncReplicaCount = partition.InSyncReplicas.Length;
    var replicaCount = partition.Replicas.Length;
    
    if (inSyncReplicaCount < replicaCount)
    {
        logger.LogWarning(
            "Under-replicated partition {Partition}: {InSync}/{Total} replicas in ISR",
            partition.PartitionId,
            inSyncReplicaCount,
            replicaCount
        );
    }
}
```

### Rack Awareness

**Problem:** All replicas on same rack = single point of failure

**Solution:** Rack-aware replica placement

```bash
# Configure broker rack
# server.properties
broker.rack=us-east-1a

# Create topic with rack-aware placement
kafka-topics --create \
  --topic orders \
  --partitions 6 \
  --replication-factor 3 \
  --config min.insync.replicas=2 \
  --bootstrap-server localhost:9092

# Kafka automatically distributes replicas across racks
```

**Benefits:**
- Tolerates rack-level failures
- Reduces network traffic within rack
- Better disaster recovery

### Preferred Leader Election

**Balancing load after failures:**

```
Initial state:
P0: Leader=B1, ISR=[B1,B2,B3]
P1: Leader=B2, ISR=[B1,B2,B3]
P2: Leader=B3, ISR=[B1,B2,B3]

Broker 1 fails:
P0: Leader=B2, ISR=[B2,B3]  ← B2 now handles 2 partitions
P1: Leader=B2, ISR=[B2,B3]
P2: Leader=B3, ISR=[B2,B3]

Broker 1 recovers:
P0: Leader=B1, ISR=[B1,B2,B3]  ← Preferred leader restored
P1: Leader=B2, ISR=[B1,B2,B3]
P2: Leader=B3, ISR=[B1,B2,B3]
```

**Configuration:**

```bash
# Enable automatic preferred leader election
# server.properties
auto.leader.rebalance.enable=true
leader.imbalance.check.interval.seconds=300  # Check every 5 minutes
leader.imbalance.per.broker.percentage=10    # Trigger if > 10% imbalance
```

```csharp
// Manually trigger preferred leader election
using var adminClient = new AdminClientBuilder(config).Build();

await adminClient.AlterConsumerGroupOffsetsAsync(
    new ConsumerGroupOffsetsSpec
    {
        GroupId = "order-processors",
        Partitions = new[]
        {
            new TopicPartitionOffset("orders", 0, Offset.Unset)
        }
    });
```

### Replica Fetcher Tuning

**Optimize follower replication:**

```bash
# server.properties
num.replica.fetchers=4                        # Parallel fetcher threads
replica.fetch.max.bytes=1048576              # 1MB per fetch
replica.fetch.min.bytes=1                    # Fetch immediately
replica.lag.time.max.ms=10000                # 10s max lag to stay in ISR
replica.high.watermark.checkpoint.interval.ms=5000  # Checkpoint frequency
```

**Impact:**
- More fetchers = faster replication
- Larger fetch size = better throughput
- Lower lag timeout = stricter ISR membership

### Cross-Datacenter Replication

**Patterns for multi-DC setup:**

**1. Active-Passive (DR):**

```
Primary DC (us-east):
  - Topic: orders (RF=3)
  - Producers write here
  - Consumers read here

Secondary DC (us-west):
  - MirrorMaker replicates orders → orders-replica
  - Standby for failover
```

**2. Active-Active (Multi-Master):**

```
DC1:
  - Topic: orders-dc1 (local writes)
  - Replicate to DC2

DC2:
  - Topic: orders-dc2 (local writes)
  - Replicate to DC1

Consumers:
  - Read from both topics
  - Handle duplicates/conflicts
```

**Using Kafka MirrorMaker 2:**

```properties
# mm2.properties
clusters = primary, backup
primary.bootstrap.servers = primary-kafka:9092
backup.bootstrap.servers = backup-kafka:9092

primary->backup.enabled = true
primary->backup.topics = orders, payments

# Replication settings
replication.factor = 3
sync.topic.configs.enabled = true
```

### Monitoring and Alerting

```csharp
public class ReplicationMonitoring
{
    public async Task MonitorClusterHealth()
    {
        var adminClient = new AdminClientBuilder(config).Build();
        
        // Get cluster metadata
        var metadata = adminClient.GetMetadata(TimeSpan.FromSeconds(10));
        
        _logger.LogInformation($"Cluster ID: {metadata.ClusterId}");
        _logger.LogInformation($"Brokers: {metadata.Brokers.Count}");
        
        // Check each topic
        foreach (var topic in metadata.Topics)
        {
            var totalPartitions = topic.Partitions.Count;
            var underReplicated = 0;
            var noLeader = 0;
            
            foreach (var partition in topic.Partitions)
            {
                // Check under-replication
                if (partition.InSyncReplicas.Length < partition.Replicas.Length)
                {
                    underReplicated++;
                    _logger.LogWarning(
                        $"Topic {topic.Topic}, Partition {partition.PartitionId}: " +
                        $"Under-replicated ({partition.InSyncReplicas.Length}/" +
                        $"{partition.Replicas.Length} ISR)");
                }
                
                // Check leader
                if (partition.Leader == -1)
                {
                    noLeader++;
                    _logger.LogError(
                        $"Topic {topic.Topic}, Partition {partition.PartitionId}: " +
                        $"No leader!");
                }
            }
            
            // Emit metrics
            _metrics.RecordGauge("kafka.under_replicated_partitions", 
                underReplicated, 
                new[] { $"topic:{topic.Topic}" });
            
            _metrics.RecordGauge("kafka.partitions_without_leader", 
                noLeader,
                new[] { $"topic:{topic.Topic}" });
            
            // Alert if critical
            if (noLeader > 0)
            {
                await _alertService.AlertAsync(
                    $"CRITICAL: {noLeader} partitions in {topic.Topic} have no leader!");
            }
            else if (underReplicated > 0)
            {
                await _alertService.AlertAsync(
                    $"WARNING: {underReplicated}/{totalPartitions} partitions in " +
                    $"{topic.Topic} are under-replicated");
            }
        }
    }
    
    public async Task MonitorBrokerHealth()
    {
        var adminClient = new AdminClientBuilder(config).Build();
        var metadata = adminClient.GetMetadata(TimeSpan.FromSeconds(10));
        
        foreach (var broker in metadata.Brokers)
        {
            _logger.LogInformation(
                $"Broker {broker.BrokerId}: {broker.Host}:{broker.Port}");
            
            // Count partitions by role
            var leaderCount = 0;
            var replicaCount = 0;
            
            foreach (var topic in metadata.Topics)
            {
                foreach (var partition in topic.Partitions)
                {
                    if (partition.Leader == broker.BrokerId)
                        leaderCount++;
                    
                    if (partition.Replicas.Contains(broker.BrokerId))
                        replicaCount++;
                }
            }
            
            _logger.LogInformation(
                $"  Leader for {leaderCount} partitions");
            _logger.LogInformation(
                $"  Replica for {replicaCount} partitions");
            
            _metrics.RecordGauge("kafka.broker.leader_count", 
                leaderCount,
                new[] { $"broker:{broker.BrokerId}" });
        }
    }
}
```

### Disaster Recovery Procedures

**Scenario 1: Single broker failure:**

```
1. Verify automatic failover occurred
2. Check under-replicated partitions
3. Monitor ISR recovery
4. Restore failed broker or provision new one
5. Wait for replicas to catch up
6. Verify all partitions back to RF
```

**Scenario 2: Multiple broker failures:**

```
1. Assess impact (check partitions without leaders)
2. Restore brokers in priority order (leaders first)
3. If data loss acceptable: enable unclean leader election temporarily
4. If data loss unacceptable: wait for ISR member to recover
5. Monitor consumer lag during recovery
6. Verify data integrity after recovery
```

**Scenario 3: Complete cluster failure:**

```
1. Restore from backups if available
2. Restart brokers in controlled order
3. Verify topic metadata
4. Check consumer group offsets
5. Validate data integrity
6. Resume production traffic gradually
7. Monitor for anomalies
```
