## Introduction

Apache Kafka is built around a fundamentally different architecture than traditional message queues. At its core, Kafka uses an append-only log structure divided into topics and partitions. Understanding this architecture is essential for designing scalable, high-throughput event streaming systems.

Unlike RabbitMQ's push-based model with exchanges and queues, Kafka uses topics as logical channels for publishing events. Each topic is subdivided into partitions—immutable, ordered sequences of messages. This design enables Kafka to achieve exceptional throughput and horizontal scalability.

## Key Concepts Summary

### Topics: Logical Channels for Events

A **topic** in Kafka is a named feed or category of messages. Topics are the primary abstraction for organizing event streams:

```
Topic: "user-registrations"
  - All events related to user registration flow
  - Multiple producers can write to this topic
  - Multiple consumer groups can read from this topic
```

Key characteristics:
- Topics are multi-producer, multi-consumer
- Messages are retained based on configured retention policy (time or size)
- Topics are created with a specific number of partitions and replication factor

### Partitions: The Unit of Parallelism

Each topic is divided into one or more **partitions**. A partition is:
- An ordered, immutable sequence of messages
- Continuously appended to (like a log file)
- Assigned a unique sequential ID called an **offset**

```
Topic: "orders" (3 partitions)

Partition 0: [msg-0, msg-1, msg-2, msg-3, ...]  ← offset increases →
Partition 1: [msg-0, msg-1, msg-2, ...]
Partition 2: [msg-0, msg-1, msg-2, msg-3, msg-4, ...]
```

**Why partitions matter:**
- **Parallelism**: Each partition can be consumed independently by different consumer instances
- **Scalability**: Partitions are distributed across multiple brokers in the cluster
- **Ordering**: Messages within a single partition are strictly ordered
- **Throughput**: More partitions = more parallel producers and consumers

### Message Ordering Guarantees

Kafka provides **strict ordering guarantees within a partition**, but **no ordering guarantees across partitions**:

```csharp
// Within Partition 0: GUARANTEED ORDER
Event 1: UserCreated (timestamp: 10:00:00)
Event 2: UserProfileUpdated (timestamp: 10:00:01)
Event 3: UserVerified (timestamp: 10:00:02)

// Across partitions: NO ORDER GUARANTEE
Partition 0: Event A (timestamp: 10:00:00)
Partition 1: Event B (timestamp: 09:59:59)  ← might be consumed AFTER Event A
```

**Design implications:**
- If order matters, related messages must go to the same partition
- Use message keys to control partition assignment
- Single partition = ordered but limited throughput
- Multiple partitions = high throughput but no global ordering

### Partition Key Strategy

Producers can specify a **partition key** when publishing messages. Kafka uses this key to determine which partition receives the message:

```csharp
// .NET Kafka producer example
var message = new Message<string, Order>
{
    Key = order.UserId,     // Partition key: all messages for same user → same partition
    Value = order
};

await producer.ProduceAsync("orders", message);
```

**Partition assignment strategies:**

1. **Key-based partitioning** (default when key is provided):
   - `partition = hash(key) % number_of_partitions`
   - Same key always goes to same partition
   - Ensures ordering for related events

2. **Round-robin** (when no key provided):
   - Messages distributed evenly across partitions
   - No ordering guarantees
   - Maximum throughput

3. **Custom partitioner**:
   - Implement custom logic for partition selection
   - E.g., route based on geographic region, message type, etc.

```csharp
// Example: Ordering matters for user events
// All events for userId "123" will go to the same partition
await producer.ProduceAsync("user-events", new Message<string, UserEvent>
{
    Key = "user-123",
    Value = new UserEvent { Type = "ProfileUpdated", UserId = "123" }
});

// Example: No ordering needed, maximize throughput
// Events distributed round-robin across partitions
await producer.ProduceAsync("log-events", new Message<Null, LogEvent>
{
    Key = null,  // No key = round-robin
    Value = new LogEvent { Level = "INFO", Message = "Processing complete" }
});
```

### Partition Count Considerations

Choosing the right number of partitions involves trade-offs:

**More partitions:**
- ✅ Higher throughput (more parallel producers/consumers)
- ✅ Better load distribution across brokers
- ❌ More metadata overhead
- ❌ More open file handles on brokers
- ❌ Longer leader election time

**Fewer partitions:**
- ✅ Lower overhead and resource usage
- ✅ Simpler to manage
- ❌ Lower maximum throughput
- ❌ Less parallelism for consumers

**General guidelines:**
- Start with topic throughput requirements: `partitions = target_throughput / single_partition_throughput`
- Single partition typically handles 10-30 MB/s (depends on hardware)
- Consider consumer parallelism: at most one consumer per partition in a consumer group
- You can increase partition count later, but never decrease it (without recreating the topic)

### Partition Assignment Algorithm

When producing with a key, Kafka uses the default partitioner:

```csharp
public class DefaultPartitioner
{
    public int GetPartition(string key, int numPartitions)
    {
        // MurmurHash2 algorithm
        var hash = MurmurHash2(Encoding.UTF8.GetBytes(key));
        return Math.Abs(hash) % numPartitions;
    }
}

// Example: Topic with 5 partitions
// Key "user-123" → hash → partition 2
// Key "user-456" → hash → partition 4
// Key "user-789" → hash → partition 2 (same as user-123)
```

**Implications:**
- **Deterministic**: Same key always goes to same partition
- **Uniform distribution**: Keys distributed evenly (with good hash function)
- **No control over which partition**: Can't force specific keys to specific partitions
- **Repartitioning changes everything**: Adding partitions changes hash distribution

### Custom Partitioners

Implement custom partitioning logic for specific requirements:

```csharp
public class GeographicPartitioner : IPartitioner
{
    public int Partition<TKey, TValue>(
        string topic,
        TKey key,
        ReadOnlySpan<byte> keyBytes,
        TValue val,
        ReadOnlySpan<byte> valBytes,
        int partitionCount)
    {
        var userId = key.ToString();
        var region = GetUserRegion(userId);
        
        return region switch
        {
            "us-east" => 0,
            "us-west" => 1,
            "eu" => 2,
            "asia" => 3,
            _ => Math.Abs(userId.GetHashCode()) % partitionCount
        };
    }
    
    private string GetUserRegion(string userId)
    {
        // Logic to determine region from user ID
        return "us-east";
    }
}

// Configure producer to use custom partitioner
var config = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    Partitioner = typeof(GeographicPartitioner)
};
```

**Use cases for custom partitioners:**
- Geographic routing (route by region)
- Priority lanes (VIP customers to specific partitions)
- Load balancing (avoid hot partitions)

### Partition Hotspots

**Problem:** Uneven load distribution causing performance bottlenecks

```
Topic: "user-events" (3 partitions)
Users per partition:
- Partition 0: 100,000 users → 10,000 events/sec
- Partition 1: 50,000 users → 5,000 events/sec
- Partition 2: 10,000 users → 1,000 events/sec

Result: Partition 0 is a hotspot!
```

**Causes:**
- Popular keys (celebrity users, viral content)
- Poor key choice (all events use same key)
- Insufficient partitions

**Solutions:**

```csharp
// 1. Add suffix to spread popular keys
public string GetPartitionKey(string userId)
{
    if (IsPopularUser(userId))
    {
        // Spread across multiple partitions
        var suffix = Random.Shared.Next(0, 10);
        return $"{userId}-{suffix}";
    }
    return userId;
}

// 2. Use composite keys
public string GetPartitionKey(Order order)
{
    // Combine multiple fields for better distribution
    return $"{order.CustomerId}:{order.Region}:{order.Category}";
}

// 3. Monitor partition sizes
public async Task MonitorPartitionSkew()
{
    var adminClient = new AdminClientBuilder(config).Build();
    var metadata = adminClient.GetMetadata("user-events", TimeSpan.FromSeconds(10));
    
    foreach (var partition in metadata.Topics[0].Partitions)
    {
        var watermarks = consumer.GetWatermarkOffsets(
            new TopicPartition("user-events", partition.PartitionId));
        
        var messageCount = watermarks.High.Value - watermarks.Low.Value;
        _logger.LogInformation($"Partition {partition.PartitionId}: {messageCount} messages");
    }
}
```

### Partition Ordering Patterns

**Pattern 1: Strict Per-Entity Ordering**

```csharp
// All events for same order go to same partition
public async Task PublishOrderEvent(OrderEvent evt)
{
    await _producer.ProduceAsync("orders", new Message<string, OrderEvent>
    {
        Key = evt.OrderId,  // Ensures ordering per order
        Value = evt
    });
}

// Consumer processes events for each order in sequence
```

**Pattern 2: Partial Ordering (Time-Bucketed)**

```csharp
// Group events by time bucket for parallelism
public string GetTimeBasedKey(Event evt, TimeSpan bucketSize)
{
    var bucket = evt.Timestamp.Ticks / bucketSize.Ticks;
    return $"{evt.EntityId}:{bucket}";
}

// Example: 1-hour buckets
var key = GetTimeBasedKey(order, TimeSpan.FromHours(1));
// "order-123:2024-02-05-10" (10am-11am bucket)
// "order-123:2024-02-05-11" (11am-12pm bucket)
```

**Pattern 3: No Ordering (Maximum Throughput)**

```csharp
// No key = round-robin distribution
await _producer.ProduceAsync("logs", new Message<Null, LogEntry>
{
    Key = null,  // Round-robin across all partitions
    Value = logEntry
});
```

### Managing Partition Growth

**Increasing partition count:**

```bash
# Add partitions (can only increase, never decrease)
kafka-topics --alter \
  --topic orders \
  --partitions 12 \
  --bootstrap-server localhost:9092
```

```csharp
// Using AdminClient
var adminClient = new AdminClientBuilder(config).Build();

await adminClient.CreatePartitionsAsync(new[]
{
    new PartitionsSpecification
    {
        Topic = "orders",
        IncreaseTo = 12
    }
});
```

**Impact of adding partitions:**
- **Existing messages**: Stay in original partitions
- **New messages**: Distributed across all partitions (including new ones)
- **Partition assignment**: Changes for all keys (hash distribution changes)
- **Consumer rebalancing**: Triggered for all consumer groups

**Warning: Key-based partitioning breaks:**

```
Before (6 partitions):
Key "user-123" → hash % 6 = partition 2

After (12 partitions):
Key "user-123" → hash % 12 = partition 5 (different!)

Result: No longer ordered per user!
```

**Mitigation strategies:**
1. Over-partition initially (anticipate growth)
2. Use consistent hashing (custom partitioner)
3. Create new topic with more partitions and migrate
4. Accept temporary disorder during transition

### Performance Benchmarking

```csharp
public class PartitionPerformanceTest
{
    public async Task BenchmarkThroughput()
    {
        var config = new ProducerConfig
        {
            BootstrapServers = "localhost:9092",
            LingerMs = 10,
            BatchSize = 16384,
            CompressionType = CompressionType.Lz4
        };
        
        var producer = new ProducerBuilder<string, byte[]>(config).Build();
        var message = new byte[1024]; // 1KB message
        
        var sw = Stopwatch.StartNew();
        var messageCount = 100_000;
        
        // Test single partition
        for (int i = 0; i < messageCount; i++)
        {
            await producer.ProduceAsync("test-1-partition", 
                new Message<string, byte[]> { Key = "fixed", Value = message });
        }
        
        sw.Stop();
        var throughputSingle = messageCount / sw.Elapsed.TotalSeconds;
        
        // Test multiple partitions (round-robin)
        sw.Restart();
        for (int i = 0; i < messageCount; i++)
        {
            await producer.ProduceAsync("test-12-partitions", 
                new Message<string, byte[]> { Key = null, Value = message });
        }
        
        sw.Stop();
        var throughputMulti = messageCount / sw.Elapsed.TotalSeconds;
        
        _logger.LogInformation($"Single partition: {throughputSingle:F0} msg/sec");
        _logger.LogInformation($"12 partitions: {throughputMulti:F0} msg/sec");
    }
}
```

### Monitoring Partitions

```csharp
public class PartitionMonitoring
{
    public async Task MonitorPartitionHealth()
    {
        var adminClient = new AdminClientBuilder(config).Build();
        var metadata = adminClient.GetMetadata("orders", TimeSpan.FromSeconds(10));
        
        foreach (var partition in metadata.Topics[0].Partitions)
        {
            // Check partition leadership
            if (partition.Leader == -1)
            {
                _logger.LogError($"Partition {partition.PartitionId} has no leader!");
            }
            
            // Check replica count
            if (partition.Replicas.Length < partition.InSyncReplicas.Length)
            {
                _logger.LogWarning(
                    $"Partition {partition.PartitionId} under-replicated: " +
                    $"{partition.InSyncReplicas.Length}/{partition.Replicas.Length} ISR");
            }
            
            // Check partition lag
            var watermarks = consumer.GetWatermarkOffsets(
                new TopicPartition("orders", partition.PartitionId));
            
            var lagMessages = watermarks.High.Value - watermarks.Low.Value;
            
            if (lagMessages > 1_000_000)
            {
                _logger.LogWarning(
                    $"Partition {partition.PartitionId} has high lag: {lagMessages} messages");
            }
        }
    }
}
```

## Self-Check Questions

1. What is the difference between a topic and a partition in Kafka?
2. Why does Kafka guarantee ordering within a partition but not across partitions?
3. How does Kafka decide which partition a message goes to when a partition key is provided?
4. When would you use round-robin partitioning vs key-based partitioning?
5. What are the trade-offs of having 10 partitions vs 100 partitions for a topic?
6. Can you decrease the number of partitions for an existing topic? Why or why not?

**Answers:**
1. Topic = logical channel for messages; Partition = ordered, immutable log segment within a topic
2. Each partition is independent; no global coordinator to order across partitions
3. Uses hash function: `partition = hash(key) % number_of_partitions`
4. Round-robin for maximum throughput without ordering; key-based for ordering related messages
5. Fewer partitions = simpler, less overhead, but lower max throughput; More partitions = higher throughput, but more overhead and complexity
6. No - decreasing partitions would break key-based routing and require data migration

## Key Takeaways

- **Topics** organize event streams into logical channels
- **Partitions** enable parallelism and horizontal scalability
- **Ordering** guaranteed within partition, not across partitions
- **Partition keys** control message placement (same key → same partition)
- **Partition count** determines maximum consumer parallelism
- **Choose wisely:** Can increase partitions later, but never decrease
- **Hotspots** occur with poor key distribution
- **Custom partitioners** enable advanced routing logic
- **Monitor** partition distribution and lag for performance
