---

## Introduction

**Offsets** are the heart of Kafka's consumption model. Unlike traditional message queues where messages are deleted after acknowledgment, Kafka retains all messages and uses offsets to track each consumer group's position in each partition. This simple yet powerful mechanism enables features like replay, parallel processing, and resilient consumption.

Understanding offset management is critical for building reliable consumers. Improper offset handling can lead to duplicate processing, message loss, or consumer group lag. This lesson explores offset semantics, commit strategies, and best practices.

## Key Concepts Summary

### What are Offsets?

An **offset** is a unique, sequential ID assigned to each message within a partition. Offsets:
- Start at 0 and increase monotonically
- Are partition-specific (each partition has independent offsets)
- Never decrease (except during log compaction or retention cleanup)
- Act as a "bookmark" for consumer position

```
Partition 0:
Offset:  0    1    2    3    4    5    6    7
Message: [A] [B] [C] [D] [E] [F] [G] [H] ...
                             ↑
                    Consumer last committed: offset 4
                    Next read: offset 5
```

**Offset types:**
- **Current offset**: The next message to be read by the consumer
- **Committed offset**: The last successfully processed offset stored by Kafka
- **Log end offset**: The highest offset in the partition (latest message)
- **High watermark**: Highest offset replicated to all in-sync replicas

### Offset Storage

Kafka stores consumer group offsets in an internal topic called `__consumer_offsets`:

```
Consumer Group: "order-processors"
  Topic: "orders", Partition: 0 → Committed Offset: 1523
  Topic: "orders", Partition: 1 → Committed Offset: 1489
  Topic: "orders", Partition: 2 → Committed Offset: 1507
```

**Why internal storage?**
- Offsets are replicated and fault-tolerant
- Centralized tracking across the cluster
- Enables Kafka to manage consumer group state
- Automatic offset expiration through compaction

**Legacy note:** Older Kafka versions (< 0.9) stored offsets in ZooKeeper. Modern systems always use the internal Kafka topic.

### Offset Commit Strategies

#### 1. Automatic Commit (Simplest, Least Control)

```csharp
var config = new ConsumerConfig
{
    GroupId = "auto-commit-group",
    BootstrapServers = "localhost:9092",
    EnableAutoCommit = true,              // Enable auto-commit
    AutoCommitIntervalMs = 5000           // Commit every 5 seconds
};

using var consumer = new ConsumerBuilder<string, Order>(config).Build();
consumer.Subscribe("orders");

while (true)
{
    var result = consumer.Consume(cancellationToken);
    
    // Process message
    await ProcessOrder(result.Message.Value);
    
    // Offset is automatically committed every 5 seconds
}
```

**Characteristics:**
- Offsets committed automatically at regular intervals
- Simplest to implement
- ⚠️ Risk: Messages between last commit and crash may be reprocessed (at-least-once)
- ⚠️ Risk: If processing fails after poll but before next commit, message is lost (at-most-once)

**When to use:**
- Low-stakes data where occasional duplicates or losses are acceptable
- Idempotent processing logic
- Rapid prototyping

#### 2. Manual Commit - Synchronous (Maximum Control, Lower Throughput)

```csharp
var config = new ConsumerConfig
{
    GroupId = "manual-commit-group",
    BootstrapServers = "localhost:9092",
    EnableAutoCommit = false              // Disable auto-commit
};

using var consumer = new ConsumerBuilder<string, Order>(config).Build();
consumer.Subscribe("orders");

while (true)
{
    var result = consumer.Consume(cancellationToken);
    
    try
    {
        // Process message
        await ProcessOrder(result.Message.Value);
        
        // Explicitly commit after successful processing
        consumer.Commit(result);          // Synchronous commit
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Failed to process order at offset {Offset}", result.Offset);
        // Don't commit - message will be reprocessed
    }
}
```

**Characteristics:**
- Commit only after successful processing
- Blocks until Kafka confirms the commit
- ✅ Guarantees at-least-once delivery
- ⚠️ Lower throughput due to blocking

**When to use:**
- Critical data where duplicates are acceptable but loss is not
- Financial transactions, audit logs
- When you need confirmation of offset commit

#### 3. Manual Commit - Asynchronous (Balance of Control and Throughput)

```csharp
var config = new ConsumerConfig
{
    GroupId = "async-commit-group",
    BootstrapServers = "localhost:9092",
    EnableAutoCommit = false
};

using var consumer = new ConsumerBuilder<string, Order>(config).Build();
consumer.Subscribe("orders");

while (true)
{
    var result = consumer.Consume(cancellationToken);
    
    try
    {
        await ProcessOrder(result.Message.Value);
        
        // Asynchronous commit with callback
        consumer.CommitAsync(result, (result, error) =>
        {
            if (error != null)
            {
                logger.LogWarning("Commit failed: {Error}", error);
            }
        });
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Failed to process order");
    }
}
```

**Characteristics:**
- Non-blocking commit
- Higher throughput than synchronous
- ⚠️ Risk: Commit may fail silently (need callback handling)
- ⚠️ Risk: Rebalancing may occur before commit completes

**When to use:**
- High-throughput scenarios where blocking is unacceptable
- When idempotent processing can handle potential duplicates

#### 4. Batch Commit (Optimized for Throughput)

```csharp
var config = new ConsumerConfig
{
    GroupId = "batch-commit-group",
    BootstrapServers = "localhost:9092",
    EnableAutoCommit = false
};

using var consumer = new ConsumerBuilder<string, Order>(config).Build();
consumer.Subscribe("orders");

const int batchSize = 100;
int messageCount = 0;

while (true)
{
    var result = consumer.Consume(cancellationToken);
    
    await ProcessOrder(result.Message.Value);
    messageCount++;
    
    // Commit every 100 messages
    if (messageCount % batchSize == 0)
    {
        consumer.Commit(result);
        logger.LogInformation("Committed batch at offset {Offset}", result.Offset);
    }
}
```

**Characteristics:**
- Reduces commit overhead
- Balances throughput and reliability
- ⚠️ Risk: Up to `batchSize` messages may be reprocessed on failure

**When to use:**
- High-throughput scenarios with idempotent processing
- When commit overhead is a bottleneck

### Auto Offset Reset Behavior

The `auto.offset.reset` configuration determines what happens when a consumer group has no committed offset (first time consuming, or offset expired):

```csharp
var config = new ConsumerConfig
{
    GroupId = "new-consumer-group",
    BootstrapServers = "localhost:9092",
    AutoOffsetReset = AutoOffsetReset.Earliest  // or Latest, or Error
};
```

**Options:**

1. **`earliest`**: Start from the beginning of the partition
   - Read all available messages
   - Use for: Historical replay, batch processing, catching up

2. **`latest`**: Start from the end of the partition
   - Read only new messages arriving after consumer starts
   - Use for: Real-time processing, when historical data isn't needed

3. **`none`** (or `error`): Throw an exception
   - Force explicit offset management
   - Use for: Production systems where offset loss is critical

**Example scenario:**

```
Partition has messages with offsets: 0 to 1000

Consumer Group "new-group" (no committed offset)
- AutoOffsetReset.Earliest → starts at offset 0
- AutoOffsetReset.Latest → starts at offset 1001 (next new message)
- AutoOffsetReset.None → throws exception
```

### Seeking to Specific Offsets

You can manually control consumer position using seek operations:

```csharp
using var consumer = new ConsumerBuilder<string, Order>(config).Build();
consumer.Subscribe("orders");

// Wait for partition assignment
consumer.Consume(TimeSpan.FromSeconds(1));

// Seek to beginning
consumer.Seek(new TopicPartitionOffset("orders", 0, Offset.Beginning));

// Seek to end
consumer.Seek(new TopicPartitionOffset("orders", 0, Offset.End));

// Seek to specific offset
consumer.Seek(new TopicPartitionOffset("orders", 0, new Offset(1500)));

// Seek backward by 100 messages from current position
var currentOffset = consumer.Position(new TopicPartition("orders", 0));
consumer.Seek(new TopicPartitionOffset("orders", 0, currentOffset - 100));
```

**Use cases:**
- **Replay**: Reprocess historical events for bug fixes or new features
- **Time-based seek**: Jump to offset based on timestamp
- **Error recovery**: Skip poison messages by seeking past them
- **Testing**: Reset to specific state for debugging

### Common Offset Issues and Solutions

#### Issue 1: Duplicate Processing

**Cause:** Consumer crashes after processing but before committing offset

**Solution:**
- Implement idempotent processing logic
- Use unique message IDs to deduplicate
- Consider exactly-once semantics (transactional consumers)

```csharp
// Idempotent processing example
public async Task ProcessOrderIdempotent(Order order)
{
    // Check if already processed
    if (await _repository.OrderExists(order.Id))
    {
        logger.LogInformation("Order {OrderId} already processed, skipping", order.Id);
        return;
    }
    
    // Process and save atomically
    await _repository.SaveOrder(order);
}
```

#### Issue 2: Message Loss

**Cause:** Auto-commit commits offset before processing completes

**Solution:**
- Disable auto-commit
- Commit manually after successful processing

#### Issue 3: Consumer Lag

**Cause:** Consumer processes slower than producer writes

**Monitoring:**
```csharp
var lag = consumer.GetWatermarkOffsets(new TopicPartition("orders", 0));
var currentOffset = consumer.Position(new TopicPartition("orders", 0));
var lagMessages = lag.High.Value - currentOffset;

logger.LogInformation("Consumer lag: {Lag} messages", lagMessages);
```

**Solutions:**
- Scale out consumer group (add more consumers)
- Optimize processing logic
- Increase partition count for more parallelism

### Transactional Offset Commits

**Exactly-once semantics with transactions:**

```csharp
public class TransactionalConsumer
{
    private readonly IConsumer<string, Order> _consumer;
    private readonly IProducer<string, OrderResult> _producer;
    
    public async Task ProcessTransactionally()
    {
        var producerConfig = new ProducerConfig
        {
            BootstrapServers = "localhost:9092",
            TransactionalId = "order-processor-1",  // Unique per instance
            EnableIdempotence = true
        };
        
        var producer = new ProducerBuilder<string, OrderResult>(producerConfig).Build();
        
        // Init transactions
        producer.InitTransactions(TimeSpan.FromSeconds(30));
        
        while (true)
        {
            var result = _consumer.Consume();
            
            try
            {
                // Begin transaction
                producer.BeginTransaction();
                
                // Process message
                var orderResult = await ProcessOrder(result.Message.Value);
                
                // Produce result
                await producer.ProduceAsync("order-results",
                    new Message<string, OrderResult>
                    {
                        Key = orderResult.OrderId,
                        Value = orderResult
                    });
                
                // Commit offsets as part of transaction
                producer.SendOffsetsToTransaction(
                    new[] {
                        new TopicPartitionOffset(
                            result.TopicPartition, 
                            result.Offset + 1)
                    },
                    _consumer.ConsumerGroupMetadata,
                    TimeSpan.FromSeconds(10));
                
                // Commit transaction (atomic: produce + offset commit)
                producer.CommitTransaction();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Transaction failed");
                producer.AbortTransaction();
                
                // Seek back to retry
                _consumer.Seek(result.TopicPartitionOffset);
            }
        }
    }
}
```

**Benefits:**
- Exactly-once processing guarantee
- Atomic consume-process-produce
- No duplicates, no message loss

**Trade-offs:**
- Lower throughput
- More complex error handling
- Requires Kafka 0.11+

### Offset Reset Strategies

**Handling invalid or out-of-range offsets:**

```csharp
public class OffsetResetHandler
{
    public void HandleOffsetOutOfRange()
    {
        var config = new ConsumerConfig
        {
            GroupId = "my-group",
            BootstrapServers = "localhost:9092",
            AutoOffsetReset = AutoOffsetReset.Earliest
        };
        
        var consumer = new ConsumerBuilder<string, Order>(config)
            .SetPartitionsAssignedHandler((c, partitions) =>
            {
                foreach (var partition in partitions)
                {
                    try
                    {
                        // Try to get committed offset
                        var committed = c.Committed(new[] { partition }, 
                            TimeSpan.FromSeconds(10));
                        
                        var offset = committed[0].Offset;
                        
                        if (offset == Offset.Unset)
                        {
                            _logger.LogInformation(
                                $"No committed offset for {partition}, " +
                                $"using auto.offset.reset policy");
                        }
                        else
                        {
                            _logger.LogInformation(
                                $"Resuming from offset {offset} for {partition}");
                        }
                    }
                    catch (KafkaException ex)
                    {
                        _logger.LogError(ex, "Error getting committed offset");
                    }
                }
            })
            .SetOffsetsCommittedHandler((c, offsets) =>
            {
                foreach (var offset in offsets.Offsets)
                {
                    if (offset.Error.IsError)
                    {
                        _logger.LogError(
                            $"Offset commit failed for {offset.TopicPartition}: " +
                            $"{offset.Error.Reason}");
                    }
                }
            })
            .Build();
        
        consumer.Subscribe("orders");
    }
}
```

### Time-Based Offset Seeking

**Seek to timestamp:**

```csharp
public class TimestampSeek
{
    public void SeekToTimestamp(DateTime targetTime)
    {
        var consumer = new ConsumerBuilder<string, Order>(config).Build();
        consumer.Subscribe("orders");
        
        // Trigger assignment
        consumer.Consume(TimeSpan.FromSeconds(1));
        
        // Get partitions
        var assignment = consumer.Assignment;
        
        // Seek each partition to timestamp
        var timestamp = new Timestamp(targetTime);
        
        var topicPartitionTimestamps = assignment
            .Select(tp => new TopicPartitionTimestamp(tp, timestamp))
            .ToList();
        
        var offsets = consumer.OffsetsForTimes(
            topicPartitionTimestamps, 
            TimeSpan.FromSeconds(10));
        
        foreach (var offset in offsets)
        {
            if (offset.Offset != Offset.Unset)
            {
                _logger.LogInformation(
                    $"Seeking partition {offset.Partition} to offset {offset.Offset}");
                consumer.Seek(offset);
            }
            else
            {
                _logger.LogWarning(
                    $"No offset found for timestamp in partition {offset.Partition}");
            }
        }
    }
}
```

**Use cases:**
- Disaster recovery (replay from specific time)
- Debugging (reproduce issues from timestamp)
- Data backfill (reprocess specific time range)

### Offset Commit Failure Handling

```csharp
public class RobustOffsetCommit
{
    public async Task CommitWithRetry(
        IConsumer<string, Order> consumer,
        ConsumeResult<string, Order> result,
        int maxRetries = 3)
    {
        for (int attempt = 1; attempt <= maxRetries; attempt++)
        {
            try
            {
                consumer.Commit(result);
                return; // Success
            }
            catch (KafkaException ex) when (ex.Error.Code == ErrorCode.RequestTimedOut)
            {
                if (attempt == maxRetries)
                {
                    _logger.LogError(
                        "Failed to commit offset after {Attempts} attempts", 
                        maxRetries);
                    throw;
                }
                
                _logger.LogWarning(
                    "Commit timeout, retry {Attempt}/{Max}", 
                    attempt, maxRetries);
                
                await Task.Delay(TimeSpan.FromSeconds(Math.Pow(2, attempt)));
            }
            catch (KafkaException ex) when (
                ex.Error.Code == ErrorCode.NotCoordinator ||
                ex.Error.Code == ErrorCode.NotCoordinatorForGroup)
            {
                _logger.LogWarning("Coordinator changed, retrying commit");
                await Task.Delay(1000);
            }
        }
    }
}
```

### Monitoring Offset Health

```csharp
public class OffsetMonitoring
{
    public async Task MonitorOffsetMetrics()
    {
        var consumer = new ConsumerBuilder<string, Order>(config).Build();
        consumer.Subscribe("orders");
        
        // Trigger assignment
        consumer.Consume(TimeSpan.FromSeconds(1));
        
        var metrics = new Dictionary<int, OffsetMetrics>();
        
        foreach (var partition in consumer.Assignment)
        {
            // Get watermarks (log start/end offsets)
            var watermarks = consumer.GetWatermarkOffsets(partition);
            
            // Get committed offset
            var committed = consumer.Committed(new[] { partition }, 
                TimeSpan.FromSeconds(10))[0];
            
            // Get current position
            var position = consumer.Position(partition);
            
            var metric = new OffsetMetrics
            {
                Partition = partition.Partition,
                LogStartOffset = watermarks.Low.Value,
                LogEndOffset = watermarks.High.Value,
                CommittedOffset = committed.Offset.Value,
                CurrentPosition = position,
                Lag = watermarks.High.Value - position,
                AvailableMessages = watermarks.High.Value - watermarks.Low.Value
            };
            
            metrics[partition.Partition] = metric;
            
            // Log warnings
            if (metric.Lag > 100000)
            {
                _logger.LogWarning(
                    $"High lag in partition {partition.Partition}: " +
                    $"{metric.Lag} messages");
            }
            
            if (metric.CurrentPosition < metric.LogStartOffset)
            {
                _logger.LogError(
                    $"Current position behind log start in partition {partition.Partition}");
            }
        }
        
        // Export to metrics system
        foreach (var (partition, metric) in metrics)
        {
            _metrics.RecordGauge($"kafka.consumer.lag", metric.Lag,
                new[] { $"partition:{partition}", "group:{config.GroupId}" });
        }
    }
}

public class OffsetMetrics
{
    public int Partition { get; set; }
    public long LogStartOffset { get; set; }
    public long LogEndOffset { get; set; }
    public long CommittedOffset { get; set; }
    public long CurrentPosition { get; set; }
    public long Lag { get; set; }
    public long AvailableMessages { get; set; }
}
```
