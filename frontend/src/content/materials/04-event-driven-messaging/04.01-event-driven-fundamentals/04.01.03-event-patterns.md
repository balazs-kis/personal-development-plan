# Lesson 3: Event Notification vs Event-Carried State Transfer

## Learning Objectives

By the end of this lesson, you will be able to:
- Distinguish between event notification and event-carried state transfer patterns
- Understand when to use each pattern
- Recognize the trade-offs between the two approaches
- Design events that follow the appropriate pattern for your use case

---

## Introduction

When designing events in an event-driven system, you face a fundamental choice: should the event contain just a notification that something happened, or should it carry all the data needed by consumers? This decision impacts coupling, message size, and system evolution. Understanding these two patterns helps you make informed architectural decisions.

## Key Concepts Summary

### Event Notification Pattern

**Definition:** An event notification contains only a reference (typically an ID) to the entity that changed. Consumers must query the source system to get the full details.

**Characteristics:**
- Minimal payload: usually just an ID or reference
- Consumers must make additional calls to get data
- Tighter coupling: consumers depend on source system availability
- Smaller message size
- Source of truth remains in the originating system

**Example:**
```csharp
// Event Notification: Only contains reference
public class OrderCreatedEvent
{
    public string OrderId { get; set; }  // Just the ID
    public DateTime OccurredAt { get; set; }
}

// Consumer must fetch details from source
public class EmailServiceHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Must query order service to get details
        var order = await _orderService.GetByIdAsync(evt.OrderId);
        
        // Now can send email with order details
        await SendOrderConfirmationEmailAsync(order);
    }
}

public class InventoryServiceHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Must query order service again
        var order = await _orderService.GetByIdAsync(evt.OrderId);
        
        // Process inventory update
        await ReserveInventoryAsync(order.Items);
    }
}
```

**Pros:**
- ✅ Small message size
- ✅ Single source of truth
- ✅ Always get latest data
- ✅ Easy to add new fields without breaking consumers

**Cons:**
- ❌ Additional network calls required
- ❌ Source system must be available
- ❌ Higher latency (multiple round trips)
- ❌ More load on source system
- ❌ Tighter coupling to source system

### Event-Carried State Transfer Pattern

**Definition:** An event carries all the data that consumers might need, making the event self-contained. Consumers don't need to query the source system.

**Characteristics:**
- Rich payload: contains all relevant data
- Self-contained: consumers don't need additional calls
- Looser coupling: consumers don't depend on source availability
- Larger message size
- Event becomes a snapshot of state at that point in time

**Example:**
```csharp
// Event-Carried State Transfer: Contains all needed data
public class OrderCreatedEvent
{
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    public string CustomerEmail { get; set; }
    public string CustomerName { get; set; }
    public List<OrderItemDto> Items { get; set; }
    public Address ShippingAddress { get; set; }
    public PaymentInfo PaymentInfo { get; set; }
    public decimal TotalAmount { get; set; }
    public DateTime CreatedAt { get; set; }
}

// Consumers can process without additional calls
public class EmailServiceHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // All data needed is in the event
        await SendOrderConfirmationEmailAsync(
            evt.CustomerEmail,
            evt.CustomerName,
            evt.OrderId,
            evt.Items,
            evt.TotalAmount
        );
    }
}

public class InventoryServiceHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Can process directly from event data
        await ReserveInventoryAsync(evt.Items);
    }
}

public class AnalyticsServiceHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Can analyze without querying source
        await TrackOrderCreatedAsync(
            evt.CustomerId,
            evt.TotalAmount,
            evt.CreatedAt
        );
    }
}
```

**Pros:**
- ✅ No additional network calls
- ✅ Works even if source system is down
- ✅ Lower latency (single message)
- ✅ Less load on source system
- ✅ Looser coupling
- ✅ Better for offline processing

**Cons:**
- ❌ Larger message size
- ❌ Data might become stale
- ❌ Duplication of data across events
- ❌ Harder to evolve (breaking changes affect all consumers)
- ❌ More storage needed

### Comparison Table

| Aspect | Event Notification | Event-Carried State Transfer |
|--------|-------------------|------------------------------|
| **Message Size** | Small | Large |
| **Network Calls** | Multiple (consumer queries source) | Single (event contains all) |
| **Coupling** | Tight (depends on source) | Loose (independent) |
| **Data Freshness** | Always current | Snapshot at event time |
| **Source System Load** | High (many queries) | Low (just publish) |
| **Availability Dependency** | High (source must be up) | Low (event is self-contained) |
| **Evolution** | Easy (add fields without breaking) | Hard (changes affect all consumers) |
| **Use Case** | When data changes frequently | When data is relatively stable |

### When to Use Each Pattern

#### Use Event Notification When:
- ✅ Data changes frequently and you want consumers to always get latest
- ✅ Message size is a concern (high-volume systems)
- ✅ Source system can handle the query load
- ✅ You want a single source of truth
- ✅ Data is too large to include in events
- ✅ You need to control access to sensitive data

**Example:** User profile updates - profile changes frequently, and you want consumers to always see the latest information.

#### Use Event-Carried State Transfer When:
- ✅ Data is relatively stable
- ✅ Source system might be unavailable
- ✅ You want to minimize latency
- ✅ You want loose coupling
- ✅ Consumers need to work offline
- ✅ You're building a data pipeline

**Example:** Order creation - order data doesn't change after creation, and multiple services need it independently.

### Hybrid Approach

You can combine both patterns:

```csharp
// Include essential data, but allow querying for more
public class OrderCreatedEvent
{
    // Essential data for most consumers
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    public List<OrderItemDto> Items { get; set; }
    public decimal TotalAmount { get; set; }
    
    // Reference for consumers who need more details
    public string OrderDetailsUrl { get; set; }  // Optional query endpoint
    
    public DateTime CreatedAt { get; set; }
}

// Most consumers use event data directly
public class InventoryHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Use data from event
        await ReserveInventoryAsync(evt.Items);
    }
}

// Some consumers might query for additional details
public class DetailedReportHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Use event data for basic processing
        await ProcessBasicInfoAsync(evt);
        
        // Query for additional details if needed
        if (needsDetailedInfo)
        {
            var details = await _orderService.GetDetailedInfoAsync(evt.OrderId);
            await ProcessDetailedInfoAsync(details);
        }
    }
}
```

### Best Practices

#### For Event Notification:
- Include enough context to make the query efficient
- Consider including version numbers to handle schema evolution
- Document what data consumers should query
- Monitor source system load

**Example:**
```csharp
// Good: Includes context for efficient queries
public class ProductUpdatedEvent
{
    public string ProductId { get; set; }
    public int Version { get; set; }
    public DateTime UpdatedAt { get; set; }
    public string UpdatedBy { get; set; }
    
    // Helps consumers construct efficient queries
    public string Category { get; set; } // For filtering
    public bool IsActive { get; set; } // For filtering
}

// Consumer can query efficiently
public class ProductCacheInvalidator
{
    public async Task HandleAsync(ProductUpdatedEvent evt)
    {
        // Efficient query with filter context
        if (evt.IsActive)
        {
            var product = await _productService.GetByIdAsync(evt.ProductId);
            await _cache.UpdateAsync(evt.ProductId, product);
        }
        else
        {
            await _cache.RemoveAsync(evt.ProductId);
        }
    }
}
```

#### For Event-Carried State Transfer:
- Include all data consumers need, but avoid unnecessary data
- Version your events to handle evolution
- Consider data retention policies
- Document event schema clearly
- Use event versioning for breaking changes

**Example:**
```csharp
// Good: Complete but focused data
public class OrderShippedEvent
{
    // Event metadata
    public string EventId { get; set; }
    public int Version { get; set; } = 2;
    public DateTime OccurredAt { get; set; }
    
    // Core data all consumers need
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    public string TrackingNumber { get; set; }
    public string Carrier { get; set; }
    public DateTime EstimatedDelivery { get; set; }
    
    // Customer data (avoid additional queries)
    public string CustomerEmail { get; set; }
    public string CustomerName { get; set; }
    
    // Shipping address (consumers need this)
    public Address ShippingAddress { get; set; }
    
    // Order summary (avoid querying for these)
    public int ItemCount { get; set; }
    public decimal OrderTotal { get; set; }
}

// Bad: Too much unnecessary data
public class OrderShippedEventBad
{
    // ... essential fields ...
    
    // Unnecessary - consumers don't need this
    public List<OrderItem> Items { get; set; }
    public List<OrderHistory> OrderHistory { get; set; }
    public CustomerProfile FullCustomerProfile { get; set; }
    public List<PaymentTransaction> PaymentHistory { get; set; }
}
```

### Schema Evolution

**Backward Compatible Changes:**
```csharp
// Version 1
public class ProductCreatedEventV1
{
    public string ProductId { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
}

// Version 2 - Backward compatible (added optional field)
public class ProductCreatedEventV2
{
    public string ProductId { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    public string Description { get; set; } = string.Empty; // New, optional
}

// Version 3 - Still backward compatible
public class ProductCreatedEventV3
{
    public string ProductId { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    public string Description { get; set; } = string.Empty;
    public List<string> Tags { get; set; } = new(); // New, optional with default
}
```

**Breaking Changes Require New Event Type:**
```csharp
// Original event
public class OrderCreatedEvent
{
    public string OrderId { get; set; }
    public decimal TotalAmount { get; set; }
}

// Breaking change: TotalAmount split into subtotal and tax
// Create new event type instead
public class OrderCreatedV2Event
{
    public string OrderId { get; set; }
    public decimal Subtotal { get; set; }
    public decimal Tax { get; set; }
    public decimal TotalAmount { get; set; }
}

// Support both events during migration
public class OrderProcessor
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Handle old format
        await ProcessOrderAsync(evt.OrderId, evt.TotalAmount, 0);
    }
    
    public async Task HandleAsync(OrderCreatedV2Event evt)
    {
        // Handle new format
        await ProcessOrderAsync(evt.OrderId, evt.Subtotal, evt.Tax);
    }
}
```

### Performance Considerations

**Event Notification - Load Management:**
```csharp
// Problem: Thundering herd - all consumers query at once
public class ProductUpdatedEvent
{
    public string ProductId { get; set; }
}

// Multiple consumers all query immediately
public class Consumer1
{
    public async Task HandleAsync(ProductUpdatedEvent evt)
    {
        var product = await _productService.GetByIdAsync(evt.ProductId); // Query 1
        // ...
    }
}

public class Consumer2
{
    public async Task HandleAsync(ProductUpdatedEvent evt)
    {
        var product = await _productService.GetByIdAsync(evt.ProductId); // Query 2
        // ...
    }
}

// Solution: Use caching or include essential data
public class ProductUpdatedEventWithCache
{
    public string ProductId { get; set; }
    public string CacheKey { get; set; }
}

public class CachingConsumer
{
    public async Task HandleAsync(ProductUpdatedEventWithCache evt)
    {
        // Check cache first
        var product = await _cache.GetAsync(evt.CacheKey);
        if (product == null)
        {
            product = await _productService.GetByIdAsync(evt.ProductId);
            await _cache.SetAsync(evt.CacheKey, product, TimeSpan.FromMinutes(5));
        }
        // ...
    }
}
```

**Event-Carried State Transfer - Size Management:**
```csharp
// Problem: Event too large
public class OrderCreatedEventTooLarge
{
    public string OrderId { get; set; }
    // ... many fields ...
    public byte[] ProductImages { get; set; } // 10MB!
    public List<ReviewDto> ProductReviews { get; set; } // 1000s of items
}

// Solution: Store large data separately, reference in event
public class OrderCreatedEventOptimized
{
    public string OrderId { get; set; }
    // ... essential fields ...
    
    // References to large data
    public string ProductImagesUrl { get; set; }
    public string ReviewsUrl { get; set; }
}

// Consumer fetches large data only if needed
public class OrderProcessor
{
    public async Task HandleAsync(OrderCreatedEventOptimized evt)
    {
        // Process order without large data
        await ProcessBasicOrderAsync(evt);
        
        // Only fetch images if needed
        if (_requiresImages)
        {
            var images = await _httpClient.GetAsync(evt.ProductImagesUrl);
        }
    }
}
```

```csharp
    public DateTime UpdatedAt { get; set; }
}
```

**Reasoning:** Price changes frequently in competitive environments. Consumers should query for latest price to avoid showing stale data. Include new price to allow quick filtering without querying.

**3. ProductStockLevelChanged → Event Notification**

```csharp
    public DateTime UpdatedAt { get; set; }
}
```
**Reasoning:** Stock changes very frequently (every order). Consumers need latest count. Include essential data (in stock flag) but require queries for detailed inventory info.

**4. ProductDiscontinued → Event-Carried State Transfer**
```csharp
public class ProductDiscontinuedEvent
{
    public string ProductId { get; set; }
    public string Name { get; set; }
    public string Category { get; set; }
    public string ReplacementProductId { get; set; }
    public string Reason { get; set; }
    public DateTime DiscontinuedAt { get; set; }
}
```
**Reasoning:** Product discontinuation is final and rare. Multiple systems need to react (remove from search, update recommendations, notify customers). Self-contained event enables all consumers to act independently.

## Self-Check Questions

1. What's the key difference between event notification and event-carried state transfer?
   - **Answer:** Event notification contains only references (like IDs), requiring consumers to query for details. Event-carried state transfer includes all needed data in the event itself, making it self-contained.

2. When would you choose event notification over event-carried state transfer?
   - **Answer:** When data changes frequently (want latest), message size is critical, source system can handle query load, you need a single source of truth, or data is too large/sensitive to include in events.

3. What are the main trade-offs between the two patterns?
   - **Answer:**
     - **Event Notification:** Smaller messages, fresher data, but requires source availability, additional network calls, higher latency
     - **Event-Carried State Transfer:** No additional calls, works when source is down, lower latency, but larger messages, potential stale data, harder to evolve

4. How does event-carried state transfer help with temporal decoupling?
   - **Answer:** By including all needed data, consumers can process events independently without querying the source system. This means consumers can work even if the source is unavailable, enabling true temporal and operational decoupling.

5. What challenges arise when evolving event schemas in event-carried state transfer?
   - **Answer:** Changes can break existing consumers, requiring careful versioning strategies. All consumers must be updated to handle schema changes. Must maintain backward compatibility or coordinate migration of all handlers.

**Additional Questions:**

6. How do you handle the "thundering herd" problem with event notification?
   - **Answer:** Use caching between the event and queries, stagger consumer processing with delays, include essential data in the event to reduce queries, or use a shared cache that the first consumer populates.

7. What's the impact of network partitions on each pattern?
   - **Answer:** Event notification fails if source system is unreachable during processing. Event-carried state transfer continues to work since all data is in the event, making it more resilient to network issues.

8. How do you decide what data to include in an event-carried state transfer event?
   - **Answer:** Include data that: (a) multiple consumers need, (b) is relatively stable, (c) is reasonably sized, (d) is non-sensitive or properly secured, and (e) forms a coherent snapshot of state at that moment.

---

## Key Takeaways

- **Event Notification** contains only references; consumers query for details
- **Event-Carried State Transfer** includes all needed data in the event
- Event notification provides fresher data but requires source system availability
- Event-carried state transfer enables better decoupling but can lead to stale data
- Choose based on data stability, coupling requirements, and availability needs
- Hybrid approaches can combine benefits of both patterns
