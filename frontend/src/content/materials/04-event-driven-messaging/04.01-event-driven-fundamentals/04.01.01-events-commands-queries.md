# Lesson 1: Events vs Commands vs Queries

## Learning Objectives

By the end of this lesson, you will be able to:
- Distinguish between events, commands, and queries in event-driven systems
- Understand when to use each type of message
- Recognize the relationship between CQRS and event-driven architecture
- Apply the appropriate message type to different scenarios

---

## Introduction

In event-driven architecture, not all messages are created equal. Understanding the fundamental differences between events, commands, and queries is crucial for designing effective asynchronous communication patterns. This distinction forms the foundation of CQRS (Command Query Responsibility Segregation) and helps you make informed decisions about message design.

## Key Concepts Summary

### Commands

**Definition:** A command is a request to perform an action. It represents an intent to change state.

**Characteristics:**
- Imperative: "Do this"
- Addressed to a specific handler
- May succeed or fail
- Typically expects a response (acknowledgment or result)
- Should be idempotent when possible

**Example:**
```csharp
// Command: Request to create an order
public class CreateOrderCommand
{
    public string CustomerId { get; set; }
    public List<OrderItem> Items { get; set; }
    public decimal TotalAmount { get; set; }
}

// Command handler processes the command
public class CreateOrderCommandHandler
{
    public async Task<OrderCreatedResult> HandleAsync(CreateOrderCommand command)
    {
        // Perform the action
        var order = await _orderRepository.CreateAsync(command);
        return new OrderCreatedResult { OrderId = order.Id };
    }
}
```

**Naming Conventions:**
- Use imperative verbs: `CreateOrder`, `UpdateInventory`, `CancelSubscription`
- Include the entity being acted upon: `Order`, `User`, `Payment`
- Suffix with `Command`: `PlaceOrderCommand`, `UpdateUserProfileCommand`

**Idempotency:**
Commands should be idempotent when possible, meaning executing the same command multiple times produces the same result:

```csharp
public class UpdateUserEmailCommand
{
    public string UserId { get; set; }
    public string NewEmail { get; set; }
    public string IdempotencyKey { get; set; } // Unique key for this request
}

public class UpdateUserEmailCommandHandler
{
    public async Task<UserUpdatedResult> HandleAsync(UpdateUserEmailCommand command)
    {
        // Check if already processed
        if (await _processedCommands.ContainsAsync(command.IdempotencyKey))
        {
            return await _processedCommands.GetResultAsync(command.IdempotencyKey);
        }
        
        // Perform the update
        var user = await _userRepository.GetByIdAsync(command.UserId);
        user.Email = command.NewEmail;
        await _userRepository.UpdateAsync(user);
        
        var result = new UserUpdatedResult { UserId = user.Id, Success = true };
        
        // Store result for future idempotency checks
        await _processedCommands.StoreAsync(command.IdempotencyKey, result);
        
        return result;
    }
}
```

**Error Handling:**
Commands can fail, and handlers should provide clear error information:

```csharp
public class ProcessPaymentCommand
{
    public string OrderId { get; set; }
    public decimal Amount { get; set; }
    public string PaymentMethodId { get; set; }
}

public class ProcessPaymentCommandHandler
{
    public async Task<PaymentResult> HandleAsync(ProcessPaymentCommand command)
    {
        try
        {
            // Validate command
            if (command.Amount <= 0)
                return PaymentResult.Failure("Amount must be greater than zero");
            
            // Process payment
            var payment = await _paymentService.ProcessAsync(
                command.PaymentMethodId,
                command.Amount
            );
            
            return PaymentResult.Success(payment.TransactionId);
        }
        catch (InsufficientFundsException ex)
        {
            return PaymentResult.Failure("Insufficient funds", ex);
        }
        catch (PaymentDeclinedException ex)
        {
            return PaymentResult.Failure("Payment declined", ex);
        }
    }
}
```

### Queries

**Definition:** A query is a request for information. It does not change state.

**Characteristics:**
- Interrogative: "What is the state?"
- Read-only operation
- Should not have side effects
- Returns data, not an action result
- Can be cached safely

**Example:**
```csharp
// Query: Request for order information
public class GetOrderQuery
{
    public string OrderId { get; set; }
}

// Query handler returns data
public class GetOrderQueryHandler
{
    public async Task<OrderDto> HandleAsync(GetOrderQuery query)
    {
        // Read data without modifying state
        return await _orderRepository.GetByIdAsync(query.OrderId);
    }
}
```

**Naming Conventions:**
- Use interrogative verbs: `GetOrder`, `ListProducts`, `FindUser`
- Describe what data is being retrieved: `GetUserById`, `SearchProducts`, `ListOrdersByCustomer`
- Suffix with `Query`: `GetOrderByIdQuery`, `SearchProductsQuery`

**Caching:**
Queries are excellent candidates for caching since they don't modify state:

```csharp
public class GetUserProfileQuery
{
    public string UserId { get; set; }
}

public class GetUserProfileQueryHandler
{
    private readonly IDistributedCache _cache;
    private readonly IUserRepository _repository;
    
    public async Task<UserProfileDto> HandleAsync(GetUserProfileQuery query)
    {
        // Check cache first
        var cacheKey = $"user-profile:{query.UserId}";
        var cachedProfile = await _cache.GetStringAsync(cacheKey);
        
        if (!string.IsNullOrEmpty(cachedProfile))
        {
            return JsonSerializer.Deserialize<UserProfileDto>(cachedProfile);
        }
        
        // Cache miss - fetch from repository
        var profile = await _repository.GetProfileAsync(query.UserId);
        
        // Store in cache
        await _cache.SetStringAsync(
            cacheKey,
            JsonSerializer.Serialize(profile),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            }
        );
        
        return profile;
    }
}
```

**Pagination and Filtering:**
Queries often include parameters for filtering and pagination:

```csharp
public class SearchProductsQuery
{
    public string SearchTerm { get; set; }
    public string Category { get; set; }
    public decimal? MinPrice { get; set; }
    public decimal? MaxPrice { get; set; }
    public int PageNumber { get; set; } = 1;
    public int PageSize { get; set; } = 20;
    public string SortBy { get; set; } = "name";
    public bool SortDescending { get; set; } = false;
}

public class SearchProductsQueryHandler
{
    public async Task<PagedResult<ProductDto>> HandleAsync(SearchProductsQuery query)
    {
        var productsQuery = _dbContext.Products.AsQueryable();
        
        // Apply filters
        if (!string.IsNullOrEmpty(query.SearchTerm))
            productsQuery = productsQuery.Where(p => p.Name.Contains(query.SearchTerm));
        
        if (!string.IsNullOrEmpty(query.Category))
            productsQuery = productsQuery.Where(p => p.Category == query.Category);
        
        if (query.MinPrice.HasValue)
            productsQuery = productsQuery.Where(p => p.Price >= query.MinPrice.Value);
        
        if (query.MaxPrice.HasValue)
            productsQuery = productsQuery.Where(p => p.Price <= query.MaxPrice.Value);
        
        // Apply sorting
        productsQuery = query.SortBy.ToLower() switch
        {
            "price" => query.SortDescending 
                ? productsQuery.OrderByDescending(p => p.Price)
                : productsQuery.OrderBy(p => p.Price),
            "name" => query.SortDescending
                ? productsQuery.OrderByDescending(p => p.Name)
                : productsQuery.OrderBy(p => p.Name),
            _ => productsQuery.OrderBy(p => p.Name)
        };
        
        // Apply pagination
        var totalCount = await productsQuery.CountAsync();
        var products = await productsQuery
            .Skip((query.PageNumber - 1) * query.PageSize)
            .Take(query.PageSize)
            .Select(p => new ProductDto
            {
                Id = p.Id,
                Name = p.Name,
                Price = p.Price,
                Category = p.Category
            })
            .ToListAsync();
        
        return new PagedResult<ProductDto>
        {
            Items = products,
            TotalCount = totalCount,
            PageNumber = query.PageNumber,
            PageSize = query.PageSize
        };
    }
}
```

### Events

**Definition:** An event is a notification that something has happened. It represents a fact about the past.

**Characteristics:**
- Declarative: "This happened"
- Immutable: represents something that already occurred
- Not addressed to a specific handler (multiple handlers can react)
- Typically no direct response expected
- Can be stored and replayed

**Example:**
```csharp
// Event: Notification that an order was created
public class OrderCreatedEvent
{
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    public DateTime CreatedAt { get; set; }
    public decimal TotalAmount { get; set; }
}

// Multiple event handlers can react to the same event
public class OrderCreatedEventHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Send confirmation email
        await _emailService.SendOrderConfirmationAsync(evt);
    }
}

public class UpdateInventoryEventHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Update inventory
        await _inventoryService.ReserveItemsAsync(evt.OrderId);
    }
}
```

**Naming Conventions:**
- Use past tense: `OrderCreated`, `PaymentProcessed`, `UserRegistered`
- Describe what happened: `InventoryReserved`, `EmailSent`, `OrderShipped`
- Suffix with `Event`: `OrderCreatedEvent`, `PaymentProcessedEvent`

**Event Metadata:**
Events should include metadata for tracing, versioning, and debugging:

```csharp
public abstract class BaseEvent
{
    public string EventId { get; set; } = Guid.NewGuid().ToString();
    public string EventType { get; set; }
    public DateTime OccurredAt { get; set; } = DateTime.UtcNow;
    public string CorrelationId { get; set; }
    public string CausationId { get; set; }
    public int Version { get; set; } = 1;
}

public class OrderCreatedEvent : BaseEvent
{
    public OrderCreatedEvent()
    {
        EventType = nameof(OrderCreatedEvent);
    }
    
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    public List<OrderItemDto> Items { get; set; }
    public decimal TotalAmount { get; set; }
    public Address ShippingAddress { get; set; }
}
```

**Event Versioning:**
Events evolve over time, and handlers must support multiple versions:

```csharp
// Version 1
public class OrderCreatedEventV1
{
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    public decimal TotalAmount { get; set; }
}

// Version 2 - Added shipping address
public class OrderCreatedEventV2
{
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    public decimal TotalAmount { get; set; }
    public Address ShippingAddress { get; set; } // New field
}

// Handler supports both versions
public class OrderCreatedEventHandler
{
    public async Task HandleV1Async(OrderCreatedEventV1 evt)
    {
        // Handle V1 event (no shipping address)
        await ProcessOrderAsync(evt.OrderId, evt.CustomerId, null);
    }
    
    public async Task HandleV2Async(OrderCreatedEventV2 evt)
    {
        // Handle V2 event (with shipping address)
        await ProcessOrderAsync(evt.OrderId, evt.CustomerId, evt.ShippingAddress);
    }
}

// Or use upcasting to convert old events to new format
public class OrderCreatedEventUpcaster
{
    public OrderCreatedEventV2 Upcast(OrderCreatedEventV1 oldEvent)
    {
        return new OrderCreatedEventV2
        {
            OrderId = oldEvent.OrderId,
            CustomerId = oldEvent.CustomerId,
            TotalAmount = oldEvent.TotalAmount,
            ShippingAddress = null // Default for old events
        };
    }
}
```

**Event Enrichment:**
Sometimes events are enriched with additional data for consumers:

```csharp
// Basic event from order service
public class OrderCreatedEvent
{
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
}

// Enriched event with customer details
public class EnrichedOrderCreatedEvent
{
    public string OrderId { get; set; }
    public string CustomerId { get; set; }
    
    // Enriched customer data
    public string CustomerName { get; set; }
    public string CustomerEmail { get; set; }
    public string CustomerTier { get; set; }
}

// Event enricher
public class OrderCreatedEventEnricher
{
    public async Task<EnrichedOrderCreatedEvent> EnrichAsync(OrderCreatedEvent evt)
    {
        var customer = await _customerService.GetByIdAsync(evt.CustomerId);
        
        return new EnrichedOrderCreatedEvent
        {
            OrderId = evt.OrderId,
            CustomerId = evt.CustomerId,
            CustomerName = customer.Name,
            CustomerEmail = customer.Email,
            CustomerTier = customer.Tier
        };
    }
}
```

### Comparison Table

| Aspect | Command | Query | Event |
|--------|---------|-------|-------|
| **Intent** | Change state | Read state | Notify of change |
| **Direction** | One-way (request) | Two-way (request/response) | One-way (notification) |
| **Handler** | Single handler | Single handler | Multiple handlers |
| **Response** | Success/failure | Data | None (fire-and-forget) |
| **Timing** | Future action | Current state | Past occurrence |
| **Idempotency** | Should be idempotent | Always idempotent | Naturally idempotent |

### CQRS: Command Query Responsibility Segregation

**Definition:** CQRS is a pattern that separates read operations (queries) from write operations (commands), often using different models for each.

**Basic CQRS Implementation:**

```csharp
// Write model (Command side)
public class Order
{
    public string Id { get; private set; }
    public string CustomerId { get; private set; }
    public List<OrderItem> Items { get; private set; }
    public OrderStatus Status { get; private set; }
    
    public void Place(string customerId, List<OrderItem> items)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Order already placed");
        
        Id = Guid.NewGuid().ToString();
        CustomerId = customerId;
        Items = items;
        Status = OrderStatus.Placed;
    }
    
    public void Cancel()
    {
        if (Status == OrderStatus.Shipped)
            throw new InvalidOperationException("Cannot cancel shipped order");
        
        Status = OrderStatus.Cancelled;
    }
}

// Read model (Query side)
public class OrderSummaryDto
{
    public string OrderId { get; set; }
    public string CustomerName { get; set; }
    public int ItemCount { get; set; }
    public decimal TotalAmount { get; set; }
    public string Status { get; set; }
    public DateTime PlacedAt { get; set; }
}

// Command handler updates write model
public class PlaceOrderCommandHandler
{
    public async Task<OrderPlacedResult> HandleAsync(PlaceOrderCommand command)
    {
        var order = new Order();
        order.Place(command.CustomerId, command.Items);
        
        await _orderRepository.SaveAsync(order);
        
        // Publish event to update read model
        await _eventBus.PublishAsync(new OrderPlacedEvent
        {
            OrderId = order.Id,
            CustomerId = order.CustomerId,
            Items = order.Items,
            PlacedAt = DateTime.UtcNow
        });
        
        return new OrderPlacedResult { OrderId = order.Id };
    }
}

// Event handler updates read model
public class OrderPlacedEventHandler
{
    public async Task HandleAsync(OrderPlacedEvent evt)
    {
        var customer = await _customerService.GetByIdAsync(evt.CustomerId);
        
        // Update read model (optimized for queries)
        var orderSummary = new OrderSummaryDto
        {
            OrderId = evt.OrderId,
            CustomerName = customer.Name,
            ItemCount = evt.Items.Count,
            TotalAmount = evt.Items.Sum(i => i.Price * i.Quantity),
            Status = "Placed",
            PlacedAt = evt.PlacedAt
        };
        
        await _readModelRepository.SaveAsync(orderSummary);
    }
}

// Query handler reads from read model
public class GetOrderSummaryQueryHandler
{
    public async Task<OrderSummaryDto> HandleAsync(GetOrderSummaryQuery query)
    {
        // Query optimized read model
        return await _readModelRepository.GetByIdAsync(query.OrderId);
    }
}
```

**Benefits of CQRS:**
- Optimized read and write models
- Better scalability (scale reads independently from writes)
- Flexibility in choosing different data stores
- Clearer separation of concerns

**CQRS with Events:**
CQRS naturally integrates with event-driven architecture. Commands modify state and emit events, which update read models:

```csharp
// Command -> Event -> Read Model Update
public class UpdateUserProfileCommandHandler
{
    public async Task<UserProfileUpdatedResult> HandleAsync(UpdateUserProfileCommand command)
    {
        // Update write model
        var user = await _userRepository.GetByIdAsync(command.UserId);
        user.UpdateProfile(command.Name, command.Bio, command.AvatarUrl);
        await _userRepository.SaveAsync(user);
        
        // Publish event
        await _eventBus.PublishAsync(new UserProfileUpdatedEvent
        {
            UserId = user.Id,
            Name = user.Name,
            Bio = user.Bio,
            AvatarUrl = user.AvatarUrl,
            UpdatedAt = DateTime.UtcNow
        });
        
        return new UserProfileUpdatedResult { Success = true };
    }
}

// Multiple read models can be updated from the same event
public class UserProfileReadModelUpdater
{
    public async Task HandleAsync(UserProfileUpdatedEvent evt)
    {
        // Update user profile read model
        await _userProfileReadModel.UpdateAsync(evt.UserId, new UserProfileDto
        {
            UserId = evt.UserId,
            Name = evt.Name,
            Bio = evt.Bio,
            AvatarUrl = evt.AvatarUrl
        });
    }
}

public class UserSearchIndexUpdater
{
    public async Task HandleAsync(UserProfileUpdatedEvent evt)
    {
        // Update search index
        await _searchService.IndexUserAsync(new UserSearchDocument
        {
            UserId = evt.UserId,
            Name = evt.Name,
            Bio = evt.Bio
        });
    }
}
```

## Self-Check Questions

1. Why should commands be idempotent when possible?
   - **Answer:** Idempotency ensures that executing the same command multiple times produces the same result, preventing duplicate operations (e.g., double charges, duplicate records) when network issues or retries occur.

2. Can an event handler modify the state that triggered the event? Why or why not?
   - **Answer:** Yes, event handlers can modify state, but they should not modify the *same* state that triggered the event in a way that creates circular dependencies. Event handlers typically update their own service's state or trigger new events based on the received event.

3. What's the key difference between a command and an event in terms of timing?
   - **Answer:** Commands represent future actions (intent to change state), while events represent past occurrences (facts about what already happened). Commands say "please do this," events say "this happened."

4. How does CQRS relate to the command/query/event distinction?
   - **Answer:** CQRS separates commands (write operations) from queries (read operations), often using different models for each. Events are often used to synchronize read models with changes made by commands, enabling optimized models for both reads and writes.

5. When would you use a query vs an event to get information about state changes?
   - **Answer:** Use queries when you need the current state on-demand (pull model). Use events when you want to be notified of changes as they happen and maintain a local copy of relevant data (push model). Events enable reactive behavior, while queries are suitable for on-demand data retrieval.

**Additional Questions:**

6. What happens if a command fails?
   - **Answer:** The command handler should return an error result indicating the failure reason. The state should remain unchanged (rollback if necessary), and the caller should handle the error appropriately (retry, notify user, log, etc.).

7. Should queries ever have side effects?
   - **Answer:** No. Queries should be side-effect-free, meaning they don't modify state. This allows them to be cached, retried, and called multiple times without issues. Any state modifications should be done through commands.

8. Why can the same event have multiple handlers?
   - **Answer:** Events represent facts about what happened, and multiple parts of the system may need to react to the same fact in different ways. This enables loose coupling and extensibility—new handlers can be added without modifying existing code.

## Key Takeaways

- **Commands** represent intent to change state and are processed by a single handler
  - Use imperative naming (e.g., `CreateOrder`, `UpdateInventory`)
  - Should be idempotent when possible to handle retries safely
  - Return success/failure results with clear error information
  - Always have exactly one handler

- **Queries** request information without side effects and return data
  - Use interrogative naming (e.g., `GetOrder`, `SearchProducts`)
  - Must be side-effect-free to enable caching and retries
  - Can be cached to improve performance
  - Support filtering, pagination, and sorting
  - Always have exactly one handler

- **Events** represent facts about the past and can be handled by multiple subscribers
  - Use past-tense naming (e.g., `OrderCreated`, `PaymentProcessed`)
  - Are immutable—they represent historical facts
  - Enable loose coupling between services
  - Can have zero, one, or many handlers
  - Should include metadata for tracing and versioning

- Understanding these distinctions helps design clearer, more maintainable event-driven systems

- **CQRS** separates commands (writes) from queries (reads), while events enable loose coupling and eventual consistency between write and read models

**Design Guidelines:**

1. **Always use the appropriate message type:**
   - Need to change state? → Command
   - Need to read data? → Query
   - Something happened? → Event

2. **Never mix concerns:**
   - Don't make queries that modify state
   - Don't make commands that are primarily for reading data
   - Don't use events to command actions

3. **Consider the consumer:**
   - Commands: Single, specific handler
   - Queries: Single handler, but result consumed by many
   - Events: Multiple handlers, each reacting independently

4. **Think about failure modes:**
   - Commands can fail and should communicate errors
   - Queries should be retryable and cacheable
   - Events represent facts and can't "fail" (handlers might fail processing them)

5. **Version and evolve carefully:**
   - Commands and queries can be versioned per handler
   - Events must be versioned carefully since multiple handlers depend on them
   - Always maintain backward compatibility for events
