## Introduction

**At-most-once delivery** is the simplest and fastest delivery guarantee: messages are sent once with no retries or acknowledgments. If a message is lost due to network issues, broker failures, or consumer crashes, it's simply gone. The system prioritizes performance and throughput over reliability.

This guarantee is often called "fire and forget"—the producer sends the message and immediately moves on without waiting for confirmation. While this may sound dangerous, there are legitimate use cases where at-most-once delivery is the right choice.

## Key Concepts Summary

### What is At-Most-Once Delivery?

**Definition:** A message will be delivered **zero or one time**—it may be lost, but will never be duplicated.

```
Producer → Message → [Network/Broker/Consumer] → Either:
                                                    - Delivered (1 time) ✓
                                                    - Lost (0 times) ✗
                                                    - NEVER duplicated
```

**Characteristics:**
- No acknowledgments or confirmations
- No retries on failure
- Fire-and-forget semantics
- Lowest latency, highest throughput
- Messages may be lost

### How It Works

#### Kafka At-Most-Once

In Kafka, at-most-once is achieved by:
1. Producer uses `acks=0` (no acknowledgment from broker)
2. Consumer commits offsets **before** processing messages
3. No retries on producer or consumer

```csharp
// Kafka producer with at-most-once semantics
var config = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    Acks = Acks.None,              // acks=0: no acknowledgment
    EnableIdempotence = false,     // disable idempotence
    Retries = 0,                   // no retries
    RequestTimeoutMs = 5000        // fast timeout
};

using var producer = new ProducerBuilder<string, TelemetryEvent>(config).Build();

try
{
    // Fire and forget - no await, no callback
    producer.Produce("telemetry", new Message<string, TelemetryEvent>
    {
        Key = device.Id,
        Value = telemetryEvent
    });
    
    // Move on immediately, don't wait for result
}
catch
{
    // Log error but don't retry
    logger.LogWarning("Failed to send telemetry, message lost");
}
```

**What happens:**
- Producer sends message to broker
- Producer doesn't wait for acknowledgment
- If network fails, broker crashes, or message is dropped → message is lost
- Producer has already moved on, no retry

#### RabbitMQ At-Most-Once

In RabbitMQ, at-most-once is achieved by:
1. Publisher doesn't use publisher confirms
2. Queue is not durable
3. Messages are not persistent
4. Consumer uses auto-ack (acknowledges before processing)

```csharp
// RabbitMQ producer with at-most-once semantics
var factory = new ConnectionFactory
{
    HostName = "localhost",
    AutomaticRecoveryEnabled = false  // don't automatically reconnect
};

using var connection = factory.CreateConnection();
using var channel = connection.CreateModel();

// Declare non-durable queue (lost on broker restart)
channel.QueueDeclare(
    queue: "logs",
    durable: false,      // not durable
    exclusive: false,
    autoDelete: false,
    arguments: null
);

var body = Encoding.UTF8.GetBytes(JsonSerializer.Serialize(logEvent));

// Publish without confirms, non-persistent
channel.BasicPublish(
    exchange: "",
    routingKey: "logs",
    basicProperties: null,  // no properties = non-persistent
    body: body
);

// Move on immediately
```

**Consumer with auto-ack:**

```csharp
var consumer = new EventingBasicConsumer(channel);

consumer.Received += (model, ea) =>
{
    // Message is auto-acknowledged BEFORE this code runs
    // If processing fails, message is already acknowledged = lost
    
    var body = ea.Body.ToArray();
    var message = Encoding.UTF8.GetString(body);
    
    try
    {
        ProcessLog(message);
    }
    catch
    {
        // Too late - message already acknowledged and removed from queue
        logger.LogWarning("Failed to process log, message lost");
    }
};

// autoAck: true = at-most-once
channel.BasicConsume(
    queue: "logs",
    autoAck: true,      // acknowledge before processing
    consumer: consumer
);
```

### When to Use At-Most-Once

**Acceptable use cases:**

1. **Monitoring and Telemetry**
   - Individual metrics/logs are not critical
   - Volume compensates for occasional loss
   - Example: Server CPU metrics every second

```csharp
// Example: Sending telemetry metrics
public async Task SendMetric(string metricName, double value)
{
    // Missing one CPU sample out of 3600 per hour is acceptable
    await _producer.ProduceAsync("metrics", new Message<string, Metric>
    {
        Key = metricName,
        Value = new Metric { Name = metricName, Value = value, Timestamp = DateTime.UtcNow }
    });
    // Don't wait for confirmation, don't retry
}
```

2. **Best-Effort Logging**
   - Application logs where 100% completeness isn't required
   - Performance is more important than capturing every log

3. **Live Video/Audio Streaming**
   - Frames/packets can be dropped
   - Retransmitting old frames would cause lag

4. **Real-Time Sensor Data**
   - New readings arrive constantly
   - Old data becomes stale quickly

**When NOT to use:**
- Financial transactions
- Order processing
- User account changes
- Any scenario where data loss is unacceptable

### Performance Characteristics

**Benefits:**
- ✅ Lowest latency (no waiting for acks)
- ✅ Highest throughput (no retry overhead)
- ✅ Simplest implementation
- ✅ Minimal broker load

**Drawbacks:**
- ❌ Messages can be lost
- ❌ No delivery guarantees
- ❌ Difficult to troubleshoot (no confirmation of receipt)
- ❌ Not suitable for critical data

**Performance comparison:**

```
Scenario: Sending 100,000 messages

At-most-once:
  - Latency: 1ms per message
  - Throughput: 100,000 msg/sec
  - Reliability: 99.5% delivered (500 lost)

At-least-once:
  - Latency: 5ms per message
  - Throughput: 20,000 msg/sec
  - Reliability: 100% delivered (with duplicates)

Exactly-once:
  - Latency: 10ms per message
  - Throughput: 10,000 msg/sec
  - Reliability: 100% delivered (no duplicates)
```

### Detecting Message Loss

With at-most-once, detecting loss requires application-level mechanisms:

```csharp
// Example: Sequence numbers to detect gaps
public class TelemetryEvent
{
    public string DeviceId { get; set; }
    public long SequenceNumber { get; set; }  // Monotonically increasing
    public double Value { get; set; }
    public DateTime Timestamp { get; set; }
}

// Consumer tracks gaps
public class TelemetryConsumer
{
    private readonly ConcurrentDictionary<string, long> _lastSequence = new();
    
    public void ProcessTelemetry(TelemetryEvent evt)
    {
        var expected = _lastSequence.GetOrAdd(evt.DeviceId, 0) + 1;
        
        if (evt.SequenceNumber > expected)
        {
            var lost = evt.SequenceNumber - expected;
            logger.LogWarning(
                "Lost {LostCount} telemetry events for device {DeviceId}",
                lost,
                evt.DeviceId
            );
        }
        
        _lastSequence[evt.DeviceId] = evt.SequenceNumber;
        ProcessValue(evt.Value);
    }
}
```

### Mitigation Strategies

**Even with at-most-once, you can reduce message loss:**

**1. Connection pooling and retry at network layer:**

```csharp
public class ResilientAtMostOnceProducer
{
    private readonly IProducer<string, TelemetryEvent> _producer;
    private readonly IConnectionPool _connectionPool;
    
    public async Task SendAsync(TelemetryEvent evt)
    {
        try
        {
            // Use connection pool for better reliability
            using var connection = await _connectionPool.GetConnectionAsync();
            
            // Send without waiting for ack (at-most-once)
            _producer.Produce("telemetry", new Message<string, TelemetryEvent>
            {
                Key = evt.DeviceId,
                Value = evt
            });
        }
        catch (Exception ex)
        {
            // Log but don't retry (at-most-once semantics)
            _logger.LogWarning(ex, "Failed to send telemetry");
            
            // Track failure rate
            _metrics.IncrementCounter("telemetry.send_failures");
        }
    }
}
```

**2. Buffering and batching:**

```csharp
public class BufferedProducer
{
    private readonly Channel<TelemetryEvent> _buffer;
    private readonly IProducer<string, TelemetryEvent> _producer;
    
    public BufferedProducer()
    {
        _buffer = Channel.CreateBounded<TelemetryEvent>(new BoundedChannelOptions(10000)
        {
            FullMode = BoundedChannelFullMode.DropOldest  // Drop old data if buffer full
        });
        
        _ = Task.Run(FlushBufferAsync);
    }
    
    public async Task SendAsync(TelemetryEvent evt)
    {
        // Write to buffer (fast, non-blocking)
        await _buffer.Writer.WriteAsync(evt);
    }
    
    private async Task FlushBufferAsync()
    {
        await foreach (var evt in _buffer.Reader.ReadAllAsync())
        {
            try
            {
                _producer.Produce("telemetry", new Message<string, TelemetryEvent>
                {
                    Key = evt.DeviceId,
                    Value = evt
                });
            }
            catch
            {
                // At-most-once: log and continue
                _logger.LogWarning("Failed to send telemetry");
            }
        }
    }
}
```

**3. Sampling and aggregation:**

```csharp
public class AggregatingProducer
{
    private readonly ConcurrentDictionary<string, MetricAggregate> _aggregates = new();
    private readonly Timer _flushTimer;
    
    public AggregatingProducer()
    {
        // Flush aggregates every 10 seconds
        _flushTimer = new Timer(FlushAggregates, null, TimeSpan.FromSeconds(10), TimeSpan.FromSeconds(10));
    }
    
    public void RecordMetric(string metricName, double value)
    {
        // Aggregate in memory
        _aggregates.AddOrUpdate(
            metricName,
            new MetricAggregate { Sum = value, Count = 1, Min = value, Max = value },
            (key, existing) => new MetricAggregate
            {
                Sum = existing.Sum + value,
                Count = existing.Count + 1,
                Min = Math.Min(existing.Min, value),
                Max = Math.Max(existing.Max, value)
            });
    }
    
    private void FlushAggregates(object state)
    {
        foreach (var (name, agg) in _aggregates)
        {
            // Send aggregate (losing one aggregate is less critical than individual metrics)
            _producer.Produce("metrics", new Message<string, MetricAggregate>
            {
                Key = name,
                Value = agg
            });
        }
        
        _aggregates.Clear();
    }
}
```

### Operational Considerations

**Monitoring at-most-once systems:**

```csharp
public class AtMostOnceMonitoring
{
    public void MonitorProducerHealth()
    {
        // Track producer errors
        var failureRate = _metrics.GetCounter("producer.failures").Value;
        var successRate = _metrics.GetCounter("producer.successes").Value;
        
        var totalMessages = failureRate + successRate;
        var lossPercentage = (failureRate / totalMessages) * 100;
        
        if (lossPercentage > 5.0)
        {
            _alertService.AlertAsync(
                $"Message loss rate ({lossPercentage:F2}%) exceeds threshold");
        }
    }
    
    public void MonitorSequenceGaps()
    {
        // Check for sequence number gaps
        var gapsDetected = _metrics.GetCounter("sequence.gaps").Value;
        
        if (gapsDetected > 100)
        {
            _logger.LogWarning($"Detected {gapsDetected} sequence gaps");
        }
    }
}
```

**Testing at-most-once behavior:**

```csharp
[Fact]
public async Task AtMostOnce_AcceptsMessageLoss()
{
    // Arrange
    var producer = CreateAtMostOnceProducer();
    var sentCount = 0;
    var receivedCount = 0;
    
    // Act: Send messages with simulated network issues
    for (int i = 0; i < 1000; i++)
    {
        try
        {
            await producer.SendAsync(new TelemetryEvent { SequenceNumber = i });
            sentCount++;
        }
        catch
        {
            // Expected: some sends may fail
        }
    }
    
    // Allow time for processing
    await Task.Delay(5000);
    
    // Assert: Received count may be less than sent count
    receivedCount = GetReceivedMessageCount();
    
    Assert.True(receivedCount >= sentCount * 0.95);  // Allow 5% loss
    Assert.True(receivedCount <= sentCount);         // No duplicates
    
    _logger.LogInformation($"Sent: {sentCount}, Received: {receivedCount}, Loss: {sentCount - receivedCount}");
}
```

### Cost-Benefit Analysis

**When to accept at-most-once:**

```
Use Case: IoT Temperature Sensors (10,000 sensors, 1 reading/minute)
- Messages per day: 14.4 million
- Critical: No
- Cost of loss: Low (next reading in 1 minute)
- Cost of processing: High (14.4M messages * $0.0001 = $1440/day)

Decision: At-most-once
- Savings: No ack overhead = 50% cost reduction
- Trade-off: 1-2% message loss acceptable
- Result: $720/day cost, occasional missing data points
```

**When to avoid at-most-once:**

```
Use Case: E-commerce Orders
- Messages per day: 100,000
- Critical: Yes
- Cost of loss: Very high (lost revenue, angry customers)
- Cost of processing: Low (100K messages * $0.0001 = $10/day)

Decision: At-least-once or exactly-once
- Extra cost: Minimal ($5-20/day)
- Trade-off: Guaranteed delivery worth the cost
- Result: No lost orders, happy customers
```
