# Lesson 5: API-First Design Workflow

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand API-first vs code-first approaches
- Design APIs using OpenAPI before coding
- Use OpenAPI design tools
- Generate server stubs from specifications
- Implement contract-driven development
- Validate implementations against contracts

---

## Introduction

API-first design means defining your API contract (OpenAPI specification) before writing any implementation code. This approach enables parallel development (frontend and backend teams work from the same contract), better design discussions, and ensures documentation never falls out of sync.

## Key Concepts Summary

### API-First Workflow

```
1. Design Phase:
   ├─ Write OpenAPI specification
   ├─ Review with stakeholders
   ├─ Iterate on design
   └─ Get approval

2. Contract Phase:
   ├─ Share spec with teams
   ├─ Generate mock server
   ├─ Frontend starts development
   └─ Backend starts development

3. Implementation Phase:
   ├─ Generate server stubs
   ├─ Implement business logic
   ├─ Validate against contract
   └─ Test with contract tests

4. Deployment Phase:
   ├─ Deploy API
   ├─ Deploy documentation
   ├─ Generate client SDKs
   └─ Monitor usage
```

### Benefits of API-First

**Advantages:**
- ✅ Parallel development (frontend/backend)
- ✅ Better design discussions
- ✅ Documentation always current
- ✅ Early feedback
- ✅ Contract-driven testing
- ✅ Mock servers for development

**Trade-offs:**
- ⚠️ More upfront design time
- ⚠️ Need OpenAPI expertise
- ⚠️ Specification maintenance
- ⚠️ Tooling learning curve

### Collaborative Design Process

**Step 1: Initial Design Workshop**

```yaml
# Stakeholders gather to define:
# - API purpose and goals
# - Key resources and operations
# - Authentication requirements
# - Rate limiting needs
# - Error handling strategy

# Output: Initial OpenAPI skeleton
openapi: 3.0.3
info:
  title: Orders API
  version: 0.1.0
  description: |
    Initial draft for orders API.
    
    ## Goals
    - Enable order creation and management
    - Support order status tracking
    - Provide order history
    
    ## Open Questions
    - Payment integration approach?
    - Inventory reservation timing?
    - Notification preferences?

paths:
  /orders:
    # TBD
  /orders/{id}:
    # TBD
```

**Step 2: Iterative Refinement**

```yaml
# Version 0.2.0 - Add endpoints
paths:
  /orders:
    get:
      summary: List orders
      description: |
        **Design Decision:** Cursor-based pagination chosen over
        offset-based to handle high-frequency inserts.
      parameters:
        - name: cursor
          in: query
          schema:
            type: string
        - name: limit
          in: query
          schema:
            type: integer
            default: 20
            maximum: 100
      responses:
        '200':
          description: Success
          content:
            application/json:
              schema:
                type: object
                properties:
                  data:
                    type: array
                    items:
                      $ref: '#/components/schemas/Order'
                  nextCursor:
                    type: string
                    nullable: true
    
    post:
      summary: Create order
      description: |
        **Design Decision:** Idempotency-Key header required
        to prevent duplicate orders from retries.
      parameters:
        - name: Idempotency-Key
          in: header
          required: true
          schema:
            type: string
            format: uuid
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
            examples:
              simple:
                summary: Simple order
                value:
                  customerId: 123
                  items:
                    - productId: 456
                      quantity: 2
              withShipping:
                summary: Order with shipping
                value:
                  customerId: 123
                  items:
                    - productId: 456
                      quantity: 2
                  shippingAddress:
                    street: "123 Main St"
                    city: "Springfield"
                    country: "US"
      responses:
        '201':
          description: Order created
          headers:
            Location:
              schema:
                type: string
                format: uri
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'
        '409':
          description: Duplicate idempotency key
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
```

**Generated Controller Interface:**

```csharp
// IOrdersApiController.cs (generated)
public interface IOrdersApiController
{
    Task<IActionResult> CreateOrder(
        [FromHeader] string idempotencyKey,
        [FromBody] CreateOrderRequest body);
        
    Task<IActionResult> GetOrders(
        [FromQuery] string? cursor,
        [FromQuery] int? limit);
        
    Task<IActionResult> GetOrder(
        [FromRoute] int id);
}

// Implementation
public class OrdersApiController : ControllerBase, IOrdersApiController
{
    private readonly IOrderService _orderService;
    
    public OrdersApiController(IOrderService orderService)
    {
        _orderService = orderService;
    }
    
    public async Task<IActionResult> CreateOrder(
        string idempotencyKey,
        CreateOrderRequest body)
    {
        // Implement business logic
        var order = await _orderService.CreateOrderAsync(idempotencyKey, body);
        return CreatedAtAction(nameof(GetOrder), new { id = order.Id }, order);
    }
    
    public async Task<IActionResult> GetOrders(string? cursor, int? limit)
    {
        // Implement business logic
        var result = await _orderService.GetOrdersAsync(cursor, limit ?? 20);
        return Ok(result);
    }
    
    public async Task<IActionResult> GetOrder(int id)
    {
        // Implement business logic
        var order = await _orderService.GetOrderAsync(id);
        return order != null ? Ok(order) : NotFound();
    }
}
```

### CI/CD Integration

**Contract Validation in Pipeline:**

```yaml
# .github/workflows/api-contract.yml
name: API Contract Validation

on:
  pull_request:
    paths:
      - 'openapi.yaml'
      - 'src/**'

jobs:
  validate-contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Validate OpenAPI spec
        uses: mbowman100/swagger-validator-action@master
        with:
          files: |
            openapi.yaml
      
      - name: Check breaking changes
        uses: oasdiff/oasdiff-action@v0.0.10
        with:
          base: 'https://api.example.com/openapi.yaml'
          revision: 'openapi.yaml'
          fail-on-diff: true
          
      - name: Start mock server
        run: |
          npm install -g @stoplight/prism-cli
          prism mock openapi.yaml --port 4010 &
          sleep 5
          
      - name: Run contract tests
        run: |
          npm install -g dredd
          dredd openapi.yaml http://localhost:4010

  test-implementation:
    runs-on: ubuntu-latest
    needs: validate-contract
    steps:
      - uses: actions/checkout@v3
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: '8.0.x'
          
      - name: Build
        run: dotnet build
        
      - name: Run API
        run: |
          dotnet run --project src/OrdersApi &
          sleep 10
          
      - name: Test against contract
        run: |
          dredd openapi.yaml http://localhost:5000
```

  title: Orders API

### Team Workflow Example

```
1. Design Phase (Week 1)
   └─ Designer creates initial OpenAPI spec
   └─ Review with stakeholders
   └─ Iterate based on feedback
   └─ Commit spec to git
   └─ Tag as v0.1.0-draft

2. Review Phase (Week 2)
   └─ Team reviews spec
   └─ Frontend team validates endpoints
   └─ Backend team validates feasibility
   └─ Security team reviews auth
   └─ Update spec based on feedback
   └─ Tag as v1.0.0-rc1

3. Mock Phase (Week 2-3)
   └─ Deploy mock server
   └─ Frontend starts development against mock
   └─ Backend starts implementation
   └─ Run contract tests
   └─ Fix any mismatches

4. Implementation Phase (Week 3-5)
   └─ Backend implements endpoints
   └─ Run contract tests in CI
   └─ Frontend switches to real API
   └─ Integration testing

5. Release Phase (Week 6)
   └─ Deploy to production
   └─ Generate and publish documentation
   └─ Generate client SDKs
   └─ Monitor for issues
   └─ Tag as v1.0.0

6. Maintenance Phase (Ongoing)
   └─ Track API usage
   └─ Collect feedback
   └─ Plan v1.1.0 features
   └─ Update spec for new features
   └─ Maintain backward compatibility
```
