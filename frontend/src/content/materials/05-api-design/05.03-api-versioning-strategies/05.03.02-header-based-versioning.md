# Lesson 2: Header-Based Versioning

## Learning Objectives

By the end of this lesson, you will be able to:

- Use custom headers and Accept headers for versioning
- Understand the trade-offs compared to URL versioning
- Configure ASP.NET Core for header versioning
- Handle version negotiation

---

## Introduction

Header-based versioning keeps URLs clean by placing the version information in HTTP headers instead of the URL path. This approach maintains a cleaner URL structure and better adheres to REST principles, but can be less discoverable and harder to test manually. Two common approaches are custom headers (e.g., `X-API-Version`) and content negotiation via the `Accept` header.

## Key Concepts Summary

### Custom Header Versioning

```csharp
// Program.cs - Configure custom header versioning
using Asp.Versioning;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;
    
    // Read version from custom header
    options.ApiVersionReader = new HeaderApiVersionReader("X-API-Version");
    
    // Or use Microsoft's standard header
    // options.ApiVersionReader = new HeaderApiVersionReader("api-version");
});

builder.Services.AddControllers();
var app = builder.Build();
app.MapControllers();
app.Run();
```

### Controller Implementation

```csharp
[ApiController]
[Route("api/products")]  // No version in URL!
[ApiVersion("1.0")]
[ApiVersion("2.0")]
public class ProductsController : ControllerBase
{
    // GET /api/products
    // Header: X-API-Version: 1.0
    [MapToApiVersion("1.0")]
    [HttpGet]
    public ActionResult<IEnumerable<ProductV1Dto>> GetProductsV1()
    {
        var products = _productService.GetAllProducts();
        return Ok(products.Select(p => new ProductV1Dto
        {
            Id = p.Id,
            Name = p.Name,
            Price = p.Price
        }));
    }
    
    // GET /api/products
    // Header: X-API-Version: 2.0
    [MapToApiVersion("2.0")]
    [HttpGet]
    public ActionResult<IEnumerable<ProductV2Dto>> GetProductsV2(
        [FromQuery] string? category = null,
        [FromQuery] int page = 1,
        [FromQuery] int pageSize = 20)
    {
        var products = _productService.GetProducts(category, page, pageSize);
        return Ok(products.Select(p => new ProductV2Dto
        {
            Id = p.Id,
            Name = p.Name,
            Price = p.Price,
            Category = p.Category,
            Tags = p.Tags,
            CreatedAt = p.CreatedAt
        }));
    }
    
    // Same endpoint, different versions
    // Version determined by header
    [HttpGet("{id}")]
    public ActionResult GetProduct(int id, ApiVersion version)
    {
        var product = _productService.GetProductById(id);
        
        if (product == null)
            return NotFound();
        
        return version.MajorVersion switch
        {
            1 => Ok(MapToV1Dto(product)),
            2 => Ok(MapToV2Dto(product)),
            _ => BadRequest("Unsupported API version")
        };
    }
}

// Client usage:
// curl -H "X-API-Version: 1.0" http://localhost:5000/api/products
// curl -H "X-API-Version: 2.0" http://localhost:5000/api/products
```

### Media Type Versioning (Accept Header)

```csharp
// Program.cs - Configure media type versioning
builder.Services.AddApiVersioning(options =>
{

    }

        // V2 implementation
    }

// Client usage:
```

### Combining Multiple Version Readers

```csharp
// Support versioning via multiple methods
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;
    
    // Try multiple sources (first found wins)
    options.ApiVersionReader = ApiVersionReader.Combine(
        new HeaderApiVersionReader("X-API-Version"),
        new HeaderApiVersionReader("api-version"),
        new QueryStringApiVersionReader("api-version"),
        new MediaTypeApiVersionReader()
    );
});

// Now clients can specify version via:
// 1. X-API-Version header
// 2. api-version header
// 3. ?api-version=1.0 query string
// 4. Accept: application/json;v=1.0
```

### Version in Response Headers

```csharp
// Add middleware to include version in response
app.Use(async (context, next) =>
{
    var endpoint = context.GetEndpoint();
    var apiVersion = endpoint?.Metadata.GetMetadata<ApiVersionMetadata>();
    
    if (apiVersion != null)
    {
        var version = apiVersion.ApiVersions.FirstOrDefault()?.ToString();
        context.Response.Headers.Add("X-API-Version", version);
    }
    
    await next();
});

// Response includes:
// X-API-Version: 1.0
// api-supported-versions: 1.0, 2.0
```

### Swagger/OpenAPI with Header Versioning

```csharp
// Configure Swagger to show version header
builder.Services.AddSwaggerGen(options =>
{
    options.SwaggerDoc("v1", new OpenApiInfo
    {
        Title = "Products API V1",
        Version = "v1"
    });
    
    options.SwaggerDoc("v2", new OpenApiInfo
    {
        Title = "Products API V2",
        Version = "v2"
    });
    
    // Add version header parameter to all operations
    options.OperationFilter<ApiVersionOperationFilter>();
});

public class ApiVersionOperationFilter : IOperationFilter
{
    public void Apply(OpenApiOperation operation, OperationFilterContext context)
    {
        operation.Parameters ??= new List<OpenApiParameter>();
        
        operation.Parameters.Add(new OpenApiParameter
        {
            Name = "X-API-Version",
            In = ParameterLocation.Header,
            Required = false,
            Description = "API Version",
            Schema = new OpenApiSchema
            {
                Type = "string",
                Default = new OpenApiString("1.0")
            }
        });
    }
}
```

### Testing with Header Versioning

```csharp
public class ProductsControllerTests
{
    private readonly HttpClient _client;
    
    [Fact]
    public async Task GetProducts_WithV1Header_ReturnsV1Format()
    {
        // Arrange
        var request = new HttpRequestMessage(HttpMethod.Get, "/api/products");
        request.Headers.Add("X-API-Version", "1.0");
        
        // Act
        var response = await _client.SendAsync(request);
        
        // Assert
        response.EnsureSuccessStatusCode();
        var products = await response.Content.ReadFromJsonAsync<List<ProductV1Dto>>();
        Assert.NotNull(products);
    }
    
    [Fact]
    public async Task GetProducts_WithV2Header_ReturnsV2Format()
    {
        // Arrange
        var request = new HttpRequestMessage(HttpMethod.Get, "/api/products");
        request.Headers.Add("X-API-Version", "2.0");
        
        // Act
        var response = await _client.SendAsync(request);
        
        // Assert
        response.EnsureSuccessStatusCode();
        var products = await response.Content.ReadFromJsonAsync<List<ProductV2Dto>>();
        Assert.NotNull(products);
        Assert.All(products, p => Assert.NotNull(p.Category));
    }
    
    [Fact]
    public async Task GetProducts_WithoutHeader_UsesDefaultVersion()
    {
        // Act
        var response = await _client.GetAsync("/api/products");
        
        // Assert - Uses default version (1.0)
        response.EnsureSuccessStatusCode();
        var versionHeader = response.Headers.GetValues("X-API-Version").First();
        Assert.Equal("1.0", versionHeader);
    }
}
```

### Version Negotiation Middleware

```csharp
// Custom middleware for advanced version negotiation
public class ApiVersionNegotiationMiddleware
{
    private readonly RequestDelegate _next;
    
    public ApiVersionNegotiationMiddleware(RequestDelegate next)
    {
        _next = next;
    }
    
    public async Task InvokeAsync(HttpContext context)
    {
        // Check if version specified
        if (!context.Request.Headers.ContainsKey("X-API-Version"))
        {
            // Check if client supports latest version via User-Agent
            var userAgent = context.Request.Headers["User-Agent"].ToString();
            
            if (userAgent.Contains("ModernClient"))
            {
                // Modern clients get latest version
                context.Request.Headers.Add("X-API-Version", "2.0");
            }
            else
            {
                // Legacy clients get v1
                context.Request.Headers.Add("X-API-Version", "1.0");
            }
        }
        
        await _next(context);
    }
}

// Register middleware
app.UseMiddleware<ApiVersionNegotiationMiddleware>();
```

### Advantages and Disadvantages

```
✅ Advantages of Header Versioning:

1. Clean URLs
   - /api/products (not /api/v1/products)
   - Better REST principles
   - Single URL for resource
   - More elegant API design

2. Better for caching
   - Same URL, different representations
   - Vary header controls caching
   - CDN can handle via Vary: X-API-Version

3. Flexible version selection
   - Can use multiple headers
   - Content negotiation built-in
   - Can combine with other strategies

4. More "RESTful"
   - Resources have single URI
   - Version is representation detail
   - Follows hypermedia principles

5. URL stability
   - URLs don't change across versions
   - Bookmarks remain valid
   - Better for SEO (if applicable)

❌ Disadvantages:

1. Less discoverable
   - Version not visible in URL
   - Harder to share/bookmark specific version
   - Need documentation to know versions
   - Not obvious in logs

2. Harder to test manually
   - Can't test in browser easily
   - Need tools like curl/Postman
   - More complex debugging
   - Requires header manipulation

3. Caching complexity
   - Must use Vary header correctly
   - CDN configuration more complex
   - Proxy servers may not handle well
   - Browser caching tricky

4. Client implementation
   - Clients must remember to set headers
   - More error-prone
   - Harder for non-technical users
   - Additional code in every request

5. API Gateway complexity
   - Routing based on headers harder
   - More complex infrastructure
   - Harder to implement rate limiting per version
   - Load balancing more complex

6. Tooling support
   - Some tools don't handle headers well
   - Harder to document
   - API explorers less intuitive
   - Testing frameworks need header support

When to use header versioning:
✅ Internal APIs with sophisticated clients
✅ When REST purity is important
✅ Machine-to-machine communication
✅ When URLs should remain stable
✅ APIs consumed by your own apps

When NOT to use:
❌ Public APIs for broad audience
❌ APIs used in browsers
❌ When discoverability is key
❌ Simple client applications
❌ Third-party integrations
```

### Content Negotiation with Custom Media Types

```csharp
// More advanced: vendor-specific media types
public static class VendorMediaTypes
{
    public const string ProductV1Json = "application/vnd.mycompany.product.v1+json";
    public const string ProductV2Json = "application/vnd.mycompany.product.v2+json";
    public const string ProductV1Xml = "application/vnd.mycompany.product.v1+xml";
    public const string ProductV2Xml = "application/vnd.mycompany.product.v2+xml";
}

[ApiController]
[Route("api/products")]
public class ProductsController : ControllerBase
{
    // Responds to both JSON and XML for v1
    [HttpGet("{id}")]
    [Produces(VendorMediaTypes.ProductV1Json, VendorMediaTypes.ProductV1Xml)]
    [MapToApiVersion("1.0")]
    public ActionResult<ProductV1Dto> GetProductV1(int id)
    {
        var product = _service.GetById(id);
        if (product == null) return NotFound();
        
        // ASP.NET Core handles content negotiation
        return Ok(MapToV1Dto(product));
    }
    
    // Responds to both JSON and XML for v2
    [HttpGet("{id}")]
    [Produces(VendorMediaTypes.ProductV2Json, VendorMediaTypes.ProductV2Xml)]
    [MapToApiVersion("2.0")]
    public ActionResult<ProductV2Dto> GetProductV2(int id)
    {
        var product = _service.GetById(id);
        if (product == null) return NotFound();
        
        return Ok(MapToV2Dto(product));
    }
}

// Client requests:
// Accept: application/vnd.mycompany.product.v1+json → JSON v1
// Accept: application/vnd.mycompany.product.v2+json → JSON v2
// Accept: application/vnd.mycompany.product.v1+xml → XML v1
```

### Real-World Header Patterns

```csharp
// GitHub-style: X-GitHub-Api-Version

{
    options.ApiVersionReader = new HeaderApiVersionReader("X-GitHub-Api-Version");

builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new HeaderApiVersionReader("api-version");
});

// Accept header with version parameter
builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new MediaTypeApiVersionReader();

builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new HeaderApiVersionReader("X-My-API-Version");
});
```

## Self-Check Questions

1. **What are the main advantages of header-based versioning?**
   - Clean URLs without version numbers
   - More RESTful (single URI per resource)
   - Better for URL stability
   - Flexible version negotiation

2. **How do you configure ASP.NET Core to read version from headers?**
   - Use `HeaderApiVersionReader` with custom header name
   - Or use `MediaTypeApiVersionReader` for Accept header
   - Configure in `AddApiVersioning` options

3. **What's the difference between custom headers and media type versioning?**
   - Custom headers: X-API-Version: 1.0 (explicit version header)
   - Media type: Accept: application/json;v=1.0 (version in content negotiation)
   - Custom headers more explicit, media types more RESTful

4. **How do you handle requests without a version header?**
   - Set `AssumeDefaultVersionWhenUnspecified = true`
   - Configure `DefaultApiVersion`
   - Or return 400 requiring version

5. **Why is header versioning considered more "RESTful"?**
   - Resources have single, stable URI
   - Version is representation detail, not resource identity
   - Follows content negotiation principles
   - Closer to Roy Fielding's REST principles

6. **What challenges does header versioning create for API consumers?**
   - Less discoverable (version not in URL)
   - Requires header manipulation in every request
   - Harder to test in browser
   - More complex client code
   - Easier to forget or misconfigure
