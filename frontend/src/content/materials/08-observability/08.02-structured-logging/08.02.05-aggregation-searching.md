## Introduction

Individual log files are difficult to search, especially in distributed systems with multiple services. Log aggregation collects logs from all sources into a centralized system, enabling unified querying, correlation, and analysis. This lesson teaches you to work with aggregated logs effectively, write efficient queries, and manage log data at scale.

## Key Concepts Summary

### Log Aggregation Architecture

**Components:**
```
Application Logs
    ↓
Log Shipper (Fluent Bit, Promtail, etc.)
    ↓
Log Aggregator/Storage (Loki, Elasticsearch, CloudWatch)
    ↓
Query Interface (Grafana, Kibana, Console)
```

**Flow:**
```
1. Application emits structured JSON logs
2. Log shipper collects and forwards
3. Aggregator parses and stores
4. Users query centralized logs
```

### Why Aggregation?

**Without aggregation:**
```
✗ SSH to each server
✗ grep through files
✗ Manual correlation
✗ No unified view
✗ Time-consuming
```

**With aggregation:**
```
✓ Single query interface
✓ Search all services at once
✓ Automatic correlation
✓ Unified timeline
✓ Fast and efficient
```

### Querying Structured Logs

**Field-based queries:**
```
Basic filters:
Level = "Error"
UserId = "user-123"
StatusCode >= 400

Combine filters:
Level = "Error" AND UserId = "user-123"
StatusCode >= 500 OR (StatusCode >= 400 AND Duration > 1000)

Pattern matching:
Message CONTAINS "timeout"
Endpoint MATCHES "/api/.*"
```

**Common queries:**
```
# Find all errors for user
WHERE UserId = "user-123" 
AND Level = "Error"
ORDER BY Timestamp DESC

# Find slow requests
WHERE Duration > 2000
AND Endpoint LIKE "/api/%"
ORDER BY Duration DESC

# Find errors by service
WHERE Level = "Error"
GROUP BY ServiceName
ORDER BY COUNT(*) DESC

# Track request flow
WHERE CorrelationId = "abc-123"
ORDER BY Timestamp ASC
```

### Search Best Practices

**Practice 1: Start narrow**
```
Bad:
- Query all logs
- Then filter

Good:
- Filter by time range first
- Add service filter
- Then add specific criteria
```

**Practice 2: Use structured fields**
```
Bad (slow):
Message CONTAINS "user-123"

Good (fast):
UserId = "user-123"
```

**Practice 3: Limit time range**
```
Bad:
- Query last 30 days
- Scan billions of logs

Good:
- Query last 1 hour
- Scan millions of logs
- Expand if needed
```

**Practice 4: Use indexes**
```
Indexed fields (fast):
- Timestamp
- Level
- UserId
- ServiceName

Non-indexed (slow):
- Message body
- Large text fields
```

### Filter Strategies

**Temporal filtering:**
```
Last hour:     WHERE Timestamp >= NOW() - 1h
Specific day:  WHERE DATE(Timestamp) = '2026-01-27'
Time range:    WHERE Timestamp BETWEEN '10:00' AND '11:00'
```

**Level filtering:**
```
Errors only:   WHERE Level = 'Error'
Warn or worse: WHERE Level IN ('Warning', 'Error', 'Fatal')
Not debug:     WHERE Level != 'Debug'
```

**Service filtering:**
```
Single service:    WHERE ServiceName = 'OrderService'
Multiple services: WHERE ServiceName IN ('OrderService', 'PaymentService')
Service pattern:   WHERE ServiceName LIKE 'Payment%'
```

**User filtering:**
```
Specific user:     WHERE UserId = 'user-123'
Authenticated:     WHERE UserId IS NOT NULL
Multiple users:    WHERE UserId IN ('user-1', 'user-2', 'user-3')
```

### Aggregation Queries

**Count operations:**
```
# Errors per service
SELECT ServiceName, COUNT(*) as ErrorCount
FROM logs
WHERE Level = 'Error'
AND Timestamp >= NOW() - 24h
GROUP BY ServiceName
ORDER BY ErrorCount DESC

# Requests per endpoint
SELECT Endpoint, COUNT(*) as RequestCount
FROM logs
WHERE Level = 'Information'
AND Message = 'Request completed'
GROUP BY Endpoint
ORDER BY RequestCount DESC
```

**Statistical operations:**
```
# Average response time
SELECT Endpoint, AVG(Duration) as AvgDuration
FROM logs
WHERE Duration IS NOT NULL
GROUP BY Endpoint
ORDER BY AvgDuration DESC

# Percentiles
SELECT Endpoint,
       PERCENTILE(Duration, 50) as P50,
       PERCENTILE(Duration, 95) as P95,
       PERCENTILE(Duration, 99) as P99
FROM logs
GROUP BY Endpoint
```

**Time-series aggregation:**
```
# Errors over time (hourly)
SELECT DATE_TRUNC('hour', Timestamp) as Hour,
       COUNT(*) as ErrorCount
FROM logs
WHERE Level = 'Error'
AND Timestamp >= NOW() - 7d
GROUP BY Hour
ORDER BY Hour
```

### Example Queries by Use Case

**Debugging a user issue:**
```
1. Find user's recent activity:
   WHERE UserId = 'user-123'
   AND Timestamp >= NOW() - 1h
   ORDER BY Timestamp DESC

2. Find user's errors:
   WHERE UserId = 'user-123'
   AND Level = 'Error'
   AND Timestamp >= NOW() - 24h

3. Find complete request flow:
   WHERE CorrelationId = 'abc-123'
   ORDER BY Timestamp ASC
```

**Investigating service errors:**
```
1. Count errors by type:
   WHERE ServiceName = 'PaymentService'
   AND Level = 'Error'
   GROUP BY ErrorType

2. Find first occurrence:
   WHERE ServiceName = 'PaymentService'
   AND Level = 'Error'
   ORDER BY Timestamp ASC
   LIMIT 1

3. Sample error logs:
   WHERE ServiceName = 'PaymentService'
   AND Level = 'Error'
   LIMIT 10
```

**Performance analysis:**
```
1. Slowest endpoints:
   WHERE Duration > 1000
   ORDER BY Duration DESC
   LIMIT 20

2. Average latency by endpoint:
   SELECT Endpoint, AVG(Duration), COUNT(*)
   FROM logs
   WHERE Duration IS NOT NULL
   GROUP BY Endpoint
   ORDER BY AVG(Duration) DESC

3. Latency trend:
   SELECT DATE_TRUNC('5min', Timestamp), AVG(Duration)
   FROM logs
   WHERE Endpoint = '/api/orders'
   GROUP BY 1
   ORDER BY 1
```

### Retention Policies

**Strategy:**
```
Hot storage (fast, expensive):
- Last 7 days
- Full detail
- All logs

Warm storage (medium):
- 8-30 days
- Reduced detail
- Errors + important events

Cold storage (slow, cheap):
- 31-90 days
- Minimal detail
- Errors only

Archive/Delete:
- > 90 days
- Compliance requirements
```

**Implementation:**
```
Different retention by level:
- Debug:   1 day
- Info:    7 days
- Warning: 30 days
- Error:   90 days
- Fatal:   1 year

Different retention by service:
- Critical services: 90 days
- Standard services: 30 days
- Development:       7 days
```

### Cost Optimization

**Reduce log volume:**
```
✓ Appropriate log levels (INFO in prod, not DEBUG)
✓ Sample high-volume logs
✓ Exclude health check logs
✓ Don't log in tight loops
✓ Use metric counters instead of individual logs
```

**Efficient storage:**
```
✓ Structured JSON (compresses well)
✓ Use compression
✓ Retention policies
✓ Archive old logs
✓ Delete non-critical logs
```

**Query optimization:**
```
✓ Use structured fields
✓ Limit time ranges
✓ Filter early
✓ Use indexes
✓ Avoid wildcards at start
✓ Cache frequent queries
```

### Best Practices

**Logging:**
```
✓ Always use structured logging
✓ Include correlation IDs
✓ Add business context
✓ Use appropriate levels
✓ Don't log sensitive data
```

**Querying:**
```
✓ Start with narrow filters
✓ Use structured fields
✓ Limit time range
✓ Test queries on small ranges first
✓ Use aggregation wisely
```

**Management:**
```
✓ Set retention policies
✓ Monitor log volume
✓ Alert on sudden increases
✓ Regular cleanup
✓ Cost monitoring
```

### Practical Example

**Scenario: Debug checkout failure**
```
1. User reports: "Checkout failed"
   User provides: Email (john@example.com)

2. Find user ID from email:
   WHERE UserEmail = "john@example.com"
   AND Level = "Information"
   AND Message = "User logged in"
   LIMIT 1
   → UserId: user-123

3. Find recent errors:
   WHERE UserId = "user-123"
   AND Level = "Error"
   AND Timestamp >= NOW() - 1h
   → Find CorrelationId: abc-123

4. Get complete flow:
   WHERE CorrelationId = "abc-123"
   ORDER BY Timestamp ASC
   → See: OrderService → PaymentService → ERROR

5. Filter to error:
   WHERE CorrelationId = "abc-123"
   AND Level = "Error"
   → Find: "Payment gateway timeout"

6. Check if widespread:
   WHERE ServiceName = "PaymentService"
   AND Message CONTAINS "gateway timeout"
   AND Timestamp >= NOW() - 1h
   → 50 occurrences

7. Root cause: Payment gateway outage
   Solution: Use fallback gateway
```
