## Introduction

Recording every single trace in a high-traffic system is often impractical due to storage costs, performance overhead, and data volume. Sampling allows you to capture a representative subset of traces while maintaining visibility into system behavior. Understanding when and how to sample is crucial for effective distributed tracing at scale.

## Key Concepts Summary

### Why Sampling?

**The Problem:**
```
High-traffic system: 10,000 requests/second
Each request generates 10 spans
= 100,000 spans/second
= 6 million spans/minute
= 360 million spans/hour
= 8.6 billion spans/day

Storage costs: $$$$$
Performance impact: Significant
```

**The Solution:**
```
Sample 1% of traces:
= 86 million spans/day
Storage costs: $
Performance impact: Minimal
Coverage: Still excellent for most use cases
```

### Sampling Rate Considerations

Typical sampling rates by traffic volume:

```
Low traffic (< 100 req/sec):     100% sampling (no sampling)
Medium traffic (100-1K req/sec):  10-20% sampling
High traffic (1K-10K req/sec):    1-5% sampling
Very high traffic (> 10K):        0.1-1% sampling
```

### Head-Based Sampling

**Definition:** Sampling decision made at the start of a trace, when the request first arrives.

```
Request arrives → Make sampling decision → Record or drop
                        ↓
                    Random chance
                (e.g., sample 10%)
```

#### How It Works

```csharp
// Decision made immediately
var sampler = new TraceIdRatioBasedSampler(0.1); // 10% sampling

// For each request:
// 1. Generate trace ID
// 2. Apply sampling algorithm
// 3. If sampled: record, if not: drop
```

#### Head-Based Sampling Strategies

**1. Always On (No Sampling)**
```csharp
.SetSampler(new AlwaysOnSampler())
```
- Records all traces
- Use for low-traffic or critical systems

**2. Always Off**
```csharp
.SetSampler(new AlwaysOffSampler())
```
- Records no traces
- Use to completely disable tracing

**3. TraceIdRatioBasedSampler (Probabilistic)**
```csharp
.SetSampler(new TraceIdRatioBasedSampler(0.1)) // 10%
```
- Samples based on trace ID
- Deterministic: same trace ID = same decision
- Most common head-based approach

**4. ParentBased (Respect Parent Decision)**
```csharp
.SetSampler(new ParentBasedSampler(
    new TraceIdRatioBasedSampler(0.1)))
```
- If parent span was sampled → sample child
- If parent span not sampled → don't sample child
- Maintains consistency across services

#### Pros and Cons

**Advantages:**
- ✓ Fast decision (no waiting)
- ✓ Low overhead
- ✓ Simple to implement
- ✓ Works at application level
- ✓ Predictable resource usage

**Disadvantages:**
- ✗ May miss important traces (errors, slow requests)
- ✗ All-or-nothing per trace
- ✗ Can't adjust after seeing results
- ✗ May lose critical debugging data

### Tail-Based Sampling

**Definition:** Sampling decision made after the complete trace is available, based on its characteristics.

```
Request completes → Analyze trace → Decide to keep or drop
                         ↓
              Check: errors? slow? important?
```

#### How It Works

```
1. Buffer all spans temporarily
   ↓
2. Wait for trace to complete
   ↓
3. Apply sampling policies
   ↓
4. Keep or drop entire trace
```

#### Tail-Based Sampling Policies

**1. Error-Based Policy**
```yaml
# Always keep traces with errors
policies:
  - name: errors
    type: status_code
    status_code:
      status_codes: [ERROR]
```

**2. Latency-Based Policy**
```yaml
# Keep slow traces
policies:
  - name: slow-traces
    type: latency
    latency:
      threshold_ms: 1000  # Keep traces > 1 second
```

**3. Probabilistic Policy**
```yaml
# Sample remaining traces at 10%
policies:
  - name: probabilistic
    type: probabilistic
    probabilistic:
      sampling_percentage: 10
```

**4. Rate Limiting Policy**
```yaml
# Keep at most 100 traces per second
policies:
  - name: rate-limit
    type: rate_limiting
    rate_limiting:
      spans_per_second: 100
```

**5. Composite Policy (Recommended)**
```yaml
# Combine multiple policies
policies:
  # Always keep errors
  - name: errors
    type: status_code
    status_code:
      status_codes: [ERROR]
  
  # Always keep slow requests
  - name: slow
    type: latency
    latency:
      threshold_ms: 2000
  
  # Sample 5% of everything else
  - name: probabilistic
    type: probabilistic
    probabilistic:
      sampling_percentage: 5
```

#### Pros and Cons

**Advantages:**
- ✓ Never miss errors or slow requests
- ✓ Intelligent sampling decisions
- ✓ Better debugging experience
- ✓ Focus on important traces

**Disadvantages:**
- ✗ Requires buffering (memory overhead)
- ✗ Adds latency (must wait for trace completion)
- ✗ More complex to implement
- ✗ Requires OpenTelemetry Collector
- ✗ Can lose traces if buffer is full

### Head-Based vs Tail-Based Comparison

```
Scenario: 1000 requests, 10 have errors

Head-Based (10% sampling):
  ✓ 100 traces kept (90% dropped)
  ✗ ~1 error trace captured (9 errors lost!)
  ✓ Fast, predictable
  
Tail-Based (errors + 5% others):
  ✓ 10 error traces kept (all errors!)
  ✓ ~50 normal traces kept
  ✓ No errors lost
  ✗ Requires buffering
```

### Implementing Head-Based Sampling in .NET

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.1))) // 10% sampling
        .AddAspNetCoreInstrumentation()
        .AddOtlpExporter());
```

**With conditional sampling:**

```csharp
// Custom sampler that always samples errors
public class ErrorAwareSampler : Sampler
{
    private readonly Sampler _baseSampler;
    
    public ErrorAwareSampler(double ratio)
    {
        _baseSampler = new TraceIdRatioBasedSampler(ratio);
    }
    
    public override SamplingResult ShouldSample(
        in SamplingParameters samplingParameters)
    {
        // Check if this is an error
        var tags = samplingParameters.Tags;
        if (tags?.Any(t => t.Key == "error" && (bool)t.Value) == true)
        {
            return new SamplingResult(SamplingDecision.RecordAndSample);
        }
        
        // Otherwise, use base sampling
        return _baseSampler.ShouldSample(samplingParameters);
    }
}

// Usage
.SetSampler(new ParentBasedSampler(new ErrorAwareSampler(0.1)))
```

### Implementing Tail-Based Sampling

Tail-based sampling requires the OpenTelemetry Collector:

```yaml
# collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317

processors:
  batch:
  
  tail_sampling:
    decision_wait: 10s  # Wait for trace completion
    num_traces: 50000   # Buffer size
    expected_new_traces_per_sec: 100
    policies:
      # Always sample errors
      - name: errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      
      # Always sample slow traces
      - name: slow
        type: latency
        latency:
          threshold_ms: 1000
      
      # Sample 10% of everything else
      - name: probabilistic
        type: probabilistic
        probabilistic:
          sampling_percentage: 10

exporters:
  otlp:
    endpoint: jaeger:4317

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [tail_sampling, batch]
      exporters: [otlp]
```

### Choosing the Right Strategy

**Decision Framework:**

```
Primary concern: Cost reduction?
├─ Yes: Head-based TraceIdRatioBased (10-20%)
└─ No: Continue...

Primary concern: Debugging production issues?
├─ Yes: Tail-based with error + latency policies
└─ No: Continue...

High traffic system?
├─ Yes: Tail-based with composite policies
└─ No: Head-based ParentBased (or no sampling)

Have OpenTelemetry Collector?
├─ Yes: Tail-based sampling is available
└─ No: Head-based sampling only
```

**Recommendations by use case:**

```
Development/Staging:
→ AlwaysOnSampler (100%)

Low traffic production (< 100 req/sec):
→ AlwaysOnSampler or ParentBased(TraceIdRatio 0.5)

Medium traffic (100-1K req/sec):
→ ParentBased(TraceIdRatio 0.1) or tail-based

High traffic (> 1K req/sec):
→ Tail-based with error + latency policies

Cost-sensitive:
→ Head-based TraceIdRatio (1-5%)

Debugging-focused:
→ Tail-based with composite policies
```

### Best Practices

**1. Start Conservative, Adjust Later:**
```csharp
// Start with higher sampling rate
.SetSampler(new TraceIdRatioBasedSampler(0.5)) // 50%

// Reduce as you gain confidence
.SetSampler(new TraceIdRatioBasedSampler(0.1)) // 10%
```

**2. Always Use ParentBased:**
```csharp
// Ensures consistency across services
.SetSampler(new ParentBasedSampler(
    new TraceIdRatioBasedSampler(0.1)))
```

**3. Monitor Sampling Effectiveness:**
```csharp
// Log sampling decisions
_logger.LogDebug("Trace {TraceId} sampled: {Sampled}",
    Activity.Current?.TraceId,
    Activity.Current?.Recorded);
```

**4. Different Rates for Different Services:**
```csharp
// Critical service: higher sampling
.SetSampler(new TraceIdRatioBasedSampler(0.5)) // 50%

// High-volume service: lower sampling
.SetSampler(new TraceIdRatioBasedSampler(0.01)) // 1%
```

**5. Consider Adaptive Sampling:**
- Automatically adjust sampling rate based on traffic
- Keep sampling rate higher during incidents
- Reduce sampling during normal operations

## Key Takeaways

- **Sampling reduces costs** and overhead while maintaining observability
- **Head-based sampling** decides early, is fast but may miss important traces
- **Tail-based sampling** decides after completion, captures all errors but requires buffering
- **TraceIdRatioBasedSampler** is the most common head-based strategy
- **ParentBasedSampler** maintains consistency across services
- **Tail-based sampling** requires the OpenTelemetry Collector
- Choose sampling strategy based on **traffic volume, cost, and debugging needs**
- Start with **higher sampling rates** and reduce as needed
