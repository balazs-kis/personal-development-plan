## Key Concepts Summary

### What is Jaeger?

**Jaeger** is an open-source, distributed tracing platform created by Uber and now part of the CNCF. It provides:
- **Trace collection** from OpenTelemetry-instrumented applications
- **Storage** of trace data (in-memory, Cassandra, Elasticsearch, or others)
- **Visualization** through a web UI
- **Analysis tools** for understanding system behavior

```
Your App → OpenTelemetry → Jaeger Collector → Storage → Jaeger UI
           (OTLP)                             (Backend)  (Visualization)
```

### Setting Up Jaeger Quickly

**Using Docker (All-in-One):**

```bash
docker run --rm --name jaeger \
  -p 16686:16686 \
  -p 4317:4317 \
  -p 4318:4318 \
  jaegertracing/all-in-one:latest
```

**Ports:**
- `16686`: Jaeger UI (web interface)
- `4317`: OTLP gRPC endpoint
- `4318`: OTLP HTTP endpoint

**Access the UI:**
```
http://localhost:16686
```

### Configuring Your Application to Send to Jaeger

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddSource("MyCompany.MyService")
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddOtlpExporter(options =>
        {
            // Send to Jaeger via OTLP
            options.Endpoint = new Uri("http://localhost:4317");
            options.Protocol = OtlpExportProtocol.Grpc;
        }));
```

### Analyzing Performance Bottlenecks

**Example: Slow Checkout Flow**

**Trace View:**
```
Trace ID: abc123...
Total Duration: 3200ms ⚠️

[0ms──────────────────────────────3200ms]
│
├─ HTTP POST /api/checkout [Server]
│  Duration: 3200ms
│
├──┬─ OrderService.ProcessOrder [Internal]
│  │  Duration: 3150ms
│  │
│  ├─ Inventory.CheckStock [Client]
│  │  Duration: 50ms ✓ Fast
│  │
│  ├─ Payment.ChargeCard [Client]
│  │  Duration: 3000ms ⚠️ BOTTLENECK!
│  │  Status: Ok
│  │  Tags:
│  │    - payment.provider: stripe
│  │    - payment.amount: 149.99
│  │  Events:
│  │    [100ms] Connecting to payment gateway
│  │    [2900ms] Payment processing...
│  │    [3000ms] Payment completed
│  │
│  └─ Shipping.CreateLabel [Client]
│     Duration: 80ms ✓ Fast
│
└─ Return response
   Duration: 5ms
```

**Analysis:**
- ✓ Total duration: 3200ms
- ✓ Bottleneck: Payment processing (3000ms = 94% of time)
- ✓ Other operations fast (< 100ms each)
- ✓ Root cause: External payment gateway slow
- ✓ Action: Add timeout, implement retry, or switch providers

### Common Analysis Patterns

#### 1. Finding the Slowest Spans

**In Jaeger:**
```
1. Search for traces in your service
2. Sort by Duration (longest first)
3. Open the slowest trace
4. Look at the waterfall view
5. Identify the longest span
6. Check its attributes and events
```

#### 2. Comparing Successful vs Failed Traces

**Search successful:**
```
Service: OrderService
Tags: http.status_code=200
```

**Search failed:**
```
Service: OrderService
Tags: http.status_code=500
```

**Compare:**
- Duration differences?
- Different code paths?
- Which span fails?
- What's the error context?

#### 3. Identifying Cascading Failures

**Pattern:**
```
Service A: ERROR (originated here)
  └─> Service B: ERROR (propagated)
      └─> Service C: ERROR (propagated)
      
Look for the first span with Status: ERROR
That's usually where the problem started.
```

#### 4. Finding N+1 Query Problems

**Bad pattern:**
```
GetOrders
  ├─ Query: SELECT * FROM orders (1 query, 10 results)
  ├─ Query: SELECT * FROM users WHERE id=1
  ├─ Query: SELECT * FROM users WHERE id=2
  ├─ Query: SELECT * FROM users WHERE id=3
  ├─ Query: SELECT * FROM users WHERE id=4
  ├─ Query: SELECT * FROM users WHERE id=5
  ├─ Query: SELECT * FROM users WHERE id=6
  ├─ Query: SELECT * FROM users WHERE id=7
  ├─ Query: SELECT * FROM users WHERE id=8
  ├─ Query: SELECT * FROM users WHERE id=9
  └─ Query: SELECT * FROM users WHERE id=10

11 queries! ⚠️ N+1 problem!
```

**Solution: Use batch query or JOIN**

### Best Practices for Trace Analysis

**1. Start with the Big Picture:**
```
Service Graph → Find problem service
    ↓
Search → Find example traces
    ↓
Timeline → Identify slow spans
    ↓
Details → Understand root cause
```

**2. Use Tags Effectively:**
```
# Find errors
error=true

# Find slow requests
http.route=/api/checkout

# Find specific user issues
user.id=user-123

# Find specific scenarios
order.type=express AND payment.method=credit_card
```

**3. Look for Patterns, Not Individual Traces:**
```
Don't: Analyze a single slow trace
Do: Compare 10 slow traces to find common patterns
```

**4. Follow the Critical Path:**
```
In parallel operations, focus on the slowest span
That's what determines total latency.

Example:
├─ Service B: 100ms
├─ Service C: 300ms ← Critical path!
└─ Service D: 50ms

Total time = 300ms (not 450ms)
```

```
  jaegertracing/example-hotrod:latest \
  all

# Access demo: http://localhost:8080
# Access Jaeger: http://localhost:16686
```

### Real-World Debugging Scenario

**Problem Report:** "Users complain checkout is slow"

**Step 1: Search for checkout traces**
```
Service: API-Gateway
Operation: POST /api/checkout
Lookback: Last hour
Min Duration: 2000ms
```

**Step 2: Analyze slowest trace**
```
Trace Duration: 5500ms

Breakdown:
- ValidateCart: 50ms (1%)
- CheckInventory: 100ms (2%)
- ProcessPayment: 5200ms (95%) ← PROBLEM!
- SendConfirmation: 100ms (2%)
```

**Step 3: Drill into ProcessPayment span**
```
Tags:
- payment.provider: legacy_system
- payment.retry_count: 3
- payment.timeout: true

Events:
[0ms] Attempt 1 started
[2000ms] Timeout - retrying
[2050ms] Attempt 2 started
[4000ms] Timeout - retrying
[4050ms] Attempt 3 started
[5200ms] Payment completed
```

**Step 4: Root cause identified**
```
Legacy payment system timing out
Each timeout = 2 seconds
3 attempts = ~6 seconds total

SOLUTION:
1. Reduce timeout to 1 second
2. Limit retries to 2
3. Switch to modern payment API
```

## Key Takeaways

- **Jaeger** visualizes distributed traces collected by OpenTelemetry
- Use **search and filters** to find relevant traces (errors, slow requests)
- The **timeline view** shows spans and their durations
- **Tags and events** provide context for understanding behavior
- **Service dependencies** reveal system architecture and call patterns
- Focus on the **critical path** when analyzing parallel operations
- Look for **patterns** across multiple traces, not just individual ones
- The **HotROD demo** is excellent for learning trace analysis
