## Introduction

Cardinality and dimensionality are critical concepts in observability that directly impact system performance, storage costs, and query speed. High cardinality—many unique values—can overwhelm time-series databases and make metrics unmanageable. Understanding how to balance rich, dimensional data with practical constraints is essential for sustainable observability.

## Key Concepts Summary

### What is Cardinality?

**Definition:**
```
Cardinality = Number of unique values
in a dimension/attribute

Low cardinality:   Few unique values
High cardinality:  Many unique values
```

**Examples:**
```
Low cardinality:
- HTTP method: GET, POST, PUT, DELETE (4 values)
- Environment: dev, staging, prod (3 values)
- Boolean: true, false (2 values)

High cardinality:
- User ID: millions of unique users
- Email address: unique per user
- Request ID: unique per request
- IP address: thousands to millions
- Timestamp: effectively infinite
```

### What is Dimensionality?

**Definition:**
```
Dimensionality = Number of labels/dimensions
attached to a metric

Each dimension can have many values
Dimensions multiply cardinality
```

**Example metric:**
```
http_request_duration_seconds{
    method="GET",           // 4 possible values
    endpoint="/api/users",  // 50 possible values
    status="200",          // 5 possible values
    region="us-east-1"     // 10 possible values
}

Total combinations: 4 × 50 × 5 × 10 = 10,000 time series
```

### The Cardinality Problem

**Why it matters:**
```
Storage cost:  More unique series = more storage
Query speed:   More series = slower queries
Memory usage:  More series = more RAM needed
Index size:    Larger indexes to search
```

**Example explosion:**
```
Metric: api_latency

Dimensions:
- endpoint: 100 values
- method: 4 values
- status: 5 values
- user_id: 1,000,000 values ← high cardinality!

Total series: 100 × 4 × 5 × 1,000,000 = 2 billion!

Storage: Potentially terabytes
Query: Very slow
Cost: Very expensive
```

### High Cardinality Challenges

**Challenge 1: Storage explosion**
```
Each unique combination = time series
Time series = storage over time
High cardinality = exponential storage growth
```

**Challenge 2: Query performance**
```
More series = more data to scan
Aggregations become expensive
Queries time out
Dashboard slowness
```

**Challenge 3: Ingestion bottleneck**
```
Too many series to ingest
Rate limits hit
Data dropped
Incomplete observability
```

**Challenge 4: Cost**
```
Storage costs grow
Processing costs increase
Infrastructure scaling needed
Budget constraints
```

### When High Cardinality is Necessary

**Use cases for high cardinality:**
```
✓ Debugging specific user issues
  → Need user_id dimension

✓ Trace individual requests
  → Need trace_id dimension

✓ Security investigations
  → Need IP address, session_id

✓ Tenant-specific metrics
  → Need customer_id dimension

✓ A/B testing analysis
  → Need experiment_id dimension
```

**The tradeoff:**
```
High cardinality enables:
+ Detailed filtering
+ Specific investigations
+ Granular analysis

But costs:
- More storage
- Slower queries
- Higher bills
```

### Managing Cardinality

**Strategy 1: Choose dimensions carefully**
```
Good dimensions (low-medium cardinality):
✓ Service name (tens)
✓ Environment (few)
✓ HTTP method (few)
✓ Endpoint (hundreds)
✓ Status code (few)
✓ Region (tens)

Bad dimensions (high cardinality):
✗ User ID (millions)
✗ Email (millions)
✗ Request ID (billions)
✗ Timestamp (infinite)
✗ Session ID (millions)
```

**Strategy 2: Use logs for high cardinality**
```
Metrics:  Aggregated, low cardinality
Logs:     Detailed, high cardinality
Traces:   Sampled, moderate cardinality

Example:
Metric:  Request count by endpoint
Log:     Individual request details with user_id
Trace:   Sampled requests with full context
```

**Strategy 3: Aggregate at source**
```
Don't: Send metric per user
http_requests{user_id="user-123"}
http_requests{user_id="user-456"}
http_requests{user_id="user-789"}

Do: Aggregate and send count
http_requests_total{endpoint="/api/users"} = 3
Use logs to track individual users
```

**Strategy 4: Sampling**
```
Collect full data for:
✓ Errors (always)
✓ Slow requests (always)
✓ Sample of normal requests (1-10%)

Reduces volume while keeping insights
```

**Strategy 5: Drop unnecessary dimensions**
```
Review metrics regularly
Remove dimensions with low value
Simplify dimensional model
Focus on actionable data
```

### Cardinality Best Practices

**Practice 1: Limit dimension values**
```
Bad:  endpoint="/api/users/123/orders/456"
      → Unlimited unique values

Good: endpoint="/api/users/:id/orders/:id"
      → Single value, parameterized

Or:   endpoint_pattern="/api/users/*"
      → Grouped by pattern
```

**Practice 2: Use bounded sets**
```
Bad:  http_code="429" (can be 100-599)
Good: http_code_class="4xx" (5 values: 1xx, 2xx, 3xx, 4xx, 5xx)

Bad:  latency_ms="1234"
Good: latency_bucket="1000-2000"
```

**Practice 3: Cardinality budgets**
```
Set limits:
- Max dimensions per metric: 5-10
- Max unique values per dimension: 1000
- Max total time series: 100,000

Monitor and enforce
Alert on violations
```

**Practice 4: Aggregate in application**
```
Don't: Send raw metrics
       latency{user="user-123"} = 100ms
       latency{user="user-456"} = 150ms

Do:    Send aggregated histogram
       latency_bucket{le="100"} = 1
       latency_bucket{le="200"} = 2
       latency_sum = 250
       latency_count = 2
```

### Cardinality in Different Pillars

**Metrics:**
```
Challenge: Time series explosion
Strategy:  Low cardinality dimensions
Solution:  Aggregate, use bounded sets

Example:
✓ http_requests{method, endpoint, status}
✗ http_requests{user_id, request_id}
```

**Logs:**
```
Challenge: High volume
Strategy:  Sampling and retention
Solution:  Accept high cardinality

Example:
✓ Log every request with user_id
✓ Use structured fields
✓ Set retention policy
```

**Traces:**
```
Challenge: Many unique traces
Strategy:  Sampling
Solution:  Keep errors, sample success

Example:
✓ 100% error traces
✓ 100% slow traces
✓ 1-10% normal traces
```

### Monitoring Cardinality

**Track cardinality metrics:**
```
Prometheus:
prometheus_tsdb_symbol_table_size_bytes
prometheus_tsdb_head_series

Number of active time series
Rate of series creation
Memory usage
```

**Alert on growth:**
```
Alert when:
- Series count > threshold
- Growth rate too high
- Memory usage high
- Query latency increasing
```

**Regular audits:**
```
Weekly review:
- Which metrics have highest cardinality?
- Which dimensions least useful?
- Can we reduce any?
- Are limits appropriate?
```

### Real-World Example

**Problem: User latency metric**
```
Initial (bad):
api_latency{user_id="user-123", endpoint="/api/products"} = 100ms

Issues:
- user_id has millions of values
- Creates millions of time series
- Storage explosion
- Slow queries
```

**Solution 1: Remove high-cardinality dimension**
```
api_latency{endpoint="/api/products"} = histogram

Result:
- Aggregated view
- Low cardinality
- Fast queries

Tradeoff:
- Can't filter by user
- Use logs for specific users
```

**Solution 2: Use exemplars**
```
api_latency{endpoint="/api/products"} = histogram
  + exemplar{trace_id="abc123", user_id="user-456"}

Result:
- Low cardinality metrics
- Link to high-cardinality traces
- Best of both worlds
```

### Tools and Techniques

**Cardinality estimation:**
```
Before adding dimension, estimate:

Current series: 10,000
New dimension: user_type (5 values)
New series: 10,000 × 5 = 50,000

Is this acceptable?
Is the dimension valuable?
Can we achieve this another way?
```

**Cardinality limits:**
```
Prometheus: Default ~10 million series
InfluxDB: Depends on hardware
Many systems: Configurable limits

Stay well below limits
Leave headroom for growth
```

## Practice Exercise

After completing the materials, analyze these scenarios (spend 10 minutes):

```
Scenario 1: New metric design
Metric: Order processing time

Proposed dimensions:
- order_id        ← High cardinality! (millions)
- user_id         ← High cardinality! (millions)
- payment_method  ← Low cardinality (few)
- region          ← Low cardinality (tens)

Better design:
Keep: payment_method, region
Remove: order_id, user_id
Log: Individual orders with full details
Trace: Sample of orders with context

Scenario 2: Cardinality explosion
Current metric:
http_requests{endpoint, method, status} = 1000 series

Proposed change: Add user_id (1M users)
New series: 1000 × 1,000,000 = 1 billion!

Decision: DON'T add user_id to metric
Instead: Use logs for per-user analysis

Scenario 3: Debugging user issue
User "user-123" reports slow checkout

With high cardinality:
Query: checkout_latency{user_id="user-123"}
Problem: Metric doesn't exist (correct!)

Solution:
1. Check aggregate: checkout_latency (is it slow overall?)
2. Find trace: Search for user-123 in traces
3. Check logs: Filter logs by user-123
4. Analyze: Trace shows slow payment service

Lesson: Don't need high-cardinality metrics
        Logs + traces handle specific cases
```
