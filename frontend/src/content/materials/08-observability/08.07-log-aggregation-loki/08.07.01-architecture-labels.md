---

## Introduction

Grafana Loki is a horizontally scalable, multi-tenant log aggregation system inspired by Prometheus. Unlike traditional logging systems like Elasticsearch that index the full text of logs, Loki only indexes metadata (labels), making it significantly more resource-efficient and cost-effective. Understanding Loki's architecture and how to design proper label schemas is essential for building performant, scalable logging infrastructure.

## Key Concepts Summary

### Loki Architecture Overview

Loki has a modular architecture with components organized into three paths:

**Write Path:**
- **Distributor:** Receives log streams from clients (Promtail, Alloy, etc.), validates them, applies rate limiting, and forwards to ingesters using consistent hashing
- **Ingester:** Builds compressed chunks of log data in memory and periodically flushes to object storage

**Read Path:**
- **Query Frontend:** Accepts queries from clients, splits them into smaller queries, and caches results
- **Query Scheduler:** Manages query queue and distributes work to queriers
- **Querier:** Executes queries against both ingesters (recent data) and object storage (historical data)

**Backend Services:**
- **Index Gateway:** Synchronizes index between ingesters and storage
- **Compactor:** Deduplicates and compacts index files
- **Ruler:** Evaluates recording and alerting rules

### How Loki Stores Logs

**Key Difference from Traditional Systems:**
```
Traditional (e.g., Elasticsearch):
┌─────────────────────────────────────┐
│ Full-text index of every log line  │
│ High storage and memory costs      │
│ Powerful full-text search          │
└─────────────────────────────────────┘

Loki:
┌─────────────────────────────────────┐
│ Index only metadata (labels)        │
│ Store compressed log chunks         │
│ Much lower resource requirements    │
│ Search via grep-like filters        │
└─────────────────────────────────────┘
```

**Log Stream:**
A unique combination of labels identifies a log stream. All logs with the same label set belong to the same stream.

```
Stream 1: {app="nginx", env="prod", host="web-01"}
Stream 2: {app="nginx", env="prod", host="web-02"}
Stream 3: {app="api", env="prod", host="api-01"}
```

Each stream is stored as a series of compressed chunks in object storage (S3, GCS, etc.).

### Labels: The Foundation of Loki

**What are Labels?**

Labels are key-value pairs attached to log streams:

```
{app="nginx", environment="production", region="us-east"}
```

Labels serve two purposes:
1. **Indexing:** Loki creates an index entry for each unique label combination
2. **Querying:** You select log streams using label matchers

**Label Best Practices:**

**✅ DO:**
- Use static, low-cardinality labels (limited, unchanging values)
- Examples: `app`, `environment`, `tier`, `region`, `namespace`, `job`
- Keep total unique label combinations low (ideally < 1000 streams per tenant)

**❌ DON'T:**
- Never use high-cardinality values as labels:
  - User IDs
  - Request IDs
  - Session IDs
  - IP addresses
  - Timestamps
  - Email addresses

**Why?** Each unique label combination creates a new stream. High cardinality = too many streams = poor performance.

### Cardinality Management

**Calculating Cardinality:**

```
Apps: 10 (api, nginx, postgres, redis, ...)
Environments: 3 (prod, staging, dev)
Regions: 2 (us-east, us-west)

Total streams = 10 × 3 × 2 = 60 streams ✅ Manageable

But if you add:
Hosts: 100 unique hosts

Total streams = 10 × 3 × 2 × 100 = 6,000 streams ⚠️ Getting high

Then add:
User IDs: 10,000 unique users

Total streams = 10 × 3 × 2 × 100 × 10,000 = 60,000,000 streams ❌ Cardinality explosion!
```

**Impact of High Cardinality:**
- Increased memory usage (each stream needs in-memory index)
- Slower queries (more streams to search)
- Higher storage costs (metadata overhead)
- Degraded ingestion performance
- System instability and potential outages

**Solution:**
Keep high-cardinality data in the log line itself, not in labels:

```yaml
# ❌ Bad: High cardinality in labels
{app="api", user_id="12345", request_id="abc-def-123"}

# ✅ Good: High cardinality in log content
{app="api"}
level=info user_id=12345 request_id=abc-def-123 msg="User logged in"
```

### Designing Label Schemas

**Good Label Schema Example:**

```yaml
# Service identification
app: "api" | "web" | "worker" | "database"

# Environment
environment: "prod" | "staging" | "dev"

# Infrastructure
region: "us-east" | "us-west" | "eu-central"
datacenter: "dc1" | "dc2"

# Kubernetes-specific
namespace: "default" | "production" | "monitoring"
container: "app" | "sidecar" | "init"

Total possible combinations: 4 × 3 × 3 × 2 × 3 × 3 = 648 streams ✅
```

**Typical Anti-patterns:**

```yaml
# ❌ Using host as a label with 100+ hosts
{app="nginx", host="web-01"}
{app="nginx", host="web-02"}
... 100+ streams just for nginx

# ✅ Better: Use a cluster or region label
{app="nginx", cluster="us-east"}
# Query for specific host in LogQL: |= "web-01"
```

### Deployment Modes

**1. Single Binary Mode (Monolithic)**
- All components run in one process
- Target: `all`
- Best for: Development, small deployments (< 100 GB/day)
- Simplest to operate

**2. Simple Scalable Deployment**
- Components grouped into three targets:
  - `read`: Query frontend, querier
  - `write`: Distributor, ingester
  - `backend`: Compactor, index gateway, ruler
- Best for: Medium deployments (100 GB - 1 TB/day)
- Balance of simplicity and scalability

**3. Microservices Mode**
- Each component runs as a separate service
- Maximum flexibility and scalability
- Best for: Large deployments (> 1 TB/day)
- More operational complexity
