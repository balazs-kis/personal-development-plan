## Introduction

On-call practices have evolved significantly in modern DevOps. The principle of "you build it, you maintain it" means developers are often on-call for the services they create. Sustainable on-call requires clear processes, proper tooling, and attention to team health to prevent burnout while maintaining service reliability.

## Key Concepts Summary

### On-Call Rotation Principles

**"You Build It, You Maintain It"**
Developers who created the code are best positioned to troubleshoot issues quickly, reducing MTTA (Mean Time to Alert) and MTTR (Mean Time to Recovery). This approach encourages more rigorous testing before deployment.

**Balanced Coverage:**
```markdown
## Sample On-Call Rotation

### Primary Rotation (1 week shifts)
- Week 1: Engineer A (Primary), Engineer B (Backup)
- Week 2: Engineer C (Primary), Engineer D (Backup)
- Week 3: Engineer E (Primary), Engineer A (Backup)
- Week 4: Engineer B (Primary), Engineer C (Backup)

### Considerations:
- Follow-the-sun support for global teams
- No consecutive weeks for the same person
- Backup engineer available for escalation
- Manager in escalation chain after 2nd level
```

**Compensation and Time Off:**
- On-call pay or comp time
- Post-incident recovery time
- Maximum alert thresholds per week
- Escalation to manager if exceeded

### Incident Management Workflow

**Phase 1: Detection and Triage (0-5 minutes)**

```markdown
## Incident Detected

1. **Alert Received**
   - PagerDuty pages on-call engineer
   - Alert includes: severity, service, description, runbook link
   
2. **Acknowledge Alert**
   - Click acknowledge in PagerDuty (stops escalation)
   - Opens incident in pending state
   
3. **Initial Assessment**
   - Check monitoring dashboards
   - Determine actual severity
   - Identify affected users/services
   
4. **Create Incident Channel**
   - Slack: #incident-2026-01-27-payment-outage
   - Post initial update: "Investigating payment service errors"
```

**Phase 2: Response and Mitigation (5-30 minutes)**

```markdown
## Active Response

1. **Execute Runbook**
   - Follow documented procedures
   - Document actions taken in incident channel
   
2. **Gather Additional Responders**
   - Page backup on-call if needed
   - Add subject matter experts
   - Assign roles:
     - Incident Commander (coordinates)
     - Technical Lead (fixes issue)
     - Communications Lead (updates stakeholders)
   
3. **Apply Mitigation**
   - Immediate fixes (restart, scale, circuit breaker)
   - Temporary workarounds if root cause unclear
   - Document all changes
   
4. **Verify Resolution**
   - Check metrics returning to normal
   - Confirm error rates dropping
   - Verify customer reports
```

**Phase 3: Resolution and Documentation (30+ minutes)**

```markdown
## Post-Mitigation

1. **Monitor Stability**
   - Watch for 15-30 minutes
   - Ensure issue doesn't recur
   - Keep incident channel active
   
2. **Update Stakeholders**
   - Post resolution in incident channel
   - Update status page if customer-facing
   - Notify leadership if major incident
   
3. **Complete Incident Report**
   - Timeline of events
   - Root cause analysis
   - Actions taken
   - Business impact
   
4. **Resolve in PagerDuty**
   - Mark incident as resolved
   - Triggers post-incident workflow
```

**Escalation Policy:**
```yaml
escalation_policy:
  name: "Engineering Team"
  escalation_rules:
    - escalation_delay_in_minutes: 0
      targets:
        - type: schedule
          id: primary-oncall-schedule
          
    - escalation_delay_in_minutes: 5
      targets:
        - type: schedule
          id: backup-oncall-schedule
          
    - escalation_delay_in_minutes: 15

        - type: user
```

### Incident Response Roles

**Incident Commander (IC):**
- Coordinates the response
- Manages communication
- Makes decisions about escalation
- Keeps incident channel organized

**Technical Lead:**
- Investigates root cause
- Executes remediation
- Reports findings to IC
- Documents technical details

**Communications Lead:**
- Updates stakeholders
- Manages status page
- Handles customer communications
- Briefs leadership

```markdown
## Example Incident Channel

@incident-commander: Incident #1234 - Payment API degraded
Severity: High | Started: 14:32 UTC

14:32 - @tech-lead: Investigating elevated error rates
14:35 - @tech-lead: Database connection pool exhausted
14:37 - @tech-lead: Scaling connection pool from 50 to 100
14:40 - @comms-lead: Status page updated - investigating
14:42 - @tech-lead: Error rates returning to normal
14:45 - @incident-commander: Monitoring for stability
14:55 - @comms-lead: Status page updated - resolved
15:00 - @incident-commander: Closing incident, postmortem scheduled
```

### Best Practices for Team Health

**Transparent Communication:**
- Set clear expectations upfront
- Define on-call responsibilities
- Communicate alert thresholds
- Regular check-ins with team

**Adequate Training:**
- Onboarding program for new on-call engineers
- Access to all necessary tools and documentation
- Shadow experienced engineers during rotation
- Practice with incident drills

**Monitor for Burnout:**
```markdown
## Warning Signs:
- Excessive alerts (>10 per shift)
- Multiple consecutive sleepless nights
- Decreased code quality
- Disengagement from team

## Actions:
- Adjust alert thresholds
- Add automation
- Rotate more frequently
- Provide recovery time
```

**Clear Handoffs:**

### Incident Documentation

**Incident Report Template:**
```markdown
# Incident Report #1234

## Summary
Payment API experienced elevated error rates affecting ~15% of checkout attempts.

## Impact
- **Duration:** 2026-01-27 14:32-14:55 UTC (23 minutes)
- **Affected users:** ~1,500 customers
- **Failed transactions:** ~350
- **Revenue impact:** ~$50,000 in delayed transactions

## Timeline
- 14:32 - Alert fired: High error rate
- 14:33 - On-call acknowledged
- 14:35 - Root cause identified: Connection pool exhausted
- 14:37 - Mitigation: Increased connection pool size
- 14:42 - Error rates returned to normal
- 14:55 - Incident resolved

## Root Cause
Database connection pool configured for 50 connections. Recent traffic increase pushed connection demand above this limit, causing new requests to timeout.

## Resolution
Increased connection pool size from 50 to 100 connections.

## Follow-up Actions
- [ ] Add monitoring for connection pool usage (@engineer-a)
- [ ] Review and right-size connection pools for all services (@team-lead)
- [ ] Add capacity planning process (@eng-manager)

## Lessons Learned
**What went well:**
- Alert fired quickly
- Runbook was helpful
- Team responded efficiently

**What could be improved:**
- Connection pool monitoring was missing
- No capacity planning for connection pools
- Need better load testing before traffic increases
```
