# Lesson 4: Runbooks and Playbooks

## Learning Objectives

By the end of this lesson, you will be able to:
- Distinguish between runbooks and playbooks
- Create effective runbooks with clear step-by-step instructions
- Develop incident response playbooks
- Apply best practices for runbook structure and maintenance
- Test and validate runbook effectiveness

---

## Introduction

Runbooks and playbooks are essential documentation that guide responders through well-understood procedures and incident response scenarios. Well-written runbooks reduce mean time to resolution (MTTR), minimize human error, and enable new team members to handle incidents effectively.

## Key Concepts Summary

### Runbooks vs Playbooks

**Runbooks:**
- Step-by-step procedures for specific, well-understood tasks
- Single purpose, decision-tree format
- Used during incidents or routine operations
- Example: "How to restart the payment service"

**Playbooks:**
- Broader prescriptive guidance for incident types
- Covers investigation, communication, and response
- Multiple decision points and branching
- Example: "How to respond to a data breach"

### Runbook Structure

Every runbook should include:

```markdown
# Runbook: [Task Name]

## Overview
- **Purpose:** Brief description of what this runbook achieves
- **When to use:** Triggering conditions or scenarios
- **Estimated time:** How long the procedure takes
- **Risk level:** Low/Medium/High

## Prerequisites
- Required permissions/access
- Tools needed
- Knowledge/skills required

## Procedure

### Step 1: [Action]
**Description:** What you're doing and why

**Command:**
```bash
kubectl get pods -n production
```

**Expected output:**
```
NAME                READY   STATUS
api-server-1        1/1     Running
api-server-2        1/1     Running
```

**Verification:**
- All pods should show "Running" status
- READY column should show "1/1"

**If verification fails:** → Go to Step 5 (Rollback)

### Step 2: [Action]
...

## Verification
- How to confirm the procedure succeeded
- Metrics or indicators to check
- Dashboard links

## Rollback
- Steps to undo changes if something goes wrong
- Recovery procedures

## Related Resources
- Dashboard: [link]
- Logs: [link]
- Related runbooks: [links]
- Escalation contact: @team-lead
```

### Best Practices for Runbooks

**1. Make Them Actionable**
```markdown
# Good: Specific, actionable steps
1. SSH to the primary database server: ssh db-prod-01.company.com
2. Check replication lag: SELECT pg_last_wal_receive_lsn()
3. If lag > 1GB, restart replication: SELECT pg_start_replication()

# Bad: Vague instructions
1. Check the database
2. Fix any issues
3. Monitor for problems
```

**2. Keep Them Clear and Concise**
- Incidents are high-pressure situations
- Trim unnecessary explanations
- Use bullet points and short paragraphs
- Highlight critical warnings

```markdown
⚠️ **WARNING:** This command will restart the service and drop active connections.

✅ **CHECKPOINT:** Verify no critical batch jobs are running before proceeding.
```

**3. Include Visual Aids Sparingly**
```markdown
# Include architecture diagrams only if they simplify understanding
![Traffic flow during incident](./diagrams/traffic-flow.png)

# Keep them minimal - don't overwhelm with details
```

**4. Test with New Team Members**
- Avoid "curse of knowledge"
- Have someone unfamiliar run through the runbook
- Identify confusing steps or missing context

**5. Link to Relevant Resources**
```markdown
## Quick Links
- **Dashboard:** https://grafana.company.com/d/api-dashboard
- **Logs:** https://loki.company.com/explore?service=api-server
- **Recent changes:** https://github.com/company/api/commits/main
- **On-call schedule:** https://pagerduty.company.com/schedules
```

### Incident Response Playbook Structure

```markdown
# Playbook: [Incident Type]

## Incident Classification
- **Type:** Security / Performance / Availability
- **Severity:** Critical / High / Medium / Low
- **Affected services:** [List]

## Initial Response (First 5 Minutes)

### 1. Assess Impact
- [ ] Check error rates in monitoring dashboard
- [ ] Review recent deployments or changes
- [ ] Identify affected customers/regions
- [ ] Estimate business impact

### 2. Establish Communication
- [ ] Create incident Slack channel: #incident-YYYYMMDD-description
- [ ] Page additional responders if needed
- [ ] Post initial status update

### 3. Begin Investigation
- [ ] Check monitoring dashboards: [links]
- [ ] Review error logs: [links]
- [ ] Examine traces for failed requests
- [ ] Review recent changes in CI/CD

## Investigation Phase

### Common Causes and Solutions

**Scenario 1: Database Connection Pool Exhausted**
- Symptoms: Connection timeout errors, slow queries
- Investigation: Check connection pool metrics
- Solution: → See Runbook: Restart Application Servers
- Escalation: If persists after restart, page @database-team

**Scenario 2: Downstream Service Degraded**
- Symptoms: Elevated latency, timeout errors
- Investigation: Check service dependency map
- Solution: → Enable circuit breaker, see Runbook: Enable Circuit Breaker
- Communication: Notify dependent team

**Scenario 3: Resource Exhaustion**
- Symptoms: High CPU/memory, pod restarts
- Investigation: Check resource usage trends
- Solution: → See Runbook: Scale Service Instances
- Prevention: Review resource limits

## Resolution Phase

### Mitigation Steps
1. Apply immediate fix (restart, scale, circuit breaker)
2. Verify metrics returning to normal
3. Monitor for 15 minutes to ensure stability

### Communication
- Post resolution update in incident channel
- Update status page if customer-facing
- Notify stakeholders of resolution

## Post-Incident

### Documentation
- [ ] Complete incident report
- [ ] Document timeline of events
- [ ] Identify what went well and what didn't

### Follow-up
- [ ] Schedule postmortem meeting (within 48 hours)
- [ ] Create action items for prevention
- [ ] Update runbooks based on learnings
- [ ] Share learnings with broader team

## Escalation Contacts
- **L1:** On-call engineer (PagerDuty)
- **L2:** Team lead @team-lead
- **L3:** Engineering manager @eng-manager
- **External:** Vendor support (for third-party service issues)
```

### Prioritizing Runbook Creation

Start with the most valuable runbooks:

1. **Frequently executed procedures**
   - Daily/weekly operational tasks
   - Common troubleshooting steps

2. **Procedures with high error rates**
   - Steps that are often done incorrectly
   - Complex multi-step processes

3. **Procedures with significant business impact**
   - Production deployments
   - Database migrations
   - Security incident response

### Runbook Maintenance

```markdown
## Runbook Metadata
- **Created:** 2025-12-01
- **Last updated:** 2026-01-15
- **Last tested:** 2026-01-20
- **Owner:** @infrastructure-team
- **Review frequency:** Quarterly

## Change Log
- 2026-01-15: Updated kubectl commands for v1.28
- 2025-12-15: Added rollback section
- 2025-12-01: Initial version
```

**Maintenance practices:**
- Review runbooks quarterly
- Update after incidents reveal gaps
- Archive outdated runbooks
- Test runbooks during incident drills
