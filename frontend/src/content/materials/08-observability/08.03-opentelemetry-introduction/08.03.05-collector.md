## Introduction

The OpenTelemetry Collector is a vendor-agnostic proxy that receives, processes, and exports telemetry data. It acts as a central hub for your observability data, allowing you to decouple your applications from specific observability backends, perform data transformation and filtering, and efficiently route telemetry to multiple destinations.

## Key Concepts Summary

### What is the OpenTelemetry Collector?

The **OpenTelemetry Collector** is a vendor-agnostic service that:
- **Receives** telemetry data in multiple formats
- **Processes** data (filters, transforms, batches, samples)
- **Exports** data to one or more backends

```
┌──────────────┐
│ Application 1│───┐
└──────────────┘   │
                   │    ┌────────────────┐         ┌──────────┐
┌──────────────┐   ├───→│   Collector    │────────→│  Jaeger  │
│ Application 2│───┤    │                │    ┌───→│ Prometheus│
└──────────────┘   │    │ Receive        │────┤    │   Loki   │
                   │    │ Process        │    └───→│  Others  │
┌──────────────┐   │    │ Export         │         └──────────┘
│ Application 3│───┘    └────────────────┘
└──────────────┘
```

### Why Use the Collector?

**Key Benefits:**

1. **Decoupling:** Applications don't need to know about backends
   ```
   Without Collector:
   App → Jaeger (hard-coded)
   
   With Collector:
   App → Collector → Any backend (configurable)
   ```

2. **Centralized Processing:** Do heavy work once, not in every app
   - Batching
   - Sampling
   - Enrichment
   - Filtering

3. **Multiple Backends:** Send data to many destinations
   ```yaml
   exporters:
     jaeger:
     prometheus:
     otlp/cloud:
   ```

4. **Resilience:** Buffer and retry if backends are unavailable

5. **Security:** Single point for credentials and TLS configuration

### Deployment Patterns

#### 1. Agent Pattern

Collector runs **alongside each application** (same host/pod):

```
┌─────────────────────────────────────┐
│         Kubernetes Pod              │
│                                     │
│  ┌──────────┐    ┌──────────────┐  │
│  │   App    │───→│   Collector  │──┼──→ Backends
│  │          │    │   (Agent)    │  │
│  └──────────┘    └──────────────┘  │
└─────────────────────────────────────┘
```

**When to use:**
- Initial telemetry processing
- Enrichment with local context
- Reducing application overhead
- Each service needs different configuration

**Pros:**
- ✓ Low latency
- ✓ Independent scaling
- ✓ Local enrichment

**Cons:**
- ✗ More resource usage (collector per app)
- ✗ Distributed configuration

#### 2. Gateway Pattern

Collector runs as a **central service**:

```
┌──────┐    ┌──────┐    ┌──────┐
│ App 1│───→│ App 2│───→│ App 3│
└──────┘    └──────┘    └──────┘
     │           │           │
     └───────────┼───────────┘
                 ↓
         ┌──────────────┐
         │  Collector   │
         │  (Gateway)   │
         └──────────────┘
                 ↓
         ┌──────────────┐
         │   Backends   │
         └──────────────┘
```

**When to use:**
- Centralized telemetry processing
- Load balancing across backends
- Sensitive credential management
- Complex processing pipelines

**Pros:**
- ✓ Centralized configuration
- ✓ Resource efficiency
- ✓ Easier security management

**Cons:**
- ✗ Single point of failure (mitigate with HA)
- ✗ Network hop adds latency

#### 3. Hybrid Pattern

Combine both: Agent → Gateway → Backends

```
Apps → Agent Collectors → Gateway Collector → Backends
```

**Use case:** Initial processing at agent, heavy processing at gateway

### Collector Architecture

The Collector uses a **pipeline model**:

```
┌─────────────┐    ┌────────────┐    ┌───────────┐
│  Receivers  │───→│ Processors │───→│ Exporters │
└─────────────┘    └────────────┘    └───────────┘
     ↑                                      ↓
   Ingest                                 Send
```

#### Components

**1. Receivers:** Ingest telemetry

Available receivers:
- `otlp`: OpenTelemetry Protocol (recommended)
- `jaeger`: Jaeger format
- `zipkin`: Zipkin format
- `prometheus`: Prometheus metrics scraping
- `kafka`: Receive from Kafka

**2. Processors:** Transform telemetry

Common processors:
- `batch`: Batch spans for efficiency
- `memory_limiter`: Prevent OOM
- `resource`: Add/modify resource attributes
- `filter`: Drop unwanted telemetry
- `attributes`: Modify span attributes
- `tail_sampling`: Sample based on complete traces

**3. Exporters:** Send telemetry

Available exporters:
- `otlp`: Send via OTLP
- `jaeger`: Export to Jaeger
- `prometheus`: Expose metrics for scraping
- `logging`: Log to console (debugging)
- `kafka`: Send to Kafka

### Configuration Example

Basic configuration structure:

```yaml
# Receivers: how data gets into the Collector
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

# Processors: what to do with received data
processors:
  batch:
    timeout: 10s
    send_batch_size: 1024
  
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
  
  resource:
    attributes:
      - key: environment
        value: production
        action: insert

# Exporters: where to send the data
exporters:
  otlp/jaeger:
    endpoint: jaeger:4317
    tls:
      insecure: true
  
  prometheus:
    endpoint: 0.0.0.0:8889
  
  logging:
    loglevel: info

# Service: tie everything together
service:
  pipelines:
    # Traces pipeline
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch, resource]
      exporters: [otlp/jaeger, logging]
    
    # Metrics pipeline
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [prometheus, logging]
```

### Running the Collector

#### Docker

```bash
# Pull the image
docker pull otel/opentelemetry-collector:latest

# Run with config file
docker run -d \
  -v $(pwd)/config.yaml:/etc/otel/config.yaml \
  -p 4317:4317 \
  -p 4318:4318 \
  -p 8889:8889 \
  otel/opentelemetry-collector:latest \
  --config=/etc/otel/config.yaml
```

#### Kubernetes

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: otel-collector
spec:
  replicas: 1
  selector:
    matchLabels:
      app: otel-collector
  template:
    metadata:
      labels:
        app: otel-collector
    spec:
      containers:
      - name: otel-collector
        image: otel/opentelemetry-collector:latest
        ports:
        - containerPort: 4317  # OTLP gRPC
        - containerPort: 4318  # OTLP HTTP
        volumeMounts:
        - name: config
          mountPath: /etc/otel
      volumes:
      - name: config
        configMap:
          name: otel-collector-config
---
apiVersion: v1
kind: Service
metadata:
  name: otel-collector
spec:
  selector:
    app: otel-collector
  ports:
  - name: otlp-grpc
    port: 4317
    targetPort: 4317
  - name: otlp-http
    port: 4318
    targetPort: 4318
```

### Connecting Applications to the Collector

From your .NET application:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddOtlpExporter(options =>
        {
            // Point to Collector, not final backend
            options.Endpoint = new Uri("http://otel-collector:4317");
            options.Protocol = OtlpExportProtocol.Grpc;
        }));
```

### Common Processor Patterns

**1. Filtering Out Health Checks:**
```yaml
processors:
  filter:
    traces:
      span:
        - 'attributes["http.target"] == "/health"'
```

**2. Sampling:**
```yaml
processors:
  probabilistic_sampler:
    sampling_percentage: 10  # Sample 10%
```

**3. Adding Standard Attributes:**
```yaml
processors:
  resource:
    attributes:
      - key: environment
        value: production
        action: insert
      - key: cluster
        value: us-east-1
        action: insert
```

**4. Tail Sampling (Advanced):**
```yaml
processors:
  tail_sampling:
    policies:
      - name: errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: slow
        type: latency
        latency:
          threshold_ms: 1000
```

### When to Use the Collector

**Use the Collector when you need to:**
- ✓ Send telemetry to multiple backends
- ✓ Perform centralized sampling or filtering
- ✓ Enrich telemetry with environment context
- ✓ Buffer telemetry during backend outages
- ✓ Isolate applications from backend changes
- ✓ Handle sensitive credentials centrally

**Direct export may be sufficient when:**
- Single backend with simple requirements
- Minimal processing needed
- Reduced operational complexity is priority

## Key Takeaways

- The **Collector** is a vendor-agnostic proxy for telemetry data
- Pipelines consist of **receivers → processors → exporters**
- **Agent pattern**: Collector per application
- **Gateway pattern**: Centralized collector
- Use collectors to **decouple** apps from backends
- **Processors** enable filtering, sampling, and enrichment
- The Collector **buffers** data and provides resilience
- Configure via **YAML** and deploy via Docker/Kubernetes
