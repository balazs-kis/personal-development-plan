## Introduction

OpenTelemetry's architecture is designed to be modular, extensible, and language-agnostic. Understanding how the pieces fit together—the specification, APIs, SDKs, instrumentation libraries, and semantic conventions—is essential for effectively implementing observability in your applications.

## Key Concepts Summary

### OpenTelemetry Architecture Layers

OpenTelemetry consists of several interconnected layers:

```
┌─────────────────────────────────────────────────┐
│           Your Application Code                 │
└─────────────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│     OpenTelemetry API (create spans, metrics)   │
└─────────────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│  OpenTelemetry SDK (sampling, processing, etc.) │
└─────────────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│      Exporters (send to backends)               │
└─────────────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│   Observability Backends (Jaeger, Prometheus)   │
└─────────────────────────────────────────────────┘
```

### Core Components

#### 1. Specification

The **specification** is the cross-language requirements document that defines:
- **API specification:** Defines the contract for generating telemetry
- **SDK specification:** Defines the implementation requirements
- **Data specification:** Defines the OTLP protocol and data formats
- **Semantic conventions:** Defines standard attributes and naming

**Why it matters:** Ensures consistency across all language implementations.

#### 2. API

The **API** is the interface your application code uses:
```csharp
// Example: Creating a span using the API
using var activity = activitySource.StartActivity("ProcessOrder");
activity?.SetTag("order.id", orderId);
activity?.SetTag("customer.id", customerId);
```

Key characteristics:
- **Stable and minimal:** Changes rarely to avoid breaking applications
- **Language-specific:** Idiomatic for each programming language
- **No implementation:** Just defines the contract

#### 3. SDK

The **SDK** is the implementation of the API:
```csharp
// Example: Configuring the SDK
var tracerProvider = Sdk.CreateTracerProviderBuilder()
    .AddSource("MyCompany.MyApp")
    .SetSampler(new TraceIdRatioBasedSampler(0.1)) // Sample 10%
    .AddConsoleExporter()
    .Build();
```

Responsibilities:
- **Sampling:** Decide which traces to keep
- **Processing:** Batch, filter, enrich telemetry
- **Resource detection:** Auto-detect environment information
- **Exporting:** Send data to backends

#### 4. Instrumentation Libraries

**Instrumentation libraries** provide automatic telemetry for popular frameworks:

```csharp
// Automatic instrumentation for ASP.NET Core
services.AddOpenTelemetry()
    .WithTracing(builder => builder
        .AddAspNetCoreInstrumentation()  // Automatic HTTP tracing
        .AddHttpClientInstrumentation()  // Automatic outbound HTTP tracing
        .AddSqlClientInstrumentation()); // Automatic SQL tracing
```

Benefits:
- No manual span creation needed
- Framework-specific best practices
- Consistent instrumentation across applications

#### 5. Exporters

**Exporters** send telemetry data to backends:

```csharp
// Multiple exporters can be configured
.AddOtlpExporter(options => {
    options.Endpoint = new Uri("http://localhost:4317");
})
.AddConsoleExporter()
.AddJaegerExporter();
```

Types:
- **OTLP (recommended):** Native OpenTelemetry protocol
- **Vendor-specific:** Jaeger, Zipkin, Prometheus
- **Cloud-native:** Azure Monitor, AWS X-Ray, Google Cloud Trace

#### 6. Collector (Optional)

The **Collector** is a vendor-agnostic proxy:
```
Applications → Collector → Multiple Backends
```

Capabilities:
- Receive telemetry from multiple sources
- Process, filter, sample, and enrich data
- Fan out to multiple backends
- Offload processing from applications

### Semantic Conventions

**Semantic conventions** standardize attribute names and values:

```csharp
// Without semantic conventions (bad)
activity?.SetTag("user", userId);
activity?.SetTag("method", "GET");

// With semantic conventions (good)
activity?.SetTag("enduser.id", userId);
activity?.SetTag("http.method", "GET");
activity?.SetTag("http.status_code", 200);
```

Benefits:
- **Consistency:** Same attribute names across all applications
- **Tooling support:** Backends recognize standard attributes
- **Best practices:** Proven naming and structure

Key semantic convention areas:
- HTTP requests/responses
- Database operations
- RPC calls
- Messaging systems
- Cloud resources

### Data Flow Example

```
1. Application code calls API
   └─> activity = activitySource.StartActivity("ProcessOrder")

2. SDK processes the call
   └─> Applies sampling decision
   └─> Adds resource attributes (service name, version, etc.)
   └─> Enriches with context (trace ID, parent span ID)

3. Activity completes
   └─> activity.Dispose()

4. SDK batches and processes
   └─> Applies processors (filtering, batching)

5. Exporter sends data
   └─> Sends to Jaeger via OTLP
   └─> Sends to console for debugging
```

## Key Takeaways

- OpenTelemetry architecture is **layered**: Specification → API → SDK → Exporters
- The **API** is what your code uses; the **SDK** is the implementation
- **Instrumentation libraries** provide automatic telemetry for frameworks
- **Semantic conventions** ensure consistency across applications
- The **Collector** is optional but provides powerful data processing capabilities
- All components work together to provide **vendor-neutral observability**
