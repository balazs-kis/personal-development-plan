## Introduction

Exporters are the bridge between your instrumented application and observability backends. They take the telemetry data collected by OpenTelemetry SDKs and send it to your chosen backend systems—whether that's Jaeger for traces, Prometheus for metrics, or cloud-native services like Azure Application Insights. Understanding exporters is key to integrating OpenTelemetry with your observability stack.

## Key Concepts Summary

### What Are Exporters?

**Exporters** are components that send telemetry data from your application to observability backends. They translate the OpenTelemetry data model into the format expected by the target system.

```
Your App → SDK → Exporter → Backend
                   ↓
        (OTLP, Jaeger, Prometheus format)
```

### Exporter Types

OpenTelemetry provides several types of exporters:

#### 1. OTLP Exporter (Recommended)

**OpenTelemetry Protocol (OTLP)** is the native protocol for OpenTelemetry data.

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddOtlpExporter(options =>
        {
            options.Endpoint = new Uri("http://localhost:4317");
            options.Protocol = OtlpExportProtocol.Grpc;
        }));
```

**Why OTLP is preferred:**
- ✓ Native OpenTelemetry format (no translation needed)
- ✓ Supports all three signals (traces, metrics, logs)
- ✓ Efficient binary format (Protocol Buffers)
- ✓ Works with OpenTelemetry Collector
- ✓ Supported by most modern backends

**OTLP Protocols:**
- **gRPC** (port 4317): More efficient, recommended
- **HTTP/Protobuf** (port 4318): Better firewall compatibility
- **HTTP/JSON** (port 4318): Human-readable, debugging

#### 2. Console Exporter (Development)

Prints telemetry to the console—ideal for development and debugging.

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddConsoleExporter(options =>
        {
            options.Targets = ConsoleExporterOutputTargets.Console;
        }));
```

**When to use:**
- ✓ Local development
- ✓ Debugging instrumentation
- ✓ Verifying telemetry data
- ✗ NOT for production

#### 3. Vendor-Specific Exporters

Direct exporters for specific backends:

**Jaeger Exporter:**
```csharp
.WithTracing(tracing => tracing
    .AddJaegerExporter(options =>
    {
        options.AgentHost = "localhost";
        options.AgentPort = 6831;
    }))
```

**Zipkin Exporter:**
```csharp
.WithTracing(tracing => tracing
    .AddZipkinExporter(options =>
    {
        options.Endpoint = new Uri("http://localhost:9411/api/v2/spans");
    }))
```

**Prometheus Exporter:**
```csharp
.WithMetrics(metrics => metrics
    .AddPrometheusExporter())

// Add endpoint for Prometheus scraping
app.MapPrometheusScrapingEndpoint();
```

#### 4. Cloud Provider Exporters

**Azure Monitor (Application Insights):**
```csharp
builder.Services.AddOpenTelemetry()
    .UseAzureMonitor(options =>
    {
        options.ConnectionString = "InstrumentationKey=...";
    });
```

**AWS X-Ray:**
```csharp
.WithTracing(tracing => tracing
    .AddXRayTraceId()
    .AddAWSInstrumentation()
    .AddOtlpExporter(options =>
    {
        options.Endpoint = new Uri("http://localhost:4317");
    }))
```

### Configuring Multiple Exporters

You can send telemetry to multiple backends simultaneously:

```csharp
builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource
        .AddService("order-service"))
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        // Export to console for debugging
        .AddConsoleExporter()
        // Export to Jaeger for distributed tracing
        .AddOtlpExporter(options =>
        {
            options.Endpoint = new Uri("http://jaeger:4317");
        })
        // Export to Azure Monitor for production monitoring
        .UseAzureMonitor());
```

**Use cases for multiple exporters:**
- Console + Production: Debug locally while monitoring production
- Multiple backends: Send to both Jaeger (tracing) and Prometheus (metrics)
- Hybrid cloud: Send to on-premises and cloud backends

### Exporter Configuration Options

#### Batching

Exporters typically batch telemetry for efficiency:

```csharp
.WithTracing(tracing => tracing
    .AddOtlpExporter()
    .AddProcessor(new BatchActivityExportProcessor(
        exporter,
        maxQueueSize: 2048,
        scheduledDelayMilliseconds: 5000,
        exporterTimeoutMilliseconds: 30000,
        maxExportBatchSize: 512)))
```

**Parameters:**
- `maxQueueSize`: Maximum spans queued before dropping
- `scheduledDelayMilliseconds`: How often to export batches
- `exporterTimeoutMilliseconds`: Timeout for export operation
- `maxExportBatchSize`: Maximum spans per batch

#### Headers and Authentication

Add authentication headers for secure backends:

```csharp
.AddOtlpExporter(options =>
{
    options.Endpoint = new Uri("https://api.observability.com:4317");
    options.Headers = "Authorization=Bearer YOUR_TOKEN";
})
```

#### Retry and Timeout

```csharp
.AddOtlpExporter(options =>
{
    options.TimeoutMilliseconds = 10000; // 10 seconds
    options.ExportProcessorType = ExportProcessorType.Batch;
})
```

### Choosing the Right Exporter

```
Decision Tree:

Using OpenTelemetry Collector?
├─ Yes → Use OTLP exporter
│        (Let collector handle routing)
└─ No → Direct export
    ├─ Cloud platform? → Use cloud exporter
    │   ├─ Azure → UseAzureMonitor()
    │   ├─ AWS → X-Ray exporter
    │   └─ GCP → Google Cloud exporter
    │
    ├─ Self-hosted backend?
    │   ├─ Supports OTLP? → Use OTLP exporter (preferred)
    │   └─ No OTLP? → Use specific exporter (Jaeger, Zipkin)
    │
    └─ Development? → Console exporter
```

### Best Practices

**1. Prefer OTLP When Possible:**
```csharp
// Good - use OTLP
.AddOtlpExporter(options => { ... })

// Less ideal - vendor-specific format
.AddJaegerExporter(options => { ... })
```

**2. Use Collector in Production:**
```csharp
// Application exports to Collector (OTLP)
.AddOtlpExporter(options =>
{
    options.Endpoint = new Uri("http://otel-collector:4317");
})

// Collector routes to multiple backends
```

**3. Handle Export Failures Gracefully:**
```csharp
// Configure timeouts and batching
.AddOtlpExporter(options =>
{
    options.TimeoutMilliseconds = 5000;
    options.ExportProcessorType = ExportProcessorType.Batch;
})
```

**4. Avoid Console Exporter in Production:**
```csharp
#if DEBUG
    .AddConsoleExporter()
#else
    .AddOtlpExporter(options => { ... })
#endif
```

### Signal-Specific Exporters

Different signals may require different exporters:

```csharp
builder.Services.AddOpenTelemetry()
    // Traces to Jaeger
    .WithTracing(tracing => tracing
        .AddOtlpExporter(options =>
        {
            options.Endpoint = new Uri("http://jaeger:4317");
        }))
    // Metrics to Prometheus
    .WithMetrics(metrics => metrics
        .AddPrometheusExporter())
    // Logs to Loki (via OTLP Collector)
    .WithLogging(logging => logging
        .AddOtlpExporter(options =>
        {
            options.Endpoint = new Uri("http://collector:4317");
        }));
```

## Key Takeaways

- **Exporters** send telemetry from your app to observability backends
- **OTLP** is the recommended protocol (native, efficient, universal)
- You can **export to multiple backends** simultaneously
- **Console exporter** is for development only
- Use the **Collector** in production for flexibility and resilience
- Different **signals** (traces, metrics, logs) can use different exporters
- Always configure **timeouts and batching** for production
