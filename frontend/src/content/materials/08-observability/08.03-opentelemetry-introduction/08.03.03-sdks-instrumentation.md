## Introduction

Instrumentation is how you add observability to your applications. OpenTelemetry provides two primary approaches: automatic instrumentation (zero-code) and manual instrumentation (code-based). Understanding when and how to use each approach is critical for effective observability implementation.

## Key Concepts Summary

### Instrumentation Approaches

OpenTelemetry offers two main instrumentation strategies:

#### 1. Automatic Instrumentation (Zero-Code)

**What it is:**
Instrumentation that happens without modifying application code, using agents or libraries that automatically capture telemetry from frameworks and libraries.

**How it works:**
```csharp
// Automatic instrumentation - no span creation needed
services.AddOpenTelemetry()
    .WithTracing(builder => builder
        .AddAspNetCoreInstrumentation()  // Auto-traces HTTP requests
        .AddHttpClientInstrumentation()  // Auto-traces HTTP calls
        .AddSqlClientInstrumentation()); // Auto-traces SQL queries
```

**Pros:**
- ✓ Minimal code changes
- ✓ Quick to implement
- ✓ Captures standard operations automatically
- ✓ Consistent across applications

**Cons:**
- ✗ Less control over what's captured
- ✗ May capture too much or too little
- ✗ Framework/library dependent

**When to use:**
- Getting started with OpenTelemetry
- Instrumenting third-party libraries
- Standard framework operations (HTTP, database, messaging)

#### 2. Manual Instrumentation

**What it is:**
Explicit code that creates spans, records metrics, and logs events at specific points in your application.

**How it works:**
```csharp
public class OrderService
{
    private static readonly ActivitySource _activitySource = 
        new ActivitySource("MyCompany.OrderService");

    public async Task<Order> ProcessOrder(int orderId)
    {
        // Manual span creation
        using var activity = _activitySource.StartActivity("ProcessOrder");
        activity?.SetTag("order.id", orderId);
        
        try
        {
            var order = await _repository.GetOrder(orderId);
            activity?.SetTag("order.total", order.Total);
            
            await _paymentService.ChargeCustomer(order);
            activity?.SetTag("payment.status", "success");
            
            return order;
        }
        catch (Exception ex)
        {
            activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
            activity?.RecordException(ex);
            throw;
        }
    }
}
```

**Pros:**
- ✓ Complete control over telemetry
- ✓ Capture business-specific context
- ✓ Fine-grained instrumentation
- ✓ Custom attributes and events

**Cons:**
- ✗ Requires code changes
- ✗ More development effort
- ✗ Must maintain instrumentation code

**When to use:**
- Business-critical operations
- Custom logic requiring detailed observability
- Domain-specific context needed
- Performance-sensitive code paths

### SDK Configuration

#### Basic Setup

```csharp
var builder = WebApplication.CreateBuilder(args);

// Add OpenTelemetry services
builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource
        .AddService("my-service", serviceVersion: "1.0.0"))
    .WithTracing(tracing => tracing
        .AddSource("MyCompany.*")  // Listen to our ActivitySources
        .AddAspNetCoreInstrumentation()
        .AddConsoleExporter())
    .WithMetrics(metrics => metrics
        .AddAspNetCoreInstrumentation()
        .AddConsoleExporter());
```

#### Key Configuration Options

**Resource Attributes:**
```csharp
.ConfigureResource(resource => resource
    .AddService(
        serviceName: "order-service",
        serviceVersion: "1.0.0",
        serviceInstanceId: Environment.MachineName)
    .AddAttributes(new Dictionary<string, object>
    {
        ["deployment.environment"] = "production",
        ["service.namespace"] = "ecommerce"
    }))
```

**Sampling:**
```csharp
.WithTracing(tracing => tracing
    .SetSampler(new TraceIdRatioBasedSampler(0.1))) // Sample 10%
```

**Processors:**
```csharp
.WithTracing(tracing => tracing
    .AddProcessor(new BatchActivityExportProcessor(exporter)))
```

### Creating Custom Spans

```csharp
public class InventoryService
{
    private static readonly ActivitySource _activitySource = 
        new ActivitySource("MyCompany.InventoryService");

    public async Task<bool> CheckInventory(int productId, int quantity)
    {
        // Create a span
        using var activity = _activitySource.StartActivity(
            "CheckInventory",
            ActivityKind.Internal);
        
        // Add attributes
        activity?.SetTag("product.id", productId);
        activity?.SetTag("quantity.requested", quantity);
        
        var available = await _repository.GetAvailableQuantity(productId);
        activity?.SetTag("quantity.available", available);
        
        var result = available >= quantity;
        
        // Add event
        activity?.AddEvent(new ActivityEvent("InventoryChecked", 
            tags: new ActivityTagsCollection
            {
                ["result"] = result
            }));
        
        return result;
    }
}
```

### Recording Metrics

```csharp
public class OrderMetrics
{
    private readonly Counter<long> _orderCounter;
    private readonly Histogram<double> _orderValue;
    
    public OrderMetrics(IMeterFactory meterFactory)
    {
        var meter = meterFactory.Create("MyCompany.Orders");
        
        _orderCounter = meter.CreateCounter<long>(
            "orders.created",
            unit: "orders",
            description: "Number of orders created");
            
        _orderValue = meter.CreateHistogram<double>(
            "order.value",
            unit: "USD",
            description: "Order value in dollars");
    }
    
    public void RecordOrder(Order order)
    {
        _orderCounter.Add(1, 
            new KeyValuePair<string, object>("order.status", order.Status));
        _orderValue.Record(order.Total,
            new KeyValuePair<string, object>("order.currency", order.Currency));
    }
}
```

### Instrumentation Best Practices

**1. Use Semantic Conventions:**
```csharp
// Good - follows semantic conventions
activity?.SetTag("http.method", "GET");
activity?.SetTag("http.status_code", 200);
activity?.SetTag("db.system", "postgresql");

// Bad - custom attributes
activity?.SetTag("method", "GET");
activity?.SetTag("status", 200);
activity?.SetTag("database", "postgres");
```

**2. Don't Over-Instrument:**
```csharp
// Good - instrument at meaningful boundaries
using var activity = _activitySource.StartActivity("ProcessOrder");

// Bad - too granular
using var activity1 = _activitySource.StartActivity("ValidateOrder");
using var activity2 = _activitySource.StartActivity("CalculateTotal");
using var activity3 = _activitySource.StartActivity("ApplyDiscount");
```

**3. Include Relevant Context:**
```csharp
activity?.SetTag("user.id", userId);
activity?.SetTag("tenant.id", tenantId);
activity?.SetTag("order.type", orderType);
```

**4. Handle Errors Properly:**
```csharp
try
{
    await ProcessOrder(orderId);
    activity?.SetStatus(ActivityStatusCode.Ok);
}
catch (Exception ex)
{
    activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
    activity?.RecordException(ex);
    throw;
}
```

## Key Takeaways

- **Automatic instrumentation** requires minimal code but offers less control
- **Manual instrumentation** provides complete control and business context
- Use **`ActivitySource`** to create custom spans in .NET
- Follow **semantic conventions** for attribute names
- Add **relevant context** to spans (user ID, tenant ID, etc.)
- Always **handle errors** and set span status appropriately
- Start with automatic instrumentation, add manual where needed
