---

## Introduction

Service dependency analysis is a powerful feature of Jaeger that automatically discovers and visualizes how services in your distributed system interact with each other. By analyzing trace data, Jaeger builds a data-driven dependency graph that shows the complete architecture of your system, helping you understand service relationships, identify bottlenecks, and plan architectural changes.

## Key Concepts Summary

### What is Service Dependency Analysis?

Service dependency analysis is the process of:
1. **Discovering** which services call which other services
2. **Visualizing** these relationships as a graph
3. **Analyzing** the patterns, volumes, and characteristics of these interactions
4. **Identifying** architectural issues, bottlenecks, and optimization opportunities

**Data Source:** Trace data automatically collected from instrumented applications

### System Architecture View

**Accessing the Dependency Graph:**

In Jaeger UI:
1. Click **"System Architecture"** tab (or **"Dependencies"**)
2. Select time range
3. View the generated dependency graph

**Example Dependency Graph:**

```
       ┌──────────┐
       │ Frontend │
       └────┬─────┘
            │
     ┌──────┴──────┐
     │             │
     ↓             ↓
┌─────────┐   ┌─────────┐
│   Auth  │   │  Order  │
└────┬────┘   └────┬────┘
     │             │
     │        ┌────┴────┐
     │        │         │
     ↓        ↓         ↓
┌─────────┐ ┌────────┐ ┌─────────┐
│   DB    │ │   DB   │ │ Payment │
└─────────┘ └────────┘ └────┬────┘
                             │
                             ↓
                        ┌─────────┐
                        │ Stripe  │
                        │  API    │
                        └─────────┘
```

### Graph Elements

**Nodes (Services):**
- Each node represents a service
- Node size may indicate request volume
- Node color may indicate error rate or other metrics

**Edges (Dependencies):**
- Arrows show direction of calls (A → B means A calls B)
- Edge thickness may indicate call volume
- Edge color may indicate error rate

**Metrics Displayed:**
- Request count (calls between services)
- Error rate
- Average latency
- P95/P99 latency

### Understanding Service Relationships

**Upstream vs. Downstream:**

```
Frontend (upstream)
    ↓
  Order (current service)
    ↓
Payment (downstream)
```

- **Upstream:** Services that call this service (clients)
- **Downstream:** Services this service calls (dependencies)

**Service Patterns:**

**1. Entry Points (No Upstream)**
```
┌──────────┐
│ Frontend │ ← Entry point (public facing)
└────┬─────┘
```
- Services with no incoming edges
- Usually API gateways, frontends, or ingress points

**2. Leaf Services (No Downstream)**
```
     ↓
┌──────────┐
│ Database │ ← Leaf service
└──────────┘
```
- Services with no outgoing edges
- Usually databases, external APIs, or storage services

**3. Hub Services (Many Dependencies)**
```
   Service A
       ↓
┌───────────┐
│ Aggregator│ ← Hub service
└─────┬─────┘
      │
  ┌───┴───┬────────┬────────┐
  ↓       ↓        ↓        ↓
 Svc1    Svc2     Svc3     Svc4
```
- Services with many downstream dependencies
- Potential bottlenecks or single points of failure

**4. Shared Services**
```
Service A    Service B    Service C
    │            │            │
    └────────────┼────────────┘
                 ↓
         ┌─────────────┐
         │ Auth Service │ ← Shared service
         └─────────────┘
```
- Services called by many other services
- Critical infrastructure components

### Identifying Architectural Issues

**1. Circular Dependencies**

```
Service A
    ↓
Service B
    ↓
Service C
    ↓
Service A ⚠️ CIRCULAR!
```

**Problem:** Can cause deadlocks, cascading failures, hard to reason about
**Solution:** Refactor to break the cycle, usually by introducing an event bus or queue

**2. Chatty Services**

```
Service A ────→ Service B
    │              │
    │ (100 calls)  │
    └──────────────┘
```

**Problem:** Too many calls between services = high latency, network overhead
**Solution:** Batch requests, caching, or consolidate into single service

**3. Long Dependency Chains**

```
A → B → C → D → E → F → G ⚠️ Too long!
```

**Problem:** High latency (sum of all hops), fragility
**Solution:** Reduce chain length, parallelize, or cache intermediate results

**4. Single Points of Failure**

```
   All Services
       ↓
   Auth Service ⚠️ SPOF!
       ↓
     Database
```

**Problem:** If auth service fails, entire system fails
**Solution:** Redundancy, circuit breakers, graceful degradation

**5. Unexpected Dependencies**

```
Frontend Service
    ↓
Legacy DB ⚠️ Unexpected!
```

**Problem:** Service shouldn't talk directly to that resource
**Solution:** Enforce proper boundaries, use API gateway

### Analyzing Call Volume

**Request Volume:**

```
Frontend → Order: 10,000 req/min
Frontend → Auth: 10,000 req/min
Order → Payment: 5,000 req/min
Order → Inventory: 5,000 req/min
```

**Insights:**
- Frontend makes same number of auth and order calls (expected)
- Order only calls payment for half of requests (abandoned carts?)
- Inventory service gets same load as payment

**Capacity Planning:**
- If frontend scales 2x, order service needs 2x capacity
- Payment and inventory need to handle 50% of frontend load

### Error Rate Analysis

**Error Propagation:**

```
Service A (1% errors)
    ↓
Service B (5% errors) ⚠️
    ↓
Service C (10% errors) ⚠️
```

**Problem:** Errors amplifying downstream
**Possible Causes:**
- Service B/C can't handle retries
- Timeout configuration issues
- Circuit breakers not working

### Latency Analysis

**Critical Path Identification:**

```
Frontend (100ms total)
    ├─ Auth (10ms) ✅ Fast
    └─ Order (85ms)
        ├─ DB (5ms) ✅ Fast
        └─ Payment (75ms) ⚠️ Bottleneck!
            └─ External API (70ms) ⚠️ Root cause
```

**Insights:**
- Most time spent in payment → external API
- Total latency dominated by one slow call
- Opportunity for caching or async processing

### Using Dependencies for Architecture Evolution

**Before Refactoring:**

```
Monolith ← All traffic
```

**During Migration (Strangler Pattern):**

```
    Frontend
    │     │
    │     └──→ New Service (20%)
    │
    └──────→ Monolith (80%)
```

**After Migration:**

```
    Frontend
    ┌────┴────┬────────┬─────────┐
    ↓         ↓        ↓         ↓
  Auth     Order    User    Analytics
```

**Use dependency graph to:**
- Track migration progress
- Verify traffic routing
- Ensure no unexpected calls to monolith
- Monitor new service health

### Real-Time vs. Historical Analysis

**Real-Time (Last Hour):**
- Current system state
- Active dependencies
- Live traffic patterns

**Historical (Days/Weeks):**
- Identify unused dependencies
- Track dependency changes over time
- Capacity planning based on growth trends

**Example Query:**
"Show dependencies in last 24 hours where call count > 1000"

### Best Practices

**1. Regular Review**
- Weekly dependency graph review
- Identify new unexpected dependencies
- Track changes in traffic patterns

**2. Document Known Dependencies**
- Maintain architecture diagrams
- Compare Jaeger graph with documentation
- Update docs when discrepancies found

**3. Set Alerts**
- Alert on new unexpected dependencies
- Monitor critical service error rates
- Track latency of critical paths

**4. Use for Onboarding**
- Show new team members system architecture
- Trace requests through actual system
- Understand service ownership boundaries

**5. Capacity Planning**
- Use call volumes for scaling decisions
- Identify services that need autoscaling
- Plan for traffic growth
