## Introduction

Jaeger requires a persistent storage backend to store trace data. The choice of storage backend significantly impacts query performance, operational complexity, and cost. While Jaeger supports multiple backends, understanding their characteristics and trade-offs is essential for making informed decisions that align with your scale, budget, and operational capabilities.

## Key Concepts Summary

### Supported Storage Backends

Jaeger supports multiple storage backends:

**Production-Ready (Distributed):**
- **Elasticsearch** (Recommended)
- **OpenSearch** (Elasticsearch fork, recommended)
- **Cassandra**

**Single-Node/Testing:**
- **Badger** (embedded key-value store)
- **Memory** (in-memory, not persistent)

**Intermediate Buffer:**
- **Kafka** (not a storage backend, but a buffer between collector and storage)

### Elasticsearch / OpenSearch

**Architecture:**
```
Jaeger Collector
      ↓
Elasticsearch Cluster
  ├─ Node 1
  ├─ Node 2
  └─ Node 3
```

**Characteristics:**

**✅ Advantages:**
- **Powerful search** with full-text indexing
- **Rich aggregations** for analytics
- **Query flexibility** for complex trace searches
- **Queryable from Kibana** for custom dashboards
- **Single write per trace** (indexing handled internally)
- **Better query performance** for complex searches
- **Native JSON support** matches trace format

**⚠️ Considerations:**
- **Higher resource usage** (memory, CPU, disk)
- **More operational complexity**
- **Index rotation required** for TTL (vs. native TTL in Cassandra)
- **Higher storage costs**

**Best For:**
- Teams needing powerful search capabilities
- Organizations already using Elastic Stack
- Advanced analytics and reporting requirements
- Flexible query patterns

**Configuration Example:**

```yaml
storage:
  type: elasticsearch
  elasticsearch:
    server-urls: http://elasticsearch:9200
    index-prefix: jaeger
    use-aliases: true
    create-index-templates: true
    num-shards: 5
    num-replicas: 1
    bulk:
      size: 5000000  # 5MB
      workers: 5
```

**Index Management:**

Elasticsearch requires index rotation for data retention:

```bash
# Create indices with date suffix
jaeger-span-2024-01-27
jaeger-service-2024-01-27
jaeger-dependencies-2024-01-27

# Delete old indices
curator --config curator.yml delete_indices.yml
```

### Cassandra

**Architecture:**
```
Jaeger Collector
      ↓
Cassandra Cluster
  ├─ Node 1 (Datacenter 1)
  ├─ Node 2 (Datacenter 1)
  ├─ Node 3 (Datacenter 2)
  └─ Node 4 (Datacenter 2)
```

**Characteristics:**

**✅ Advantages:**
- **Native TTL support** (simpler data retention)
- **Fast single writes** (per span)
- **High write throughput**
- **Simpler operational model** for some teams
- **Multi-datacenter replication** built-in
- **Predictable performance**

**⚠️ Considerations:**
- **Limited search capabilities** (key-value store)
- **Write amplification** (multiple writes per trace for indexing)
  - Service name index
  - Operation name index
  - Tag indices
- **Client-side search implementation** (less flexible)
- **Eventual consistency** model
- **Query performance** worse than Elasticsearch for complex searches

**Best For:**
- Teams experienced with Cassandra
- High write throughput requirements
- Simple operational requirements (TTL)
- Straightforward query patterns (by trace ID, service, operation)

**Configuration Example:**

```yaml
storage:
  type: cassandra
  cassandra:
    servers: cassandra:9042
    keyspace: jaeger_v1_dc1
    local-dc: dc1
    connections-per-host: 2
    max-retry-attempts: 3
    timeout: 30s
    port: 9042
```

**TTL Configuration:**

```yaml
# Automatic deletion after 7 days
cassandra:
  span-store-ttl: 168h  # 7 days
```

### Elasticsearch vs Cassandra Comparison

**The Jaeger Team Recommendation:**
> Use Elasticsearch or OpenSearch over Cassandra for production deployments.

| Aspect | Elasticsearch | Cassandra |
|--------|---------------|-----------|
| **Search Capability** | ✅ Excellent (full-text) | ⚠️ Limited (key-value) |
| **Query Performance** | ✅ Fast for complex queries | ⚠️ Slower for complex searches |
| **Write Performance** | ✅ Good (single write) | ⚠️ Write amplification |
| **Resource Usage** | ⚠️ Higher | ✅ Lower |
| **Operational Complexity** | ⚠️ Higher | ✅ Lower (with TTL) |
| **Data Retention** | ⚠️ Index rotation needed | ✅ Native TTL |
| **Analytics** | ✅ Rich aggregations | ❌ Limited |
| **Kibana Integration** | ✅ Yes | ❌ No |
| **Multi-DC** | ⚠️ Complex | ✅ Built-in |

**Write Amplification in Cassandra:**

For each span, Cassandra must write:
1. Span data (by trace ID)
2. Service name index
3. Operation name index
4. Tag indices (for each indexed tag)
5. Duration index

Total: 5+ writes per span vs. 1 write in Elasticsearch

**Query Example Comparison:**

```yaml
# Find slow traces for service "checkout" with tag "error=true"

Elasticsearch:
  - Fast: Single query with filters
  - Flexible: Can add any filter combination

Cassandra:
  - Slower: Must scan multiple indices
  - Limited: Only pre-indexed tags searchable
  - Client-side filtering required
```

### OpenSearch (Elasticsearch Fork)

OpenSearch is an open-source fork of Elasticsearch:

**Why OpenSearch?**
- Fully open-source (Apache 2.0 license)
- Compatible with Elasticsearch APIs
- No licensing concerns
- Active development and community

**Configuration:**

```yaml
storage:
  type: opensearch
  opensearch:
    server-urls: http://opensearch:9200
    # Similar configuration to Elasticsearch
```

**Recommendation:** Use OpenSearch for new deployments unless you have existing Elasticsearch infrastructure.

### Badger (Single-Node)

**Use Cases:**
- Local development
- Single-node deployments
- Edge deployments
- Testing and demos

**Characteristics:**
- Embedded key-value store (like LevelDB)
- No external dependencies
- Limited to single node
- Lower performance than distributed backends

**Configuration:**

```yaml
storage:
  type: badger
  badger:
    directory-data: /data/badger/data
    directory-keys: /data/badger/keys
    ephemeral: false
    span-store-ttl: 168h
```

### Memory Storage (Development Only)

**Never use in production:**

```yaml
storage:
  type: memory
  memory:
    max-traces: 10000
```

**Characteristics:**
- No persistence
- Data lost on restart
- Useful for:
  - Quick local testing
  - CI/CD pipelines
  - Demos

### Storage Sizing Guidelines

**Elasticsearch/OpenSearch:**

```
Trace Size: ~1KB - 10KB per trace
Daily Volume: 100M traces/day = 100GB - 1TB/day
Retention: 7 days = 700GB - 7TB
Replication: 1 replica = 1.4TB - 14TB total
Recommendation: 3-5 nodes, 16-32GB RAM each
```

**Cassandra:**

```
Trace Size: ~2KB - 15KB per trace (with indices)
Daily Volume: 100M traces/day = 200GB - 1.5TB/day
Retention: 7 days = 1.4TB - 10.5TB
Replication: RF=3 = 4.2TB - 31.5TB total
Recommendation: 5-10 nodes, 16-32GB RAM each
```

**Rule of Thumb:**
- Plan for 3x raw data size in Elasticsearch (indices + replicas)
- Plan for 5x raw data size in Cassandra (indices + replication)

### Data Retention Strategies

**Elasticsearch Index Rotation:**

```bash
# Daily indices
jaeger-span-2024-01-27
jaeger-span-2024-01-28
...

# Curator config to delete old indices
actions:
  1:
    action: delete_indices
    filters:
      - filtertype: age
        source: name
        direction: older
        timestring: '%Y-%m-%d'
        unit: days
        unit_count: 7
```

**Cassandra TTL:**

```yaml
# Set at write time
INSERT INTO traces (trace_id, span_id, data)
VALUES (?, ?, ?)
USING TTL 604800;  -- 7 days in seconds
```

**Automatic vs Manual:**
- Cassandra: Automatic cleanup via TTL
- Elasticsearch: Requires cron job or Curator

### Hybrid Approaches

**Hot/Cold Storage:**

```
Recent traces (last 7 days):
  └─ Elasticsearch (fast queries)

Archived traces (7-90 days):
  └─ S3/Object Storage (compliance, slow retrieval)
```

**Multi-Backend:**

```
High-priority services:
  └─ Elasticsearch (1% sampling, 30-day retention)

Other services:
  └─ Cassandra (0.1% sampling, 7-day retention)
```
