---

## Introduction

Jaeger is an open-source distributed tracing platform released by Uber Technologies in 2016 and is now a graduated Cloud Native Computing Foundation (CNCF) project. It implements the OpenTracing specification and helps teams monitor microservices, identify performance bottlenecks, track root causes, and analyze service dependencies. Understanding Jaeger's architecture is essential for deploying and operating it effectively in production environments.

## Key Concepts Summary

### What is Jaeger?

Jaeger is a distributed tracing system that helps you:
- **Monitor distributed workflows** across microservices
- **Identify performance bottlenecks** in request paths
- **Track root causes** of failures and errors
- **Analyze service dependencies** and system topology
- **Understand request flow** through complex systems

### Core Data Model

**Trace**
- Represents the complete journey of a request through a distributed system
- Composed of one or more spans
- Visualized as a directed acyclic graph (DAG)
- Has a unique trace ID

**Span**
- A logical unit of work with an operation name, start time, and duration
- Represents a single operation (e.g., database query, HTTP request, function call)
- Contains:
  - Operation name
  - Start timestamp and duration
  - Tags (key-value pairs for metadata)
  - Logs (timestamped events)
  - Span context (trace ID, span ID, parent span ID)

**Baggage**
- User-defined key-value pairs propagated through the distributed context
- Available to all spans in a trace
- Useful for passing request-scoped data (user ID, tenant ID, feature flags)
- Be cautious: baggage is transmitted across process boundaries

**Example Trace Structure:**

```
Trace ID: abc123
├─ Span 1: API Gateway (200ms)
│  ├─ Span 2: Auth Service (50ms)
│  └─ Span 3: Order Service (100ms)
│     ├─ Span 4: Database Query (30ms)
│     └─ Span 5: Payment Service (50ms)
│        └─ Span 6: External API Call (40ms)
```

### Jaeger Components

**Client Libraries (Deprecated)**
- Legacy Jaeger SDKs (no longer supported since 2022)
- **Use OpenTelemetry SDKs instead** for instrumentation

**Jaeger Agent (Deprecated in v2)**
- Historically, a daemon that listened for spans and forwarded to collector
- No longer needed in Jaeger v2 with OpenTelemetry integration

**Jaeger Collector**
- Receives traces from applications (via OTLP protocol)
- Validates, transforms, and stores traces
- Handles backpressure with in-memory queues
- Supports remote sampling configuration
- Can write directly to storage or to Kafka

**Jaeger Query**
- Serves the Jaeger UI
- Provides API for retrieving traces from storage
- Handles search queries and trace aggregation

**Jaeger Ingester** (Optional)
- Used when Kafka is part of the architecture
- Reads traces from Kafka and writes to storage
- Provides buffering and prevents data loss during storage outages

**Storage Backend**
- Persistent storage for traces
- Options: Cassandra, Elasticsearch, OpenSearch, Badger, Memory
- Configured based on scale and requirements

### Deployment Architectures

**1. All-in-One**

```
┌────────────────────────────────┐
│      Jaeger All-in-One         │
│  ┌──────────────────────────┐  │
│  │ Collector, Query, UI     │  │
│  │ In-Memory Storage        │  │
│  └──────────────────────────┘  │
└────────────────────────────────┘
        ↑
        │ OTLP
        │
  Applications
```

**Use cases:**
- Local development
- Testing and demos
- Learning and experimentation
- NOT for production

**Characteristics:**
- Single binary/container
- In-memory storage only
- No persistence across restarts
- Simplest to deploy

**2. Direct to Storage (Production)**

```
  Applications
        │ OTLP
        ↓
  ┌───────────┐
  │ Collector │───────────┐
  └───────────┘           │
        │                 │
        ↓                 ↓
  ┌──────────┐      ┌─────────┐
  │ Storage  │      │  Query  │
  │(Elastic/ │      │   + UI  │
  │Cassandra)│      └─────────┘
  └──────────┘
```

**Use cases:**
- Production deployments
- Moderate to high scale
- Direct writes acceptable

**Characteristics:**
- Collector writes directly to storage
- In-memory queues handle traffic spikes
- Multiple collector instances for HA
- Storage is the scaling bottleneck

**3. Via Kafka (High Scale)**

```
  Applications
        │ OTLP
        ↓
  ┌───────────┐
  │ Collector │
  └───────────┘
        │
        ↓
   ┌────────┐
   │ Kafka  │───────────┐
   └────────┘           │
        │               │
        ↓               ↓
  ┌──────────┐    ┌─────────┐
  │ Ingester │    │  Query  │
  └──────────┘    │   + UI  │
        │         └─────────┘
        ↓
  ┌──────────┐
  │ Storage  │
  └──────────┘
```

**Use cases:**
- Very high scale deployments
- Need for guaranteed delivery
- Buffering during storage outages
- Decoupling collection from storage

**Characteristics:**
- Kafka as persistent buffer
- Prevents data loss if storage is down
- Additional operational complexity
- Higher resource requirements

### Jaeger v1 vs v2

**Jaeger v1 (Legacy)**
- Custom architecture
- Jaeger-specific SDKs (deprecated)
- Agent component for local batching
- Current version: 1.76 (archived)

**Jaeger v2 (Current)**
- Based on OpenTelemetry Collector framework
- Native OTLP protocol support
- No agent needed (OTLP handles batching)
- Released November 2024
- Current version: 2.14+
- Better extensibility and flexibility
- Unified configuration model

**Key Differences:**

| Feature | v1 | v2 |
|---------|----|----|
| **Base** | Custom architecture | OpenTelemetry Collector |
| **Protocol** | Jaeger Thrift | OTLP (gRPC/HTTP) |
| **Agent** | Required | Not needed |
| **SDKs** | Jaeger SDKs | OpenTelemetry SDKs |
| **Configuration** | Custom format | OTEL Collector YAML |
| **Extensibility** | Limited | High (OTEL ecosystem) |

**Migration Path:**
- Applications using OpenTelemetry SDKs work with both v1 and v2
- Simply update Jaeger deployment from v1 to v2
- No application code changes needed if using OTLP

### Sampling Strategies

Sampling reduces overhead and storage costs:

**Head-based Sampling (at instrumentation)**
- **Probabilistic:** Sample X% of traces (e.g., 1%)
- **Rate Limiting:** Sample max N traces per second
- **Adaptive:** Adjust sampling rate based on system load

**Tail-based Sampling (at collector)**
- Make sampling decisions after seeing entire trace
- Keep all error traces
- Sample slow requests at higher rate
- Drop successful, fast requests

**Remote Sampling**
- Jaeger serves sampling configuration to applications
- Centralized control of sampling rates
- Per-service sampling strategies
