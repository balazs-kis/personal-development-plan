Understanding its architecture—how it collects, stores, and queries time-series data—is fundamental to implementing effective metrics-based monitoring. This lesson covers the core components and how they work together to provide comprehensive system observability.

## Key Concepts Summary

### What is Prometheus?

**Prometheus** is an open-source monitoring and alerting toolkit originally built at SoundCloud in 2012. It's now a standalone project under the Cloud Native Computing Foundation (CNCF).

**Key characteristics:**
- **Time-series database**: Stores metrics with timestamps
- **Pull-based model**: Scrapes metrics from targets via HTTP
- **Multi-dimensional data**: Identifies metrics using name + key-value labels
- **Powerful query language**: PromQL for flexible data analysis
- **No distributed storage dependency**: Each server is autonomous

#### 1. Prometheus Server

The **Prometheus server** is the core component that:
- **Scrapes metrics** from configured targets at regular intervals
- **Stores data** in a local time-series database (TSDB)
- **Evaluates rules** for recording and alerting
- **Serves queries** via HTTP API and web UI

**Configuration:**
```yaml
# prometheus.yml
global:
  scrape_interval: 15s      # Default scrape frequency
  evaluation_interval: 15s   # Rule evaluation frequency

scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']
  
  - job_name: 'node-exporter'
    static_configs:
      - targets: ['localhost:9100']
```

#### 2. Time-Series Database (TSDB)

The **TSDB** efficiently stores metric data on local disk:

**Storage format:**
```
{metric_name}{ label1="value1", label2="value2" } value timestamp
http_requests_total{method="GET", status="200"} 1234 1640000000
```

**Key features:**
- **Local storage**: Fast, no network dependencies
- **Efficient compression**: Optimized for time-series workloads
- **Retention policies**: Configurable data retention (default: 15 days)
- **Remote storage**: Optional integration with long-term storage

**Storage structure:**
```
data/
├── 01ABCDEFG/
│   ├── chunks/
│   ├── index
│   └── meta.json
├── 01ABCDEFH/
│   ├── chunks/
│   ├── index
│   └── meta.json
└── wal/
```

#### 3. Targets and Exporters

**Targets** are endpoints that expose metrics for Prometheus to scrape.

**Types of targets:**

**a) Instrumented Applications:**
```go
// Example: Go application with Prometheus client
package main

import (
    "net/http"
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

func main() {
    http.Handle("/metrics", promhttp.Handler())
    http.ListenAndServe(":8080", nil)
}
```

**b) Exporters:**
Third-party services that expose metrics in Prometheus format:
- **Node Exporter**: Hardware and OS metrics (CPU, memory, disk)
- **Blackbox Exporter**: Probing endpoints (HTTP, DNS, TCP)
- **Database Exporters**: MySQL, PostgreSQL, MongoDB metrics
- **Cloud Exporters**: AWS, Azure, GCP metrics

**Metrics endpoint format:**
```
# HELP http_requests_total Total number of HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 1234
http_requests_total{method="POST",status="200"} 567

# HELP http_request_duration_seconds HTTP request latency
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1"} 100
http_request_duration_seconds_bucket{le="0.5"} 450
http_request_duration_seconds_bucket{le="1.0"} 800
http_request_duration_seconds_bucket{le="+Inf"} 1000
http_request_duration_seconds_sum 450.5
http_request_duration_seconds_count 1000
```

#### 4. Service Discovery

Prometheus supports multiple **service discovery** mechanisms for dynamic environments:

**Static configuration:**
```yaml
scrape_configs:
  - job_name: 'web-servers'
    static_configs:
      - targets:
        - 'web-1:8080'
        - 'web-2:8080'
```

**Dynamic discovery:**
```yaml
scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
```

**Supported mechanisms:**
- Kubernetes (pods, services, endpoints)
- Consul
- EC2, GCE, Azure
- DNS
- File-based discovery

#### 5. Pushgateway

The **Pushgateway** handles metrics from short-lived jobs that can't be scraped:

```
Short-lived job → Push metrics → Pushgateway → Prometheus scrapes
```

**Use case:**
```bash
# Batch job pushes metrics before exiting
echo "batch_job_duration_seconds 45" | \
  curl --data-binary @- http://pushgateway:9091/metrics/job/backup
```

**Important**: Use sparingly—Prometheus is designed for pull, not push.

#### 6. Alertmanager

The **Alertmanager** handles alerts sent by Prometheus:

**Responsibilities:**
- **Deduplicates** identical alerts
- **Groups** related alerts together
- **Routes** alerts to correct receivers
- **Silences** alerts during maintenance
- **Inhibits** alerts based on other active alerts

**Alert flow:**
```
Prometheus evaluates rules
    ↓
Fires alert to Alertmanager
    ↓
Alertmanager processes alert
    ↓
Routes to receivers (email, Slack, PagerDuty, etc.)
```

**Example configuration:**
```yaml
route:
  group_by: ['alertname', 'cluster']
  group_wait: 10s
  group_interval: 10s
  repeat_interval: 12h
  receiver: 'team-email'
  
receivers:
  - name: 'team-email'
    email_configs:
      - to: 'team@example.com'
```

#### 7. Visualization and APIs

**Prometheus Web UI:**
- **Expression browser**: Query metrics with PromQL
- **Graph**: Visualize query results
- **Alerts**: View active and pending alerts
- **Status**: Server configuration and target health

**HTTP API:**
```bash
# Query instant value
curl 'http://localhost:9090/api/v1/query?query=up'

# Query range
curl 'http://localhost:9090/api/v1/query_range?query=rate(http_requests_total[5m])&start=2024-01-01T00:00:00Z&end=2024-01-01T01:00:00Z&step=15s'
```

**Grafana integration:**
- Prometheus as data source
- Pre-built dashboards
- Advanced visualization

### Pull vs Push Model

**Pull Model (Prometheus):**
```
Advantages:
✓ Prometheus controls scrape frequency
✓ Can detect if target is down
✓ Easier to reason about (single source of truth)
✓ Targets don't need to know about Prometheus

Disadvantages:
✗ Targets must be reachable
✗ Not ideal for short-lived jobs
✗ Network firewalls can complicate
```

**How it works:**
```
1. Prometheus initiates connection
2. Scrapes /metrics endpoint via HTTP GET
3. Parses metrics in text format
4. Stores in TSDB
5. Repeats at scrape_interval
```

### Data Flow Example

**Complete monitoring flow:**

```
1. Application exposes metrics:
   http://app:8080/metrics
   
2. Prometheus configuration:
   scrape_configs:
     - job_name: 'my-app'
       scrape_interval: 10s
       static_configs:
         - targets: ['app:8080']

3. Prometheus scrapes every 10 seconds:
   GET http://app:8080/metrics
   
4. Data stored in TSDB:
   app_requests_total{method="GET"} 1234 @timestamp

5. User queries via PromQL:
   rate(app_requests_total[5m])
   
6. Alert rule evaluates:
   ALERT HighRequestRate
     IF rate(app_requests_total[5m]) > 100
     FOR 5m
   
7. Alert fires to Alertmanager
   
8. Alertmanager sends notification:
   → Email, Slack, PagerDuty, etc.
```

### Best Practices

**1. Use Labels Wisely:**
```yaml
# Good - reasonable cardinality
http_requests_total{method="GET", status="200", endpoint="/api/users"}

# Bad - high cardinality (user_id changes for every user)
http_requests_total{user_id="12345"}
```

**2. Set Appropriate Scrape Intervals:**
```yaml
# Standard: 15s for most metrics
scrape_interval: 15s

# High-frequency: 5s for critical metrics
scrape_interval: 5s

# Low-frequency: 1m for slow-changing metrics
scrape_interval: 60s
```

**3. Configure Retention:**
```bash
# Start Prometheus with 30-day retention
prometheus --storage.tsdb.retention.time=30d \
           --storage.tsdb.retention.size=50GB
```

**4. Use Remote Storage for Long-Term:**
```yaml
remote_write:
  - url: "http://remote-storage:9009/api/v1/write"
```

## Key Takeaways

- **Prometheus server** scrapes, stores, and queries metrics
- Uses a **pull-based model** to collect metrics from targets
- **TSDB** provides efficient local storage with configurable retention
- **Exporters** expose metrics from third-party services
- **Service discovery** enables dynamic target detection
- **Alertmanager** handles alert routing and notification
- Prometheus is designed for **reliability** and **autonomy**
