By the end of this lesson, you will be able to:
- Understand the role of each control plane component

- Describe etcd's role as the cluster's data store

## Introduction

The Kubernetes control plane is the brain of the cluster, making global decisions about scheduling, detecting cluster events, and responding to maintain desired state. The control plane consists of five core components that work together to manage your entire cluster.

## Key Concepts Summary

### Control Plane Overview

```
┌─────────────────────────────────────────────────────┐
│              CONTROL PLANE (Master Nodes)            │
│  ┌──────────────┐  ┌────────┐  ┌──────────────┐   │
│  │  API Server  │←→│  etcd  │  │  Scheduler   │   │
│  └──────────────┘  └────────┘  └──────────────┘   │
│         ↕                              ↕            │
│  ┌─────────────────────────────────────────────┐   │
│  │     Controller Manager                      │   │
│  └─────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
                         ↕
┌─────────────────────────────────────────────────────┐
│                  WORKER NODES                        │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────┐   │
│  │  Kubelet    │  │ Kube-proxy  │  │ Pods     │   │
│  └─────────────┘  └─────────────┘  └──────────┘   │
└─────────────────────────────────────────────────────┘
```

The control plane makes global decisions about the cluster and responds to cluster events.

### 1. kube-apiserver: The Central Hub

**Role:** The API server is the front-end for the Kubernetes control plane, exposing the Kubernetes API.

**Key Responsibilities:**
- Validates and configures data for API objects (pods, services, deployments, etc.)
- Serves the Kubernetes REST API over HTTPS
- Processes and authenticates all requests
- Updates corresponding objects in etcd

**Architecture:**
```
┌──────────────────────────────────────────┐
│         kubectl / API Clients            │
└──────────────┬───────────────────────────┘
               ↓ (HTTPS/JSON)
┌──────────────────────────────────────────┐
│         kube-apiserver                    │
│  ┌────────────────────────────────────┐  │
│  │ 1. Authentication                  │  │
│  │ 2. Authorization (RBAC)            │  │
│  │ 3. Admission Controllers           │  │
│  │ 4. Validation                      │  │
│  │ 5. Persistence to etcd             │  │
│  └────────────────────────────────────┘  │
└──────────────┬───────────────────────────┘
               ↓
         ┌──────────┐
         │   etcd   │
         └──────────┘
```

**Features:**
- Horizontally scalable (run multiple instances with load balancing)
- Supports multiple API versions simultaneously
- Extensible via Custom Resource Definitions (CRDs)
- Built-in admission webhooks for policy enforcement

**Example API Request:**
```bash
# Create a deployment via API
kubectl create deployment nginx --image=nginx

# What happens internally:
# 1. kubectl sends HTTPS POST to API server
# 2. API server authenticates the request
# 3. Checks authorization (RBAC)
# 4. Runs admission controllers
# 5. Validates the deployment spec
# 6. Persists to etcd
# 7. Returns success to kubectl
```

### 2. etcd: The Cluster Data Store

**Role:** Consistent and highly-available key-value store used as Kubernetes' backing store for all cluster data.

**What it stores:**
- Cluster configuration
- Resource definitions (pods, services, deployments, etc.)
- Current state of all objects
- Secrets and ConfigMaps
- Service discovery information

**Architecture:**
```
┌──────────────────────────────────────────┐
│           etcd Cluster                    │
│  ┌──────┐    ┌──────┐    ┌──────┐       │
│  │ etcd │←→│ etcd │←→│ etcd │       │
│  │  1   │    │  2   │    │  3   │       │
│  └──────┘    └──────┘    └──────┘       │
│         (Raft Consensus)                  │
└──────────────────────────────────────────┘
```

**Key Features:**
- Distributed consensus using Raft algorithm
- Strong consistency guarantees
- Watch API for real-time change notifications
- Automatic leader election
- Backup and restore capabilities

**Data Structure Example:**
```
/registry/
├── pods/
│   └── default/
│       └── nginx-abc123
├── services/
│   └── default/
│       └── kubernetes
├── deployments/
│   └── default/
│       └── nginx
└── secrets/
    └── default/
        └── db-password
```

**Best Practices:**
```bash
# Always run odd number of etcd nodes (3, 5, 7)
# 3 nodes = tolerate 1 failure
# 5 nodes = tolerate 2 failures

# Regular backups
ETCDCTL_API=3 etcdctl snapshot save backup.db

# Restore from backup
ETCDCTL_API=3 etcdctl snapshot restore backup.db
```

### 3. kube-scheduler: Workload Placement

**Role:** Watches for newly created Pods with no assigned node and selects a node for them to run on.

**Scheduling Process:**
```
1. Watch for unscheduled pods
   ↓
2. Filter nodes (feasible nodes)
   - Resource requirements met?
   - Port conflicts?
   - Node selector matches?
   - Taints and tolerations?
   ↓
3. Score nodes (best fit)
   - Resource utilization
   - Affinity/anti-affinity rules
   - Data locality
   ↓
4. Assign pod to highest-scoring node
   ↓
5. Update pod spec with node assignment
```

**Filtering Factors:**
```yaml
# Node selection constraints
apiVersion: v1
kind: Pod
metadata:
  name: myapp
spec:
  # Resource requirements
  containers:
  - name: app
    resources:
      requests:
        memory: "1Gi"
        cpu: "500m"
  
  # Node selector
  nodeSelector:
    disktype: ssd
  
  # Node affinity
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: kubernetes.io/zone
            operator: In
            values:
            - us-east-1a
            - us-east-1b
  
  # Tolerations for taints
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
```

**Scoring Example:**
```
Nodes after filtering: node1, node2, node3

Scoring:
- node1: CPU utilization 20%, Memory 30% → Score: 85
- node2: CPU utilization 60%, Memory 70% → Score: 50
- node3: CPU utilization 40%, Memory 45% → Score: 70

Winner: node1 (highest score)
```

### 4. kube-controller-manager: State Reconciliation

**Role:** Runs controller processes that watch the cluster state and make changes to move the current state toward desired state.

**Built-in Controllers:**

**Node Controller:**
- Monitors node health
- Marks nodes as NotReady after 40 seconds of no heartbeat
- Evicts pods from failed nodes after 5 minutes

**Deployment Controller:**
- Watches Deployment resources
- Creates/updates ReplicaSets
- Manages rollouts and rollbacks

**ReplicaSet Controller:**
- Ensures correct number of pod replicas
- Creates new pods if count is too low
- Deletes pods if count is too high

**Service Controller:**
- Creates cloud load balancers for LoadBalancer services
- Updates endpoints for services

**Example Reconciliation Loop:**
```
Desired State: 3 replicas of nginx
Current State: 2 replicas running

Deployment Controller:
1. Watches Deployment object in etcd
2. Compares desired (3) vs actual (2)
3. Creates 1 new pod via API server
4. API server persists to etcd
5. Scheduler assigns pod to node
6. Kubelet starts the container
7. Controller sees 3 replicas → reconciled ✓
```

**Controller Pattern:**
```go
// Simplified controller loop
for {
    desired := getDesiredState()
    actual := getCurrentState()
    
    if desired != actual {
        makeChanges(desired, actual)
    }
    
    wait(30 * time.Second)
}
```

### 5. cloud-controller-manager: Cloud Integration

**Role:** Runs controllers specific to your cloud provider (AWS, Azure, GCP).

**Cloud-Specific Controllers:**
- **Node controller:** Checks with cloud provider if a node has been deleted
- **Route controller:** Sets up routes in cloud network
- **Service controller:** Creates/deletes cloud load balancers
- **Volume controller:** Creates/attaches/mounts cloud storage volumes

**Example (AWS):**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 8080

# Cloud controller manager:
# 1. Detects new LoadBalancer service
# 2. Calls AWS API to create ELB
# 3. Configures health checks
# 4. Updates service with ELB hostname
# 5. Manages ELB lifecycle
```

### Control Plane High Availability

**Production Setup:**
```
┌─────────────────────────────────────────────────┐
│                 Load Balancer                    │
│              (HAProxy / cloud LB)                │
└──────┬──────────────┬──────────────┬────────────┘
       ↓              ↓              ↓
┌──────────┐   ┌──────────┐   ┌──────────┐
│ Master 1 │   │ Master 2 │   │ Master 3 │
│          │   │          │   │          │
│ API      │   │ API      │   │ API      │
│ Sched    │   │ Sched    │   │ Sched    │
│ Ctrl Mgr │   │ Ctrl Mgr │   │ Ctrl Mgr │
└────┬─────┘   └────┬─────┘   └────┬─────┘
     ↓              ↓              ↓
┌──────────────────────────────────────────┐
│       etcd Cluster (3 or 5 nodes)        │
└──────────────────────────────────────────┘
```

**HA Considerations:**
- Run odd number of control plane nodes (3 or 5)
- API servers are stateless and can run active-active
- Scheduler and controller managers use leader election (only one active)
- etcd requires quorum (majority) to function

**Leader Election:**
```
Controller Manager / Scheduler:
┌──────────┐   ┌──────────┐   ┌──────────┐
│ Master 1 │   │ Master 2 │   │ Master 3 │
│ (Leader) │   │(Standby) │   │(Standby) │
│  Active  │   │ Waiting  │   │ Waiting  │
└──────────┘   └──────────┘   └──────────┘
     ↓
If Leader fails:
     ↓
┌──────────┐   ┌──────────┐   ┌──────────┐
│ Master 1 │   │ Master 2 │   │ Master 3 │
│  (Down)  │   │ (Leader) │   │(Standby) │
│          │   │  Active  │   │ Waiting  │
└──────────┘   └──────────┘   └──────────┘
```

**Load Balancer Configuration:**
```yaml
# Example HAProxy configuration
frontend k8s-api
    bind *:6443
    mode tcp
    option tcplog
    default_backend k8s-api-backend

backend k8s-api-backend
    mode tcp
    balance roundrobin
    option tcp-check
    server master1 192.168.1.10:6443 check
    server master2 192.168.1.11:6443 check
    server master3 192.168.1.12:6443 check
```

### Component Communication Patterns

**Watch Mechanism:**
```
kubelet watches API server for pod assignments:

1. kubelet → API server: "Watch pods in my namespace"
2. API server: Opens HTTP connection, keeps alive
3. When change occurs:
   API server → kubelet: Pod update event
4. kubelet: Reconciles local state
5. Connection remains open for future updates
```

**Benefits:**
- Efficient (no polling)
- Real-time updates
- Reduced API server load

**API Server Request Flow:**
```
┌──────────────────────────────────────────────┐
│ 1. kubectl create deployment nginx           │
└──────────────┬───────────────────────────────┘
               ↓
┌──────────────────────────────────────────────┐
│ 2. API Server: Authentication                 │
│    - Verify client certificate                │
│    - Or: Bearer token, service account        │
└──────────────┬───────────────────────────────┘
               ↓
┌──────────────────────────────────────────────┐
│ 3. API Server: Authorization (RBAC)          │
│    - Check user/service account permissions   │
│    - Can this user create deployments?        │
└──────────────┬───────────────────────────────┘
               ↓
┌──────────────────────────────────────────────┐
│ 4. API Server: Admission Controllers          │
│    - Mutating: Add default values, inject     │
│    - Validating: Enforce policies, quotas     │
└──────────────┬───────────────────────────────┘
               ↓
┌──────────────────────────────────────────────┐
│ 5. API Server: Schema Validation             │
│    - Is this valid YAML/JSON?                │
│    - Does it match the resource schema?       │
└──────────────┬───────────────────────────────┘
               ↓
┌──────────────────────────────────────────────┐
│ 6. API Server: Persist to etcd               │
│    - Write deployment object to etcd          │
└──────────────┬───────────────────────────────┘
               ↓
┌──────────────────────────────────────────────┐
│ 7. API Server: Return response                │
│    - HTTP 201 Created                         │
│    - Return created object                    │
└──────────────────────────────────────────────┘
```

### Advanced Control Plane Topics

**Admission Controllers:**
```
Built-in admission controllers:
- NamespaceLifecycle: Prevents operations in terminating namespaces
- LimitRanger: Enforces resource limits
- ServiceAccount: Automatically injects service account tokens
- ResourceQuota: Enforces namespace quotas
- PodSecurityPolicy: Enforces pod security standards
- MutatingAdmissionWebhook: Custom mutation logic
- ValidatingAdmissionWebhook: Custom validation logic
```

**Example Admission Webhook:**
```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: validate-pods
webhooks:
- name: validate.pods.example.com
  clientConfig:
    service:
      name: validation-service
      namespace: default
      path: /validate
  rules:
  - operations: ["CREATE", "UPDATE"]
    apiGroups: [""]
    apiVersions: ["v1"]
    resources: ["pods"]
  admissionReviewVersions: ["v1"]
  sideEffects: None
```

**etcd Maintenance:**
```bash
# Check etcd health
ETCDCTL_API=3 etcdctl endpoint health

# Check etcd status
ETCDCTL_API=3 etcdctl endpoint status

# Defragment etcd (reduces disk usage)
ETCDCTL_API=3 etcdctl defrag

# Compact history (remove old revisions)
ETCDCTL_API=3 etcdctl compact <revision>

# Take backup
ETCDCTL_API=3 etcdctl snapshot save backup.db

# Verify backup
ETCDCTL_API=3 etcdctl snapshot status backup.db
```

**Scheduler Extenders:**
```
Custom scheduling logic:
┌──────────────┐
│   Scheduler  │
└──────┬───────┘
       ↓ (After filtering and scoring)
┌──────────────────────────────┐
│  Scheduler Extender (HTTP)   │
│  - Custom business logic      │
│  - External resource checks   │
│  - Additional scoring         │
└──────┬───────────────────────┘
       ↓
  Final node selection
```

## Practice Exercise

After completing the materials (20 minutes max):

1. **Inspect control plane components:**
```bash
# View control plane pods (if running as pods)
kubectl get pods -n kube-system

# Check API server health
kubectl get --raw /healthz
kubectl get --raw /livez
kubectl get --raw /readyz

# View component statuses
kubectl get componentstatuses

# Check control plane versions
kubectl version
```

2. **Query etcd (if you have access):**
```bash
# List all keys in etcd
kubectl exec -n kube-system etcd-master -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get / --prefix --keys-only

# Check etcd health
kubectl exec -n kube-system etcd-master -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint health
```

3. **Watch scheduler in action:**
```bash
# Create deployment
kubectl create deployment test --image=nginx --replicas=3

# Watch pod scheduling with events
kubectl get events --watch &
kubectl get pods -w

# Check which nodes pods are on
kubectl get pods -o wide

# View scheduler logs
kubectl logs -n kube-system -l component=kube-scheduler
```

4. **Observe controller manager:**
```bash
# Scale deployment
kubectl scale deployment test --replicas=5

# Watch controller create new pods
kubectl get pods -w

# View controller manager logs
kubectl logs -n kube-system -l component=kube-controller-manager | tail -20

# Scale down
kubectl scale deployment test --replicas=2

# Watch controller delete extra pods
kubectl get pods -w
```

5. **Test API server directly:**
```bash
# Start kubectl proxy
kubectl proxy --port=8080 &

# Query API directly
curl http://localhost:8080/api/v1/namespaces/default/pods

# Check API versions
curl http://localhost:8080/api
curl http://localhost:8080/apis

# Stop proxy when done
kill %1
```
