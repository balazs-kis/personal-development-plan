# Lesson 4: Resource Limits and Constraints

## Learning Objectives

By the end of this lesson, you will be able to:
- Set CPU and memory limits for containers
- Prevent resource exhaustion attacks
- Monitor container resource usage
- Configure resource requests and limits in Kubernetes
- Understand the impact of resource constraints on performance

---

## Introduction

Without resource limits, a single container can consume all available CPU and memory, causing denial of service for other containers and the host system. Resource limits prevent "noisy neighbor" problems and protect against resource exhaustion attacks. This lesson covers how to set and manage resource constraints effectively.

## Key Concepts Summary

### Why Resource Limits Matter

**Without limits:**
```bash
# Container can consume ALL host resources
docker run myapp
```

**Potential issues:**
- One container starves others
- Memory leaks crash the host
- CPU-intensive containers slow everything down
- DoS attacks can exhaust resources

**With limits:**
```bash
# Container is constrained
docker run -m 512m --cpus="1.0" myapp
```

### Memory Limits

**Set memory limit:**
```bash
# Limit to 512 MB
docker run -m 512m myapp

# Limit to 2 GB
docker run -m 2g myapp

# Limit with reservation
docker run -m 1g --memory-reservation 750m myapp
```

**What happens when limit is exceeded:**
```
Container → Exceeds memory limit → OOM Killer → Container killed
```

**Memory options:**
- `-m, --memory`: Hard limit
- `--memory-reservation`: Soft limit (memory guarantee)
- `--memory-swap`: Total memory (memory + swap)
- `--oom-kill-disable`: Disable OOM killer (dangerous!)

**Example:**
```bash
docker run \
  --memory 1g \
  --memory-reservation 750m \
  --memory-swap 2g \
  myapp
```

### CPU Limits

**Limit CPU usage:**
```bash
# Limit to 1 CPU core
docker run --cpus="1.0" myapp

# Limit to 0.5 CPU cores (50%)
docker run --cpus="0.5" myapp

# Limit to 2.5 CPU cores
docker run --cpus="2.5" myapp
```

**CPU shares (relative weight):**
```bash
# Default is 1024
docker run --cpu-shares 512 myapp  # Gets 50% priority
```

**Pin to specific CPUs:**
```bash
# Use only CPUs 0 and 1
docker run --cpuset-cpus="0,1" myapp

# Use CPUs 0 through 3
docker run --cpuset-cpus="0-3" myapp
```

### Combined Resource Limits

```bash
docker run -d \
  --name myapp \
  --memory 1g \
  --memory-reservation 750m \
  --cpus="1.5" \
  --pids-limit 100 \
  myapp:latest
```

### Docker Compose Resource Limits

```yaml
version: '3.8'

services:
  api:
    image: myapi:latest
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 512M
        reservations:
          cpus: '0.5'
          memory: 256M
    restart: unless-stopped

  db:
    image: postgres:15
    deploy:
      resources:
        limits:
          cpus: '2.0'
          memory: 2G
        reservations:
          cpus: '1.0'
          memory: 1G
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

### Kubernetes Resource Requests and Limits

**Requests vs Limits:**
- **Requests:** Guaranteed resources (used for scheduling)
- **Limits:** Maximum resources allowed

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp
spec:
  containers:
  - name: app
    image: myapp:latest
    resources:
      requests:
        memory: "256Mi"
        cpu: "250m"       # 0.25 CPU cores
      limits:
        memory: "512Mi"
        cpu: "500m"       # 0.5 CPU cores
```

**CPU units:**
- `1000m` = `1.0` = 1 CPU core
- `500m` = `0.5` = half a CPU core
- `100m` = `0.1` = 1/10th of a CPU core

**Memory units:**
- `Mi` = Mebibytes (1024^2 bytes)
- `Gi` = Gibibytes (1024^3 bytes)
- `M` = Megabytes (1000^2 bytes)
- `G` = Gigabytes (1000^3 bytes)

### QoS Classes in Kubernetes

**Guaranteed (highest priority):**
```yaml
resources:
  requests:
    memory: "512Mi"
    cpu: "500m"
  limits:
    memory: "512Mi"  # Same as request
    cpu: "500m"      # Same as request
```

**Burstable (medium priority):**
```yaml
resources:
  requests:
    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"  # Higher than request
    cpu: "500m"      # Higher than request
```

**BestEffort (lowest priority):**
```yaml
# No requests or limits specified
resources: {}
```

### LimitRange (Namespace defaults)

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: production
spec:
  limits:
  - default:
      cpu: "500m"
      memory: "512Mi"
    defaultRequest:
      cpu: "250m"
      memory: "256Mi"
    max:
      cpu: "2"
      memory: "2Gi"
    min:
      cpu: "100m"
      memory: "64Mi"
    type: Container
```

### ResourceQuota (Namespace total)

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: development
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"
    pods: "50"
```

### Resource Limit Best Practices

**1. Always set limits:**
```yaml
# Bad - no limits
containers:
- name: app
  image: myapp

# Good - explicit limits
containers:
- name: app
  image: myapp
  resources:
    limits:
      memory: "512Mi"
      cpu: "500m"
    requests:
      memory: "256Mi"
      cpu: "250m"
```

**2. Base limits on actual usage:**
```bash
# Monitor first
docker stats myapp

# Then set appropriate limits
docker run -m 512m --cpus="0.5" myapp
```

**3. Set both requests and limits:**
```yaml
# Requests for scheduling
# Limits for protection
resources:
  requests:
    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"
    cpu: "500m"
```

**4. Don't over-provision:**
```yaml
# Bad - requesting more than you need
requests:
  memory: "10Gi"
  cpu: "8"

# Good - based on actual usage + headroom
requests:
  memory: "512Mi"
  cpu: "500m"
```

**5. Use Guaranteed QoS for critical services:**
```yaml
# Critical service
resources:
  requests:
    memory: "1Gi"
    cpu: "1"
  limits:
    memory: "1Gi"
    cpu: "1"
```

### Tuning Resource Limits

**Baseline determination process:**
```bash
# Step 1: Run without limits and monitor
kubectl run test --image=myapp --restart=Never
kubectl top pod test --containers

# Step 2: Observe steady-state usage
# Monitor for 24-48 hours under typical load
kubectl top pod test --containers > metrics.log

# Step 3: Calculate requirements
# Requests: Average usage + 20% buffer
# Limits: Peak usage + 30% buffer

# Step 4: Apply and iterate
```

**Load testing with different limits:**
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: load-test-256m
spec:
  template:
    spec:
      containers:
      - name: app
        image: myapp:latest
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
            cpu: "200m"
      restartPolicy: Never
```

```bash
# Run load test
kubectl apply -f load-test-256m.yaml

# Monitor performance
kubectl top pods
kubectl logs load-test-256m

# Test with different limits
# 256Mi, 512Mi, 1Gi, etc.
```

### Cost Optimization Strategies

**Right-sizing workloads:**
```
Over-provisioned (wasteful):
requests: memory: "2Gi", cpu: "2"
actual usage: memory: "200Mi", cpu: "0.2"
→ Wasting 90% of resources

Right-sized (optimal):
requests: memory: "256Mi", cpu: "250m"
limits: memory: "512Mi", cpu: "500m"
→ Cost-effective with headroom
```

**Vertical Pod Autoscaler (VPA):**
```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: myapp-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  updatePolicy:
    updateMode: "Auto"
  resourcePolicy:
    containerPolicies:
    - containerName: app
      minAllowed:
        memory: "128Mi"
        cpu: "100m"
      maxAllowed:
        memory: "1Gi"
        cpu: "1"
```

**Horizontal Pod Autoscaler (HPA) with resource metrics:**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
```

### Troubleshooting Resource Issues

**OOMKilled (Out of Memory):**
```bash
# Check pod status
kubectl get pods
# NAME    READY   STATUS      RESTARTS   AGE
# myapp   0/1     OOMKilled   5          10m

# Check events
kubectl describe pod myapp
# Events:
#   Type     Reason     Message
#   ----     ------     -------
#   Warning  BackOff    Back-off restarting failed container
#   Normal   Killing    Memory limit exceeded: container was killed

# Solution: Increase memory limit
resources:
  limits:
    memory: "1Gi"  # Increased from 512Mi
```

**CPU throttling:**
```bash
# Check CPU throttling metrics
kubectl top pods myapp
# NAME    CPU(cores)   MEMORY(bytes)
# myapp   500m/500m    256Mi/512Mi
#         ↑ At limit, being throttled

# Check container metrics
kubectl exec myapp -- cat /sys/fs/cgroup/cpu/cpu.stat
# nr_throttled: 1234
# throttled_time: 56789000000

# Solution: Increase CPU limit or optimize code
```

**Eviction scenarios:**
```
Pod eviction priority (lowest to highest):
1. BestEffort pods (no requests/limits)
2. Burstable pods exceeding requests
3. Burstable pods within requests
4. Guaranteed pods
```

```bash
# Check node pressure
kubectl describe node
# Conditions:
#   Type             Status  Reason
#   ----             ------  ------
#   MemoryPressure   True    NodeHasSufficientMemory
#   DiskPressure     False   NodeHasNoDiskPressure

# Pods will be evicted to free memory
```

**Pending pods due to insufficient resources:**
```bash
kubectl get pods
# NAME    READY   STATUS    RESTARTS   AGE
# myapp   0/1     Pending   0          5m

kubectl describe pod myapp
# Events:
#   Warning  FailedScheduling  pod has unbound immediate PersistentVolumeClaims
#   Warning  FailedScheduling  0/3 nodes are available: 3 Insufficient memory

# Solution: Add nodes or reduce requests
```

### Security Implications

**Resource exhaustion attacks:**
```yaml
# Without limits (vulnerable):
apiVersion: v1
kind: Pod
metadata:
  name: vulnerable
spec:
  containers:
  - name: app
    image: malicious:latest
    # No limits - can consume all node resources!

# With limits (protected):
apiVersion: v1
kind: Pod
metadata:
  name: protected
spec:
  containers:
  - name: app
    image: app:latest
    resources:
      limits:
        memory: "512Mi"
        cpu: "500m"
    # Limited blast radius
```

**Denial of service prevention:**
```yaml
# Namespace-level protection
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dos-protection
  namespace: untrusted
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"
    pods: "50"
    services: "10"
```

### Monitoring and Alerting

**Prometheus queries for resource monitoring:**
```promql
# CPU usage vs limit
sum(rate(container_cpu_usage_seconds_total[5m])) by (pod) 
/ 
sum(container_spec_cpu_quota/container_spec_cpu_period) by (pod)

# Memory usage vs limit
sum(container_memory_working_set_bytes) by (pod) 
/ 
sum(container_spec_memory_limit_bytes) by (pod)

# Pods at CPU limit (being throttled)
sum(rate(container_cpu_cfs_throttled_periods_total[5m])) by (pod) > 0

# OOMKill events
sum(rate(container_oom_events_total[5m])) by (pod) > 0
```

**Alert rules:**
```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: resource-alerts
spec:
  groups:
  - name: resources
    rules:
    - alert: HighMemoryUsage
      expr: |
        sum(container_memory_working_set_bytes) by (pod) 
        / 
        sum(container_spec_memory_limit_bytes) by (pod) 
        > 0.9
      for: 5m
      annotations:
        summary: "Pod {{ $labels.pod }} using >90% memory"
    
    - alert: CPUThrottling
      expr: |
        sum(rate(container_cpu_cfs_throttled_periods_total[5m])) by (pod) 
        / 
        sum(rate(container_cpu_cfs_periods_total[5m])) by (pod) 
        > 0.25
      for: 5m
      annotations:
        summary: "Pod {{ $labels.pod }} CPU throttled >25%"
```
