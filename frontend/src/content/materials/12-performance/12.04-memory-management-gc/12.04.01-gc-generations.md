## Introduction

The .NET garbage collector (GC) is an automatic memory manager that uses a generational algorithm to optimize performance. Understanding how generations work and when collections occur enables you to write code that minimizes GC overhead and prevents performance problems.

## Key Concepts Summary

### The Generational Algorithm

**Core Principle:** Most objects die young.

The GC divides the managed heap into three generations based on object age:
- **Generation 0 (Gen 0):** Newly allocated objects
- **Generation 1 (Gen 1):** Objects that survived one GC
- **Generation 2 (Gen 2):** Long-lived objects

**Why Generations Matter:**
```
Collecting only part of the heap (Gen 0) is faster than collecting the entire heap.
Younger objects tend to be related and accessed together.
Older objects tend to live longer.
```

### Generation 0: Short-Lived Objects

```csharp
public void ProcessRequest(HttpContext context)
{
    // These objects typically die in Gen 0
    var request = new Request();
    var response = new Response();
    var tempData = new byte[1024];
    
    // Process request
    response.Send(tempData);
    
    // After method returns, these objects become garbage
    // Collected in next Gen 0 GC
}
```

**Characteristics:**
- Contains newly allocated small objects (< 85,000 bytes)
- Collected most frequently (fastest collections)
- Most objects die here and never move to Gen 1
- Typical survival rate: 10-20%

**Trigger:** When Gen 0 fills up (threshold ~256 KB - 4 GB depending on system)

### Generation 1: Buffer Between Young and Old

```csharp
public class RequestHandler
{
    // These objects might survive initial GC
    private readonly HttpClient _client = new();
    private readonly Logger _logger = new();
    
    public async Task HandleRequest()
    {
        // Temporary objects (Gen 0)
        var data = await _client.GetStringAsync("https://api.example.com");
        
        // Process...
        _logger.Log(data);  // _logger survives in Gen 1
    }
}
```

**Characteristics:**
- Acts as buffer between short-lived and long-lived objects
- Smaller than Gen 0 and Gen 2
- Objects promoted from Gen 0 after surviving first GC
- Typical survival rate: 20-30%

**Trigger:** When Gen 0 GC doesn't reclaim enough memory

### Generation 2: Long-Lived Objects

```csharp
public class Application
{
    // These objects live in Gen 2
    private static readonly Dictionary<string, string> _config = new();
    private static readonly ConcurrentDictionary<int, User> _userCache = new();
    
    static Application()
    {
        // Static fields live for application lifetime
        _config["ApiKey"] = "...";
    }
}
```

**Characteristics:**
- Contains objects that survived multiple GCs
- Rarely collected (expensive, full heap collection)
- Includes static fields and long-lived caches
- High survival rate: 80-95%

**Trigger:** 
- When Gen 1 GC doesn't reclaim enough memory
- Low physical memory
- Explicit `GC.Collect()` call

### Promotion Flow

```
New Object
    ↓
[Gen 0] → Survives Gen 0 GC
    ↓
[Gen 1] → Survives Gen 1 GC
    ↓
[Gen 2] → Survives Gen 2 GC
    ↓
[Gen 2] (stays here)
```

**Example:**
```csharp
public class PromotionExample
{
    private static List<int> _survives = new();  // Goes to Gen 2
    
    public void Method()
    {
        var temp = new int[100];  // Gen 0, dies quickly
        
        // Force Gen 0 collection
        GC.Collect(0);
        
        // _survives promoted to Gen 1
        GC.Collect(1);
        
        // _survives promoted to Gen 2
        GC.Collect(2);
        
        // _survives stays in Gen 2
    }
}
```

### GC Collection Phases

**Phase 1: Marking**
```csharp
// GC finds all live objects by tracing from roots
// Roots include:
// - Static fields
// - Local variables on thread stacks
// - CPU registers
// - GC handles

public class RootExample
{
    private static User _staticUser;  // Root: static field
    
    public void Method()
    {
        var localUser = new User();  // Root: local variable
        
        // Both _staticUser and localUser are roots
        // Objects they reference are also marked as live
    }
}
```

**Phase 2: Relocating**
```csharp
// GC updates all references to point to new locations
// after compaction

// Before relocation:
// Memory: [Obj1][Dead][Obj2][Dead][Obj3]
//          ↑           ↑           ↑
//          ref1        ref2        ref3

// After relocation (pointers updated):
// Memory: [Obj1][Obj2][Obj3][Free Space]
//          ↑     ↑     ↑
//          ref1  ref2  ref3
```

**Phase 3: Compacting**
```csharp
// GC moves live objects together to eliminate fragmentation

// Before compaction:
// [Live][Dead][Live][Dead][Dead][Live]
//  100B  50B   80B   30B   20B   60B

// After compaction:
// [Live][Live][Live][Free Space      ]
//  100B  80B   60B   180B available
```

### When Does GC Occur?

**Condition 1: Allocation Threshold Exceeded**
```csharp
// Most common trigger
public void AllocateObjects()
{
    for (int i = 0; i < 10000; i++)
    {
        var obj = new MyObject();  // Allocates in Gen 0
        // When Gen 0 fills up → Gen 0 GC triggered
    }
}
```

**Condition 2: Low Physical Memory**
```csharp
// OS notifies CLR of low memory
// CLR triggers Gen 2 GC to free memory

// You can also check memory pressure:
GCMemoryInfo info = GC.GetGCMemoryInfo();
long totalMemory = info.TotalAvailableMemoryBytes;
long heapSize = info.HeapSizeBytes;

if (heapSize > totalMemory * 0.9)
{
    // High memory pressure
}
```

**Condition 3: Explicit GC.Collect() Call**
```csharp
// ⚠️ Rarely needed - GC usually knows best
public void AfterLargeOperation()
{
    // Process large amount of data
    var largeData = ProcessData();
    
    // Explicitly request GC (use sparingly!)
    largeData = null;
    GC.Collect();
    GC.WaitForPendingFinalizers();
    GC.Collect();
}
```

### Managed Heap Structure

```
┌─────────────────────────────────────┐
│         Managed Heap                │
├─────────────────────────────────────┤
│  Generation 0 (Young Objects)       │  ← Frequent collections
│  - Size: ~256 KB - 4 GB            │
│  - Most allocations happen here     │
├─────────────────────────────────────┤
│  Generation 1 (Buffer)              │  ← Less frequent
│  - Smaller than Gen 0 & Gen 2       │
│  - Survivors from Gen 0             │
├─────────────────────────────────────┤
│  Generation 2 (Long-lived)          │  ← Rare, expensive
│  - Static fields, caches            │
│  - Objects that survived many GCs   │
├─────────────────────────────────────┤
│  Large Object Heap (LOH)            │  ← Separate heap
│  - Objects ≥ 85,000 bytes           │  (covered in Lesson 2)
│  - Not compacted by default         │
└─────────────────────────────────────┘
```

### Optimizing for Generations

**Bad: Creates Many Short-Lived Objects**
```csharp
// ❌ Allocates string on each iteration
public string BuildReport(List<Item> items)
{
    string report = "";
    foreach (var item in items)
    {
        report += $"{item.Name}: {item.Value}\n";  // Many Gen 0 allocations!
    }
    return report;
}

// Gen 0 GCs: High (many small string allocations)
```

**Good: Reduces Allocations**
```csharp
// ✅ Single allocation, reused buffer
public string BuildReport(List<Item> items)
{
    var sb = new StringBuilder(items.Count * 50);  // Pre-size
    foreach (var item in items)
    {
        sb.Append(item.Name).Append(": ").Append(item.Value).Append('\n');
    }
    return sb.ToString();
}

// Gen 0 GCs: Low (minimal allocations)
```

### Ephemeral Segment

**Gen 0 and Gen 1 together form the "ephemeral segment":**

```csharp
// Default ephemeral segment sizes:
// 32-bit Workstation GC: 16 MB
// 64-bit Workstation GC: 256 MB
// 64-bit Server GC: up to 4 GB

public void UnderstandEphemeral()
{
    // New segment becomes ephemeral segment
    // Old ephemeral becomes Gen 2 segment
    
    // Memory freed from ephemeral GC is limited
    // to size of ephemeral segment
}
```

## Common Patterns and Anti-Patterns

### Anti-Pattern 1: Frequent Gen 2 Collections

```csharp
// ❌ Problem: Too many large objects promoted to Gen 2
public class CacheManager
{
    private Dictionary<string, byte[]> _cache = new();
    
    public void AddToCache(string key, byte[] data)
    {
        _cache[key] = data;  // Lives forever in Gen 2
        // Cache grows unbounded → Gen 2 GCs increase
    }
}

// ✅ Solution: Implement cache eviction
public class BetterCacheManager
{
    private LruCache<string, byte[]> _cache = new(maxSize: 1000);
    
    public void AddToCache(string key, byte[] data)
    {
        _cache.Add(key, data);  // Old entries evicted → less Gen 2 pressure
    }
}
```

### Anti-Pattern 2: Allocating in Loops

```csharp
// ❌ Problem: Many temporary objects in Gen 0
public void ProcessData(int[] data)
{
    for (int i = 0; i < data.Length; i++)
    {
        var temp = new DataWrapper(data[i]);  // Allocated every iteration!
        Process(temp);
    }
}

// ✅ Solution: Reuse objects or avoid allocation
public void ProcessData(int[] data)
{
    var temp = new DataWrapper();  // Allocate once
    for (int i = 0; i < data.Length; i++)
    {
        temp.Value = data[i];  // Reuse
        Process(temp);
    }
}
```

### Pattern: Pooling Long-Lived Objects

```csharp
// ✅ Keep pool in Gen 2, but objects cycle through
public class ObjectPool<T>
{
    private readonly ConcurrentBag<T> _pool = new();  // Lives in Gen 2
    
    public T Rent()
    {
        return _pool.TryTake(out var item) ? item : Create();
    }
    
    public void Return(T item)
    {
        _pool.Add(item);  // Object stays in Gen 2, reused
    }
    
    private T Create() => Activator.CreateInstance<T>();
}
```

## Summary

The .NET garbage collector uses a generational algorithm with three generations (0, 1, 2) to optimize performance. Gen 0 contains short-lived objects and is collected frequently, Gen 1 acts as a buffer, and Gen 2 contains long-lived objects. GC occurs in three phases: marking live objects, relocating references, and compacting memory. Collections are triggered by allocation thresholds, low memory, or explicit calls. Understanding generations helps you write code that minimizes GC overhead and avoids performance problems.
