## Learning Objectives

By the end of this lesson, you will be able to:
- Understand different database scaling strategies
- Implement read replicas for read-heavy workloads
- Apply sharding techniques for horizontal database scaling
- Choose appropriate partitioning strategies
- Design database architectures that scale with your application
- Recognize trade-offs between consistency and scalability

## Introduction

Databases are often the first bottleneck when scaling applications. While application servers are relatively easy to scale horizontally, databases present unique challenges due to data consistency requirements. This lesson covers proven patterns for scaling databases while maintaining acceptable consistency guarantees.

## Key Concepts Summary

### The Database Scaling Challenge

**Why databases are hard to scale:**
- Data must remain consistent across nodes
- ACID transactions require coordination
- Complex queries may need access to all data
- Writes are harder to distribute than reads
- Network latency affects distributed operations

### Database Scaling Strategies

```
Application
Tier            [App] [App] [App] ← Easy to scale horizontally
                    │   │   │
                    └───┼───┘
                        │
Database               [DB]  ← Hard to scale (data consistency)
Tier
```

### Strategy 1: Vertical Scaling (Scale Up)

**Approach:** Increase database server resources (CPU, RAM, storage, IOPS).

**Example:**
```
Before:              After:
┌──────────┐        ┌──────────┐
│ Database │        │ Database │
│ 4 CPU    │   →    │ 32 CPU   │
│ 16 GB    │        │ 128 GB   │
│ 500 IOPS │        │ 10K IOPS │
└──────────┘        └──────────┘
```

**Advantages:**
✅ Simple - no application changes
✅ Maintains ACID guarantees
✅ All data in one place
✅ No distributed transaction complexity

**Disadvantages:**
❌ Hard limits (largest available hardware)
❌ Single point of failure
❌ Expensive at high end
❌ Downtime for upgrades

**When to use:**
- Early stages (< 10,000 queries/sec)
- Strong consistency requirements
- Complex join queries
- Quick fix for moderate growth

### Strategy 2: Read Replicas (Leader-Follower Replication)

**Approach:** Create read-only copies of the database to distribute read load.

**Architecture:**
```
Application Servers
    │
    ├──────────────┬──────────────┐
    │(writes)      │(reads)       │(reads)
    ▼              ▼              ▼
┌─────────┐   ┌─────────┐   ┌─────────┐
│ Primary │──►│Replica 1│   │Replica 2│
│(R/W)    │   │(R only) │   │(R only) │
└─────────┘   └─────────┘   └─────────┘
     │
     └──replication──►
```

**How it works:**
1. All writes go to primary database
2. Primary replicates changes to replicas
3. Reads distributed across primary and replicas
4. Asynchronous or synchronous replication

**Advantages:**
✅ Scales read capacity horizontally
✅ Improved read latency (geographic distribution)
✅ High availability (failover to replica)
✅ No application logic changes (mostly)

**Disadvantages:**
❌ Replication lag (eventual consistency)
❌ Doesn't scale writes
❌ Read-after-write consistency challenges
❌ Failover complexity

**When to use:**
- Read-heavy workloads (90%+ reads)
- Can tolerate eventual consistency
- Need high availability
- Want to distribute reads geographically

#### Implementing Read Replicas in .NET

**Database Configuration:**

```csharp
public class DatabaseOptions
{
    public string PrimaryConnectionString { get; set; }
    public List<string> ReplicaConnectionStrings { get; set; }
}

public static class DbConnectionExtensions
{
    public static void AddScalableDatabase(
        this IServiceCollection services,
        IConfiguration config)
    {
        var options = config.GetSection("Database").Get<DatabaseOptions>();
        
        // Register primary for writes
        services.AddDbContext<ApplicationDbContext>(opt =>
            opt.UseSqlServer(options.PrimaryConnectionString));
        
        // Register replicas for reads
        services.AddSingleton<IReplicaConnectionProvider>(
            new ReplicaConnectionProvider(options.ReplicaConnectionStrings));
    }
}
```

**Read/Write Separation:**

```csharp
public class OrderService
{
    private readonly ApplicationDbContext _writeDb;
    private readonly IReplicaConnectionProvider _readDb;
    
    public OrderService(
        ApplicationDbContext writeDb,
        IReplicaConnectionProvider readDb)
    {
        _writeDb = writeDb;
        _readDb = readDb;
    }
    
    // Write to primary
    public async Task<Order> CreateOrderAsync(CreateOrderRequest request)
    {
        var order = new Order
        {
            UserId = request.UserId,
            Total = request.Total,
            CreatedAt = DateTime.UtcNow
        };
        
        _writeDb.Orders.Add(order);
        await _writeDb.SaveChangesAsync();
        
        return order;
    }
    
    // Read from replica
    public async Task<List<Order>> GetUserOrdersAsync(int userId)
    {
        using var connection = _readDb.GetConnection();
        return await connection.QueryAsync<Order>(
            "SELECT * FROM Orders WHERE UserId = @UserId ORDER BY CreatedAt DESC",
            new { UserId = userId });
    }
}
```

**Handling Replication Lag:**

```csharp
public class OrderService
{
    public async Task<Order> CreateOrderAsync(CreateOrderRequest request)
    {
        var order = new Order { /* ... */ };
        _writeDb.Orders.Add(order);
        await _writeDb.SaveChangesAsync();
        
        // Store in cache to handle read-after-write
        await _cache.SetAsync(
            $"order:{order.Id}",
            order,
            TimeSpan.FromSeconds(10)); // Cover replication lag
        
        return order;
    }
    
    public async Task<Order> GetOrderAsync(int orderId)
    {
        // Check cache first (handles recent writes)
        var cached = await _cache.GetAsync<Order>($"order:{orderId}");
        if (cached != null)
            return cached;
        
        // Otherwise read from replica
        using var connection = _readDb.GetConnection();
        return await connection.QuerySingleAsync<Order>(
            "SELECT * FROM Orders WHERE Id = @Id",
            new { Id = orderId });
    }
}
```

### Strategy 3: Sharding (Horizontal Partitioning)

**Approach:** Split data across multiple databases based on a sharding key.

**Architecture:**
```
Application
    │
    └─── Routing Logic ───┐
                          │
    ┌─────────────────────┼─────────────────────┐
    │                     │                     │
    ▼                     ▼                     ▼
┌─────────┐          ┌─────────┐          ┌─────────┐
│ Shard 1 │          │ Shard 2 │          │ Shard 3 │
│Users    │          │Users    │          │Users    │
│1-10000  │          │10001-   │          │20001-   │
│         │          │20000    │          │30000    │
└─────────┘          └─────────┘          └─────────┘
```

**Sharding Strategies:**

#### 1. Range-Based Sharding

Partition by ranges of shard key values:

```csharp
public class RangeShardRouter
{
    private readonly Dictionary<int, string> _shardRanges = new()
    {
        { 10000, "Server1" },    // Users 1-10000
        { 20000, "Server2" },    // Users 10001-20000
        { 30000, "Server3" },    // Users 20001-30000
        { int.MaxValue, "Server4" } // Users 30001+
    };
    
    public string GetShardForUser(int userId)
    {
        foreach (var (maxId, server) in _shardRanges.OrderBy(x => x.Key))
        {
            if (userId <= maxId)
                return server;
        }
        
        throw new Exception("No shard found");
    }
}
```

**Pros:**
✅ Range queries are efficient
✅ Easy to add new ranges
✅ Logical data grouping

**Cons:**
❌ Can create hotspots (uneven distribution)
❌ Rebalancing is complex

#### 2. Hash-Based Sharding

Use hash function to determine shard:

```csharp
public class HashShardRouter
{
    private readonly List<string> _shards = new()
    {
        "Server1", "Server2", "Server3", "Server4"
    };
    
    public string GetShardForUser(int userId)
    {
        var hash = userId.GetHashCode();
        var shardIndex = Math.Abs(hash % _shards.Count);
        return _shards[shardIndex];
    }
}
```

**Pros:**
✅ Even distribution
✅ No hotspots
✅ Simple implementation

**Cons:**
❌ Range queries require checking all shards
❌ Rebalancing requires rehashing many keys

#### 3. Geographic Sharding

Shard by location:

```csharp
public class GeoShardRouter
{
    private readonly Dictionary<string, string> _regionShards = new()
    {
        { "US-EAST", "USEastDB" },
        { "US-WEST", "USWestDB" },
        { "EU", "EuropeDB" },
        { "ASIA", "AsiaDB" }
    };
    
    public string GetShardForRegion(string region)
    {
        return _regionShards.TryGetValue(region, out var shard)
            ? shard
            : _regionShards["US-EAST"]; // Default
    }
}
```

**Pros:**
✅ Reduced latency (data near users)
✅ Compliance (data residency requirements)
✅ Natural partitioning

**Cons:**
❌ Cross-region queries are expensive
❌ Uneven growth across regions

#### 4. Entity/Tenant-Based Sharding

Shard by business entity (multi-tenant SaaS):

```csharp
public class TenantShardRouter
{
    private readonly Dictionary<int, string> _tenantShards;
    
    public string GetShardForTenant(int tenantId)
    {
        return _tenantShards.TryGetValue(tenantId, out var shard)
            ? shard
            : AssignNewTenant(tenantId);
    }
    
    private string AssignNewTenant(int tenantId)
    {
        // Assign to least loaded shard
        var shard = GetLeastLoadedShard();
        _tenantShards[tenantId] = shard;
        return shard;
    }
}
```

**Pros:**
✅ Complete tenant isolation
✅ Easy per-tenant optimization
✅ Simple compliance (delete all tenant data)

**Cons:**
❌ Large tenants can create hotspots
❌ Cross-tenant analytics are difficult

### Implementing Sharding in .NET

```csharp
public interface IShardRouter
{
    string GetShard(int shardKey);
    IEnumerable<string> GetAllShards();
}

public class ShardedDbContextFactory
{
    private readonly IShardRouter _router;
    private readonly Dictionary<string, string> _shardConnections;
    
    public ApplicationDbContext CreateContext(int shardKey)
    {
        var shardName = _router.GetShard(shardKey);
        var connectionString = _shardConnections[shardName];
        
        var options = new DbContextOptionsBuilder<ApplicationDbContext>()
            .UseSqlServer(connectionString)
            .Options;
        
        return new ApplicationDbContext(options);
    }
}

public class ShardedOrderRepository
{
    private readonly ShardedDbContextFactory _factory;
    
    public async Task<Order> GetOrderAsync(int userId, int orderId)
    {
        // Route to correct shard based on user
        using var context = _factory.CreateContext(userId);
        return await context.Orders.FindAsync(orderId);
    }
    
    public async Task<List<Order>> GetAllOrdersForUserAsync(int userId)
    {
        // Single shard query
        using var context = _factory.CreateContext(userId);
        return await context.Orders
            .Where(o => o.UserId == userId)
            .ToListAsync();
    }
    
    public async Task<List<Order>> GetAllRecentOrdersAsync()
    {
        // Cross-shard query - expensive!
        var tasks = _factory.GetAllShards()
            .Select(async shard =>
            {
                using var context = _factory.CreateContext(shard);
                return await context.Orders
                    .Where(o => o.CreatedAt > DateTime.UtcNow.AddDays(-7))
                    .ToListAsync();
            });
        
        var results = await Task.WhenAll(tasks);
        return results.SelectMany(x => x).ToList();
    }
}
```

### Strategy 4: Vertical Partitioning

**Approach:** Split tables by columns, separating frequently accessed from rarely accessed data.

**Example:**
```
Original Table:
┌──────────────────────────────────────────┐
│ Users                                    │
├──────────────────────────────────────────┤
│ Id, Email, Name, PasswordHash, Address,  │
│ Phone, Bio, PreferenceJSON, AvatarBlob   │
└──────────────────────────────────────────┘

After Vertical Partitioning:
┌─────────────────────┐    ┌──────────────────────┐
│ Users (Hot Data)    │    │ UserDetails (Cold)   │
├─────────────────────┤    ├──────────────────────┤
│ Id, Email, Name     │    │ UserId, Address,     │
│ PasswordHash        │    │ Phone, Bio,          │
└─────────────────────┘    │ PreferenceJSON       │
                            └──────────────────────┘
```

**In .NET:**
```csharp
public class User
{
    public int Id { get; set; }
    public string Email { get; set; }
    public string Name { get; set; }
    public string PasswordHash { get; set; }
    
    // Reference to extended data
    public UserDetails Details { get; set; }
}

public class UserDetails
{
    public int UserId { get; set; }
    public string Address { get; set; }
    public string Phone { get; set; }
    public string Bio { get; set; }
    public string PreferenceJSON { get; set; }
}

// Query only what you need
var user = await _db.Users
    .Where(u => u.Email == email)
    .FirstOrDefaultAsync(); // Fast - small table

// Load details only when needed
var details = await _db.UserDetails
    .Where(d => d.UserId == user.Id)
    .FirstOrDefaultAsync();
```

### CAP Theorem and Consistency Trade-offs

**CAP Theorem:** You can only guarantee 2 of 3:
- **C**onsistency: All nodes see the same data
- **A**vailability: System responds to all requests
- **P**artition tolerance: System works despite network failures

```
            Consistency
                 △
                /│\
               / │ \
              /  │  \
             /   │   \
            / CA │ CP \
           /     │     \
          /      │      \
         /       │       \
        /________|________\
   Availability     Partition
                  Tolerance
          └────────────────┘
                  AP
```

**Practical implications:**

**CP (Consistency + Partition Tolerance):**
- Traditional SQL databases with strong consistency
- MongoDB with majority write concern
- System may be unavailable during network partition

**AP (Availability + Partition Tolerance):**
- Cassandra, DynamoDB
- System always available but may serve stale data
- Eventual consistency

**For most applications:**
```csharp
// Strong consistency for critical operations
using var transaction = await _db.Database.BeginTransactionAsync();
try
{
    // Transfer money - must be consistent
    await DebitAccount(fromAccount, amount);
    await CreditAccount(toAccount, amount);
    await transaction.CommitAsync();
}
catch
{
    await transaction.RollbackAsync();
}

// Eventual consistency for less critical data
await _cache.SetAsync("user-profile", profile, TimeSpan.FromMinutes(5));
// Profile updates propagate eventually, but UI is fast
```

### Challenges with Sharding

#### 1. Cross-Shard Queries

```csharp
// ❌ Expensive: Query across all shards
public async Task<List<Order>> SearchOrders(string productName)
{
    var tasks = _shards.Select(async shard =>
    {
        using var context = CreateContext(shard);
        return await context.Orders
            .Where(o => o.Items.Any(i => i.ProductName.Contains(productName)))
            .ToListAsync();
    });
    
    return (await Task.WhenAll(tasks)).SelectMany(x => x).ToList();
}

// ✅ Better: Use search index (Elasticsearch)
public async Task<List<Order>> SearchOrders(string productName)
{
    return await _searchClient.SearchAsync<Order>(
        s => s.Match(m => m.Field(f => f.ProductName).Query(productName)));
}
```

#### 2. Resharding

```csharp
// Moving data between shards is complex
public async Task ReshardUser(int userId, string fromShard, string toShard)
{
    // 1. Copy data to new shard
    using var sourceContext = CreateContext(fromShard);
    using var destContext = CreateContext(toShard);
    
    var userData = await sourceContext.Users
        .Include(u => u.Orders)
        .FirstAsync(u => u.Id == userId);
    
    destContext.Users.Add(userData);
    await destContext.SaveChangesAsync();
    
    // 2. Update shard routing
    await _router.UpdateUserShard(userId, toShard);
    
    // 3. Delete from old shard
    sourceContext.Users.Remove(userData);
    await sourceContext.SaveChangesAsync();
}
```

#### 3. Distributed Transactions

Use Saga pattern instead of 2PC:

```csharp
public class CreateOrderSaga
{
    public async Task ExecuteAsync(CreateOrderRequest request)
    {
        var orderId = Guid.NewGuid();
        
        try
        {
            // Step 1: Create order in user's shard
            using var orderContext = _factory.CreateContext(request.UserId);
            var order = new Order { Id = orderId, UserId = request.UserId };
            orderContext.Orders.Add(order);
            await orderContext.SaveChangesAsync();
            
            // Step 2: Update inventory (different shard)
            using var inventoryContext = _factory.CreateContext(request.ProductId);
            await inventoryContext.ReserveInventoryAsync(request.ProductId, request.Quantity);
            
            // Step 3: Process payment (external service)
            await _paymentService.ChargeAsync(orderId, request.PaymentInfo);
        }
        catch (Exception ex)
        {
            // Compensating transactions
            await CompensateAsync(orderId, request);
            throw;
        }
    }
}
```

## Choosing the Right Strategy

| Workload | Strategy | Why |
|----------|----------|-----|
| Read-heavy (90%+ reads) | Read replicas | Distributes read load |
| Write-heavy | Sharding | Distributes write load |
| Moderate load | Vertical scaling | Simplest approach |
| Geographic users | Geographic sharding | Reduces latency |
| Multi-tenant SaaS | Tenant sharding | Isolation and compliance |
| Exponential growth | Sharding + replicas | Maximum scalability |

---

## Key Takeaways

- **Vertical scaling is simplest** but has hard limits
- **Read replicas scale reads** but not writes - ideal for read-heavy workloads
- **Sharding scales writes** by distributing data across databases
- **Choose shard key carefully** - it determines query patterns and hotspots
- **Cross-shard queries are expensive** - design to avoid them
- **CAP theorem** - understand consistency trade-offs when scaling
- **Most systems combine strategies** - replicas within shards, vertical + horizontal
