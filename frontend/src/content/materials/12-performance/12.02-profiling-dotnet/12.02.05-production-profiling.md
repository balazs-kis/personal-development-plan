## Learning Objectives

By the end of this lesson, you will be able to:

## Introduction

Production profiling identifies performance issues that only appear with real users, real data, and real load. Unlike development profiling, production profiling must have minimal overhead and can't disrupt service. Modern .NET provides tools designed specifically for safe production diagnostics.

## Key Concepts Summary

### Production Profiling Challenges

**Must minimize overhead:**
- Can't pause application
- Can't restart services
- Performance impact < 5%
- No debugging symbols in production

**Must be safe:**
- No crashes or exceptions
- No memory leaks from profiler
- No data corruption
- Secure handling of sensitive data

**Must be actionable:**
- Capture real user scenarios
- Represent actual production load
- Include sufficient context

## dotnet-trace: Cross-Platform Production Tracing

### Why dotnet-trace?

**Advantages:**
- Low overhead (~5%)
- Cross-platform (Windows, Linux, macOS)
- No restart required
- Works with any .NET Core/.NET application
- Collects EventPipe traces

### Installing dotnet-trace

```bash
# Install globally
dotnet tool install --global dotnet-trace

# Or update if already installed
dotnet tool update --global dotnet-trace

# Verify installation
dotnet-trace --version
```

### Collecting Traces

**Basic collection:**
```bash
# Find processes
dotnet-trace ps

# Output:
# 12345  MyApp       /app/MyApp.dll

# Collect trace (default: 30 seconds)
dotnet-trace collect --process-id 12345

# Collect with duration
dotnet-trace collect --process-id 12345 --duration 00:01:00

# Collect specific events
dotnet-trace collect --process-id 12345 --providers Microsoft-Windows-DotNETRuntime
```

**Advanced collection:**
```bash
# Collect with CPU samples (better call stacks)
dotnet-trace collect --process-id 12345 --profile cpu-sampling

# Collect with GC events
dotnet-trace collect --process-id 12345 --profile gc-collect

# Output formats
dotnet-trace collect --process-id 12345 --format Speedscope  # For SpeedScope
dotnet-trace collect --process-id 12345 --format Chromium   # For Chrome DevTools
```

### Analyzing Traces

**Convert for analysis:**
```bash
# Convert to speedscope format
dotnet-trace convert trace.nettrace --format Speedscope

# Convert to Chromium format
dotnet-trace convert trace.nettrace --format Chromium

# View in:
# - Visual Studio (open .nettrace directly)
# - PerfView (Windows)
# - SpeedScope (web-based, any platform)
# - Chrome DevTools (chrome://tracing)
```

**Example workflow:**
```bash
# 1. Collect during slow request
dotnet-trace collect -p 12345 --duration 00:00:30

# 2. Convert to Speedscope
dotnet-trace convert trace_20260130_163000.nettrace --format Speedscope

# 3. Open in SpeedScope
# Visit https://www.speedscope.app/
# Drag and drop trace_20260130_163000.speedscope.json

# 4. Identify hot paths
# 5. Optimize code
# 6. Collect again to verify improvement
```

## dotnet-monitor: Automated Production Diagnostics

### What is dotnet-monitor?

A tool for **continuous monitoring** and **automated collection** of diagnostics:
- Collects traces, dumps, logs, and metrics
- REST API for triggering collection
- Rule-based automatic collection
- Designed for Kubernetes and containers

### Installing dotnet-monitor

**As Global Tool:**
```bash
dotnet tool install -g dotnet-monitor

# Run
dotnet monitor collect
```

**As Docker Container:**
```bash
docker run -d \
  --name dotnet-monitor \
  -p 52323:52323 \
  -v /tmp:/tmp \
  -e DOTNETMONITOR_Urls=http://*:52323 \
  mcr.microsoft.com/dotnet/monitor:8
```

**In Kubernetes:**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp
spec:
  containers:
  - name: app
    image: myapp:latest
    ports:
    - containerPort: 80
  - name: monitor
    image: mcr.microsoft.com/dotnet/monitor:8
    ports:
    - containerPort: 52323
    env:
    - name: DOTNETMONITOR_Urls
      value: http://*:52323
```

### Triggering Collections via API

**Collect trace:**
```bash
# CPU trace
curl http://localhost:52323/trace \
  -H "Content-Type: application/json" \
  -d '{"profile": "Cpu", "duration": "00:00:30"}' \
  --output cpu-trace.nettrace

# GC trace
curl http://localhost:52323/trace \
  -H "Content-Type: application/json" \
  -d '{"profile": "GcCollect", "duration": "00:00:30"}' \
  --output gc-trace.nettrace
```

**Collect memory dump:**
```bash
curl http://localhost:52323/dump \
  -o memory-dump.dmp
```

**Get metrics:**
```bash
curl http://localhost:52323/metrics
```

### Automated Collection Rules

**Configuration (appsettings.json):**
```json
{
  "DiagnosticPort": "/tmp/dotnet-monitor.sock",
  "Urls": "http://*:52323",
  "CollectionRules": {
    "HighCpuUsage": {
      "Trigger": {
        "Type": "EventCounter",
        "Settings": {
          "ProviderName": "System.Runtime",
          "CounterName": "cpu-usage",
          "GreaterThan": 80,
          "SlidingWindowDuration": "00:01:00"
        }
      },
      "Actions": [
        {
          "Type": "CollectTrace",
          "Settings": {
            "Profile": "Cpu",
            "Duration": "00:00:30",
            "Egress": "artifacts"
          }
        }
      ]
    },
    "HighMemoryUsage": {
      "Trigger": {
        "Type": "EventCounter",
        "Settings": {
          "ProviderName": "System.Runtime",
          "CounterName": "working-set",
          "GreaterThan": 500000000,
          "SlidingWindowDuration": "00:01:00"
        }
      },
      "Actions": [
        {
          "Type": "CollectGCDump",
          "Settings": {
            "Egress": "artifacts"
          }
        }
      ]
    }
  }
}
```

**How it works:**
1. dotnet-monitor watches metrics
2. When CPU > 80% for 1 minute → automatically collect CPU trace
3. When memory > 500 MB → automatically collect GC dump
4. Artifacts saved for analysis

## Application Insights Profiler

### Cloud-Based Profiling

**Advantages:**
- Always-on profiling in production
- No manual trace collection
- Automatic sampling (low overhead)
- Integrated with Application Insights
- AI-powered optimization recommendations

### Setting Up Application Insights Profiler

**1. Enable Application Insights:**
```csharp
// Program.cs
builder.Services.AddApplicationInsightsTelemetry();
```

**2. Enable Profiler:**
```bash
# Azure Portal:
# Application Insights → Configure → Profiler → Enable Profiler

# Or via NuGet package:
dotnet add package Microsoft.ApplicationInsights.Profiler.AspNetCore
```

```csharp
// Program.cs
builder.Services.AddServiceProfiler();
```

**3. Configure sampling:**
```json
{
  "ApplicationInsights": {
    "InstrumentationKey": "your-key",
    "Profiler": {
      "Enabled": true,
      "CollectionInterval": "00:01:00",
      "Duration": "00:00:30",
      "InitialDelay": "00:00:30"
    }
  }
}
```

### Analyzing Profiler Data

**In Azure Portal:**
```
1. Navigate to Application Insights
2. Performance → Profiler traces
3. Select time range
4. View flame graphs for actual requests
5. Identify slow operations
```

**Example insights:**

## PerfView Production Techniques

### Flight Recorder Mode

**Continuous, low-overhead monitoring:**
```bash
# Start circular buffer collection
PerfView.exe collect -CircularMB:500 -Process:MyApp

# Runs indefinitely with 500 MB ring buffer
# When issue occurs, stop collection
# Only last 500 MB of data is saved
```

**Triggered collection:**
```bash
# Collect when CPU exceeds threshold
PerfView.exe collect \
  -CircularMB:500 \
  -CollectMultiple:3 \
  -StopOnPerfCounter:Processor:*:% Processor Time:80

# Collects 3 traces when CPU > 80%
```

### Remote Collection

**Collect from remote machine:**
```bash
# On target machine: Enable Remote Desktop
# Run PerfView as Administrator

# Or use PerfView's remote collection:
PerfView.exe collect /AcceptEULA /MaxCollectSec:60 ^
  /DataFile:C:\traces\remote-trace.etl ^
  /Providers:*Microsoft-Windows-DotNETRuntime
```

## Production Profiling Best Practices

### 1. Minimize Overhead

```
Target overhead: < 5% performance impact

Techniques:
✅ Use sampling (not instrumentation)
✅ Collect short durations (30-60 seconds)
✅ Use profiler sampling rates (e.g., 1 sample/ms)
❌ Don't collect full heap dumps in production
❌ Don't enable verbose GC logging permanently
```

### 2. Secure Sensitive Data

```csharp
// Redact sensitive data in traces
public class SecureLogger
{
    public void LogRequest(HttpRequest request)
    {
        var sanitizedHeaders = request.Headers
            .Where(h => !IsSensitiveHeader(h.Key))
            .ToDictionary(h => h.Key, h => h.Value);
        
        _logger.LogInformation(
            "Request: {Method} {Path} Headers: {@Headers}",
            request.Method,
            request.Path,
            sanitizedHeaders);
    }
    
    private bool IsSensitiveHeader(string headerName)
    {
        return headerName.Equals("Authorization", StringComparison.OrdinalIgnoreCase)
            || headerName.Equals("Cookie", StringComparison.OrdinalIgnoreCase);
    }
}
```

### 3. Automate Collection

```csharp
// Health check triggers diagnostic collection
public class PerformanceHealthCheck : IHealthCheck
{
    private readonly IDiagnosticCollector _collector;
    
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context,
        CancellationToken ct)
    {
        var cpu = GetCpuUsage();
        
        if (cpu > 90)
        {
            // Trigger automatic trace collection
            await _collector.CollectCpuTraceAsync(TimeSpan.FromSeconds(30));
            
            return HealthCheckResult.Unhealthy(
                $"CPU critical: {cpu}%. Trace collected.");
        }
        
        return HealthCheckResult.Healthy($"CPU normal: {cpu}%");
    }
}
```

### 4. Correlate with Monitoring

```csharp
// Add correlation IDs to traces
public class TraceCorrelationMiddleware
{
    private readonly RequestDelegate _next;
    
    public async Task InvokeAsync(HttpContext context)
    {
        var correlationId = Guid.NewGuid().ToString();
        context.Items["CorrelationId"] = correlationId;
        
        // Add to Activity for distributed tracing
        Activity.Current?.SetTag("correlation.id", correlationId);
        
        // Log for correlation with metrics/logs
        using (_logger.BeginScope(new Dictionary<string, object>
        {
            ["CorrelationId"] = correlationId
        }))
        {
            await _next(context);
        }
    }
}

// When profiling, include correlation ID:
// dotnet-trace collect -p 12345 --tag correlation.id=abc-123
```

## Example: Investigating Production Slowness

### Scenario

**Symptom:** API response times increased from 100ms to 1000ms.

**Investigation steps:**

**1. Collect trace:**
```bash
# During slow period
dotnet-trace collect -p 12345 --duration 00:01:00 --format Speedscope

# Save with timestamp for correlation
mv trace.nettrace traces/slow-$(date +%Y%m%d_%H%M%S).nettrace
```

**2. Analyze flame graph:**
```
[HTTP Handler] 100% (1000ms)
└─ [GetOrders] 95% (950ms)
   ├─ [DatabaseQuery] 10% (100ms)
   └─ [EnrichOrders] 85% (850ms) ← HOT PATH
      └─ [GetCustomerDetails] 85% (850ms)
         └─ [HttpClient.GetAsync] 85% (850ms) ← External API!
```

**3. Root cause:**
- External API (customer service) experiencing issues
- Slowing down every request
- No timeout configured

**4. Fix:**
```csharp
// Add timeout and fallback
public async Task<CustomerDetails> GetCustomerDetails(int customerId)
{
    using var cts = new CancellationTokenSource(TimeSpan.FromMilliseconds(500));
    
    try
    {
        var response = await _httpClient.GetAsync(
            $"/customers/{customerId}",
            cts.Token);
        
        return await response.Content.ReadFromJsonAsync<CustomerDetails>();
    }
    catch (OperationCanceledException)
    {
        // Return cached/default data
        return await _cache.GetOrDefault(customerId);
    }
}
```

**5. Verify fix:**
```bash
# Collect trace after fix
dotnet-trace collect -p 12345 --duration 00:01:00 --format Speedscope

# Compare: 1000ms → 150ms (timeout enforced, fallback used)
```

## Summary

Production profiling uses low-overhead tools like dotnet-trace, dotnet-monitor, and Application Insights Profiler to diagnose issues in live systems. Always minimize overhead (< 5%), automate collection with triggers, and correlate profiling data with logs and metrics. Use sampling-based profiling, collect short durations, and secure sensitive data in traces. Production profiling reveals issues that only appear with real users and real load, making it essential for maintaining performance at scale.
