## Introduction

When working with multiple database records, the difference between operating one-at-a-time versus in batches can be dramatic—potentially reducing operation time from minutes to seconds. Entity Framework Core includes batching capabilities that group multiple operations into fewer database roundtrips. Additionally, EF Core 7+ introduces `ExecuteUpdateAsync` and `ExecuteDeleteAsync` for direct bulk operations without loading entities into memory. Understanding when and how to use these techniques is essential for high-performance data operations.

## Key Concepts Summary

### Understanding EF Core Batching

**How Batching Works:**
```csharp
// Without explicit batching - each Save is a separate roundtrip
foreach (var customer in customers)
{
    _context.Customers.Add(customer);
    await _context.SaveChangesAsync(); // ❌ 100 roundtrips for 100 records
}

// With batching - multiple operations in one roundtrip
_context.Customers.AddRange(customers); // Track all
await _context.SaveChangesAsync(); // ✅ 1-3 roundtrips for 100 records
```

**Automatic Batching:**
```
EF Core automatically batches operations when you call SaveChanges:
- Groups multiple INSERT, UPDATE, DELETE statements
- Sends them in fewer database roundtrips
- SQL Server default: up to 42 statements per batch
- Reduces network latency overhead
```

**Batch Size Configuration:**
```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString, sqlOptions =>
    {
        sqlOptions.MinBatchSize(4);  // Batch if >= 4 statements
        sqlOptions.MaxBatchSize(100); // Max 100 statements per batch
    }));

// Default values:
// MinBatchSize: 4
// MaxBatchSize: 42 (SQL Server)
// Provider-specific defaults may vary
```

### Using AddRange for Bulk Inserts

**AddRange Best Practices:**
```csharp
// ✅ GOOD: Add all entities at once
var orders = GenerateOrders(1000);
_context.Orders.AddRange(orders);
await _context.SaveChangesAsync();

// Results in ~3 batches of ~350 records each (depending on config)
// Much faster than 1000 individual inserts

// ❌ BAD: Adding and saving one at a time
foreach (var order in orders)
{
    _context.Orders.Add(order);
    await _context.SaveChangesAsync(); // DON'T DO THIS!
}
```

**Performance Comparison:**
```
Inserting 1,000 records:

Method 1 (Individual saves):
- 1,000 SaveChanges calls
- 1,000 database roundtrips
- ~15-30 seconds

Method 2 (AddRange + one Save):
- 1 SaveChanges call
- 3-5 database roundtrips (batched)
- ~500ms - 1 second

Result: 15-30x performance improvement!
```

**Chunking Large Datasets:**
```csharp
// For very large datasets (100,000+ records), process in chunks
public async Task BulkInsertAsync<T>(IEnumerable<T> entities) where T : class
{
    const int chunkSize = 10_000;
    
    var chunks = entities.Chunk(chunkSize);
    
    foreach (var chunk in chunks)
    {
        _context.Set<T>().AddRange(chunk);
        await _context.SaveChangesAsync();
        _context.ChangeTracker.Clear(); // Clear tracking to free memory
    }
}

// Why chunk?
// - Prevents excessive memory usage
// - Avoids transaction log overflow
// - Provides progress feedback opportunity
```

### Bulk Updates and Deletes (EF Core 7+)

**Traditional Update Approach (Slow):**
```csharp
// ❌ SLOW: Load entities, modify, save
var orders = await _context.Orders
    .Where(o => o.Status == "Pending")
    .ToListAsync(); // Loads all matching records into memory

foreach (var order in orders)
{
    order.Status = "Cancelled";
}

await _context.SaveChangesAsync();

// Problems:
// - Loads all data into memory (unnecessary)
// - Generates UPDATE statement for each row
// - Slow for large datasets
```

**ExecuteUpdate (Fast):**
```csharp
// ✅ FAST: Direct SQL UPDATE without loading entities
await _context.Orders
    .Where(o => o.Status == "Pending")
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(o => o.Status, "Cancelled")
        .SetProperty(o => o.UpdatedAt, DateTime.UtcNow));

// Generates single SQL statement:
// UPDATE Orders 
// SET Status = 'Cancelled', UpdatedAt = GETUTCDATE()
// WHERE Status = 'Pending'

// Benefits:
// - No entities loaded into memory
// - Single UPDATE statement (not one per row)
// - 60x faster for large datasets
```

**ExecuteUpdate Advanced Examples:**
```csharp
// Update with calculations
await _context.Products
    .Where(p => p.Category == "Electronics")
    .ExecuteUpdateAsync(s => s
        .SetProperty(p => p.Price, p => p.Price * 0.9m)); // 10% discount

// Update with concatenation
await _context.Users
    .Where(u => u.IsVerified)
    .ExecuteUpdateAsync(s => s
        .SetProperty(u => u.DisplayName, u => u.FirstName + " " + u.LastName));

// Conditional update
await _context.Orders
    .Where(o => o.OrderDate < DateTime.UtcNow.AddDays(-30))
    .ExecuteUpdateAsync(s => s
        .SetProperty(o => o.Status, o => o.TotalAmount > 1000 ? "VIP" : "Standard"));
```

**ExecuteDelete:**
```csharp
// ❌ SLOW: Load and delete
var oldLogs = await _context.Logs
    .Where(l => l.CreatedAt < DateTime.UtcNow.AddMonths(-6))
    .ToListAsync();
_context.Logs.RemoveRange(oldLogs);
await _context.SaveChangesAsync();

// ✅ FAST: Direct DELETE
await _context.Logs
    .Where(l => l.CreatedAt < DateTime.UtcNow.AddMonths(-6))
    .ExecuteDeleteAsync();

// Generates:
// DELETE FROM Logs WHERE CreatedAt < @date
```

### When to Use Each Approach

**ExecuteUpdate / ExecuteDelete:**
```
✅ Use when:
- Updating/deleting many records based on criteria
- Don't need to load entities into memory
- Don't need change tracking
- Don't need to trigger entity events
- Performance is critical

❌ Don't use when:
- Need to execute business logic per entity
- Need to trigger navigation property updates
- Need audit logging via interceptors
- Working with complex entity graphs
```

**AddRange / UpdateRange / RemoveRange:**
```
✅ Use when:
- Need change tracking and navigation fix-up
- Entities already loaded for other reasons
- Need to validate/transform entities in memory
- Working with related entities
- Need audit trail through interceptors

❌ Don't use when:
- Simple bulk updates without business logic
- Very large datasets (memory constraints)
```

**Traditional One-by-One:**
```
✅ Use when:
- Complex business logic per entity
- Need fine-grained error handling
- Processing heterogeneous operations
- Small datasets (<100 records)

❌ Avoid when:
- Bulk operations on similar entities
- Performance is important
- Large datasets
```

### Handling Large Batches

**Memory-Efficient Processing:**
```csharp
public async Task ProcessLargeDataset(IQueryable<Order> query)
{
    const int pageSize = 1000;
    var page = 0;
    
    while (true)
    {
        var batch = await query
            .OrderBy(o => o.Id)
            .Skip(page * pageSize)
            .Take(pageSize)
            .ToListAsync();
        
        if (!batch.Any()) break;
        
        // Process batch
        foreach (var order in batch)
        {
            order.ProcessingDate = DateTime.UtcNow;
        }
        
        await _context.SaveChangesAsync();
        _context.ChangeTracker.Clear(); // Free memory
        
        page++;
    }
}
```

**Monitoring Batch Performance:**
```csharp
public async Task BulkInsertWithMonitoring<T>(List<T> entities) where T : class
{
    var stopwatch = Stopwatch.StartNew();
    var entityCount = entities.Count;
    
    _context.Set<T>().AddRange(entities);
    
    var tracked = stopwatch.ElapsedMilliseconds;
    Console.WriteLine($"Tracked {entityCount} entities in {tracked}ms");
    
    await _context.SaveChangesAsync();
    
    var saved = stopwatch.ElapsedMilliseconds;
    Console.WriteLine($"Saved {entityCount} entities in {saved}ms");
    Console.WriteLine($"Average: {(double)saved / entityCount:F2}ms per entity");
}
```
