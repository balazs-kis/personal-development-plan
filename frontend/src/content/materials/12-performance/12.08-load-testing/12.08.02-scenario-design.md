# Lesson 2: Test Scenario Design and Planning

## Learning Objectives

By the end of this lesson, you will be able to:
- Design realistic load test scenarios based on user behavior
- Gather data to inform test design
- Create virtual user patterns that simulate production traffic
- Plan test environments and data requirements
- Avoid common scenario design mistakes

---

## Introduction

The most common load testing mistake is unrealistic scenarios. Simply hammering an endpoint with requests doesn't reveal how your system will behave under real user traffic. Effective load testing requires understanding user behavior patterns and simulating them accurately.

## Key Concepts Summary

### Understanding User Behavior

#### Gathering Real Data

Before designing scenarios, gather data from:

1. **Analytics Tools**
   - Google Analytics, Adobe Analytics, or similar
   - Page views, session duration, conversion funnels
   - Popular user flows and paths
   - Peak usage times and patterns

2. **Application Logs**
   - API endpoint hit frequencies
   - Request patterns and sequences
   - User session characteristics
   - Error rates and failure modes

3. **Business Requirements**
   - Expected user growth
   - Marketing campaigns and their expected impact
   - Seasonal patterns (e.g., tax season, holidays)
   - SLA commitments

4. **Stakeholder Interviews**
   - Product managers: feature usage expectations
   - Marketing: campaign volumes and timing
   - Support: common user issues and workflows

#### Key Questions to Answer

- **How many total users?** Daily active users, monthly active users
- **How many concurrent users?** Peak simultaneous users
- **What do users do?** Common workflows and actions
- **How often?** Request frequency, session duration
- **What's the think time?** Delays between user actions
- **What's the distribution?** Not all users do the same things

### Virtual User Design Patterns

#### 1. Realistic User Journeys

❌ **Wrong:** Send 1,000 requests/second to a single endpoint

✅ **Right:** Simulate user journeys with multiple steps

```javascript
// Pseudo-code for realistic scenario
scenario: 'Shop and Buy'
  1. GET /home                    (start)
  2. Think 3-5 seconds            (user reads)
  3. GET /products?category=electronics
  4. Think 5-10 seconds           (user browses)
  5. GET /product/123             (view details)
  6. Think 8-15 seconds           (user decides)
  7. POST /cart/add               (add to cart)
  8. Think 2-3 seconds
  9. GET /cart                    (view cart)
  10. Think 5-10 seconds          (user reviews)
  11. POST /checkout              (purchase)
```

#### 2. Think Time

Users don't instantly move between actions. They read, decide, get distracted.

```javascript
// Without think time (unrealistic)
for (i = 0; i < 100; i++) {
  http.get('/page');
  http.post('/action');
}

// With realistic think time
for (i = 0; i < 100; i++) {
  http.get('/page');
  sleep(randomBetween(3, 8));  // seconds
  http.post('/action');
  sleep(randomBetween(2, 5));
}
```

**Think time considerations:**
- Varies by user action (reading takes longer than clicking)
- Should be randomized (not all users identical)
- Includes network latency in real scenarios
- Shorter during urgent tasks (checkout vs browsing)

#### 3. User Personas and Distribution

Not all users follow the same path. Create personas with different behavior:

```
Scenario Mix:
- 60% Browsers: view products, search, leave
- 25% Shoppers: browse, add to cart, abandon
- 10% Buyers: browse, add to cart, checkout
- 5% Account Managers: login, view orders, update profile
```

Each persona has:
- Different actions
- Different think times
- Different success criteria
- Different data requirements

#### 4. Stateful Sessions

Maintain state across requests like real browsers:

```javascript
// Track session state
let sessionId = login(username, password);
let cartId = createCart(sessionId);
addToCart(sessionId, cartId, productId);
checkout(sessionId, cartId);
```

Include:
- Authentication tokens
- Session cookies
- CSRF tokens
- Shopping cart state
- User preferences

### Data Requirements

#### Test Data Characteristics

1. **Volume**
   - Match production data size
   - Realistic database record counts
   - Appropriate number of users, products, orders

2. **Variety**
   - Different data types and values
   - Edge cases (empty strings, nulls, large values)
   - Avoid patterns that artificially help caching

3. **Realism**
   - Real-world data distributions
   - Appropriate relationships between entities
   - Valid but varied input data

#### Dynamic vs Static Data

**Static Data:** Same for all users
- Product catalog
- Category listings
- Content pages

**Dynamic Data:** Unique per user/session
- User credentials
- Email addresses
- Order IDs
- Payment information

#### Data Generation Strategies

**Option 1: CSV Files**
```
username,password,email
user001,Pass123!,user001@test.com
user002,Pass456!,user002@test.com
user003,Pass789!,user003@test.com
```

**Option 2: Faker Libraries**
```javascript
import { faker } from 'faker';

let user = {
  email: faker.internet.email(),
  name: faker.person.fullName(),
  address: faker.location.streetAddress()
};
```

**Option 3: API-Generated**
```javascript
// Pre-test setup: create test users via API
let users = [];
for (let i = 0; i < 1000; i++) {
  let user = createTestUser();
  users.push(user);
}
```

### Load Profile Design

#### Ramp-Up Patterns

**Gradual Ramp:**
```
0 min:    0 users
5 min:  100 users
10 min: 200 users
15 min: 300 users
20 min: 300 users (sustained)
25 min: 200 users
30 min: 100 users
35 min:   0 users
```

**Spike Pattern:**
```
0 min:    100 users
5 min:    100 users
6 min:  1,000 users (sudden spike)
10 min: 1,000 users
11 min:   100 users (return to normal)
15 min:   100 users
```

**Step Pattern:**
```
0-5 min:   100 users
5-10 min:  200 users
10-15 min: 400 users
15-20 min: 800 users
```

### Environment Considerations

#### Production-Like Environment

Your test environment should match production:

**Infrastructure:**
- Same server types and sizes
- Same network topology
- Same geographical distribution
- Similar database configuration

**Dependencies:**
- External APIs (mocked or sandbox versions)
- Authentication services
- Payment gateways (test mode)
- Caching layers
- Message queues

#### Test Environment Challenges

| Challenge | Solution |
|-----------|----------|
| Cost of full-size environment | Scale down proportionally but maintain ratios |
| External service limits | Use mocks or stubs for testing |
| Data privacy | Anonymize production data or generate synthetic data |
| Database state | Reset between tests or use isolated test data |

### Scenario Design Template

```markdown
## Scenario: [Name]

**Purpose:** [What are we testing?]

**User Type:** [Browser/Buyer/Admin/etc.]

**Frequency:** [What % of total users?]

**Steps:**
1. [Action] - Expected response time: [X]ms
   - Request: [Method] [URL]
   - Data: [Description]
   - Think time: [X-Y] seconds

2. [Action] - Expected response time: [X]ms
   - Request: [Method] [URL]
   - Data: [Description]
   - Think time: [X-Y] seconds

**Success Criteria:**
- Average response time < [X]ms
- 95th percentile < [Y]ms
- Error rate < [Z]%

**Load Profile:**
- Concurrent users: [N]
- Duration: [X] minutes
- Ramp-up: [Y] minutes
```

### Common Scenario Design Mistakes

| Mistake | Problem | Solution |
|---------|---------|----------|
| **No think time** | Unrealistic request rate | Add randomized delays |
| **Static data** | Caching artificially helps | Vary request parameters |
| **Single endpoint** | Doesn't test real flows | Create complete user journeys |
| **Uniform users** | All users act identically | Create personas with different behaviors |
| **Ignoring dependencies** | Bottlenecks in external services missed | Include dependencies in test |
| **No warm-up period** | Initial cold start skews results | Add gradual ramp-up |

## Practical Example: API Load Test Design

### Scenario: E-Commerce API

#### Step 1: Gather Data

From analytics:
- 10,000 daily active users
- Peak: 500 concurrent users
- Average session: 5 minutes
- 60% browse only
- 30% add to cart
- 10% complete purchase

#### Step 2: Define Personas

**Browser (60%)**
```
1. GET /api/products?category=random
2. Think 5-8 seconds
3. GET /api/products/{id}
4. Think 10-15 seconds
5. Repeat 2-3 times
6. Exit
```

**Shopper (30%)**
```
1. GET /api/products?category=random
2. Think 5-8 seconds
3. GET /api/products/{id}
4. Think 8-12 seconds
5. POST /api/cart/items (add to cart)
6. Think 3-5 seconds
7. GET /api/cart
8. Think 5-10 seconds
9. Exit (abandon cart)
```

**Buyer (10%)**
```
1. POST /api/auth/login
2. Think 2-3 seconds
3. GET /api/products?category=random
4. Think 5-8 seconds
5. GET /api/products/{id}
6. Think 8-12 seconds
7. POST /api/cart/items
8. Think 2-3 seconds
9. GET /api/cart
10. Think 3-5 seconds
11. POST /api/checkout
12. Think 15-20 seconds (payment form)
13. POST /api/orders
```

#### Step 3: Load Profile

```
Target: 500 concurrent users at peak

0-5 min:   Ramp to 100 users
5-10 min:  Ramp to 300 users
10-20 min: Ramp to 500 users (peak)
20-30 min: Maintain 500 users
30-35 min: Ramp down to 100 users
35-40 min: Ramp down to 0 users
```

#### Step 4: Success Criteria

| Metric | Target |
|--------|--------|
| Product listing | < 200ms (95th percentile) |
| Product details | < 150ms (95th percentile) |
| Add to cart | < 100ms (95th percentile) |
| Checkout | < 500ms (95th percentile) |
| Overall error rate | < 0.1% |
| Database CPU | < 70% |
| API server CPU | < 80% |

## Best Practices Checklist

✅ Base scenarios on real user data from analytics

✅ Create multiple user personas with different behaviors

✅ Include realistic think times between actions

✅ Use dynamic, varied test data

✅ Simulate complete user journeys, not isolated requests

✅ Maintain state (cookies, tokens) across requests

✅ Include warm-up period before measuring

✅ Test in production-like environment

✅ Define clear success criteria before testing

✅ Consider dependencies and external services

## Practice Exercise

Design a load test scenario for your application:

1. **Gather data:**
   - Review analytics or logs
   - Identify top 3-5 user flows
   - Determine typical and peak user counts

2. **Create personas:**
   - Define 2-3 user types
   - Map their typical actions
   - Estimate distribution (%)

3. **Design scenario:**
   - Write step-by-step user journey
   - Add think times
   - Specify test data requirements

4. **Define load profile:**
   - Determine concurrent user targets
   - Plan ramp-up/ramp-down
   - Set test duration

5. **Set success criteria:**
   - Response time targets
   - Error rate thresholds
   - Resource utilization limits
