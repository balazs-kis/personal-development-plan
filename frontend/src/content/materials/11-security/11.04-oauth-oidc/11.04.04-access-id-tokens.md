# Lesson 4: Access Tokens vs ID Tokens

## Learning Objectives

By the end of this lesson, you will be able to:
- Clearly distinguish between access tokens and ID tokens
- Understand when to use each token type
- Identify common mistakes in token usage
- Implement proper token handling in applications

---

## Introduction

One of the most common sources of OAuth 2.0 and OpenID Connect implementation errors is confusing access tokens and ID tokens. While both are credentials, they serve fundamentally different purposes and must be used correctly to maintain security.

**The golden rule:** ID tokens are for authentication (who the user is), access tokens are for authorization (what the user can access).

## Key Concepts Summary

### The Core Difference

```
┌────────────────────────────────────────────────────────┐
│ ID TOKEN                                               │
│ ─────────                                              │
│ Purpose:  AUTHENTICATION - "Who is the user?"          │
│ Audience: Your application (the client)                │
│ Contains: User identity claims (name, email, etc.)     │
│ Used for: Login, displaying user info, creating       │
│           sessions                                     │
│ Format:   Always JWT                                   │
│ Where:    Sent to and validated by your app           │
└────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────┐
│ ACCESS TOKEN                                           │
│ ────────────                                           │
│ Purpose:  AUTHORIZATION - "What can the user do?"      │
│ Audience: Resource server (API)                        │
│ Contains: Scopes, permissions, authorization data      │
│ Used for: Accessing protected APIs                     │
│ Format:   Opaque string OR JWT (depends on provider)   │
│ Where:    Sent to and validated by API servers        │
└────────────────────────────────────────────────────────┘
```

### Real-World Analogy

```
ID Token = Your Driver's License
  - Proves who you are
  - Contains your photo, name, address
  - You show it to prove your identity

Access Token = Your Hotel Room Key
  - Proves what you can access
  - Grants access to specific resources (your room)
  - You use it to open doors, not to identify yourself
```

## Token Structure Comparison

### ID Token (Always JWT)

```json
{
  "iss": "https://auth.example.com",      // Who issued it
  "sub": "248289761001",                  // User ID (unique identifier)
  "aud": "your-client-id",                // YOUR APP (audience)
  "exp": 1641234567,                      // Expiration
  "iat": 1641230967,                      // Issued at
  "nonce": "abc123",                      // CSRF protection
  
  // User identity information
  "name": "Jane Smith",
  "email": "jane.smith@example.com",
  "email_verified": true,
  "picture": "https://example.com/jane.jpg",
  "locale": "en-US"
}
```

**Key characteristics:**
- Always a JWT (can be decoded and read)
- Contains user identity claims
- Audience (`aud`) is your client application
- Validated by your application
- Not sent to APIs

### Access Token (Opaque or JWT)

**Option 1: Opaque (Reference Token)**
```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWV9.TJVA95OrM7E2cBab30RMHrHDcEfxjoYZgeFONFh7HgQ
```
- Meaningless string to the client
- API validates with authorization server
- More secure (can't be decoded)

**Option 2: JWT (Self-Contained)**
```json
{
  "iss": "https://auth.example.com",      // Who issued it
  "sub": "248289761001",                  // User ID
  "aud": "https://api.example.com",       // API ENDPOINT (audience)
  "exp": 1641234567,                      // Short expiration
  "iat": 1641230967,                      // Issued at
  
  // Authorization information
  "scope": "read:posts write:posts",
  "permissions": ["post:create", "post:edit"],
  "roles": ["editor"],
  
  // Minimal user info (if any)
  "email": "jane.smith@example.com"
}
```

**Key characteristics:**
- May be opaque or JWT
- Contains authorization data (scopes, permissions)
- Audience (`aud`) is the API/resource server
- Validated by the API
- Sent with every API request

## Usage Patterns

### ❌ WRONG: Using ID Token for API Calls

```csharp
// DON'T DO THIS
var idToken = await HttpContext.GetTokenAsync("id_token");

var apiRequest = new HttpRequestMessage(HttpMethod.Get, "https://api.example.com/data");
apiRequest.Headers.Authorization = new AuthenticationHeaderValue("Bearer", idToken);

var response = await httpClient.SendAsync(apiRequest);
// This will fail or create security vulnerabilities
```

**Why this is wrong:**
1. ID token audience (`aud`) is your app, not the API
2. API can't validate the ID token (wrong audience)
3. ID token contains identity data, not authorization data
4. Violates the principle of least privilege

### ✅ CORRECT: Using Access Token for API Calls

```csharp
// Correct approach
var accessToken = await HttpContext.GetTokenAsync("access_token");

var apiRequest = new HttpRequestMessage(HttpMethod.Get, "https://api.example.com/data");
apiRequest.Headers.Authorization = new AuthenticationHeaderValue("Bearer", accessToken);

var response = await httpClient.SendAsync(apiRequest);
// API validates access token and checks permissions
```

### ❌ WRONG: Using Access Token for User Information

```csharp
// DON'T DO THIS
var accessToken = ParseJwt(await HttpContext.GetTokenAsync("access_token"));
var userName = accessToken.Claims.FirstOrDefault(c => c.Type == "name")?.Value;

// Access token might not contain user claims
// Even if it does, this is not its intended purpose
```

### ✅ CORRECT: Using ID Token for User Information

```csharp
// Correct approach
var idToken = ParseJwt(await HttpContext.GetTokenAsync("id_token"));
var userName = idToken.Claims.FirstOrDefault(c => c.Type == "name")?.Value;
var userEmail = idToken.Claims.FirstOrDefault(c => c.Type == "email")?.Value;

// Display user information in UI
return View(new { Name = userName, Email = userEmail });
```

## Complete Example

### Login and Display User Info

```csharp
[Authorize]
public class ProfileController : Controller
{
    private readonly IHttpClientFactory _httpClientFactory;
    
    public async Task<IActionResult> Index()
    {
        // Get ID token for user identity
        var idToken = await HttpContext.GetTokenAsync("id_token");
        var idTokenJwt = new JwtSecurityTokenHandler().ReadJwtToken(idToken);
        
        // Extract user claims from ID token
        var userId = idTokenJwt.Claims.First(c => c.Type == "sub").Value;
        var userName = idTokenJwt.Claims.First(c => c.Type == "name").Value;
        var userEmail = idTokenJwt.Claims.First(c => c.Type == "email").Value;
        var userPicture = idTokenJwt.Claims.FirstOrDefault(c => c.Type == "picture")?.Value;
        
        // Get access token for API calls
        var accessToken = await HttpContext.GetTokenAsync("access_token");
        
        // Call API with access token
        var httpClient = _httpClientFactory.CreateClient();
        httpClient.DefaultRequestHeaders.Authorization = 
            new AuthenticationHeaderValue("Bearer", accessToken);
        
        var userData = await httpClient.GetFromJsonAsync<UserData>(
            "https://api.example.com/users/me");
        
        return View(new ProfileViewModel
        {
            // From ID token
            UserId = userId,
            Name = userName,
            Email = userEmail,
            Picture = userPicture,
            
            // From API (using access token)
            Posts = userData.Posts,
            Followers = userData.Followers
        });
    }
}
```

## Token Lifetime and Storage

### ID Tokens

```
Lifetime: Short to medium (15 minutes - 1 hour)
Storage:  
  - Server-side session (best)
  - HttpOnly cookie (good)
  - Memory only (for SPAs)
  - Never in localStorage (XSS vulnerable)

Refresh: No direct refresh mechanism
         Get new ID token by:
         1. Re-authenticating user, OR
         2. Using refresh token to get new token set
```

### Access Tokens

```
Lifetime: Very short (5 minutes - 1 hour)
Storage:
  - Server-side session (best)
  - Memory only (for SPAs)
  - Never in localStorage (XSS vulnerable)

Refresh: Use refresh token to get new access token
         without re-authentication
```

## Token Validation

### ID Token Validation (Client-Side)

```csharp
public bool ValidateIdToken(string idToken, string expectedNonce)
{
    var tokenHandler = new JwtSecurityTokenHandler();
    var validationParameters = new TokenValidationParameters
    {
        ValidateIssuer = true,
        ValidIssuer = "https://auth.example.com",
        
        ValidateAudience = true,
        ValidAudience = "your-client-id",  // YOUR APP
        
        ValidateLifetime = true,
        ClockSkew = TimeSpan.FromMinutes(5),
        
        ValidateIssuerSigningKey = true,
        IssuerSigningKeys = GetSigningKeysFromJwks()
    };
    
    try
    {
        var principal = tokenHandler.ValidateToken(idToken, validationParameters, 
            out SecurityToken validatedToken);
        
        // Validate nonce
        var nonce = principal.FindFirst("nonce")?.Value;
        if (nonce != expectedNonce)
            return false;
        
        return true;
    }
    catch
    {
        return false;
    }
}
```

### Access Token Validation (API-Side)

```csharp
// In your API
services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://auth.example.com";
        options.Audience = "https://api.example.com";  // API ENDPOINT
        
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true
        };
    });

// In your controller
[Authorize]
[ApiController]
[Route("api/[controller]")]
public class DataController : ControllerBase
{
    [HttpGet]
    public IActionResult GetData()
    {
        // Access token automatically validated by middleware
        var userId = User.FindFirst("sub")?.Value;
        var scopes = User.FindFirst("scope")?.Value.Split(' ');
        
        if (!scopes.Contains("read:data"))
            return Forbid();
        
        return Ok(GetUserData(userId));
    }
}
```

## Common Mistakes and Fixes

### Mistake 1: Sending ID Token to APIs

```csharp
// ❌ WRONG
Authorization: Bearer <ID_TOKEN>

// ✅ CORRECT
Authorization: Bearer <ACCESS_TOKEN>
```

### Mistake 2: Using Access Token for User Display

```csharp
// ❌ WRONG - Access token might not have name claim
var name = accessToken.Claims["name"];

// ✅ CORRECT - Use ID token for identity
var name = idToken.Claims["name"];
```

### Mistake 3: Validating Token Against Wrong Audience

```csharp
// API validation
// ❌ WRONG - Accepting your client ID as audience
ValidAudience = "your-client-id"

// ✅ CORRECT - API expects its own identifier
ValidAudience = "https://api.example.com"
```

### Mistake 4: Storing Tokens Insecurely

```javascript
// ❌ WRONG - Vulnerable to XSS
localStorage.setItem('access_token', token);
localStorage.setItem('id_token', idToken);

// ✅ CORRECT - Memory only (or httpOnly cookie for server)
let accessToken = null;  // In-memory, cleared on page reload

// Or better: Backend for Frontend (BFF) pattern
// Tokens stay in backend, session cookie to frontend
```

## When You Need Both

Most real applications use both tokens:

```typescript
// After successful login
const tokenResponse = await exchangeCodeForTokens(code);

// Store tokens
const idToken = tokenResponse.id_token;      // For user info
const accessToken = tokenResponse.access_token;  // For API calls
const refreshToken = tokenResponse.refresh_token; // For refresh

// Display user information (use ID token)
const userClaims = parseJwt(idToken);
displayWelcomeMessage(userClaims.name);
displayUserAvatar(userClaims.picture);

// Fetch user's data from API (use access token)
const response = await fetch('https://api.example.com/user/posts', {
  headers: {
    'Authorization': `Bearer ${accessToken}`
  }
});

const posts = await response.json();
displayPosts(posts);
```

## Summary Table

| Aspect | ID Token | Access Token |
|--------|----------|--------------|
| **Purpose** | Authentication | Authorization |
| **Question** | Who is the user? | What can they access? |
| **Audience** | Client application | Resource server (API) |
| **Format** | Always JWT | Opaque or JWT |
| **Contains** | User identity claims | Scopes, permissions |
| **Validated by** | Client application | API server |
| **Sent to** | Client only | APIs |
| **Used for** | Login, user display | API requests |
| **Can be decoded?** | Yes (JWT) | Maybe (if JWT) |
| **Refresh** | No direct refresh | Yes (refresh token) |
