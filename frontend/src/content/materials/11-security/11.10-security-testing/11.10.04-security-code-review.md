- Provide actionable security feedback to developers

---

## Introduction

Security code review is the practice of manually examining source code to identify security vulnerabilities, logic flaws, and design weaknesses that automated tools miss. While SAST tools catch many issues, human reviewers understand context, business logic, and subtle attack vectors that tools can't detect.

A skilled security code reviewer can find authentication bypasses, authorization flaws, race conditions, and business logic vulnerabilities that no automated tool would catch.

## Key Concepts Summary

### What is Security Code Review?

Security code review is a systematic examination of source code with a security mindset, looking for:
- **Vulnerability patterns:** SQL injection, XSS, CSRF, etc.
- **Logic flaws:** Authentication bypasses, privilege escalation
- **Cryptographic mistakes:** Weak algorithms, poor key management
- **Configuration issues:** Hard-coded secrets, insecure defaults
- **Architecture weaknesses:** Trust boundary violations, missing validation

### Why Manual Review Matters

**Context Awareness:** Humans understand business logic and can spot flaws that tools can't reason about.

**Logic Flaws:** Authentication bypasses, race conditions, and business logic vulnerabilities require human analysis.

**False Negative Reduction:** Automated tools miss many issues. Manual review catches what tools miss.

**Design Validation:** Reviewers validate security architecture and design decisions.

**Knowledge Sharing:** Reviews educate developers on secure coding practices.

### Security Review vs Functional Review

| Functional Review | Security Review |
|-------------------|-----------------|
| Does it work correctly? | Can it be exploited? |
| Is it maintainable? | Are trust boundaries respected? |
| Does it meet requirements? | Are inputs validated? |
| Is it efficient? | Are credentials protected? |

**Best Practice:** Integrate security checks into regular code reviews rather than treating them as separate activities.

## Security Code Review Process

### 1. Understand the Context

Before reviewing code, understand:
- **What does this code do?** (Authentication, data processing, API endpoint?)
- **What data does it handle?** (Public, sensitive, PII?)
- **Who can access it?** (Public, authenticated users, admins?)
- **What are the trust boundaries?** (User input, external APIs, database?)

### 2. Identify Risk Areas

Focus on high-risk code:
- **Authentication and authorization:** Login, password reset, role checks
- **Input validation:** User input, file uploads, API parameters
- **Data access:** Database queries, file operations, external APIs
- **Cryptography:** Encryption, hashing, key management
- **Session management:** Token generation, cookie handling
- **Error handling:** Exception messages, logging

### 3. Apply Security Patterns

Look for common vulnerability patterns:
- **Injection flaws:** SQL, NoSQL, command, LDAP injection
- **Broken authentication:** Weak passwords, session fixation, insecure storage
- **Sensitive data exposure:** Logging secrets, verbose errors
- **XML External Entities (XXE):** Unsafe XML parsing
- **Broken access control:** Missing authorization checks
- **Security misconfiguration:** Default credentials, debug mode enabled
- **Cross-Site Scripting (XSS):** Unescaped output
- **Insecure deserialization:** Unsafe object deserialization
- **Using components with known vulnerabilities:** Outdated dependencies
- **Insufficient logging:** Missing security event logs

### 4. Review with Checklist

Use a structured checklist (see below) to ensure comprehensive coverage.

### 5. Provide Actionable Feedback

Document findings with:
- **Severity:** Critical, High, Medium, Low
- **Description:** What's the vulnerability?
- **Exploit scenario:** How could an attacker exploit it?
- **Remediation:** Specific fix recommendations
- **References:** Links to OWASP or CWE documentation

## Security Code Review Checklist

### Input Validation

```csharp
// ❌ BAD: No validation
public ActionResult CreateUser(string username, string email)
{
    var user = new User { Username = username, Email = email };
    db.Users.Add(user);
    db.SaveChanges();
    return Ok();
}

// ✅ GOOD: Validate and sanitize
public ActionResult CreateUser(string username, string email)
{
    // Validate format
    if (string.IsNullOrWhiteSpace(username) || username.Length > 50)
        return BadRequest("Invalid username");
    
    if (!IsValidEmail(email))
        return BadRequest("Invalid email");
    
    // Sanitize (remove dangerous characters)
    username = SanitizeInput(username);
    
    var user = new User { Username = username, Email = email };
    db.Users.Add(user);
    db.SaveChanges();
    return Ok();
}
```

**Review Questions:**
- ✓ Is all external input validated?
- ✓ Is validation done server-side (not just client-side)?
- ✓ Are allow-lists used instead of deny-lists?
- ✓ Are length limits enforced?
- ✓ Are special characters handled correctly?

### Authentication and Authorization

```csharp
// ❌ BAD: No authorization check
[HttpGet("users/{id}/profile")]
public ActionResult GetProfile(int id)
{
    var user = db.Users.Find(id);
    return Ok(user);  // Any user can access any profile!
}

// ✅ GOOD: Check authorization
[HttpGet("users/{id}/profile")]
[Authorize]
public ActionResult GetProfile(int id)
{
    var currentUserId = User.GetUserId();
    
    // Users can only access their own profile
    if (currentUserId != id && !User.IsInRole("Admin"))
        return Forbid();
    
    var user = db.Users.Find(id);
    return Ok(user);
}
```

**Review Questions:**
- ✓ Are authentication checks present on all protected endpoints?
- ✓ Are authorization checks enforced (not just authentication)?
- ✓ Is the principle of least privilege applied?
- ✓ Are role checks done correctly?
- ✓ Can users access resources they shouldn't?

### SQL Injection Prevention

```csharp
// ❌ BAD: String concatenation
public User GetUser(string username)
{
    string query = "SELECT * FROM Users WHERE Username = '" + username + "'";
    return db.ExecuteQuery<User>(query).FirstOrDefault();
    // Vulnerable to: ' OR '1'='1
}

// ✅ GOOD: Parameterized query
public User GetUser(string username)
{
    string query = "SELECT * FROM Users WHERE Username = @username";
    return db.ExecuteQuery<User>(query, new { username }).FirstOrDefault();
}

// ✅ BETTER: Use ORM
public User GetUser(string username)
{
    return db.Users.FirstOrDefault(u => u.Username == username);
}
```

**Review Questions:**
- ✓ Are parameterized queries used?
- ✓ Is user input never concatenated into SQL?
- ✓ Are ORMs used correctly?
- ✓ Are stored procedures parameterized?

### Output Encoding (XSS Prevention)

```javascript
// ❌ BAD: Directly inserting user content
function displayComment(comment) {
    document.getElementById('comments').innerHTML = comment;
    // Vulnerable to: <script>alert('XSS')</script>
}

// ✅ GOOD: Escape HTML
function displayComment(comment) {
    const div = document.createElement('div');
    div.textContent = comment;  // Automatically escapes
    document.getElementById('comments').appendChild(div);
}

// ✅ GOOD: Use framework (React)
function CommentDisplay({ comment }) {
    return <div>{comment}</div>;  // React escapes by default
}
```

**Review Questions:**
- ✓ Is all user-supplied content escaped before rendering?
- ✓ Is context-appropriate encoding used (HTML, JavaScript, URL)?
- ✓ Are framework security features used correctly?
- ✓ Is `innerHTML` avoided when displaying user content?

### Secrets Management

```csharp
// ❌ BAD: Hard-coded credentials
public class DatabaseConnection
{
    private const string ConnectionString = 
        "Server=prod.db;Database=mydb;User=admin;Password=P@ssw0rd123";
}

// ❌ BAD: Secrets in configuration files committed to Git
// appsettings.json (in Git)
{
    "ConnectionStrings": {
        "Default": "Server=prod.db;User=admin;Password=P@ssw0rd123"
    }
}

// ✅ GOOD: Use environment variables
public class DatabaseConnection
{
    private readonly string _connectionString;
    
    public DatabaseConnection(IConfiguration config)
    {
        _connectionString = config.GetConnectionString("Default");
        // Set via environment variable: ConnectionStrings__Default
    }
}

// ✅ BETTER: Use secret management service
public class DatabaseConnection
{
    private readonly string _connectionString;
    
    public DatabaseConnection(ISecretManager secretManager)
    {
        _connectionString = secretManager.GetSecret("db-connection-string");
        // Retrieved from Azure Key Vault, AWS Secrets Manager, etc.
    }
}
```

**Review Questions:**
- ✓ Are credentials ever hard-coded?
- ✓ Are secrets stored in environment variables or secret managers?
- ✓ Are API keys excluded from version control?
- ✓ Are secrets logged or exposed in errors?

### Cryptography

```csharp
// ❌ BAD: Weak hashing
public string HashPassword(string password)
{
    using (var md5 = MD5.Create())
    {
        byte[] hash = md5.ComputeHash(Encoding.UTF8.GetBytes(password));
        return Convert.ToBase64String(hash);  // MD5 is broken!
    }
}

// ❌ BAD: No salt
public string HashPassword(string password)
{
    using (var sha256 = SHA256.Create())
    {
        byte[] hash = sha256.ComputeHash(Encoding.UTF8.GetBytes(password));
        return Convert.ToBase64String(hash);  // Rainbow table attack!
    }
}

// ✅ GOOD: Use proper password hashing
public string HashPassword(string password)
{
    // Use bcrypt, scrypt, or Argon2
    return BCrypt.Net.BCrypt.HashPassword(password, workFactor: 12);
}

// Verification
public bool VerifyPassword(string password, string hash)
{
    return BCrypt.Net.BCrypt.Verify(password, hash);
}
```

**Review Questions:**
- ✓ Are strong algorithms used (AES-256, RSA-2048+, SHA-256+)?
- ✓ Are passwords hashed with bcrypt, scrypt, or Argon2?
- ✓ Are salts used for hashing?
- ✓ Are encryption keys properly managed?
- ✓ Is cryptography implemented correctly (not reinvented)?

### Error Handling and Logging

```csharp
// ❌ BAD: Verbose error messages
[HttpPost("login")]
public ActionResult Login(string username, string password)
{
    var user = db.Users.FirstOrDefault(u => u.Username == username);
    
    if (user == null)
        return Unauthorized("User not found");  // Reveals user existence!
    
    if (!VerifyPassword(password, user.PasswordHash))
        return Unauthorized("Invalid password");  // Reveals valid username!
    
    return Ok(GenerateToken(user));
}

// ✅ GOOD: Generic error messages
[HttpPost("login")]
public ActionResult Login(string username, string password)
{
    var user = db.Users.FirstOrDefault(u => u.Username == username);
    
    if (user == null || !VerifyPassword(password, user.PasswordHash))
    {
        logger.LogWarning("Failed login attempt for username: {Username}", username);
        return Unauthorized("Invalid username or password");  // Generic message
    }
    
    return Ok(GenerateToken(user));
}

// ❌ BAD: Logging sensitive data
logger.LogInformation("User logged in: {Username}, Password: {Password}", 
    username, password);  // Never log passwords!

// ✅ GOOD: Log security events without sensitive data
logger.LogInformation("User logged in: {Username} from IP: {IpAddress}", 
    username, httpContext.Connection.RemoteIpAddress);
```

**Review Questions:**
- ✓ Are error messages generic (no information disclosure)?
- ✓ Are stack traces hidden in production?
- ✓ Are security events logged (login, logout, access denied)?
- ✓ Are sensitive data (passwords, tokens) never logged?
- ✓ Are logs centralized and monitored?

### Access Control

```csharp
// ❌ BAD: Insecure direct object reference
[HttpGet("documents/{id}")]
public ActionResult GetDocument(int id)
{
    var document = db.Documents.Find(id);
    return File(document.Content, document.MimeType);
    // Any user can access any document by changing ID!
}

// ✅ GOOD: Verify ownership
[HttpGet("documents/{id}")]
[Authorize]
public ActionResult GetDocument(int id)
{
    var userId = User.GetUserId();
    var document = db.Documents
        .FirstOrDefault(d => d.Id == id && d.OwnerId == userId);
    
    if (document == null)
        return NotFound();  // Don't reveal if document exists
    
    return File(document.Content, document.MimeType);
}
```

**Review Questions:**
- ✓ Are object references validated against current user?
- ✓ Is authorization checked on every request?
- ✓ Are default deny policies used?
- ✓ Can users escalate privileges?

## Hybrid Approach: Manual + Automated

### Strengths and Weaknesses

| Aspect | Manual Review | Automated Tools |
|--------|---------------|-----------------|
| **Speed** | Slow | Fast |
| **Coverage** | Limited by time | Comprehensive |
| **Context** | Excellent | Poor |
| **Logic Flaws** | Detects well | Often misses |
| **Known Patterns** | Can miss | Detects reliably |
| **Cost** | Expensive | Inexpensive |

**Best Practice:** Use automated tools (SAST) for first pass, then manually review high-risk code and logic.

### Workflow

1. **Automated SAST Scan:** Catch obvious issues (SQL injection, XSS, etc.)
2. **Developer Review:** Fix SAST findings
3. **Manual Security Review:** Focus on:
   - Authentication and authorization logic
   - Business logic flaws
   - Complex validation scenarios
   - Cryptographic implementations
   - Sensitive data handling
4. **Peer Review:** Another developer reviews the security fixes
5. **Security Team Review (Optional):** For critical features or high-risk changes

## Providing Effective Feedback

### Example Security Review Comment

**❌ Poor Feedback:**
```
This code is insecure. Fix it.
```

**✅ Good Feedback:**
```markdown
**Security Issue: SQL Injection Vulnerability**

**Severity:** Critical
**Location:** UserRepository.cs, Line 45

**Issue:**
User input is concatenated directly into SQL query:
`string query = "SELECT * FROM Users WHERE Username = '" + username + "'";`

**Attack Scenario:**
An attacker can inject SQL by providing: `' OR '1'='1`
This bypasses authentication and exposes all user records.

**Remediation:**
Use parameterized queries:
```csharp
string query = "SELECT * FROM Users WHERE Username = @username";
return db.ExecuteQuery<User>(query, new { username });
```

**References:**
- OWASP SQL Injection: https://owasp.org/www-community/attacks/SQL_Injection
- CWE-89: Improper Neutralization of Special Elements used in an SQL Command
```

## When to Escalate

Escalate to security experts when:
- **High-risk features:** Payment processing, authentication systems
- **Cryptographic implementations:** Custom crypto is almost always wrong
- **Complex authorization:** Multi-tenant systems, role hierarchies
- **Regulatory requirements:** HIPAA, PCI-DSS, GDPR
- **Novel attack vectors:** Unusual scenarios requiring deep security expertise
- **Disagreement:** If developers disagree about security implications

## Best Practices

### 1. Review Early and Often
Integrate security reviews into regular development workflow, not just before releases.

### 2. Focus on High-Risk Code
Prioritize authentication, authorization, data access, and input handling.

### 3. Use Checklists
Ensure consistent coverage with security checklists (OWASP, custom).

### 4. Educate, Don't Just Criticize
Use reviews as teaching opportunities. Explain why code is insecure and how to fix it.

### 5. Balance Speed and Thoroughness
Not every line needs deep security review. Focus on trust boundaries and high-risk areas.

### 6. Document Findings
Track security findings, remediation, and verification.
