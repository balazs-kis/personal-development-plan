## Introduction

Static Application Security Testing (SAST) analyzes source code, bytecode, or binaries to identify security vulnerabilities without executing the application. It's a "white-box" testing method that gives tools full access to your codebase, enabling early detection of security flaws when they're cheapest to fix.

SAST catches issues like SQL injection, cross-site scripting (XSS), hard-coded credentials, insecure cryptography, and more—all before your code runs in production.

## Key Concepts Summary

### What is SAST?

SAST tools scan your source code, bytecode, or binaries looking for security vulnerabilities using pattern matching, data flow analysis, and control flow analysis. They identify issues like:
- Injection flaws (SQL, command, LDAP)
- Cross-site scripting (XSS)
- Security misconfiguration
- Insecure cryptographic storage
- Hard-coded credentials
- Insecure deserialization

### Why SAST Matters

**Early Detection:** Find vulnerabilities during development when fixes are simple and inexpensive, not in production when they're costly and risky.

**Compliance:** Many regulations (PCI DSS, HIPAA, ISO 27001) require SAST as part of secure development practices.

**Scale:** Automatically scan millions of lines of code rapidly with high confidence.

**Education:** Developers learn secure coding patterns by seeing what the tool flags and why.

### How SAST Works

The typical SAST workflow:

1. **Scanning:** Tool analyzes source code or compiled artifacts
2. **Prioritizing:** Findings are ranked by severity (Critical, High, Medium, Low)
3. **Understanding:** Review vulnerability details, affected code, and attack vectors
4. **Fixing:** Apply remediation based on tool recommendations
5. **Rescanning:** Verify fixes and track progress
6. **Continuous Integration:** Integrate into CI/CD for ongoing protection

### SonarQube Setup

```yaml
# docker-compose.yml for SonarQube
version: "3"
services:
  sonarqube:
    image: sonarqube:community
    ports:
      - "9000:9000"
    environment:
      - SONAR_ES_BOOTSTRAP_CHECKS_DISABLE=true
    volumes:
      - sonarqube_data:/opt/sonarqube/data
      - sonarqube_logs:/opt/sonarqube/logs
      - sonarqube_extensions:/opt/sonarqube/extensions

volumes:
  sonarqube_data:
  sonarqube_logs:
  sonarqube_extensions:
```

Start SonarQube:
```bash
docker-compose up -d
# Access at http://localhost:9000
# Default credentials: admin/admin
```

### Running Your First Scan

**For .NET Projects:**
```bash
# Install SonarScanner for .NET
dotnet tool install --global dotnet-sonarscanner

# Begin analysis
dotnet sonarscanner begin /k:"project-key" /d:sonar.host.url="http://localhost:9000" /d:sonar.token="your-token"

# Build your project
dotnet build

# End analysis (uploads results)
dotnet sonarscanner end /d:sonar.token="your-token"
```

**For JavaScript/TypeScript Projects:**
```bash
# Install SonarScanner
npm install -g sonarqube-scanner

# Create sonar-project.properties
cat > sonar-project.properties << EOF
sonar.projectKey=my-project
sonar.sources=src
sonar.host.url=http://localhost:9000
sonar.token=your-token
EOF

# Run scan
sonar-scanner
```

### Interpreting Results

SonarQube reports include:

**Bugs:** Code that is demonstrably wrong and will likely fail.

**Vulnerabilities:** Security-sensitive issues that require review.

**Code Smells:** Maintainability issues that make code harder to understand or change.

**Security Hotspots:** Security-sensitive code that requires manual review.

**Coverage:** Test coverage percentage.

**Duplications:** Duplicated code blocks.

Example vulnerability finding:
```
SQL Injection vulnerability
Severity: CRITICAL
File: UserRepository.cs, Line 45

Dangerous: string query = "SELECT * FROM Users WHERE id = " + userId;

Reason: Untrusted user input concatenated into SQL query.

Fix: Use parameterized queries:
string query = "SELECT * FROM Users WHERE id = @userId";
command.Parameters.AddWithValue("@userId", userId);
```

### CI/CD Integration

**GitHub Actions Example:**
```yaml
name: SonarQube Analysis

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  sonarqube:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
        with:
          fetch-depth: 0  # Shallow clones should be disabled
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: '8.0'
      
      - name: Install SonarScanner
        run: dotnet tool install --global dotnet-sonarscanner
      
      - name: Begin SonarQube Analysis
        run: |
          dotnet sonarscanner begin \
            /k:"${{ secrets.SONAR_PROJECT_KEY }}" \
            /d:sonar.host.url="${{ secrets.SONAR_HOST_URL }}" \
            /d:sonar.token="${{ secrets.SONAR_TOKEN }}"
      
      - name: Build
        run: dotnet build
      
      - name: End SonarQube Analysis
        run: |
          dotnet sonarscanner end \
            /d:sonar.token="${{ secrets.SONAR_TOKEN }}"
```

**Azure DevOps Pipeline:**
```yaml
trigger:
  - main

pool:
  vmImage: 'ubuntu-latest'

steps:
- task: SonarQubePrepare@5
  inputs:
    SonarQube: 'SonarQube-Connection'
    scannerMode: 'MSBuild'
    projectKey: 'my-project-key'
    projectName: 'My Project'

- task: DotNetCoreCLI@2
  inputs:
    command: 'build'
    projects: '**/*.csproj'

- task: SonarQubeAnalyze@5

- task: SonarQubePublish@5
  inputs:
    pollingTimeoutSec: '300'
```

### Quality Gates

Quality Gates define pass/fail criteria for code quality:

```json
{
  "name": "Strict Security Gate",
  "conditions": [
    {
      "metric": "new_vulnerabilities",
      "operator": "GREATER_THAN",
      "threshold": "0"
    },
    {
      "metric": "new_security_hotspots",
      "operator": "GREATER_THAN", 
      "threshold": "0"
    },
    {
      "metric": "new_security_rating",
      "operator": "WORSE_THAN",
      "threshold": "A"
    }
  ]
}
```

If conditions aren't met, the build fails—preventing vulnerable code from being merged.

## SAST Limitations

| Limitation | Impact | Mitigation |
|------------|--------|------------|
| **False Positives** | Wastes time reviewing non-issues | Tune rules, train developers to recognize patterns |
| **No Runtime Context** | Can't detect logic flaws or configuration issues | Complement with DAST and manual testing |
| **Language Coverage** | Not all languages equally supported | Choose tools that support your stack |
| **Performance** | Large codebases can take time to scan | Optimize scans, use incremental analysis |
| **Configuration Required** | Tools need tuning to be effective | Invest time in initial configuration |

---

## Best Practices

### 1. Start Early
Integrate SAST from day one. Fixing issues in development costs 10-100x less than in production.

### 2. Don't Rely on SAST Alone
SAST is one layer. Combine with DAST, dependency scanning, code review, and penetration testing.

### 3. Tune Your Tools
Out-of-the-box rules generate noise. Customize rules to your codebase, suppress false positives, and adjust severity levels.

### 4. Educate Developers
Use findings as teaching moments. Explain why code is vulnerable and how to fix it securely.

### 5. Fix Critical Issues First
Prioritize by severity and exploitability. Don't let perfect be the enemy of good—fix critical issues immediately, medium/low issues during refactoring.

### 6. Track Metrics
Monitor trends: new vulnerabilities introduced, time to fix, vulnerability density per 1000 lines of code.

## Summary

SAST is essential for building secure software. It finds vulnerabilities early, educates developers, and scales to large codebases. While not perfect, when combined with other testing methods and integrated into CI/CD, SAST dramatically reduces security risk.
