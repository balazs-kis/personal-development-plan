## Introduction

One of the most important decisions in PostgreSQL schema design is choosing between JSONB and normalized relational tables. While JSONB offers flexibility, it comes with trade-offs in query performance, maintainability, and PostgreSQL's ability to optimize queries. Understanding when to use each approach—and how to combine them effectively—is crucial for building scalable applications.

The best designs often use a hybrid approach: normalized tables for core business data, with JSONB for truly variable or semi-structured data.

## Key Concepts Summary

### When to Use Normalized Tables

**Use normalized relational tables when:**

1. **Data has consistent structure**
   ```sql
   -- GOOD: Predictable structure, use normalized tables
   CREATE TABLE users (
       id SERIAL PRIMARY KEY,
       email TEXT UNIQUE NOT NULL,
       first_name TEXT NOT NULL,
       last_name TEXT NOT NULL,
       created_at TIMESTAMP DEFAULT NOW()
   );
   ```

2. **Frequent filtering, sorting, or aggregation**
   ```sql
   -- GOOD: Regular columns enable efficient queries
   SELECT COUNT(*), DATE(created_at) 
   FROM users 
   WHERE last_name LIKE 'S%'
   GROUP BY DATE(created_at);
   -- PostgreSQL can optimize this with accurate statistics
   ```

3. **Need accurate query planning**
   - PostgreSQL cannot gather statistics on JSONB column values
   - Query planner makes poor decisions without statistics
   - Leads to inefficient execution plans

4. **Strong consistency and referential integrity**
   ```sql
   -- GOOD: Foreign keys ensure data integrity
   CREATE TABLE orders (
       id SERIAL PRIMARY KEY,
       user_id INTEGER REFERENCES users(id),
       product_id INTEGER REFERENCES products(id)
   );
   ```

5. **Transactional or financial data**
   ```sql
   -- BAD: Don't store transactions as JSONB
   CREATE TABLE payments (
       id SERIAL PRIMARY KEY,
       data JSONB  -- Nested year/month/transactions
   );
   
   -- GOOD: Normalize transactions
   CREATE TABLE transactions (
       id SERIAL PRIMARY KEY,
       user_id INTEGER REFERENCES users(id),
       amount NUMERIC(10,2) NOT NULL,
       type TEXT NOT NULL,
       created_at TIMESTAMP DEFAULT NOW()
   );
   ```

### When to Use JSONB

**Use JSONB when:**

1. **Truly variable or semi-structured data**
   ```sql
   -- GOOD: API responses (structure varies by endpoint)
   CREATE TABLE api_logs (
       id SERIAL PRIMARY KEY,
       endpoint TEXT NOT NULL,
       response JSONB,
       created_at TIMESTAMP DEFAULT NOW()
   );
   
   -- GOOD: Event logging (different event types have different fields)
   CREATE TABLE events (
       id SERIAL PRIMARY KEY,
       event_type TEXT NOT NULL,
       payload JSONB,
       occurred_at TIMESTAMP DEFAULT NOW()
   );
   ```

2. **Flexible product attributes**
   ```sql
   -- GOOD: Different products have different attributes
   CREATE TABLE products (
       id SERIAL PRIMARY KEY,
       category TEXT NOT NULL,
       name TEXT NOT NULL,
       price NUMERIC(10,2) NOT NULL,  -- Core fields normalized
       attributes JSONB DEFAULT '{}'   -- Variable attributes in JSONB
   );
   
   INSERT INTO products (category, name, price, attributes) VALUES
       ('laptop', 'MacBook Pro', 1299.00, '{"cpu": "M2", "ram": "16GB"}'),
       ('book', 'PostgreSQL Guide', 45.00, '{"author": "John Doe", "pages": 400}'),
       ('clothing', 'T-Shirt', 19.99, '{"size": "L", "color": "blue"}');
   ```

3. **User preferences and settings**
   ```sql
   -- GOOD: Each user can customize different settings
   CREATE TABLE user_preferences (
       user_id INTEGER PRIMARY KEY REFERENCES users(id),
       settings JSONB DEFAULT '{}'
   );
   ```

4. **Metadata and configuration**
   ```sql
   -- GOOD: Internal metadata that varies by record
   CREATE TABLE jobs (
       id SERIAL PRIMARY KEY,
       job_type TEXT NOT NULL,
       status TEXT NOT NULL,
       metadata JSONB DEFAULT '{}'  -- Variable processing metadata
   );
   ```

5. **Rapidly evolving schemas**
   - Avoid constant ALTER TABLE migrations
   - Add new fields without schema changes
   - Good for experimental features

### The Hybrid Approach (Recommended)

**Combine normalized columns with JSONB for best of both worlds:**

```sql
CREATE TABLE products (
    -- Normalized columns for frequently queried fields
    id SERIAL PRIMARY KEY,
    category TEXT NOT NULL,
    name TEXT NOT NULL,
    price NUMERIC(10,2) NOT NULL,
    in_stock BOOLEAN DEFAULT true,
    created_at TIMESTAMP DEFAULT NOW(),
    
    -- JSONB for variable attributes
    attributes JSONB DEFAULT '{}',
    
    -- Indexes on normalized columns
    INDEX idx_category (category),
    INDEX idx_price (price),
    INDEX idx_in_stock (in_stock)
);

-- Queries on normalized fields are fast
SELECT * FROM products 
WHERE category = 'electronics' 
  AND price < 1000 
  AND in_stock = true
ORDER BY price;

-- JSONB provides flexibility for category-specific attributes
SELECT * FROM products 
WHERE category = 'laptop' 
  AND attributes @> '{"cpu": "Intel i7"}';
```

### Generated Columns Pattern

Extract frequently-queried JSONB fields into generated columns:

```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    attributes JSONB DEFAULT '{}',
    
    -- Generated columns from JSONB
    brand TEXT GENERATED ALWAYS AS (attributes->>'brand') STORED,
    price NUMERIC GENERATED ALWAYS AS ((attributes->>'price')::numeric) STORED,
    
    -- Index generated columns for fast queries
    INDEX idx_brand (brand),
    INDEX idx_price (price)
);

-- Insert with JSONB
INSERT INTO products (name, attributes) VALUES
    ('Laptop', '{"brand": "Apple", "price": 1299, "cpu": "M2"}');

-- Query using generated column (fast, uses index)
SELECT * FROM products WHERE brand = 'Apple' ORDER BY price;

-- Still have flexibility of JSONB
SELECT * FROM products WHERE attributes @> '{"cpu": "M2"}';
```

**Benefits:**
- Query performance of normalized columns
- Flexibility of JSONB
- Automatic updates when JSONB changes
- Can create indexes on generated columns

### Common Anti-Patterns

**Anti-Pattern 1: Storing Entire Tables as JSONB**

```sql
-- BAD: Defeats purpose of relational database
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    data JSONB  -- Everything in JSONB
);

-- GOOD: Normalize core fields
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    first_name TEXT NOT NULL,
    last_name TEXT NOT NULL,
    profile_extras JSONB DEFAULT '{}'  -- Only extras in JSONB
);
```

**Anti-Pattern 2: Nested Relational Data**

```sql
-- BAD: Relational data nested in JSONB
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email TEXT,
    orders JSONB  -- Array of order objects
);

-- GOOD: Separate tables with foreign keys
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email TEXT
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    total NUMERIC(10,2)
);
```

**Anti-Pattern 3: Frequently Aggregated Data**

```sql
-- BAD: Data frequently used in aggregations
CREATE TABLE sales (
    id SERIAL PRIMARY KEY,
    data JSONB  -- Contains amount, date, etc.
);

-- Queries are slow
SELECT 
    DATE(data->>'date'),
    SUM((data->>'amount')::numeric)
FROM sales
GROUP BY DATE(data->>'date');

-- GOOD: Normalize fields used in aggregations
CREATE TABLE sales (
    id SERIAL PRIMARY KEY,
    amount NUMERIC(10,2) NOT NULL,
    sale_date DATE NOT NULL,
    details JSONB DEFAULT '{}'
);

-- Fast queries with proper indexes
SELECT sale_date, SUM(amount)
FROM sales
GROUP BY sale_date;
```

**Anti-Pattern 4: Deeply Nested Structures**

```sql
-- BAD: Hard to query, poor performance
CREATE TABLE config (
    id SERIAL PRIMARY KEY,
    settings JSONB  -- 5+ levels of nesting
);

-- GOOD: Flatten or break into related tables
CREATE TABLE config_sections (
    id SERIAL PRIMARY KEY,
    section_name TEXT NOT NULL,
    settings JSONB DEFAULT '{}'  -- Shallow nesting
);
```

### Design Decision Framework

**Ask these questions:**

1. **Will this data be frequently queried?**
   - Yes → Normalized column
   - No → JSONB

2. **Does the structure vary significantly?**
   - Yes → JSONB
   - No → Normalized columns

3. **Do I need accurate query statistics?**
   - Yes → Normalized column
   - No → JSONB (with possible generated column)

4. **Will I aggregate or sort by this field?**
   - Yes → Normalized column (or generated column from JSONB)
   - No → JSONB

5. **Is referential integrity important?**
   - Yes → Normalized table with foreign keys
   - No → JSONB

6. **How often does the schema change?**
   - Frequently → JSONB
   - Rarely → Normalized columns

### Migration Strategies

**From JSONB to Normalized:**

```sql
-- Extract commonly queried fields
ALTER TABLE products 
ADD COLUMN brand TEXT;

UPDATE products 
SET brand = attributes->>'brand';

CREATE INDEX idx_products_brand ON products(brand);

-- Or use generated column
ALTER TABLE products 
ADD COLUMN brand TEXT GENERATED ALWAYS AS (attributes->>'brand') STORED;

CREATE INDEX idx_products_brand ON products(brand);
```

**From Normalized to JSONB:**

```sql
-- Consolidate rarely queried fields
UPDATE products 
SET attributes = attributes || jsonb_build_object(
    'warranty_years', warranty_years,
    'manufacture_date', manufacture_date
);

-- Remove old columns after verification
ALTER TABLE products 
DROP COLUMN warranty_years,
DROP COLUMN manufacture_date;
```

### Performance Monitoring

**Check JSONB query performance:**

```sql
-- Slow queries on JSONB
SELECT 
    query,
    calls,
    mean_exec_time,
    max_exec_time
FROM pg_stat_statements
WHERE query LIKE '%JSONB%'
  OR query LIKE '%->%'
  OR query LIKE '%@>%'
ORDER BY mean_exec_time DESC
LIMIT 20;

-- Consider converting slow JSONB queries to normalized columns
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

1. Design a hybrid schema:

```sql
-- E-commerce product catalog
CREATE TABLE products (
    -- Core normalized fields
    id SERIAL PRIMARY KEY,
    sku TEXT UNIQUE NOT NULL,
    name TEXT NOT NULL,
    category TEXT NOT NULL,
    base_price NUMERIC(10,2) NOT NULL,
    in_stock BOOLEAN DEFAULT true,
    created_at TIMESTAMP DEFAULT NOW(),
    
    -- Variable attributes per category
    attributes JSONB DEFAULT '{}',
    
    -- Generated columns for common queries
    brand TEXT GENERATED ALWAYS AS (attributes->>'brand') STORED,
    
    -- Indexes
    INDEX idx_category (category),
    INDEX idx_brand (brand),
    INDEX idx_price (base_price),
    INDEX idx_attributes_gin (attributes) USING GIN
);

-- Insert different product types
INSERT INTO products (sku, name, category, base_price, attributes) VALUES
    ('LAP001', 'Business Laptop', 'electronics', 1299.00, 
     '{"brand": "TechCorp", "cpu": "i7", "ram": "16GB", "warranty": "3 years"}'),
    ('BOOK001', 'SQL Mastery', 'books', 45.00,
     '{"brand": "TechPublish", "author": "Jane Doe", "pages": 400, "isbn": "123-456"}'),
    ('SHIRT001', 'Cotton T-Shirt', 'clothing', 19.99,
     '{"brand": "FashionCo", "size": "L", "color": "blue", "material": "cotton"}');
```

2. Write efficient hybrid queries:

```sql
-- Fast query on normalized and generated columns
SELECT name, brand, base_price 
FROM products 
WHERE category = 'electronics' 
  AND brand = 'TechCorp'
  AND base_price < 1500
ORDER BY base_price;

-- Flexible query on JSONB for category-specific attributes
SELECT name, base_price
FROM products 
WHERE category = 'electronics'
  AND attributes @> '{"cpu": "i7", "ram": "16GB"}';

-- Combined query
SELECT name, brand, base_price, attributes->'warranty' AS warranty
FROM products 
WHERE category = 'electronics'
  AND brand = 'TechCorp'
  AND in_stock = true
ORDER BY base_price;
```

3. Refactor a bad design:

```sql
-- BAD design: Everything in JSONB
CREATE TABLE orders_bad (
    id SERIAL PRIMARY KEY,
    data JSONB
);

-- GOOD design: Hybrid approach
CREATE TABLE orders_good (
    -- Core transactional fields normalized
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL,
    status TEXT NOT NULL,
    total_amount NUMERIC(10,2) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    
    -- Flexible metadata in JSONB
    metadata JSONB DEFAULT '{}',
    
    -- Indexes on normalized columns
    INDEX idx_user_id (user_id),
    INDEX idx_status (status),
    INDEX idx_created_at (created_at)
);

-- Separate table for line items
CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INTEGER REFERENCES orders_good(id),
    product_id INTEGER NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(10,2) NOT NULL
);
```

### Key Takeaways

1. **JSONB is almost always better than JSON** - Use JSONB for production workloads
2. **Index your JSONB** - GIN indexes provide massive performance improvements
3. **Hybrid approach is best** - Normalize core fields, use JSONB for variable data
4. **Generated columns bridge the gap** - Extract JSONB fields for better query performance
5. **Don't abuse JSONB** - Avoid storing entire tables or transactional data as JSONB
