## Introduction

Query optimization is both an art and a science. While understanding EXPLAIN output, indexes, and statistics provides the foundation, knowing practical optimization techniques helps you solve real-world performance problems. This lesson covers common patterns, anti-patterns, and systematic approaches to making queries faster.

Most query optimization follows a pattern: identify the bottleneck using EXPLAIN ANALYZE, understand why the planner made that choice, then fix it through indexing, query rewriting, or configuration changes.

## Key Concepts Summary

### Systematic Optimization Process

1. **Identify the slow query**
   - Use pg_stat_statements extension
   - Check application logs
   - Monitor slow query log

2. **Get the EXPLAIN ANALYZE output**
   ```sql
   EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
   SELECT ...;
   ```

3. **Find the bottleneck**
   - Look for the most expensive node (highest actual time)
   - Check for estimate mismatches (rows estimated vs actual)
   - Identify sequential scans on large tables
   - Look for sorts that spill to disk

4. **Understand why**
   - Missing index?
   - Stale statistics?
   - Insufficient memory?
   - Poor query structure?

5. **Fix and verify**
   - Apply fix (index, ANALYZE, query rewrite)
   - Re-run EXPLAIN ANALYZE
   - Measure improvement
   - Test in production with monitoring

### Common Problems and Solutions

#### Problem 1: Sequential Scan on Large Table

```sql
-- Before
EXPLAIN ANALYZE
SELECT * FROM orders WHERE status = 'pending';

-- Shows
Seq Scan on orders  (cost=0.00..1693.00 rows=50 width=100) 
                    (actual time=0.015..25.123 rows=42 loops=1)
  Filter: (status = 'pending'::text)
  Rows Removed by Filter: 99958
```

**Solutions:**

```sql
-- Solution 1: Add index
CREATE INDEX idx_orders_status ON orders(status);
ANALYZE orders;

-- Solution 2: Partial index if filtering specific values
CREATE INDEX idx_orders_pending 
ON orders(status) 
WHERE status = 'pending';
```

#### Problem 2: Poor Row Estimates

```sql
-- Estimated 50 rows, actually 15,000
Seq Scan on orders  (cost=0.00..1693.00 rows=50 width=100)
                    (actual time=0.015..25.123 rows=15432 loops=1)
```

**Solutions:**

```sql
-- Solution 1: Update statistics
ANALYZE orders;

-- Solution 2: Increase statistics target
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 200;
ANALYZE orders;

-- Solution 3: Extended statistics for correlated columns
CREATE STATISTICS stats_order_status_date 
ON status, created_at FROM orders;
ANALYZE orders;
```

#### Problem 3: Nested Loop with Large Outer Table

```sql
-- Nested loop iterating 10,000 times
Nested Loop  (cost=0.29..50000.00 rows=10000 width=100)
             (actual time=0.015..5000.123 rows=10000 loops=1)
  ->  Seq Scan on orders o  (cost=0.00..1000.00 rows=10000 width=64)
  ->  Index Scan using users_pkey on users u  (cost=0.29..4.90 rows=1)
        Index Cond: (id = o.user_id)
```

**Solutions:**

```sql
-- Solution 1: Ensure join columns are indexed
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Solution 2: Increase work_mem to enable hash join
SET work_mem = '256MB';

-- Solution 3: Rewrite query to reduce outer table size
-- Add WHERE clause to filter orders before joining
SELECT u.*, o.*
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.created_at > NOW() - INTERVAL '7 days';  -- Filter first
```

#### Problem 4: Hash Join Spilling to Disk

```sql
-- Multiple batches = spilling to disk
Hash Join  (cost=1000.00..50000.00 rows=10000 width=100)
           (actual time=100.123..5000.456 rows=10000 loops=1)
  Hash Cond: (o.product_id = p.id)
  ->  Seq Scan on orders o  (cost=0.00..1000.00 rows=10000)
  ->  Hash  (cost=500.00..500.00 rows=5000)
        Buckets: 8192  Batches: 8  Memory Usage: 1024kB  -- 8 batches is bad!
        ->  Seq Scan on products p  (cost=0.00..500.00 rows=5000)
```

**Solutions:**

```sql
-- Solution 1: Increase work_mem
SET work_mem = '64MB';  -- Or tune globally in postgresql.conf

-- Solution 2: Add indexes to enable merge join instead
CREATE INDEX idx_orders_product_id ON orders(product_id);
CREATE INDEX idx_products_id ON products(id);

-- Solution 3: Reduce the hash table size
-- Filter products before joining if possible
SELECT o.*, p.*
FROM orders o
JOIN products p ON o.product_id = p.id
WHERE p.category = 'Electronics';  -- Reduce hash table
```

#### Problem 5: Sort Spilling to Disk

```sql
-- External merge disk sort = very slow
Sort  (cost=5000.00..5250.00 rows=100000 width=100)
      (actual time=2000.123..2500.456 rows=100000 loops=1)
  Sort Key: created_at
  Sort Method: external merge  Disk: 15264kB  -- Spilling to disk!
  ->  Seq Scan on orders  (cost=0.00..1000.00 rows=100000)
```

**Solutions:**

```sql
-- Solution 1: Increase work_mem
SET work_mem = '32MB';

-- Solution 2: Add index for sorted access
CREATE INDEX idx_orders_created_at ON orders(created_at);

-- Solution 3: Reduce rows before sorting
SELECT * FROM orders 
WHERE status = 'active'  -- Filter first
ORDER BY created_at;

-- Solution 4: Use LIMIT if possible
SELECT * FROM orders 
ORDER BY created_at 
LIMIT 100;  -- Much faster, can use index scan
```

#### Problem 6: Inefficient Subqueries

```sql
-- Correlated subquery runs for each row
SELECT o.*, 
       (SELECT COUNT(*) FROM order_items 
        WHERE order_id = o.id) as item_count
FROM orders o;
```

**Solutions:**

```sql
-- Solution 1: Use JOIN instead
SELECT o.*, COUNT(oi.id) as item_count
FROM orders o
LEFT JOIN order_items oi ON o.id = oi.order_id
GROUP BY o.id;

-- Solution 2: Use window function
SELECT o.*, 
       COUNT(*) OVER (PARTITION BY o.id) as item_count
FROM orders o
JOIN order_items oi ON o.id = oi.order_id;

-- Solution 3: Use CTE
WITH item_counts AS (
    SELECT order_id, COUNT(*) as item_count
    FROM order_items
    GROUP BY order_id
)
SELECT o.*, COALESCE(ic.item_count, 0) as item_count
FROM orders o
LEFT JOIN item_counts ic ON o.id = ic.order_id;
```

### Configuration Parameters for Performance

```sql
-- Memory for sorts and hash tables (per operation)
SET work_mem = '256MB';  -- Default: 4MB, increase for complex queries

-- Memory for maintenance operations (VACUUM, CREATE INDEX)
SET maintenance_work_mem = '1GB';  -- Default: 64MB

-- Shared buffer cache
-- SET in postgresql.conf: shared_buffers = '4GB'  -- 25% of RAM

-- Query planner settings
SET random_page_cost = 1.1;  -- For SSD, closer to seq_page_cost
SET effective_cache_size = '12GB';  -- Estimate of OS cache (75% of RAM)

-- Enable parallel query
SET max_parallel_workers_per_gather = 4;
SET parallel_setup_cost = 100;
SET parallel_tuple_cost = 0.01;
```

### Query Rewriting Patterns

#### Pattern 1: Filter Early

```sql
-- Bad: Join then filter
SELECT u.*, o.*
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'pending';

-- Good: Filter before join
SELECT u.*, o.*
FROM users u
JOIN (SELECT * FROM orders WHERE status = 'pending') o 
ON u.id = o.user_id;
```

#### Pattern 2: Use EXISTS Instead of IN for Large Lists

```sql
-- Bad: Large IN list
SELECT * FROM orders 
WHERE user_id IN (SELECT id FROM users WHERE country = 'USA');

-- Good: Use EXISTS
SELECT * FROM orders o
WHERE EXISTS (
    SELECT 1 FROM users u 
    WHERE u.id = o.user_id AND u.country = 'USA'
);

-- Even better: Use JOIN if you need user data
SELECT o.* FROM orders o
JOIN users u ON o.user_id = u.id
WHERE u.country = 'USA';
```

#### Pattern 3: Avoid SELECT *

```sql
-- Bad: Fetches unnecessary data
SELECT * FROM orders 
WHERE status = 'pending';

-- Good: Select only needed columns
SELECT id, user_id, total, created_at 
FROM orders 
WHERE status = 'pending';

-- Enables covering indexes
CREATE INDEX idx_orders_status_covering 
ON orders(status) INCLUDE (id, user_id, total, created_at);
```

#### Pattern 4: Use LATERAL for Dependent Subqueries

```sql
-- Get the 3 most recent orders for each user
-- Bad: Correlated subquery
SELECT u.*, (
    SELECT json_agg(o ORDER BY created_at DESC)
    FROM (
        SELECT * FROM orders 
        WHERE user_id = u.id 
        ORDER BY created_at DESC 
        LIMIT 3
    ) o
) as recent_orders
FROM users u;

-- Good: LATERAL join
SELECT u.*, o.recent_orders
FROM users u
CROSS JOIN LATERAL (
    SELECT json_agg(orders ORDER BY created_at DESC) as recent_orders
    FROM orders
    WHERE user_id = u.id
    ORDER BY created_at DESC
    LIMIT 3
) o;
```

### Monitoring and Prevention

```sql
-- Enable pg_stat_statements for query monitoring
CREATE EXTENSION pg_stat_statements;

-- Find slowest queries
SELECT 
    query,
    calls,
    total_exec_time / 1000 as total_time_seconds,
    mean_exec_time / 1000 as mean_time_seconds,
    max_exec_time / 1000 as max_time_seconds
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 20;

-- Find queries with estimate mismatches (requires auto_explain)
-- Configure in postgresql.conf:
-- shared_preload_libraries = 'auto_explain'
-- auto_explain.log_min_duration = 1000  -- Log queries > 1s
-- auto_explain.log_analyze = on
-- auto_explain.log_buffers = on
```

### Optimization Checklist

- [ ] Run EXPLAIN (ANALYZE, BUFFERS) on slow queries
- [ ] Check for sequential scans on large tables → add indexes
- [ ] Check for estimate mismatches → run ANALYZE
- [ ] Check for sorts/hashes spilling to disk → increase work_mem
- [ ] Check for nested loops with large outer tables → add indexes or rewrite
- [ ] Verify indexes are actually being used
- [ ] Update outdated statistics with ANALYZE
- [ ] Consider partial indexes for filtered queries
- [ ] Consider covering indexes for SELECT-only columns
- [ ] Review query structure for unnecessary complexity
- [ ] Test configuration changes (work_mem, random_page_cost)
- [ ] Measure improvement and verify in production

After completing the materials, try this comprehensive exercise (do not spend more than 30 minutes):

1. Create a realistic schema:

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email TEXT UNIQUE,
    name TEXT,
    country TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER,
    status TEXT,
    total NUMERIC,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INTEGER,
    product_name TEXT,
    quantity INTEGER,
    price NUMERIC
);

-- Insert sample data
INSERT INTO users (email, name, country)
SELECT 
    'user' || i || '@example.com',
    'User ' || i,
    CASE (i % 5) 
        WHEN 0 THEN 'USA'
        WHEN 1 THEN 'Canada'
        ELSE 'Other'
    END
FROM generate_series(1, 10000) i;

INSERT INTO orders (user_id, status, total, created_at)
SELECT 
    (random() * 9999 + 1)::integer,
    CASE (random() * 10)::integer
        WHEN 0 THEN 'pending'
        WHEN 1 THEN 'processing'
        ELSE 'completed'
    END,
    random() * 1000,
    NOW() - (random() * 365 || ' days')::interval
FROM generate_series(1, 50000) i;

INSERT INTO order_items (order_id, product_name, quantity, price)
SELECT 
    (random() * 49999 + 1)::integer,
    'Product ' || (random() * 100)::integer,
    (random() * 10 + 1)::integer,
    random() * 100
FROM generate_series(1, 150000) i;

ANALYZE users;
ANALYZE orders;
ANALYZE order_items;
```

2. Identify and fix problems:

```sql
-- Problem: Sequential scan on large table
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'pending';

-- Fix:
CREATE INDEX idx_orders_status ON orders(status);
ANALYZE orders;

-- Verify:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'pending';
```

3. Optimize a complex query:

```sql
-- Slow query: users with their total order count and value
EXPLAIN (ANALYZE, BUFFERS)
SELECT 
    u.email,
    u.country,
    (SELECT COUNT(*) FROM orders WHERE user_id = u.id) as order_count,
    (SELECT SUM(total) FROM orders WHERE user_id = u.id) as total_spent
FROM users u
WHERE u.country = 'USA'
ORDER BY total_spent DESC NULLS LAST;

-- Optimize it:
EXPLAIN (ANALYZE, BUFFERS)
SELECT 
    u.email,
    u.country,
    COUNT(o.id) as order_count,
    SUM(o.total) as total_spent
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.country = 'USA'
GROUP BY u.id, u.email, u.country
ORDER BY total_spent DESC NULLS LAST;

-- Add indexes:
CREATE INDEX idx_users_country ON users(country);
CREATE INDEX idx_orders_user_id ON orders(user_id);
ANALYZE users;
ANALYZE orders;

-- Verify improvement:
EXPLAIN (ANALYZE, BUFFERS)
SELECT 
    u.email,
    u.country,
    COUNT(o.id) as order_count,
    SUM(o.total) as total_spent
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.country = 'USA'
GROUP BY u.id, u.email, u.country
ORDER BY total_spent DESC NULLS LAST;
```

4. Test work_mem impact:

```sql
-- Large sort
SET work_mem = '4MB';  -- Small
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY created_at;
-- Look for "external merge Disk"

-- Increase memory
SET work_mem = '64MB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY created_at;
-- Should use "quicksort Memory"

-- Better: use index
CREATE INDEX idx_orders_created_at ON orders(created_at);
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY created_at;
-- Should use index scan
```
