## Introduction

Transaction isolation controls how concurrent transactions see each other's changes. PostgreSQL implements three isolation levels: Read Committed (default), Repeatable Read, and Serializable. Each level provides different trade-offs between data consistency and concurrency performance.

Understanding isolation levels is critical for building correct concurrent applications. The wrong isolation level can lead to subtle race conditions that only manifest under high load or specific timing conditions.

## Key Concepts Summary

### Transaction Isolation Levels Overview

PostgreSQL implements three isolation levels (it treats Read Uncommitted as Read Committed):

| Isolation Level | Dirty Read | Nonrepeatable Read | Phantom Read | Serialization Anomaly |
|-----------------|------------|--------------------|--------------|-----------------------|
| Read Committed  | Not possible | Possible | Possible | Possible |
| Repeatable Read | Not possible | Not possible | Not possible (in PostgreSQL) | Possible |
| Serializable    | Not possible | Not possible | Not possible | Not possible |

### Isolation Level 1: Read Committed (Default)

**How it works:**
- Each statement sees data committed before it began
- Different statements in the same transaction can see different data
- Most commonly used isolation level

```sql
-- Transaction 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1000

-- Transaction 2 (runs and commits while Transaction 1 is active)
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;
COMMIT;

-- Transaction 1 continues
SELECT balance FROM accounts WHERE id = 1;  -- Returns 500 (sees the committed change)
COMMIT;
```

**Anomalies prevented:**
- ✅ Dirty reads (never sees uncommitted data)

**Anomalies possible:**
- ❌ Nonrepeatable reads (same query can return different results)
- ❌ Phantom reads (query can return different rows)
- ❌ Serialization anomalies

**When to use:**
- Most applications (it's the default for good reason)
- When you want to see the latest committed data
- When strict consistency isn't required
- High-concurrency scenarios where blocking is problematic

**Example anomaly - Nonrepeatable Read:**
```sql
-- Transaction 1: Banking application checking account balance twice
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1000
-- Do some calculations...

-- Transaction 2: Another user deposits money
BEGIN;
UPDATE accounts SET balance = balance + 500 WHERE id = 1;
COMMIT;

-- Transaction 1: Read again
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1500 (different!)
COMMIT;
```

### Isolation Level 2: Repeatable Read

**How it works:**
- Sees a snapshot of data as it was at the start of the transaction
- All queries in the transaction see the same data
- Other transactions' commits are invisible

```sql
-- Transaction 1
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1000

-- Transaction 2 (runs and commits)
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;
COMMIT;

-- Transaction 1 continues
SELECT balance FROM accounts WHERE id = 1;  -- Still returns 1000 (snapshot isolation)
COMMIT;
```

**Anomalies prevented:**
- ✅ Dirty reads
- ✅ Nonrepeatable reads (consistent snapshot)
- ✅ Phantom reads (PostgreSQL-specific: standard SQL allows these at Repeatable Read)

**Anomalies possible:**
- ❌ Serialization anomalies (write skew, read skew)

**When to use:**
- Reports that need consistent data across multiple queries
- Complex calculations that depend on consistent state
- When you need a stable view of data
- Batch processing jobs

**Handling update conflicts:**
```sql
-- Transaction 1
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1000
-- Calculate new balance: 1000 - 100 = 900

-- Transaction 2 (commits first)
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
UPDATE accounts SET balance = 800 WHERE id = 1;
COMMIT;

-- Transaction 1 tries to update
UPDATE accounts SET balance = 900 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update

-- Must handle error and retry
ROLLBACK;
```

### Isolation Level 3: Serializable

**How it works:**
- Strongest isolation level
- Guarantees execution is equivalent to running transactions serially (one after another)
- Uses predicate locking and conflict detection

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- All operations here behave as if no other transactions are running
COMMIT;
```

**Anomalies prevented:**
- ✅ All anomalies (dirty reads, nonrepeatable reads, phantom reads, serialization anomalies)

**Anomalies possible:**
- ✅ None

**When to use:**
- Critical financial transactions
- When absolute consistency is required
- Situations where anomalies would cause serious problems
- When correctness is more important than performance

**Performance cost:**
- More likely to encounter serialization failures
- Requires more monitoring and tracking overhead
- May need retry logic in application code

**Example preventing write skew:**
```sql
-- Scenario: Two doctors on-call, at least one must be available

-- Transaction 1: Doctor A requests time off
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM schedules 
WHERE date = '2024-01-15' AND on_call = true;  -- Returns 2

-- Safe to go off-call (another doctor is on)
UPDATE schedules 
SET on_call = false 
WHERE doctor_id = 1 AND date = '2024-01-15';

-- Transaction 2: Doctor B requests time off (concurrent)
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM schedules 
WHERE date = '2024-01-15' AND on_call = true;  -- Returns 2

-- Safe to go off-call (another doctor is on)
UPDATE schedules 
SET on_call = false 
WHERE doctor_id = 2 AND date = '2024-01-15';

-- One transaction will fail with serialization error
-- Prevents both doctors from going off-call
```

### Setting Isolation Levels

**Per transaction:**
```sql
-- At BEGIN time
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- or
BEGIN ISOLATION LEVEL SERIALIZABLE;

-- After BEGIN
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- must be first statement in transaction
```

**For session:**
```sql
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- All future transactions in this session use Repeatable Read
```

**For database (requires superuser):**
```sql
ALTER DATABASE mydb SET default_transaction_isolation = 'repeatable read';
```

**Check current level:**
```sql
SHOW transaction_isolation;
-- or
SELECT current_setting('transaction_isolation');
```

### Transaction Anomalies Explained

**Dirty Read (Not possible in PostgreSQL):**
```sql
-- Transaction 1
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;
-- Not yet committed

-- Transaction 2
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  
-- Would return 500 in databases allowing dirty reads
-- PostgreSQL returns old value (1000)
```

**Nonrepeatable Read:**
```sql
-- Transaction 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1000

-- Transaction 2
BEGIN;
UPDATE accounts SET balance = 1500 WHERE id = 1;
COMMIT;

-- Transaction 1
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1500 at Read Committed
COMMIT;                                      -- Returns 1000 at Repeatable Read
```

**Phantom Read:**
```sql
-- Transaction 1
BEGIN;
SELECT COUNT(*) FROM orders WHERE status = 'pending';  -- Returns 5

-- Transaction 2
BEGIN;
INSERT INTO orders (status) VALUES ('pending');
COMMIT;

-- Transaction 1
SELECT COUNT(*) FROM orders WHERE status = 'pending';  
-- Returns 6 at Read Committed (phantom row appeared)
-- Returns 5 at Repeatable Read/Serializable
COMMIT;
```

**Serialization Anomaly (Write Skew):**
```sql
-- Constraint: total of accounts 1 and 2 must be >= 1000

-- Transaction 1
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT SUM(balance) FROM accounts WHERE id IN (1, 2);  -- Returns 1000
-- Safe to withdraw 100 from account 1
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- Transaction 2 (concurrent)
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT SUM(balance) FROM accounts WHERE id IN (1, 2);  -- Returns 1000
-- Safe to withdraw 100 from account 2
UPDATE accounts SET balance = balance - 100 WHERE id = 2;

-- Both commit successfully
COMMIT;  -- Transaction 1
COMMIT;  -- Transaction 2

-- Result: sum is now 800, violating constraint!
-- Serializable would prevent this
```

### Handling Serialization Failures

Applications must handle serialization failures with retry logic:

```sql
-- Python example (pseudocode)
max_retries = 3
for attempt in range(max_retries):
    try:
        BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE
        -- do work
        COMMIT
        break  -- Success!
    except SerializationFailure:
        ROLLBACK
        if attempt == max_retries - 1:
            raise  -- Give up after max retries
        -- Otherwise retry
```

**Best practices for retries:**
- Limit retry attempts (3-5 typically)
- Use exponential backoff
- Log serialization failures
- Monitor failure rates
- Consider lowering isolation level if failures are common

### Choosing an Isolation Level

**Use Read Committed (default) when:**
- Most CRUD operations
- You need to see latest committed changes
- High concurrency is important
- Application handles inconsistencies

**Use Repeatable Read when:**
- Generating reports
- Batch processing
- Multi-step calculations need consistent view
- Can handle occasional serialization failures

**Use Serializable when:**
- Financial transactions
- Inventory management with constraints
- Critical correctness requirements
- Write skew must be prevented

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

1. Create test data:

```sql
CREATE TABLE inventory (
    id SERIAL PRIMARY KEY,
    product TEXT NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity >= 0)
);

INSERT INTO inventory (product, quantity) VALUES 
    ('Widget', 10),
    ('Gadget', 5);
```

2. Demonstrate nonrepeatable read at Read Committed:

```sql
-- Terminal 1: Transaction 1
BEGIN;  -- Uses default Read Committed
SELECT quantity FROM inventory WHERE product = 'Widget';  -- Returns 10

-- Terminal 2: Transaction 2
BEGIN;
UPDATE inventory SET quantity = 15 WHERE product = 'Widget';
COMMIT;

-- Terminal 1: Transaction 1 continues
SELECT quantity FROM inventory WHERE product = 'Widget';  -- Returns 15 (changed!)
COMMIT;
```

3. Demonstrate snapshot isolation at Repeatable Read:

```sql
-- Terminal 1: Transaction 1
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT quantity FROM inventory WHERE product = 'Widget';  -- Returns 10

-- Terminal 2: Transaction 2
BEGIN;
UPDATE inventory SET quantity = 20 WHERE product = 'Widget';
COMMIT;

-- Terminal 1: Transaction 1 continues
SELECT quantity FROM inventory WHERE product = 'Widget';  -- Still returns 10 (snapshot)
COMMIT;
```

4. Demonstrate update conflict:

```sql
-- Terminal 1
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT quantity FROM inventory WHERE product = 'Widget';  -- 10

-- Terminal 2
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
UPDATE inventory SET quantity = 8 WHERE product = 'Widget';
COMMIT;

-- Terminal 1 (tries to update)
UPDATE inventory SET quantity = 7 WHERE product = 'Widget';
-- ERROR: could not serialize access due to concurrent update
ROLLBACK;
```

5. Test Serializable preventing write skew:

```sql
-- Ensure total inventory >= 10

-- Terminal 1
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(quantity) FROM inventory;  -- Returns 15
UPDATE inventory SET quantity = quantity - 6 WHERE product = 'Widget';

-- Terminal 2 (concurrent)
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(quantity) FROM inventory;  -- Returns 15
UPDATE inventory SET quantity = quantity - 6 WHERE product = 'Gadget';

-- Try to commit both
COMMIT;  -- Terminal 1 (succeeds)
COMMIT;  -- Terminal 2 (fails with serialization error)
```
