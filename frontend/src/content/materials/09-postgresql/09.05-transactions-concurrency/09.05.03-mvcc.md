## Introduction

Multi-Version Concurrency Control (MVCC) is PostgreSQL's core mechanism for handling concurrent access to data. Instead of using locks to control access, MVCC maintains multiple versions of each row, allowing readers and writers to operate simultaneously without blocking each other. This is the secret behind PostgreSQL's high-concurrency performance.

Understanding MVCC is essential for understanding PostgreSQL's behavior under load, troubleshooting performance issues, and making informed decisions about database tuning and maintenance.

## Key Concepts Summary

### The MVCC Principle

**Core idea:** Readers never block writers, and writers never block readers.

Traditional locking approach:
```
Reader wants data → Must wait if writer has lock
Writer wants data → Must wait if reader has lock
Result: Contention, blocking, reduced concurrency
```

MVCC approach:
```
Reader wants data → Reads appropriate version, never waits
Writer wants data → Creates new version, never blocks readers
Result: High concurrency, no blocking between readers/writers
```

### How MVCC Works: Row Versions

When you update a row, PostgreSQL doesn't modify it in place. Instead:

1. **Original row** is marked as "deleted" by the updating transaction
2. **New row version** is inserted with the updated data
3. Both versions coexist in the table
4. Each transaction sees the appropriate version based on its snapshot

```sql
-- Initial state
CREATE TABLE accounts (id INTEGER, balance INTEGER);
INSERT INTO accounts VALUES (1, 1000);

-- Transaction 1 starts
BEGIN;  -- Gets transaction ID 100, snapshot taken
SELECT balance FROM accounts WHERE id = 1;  -- Sees 1000

-- Transaction 2 updates (different connection)
BEGIN;  -- Gets transaction ID 101
UPDATE accounts SET balance = 1500 WHERE id = 1;
-- Old row marked with xmax=101
-- New row inserted with xmin=101
COMMIT;

-- Transaction 1 continues
SELECT balance FROM accounts WHERE id = 1;  
-- Still sees 1000 (old version is visible to transaction 100)
COMMIT;

-- New transaction
BEGIN;  -- Gets transaction ID 102
SELECT balance FROM accounts WHERE id = 1;
-- Sees 1500 (new version is visible to transaction 102)
COMMIT;
```

### Transaction IDs and Row Visibility

Every row in PostgreSQL has hidden system columns:

```sql
-- View system columns
SELECT xmin, xmax, ctid, * FROM accounts;
```

**xmin:** Transaction ID that inserted this row version
**xmax:** Transaction ID that deleted/updated this row (0 if still current)
**ctid:** Physical location (page and item)

**Visibility rules (simplified):**

For a row to be visible to a transaction:
1. `xmin` must be committed and ≤ transaction's snapshot
2. `xmax` must be 0 (not deleted) OR not committed OR > transaction's snapshot

```sql
-- Example visibility
Row version A: xmin=100, xmax=0
Row version B: xmin=101, xmax=0

Transaction 102's snapshot: sees transactions ≤ 101
- Can see row A (xmin=100 ≤ 101, xmax=0)
- Can see row B (xmin=101 ≤ 101, xmax=0)

Transaction 101's snapshot: sees transactions ≤ 100
- Can see row A (xmin=100 ≤ 100, xmax=0)
- Cannot see row B (xmin=101 > 100)
```

### Snapshots

A snapshot is a view of which transactions were committed at a specific point in time.

**When snapshots are taken:**
- **Read Committed:** New snapshot at the start of each statement
- **Repeatable Read/Serializable:** Single snapshot at first query in transaction

```sql
-- Read Committed (default)
BEGIN;
SELECT * FROM orders;  -- Snapshot 1: sees transactions ≤ 100
-- Another transaction commits (101)
SELECT * FROM orders;  -- Snapshot 2: sees transactions ≤ 101 (different data!)
COMMIT;

-- Repeatable Read
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM orders;  -- Snapshot 1: sees transactions ≤ 100
-- Another transaction commits (101)
SELECT * FROM orders;  -- Still Snapshot 1: sees transactions ≤ 100 (same data!)
COMMIT;
```

### Example: Concurrent Reads and Writes

```sql
-- Setup
CREATE TABLE products (id INTEGER PRIMARY KEY, stock INTEGER);
INSERT INTO products VALUES (1, 100);

-- Connection 1: Long-running read transaction
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT stock FROM products WHERE id = 1;  -- Returns 100
-- Transaction holds snapshot seeing stock=100

-- Connection 2: Update stock
BEGIN;
UPDATE products SET stock = 95 WHERE id = 1;
-- Creates new row version with xmin=<current_txid>
COMMIT;

-- Connection 3: Another update
BEGIN;
UPDATE products SET stock = 90 WHERE id = 1;
-- Creates another new row version
COMMIT;

-- Connection 1: Still reading
SELECT stock FROM products WHERE id = 1;  -- Still returns 100!
-- Old version still exists for this transaction
COMMIT;

-- Now old versions can be cleaned up by VACUUM
```

At this point, the table has 3 versions of the row:
1. stock=100 (old, can be vacuumed after Connection 1 commits)
2. stock=95 (old, can be vacuumed)
3. stock=90 (current)

### VACUUM and Row Version Cleanup

MVCC creates old row versions that must be cleaned up:

```sql
-- Check table bloat
SELECT schemaname, tablename, 
       pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS size,
       n_dead_tup AS dead_tuples,
       n_live_tup AS live_tuples
FROM pg_stat_user_tables
WHERE tablename = 'products';
```

**What VACUUM does:**
1. Identifies rows visible to no active transaction
2. Marks space as reusable (doesn't return to OS by default)
3. Updates visibility maps
4. Updates statistics
5. Prevents transaction ID wraparound

**VACUUM types:**

```sql
-- Regular VACUUM (doesn't block reads/writes)
VACUUM products;

-- VACUUM FULL (locks table, rewrites entire table, returns space to OS)
VACUUM FULL products;

-- ANALYZE (updates statistics)
VACUUM ANALYZE products;
```

**Autovacuum:** PostgreSQL automatically runs VACUUM in the background.

```sql
-- Check autovacuum settings
SHOW autovacuum;
SELECT name, setting FROM pg_settings 
WHERE name LIKE 'autovacuum%';

-- Check last vacuum time
SELECT schemaname, tablename, 
       last_vacuum, last_autovacuum,
       last_analyze, last_autoanalyze
FROM pg_stat_user_tables
WHERE tablename = 'products';
```

### MVCC Performance Implications

**Advantages:**
- ✅ High concurrency (no blocking between readers/writers)
- ✅ Consistent reads without locking
- ✅ Rollback is fast (just mark transaction as aborted)
- ✅ Multiple isolation levels with same mechanism

**Costs:**
- ❌ Tables grow larger (multiple versions stored)
- ❌ Requires regular VACUUM maintenance
- ❌ UPDATE/DELETE creates extra work (new versions)
- ❌ Long transactions keep old versions alive longer

### Long-Running Transactions Problem

Long transactions prevent VACUUM from cleaning up old versions:

```sql
-- Connection 1: Long transaction (problem!)
BEGIN;
SELECT * FROM products WHERE id = 1;
-- Transaction runs for hours...
-- Keeps all row versions created during this time

-- Connection 2: Many updates
UPDATE products SET stock = stock - 1 WHERE id = 1;  -- 1000 times
-- Creates 1000 row versions that can't be cleaned up

-- Result: Table bloat, performance degradation
```

**Best practices:**
- Keep transactions as short as possible
- Avoid idle transactions in applications
- Use connection pooling to prevent abandoned transactions
- Monitor `pg_stat_activity` for long-running queries

```sql
-- Find long-running transactions
SELECT pid, usename, state, 
       now() - xact_start AS transaction_duration,
       query
FROM pg_stat_activity
WHERE state != 'idle'
  AND xact_start IS NOT NULL
ORDER BY xact_start;
```

### Transaction ID Wraparound

PostgreSQL uses 32-bit transaction IDs (2 billion transactions):

```sql
-- Check transaction ID age
SELECT datname, age(datfrozenxid) 
FROM pg_database 
ORDER BY age(datfrozenxid) DESC;
```

**Wraparound protection:**
- VACUUM "freezes" old rows (marks them as visible to all future transactions)
- Autovacuum runs aggressively when approaching wraparound
- Database stops accepting writes at 2 billion transaction age

**Prevention:**
- Let autovacuum run regularly
- VACUUM large tables periodically
- Monitor transaction ID age
- Don't disable autovacuum globally

### Monitoring MVCC Health

```sql
-- Check table bloat indicators
SELECT schemaname, tablename,
       n_live_tup AS live_rows,
       n_dead_tup AS dead_rows,
       ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
       last_vacuum,
       last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC;

-- Check for bloat requiring attention
SELECT schemaname, tablename,
       pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS size,
       n_dead_tup
FROM pg_stat_user_tables
WHERE n_dead_tup > n_live_tup * 0.2  -- More than 20% dead tuples
ORDER BY n_dead_tup DESC;
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

1. Create test table and observe row versions:

```sql
CREATE TABLE mvcc_demo (
    id INTEGER PRIMARY KEY,
    value TEXT
);

INSERT INTO mvcc_demo VALUES (1, 'original');

-- View system columns
SELECT xmin, xmax, cmin, cmax, ctid, * FROM mvcc_demo;
-- Note the xmin (insert transaction ID) and xmax (0 = not deleted)
```

2. Observe multiple versions:

```sql
-- Update the row multiple times
UPDATE mvcc_demo SET value = 'update 1' WHERE id = 1;
UPDATE mvcc_demo SET value = 'update 2' WHERE id = 1;
UPDATE mvcc_demo SET value = 'update 3' WHERE id = 1;

-- Check dead tuples
SELECT n_live_tup, n_dead_tup 
FROM pg_stat_user_tables 
WHERE relname = 'mvcc_demo';
-- Should show 1 live tuple and 3 dead tuples

-- View current version
SELECT xmin, xmax, ctid, * FROM mvcc_demo;
```

3. Demonstrate concurrent visibility:

```sql
-- Terminal 1: Start long transaction
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT xmin, xmax, value FROM mvcc_demo WHERE id = 1;
-- Note the xmin value

-- Terminal 2: Update the row
BEGIN;
UPDATE mvcc_demo SET value = 'concurrent update' WHERE id = 1;
SELECT xmin, xmax, value FROM mvcc_demo WHERE id = 1;
COMMIT;

-- Terminal 1: Read again
SELECT xmin, xmax, value FROM mvcc_demo WHERE id = 1;
-- Still sees old version! Note xmin is same as before
COMMIT;

-- New transaction sees new version
SELECT xmin, xmax, value FROM mvcc_demo WHERE id = 1;
-- Now sees 'concurrent update' with different xmin
```

4. See VACUUM in action:

```sql
-- Generate dead tuples
UPDATE mvcc_demo SET value = 'version ' || generate_series 
FROM generate_series(1, 100);

-- Check bloat
SELECT n_live_tup, n_dead_tup,
       pg_size_pretty(pg_total_relation_size('mvcc_demo')) AS size
FROM pg_stat_user_tables 
WHERE relname = 'mvcc_demo';

-- Run VACUUM
VACUUM VERBOSE mvcc_demo;

-- Check again
SELECT n_live_tup, n_dead_tup,
       pg_size_pretty(pg_total_relation_size('mvcc_demo')) AS size
FROM pg_stat_user_tables 
WHERE relname = 'mvcc_demo';
-- Dead tuples should be reduced
```

5. Observe long transaction impact:

```sql
-- Terminal 1: Start long transaction
BEGIN;
SELECT * FROM mvcc_demo;
-- Leave transaction open (don't commit yet)

-- Terminal 2: Make many updates
UPDATE mvcc_demo SET value = 'update ' || i 
FROM generate_series(1, 1000) i;

-- Run VACUUM
VACUUM VERBOSE mvcc_demo;

-- Check dead tuples
SELECT n_live_tup, n_dead_tup 
FROM pg_stat_user_tables 
WHERE relname = 'mvcc_demo';
-- Dead tuples can't be cleaned because Terminal 1's transaction is still active

-- Terminal 1: Now commit
COMMIT;

-- Terminal 2: VACUUM again
VACUUM VERBOSE mvcc_demo;

-- Check again
SELECT n_live_tup, n_dead_tup 
FROM pg_stat_user_tables 
WHERE relname = 'mvcc_demo';
-- Now dead tuples can be cleaned
```
