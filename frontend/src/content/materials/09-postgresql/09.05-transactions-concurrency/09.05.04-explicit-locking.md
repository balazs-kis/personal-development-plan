## Introduction

While MVCC handles most concurrency automatically, some scenarios require explicit locking to ensure data integrity. PostgreSQL provides several row-level locking modes that give you fine-grained control over concurrent access. Understanding when and how to use explicit locks is essential for implementing correct concurrent operations like queue processing, reservation systems, and inventory management.

Explicit locking is a powerful tool, but it must be used carefully. Improper use can lead to deadlocks, poor performance, and reduced concurrency.

## Key Concepts Summary

### Row-Level Locking Modes

PostgreSQL provides four row-level locking modes with increasing strength:

| Mode | Blocks | Use Case |
|------|--------|----------|
| FOR KEY SHARE | FOR UPDATE, FOR NO KEY UPDATE | Allow shared locks on referenced rows |
| FOR SHARE | FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE | Multiple transactions can read, none can modify |
| FOR NO KEY UPDATE | All except FOR KEY SHARE | Lock for update without blocking key references |
| FOR UPDATE | All other locks | Exclusive lock for modification |

### SELECT FOR UPDATE

The most commonly used explicit lock. Locks rows for exclusive modification:

```sql
BEGIN;

-- Lock the row for update
SELECT * FROM accounts 
WHERE id = 1 
FOR UPDATE;

-- Now safe to update (no other transaction can modify this row)
UPDATE accounts 
SET balance = balance - 100 
WHERE id = 1;

COMMIT;
```

**How it works:**
- Acquires exclusive row lock
- Other transactions attempting FOR UPDATE on same row will block
- Other transactions can still read the row (MVCC visibility)
- Lock released at COMMIT or ROLLBACK

**Common pattern - prevent lost updates:**

```sql
-- Without FOR UPDATE (WRONG - race condition)
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- Returns 1000
-- Calculate new balance: 1000 - 100 = 900
UPDATE accounts SET balance = 900 WHERE id = 1;
COMMIT;
-- Another concurrent transaction might update between SELECT and UPDATE!

-- With FOR UPDATE (CORRECT)
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- Locks row
-- Calculate new balance: 1000 - 100 = 900
-- No other transaction can modify this row while we hold the lock
UPDATE accounts SET balance = 900 WHERE id = 1;
COMMIT;
```

### FOR UPDATE NOWAIT

Fails immediately instead of waiting for lock:

```sql
BEGIN;

-- Try to lock row, fail immediately if already locked
SELECT * FROM accounts 
WHERE id = 1 
FOR UPDATE NOWAIT;
-- ERROR: could not obtain lock on row in relation "accounts"

ROLLBACK;
```

**Use cases:**
- Web applications that shouldn't wait indefinitely
- Preventing timeout issues
- User-facing operations where feedback is important

```sql
-- Application code pattern
BEGIN;
BEGIN TRY
    SELECT * FROM seats WHERE id = @seat_id FOR UPDATE NOWAIT;
    UPDATE seats SET reserved = true WHERE id = @seat_id;
    COMMIT;
    RETURN "Seat reserved successfully";
CATCH lock_not_available
    ROLLBACK;
    RETURN "Seat is currently being reserved by another user";
END TRY
```

### FOR UPDATE SKIP LOCKED

Skips locked rows and returns only available ones:

```sql
-- Queue processing pattern
BEGIN;

-- Get next available job (skip locked ones)
SELECT * FROM jobs 
WHERE status = 'pending' 
ORDER BY created_at 
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- Process job
UPDATE jobs SET status = 'processing' WHERE id = @job_id;

COMMIT;
```

**Multiple workers can run this concurrently:**
- Worker 1: Gets job ID 1 (locks it)
- Worker 2: Skips job ID 1 (locked), gets job ID 2
- Worker 3: Skips jobs 1 and 2, gets job ID 3
- No blocking, maximum concurrency!

**Queue processing pattern:**

```sql
CREATE TABLE queue (
    id SERIAL PRIMARY KEY,
    task TEXT NOT NULL,
    status TEXT DEFAULT 'pending',
    created_at TIMESTAMP DEFAULT NOW(),
    processed_at TIMESTAMP
);

-- Worker process
DO $$
DECLARE
    task_record RECORD;
BEGIN
    LOOP
        -- Get next task
        SELECT * INTO task_record
        FROM queue
        WHERE status = 'pending'
        ORDER BY created_at
        LIMIT 1
        FOR UPDATE SKIP LOCKED;
        
        EXIT WHEN NOT FOUND;  -- No more tasks
        
        -- Mark as processing
        UPDATE queue 
        SET status = 'processing', processed_at = NOW()
        WHERE id = task_record.id;
        
        -- Do work here
        RAISE NOTICE 'Processing task %', task_record.id;
        
        -- Mark as complete
        UPDATE queue SET status = 'complete' WHERE id = task_record.id;
        
        COMMIT;
    END LOOP;
END $$;
```

### FOR SHARE

Multiple transactions can hold shared locks (all can read, none can modify):

```sql
-- Transaction 1
BEGIN;
SELECT * FROM products WHERE id = 1 FOR SHARE;
-- Holds shared lock

-- Transaction 2 (concurrent)
BEGIN;
SELECT * FROM products WHERE id = 1 FOR SHARE;
-- Also gets shared lock (compatible with Transaction 1)

-- Transaction 3 (concurrent)
BEGIN;
UPDATE products SET stock = 10 WHERE id = 1;
-- Blocks waiting for shared locks to release
```

**Use case - prevent updates during complex read:**

```sql
BEGIN;

-- Lock orders and related items for reading
SELECT * FROM orders WHERE id = 1 FOR SHARE;
SELECT * FROM order_items WHERE order_id = 1 FOR SHARE;

-- Do complex calculation
-- ... calculate total, validate inventory, check limits ...

-- No other transaction can modify these rows while we calculate

COMMIT;
```

### FOR NO KEY UPDATE

Allows key shares but prevents updates:

```sql
-- Transaction 1: Update non-key column
BEGIN;
SELECT * FROM users WHERE id = 1 FOR NO KEY UPDATE;
UPDATE users SET last_login = NOW() WHERE id = 1;

-- Transaction 2: Can still reference user in foreign key
BEGIN;
INSERT INTO orders (user_id, total) VALUES (1, 100);  -- Does not block
COMMIT;

-- Transaction 3: Cannot update user
BEGIN;
UPDATE users SET email = 'new@example.com' WHERE id = 1;  -- Blocks
```

**Use case:** Update non-key columns while allowing foreign key references

### Optimistic vs Pessimistic Locking

**Pessimistic Locking (SELECT FOR UPDATE):**

```sql
-- Assume conflicts will happen, lock preemptively
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- Lock acquired, no one else can modify
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**Pros:**
- Guaranteed no conflicts
- Simpler application logic
- Good for high-conflict scenarios

**Cons:**
- Reduced concurrency (blocking)
- Risk of deadlocks
- Holds locks longer

**Optimistic Locking (Version Column):**

```sql
-- Assume conflicts are rare, check at update time
BEGIN;
SELECT balance, version FROM accounts WHERE id = 1;  -- No lock
-- Calculate: new_balance = 1000 - 100 = 900

-- Update only if version hasn't changed
UPDATE accounts 
SET balance = 900, version = version + 1
WHERE id = 1 AND version = @original_version;

-- Check if update succeeded
IF @@ROWCOUNT = 0 THEN
    ROLLBACK;
    RAISE EXCEPTION 'Concurrent modification detected, please retry';
END IF;

COMMIT;
```

**Pros:**
- Higher concurrency (no blocking on reads)
- No deadlock risk
- Good for low-conflict scenarios

**Cons:**
- Must handle conflicts in application
- Requires retry logic
- Wasted work on conflicts

**Choosing between them:**

Use **pessimistic locking** when:
- Conflicts are common (>10% of transactions)
- Updates are expensive
- Retry logic is complex
- Example: Inventory with high contention

Use **optimistic locking** when:
- Conflicts are rare (<1% of transactions)
- Reads are common, updates are rare
- High concurrency is priority
- Example: User profile updates

### Lock Scope and Locking Multiple Rows

```sql
-- Lock all matching rows
BEGIN;
SELECT * FROM orders 
WHERE user_id = 1 AND status = 'pending'
FOR UPDATE;
-- Locks ALL matching orders for this user
COMMIT;

-- Lock specific rows with WHERE
BEGIN;
SELECT * FROM inventory 
WHERE product_id IN (10, 20, 30)
FOR UPDATE;
-- Locks inventory for three products
COMMIT;

-- Lock join results
BEGIN;
SELECT o.*, oi.*
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
WHERE o.id = 1
FOR UPDATE;
-- Locks all matched rows in both tables
COMMIT;
```

### Lock Ordering to Prevent Deadlocks

Always lock rows in the same order across transactions:

```sql
-- WRONG - Different order in different transactions
-- Transaction 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- Locks account 1
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- Waits for account 2

-- Transaction 2
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- Locks account 2
UPDATE accounts SET balance = balance + 50 WHERE id = 1;   -- Waits for account 1
-- DEADLOCK!

-- CORRECT - Same order in all transactions
-- Always lock accounts in ascending ID order
BEGIN;
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

### Advisory Locks

Application-level locks not tied to rows:

```sql
-- Acquire advisory lock
SELECT pg_advisory_lock(123);  -- Blocks until lock acquired

-- Do work...

-- Release lock
SELECT pg_advisory_unlock(123);

-- Non-blocking variant
SELECT pg_try_advisory_lock(123);  -- Returns true/false immediately
```

**Use cases:**
- Application-level coordination
- Preventing duplicate cron jobs
- Resource locking outside database

```sql
-- Prevent duplicate job execution
DO $$
BEGIN
    -- Try to acquire lock for job 42
    IF pg_try_advisory_lock(42) THEN
        -- Got lock, safe to run job
        RAISE NOTICE 'Running job 42';
        -- ... do work ...
        PERFORM pg_advisory_unlock(42);
    ELSE
        RAISE NOTICE 'Job 42 already running, skipping';
    END IF;
END $$;
```

4. Implement queue processing with SKIP LOCKED:

```sql
-- Terminal 1: Worker 1
BEGIN;
SELECT * FROM work_queue 
WHERE status = 'pending' 
ORDER BY id 
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- Gets Task 1

UPDATE work_queue SET status = 'processing' WHERE id = 1;
COMMIT;

-- Terminal 2: Worker 2 (concurrent)
BEGIN;
SELECT * FROM work_queue 
WHERE status = 'pending' 
ORDER BY id 
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- Gets Task 2 (skips locked Task 1)

UPDATE work_queue SET status = 'processing' WHERE id = 2;
COMMIT;
```

5. Compare optimistic vs pessimistic locking:

```sql
-- Pessimistic approach
BEGIN;
SELECT stock FROM inventory WHERE product = 'Widget' FOR UPDATE;
-- Lock acquired immediately
UPDATE inventory SET stock = stock - 1 WHERE product = 'Widget';
COMMIT;

-- Optimistic approach
BEGIN;
SELECT stock, version FROM inventory WHERE product = 'Widget';
-- No lock, others can read/update

UPDATE inventory 
SET stock = stock - 1, version = version + 1
WHERE product = 'Widget' AND version = @original_version;

-- Check if update succeeded
-- If 0 rows updated, someone else changed it - need to retry
COMMIT;
```
