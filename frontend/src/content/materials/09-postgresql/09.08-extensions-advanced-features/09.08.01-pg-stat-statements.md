## Introduction

`pg_stat_statements` is PostgreSQL's most important performance monitoring extension. Unlike `EXPLAIN` which analyzes individual queries, pg_stat_statements provides macro-level workload analysis by tracking statistics for all SQL statements executed by your server. It's the de-facto standard tool for identifying which queries need optimization and understanding overall database performance patterns.

## Key Concepts Summary

### What is pg_stat_statements?

`pg_stat_statements` tracks planning and execution statistics for all SQL statements executed by a PostgreSQL server. It provides:

- **Query normalization:** Groups similar queries together (e.g., `WHERE id = 1` and `WHERE id = 2` become one entry)
- **Cumulative metrics:** Aggregates statistics across all executions
- **Workload visibility:** Shows which queries consume the most resources
- **Optimization guidance:** Helps prioritize which queries to optimize first

### Macro vs. Micro Optimization

**Macro optimization (pg_stat_statements):**
- Analyzes the entire query workload
- Identifies which queries to optimize
- Prioritizes optimization efforts
- Tracks performance trends over time

**Micro optimization (EXPLAIN):**
- Analyzes individual query execution plans
- Shows how to optimize specific queries
- Requires query examples with actual parameters

**Best practice:** Start with pg_stat_statements to find problematic queries, then use EXPLAIN to optimize them.

## Installation and Setup

### Step 1: Enable in postgresql.conf

```bash
# Edit postgresql.conf
shared_preload_libraries = 'pg_stat_statements'

# Enable query ID calculation (PostgreSQL 14+)
compute_query_id = on

# Optional: adjust tracking settings
pg_stat_statements.track = all  # track all statements (default: top)
pg_stat_statements.max = 10000  # number of statements tracked (default: 5000)
```

**Important:** Changes to `shared_preload_libraries` require a PostgreSQL restart.

### Step 2: Restart PostgreSQL

```bash
# On Linux/macOS
sudo systemctl restart postgresql

# On Windows
net stop postgresql-15
net start postgresql-15

# Using pg_ctl
pg_ctl restart -D /path/to/data/directory
```

### Step 3: Create the Extension

```sql
-- Create extension in your database
CREATE EXTENSION pg_stat_statements;

-- Verify installation
SELECT * FROM pg_stat_statements LIMIT 1;
```

### Verification

```sql
-- Check if extension is loaded
SELECT * FROM pg_extension WHERE extname = 'pg_stat_statements';

-- Confirm shared library is loaded
SHOW shared_preload_libraries;

-- Check query ID computation
SHOW compute_query_id;
```

## Key Metrics and Columns

### Essential Columns

| Column | Description |
|--------|-------------|
| `queryid` | Unique hash identifier for normalized query |
| `query` | Normalized query text (parameters replaced with `$1`, `$2`, etc.) |
| `calls` | Number of times query was executed |
| `total_exec_time` | Total execution time (milliseconds) |
| `mean_exec_time` | Average execution time per call |
| `min_exec_time` | Fastest execution time |
| `max_exec_time` | Slowest execution time |
| `stddev_exec_time` | Standard deviation of execution time |
| `rows` | Total number of rows returned/affected |

### Buffer and I/O Metrics

| Column | Description |
|--------|-------------|
| `shared_blks_hit` | Buffer cache hits (in memory) |
| `shared_blks_read` | Disk reads (cache misses) |
| `shared_blks_written` | Blocks written to disk |
| `temp_blks_read` | Temporary blocks read (sorts, hashes) |
| `temp_blks_written` | Temporary blocks written |

### Planning Metrics

| Column | Description |
|--------|-------------|
| `total_plan_time` | Total query planning time |
| `mean_plan_time` | Average planning time |

### Cache Hit Ratio

```sql
-- Calculate cache hit ratio for each query
SELECT 
    queryid,
    query,
    shared_blks_hit,
    shared_blks_read,
    CASE 
        WHEN (shared_blks_hit + shared_blks_read) > 0 
        THEN 100.0 * shared_blks_hit / (shared_blks_hit + shared_blks_read)
        ELSE 0 
    END AS cache_hit_ratio
FROM pg_stat_statements
ORDER BY (shared_blks_hit + shared_blks_read) DESC
LIMIT 20;
```

## Common Analysis Queries

### 1. Top Queries by Total Time

```sql
-- Queries consuming the most total execution time
SELECT 
    queryid,
    LEFT(query, 80) AS query_snippet,
    calls,
    ROUND(total_exec_time::numeric, 2) AS total_time_ms,
    ROUND(mean_exec_time::numeric, 2) AS avg_time_ms,
    ROUND((100 * total_exec_time / SUM(total_exec_time) OVER ())::numeric, 2) AS percentage
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_stat_statements%'
ORDER BY total_exec_time DESC
LIMIT 10;

-- These queries are the best optimization targets
-- Even small per-query improvements have large aggregate impact
```

### 2. Slowest Queries (by Average Time)

```sql
-- Queries with highest average execution time
SELECT 
    queryid,
    LEFT(query, 80) AS query_snippet,
    calls,
    ROUND(mean_exec_time::numeric, 2) AS avg_time_ms,
    ROUND(max_exec_time::numeric, 2) AS max_time_ms,
    ROUND(stddev_exec_time::numeric, 2) AS stddev_ms
FROM pg_stat_statements
WHERE calls > 10  -- Filter out rarely-executed queries
  AND query NOT LIKE '%pg_stat_statements%'
ORDER BY mean_exec_time DESC
LIMIT 10;
```

### 3. Most Frequently Executed Queries

```sql
-- Queries executed most often
SELECT 
    queryid,
    LEFT(query, 80) AS query_snippet,
    calls,
    ROUND(mean_exec_time::numeric, 2) AS avg_time_ms,
    ROUND(total_exec_time::numeric, 2) AS total_time_ms
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_stat_statements%'
ORDER BY calls DESC
LIMIT 10;

-- High-frequency queries are optimization targets even if individually fast
```

### 4. Queries Using Temporary Storage

```sql
-- Queries writing to disk (expensive operations)
SELECT 
    queryid,
    LEFT(query, 80) AS query_snippet,
    calls,
    temp_blks_read,
    temp_blks_written,
    ROUND((temp_blks_written * 8.0 / 1024)::numeric, 2) AS temp_mb_written
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC
LIMIT 10;

-- These queries may need work_mem tuning or optimization
```

### 5. Queries with Poor Cache Hit Ratio

```sql
-- Queries reading frequently from disk
SELECT 
    queryid,
    LEFT(query, 80) AS query_snippet,
    calls,
    shared_blks_hit,
    shared_blks_read,
    ROUND(100.0 * shared_blks_hit / NULLIF(shared_blks_hit + shared_blks_read, 0), 2) AS cache_hit_ratio
FROM pg_stat_statements
WHERE shared_blks_read > 0
ORDER BY shared_blks_read DESC
LIMIT 10;

-- Low cache hit ratio may indicate missing indexes or insufficient shared_buffers
```

### 6. Most Variable Queries

```sql
-- Queries with high execution time variance
SELECT 
    queryid,
    LEFT(query, 80) AS query_snippet,
    calls,
    ROUND(mean_exec_time::numeric, 2) AS avg_time_ms,
    ROUND(stddev_exec_time::numeric, 2) AS stddev_ms,
    ROUND((stddev_exec_time / NULLIF(mean_exec_time, 0))::numeric, 2) AS coefficient_variation
FROM pg_stat_statements
WHERE calls > 100
  AND stddev_exec_time > 0
ORDER BY (stddev_exec_time / NULLIF(mean_exec_time, 0)) DESC
LIMIT 10;

-- High variance may indicate parameter sniffing issues or inconsistent data distribution
```

## Practical Examples

### Example 1: Finding Optimization Targets

```sql
-- Comprehensive query performance report
WITH totals AS (
    SELECT SUM(total_exec_time) AS total_time
    FROM pg_stat_statements
)
SELECT 
    queryid,
    LEFT(query, 100) AS query_snippet,
    calls,
    ROUND(mean_exec_time::numeric, 2) AS avg_ms,
    ROUND(total_exec_time::numeric, 2) AS total_ms,
    ROUND((100 * total_exec_time / totals.total_time)::numeric, 2) AS pct_total_time,
    ROUND((100 * shared_blks_hit / NULLIF(shared_blks_hit + shared_blks_read, 0))::numeric, 2) AS cache_hit_pct
FROM pg_stat_statements, totals
WHERE query NOT LIKE '%pg_stat_statements%'
  AND total_exec_time > 1000  -- More than 1 second total
ORDER BY total_exec_time DESC
LIMIT 20;
```

### Example 2: Before/After Optimization Tracking

```sql
-- Snapshot before optimization
CREATE TABLE query_stats_baseline AS
SELECT 
    queryid,
    query,
    calls,
    total_exec_time,
    mean_exec_time,
    NOW() AS snapshot_time
FROM pg_stat_statements
WHERE queryid = 123456789;  -- Your query ID

-- After optimization, compare
SELECT 
    b.query,
    b.calls AS baseline_calls,
    c.calls AS current_calls,
    ROUND(b.mean_exec_time::numeric, 2) AS baseline_avg_ms,
    ROUND(c.mean_exec_time::numeric, 2) AS current_avg_ms,
    ROUND(((c.mean_exec_time - b.mean_exec_time) / b.mean_exec_time * 100)::numeric, 2) AS improvement_pct
FROM query_stats_baseline b
JOIN pg_stat_statements c USING (queryid);
```

### Example 3: Monitoring Query Trends

```sql
-- Save hourly snapshots for trend analysis
CREATE TABLE pg_stat_statements_history (
    snapshot_time TIMESTAMP NOT NULL,
    queryid BIGINT NOT NULL,
    query TEXT,
    calls BIGINT,
    total_exec_time DOUBLE PRECISION,
    mean_exec_time DOUBLE PRECISION,
    PRIMARY KEY (snapshot_time, queryid)
);

-- Periodic snapshot (run via cron or pg_cron)
INSERT INTO pg_stat_statements_history
SELECT 
    NOW(),
    queryid,
    query,
    calls,
    total_exec_time,
    mean_exec_time
FROM pg_stat_statements;

-- Analyze trends
SELECT 
    DATE_TRUNC('hour', snapshot_time) AS hour,
    LEFT(query, 80) AS query_snippet,
    MAX(calls) - MIN(calls) AS calls_per_hour,
    ROUND(AVG(mean_exec_time)::numeric, 2) AS avg_exec_time
FROM pg_stat_statements_history
WHERE queryid = 123456789
GROUP BY 1, 2
ORDER BY 1 DESC;
```

## Workflow: From pg_stat_statements to EXPLAIN

### Step 1: Identify Problematic Query

```sql
-- Find query consuming most time
SELECT queryid, query, calls, mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 1;

-- Result: queryid = 123456789
-- Query: SELECT * FROM orders WHERE user_id = $1
```

### Step 2: Find Actual Query Examples

pg_stat_statements shows normalized queries. You need actual parameters for EXPLAIN.

**Option A: From application logs**
- Enable query logging temporarily
- Search logs for the query pattern

**Option B: From pg_stat_activity**
```sql
-- If query is currently running
SELECT query, query_start
FROM pg_stat_activity
WHERE query LIKE '%FROM orders WHERE user_id%'
  AND state = 'active';
```

**Option C: Query log sampling**
```sql
-- Enable query logging for slow queries
ALTER DATABASE mydb SET log_min_duration_statement = 1000;  -- Log queries > 1s
```

### Step 3: Analyze with EXPLAIN

```sql
-- Get execution plan for actual query
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 12345;

-- Optimize based on results (add indexes, rewrite query, etc.)
```

### Step 4: Monitor Improvement

```sql
-- Check if optimization worked
SELECT 
    queryid,
    calls,
    ROUND(mean_exec_time::numeric, 2) AS avg_ms
FROM pg_stat_statements
WHERE queryid = 123456789;
```

## Maintenance and Best Practices

### Resetting Statistics

```sql
-- Reset all statistics
SELECT pg_stat_statements_reset();

-- Reset statistics for specific query
SELECT pg_stat_statements_reset(userid, dbid, queryid);

-- Typical workflow: reset after major optimization or deployment
```

### Managing Statement Limit

```sql
-- Check current statement count
SELECT COUNT(*) FROM pg_stat_statements;

-- Increase max tracked statements if needed
ALTER SYSTEM SET pg_stat_statements.max = 20000;
-- Requires restart

-- View least-used statements (candidates for eviction)
SELECT queryid, query, calls
FROM pg_stat_statements
ORDER BY calls ASC
LIMIT 10;
```

### Configuration Options

```sql
-- View current configuration
SELECT name, setting, unit, short_desc
FROM pg_settings
WHERE name LIKE 'pg_stat_statements%';

-- Common settings
-- pg_stat_statements.max = 10000         -- max statements tracked
-- pg_stat_statements.track = all         -- track all, top, or none
-- pg_stat_statements.track_utility = on  -- track DDL statements
-- pg_stat_statements.save = on           -- persist across restarts
```

## Key Takeaways

- `pg_stat_statements` is essential for database performance monitoring
- It provides workload-wide analysis, not just individual query analysis
- Query normalization groups similar queries for aggregate analysis
- Focus on queries with high `total_exec_time` for maximum impact
- Use `calls` and `mean_exec_time` together to prioritize optimization
- High temp disk usage indicates need for work_mem tuning or query optimization
- Always start with macro optimization (pg_stat_statements) before micro (EXPLAIN)
- Track trends over time by snapshotting statistics periodically
- Reset statistics after major changes to measure improvement
- Integrate with monitoring tools for continuous performance awareness
