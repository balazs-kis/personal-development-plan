## Introduction

Table partitioning divides large tables into smaller, more manageable pieces called partitions. Each partition stores a subset of the data based on partition keys. Partitioning improves query performance, simplifies maintenance operations like archiving old data, and enables better control over data storage and management as your database scales.

## Key Concepts Summary

### What is Table Partitioning?

Partitioning splits a large table into smaller physical pieces (partitions) while appearing as a single table to queries. Each partition stores a subset of data based on partition criteria.

**Benefits:**
- **Performance:** Queries scan only relevant partitions (partition pruning)
- **Maintenance:** Easier to archive, delete, or backup specific data ranges
- **Scalability:** Distribute data across tablespaces or storage tiers
- **Bulk operations:** Attach/detach partitions instead of large DELETE operations
- **Memory efficiency:** Frequently accessed partitions stay in cache

**When to use partitioning:**
- Tables larger than database RAM (>100GB as a rule of thumb)
- Clear partitioning key (e.g., date, region, tenant)
- Queries naturally filter by partition key
- Need for efficient data archiving/purging
- Time-series or multi-tenant applications

**When NOT to use partitioning:**
- Small tables (<10-100 million rows)
- No natural partition key
- Queries don't filter by partition key
- Added complexity outweighs benefits

## Declarative Partitioning

PostgreSQL supports three partitioning methods:

### 1. Range Partitioning

Divides data into ranges based on a column value. Most common for time-series data.

```sql
-- Create partitioned table
CREATE TABLE orders (
    order_id SERIAL,
    customer_id INT NOT NULL,
    order_date DATE NOT NULL,
    amount DECIMAL(10,2),
    status TEXT
) PARTITION BY RANGE (order_date);

-- Create partitions for each month
CREATE TABLE orders_2024_01 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE orders_2024_02 PARTITION OF orders
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

CREATE TABLE orders_2024_03 PARTITION OF orders
    FOR VALUES FROM ('2024-03-01') TO ('2024-04-01');

-- Create default partition for unmatched data
CREATE TABLE orders_default PARTITION OF orders DEFAULT;
```

**Key characteristics:**
- Range boundaries: `FROM (inclusive) TO (exclusive)`
- Common for dates, timestamps, sequential IDs
- Enables efficient time-based queries and archiving

### 2. List Partitioning

Divides data by discrete values. Good for categorical data.

```sql
-- Create partitioned table by region
CREATE TABLE sales (
    sale_id SERIAL,
    product_id INT NOT NULL,
    region TEXT NOT NULL,
    sale_date DATE NOT NULL,
    amount DECIMAL(10,2)
) PARTITION BY LIST (region);

-- Create partitions for each region
CREATE TABLE sales_north_america PARTITION OF sales
    FOR VALUES IN ('US', 'CA', 'MX');

CREATE TABLE sales_europe PARTITION OF sales
    FOR VALUES IN ('UK', 'DE', 'FR', 'IT', 'ES');

CREATE TABLE sales_asia PARTITION OF sales
    FOR VALUES IN ('JP', 'CN', 'IN', 'KR');

-- Default partition
CREATE TABLE sales_other PARTITION OF sales DEFAULT;
```

**Key characteristics:**
- Exact value matching
- Good for multi-tenant databases (partition by tenant_id)
- Efficient for categorical or enumerated data

### 3. Hash Partitioning

Distributes data evenly across partitions using a hash function.

```sql
-- Create hash-partitioned table
CREATE TABLE users (
    user_id SERIAL,
    username TEXT NOT NULL,
    email TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
) PARTITION BY HASH (user_id);

-- Create 4 hash partitions
CREATE TABLE users_p0 PARTITION OF users
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);

CREATE TABLE users_p1 PARTITION OF users
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);

CREATE TABLE users_p2 PARTITION OF users
    FOR VALUES WITH (MODULUS 4, REMAINDER 2);

CREATE TABLE users_p3 PARTITION OF users
    FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```

**Key characteristics:**
- Even data distribution across partitions
- Good when no natural partition key exists
- Enables parallel query execution
- More complex to manage (can't easily detach partitions with specific data)

## Creating and Managing Partitions

### Indexes on Partitioned Tables

```sql
-- Create index on parent table (automatically creates on all partitions)
CREATE INDEX orders_customer_idx ON orders (customer_id);

-- Index on specific partition
CREATE INDEX orders_2024_01_customer_idx ON orders_2024_01 (customer_id);

-- Check indexes on all partitions
SELECT 
    schemaname,
    tablename,
    indexname
FROM pg_indexes
WHERE tablename LIKE 'orders%'
ORDER BY tablename, indexname;
```

**Best practice:** Create indexes on the parent table to automatically apply to all partitions.

### Constraints on Partitions

```sql
-- Constraints on parent apply to all partitions
ALTER TABLE orders ADD CONSTRAINT orders_amount_positive CHECK (amount > 0);

-- Partition-specific constraints
ALTER TABLE orders_2024_01 ADD CONSTRAINT orders_2024_01_check 
    CHECK (order_date >= '2024-01-01' AND order_date < '2024-02-01');
```

### Adding New Partitions

```sql
-- Manually create next month's partition
CREATE TABLE orders_2024_04 PARTITION OF orders
    FOR VALUES FROM ('2024-04-01') TO ('2024-05-01');

-- Automate with function and pg_cron
CREATE OR REPLACE FUNCTION create_next_month_partition()
RETURNS VOID AS $$
DECLARE
    partition_date DATE := DATE_TRUNC('month', NOW() + INTERVAL '1 month');
    partition_name TEXT := 'orders_' || TO_CHAR(partition_date, 'YYYY_MM');
    start_date TEXT := partition_date::TEXT;
    end_date TEXT := (partition_date + INTERVAL '1 month')::TEXT;
BEGIN
    EXECUTE FORMAT('CREATE TABLE IF NOT EXISTS %I PARTITION OF orders ' ||
                   'FOR VALUES FROM (%L) TO (%L)',
                   partition_name, start_date, end_date);
END;
$$ LANGUAGE plpgsql;

-- Schedule monthly execution
-- SELECT cron.schedule('create-partition', '0 0 25 * *', 
--                      'SELECT create_next_month_partition()');
```

## Partition Pruning

Partition pruning is the optimizer's ability to skip scanning irrelevant partitions.

```sql
-- Query with partition pruning
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE order_date = '2024-02-15';

-- Result shows only orders_2024_02 is scanned
-- Partitions pruned: orders_2024_01, orders_2024_03, etc.

-- Check if pruning occurred
-- Look for "Partitions removed by partition pruning" in EXPLAIN output
```

**Conditions for effective pruning:**
- WHERE clause filters on partition key
- Filter uses operators that match partition strategy
- Planner can determine which partitions to scan at plan time

**Example of good pruning:**
```sql
-- Date range query (scans 3 partitions)
SELECT * FROM orders
WHERE order_date >= '2024-01-15' AND order_date < '2024-04-01';

-- IN clause (scans specific partitions)
SELECT * FROM sales
WHERE region IN ('US', 'CA');
```

**Example of poor/no pruning:**
```sql
-- Function on partition key (scans all)
SELECT * FROM orders
WHERE EXTRACT(MONTH FROM order_date) = 2;

-- Better: rewrite to enable pruning
SELECT * FROM orders
WHERE order_date >= '2024-02-01' AND order_date < '2024-03-01';
```

## Practical Examples

### Example 1: Time-Series Data with Monthly Partitions

```sql
-- Events table for log data
CREATE TABLE events (
    event_id BIGSERIAL,
    user_id INT NOT NULL,
    event_type TEXT NOT NULL,
    event_time TIMESTAMP NOT NULL,
    properties JSONB
) PARTITION BY RANGE (event_time);

-- Create partitions for last 12 months + future 3 months
DO $$
DECLARE
    partition_date DATE;
    partition_name TEXT;
BEGIN
    FOR i IN -12..3 LOOP
        partition_date := DATE_TRUNC('month', NOW() + (i || ' months')::INTERVAL);
        partition_name := 'events_' || TO_CHAR(partition_date, 'YYYY_MM');
        
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF events ' ||
            'FOR VALUES FROM (%L) TO (%L)',
            partition_name,
            partition_date,
            partition_date + INTERVAL '1 month'
        );
    END LOOP;
END $$;

-- Create indexes
CREATE INDEX events_user_time_idx ON events (user_id, event_time);
CREATE INDEX events_type_time_idx ON events (event_type, event_time);

-- Efficient query (prunes to single partition)
SELECT * FROM events
WHERE event_time >= '2024-01-01' 
  AND event_time < '2024-02-01'
  AND user_id = 12345;
```

### Example 2: Multi-Tenant SaaS Application

```sql
-- Partition by tenant for data isolation
CREATE TABLE documents (
    document_id BIGSERIAL,
    tenant_id INT NOT NULL,
    title TEXT NOT NULL,
    content TEXT,
    created_at TIMESTAMP DEFAULT NOW()
) PARTITION BY LIST (tenant_id);

-- Create partition per major tenant
CREATE TABLE documents_tenant_1001 PARTITION OF documents
    FOR VALUES IN (1001);

CREATE TABLE documents_tenant_1002 PARTITION OF documents
    FOR VALUES IN (1002);

-- Small tenants share a partition
CREATE TABLE documents_small_tenants PARTITION OF documents
    FOR VALUES IN (1003, 1004, 1005, 1006, 1007);

-- Default for new tenants
CREATE TABLE documents_default PARTITION OF documents DEFAULT;

-- Row-level security per tenant
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
    USING (tenant_id = current_setting('app.current_tenant')::INT);

-- Efficient tenant-specific queries
SET app.current_tenant = 1001;
SELECT * FROM documents WHERE tenant_id = 1001;  -- Only scans documents_tenant_1001
```

### Example 3: Data Retention and Archiving

```sql
-- Orders with automatic archiving
CREATE TABLE orders (
    order_id BIGSERIAL,
    order_date DATE NOT NULL,
    customer_id INT NOT NULL,
    total DECIMAL(10,2)
) PARTITION BY RANGE (order_date);

-- Create quarterly partitions
CREATE TABLE orders_2023_q4 PARTITION OF orders
    FOR VALUES FROM ('2023-10-01') TO ('2024-01-01');

CREATE TABLE orders_2024_q1 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');

CREATE TABLE orders_2024_q2 PARTITION OF orders
    FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');

-- Archive old partitions (instant operation)
CREATE TABLE orders_archive (LIKE orders INCLUDING ALL);

-- Detach partition from main table
ALTER TABLE orders DETACH PARTITION orders_2023_q4;

-- Attach to archive table
ALTER TABLE orders_archive ATTACH PARTITION orders_2023_q4
    FOR VALUES FROM ('2023-10-01') TO ('2024-01-01');

-- Or export to external storage and drop
-- pg_dump orders_2023_q4 > orders_2023_q4.sql
-- DROP TABLE orders_2023_q4;
```

### Example 4: Sub-Partitioning (Hierarchical)

```sql
-- Partition by year, then by month
CREATE TABLE metrics (
    metric_id BIGSERIAL,
    recorded_at TIMESTAMP NOT NULL,
    metric_name TEXT NOT NULL,
    value NUMERIC
) PARTITION BY RANGE (recorded_at);

-- Year partition
CREATE TABLE metrics_2024 PARTITION OF metrics
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01')
    PARTITION BY RANGE (recorded_at);

-- Month partitions within year
CREATE TABLE metrics_2024_01 PARTITION OF metrics_2024
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE metrics_2024_02 PARTITION OF metrics_2024
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Query benefits from multi-level pruning
SELECT * FROM metrics
WHERE recorded_at >= '2024-01-15' AND recorded_at < '2024-01-20';
-- Prunes to metrics_2024 → metrics_2024_01
```

## Attaching and Detaching Partitions

### Attaching Existing Table as Partition

```sql
-- Create standalone table
CREATE TABLE new_orders (
    order_id SERIAL,
    order_date DATE NOT NULL,
    customer_id INT NOT NULL,
    amount DECIMAL(10,2)
);

-- Populate with data
INSERT INTO new_orders VALUES (1, '2024-05-15', 100, 50.00);

-- Add constraint matching partition bounds
ALTER TABLE new_orders ADD CONSTRAINT new_orders_date_check
    CHECK (order_date >= '2024-05-01' AND order_date < '2024-06-01');

-- Attach as partition (validation may be slow)
ALTER TABLE orders ATTACH PARTITION new_orders
    FOR VALUES FROM ('2024-05-01') TO ('2024-06-01');

-- Skip validation if confident data matches (faster)
ALTER TABLE orders ATTACH PARTITION new_orders
    FOR VALUES FROM ('2024-05-01') TO ('2024-06-01')
    WITHOUT VALIDATION;  -- Use with caution!
```

### Detaching Partitions

```sql
-- Detach partition (table remains but independent)
ALTER TABLE orders DETACH PARTITION orders_2023_q4;

-- Now orders_2023_q4 is a regular table
-- Can be dropped, archived, or modified independently

-- Concurrently detach (PostgreSQL 14+, doesn't block queries)
ALTER TABLE orders DETACH PARTITION orders_2023_q4 CONCURRENTLY;
```

## Performance Considerations

### Partition Size

```sql
-- Check partition sizes
SELECT 
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname || '.' || tablename)) AS size
FROM pg_tables
WHERE tablename LIKE 'orders%'
ORDER BY pg_total_relation_size(schemaname || '.' || tablename) DESC;
```

**Guidelines:**
- Target: 10-100GB per partition
- Too many partitions (>1000): planning overhead increases
- Too few partitions: defeats purpose of partitioning

### Index Strategy

```sql
-- Local indexes (per partition) vs global indexes
-- PostgreSQL creates local indexes automatically

-- Check index sizes across partitions
SELECT 
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexname::regclass)) AS index_size
FROM pg_indexes
WHERE tablename LIKE 'orders%'
ORDER BY tablename, indexname;
```

### Constraint Exclusion (Legacy)

```sql
-- For older PostgreSQL versions without native pruning
SET constraint_exclusion = partition;  -- Enable for partitioned tables only
```

## Best Practices

### 1. Choose the Right Partition Key

✅ **Good partition keys:**
- Date/timestamp columns (most common)
- Tenant ID in multi-tenant systems
- Geographic region
- Category/type with low cardinality

❌ **Poor partition keys:**
- High-cardinality columns (user_id in user table)
- Columns not used in WHERE clauses
- Frequently updated columns

### 2. Plan Partition Maintenance

```sql
-- Automate partition creation
-- Use pg_cron or external scheduler

-- Monitor partition growth
CREATE VIEW partition_stats AS
SELECT 
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname || '.' || tablename)) AS total_size,
    (SELECT count(*) FROM only pg_class 
     WHERE relname = tablename) AS row_estimate
FROM pg_tables
WHERE tablename LIKE 'orders%'
ORDER BY pg_total_relation_size(schemaname || '.' || tablename) DESC;
```

### 3. Partition Boundaries

```sql
-- Use consistent, predictable boundaries
-- Good: Monthly boundaries at month start
CREATE TABLE orders_2024_01 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

-- Avoid: Arbitrary date boundaries
-- Bad: CREATE TABLE orders_part1 PARTITION OF orders
--      FOR VALUES FROM ('2024-01-07') TO ('2024-02-13');
```

### 4. Default Partitions

```sql
-- Always create a default partition to avoid insert failures
CREATE TABLE orders_default PARTITION OF orders DEFAULT;

-- Monitor default partition for unexpected data
SELECT COUNT(*) FROM orders_default;

-- If default accumulates data, analyze and create proper partitions
```

## Practice Exercise

Create a partitioned events system with retention:

1. Create a partitioned `user_events` table by timestamp
2. Create partitions for the past 6 months
3. Set up indexes appropriately
4. Write queries that benefit from partition pruning
5. Implement a retention policy (archive data older than 6 months)

**Example solution:**

```sql
-- Step 1: Create partitioned table
CREATE TABLE user_events (
    event_id BIGSERIAL,
    user_id INT NOT NULL,
    event_type TEXT NOT NULL,
    event_data JSONB,
    event_time TIMESTAMP NOT NULL
) PARTITION BY RANGE (event_time);

-- Step 2: Create partitions
DO $$
DECLARE
    start_date DATE;
    end_date DATE;
    partition_name TEXT;
BEGIN
    FOR i IN 0..5 LOOP
        start_date := DATE_TRUNC('month', NOW() - (i || ' months')::INTERVAL);
        end_date := start_date + INTERVAL '1 month';
        partition_name := 'user_events_' || TO_CHAR(start_date, 'YYYY_MM');
        
        EXECUTE FORMAT(
            'CREATE TABLE %I PARTITION OF user_events ' ||
            'FOR VALUES FROM (%L) TO (%L)',
            partition_name, start_date, end_date
        );
    END LOOP;
END $$;

-- Default partition
CREATE TABLE user_events_default PARTITION OF user_events DEFAULT;

-- Step 3: Create indexes
CREATE INDEX user_events_user_time_idx ON user_events (user_id, event_time DESC);
CREATE INDEX user_events_type_time_idx ON user_events (event_type, event_time DESC);

-- Step 4: Test queries with pruning
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM user_events
WHERE event_time >= NOW() - INTERVAL '1 day'
  AND user_id = 12345;

-- Step 5: Retention policy
CREATE OR REPLACE FUNCTION archive_old_events()
RETURNS VOID AS $$
DECLARE
    old_partition TEXT;
    archive_date DATE := DATE_TRUNC('month', NOW() - INTERVAL '6 months');
BEGIN
    old_partition := 'user_events_' || TO_CHAR(archive_date, 'YYYY_MM');
    
    -- Detach old partition
    EXECUTE 'ALTER TABLE user_events DETACH PARTITION ' || old_partition;
    
    -- Archive (example: copy to cold storage table)
    EXECUTE 'INSERT INTO user_events_archive SELECT * FROM ' || old_partition;
    
    -- Drop partition
    EXECUTE 'DROP TABLE ' || old_partition;
END;
$$ LANGUAGE plpgsql;

-- Schedule with pg_cron
-- SELECT cron.schedule('archive-events', '0 0 1 * *', 'SELECT archive_old_events()');
```

## Key Takeaways

- Partitioning divides large tables into manageable pieces for performance and maintenance
- Use range partitioning for time-series, list for categorical, hash for even distribution
- Declarative partitioning is simpler and more efficient than inheritance-based partitioning
- Partition pruning dramatically improves query performance by skipping irrelevant partitions
- Create indexes on parent table to automatically apply to all partitions
- Attach/detach operations enable efficient archiving without expensive DELETE operations
- Plan partition key carefully—it should be used in most WHERE clauses
- Automate partition creation to stay ahead of data growth
- Monitor partition sizes and query patterns to optimize partition strategy
- Default partitions prevent insert failures but should be monitored
