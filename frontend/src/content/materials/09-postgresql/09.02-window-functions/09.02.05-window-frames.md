## Introduction

Window frames give you fine-grained control over which rows are included in window function calculations. While PARTITION BY and ORDER BY define the overall window, frame specifications let you define a sliding subset of rows relative to the current row. This is essential for accurate moving averages, rolling calculations, and complex time-based analytics.

## Key Concepts Summary

### Window Frame Basics

A frame specification defines which rows are included in the calculation:

```sql
-- Syntax
function() OVER (
    [PARTITION BY ...]
    [ORDER BY ...]
    [frame_mode BETWEEN frame_start AND frame_end]
)

-- frame_mode: ROWS or RANGE
-- frame_start/frame_end:
--   UNBOUNDED PRECEDING
--   n PRECEDING
--   CURRENT ROW
--   n FOLLOWING
--   UNBOUNDED FOLLOWING
```

### ROWS vs RANGE

**ROWS**: Physical row offset (counts actual rows)

**RANGE**: Logical value-based offset (considers values in ORDER BY column)

```sql
-- ROWS: exactly 3 physical rows
SELECT 
    date,
    amount,
    AVG(amount) OVER (
        ORDER BY date
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) as moving_avg_3_rows
FROM sales;

-- RANGE: all rows with similar date values (useful for ties)
SELECT 
    date,
    amount,
    SUM(amount) OVER (
        ORDER BY date
        RANGE BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
    ) as remaining_total
FROM sales;
```

### Default Frame Behavior

Important: Default frames change based on ORDER BY presence:

```sql
-- Without ORDER BY: entire partition
SUM(amount) OVER ()
-- Implicit: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING

-- With ORDER BY: start to current row
SUM(amount) OVER (ORDER BY date)
-- Implicit: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

### Common Frame Patterns

```sql
-- 1. Running total (default behavior with ORDER BY)
SELECT 
    date,
    amount,
    SUM(amount) OVER (ORDER BY date) as running_total
FROM sales;
-- Implicit: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

-- 2. Moving average (N-period)
SELECT 
    date,
    amount,
    AVG(amount) OVER (
        ORDER BY date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) as moving_avg_7_days
FROM daily_sales;

-- 3. Centered moving average
SELECT 
    date,
    amount,
    AVG(amount) OVER (
        ORDER BY date
        ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
    ) as centered_avg_3_days
FROM daily_sales;

-- 4. Entire window calculation
SELECT 
    date,
    amount,
    SUM(amount) OVER (
        ORDER BY date
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) as grand_total
FROM sales;
```

### Forward-Looking Calculations

```sql
-- Sum of all future values
SELECT 
    date,
    amount,
    SUM(amount) OVER (
        ORDER BY date
        ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
    ) as remaining_total
FROM sales;

-- Next 30 days total
SELECT 
    date,
    amount,
    SUM(amount) OVER (
        ORDER BY date
        ROWS BETWEEN CURRENT ROW AND 30 FOLLOWING
    ) as next_30_days_total
FROM daily_sales;
```

### LAST_VALUE with Proper Frame

LAST_VALUE requires explicit frame specification to work as expected:

```sql
-- WRONG: Only sees current row (default frame)
SELECT 
    date,
    stock_price,
    LAST_VALUE(stock_price) OVER (ORDER BY date) as last_price
FROM stock_prices;

-- CORRECT: Sees all rows in partition
SELECT 
    date,
    stock_price,
    LAST_VALUE(stock_price) OVER (
        ORDER BY date
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) as final_price
FROM stock_prices;
```

### RANGE with Time Intervals

RANGE works great with date/time intervals:

```sql
-- All sales within 7 days before current date
SELECT 
    date,
    amount,
    SUM(amount) OVER (
        ORDER BY date
        RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW
    ) as rolling_7_day_total
FROM daily_sales;

-- Sales in a 30-day window centered on current date
SELECT 
    date,
    amount,
    AVG(amount) OVER (
        ORDER BY date
        RANGE BETWEEN INTERVAL '15 days' PRECEDING 
                  AND INTERVAL '15 days' FOLLOWING
    ) as centered_30_day_avg
FROM daily_sales;
```

### Combining Frames with Partitions

```sql
-- Moving average per product
SELECT 
    product_id,
    date,
    sales,
    AVG(sales) OVER (
        PARTITION BY product_id
        ORDER BY date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) as product_moving_avg_7_days
FROM product_sales
ORDER BY product_id, date;
```

### Practical Example: Financial Analysis

```sql
-- Comprehensive financial metrics
SELECT 
    date,
    revenue,
    -- Running total (year to date)
    SUM(revenue) OVER (
        ORDER BY date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) as ytd_revenue,
    -- 30-day moving average
    AVG(revenue) OVER (
        ORDER BY date
        ROWS BETWEEN 29 PRECEDING AND CURRENT ROW
    ) as moving_avg_30_days,
    -- 7-day moving sum
    SUM(revenue) OVER (
        ORDER BY date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) as rolling_7_day_sum,
    -- Remaining revenue (forward looking)
    SUM(revenue) OVER (
        ORDER BY date
        ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
    ) as remaining_revenue,
    -- Percentage of total
    ROUND(
        100.0 * revenue / SUM(revenue) OVER (
            ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
        ),
        2
    ) as pct_of_total
FROM daily_revenue
ORDER BY date;
```

### Practical Example: Inventory Analysis

```sql
-- Track inventory with future projections
SELECT 
    date,
    quantity_sold,
    quantity_received,
    -- Running inventory balance
    SUM(quantity_received - quantity_sold) OVER (
        ORDER BY date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) as current_inventory,
    -- Projected demand (next 14 days)
    SUM(quantity_sold) OVER (
        ORDER BY date
        ROWS BETWEEN 1 FOLLOWING AND 14 FOLLOWING
    ) as projected_demand_14_days,
    -- Average daily sales (last 30 days)
    AVG(quantity_sold) OVER (
        ORDER BY date
        ROWS BETWEEN 29 PRECEDING AND CURRENT ROW
    ) as avg_daily_sales_30_days
FROM inventory_movements
ORDER BY date;
```

### Performance Considerations

```sql
-- ROWS is generally faster than RANGE
-- Good: specific row counts
AVG(amount) OVER (
    ORDER BY date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
)

-- Can be slower: value-based ranges
AVG(amount) OVER (
    ORDER BY date
    RANGE BETWEEN 6 PRECEDING AND CURRENT ROW
)

-- Use RANGE when you need logical value-based windows
-- Use ROWS when you need physical row-based windows
```
