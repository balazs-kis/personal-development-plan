---

## Introduction

Composite indexes (also called multi-column or concatenated indexes) contain multiple columns in a specific order. They're powerful for queries that filter on multiple columns, but column order is critical. Understanding how to design composite indexes is key to optimizing complex queries.

## Key Concepts Summary

### Creating Composite Indexes

```sql
-- Basic composite index
CREATE INDEX idx_orders_user_date 
ON orders (user_id, created_at);

-- Can include up to 32 columns
CREATE INDEX idx_complex 
ON table_name (col1, col2, col3, col4);
```

### The Leftmost Prefix Rule

A composite index can be used for queries that filter on:
- The first column alone
- The first two columns
- The first three columns
- etc.

But NOT on later columns alone:

```sql
-- Index: (user_id, created_at, status)
CREATE INDEX idx_orders_composite 
ON orders (user_id, created_at, status);

-- ✅ Uses index: filters on first column
SELECT * FROM orders WHERE user_id = 123;

-- ✅ Uses index: filters on first two columns
SELECT * FROM orders 
WHERE user_id = 123 AND created_at > '2024-01-01';

-- ✅ Uses index: filters on all three columns
SELECT * FROM orders 
WHERE user_id = 123 
  AND created_at > '2024-01-01' 
  AND status = 'pending';

-- ❌ Cannot use index efficiently: skips first column
SELECT * FROM orders WHERE created_at > '2024-01-01';

-- ❌ Cannot use index efficiently: skips first column
SELECT * FROM orders WHERE status = 'pending';

-- ⚠️ Partial use: uses index for user_id, then filters status
SELECT * FROM orders WHERE user_id = 123 AND status = 'pending';
```

### Column Order Matters

Order columns by selectivity and query patterns:

```sql
-- Scenario: Query orders by user and status
SELECT * FROM orders WHERE user_id = 123 AND status = 'pending';

-- Option 1: user_id first (usually better)
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
-- Why: user_id is more selective (fewer rows per user than per status)

-- Option 2: status first (usually worse)
CREATE INDEX idx_orders_status_user ON orders (status, user_id);
-- Why: status has few distinct values (low selectivity)
```

### Ordering Principles

1. **Equality columns first**: Put columns used with `=` before range columns (`>`, `<`, `BETWEEN`)
2. **Most selective first**: Put the most discriminating column first
3. **Match query patterns**: Order columns as they appear in your WHERE clauses

```sql
-- Common query pattern
SELECT * FROM orders 
WHERE user_id = 123 
  AND created_at >= '2024-01-01' 
  AND created_at < '2024-02-01'
  AND status = 'pending';

-- Optimal index: equality columns first, then range
CREATE INDEX idx_orders_optimal 
ON orders (user_id, status, created_at);

-- Not optimal: range column in the middle
CREATE INDEX idx_orders_suboptimal 
ON orders (user_id, created_at, status);
-- Problem: status filter can't use index effectively
```

### Composite Index vs Multiple Single Indexes

```sql
-- Approach 1: Composite index (usually better)
CREATE INDEX idx_orders_user_date ON orders (user_id, created_at);

-- Approach 2: Two separate indexes (usually less efficient)
CREATE INDEX idx_orders_user ON orders (user_id);
CREATE INDEX idx_orders_date ON orders (created_at);

-- Query
SELECT * FROM orders 
WHERE user_id = 123 AND created_at > '2024-01-01';

-- With composite index: single efficient scan
-- With separate indexes: PostgreSQL may use bitmap scan or pick one index
```

**When to use multiple single-column indexes:**
- Queries filter on columns in different combinations
- Columns are queried independently often

**When to use composite indexes:**
- Queries consistently filter on same columns together
- Need to optimize specific critical queries

### Practical Examples

#### Example 1: User Orders Query

```sql
-- Common query pattern
SELECT * FROM orders 
WHERE user_id = 123 
ORDER BY created_at DESC 
LIMIT 10;

-- Perfect composite index
CREATE INDEX idx_orders_user_date_desc 
ON orders (user_id, created_at DESC);

-- Benefits:
-- 1. Filters by user_id
-- 2. Results already sorted by created_at DESC
-- 3. No separate sort operation needed
```

#### Example 2: Date Range with Status

```sql
-- Query: recent pending orders
SELECT * FROM orders 
WHERE created_at >= CURRENT_DATE - INTERVAL '7 days'
  AND status = 'pending';

-- Good index
CREATE INDEX idx_orders_status_date 
ON orders (status, created_at);

-- Why: status is equality, created_at is range
```

#### Example 3: Multi-tenant Application

```sql
-- Query pattern: filter by tenant, then various conditions
SELECT * FROM documents 
WHERE tenant_id = 456 
  AND category = 'invoices'
  AND created_at > '2024-01-01';

-- Optimal index
CREATE INDEX idx_docs_tenant_category_date 
ON documents (tenant_id, category, created_at);

-- tenant_id first (partition data by tenant)
-- category second (equality condition)
-- created_at last (range condition)
```

### Index Bloat with Composite Indexes

Composite indexes are larger than single-column indexes:

```sql
-- Single column index: stores (user_id, row_pointer)
CREATE INDEX idx_orders_user ON orders (user_id);

-- Composite index: stores (user_id, status, row_pointer)
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
-- Larger, but may replace need for idx_orders_user
```

### Covering Composite Indexes

```sql
-- Query that only needs indexed columns
SELECT user_id, created_at 
FROM orders 
WHERE user_id = 123;

-- Composite index can satisfy entirely (index-only scan)
CREATE INDEX idx_orders_user_date ON orders (user_id, created_at);
-- No need to access table!
```

### When Column Order Doesn't Matter

For queries with only equality conditions, PostgreSQL can efficiently use the index regardless of order:

```sql
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- Both work equally well with index (both are equality)
SELECT * FROM orders WHERE user_id = 123 AND status = 'pending';
SELECT * FROM orders WHERE status = 'pending' AND user_id = 123;
```

### Analyzing Query Plans

```sql
-- Check if index is being used correctly
EXPLAIN ANALYZE
SELECT * FROM orders 
WHERE user_id = 123 AND created_at > '2024-01-01';

-- Look for:
-- - Index Scan using idx_orders_user_date
-- - Index Cond shows which columns used from index
-- - Filter shows conditions applied after index scan
```

### Common Patterns

```sql
-- Pattern 1: Tenant + Date ranges
CREATE INDEX idx_data_tenant_date ON data (tenant_id, created_at);

-- Pattern 2: Status + Priority + Date
CREATE INDEX idx_tasks_status_priority_date 
ON tasks (status, priority, created_at);

-- Pattern 3: Category + Subcategory + Name
CREATE INDEX idx_products_cat_subcat_name 
ON products (category_id, subcategory_id, name);

-- Pattern 4: User + Type + Date (with sort order)
CREATE INDEX idx_events_user_type_date 
ON events (user_id, event_type, created_at DESC);
```
