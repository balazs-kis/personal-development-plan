## Introduction

B-tree indexes are PostgreSQL's default and most versatile index type. They work efficiently for equality and range queries, sorting, and min/max operations. Understanding B-tree fundamentals is essential because most of what you learn applies to other index types and helps you reason about query performance.

## Key Concepts Summary

### What is an Index?

An index is a separate data structure that allows fast lookups:

```sql
-- Without index: sequential scan (reads entire table)
SELECT * FROM users WHERE email = 'john@example.com';

-- Create index
CREATE INDEX idx_users_email ON users(email);

-- With index: index scan (fast lookup)
SELECT * FROM users WHERE email = 'john@example.com';
```

### B-tree Structure

B-trees store data in sorted order in a tree structure:
- **Root node**: Top of the tree
- **Branch nodes**: Navigation nodes
- **Leaf nodes**: Contain actual data pointers (CTIDs)

This structure provides O(log n) lookup time.

### Creating Indexes

```sql
-- Basic index creation
CREATE INDEX index_name ON table_name (column_name);

-- Index with specific name
CREATE INDEX idx_products_price ON products (price);

-- Unique index
CREATE UNIQUE INDEX idx_users_email ON users (email);

-- Index with specific method (usually automatic)
CREATE INDEX idx_products_price ON products USING btree (price);
```

### When Indexes Help

Indexes speed up queries with WHERE, ORDER BY, JOIN conditions:

```sql
-- Fast with index on user_id
SELECT * FROM orders WHERE user_id = 123;

-- Fast with index on created_at
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;

-- Fast with indexes on both foreign keys
SELECT o.*, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE u.email = 'john@example.com';
```

### When Indexes Don't Help

Indexes can't be used in certain situations:

```sql
-- 1. Functions on indexed column
-- BAD: Can't use index
SELECT * FROM users WHERE LOWER(email) = 'john@example.com';

-- GOOD: Can use index
SELECT * FROM users WHERE email = 'john@example.com';

-- 2. Leading wildcards in LIKE
-- BAD: Can't use index efficiently
SELECT * FROM products WHERE name LIKE '%phone%';

-- GOOD: Can use index
SELECT * FROM products WHERE name LIKE 'phone%';

-- 3. OR conditions on different columns
-- BAD: May not use indexes efficiently
SELECT * FROM users WHERE email = 'john@example.com' OR phone = '555-1234';

-- 4. NOT operators
-- Usually can't use index efficiently
SELECT * FROM orders WHERE status != 'shipped';
```

### Index Overhead

Indexes have costs:

```sql
-- Indexes slow down writes
INSERT INTO users (name, email) VALUES ('John', 'john@example.com');
-- Must update table AND all indexes on the table

UPDATE users SET email = 'new@example.com' WHERE id = 123;
-- Must update table AND email index

DELETE FROM users WHERE id = 123;
-- Must update table AND all indexes
```

**Trade-offs:**
- **Reads**: Faster (main benefit)
- **Writes**: Slower (INSERT, UPDATE, DELETE)
- **Storage**: More disk space required
- **Maintenance**: VACUUM must process indexes

### Selectivity and Index Effectiveness

Index effectiveness depends on selectivity (percentage of rows matched):

```sql
-- High selectivity: index very helpful
SELECT * FROM users WHERE email = 'unique@example.com';
-- Returns 1 row out of 1 million (0.0001%)

-- Low selectivity: index may not help
SELECT * FROM users WHERE country = 'USA';
-- Returns 800,000 rows out of 1 million (80%)

-- Very low selectivity: index probably won't be used
SELECT * FROM orders WHERE is_paid = true;
-- Returns 950,000 rows out of 1 million (95%)
```

PostgreSQL may choose a sequential scan over an index scan when selectivity is low.

### Covering Index Scans

B-tree leaf nodes store the indexed column value and a pointer to the table row:

```sql
-- Index-only scan possible
CREATE INDEX idx_users_email ON users (email);

SELECT email FROM users WHERE email LIKE 'john%';
-- Can satisfy query entirely from index (no table access)

-- Must access table
SELECT email, name FROM users WHERE email LIKE 'john%';
-- Index finds rows, then fetches name from table
```

### Monitoring Index Usage

```sql
-- Check if index is being used
SELECT schemaname, tablename, indexname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE indexname = 'idx_users_email';

-- Find unused indexes
SELECT schemaname, tablename, indexname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexname NOT LIKE 'pg_toast%'
ORDER BY pg_relation_size(indexrelid) DESC;
```

### Practical Example: E-commerce Orders

```sql
-- Frequently queried by user
CREATE INDEX idx_orders_user_id ON orders (user_id);

-- Frequently queried by status
CREATE INDEX idx_orders_status ON orders (status);

-- Frequently sorted by date
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);

-- Now these queries are fast:
SELECT * FROM orders WHERE user_id = 123;
SELECT * FROM orders WHERE status = 'pending';
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20;
```

### Common Mistakes

```sql
-- MISTAKE 1: Indexing every column
-- Don't do this! Only index columns used in WHERE, JOIN, ORDER BY

-- MISTAKE 2: Forgetting foreign keys
-- Always index foreign key columns
CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);

-- MISTAKE 3: Using functions in WHERE clause
-- BAD
WHERE DATE(created_at) = '2024-01-15'
-- GOOD
WHERE created_at >= '2024-01-15' AND created_at < '2024-01-16'

-- MISTAKE 4: Not monitoring index usage
-- Regularly check pg_stat_user_indexes for unused indexes
```
