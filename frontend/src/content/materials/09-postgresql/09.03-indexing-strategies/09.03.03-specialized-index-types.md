## Introduction

While B-tree indexes work for most scenarios, PostgreSQL provides specialized index types optimized for specific data types and query patterns. GIN indexes excel at searching within composite values like arrays and JSONB. GiST handles geometric data and full-text search. BRIN provides efficient indexing for massive tables. Understanding these options helps you optimize beyond what B-tree can offer.

## Key Concepts Summary

### GIN (Generalized Inverted Index)

GIN indexes are designed for indexing composite values where you need to search for elements:

**Best for:**
- Array columns
- JSONB data
- Full-text search (tsvector)
- Any data type that can be decomposed into elements

```sql
-- Index on array column
CREATE INDEX idx_tags_gin ON articles USING GIN (tags);

-- Query: find articles with specific tag
SELECT * FROM articles WHERE tags @> ARRAY['postgresql'];

-- Index on JSONB column
CREATE INDEX idx_metadata_gin ON products USING GIN (metadata);

-- Query: find products with specific JSONB attribute
SELECT * FROM products WHERE metadata @> '{"color": "red"}';

-- Full-text search index
CREATE INDEX idx_content_fts ON documents USING GIN (to_tsvector('english', content));

-- Query: full-text search
SELECT * FROM documents 
WHERE to_tsvector('english', content) @@ to_tsquery('postgresql & performance');
```

**GIN Characteristics:**
- **Large indexes**: Stores every element value with pointers to rows
- **Slow inserts**: Must update index for every element
- **Fast searches**: Very efficient for containment queries
- **No ordering**: Can't be used for ORDER BY

**GIN Index Size Optimization:**

```sql
-- Standard GIN index (larger, faster queries)
CREATE INDEX idx_tags_gin ON articles USING GIN (tags);

-- Compressed GIN index (smaller, slightly slower queries)
CREATE INDEX idx_tags_gin_fast ON articles USING GIN (tags)
WITH (fastupdate = off);
```

### GiST (Generalized Search Tree)

GiST is a balanced tree structure that supports various data types:

**Best for:**
- Geometric data (points, boxes, circles, polygons)
- Range types (int4range, tsrange, daterange)
- Full-text search (alternative to GIN)
- Nearest-neighbor searches

```sql
-- Geometric data index
CREATE INDEX idx_locations_gist ON stores USING GiST (location);

-- Query: find nearby stores (within 1000 meters)
SELECT * FROM stores 
WHERE ST_DWithin(location, ST_MakePoint(-73.935242, 40.730610), 1000);

-- Range type index
CREATE INDEX idx_booking_range ON bookings USING GiST (booking_period);

-- Query: find overlapping bookings
SELECT * FROM bookings 
WHERE booking_period && '[2024-01-15, 2024-01-20)'::daterange;

-- Full-text search with GiST
CREATE INDEX idx_content_gist ON documents USING GiST (to_tsvector('english', content));
```

**GiST vs GIN for Full-Text Search:**
- **GIN**: Larger index, faster queries, slower updates
- **GiST**: Smaller index, slower queries, faster updates
- Use GIN for mostly-read data, GiST for frequently updated data

**GiST Characteristics:**
- **Balanced tree**: Similar structure to B-tree
- **Lossy**: May have false positives (requires recheck)
- **Smaller than GIN**: More compact for certain data types
- **Supports nearest-neighbor**: Can find closest matches

### BRIN (Block Range Index)

BRIN indexes are extremely compact, storing min/max values for blocks of rows:

**Best for:**
- Very large tables (multi-GB)
- Naturally ordered data (timestamps, incrementing IDs)
- Data warehouse / analytics tables
- Append-only tables

```sql
-- BRIN index on timestamp column
CREATE INDEX idx_logs_time_brin ON logs USING BRIN (created_at);

-- Query: recent logs
SELECT * FROM logs 
WHERE created_at > CURRENT_DATE - INTERVAL '7 days';

-- BRIN with custom pages_per_range
CREATE INDEX idx_sales_date_brin ON sales USING BRIN (sale_date)
WITH (pages_per_range = 128);
```

**BRIN Characteristics:**
- **Tiny indexes**: Often 1000x smaller than B-tree
- **Fast inserts**: Minimal overhead
- **Good for sequential scans**: Skip blocks that can't match
- **Requires correlation**: Data must be physically ordered
- **Lossy**: Scans multiple blocks, filters in executor

**When BRIN Doesn't Work:**

```sql
-- BAD: Random data (no correlation)
-- BRIN won't help if user_id is randomly distributed
CREATE INDEX idx_orders_user_brin ON orders USING BRIN (user_id);

-- GOOD: Naturally ordered data
-- created_at is naturally ordered (newer records appended)
CREATE INDEX idx_orders_created_brin ON orders USING BRIN (created_at);
```

**Checking Data Correlation:**

```sql
-- Check if column is physically ordered
SELECT attname, correlation
FROM pg_stats
WHERE tablename = 'logs' AND attname = 'created_at';

-- correlation close to 1.0 or -1.0: BRIN will work well
-- correlation close to 0: BRIN won't help, use B-tree
```

### Hash Indexes

Hash indexes use hash functions for equality comparisons:

**Best for:**
- Equality comparisons only (`=`)
- When B-tree overhead is unnecessary
- Limited use cases (B-tree usually better)

```sql
-- Hash index (rarely needed)
CREATE INDEX idx_users_email_hash ON users USING HASH (email);

-- Can only be used for equality
SELECT * FROM users WHERE email = 'john@example.com';

-- Cannot be used for:
-- - Range queries (>, <, BETWEEN)
-- - Pattern matching (LIKE)
-- - Sorting (ORDER BY)
```

**Hash Index Characteristics:**
- **Equality only**: Only supports `=` operator
- **No ordering**: Can't use for ORDER BY
- **Smaller than B-tree**: Slightly more compact
- **Rarely recommended**: B-tree usually better choice
- **Not replicated**: Not included in streaming replication (prior to PG 10)

**When to Use Hash:**
- Almost never—B-tree handles equality just as well
- Possibly for very wide keys where hash is more compact
- PostgreSQL documentation recommends B-tree over Hash in most cases

### Comparison Table

| Index Type | Best For | Size | Insert Speed | Query Speed |
|------------|----------|------|--------------|-------------|
| B-tree | General purpose, ranges, sorting | Medium | Fast | Fast |
| GIN | Arrays, JSONB, full-text | Large | Slow | Very Fast |
| GiST | Geometric, ranges, spatial | Medium | Medium | Medium |
| BRIN | Huge tables, ordered data | Tiny | Very Fast | Medium |
| Hash | Equality only (rarely used) | Small | Fast | Fast |

### Practical Examples

#### Example 1: E-commerce Product Search

```sql
-- Products with tags array
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT,
    tags TEXT[],
    metadata JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);

-- GIN index for tags
CREATE INDEX idx_products_tags ON products USING GIN (tags);

-- GIN index for JSONB metadata
CREATE INDEX idx_products_metadata ON products USING GIN (metadata);

-- Queries
SELECT * FROM products WHERE tags @> ARRAY['electronics', 'laptop'];
SELECT * FROM products WHERE metadata @> '{"brand": "Apple"}';
```

#### Example 2: Logging System

```sql
-- Large logs table (append-only)
CREATE TABLE logs (
    id BIGSERIAL PRIMARY KEY,
    level TEXT,
    message TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);

-- BRIN index for timestamp (naturally ordered)
CREATE INDEX idx_logs_created ON logs USING BRIN (created_at);

-- B-tree for level (small cardinality, frequently queried)
CREATE INDEX idx_logs_level ON logs (level);

-- Queries
SELECT * FROM logs WHERE created_at > NOW() - INTERVAL '1 hour';
SELECT * FROM logs WHERE level = 'ERROR' AND created_at > NOW() - INTERVAL '1 day';
```

#### Example 3: Geospatial Application

```sql
-- Stores with location data
CREATE TABLE stores (
    id SERIAL PRIMARY KEY,
    name TEXT,
    location GEOMETRY(Point, 4326)
);

-- GiST index for spatial queries
CREATE INDEX idx_stores_location ON stores USING GiST (location);

-- Queries
-- Find stores within 5km of a point
SELECT name, ST_Distance(location, ST_MakePoint(-73.935242, 40.730610)) as distance
FROM stores
WHERE ST_DWithin(location, ST_MakePoint(-73.935242, 40.730610), 5000)
ORDER BY distance;
```
