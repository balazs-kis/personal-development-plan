## Introduction

Indexes require ongoing maintenance to remain effective. Over time, they can become bloated with dead tuples, degrading performance. Understanding when and how to maintain indexes—and how to identify indexes that aren't pulling their weight—is essential for production database health.

## Key Concepts Summary

### Understanding Index Bloat

Index bloat occurs when indexes accumulate dead tuples:

```sql
-- What causes bloat:
-- 1. UPDATE operations (create new row versions)
UPDATE users SET last_login = NOW() WHERE id = 123;
-- Old index entry marked dead, new entry added

-- 2. DELETE operations (mark rows as dead)
DELETE FROM orders WHERE created_at < '2020-01-01';
-- Index entries marked dead but not removed

-- 3. Failed transactions (leave dead tuples)
BEGIN;
INSERT INTO products VALUES (...);
ROLLBACK;
-- Index entry exists but points to aborted row
```

### VACUUM: Regular Maintenance

VACUUM removes dead tuples and updates statistics:

```sql
-- Vacuum a specific table
VACUUM orders;

-- Vacuum and analyze (recommended)
VACUUM ANALYZE orders;

-- Vacuum entire database
VACUUM;

-- Verbose output for monitoring
VACUUM VERBOSE orders;
```

**What VACUUM Does:**
- Marks dead tuple space as reusable
- Updates visibility map for index-only scans
- Updates statistics for query planner
- Prevents transaction ID wraparound

**What VACUUM Doesn't Do:**
- Doesn't return space to OS (space remains in file)
- Doesn't block normal operations (runs concurrently)
- Doesn't rebuild index structure

### VACUUM FULL: Aggressive Cleanup

VACUUM FULL reclaims space but locks the table:

```sql
-- Reclaim disk space (blocks writes!)
VACUUM FULL orders;

-- With analyze
VACUUM FULL ANALYZE orders;
```

**VACUUM FULL Characteristics:**
- Returns disk space to OS
- Rewrites entire table and indexes
- Requires exclusive lock (blocks all operations)
- Takes much longer than regular VACUUM
- Use rarely, typically for space reclamation

### REINDEX: Rebuilding Indexes

REINDEX rebuilds indexes from scratch:

```sql
-- Reindex a specific index
REINDEX INDEX idx_orders_user_id;

-- Reindex all indexes on a table
REINDEX TABLE orders;

-- Reindex concurrently (doesn't block writes)
REINDEX INDEX CONCURRENTLY idx_orders_user_id;

-- Reindex entire database (careful!)
REINDEX DATABASE mydb;
```

**When to REINDEX:**
1. Index is significantly bloated
2. After bulk data operations
3. Index corruption suspected
4. Changed storage parameters (e.g., fillfactor)

**REINDEX vs VACUUM:**
- **REINDEX**: Rebuilds index, removes all bloat, locks table
- **VACUUM**: Marks space reusable, doesn't lock, doesn't remove bloat completely

### REINDEX CONCURRENTLY

```sql
-- PostgreSQL 12+: Reindex without blocking writes
REINDEX INDEX CONCURRENTLY idx_orders_user_id;

-- Process:
-- 1. Creates new index alongside old one
-- 2. Builds new index while old one serves queries
-- 3. Swaps new index for old
-- 4. Drops old index

-- Trade-offs:
-- + No write blocking
-- + Can be cancelled safely
-- - Takes longer
-- - Requires more disk space temporarily
-- - Cannot be run in transaction block
```

### Monitoring Index Bloat

```sql
-- Estimate index bloat (approximate)
SELECT
    schemaname,
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) as index_size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;

-- Check table and index sizes
SELECT
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) as total_size,
    pg_size_pretty(pg_relation_size(schemaname||'.'||tablename)) as table_size,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename) - 
                   pg_relation_size(schemaname||'.'||tablename)) as index_size
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC;
```

### Finding Unused Indexes

```sql
-- Indexes that are never used
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    pg_size_pretty(pg_relation_size(indexrelid)) as index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
    AND indexname NOT LIKE '%_pkey'  -- Exclude primary keys
ORDER BY pg_relation_size(indexrelid) DESC;

-- Indexes with low usage relative to size
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    pg_size_pretty(pg_relation_size(indexrelid)) as index_size,
    pg_relation_size(indexrelid) / NULLIF(idx_scan, 0) as bytes_per_scan
FROM pg_stat_user_indexes
WHERE idx_scan < 100
    AND pg_relation_size(indexrelid) > 1000000  -- > 1MB
ORDER BY bytes_per_scan DESC NULLIF;
```

### Finding Duplicate Indexes

```sql
-- Indexes on the same columns
SELECT
    a.indexrelid::regclass as index1,
    b.indexrelid::regclass as index2,
    a.indrelid::regclass as table_name,
    a.indkey as columns
FROM pg_index a
JOIN pg_index b ON a.indrelid = b.indrelid
    AND a.indkey = b.indkey
    AND a.indexrelid > b.indexrelid
WHERE NOT a.indisprimary;
```

### Autovacuum Configuration

PostgreSQL's autovacuum runs automatically:

```sql
-- Check autovacuum settings
SHOW autovacuum;
SHOW autovacuum_vacuum_threshold;
SHOW autovacuum_vacuum_scale_factor;

-- Per-table autovacuum tuning
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.05,
    autovacuum_vacuum_threshold = 1000,
    autovacuum_analyze_scale_factor = 0.05
);

-- More aggressive for high-churn tables
ALTER TABLE logs SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 500
);
```

### Monitoring Autovacuum Activity

```sql
-- Last vacuum and analyze times
SELECT
    schemaname,
    tablename,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY last_autovacuum DESC NULLS LAST;

-- Tables that need vacuum
SELECT
    schemaname,
    tablename,
    n_dead_tup,
    n_live_tup,
    ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 2) as dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY dead_pct DESC;
```

### Index Maintenance Schedule

```sql
-- Weekly maintenance script
DO $$
DECLARE
    r RECORD;
BEGIN
    -- Vacuum analyze all tables
    FOR r IN 
        SELECT schemaname, tablename 
        FROM pg_tables 
        WHERE schemaname = 'public'
    LOOP
        EXECUTE 'VACUUM ANALYZE ' || quote_ident(r.schemaname) || '.' || quote_ident(r.tablename);
        RAISE NOTICE 'Vacuumed %', r.tablename;
    END LOOP;
END $$;
```

### Best Practices

#### 1. Regular Monitoring

```sql
-- Daily check: Find bloated indexes
-- Weekly check: Review unused indexes
-- Monthly check: Analyze index usage patterns
```

#### 2. Proactive Maintenance

```sql
-- After bulk operations
VACUUM ANALYZE orders;

-- After large deletes
REINDEX TABLE CONCURRENTLY orders;

-- During maintenance windows
VACUUM FULL ANALYZE historical_data;
```

#### 3. Index Lifecycle Management

```sql
-- Create index
CREATE INDEX CONCURRENTLY idx_new ON orders (status);

-- Monitor usage
-- (wait 1-2 weeks)

-- If unused, drop it
DROP INDEX CONCURRENTLY idx_new;
```

### Performance Impact

```sql
-- Check index cache hit ratio
SELECT
    'index cache hit rate' as metric,
    ROUND(
        sum(idx_blks_hit) * 100.0 / 
        NULLIF(sum(idx_blks_hit + idx_blks_read), 0),
        2
    ) as percentage
FROM pg_statio_user_indexes;

-- Good: > 99%
-- OK: 95-99%
-- Poor: < 95% (may need more memory or better indexes)
```

### Common Issues and Solutions

```sql
-- Issue 1: Index not being used
-- Check: Is it actually selective?
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending';
-- Solution: Check if sequential scan is actually faster

-- Issue 2: Slow writes
-- Check: Too many indexes?
SELECT count(*) FROM pg_indexes WHERE tablename = 'orders';
-- Solution: Remove unused indexes

-- Issue 3: Growing database size
-- Check: When was last vacuum?
SELECT last_autovacuum FROM pg_stat_user_tables WHERE tablename = 'orders';
-- Solution: Manual VACUUM or tune autovacuum

-- Issue 4: Index bloat after bulk update
-- Check: Index size vs table size
-- Solution: REINDEX CONCURRENTLY
```

### Practical Maintenance Workflow

```sql
-- 1. Identify problem indexes
SELECT indexname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan < 10 AND pg_relation_size(indexrelid) > 10000000;

-- 2. Check bloat estimates
-- (use pgstattuple extension)
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstatindex('idx_orders_user_id');

-- 3. Decide on action
-- If bloated: REINDEX CONCURRENTLY
-- If unused: DROP INDEX CONCURRENTLY
-- If needed but bloated: REINDEX CONCURRENTLY

-- 4. Execute maintenance
REINDEX INDEX CONCURRENTLY idx_orders_user_id;

-- 5. Monitor results
SELECT pg_size_pretty(pg_relation_size('idx_orders_user_id'));
```
