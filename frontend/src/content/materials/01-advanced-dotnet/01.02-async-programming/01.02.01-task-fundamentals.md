## Introduction

The Task-based Asynchronous Pattern (TAP) is the foundation of modern asynchronous programming in .NET. While `async` and `await` make asynchronous code look simple, understanding what happens beneath these keywords is crucial for writing high-performance, bug-free applications. This lesson explores the internals of async/await, including state machines, synchronization contexts, and best practices.

## Key Concepts Summary

### What Async/Await Does

When you write an async method, the C# compiler transforms it into a state machine:

```csharp
// What you write
public async Task<string> GetDataAsync()
{
    var client = new HttpClient();
    var response = await client.GetStringAsync("https://api.example.com");
    return response.ToUpper();
}

// What the compiler generates (simplified)
public Task<string> GetDataAsync()
{
    var stateMachine = new GetDataAsyncStateMachine
    {
        // captures local variables and this reference
    };
    stateMachine.MoveNext();
    return stateMachine.Task;
}
```

### The State Machine

Each `await` creates a state in the state machine:

```csharp
// State 0: Start of method
// State 1: After first await
// State 2: After second await
// State -1: Completed
// State -2: Faulted
```

**Key Characteristics:**
- Each async method becomes a struct implementing `IAsyncStateMachine`
- Local variables become fields on the state machine
- The state machine handles resumption after awaits
- Exceptions are captured and stored in the Task

### Task and Task<T>

**Task** represents an asynchronous operation that can be awaited:

```csharp
// Task - operation with no return value
public async Task DoWorkAsync()
{
    await Task.Delay(1000);
    Console.WriteLine("Work complete");
}

// Task<T> - operation that returns a value
public async Task<int> CalculateAsync()
{
    await Task.Delay(100);
    return 42;
}
```

**Task Properties:**
```csharp
Task<int> task = GetValueAsync();

// Status properties
bool isCompleted = task.IsCompleted;
bool isSuccess = task.IsCompletedSuccessfully;
bool isFaulted = task.IsFaulted;
bool isCanceled = task.IsCanceled;

// Result (blocks if not completed!)
int result = task.Result; // ⚠️ Don't use in async code

// Exception information
Exception? exception = task.Exception;
```

### Synchronization Context

The SynchronizationContext determines where code resumes after an await:

```csharp
// UI application (WPF/WinForms)
public async Task LoadDataAsync()
{
    // Running on UI thread
    var data = await GetDataAsync(); // Captures UI SynchronizationContext
    
    // After await, resumes on UI thread
    textBox.Text = data; // ✅ Safe - back on UI thread
}

// ASP.NET Core (no context by default in .NET Core+)
public async Task<IActionResult> Index()
{
    var data = await GetDataAsync(); // No context captured
    
    // Resumes on any thread pool thread
    return View(data); // ✅ Safe - ASP.NET Core is thread-safe
}
```

### ConfigureAwait: The Most Misunderstood Feature

`ConfigureAwait(false)` tells the awaiter not to capture the synchronization context:

```csharp
// Library method - use ConfigureAwait(false)
public async Task<string> FetchDataAsync()
{
    using var client = new HttpClient();
    
    // Don't need to resume on original context
    var response = await client.GetStringAsync(url)
        .ConfigureAwait(false);
    
    // Process data - doesn't need UI or request context
    return await ProcessDataAsync(response)
        .ConfigureAwait(false);
}

// UI method - DON'T use ConfigureAwait(false)
public async Task LoadDataAsync()
{
    var data = await FetchDataAsync(); // Let it default
    
    // Need to be on UI thread here
    textBox.Text = data; // Would crash if we used ConfigureAwait(false)
}
```

**Rules of Thumb:**
- ✅ Use `ConfigureAwait(false)` in library code
- ✅ Use `ConfigureAwait(false)` for I/O-bound operations that don't need context
- ❌ Never use `ConfigureAwait(false)` before updating UI
- ❌ Not needed in ASP.NET Core (no context by default)
- ⚠️ Apply to **every await**, not just the first one (it's not transitive)

### Common Patterns

#### 1. Simple Async Method
```csharp
public async Task<User> GetUserAsync(int id)
{
    using var connection = new SqlConnection(connectionString);
    await connection.OpenAsync();
    
    var command = new SqlCommand("SELECT * FROM Users WHERE Id = @Id", connection);
    command.Parameters.AddWithValue("@Id", id);
    
    using var reader = await command.ExecuteReaderAsync();
    if (await reader.ReadAsync())
    {
        return new User
        {
            Id = reader.GetInt32(0),
            Name = reader.GetString(1)
        };
    }
    
    throw new KeyNotFoundException($"User {id} not found");
}
```

#### 2. Multiple Concurrent Operations
```csharp
public async Task<Dashboard> GetDashboardDataAsync()
{
    // Start all operations concurrently
    var usersTask = GetUsersAsync();
    var ordersTask = GetOrdersAsync();
    var statsTask = GetStatsAsync();
    
    // Wait for all to complete
    await Task.WhenAll(usersTask, ordersTask, statsTask);
    
    // All results are now available
    return new Dashboard
    {
        Users = await usersTask,
        Orders = await ordersTask,
        Stats = await statsTask
    };
}
```

#### 3. Sequential Operations with Dependency
```csharp
public async Task<Order> ProcessOrderAsync(OrderRequest request)
{
    // Must happen sequentially
    var validatedRequest = await ValidateAsync(request);
    var inventory = await CheckInventoryAsync(validatedRequest.Items);
    var order = await CreateOrderAsync(validatedRequest, inventory);
    await SendConfirmationAsync(order);
    
    return order;
}
```

### Task.Run vs async/await

```csharp
// ❌ Don't use Task.Run for I/O operations
public Task<string> ReadFileAsync(string path)
{
    // This just moves I/O to thread pool unnecessarily
    return Task.Run(() => File.ReadAllText(path));
}

// ✅ Use async I/O methods directly
public async Task<string> ReadFileAsync(string path)
{
    return await File.ReadAllTextAsync(path);
}

// ✅ Use Task.Run for CPU-bound work in UI applications
public async Task ProcessDataAsync()
{
    var data = await LoadDataAsync(); // I/O
    
    // CPU-intensive work - run on thread pool
    var result = await Task.Run(() => ComplexCalculation(data));
    
    DisplayResult(result); // Back on UI thread
}
```

### Exception Handling

```csharp
public async Task<Result> TryProcessAsync()
{
    try
    {
        var data = await GetDataAsync();
        await ProcessAsync(data);
        return Result.Success();
    }
    catch (HttpRequestException ex)
    {
        logger.LogError(ex, "Network error occurred");
        return Result.Failure("Network error");
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Unexpected error");
        throw; // Re-throw unexpected errors
    }
}
```

### Best Practices

1. **Return Task directly when possible**
   ```csharp
   // ❌ Unnecessary async/await
   public async Task<User> GetUserAsync(int id)
   {
       return await repository.GetUserAsync(id);
   }
   
   // ✅ Return Task directly
   public Task<User> GetUserAsync(int id)
   {
       return repository.GetUserAsync(id);
   }
   ```

2. **Use async all the way down**
   ```csharp
   // ❌ Mixing sync and async
   public void LoadData()
   {
       var data = GetDataAsync().Result; // Deadlock risk!
   }
   
   // ✅ Async all the way
   public async Task LoadDataAsync()
   {
       var data = await GetDataAsync();
   }
   ```

3. **Avoid async void except for event handlers**
   ```csharp
   // ❌ Can't await, can't catch exceptions
   public async void ProcessData()
   {
       await DoWorkAsync();
   }
   
   // ✅ Return Task
   public async Task ProcessDataAsync()
   {
       await DoWorkAsync();
   }
   
   // ✅ Event handler - only acceptable use of async void
   private async void Button_Click(object sender, EventArgs e)
   {
       await ProcessDataAsync();
   }
   ```
