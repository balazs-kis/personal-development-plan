## Introduction

Schema migrations are changes to database structure deployed to production. Unlike code, databases contain valuable stateful data that must be preserved during changes. Proper migration strategies enable continuous delivery, minimize downtime, and reduce risk. This lesson covers patterns for safely evolving database schemas in production environments.

## Key Concepts Summary

### Principles of Evolutionary Database Design

1. **All database changes are migrations**
   - No manual SQL in production
   - Version controlled
   - Tested before deployment

2. **Continuous integration of database changes**
   - Automated testing with CI/CD
   - Database changes integrated with application code

3. **Everyone can update the database schema**
   - Developers have local database instances
   - Clear migration creation process

4. **Separate database refactoring from code refactoring**
   - Database changes can span multiple releases
   - Maintain backward compatibility

5. **Automate database migrations**
   - Use migration tools
   - Run migrations in deployment pipeline

## Migration Strategies

### Strategy 1: Expand-Contract Pattern

**Safest approach for production systems**

**Three phases:**
1. **Expand:** Add new structure alongside old
2. **Migrate:** Dual-write to both old and new
3. **Contract:** Remove old structure

**Example: Splitting a Column**

```sql
-- Current state: single 'name' column
CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL
);

-- Phase 1: EXPAND - Add new columns
ALTER TABLE users
ADD COLUMN first_name TEXT,
ADD COLUMN last_name TEXT;

-- Backfill existing data
UPDATE users
SET 
    first_name = SPLIT_PART(name, ' ', 1),
    last_name = SPLIT_PART(name, ' ', 2)
WHERE first_name IS NULL;

-- Phase 2: MIGRATE - Application writes to both
-- Application code updated to:
-- - Write to name, first_name, last_name
-- - Read from first_name/last_name with fallback to name

-- Trigger for consistency during transition
CREATE OR REPLACE FUNCTION sync_name_fields()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.first_name IS NOT NULL AND NEW.last_name IS NOT NULL THEN
        NEW.name := NEW.first_name || ' ' || NEW.last_name;
    ELSIF NEW.name IS NOT NULL THEN
        NEW.first_name := SPLIT_PART(NEW.name, ' ', 1);
        NEW.last_name := SPLIT_PART(NEW.name, ' ', 2);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER sync_name_fields_trigger
BEFORE INSERT OR UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION sync_name_fields();

-- Phase 3: CONTRACT - Remove old column
-- After all applications updated to use new columns
ALTER TABLE users DROP COLUMN name;
DROP TRIGGER sync_name_fields_trigger ON users;
DROP FUNCTION sync_name_fields();

-- Add NOT NULL constraints
ALTER TABLE users 
ALTER COLUMN first_name SET NOT NULL,
ALTER COLUMN last_name SET NOT NULL;
```

### Strategy 2: Zero-Downtime Deployments

**Key principles:**
- Avoid table locks on large tables
- Make changes backward compatible
- Deploy schema changes before code changes

**Safe Operations (no locks):**
```sql
-- Add nullable column (fast, no lock)
ALTER TABLE users ADD COLUMN phone TEXT;

-- Add column with default (PostgreSQL 11+, no rewrite)
ALTER TABLE users ADD COLUMN status TEXT DEFAULT 'active';

-- Create index concurrently (no lock)
CREATE INDEX CONCURRENTLY users_email_idx ON users (email);

-- Add constraint as NOT VALID, then validate
ALTER TABLE users 
ADD CONSTRAINT users_email_check 
CHECK (email LIKE '%@%') NOT VALID;

VALIDATE CONSTRAINT users_email_check;
```

**Unsafe Operations (locks):**
```sql
-- Add NOT NULL column with default (blocks writes)
ALTER TABLE large_table ADD COLUMN required_field TEXT NOT NULL DEFAULT 'default';
-- Solution: Add nullable first, backfill, then add NOT NULL

-- Drop column (takes lock)
ALTER TABLE large_table DROP COLUMN old_column;
-- Solution: Stop using column first, drop later during maintenance

-- Change column type (rewrites table)
ALTER TABLE large_table ALTER COLUMN id TYPE BIGINT;
-- Solution: Use expand-contract pattern
```

### Strategy 3: Blue-Green Database Migrations

**For major schema changes:**

```sql
-- Phase 1: Create new schema version
CREATE SCHEMA app_v2;

-- Copy and transform tables to new schema
CREATE TABLE app_v2.users AS
SELECT 
    user_id,
    SPLIT_PART(name, ' ', 1) AS first_name,
    SPLIT_PART(name, ' ', 2) AS last_name,
    email
FROM public.users;

-- Phase 2: Sync changes during transition
-- Use triggers or application logic to keep schemas in sync

-- Phase 3: Switch application to new schema
-- Update connection strings to use app_v2

-- Phase 4: Drop old schema
DROP SCHEMA public CASCADE;
ALTER SCHEMA app_v2 RENAME TO public;
```

## Migration Tools and Patterns

### File-Based Migrations

**Pattern:** Each migration is a numbered SQL file.

```bash
migrations/
├── 001_create_users_table.sql
├── 002_add_email_to_users.sql
├── 003_create_orders_table.sql
└── 004_add_user_status.sql
```

**Migration tracking table:**
```sql
CREATE TABLE schema_migrations (
    version BIGINT PRIMARY KEY,
    applied_at TIMESTAMP DEFAULT NOW()
);
```

**Example migration runner (pseudocode):**
```sql
-- Check which migrations are applied
SELECT version FROM schema_migrations;

-- Apply pending migrations
BEGIN;
    -- Run migration SQL
    \i migrations/005_new_migration.sql
    
    -- Record migration
    INSERT INTO schema_migrations (version) VALUES (5);
COMMIT;
```

### Popular Migration Tools

#### 1. Flyway
```bash
# Java-based migration tool
flyway migrate

# Migration file format: V1__Description.sql
# migrations/V1__Create_users_table.sql
```

#### 2. Liquibase
```xml
<!-- XML-based changesets -->
<changeSet id="1" author="dev">
    <createTable tableName="users">
        <column name="user_id" type="int" autoIncrement="true">
            <constraints primaryKey="true"/>
        </column>
        <column name="username" type="varchar(50)">
            <constraints nullable="false"/>
        </column>
    </createTable>
</changeSet>
```

#### 3. pgmigrate
```bash
# Simple Python-based tool
pgmigrate migrate

# Uses numbered .sql files
```

#### 4. Alembic (Python/SQLAlchemy)
```python
# Revision: 001
# Revises: None
def upgrade():
    op.create_table(
        'users',
        sa.Column('user_id', sa.Integer(), primary_key=True),
        sa.Column('username', sa.String(50), nullable=False)
    )

def downgrade():
    op.drop_table('users')
```

## Safe Migration Patterns

### Pattern 1: Adding Columns Safely

```sql
-- Step 1: Add nullable column (fast)
ALTER TABLE users ADD COLUMN middle_name TEXT;

-- Step 2: Backfill in batches to avoid long transactions
DO $$
DECLARE
    batch_size INT := 1000;
    rows_updated INT;
BEGIN
    LOOP
        UPDATE users
        SET middle_name = COALESCE(middle_name, '')
        WHERE user_id IN (
            SELECT user_id
            FROM users
            WHERE middle_name IS NULL
            LIMIT batch_size
        );
        
        GET DIAGNOSTICS rows_updated = ROW_COUNT;
        EXIT WHEN rows_updated = 0;
        
        -- Small delay between batches
        PERFORM pg_sleep(0.1);
    END LOOP;
END $$;

-- Step 3: Add NOT NULL constraint (after backfill complete)
ALTER TABLE users ALTER COLUMN middle_name SET NOT NULL;
```

### Pattern 2: Renaming Columns

```sql
-- DON'T DO THIS (breaks existing queries):
-- ALTER TABLE users RENAME COLUMN name TO full_name;

-- DO THIS (expand-contract):

-- Step 1: Add new column
ALTER TABLE users ADD COLUMN full_name TEXT;

-- Step 2: Backfill and sync
UPDATE users SET full_name = name WHERE full_name IS NULL;

CREATE OR REPLACE FUNCTION sync_name_columns()
RETURNS TRIGGER AS $$
BEGIN
    NEW.full_name := COALESCE(NEW.full_name, NEW.name);
    NEW.name := COALESCE(NEW.name, NEW.full_name);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER sync_name_trigger
BEFORE INSERT OR UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION sync_name_columns();

-- Step 3: Update application to use full_name

-- Step 4: Remove old column (later)
DROP TRIGGER sync_name_trigger ON users;
DROP FUNCTION sync_name_columns();
ALTER TABLE users DROP COLUMN name;
```

### Pattern 3: Changing Column Types

```sql
-- DON'T DO THIS (locks table, rewrites data):
-- ALTER TABLE orders ALTER COLUMN order_id TYPE BIGINT;

-- DO THIS (expand-contract with new column):

-- Step 1: Add new column
ALTER TABLE orders ADD COLUMN order_id_new BIGINT;

-- Step 2: Backfill in batches
UPDATE orders
SET order_id_new = order_id::BIGINT
WHERE order_id_new IS NULL;

-- Step 3: Create indexes on new column
CREATE INDEX CONCURRENTLY orders_order_id_new_idx 
    ON orders (order_id_new);

-- Step 4: Swap columns (during maintenance window)
BEGIN;
    ALTER TABLE orders DROP CONSTRAINT orders_pkey;
    ALTER TABLE orders DROP COLUMN order_id;
    ALTER TABLE orders RENAME COLUMN order_id_new TO order_id;
    ALTER TABLE orders ADD PRIMARY KEY (order_id);
COMMIT;
```

### Pattern 4: Adding Indexes Without Blocking

```sql
-- Bad: Blocks writes during index creation
-- CREATE INDEX users_email_idx ON users (email);

-- Good: Doesn't block writes
CREATE INDEX CONCURRENTLY users_email_idx ON users (email);

-- If creation fails, clean up invalid index
DROP INDEX CONCURRENTLY IF EXISTS users_email_idx;
-- Then retry

-- Note: Cannot run CREATE INDEX CONCURRENTLY inside transaction
```

### Pattern 5: Adding Foreign Keys Safely

```sql
-- Bad: Validates immediately, can take a long time
-- ALTER TABLE orders 
-- ADD CONSTRAINT orders_customer_fk 
-- FOREIGN KEY (customer_id) REFERENCES customers(customer_id);

-- Good: Add as NOT VALID first, then validate separately
ALTER TABLE orders
ADD CONSTRAINT orders_customer_fk
FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
NOT VALID;

-- Validate separately (can be interrupted and restarted)
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;
```

## Handling Failures and Rollbacks

### Transaction Boundaries

```sql
-- Wrap migrations in transactions where possible
BEGIN;
    CREATE TABLE new_table (...);
    CREATE INDEX ...;
    INSERT INTO schema_migrations (version) VALUES (5);
COMMIT;

-- Some operations cannot be in transactions:
-- - CREATE INDEX CONCURRENTLY
-- - ALTER TABLE ... ADD CONSTRAINT ... NOT VALID
-- Use separate migrations for these
```

### Rollback Strategies

```sql
-- Option 1: Down migrations (risky)
-- migrations/001_up.sql
CREATE TABLE users (...);

-- migrations/001_down.sql
DROP TABLE users;

-- Option 2: Forward-only migrations (safer)
-- Never roll back, only roll forward with fixes
-- migrations/002_fix_users_table.sql
ALTER TABLE users ADD COLUMN missing_field TEXT;
```

### Testing Migrations

```bash
# Test migrations on production copy
pg_dump production_db > backup.sql
createdb test_db
psql test_db < backup.sql

# Run migrations on test database
flyway migrate -url=jdbc:postgresql://localhost/test_db

# Verify data integrity
psql test_db -c "SELECT COUNT(*) FROM users"

# Test application against migrated schema
```

## Practical Examples

### Example 1: Complete Migration Workflow

```sql
-- File: migrations/V20240127__split_user_name.sql
-- Description: Split users.name into first_name and last_name

-- Step 1: Add new columns
ALTER TABLE users 
ADD COLUMN IF NOT EXISTS first_name TEXT,
ADD COLUMN IF NOT EXISTS last_name TEXT;

-- Step 2: Backfill existing data
UPDATE users
SET 
    first_name = SPLIT_PART(name, ' ', 1),
    last_name = CASE 
        WHEN name LIKE '% %' THEN SUBSTRING(name FROM POSITION(' ' IN name) + 1)
        ELSE ''
    END
WHERE first_name IS NULL;

-- Step 3: Create sync trigger for transition period
CREATE OR REPLACE FUNCTION maintain_name_consistency()
RETURNS TRIGGER AS $$
BEGIN
    -- Keep fields in sync during transition
    IF NEW.first_name IS NOT NULL AND NEW.last_name IS NOT NULL THEN
        NEW.name := NEW.first_name || ' ' || NEW.last_name;
    ELSIF NEW.name IS NOT NULL AND (NEW.first_name IS NULL OR NEW.last_name IS NULL) THEN
        NEW.first_name := SPLIT_PART(NEW.name, ' ', 1);
        NEW.last_name := CASE 
            WHEN NEW.name LIKE '% %' THEN SUBSTRING(NEW.name FROM POSITION(' ' IN NEW.name) + 1)
            ELSE ''
        END;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS maintain_name_consistency_trigger ON users;
CREATE TRIGGER maintain_name_consistency_trigger
BEFORE INSERT OR UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION maintain_name_consistency();

-- Step 4: Add indexes (concurrently, in separate transaction)
-- Run separately: CREATE INDEX CONCURRENTLY users_first_name_idx ON users (first_name);

-- Migration tracking
INSERT INTO schema_migrations (version, description)
VALUES (20240127, 'Split users.name into first_name and last_name')
ON CONFLICT DO NOTHING;
```

```sql
-- File: migrations/V20240201__remove_old_name_column.sql
-- Description: Complete name column migration (run after application updated)

-- Remove sync trigger
DROP TRIGGER IF EXISTS maintain_name_consistency_trigger ON users;
DROP FUNCTION IF EXISTS maintain_name_consistency();

-- Add NOT NULL constraints
ALTER TABLE users 
ALTER COLUMN first_name SET NOT NULL,
ALTER COLUMN last_name SET NOT NULL;

-- Drop old column
ALTER TABLE users DROP COLUMN IF EXISTS name;

-- Migration tracking
INSERT INTO schema_migrations (version, description)
VALUES (20240201, 'Remove old users.name column')
ON CONFLICT DO NOTHING;
```

## Best Practices Checklist

### Before Migration

- [ ] Test on production-like data volume
- [ ] Review execution plan (EXPLAIN)
- [ ] Estimate downtime/lock duration
- [ ] Have rollback plan
- [ ] Schedule during low-traffic period
- [ ] Backup database
- [ ] Communicate with team

### During Migration

- [ ] Monitor active queries (pg_stat_activity)
- [ ] Watch for locks (pg_locks)
- [ ] Monitor application errors
- [ ] Be ready to cancel if needed
- [ ] Log migration execution time

### After Migration

- [ ] Verify data integrity
- [ ] Run ANALYZE on modified tables
- [ ] Monitor application performance
- [ ] Check for missing indexes
- [ ] Update statistics
- [ ] Document any issues

## Common Pitfalls

### 1. Long-Running Transactions

```sql
-- Bad: Single transaction for large backfill
BEGIN;
    UPDATE large_table SET new_column = expensive_calculation(old_column);
COMMIT;

-- Good: Batch updates
DO $$
DECLARE
    batch_size INT := 1000;
BEGIN
    LOOP
        UPDATE large_table
        SET new_column = expensive_calculation(old_column)
        WHERE id IN (
            SELECT id FROM large_table
            WHERE new_column IS NULL
            LIMIT batch_size
        );
        EXIT WHEN NOT FOUND;
        PERFORM pg_sleep(0.1);
    END LOOP;
END $$;
```

### 2. Breaking Backward Compatibility

```sql
-- Bad: Deploy schema change and code at same time
ALTER TABLE orders DROP COLUMN old_status;
-- Old application version crashes

-- Good: Three-step deployment
-- 1. Deploy code that doesn't use old_status
-- 2. Verify old code is fully replaced
-- 3. Drop column in separate deployment
```

### 3. Missing Index After Migration

```sql
-- Always add indexes when adding foreign keys
ALTER TABLE orders 
ADD COLUMN customer_id INT REFERENCES customers(customer_id);

-- Don't forget the index!
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
```

## Key Takeaways

- All database changes should be version-controlled migrations
- Use expand-contract pattern for safe production changes
- Avoid table locks on large tables (use CONCURRENTLY)
- Test migrations on production-like data
- Add constraints as NOT VALID, then validate separately
- Batch large data updates to avoid long transactions
- Deploy schema changes before code changes for backward compatibility
- Use migration tools (Flyway, Liquibase, etc.) for consistency
- Always have a rollback plan
- Monitor migrations in production
- Keep migrations forward-only when possible
- Document migration decisions and lessons learned
