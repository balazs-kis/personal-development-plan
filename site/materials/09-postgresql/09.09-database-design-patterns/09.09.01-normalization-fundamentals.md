## Introduction

Database normalization is a systematic process of organizing data to minimize redundancy and dependency. It divides large tables into smaller, related tables and defines relationships between them. Normalization improves data integrity, reduces storage requirements, and makes databases easier to maintain. Understanding normalization forms is fundamental to designing robust database schemas.

## Key Concepts Summary

### What is Normalization?

**Definition:** Normalization is the process of organizing data in a database to reduce redundancy and improve data integrity.

**Goals:**
- Eliminate data redundancy (duplicate data)
- Ensure data dependencies make sense
- Reduce update, insert, and delete anomalies
- Make the database more maintainable and flexible

**Anomalies that normalization prevents:**

1. **Update Anomaly:** Same information stored in multiple places requiring multiple updates
2. **Insert Anomaly:** Unable to add data without adding unrelated data
3. **Delete Anomaly:** Deleting data unintentionally removes other important data

## First Normal Form (1NF)

### Rules

A table is in 1NF if:
1. Each cell contains only atomic (indivisible) values
2. Each row is unique (has a primary key)
3. Each column contains values of the same type
4. The order of rows and columns doesn't matter

### Example: Converting to 1NF

**Unnormalized table (violates 1NF):**

```sql
-- Students table (NOT in 1NF)
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name TEXT,
    courses TEXT  -- Multiple courses in one cell!
);

INSERT INTO students VALUES
    (1, 'Alice', 'Math, Physics, Chemistry'),
    (2, 'Bob', 'English, History');

-- Problem: courses column contains multiple values
```

**Converted to 1NF:**

```sql
-- Students table (1NF)
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name TEXT
);

-- Student_Courses table (1NF)
CREATE TABLE student_courses (
    student_id INT,
    course TEXT,
    PRIMARY KEY (student_id, course),
    FOREIGN KEY (student_id) REFERENCES students(student_id)
);

INSERT INTO students VALUES
    (1, 'Alice'),
    (2, 'Bob');

INSERT INTO student_courses VALUES
    (1, 'Math'),
    (1, 'Physics'),
    (1, 'Chemistry'),
    (2, 'English'),
    (2, 'History');

-- Now each cell contains atomic values
```

### Common 1NF Violations

```sql
-- Violation 1: Multiple values in one cell
CREATE TABLE orders (
    order_id INT,
    products TEXT  -- 'Product1, Product2, Product3'
);

-- Violation 2: Repeating columns
CREATE TABLE survey (
    response_id INT,
    question1 TEXT,
    question2 TEXT,
    question3 TEXT,
    -- ... question20 TEXT
);

-- Violation 3: Mixed data types
CREATE TABLE inventory (
    product_id INT,
    description TEXT  -- Sometimes contains quantities like '100 units'
);
```

## Second Normal Form (2NF)

### Rules

A table is in 2NF if:
1. It is in 1NF
2. All non-key attributes are fully dependent on the entire primary key (no partial dependencies)

**Note:** 2NF only applies to tables with composite primary keys.

### Understanding Partial Dependency

**Partial dependency** occurs when a non-key column depends on only part of a composite primary key.

### Example: Converting to 2NF

**Table in 1NF but not 2NF:**

```sql
-- Order_Items table (1NF but NOT 2NF)
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    product_name TEXT,      -- Depends only on product_id
    product_price DECIMAL,  -- Depends only on product_id
    PRIMARY KEY (order_id, product_id)
);

-- Problem: product_name and product_price depend only on product_id,
-- not on the full composite key (order_id, product_id)
```

**Converted to 2NF:**

```sql
-- Products table (2NF)
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name TEXT,
    product_price DECIMAL
);

-- Order_Items table (2NF)
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);

-- Now all non-key attributes depend on the entire primary key
```

### Why 2NF Matters

**Without 2NF:**
- Product information duplicated across multiple orders
- Updating product name requires updating all order_items rows
- Deleting all orders for a product loses product information

**With 2NF:**
- Product information stored once
- Updates happen in one place
- Product information persists independently

## Third Normal Form (3NF)

### Rules

A table is in 3NF if:
1. It is in 2NF
2. No transitive dependencies exist (non-key attributes depend only on the primary key, not on other non-key attributes)

### Understanding Transitive Dependency

**Transitive dependency:** When column A depends on column B, and column B depends on the primary key.

Primary Key → Column B → Column A (transitive dependency)

### Example: Converting to 3NF

**Table in 2NF but not 3NF:**

```sql
-- Employees table (2NF but NOT 3NF)
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name TEXT,
    department_id INT,
    department_name TEXT,    -- Depends on department_id
    department_location TEXT -- Depends on department_id
);

-- Problem: department_name and department_location depend on department_id,
-- which depends on employee_id (transitive dependency)
```

**Converted to 3NF:**

```sql
-- Departments table (3NF)
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name TEXT,
    department_location TEXT
);

-- Employees table (3NF)
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name TEXT,
    department_id INT,
    FOREIGN KEY (department_id) REFERENCES departments(department_id)
);

-- Now all non-key attributes depend directly on the primary key
```

### Why 3NF Matters

**Without 3NF:**
- Department information duplicated for each employee
- Changing department location requires updating all employees in that department
- Deleting all employees from a department loses department information

**With 3NF:**
- Department information stored once
- Updates affect one row
- Departments can exist without employees

## Boyce-Codd Normal Form (BCNF)

### Rules

A table is in BCNF if:
1. It is in 3NF
2. For every functional dependency (A → B), A must be a superkey

**BCNF is a stronger version of 3NF** that handles certain anomalies 3NF doesn't address.

### When 3NF isn't enough

```sql
-- Course_Instructor table (3NF but NOT BCNF)
CREATE TABLE course_instructor (
    course_id INT,
    instructor_id INT,
    instructor_specialty TEXT,
    PRIMARY KEY (course_id, instructor_id)
);

-- Functional dependencies:
-- instructor_id → instructor_specialty
-- course_id, instructor_id → (everything)

-- Problem: instructor_specialty depends on instructor_id,
-- but instructor_id is not a superkey
```

**Converted to BCNF:**

```sql
-- Instructors table (BCNF)
CREATE TABLE instructors (
    instructor_id INT PRIMARY KEY,
    instructor_specialty TEXT
);

-- Course_Instructor table (BCNF)
CREATE TABLE course_instructor (
    course_id INT,
    instructor_id INT,
    PRIMARY KEY (course_id, instructor_id),
    FOREIGN KEY (instructor_id) REFERENCES instructors(instructor_id)
);
```

## Practical Examples

### Example 1: Student Registration System

**Unnormalized:**

```sql
-- Unnormalized student_registrations
CREATE TABLE student_registrations (
    registration_id INT PRIMARY KEY,
    student_name TEXT,
    student_email TEXT,
    courses TEXT,  -- 'CS101, MATH201, PHYS101'
    instructors TEXT  -- 'Dr. Smith, Dr. Jones, Dr. Wilson'
);
```

**Normalized to 3NF:**

```sql
-- Students table
CREATE TABLE students (
    student_id SERIAL PRIMARY KEY,
    student_name TEXT NOT NULL,
    student_email TEXT UNIQUE NOT NULL
);

-- Courses table
CREATE TABLE courses (
    course_id TEXT PRIMARY KEY,
    course_name TEXT NOT NULL,
    instructor_id INT,
    FOREIGN KEY (instructor_id) REFERENCES instructors(instructor_id)
);

-- Instructors table
CREATE TABLE instructors (
    instructor_id SERIAL PRIMARY KEY,
    instructor_name TEXT NOT NULL
);

-- Registrations table (junction table)
CREATE TABLE registrations (
    registration_id SERIAL PRIMARY KEY,
    student_id INT NOT NULL,
    course_id TEXT NOT NULL,
    registration_date DATE DEFAULT CURRENT_DATE,
    FOREIGN KEY (student_id) REFERENCES students(student_id),
    FOREIGN KEY (course_id) REFERENCES courses(course_id),
    UNIQUE (student_id, course_id)
);
```

### Example 2: E-commerce Order System

**Unnormalized:**

```sql
CREATE TABLE orders_unnormalized (
    order_id INT PRIMARY KEY,
    customer_name TEXT,
    customer_email TEXT,
    customer_address TEXT,
    customer_city TEXT,
    customer_state TEXT,
    customer_zip TEXT,
    product_names TEXT,  -- 'Product1, Product2'
    product_prices TEXT, -- '19.99, 29.99'
    quantities TEXT      -- '2, 1'
);
```

**Normalized to 3NF:**

```sql
-- Customers table
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    customer_name TEXT NOT NULL,
    customer_email TEXT UNIQUE NOT NULL
);

-- Addresses table
CREATE TABLE addresses (
    address_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL,
    street_address TEXT,
    city TEXT,
    state TEXT,
    zip_code TEXT,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- Products table
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,
    product_name TEXT NOT NULL,
    product_price DECIMAL(10,2) NOT NULL
);

-- Orders table
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date TIMESTAMP DEFAULT NOW(),
    shipping_address_id INT,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id),
    FOREIGN KEY (shipping_address_id) REFERENCES addresses(address_id)
);

-- Order_Items table
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id) REFERENCES orders(order_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

## Normalization Process Workflow

### Step-by-Step Approach

1. **Start with requirements**
   - Gather all data fields needed
   - Identify entities and relationships

2. **Create initial table**
   - Put all fields in one table
   - Identify potential primary key

3. **Apply 1NF**
   - Remove repeating groups
   - Ensure atomic values
   - Create junction tables for many-to-many relationships

4. **Apply 2NF**
   - Identify partial dependencies
   - Split into separate tables
   - Create foreign keys

5. **Apply 3NF**
   - Identify transitive dependencies
   - Create additional tables
   - Establish proper relationships

6. **Check for BCNF (if necessary)**
   - Verify all dependencies have superkeys as determinants
   - Decompose further if needed

## Benefits of Normalization

### Advantages

✅ **Reduced Redundancy**
- Less duplicate data
- Smaller database size
- More efficient storage

✅ **Improved Data Integrity**
- Updates happen in one place
- Consistency guaranteed by foreign keys
- Anomalies eliminated

✅ **Easier Maintenance**
- Schema changes affect fewer tables
- Clear data relationships
- Better organized structure

✅ **Query Flexibility**
- Can query related data efficiently
- Join tables as needed
- Support complex queries

### Disadvantages

❌ **More Complex Queries**
- Require joins to retrieve related data
- May need multiple table access
- More complex SQL

❌ **Potential Performance Impact**
- Joins can be expensive
- More tables to query
- May need denormalization for specific use cases

❌ **Initial Design Complexity**
- Takes more time to design
- Requires understanding of relationships
- May need iterative refinement

---

## When to Normalize

### Good Candidates for Normalization

✅ **OLTP Systems (Online Transaction Processing)**
- Frequent inserts, updates, deletes
- Data integrity is critical
- Many concurrent users

✅ **Source of Truth Databases**
- Operational databases
- Master data management
- Systems requiring data consistency

✅ **Applications with Evolving Schemas**
- Adding new features frequently
- Changing business requirements
- Need for flexibility

### When to Consider Alternatives

⚠️ **Read-Heavy Analytics (OLAP)**
- Reporting and dashboards
- Data warehouses
- Historical analysis

⚠️ **Performance-Critical Queries**
- Specific queries needing sub-second response
- Real-time dashboards
- High-traffic read operations

## Practice Exercise

Normalize an unnormalized library system:

1. Start with this unnormalized table
2. Apply 1NF, 2NF, and 3NF
3. Create appropriate indexes
4. Write queries to verify functionality

**Unnormalized table:**

```sql
CREATE TABLE library_unnormalized (
    record_id INT PRIMARY KEY,
    member_name TEXT,
    member_email TEXT,
    member_phone TEXT,
    book_titles TEXT,  -- 'Book1, Book2, Book3'
    book_authors TEXT, -- 'Author1, Author2, Author3'
    book_isbns TEXT,   -- 'ISBN1, ISBN2, ISBN3'
    checkout_dates TEXT, -- '2024-01-01, 2024-01-05, 2024-01-10'
    due_dates TEXT     -- '2024-01-15, 2024-01-19, 2024-01-24'
);
```

**Example solution:**

```sql
-- 1NF: Members table
CREATE TABLE members (
    member_id SERIAL PRIMARY KEY,
    member_name TEXT NOT NULL,
    member_email TEXT UNIQUE NOT NULL,
    member_phone TEXT
);

-- 1NF: Books table
CREATE TABLE books (
    isbn TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    author TEXT NOT NULL
);

-- 1NF: Checkouts table
CREATE TABLE checkouts (
    checkout_id SERIAL PRIMARY KEY,
    member_id INT NOT NULL,
    isbn TEXT NOT NULL,
    checkout_date DATE NOT NULL DEFAULT CURRENT_DATE,
    due_date DATE NOT NULL,
    return_date DATE,
    FOREIGN KEY (member_id) REFERENCES members(member_id),
    FOREIGN KEY (isbn) REFERENCES books(isbn)
);

-- Create indexes for common queries
CREATE INDEX checkouts_member_id_idx ON checkouts(member_id);
CREATE INDEX checkouts_isbn_idx ON checkouts(isbn);
CREATE INDEX checkouts_due_date_idx ON checkouts(due_date);

-- Query: Find overdue books
SELECT 
    m.member_name,
    b.title,
    c.due_date,
    CURRENT_DATE - c.due_date AS days_overdue
FROM checkouts c
JOIN members m ON c.member_id = m.member_id
JOIN books b ON c.isbn = b.isbn
WHERE c.return_date IS NULL
  AND c.due_date < CURRENT_DATE
ORDER BY days_overdue DESC;

-- Query: Member's checkout history
SELECT 
    b.title,
    b.author,
    c.checkout_date,
    c.return_date,
    CASE 
        WHEN c.return_date IS NULL THEN 'Checked Out'
        ELSE 'Returned'
    END AS status
FROM checkouts c
JOIN books b ON c.isbn = b.isbn
WHERE c.member_id = 1
ORDER BY c.checkout_date DESC;
```

## Key Takeaways

- Normalization organizes data to eliminate redundancy and anomalies
- **1NF**: Atomic values, unique rows, no repeating groups
- **2NF**: 1NF + no partial dependencies (applies to composite keys)
- **3NF**: 2NF + no transitive dependencies
- **BCNF**: 3NF + every functional dependency has a superkey as determinant
- Normalization improves data integrity and maintainability
- Higher normal forms require more joins, which may impact query performance
- Normalize for OLTP, consider denormalization for OLAP/analytics
- Most production databases aim for 3NF as a sweet spot
- BCNF addresses edge cases not covered by 3NF
