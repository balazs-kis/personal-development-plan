## Introduction

Denormalization is the strategic process of adding redundancy to a normalized database to improve read performance. While normalization focuses on data integrity and eliminating redundancy, denormalization prioritizes query speed and simplicity—often at the cost of storage and update complexity. Understanding when and how to denormalize is crucial for building high-performance database systems.

## Key Concepts Summary

### What is Denormalization?

**Definition:** Denormalization is the intentional introduction of redundancy into a database to improve query performance.

**Key principle:** Trade storage space and write complexity for faster reads.

### Normalization vs. Denormalization

| Aspect | Normalization | Denormalization |
|--------|---------------|-----------------|
| **Goal** | Data integrity, no redundancy | Query performance |
| **Storage** | Minimal redundancy | Intentional redundancy |
| **Reads** | Slower (requires joins) | Faster (pre-joined data) |
| **Writes** | Faster, simpler | Slower (maintain redundancy) |
| **Consistency** | Easier to maintain | Requires careful management |
| **Use Case** | OLTP, operational systems | OLAP, analytics, reporting |

## When to Denormalize

### Good Candidates for Denormalization

✅ **Read-Heavy Workloads**
- Applications with 90%+ read queries
- Reporting and analytics systems
- Data warehouses
- Dashboard backends

✅ **Performance-Critical Queries**
- Real-time dashboards
- Customer-facing features
- High-traffic pages
- Sub-second response requirements

✅ **Infrequently Updated Data**
- Historical data
- Reference data (countries, categories)
- Computed aggregates (daily totals)
- Rarely changing dimensions

✅ **High Join Complexity**
- Queries joining 5+ tables
- Deep hierarchical queries
- Complex reporting queries
- Frequently executed analytical queries

### Poor Candidates for Denormalization

❌ **Write-Heavy Applications**
- High-frequency transaction systems
- Real-time data ingestion
- Applications with concurrent updates
- Systems requiring strong consistency

❌ **Frequently Changing Data**
- Dynamic content
- Real-time inventory
- Live financial data
- Constantly updated user activity

❌ **Strong Consistency Requirements**
- Financial transactions
- Compliance-critical systems
- Audit-required data
- Mission-critical operations

## Denormalization Techniques

### 1. Redundant Columns

**Pattern:** Duplicate data from related tables to avoid joins.

**Example: Customer Name in Orders**

**Normalized (requires join):**
```sql
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    customer_name TEXT NOT NULL,
    email TEXT NOT NULL
);

CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date DATE NOT NULL,
    total DECIMAL(10,2),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- Query requires join
SELECT o.order_id, c.customer_name, o.total
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date = CURRENT_DATE;
```

**Denormalized (no join needed):**
```sql
CREATE TABLE orders_denorm (
    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL,
    customer_name TEXT NOT NULL,  -- Redundant data
    order_date DATE NOT NULL,
    total DECIMAL(10,2),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- Fast query without join
SELECT order_id, customer_name, total
FROM orders_denorm
WHERE order_date = CURRENT_DATE;

-- But updates require maintaining consistency
UPDATE orders_denorm
SET customer_name = 'New Name'
WHERE customer_id = 123;  -- Update multiple rows
```

### 2. Pre-Computed Aggregates

**Pattern:** Store calculated values instead of computing them on each query.

**Example: Order Totals and Item Counts**

**Normalized (computed on query):**
```sql
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date DATE NOT NULL
);

CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    unit_price DECIMAL(10,2),
    PRIMARY KEY (order_id, product_id)
);

-- Expensive query
SELECT 
    o.order_id,
    COUNT(oi.product_id) AS item_count,
    SUM(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id;
```

**Denormalized (pre-computed):**
```sql
CREATE TABLE orders_denorm (
    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date DATE NOT NULL,
    item_count INT DEFAULT 0,     -- Pre-computed
    order_total DECIMAL(10,2) DEFAULT 0  -- Pre-computed
);

-- Maintain with triggers
CREATE OR REPLACE FUNCTION update_order_totals()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE orders_denorm
    SET 
        item_count = (
            SELECT COUNT(*) 
            FROM order_items 
            WHERE order_id = NEW.order_id
        ),
        order_total = (
            SELECT COALESCE(SUM(quantity * unit_price), 0)
            FROM order_items 
            WHERE order_id = NEW.order_id
        )
    WHERE order_id = NEW.order_id;
    
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER maintain_order_totals
AFTER INSERT OR UPDATE OR DELETE ON order_items
FOR EACH ROW EXECUTE FUNCTION update_order_totals();

-- Fast query without aggregation
SELECT order_id, item_count, order_total
FROM orders_denorm;
```

### 3. Materialized Views

**Pattern:** Store complex query results as physical tables.

**Example: Sales Summary**

```sql
-- Expensive analytical query
CREATE VIEW sales_by_category AS
SELECT 
    p.category,
    DATE_TRUNC('month', o.order_date) AS month,
    COUNT(DISTINCT o.order_id) AS order_count,
    SUM(oi.quantity) AS units_sold,
    SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
GROUP BY p.category, DATE_TRUNC('month', o.order_date);

-- Materialize for fast access
CREATE MATERIALIZED VIEW sales_by_category_mv AS
SELECT 
    p.category,
    DATE_TRUNC('month', o.order_date) AS month,
    COUNT(DISTINCT o.order_id) AS order_count,
    SUM(oi.quantity) AS units_sold,
    SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
WHERE o.order_date >= DATE_TRUNC('year', NOW()) - INTERVAL '1 year'
GROUP BY p.category, DATE_TRUNC('month', o.order_date);

-- Create index
CREATE INDEX sales_category_month_idx 
    ON sales_by_category_mv (category, month);

-- Refresh periodically (e.g., nightly)
REFRESH MATERIALIZED VIEW CONCURRENTLY sales_by_category_mv;

-- Fast queries
SELECT * FROM sales_by_category_mv
WHERE category = 'Electronics'
ORDER BY month DESC;
```

### 4. Flattened Hierarchies

**Pattern:** Store hierarchical paths for fast ancestor/descendant queries.

**Example: Category Tree**

**Normalized (recursive queries):**
```sql
CREATE TABLE categories (
    category_id SERIAL PRIMARY KEY,
    category_name TEXT NOT NULL,
    parent_category_id INT,
    FOREIGN KEY (parent_category_id) REFERENCES categories(category_id)
);

-- Find all ancestors (expensive recursive query)
WITH RECURSIVE category_path AS (
    SELECT category_id, category_name, parent_category_id, 1 AS level
    FROM categories
    WHERE category_id = 10
    
    UNION ALL
    
    SELECT c.category_id, c.category_name, c.parent_category_id, cp.level + 1
    FROM categories c
    JOIN category_path cp ON c.category_id = cp.parent_category_id
)
SELECT * FROM category_path;
```

**Denormalized (path stored):**
```sql
CREATE TABLE categories_denorm (
    category_id SERIAL PRIMARY KEY,
    category_name TEXT NOT NULL,
    parent_category_id INT,
    path TEXT,  -- e.g., '/1/5/10' for fast queries
    level INT,
    FOREIGN KEY (parent_category_id) REFERENCES categories_denorm(category_id)
);

-- Maintain path with triggers
CREATE OR REPLACE FUNCTION update_category_path()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.parent_category_id IS NULL THEN
        NEW.path := '/' || NEW.category_id;
        NEW.level := 1;
    ELSE
        SELECT path || '/' || NEW.category_id, level + 1
        INTO NEW.path, NEW.level
        FROM categories_denorm
        WHERE category_id = NEW.parent_category_id;
    END IF;
    
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER maintain_category_path
BEFORE INSERT OR UPDATE ON categories_denorm
FOR EACH ROW EXECUTE FUNCTION update_category_path();

-- Fast ancestor query (no recursion)
SELECT * FROM categories_denorm
WHERE '/1/5/10' LIKE path || '%'
ORDER BY level;

-- Fast descendant query
SELECT * FROM categories_denorm
WHERE path LIKE '/1/5%'
ORDER BY path;
```

### 5. JSONB Aggregation

**Pattern:** Store related records as JSONB for single-table queries.

**Example: Product with Reviews**

```sql
-- Normalized (requires join)
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,
    product_name TEXT NOT NULL,
    price DECIMAL(10,2)
);

CREATE TABLE reviews (
    review_id SERIAL PRIMARY KEY,
    product_id INT NOT NULL,
    rating INT CHECK (rating BETWEEN 1 AND 5),
    comment TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);

-- Denormalized with JSONB
CREATE TABLE products_denorm (
    product_id SERIAL PRIMARY KEY,
    product_name TEXT NOT NULL,
    price DECIMAL(10,2),
    avg_rating DECIMAL(3,2),  -- Pre-computed
    review_count INT DEFAULT 0,
    recent_reviews JSONB  -- Last 5 reviews
);

-- Maintain with trigger or periodic update
CREATE OR REPLACE FUNCTION update_product_reviews()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE products_denorm
    SET 
        avg_rating = (
            SELECT AVG(rating)
            FROM reviews
            WHERE product_id = NEW.product_id
        ),
        review_count = (
            SELECT COUNT(*)
            FROM reviews
            WHERE product_id = NEW.product_id
        ),
        recent_reviews = (
            SELECT jsonb_agg(
                jsonb_build_object(
                    'rating', rating,
                    'comment', comment,
                    'created_at', created_at
                ) ORDER BY created_at DESC
            )
            FROM (
                SELECT rating, comment, created_at
                FROM reviews
                WHERE product_id = NEW.product_id
                ORDER BY created_at DESC
                LIMIT 5
            ) sub
        )
    WHERE product_id = NEW.product_id;
    
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER maintain_product_reviews
AFTER INSERT OR UPDATE ON reviews
FOR EACH ROW EXECUTE FUNCTION update_product_reviews();

-- Fast single-table query
SELECT 
    product_name,
    price,
    avg_rating,
    review_count,
    recent_reviews
FROM products_denorm
WHERE product_id = 123;
```

## Practical Examples

### Example 1: E-commerce Product Catalog

**Scenario:** Product search with category names and review stats.

**Normalized:**
```sql
SELECT 
    p.product_id,
    p.product_name,
    c.category_name,
    AVG(r.rating) AS avg_rating,
    COUNT(r.review_id) AS review_count
FROM products p
JOIN categories c ON p.category_id = c.category_id
LEFT JOIN reviews r ON p.product_id = r.product_id
GROUP BY p.product_id, p.product_name, c.category_name
LIMIT 20;
-- Expensive: 2 joins + aggregation
```

**Denormalized:**
```sql
CREATE TABLE products_search (
    product_id INT PRIMARY KEY,
    product_name TEXT,
    category_name TEXT,  -- Denormalized
    price DECIMAL(10,2),
    avg_rating DECIMAL(3,2),  -- Pre-computed
    review_count INT,         -- Pre-computed
    in_stock BOOLEAN,
    search_vector tsvector    -- For full-text search
);

-- Single table query
SELECT * FROM products_search
WHERE in_stock = true
ORDER BY avg_rating DESC
LIMIT 20;
-- Fast: No joins, no aggregation
```

### Example 2: User Activity Dashboard

**Scenario:** Real-time dashboard showing user stats.

**Normalized (slow):**
```sql
SELECT 
    u.user_id,
    u.username,
    COUNT(DISTINCT p.post_id) AS post_count,
    COUNT(DISTINCT c.comment_id) AS comment_count,
    COUNT(DISTINCT l.like_id) AS like_count,
    MAX(p.created_at) AS last_post_date
FROM users u
LEFT JOIN posts p ON u.user_id = p.user_id
LEFT JOIN comments c ON u.user_id = c.user_id
LEFT JOIN likes l ON u.user_id = l.user_id
GROUP BY u.user_id, u.username;
```

**Denormalized (fast):**
```sql
CREATE TABLE user_stats (
    user_id INT PRIMARY KEY,
    username TEXT,
    post_count INT DEFAULT 0,
    comment_count INT DEFAULT 0,
    like_count INT DEFAULT 0,
    last_activity TIMESTAMP,
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Update with triggers on each activity table
-- Or periodic batch update

SELECT * FROM user_stats
WHERE user_id = 123;
-- Instant response
```

## Maintaining Denormalized Data

### Strategy 1: Triggers

```sql
-- Automatic synchronization
CREATE OR REPLACE FUNCTION sync_customer_name()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'UPDATE' AND OLD.customer_name != NEW.customer_name THEN
        UPDATE orders
        SET customer_name = NEW.customer_name
        WHERE customer_id = NEW.customer_id;
    END IF;
    
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER sync_customer_name_trigger
AFTER UPDATE ON customers
FOR EACH ROW EXECUTE FUNCTION sync_customer_name();
```

**Pros:** Automatic, consistent
**Cons:** Adds overhead to writes, can cause performance issues

### Strategy 2: Application Logic

```sql
-- Application handles updates
BEGIN;
    UPDATE customers SET customer_name = 'New Name' WHERE customer_id = 123;
    UPDATE orders SET customer_name = 'New Name' WHERE customer_id = 123;
COMMIT;
```

**Pros:** Full control, can batch updates
**Cons:** Risk of inconsistency, more complex code

### Strategy 3: Periodic Batch Updates

```sql
-- Scheduled job (e.g., nightly)
UPDATE products_search p
SET 
    avg_rating = r.avg_rating,
    review_count = r.review_count
FROM (
    SELECT 
        product_id,
        AVG(rating) AS avg_rating,
        COUNT(*) AS review_count
    FROM reviews
    GROUP BY product_id
) r
WHERE p.product_id = r.product_id;
```

**Pros:** Doesn't impact write performance, can optimize bulk updates
**Cons:** Data staleness, eventual consistency

### Strategy 4: Materialized Views with Refresh

```sql
-- Best of both worlds
CREATE MATERIALIZED VIEW product_summary AS
SELECT 
    p.product_id,
    p.product_name,
    c.category_name,
    AVG(r.rating) AS avg_rating,
    COUNT(r.review_id) AS review_count
FROM products p
JOIN categories c ON p.category_id = c.category_id
LEFT JOIN reviews r ON p.product_id = r.product_id
GROUP BY p.product_id, p.product_name, c.category_name;

-- Refresh strategy
-- Option 1: Scheduled (pg_cron)
SELECT cron.schedule('refresh-product-summary', '0 */6 * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY product_summary$$);

-- Option 2: Event-driven (application calls after data changes)
REFRESH MATERIALIZED VIEW CONCURRENTLY product_summary;
```

## Best Practices

### 1. Document Denormalization Decisions

```sql
-- Add comments explaining denormalization
COMMENT ON COLUMN orders.customer_name IS 
    'Denormalized from customers table for performance. 
     Updated via trigger on customers.customer_name changes.';

COMMENT ON TABLE product_summary IS
    'Materialized view refreshed every 6 hours via pg_cron.
     Denormalized to avoid expensive joins in product search.';
```

### 2. Monitor Data Consistency

```sql
-- Validation query
SELECT o.order_id, o.customer_name AS order_name, c.customer_name AS customer_name
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.customer_name != c.customer_name;
-- Should return no rows
```

### 3. Measure Performance Impact

```sql
-- Before denormalization
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... FROM normalized_schema;

-- After denormalization
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... FROM denormalized_schema;

-- Compare execution time, buffer usage, etc.
```

### 4. Use Hybrid Approach

```sql
-- Keep normalized tables as source of truth
-- Create denormalized tables/views for specific use cases
-- Best of both worlds

-- Source of truth (normalized)
CREATE TABLE customers (...);
CREATE TABLE orders (...);

-- Performance layer (denormalized)
CREATE TABLE orders_search (...);  -- For search
CREATE MATERIALIZED VIEW sales_summary AS ...;  -- For reporting
```

## Key Takeaways

- Denormalization trades data redundancy for query performance
- Use for read-heavy workloads with infrequent writes
- Common techniques: redundant columns, pre-computed aggregates, materialized views
- Maintain denormalized data with triggers, application logic, or batch jobs
- Always keep normalized tables as source of truth
- Monitor consistency between normalized and denormalized data
- Document denormalization decisions for future maintainers
- Measure performance before and after denormalization
- Consider materialized views as a middle ground
- Use hybrid normalized/denormalized approach for best results
