## Introduction

Soft deletes and audit logging are essential patterns for maintaining data history and enabling recovery. Instead of permanently removing data, soft deletes mark records as deleted while keeping them in the database. Audit logging tracks all changes (inserts, updates, deletes) for compliance, debugging, and forensic analysis.

## Key Concepts Summary

### Soft Delete Pattern

**Definition:** Mark records as deleted rather than removing them from the database.

**Implementation:** Add a `deleted_at` timestamp column (NULL = active, timestamp = deleted).

**Benefits:**
- Data recovery capability
- Audit trail maintenance
- Historical analysis
- Compliance requirements
- Cascade delete performance (mark vs. actual delete)

**Trade-offs:**
- Additional storage required
- Queries must filter deleted records
- Indexes grow larger
- Referential integrity more complex

## Implementing Soft Deletes

### Basic Implementation

```sql
-- Add deleted_at column to existing table
ALTER TABLE users ADD COLUMN deleted_at TIMESTAMP;

-- Create index for filtering
CREATE INDEX users_deleted_at_idx ON users (deleted_at) 
WHERE deleted_at IS NULL;

-- "Delete" a user (soft delete)
UPDATE users
SET deleted_at = CURRENT_TIMESTAMP
WHERE user_id = 123;

-- Query active users
SELECT * FROM users
WHERE deleted_at IS NULL;

-- Query deleted users
SELECT * FROM users
WHERE deleted_at IS NOT NULL;

-- Restore deleted user
UPDATE users
SET deleted_at = NULL
WHERE user_id = 123;

-- Hard delete (permanent)
DELETE FROM users
WHERE user_id = 123 AND deleted_at IS NOT NULL;
```

### Database-Level Soft Delete

**Using Views:**

```sql
-- Base table with deleted_at
CREATE TABLE users_base (
    user_id SERIAL PRIMARY KEY,
    username TEXT NOT NULL,
    email TEXT NOT NULL,
    deleted_at TIMESTAMP
);

-- View of active users (hides soft-deleted)
CREATE VIEW users AS
SELECT user_id, username, email
FROM users_base
WHERE deleted_at IS NULL;

-- Instead of delete trigger
CREATE OR REPLACE FUNCTION users_soft_delete()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE users_base
    SET deleted_at = CURRENT_TIMESTAMP
    WHERE user_id = OLD.user_id;
    RETURN NULL;  -- Prevent actual delete
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER users_instead_of_delete
INSTEAD OF DELETE ON users
FOR EACH ROW EXECUTE FUNCTION users_soft_delete();

-- Application code remains simple
DELETE FROM users WHERE user_id = 123;  -- Actually does soft delete
SELECT * FROM users;  -- Only shows active records
```

### Cascading Soft Deletes

```sql
-- Parent table
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    customer_name TEXT NOT NULL,
    deleted_at TIMESTAMP
);

-- Child table
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(customer_id),
    order_date DATE NOT NULL,
    deleted_at TIMESTAMP
);

-- Cascade soft delete function
CREATE OR REPLACE FUNCTION cascade_soft_delete_orders()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.deleted_at IS NOT NULL AND OLD.deleted_at IS NULL THEN
        -- Customer was soft-deleted, cascade to orders
        UPDATE orders
        SET deleted_at = NEW.deleted_at
        WHERE customer_id = NEW.customer_id
          AND deleted_at IS NULL;
    ELSIF NEW.deleted_at IS NULL AND OLD.deleted_at IS NOT NULL THEN
        -- Customer was restored, restore orders
        UPDATE orders
        SET deleted_at = NULL
        WHERE customer_id = NEW.customer_id
          AND deleted_at = OLD.deleted_at;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER cascade_soft_delete_orders_trigger
AFTER UPDATE OF deleted_at ON customers
FOR EACH ROW EXECUTE FUNCTION cascade_soft_delete_orders();

-- Test cascade
UPDATE customers SET deleted_at = CURRENT_TIMESTAMP WHERE customer_id = 1;
-- All orders for customer 1 are also soft-deleted

-- Restore
UPDATE customers SET deleted_at = NULL WHERE customer_id = 1;
-- Orders are restored too
```

## Audit Logging Patterns

### Pattern 1: Audit Column Approach

```sql
-- Add audit columns to tables
ALTER TABLE products ADD COLUMN created_at TIMESTAMP DEFAULT NOW();
ALTER TABLE products ADD COLUMN created_by TEXT;
ALTER TABLE products ADD COLUMN updated_at TIMESTAMP;
ALTER TABLE products ADD COLUMN updated_by TEXT;

-- Trigger to maintain audit columns
CREATE OR REPLACE FUNCTION update_audit_columns()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at := CURRENT_TIMESTAMP;
    NEW.updated_by := CURRENT_USER;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER products_audit_trigger
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION update_audit_columns();
```

**Pros:** Simple, integrated with main table
**Cons:** Limited history, doesn't track deletes

### Pattern 2: Audit Table (Journal/History)

```sql
-- Main table
CREATE TABLE employees (
    employee_id SERIAL PRIMARY KEY,
    employee_name TEXT NOT NULL,
    department TEXT NOT NULL,
    salary DECIMAL(10,2) NOT NULL
);

-- Audit table (tracks all changes)
CREATE TABLE employees_audit (
    audit_id BIGSERIAL PRIMARY KEY,
    employee_id INT NOT NULL,
    employee_name TEXT,
    department TEXT,
    salary DECIMAL(10,2),
    operation CHAR(1) NOT NULL,  -- 'I', 'U', 'D'
    operation_time TIMESTAMP NOT NULL DEFAULT NOW(),
    operation_user TEXT NOT NULL DEFAULT CURRENT_USER,
    old_values JSONB,  -- Previous values for UPDATE
    new_values JSONB   -- New values for INSERT/UPDATE
);

-- Create indexes
CREATE INDEX employees_audit_employee_id_idx 
    ON employees_audit (employee_id);
CREATE INDEX employees_audit_operation_time_idx 
    ON employees_audit (operation_time);

-- Audit trigger function
CREATE OR REPLACE FUNCTION employees_audit_trigger()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO employees_audit (
            employee_id, employee_name, department, salary,
            operation, new_values
        ) VALUES (
            NEW.employee_id, NEW.employee_name, NEW.department, NEW.salary,
            'I', to_jsonb(NEW)
        );
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO employees_audit (
            employee_id, employee_name, department, salary,
            operation, old_values, new_values
        ) VALUES (
            NEW.employee_id, NEW.employee_name, NEW.department, NEW.salary,
            'U', to_jsonb(OLD), to_jsonb(NEW)
        );
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO employees_audit (
            employee_id, employee_name, department, salary,
            operation, old_values
        ) VALUES (
            OLD.employee_id, OLD.employee_name, OLD.department, OLD.salary,
            'D', to_jsonb(OLD)
        );
        RETURN OLD;
    END IF;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER employees_audit_trig
AFTER INSERT OR UPDATE OR DELETE ON employees
FOR EACH ROW EXECUTE FUNCTION employees_audit_trigger();
```

### Querying Audit Logs

```sql
-- View all changes for an employee
SELECT 
    operation,
    operation_time,
    operation_user,
    old_values,
    new_values
FROM employees_audit
WHERE employee_id = 1
ORDER BY operation_time DESC;

-- View salary changes
SELECT 
    operation_time,
    old_values->>'salary' AS old_salary,
    new_values->>'salary' AS new_salary,
    operation_user
FROM employees_audit
WHERE employee_id = 1
  AND operation = 'U'
  AND (old_values->>'salary') != (new_values->>'salary')
ORDER BY operation_time;

-- Who changed what in the last 24 hours
SELECT 
    e.employee_name,
    a.operation,
    a.operation_time,
    a.operation_user,
    jsonb_pretty(a.old_values) AS before,
    jsonb_pretty(a.new_values) AS after
FROM employees_audit a
JOIN employees e ON a.employee_id = e.employee_id
WHERE a.operation_time >= NOW() - INTERVAL '24 hours'
ORDER BY a.operation_time DESC;
```

### Pattern 3: Generic Audit System

```sql
-- Single audit table for multiple tables
CREATE TABLE audit_log (
    audit_id BIGSERIAL PRIMARY KEY,
    table_name TEXT NOT NULL,
    record_id BIGINT NOT NULL,
    operation CHAR(1) NOT NULL,
    operation_time TIMESTAMP NOT NULL DEFAULT NOW(),
    operation_user TEXT NOT NULL DEFAULT CURRENT_USER,
    old_data JSONB,
    new_data JSONB,
    changed_fields TEXT[]  -- Array of changed column names
);

CREATE INDEX audit_log_table_record_idx 
    ON audit_log (table_name, record_id);
CREATE INDEX audit_log_operation_time_idx 
    ON audit_log (operation_time);
CREATE INDEX audit_log_user_idx 
    ON audit_log (operation_user);

-- Reusable audit function
CREATE OR REPLACE FUNCTION audit_trigger_function()
RETURNS TRIGGER AS $$
DECLARE
    changed_cols TEXT[];
    old_json JSONB;
    new_json JSONB;
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit_log (
            table_name, record_id, operation, new_data
        ) VALUES (
            TG_TABLE_NAME, 
            (to_jsonb(NEW)->>'id')::BIGINT,
            'I',
            to_jsonb(NEW)
        );
        RETURN NEW;
        
    ELSIF TG_OP = 'UPDATE' THEN
        old_json := to_jsonb(OLD);
        new_json := to_jsonb(NEW);
        
        -- Identify changed fields
        SELECT ARRAY_AGG(key)
        INTO changed_cols
        FROM jsonb_each(old_json)
        WHERE value IS DISTINCT FROM new_json->key;
        
        INSERT INTO audit_log (
            table_name, record_id, operation, 
            old_data, new_data, changed_fields
        ) VALUES (
            TG_TABLE_NAME,
            (new_json->>'id')::BIGINT,
            'U',
            old_json,
            new_json,
            changed_cols
        );
        RETURN NEW;
        
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit_log (
            table_name, record_id, operation, old_data
        ) VALUES (
            TG_TABLE_NAME,
            (to_jsonb(OLD)->>'id')::BIGINT,
            'D',
            to_jsonb(OLD)
        );
        RETURN OLD;
    END IF;
END;
$$ LANGUAGE plpgsql;

-- Apply to any table
CREATE TRIGGER products_audit
AFTER INSERT OR UPDATE OR DELETE ON products
FOR EACH ROW EXECUTE FUNCTION audit_trigger_function();

CREATE TRIGGER customers_audit
AFTER INSERT OR UPDATE OR DELETE ON customers
FOR EACH ROW EXECUTE FUNCTION audit_trigger_function();
```

## Practical Examples

### Example 1: User Account Soft Delete with Anonymization

```sql
CREATE TABLE user_accounts (
    user_id SERIAL PRIMARY KEY,
    username TEXT NOT NULL,
    email TEXT NOT NULL,
    full_name TEXT,
    phone TEXT,
    deleted_at TIMESTAMP,
    anonymized BOOLEAN DEFAULT FALSE
);

-- Soft delete with optional anonymization
CREATE OR REPLACE FUNCTION soft_delete_user(p_user_id INT, p_anonymize BOOLEAN DEFAULT FALSE)
RETURNS VOID AS $$
BEGIN
    UPDATE user_accounts
    SET 
        deleted_at = CURRENT_TIMESTAMP,
        anonymized = p_anonymize,
        email = CASE WHEN p_anonymize THEN 'deleted_' || user_id || '@example.com' ELSE email END,
        full_name = CASE WHEN p_anonymize THEN 'Deleted User' ELSE full_name END,
        phone = CASE WHEN p_anonymize THEN NULL ELSE phone END
    WHERE user_id = p_user_id;
END;
$$ LANGUAGE plpgsql;

-- Usage
SELECT soft_delete_user(123, true);  -- Delete and anonymize (GDPR compliance)
```

### Example 2: Compliance-Ready Audit Trail

```sql
-- Immutable audit log (append-only)
CREATE TABLE compliance_audit (
    audit_id BIGSERIAL PRIMARY KEY,
    event_type TEXT NOT NULL,
    entity_type TEXT NOT NULL,
    entity_id BIGINT NOT NULL,
    user_id INT,
    ip_address INET,
    event_data JSONB NOT NULL,
    event_time TIMESTAMP NOT NULL DEFAULT NOW()
);

-- Make table append-only (prevent updates/deletes)
REVOKE UPDATE, DELETE ON compliance_audit FROM PUBLIC;
GRANT INSERT, SELECT ON compliance_audit TO application_role;

-- Function to log compliance events
CREATE OR REPLACE FUNCTION log_compliance_event(
    p_event_type TEXT,
    p_entity_type TEXT,
    p_entity_id BIGINT,
    p_event_data JSONB
) RETURNS VOID AS $$
BEGIN
    INSERT INTO compliance_audit (
        event_type, entity_type, entity_id,
        user_id, ip_address, event_data
    ) VALUES (
        p_event_type, p_entity_type, p_entity_id,
        CURRENT_USER::INT, INET_CLIENT_ADDR(), p_event_data
    );
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- Usage
SELECT log_compliance_event(
    'DATA_ACCESS',
    'customer',
    12345,
    jsonb_build_object('fields_accessed', ARRAY['ssn', 'bank_account'])
);
```

## Soft Deletes vs. Journal Tables

### Comparison

| Feature | Soft Deletes | Journal Tables |
|---------|-------------|----------------|
| **Complexity** | Simple | Moderate to Complex |
| **Storage** | One table | Two tables (main + audit) |
| **History** | Limited (one deletion) | Complete change history |
| **Recovery** | Easy (UPDATE) | Requires reconstruction |
| **Performance** | Queries need filtering | No impact on main table |
| **Use Case** | Undo deletes | Full audit trail |

### When to Use Each

**Soft Deletes:**
- Simple undo functionality
- No detailed history needed
- Want to preserve referential integrity
- Regulatory compliance for retention

**Journal Tables:**
- Need complete change history
- Compliance/audit requirements
- Forensic analysis
- Time-travel queries
- When soft deletes aren't sufficient

## Performance Considerations

### Optimizing Soft Delete Queries

```sql
-- Bad: Full table scan
SELECT * FROM users WHERE deleted_at IS NULL;

-- Good: Partial index
CREATE INDEX users_active_idx ON users (user_id) 
WHERE deleted_at IS NULL;

-- Query uses index
SELECT * FROM users WHERE deleted_at IS NULL AND user_id = 123;
```

### Archiving Old Soft-Deleted Records

```sql
-- Move old soft-deleted records to archive table
BEGIN;
    -- Copy to archive
    INSERT INTO users_archive
    SELECT * FROM users
    WHERE deleted_at < NOW() - INTERVAL '2 years';
    
    -- Remove from main table
    DELETE FROM users
    WHERE deleted_at < NOW() - INTERVAL '2 years';
COMMIT;
```

### Partitioning Audit Tables

```sql
-- Partition audit log by month
CREATE TABLE audit_log (
    audit_id BIGSERIAL,
    operation_time TIMESTAMP NOT NULL,
    -- other columns
) PARTITION BY RANGE (operation_time);

CREATE TABLE audit_log_2024_01 PARTITION OF audit_log
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE audit_log_2024_02 PARTITION OF audit_log
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
```

## Key Takeaways

- Soft deletes mark records as deleted without removing them
- Implement with `deleted_at` timestamp column (NULL = active)
- Use database views and triggers for transparent soft delete handling
- Audit logging tracks all changes for compliance and debugging
- Journal tables provide complete change history
- Generic audit functions can be reused across multiple tables
- Store audit data as JSONB for flexibility
- Soft deletes good for simple undo; journal tables for full history
- Consider archiving old deleted records for performance
- Partition audit tables for better query performance
- Make audit logs append-only for compliance
