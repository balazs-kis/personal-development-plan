## Introduction

Transactions are the foundation of reliable database systems. A transaction groups multiple operations into a single, atomic unit that either completely succeeds or completely fails. PostgreSQL guarantees ACID properties (Atomicity, Consistency, Isolation, Durability) for all transactions, ensuring data integrity even in the face of failures, crashes, or concurrent access.

Understanding transaction fundamentals is essential for building robust applications. Poor transaction management leads to data corruption, race conditions, and difficult-to-debug concurrency issues.

## Key Concepts Summary

### ACID Properties

PostgreSQL guarantees four fundamental properties for every transaction:

**Atomicity:**
- All operations in a transaction complete successfully, or none do
- No partial updates are visible to other transactions
- If a failure occurs, all changes are rolled back

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- If either UPDATE fails, both are rolled back
COMMIT;
```

**Consistency:**
- Transactions transform the database from one valid state to another
- Constraints (foreign keys, check constraints, etc.) are enforced
- Application-level invariants are maintained

```sql
BEGIN;
INSERT INTO orders (user_id, total) VALUES (123, 50.00);
-- This will fail if user_id 123 doesn't exist (foreign key constraint)
-- Database remains consistent
COMMIT;
```

**Isolation:**
- Concurrent transactions don't interfere with each other
- Each transaction sees a consistent view of the data
- Controlled by isolation levels (covered in next lesson)

```sql
-- Transaction 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- Sees 1000

-- Transaction 2 (concurrent)
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;
COMMIT;

-- Transaction 1 (still running)
SELECT balance FROM accounts WHERE id = 1;  -- Still sees 1000 at default isolation level
COMMIT;
```

**Durability:**
- Once a transaction commits, its changes are permanent
- Survives power failures, crashes, and system restarts
- Guaranteed by write-ahead logging (WAL)

```sql
BEGIN;
INSERT INTO critical_data (value) VALUES ('important');
COMMIT;  -- At this point, data is durable even if server crashes immediately
```

### Basic Transaction Commands

**BEGIN (or START TRANSACTION):**
```sql
BEGIN;  -- Start explicit transaction
-- or
BEGIN TRANSACTION;
-- or
START TRANSACTION;
```

**COMMIT:**
```sql
COMMIT;  -- Save all changes permanently
-- or
COMMIT WORK;
-- or
END;
```

**ROLLBACK:**
```sql
ROLLBACK;  -- Undo all changes since BEGIN
-- or
ROLLBACK WORK;
-- or
ABORT;
```

### Explicit vs Implicit Transactions

**Implicit (autocommit mode - default):**
```sql
-- Each statement is automatically wrapped in a transaction
INSERT INTO users (name) VALUES ('Alice');  -- Automatically committed
UPDATE users SET name = 'Bob' WHERE id = 1;  -- Separate transaction
```

**Explicit:**
```sql
-- Multiple statements in one transaction
BEGIN;
INSERT INTO users (name) VALUES ('Alice');
UPDATE settings SET last_user = 'Alice';
COMMIT;  -- Both changes committed together
```

**When to use explicit transactions:**
- Multiple related operations that must succeed or fail together
- Operations that depend on reading then modifying data
- When you need to verify results before committing
- To maintain application-level invariants across multiple tables

### Savepoints (Subtransactions)

Savepoints allow you to create nested transaction boundaries within a larger transaction:

```sql
BEGIN;

INSERT INTO orders (user_id, total) VALUES (1, 100.00);

SAVEPOINT order_items;  -- Create savepoint

-- Try to insert items
INSERT INTO order_items (order_id, product_id, quantity) VALUES (1, 10, 2);
INSERT INTO order_items (order_id, product_id, quantity) VALUES (1, 99999, 1);  -- May fail

-- If item insert failed, rollback to savepoint
ROLLBACK TO SAVEPOINT order_items;

-- But order insert is still there
-- Can continue with transaction or commit
COMMIT;
```

**Savepoint commands:**
```sql
SAVEPOINT savepoint_name;           -- Create savepoint
RELEASE SAVEPOINT savepoint_name;   -- Delete savepoint (but keep changes)
ROLLBACK TO SAVEPOINT savepoint_name;  -- Rollback to savepoint
```

**Use cases:**
- Error handling within long transactions
- Trying optional operations that may fail
- Implementing retry logic within a transaction
- Complex business logic with multiple paths

### Transaction Lifecycle

```
┌─────────────┐
│   BEGIN     │
└─────┬───────┘
      │
      v
┌─────────────────────┐
│  Execute Statements │
│  (Read/Write Data)  │
└─────┬────────┬──────┘
      │        │
      v        v
   COMMIT   ROLLBACK
      │        │
      v        v
   Success   Aborted
```

### Common Patterns

**Pattern 1: Bank Transfer**
```sql
BEGIN;

-- Debit from account 1
UPDATE accounts 
SET balance = balance - 100 
WHERE id = 1 AND balance >= 100;

-- Check if debit succeeded
IF NOT FOUND THEN
    ROLLBACK;
    RAISE EXCEPTION 'Insufficient funds';
END IF;

-- Credit to account 2
UPDATE accounts 
SET balance = balance + 100 
WHERE id = 2;

COMMIT;
```

**Pattern 2: Idempotent Updates**
```sql
BEGIN;

-- Check if already processed
SELECT status FROM jobs WHERE id = 123;

IF status = 'completed' THEN
    ROLLBACK;  -- Already done, nothing to do
    RETURN;
END IF;

-- Process job
UPDATE jobs SET status = 'processing' WHERE id = 123;
-- ... do work ...
UPDATE jobs SET status = 'completed' WHERE id = 123;

COMMIT;
```

**Pattern 3: Error Handling with Savepoints**
```sql
BEGIN;

-- Critical operation (must succeed)
INSERT INTO orders (user_id, total) VALUES (1, 100.00);

-- Optional operations (can fail)
SAVEPOINT optional_ops;
BEGIN
    INSERT INTO order_audit (order_id, details) VALUES (1, 'some info');
EXCEPTION WHEN OTHERS THEN
    ROLLBACK TO SAVEPOINT optional_ops;
    -- Log error but continue
END;

COMMIT;
```

### Transaction Best Practices

1. **Keep transactions short:**
   - Long transactions hold locks longer
   - Increase risk of deadlocks
   - Block other operations
   - Hold database resources

2. **Don't do I/O in transactions:**
   ```sql
   -- Bad: external API call during transaction
   BEGIN;
   UPDATE orders SET status = 'processing';
   -- Call external payment API (slow!)
   UPDATE orders SET status = 'paid';
   COMMIT;
   
   -- Good: external calls outside transaction
   UPDATE orders SET status = 'processing';
   -- Call external payment API
   BEGIN;
   UPDATE orders SET status = 'paid';
   COMMIT;
   ```

3. **Handle errors appropriately:**
   - Always ROLLBACK on errors
   - Use savepoints for partial rollbacks
   - Log transaction failures

4. **Be explicit when needed:**
   - Use explicit BEGIN/COMMIT for multi-statement operations
   - Rely on autocommit for single statements
   - Document transaction boundaries in code

5. **Understand isolation level implications:**
   - Default (Read Committed) is suitable for most cases
   - Use higher levels when needed (covered in next lesson)
   - Test concurrent scenarios

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

1. Create test tables:

```sql
CREATE TABLE accounts (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    balance NUMERIC(10,2) NOT NULL CHECK (balance >= 0)
);

CREATE TABLE transactions (
    id SERIAL PRIMARY KEY,
    from_account INTEGER REFERENCES accounts(id),
    to_account INTEGER REFERENCES accounts(id),
    amount NUMERIC(10,2) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

INSERT INTO accounts (name, balance) VALUES 
    ('Alice', 1000.00),
    ('Bob', 500.00),
    ('Charlie', 250.00);
```

2. Implement a money transfer with proper transaction handling:

```sql
-- Transfer $100 from Alice to Bob
BEGIN;

-- Debit source account
UPDATE accounts 
SET balance = balance - 100 
WHERE id = 1 AND balance >= 100;

-- Verify debit succeeded
DO $$
DECLARE
    rows_affected INTEGER;
BEGIN
    GET DIAGNOSTICS rows_affected = ROW_COUNT;
    IF rows_affected = 0 THEN
        RAISE EXCEPTION 'Insufficient funds or account not found';
    END IF;
END $$;

-- Credit destination account
UPDATE accounts 
SET balance = balance + 100 
WHERE id = 2;

-- Record transaction
INSERT INTO transactions (from_account, to_account, amount)
VALUES (1, 2, 100);

COMMIT;

-- Verify results
SELECT * FROM accounts;
SELECT * FROM transactions;
```

3. Test transaction rollback:

```sql
BEGIN;

UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;

-- Check intermediate state
SELECT * FROM accounts;

-- Oops, changed our mind
ROLLBACK;

-- Verify rollback worked
SELECT * FROM accounts;  -- Should show original balances
```

4. Practice with savepoints:

```sql
BEGIN;

-- Main operation
UPDATE accounts SET balance = balance + 100 WHERE id = 1;

SAVEPOINT after_deposit;

-- Try risky operation
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;  -- Will fail constraint

-- Rollback just the risky part
ROLLBACK TO SAVEPOINT after_deposit;

-- Main operation still valid
SELECT * FROM accounts WHERE id = 1;  -- Should show +100 balance

COMMIT;
```

5. Test constraint enforcement:

```sql
-- This should fail and rollback entire transaction
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = -50 WHERE id = 1;  -- Violates CHECK constraint
COMMIT;  -- Never reached

-- Verify no changes were made
SELECT * FROM accounts WHERE id = 1;
```
