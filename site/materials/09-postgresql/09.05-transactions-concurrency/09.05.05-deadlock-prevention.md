## Introduction

Deadlocks occur when two or more transactions wait for each other to release locks, creating a circular dependency that prevents all of them from proceeding. PostgreSQL automatically detects deadlocks and breaks them by aborting one transaction, but frequent deadlocks indicate design problems that should be fixed at the application level.

Understanding deadlock causes and prevention strategies is essential for building robust concurrent systems. Properly designed applications should experience deadlocks rarely, if ever.

## Key Concepts Summary

### What is a Deadlock?

A deadlock occurs when transactions wait for each other in a circular pattern:

```
Transaction 1: Holds lock on Row A, waits for Row B
Transaction 2: Holds lock on Row B, waits for Row A

Neither can proceed → Deadlock!
```

**Simple example:**

```sql
-- Terminal 1: Transaction 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- Locks row 1
-- Now try to lock row 2
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- WAITS

-- Terminal 2: Transaction 2 (concurrent)
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- Locks row 2
-- Now try to lock row 1
UPDATE accounts SET balance = balance + 50 WHERE id = 1;   -- WAITS

-- PostgreSQL detects deadlock after 1 second (deadlock_timeout)
-- One transaction gets error:
-- ERROR: deadlock detected
-- DETAIL: Process 12345 waits for ShareLock on transaction 67890; 
--         blocked by process 12346.
```

### How PostgreSQL Detects Deadlocks

**Detection mechanism:**
1. Transaction waits for a lock
2. After `deadlock_timeout` (default 1 second), check for circular wait
3. If deadlock found, abort one transaction (the "victim")
4. Choose victim based on amount of work done (abort the one that's done less)

**Configuration:**

```sql
-- View current setting
SHOW deadlock_timeout;  -- Default: 1s

-- Adjust if needed (in postgresql.conf or session)
SET deadlock_timeout = '2s';  -- Wait longer before checking
```

**Trade-off:**
- Lower value: Faster deadlock detection, more overhead
- Higher value: Slower detection, less overhead checking for deadlocks

### Common Deadlock Patterns

**Pattern 1: Lock Order Inversion**

```sql
-- Transaction 1
BEGIN;
UPDATE table1 WHERE id = 1;  -- Locks table1 row 1
UPDATE table2 WHERE id = 2;  -- Waits for table2 row 2

-- Transaction 2
BEGIN;
UPDATE table2 WHERE id = 2;  -- Locks table2 row 2
UPDATE table1 WHERE id = 1;  -- Waits for table1 row 1
-- DEADLOCK!
```

**Solution: Always lock in same order**

```sql
-- Both transactions use same order
BEGIN;
UPDATE table1 WHERE id = 1;
UPDATE table2 WHERE id = 2;
COMMIT;
```

**Pattern 2: Multiple Row Updates in Different Order**

```sql
-- Transaction 1
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;

-- Transaction 2
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- DEADLOCK!
```

**Solution: Lock all rows at once in consistent order**

```sql
BEGIN;
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;
COMMIT;
```

**Pattern 3: Foreign Key Cascades**

```sql
-- Parent-child relationships can cause deadlocks

-- Transaction 1
BEGIN;
INSERT INTO child (parent_id, value) VALUES (1, 'A');  -- Locks parent row 1
-- Then tries to lock parent row 2 for another operation

-- Transaction 2
BEGIN;
INSERT INTO child (parent_id, value) VALUES (2, 'B');  -- Locks parent row 2
-- Then tries to lock parent row 1
-- DEADLOCK!
```

**Solution: Lock parent rows explicitly first**

```sql
BEGIN;
SELECT * FROM parent WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
INSERT INTO child (parent_id, value) VALUES (1, 'A');
INSERT INTO child (parent_id, value) VALUES (2, 'B');
COMMIT;
```

**Pattern 4: Index Lock Conflicts**

```sql
-- Two transactions insert rows that hash to same index page
-- Can cause deadlock on index page locks
-- Less common, but can happen with specific data patterns
```

### Deadlock Prevention Strategies

**Strategy 1: Consistent Lock Ordering**

```sql
-- Always acquire locks in the same order (e.g., by primary key)
BEGIN;

-- Get IDs to update
ids = [5, 2, 8, 1]

-- Sort them
sorted_ids = sort(ids)  -- [1, 2, 5, 8]

-- Lock in order
SELECT * FROM accounts WHERE id IN (1, 2, 5, 8) ORDER BY id FOR UPDATE;

-- Now safe to update in any order
UPDATE accounts SET balance = balance - 10 WHERE id = 5;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- etc.

COMMIT;
```

**Strategy 2: Lock Everything Upfront**

```sql
-- Identify all rows you'll need
BEGIN;

-- Lock all rows at the start
SELECT * FROM orders WHERE id = @order_id FOR UPDATE;
SELECT * FROM order_items WHERE order_id = @order_id FOR UPDATE;
SELECT * FROM inventory WHERE product_id IN (...) ORDER BY id FOR UPDATE;

-- Now safe to update anything
UPDATE orders SET status = 'processing' WHERE id = @order_id;
UPDATE inventory SET stock = stock - 1 WHERE product_id = @product_id;

COMMIT;
```

**Strategy 3: Keep Transactions Short**

```sql
-- BAD: Long transaction
BEGIN;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
-- Call external API (slow!)
-- Do complex calculations
-- Wait for user input
UPDATE orders SET status = 'complete' WHERE id = 1;
COMMIT;

-- GOOD: Short transaction
-- Do preparation work first (outside transaction)
-- Call external API
-- Do complex calculations

-- Then quick transaction
BEGIN;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
UPDATE orders SET status = 'complete' WHERE id = 1;
COMMIT;
```

**Strategy 4: Use NOWAIT or SKIP LOCKED**

```sql
-- Instead of waiting (and potentially deadlocking), fail fast
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- If locked, abort immediately with error instead of waiting
COMMIT;

-- Or skip locked rows
SELECT * FROM work_queue 
WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- Never waits, never deadlocks on queue processing
```

**Strategy 5: Retry Logic in Application**

```sql
-- Pseudocode for handling deadlocks
max_retries = 3
for attempt in range(max_retries):
    try:
        BEGIN
        -- do work
        COMMIT
        break  # Success
    except DeadlockDetected:
        ROLLBACK
        if attempt == max_retries - 1:
            raise  # Give up
        # Add exponential backoff
        sleep(2 ** attempt * 0.1)  # 0.1s, 0.2s, 0.4s
```

### Monitoring Deadlocks

**Check deadlock count:**

```sql
-- View deadlock statistics
SELECT datname, deadlocks 
FROM pg_stat_database 
WHERE datname = current_database();
```

**Enable deadlock logging:**

```sql
-- In postgresql.conf or via ALTER SYSTEM
log_lock_waits = on                    -- Log when waiting > deadlock_timeout
deadlock_timeout = '1s'                -- When to check for deadlocks
log_min_error_statement = 'error'      -- Log statements causing errors
```

**View lock waits:**

```sql
-- See which queries are waiting for locks
SELECT 
    blocked_locks.pid AS blocked_pid,
    blocked_activity.usename AS blocked_user,
    blocking_locks.pid AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query AS blocked_statement,
    blocking_activity.query AS blocking_statement
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity 
    ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks 
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity 
    ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

### Debugging Deadlocks from Logs

Deadlock log entry example:

```
ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 67890; 
        blocked by process 12346.
        Process 12346 waits for ShareLock on transaction 67889; 
        blocked by process 12345.
HINT: See server log for query details.
CONTEXT: while updating tuple (0,1) in relation "accounts"
```

**What to look for:**
1. Which tables/rows are involved
2. Which transactions are waiting
3. The query that triggered deadlock detection
4. Pattern of locks (order of operations)

**How to fix:**
1. Identify the conflicting operations
2. Determine lock order
3. Standardize lock order across application
4. Add appropriate SELECT FOR UPDATE statements

### Advanced: Lock Monitoring View

Create a helper view for easier lock monitoring:

```sql
CREATE VIEW lock_monitor AS
SELECT 
    l.pid,
    l.locktype,
    l.relation::regclass AS table_name,
    l.mode,
    l.granted,
    a.usename,
    a.query,
    a.state,
    age(now(), a.query_start) AS query_age
FROM pg_locks l
LEFT JOIN pg_stat_activity a ON l.pid = a.pid
WHERE l.pid != pg_backend_pid()  -- Exclude current session
ORDER BY a.query_start;

-- Use it
SELECT * FROM lock_monitor WHERE NOT granted;  -- See waiting locks
```

### Deadlock Prevention Checklist

- [ ] Always acquire locks in consistent order (e.g., by ID ascending)
- [ ] Lock all needed rows at the beginning of transaction
- [ ] Keep transactions as short as possible
- [ ] Avoid user input or external calls within transactions
- [ ] Use NOWAIT or SKIP LOCKED for queue processing
- [ ] Implement retry logic for deadlock errors
- [ ] Monitor deadlock frequency in production
- [ ] Enable lock wait logging for diagnosis
- [ ] Review and test high-concurrency code paths
- [ ] Document lock ordering conventions in code

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

1. Create test scenario:

```sql
CREATE TABLE accounts (
    id INTEGER PRIMARY KEY,
    balance NUMERIC(10,2)
);

INSERT INTO accounts VALUES (1, 1000), (2, 1000);
```

2. Reproduce a deadlock:

```sql
-- Terminal 1: Transaction 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- WAIT before next statement

-- Terminal 2: Transaction 2
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
-- Now try to update row 1
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
-- BLOCKS waiting for Transaction 1

-- Terminal 1: Continue Transaction 1
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- DEADLOCK DETECTED!
-- One transaction will fail
```

3. Fix with lock ordering:

```sql
-- Terminal 1: Transaction 1 (fixed)
BEGIN;
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- Terminal 2: Transaction 2 (fixed)
BEGIN;
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
COMMIT;

-- No deadlock! Transaction 2 waits, then completes after Transaction 1
```

4. Monitor deadlocks:

```sql
-- Check deadlock count
SELECT datname, deadlocks 
FROM pg_stat_database 
WHERE datname = current_database();

-- Enable logging
ALTER SYSTEM SET log_lock_waits = on;
ALTER SYSTEM SET deadlock_timeout = '1s';
SELECT pg_reload_conf();

-- Reproduce deadlock from step 2
-- Check PostgreSQL logs for detailed deadlock information
```

5. Practice NOWAIT pattern:

```sql
-- Connection 1
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- Holds lock

-- Connection 2
DO $$
BEGIN
    BEGIN
        PERFORM * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
        RAISE NOTICE 'Lock acquired successfully';
    EXCEPTION WHEN lock_not_available THEN
        RAISE NOTICE 'Could not acquire lock, row is busy';
    END;
END $$;

-- Connection 1
COMMIT;
```

### Key Takeaways

1. **ACID guarantees reliability** - Atomicity, Consistency, Isolation, Durability ensure data integrity
2. **Isolation levels trade consistency for performance** - Choose based on your consistency requirements
3. **MVCC enables high concurrency** - Readers never block writers, writers never block readers
4. **Explicit locks provide fine-grained control** - Use FOR UPDATE, SKIP LOCKED for specific scenarios
5. **Deadlock prevention requires design** - Consistent lock ordering and short transactions are essential
