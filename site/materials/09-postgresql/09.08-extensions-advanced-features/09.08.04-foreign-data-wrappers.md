## Introduction

Foreign Data Wrappers (FDWs) allow PostgreSQL to access and query data from external sources as if they were local tables. They implement the SQL/MED (Management of External Data) standard, enabling you to integrate data from other PostgreSQL servers, other database systems, flat files, web services, and more—all using standard SQL.

## Key Concepts Summary

### What are Foreign Data Wrappers?

Foreign Data Wrappers are libraries that enable PostgreSQL to communicate with external data sources. They hide the complexity of connections and data access behind a standard SQL interface.

**Architecture:**
```
PostgreSQL Database
    ↓
Foreign Data Wrapper (FDW)
    ↓
External Data Source (PostgreSQL, MySQL, MongoDB, CSV, API, etc.)
```

**Key components:**
- **Foreign Data Wrapper:** The extension that handles communication
- **Foreign Server:** Connection details to the external source
- **User Mapping:** Authentication credentials
- **Foreign Table:** Table definition that maps to external data

### When to Use FDWs

✅ **Good use cases:**
- Querying data from multiple databases
- Data federation and consolidation
- Migrating data between systems
- Accessing legacy systems
- Hybrid cloud architectures
- Reporting across multiple data sources
- Accessing external APIs or files from SQL

❌ **Avoid when:**
- High-frequency transactional workloads (network latency)
- Large data transfers (slow, consider ETL instead)
- Need for strong consistency across sources
- Complex joins across remote tables (can be slow)

## Setting Up postgres_fdw

### Step 1: Install the Extension

```sql
-- Install postgres_fdw extension
CREATE EXTENSION postgres_fdw;

-- Verify installation
SELECT * FROM pg_extension WHERE extname = 'postgres_fdw';
```

### Step 2: Create Foreign Server

```sql
-- Define connection to remote PostgreSQL server
CREATE SERVER remote_pg
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (
    host 'remote-host.example.com',
    port '5432',
    dbname 'remote_database'
);

-- View foreign servers
SELECT * FROM pg_foreign_server;
```

**Common options:**
- `host`: Remote server hostname or IP
- `port`: PostgreSQL port (default 5432)
- `dbname`: Database name on remote server
- `use_remote_estimate`: Use remote statistics for query planning (default false)
- `fdw_startup_cost`: Cost estimate for starting foreign scan
- `fdw_tuple_cost`: Cost estimate per retrieved row

### Step 3: Create User Mapping

```sql
-- Map local user to remote credentials
CREATE USER MAPPING FOR current_user
SERVER remote_pg
OPTIONS (
    user 'remote_username',
    password 'remote_password'
);

-- Alternatively, use same credentials for all local users
CREATE USER MAPPING FOR PUBLIC
SERVER remote_pg
OPTIONS (
    user 'remote_readonly',
    password 'secure_password'
);

-- View user mappings
SELECT * FROM pg_user_mappings;
```

### Step 4: Create Foreign Tables

#### Option A: Manual Definition

```sql
-- Manually define foreign table structure
CREATE FOREIGN TABLE remote_customers (
    customer_id INT,
    customer_name TEXT,
    email TEXT,
    country TEXT,
    created_at TIMESTAMP
) SERVER remote_pg
OPTIONS (
    schema_name 'public',
    table_name 'customers'
);
```

#### Option B: Import Foreign Schema (Recommended)

```sql
-- Import all tables from remote schema
IMPORT FOREIGN SCHEMA public
FROM SERVER remote_pg
INTO local_schema;

-- Import specific tables only
IMPORT FOREIGN SCHEMA public
LIMIT TO (customers, orders)
FROM SERVER remote_pg
INTO local_schema;

-- Import all except specific tables
IMPORT FOREIGN SCHEMA public
EXCEPT (audit_logs, temp_data)
FROM SERVER remote_pg
INTO local_schema;
```

### Step 5: Query Foreign Tables

```sql
-- Query foreign table like a local table
SELECT * FROM remote_customers
WHERE country = 'USA'
LIMIT 10;

-- Join local and foreign tables
SELECT 
    l.order_id,
    l.order_date,
    r.customer_name,
    r.email
FROM local_orders l
JOIN remote_customers r ON l.customer_id = r.customer_id
WHERE l.order_date >= '2024-01-01';
```

## Advanced Configuration

### Connection Pooling

```sql
-- Enable connection reuse
CREATE SERVER remote_pg
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (
    host 'remote-host.example.com',
    port '5432',
    dbname 'remote_database',
    fetch_size '1000',  -- Fetch rows in batches
    use_remote_estimate 'true'  -- Use remote statistics
);
```

### Read-Only Access

```sql
-- Create read-only user mapping for safety
CREATE USER MAPPING FOR app_user
SERVER remote_pg
OPTIONS (
    user 'readonly_user',
    password 'password'
);

-- Remote user has SELECT-only privileges
-- Prevents accidental modifications
```

### SSL/TLS Connections

```sql
CREATE SERVER secure_remote_pg
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (
    host 'remote-host.example.com',
    port '5432',
    dbname 'remote_database',
    sslmode 'require',  -- require, verify-ca, or verify-full
    sslcert '/path/to/client-cert.pem',
    sslkey '/path/to/client-key.pem',
    sslrootcert '/path/to/ca-cert.pem'
);
```

## Practical Examples

### Example 1: Cross-Database Reporting

```sql
-- Scenario: Sales database separate from warehouse database

-- On reporting database, set up FDW to sales database
CREATE EXTENSION postgres_fdw;

CREATE SERVER sales_db
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (host 'sales-db.internal', dbname 'sales', port '5432');

CREATE USER MAPPING FOR CURRENT_USER
SERVER sales_db
OPTIONS (user 'reporting_user', password 'password');

-- Import sales tables
IMPORT FOREIGN SCHEMA public
LIMIT TO (orders, order_items)
FROM SERVER sales_db
INTO sales_schema;

-- Set up FDW to warehouse database
CREATE SERVER warehouse_db
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (host 'warehouse-db.internal', dbname 'inventory', port '5432');

CREATE USER MAPPING FOR CURRENT_USER
SERVER warehouse_db
OPTIONS (user 'reporting_user', password 'password');

IMPORT FOREIGN SCHEMA public
LIMIT TO (products, inventory)
FROM SERVER warehouse_db
INTO warehouse_schema;

-- Cross-database reporting query
CREATE VIEW unified_sales_report AS
SELECT 
    o.order_id,
    o.order_date,
    p.product_name,
    oi.quantity,
    oi.unit_price,
    i.stock_quantity
FROM sales_schema.orders o
JOIN sales_schema.order_items oi ON o.order_id = oi.order_id
JOIN warehouse_schema.products p ON oi.product_id = p.product_id
LEFT JOIN warehouse_schema.inventory i ON p.product_id = i.product_id;

-- Query the unified view
SELECT * FROM unified_sales_report
WHERE order_date >= CURRENT_DATE - INTERVAL '30 days';
```

### Example 2: Data Migration with FDW

```sql
-- Migrate data from legacy to new database

-- On new database, connect to legacy
CREATE EXTENSION postgres_fdw;

CREATE SERVER legacy_db
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (host 'legacy-server', dbname 'old_system', port '5432');

CREATE USER MAPPING FOR CURRENT_USER
SERVER legacy_db
OPTIONS (user 'migration_user', password 'password');

-- Import legacy schema
IMPORT FOREIGN SCHEMA public
FROM SERVER legacy_db
INTO legacy;

-- Migrate data with transformations
INSERT INTO customers (customer_id, name, email, migrated_at)
SELECT 
    id,
    first_name || ' ' || last_name AS name,
    LOWER(email_address) AS email,
    NOW() AS migrated_at
FROM legacy.old_customers
WHERE active = true;

-- Verify migration
SELECT 
    (SELECT COUNT(*) FROM legacy.old_customers WHERE active = true) AS source_count,
    (SELECT COUNT(*) FROM customers WHERE migrated_at IS NOT NULL) AS migrated_count;
```

### Example 3: Multi-Tenant Data Consolidation

```sql
-- Consolidate data from multiple tenant databases

-- Connect to tenant 1 database
CREATE SERVER tenant1_db
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (host 'tenant1.internal', dbname 'app_db', port '5432');

CREATE USER MAPPING FOR CURRENT_USER
SERVER tenant1_db
OPTIONS (user 'readonly', password 'password');

CREATE FOREIGN TABLE tenant1_users (
    user_id INT,
    username TEXT,
    email TEXT,
    created_at TIMESTAMP
) SERVER tenant1_db
OPTIONS (schema_name 'public', table_name 'users');

-- Connect to tenant 2 database
CREATE SERVER tenant2_db
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (host 'tenant2.internal', dbname 'app_db', port '5432');

CREATE USER MAPPING FOR CURRENT_USER
SERVER tenant2_db
OPTIONS (user 'readonly', password 'password');

CREATE FOREIGN TABLE tenant2_users (
    user_id INT,
    username TEXT,
    email TEXT,
    created_at TIMESTAMP
) SERVER tenant2_db
OPTIONS (schema_name 'public', table_name 'users');

-- Consolidated query across tenants
SELECT 
    1 AS tenant_id,
    COUNT(*) AS user_count,
    MAX(created_at) AS last_user_created
FROM tenant1_users
UNION ALL
SELECT 
    2 AS tenant_id,
    COUNT(*) AS user_count,
    MAX(created_at) AS last_user_created
FROM tenant2_users;
```

### Example 4: Read Replica for Analytics

```sql
-- Query read replica to avoid load on primary

-- Connect to read replica
CREATE SERVER replica_db
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (
    host 'replica.internal',
    dbname 'production',
    port '5432',
    fetch_size '10000',  -- Larger batches for analytics
    use_remote_estimate 'true'
);

CREATE USER MAPPING FOR analyst_user
SERVER replica_db
OPTIONS (user 'readonly', password 'password');

-- Import analytical tables
IMPORT FOREIGN SCHEMA public
LIMIT TO (events, sessions, conversions)
FROM SERVER replica_db
INTO replica;

-- Heavy analytical query runs on replica
SELECT 
    DATE(event_time) AS day,
    event_type,
    COUNT(*) AS event_count,
    COUNT(DISTINCT user_id) AS unique_users
FROM replica.events
WHERE event_time >= CURRENT_DATE - INTERVAL '90 days'
GROUP BY DATE(event_time), event_type
ORDER BY day DESC, event_count DESC;
```

## Modifying Foreign Data

### INSERT Operations

```sql
-- Insert into remote table
INSERT INTO remote_customers (customer_name, email, country)
VALUES ('John Doe', 'john@example.com', 'USA');

-- Batch insert
INSERT INTO remote_customers (customer_name, email, country)
SELECT name, email, country
FROM local_staging_customers;
```

### UPDATE Operations

```sql
-- Update remote data
UPDATE remote_customers
SET country = 'United States'
WHERE country = 'USA';

-- Update based on local data
UPDATE remote_customers r
SET email = l.new_email
FROM local_email_updates l
WHERE r.customer_id = l.customer_id;
```

### DELETE Operations

```sql
-- Delete from remote table
DELETE FROM remote_customers
WHERE created_at < '2020-01-01';
```

**Important:** Modifications depend on remote user permissions. Ensure the mapped user has appropriate privileges.

## Performance Optimization

### Use WHERE Clauses Effectively

```sql
-- Good: WHERE clause pushed to remote server
EXPLAIN (VERBOSE)
SELECT * FROM remote_customers
WHERE country = 'USA' AND created_at >= '2024-01-01';
-- Remote Filter: ((country = 'USA'::text) AND (created_at >= '2024-01-01'::timestamp))

-- Bad: Function prevents pushdown
SELECT * FROM remote_customers
WHERE UPPER(country) = 'USA';
-- Fetches all rows, filters locally
```

### Adjust fetch_size

```sql
-- Larger fetch_size for analytical queries
ALTER SERVER remote_pg
OPTIONS (ADD fetch_size '10000');

-- Smaller fetch_size for OLTP
ALTER SERVER remote_pg
OPTIONS (SET fetch_size '100');
```

### Use Remote Statistics

```sql
-- Enable remote query cost estimation
ALTER SERVER remote_pg
OPTIONS (ADD use_remote_estimate 'true');

-- Helps query planner make better decisions
EXPLAIN SELECT * FROM remote_customers
JOIN local_orders USING (customer_id);
```

### Minimize Data Transfer

```sql
-- Bad: Fetch all data then filter locally
SELECT * FROM (
    SELECT * FROM remote_large_table
) sub
WHERE important_column = 'value';

-- Good: Push filter to remote
SELECT * FROM remote_large_table
WHERE important_column = 'value';
```

## Other Foreign Data Wrappers

### file_fdw (CSV Files)

```sql
-- Read CSV files
CREATE EXTENSION file_fdw;

CREATE SERVER csv_server
FOREIGN DATA WRAPPER file_fdw;

CREATE FOREIGN TABLE customers_csv (
    customer_id INT,
    customer_name TEXT,
    email TEXT
) SERVER csv_server
OPTIONS (
    filename '/path/to/customers.csv',
    format 'csv',
    header 'true'
);

SELECT * FROM customers_csv;
```

### postgres_fdw Advanced: Async Execution

```sql
-- Enable async execution for parallel queries (PostgreSQL 14+)
ALTER SERVER remote_pg1 OPTIONS (ADD async_capable 'true');
ALTER SERVER remote_pg2 OPTIONS (ADD async_capable 'true');

-- Parallel query across multiple servers
SELECT 'server1' AS source, COUNT(*) FROM remote_pg1.customers
UNION ALL
SELECT 'server2' AS source, COUNT(*) FROM remote_pg2.customers;
-- Executes in parallel when possible
```

## Security Considerations

### Password Storage

```sql
-- Option 1: Store encrypted in pg_user_mappings (default)
CREATE USER MAPPING FOR user
SERVER remote
OPTIONS (user 'remote_user', password 'password');

-- Option 2: Use connection string (avoid hardcoded passwords)
-- Set up .pgpass file instead: hostname:port:database:username:password

-- Option 3: Use environment variables
-- On remote server: grant access via pg_hba.conf with cert authentication
```

### Limiting Access

```sql
-- Create role with limited FDW access
CREATE ROLE fdw_reader;
GRANT USAGE ON FOREIGN SERVER remote_pg TO fdw_reader;
GRANT SELECT ON ALL FOREIGN TABLES IN SCHEMA remote_schema TO fdw_reader;

-- Users in fdw_reader role can only read, not modify
```

### Auditing

```sql
-- Track FDW usage
SELECT 
    usename,
    application_name,
    client_addr,
    query
FROM pg_stat_activity
WHERE query LIKE '%FOREIGN%';
```

## Monitoring and Troubleshooting

### View Foreign Server Connections

```sql
-- Check active foreign server queries
SELECT * FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND query LIKE '%FROM remote_%';
```

### Debug Connection Issues

```sql
-- Test server connectivity
SELECT * FROM remote_customers LIMIT 1;
-- Error messages indicate connection or permission issues

-- Verify user mapping
SELECT * FROM pg_user_mappings WHERE srvname = 'remote_pg';

-- Check server options
SELECT * FROM pg_foreign_server WHERE srvname = 'remote_pg';
```

### Analyze Query Performance

```sql
-- See what's executed remotely vs locally
EXPLAIN (VERBOSE, COSTS)
SELECT * FROM remote_customers
WHERE country = 'USA';

-- Look for:
-- "Foreign Scan" - good (remote execution)
-- "Seq Scan" on foreign table - bad (fetching all data)
```

## Key Takeaways

- Foreign Data Wrappers enable accessing external data sources using SQL
- postgres_fdw is the most common FDW for connecting to other PostgreSQL databases
- Setup involves: extension, foreign server, user mapping, and foreign tables
- IMPORT FOREIGN SCHEMA automatically creates foreign table definitions
- FDWs are excellent for data federation, reporting, and migration
- Query performance depends on network latency and predicate pushdown
- Use WHERE clauses that can be pushed down to remote servers
- Enable `use_remote_estimate` for better query planning
- Consider FDWs for read-heavy analytical workloads, not high-frequency transactions
- Always use appropriate security measures for credentials and access control
- Monitor query performance with EXPLAIN to ensure efficient remote execution
