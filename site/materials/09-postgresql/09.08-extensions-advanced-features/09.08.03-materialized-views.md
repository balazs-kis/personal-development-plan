## Introduction

Materialized views are database objects that store the results of a query physically on disk. Unlike regular views, which execute their query every time they're accessed, materialized views cache the results for fast retrieval. They're ideal for expensive queries on data that doesn't need to be real-time, trading freshness for performance.

## Key Concepts Summary

### Views vs. Materialized Views

#### Regular Views

```sql
-- Regular view (virtual)
CREATE VIEW active_orders AS
SELECT 
    o.order_id,
    o.order_date,
    c.customer_name,
    SUM(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN customers c USING (customer_id)
JOIN order_items oi USING (order_id)
WHERE o.status = 'active'
GROUP BY o.order_id, o.order_date, c.customer_name;

-- Query view (executes underlying query every time)
SELECT * FROM active_orders WHERE order_date > '2024-01-01';
-- Full query execution: joins, aggregation, etc.
```

**Characteristics:**
- No data stored (virtual)
- Always returns current data
- Query executes on every access
- Can be slow for complex queries

#### Materialized Views

```sql
-- Materialized view (physical)
CREATE MATERIALIZED VIEW active_orders_mv AS
SELECT 
    o.order_id,
    o.order_date,
    c.customer_name,
    SUM(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN customers c USING (customer_id)
JOIN order_items oi USING (order_id)
WHERE o.status = 'active'
GROUP BY o.order_id, o.order_date, c.customer_name;

-- Query materialized view (reads cached data)
SELECT * FROM active_orders_mv WHERE order_date > '2024-01-01';
-- Fast: simple table scan on pre-computed results
```

**Characteristics:**
- Data stored on disk
- Returns cached results (may be stale)
- Fast queries (no re-computation)
- Requires manual refresh

### When to Use Materialized Views

✅ **Good use cases:**
- Complex queries with joins and aggregations
- Reports and dashboards (data can be slightly stale)
- Analytics and data warehousing
- Reducing load on production databases
- Pre-computing expensive calculations
- Data that changes infrequently relative to query frequency

❌ **Avoid when:**
- Need real-time data
- Source tables change frequently
- Simple queries that are already fast
- Storage is very limited
- Can't tolerate any staleness

## Creating Materialized Views

### Basic Syntax

```sql
CREATE MATERIALIZED VIEW view_name AS
query
[ WITH [ NO ] DATA ];
```

### Examples

```sql
-- Create with data (default)
CREATE MATERIALIZED VIEW monthly_sales AS
SELECT 
    DATE_TRUNC('month', order_date) AS month,
    COUNT(*) AS order_count,
    SUM(total_amount) AS total_sales
FROM orders
GROUP BY DATE_TRUNC('month', order_date);

-- Create without initial data (faster, but unusable until refreshed)
CREATE MATERIALIZED VIEW product_summary WITH NO DATA AS
SELECT 
    product_id,
    product_name,
    COUNT(*) AS order_count,
    AVG(quantity) AS avg_quantity
FROM order_items
JOIN products USING (product_id)
GROUP BY product_id, product_name;

-- Refresh before use
REFRESH MATERIALIZED VIEW product_summary;
```

### Creating Indexes

```sql
-- Materialized views can have indexes like regular tables
CREATE UNIQUE INDEX monthly_sales_month_idx ON monthly_sales (month);
CREATE INDEX product_summary_name_idx ON product_summary (product_name);

-- Indexes improve query performance on the materialized view
SELECT * FROM monthly_sales WHERE month = '2024-01-01';  -- Uses index
```

## Refreshing Materialized Views

### Full Refresh (Default)

```sql
-- Complete refresh (blocks reads during refresh)
REFRESH MATERIALIZED VIEW monthly_sales;
```

**Characteristics:**
- Replaces all data
- Blocks SELECT queries during refresh
- Required when no unique index exists
- Fastest refresh method

**Process:**
1. Executes underlying query
2. Replaces existing data atomically
3. Drops and recreates indexes
4. Blocks concurrent access

### Concurrent Refresh

```sql
-- Concurrent refresh (allows reads during refresh)
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales;
```

**Requirements:**
- Must have at least one UNIQUE index
- Index must be on column names only (no expressions)
- View must already be populated (can't use WITH NO DATA)

**Characteristics:**
- Allows concurrent SELECT queries
- Slower than regular refresh
- Better for production systems
- Uses more disk space during refresh

**Setting up for concurrent refresh:**

```sql
-- Step 1: Create materialized view
CREATE MATERIALIZED VIEW user_stats AS
SELECT 
    user_id,
    COUNT(*) AS activity_count,
    MAX(last_activity) AS last_seen
FROM user_activities
GROUP BY user_id;

-- Step 2: Create unique index (required)
CREATE UNIQUE INDEX user_stats_user_id_idx ON user_stats (user_id);

-- Step 3: Now concurrent refresh is possible
REFRESH MATERIALIZED VIEW CONCURRENTLY user_stats;
```

### Refresh with NO DATA

```sql
-- Clear data without executing query
REFRESH MATERIALIZED VIEW monthly_sales WITH NO DATA;

-- View becomes unscannable until refreshed with data
-- SELECT * FROM monthly_sales;  -- ERROR: materialized view not populated
```

## Refresh Strategies

### 1. Manual Refresh

```sql
-- Refresh when needed
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales;
```

**Use when:**
- Data changes infrequently
- You control when refresh happens
- Can coordinate with batch processing

### 2. Scheduled Refresh (pg_cron)

```sql
-- Install pg_cron extension
CREATE EXTENSION pg_cron;

-- Schedule nightly refresh at 2 AM
SELECT cron.schedule(
    'refresh-monthly-sales',
    '0 2 * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales$$
);

-- Schedule hourly refresh
SELECT cron.schedule(
    'refresh-user-stats',
    '0 * * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY user_stats$$
);

-- View scheduled jobs
SELECT * FROM cron.job;

-- Unschedule job
SELECT cron.unschedule('refresh-monthly-sales');
```

### 3. Trigger-Based Refresh

```sql
-- Refresh when source data changes (use with caution)
CREATE OR REPLACE FUNCTION refresh_monthly_sales_trigger()
RETURNS TRIGGER AS $$
BEGIN
    -- Queue refresh (don't refresh immediately to avoid locks)
    PERFORM pg_notify('refresh_mv', 'monthly_sales');
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER orders_refresh_mv
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH STATEMENT
EXECUTE FUNCTION refresh_monthly_sales_trigger();

-- Separate process listens for notifications and refreshes
-- (Typically implemented in application code)
```

**Warning:** Trigger-based refresh can cause performance issues with high-frequency updates. Use scheduled refresh instead.

### 4. Application-Controlled Refresh

```sql
-- Application refreshes after batch operations
BEGIN;
    -- Batch insert/update operations
    INSERT INTO orders (customer_id, order_date, total_amount)
    SELECT * FROM staging.orders;
    
    -- Refresh materialized view
    REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales;
COMMIT;
```

## Practical Examples

### Example 1: Dashboard Metrics

```sql
-- Complex dashboard query
CREATE MATERIALIZED VIEW dashboard_metrics AS
SELECT 
    DATE(NOW()) AS report_date,
    COUNT(DISTINCT user_id) AS active_users,
    COUNT(DISTINCT order_id) AS total_orders,
    SUM(order_total) AS total_revenue,
    AVG(order_total) AS avg_order_value,
    COUNT(DISTINCT CASE WHEN is_first_order THEN user_id END) AS new_customers
FROM (
    SELECT 
        o.user_id,
        o.order_id,
        o.total AS order_total,
        ROW_NUMBER() OVER (PARTITION BY o.user_id ORDER BY o.order_date) = 1 AS is_first_order
    FROM orders o
    WHERE o.order_date >= DATE_TRUNC('month', NOW())
) subquery;

-- Index for fast access
CREATE UNIQUE INDEX dashboard_metrics_date_idx ON dashboard_metrics (report_date);

-- Schedule daily refresh at 1 AM
SELECT cron.schedule(
    'refresh-dashboard',
    '0 1 * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY dashboard_metrics$$
);

-- Fast dashboard query
SELECT * FROM dashboard_metrics WHERE report_date = CURRENT_DATE;
```

### Example 2: Product Analytics

```sql
-- Product performance summary
CREATE MATERIALIZED VIEW product_performance AS
SELECT 
    p.product_id,
    p.product_name,
    p.category,
    COUNT(DISTINCT o.order_id) AS times_ordered,
    SUM(oi.quantity) AS units_sold,
    SUM(oi.quantity * oi.unit_price) AS total_revenue,
    AVG(r.rating) AS avg_rating,
    COUNT(DISTINCT r.review_id) AS review_count
FROM products p
LEFT JOIN order_items oi USING (product_id)
LEFT JOIN orders o USING (order_id)
LEFT JOIN reviews r USING (product_id)
WHERE o.order_date >= NOW() - INTERVAL '90 days'
GROUP BY p.product_id, p.product_name, p.category;

-- Indexes for different access patterns
CREATE UNIQUE INDEX product_perf_id_idx ON product_performance (product_id);
CREATE INDEX product_perf_category_idx ON product_performance (category);
CREATE INDEX product_perf_revenue_idx ON product_performance (total_revenue DESC);

-- Refresh daily
SELECT cron.schedule(
    'refresh-product-performance',
    '0 3 * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY product_performance$$
);
```

### Example 3: Pre-Aggregated Time Series

```sql
-- Hourly metrics for fast charting
CREATE MATERIALIZED VIEW hourly_metrics AS
SELECT 
    DATE_TRUNC('hour', event_time) AS hour,
    event_type,
    COUNT(*) AS event_count,
    COUNT(DISTINCT user_id) AS unique_users
FROM events
WHERE event_time >= NOW() - INTERVAL '30 days'
GROUP BY DATE_TRUNC('hour', event_time), event_type;

-- Composite unique index
CREATE UNIQUE INDEX hourly_metrics_hour_type_idx 
    ON hourly_metrics (hour, event_type);

-- Refresh every hour
SELECT cron.schedule(
    'refresh-hourly-metrics',
    '5 * * * *',  -- Run at 5 minutes past each hour
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY hourly_metrics$$
);

-- Fast queries for charts
SELECT hour, event_count
FROM hourly_metrics
WHERE event_type = 'page_view'
  AND hour >= NOW() - INTERVAL '7 days'
ORDER BY hour;
```

### Example 4: Incremental Refresh Pattern

```sql
-- Track last refresh time
CREATE TABLE mv_refresh_log (
    view_name TEXT PRIMARY KEY,
    last_refresh TIMESTAMP NOT NULL
);

-- Function for incremental-style refresh
CREATE OR REPLACE FUNCTION refresh_user_stats_incremental()
RETURNS VOID AS $$
DECLARE
    last_refresh TIMESTAMP;
BEGIN
    -- Get last refresh time
    SELECT last_refresh INTO last_refresh
    FROM mv_refresh_log
    WHERE view_name = 'user_stats';
    
    -- If first run, set to beginning of time
    IF last_refresh IS NULL THEN
        last_refresh := '1970-01-01'::TIMESTAMP;
    END IF;
    
    -- Update only changed users (delete and re-insert)
    DELETE FROM user_stats
    WHERE user_id IN (
        SELECT DISTINCT user_id
        FROM user_activities
        WHERE updated_at > last_refresh
    );
    
    INSERT INTO user_stats
    SELECT 
        user_id,
        COUNT(*) AS activity_count,
        MAX(last_activity) AS last_seen
    FROM user_activities
    WHERE user_id IN (
        SELECT DISTINCT user_id
        FROM user_activities
        WHERE updated_at > last_refresh
    )
    GROUP BY user_id;
    
    -- Update refresh log
    INSERT INTO mv_refresh_log (view_name, last_refresh)
    VALUES ('user_stats', NOW())
    ON CONFLICT (view_name) DO UPDATE
    SET last_refresh = NOW();
END;
$$ LANGUAGE plpgsql;

-- Note: This requires user_stats to be a regular table, not a materialized view
-- It simulates incremental refresh behavior
```

## Performance Comparison

### Measuring Query Performance

```sql
-- Regular view query time
\timing on
SELECT * FROM active_orders;  -- Executes full query
\timing off

-- Materialized view query time
\timing on
SELECT * FROM active_orders_mv;  -- Reads cached data
\timing off

-- With EXPLAIN ANALYZE
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM active_orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM active_orders_mv;
```

**Typical results:**
- Regular view: 1000-5000ms for complex queries
- Materialized view: 10-50ms (100x faster)

### Refresh Performance

```sql
-- Time refresh operation
\timing on
REFRESH MATERIALIZED VIEW monthly_sales;
\timing off

-- Compare concurrent vs non-concurrent
\timing on
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales;
\timing off

-- Concurrent refresh is typically 2-3x slower but allows queries
```

## Monitoring Materialized Views

### View Metadata

```sql
-- List all materialized views
SELECT 
    schemaname,
    matviewname,
    pg_size_pretty(pg_total_relation_size(schemaname || '.' || matviewname)) AS size,
    ispopulated
FROM pg_matviews
ORDER BY pg_total_relation_size(schemaname || '.' || matviewname) DESC;
```

### Refresh History

```sql
-- Create table to log refreshes
CREATE TABLE mv_refresh_history (
    view_name TEXT NOT NULL,
    refresh_start TIMESTAMP NOT NULL,
    refresh_end TIMESTAMP,
    duration_ms INT,
    success BOOLEAN,
    error_message TEXT
);

-- Function to log refreshes
CREATE OR REPLACE FUNCTION refresh_mv_with_logging(mv_name TEXT)
RETURNS VOID AS $$
DECLARE
    start_time TIMESTAMP := NOW();
    end_time TIMESTAMP;
    duration INT;
BEGIN
    -- Attempt refresh
    EXECUTE FORMAT('REFRESH MATERIALIZED VIEW CONCURRENTLY %I', mv_name);
    
    end_time := NOW();
    duration := EXTRACT(EPOCH FROM (end_time - start_time)) * 1000;
    
    -- Log success
    INSERT INTO mv_refresh_history 
    VALUES (mv_name, start_time, end_time, duration, true, NULL);
    
EXCEPTION WHEN OTHERS THEN
    -- Log failure
    INSERT INTO mv_refresh_history 
    VALUES (mv_name, start_time, NOW(), NULL, false, SQLERRM);
    RAISE;
END;
$$ LANGUAGE plpgsql;

-- Use in scheduled jobs
SELECT cron.schedule(
    'refresh-monthly-sales-logged',
    '0 2 * * *',
    $$SELECT refresh_mv_with_logging('monthly_sales')$$
);
```

## Best Practices

### 1. Create Appropriate Indexes

```sql
-- Always create at least one unique index for concurrent refresh
CREATE UNIQUE INDEX mv_primary_key_idx ON my_mv (id);

-- Create indexes based on query patterns
CREATE INDEX mv_filter_idx ON my_mv (category, created_date);
```

### 2. Choose Refresh Frequency Wisely

```sql
-- Consider:
-- - How often source data changes
-- - How stale data can be
-- - Refresh operation cost

-- High-frequency data: hourly refresh
-- Daily reports: nightly refresh
-- Weekly analytics: weekly refresh
```

### 3. Monitor Refresh Duration

```sql
-- Alert if refresh takes too long
SELECT 
    view_name,
    AVG(duration_ms) AS avg_duration_ms,
    MAX(duration_ms) AS max_duration_ms
FROM mv_refresh_history
WHERE refresh_start >= NOW() - INTERVAL '7 days'
GROUP BY view_name
HAVING MAX(duration_ms) > 300000;  -- More than 5 minutes
```

### 4. Use CONCURRENTLY in Production

```sql
-- Always use CONCURRENTLY to avoid blocking queries
REFRESH MATERIALIZED VIEW CONCURRENTLY my_mv;

-- Exception: During maintenance windows
-- Regular refresh is faster when users aren't querying
```

### 5. Consider Partitioning for Large MVs

```sql
-- For very large materialized views, consider partitioning source table
-- Then create multiple smaller MVs instead of one large one

-- Example: Instead of one large MV
-- CREATE MATERIALIZED VIEW all_orders_summary AS...

-- Create per-month MVs
CREATE MATERIALIZED VIEW orders_summary_2024_01 AS
SELECT * FROM orders_summary WHERE month = '2024-01-01';

-- Union view for convenience
CREATE VIEW orders_summary_all AS
SELECT * FROM orders_summary_2024_01
UNION ALL
SELECT * FROM orders_summary_2024_02
-- ... etc
```

## Common Mistakes to Avoid

### 1. Forgetting Unique Index for CONCURRENTLY

```sql
-- ERROR: cannot refresh materialized view "my_mv" concurrently
-- HINT: Create a unique index with no WHERE clause on one or more columns.

-- Fix: Create unique index
CREATE UNIQUE INDEX my_mv_id_idx ON my_mv (id);
```

### 2. Using Materialized Views for Real-Time Data

```sql
-- Bad: MV for data that must be current
CREATE MATERIALIZED VIEW current_inventory AS
SELECT product_id, SUM(quantity) AS stock
FROM inventory_transactions
GROUP BY product_id;

-- Better: Use regular view or cache at application layer
```

### 3. Not Monitoring Staleness

```sql
-- Add timestamp to track freshness
CREATE MATERIALIZED VIEW dashboard_metrics AS
SELECT 
    NOW() AS refreshed_at,  -- Track when data was last computed
    DATE(NOW()) AS report_date,
    -- ... other metrics
FROM orders;

-- Query shows data age
SELECT 
    report_date,
    active_users,
    NOW() - refreshed_at AS data_age
FROM dashboard_metrics;
```

## Practice Exercise

Create a materialized view for an analytics dashboard:

1. Create a `user_engagement_summary` materialized view with:
   - User activity metrics (logins, actions, time spent)
   - Aggregated over last 30 days
2. Add appropriate indexes
3. Set up concurrent refresh
4. Schedule automatic refresh
5. Monitor query performance improvement

**Example solution:**

```sql
-- Step 1: Create materialized view
CREATE MATERIALIZED VIEW user_engagement_summary AS
SELECT 
    u.user_id,
    u.username,
    u.email,
    COUNT(DISTINCT DATE(a.activity_time)) AS active_days,
    COUNT(a.activity_id) AS total_actions,
    SUM(a.duration_seconds) AS total_time_seconds,
    MAX(a.activity_time) AS last_activity,
    NOW() AS refreshed_at
FROM users u
LEFT JOIN user_activities a ON u.user_id = a.user_id
WHERE a.activity_time >= NOW() - INTERVAL '30 days'
   OR a.activity_time IS NULL
GROUP BY u.user_id, u.username, u.email;

-- Step 2: Add indexes
CREATE UNIQUE INDEX user_engagement_user_id_idx 
    ON user_engagement_summary (user_id);
CREATE INDEX user_engagement_last_activity_idx 
    ON user_engagement_summary (last_activity DESC);

-- Step 3: Test concurrent refresh
REFRESH MATERIALIZED VIEW CONCURRENTLY user_engagement_summary;

-- Step 4: Schedule refresh (hourly)
CREATE EXTENSION IF NOT EXISTS pg_cron;

SELECT cron.schedule(
    'refresh-user-engagement',
    '0 * * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY user_engagement_summary$$
);

-- Step 5: Performance comparison
-- Complex query with joins (slow)
\timing on
SELECT 
    u.user_id,
    COUNT(DISTINCT DATE(a.activity_time)) AS active_days
FROM users u
LEFT JOIN user_activities a ON u.user_id = a.user_id
WHERE a.activity_time >= NOW() - INTERVAL '30 days'
GROUP BY u.user_id
LIMIT 100;
\timing off

-- Materialized view query (fast)
\timing on
SELECT * FROM user_engagement_summary
LIMIT 100;
\timing off
```

## Key Takeaways

- Materialized views cache query results for fast access
- Use when queries are expensive and data can tolerate staleness
- Regular refresh replaces all data; concurrent refresh allows reads during refresh
- Concurrent refresh requires a unique index
- Schedule refreshes based on data change frequency and staleness tolerance
- Materialized views are ideal for dashboards, reports, and analytics
- Monitor refresh duration and query performance
- Create indexes on materialized views like regular tables
- Consider incremental refresh patterns for very large datasets
- Balance refresh frequency with system load and staleness requirements
