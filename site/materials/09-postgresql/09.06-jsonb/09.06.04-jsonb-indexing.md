---

## Introduction

While JSONB queries are faster than JSON due to binary storage, unindexed JSONB columns still require sequential scans for most queries. GIN (Generalized Inverted Index) indexes are specifically designed for JSONB and can dramatically improve query performance—often by 100x or more.

Understanding how to properly index JSONB data is critical for production systems. The right indexing strategy can make the difference between sub-second queries and queries that take minutes to complete.

## Key Concepts Summary

### Why Index JSONB?

**Without index (sequential scan):**
```sql
EXPLAIN ANALYZE
SELECT * FROM products 
WHERE attributes @> '{"brand": "Apple"}';

-- Seq Scan on products  (cost=0.00..1693.00 rows=50 width=100)
--                        (actual time=125.123..250.456 rows=42)
-- Execution Time: 251.234 ms
```

**With GIN index:**
```sql
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);

EXPLAIN ANALYZE
SELECT * FROM products 
WHERE attributes @> '{"brand": "Apple"}';

-- Bitmap Heap Scan on products  (cost=12.00..120.00 rows=42 width=100)
--                                (actual time=1.234..2.456 rows=42)
--   Recheck Cond: (attributes @> '{"brand": "Apple"}')
--   ->  Bitmap Index Scan on idx_products_attributes
-- Execution Time: 2.789 ms
```

**Performance improvement: 90x faster!**

### GIN Index Basics

**Creating a GIN Index:**

```sql
-- Basic GIN index on entire JSONB column
CREATE INDEX idx_data_gin ON table_name USING GIN (jsonb_column);

-- Named index
CREATE INDEX idx_users_profile_gin ON users USING GIN (profile);

-- Concurrent creation (doesn't lock table)
CREATE INDEX CONCURRENTLY idx_data_gin ON table_name USING GIN (jsonb_column);
```

**How GIN Works:**

GIN creates an inverted index structure:
- Breaks apart JSONB document into (key, value) pairs
- Each unique key-value pair stored once
- Maintains posting lists of rows containing each pair
- Extremely efficient for containment queries

Example document: `{"brand": "Apple", "price": 999}`
- Index entries: `brand => Apple` → [row_id]
- Index entries: `price => 999` → [row_id]

### Default GIN vs `jsonb_path_ops`

**Default GIN Operator Class:**

```sql
CREATE INDEX idx_data_gin ON products USING GIN (attributes);
```

**Supports all JSONB operators:**
- `@>` (contains)
- `<@` (contained in)
- `?` (key exists)
- `?&` (all keys exist)
- `?|` (any key exists)

**Stores:** Keys and values

**jsonb_path_ops Operator Class:**

```sql
CREATE INDEX idx_data_gin ON products USING GIN (attributes jsonb_path_ops);
```

**Supports only:**
- `@>` (contains)

**Stores:** Only values (smaller index)

**Comparison:**

| Feature | Default GIN | jsonb_path_ops |
|---------|-------------|----------------|
| Size | Larger | 30-50% smaller |
| Supported operators | All (`@>`, `?`, `?&`, `?|`) | Only `@>` |
| Best for | General purpose | Containment queries only |
| Performance | Good | Better for `@>` |

**When to use each:**

```sql
-- Use default if you need key existence checks
CREATE INDEX idx_default ON products USING GIN (attributes);
SELECT * FROM products WHERE attributes ? 'warranty';  -- Uses index

-- Use jsonb_path_ops if you only do containment
CREATE INDEX idx_path_ops ON products USING GIN (attributes jsonb_path_ops);
SELECT * FROM products WHERE attributes @> '{"brand": "Apple"}';  -- Uses index
SELECT * FROM products WHERE attributes ? 'warranty';  -- Cannot use index
```

### Indexing Specific Fields

Instead of indexing the entire JSONB column, index specific frequently-queried fields:

```sql
-- Index specific top-level field
CREATE INDEX idx_brand ON products USING GIN ((attributes->'brand'));

-- Query that uses this index
SELECT * FROM products 
WHERE attributes->'brand' = '"Apple"';  -- Note: JSONB value with quotes

-- Index nested field
CREATE INDEX idx_cpu ON products USING GIN ((attributes->'specs'->'cpu'));

-- Query
SELECT * FROM products 
WHERE attributes->'specs'->'cpu' = '"Intel i7"';
```

**Advantages:**
- Smaller index size
- Faster queries on specific fields
- Can combine multiple single-field indexes

**Best practice:**

```sql
-- Instead of one large index on everything
CREATE INDEX idx_attrs_all ON products USING GIN (attributes);

-- Create targeted indexes on commonly queried fields
CREATE INDEX idx_attrs_brand ON products USING GIN ((attributes->'brand'));
CREATE INDEX idx_attrs_category ON products USING GIN ((attributes->'category'));
CREATE INDEX idx_attrs_price ON products USING GIN ((attributes->'price'));
```

### Expression Indexes

Create indexes on computed JSONB values:

```sql
-- Index extracted text value (for equality/comparison)
CREATE INDEX idx_brand_text ON products ((attributes->>'brand'));

-- Query using text value
SELECT * FROM products 
WHERE attributes->>'brand' = 'Apple';  -- Uses index (no quotes needed)

-- Index computed value
CREATE INDEX idx_total_price ON orders ((
    (data->>'subtotal')::numeric + (data->>'tax')::numeric
));

-- Partial index on JSONB condition
CREATE INDEX idx_active_users ON users (profile) 
WHERE profile->>'status' = 'active';

-- Index on array length
CREATE INDEX idx_tag_count ON articles ((jsonb_array_length(tags)));
```

### Operator Support

**Operators that can use GIN indexes:**

```sql
-- Containment (always uses GIN if available)
SELECT * FROM products WHERE attributes @> '{"brand": "Apple"}';

-- Key existence (uses default GIN, not jsonb_path_ops)
SELECT * FROM products WHERE attributes ? 'warranty';

-- Multiple key existence
SELECT * FROM products WHERE attributes ?& ARRAY['brand', 'price'];

-- Any key existence
SELECT * FROM products WHERE attributes ?| ARRAY['sale', 'clearance'];
```

**Operators that CANNOT use GIN indexes:**

```sql
-- Extraction operators (need expression index)
SELECT * FROM products WHERE attributes->>'brand' = 'Apple';  -- Sequential scan

-- Solution: Create expression index
CREATE INDEX idx_brand_text ON products ((attributes->>'brand'));
-- Now the query can use the index
```

### Multi-Column Indexes

Combine JSONB with other columns:

```sql
-- Composite index with regular column and JSONB
CREATE INDEX idx_category_attrs ON products (category, attributes jsonb_path_ops);

-- Benefits queries that filter on both
SELECT * FROM products 
WHERE category = 'electronics' 
  AND attributes @> '{"brand": "Apple"}';
```

### Index Maintenance

**Monitor index usage:**

```sql
-- Check if index is being used
SELECT 
    schemaname,
    tablename,
    indexname,
    idx_scan,  -- Number of index scans
    idx_tup_read,  -- Tuples returned by index
    idx_tup_fetch  -- Tuples fetched from table
FROM pg_stat_user_indexes
WHERE indexname LIKE '%jsonb%'
ORDER BY idx_scan DESC;

-- Find unused indexes
SELECT 
    schemaname,
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexname LIKE '%gin%'
ORDER BY pg_relation_size(indexrelid) DESC;
```

**Reindex when needed:**

```sql
-- Reindex single index
REINDEX INDEX idx_products_attributes;

-- Reindex all indexes on table
REINDEX TABLE products;

-- Concurrent reindex (PostgreSQL 12+, doesn't lock)
REINDEX INDEX CONCURRENTLY idx_products_attributes;
```

**Index bloat:**

```sql
-- Estimate index bloat
SELECT 
    schemaname,
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan
FROM pg_stat_user_indexes
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_relation_size(indexrelid) DESC;
```

### Performance Best Practices

**1. Don't GIN the whole column if you don't need to**

```sql
-- BAD: Indexes everything (large, slow to update)
CREATE INDEX idx_all ON products USING GIN (attributes);

-- GOOD: Index only what you query
CREATE INDEX idx_brand ON products USING GIN ((attributes->'brand'));
CREATE INDEX idx_category ON products USING GIN ((attributes->'category'));
```

**2. Use jsonb_path_ops for containment-only queries**

```sql
-- If you only use @> operator
CREATE INDEX idx_attrs ON products USING GIN (attributes jsonb_path_ops);
```

**3. Consider partial indexes**

```sql
-- Only index active products
CREATE INDEX idx_active_attrs ON products USING GIN (attributes)
WHERE status = 'active';
```

**4. Monitor index size vs benefit**

```sql
-- Check index size
SELECT 
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan
FROM pg_stat_user_indexes
WHERE tablename = 'products';
```

**5. Create indexes concurrently in production**

```sql
-- Doesn't lock table for writes
CREATE INDEX CONCURRENTLY idx_attrs ON products USING GIN (attributes);
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

1. Create test table with data:

```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    category TEXT NOT NULL,
    attributes JSONB
);

-- Insert 10,000 products
INSERT INTO products (name, category, attributes)
SELECT 
    'Product ' || i,
    CASE (i % 3)
        WHEN 0 THEN 'electronics'
        WHEN 1 THEN 'books'
        ELSE 'clothing'
    END,
    jsonb_build_object(
        'brand', CASE (i % 5)
            WHEN 0 THEN 'BrandA'
            WHEN 1 THEN 'BrandB'
            ELSE 'BrandC'
        END,
        'price', (random() * 1000)::int,
        'in_stock', (random() > 0.3)
    )
FROM generate_series(1, 10000) i;

ANALYZE products;
```

2. Test query without index:

```sql
-- Measure performance without index
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products 
WHERE attributes @> '{"brand": "BrandA"}';
-- Note the execution time and plan (Sequential Scan)
```

3. Create and test GIN index:

```sql
-- Create default GIN index
CREATE INDEX idx_products_attrs_gin ON products USING GIN (attributes);

ANALYZE products;

-- Test same query
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products 
WHERE attributes @> '{"brand": "BrandA"}';
-- Should now use Bitmap Index Scan, much faster
```

4. Compare jsonb_path_ops:

```sql
-- Drop previous index
DROP INDEX idx_products_attrs_gin;

-- Create jsonb_path_ops index
CREATE INDEX idx_products_attrs_ops ON products USING GIN (attributes jsonb_path_ops);

ANALYZE products;

-- Test containment query
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products 
WHERE attributes @> '{"brand": "BrandA"}';
-- Still fast

-- Test key existence query
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products 
WHERE attributes ? 'warranty';
-- Cannot use jsonb_path_ops index!
```

5. Create field-specific indexes:

```sql
-- Drop general index
DROP INDEX idx_products_attrs_ops;

-- Create indexes on specific fields
CREATE INDEX idx_brand ON products USING GIN ((attributes->'brand'));
CREATE INDEX idx_price_text ON products ((attributes->>'price'));

ANALYZE products;

-- Test field-specific query
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products 
WHERE attributes->'brand' = '"BrandA"';
-- Uses idx_brand

-- Test text extraction query
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products 
WHERE attributes->>'brand' = 'BrandA';
-- Might not use index (need expression index on text)

-- Create text expression index
CREATE INDEX idx_brand_text ON products ((attributes->>'brand'));

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products 
WHERE attributes->>'brand' = 'BrandA';
-- Now uses idx_brand_text
```

6. Monitor index usage:

```sql
-- Check index statistics
SELECT 
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE tablename = 'products'
ORDER BY indexname;
```
