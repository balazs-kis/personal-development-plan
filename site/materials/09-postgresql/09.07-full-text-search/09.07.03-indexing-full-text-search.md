## Introduction

Full-text search without indexes is impractical for production systems with significant data volumes. PostgreSQL provides specialized index types—GIN (Generalized Inverted Index) and GiST (Generalized Search Tree)—designed for text search. Understanding how these indexes work and when to use each type is crucial for building performant search features.

## Key Concepts Summary

### Why Indexes are Essential

**Without an index:**
```sql
-- This performs a sequential scan on every search
SELECT * FROM articles
WHERE to_tsvector('english', title || ' ' || body) 
      @@ plainto_tsquery('english', 'postgresql');
-- On a 1M row table: ~10 seconds
```

**With an index:**
```sql
-- Same query with proper indexing: ~10 milliseconds
-- That's a 1000x performance improvement!
```

### GIN Index (Generalized Inverted Index)

**How GIN works:**
- Creates an index entry for each unique lexeme (word)
- Each entry contains a compressed list of document locations
- Similar to an index in the back of a book

**Characteristics:**
- ✅ **Fast lookups:** Excellent query performance
- ✅ **Accurate:** Non-lossy (no false positives)
- ✅ **Compact:** Efficiently compressed
- ❌ **Slow updates:** INSERT/UPDATE operations are more expensive
- ❌ **Larger size:** Takes more disk space than GiST

**Best for:**
- Read-heavy workloads
- Static or slowly-changing data
- Production search features
- **This is the recommended choice for most use cases**

### GiST Index (Generalized Search Tree)

**How GiST works:**
- Represents each document with a fixed-length signature
- Uses bit-hashing, which can produce false positives
- Requires rechecking table rows for matches

**Characteristics:**
- ✅ **Fast updates:** Better for high-write scenarios
- ✅ **Smaller size:** More compact than GIN
- ❌ **Slower queries:** Due to false positives requiring rechecks
- ❌ **Lossy:** Can produce false matches (automatically filtered)

**Best for:**
- Write-heavy workloads with frequent updates
- When disk space is critical
- Rarely used in practice for text search

## Creating GIN Indexes

### Method 1: Index the Expression (Simple)

```sql
-- Index the tsvector expression directly
CREATE INDEX articles_search_idx ON articles 
USING GIN (to_tsvector('english', title || ' ' || body));

-- Query must match the index expression exactly
SELECT * FROM articles
WHERE to_tsvector('english', title || ' ' || body) 
      @@ plainto_tsquery('english', 'search terms');
```

**Pros:**
- Simple to implement
- No schema changes

**Cons:**
- Expression must match exactly in queries
- Recomputes tsvector on every write
- Can't easily change configuration

### Method 2: Generated Column (Recommended)

```sql
-- Add a generated tsvector column
ALTER TABLE articles 
ADD COLUMN search_vector tsvector 
GENERATED ALWAYS AS (
    to_tsvector('english', COALESCE(title, '') || ' ' || COALESCE(body, ''))
) STORED;

-- Create GIN index on the column
CREATE INDEX articles_search_idx ON articles 
USING GIN (search_vector);

-- Query using the column
SELECT * FROM articles
WHERE search_vector @@ plainto_tsquery('english', 'search terms');
```

**Pros:**
- Precomputed vectors (faster writes)
- Cleaner queries
- Easy to inspect and debug
- Can change configuration by regenerating column

**Cons:**
- Requires additional storage for the column
- Schema change required

### Method 3: Manually Maintained Column (Legacy)

```sql
-- Add a regular tsvector column
ALTER TABLE articles ADD COLUMN search_vector tsvector;

-- Create trigger to maintain it
CREATE FUNCTION articles_search_trigger() RETURNS trigger AS $$
BEGIN
    NEW.search_vector := to_tsvector('english', 
                                     COALESCE(NEW.title, '') || ' ' || 
                                     COALESCE(NEW.body, ''));
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER articles_search_update 
BEFORE INSERT OR UPDATE ON articles
FOR EACH ROW EXECUTE FUNCTION articles_search_trigger();

-- Create index
CREATE INDEX articles_search_idx ON articles 
USING GIN (search_vector);
```

**Pros:**
- Works in older PostgreSQL versions (pre-12)
- Full control over update logic

**Cons:**
- More complex
- Manual trigger maintenance
- Use generated columns instead (PostgreSQL 12+)

## Practical Examples

### Example 1: Blog Search with Generated Column

```sql
-- Create table
CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    author TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Add generated search column
ALTER TABLE posts
ADD COLUMN search_vector tsvector
GENERATED ALWAYS AS (
    to_tsvector('english', 
                title || ' ' || 
                content)
) STORED;

-- Create GIN index
CREATE INDEX posts_search_idx ON posts 
USING GIN (search_vector);

-- Insert sample data
INSERT INTO posts (title, content, author) VALUES
    ('Getting Started with PostgreSQL', 'PostgreSQL is a powerful open source database...', 'Alice'),
    ('Advanced Full-Text Search', 'Learn how to implement full-text search in PostgreSQL...', 'Bob'),
    ('Database Performance Tuning', 'Optimize your database queries for better performance...', 'Charlie');

-- Search posts
SELECT id, title, author
FROM posts
WHERE search_vector @@ plainto_tsquery('english', 'postgresql search')
ORDER BY created_at DESC;
```

### Example 2: Weighted Search (Title vs Content)

```sql
-- Create weighted search vector
ALTER TABLE posts
ADD COLUMN search_vector tsvector
GENERATED ALWAYS AS (
    setweight(to_tsvector('english', COALESCE(title, '')), 'A') ||
    setweight(to_tsvector('english', COALESCE(content, '')), 'B')
) STORED;

-- Create index
CREATE INDEX posts_weighted_search_idx ON posts 
USING GIN (search_vector);

-- Search with weighted ranking (covered in next lesson)
SELECT id, title,
       ts_rank(search_vector, query) AS rank
FROM posts, plainto_tsquery('english', 'postgresql') query
WHERE search_vector @@ query
ORDER BY rank DESC;

-- Weights: A > B > C > D (A is most important)
```

### Example 3: Multi-Language Documents

```sql
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    language TEXT NOT NULL DEFAULT 'english',
    search_vector tsvector
);

-- Trigger for language-aware indexing
CREATE FUNCTION documents_search_trigger() RETURNS trigger AS $$
BEGIN
    NEW.search_vector := to_tsvector(
        NEW.language::regconfig,
        COALESCE(NEW.title, '') || ' ' || COALESCE(NEW.content, '')
    );
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER documents_search_update 
BEFORE INSERT OR UPDATE ON documents
FOR EACH ROW EXECUTE FUNCTION documents_search_trigger();

CREATE INDEX documents_search_idx ON documents 
USING GIN (search_vector);

-- Search using document's language
SELECT id, title, language
FROM documents
WHERE search_vector @@ plainto_tsquery(language::regconfig, 'search terms');
```

### Example 4: Partial Index for Active Content

```sql
-- Index only active/published content
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    title TEXT,
    content TEXT,
    status TEXT DEFAULT 'draft',  -- 'draft', 'published', 'archived'
    search_vector tsvector GENERATED ALWAYS AS (
        to_tsvector('english', title || ' ' || content)
    ) STORED
);

-- Partial index: only published articles
CREATE INDEX articles_published_search_idx ON articles 
USING GIN (search_vector)
WHERE status = 'published';

-- Query uses the partial index automatically
SELECT * FROM articles
WHERE search_vector @@ plainto_tsquery('english', 'search terms')
  AND status = 'published';

-- Benefits: smaller index, faster searches, faster updates
```

## Creating GiST Indexes

```sql
-- Create GiST index (rarely recommended)
CREATE INDEX articles_gist_idx ON articles 
USING GiST (to_tsvector('english', title || ' ' || body));

-- Or on a tsvector column
CREATE INDEX articles_gist_idx ON articles 
USING GiST (search_vector);
```

**When to consider GiST:**
- Extremely high update frequency
- Very tight disk space constraints
- You're also using it for other GiST-enabled types (e.g., geometric data)

## Index Maintenance

### Monitoring Index Size

```sql
-- Check index size
SELECT 
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE indexname LIKE '%search%'
ORDER BY pg_relation_size(indexrelid) DESC;
```

### Monitoring Index Usage

```sql
-- Check if indexes are being used
SELECT 
    schemaname,
    tablename,
    indexname,
    idx_scan,          -- Number of index scans
    idx_tup_read,      -- Tuples read from index
    idx_tup_fetch      -- Tuples fetched from table
FROM pg_stat_user_indexes
WHERE indexname LIKE '%search%'
ORDER BY idx_scan DESC;
```

### Rebuilding Indexes

```sql
-- GIN indexes can become bloated over time
-- Rebuild to reclaim space and improve performance
REINDEX INDEX articles_search_idx;

-- Or rebuild all indexes on a table
REINDEX TABLE articles;

-- Concurrent rebuild (doesn't lock the table)
CREATE INDEX CONCURRENTLY articles_search_idx_new ON articles 
USING GIN (search_vector);

-- Drop old index and rename
DROP INDEX articles_search_idx;
ALTER INDEX articles_search_idx_new RENAME TO articles_search_idx;
```

### VACUUM and ANALYZE

```sql
-- Regular maintenance
VACUUM ANALYZE articles;

-- After bulk inserts/updates, update statistics
ANALYZE articles;
```

## Performance Optimization

### 1. GIN Fast Update (pending list)

```sql
-- Enable fast update (default is ON)
CREATE INDEX articles_search_idx ON articles 
USING GIN (search_vector)
WITH (fastupdate = on);

-- Disable for slightly better query performance
WITH (fastupdate = off);
```

**How it works:**
- Fast update queues changes in a pending list
- Queries check both the index and pending list
- Periodic maintenance flushes the pending list
- Trade-off: slightly slower queries, much faster writes

### 2. GIN Pending List Limit

```sql
-- Control pending list size (default 4MB)
CREATE INDEX articles_search_idx ON articles 
USING GIN (search_vector)
WITH (gin_pending_list_limit = 16384);  -- 16MB in KB

-- Larger limit: fewer maintenance flushes, more memory
-- Smaller limit: more frequent flushes, less memory
```

### 3. Covering Index Pattern

```sql
-- Include frequently accessed columns in the index
CREATE INDEX posts_search_covering_idx ON posts 
USING GIN (search_vector)
INCLUDE (title, author, created_at);

-- Query can be satisfied entirely from the index
SELECT title, author, created_at
FROM posts
WHERE search_vector @@ plainto_tsquery('english', 'postgresql');
-- No heap access needed!
```

## Verifying Index Usage

```sql
-- Check if query uses the index
EXPLAIN ANALYZE
SELECT * FROM articles
WHERE search_vector @@ plainto_tsquery('english', 'postgresql');

-- Look for:
-- -> Bitmap Index Scan on articles_search_idx
-- Good: means the index is being used

-- Bad signs:
-- -> Seq Scan (sequential scan - no index used)
```

## Common Pitfalls

### 1. Expression Mismatch

```sql
-- Index created with:
CREATE INDEX idx ON articles 
USING GIN (to_tsvector('english', title || ' ' || body));

-- Query with different expression: DOESN'T USE INDEX!
SELECT * FROM articles
WHERE to_tsvector('english', body || ' ' || title) 
      @@ plainto_tsquery('english', 'search');
-- Order matters! title || body ≠ body || title

-- Solution: Use generated columns for consistency
```

### 2. Wrong Configuration

```sql
-- Index with 'english' configuration
CREATE INDEX idx ON articles 
USING GIN (to_tsvector('english', content));

-- Query with 'simple' configuration: DOESN'T USE INDEX!
SELECT * FROM articles
WHERE to_tsvector('simple', content) 
      @@ plainto_tsquery('simple', 'search');

-- Solution: Match configurations or use column-based indexes
```

### 3. Forgetting to ANALYZE

```sql
-- After creating an index or bulk loading data
ANALYZE articles;

-- Otherwise, the query planner might not use the index
```

Create an optimized search system for an e-commerce product catalog:

1. Create a `products` table with name, description, and category

4. Create a partial index for only active products

```sql
-- Step 1: Create table

CREATE INDEX products_search_idx ON products
```

## Key Takeaways

- GIN indexes are the recommended choice for full-text search in most cases
- Generated columns provide the best balance of performance and maintainability
- GiST indexes are suitable for high-write scenarios but are rarely needed
- Index expressions must exactly match query expressions
- Use partial indexes to reduce index size for filtered queries
- Weighted search vectors allow prioritizing different document parts
- Regular VACUUM and ANALYZE maintain index health
- Monitor index usage to ensure indexes are being utilized
- GIN fast update trades slightly slower queries for much faster writes
