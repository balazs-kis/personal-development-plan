## Introduction

Partial indexes and covering indexes are powerful optimization techniques. Partial indexes reduce size and overhead by indexing only a subset of rows. Covering indexes (using INCLUDE) allow queries to be satisfied entirely from the index without accessing the table. Both techniques can dramatically improve performance for specific query patterns.

## Key Concepts Summary

### Partial Indexes: Basics

Partial indexes contain entries only for rows that satisfy a predicate:

```sql
-- Syntax
CREATE INDEX index_name ON table_name (column)
WHERE condition;

-- Example: Index only active users
CREATE INDEX idx_users_active ON users (email)
WHERE is_active = true;

-- This query uses the index
SELECT * FROM users WHERE email = 'john@example.com' AND is_active = true;

-- This query CANNOT use the index (violates predicate)
SELECT * FROM users WHERE email = 'john@example.com' AND is_active = false;
```

### Benefits of Partial Indexes

1. **Smaller size**: Fewer entries = smaller index
2. **Faster updates**: Less index maintenance
3. **Better cache utilization**: More relevant data fits in memory
4. **Targeted optimization**: Optimize for specific query patterns

```sql
-- Scenario: Most orders are 'completed', you query 'pending' orders
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    status TEXT,
    user_id INT,
    created_at TIMESTAMP
);

-- BAD: Index all orders
CREATE INDEX idx_orders_status ON orders (status);
-- Problem: Huge index, mostly unused (95% are 'completed')

-- GOOD: Index only pending orders
CREATE INDEX idx_orders_pending ON orders (user_id, created_at)
WHERE status = 'pending';
-- Benefit: 20x smaller, only indexes relevant 5% of rows
```

### Partial Index Patterns

#### Pattern 1: Status-Based Filtering

```sql
-- Index only unprocessed records
CREATE INDEX idx_tasks_unprocessed ON tasks (priority, created_at)
WHERE processed_at IS NULL;

-- Index only failed jobs for retry
CREATE INDEX idx_jobs_failed ON jobs (retry_count, failed_at)
WHERE status = 'failed';
```

#### Pattern 2: Excluding Common Values

```sql
-- Exclude your own IPs from web logs
CREATE INDEX idx_logs_external ON access_logs (ip_address, request_path)
WHERE NOT (ip_address >= '192.168.0.0' AND ip_address <= '192.168.255.255');

-- Index only non-deleted records
CREATE INDEX idx_products_active ON products (category, price)
WHERE deleted_at IS NULL;
```

#### Pattern 3: Date Range Filtering

```sql
-- Index only recent data
CREATE INDEX idx_events_recent ON events (user_id, event_type)
WHERE created_at > '2024-01-01';

-- Index only future bookings
CREATE INDEX idx_bookings_upcoming ON bookings (user_id, room_id)
WHERE check_in_date >= CURRENT_DATE;
```

#### Pattern 4: Boolean Flags

```sql
-- Index only premium users
CREATE INDEX idx_users_premium ON users (last_login, country)
WHERE is_premium = true;

-- Index only verified accounts
CREATE INDEX idx_accounts_verified ON accounts (created_at, email)
WHERE email_verified = true;
```

### Covering Indexes with INCLUDE

The INCLUDE clause adds non-key columns to the index for index-only scans:

```sql
-- Syntax
CREATE INDEX index_name ON table_name (key_columns)
INCLUDE (non_key_columns);

-- Example: Include frequently selected columns
CREATE INDEX idx_users_email_include ON users (email)
INCLUDE (name, created_at);

-- This query is an index-only scan (no table access!)
SELECT name, created_at FROM users WHERE email = 'john@example.com';
```

### Key Columns vs INCLUDE Columns

```sql
-- Key columns: Used for searching and ordering
-- INCLUDE columns: Just stored in index for retrieval

CREATE INDEX idx_orders_user_include ON orders (user_id)
INCLUDE (total_amount, created_at);

-- Key column (user_id): Used in WHERE clause
-- INCLUDE columns: Retrieved without table access
SELECT total_amount, created_at 
FROM orders 
WHERE user_id = 123;
```

### Benefits of INCLUDE

1. **Index-only scans**: Avoid table access entirely
2. **Smaller key**: Simpler B-tree structure
3. **Better ordering**: Key columns remain optimized for search

```sql
-- Without INCLUDE: Must access table
CREATE INDEX idx_products_category ON products (category_id);

SELECT category_id, name, price 
FROM products 
WHERE category_id = 5;
-- Requires: Index Scan + Table Access

-- With INCLUDE: Index-only scan
CREATE INDEX idx_products_category_include ON products (category_id)
INCLUDE (name, price);

SELECT category_id, name, price 
FROM products 
WHERE category_id = 5;
-- Index-only scan: NO table access!
```

### Combining Partial and INCLUDE

```sql
-- Powerful combination
CREATE INDEX idx_orders_pending_include ON orders (user_id, created_at)
INCLUDE (total_amount, status)
WHERE status IN ('pending', 'processing');

-- Optimized query
SELECT user_id, created_at, total_amount, status
FROM orders
WHERE user_id = 123 
  AND status = 'pending'
ORDER BY created_at DESC;
```

### Index-Only Scans: Understanding Visibility

Index-only scans require the visibility map:

```sql
-- After many updates, VACUUM is needed
-- VACUUM updates the visibility map
VACUUM ANALYZE orders;

-- Check if index-only scan is possible
EXPLAIN (ANALYZE, BUFFERS) 
SELECT email FROM users WHERE email LIKE 'john%';

-- Look for "Index Only Scan" in output
-- "Heap Fetches: 0" means true index-only scan
-- "Heap Fetches: N" means visibility check needed
```

### Practical Examples

#### Example 1: E-commerce Order Processing

```sql
-- Most orders are completed, we work with pending/processing
CREATE INDEX idx_orders_active_detailed ON orders (user_id, created_at DESC)
INCLUDE (total_amount, status, shipping_address)
WHERE status IN ('pending', 'processing', 'shipped');

-- Optimized queries
SELECT user_id, created_at, total_amount, status
FROM orders
WHERE user_id = 123 AND status = 'pending'
ORDER BY created_at DESC;
-- Small index, index-only scan, very fast!
```

#### Example 2: Content Moderation

```sql
-- Most content is approved, index only pending moderation
CREATE INDEX idx_content_pending_mod ON content (priority, submitted_at)
INCLUDE (title, author_id, content_type)
WHERE moderation_status = 'pending';

-- Dashboard query
SELECT title, author_id, content_type, submitted_at
FROM content
WHERE moderation_status = 'pending'
ORDER BY priority DESC, submitted_at ASC
LIMIT 50;
```

#### Example 3: Multi-tenant SaaS

```sql
-- Index only active tenants with premium features
CREATE INDEX idx_tenants_premium_active ON tenants (name)
INCLUDE (plan_type, max_users, features)
WHERE is_active = true AND plan_type IN ('premium', 'enterprise');

-- Fast tenant lookup
SELECT name, plan_type, max_users, features
FROM tenants
WHERE name = 'acme-corp' AND is_active = true;
```

### Monitoring Index-Only Scans

```sql
-- Check index-only scan usage
SELECT schemaname, tablename, indexname,
       idx_scan as total_scans,
       idx_tup_read as tuples_read,
       idx_tup_fetch as tuples_fetched
FROM pg_stat_user_indexes
WHERE indexname = 'idx_users_email_include';

-- If tuples_read ~= tuples_fetched, index-only scans are working
-- If tuples_fetched is much lower, true index-only scans
```

### Design Considerations

**Partial Index Considerations:**
- Predicate must be simple and stable
- WHERE clause in query must match or be more restrictive
- Most beneficial when filtering excludes large percentage of rows

**INCLUDE Considerations:**
- Only add frequently accessed columns
- Don't add large columns (TEXT, BYTEA)
- Balance between index size and query performance
- Most beneficial for small, frequently selected columns

### Common Mistakes

```sql
-- MISTAKE 1: Predicate too complex
-- BAD: Complex expression
CREATE INDEX idx_bad ON table (col)
WHERE complex_function(col) > computed_value();

-- GOOD: Simple, stable predicate
CREATE INDEX idx_good ON table (col)
WHERE status = 'active';

-- MISTAKE 2: Including large columns
-- BAD: Large text field
CREATE INDEX idx_bad ON articles (category_id)
INCLUDE (full_text_content);  -- Could be megabytes!

-- GOOD: Small, frequently accessed columns
CREATE INDEX idx_good ON articles (category_id)
INCLUDE (title, author_id, published_at);

-- MISTAKE 3: Query doesn't match predicate
CREATE INDEX idx_orders ON orders (user_id)
WHERE status = 'pending';

-- Won't use index: query is less restrictive
SELECT * FROM orders WHERE user_id = 123;

-- Will use index: query matches or is more restrictive
SELECT * FROM orders WHERE user_id = 123 AND status = 'pending';
```
