## Introduction

PostgreSQL uses three primary join algorithms: nested loop, hash join, and merge join. Each has different performance characteristics and is optimal for different scenarios. The query planner automatically selects the best algorithm based on table sizes, available indexes, join conditions, and memory settings.

Understanding join algorithms helps you write better queries and create appropriate indexes. Many slow query problems stem from the planner choosing a suboptimal join strategy, often due to missing indexes, outdated statistics, or insufficient memory configuration.

## Key Concepts Summary

### Nested Loop Join

The simplest join algorithm: for each row in the outer table, scan the inner table to find matching rows.

```sql
EXPLAIN ANALYZE
SELECT o.*, u.name 
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'pending';

-- Example output
Nested Loop  (cost=0.29..24.75 rows=2 width=100)
  ->  Seq Scan on orders o  (cost=0.00..8.00 rows=2 width=64)
        Filter: (status = 'pending'::text)
  ->  Index Scan using users_pkey on users u  (cost=0.29..8.31 rows=1 width=36)
        Index Cond: (id = o.user_id)
```

**How it works:**
1. Scan the outer table (orders) and filter rows
2. For each matching outer row, look up the inner table (users)
3. Combine matching pairs into the result

**When it's used:**
- Small outer table (few rows after filtering)
- Inner table has an index on the join key
- Join condition is not an equality (e.g., `<`, `>`, `BETWEEN`)

**Performance characteristics:**
- **Best case:** Small outer table + indexed inner table
- **Worst case:** Large outer table + unindexed inner table (O(n*m) complexity)
- Very efficient when outer table is small (< 100 rows typically)

**Key indicator:** Index scan on the inner table is crucial for performance

### Hash Join

Creates a hash table from one input, then probes it with rows from the other input.

```sql
EXPLAIN ANALYZE
SELECT o.*, p.name 
FROM orders o
JOIN products p ON o.product_id = p.id;

-- Example output
Hash Join  (cost=35.00..125.00 rows=1000 width=100)
  Hash Cond: (o.product_id = p.id)
  ->  Seq Scan on orders o  (cost=0.00..50.00 rows=1000 width=64)
  ->  Hash  (cost=20.00..20.00 rows=500 width=36)
        Buckets: 1024  Batches: 1  Memory Usage: 25kB
        ->  Seq Scan on products p  (cost=0.00..20.00 rows=500 width=36)
```

**How it works:**
1. Build a hash table from the smaller input (products)
2. Scan the larger input (orders)
3. For each row, probe the hash table for matches
4. Combine matching pairs

**When it's used:**
- Both tables are relatively large
- Join condition is an equality (`=`)
- Sufficient memory available (work_mem)
- No suitable indexes exist

**Performance characteristics:**
- **Best case:** O(n+m) complexity - very efficient
- Hash table fits in memory (watch "Batches" in EXPLAIN)
- **Batches > 1:** Hash table doesn't fit in work_mem, performance degrades

**Key indicators:**
- "Batches: 1" is good (hash fits in memory)
- "Batches: 8" means spilling to disk (increase work_mem)

### Merge Join

Merges two pre-sorted inputs, advancing through both simultaneously.

```sql
CREATE INDEX idx_orders_product_id ON orders(product_id);
CREATE INDEX idx_products_id ON products(id);

EXPLAIN ANALYZE
SELECT o.*, p.name 
FROM orders o
JOIN products p ON o.product_id = p.id
ORDER BY p.id;

-- Example output
Merge Join  (cost=0.57..150.00 rows=1000 width=100)
  Merge Cond: (o.product_id = p.id)
  ->  Index Scan using idx_orders_product_id on orders o  (cost=0.29..80.00 rows=1000)
  ->  Index Scan using idx_products_id on products p  (cost=0.29..60.00 rows=500)
```

**How it works:**
1. Ensure both inputs are sorted by the join key
2. Advance through both inputs simultaneously
3. When keys match, output the joined row
4. Advance the input with the smaller key

**When it's used:**
- Join condition is an equality
- Both inputs are already sorted (via indexes)
- Query has an ORDER BY that matches the join key
- Both tables are large

**Performance characteristics:**
- **Best case:** Inputs already sorted by indexes - very efficient O(n+m)
- Produces sorted output (beneficial for ORDER BY)
- **Worst case:** Must sort inputs first - adds significant cost

**Key indicators:**
- Index scans on both sides (good - already sorted)
- "Sort" nodes present (bad - must sort first, may spill to disk)

### Join Algorithm Comparison

| Algorithm | Complexity | Best For | Requirements | Memory |
|-----------|-----------|----------|--------------|--------|
| **Nested Loop** | O(n*m) | Small outer table | Index on inner table | Minimal |
| **Hash Join** | O(n+m) | Large tables | Equality joins | work_mem |
| **Merge Join** | O(n+m) | Large sorted tables | Equality joins, sorted inputs | Minimal (if pre-sorted) |

### Multi-way Joins

For queries with multiple joins, PostgreSQL must choose the join order and algorithm for each step:

```sql
EXPLAIN ANALYZE
SELECT u.name, o.id, p.name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN products p ON o.product_id = p.id
WHERE u.country = 'USA';

-- Example output (join order matters!)
Hash Join  (cost=100.00..500.00 rows=1000 width=100)
  Hash Cond: (o.product_id = p.id)
  ->  Nested Loop  (cost=0.29..200.00 rows=1000 width=72)
        ->  Seq Scan on users u  (cost=0.00..50.00 rows=500 width=36)
              Filter: (country = 'USA'::text)
        ->  Index Scan using idx_orders_user_id on orders o  (cost=0.29..0.30 rows=2)
              Index Cond: (user_id = u.id)
  ->  Hash  (cost=20.00..20.00 rows=1000 width=36)
        ->  Seq Scan on products p  (cost=0.00..20.00 rows=1000 width=36)
```

**Join order considerations:**
- Start with the most selective table (users filtered by country)
- Use nested loop for small intermediate results
- Use hash join for larger intermediate results
- The planner considers multiple permutations

### Influencing Join Selection

```sql
-- Increase memory for hash joins
SET work_mem = '256MB';

-- Disable specific join types (for testing only!)
SET enable_nestloop = off;
SET enable_hashjoin = off;
SET enable_mergejoin = off;

-- Better: ensure proper indexes and statistics
CREATE INDEX idx_orders_user_id ON orders(user_id);
ANALYZE orders;
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

1. Create test tables with different sizes:

```sql
-- Small table
CREATE TABLE customers (
    id SERIAL PRIMARY KEY,
    name TEXT,
    country TEXT
);

INSERT INTO customers (name, country)
SELECT 'Customer ' || i, 
       CASE (i % 5) WHEN 0 THEN 'USA' ELSE 'Other' END
FROM generate_series(1, 1000) i;

-- Large table
CREATE TABLE transactions (
    id SERIAL PRIMARY KEY,
    customer_id INTEGER,
    amount NUMERIC,
    created_at TIMESTAMP DEFAULT NOW()
);

INSERT INTO transactions (customer_id, amount)
SELECT 
    (random() * 999 + 1)::integer,
    random() * 1000
FROM generate_series(1, 100000) i;

ANALYZE customers;
ANALYZE transactions;
```

2. Test different join algorithms:

```sql
-- Nested Loop (small outer, indexed inner)
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, t.amount
FROM customers c
JOIN transactions t ON c.id = t.customer_id
WHERE c.country = 'USA';

-- Add index to enable nested loop on inner
CREATE INDEX idx_transactions_customer_id ON transactions(customer_id);

-- Retry - should use Nested Loop now
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, t.amount
FROM customers c
JOIN transactions t ON c.id = t.customer_id
WHERE c.country = 'USA';

-- Hash Join (both tables large, no good filtering)
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, COUNT(*) 
FROM customers c
JOIN transactions t ON c.id = t.customer_id
GROUP BY c.name;

-- Merge Join (force sorting)
SET enable_hashjoin = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, COUNT(*) 
FROM customers c
JOIN transactions t ON c.id = t.customer_id
GROUP BY c.name;
SET enable_hashjoin = on;
```

3. Examine multi-way joins:

```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT,
    category TEXT
);

INSERT INTO products (name, category)
SELECT 'Product ' || i, 
       CASE (i % 3) WHEN 0 THEN 'A' WHEN 1 THEN 'B' ELSE 'C' END
FROM generate_series(1, 1000) i;

-- Add product_id to transactions
ALTER TABLE transactions ADD COLUMN product_id INTEGER;
UPDATE transactions SET product_id = (random() * 999 + 1)::integer;
ANALYZE transactions;

-- Three-way join
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, p.name, SUM(t.amount)
FROM customers c
JOIN transactions t ON c.id = t.customer_id
JOIN products p ON t.product_id = p.id
WHERE c.country = 'USA'
GROUP BY c.name, p.name;
```
