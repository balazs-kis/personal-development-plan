---

## Introduction

PostgreSQL has several methods for retrieving data from tables, each optimized for different scenarios. Understanding when and why the planner chooses sequential scans, index scans, or bitmap scans is crucial for optimization. Contrary to common belief, sequential scans aren't always bad - they're often the most efficient choice for certain query patterns.

The planner's choice of scan type depends on factors like table size, selectivity of the WHERE clause, available indexes, and memory settings. Learning to recognize these patterns helps you create effective indexes and write queries that use them appropriately.

## Key Concepts Summary

### Sequential Scan

A sequential scan reads the entire table from beginning to end, processing every row.

```sql
EXPLAIN ANALYZE 
SELECT * FROM large_table WHERE status = 'active';

-- Example output
Seq Scan on large_table  (cost=0.00..1693.00 rows=50000 width=100)
  Filter: (status = 'active'::text)
  Rows Removed by Filter: 50000
```

**When it's used:**
- No suitable index exists
- Query needs most of the table (> 5-10% typically)
- Table is very small (faster to scan than use index)
- Statistics suggest sequential scan is cheaper

**Why it's sometimes optimal:**
- Sequential I/O is fast - reads continuous disk blocks
- No index overhead (no extra I/O to read index)
- Better for queries returning large percentages of rows

### Index Scan

An index scan uses an index to find specific rows, then fetches each row from the table immediately.

```sql
CREATE INDEX idx_users_email ON users(email);

EXPLAIN ANALYZE 
SELECT * FROM users WHERE email = 'user@example.com';

-- Example output
Index Scan using idx_users_email on users  (cost=0.29..8.31 rows=1 width=100)
  Index Cond: (email = 'user@example.com'::text)
```

**When it's used:**
- Suitable index exists
- Query is highly selective (returns small percentage of rows)
- Index covers the WHERE clause conditions

**Characteristics:**
- Fetches one row at a time from the table
- Random I/O pattern (jumps around the table)
- Efficient for small result sets (< 1-5% of table)
- Can be inefficient for larger result sets due to random access

### Bitmap Heap Scan

A two-phase scan: first builds a bitmap of matching rows from the index, then fetches rows from the table in physical order.

```sql
CREATE INDEX idx_orders_status ON orders(status);

EXPLAIN ANALYZE 
SELECT * FROM orders WHERE status = 'pending';

-- Example output
Bitmap Heap Scan on orders  (cost=12.00..120.00 rows=500 width=80)
  Recheck Cond: (status = 'pending'::text)
  ->  Bitmap Index Scan on idx_orders_status  (cost=0.00..11.87 rows=500)
        Index Cond: (status = 'pending'::text)
```

**How it works:**
1. **Phase 1:** Scan the index and build an in-memory bitmap of matching rows
2. **Phase 2:** Sort the bitmap by physical location and fetch rows from the table in order

**When it's used:**
- Moderate selectivity (typically 1-10% of table)
- Multiple indexes can be combined (AND/OR conditions)
- Result set too large for index scan but too small for sequential scan

**Advantages:**
- Converts random I/O into sequential I/O
- Reduces number of table page visits
- Can combine multiple indexes efficiently

**The "Recheck Cond":**
- Bitmap is lossy (stores page-level information, not exact rows)
- After fetching pages, must recheck condition for each row
- More likely with large result sets

### BitmapAnd and BitmapOr

When multiple indexes exist, PostgreSQL can combine them:

```sql
CREATE INDEX idx_products_category ON products(category);
CREATE INDEX idx_products_price ON products(price);

EXPLAIN ANALYZE 
SELECT * FROM products 
WHERE category = 'Electronics' AND price < 100;

-- Example output
Bitmap Heap Scan on products
  Recheck Cond: ((category = 'Electronics') AND (price < 100))
  ->  BitmapAnd
        ->  Bitmap Index Scan on idx_products_category
              Index Cond: (category = 'Electronics')
        ->  Bitmap Index Scan on idx_products_price
              Index Cond: (price < 100)
```

### Index Only Scan

Special case where all needed columns are in the index:

```sql
CREATE INDEX idx_users_email_name ON users(email, name);

EXPLAIN ANALYZE 
SELECT email, name FROM users WHERE email LIKE 'admin%';

-- Example output
Index Only Scan using idx_users_email_name on users
  Index Cond: ((email >= 'admin') AND (email < 'admio'))
  Heap Fetches: 0
```

**Requirements:**
- All selected columns must be in the index
- Table must be properly vacuumed (visibility map up to date)

**"Heap Fetches":**
- Shows how many times the table was accessed
- `0` means truly index-only (optimal)
- Non-zero means visibility checks required table access

### Comparison Table

| Scan Type | Selectivity | I/O Pattern | Best For |
|-----------|-------------|-------------|----------|
| Sequential Scan | High (> 5-10%) | Sequential | Large result sets, small tables |
| Index Scan | Very Low (< 1-5%) | Random | Specific lookups, tiny result sets |
| Bitmap Scan | Medium (1-10%) | Semi-sequential | Moderate result sets, multiple conditions |
| Index Only Scan | Any | Sequential | Covered queries, frequent vacuuming |

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

1. Create a test table and add varying amounts of data:

```sql
CREATE TABLE scan_test (
    id SERIAL PRIMARY KEY,
    category TEXT,
    value INTEGER,
    data TEXT
);

-- Insert 100,000 rows
INSERT INTO scan_test (category, value, data)
SELECT 
    CASE (i % 10)
        WHEN 0 THEN 'rare'
        WHEN 1 THEN 'uncommon'
        ELSE 'common'
    END,
    random() * 1000,
    'Data for row ' || i
FROM generate_series(1, 100000) i;

-- Update statistics
ANALYZE scan_test;
```

2. Compare scan types for different selectivity levels:

```sql
-- High selectivity (should use Seq Scan)
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM scan_test WHERE category = 'common';

-- Add an index
CREATE INDEX idx_scan_test_category ON scan_test(category);

-- Low selectivity (should use Index Scan or Bitmap Scan)
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM scan_test WHERE category = 'rare';

-- Medium selectivity (likely Bitmap Scan)
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM scan_test WHERE category = 'uncommon';

-- High selectivity - still Seq Scan despite index?
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM scan_test WHERE category = 'common';
```

3. Test Index Only Scan:

```sql
-- This should require table access
EXPLAIN (ANALYZE, BUFFERS) 
SELECT category, value FROM scan_test WHERE category = 'rare';

-- Vacuum to update visibility map
VACUUM scan_test;

-- Now should be index-only (check Heap Fetches)
EXPLAIN (ANALYZE, BUFFERS) 
SELECT category FROM scan_test WHERE category = 'rare';

-- Add a covering index
CREATE INDEX idx_scan_test_category_value ON scan_test(category, value);

-- Should be index-only for both columns
EXPLAIN (ANALYZE, BUFFERS) 
SELECT category, value FROM scan_test WHERE category = 'rare';
```
