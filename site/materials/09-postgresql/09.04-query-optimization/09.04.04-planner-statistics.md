## Introduction

The PostgreSQL query planner relies heavily on statistics to estimate costs and choose execution plans. These statistics include information about table sizes, column value distributions, correlations, and common values. When statistics are outdated or insufficient, the planner makes poor decisions, leading to slow queries.

Understanding how statistics work and how to maintain them is critical for consistent query performance. Many mysterious performance issues trace back to outdated statistics causing the planner to choose suboptimal execution strategies.

## Key Concepts Summary

### What Statistics PostgreSQL Collects

PostgreSQL maintains statistics in system catalogs:

1. **pg_class** - Table-level statistics:
   - `reltuples`: estimated number of rows
   - `relpages`: estimated number of disk pages
   - Updated by VACUUM, ANALYZE, and DDL commands

2. **pg_statistic** - Column-level statistics:
   - Most common values (MCVs) and their frequencies
   - Histogram of value distribution
   - NULL fraction
   - Average column width
   - Correlation with physical row order

**View statistics:**

```sql
-- Table-level stats
SELECT relname, reltuples, relpages 
FROM pg_class 
WHERE relname = 'orders';

-- Column-level stats (human-readable view)
SELECT * FROM pg_stats 
WHERE tablename = 'orders' AND attname = 'status';
```

### The ANALYZE Command

ANALYZE collects statistics by sampling table data:

```sql
-- Analyze all tables in database
ANALYZE;

-- Analyze specific table
ANALYZE orders;

-- Analyze specific columns
ANALYZE orders (status, created_at);

-- Verbose output
ANALYZE VERBOSE orders;
```

**How ANALYZE works:**
- Samples random rows (not full scan)
- Default samples 30,000 rows per table
- Stores results in pg_statistic
- Acquires only SHARE UPDATE EXCLUSIVE lock (doesn't block reads/writes)
- Relatively fast, safe to run frequently

**When to run ANALYZE:**
- After bulk data loads
- After significant updates/deletes
- After major schema changes
- Periodically via autovacuum (automatic)

### Statistics Target

Controls how much detail ANALYZE collects:

```sql
-- Global setting (default: 100)
SET default_statistics_target = 100;

-- Per-column setting (more detailed for important columns)
ALTER TABLE orders 
ALTER COLUMN status SET STATISTICS 200;

-- Zero means no statistics (for columns never used in WHERE/GROUP BY)
ALTER TABLE orders 
ALTER COLUMN description SET STATISTICS 0;
```

**Statistics target determines:**
- Number of most common values (MCVs) stored
- Number of histogram bins
- Higher values = more accurate estimates = slower ANALYZE

**Guidelines:**
- Default (100) works for most cases
- Increase (200-500) for columns with:
  - Skewed distributions
  - Used in complex WHERE clauses
  - Causing bad estimate mismatches
- Increase (1000+) for very large tables with problematic plans

### Recognizing Statistics Problems in EXPLAIN

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE status = 'shipped';

-- Example output showing estimate mismatch
Seq Scan on orders  (cost=0.00..1693.00 rows=50 width=100) 
                    (actual time=0.015..25.123 rows=15432 loops=1)
  Filter: (status = 'shipped'::text)
  Rows Removed by Filter: 4568
```

**Red flags:**
- **"rows=50"** (estimated) vs **"rows=15432"** (actual) - 300x mismatch!
- Large discrepancy indicates stale or insufficient statistics
- Can cause wrong join algorithm, scan type, or join order

**Fix:**

```sql
-- Update statistics
ANALYZE orders;

-- Or increase statistics target and re-analyze
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 200;
ANALYZE orders;
```

### Statistics and Autovacuum

PostgreSQL runs autovacuum automatically to maintain statistics:

```sql
-- Check autovacuum settings
SHOW autovacuum;
SHOW autovacuum_analyze_threshold;
SHOW autovacuum_analyze_scale_factor;

-- View last autovacuum/analyze times
SELECT schemaname, relname, 
       last_vacuum, last_autovacuum,
       last_analyze, last_autoanalyze,
       n_tup_ins, n_tup_upd, n_tup_del
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

**Default autovacuum analyze trigger:**
- Runs when: `changed_tuples > threshold + scale_factor * reltuples`
- Default: 50 rows + 10% of table
- For large tables, this can be too infrequent

**Tuning per-table:**

```sql
-- More aggressive autovacuum for critical tables
ALTER TABLE orders SET (
    autovacuum_analyze_threshold = 100,
    autovacuum_analyze_scale_factor = 0.02  -- 2% instead of 10%
);
```

### Extended Statistics (PostgreSQL 10+)

For correlated columns, create extended statistics:

```sql
-- Columns are correlated (e.g., city and state)
CREATE STATISTICS stats_address 
ON city, state FROM addresses;

ANALYZE addresses;

-- Now the planner understands the correlation
EXPLAIN SELECT * FROM addresses 
WHERE city = 'Boston' AND state = 'MA';
```

**When to use:**
- Columns with functional dependencies
- Columns with correlations
- Multi-column WHERE clauses with bad estimates

### Viewing Statistics Quality

```sql
-- Check for tables with no or old statistics
SELECT schemaname, relname, 
       last_analyze, last_autoanalyze,
       n_live_tup
FROM pg_stat_user_tables
WHERE last_analyze IS NULL 
   OR last_analyze < NOW() - INTERVAL '7 days'
ORDER BY n_live_tup DESC;

-- Check for estimate vs actual mismatches in slow query log
-- (requires log_min_duration_statement and auto_explain extension)
```

### Statistics Maintenance Best Practices

1. **Let autovacuum work:**
   - Don't disable it globally
   - Tune per-table if needed

2. **Run ANALYZE after bulk operations:**
   ```sql
   COPY orders FROM 'data.csv';
   ANALYZE orders;
   ```

3. **Monitor statistics freshness:**
   - Check last_analyze dates regularly
   - Alert on stale statistics for critical tables

4. **Increase statistics target for problem columns:**
   - Identify via EXPLAIN estimate mismatches
   - Start with 200, increase if needed

5. **Consider extended statistics:**
   - For multi-column WHERE clauses
   - When single-column stats aren't enough

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

1. Create a table and observe statistics:

```sql
CREATE TABLE stats_demo (
    id SERIAL PRIMARY KEY,
    category TEXT,
    value INTEGER,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Insert data with skewed distribution
INSERT INTO stats_demo (category, value)
SELECT 
    CASE 
        WHEN i <= 90000 THEN 'common'      -- 90%
        WHEN i <= 99000 THEN 'uncommon'    -- 9%
        ELSE 'rare'                         -- 1%
    END,
    (random() * 1000)::integer
FROM generate_series(1, 100000) i;

-- Run ANALYZE
ANALYZE stats_demo;
```

2. View collected statistics:

```sql
-- Table-level statistics
SELECT relname, reltuples, relpages 
FROM pg_class 
WHERE relname = 'stats_demo';

-- Column-level statistics
SELECT tablename, attname, 
       n_distinct,                    -- number of distinct values
       most_common_vals[1:5],         -- top 5 most common values
       most_common_freqs[1:5],        -- their frequencies
       null_frac                      -- fraction of NULLs
FROM pg_stats 
WHERE tablename = 'stats_demo' AND attname = 'category';
```

3. Test estimate accuracy:

```sql
-- Query rare category
EXPLAIN ANALYZE
SELECT * FROM stats_demo WHERE category = 'rare';
-- Check rows estimate vs actual

-- Query common category
EXPLAIN ANALYZE
SELECT * FROM stats_demo WHERE category = 'common';
-- Check rows estimate vs actual

-- Create index and retest
CREATE INDEX idx_stats_demo_category ON stats_demo(category);
ANALYZE stats_demo;

EXPLAIN ANALYZE
SELECT * FROM stats_demo WHERE category = 'rare';
```

4. Simulate stale statistics:

```sql
-- Insert more data without ANALYZE
INSERT INTO stats_demo (category, value)
SELECT 'rare', (random() * 1000)::integer
FROM generate_series(1, 50000) i;

-- Statistics still think 'rare' is 1%
EXPLAIN ANALYZE
SELECT * FROM stats_demo WHERE category = 'rare';
-- Should see estimate mismatch

-- Fix with ANALYZE
ANALYZE stats_demo;

EXPLAIN ANALYZE
SELECT * FROM stats_demo WHERE category = 'rare';
-- Should see better estimates
```

5. Test statistics target:

```sql
-- Set higher statistics target
ALTER TABLE stats_demo 
ALTER COLUMN value SET STATISTICS 500;

ANALYZE stats_demo;

-- Check the difference in histogram bins
SELECT tablename, attname, 
       array_length(histogram_bounds, 1) as num_bins
FROM pg_stats 
WHERE tablename = 'stats_demo';
```
