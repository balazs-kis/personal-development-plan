## Introduction

The Dependency Inversion Principle (DIP) states that:
1. **High-level modules should not depend on low-level modules. Both should depend on abstractions.**
2. **Abstractions should not depend on details. Details should depend on abstractions.**

This principle is often confused with Dependency Injection (DI), but they're related yet distinct concepts:

**Dependency Inversion Principle (DIP)**: An architectural principle about how modules should be structured and what they should depend on.

**Dependency Injection (DI)**: A design pattern and technique for implementing DIP by injecting dependencies rather than creating them internally.

### Why DIP Matters

Without DIP, your application's architecture looks like this:

```
┌─────────────────────────────────────┐
│   High-level Business Logic         │
│   (OrderService)                    │
└───────────┬─────────────────────────┘
            │ depends on (coupled to)
            ▼
┌─────────────────────────────────────┐
│   Low-level Infrastructure          │
│   (SqlServerRepository)             │
│   (SmtpEmailClient)                 │
└─────────────────────────────────────┘
```

**Problems:**
- Business logic is tightly coupled to infrastructure
- Can't test business logic without database
- Can't switch from SQL Server to MongoDB without changing business logic
- Can't mock email service for testing

With DIP, your architecture looks like this:

```
┌─────────────────────────────────────┐
│   High-level Business Logic         │
│   (OrderService)                    │
└───────────┬─────────────────────────┘
            │ depends on
            ▼
┌─────────────────────────────────────┐
│   Abstractions (Interfaces)         │
│   IOrderRepository                  │
│   IEmailService                     │
└──────────┬──────────────────────────┘
           │ implemented by
           ▼
┌─────────────────────────────────────┐
│   Low-level Infrastructure          │
│   SqlServerRepository               │
│   SmtpEmailClient                   │
└─────────────────────────────────────┘
```

**Benefits:**
- Business logic depends only on abstractions
- Easy to test with mocks
- Easy to swap implementations
- Infrastructure concerns don't leak into business logic

## Key Concepts Summary

### The Problem: Dependency on Concretions

**Violates DIP - Tight Coupling**

```csharp
// High-level module depends directly on low-level modules
public class OrderService
{
    // Creating dependencies internally = tight coupling
    private readonly SqlServerRepository _repository = new();
    private readonly SmtpEmailSender _emailSender = new();
    private readonly FileLogger _logger = new("/logs/app.log");
    
    public void ProcessOrder(Order order)
    {
        // Validate
        if (order.Total < 0)
            throw new ArgumentException("Invalid order total");
        
        // Save to SQL Server (can't use any other database!)
        _repository.Save(order);
        
        // Send via SMTP (can't use any other email provider!)
        _emailSender.SendConfirmation(order);
        
        // Log to file (can't use any other logger!)
        _logger.Log($"Order {order.Id} processed");
    }
}

// Low-level module: concrete implementation
public class SqlServerRepository
{
    private readonly string _connectionString = "Server=...";
    
    public void Save(Order order)
    {
        using var connection = new SqlConnection(_connectionString);
        connection.Open();
        // SQL Server specific code
    }
}
```

**Problems with this design:**
- ❌ **Cannot test** without a real SQL Server database
- ❌ **Cannot mock** email sending - will actually send emails in tests!
- ❌ **Cannot switch** to PostgreSQL, MongoDB, or any other database without changing `OrderService`
- ❌ **Cannot reuse** `OrderService` in different contexts (different DB, different email provider)
- ❌ **Tight coupling** - `OrderService` knows about SQL Server, SMTP, and file system
- ❌ **Violates SRP** - `OrderService` responsible for creating its dependencies

### The Solution: Dependency Inversion

**Follows DIP - Loose Coupling through Abstractions**

```csharp
// Step 1: Define abstractions (interfaces)
public interface IOrderRepository
{
    Task Save(Order order);
    Task<Order> GetById(string orderId);
    Task<IEnumerable<Order>> GetByCustomerId(string customerId);
}

public interface IEmailSender
{
    Task SendConfirmation(Order order);
    Task SendShippingNotification(Order order);
}

public interface ILogger
{
    void LogInformation(string message);
    void LogError(string message, Exception ex);
}

// Step 2: High-level module depends ONLY on abstractions
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IEmailSender _emailSender;
    private readonly ILogger _logger;
    
    // Dependencies injected via constructor
    public OrderService(
        IOrderRepository repository,
        IEmailSender emailSender,
        ILogger logger)
    {
        _repository = repository ?? throw new ArgumentNullException(nameof(repository));
        _emailSender = emailSender ?? throw new ArgumentNullException(nameof(emailSender));
        _logger = logger ?? throw new ArgumentNullException(nameof(logger));
    }
    
    public async Task ProcessOrder(Order order)
    {
        try
        {
            // Validate
            if (order.Total < 0)
                throw new ArgumentException("Invalid order total");
            
            // Save (don't know or care if it's SQL Server, MongoDB, etc.)
            await _repository.Save(order);
            
            // Send email (don't know or care if it's SMTP, SendGrid, etc.)
            await _emailSender.SendConfirmation(order);
            
            // Log (don't know or care if it's file, console, Application Insights, etc.)
            _logger.LogInformation($"Order {order.Id} processed successfully");
        }
        catch (Exception ex)
        {
            _logger.LogError($"Failed to process order {order.Id}", ex);
            throw;
        }
    }
}

// Step 3: Low-level modules implement the abstractions
public class SqlServerOrderRepository : IOrderRepository
{
    private readonly string _connectionString;
    
    public SqlServerOrderRepository(IConfiguration configuration)
    {
        _connectionString = configuration.GetConnectionString("DefaultConnection");
    }
    
    public async Task Save(Order order)
    {
        using var connection = new SqlConnection(_connectionString);
        await connection.OpenAsync();
        
        var command = new SqlCommand(
            "INSERT INTO Orders (Id, CustomerId, Total) VALUES (@Id, @CustomerId, @Total)",
            connection);
        
        command.Parameters.AddWithValue("@Id", order.Id);
        command.Parameters.AddWithValue("@CustomerId", order.CustomerId);
        command.Parameters.AddWithValue("@Total", order.Total);
        
        await command.ExecuteNonQueryAsync();
    }
    
    public async Task<Order> GetById(string orderId)
    {
        using var connection = new SqlConnection(_connectionString);
        await connection.OpenAsync();
        
        var command = new SqlCommand(
            "SELECT * FROM Orders WHERE Id = @Id",
            connection);
        
        command.Parameters.AddWithValue("@Id", orderId);
        
        using var reader = await command.ExecuteReaderAsync();
        if (await reader.ReadAsync())
        {
            return new Order
            {
                Id = reader.GetString(0),
                CustomerId = reader.GetString(1),
                Total = reader.GetDecimal(2)
            };
        }
        
        return null;
    }
    
    public async Task<IEnumerable<Order>> GetByCustomerId(string customerId)
    {
        // Implementation...
        return new List<Order>();
    }
}

// Alternative implementation: MongoDB (can swap without changing OrderService!)
public class MongoDbOrderRepository : IOrderRepository
{
    private readonly IMongoCollection<Order> _orders;
    
    public MongoDbOrderRepository(IMongoDatabase database)
    {
        _orders = database.GetCollection<Order>("orders");
    }
    
    public async Task Save(Order order)
    {
        await _orders.InsertOneAsync(order);
    }
    
    public async Task<Order> GetById(string orderId)
    {
        var filter = Builders<Order>.Filter.Eq(o => o.Id, orderId);
        return await _orders.Find(filter).FirstOrDefaultAsync();
    }
    
    public async Task<IEnumerable<Order>> GetByCustomerId(string customerId)
    {
        var filter = Builders<Order>.Filter.Eq(o => o.CustomerId, customerId);
        return await _orders.Find(filter).ToListAsync();
    }
}

// Email sender implementation
public class SmtpEmailSender : IEmailSender
{
    private readonly IOptions<EmailSettings> _settings;
    private readonly ILogger<SmtpEmailSender> _logger;
    
    public SmtpEmailSender(

    }

            using var client = new SmtpClient(_settings.Value.SmtpServer, _settings.Value.Port);
            client.Credentials = new NetworkCredential(

            await client.SendMailAsync(message);
            _logger.LogInformation("Confirmation email sent for order {OrderId}", order.Id);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Failed to send confirmation email for order {OrderId}", order.Id);
            throw;
        }
    }
    
    public async Task SendShippingNotification(Order order)
    {
        // Implementation...
    }
}

// Alternative email implementation: SendGrid (can swap!)
public class SendGridEmailSender : IEmailSender
{
    private readonly ISendGridClient _client;
    
    public SendGridEmailSender(ISendGridClient client)
    {
        _client = client;
    }
    
    public async Task SendConfirmation(Order order)
    {
        var msg = new SendGridMessage
        {
            From = new EmailAddress("orders@company.com"),
            Subject = "Order Confirmation",
            HtmlContent = $"<p>Your order {order.Id} has been confirmed!</p>"
        };
        
        msg.AddTo(order.CustomerEmail);

    }
    
    public async Task SendShippingNotification(Order order)
    {
        // Implementation...
    }
}
```

**Benefits of DIP implementation:**
- ✅ **Testable** - can inject mock repositories and email senders
- ✅ **Flexible** - can swap SQL Server for MongoDB by changing registration
- ✅ **Reusable** - `OrderService` works with any implementation
- ✅ **Maintainable** - changes to database don't affect `OrderService`
- ✅ **Follows SRP** - `OrderService` focuses on business logic only

### Service Registration in .NET

The .NET dependency injection container manages the creation and lifetime of services. Understanding how to register services is crucial for implementing DIP correctly.

**Basic Registration Patterns:**

```csharp
// Program.cs (modern .NET 6+)
var builder = WebApplication.CreateBuilder(args);

// Transient - created each time they're requested
// Use for: Lightweight, stateless services
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();
builder.Services.AddTransient<IReportGenerator, PdfReportGenerator>();

// Scoped - created once per HTTP request (or scope)
// Use for: Database contexts, request-specific services
builder.Services.AddScoped<IOrderRepository, SqlServerOrderRepository>();
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<IUnitOfWork, UnitOfWork>();

// Singleton - created once for the application lifetime
// Use for: Thread-safe services, configuration, caching
builder.Services.AddSingleton<IMemoryCache, MemoryCache>();
builder.Services.AddSingleton<IApplicationSettings, ApplicationSettings>();
builder.Services.AddSingleton<IMetricsCollector, MetricsCollector>();

// Register multiple implementations (all will be injected)
builder.Services.AddTransient<INotificationHandler, EmailNotificationHandler>();
builder.Services.AddTransient<INotificationHandler, SmsNotificationHandler>();
builder.Services.AddTransient<INotificationHandler, PushNotificationHandler>();

var app = builder.Build();
```

**Factory Pattern for Complex Creation:**

```csharp
// Conditional registration based on configuration
builder.Services.AddScoped<IPaymentProcessor>(serviceProvider =>
{
    var config = serviceProvider.GetRequiredService<IConfiguration>();
    var logger = serviceProvider.GetRequiredService<ILogger<IPaymentProcessor>>();
    var useTestMode = config.GetValue<bool>("PaymentTestMode");
    
    if (useTestMode)
    {
        return new MockPaymentProcessor(logger);
    }
    else
    {
        var stripeKey = config["Stripe:ApiKey"];
        return new StripePaymentProcessor(stripeKey, logger);
    }
});

// Factory with dependencies from DI
builder.Services.AddScoped<IEmailService>(sp =>
{
    var settings = sp.GetRequiredService<IOptions<EmailSettings>>();
    var logger = sp.GetRequiredService<ILogger<EmailService>>();
    
    return settings.Value.Provider switch
    {
        "SMTP" => new SmtpEmailService(settings, logger),
        "SendGrid" => new SendGridEmailService(settings, logger),
        "AWS" => new AwsSesEmailService(settings, logger),
        _ => throw new InvalidOperationException($"Unknown email provider: {settings.Value.Provider}")
    };
});

// Generic registration
builder.Services.AddScoped(typeof(IRepository<>), typeof(Repository<>));
```

**Configuration-based Registration:**

```csharp
// appsettings.json
{
  "Database": {
    "Provider": "SqlServer",  // or "MongoDB", "PostgreSQL"
    "ConnectionString": "Server=..."
  },
  "Email": {
    "Provider": "SendGrid",   // or "SMTP", "AWS"
    "ApiKey": "..."
  }
}

// Registration based on configuration
public static class ServiceRegistration
{
    public static IServiceCollection AddDataAccess(
        this IServiceCollection services,
        IConfiguration configuration)
    {
        var provider = configuration["Database:Provider"];
        
        switch (provider)
        {
            case "SqlServer":
                services.AddScoped<IOrderRepository, SqlServerOrderRepository>();
                services.AddScoped<ICustomerRepository, SqlServerCustomerRepository>();
                break;
                
            case "MongoDB":
                services.AddScoped<IOrderRepository, MongoDbOrderRepository>();
                services.AddScoped<ICustomerRepository, MongoDbCustomerRepository>();
                break;
                
            case "PostgreSQL":
                services.AddScoped<IOrderRepository, PostgresOrderRepository>();
                services.AddScoped<ICustomerRepository, PostgresCustomerRepository>();
                break;
                
            default:
                throw new InvalidOperationException($"Unknown database provider: {provider}");
        }
        
        return services;
    }
    
    public static IServiceCollection AddEmailService(
        this IServiceCollection services,
        IConfiguration configuration)
    {
        var provider = configuration["Email:Provider"];
        
        services.AddScoped<IEmailSender>(sp =>
        {
            var logger = sp.GetRequiredService<ILogger<IEmailSender>>();
            
            return provider switch
            {
                "SMTP" => new SmtpEmailSender(configuration, logger),
                "SendGrid" => new SendGridEmailSender(configuration, logger),
                "AWS" => new AwsSesEmailSender(configuration, logger),
                _ => throw new InvalidOperationException($"Unknown email provider: {provider}")
            };
        });
        
        return services;
    }
}

// Usage in Program.cs
builder.Services.AddDataAccess(builder.Configuration);
builder.Services.AddEmailService(builder.Configuration);
```

### Service Lifetimes: Deep Dive

Understanding service lifetimes is critical for avoiding memory leaks and bugs in DI-based applications.

**Visual representation:**

```
Application Start
     │
     ├─ SINGLETON (lives entire app lifetime)
     │  └─ IMemoryCache instance created once
     │     └─ Same instance for all requests
     │
     ├─ Request 1
     │  ├─ SCOPED (lives for request duration)
     │  │  └─ DbContext instance 1
     │  │  └─ OrderService instance 1
     │  │     ├─ TRANSIENT (new every time)
     │  │     │  └─ EmailSender instance 1
     │  │     └─ TRANSIENT
     │  │        └─ EmailSender instance 2 (different!)
     │  └─ Request 1 ends, scoped instances disposed
     │
     ├─ Request 2
     │  ├─ SCOPED (new instances for new request)
     │  │  └─ DbContext instance 2 (different from Request 1!)
     │  │  └─ OrderService instance 2 (different from Request 1!)
     │  └─ Request 2 ends, scoped instances disposed
     │
Application End
     └─ Singleton instances disposed
```

**Detailed Examples:**

```csharp
// TRANSIENT: New instance every time
// Perfect for: Lightweight, stateless services
services.AddTransient<IEmailSender, SmtpEmailSender>();

public class OrderService
{
    private readonly IEmailSender _emailSender1;
    private readonly IEmailSender _emailSender2;
    
    public OrderService(
        IEmailSender emailSender1,  // New instance
        IEmailSender emailSender2)  // Different new instance!
    {
        _emailSender1 = emailSender1;
        _emailSender2 = emailSender2;
        
        Console.WriteLine(_emailSender1 == _emailSender2); // False!
    }
}

// SCOPED: One instance per request/scope
// Perfect for: Database contexts, request-specific data
services.AddScoped<ApplicationDbContext>();
services.AddScoped<IOrderService, OrderService>();

public class OrderController
{
    private readonly IOrderService _orderService1;
    private readonly IOrderService _orderService2;
    
    public OrderController(
        IOrderService orderService1,  // Same instance
        IOrderService orderService2)  // Same instance (within request)
    {
        _orderService1 = orderService1;
        _orderService2 = orderService2;
        
        Console.WriteLine(_orderService1 == _orderService2); // True!
    }
}

// SINGLETON: One instance for entire application
// Perfect for: Thread-safe services, configuration, caching
services.AddSingleton<IMemoryCache, MemoryCache>();
services.AddSingleton<IConfiguration>(configuration);

public class CacheService
{
    private readonly IMemoryCache _cache;
    
    public CacheService(IMemoryCache cache)
    {
        _cache = cache; // Same instance across ALL requests
    }
}
```

**Common Lifetime Mistakes:**

```csharp
// ❌ CAPTIVE DEPENDENCY: Singleton capturing Scoped
// This is DANGEROUS!
services.AddSingleton<ReportService>();        // Singleton
services.AddScoped<ApplicationDbContext>();    // Scoped

public class ReportService  // Singleton!
{
    private readonly ApplicationDbContext _context;  // Scoped!
    
    // BUG: Singleton holds reference to first DbContext forever!
    // DbContext from first request is never disposed
    // Subsequent requests use stale DbContext
    public ReportService(ApplicationDbContext context)
    {
        _context = context;  // MEMORY LEAK!
    }
}

// ✅ FIX: Use matching lifetimes or inject IServiceProvider
services.AddScoped<ReportService>();  // Match DbContext lifetime

// Or inject factory
public class ReportService
{
    private readonly IServiceScopeFactory _scopeFactory;
    
    public ReportService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }
    
    public async Task GenerateReport()
    {
        using var scope = _scopeFactory.CreateScope();
        var context = scope.ServiceProvider.GetRequiredService<ApplicationDbContext>();
        // Use context safely
    }
}
```

**Lifetime Decision Tree:**

```
Is the service thread-safe and stateless?
├─ Yes: Does it need to live forever?
│  ├─ Yes → SINGLETON (e.g., IMemoryCache, IConfiguration)
│  └─ No: Does it need per-request data?
│     ├─ Yes → SCOPED (e.g., ICurrentUser, IRequestContext)
│     └─ No → TRANSIENT (e.g., IEmailSender, IValidator)
└─ No: Is it tied to request context?
   ├─ Yes → SCOPED (e.g., DbContext, IUnitOfWork)
   └─ No → TRANSIENT (default choice)
```

### Constructor Injection (Preferred Method)

Constructor injection is the recommended approach for DI because it makes dependencies explicit and required.

**Complete Example:**

```csharp
public class OrderController : ControllerBase
{
    private readonly IOrderService _orderService;
    private readonly ILogger<OrderController> _logger;
    private readonly ICurrentUser _currentUser;
    
    // All dependencies injected via constructor
    // This makes dependencies explicit and required
    public OrderController(
        IOrderService orderService,
        ILogger<OrderController> logger,
        ICurrentUser currentUser)
    {
        // Validate dependencies (optional but good practice)
        _orderService = orderService ?? throw new ArgumentNullException(nameof(orderService));
        _logger = logger ?? throw new ArgumentNullException(nameof(logger));
        _currentUser = currentUser ?? throw new ArgumentNullException(nameof(currentUser));
    }
    
    [HttpPost]
    public async Task<IActionResult> CreateOrder([FromBody] CreateOrderRequest request)
    {
        try
        {
            _logger.LogInformation(
                "Creating order for user {UserId}",
                _currentUser.UserId);
            
            var order = await _orderService.CreateOrder(request);
            
            _logger.LogInformation(
                "Order {OrderId} created successfully",
                order.Id);
            
            return CreatedAtAction(
                nameof(GetOrder),
                new { id = order.Id },
                order);
        }
        catch (ValidationException ex)
        {
            _logger.LogWarning(ex, "Order validation failed");
            return BadRequest(new { errors = ex.Errors });
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Failed to create order");
            return StatusCode(500, new { error = "Internal server error" });
        }
    }
    
    [HttpGet("{id}")]
    public async Task<IActionResult> GetOrder(string id)
    {
        var order = await _orderService.GetOrder(id);
        
        if (order == null)
            return NotFound();
        
        return Ok(order);
    }
}

// Service with its own dependencies
public class OrderService : IOrderService
{
    private readonly IOrderRepository _orderRepository;
    private readonly IInventoryService _inventoryService;
    private readonly IPaymentService _paymentService;
    private readonly IEmailService _emailService;
    private readonly ILogger<OrderService> _logger;
    
    public OrderService(
        IOrderRepository orderRepository,
        IInventoryService inventoryService,
        IPaymentService paymentService,
        IEmailService emailService,
        ILogger<OrderService> logger)
    {
        _orderRepository = orderRepository;
        _inventoryService = inventoryService;
        _paymentService = paymentService;
        _emailService = emailService;
        _logger = logger;
    }
    
    public async Task<Order> CreateOrder(CreateOrderRequest request)
    {
        // Business logic using injected dependencies
        var order = new Order
        {
            Id = Guid.NewGuid().ToString(),
            CustomerId = request.CustomerId,
            Items = request.Items,
            Total = request.Items.Sum(i => i.Price * i.Quantity)
        };
        
        // Check inventory
        await _inventoryService.ReserveStock(order.Items);
        
        // Process payment
        var paymentResult = await _paymentService.ProcessPayment(
            new PaymentRequest
            {
                Amount = order.Total,
                PaymentMethod = request.PaymentMethod
            });
        
        if (!paymentResult.Success)
            throw new PaymentException("Payment failed");
        
        // Save order
        await _orderRepository.Save(order);
        
        // Send confirmation
        await _emailService.SendOrderConfirmation(order);
        
        _logger.LogInformation("Order {OrderId} created successfully", order.Id);
        
        return order;
    }
    
    public async Task<Order> GetOrder(string orderId)
    {
        return await _orderRepository.GetById(orderId);
    }
}
```

**Why Constructor Injection is Best:**

```csharp
// ✅ Constructor Injection (BEST)
public class UserService
{
    private readonly IUserRepository _repository;
    
    public UserService(IUserRepository repository)
    {
        _repository = repository;  // Required, explicit
    }
}

// ❌ Property Injection (AVOID - hides dependencies)
public class UserService
{
    public IUserRepository Repository { get; set; }  // Optional, implicit
    
    public void CreateUser(User user)
    {
        Repository.Save(user);  // NullReferenceException if not set!
    }
}

// ❌ Method Injection (RARE - only for optional dependencies)
public class UserService
{
    public void CreateUser(User user, IUserRepository repository)
    {
        repository.Save(user);  // Dependency passed per method call
    }
}
```

### Testing with DI

One of the biggest benefits of DIP is testability. By depending on abstractions, you can easily mock dependencies in tests.

**Complete Testing Example:**

```csharp
// Unit test for OrderService
public class OrderServiceTests
{
    private readonly Mock<IOrderRepository> _mockRepository;
    private readonly Mock<IInventoryService> _mockInventory;
    private readonly Mock<IPaymentService> _mockPayment;
    private readonly Mock<IEmailService> _mockEmail;
    private readonly Mock<ILogger<OrderService>> _mockLogger;
    private readonly OrderService _sut;  // System Under Test
    
    public OrderServiceTests()
    {
        // Arrange - create mocks
        _mockRepository = new Mock<IOrderRepository>();
        _mockInventory = new Mock<IInventoryService>();
        _mockPayment = new Mock<IPaymentService>();
```

### Options Pattern for Configuration

The Options pattern provides a strongly-typed way to access configuration with DI.

**Complete Options Pattern Example:**

```csharp
// 1. Define settings class
public class EmailSettings
{
    public string SmtpServer { get; set; }
    public int Port { get; set; }
    public string Username { get; set; }
    public string Password { get; set; }
    public string FromAddress { get; set; }
    public bool EnableSsl { get; set; }
}

public class PaymentSettings
{
    public string StripeApiKey { get; set; }
    public string WebhookSecret { get; set; }
    public bool TestMode { get; set; }
    public decimal MinimumAmount { get; set; }
    public decimal MaximumAmount { get; set; }
}

// 2. appsettings.json
{
  "Email": {
    "SmtpServer": "smtp.gmail.com",
    "Port": 587,
    "Username": "your-email@gmail.com",
    "Password": "your-app-password",
    "FromAddress": "noreply@yourcompany.com",
    "EnableSsl": true
  },
  "Payment": {
    "StripeApiKey": "sk_test_...",
    "WebhookSecret": "whsec_...",
    "TestMode": true,
    "MinimumAmount": 1.00,
    "MaximumAmount": 10000.00
  }
}

// 3. Register in Program.cs
builder.Services.Configure<EmailSettings>(
    builder.Configuration.GetSection("Email"));

builder.Services.Configure<PaymentSettings>(
    builder.Configuration.GetSection("Payment"));

// 4. Use in service with IOptions<T>
public class EmailService : IEmailService
{
    private readonly EmailSettings _settings;
    private readonly ILogger<EmailService> _logger;
    
    // IOptions<T> injected by DI container
    public EmailService(
        IOptions<EmailSettings> options,
        ILogger<EmailService> logger)
    {
        _settings = options.Value;  // Get the actual settings
        _logger = logger;
    }
    
    public async Task SendEmail(string to, string subject, string body)
    {
        try
        {
            using var client = new SmtpClient(_settings.SmtpServer, _settings.Port);
            client.EnableSsl = _settings.EnableSsl;
            client.Credentials = new NetworkCredential(
                _settings.Username,
                _settings.Password);
            
            var message = new MailMessage
            {
                From = new MailAddress(_settings.FromAddress),
                Subject = subject,
                Body = body,
                IsBodyHtml = true
            };
            
            message.To.Add(to);
            
            await client.SendMailAsync(message);
            
            _logger.LogInformation(
                "Email sent successfully to {To} via {SmtpServer}",
                to,
                _settings.SmtpServer);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Failed to send email to {To}", to);
            throw;
        }
    }
}

// 5. Use IOptionsSnapshot<T> for reloadable configuration
public class PaymentService : IPaymentService
{
    private readonly IOptionsSnapshot<PaymentSettings> _settingsSnapshot;
    private readonly ILogger<PaymentService> _logger;
    
    // IOptionsSnapshot reloads when appsettings.json changes
    public PaymentService(
        IOptionsSnapshot<PaymentSettings> settingsSnapshot,
        ILogger<PaymentService> logger)
    {
        _settingsSnapshot = settingsSnapshot;
        _logger = logger;
    }
    
    public async Task<PaymentResult> ProcessPayment(PaymentRequest request)
    {
        // Get latest settings (reloaded if appsettings.json changed)
        var settings = _settingsSnapshot.Value;
        
        // Validate amount
        if (request.Amount < settings.MinimumAmount)
        {
            return new PaymentResult
            {
                Success = false,
                ErrorMessage = $"Amount must be at least ${settings.MinimumAmount}"
            };
        }
        
        if (request.Amount > settings.MaximumAmount)
        {
            return new PaymentResult
            {
                Success = false,
                ErrorMessage = $"Amount cannot exceed ${settings.MaximumAmount}"
            };
        }
        
        // Use Stripe API
        StripeConfiguration.ApiKey = settings.StripeApiKey;
        
        var chargeOptions = new ChargeCreateOptions
        {
            Amount = (long)(request.Amount * 100), // Convert to cents
            Currency = "usd",
            Source = request.PaymentMethod.Token
        };
        
        var service = new ChargeService();
        var charge = await service.CreateAsync(chargeOptions);
        
        return new PaymentResult
        {
            Success = charge.Status == "succeeded",
            TransactionId = charge.Id
        };
    }
}

// 6. Options validation
public class EmailSettingsValidator : IValidateOptions<EmailSettings>
{
    public ValidateOptionsResult Validate(string name, EmailSettings options)
    {
        var errors = new List<string>();
        
        if (string.IsNullOrEmpty(options.SmtpServer))
            errors.Add("SMTP server is required");
        
        if (options.Port <= 0 || options.Port > 65535)
            errors.Add("Invalid SMTP port");
        
        if (string.IsNullOrEmpty(options.FromAddress))
            errors.Add("From address is required");
        
        if (!IsValidEmail(options.FromAddress))
            errors.Add("From address is not a valid email");
        
        if (errors.Any())
            return ValidateOptionsResult.Fail(errors);
        
        return ValidateOptionsResult.Success;
    }
    
    private bool IsValidEmail(string email) =>
        new EmailAddressAttribute().IsValid(email);
}

// Register validator
builder.Services.AddSingleton<IValidateOptions<EmailSettings>, EmailSettingsValidator>();

// 7. IOptionsMonitor<T> for real-time change notifications
public class ConfigurationMonitorService : BackgroundService
{
    private readonly IOptionsMonitor<EmailSettings> _emailMonitor;
    private readonly ILogger<ConfigurationMonitorService> _logger;
    
    public ConfigurationMonitorService(
        IOptionsMonitor<EmailSettings> emailMonitor,
        ILogger<ConfigurationMonitorService> logger)
    {
        _emailMonitor = emailMonitor;
        _logger = logger;
        
        // Subscribe to changes
        _emailMonitor.OnChange(settings =>
        {
            _logger.LogInformation(
                "Email configuration changed. New SMTP server: {SmtpServer}",
                settings.SmtpServer);
        });
    }
    
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // Use current settings
            var settings = _emailMonitor.CurrentValue;
            _logger.LogInformation("Current SMTP: {SmtpServer}", settings.SmtpServer);
            
            await Task.Delay(TimeSpan.FromMinutes(5), stoppingToken);
        }
    }
}
```

**Options Pattern Comparison:**

| Interface | Behavior | Use When |
|-----------|----------|----------|
| `IOptions<T>` | Singleton, cached forever | Settings never change during app lifetime |
| `IOptionsSnapshot<T>` | Scoped, reloaded per request | Settings can change, need per-request reload |
| `IOptionsMonitor<T>` | Singleton, real-time updates | Need to react to configuration changes immediately |

## Common DI Anti-Patterns

Understanding and avoiding these anti-patterns is crucial for effective DI implementation.

### 1. Service Locator Anti-Pattern

**The Problem:**

```csharp
// BAD - Service Locator hides dependencies
public class OrderService
{
    public void ProcessOrder(Order order)
    {
        // Dependencies hidden - not obvious what this class needs!
        var repository = ServiceLocator.Get<IOrderRepository>();
        var emailSender = ServiceLocator.Get<IEmailSender>();
        var logger = ServiceLocator.Get<ILogger>();
        
        repository.Save(order);
        emailSender.SendConfirmation(order);
        logger.LogInformation($"Order {order.Id} processed");
    }
}

// Service Locator implementation (DON'T DO THIS!)
public static class ServiceLocator
{
    private static IServiceProvider _serviceProvider;
    
    public static void Initialize(IServiceProvider serviceProvider)
    {
        _serviceProvider = serviceProvider;
    }
    
    public static T Get<T>()
    {
        return _serviceProvider.GetRequiredService<T>();
    }
}
```

**Problems:**
- ❌ Hidden dependencies - can't tell what the class needs
- ❌ Hard to test - must initialize Service Locator
- ❌ Runtime errors - dependencies resolved late, failures at runtime not compile-time
- ❌ Poor design - violates Dependency Inversion Principle

**GOOD - Constructor Injection:**

```csharp
// GOOD - Dependencies are explicit and required
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IEmailSender _emailSender;
    private readonly ILogger _logger;
    
    // Clear what this class depends on!
    public OrderService(
        IOrderRepository repository,
        IEmailSender emailSender,
        ILogger logger)
    {
        _repository = repository;
        _emailSender = emailSender;
        _logger = logger;
    }
    
    public void ProcessOrder(Order order)
    {
        _repository.Save(order);
        _emailSender.SendConfirmation(order);
        _logger.LogInformation($"Order {order.Id} processed");
    }
}
```

### 2. God Constructor (Constructor Over-Injection)

**The Problem:**

```csharp
// BAD - Too many dependencies (Constructor Over-Injection)
public class OrderService
{
    public OrderService(
        IOrderRepository orderRepository,
        ICustomerRepository customerRepository,
        IProductRepository productRepository,
        IInventoryService inventoryService,
        IPaymentService paymentService,
        IShippingService shippingService,
        IEmailService emailService,
        ISmsService smsService,
        INotificationService notificationService,
        ITaxCalculator taxCalculator,
        IDiscountCalculator discountCalculator,
        ILogger logger,
        IMetricsCollector metrics,
        IConfiguration configuration)  // 14 dependencies!
    {
        // This is a code smell - class doing too much (SRP violation)
    }
}
```

**Solution - Refactor using these strategies:**

```csharp
// Strategy 1: Split into smaller services (BEST)
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IOrderValidator _validator;
    private readonly IOrderProcessor _processor;
    private readonly ILogger _logger;
    
    public OrderService(
        IOrderRepository repository,
        IOrderValidator validator,
        IOrderProcessor processor,
        ILogger logger)  // Only 4 dependencies!
    {
        _repository = repository;
        _validator = validator;
        _processor = processor;
        _logger = logger;
    }
}

// OrderProcessor handles its own concerns
public class OrderProcessor
{
    private readonly IPaymentService _paymentService;
    private readonly IInventoryService _inventoryService;
    private readonly INotificationService _notificationService;
    
    public OrderProcessor(
        IPaymentService paymentService,
        IInventoryService inventoryService,
        INotificationService notificationService)
    {
        _paymentService = paymentService;
        _inventoryService = inventoryService;
        _notificationService = notificationService;
    }
}

// Strategy 2: Facade pattern for related dependencies
public interface IOrderDependencies
{
    IOrderRepository Repository { get; }
    IPaymentService PaymentService { get; }
    IInventoryService InventoryService { get; }
    IEmailService EmailService { get; }
}

public class OrderService
{
    private readonly IOrderDependencies _dependencies;
    
    public OrderService(IOrderDependencies dependencies)
    {
        _dependencies = dependencies;
    }
}
```

### 3. Control Freak (Creating Dependencies Internally)

**The Problem:**

```csharp
// BAD - Creates dependencies internally
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IEmailSender _emailSender;
    
    public OrderService()
    {
        // Creating concrete implementations = tight coupling!
        _repository = new SqlServerOrderRepository();
        _emailSender = new SmtpEmailSender();
    }
}
```

**Solution:**

```csharp
// GOOD - Dependencies injected
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IEmailSender _emailSender;
    
    public OrderService(
        IOrderRepository repository,
        IEmailSender emailSender)
    {
        _repository = repository;
        _emailSender = emailSender;
    }
}
```

### 4. Ambient Context (Static Dependencies)

**The Problem:**

```csharp
// BAD - Static dependencies
public class OrderService
{
    public void ProcessOrder(Order order)
    {
        // Static dependencies are hard to test and replace
        Database.Current.Save(order);
        Logger.Current.LogInformation($"Order {order.Id} processed");
        EmailSender.Current.SendConfirmation(order);
    }
}
```

**Solution:**

```csharp
// GOOD - Inject dependencies
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly ILogger _logger;
    private readonly IEmailSender _emailSender;
    
    public OrderService(
        IOrderRepository repository,
        ILogger logger,
        IEmailSender emailSender)
    {
        _repository = repository;
        _logger = logger;
        _emailSender = emailSender;
    }
    
    public void ProcessOrder(Order order)
    {
        _repository.Save(order);
        _logger.LogInformation($"Order {order.Id} processed");
        _emailSender.SendConfirmation(order);
    }
}
```

### 5. Captive Dependencies (Lifetime Mismatch)

**The Problem:**

```csharp
// BAD - Singleton capturing Scoped dependency
services.AddSingleton<ReportService>();        // Lives forever
services.AddScoped<ApplicationDbContext>();    // Lives per request

public class ReportService  // Singleton!
{
    private readonly ApplicationDbContext _context;  // Scoped!
    
    // BUG: Singleton holds reference to first DbContext
    // DbContext from first request never disposed!
    public ReportService(ApplicationDbContext context)
    {
        _context = context;  // MEMORY LEAK!
    }
}
```

**Solution:**

```csharp
// Solution 1: Match lifetimes
services.AddScoped<ReportService>();  // Match DbContext lifetime

// Solution 2: Inject IServiceScopeFactory
services.AddSingleton<ReportService>();

public class ReportService
{
    private readonly IServiceScopeFactory _scopeFactory;
    
    public ReportService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }
    
    public async Task<Report> GenerateReport()
    {
        // Create a scope to get scoped dependencies
        using var scope = _scopeFactory.CreateScope();
        var context = scope.ServiceProvider
            .GetRequiredService<ApplicationDbContext>();
        
        // Use context safely within scope
        var data = await context.Orders.ToListAsync();
        return new Report(data);
    }
}
```

### Anti-Pattern Summary Table

| Anti-Pattern | Problem | Solution |
|--------------|---------|----------|
| **Service Locator** | Hidden dependencies, poor testability | Constructor injection |
| **God Constructor** | Too many dependencies (>5-6) | Refactor class (SRP violation) |
| **Control Freak** | Creating dependencies internally | Inject via constructor |
| **Ambient Context** | Static dependencies | Make explicit through DI |
| **Captive Dependencies** | Lifetime mismatch (Singleton→Scoped) | Match lifetimes or use factory |
| **Property Injection** | Optional dependencies, can be null | Constructor injection |
| **Method Injection** | Dependencies per method call | Constructor injection for required deps |

## Key Takeaways

🎯 **DIP is about architecture, DI is about implementation**
- DIP: High-level modules depend on abstractions
- DI: Technique for injecting dependencies
- Together they enable flexible, testable systems

🎯 **Constructor injection is the preferred method**
- Makes dependencies explicit and required
- Enables compile-time checking
- Facilitates testing with mocks

🎯 **Service lifetimes matter**
- Transient: New instance every time (lightweight, stateless)
- Scoped: One per request (DbContext, request-specific)
- Singleton: One forever (caching, thread-safe services)
- Captive dependencies (Singleton→Scoped) cause memory leaks!

🎯 **Benefits of DIP and DI**
- Loose coupling between modules
- Easy to test with mocks
- Easy to swap implementations
- Flexible architecture
- Clear dependencies

🎯 **Anti-patterns to avoid**
- Service Locator (hidden dependencies)
- God Constructors (too many dependencies = SRP violation)
- Control Freak (creating dependencies internally)
- Ambient Context (static dependencies)
- Captive Dependencies (lifetime mismatches)

🎯 **The Options pattern for configuration**
- IOptions: Cached forever
- IOptionsSnapshot: Reloaded per request
- IOptionsMonitor: Real-time updates with notifications

## Common Mistakes Checklist

When reviewing code, watch for these DIP violations:

- [ ] Classes instantiate dependencies with `new` operator
- [ ] Static dependencies (`Database.Current`, `Logger.Instance`)
- [ ] Service Locator pattern (`ServiceLocator.Get<T>()`)
- [ ] More than 5-6 constructor parameters (God Constructor)
- [ ] Property injection instead of constructor injection
- [ ] Singleton services capturing Scoped dependencies
- [ ] Concrete classes instead of interfaces in constructors
- [ ] Hidden dependencies not visible in constructor
- [ ] Dependencies resolved late (runtime errors instead of compile errors)
