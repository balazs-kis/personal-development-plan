# Lesson 1: Ubiquitous Language and Domain Modeling

## Learning Objectives

By the end of this lesson, you will be able to:
- Establish a ubiquitous language with domain experts
- Model core business concepts in code
- Distinguish between domain terms and technical implementation
- Apply domain modeling techniques to real-world scenarios
- Recognize and eliminate ambiguous language in your domain model
- Create a domain glossary and maintain it throughout the project lifecycle

---

## Introduction

Ubiquitous Language is the foundation of Domain-Driven Design. It's a shared language between developers and domain experts that permeates the codebase, documentation, and conversations. This eliminates translation errors and ensures the software accurately reflects business concepts.

When business experts and developers speak different languages, a "translation layer" emerges where concepts are constantly being interpreted and misinterpreted. This translation gap is where bugs are born, features are misunderstood, and technical debt accumulates. Ubiquitous Language eliminates this gap by creating a single, shared vocabulary that everyone uses consistently—from requirements documents to code comments to class names.

The power of Ubiquitous Language isn't just about naming things correctly. It's about creating a feedback loop where the code itself becomes a living specification of the business domain. When a business expert can read your code (or at least the method signatures and class names) and understand what it does, you've achieved true domain-driven design.

## Key Concepts Summary

### What is Ubiquitous Language?

A shared language between developers and domain experts that:
- Uses business terminology, not technical jargon
- Is used in code, documentation, and conversations
- Evolves as understanding deepens
- Eliminates the need for "translation"

### Bad Communication (No Ubiquitous Language)
```
Business Expert: "When a customer wants to buy something, they add it to their basket. 
                  If they complete the purchase, we create a receipt."

Developer's Code:
public class ShoppingCart { }  // Not "basket"
public class Order { }         // Not "receipt"
public class PurchaseProcess { } // Vague technical term

// Result: Confusion and misalignment
```

### Good Communication (With Ubiquitous Language)
```
Business Expert: "When a customer adds items to their Basket, they can proceed to 
                  Checkout. Upon payment, we generate a Receipt and fulfill the Order."

Developer's Code:
public class Basket { }
public class Checkout { }
public class Receipt { }
public class Order { }
public class Fulfillment { }

// Result: Code that speaks the business language
```

### Domain Modeling Example: E-Commerce
```csharp
// Rich domain model using ubiquitous language
public class Order
{
    public OrderId Id { get; private set; }
    public Customer Customer { get; private set; }
    private List<OrderLine> _lines = new();
    public IReadOnlyCollection<OrderLine> Lines => _lines.AsReadOnly();
    public OrderStatus Status { get; private set; }
    public Money TotalAmount { get; private set; }
    
    // Factory method uses domain language
    public static Order CreateNew(Customer customer)
    {
        return new Order 
        { 
            Id = OrderId.Generate(),
            Customer = customer,
            Status = OrderStatus.Draft,
            TotalAmount = Money.Zero
        };
    }
    
    // Methods reflect business operations
    public void AddLine(Product product, Quantity quantity)
    {
        if (Status != OrderStatus.Draft)
            throw new OrderCannotBeModifiedException();
            
        var line = new OrderLine(product, quantity);
        _lines.Add(line);
        RecalculateTotalAmount();
    }
    
    public void Submit()
    {
        if (_lines.Count == 0)
            throw new EmptyOrderException();
            
        Status = OrderStatus.Submitted;
        // Domain event
        DomainEvents.Raise(new OrderSubmitted(Id));
    }
    
    public void Confirm()
    {
        if (Status != OrderStatus.Submitted)
            throw new InvalidOrderStateException();
            
        Status = OrderStatus.Confirmed;
        DomainEvents.Raise(new OrderConfirmed(Id));
    }
    
    private void RecalculateTotalAmount()
    {
        TotalAmount = _lines
            .Select(l => l.LineTotal)
            .Aggregate(Money.Zero, (sum, lineTotal) => sum + lineTotal);
    }
}

// Value objects with business meaning
public record OrderId(Guid Value)
{
    public static OrderId Generate() => new(Guid.NewGuid());
}

public record Money(decimal Amount, Currency Currency)
{
    public static Money Zero => new(0, Currency.USD);
    
    public static Money operator +(Money left, Money right)
    {
        if (left.Currency != right.Currency)
            throw new CurrencyMismatchException();
            
        return new Money(left.Amount + right.Amount, left.Currency);
    }
}

public record Quantity(int Value)
{
    public Quantity
    {
        if (Value <= 0)
            throw new ArgumentException("Quantity must be positive");
    }
}

// Enums reflect business states
public enum OrderStatus
{
    Draft,
    Submitted,
    Confirmed,
    Shipped,
    Delivered,
    Cancelled
}
```

### Building Ubiquitous Language

The process of developing ubiquitous language is iterative and collaborative. It requires continuous refinement as the team's understanding of the domain deepens.

**Technique 1: Event Storming**

Event Storming is a workshop-based technique that brings domain experts and developers together to explore complex business domains.

Process:
1. Gather domain experts and developers in a room with unlimited wall space
2. Use orange sticky notes to identify domain events (things that happen in past tense): "Order Placed", "Payment Received", "Item Shipped"
3. Use blue sticky notes to work backwards and find commands (actions that trigger events): "Place Order", "Process Payment", "Ship Item"
4. Use yellow sticky notes to discover entities and aggregates involved: "Order", "Payment", "Shipment"
5. Use red sticky notes to highlight problems, questions, and areas of confusion
6. Use purple sticky notes to define policies (when X happens, then do Y)
7. Use green sticky notes to identify external systems

Benefits:
- Reveals hidden complexity early
- Creates shared understanding across technical and business teams
- Identifies boundaries naturally (future bounded contexts)
- Exposes conflicting mental models

Example Session Output:
```
[Customer Registered] ← [Register Customer] → Customer aggregate
[Basket Created] ← [Create Basket] → Basket aggregate
[Item Added to Basket] ← [Add Item] → Basket aggregate
[Order Placed] ← [Place Order] → Order aggregate
[Payment Initiated] ← [Initiate Payment] → Payment aggregate
[Payment Confirmed] → [Send Confirmation Email] (policy)
[Order Confirmed] ← [Confirm Order] → Order aggregate
[Shipment Created] ← [Create Shipment] → Shipment aggregate
```

**Technique 2: Example Mapping**

Example Mapping uses concrete business scenarios to extract rules and terminology.

Process:
1. Write the feature/story on a yellow card
2. Write rules on blue cards (business rules that apply)
3. Write examples on green cards (concrete scenarios)
4. Write questions on red cards (unknowns to clarify)

Example: E-Commerce Discount Feature
```
Story (Yellow): Apply customer loyalty discounts to orders

Rules (Blue):
- Bronze members get 5% discount
- Silver members get 10% discount
- Gold members get 15% discount
- Discounts apply to order subtotal before tax
- Only one membership discount per order

Examples (Green):
- Given a Bronze member with $100 order → Discount is $5
- Given a Gold member with $200 order → Discount is $30
- Given a non-member → No discount applied

Questions (Red):
- Can discounts be combined with promotional codes?
- What happens if membership expires during checkout?
- Do discounts apply to sale items?
```

From these examples, we extract ubiquitous language:
- **Membership Tier**: Bronze, Silver, Gold (enum)
- **Discount**: Percentage-based reduction on order subtotal (value object)
- **Order Subtotal**: Total before tax and after discounts (calculated value)

**Technique 3: Domain Glossary**

A living document that defines all domain terms with precision.

```markdown
# Domain Glossary: E-Commerce

**Basket**: A collection of products a customer intends to purchase. A basket is temporary 
and belongs to a single customer session. Items can be added, removed, or modified freely. 
A basket becomes an Order when the customer proceeds through checkout and provides payment.
- Synonym: Shopping Cart (internal term: use "Basket")
- Lifespan: Session-based, expires after 24 hours of inactivity
- Owner: Customer (may be anonymous or authenticated)

**Order**: A confirmed purchase request with payment information and shipping details. 
Once an order is confirmed, its line items cannot be modified—only the entire order can 
be cancelled. An order represents a commitment to purchase.
- Not to be confused with: Basket (pre-purchase), Receipt (post-payment proof)
- States: Draft → Submitted → Confirmed → Shipped → Delivered → Completed
- Invariant: Must contain at least one order line

**Receipt**: Proof of payment generated after successful order payment processing. 
Contains a snapshot of order details at time of purchase, payment method, and transaction ID. 
Receipts are immutable and kept for auditing purposes.
- Generated: After successful payment confirmation
- Format: PDF document, stored permanently
- Purpose: Customer record, tax compliance, returns processing

**Fulfillment**: The end-to-end process of preparing, packing, and shipping ordered items 
to the customer. Begins when an order is confirmed and payment is received. Includes 
inventory allocation, picking, packing, and carrier handoff.
- Triggered by: OrderConfirmed event
- Consists of: Pick → Pack → Ship → Deliver
- Owner: Warehouse team
- SLA: Ships within 2 business days of confirmation

**Return**: A customer-initiated request to send back purchased items for refund or exchange. 
Returns must be initiated within 30 days of delivery. Some items (custom, perishable) are 
non-returnable.
- Conditions: Within 30-day window, item in original condition
- Process: Request → Approve → Ship → Inspect → Refund/Exchange
- Refund: Processed to original payment method within 5-7 business days
- Not the same as: Cancellation (before shipment)

**Product Catalog**: The authoritative source of product information including descriptions, 
pricing, images, and specifications. Used for browsing and discovery.
- Maintained by: Merchandising team
- Updated: Real-time via admin interface
- Separate from: Inventory (stock levels), Order Items (purchase snapshots)

**Inventory**: Physical stock levels for products across warehouses. Tracks quantity 
available, quantity allocated (reserved for orders), and quantity on order from suppliers.
- Real-time tracking: Yes
- Locations: Multiple warehouse support
- Reservation: Allocated when order confirmed, released if order cancelled

**Customer**: A person or business entity with an account in the system. Can have multiple 
shipping addresses, payment methods, and order history.
- Identified by: Email address (unique)
- Authentication: Email/password or social login
- Membership: None, Bronze, Silver, Gold (affects discounts)

**Promotional Code**: A time-limited, single-use or multi-use code that provides discounts 
or benefits. Can be percentage-based, fixed amount, or free shipping.
- Format: Alphanumeric, 6-12 characters
- Rules: Expiry date, usage limits, minimum order value, eligible products
- Combination: May or may not stack with membership discounts (configured per promotion)
```

## Anti-Patterns: What NOT to Do

### Anti-Pattern 1: Technical Language Leaking into Domain

```csharp
// BAD - Technical implementation details
public class OrderDTO
{
    public int PK_OrderID { get; set; }  // Database speak
    public int FK_CustomerID { get; set; }
    public List<OrderItemDTO> Items { get; set; }
    public string StatusFlag { get; set; }  // "0", "1", "2"
}

public class OrderService
{
    public async Task<bool> ProcessOrder(int orderId)  // Vague technical term
    {
        var dto = await _repo.SelectOrderById(orderId);  // SQL speak
        // ...
    }
}

// GOOD - Domain language
public class Order
{
    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }
    private List<OrderLine> _lines = new();
    public OrderStatus Status { get; private set; }  // Enum with business meaning
}

public class OrderService
{
    public async Task ConfirmOrder(OrderId orderId)  // Business language
    {
        var order = await _orderRepository.GetById(orderId);  // Domain language
        order.Confirm();  // Business operation
    }
}
```

### Anti-Pattern 2: Generic Names that Hide Domain Concepts

```csharp
// BAD - Generic, meaningless names
public class Item { }  // Item of what?

public class Info { }

public class Handler { }
public class Helper { }
public class Utility { }

// GOOD - Specific domain names

public class ProductSpecifications { }
public class ShippingAddress { }
public class PaymentProcessor { }
public class OrderConfirmationHandler { }
public class PriceCalculator { }

public void ProcessRefund(Return return) { }
```

### Anti-Pattern 3: Synonyms Creating Confusion

```csharp
// BAD - Multiple terms for same concept
public class ShoppingCart { }  // In UI layer
public class Basket { }  // In domain layer
public class Order { }  // Wait, is this the same thing?

public void AddToCart() { }
public void AddToBasket() { }
public void AddToOrder() { }  // Are these different?

// GOOD - One term, used everywhere
public class Basket { }  // Agreed ubiquitous term

public void AddToBasket() { }  // Used consistently
```

### Anti-Pattern 4: Abbreviations and Acronyms

```csharp
// BAD - Unclear abbreviations
public class CustOrdProc { }
public class PmtGw { }
public class InvMgr { }
public Money CalcTotAmt() { }

// GOOD - Full, clear names

// Exception: Well-known business acronyms
public class SLAPolicy { }  // If "SLA" is used in business
public class APIEndpoint { }  // Universally understood
```

## Advanced Domain Modeling Patterns

### Pattern 1: Making Implicit Concepts Explicit

Often, important domain concepts are implied but never explicitly modeled. Making them explicit strengthens the model.

```csharp
// IMPLICIT - "Special price" is implied but not modeled
public class Product
{
    public Money RegularPrice { get; set; }
    public Money? SpecialPrice { get; set; }  // Nullable, unclear when it applies
    public DateTime? SpecialPriceStart { get; set; }
    public DateTime? SpecialPriceEnd { get; set; }
}

public Money GetPrice(DateTime date)
{
    if (SpecialPrice.HasValue 
        && SpecialPriceStart <= date 
        && date <= SpecialPriceEnd)
        return SpecialPrice.Value;
    return RegularPrice;
}

// EXPLICIT - "Promotion" is now a first-class concept
public class Product
{
    public Money RegularPrice { get; private set; }
    private List<Promotion> _promotions = new();
    
    public Money GetPrice(DateTime date)
    {
        var activePromotion = _promotions
            .Where(p => p.IsActiveOn(date))
            .OrderBy(p => p.Price)
            .FirstOrDefault();
            
        return activePromotion?.Price ?? RegularPrice;
    }
}

public class Promotion  // Explicit domain concept
{
    public Money Price { get; private set; }
    public DateRange ActivePeriod { get; private set; }
    public string Description { get; private set; }
    
    public bool IsActiveOn(DateTime date) => ActivePeriod.Contains(date);
}

public record DateRange(DateTime Start, DateTime End)
{
    public bool Contains(DateTime date) => date >= Start && date <= End;
}
```

### Pattern 2: Specifications Pattern for Business Rules

Encapsulate complex business rules into reusable, testable specifications.

```csharp
// Business rule: "Eligible customers can place orders"
// Eligibility means: account in good standing, no overdue payments, verified email

// Without Specification - Rules scattered
public class OrderService
{
    public async Task<Result> PlaceOrder(CustomerId customerId)
    {
        var customer = await _customerRepo.GetById(customerId);
        
        if (customer.AccountStatus != AccountStatus.Active)
            return Result.Fail("Account not active");
        
        if (customer.OverduePayments > Money.Zero)
            return Result.Fail("Outstanding payments");
        
        if (!customer.EmailVerified)
            return Result.Fail("Email not verified");
        
        // Place order...
    }
}

// With Specification - Rules encapsulated
public interface ISpecification<T>
{
    bool IsSatisfiedBy(T candidate);
    string ReasonForDissatisfaction { get; }
}

public class CustomerEligibilitySpecification : ISpecification<Customer>
{
    public bool IsSatisfiedBy(Customer customer)
    {
        if (customer.AccountStatus != AccountStatus.Active)
        {
            ReasonForDissatisfaction = "Account is not active";
            return false;
        }
        
        if (customer.OverduePayments > Money.Zero)
        {
            ReasonForDissatisfaction = $"Overdue payments: {customer.OverduePayments}";
            return false;
        }
        
        if (!customer.EmailVerified)
        {
            ReasonForDissatisfaction = "Email address not verified";
            return false;
        }
        
        return true;
    }
    
    public string ReasonForDissatisfaction { get; private set; }
}

public class OrderService
{
    private readonly CustomerEligibilitySpecification _eligibility;
    
    public async Task<Result> PlaceOrder(CustomerId customerId)
    {
        var customer = await _customerRepo.GetById(customerId);
        
        if (!_eligibility.IsSatisfiedBy(customer))
            return Result.Fail(_eligibility.ReasonForDissatisfaction);
        
        // Place order...
    }
}
```

### Pattern 3: Policy Objects for Complex Rules

When business rules are complex and conditional, extract them into policy objects.

```csharp
// Business rule: "Shipping cost depends on multiple factors"
public interface IShippingCostPolicy
{
    Money Calculate(Order order, ShippingAddress address);
}

public class StandardShippingPolicy : IShippingCostPolicy
{
    private const decimal BaseRate = 5.99m;
    private const decimal PerItemRate = 1.50m;
    private const decimal FreeShippingThreshold = 50.00m;
    
    public Money Calculate(Order order, ShippingAddress address)
    {
        // Free shipping over threshold
        if (order.SubTotal >= new Money(FreeShippingThreshold, Currency.USD))
            return Money.Zero;
        
        // Base rate plus per-item charge
        var itemsCharge = order.Lines.Count * PerItemRate;
        var total = BaseRate + itemsCharge;
        
        return new Money(total, Currency.USD);
    }
}

public class ExpressShippingPolicy : IShippingCostPolicy
{
    public Money Calculate(Order order, ShippingAddress address)
    {
        // Express is 2x standard, no free shipping
        var standard = new StandardShippingPolicy().Calculate(order, address);
        return standard * 2;
    }
}

public class InternationalShippingPolicy : IShippingCostPolicy
{
    private readonly ICountryZoneService _zones;
    
    public Money Calculate(Order order, ShippingAddress address)
    {
        var zone = _zones.GetZone(address.Country);
        var weight = order.Lines.Sum(l => l.Product.Weight);
        
        return zone.CalculateShipping(weight);
    }
}
```

## Real-World Case Study: Payment Processing

Let's examine how ubiquitous language evolves in a real payment processing domain.

### Initial Understanding (Naive Model)

```csharp
// First attempt - Technical view
public class Payment
{
    public int Id { get; set; }
    public decimal Amount { get; set; }
    public string Status { get; set; }  // "pending", "success", "failed"
    public DateTime Date { get; set; }
}

public class PaymentService
{
    public bool ProcessPayment(Payment payment)
    {
        // Call payment gateway...
        return true;
    }
}
```

### After Domain Discussions (Improved Model)

Through conversations with payment domain experts, we discover:
- Payments aren't just "processed"—they go through authorization, capture, and settlement
- There are different payment methods (card, bank transfer, digital wallet)
- Refunds are not "negative payments"—they're separate concepts
- Failed payments need retry logic with different failure reasons

```csharp
// Improved model with ubiquitous language
public class PaymentTransaction
{
    public PaymentTransactionId Id { get; private set; }
    public Money Amount { get; private set; }
    public PaymentMethod Method { get; private set; }
    public PaymentStatus Status { get; private set; }
    
    // Payment lifecycle matches business process
    public void Authorize()
    {
        if (Status != PaymentStatus.Pending)
            throw new InvalidPaymentStateException();
        
        Status = PaymentStatus.Authorized;
        DomainEvents.Raise(new PaymentAuthorized(Id));
    }
    
    public void Capture()
    {
        if (Status != PaymentStatus.Authorized)
            throw new InvalidPaymentStateException();
        
        Status = PaymentStatus.Captured;
        DomainEvents.Raise(new PaymentCaptured(Id, Amount));
    }
    
    public void Fail(PaymentFailureReason reason)
    {
        Status = PaymentStatus.Failed;
        FailureReason = reason;
        DomainEvents.Raise(new PaymentFailed(Id, reason));
    }
}

public enum PaymentStatus
{
    Pending,
    Authorized,  // Funds reserved but not captured
    Captured,    // Funds deducted from customer
    Settled,     // Funds transferred to merchant account
    Failed,
    Cancelled
}

public enum PaymentFailureReason
{
    InsufficientFunds,
    ExpiredCard,
    DeclinedByBank,
    NetworkTimeout,
    FraudDetected,
    InvalidCvv,
    CardReported​Lost
}

public abstract class PaymentMethod
{
    public abstract Task<PaymentResult> ProcessAuthorization(Money amount);
}

public class CreditCardPayment : PaymentMethod
{
    public CardNumber Number { get; private set; }
    public ExpiryDate Expiry { get; private set; }
    public Cvv Cvv { get; private set; }
    public CardholderName Name { get; private set; }
    
    public override async Task<PaymentResult> ProcessAuthorization(Money amount)
    {
        // Credit card specific authorization logic
    }
}

public class BankTransferPayment : PaymentMethod
{
    public BankAccount AccountNumber { get; private set; }
    public RoutingNumber RoutingNumber { get; private set; }
    
    public override async Task<PaymentResult> ProcessAuthorization(Money amount)
    {
        // Bank transfer specific authorization logic
    }
}

// Refund is separate concept, not reverse payment
public class Refund
{
    public RefundId Id { get; private set; }
    public PaymentTransactionId OriginalPaymentId { get; private set; }
    public Money Amount { get; private set; }
    public RefundReason Reason { get; private set; }
    public RefundStatus Status { get; private set; }
    
    public void Process()
    {
        // Refund processing logic
    }
}
```

Now the code reads like a conversation with a payment expert. Terms like "authorize," "capture," "settlement," "chargeback" are used consistently everywhere.

## Domain Discovery Questions

When modeling a domain, systematically explore these questions:

### Structural Questions
1. **What are the key business concepts?** (nouns)
   - What "things" does the business track and care about?
   - Which concepts have identity? Which are just values?

2. **What actions can be performed?** (verbs)
   - What can users do in this system?
   - What operations do business experts talk about?

3. **What are the relationships?**
   - How do concepts relate to each other?
   - What owns what? What references what?

### Behavioral Questions
4. **What rules must never be violated?** (invariants)
   - What would make data "invalid" from a business perspective?
   - What consistency rules must always hold true?

5. **What events are important to the business?** (domain events)
   - What significant things happen that others care about?
   - What triggers notifications or downstream processes?

6. **When does the business care about something happening?** (triggers)
   - What causes state transitions?
   - What conditions trigger business rules?

### Lifecycle Questions
7. **What are the states and transitions?**
   - What lifecycle stages do entities go through?
   - What triggers state changes?
   - What operations are valid in each state?

8. **What are the temporal aspects?**
   - Are there time-based rules?
   - Do concepts have validity periods?
   - Are there deadlines or expirations?

### Boundary Questions
9. **Where are the natural seams?**
   - What areas have different vocabularies?
   - What teams own different concepts?
   - Where do integration points exist?

10. **What are the exceptional cases?**
    - What can go wrong?
    - How does the business handle errors?
    - What compensating actions exist?

### Example Dialogue: E-Commerce Order

**Q: What are the key concepts?**
A: Order, Customer, Product, Payment, Shipment

**Q: What actions can be performed?**
A: Place order, confirm payment, ship order, deliver order, return item, cancel order

**Q: What rules must never be violated?**
A: 
- Order must have at least one item
- Cannot modify order after confirmation
- Cannot ship without payment confirmation
- Cannot return items after 30 days

**Q: What events are important?**
A: Order Placed, Payment Confirmed, Order Shipped, Order Delivered, Return Requested

**Q: What are the states of an Order?**
A: Draft → Submitted → Confirmed → Shipped → Delivered → Completed
    (with possible transitions to Cancelled or Returned)

## Common Challenges and Solutions

### Challenge 1: Business Experts Use Inconsistent Terms

**Problem:** Different domain experts use different words for the same concept.

**Solution:** Facilitate consensus sessions. Document the agreed term and its alternatives in the glossary.

```markdown
**Order** (agreed term)
- Also called: "Purchase", "Transaction" (sales team)
- Deprecated terms: "Cart" (this is actually Basket)
- Definition: A confirmed purchase with payment information
```

### Challenge 2: Same Word, Multiple Meanings

**Problem:** "Product" means different things to different people.

**Solution:** Recognize this as a bounded context boundary. Use different terms or qualify the context.

```csharp
// In Catalog context
namespace ECommerce.Catalog
{
    public class Product { /* rich details for browsing */ }
}

// In Orders context
namespace ECommerce.Orders
{
    public class OrderLine { /* snapshot of product at purchase time */ }
}

// In Warehouse context
namespace ECommerce.Warehouse
{
    public class InventoryItem { /* physical stock tracking */ }
}
```

### Challenge 3: Developers Want Generic, Reusable Names

**Problem:** Developers trained to think in generic terms resist specific domain language.

**Solution:** Emphasize that specificity is a feature, not a bug. Specific names prevent misuse.

```csharp
// Generic (reusable but unclear)
public class Item { }
public class Collection { }
public void Process(Item item) { }

// Specific (clear intent, prevents misuse)
public class OrderLine { }
public class ShoppingBasket { }
public void ConfirmPayment(PaymentTransaction payment) { }
```

### Challenge 4: Language Evolution and Breaking Changes

**Problem:** As understanding deepens, you realize existing names are wrong.

**Solution:** Refactor boldly. Use compiler to find all usages. Update glossary with deprecation notes.

```csharp
// Before: Realized "Invoice" was wrong term
public class Invoice 
{ 
    // This was actually modeling a receipt, not an invoice
}

// After: Renamed to correct term
[Obsolete("Use Receipt instead. See glossary for distinction.")]
public class Invoice { }  // Mark obsolete temporarily

public class Receipt 
{ 
    // Correct term for payment confirmation document
}

// Update glossary
```

```markdown
**Receipt**: Proof of payment provided to customer (correct term, use this)
**Invoice**: Request for payment sent before payment (different concept)
Note: Prior to v2.5, we incorrectly called receipts "invoices". Code refactored 2024-01.
```

## Deep Dive: Anemic vs. Rich Domain Models

### The Anemic Model Anti-Pattern

An anemic model is when domain objects are just data bags with getters/setters, and all business logic lives in services.

```csharp
// ANEMIC MODEL - Just data, no behavior
public class Order
{
    public Guid Id { get; set; }
    public Guid CustomerId { get; set; }
    public List<OrderLineDto> Lines { get; set; }
    public string Status { get; set; }
    public decimal TotalAmount { get; set; }
    public decimal ShippingCost { get; set; }
    public decimal TaxAmount { get; set; }
}

// All business logic in services
public class OrderService
{
    public void AddLineToOrder(Guid orderId, Guid productId, int quantity, decimal price)
    {
        var order = _repository.GetById(orderId);
        
        // Validation logic scattered in service
        if (order.Status != "Draft")
            throw new Exception("Cannot modify order");
        
        if (order.Lines == null)
            order.Lines = new List<OrderLineDto>();
        
        if (order.Lines.Count >= 50)
            throw new Exception("Too many lines");
        
        // Business logic in service
        order.Lines.Add(new OrderLineDto 
        { 
            ProductId = productId,
            Quantity = quantity,
            Price = price
        });
        
        // Calculation logic in service
        order.TotalAmount = order.Lines.Sum(l => l.Price * l.Quantity);
        order.TaxAmount = order.TotalAmount * 0.10m;
        order.ShippingCost = CalculateShipping(order);
        
        _repository.Save(order);
    }
    
    public void SubmitOrder(Guid orderId)
    {
        var order = _repository.GetById(orderId);
        
        // Business rules in service
        if (order.Lines == null || order.Lines.Count == 0)
            throw new Exception("Empty order");
        
        if (order.Status != "Draft")
            throw new Exception("Invalid status");
        
        order.Status = "Submitted";
        _repository.Save(order);
        
        // Coordination in service
        _emailService.SendConfirmation(order.CustomerId);
        _inventoryService.ReserveItems(order.Lines);
    }
}
```

**Problems with Anemic Model:**
- Business logic is scattered across multiple services
- Impossible to enforce invariants (anyone can set Status directly)
- Domain objects don't reflect domain language
- Hard to understand business rules by reading code
- Easy to violate business rules accidentally
- Testing requires mocking many services

### The Rich Domain Model

A rich domain model encapsulates business logic within domain objects, making them responsible for maintaining their own consistency.

```csharp
// RICH DOMAIN MODEL - Behavior and data together
public class Order  // Aggregate root
{
    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }
    
    // Encapsulated collection
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyCollection<OrderLine> Lines => _lines.AsReadOnly();
    
    // Business state
    public OrderStatus Status { get; private set; }
    
    // Calculated values maintained by aggregate
    public Money SubTotal { get; private set; }
    public Money TaxAmount { get; private set; }
    public Money ShippingCost { get; private set; }
    public Money TotalAmount { get; private set; }
    
    // Domain events
    private readonly List<DomainEvent> _domainEvents = new();
    public IReadOnlyCollection<DomainEvent> DomainEvents => _domainEvents.AsReadOnly();
    
    // Factory method - controls creation
    public static Order CreateNew(CustomerId customerId, ShippingAddress address)
    {
        var order = new Order
        {
            Id = OrderId.Generate(),
            CustomerId = customerId,
            Status = OrderStatus.Draft,
            SubTotal = Money.Zero,
            TaxAmount = Money.Zero,
            ShippingCost = Money.Zero,
            TotalAmount = Money.Zero
        };
        
        order._domainEvents.Add(new OrderCreated(order.Id, customerId));
        return order;
    }
    
    // Business operations with intention-revealing names
    public void AddLine(Product product, Quantity quantity)
    {
        // Enforce business rules
        if (Status != OrderStatus.Draft)
            throw new OrderCannotBeModifiedException(
                "Only draft orders can be modified");
        
        if (_lines.Count >= 50)
            throw new MaxOrderLinesExceededException(
                "Orders cannot exceed 50 lines");
        
        // Check if product already in order
        var existingLine = _lines.FirstOrDefault(l => l.ProductId == product.Id);
        if (existingLine != null)
        {
            existingLine.IncreaseQuantity(quantity);
        }
        else
        {
            var line = new OrderLine(product.Id, product.Name, product.Price, quantity);
            _lines.Add(line);
        }
        
        // Maintain consistency
        RecalculateTotals();
        
        _domainEvents.Add(new OrderLineAdded(Id, product.Id, quantity));
    }
    
    public void RemoveLine(OrderLineId lineId)
    {
        if (Status != OrderStatus.Draft)
            throw new OrderCannotBeModifiedException();
        
        var line = _lines.FirstOrDefault(l => l.Id == lineId)
            ?? throw new OrderLineNotFoundException();
        
        _lines.Remove(line);
        RecalculateTotals();
        
        _domainEvents.Add(new OrderLineRemoved(Id, lineId));
    }
    
    public void ApplyDiscountCode(DiscountCode code)
    {
        if (Status != OrderStatus.Draft)
            throw new OrderCannotBeModifiedException();
        
        if (!code.IsValidFor(this))
            throw new InvalidDiscountCodeException();
        
        _appliedDiscount = code.CalculateDiscount(SubTotal);
        RecalculateTotals();
    }
    
    public void Submit()
    {
        // Enforce invariants
        if (_lines.Count == 0)
            throw new EmptyOrderException("Cannot submit order with no items");
        
        if (Status != OrderStatus.Draft)
            throw new InvalidOrderStateException(
                $"Cannot submit order in {Status} status");
        
        // State transition
        Status = OrderStatus.Submitted;
        SubmittedAt = DateTime.UtcNow;
        
        // Domain event
        _domainEvents.Add(new OrderSubmitted(Id, CustomerId, TotalAmount));
    }
    
    public void Confirm(PaymentId paymentId)
    {
        if (Status != OrderStatus.Submitted)
            throw new InvalidOrderStateException();
        
        Status = OrderStatus.Confirmed;
        PaymentId = paymentId;
        ConfirmedAt = DateTime.UtcNow;
        
        _domainEvents.Add(new OrderConfirmed(Id, paymentId));
    }
    
    public void Cancel(CancellationReason reason)
    {
        // Business rule: Can only cancel before shipping
        if (Status == OrderStatus.Shipped || Status == OrderStatus.Delivered)
            throw new OrderCannotBeCancelledException(
                "Cannot cancel order after shipping");
        
        if (Status == OrderStatus.Cancelled)
            throw new OrderAlreadyCancelledException();
        
        var previousStatus = Status;
        Status = OrderStatus.Cancelled;
        CancellationReason = reason;
        CancelledAt = DateTime.UtcNow;
        
        _domainEvents.Add(new OrderCancelled(Id, previousStatus, reason));
    }
    
    // Private methods for internal consistency
    private void RecalculateTotals()
    {
        SubTotal = _lines
            .Select(l => l.LineTotal)
            .Aggregate(Money.Zero, (sum, total) => sum + total);
        
        if (_appliedDiscount != null)
            SubTotal = SubTotal - _appliedDiscount;
        
        TaxAmount = SubTotal * 0.10m;  // 10% tax (simplified)
        ShippingCost = CalculateShippingCost();
        TotalAmount = SubTotal + TaxAmount + ShippingCost;
    }
    
    private Money CalculateShippingCost()
    {
        // Free shipping over $50
        if (SubTotal >= new Money(50, Currency.USD))
            return Money.Zero;
        
        // Base rate + per item
        return new Money(5.99m + (_lines.Count * 1.50m), Currency.USD);
    }
}

// Entity within aggregate
public class OrderLine
{
    internal OrderLine(ProductId productId, string productName, Money price, Quantity quantity)
    {
        Id = OrderLineId.Generate();
        ProductId = productId;
        ProductName = productName;  // Snapshot at time of order
        PriceAtTimeOfOrder = price;  // Price might change later
        Quantity = quantity;
    }
    
    public OrderLineId Id { get; private set; }
    public ProductId ProductId { get; private set; }
    public string ProductName { get; private set; }
    public Money PriceAtTimeOfOrder { get; private set; }
    public Quantity Quantity { get; private set; }
    
    public Money LineTotal => new(
        PriceAtTimeOfOrder.Amount * Quantity.Value,
        PriceAtTimeOfOrder.Currency);
    
    internal void IncreaseQuantity(Quantity additionalQuantity)
    {
        Quantity = new Quantity(Quantity.Value + additionalQuantity.Value);
    }
}

// Now the service is thin - just coordinates
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IProductRepository _products;
    
    public async Task<OrderId> CreateOrder(CustomerId customerId)
    {
        var order = Order.CreateNew(customerId);
        await _repository.Add(order);
        return order.Id;
    }
    
    public async Task AddProductToOrder(OrderId orderId, ProductId productId, int quantity)
    {
        var order = await _repository.GetById(orderId);
        var product = await _products.GetById(productId);
        
        // Domain logic in aggregate
        order.AddLine(product, new Quantity(quantity));
        
        await _repository.SaveChanges();
    }
}
```

**Benefits of Rich Domain Model:**
- Business logic is encapsulated where it belongs
- Invariants are enforced automatically
- Code reads like ubiquitous language
- Easy to understand business rules
- Impossible to violate rules (private setters)
- Easy to test (just create aggregate, call methods)
- Domain events emerge naturally

## Self-Check Questions

1. **What's the difference between ubiquitous language and technical terminology?**
   - Ubiquitous language uses business terms from the domain
   - It's shared between developers and domain experts
   - Technical terminology is implementation-specific (repositories, services, DTOs)
   - Ubiquitous language appears in code, conversations, and documentation consistently

2. **How does ubiquitous language improve communication between developers and business experts?**
   - Eliminates the need for "translation" between business and technical terms
   - Reduces misunderstandings and ambiguity
   - Creates a shared mental model
   - Makes code reviewable by domain experts
   - Accelerates onboarding of new team members

3. **What is an anemic domain model and why is it problematic?**
   - Domain objects are just data bags with no behavior
   - All business logic lives in services
   - Problems: scattered logic, can't enforce invariants, hard to maintain, doesn't reflect domain
   - Preferred: Rich domain model with behavior and data together

4. **How do you discover and refine ubiquitous language?**
   - Event Storming workshops with domain experts
   - Example Mapping to extract terms from scenarios
   - Creating and maintaining a domain glossary
   - Domain storytelling and visual modeling
   - Iterative refinement as understanding deepens
   - Refactoring code when better terms are discovered

5. **What are some anti-patterns to avoid when creating domain models?**
   - Using technical terms instead of business terms
   - Generic names (Manager, Handler, Data, Info)
   - Inconsistent terminology (synonyms for same concept)
   - Unclear abbreviations and acronyms
   - Anemic models with no behavior

6. **How should method names reflect business operations?**
   - Use intention-revealing names (ConfirmOrder, not UpdateStatus)
   - Use domain verbs (Submit, Approve, Cancel, not Process, Handle)
   - Avoid technical implementation details in names
   - Make impossible states impossible to represent

## Key Takeaways

1. **Ubiquitous Language is foundational** - Everything else in DDD builds on having a shared, precise language

2. **Language evolves** - Your understanding of the domain will deepen over time; refactor code as language improves

3. **Avoid translation** - If you find yourself "translating" between business terms and code terms, something is wrong

4. **Rich models over anemic models** - Put business logic where it belongs: in domain objects

5. **Make implicit concepts explicit** - Important domain concepts should be first-class objects in your model

6. **Method names matter** - They should read like conversations with domain experts

7. **Document the language** - Maintain a glossary, keep it updated, make it accessible

8. **Involve domain experts** - Regular collaboration is essential; they are your partners, not just requirements sources

9. **Question everything** - When terms are ambiguous, dig deeper; precision matters

10. **Code should tell a story** - Well-modeled domain code reads like documentation
