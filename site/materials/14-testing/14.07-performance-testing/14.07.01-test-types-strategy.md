# Lesson 1: Performance Test Types and Strategy

## Learning Objectives

By the end of this lesson, you will be able to:
- Distinguish between different performance test types
- Understand when to apply each test type
- Develop a performance testing strategy
- Define meaningful performance metrics
- Avoid common performance testing mistakes

---

## Introduction

Performance testing isn't just about throwing load at your system and seeing what breaks. Different test types serve different purposes, from validating capacity to discovering failure modes. Understanding which test to run and when is essential for building confidence in your system's performance characteristics.

## Key Concepts Summary

### Performance Test Types

#### 1. Smoke Testing
**Purpose:** Verify the system functions with minimal load.

**When to use:**
- Before running larger tests
- After deployments
- As a sanity check

**Characteristics:**
- 1-2 virtual users
- Short duration (1-5 minutes)
- Basic functionality validation

```javascript
// k6 smoke test example
export const options = {
  vus: 2,
  duration: '1m',
};
```

#### 2. Load Testing
**Purpose:** Verify the system can handle expected traffic.

**When to use:**
- Validating SLA compliance
- Capacity planning
- Before major releases

**Characteristics:**
- Gradual ramp-up to target load
- Sustained period at target
- Gradual ramp-down
- Measures response time under normal conditions

**Load Pattern:**
```
Users
  ^
  |     /‾‾‾‾‾‾\
  |    /        \
  |   /          \
  +--+------------+---> Time
     Ramp Sustain Ramp
     Up          Down
```

#### 3. Stress Testing
**Purpose:** Find the system's breaking point.

**When to use:**
- Understanding maximum capacity
- Planning for growth
- Identifying failure modes

**Characteristics:**
- Increases load beyond normal capacity
- Continues until system degrades
- Tests recovery after failure
- Identifies bottlenecks

**Load Pattern:**
```
Users
  ^
  |           /|
  |          / |
  |         /  | (System breaks)
  |        /   |
  +-------/----+---> Time
```

#### 4. Spike Testing
**Purpose:** Test system behavior under sudden traffic spikes.

**When to use:**
- Systems exposed to viral events
- Flash sales or promotions
- News sites during breaking stories

**Characteristics:**
- Sudden increase in load
- Short duration at peak
- Measures recovery time
- Tests auto-scaling

**Load Pattern:**
```
Users
  ^
  |        ╱‾‾‾╲
  |       /     \
  |______/       \____
  +--------------------> Time
```

#### 5. Soak Testing (Endurance Testing)
**Purpose:** Detect issues that appear over time.

**When to use:**
- Finding memory leaks
- Detecting resource exhaustion
- Validating long-running stability

**Characteristics:**
- Moderate load
- Extended duration (hours or days)
- Monitors for gradual degradation
- Tests resource cleanup

**Load Pattern:**
```
Users
  ^
  |  /‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\
  | /                             \
  |/                               \
  +----------------------------------> Time
       Hours or Days
```

## Key Performance Metrics

### Response Time Metrics
- **Average Response Time:** Can hide outliers, use with caution
- **Median (p50):** Middle value, better than average
- **p95, p99, p99.9:** Capture tail latency and worst-case scenarios
- **Max Response Time:** Absolute worst case

**Why percentiles matter:**
```
If p95 = 200ms and p99 = 2000ms:
- 95% of users get 200ms or better
- 5% of users experience 200ms-2000ms
- 1% of users experience near 2000ms (10x worse!)
```

### Throughput Metrics
- **Requests per Second (RPS):** Total system throughput
- **Data Transfer Rate:** Network bandwidth usage
- **Transactions per Second (TPS):** Business transaction rate

### Resource Metrics
- **CPU Utilization:** Should remain under 70-80% for headroom
- **Memory Usage:** Watch for steady increases (memory leaks)
- **Disk I/O:** Can become bottleneck for data-heavy operations
- **Network I/O:** Important for distributed systems

### Error Metrics
- **Error Rate:** Percentage of failed requests
- **Error Types:** Different errors indicate different problems
- **Time to First Error:** When system starts failing

## Performance Testing Strategy

### 1. Define Success Criteria

Before testing, establish:
- **Target response times:** e.g., p95 < 500ms
- **Expected throughput:** e.g., 1000 RPS
- **Acceptable error rate:** e.g., < 0.1%
- **Resource limits:** e.g., CPU < 80%

### 2. Start Small and Expand

```
1. Smoke Test (baseline)
   ↓
2. Load Test (expected traffic)
   ↓
3. Stress Test (find limits)
   ↓
4. Spike Test (resilience)
   ↓
5. Soak Test (stability)
```

### 3. Test in Isolation, Then Integration

- Start with individual components
- Progress to full end-to-end flows
- Include external dependencies
- Test with realistic data volumes

### 4. Common Mistakes to Avoid

❌ **Testing without clear objectives**
- Define what you're testing and why
- Set measurable success criteria

❌ **Unrealistic test scenarios**
- Use real user behavior patterns
- Include think time between requests
- Vary request parameters

❌ **Testing in production-like environments**
- Use production-equivalent infrastructure
- Match data volumes and complexity
- Include network latency

❌ **Ignoring errors**
- A fast system that returns errors is not acceptable
- Track error rates and types
- Investigate all failures

❌ **Only measuring average response time**
- Averages hide outliers
- Use percentiles (p95, p99)
- Monitor tail latency

❌ **Testing too late**
- Integrate performance testing in CI/CD
- Test early and often
- Catch regressions before production

---

## The Importance of Measuring Performance

> "Running tests without measuring performance metrics constitutes resilience testing rather than actual performance testing."

**True performance testing requires:**
- Specific, measurable metrics
- Clear pass/fail criteria
- Automated result validation
- Trend analysis over time

If you're just checking that the system doesn't crash under load, that's resilience testing, not performance testing.
