## Introduction

Performance testing is most valuable when done continuously. A one-time performance test tells you how your system performs today, but continuous testing catches regressions before they reach production. This lesson covers how to establish baselines, set thresholds, and integrate performance testing into your development workflow.

## Key Concepts Summary

### What is a Performance Baseline?

A **performance baseline** is a set of metrics that represent acceptable performance for your application under normal conditions.

**Baseline includes:**
- Response time percentiles (p50, p95, p99)
- Throughput (requests per second)
- Error rate
- Resource utilization (CPU, memory, disk, network)

**Purpose:**
- Provides a reference point for comparison
- Enables regression detection
- Helps set realistic SLAs
- Guides capacity planning

---

### Establishing a Baseline

#### Step 1: Run Initial Performance Tests

**Start with smoke tests:**
```javascript
// Smoke test: minimal load to verify functionality
export const options = {
  vus: 1,
  duration: '30s',
  thresholds: {
    'http_req_failed': ['rate==0'], // No errors in smoke test
  },
};
```

**Progress to load tests:**
```javascript
// Load test: expected production traffic
export const options = {
  scenarios: {
    baseline_test: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '2m', target: 50 },
        { duration: '10m', target: 50 },
        { duration: '2m', target: 0 },
      ],
    },
  },
};
```

#### Step 2: Run Multiple Times

**Why multiple runs matter:**
- Environment variations
- Cold vs. warm starts
- Cache effects
- Network fluctuations

**Best practice:**
- Run at least 3-5 times
- Calculate average, median, and standard deviation
- Discard outliers (first run often slower due to cold start)

```bash
# Run test 5 times and collect results
for i in {1..5}; do
  k6 run --out json=results_$i.json test.js
done
```

#### Step 3: Analyze Results

**Example baseline data:**
```
Run 1:  p95=450ms, p99=680ms, RPS=48, Error rate=0.1%
Run 2:  p95=440ms, p99=670ms, RPS=49, Error rate=0.0%
Run 3:  p95=460ms, p99=710ms, RPS=47, Error rate=0.2%
Run 4:  p95=445ms, p99=675ms, RPS=49, Error rate=0.1%
Run 5:  p95=455ms, p99=690ms, RPS=48, Error rate=0.1%

Baseline:
  p95: 450ms (avg), σ=7ms
  p99: 685ms (avg), σ=16ms
  RPS: 48 (avg), σ=0.8
  Error rate: 0.1% (avg)
```

#### Step 4: Set Thresholds

Based on baseline, set thresholds with **buffer for variability**:

```javascript
export const options = {
  thresholds: {
    // p95 baseline: 450ms, set threshold at 500ms (11% buffer)
    'http_req_duration': ['p(95)<500'],
    
    // p99 baseline: 685ms, set threshold at 800ms (17% buffer)
    'http_req_duration': ['p(99)<800'],
    
    // Error rate baseline: 0.1%, set threshold at 1% (10x buffer)
    'http_req_failed': ['rate<0.01'],
    
    // RPS baseline: 48, set minimum at 45 (6% buffer)
    'http_reqs': ['rate>45'],
  },
};
```

### Configuring Thresholds in k6

#### Basic Threshold Syntax

```javascript
export const options = {
  thresholds: {
    // Metric name: [threshold expressions]
    'http_req_duration': ['p(95)<500', 'p(99)<1000'],
  },
};
```

#### Available Metrics

```javascript
export const options = {
  thresholds: {
    // HTTP metrics
    'http_req_duration': ['p(95)<500'],           // Response time
    'http_req_failed': ['rate<0.01'],             // Error rate
    'http_req_blocked': ['avg<10'],               // Time blocked
    'http_req_connecting': ['avg<50'],            // Connection time
    'http_req_receiving': ['avg<20'],             // Time receiving
    
    // Generic metrics
    'http_reqs': ['rate>100'],                    // Throughput
    'data_received': ['rate>1000000'],            // Bytes received/s
    'data_sent': ['rate>100000'],                 // Bytes sent/s
    
    // Check metrics
    'checks': ['rate>0.95'],                      // 95% of checks pass
    
    // Custom metrics
    'my_custom_metric': ['avg<200'],
  },
};
```

#### Threshold Aggregation Methods

```javascript
export const options = {
  thresholds: {
    'http_req_duration': [
      'avg<200',      // Average
      'min<100',      // Minimum
      'max<2000',     // Maximum
      'med<180',      // Median (p50)
      'p(90)<300',    // 90th percentile
      'p(95)<400',    // 95th percentile
      'p(99)<800',    // 99th percentile
      'p(99.9)<1500', // 99.9th percentile
    ],
  },
};
```

#### Tagged Thresholds

Apply thresholds to specific requests:

```javascript
export const options = {
  thresholds: {
    // All requests
    'http_req_duration': ['p(95)<500'],
    
    // Only successful requests
    'http_req_duration{status:200}': ['p(95)<400'],
    
    // Specific endpoint
    'http_req_duration{name:GetUsers}': ['p(95)<300'],
    
    // Specific tag
    'http_req_duration{type:api}': ['p(95)<450'],
  },
};

export default function () {
  http.get('https://api.example.com/users', {
    tags: { name: 'GetUsers', type: 'api' },
  });
}
```

#### Abort on Threshold Failure

```javascript
export const options = {
  thresholds: {
    // Abort test if error rate exceeds 5%
    'http_req_failed': [
      { threshold: 'rate<0.05', abortOnFail: true },
    ],
    
    // Delay abort by 10 seconds to allow recovery
    'http_req_duration': [
      { threshold: 'p(95)<500', abortOnFail: true, delayAbortEval: '10s' },
    ],
  },
};
```

### Performance Testing in CI/CD

#### GitHub Actions Example

**.github/workflows/performance-test.yml:**
```yaml
name: Performance Tests

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  performance-test:
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v3
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: '8.0.x'
      
      - name: Build and run application
        run: |
          dotnet build
          dotnet run --project ./MyApi &
          sleep 10  # Wait for app to start
      
      - name: Install k6
        run: |
          curl https://github.com/grafana/k6/releases/download/v0.48.0/k6-v0.48.0-linux-amd64.tar.gz -L | tar xvz
          sudo mv k6-v0.48.0-linux-amd64/k6 /usr/local/bin/
      
      - name: Run performance tests
        run: |
          k6 run --out json=results.json tests/performance/load-test.js
      
      - name: Upload results
        if: always()
        uses: actions/upload-artifact@v3
        with:
          name: performance-results
          path: results.json
      
      - name: Comment PR with results
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v6
        with:
          script: |
            const fs = require('fs');
            const results = JSON.parse(fs.readFileSync('results.json'));
            // Parse and comment results on PR
```

### Regression Detection Strategies

#### 1. Static Threshold Method (Simple)

**Approach:** Set fixed thresholds based on baseline.

**Pros:**
- Simple to implement
- Easy to understand
- Quick to execute

**Cons:**
- Doesn't account for natural variance
- Can have false positives
- Requires manual threshold updates

**Example:**
```javascript
export const options = {
  thresholds: {
    'http_req_duration': ['p(95)<500'],  // Fixed threshold
  },
};
```

**When to use:** Small teams, stable applications, infrequent changes.

---

#### 2. Statistical Continuous Benchmarking

**Approach:** Track metrics over time, detect statistically significant changes.

**Pros:**
- Accounts for natural variance
- Fewer false positives
- Adapts to gradual changes

**Cons:**
- More complex to implement
- Requires historical data
- Longer detection time

**Process:**
1. Store test results in a database/service
2. Calculate moving average and standard deviation
3. Alert when new results exceed threshold (e.g., 2σ from mean)

**Example with Bencher:**
```bash
# Run benchmark and track with Bencher
bencher run \
  --project my-project \
  --testbed ci-runner \
  --adapter json \
  "k6 run --out json=- test.js"
```

**When to use:** Large teams, mission-critical apps, frequent deployments.

---

#### 3. Relative Continuous Benchmarking

**Approach:** Compare new code against baseline code directly.

**Pros:**
- Detects regressions immediately
- No need for historical data
- Works well for PRs

**Cons:**
- Requires running both versions
- More resource-intensive
- Environment variance can affect results

**Example:**
```yaml
# GitHub Actions: Compare PR branch vs. main
steps:
  - name: Checkout main
    uses: actions/checkout@v3
    with:
      ref: main
      path: main
  
  - name: Checkout PR
    uses: actions/checkout@v3
    with:
      path: pr
  
  - name: Test main branch
    run: |
      cd main
      dotnet run &
      k6 run --out json=main-results.json test.js
  
  - name: Test PR branch
    run: |
      cd pr
      dotnet run &
      k6 run --out json=pr-results.json test.js
  
  - name: Compare results
    run: |
      python compare-results.py main-results.json pr-results.json
```

**When to use:** Pull request validation, critical path changes, A/B testing.

---

#### 4. Change Point Detection

**Approach:** Periodically run benchmarks, use algorithms to detect when performance changed.

**Pros:**
- Identifies exact commit that caused regression
- Good for post-merge detection
- Can bisect to find root cause

**Cons:**
- Delayed detection
- Requires many test runs
- Complex analysis

**Process:**
1. Run benchmarks on every commit (or periodically)
2. Use change point detection algorithm (e.g., CUSUM, Bayesian)
3. When regression detected, bisect to find offending commit

**When to use:** Post-deployment monitoring, root cause analysis, research teams.

### Practical Threshold Configuration

#### Conservative Approach (Avoid False Positives)

```javascript
export const options = {
  thresholds: {
    // Allow 20% degradation before failing
    'http_req_duration': ['p(95)<600'],  // Baseline: 500ms
    'http_req_failed': ['rate<0.02'],    // Baseline: 0.01
    'http_reqs': ['rate>40'],            // Baseline: 50
  },
};
```

#### Strict Approach (Catch Small Regressions)

```javascript
export const options = {
  thresholds: {
    // Allow only 5% degradation
    'http_req_duration': ['p(95)<525'],  // Baseline: 500ms
    'http_req_failed': ['rate<0.011'],   // Baseline: 0.01
    'http_reqs': ['rate>47'],            // Baseline: 50
  },
};
```

#### Balanced Approach (Recommended)

```javascript
export const options = {
  thresholds: {
    // 10-15% buffer for natural variance
    'http_req_duration': [
      'p(50)<250',   // Baseline: 220ms, +14%
      'p(95)<575',   // Baseline: 500ms, +15%
      'p(99)<920',   // Baseline: 800ms, +15%
    ],
    'http_req_failed': ['rate<0.015'],  // Baseline: 0.01, +50%
    'http_reqs': ['rate>45'],           // Baseline: 50, -10%
  },
};
```

### Storing and Tracking Results

#### Time-Series Database (Recommended)

**InfluxDB + Grafana:**
```bash
# Run k6 with InfluxDB output
k6 run --out influxdb=http://localhost:8086/k6 test.js
```

**Query in Grafana:**
```sql
SELECT mean("value")
FROM "http_req_duration"
WHERE $timeFilter
GROUP BY time($__interval)
```

#### JSON Output + Storage

```bash
# Generate JSON results
k6 run --out json=results.json test.js

# Parse and store in database
node parse-results.js results.json
```

**parse-results.js:**
```javascript
const fs = require('fs');
const results = fs.readFileSync('results.json', 'utf8')
  .split('\n')
  .filter(line => line)
  .map(line => JSON.parse(line));

const summary = results
  .filter(r => r.type === 'Point' && r.metric === 'http_req_duration')
  .map(r => r.data.value);

const p95 = percentile(summary, 95);
const p99 = percentile(summary, 99);

console.log(`p95: ${p95}ms, p99: ${p99}ms`);

// Store in database
```

### Complete CI/CD Example with Regression Detection

**test.js:**
```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    load_test: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '1m', target: 20 },
        { duration: '3m', target: 20 },
        { duration: '1m', target: 0 },
      ],
    },
  },
  thresholds: {
    'http_req_duration': ['p(95)<500', 'p(99)<1000'],
    'http_req_failed': ['rate<0.01'],
    'checks': ['rate>0.95'],
  },
};

export default function () {
  const res = http.get('http://localhost:5000/api/users');
  
  check(res, {
    'status is 200': (r) => r.status === 200,
    'response time < 500ms': (r) => r.timings.duration < 500,
  });
}
```

## Best Practices Summary

### ✅ Do's

1. **Establish baselines early** in the project lifecycle
2. **Run tests multiple times** to account for variance
3. **Use percentiles** (p95, p99) instead of averages
4. **Set realistic thresholds** with appropriate buffers
5. **Track trends over time** using time-series databases
6. **Integrate into CI/CD** for continuous monitoring
7. **Test in production-like environments**

### ❌ Don'ts

1. **Don't set thresholds too tight** (causes false positives)
2. **Don't ignore natural variance** in results
3. **Don't test in unrealistic environments**
4. **Don't skip warm-up periods** before measuring
5. **Don't compare cold vs. warm starts**
6. **Don't forget to version your test scripts**
7. **Don't test only once** and call it a baseline
