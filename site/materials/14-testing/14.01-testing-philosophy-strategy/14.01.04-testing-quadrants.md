# Lesson 4: Testing Quadrants

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the Agile Testing Quadrants model
- Categorize tests across business-facing and technology-facing dimensions
- Distinguish between tests that support the team vs. critique the product
- Use quadrants to identify gaps in your testing strategy
- Apply the quadrants model to plan comprehensive testing

---

## Introduction

The Agile Testing Quadrants, developed by Brian Marick and refined by Lisa Crispin and Janet Gregory, provide a thinking tool to help teams plan and execute testing activities. Rather than being a strict categorization, the quadrants help you ensure you're covering all aspects of quality while delivering customer value.

## Key Concepts Summary

### The Four Quadrants

The testing quadrants are organized along two axes:
- **Horizontal axis:** Business-Facing ← → Technology-Facing
- **Vertical axis:** Support the Team ↑ / Critique the Product ↓

```
                    Business-Facing
                          │
          Q2              │              Q3
    Story Tests           │     Exploratory Testing
    Prototypes            │     Usability Testing
    Simulations           │     UAT
                          │     A/B Testing
    ──────────────────────┼──────────────────────
Support the Team          │     Critique the Product
    ──────────────────────┼──────────────────────
          Q1              │              Q4
    Unit Tests            │     Performance Tests
    Component Tests       │     Security Tests
    API Tests             │     Load Tests
                          │     "ility" Tests
                          │
                  Technology-Facing
```

### Quadrant 1: Technology-Facing, Support the Team

**Purpose:** Guide development with fast feedback on technical correctness

**Tests include:**
- Unit tests
- Component tests
- API tests
- Integration tests (at component level)

**Characteristics:**
- **Automated:** Nearly 100% automation
- **Fast:** Run in seconds to minutes
- **Frequent:** Every commit or multiple times per day
- **Granular:** Test small pieces of functionality
- **Written by:** Developers

**Value:** Catch bugs immediately, enable refactoring, document intent

**Example:**
```csharp
[Fact]
public void CalculateDiscount_PremiumUser_Returns25PercentOff()
{
    // Arrange
    var calculator = new DiscountCalculator();
    var user = new User { IsPremium = true, YearsActive = 6 };
    
    // Act
    var discount = calculator.Calculate(user);
    
    // Assert
    discount.Should().Be(0.25m);
}
```

### Quadrant 2: Business-Facing, Support the Team

**Purpose:** Guide development with business context and examples

**Tests include:**
- Story tests / Scenario tests
- Example-driven tests
- BDD scenarios
- Prototypes and wireframes
- Simulations

**Characteristics:**
- **Automated:** Many can be automated (BDD scenarios)
- **Collaboration:** Written with business stakeholders
- **Clarity:** Use business language, not technical jargon
- **Living Documentation:** Tests serve as executable specifications
- **Written by:** Developers with BAs/Product Owners

**Value:** Ensure features meet business requirements, facilitate communication

**Example BDD Scenario:**
```gherkin
Scenario: Premium user receives discount
  Given a premium user with 6 years of membership
  When they view a product priced at $100
  Then they should see a discounted price of $75
  And the discount badge should show "25% OFF"
```

### Quadrant 3: Business-Facing, Critique the Product

**Purpose:** Validate the product meets user needs and delivers value

**Tests include:**
- Exploratory testing
- User acceptance testing (UAT)
- Usability testing
- A/B testing
- Beta testing
- Showcases and demos

**Characteristics:**
- **Manual:** Primarily human-driven
- **Creative:** Testers use intuition and experience
- **Holistic:** Evaluate overall product quality
- **User-Focused:** From end-user perspective
- **Done by:** QA, Users, Product Owners

**Value:** Find issues automation misses, validate user experience, ensure business value

**Activities:**
- Exploratory testing sessions
- Usability studies with real users
- Beta programs
- Customer feedback sessions
- Accessibility testing

### Quadrant 4: Technology-Facing, Critique the Product

**Purpose:** Validate non-functional requirements and system qualities

**Tests include:**
- Performance testing
- Load testing
- Security testing
- Scalability testing
- Reliability testing
- Compliance testing
- "ility" tests (maintainability, compatibility, etc.)

**Characteristics:**
- **Automated:** Usually automated
- **Specialized:** Often require specialized tools and expertise
- **Expensive:** Can be resource-intensive
- **Periodic:** May not run on every commit
- **Done by:** Specialized testers, DevOps, Security teams

**Value:** Ensure system meets non-functional requirements, prevent production issues

**Example:**
```javascript
// k6 performance test
export default function() {
  let response = http.get('https://api.example.com/products');
  check(response, {
    'status is 200': (r) => r.status === 200,
    'response time < 200ms': (r) => r.timings.duration < 200,
  });
}
```

### How to Use the Quadrants

**1. Assess Current Coverage**
```
Create a checklist:
□ Q1: Do we have comprehensive unit/component tests?
□ Q2: Are our features driven by business examples?
□ Q3: Do we conduct exploratory testing regularly?
□ Q4: Have we tested performance, security, etc.?
```

**2. Identify Gaps**

Common gaps:
- **Missing Q2:** Features built without business examples → misunderstood requirements
- **Missing Q3:** No exploratory testing → missed UX issues
- **Missing Q4:** No performance testing → production surprises
- **Over-emphasis on Q1:** Unit tests only → false confidence

**3. Balance Your Approach**

The quadrants are complementary:
- Q1 provides foundation (fast feedback)
- Q2 ensures right features (business alignment)
- Q3 validates user value (product quality)
- Q4 ensures system qualities (production readiness)

**You need all four quadrants for comprehensive quality.**

### Key Insights

**Not a Lifecycle**
The quadrants are NOT sequential phases. Activities from all quadrants happen throughout development:
- Q1 & Q2: Throughout iteration (TDD, BDD)
- Q3: Continuously and at iteration end
- Q4: Periodically and before release

**Not About Tools**
Don't organize by tools (Selenium, JUnit, etc.). Organize by purpose and perspective.

**Not About Roles**
In agile teams, testing is everyone's responsibility:
- Developers focus on Q1 & Q2
- QA helps with all quadrants
- Product Owners contribute to Q2 & Q3
- Specialists help with Q4

**Thinking Tool**
The quadrants help you think about:
- What types of testing are we doing?
- What are we missing?
- Who should be involved?
- What's the right balance?

## Practice Exercise

After completing the materials (15 minutes max):

For your current project:
1. Map your existing tests to the four quadrants
2. Calculate rough percentage of effort in each quadrant
3. Identify which quadrant has the biggest gap
4. Propose one concrete test or activity for the weakest quadrant
5. Consider: Are you doing any testing that doesn't fit the quadrants?

## Self-Check Questions

1. How do "support the team" tests differ from "critique the product" tests?
2. Why can't you replace Q3 (exploratory testing) with more Q1 tests?
3. In which quadrant would you place contract testing? Why?
4. How do the quadrants relate to the testing pyramid?
5. What risks arise from focusing only on technology-facing tests (Q1 & Q4)?
