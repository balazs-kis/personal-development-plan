# Lesson 2: Steady State Hypothesis and Experiment Design

## Learning Objectives

By the end of this lesson, you will be able to:
- Define steady state for your systems
- Write testable hypotheses for chaos experiments
- Design structured chaos experiments
- Use probes to validate system behavior
- Understand the experiment execution flow
- Document experiments effectively

---

## Introduction

A chaos experiment without a hypothesis is just breaking things randomly. The steady state hypothesis defines "what normal looks like" and provides the foundation for meaningful experiments. This lesson teaches you how to design structured, scientific experiments that generate actionable insights about your system's resilience.

## Key Concepts Summary

### What is Steady State?

**Steady state** describes "what normal looks like" for your system. It's a set of measurable outputs that indicate the system is functioning properly and meeting its objectives.

**Not just "up" or "down":**
```
❌ Bad: "The service is running"
❌ Bad: "The API returns 200"
✅ Good: "95% of requests complete in < 500ms with < 0.1% errors"
✅ Good: "Orders processed per minute > 1000"
✅ Good: "Customer login success rate > 99%"
```

**Characteristics of good steady state metrics:**
- **Measurable:** Can be objectively observed
- **Specific:** Clear thresholds or ranges
- **Meaningful:** Relates to actual system health or business value
- **Observable:** Can be monitored during experiments

---

### Types of Steady State Metrics

#### 1. Performance Metrics

**Response time:**
```json
{
  "steady-state-hypothesis": {
    "title": "API response time is acceptable",
    "probes": [
      {
        "type": "probe",
        "name": "api-response-time",
        "tolerance": {
          "type": "range",
          "target": "p95_latency",
          "range": [0, 500]
        },
        "provider": {
          "type": "python",
          "module": "metrics",
          "func": "get_p95_latency"
        }
      }
    ]
  }
}
```

**Throughput:**
```json
{
  "name": "minimum-throughput",
  "tolerance": {
    "type": "range",
    "target": "requests_per_second",
    "range": [100, 10000]
  }
}
```

#### 2. Availability Metrics

**Error rate:**
```json
{
  "name": "error-rate-acceptable",
  "tolerance": {
    "type": "range",
    "target": "error_rate",
    "range": [0, 0.01]  // Less than 1%
  }
}
```

**Success rate:**
```json
{
  "name": "login-success-rate",
  "tolerance": {
    "type": "range",
    "target": "login_success_rate",
    "range": [0.99, 1.0]  // At least 99%
  }
}
```

#### 3. Resource Metrics

**CPU utilization:**
```json
{
  "name": "cpu-under-threshold",
  "tolerance": {
    "type": "range",
    "target": "cpu_percent",
    "range": [0, 80]  // Below 80%
  }
}
```

**Memory usage:**
```json
{
  "name": "memory-available",
  "tolerance": {
    "type": "range",
    "target": "memory_available_mb",
    "range": [1000, 16000]  // At least 1GB available
  }
}
```

#### 4. Business Metrics

**Orders per minute:**
```json
{
  "name": "order-processing-rate",

    "type": "range",

  }
```

### Writing Hypotheses

A **hypothesis** is a statement about how you believe the system will behave when chaos is introduced.

#### Hypothesis Structure

```
IF [chaos action]
THEN [expected behavior]
BECAUSE [resilience mechanism]
```

#### Good Hypothesis Examples

**Example 1: Instance failure**
```
IF: We terminate one instance of the API service
THEN: The remaining instances will handle the load and maintain 
      p95 response time < 500ms with error rate < 0.1%
BECAUSE: We have auto-scaling configured and load balancing across 
         multiple instances
```

**Example 2: Database latency**
```
IF: We inject 1000ms latency to database queries
THEN: The API will continue to serve requests with response time 
      < 2000ms by using cached data
BECAUSE: We implemented Redis caching with a fallback to database
```

**Example 3: Network partition**
```
IF: We block network traffic between services A and B
THEN: Service A will degrade gracefully, logging errors but 
      continuing to serve other functionality
BECAUSE: We implemented circuit breakers and fallback responses
```

#### Poor Hypothesis Examples

```
❌ "The system will work"
   (Too vague, not measurable)

❌ "Nothing will happen"
   (Not a useful hypothesis)

❌ "Some requests might fail"
   (No specific expectations or thresholds)

❌ "It will probably be fine"
   (Not scientific or measurable)
```

### Experiment Structure

A complete chaos experiment has these components:

#### 1. Metadata
```json
{
  "version": "1.0.0",
  "title": "API resilience to instance failure",
  "description": "Verify that the API maintains SLA when one instance is terminated",
  "tags": ["api", "availability", "kubernetes"],
  "contributions": {
    "availability": "high",
    "reliability": "high",
    "performance": "medium"
  }
}
```

#### 2. Steady State Hypothesis (Before)
```json
{
  "steady-state-hypothesis": {
    "title": "API is healthy and performant",
    "probes": [
      {
        "name": "api-responds-ok",
        "type": "probe",
        "tolerance": 200,
        "provider": {
          "type": "http",
          "url": "https://api.example.com/health"
        }
      },
      {
        "name": "response-time-acceptable",
        "type": "probe",
        "tolerance": {
          "type": "range",
          "range": [0, 500]
        },
        "provider": {
          "type": "python",
          "module": "metrics",
          "func": "get_p95_latency",
          "arguments": {
            "service": "api",
            "duration": "1m"
          }
        }
      }
    ]
  }
}
```

#### 3. Method (Actions and Probes)
```json
{
  "method": [
    {
      "type": "action",
      "name": "terminate-one-api-instance",
      "provider": {
        "type": "python",
        "module": "chaoskube.actions",
        "func": "terminate_pods",
        "arguments": {
          "label_selector": "app=api",
          "qty": 1,
          "ns": "production"
        }
      },
      "pauses": {
        "after": 30  // Wait 30s for system to react
      }
    },
    {
      "type": "probe",
      "name": "check-remaining-instances",
      "provider": {
        "type": "python",
        "module": "chaoskube.probes",
        "func": "count_pods",
        "arguments": {
          "label_selector": "app=api",
          "ns": "production"
        }
      },
      "tolerance": {
        "type": "range",
        "range": [2, 10]  // Should have at least 2 remaining
      }
    }
  ]
}
```

#### 4. Steady State Hypothesis (After)
The same hypothesis runs again to detect deviations from normal behavior.

#### 5. Rollbacks
```json
{
  "rollbacks": [
    {
      "type": "action",
      "name": "restore-api-instances",
      "provider": {
        "type": "python",
        "module": "chaoskube.actions",
        "func": "scale_deployment",
        "arguments": {
          "name": "api",
          "replicas": 5,
          "ns": "production"
        }
      }
    }
  ]
}
```

### Probes: Measuring System Behavior

**Probes** are observations that collect information about your system during an experiment.

#### Probe Types

**1. HTTP Probes**
```json
{
  "type": "probe",
  "name": "api-health-check",
  "provider": {
    "type": "http",
    "url": "https://api.example.com/health",
    "timeout": 5,
    "headers": {
      "Accept": "application/json"
    }
  },
  "tolerance": 200
}
```

**2. Command Probes**
```json
{
  "type": "probe",
  "name": "check-cpu-usage",
  "provider": {
    "type": "process",
    "path": "top",
    "arguments": "-bn1"
  },
  "tolerance": {
    "type": "regex",
    "pattern": "Cpu\\(s\\):.*?(\\d+\\.\\d+).*?id",
    "target": "stdout"
  }
}
```

**3. Python Module Probes**
```json
{
  "type": "probe",
  "name": "get-prometheus-metric",
  "provider": {
    "type": "python",
    "module": "chaosprom.probes",
    "func": "query_prometheus",
    "arguments": {
      "query": "rate(http_requests_total[5m])",
      "url": "http://prometheus:9090"
    }
  }
}
```

**4. Kubernetes Probes**
```json
{
  "type": "probe",
  "name": "pods-are-running",
  "provider": {
    "type": "python",
    "module": "chaoskube.probes",
    "func": "pods_in_phase",
    "arguments": {
      "label_selector": "app=api",
      "phase": "Running",
      "ns": "production"
    }
  },
  "tolerance": {
    "type": "range",
    "range": [3, 10]
  }
}
```

---

### Tolerances: Defining Acceptable Behavior

**Tolerances** specify what probe results are acceptable.

#### Exact Value
```json
{
  "tolerance": 200  // HTTP status must be exactly 200
}
```

#### Range
```json
{
  "tolerance": {
    "type": "range",
    "range": [100, 1000]  // Between 100 and 1000 (inclusive)
  }
}
```

#### Regex Pattern
```json
{
  "tolerance": {
    "type": "regex",
    "pattern": "^(Running|Ready)$"
  }
}
```

#### JSON Path
```json
{
  "tolerance": {
    "type": "jsonpath",
    "path": "$.status.phase",
    "expect": "Running"
  }
}
```

#### Custom Function
```json
{
  "tolerance": {
    "type": "python",
    "module": "tolerances",
    "func": "is_within_slo",
    "arguments": {
      "max_response_time": 500,
      "max_error_rate": 0.01
    }
  }
}
```

### Experiment Execution Flow

```
┌─────────────────────────────────────────────────┐
│ 1. STEADY STATE HYPOTHESIS (Before)            │
│    Run all probes to check baseline            │
│    If fails: Abort (system not healthy)        │
└─────────────────┬───────────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────────┐
│ 2. METHOD                                       │
│    Execute actions (inject chaos)              │
│    Run probes to observe behavior              │
└─────────────────┬───────────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────────┐
│ 3. STEADY STATE HYPOTHESIS (After)             │
│    Run all probes again                         │
│    Compare with baseline                        │
│    Detect deviations                            │
└─────────────────┬───────────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────────┐
│ 4. ROLLBACKS                                    │
│    Execute cleanup actions                      │
│    Restore system to normal state              │
└─────────────────────────────────────────────────┘
```

**Hypothesis Testing Strategies:**

1. **Default:** Before method, after method
2. **Before-method-only:** Only validate baseline
3. **After-method-only:** Assume baseline is good
4. **During-method-only:** Check while chaos is active
5. **Continuously:** Constant monitoring throughout

### Complete Experiment Example

**Scenario:** Test API resilience when database connection pool is exhausted

```json
{
  "version": "1.0.0",
  "title": "API handles database connection exhaustion",
  "description": "Verify that the API degrades gracefully when database connections are exhausted",
  "tags": ["api", "database", "resilience"],
  
  "steady-state-hypothesis": {
    "title": "API is healthy and database is available",
    "probes": [
      {
        "type": "probe",
        "name": "api-health-check",
        "tolerance": 200,
        "provider": {
          "type": "http",
          "url": "http://api:8080/health"
        }
      },
      {
        "type": "probe",
        "name": "api-response-time",
        "tolerance": {
          "type": "range",
          "range": [0, 500]
        },
        "provider": {
          "type": "python",
          "module": "metrics.api",
          "func": "get_p95_response_time",
          "arguments": {
            "endpoint": "/api/users",
            "duration_seconds": 60
          }
        }
      },
      {
        "type": "probe",
        "name": "error-rate-low",
        "tolerance": {
          "type": "range",
          "range": [0, 0.01]
        },
        "provider": {
          "type": "python",
          "module": "metrics.api",
          "func": "get_error_rate",
          "arguments": {
            "duration_seconds": 60
          }
        }
      }
    ]
  },
  
  "method": [
    {
      "type": "action",
      "name": "exhaust-database-connections",
      "provider": {
        "type": "python",
        "module": "chaos.database",
        "func": "exhaust_connection_pool",
        "arguments": {
          "host": "postgres",
          "port": 5432,
          "connections_to_hold": 95
        }
      },
      "pauses": {
        "after": 10
      }
    },
    {
      "type": "probe",
      "name": "check-api-still-responds",
      "provider": {
        "type": "http",
        "url": "http://api:8080/api/users/1",
        "timeout": 10
      },
      "tolerance": [200, 503]
    },
    {
      "type": "probe",
      "name": "check-error-messages",
      "provider": {
        "type": "python",
        "module": "chaos.logs",
        "func": "check_logs_for_pattern",
        "arguments": {
          "service": "api",
          "pattern": "Connection pool exhausted",
          "since_seconds": 30
        }
      },
      "tolerance": true
    },
    {
      "type": "action",
      "name": "wait-for-recovery",
      "provider": {
        "type": "python",
        "module": "builtins",
        "func": "time.sleep",
        "arguments": {
          "seconds": 30
        }
      }
    }
  ],
  
  "rollbacks": [
    {
      "type": "action",
      "name": "release-database-connections",
      "provider": {
        "type": "python",
        "module": "chaos.database",
        "func": "release_connections"
      }
    },
    {
      "type": "action",
      "name": "restart-api-if-needed",
      "provider": {
        "type": "python",
        "module": "chaoskube.actions",
        "func": "restart_deployment",
        "arguments": {
          "name": "api",
          "ns": "production"
        }
      },
      "pauses": {
        "after": 30
      }
    }
  ]
}
```

### Experiment Documentation Template

```markdown
# Experiment: [Name]

## Hypothesis
IF [chaos action]
THEN [expected behavior]
BECAUSE [resilience mechanism]

## Steady State
- Metric 1: [Description and threshold]
- Metric 2: [Description and threshold]
- Metric 3: [Description and threshold]

## Chaos Action
[Description of what will be broken]

## Blast Radius
- Scope: [What's affected]
- Duration: [How long]
- Impact: [Expected customer impact]

## Safety Measures
- Rollback plan: [How to undo the chaos]
- Abort criteria: [When to stop]
- Monitoring: [What to watch]

## Expected Outcome
[What you expect to observe]

## Actual Outcome
[What actually happened - fill in after running]

## Learnings
[What you learned - fill in after running]

## Action Items
- [ ] Improvement 1
- [ ] Improvement 2
- [ ] Improvement 3
```

## Practice Exercise

1. **Define Steady State for Your Service:**
   - Choose a critical service
   - List 5 measurable metrics
   - Set acceptable ranges/thresholds
   - Document how to measure each metric

2. **Write Three Hypotheses:**
   - Pick 3 potential failures
   - Write hypothesis for each (IF/THEN/BECAUSE)
   - Define expected behavior
   - Identify resilience mechanisms

3. **Design a Simple Experiment:**
   - Choose one hypothesis
   - Write the steady state probes
   - Define the chaos action
   - Plan the rollback
   - Use the JSON structure (or pseudocode)

4. **Create an Experiment Document:**
   - Use the template above
   - Document your experiment
   - Include all sections
   - Share with your team for review
