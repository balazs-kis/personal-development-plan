- Measure the impact of parallelization on pipeline execution time

---

## Introduction

Running tests sequentially in CI/CD pipelines is slow and delays feedback. A test suite that takes 30 minutes to run sequentially can often complete in 5-10 minutes with proper parallelization. This lesson teaches you how to distribute test execution across multiple workers to dramatically reduce pipeline time.

**Key principle:** Parallelization is the easiest performance win in CI/CD. The speedup is nearly linear—2 workers give you ~2x speed, 4 workers give you ~4x speed.

## Key Concepts Summary

### Why Parallelization Matters

```
Sequential Execution:
Test Suite: 1000 tests @ 50ms each = 50 seconds
1 Worker: 50 seconds total

Parallel Execution:
1000 tests split across 4 workers:
Worker 1: 250 tests = 12.5 seconds
Worker 2: 250 tests = 12.5 seconds
Worker 3: 250 tests = 12.5 seconds
Worker 4: 250 tests = 12.5 seconds
Total: 12.5 seconds (4x speedup!)

Real-world impact:
- Faster feedback to developers
- Higher deployment frequency
- Better developer experience
- More efficient resource usage
```

### Parallelization Approaches

```
1. MULTIPLE AGENTS/WORKERS
   Run entire test suite on multiple machines simultaneously
   Best for: Different test categories (unit, integration, e2e)

2. TEST SPLITTING
   Divide tests into groups, run each group on separate worker
   Best for: Large test suites with similar test types

3. MATRIX STRATEGY
   Run same tests across multiple configurations (OS, runtime versions)
   Best for: Cross-platform testing, version compatibility

4. FRAMEWORK-LEVEL PARALLELIZATION
   xUnit/NUnit run tests in parallel within a single process
   Best for: Quick wins without infrastructure changes
```

### GitHub Actions: Matrix Strategy

```yaml
# Basic matrix: Test on multiple .NET versions
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    
    strategy:
      matrix:
        dotnet-version: ['6.0.x', '7.0.x', '8.0.x']
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ matrix.dotnet-version }}
      
      - name: Restore dependencies
        run: dotnet restore
      
      - name: Build
        run: dotnet build --no-restore
      
      - name: Test
        run: dotnet test --no-build --verbosity normal
```

```yaml
# Advanced matrix: Multiple dimensions
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ${{ matrix.os }}
    
    strategy:
      fail-fast: false  # Continue other jobs if one fails
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        dotnet-version: ['6.0.x', '8.0.x']
        # This creates 6 jobs: 3 OS × 2 versions
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ matrix.dotnet-version }}
      
      - name: Test
        run: dotnet test --verbosity normal
```

```yaml
# Matrix with exclusions and inclusions
name: CI

jobs:
  test:
    runs-on: ${{ matrix.os }}
    
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest]
        dotnet-version: ['6.0.x', '8.0.x']
        exclude:
          # Don't test .NET 6 on Windows
          - os: windows-latest
            dotnet-version: '6.0.x'
        include:
          # Add specific configuration
          - os: ubuntu-latest
            dotnet-version: '9.0.x'
            experimental: true
    
    steps:
      - uses: actions/checkout@v4
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ matrix.dotnet-version }}
      - name: Test
        run: dotnet test
```

### Azure DevOps: Parallel Jobs

```yaml
# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: 'ubuntu-latest'

strategy:
  parallel: 4  # Run on 4 agents in parallel

steps:
  - task: UseDotNet@2
    inputs:
      version: '8.0.x'
  
  - script: dotnet restore
    displayName: 'Restore dependencies'
  
  - script: dotnet build --no-restore
    displayName: 'Build'
  
  - task: VSTest@2
    inputs:
      testSelector: 'testAssemblies'
      testAssemblyVer2: |
        **\*Tests.dll
        !**\*TestAdapter.dll
        !**\obj\**
      searchFolder: '$(System.DefaultWorkingDirectory)'
      runInParallel: true
      distributionBatchType: 'basedOnTestCases'
      batchingBasedOnAgentsOption: 'autoBatchSize'
```

### Azure DevOps: VSTest Intelligent Slicing

```yaml
# azure-pipelines.yml with intelligent test distribution
trigger:
  - main

pool:
  vmImage: 'windows-latest'

strategy:
  parallel: 4  # 4 parallel agents

steps:
  - task: VSTest@2
    inputs:
      testSelector: 'testAssemblies'
      testAssemblyVer2: |
        **\*Tests.dll
        !**\obj\**
      runInParallel: true
      
      # Intelligent slicing options
      distributionBatchType: 'basedOnExecutionTime'
      # Options:
      # - 'basedOnTestCases': Simple division by test count
      # - 'basedOnExecutionTime': Balance by historical run times
      # - 'basedOnAssembly': Each assembly on separate agent
      
      # Automatically determine optimal batch size
      batchingBasedOnAgentsOption: 'autoBatchSize'
      
      # Or manually specify tests per batch
      # batchingBasedOnAgentsOption: 'customBatchSize'
      # customBatchSizeValue: 250
      
      # Enable test impact analysis (run only affected tests)
      testImpactEnabled: true
```

### Framework-Level Parallelization

```csharp
// xUnit: Parallel by default (within assembly)
// Control with collection fixtures

// Tests in different classes run in parallel by default
public class CustomerTests
{
    [Fact]
    public void Test1() { /* runs in parallel */ }
}

public class OrderTests
{
    [Fact]
    public void Test2() { /* runs in parallel with Test1 */ }
}

// Disable parallelization for specific test class
[Collection("Sequential")]
public class DatabaseTests
{
    [Fact]
    public void Test3() { /* runs sequentially with other Sequential tests */ }
}

// Configure parallelization in xunit.runner.json
{
  "parallelizeAssembly": true,
  "parallelizeTestCollections": true,
  "maxParallelThreads": 4  // or -1 for unlimited
}
```

```csharp
// NUnit: Configure parallelization
[assembly: Parallelizable(ParallelScope.All)]  // All tests run in parallel
[assembly: LevelOfParallelism(4)]  // Use 4 threads

// Control at class level
[Parallelizable(ParallelScope.Children)]  // Tests in class run in parallel
public class CustomerTests
{
    [Test]
    public void Test1() { }
    
    [Test]
    public void Test2() { }
}

// Disable parallelization for specific test
[Test, NonParallelizable]
public void DatabaseTest() { }
```

### Test Splitting by Timing Data

```yaml
# GitHub Actions: Manual test splitting
# Requires external tool or script to split tests

name: CI

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]  # 4 shards
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Get test list
        id: tests
        run: |
          # Get all tests and split into 4 groups
          dotnet test --list-tests --no-build > all_tests.txt
          # Custom script to split tests
          ./scripts/split-tests.sh all_tests.txt ${{ matrix.shard }} 4
      
      - name: Run test shard
        run: dotnet test --filter "FullyQualifiedName~${{ steps.tests.outputs.filter }}"
```

```bash
# scripts/split-tests.sh
#!/bin/bash
TEST_FILE=$1
SHARD_INDEX=$2
TOTAL_SHARDS=$3

# Simple splitting by line number
total_tests=$(wc -l < "$TEST_FILE")
tests_per_shard=$((total_tests / TOTAL_SHARDS))
start_line=$(( (SHARD_INDEX - 1) * tests_per_shard + 1 ))
end_line=$(( SHARD_INDEX * tests_per_shard ))

# Extract test names for this shard
sed -n "${start_line},${end_line}p" "$TEST_FILE" > "shard_${SHARD_INDEX}.txt"
```

### Measuring Parallelization Impact

```yaml
# GitHub Actions: Track pipeline duration
name: CI

on: [push, pull_request]

jobs:
  test-sequential:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Test (Sequential)
        run: |
          echo "::group::Sequential Test Execution"
          START=$(date +%s)
          dotnet test --verbosity normal
          END=$(date +%s)
          DURATION=$((END - START))
          echo "Sequential execution: ${DURATION}s"
          echo "::endgroup::"
  
  test-parallel:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Test (Parallel Shard ${{ matrix.shard }})
        run: |
          echo "::group::Parallel Test Execution - Shard ${{ matrix.shard }}"
          START=$(date +%s)
          # Run subset of tests
          dotnet test --filter "Category=Shard${{ matrix.shard }}" --verbosity normal
          END=$(date +%s)
          DURATION=$((END - START))
          echo "Shard ${{ matrix.shard }} execution: ${DURATION}s"
          echo "::endgroup::"
```

### Best Practices for Parallelization

```
✅ DO:
- Start with test categorization (unit, integration, e2e)
- Use matrix strategies for cross-platform/version testing
- Enable framework-level parallelization for quick wins
- Monitor pipeline analytics to identify bottlenecks
- Use test splitting for large homogeneous test suites
- Set fail-fast: false to see all failures

❌ DON'T:
- Over-parallelize (diminishing returns beyond 4-8 workers)
- Run tests with shared state in parallel
- Ignore test isolation issues
- Forget to consider CI/CD infrastructure limits
- Use parallelization to hide slow tests

Common Pitfalls:
1. Shared databases causing race conditions
2. File system conflicts (temp files, logs)
3. Port conflicts (web servers, APIs)
4. Resource exhaustion (memory, connections)
5. Test order dependencies

Solutions:
- Use Testcontainers for isolated databases
- Generate unique temp directories per test
- Use port 0 (OS assigns random available port)
- Implement resource pooling and cleanup
- Design tests to be order-independent
```

### Cost Considerations

```
Azure DevOps:
- Self-hosted agents: Free (use your own machines)
- Microsoft-hosted agents: 
  - Free tier: 1,800 minutes/month (single parallel job)
  - Additional parallel jobs: ~$40/month each

GitHub Actions:
- Free tier: 2,000 minutes/month (Linux)
- Additional minutes:
  - Linux: $0.008/minute
  - Windows: $0.016/minute
  - macOS: $0.08/minute
- Self-hosted runners: Free

Example Cost Analysis:
Test suite: 20 minutes sequential, 5 minutes with 4 parallel jobs

Sequential:
- 100 runs/month × 20 min = 2,000 minutes (within free tier)

Parallel (4 jobs):
- 100 runs/month × 5 min × 4 jobs = 2,000 minutes (within free tier)
- But: 4x the parallel job capacity needed

Optimization: Use parallelization strategically
- Parallel on main branch (critical path)
- Sequential on feature branches (cost savings)
```
