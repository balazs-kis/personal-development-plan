# Lesson 1: Test Structure and AAA Pattern

## Learning Objectives

By the end of this lesson, you will be able to:
- Structure unit tests using the Arrange-Act-Assert (AAA) pattern
- Write clear, readable tests with proper separation of concerns
- Understand the Given-When-Then alternative naming
- Organize test code for maximum maintainability
- Recognize and avoid common test structure anti-patterns

---

## Introduction

The Arrange-Act-Assert (AAA) pattern is the gold standard for structuring unit tests. This three-phase pattern creates consistency across your test suite, makes tests self-documenting, and helps identify tests that are trying to do too much. Mastering this pattern is foundational to writing effective unit tests.

## Key Concepts Summary

### The AAA Pattern

The Arrange-Act-Assert pattern divides tests into three distinct phases:

```csharp
[Fact]
public void Add_TwoPositiveNumbers_ReturnsSum()
{
    // Arrange - Set up the test
    var calculator = new Calculator();
    int a = 5;
    int b = 3;
    
    // Act - Execute the behavior being tested
    var result = calculator.Add(a, b);
    
    // Assert - Verify the expected outcome
    Assert.Equal(8, result);
}
```

### Phase 1: Arrange

**Purpose:** Set up the test environment and prepare everything needed for the test.

**Activities:**
- Create instances of classes under test
- Set up test data
- Configure mocks and stubs
- Set initial state

**Example:**
```csharp
// Arrange
var user = new User 
{ 
    Id = 1, 
    Name = "Alice", 
    IsPremium = true 
};
var calculator = new DiscountCalculator();
var expectedDiscount = 0.25m;
```

**Guidelines:**
- Keep arrangement minimal but sufficient
- Use test data builders for complex objects
- Avoid duplicating production code logic
- Make test data obvious and meaningful

### Phase 2: Act

**Purpose:** Execute the specific behavior or method being tested.

**Activities:**
- Call the method under test
- Trigger the action
- Capture the result

**Example:**
```csharp
// Act
var discount = calculator.CalculateDiscount(user);
```

**Guidelines:**
- **Single action only** - If you're calling multiple methods, you're testing too much
- Keep this phase to one or two lines maximum
- Don't include assertions here
- Don't include additional setup here

**Anti-pattern to avoid:**
```csharp
// ❌ BAD - Too much in the Act phase
var result1 = service.Process(data);
var result2 = service.Validate(result1);
var result3 = service.Save(result2);
```

### Phase 3: Assert

**Purpose:** Verify that the action produced the expected results.

**Activities:**
- Check return values
- Verify state changes
- Confirm method calls on mocks
- Validate thrown exceptions

**Example:**
```csharp
// Assert
Assert.Equal(expectedDiscount, discount);
```

**Guidelines:**
- Be specific about what you're testing
- One logical assertion per test (can be multiple Assert statements for the same concept)
- Make assertions meaningful and clear
- Use assertion libraries like FluentAssertions for readability

**Good - Multiple assertions for one logical concept:**
```csharp
// Assert - Verify the user was created correctly
Assert.Equal("Alice", user.Name);
Assert.Equal("alice@example.com", user.Email);
Assert.True(user.IsActive);
```

**Bad - Multiple unrelated assertions:**
```csharp
// ❌ Testing too many things at once
Assert.Equal("Alice", user.Name);
Assert.Equal(5, orders.Count);
Assert.NotNull(shippingAddress);
```

### Given-When-Then (BDD Alternative)

The AAA pattern has a BDD-style equivalent called Given-When-Then:

- **Given** (Arrange) - The initial context
- **When** (Act) - The action that occurs
- **Then** (Assert) - The expected outcome

```csharp
[Fact]
public void PremiumUser_WhenCalculatingDiscount_ThenReceives25Percent()
{
    // Given a premium user with 6 years membership
    var user = new User { IsPremium = true, YearsActive = 6 };
    var calculator = new DiscountCalculator();
    
    // When calculating the discount
    var discount = calculator.Calculate(user);
    
    // Then the discount should be 25%
    Assert.Equal(0.25m, discount);
}
```

Choose one style and be consistent across your codebase.

### Complete Example

```csharp
public class ShoppingCartTests
{
    [Fact]
    public void AddItem_EmptyCart_IncreaseCountByOne()
    {
        // Arrange
        var cart = new ShoppingCart();
        var product = new Product 
        { 
            Id = 1, 
            Name = "Laptop", 
            Price = 999.99m 
        };
        
        // Act
        cart.AddItem(product);
        
        // Assert
        Assert.Equal(1, cart.ItemCount);
        Assert.Contains(product, cart.Items);
    }
    
    [Fact]
    public void RemoveItem_CartWithOneItem_EmptiesCart()
    {
        // Arrange
        var cart = new ShoppingCart();
        var product = new Product { Id = 1, Name = "Mouse", Price = 25.00m };
        cart.AddItem(product);
        
        // Act
        cart.RemoveItem(product);
        
        // Assert
        Assert.Equal(0, cart.ItemCount);
        Assert.Empty(cart.Items);
    }
    
    [Fact]
    public void CalculateTotal_MultipleItems_ReturnsSumOfPrices()
    {
        // Arrange
        var cart = new ShoppingCart();
        cart.AddItem(new Product { Id = 1, Price = 10.00m });
        cart.AddItem(new Product { Id = 2, Price = 20.00m });
        cart.AddItem(new Product { Id = 3, Price = 30.00m });
        var expectedTotal = 60.00m;
        
        // Act
        var total = cart.CalculateTotal();
        
        // Assert
        Assert.Equal(expectedTotal, total);
    }
}
```

### Visual Separation

Use blank lines or comments to separate the three phases:

**Option 1: Blank lines**
```csharp
[Fact]
public void Test()
{
    var sut = new ClassUnderTest();
    var input = "test";

    var result = sut.Method(input);

    Assert.Equal("expected", result);
}
```

**Option 2: Comments**
```csharp
[Fact]
public void Test()
{
    // Arrange
    var sut = new ClassUnderTest();
    var input = "test";
    
    // Act
    var result = sut.Method(input);
    
    // Assert
    Assert.Equal("expected", result);
}
```

Choose your team's preference and stay consistent.

### Common Anti-Patterns to Avoid

**❌ Anti-Pattern 1: Mixing Phases**
```csharp
// BAD - Act and Assert mixed together
var result = sut.Calculate(input); // Act
Assert.NotNull(result); // Assert
result.Process(); // More Act!
Assert.True(result.IsComplete); // More Assert!
```

**❌ Anti-Pattern 2: Testing Multiple Things**
```csharp
// BAD - Testing add AND remove in one test
cart.AddItem(item1); // Act 1
Assert.Equal(1, cart.Count); // Assert 1
cart.RemoveItem(item1); // Act 2
Assert.Equal(0, cart.Count); // Assert 2
```

**❌ Anti-Pattern 3: Logic in Tests**
```csharp
// BAD - Contains logic (if statement)
if (user.IsPremium)
{
    Assert.Equal(0.25m, discount);
}
else
{
    Assert.Equal(0.10m, discount);
}
```

**❌ Anti-Pattern 4: Excessive Arrange**
```csharp
// BAD - Too much setup, unclear what matters
var user = CreateComplexUser();
var product = CreateComplexProduct();
var inventory = SetupInventorySystem();
var pricing = ConfigurePricingRules();
var shipping = SetupShippingCalculator();
// ... 20 more lines of setup
```

**Solution:** Use Test Data Builders, Factory Methods, or extract to helper methods.

### Benefits of AAA Pattern

✅ **Consistency** - All tests follow the same structure
✅ **Readability** - Clear separation makes tests easy to understand
✅ **Maintainability** - Changes are easier to make
✅ **Self-Documenting** - Tests communicate intent clearly
✅ **Reveals Problems** - Difficulty following AAA suggests the test (or code) is too complex
