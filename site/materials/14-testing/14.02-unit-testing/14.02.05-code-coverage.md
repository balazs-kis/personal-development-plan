# Lesson 5: Code Coverage and Its Limits

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand what code coverage measures and what it doesn't
- Use coverage tools in .NET (Coverlet, dotnet-coverage)
- Interpret coverage reports meaningfully
- Recognize the limitations of coverage metrics
- Set appropriate coverage goals for your projects
- Focus on test quality over coverage percentage

---

## Introduction

Code coverage tells you which lines of code are executed during testing, but it can't tell you if those tests are good. A project with 100% coverage can still have bugs, while a project with 60% coverage might be well-tested in the areas that matter. This lesson explores how to use coverage as a tool for improvement, not a target to hit.

## Key Concepts Summary

### What is Code Coverage?

**Code coverage** measures which parts of your code are executed when tests run. It's typically expressed as a percentage:

```
Coverage = (Lines Executed During Tests / Total Lines) × 100%
```

**Types of Coverage:**
- **Line Coverage** - Percentage of lines executed
- **Branch Coverage** - Percentage of decision branches (if/else) taken
- **Method Coverage** - Percentage of methods called
- **Statement Coverage** - Similar to line coverage

**Example:**
```csharp
public class Calculator
{
    public int Divide(int a, int b)  // Line 1
    {                                 // Line 2
        if (b == 0)                   // Line 3 (Branch: true/false)
            throw new DivideByZeroException();  // Line 4
        return a / b;                 // Line 5
    }                                 // Line 6
}

[Fact]
public void Divide_ValidNumbers_ReturnsQuotient()
{
    var calc = new Calculator();
    var result = calc.Divide(10, 2);
    result.Should().Be(5);
}

// Coverage:
// Line Coverage: 4/5 = 80% (line 4 not executed)
// Branch Coverage: 1/2 = 50% (only false branch of if)
```

### Setting Up Coverage in .NET

**Install Coverlet:**
```bash
dotnet add package coverlet.collector
```

**Run Tests with Coverage:**
```bash
# Basic coverage
dotnet test --collect:"XPlat Code Coverage"

# With detailed output
dotnet test --collect:"XPlat Code Coverage" --results-directory ./coverage

# Exclude test project from coverage
dotnet test /p:CollectCoverage=true /p:Exclude="[xunit.*]*"
```

**Generate HTML Report:**
```bash
# Install ReportGenerator
dotnet tool install -g dotnet-reportgenerator-globaltool

# Generate report
reportgenerator -reports:"coverage/**/coverage.cobertura.xml" \
                 -targetdir:"coveragereport" \
                 -reporttypes:Html
```

**Coverage Report Example:**

### What Coverage Tells You

**✅ Coverage CAN Tell You:**
- Which code is **not** tested at all
- Where to find **easy wins** (untested but simple code)
- If major features are **completely ignored**
- Which modules might need **attention**

**❌ Coverage CANNOT Tell You:**
- If your tests are **any good**
- If you're testing the **right things**
- If your tests would **catch bugs**
- If tests verify **correct behavior**

### The False Sense of Security

**Bad Test with 100% Coverage:**
```csharp
public class UserValidator
{
    public bool ValidateEmail(string email)
    {
        if (string.IsNullOrEmpty(email))
            return false;
            
        if (!email.Contains("@"))
            return false;
            
        if (email.Length < 5)
            return false;
            
        return true;
    }
}

// 100% coverage, but terrible test!
[Fact]
public void ValidateEmail_Test()
{
    var validator = new UserValidator();
    
    // Execute all lines, but don't verify behavior!
    validator.ValidateEmail(null);
    validator.ValidateEmail("a");
    validator.ValidateEmail("a@b");
    validator.ValidateEmail("valid@email.com");
    
    // No assertions! 100% coverage, 0% value
}
```

**Good Tests with Same Coverage:**
```csharp
[Fact]
public void ValidateEmail_NullEmail_ReturnsFalse()
{
    var validator = new UserValidator();
    var result = validator.ValidateEmail(null);
    result.Should().BeFalse();
}

[Fact]
public void ValidateEmail_EmptyEmail_ReturnsFalse()
{
    var validator = new UserValidator();
    var result = validator.ValidateEmail("");
    result.Should().BeFalse();
}

[Fact]
public void ValidateEmail_NoAtSymbol_ReturnsFalse()
{
    var validator = new UserValidator();
    var result = validator.ValidateEmail("notanemail");
    result.Should().BeFalse();
}

[Fact]
public void ValidateEmail_TooShort_ReturnsFalse()
{
    var validator = new UserValidator();
    var result = validator.ValidateEmail("a@b");
    result.Should().BeFalse();
}

[Fact]
public void ValidateEmail_ValidEmail_ReturnsTrue()
{
    var validator = new UserValidator();
    var result = validator.ValidateEmail("user@example.com");
    result.Should().BeTrue();
}
```

### Coverage Doesn't Catch Logic Bugs

```csharp
public decimal CalculateDiscount(User user)
{
    if (user.IsPremium && user.YearsActive > 5)
        return 0.25m;
    else if (user.IsPremium)
        return 0.15m;
    else
        return 0.10m;
}

// 100% coverage, but wrong test!
[Fact]
public void CalculateDiscount_PremiumUserLongMembership_Returns25Percent()
{
    var user = new User { IsPremium = true, YearsActive = 6 };
    var discount = CalculateDiscount(user);
    discount.Should().Be(0.15m);  // ❌ Wrong! Should be 0.25m
    // Test passes, coverage is 100%, but test is wrong!
}
```

### Coverage Doesn't Test Edge Cases

```csharp
public int GetAge(DateTime birthDate)
{
    return DateTime.Now.Year - birthDate.Year;
}

// 100% coverage, missing edge case
[Fact]
public void GetAge_ValidBirthDate_ReturnsAge()
{
    var birthDate = new DateTime(1990, 1, 1);
    var age = GetAge(birthDate);
    age.Should().Be(DateTime.Now.Year - 1990);
}

// Missing: What if birthday hasn't happened yet this year?
// Coverage says 100%, but edge case not tested!
```

### Diminishing Returns

Getting to 100% coverage often means testing trivial code:

```csharp
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
}

// Do you really need to test auto-properties?
[Fact]
public void User_SetName_StoresName()
{
    var user = new User();
    user.Name = "Alice";
    user.Name.Should().Be("Alice");
}
```

**Coverage vs Effort:**
```
Coverage   Effort    Value
0-60%      Low       High     (Test critical logic)
60-80%     Medium    Medium   (Test important paths)
80-95%     High      Low      (Test edge cases)
95-100%    Very High Very Low (Test trivial code)
```

### What to Aim For

**Recommended Coverage Targets:**
- **Critical Business Logic:** 90-100%
- **Services and Domain Logic:** 70-85%
- **Controllers/Presentation:** 50-70%
- **Infrastructure/Plumbing:** 40-60%
- **Overall Project:** 60-80%

**More Important Than Coverage Percentage:**
1. Test quality and assertions
2. Testing critical paths
3. Edge case coverage
4. Test maintainability
5. Fast feedback loops

### Using Coverage Effectively

**✅ DO: Use Coverage to Find Gaps**
```
Coverage report shows OrderService.ProcessRefund is 0%
→ Add tests for refund processing
```

**✅ DO: Focus on Critical Areas First**
```
PaymentService: 45% coverage → Priority: High
LoggingService: 45% coverage → Priority: Low
```

**✅ DO: Track Coverage Trends**
```
Sprint 1: 65%
Sprint 2: 68%
Sprint 3: 70%
Trend: Improving ✅
```

**❌ DON'T: Chase Arbitrary Targets**
```
"We need 100% coverage!"
Result: Tests with no assertions, tests for getters/setters
```

**❌ DON'T: Exclude "Hard to Test" Code**
```
// ❌ Bad - Excluding because it's hard
[ExcludeFromCodeCoverage]
public void ComplexBusinessLogic() { }
```

**✅ DO: Exclude Generated/Framework Code**
```
// ✅ Good - Excluding auto-generated
[ExcludeFromCodeCoverage]
public class Migrations { }
```

### Setting Up Coverage Gates in CI/CD

**Azure DevOps:**
```yaml
- task: DotNetCoreCLI@2
  inputs:
    command: 'test'
    arguments: '--collect:"XPlat Code Coverage"'
    
- task: PublishCodeCoverageResults@1
  inputs:
    codeCoverageTool: 'Cobertura'
    summaryFileLocation: '$(Agent.TempDirectory)/**/coverage.cobertura.xml'
    failIfCoverageEmpty: true
```

**GitHub Actions:**
```yaml
- name: Test with coverage
  run: dotnet test --collect:"XPlat Code Coverage"
  
- name: Upload coverage
  uses: codecov/codecov-action@v3
  with:
    files: ./coverage/coverage.cobertura.xml
    fail_ci_if_error: true
```

**Set Minimum Coverage (Use Sparingly):**
```bash
# Fail build if coverage drops below 70%
dotnet test /p:CollectCoverage=true /p:Threshold=70 /p:ThresholdType=line
```

### Real-World Wisdom

**Google's Approach:**
- No coverage mandates
- Focus on testing that provides value
- Coverage used as a signal, not a target

**Microsoft's Guidance:**
- Write tests that are resilient and easy to understand
- Coverage is one metric among many
- Quality over quantity

**Kent Beck's View:**
> "I get paid for code that works, not for tests, so my philosophy is to test as little as possible to reach a given level of confidence."

### Best Practices Summary

**✅ DO:**
- Use coverage to find untested code
- Focus on critical business logic first
- Write meaningful assertions
- Test edge cases and error conditions
- Review coverage reports regularly
- Track trends over time

**❌ DON'T:**
- Make 100% coverage a goal
- Write tests without assertions just for coverage
- Test trivial code (getters, setters)
- Use coverage as the only quality metric
- Exclude code because it's "hard to test"
- Punish teams for "low" coverage
