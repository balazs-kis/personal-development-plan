## Key Concepts Summary

### The CAP Theorem

The CAP theorem (also known as Brewer's theorem) states that a distributed data store can provide at most **two of three** guarantees:

#### **C - Consistency**
Every read receives the most recent write or an error. All nodes see the same data at the same time.

```
Example:
- Write: Set balance = $100
- Read from any node → Always returns $100 (or error)
- Never returns stale value like $50
```

#### **A - Availability**
Every request receives a non-error response, without guarantee that it contains the most recent write.

```
Example:
- System always responds to requests
- May return stale data during network issues
- Never returns "service unavailable"
```

#### **P - Partition Tolerance**
The system continues to operate despite network partitions (communication failures between nodes).

```
Example:
- Network split between data centers
- System continues functioning
- Some nodes can't communicate with others
```

---

### The Trade-Off

In the presence of a network partition, you must choose between **Consistency** and **Availability**:

**Choose Consistency (CP):**
- Reject requests to maintain consistency
- Return errors during partitions
- Example: Banking transactions

**Choose Availability (AP):**
- Accept requests during partitions
- Allow temporary inconsistency
- Example: Social media feeds

**Normal Operation:**
When no partition exists, both consistency and availability can be satisfied.

---

### Database Classifications by CAP

#### CP Databases (Consistency + Partition Tolerance)

**Characteristics:**
- Sacrifice availability during partitions
- Strong consistency guarantees
- May reject writes to maintain consistency

**Examples:**
- MongoDB (configurable)
- HBase
- Redis (single-node or sentinel mode)
- Consul
- ZooKeeper

**Use Cases:**
- Financial transactions
- Inventory management
- Reservation systems
- Anything requiring strong consistency

```csharp
// MongoDB with strong read concern
var options = new FindOptions<Order>
{
    ReadConcern = ReadConcern.Majority // Wait for majority acknowledgment
};

var order = await collection.Find(filter, options).FirstOrDefaultAsync();
// Returns consistent data or fails if majority unavailable
```

---

#### AP Databases (Availability + Partition Tolerance)

**Characteristics:**
- Sacrifice consistency during partitions
- Always available (eventual consistency)
- Accept writes even during network issues

**Examples:**
- Cassandra
- CouchDB
- DynamoDB
- Riak
- Cosmos DB (configurable)

**Use Cases:**
- Social media feeds
- Product catalogs
- Content management
- Analytics and logging
- Shopping carts

```csharp
// Cassandra - eventual consistency
var statement = new SimpleStatement(
    "SELECT * FROM products WHERE category = ?",
    "electronics"
);
statement.SetConsistencyLevel(ConsistencyLevel.One); // Read from one node

var result = await session.ExecuteAsync(statement);
// Returns immediately, may be slightly stale
```

---

#### CA Databases (Consistency + Availability)

**Reality:** No distributed database can truly be CA in practice because network partitions are inevitable.

**Traditional Single-Node Databases:**
- PostgreSQL (single instance)
- MySQL (single instance)
- SQL Server (single instance)

These can provide CA only when not distributed (no partitions to tolerate).

### ACID vs BASE

Two different consistency models represent opposing philosophies:

#### ACID (SQL Default)

**Atomicity:** Transactions are all-or-nothing
```sql
BEGIN TRANSACTION;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- Both updates succeed or both fail
```

**Consistency:** Data moves from one valid state to another
```sql
-- Constraint ensures balance never negative
ALTER TABLE accounts ADD CONSTRAINT balance_positive CHECK (balance >= 0);
```

**Isolation:** Concurrent transactions don't interfere
```sql
-- Transaction 1 and Transaction 2 execute independently
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

**Durability:** Committed transactions persist
```sql
COMMIT; -- Guaranteed to survive crashes
```

**Best For:**
- Financial systems
- Order processing
- Inventory management
- Anywhere correctness > performance

---

#### BASE (NoSQL Default)

**Basically Available:** System is available most of the time
**Soft state:** State may change without input (due to eventual consistency)
**Eventual consistency:** System becomes consistent over time

```javascript
// MongoDB - eventual consistency example
// Write to primary
db.users.updateOne(
  { _id: 1 },
  { $set: { status: "active" } }
);

// Immediate read from secondary might return old value
db.users.findOne({ _id: 1 }).readPref("secondary");
// May still show status: "inactive" for brief period

// Eventually, all replicas converge to: status: "active"
```

**Best For:**
- Social networks
- Content delivery
- Caching layers
- Analytics pipelines

---

### Consistency Levels Spectrum

Most modern databases offer configurable consistency:

#### Strong Consistency
```
Write → All nodes updated → Read returns new value
Latency: Higher | Availability: Lower | Consistency: Guaranteed
```

**Example (MongoDB):**
```csharp
var writeConcern = WriteConcern.WMajority; // Wait for majority
var readConcern = ReadConcern.Majority;    // Read from majority

await collection.InsertOneAsync(document, new InsertOneOptions
{
    WriteConcern = writeConcern
});
```

---

#### Eventual Consistency
```
Write → Some nodes updated → Read may return old value → Eventually consistent
Latency: Lower | Availability: Higher | Consistency: Eventually
```

**Example (Cassandra):**
```csharp
var statement = new SimpleStatement("INSERT INTO users (id, name) VALUES (?, ?)", 1, "John");
statement.SetConsistencyLevel(ConsistencyLevel.One); // Write to one node
await session.ExecuteAsync(statement);

// Read might not see new value immediately from different node
var readStatement = new SimpleStatement("SELECT * FROM users WHERE id = ?", 1);
readStatement.SetConsistencyLevel(ConsistencyLevel.One);
```

---

#### Tunable Consistency
```
Application chooses consistency level per operation
```

**Example (Cosmos DB):**
```csharp
// Strong consistency for critical reads
var requestOptions = new ItemRequestOptions
{
    ConsistencyLevel = ConsistencyLevel.Strong
};
var response = await container.ReadItemAsync<Order>(orderId, partitionKey, requestOptions);

// Eventual consistency for less critical reads
var feedOptions = new QueryRequestOptions
{
    ConsistencyLevel = ConsistencyLevel.Eventual
};
var query = container.GetItemQueryIterator<Product>(queryDefinition, requestOptions: feedOptions);
```

### Consistency in Distributed SQL

Modern distributed SQL databases (NewSQL) attempt to provide ACID guarantees across distributed nodes:

**Examples:**
- CockroachDB
- Google Spanner
- YugabyteDB
- TiDB

**How They Do It:**
- Distributed consensus (Raft, Paxos)
- Synchronized clocks
- Multi-version concurrency control (MVCC)

```sql
-- CockroachDB - ACID across distributed cluster
BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- Guaranteed atomic even if accounts are on different nodes
```

## Decision Framework

### When to Choose Strong Consistency (CP)

✅ **Use strong consistency when:**
- Financial transactions
- Inventory with limited quantity
- Reservations and bookings
- Regulatory compliance
- Correctness > availability

**Example Scenarios:**
```
❌ Double-booking hotel rooms
❌ Overselling concert tickets
❌ Incorrect account balances
✅ Accept brief unavailability to ensure correctness
```

---

### When to Choose Eventual Consistency (AP)

✅ **Use eventual consistency when:**
- Social media feeds
- Product catalogs
- Comment systems
- Analytics and logs
- Availability > immediate consistency

**Example Scenarios:**
```
✅ Like count slightly off
✅ Comment appears with 1-second delay
✅ Search results not instantly updated
❌ Cannot tolerate any inconsistency
```

---

### Hybrid Approaches

Many applications use different consistency models for different data:

```csharp
// Example: E-commerce platform

// Strong consistency for orders and payments (PostgreSQL)
public class OrderService
{
    private readonly IDbConnection _db;
    
    public async Task<Order> PlaceOrderAsync(Order order)
    {
        using var transaction = _db.BeginTransaction();
        
        // Deduct inventory (must be consistent)
        await _db.ExecuteAsync(
            "UPDATE products SET stock = stock - @Quantity WHERE id = @ProductId",
            order.Items
        );
        
        // Create order (must be atomic)
        await _db.ExecuteAsync("INSERT INTO orders ...", order);
        
        transaction.Commit();
        return order;
    }
}

// Eventual consistency for product catalog (MongoDB)
public class ProductCatalogService
{
    private readonly IMongoCollection<Product> _products;
    
    public async Task UpdateProductDescriptionAsync(string productId, string description)
    {
        // Update can be eventually consistent
        await _products.UpdateOneAsync(
            p => p.Id == productId,
            Builders<Product>.Update.Set(p => p.Description, description)
        );
        // Replicas sync asynchronously
    }
}

// No consistency needed for analytics (Cassandra/ClickHouse)
public class AnalyticsService
{
    public async Task TrackPageViewAsync(PageView view)
    {
        // Fire and forget
        await _analytics.InsertAsync(view);
    }
}
```

## Real-World Examples

### Amazon DynamoDB
- **Default:** Eventual consistency (AP)
- **Optional:** Strong consistency for critical reads
- **Trade-off:** Lower latency with eventual, higher latency with strong

### MongoDB
- **Default:** Strong consistency (CP) for single primary
- **Optional:** Read from secondaries (eventual consistency)
- **Configurable:** Write/read concern levels

### Cassandra
- **Default:** Tunable consistency (typically AP)
- **Configuration:** Can configure for strong consistency at cost of performance
- **Quorum:** Read + Write quorum = Strong consistency

## Best Practices

1. **Default to Appropriate Consistency:**
   - Financial: Strong (CP)
   - Social: Eventual (AP)
   - Mixed: Polyglot approach

2. **Understand Trade-offs:**
   - Consistency costs availability and latency
   - Availability risks temporary inconsistency
   - Partition tolerance is mandatory for distributed systems

3. **Test Partition Scenarios:**
   - Simulate network failures
   - Verify behavior during outages
   - Test recovery and convergence

4. **Monitor Consistency:**
   - Track replication lag
   - Alert on extended inconsistency
   - Measure convergence time

5. **Educate Stakeholders:**
   - Explain trade-offs to business
   - Document consistency guarantees
   - Set appropriate expectations
