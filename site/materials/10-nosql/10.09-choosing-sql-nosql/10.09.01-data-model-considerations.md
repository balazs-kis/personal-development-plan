## Learning Objectives

## Introduction

The nature of your data is the most fundamental factor in database selection. Understanding whether your data is structured with clear relationships, semi-structured with flexible schemas, or completely unstructured determines which database technologies are appropriate. This lesson explores how data characteristics drive database choice.

## Key Concepts Summary

### Data Types and Formats

#### Structured Data (SQL)

**Characteristics:**
- Organized in tables with rows and columns
- Predefined schema (schema-on-write)
- Data types defined upfront
- Consistent format across all records
- Strong relationships between entities

**Examples:**
- Customer information (name, email, address)
- Financial transactions
- Inventory records
- Employee databases
- Order management systems

**Best Database Choice:**
- Relational databases (PostgreSQL, SQL Server, MySQL, Oracle)

```sql
-- Structured data example
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date TIMESTAMP,
    total_amount DECIMAL(10, 2),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```

---

#### Semi-Structured Data (NoSQL)

**Characteristics:**
- Flexible schema (schema-on-read)
- Self-describing data with embedded metadata
- Hierarchical or nested structure
- Can evolve without migrations
- Formats: JSON, XML, YAML

**Examples:**
- API responses
- Configuration files
- Log data with varying fields
- User-generated content
- IoT sensor data

**Best Database Choice:**
- Document databases (MongoDB, CouchDB)
- Wide-column stores (Cassandra, HBase)

```json
// Semi-structured data example
{
  "customer_id": 12345,
  "name": "John Doe",
  "email": "john@example.com",
  "preferences": {
    "newsletter": true,
    "notifications": {
      "email": true,
      "sms": false
    }
  },
  "orders": [
    {
      "order_id": 67890,
      "date": "2024-01-15",
      "items": [
        { "product": "Laptop", "quantity": 1, "price": 999.99 }
      ]
    }
  ],
  "metadata": {
    "source": "web",
    "campaign": "spring_sale"
  }
}
```

---

#### Unstructured Data

**Characteristics:**
- No predefined schema or format
- Cannot be easily organized in tables
- Often large binary objects (BLOBs)
- Requires specialized storage and indexing

**Examples:**
- Images, videos, audio files
- PDF documents
- Email bodies
- Social media posts
- Log files (text-based)

**Best Database Choice:**
- Object storage (AWS S3, Azure Blob Storage)
- Document databases (for metadata)
- Search engines (Elasticsearch) for text indexing

---

### Data Relationships

#### Strong Relationships (SQL Advantage)

When data has well-defined relationships with referential integrity:

```sql
-- One-to-Many: Customer has many orders
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100)
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- Many-to-Many: Orders have many products, products in many orders
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id) REFERENCES orders(order_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);

-- Complex query leveraging relationships
SELECT c.name, COUNT(o.order_id) as order_count, SUM(o.total_amount) as total_spent
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
HAVING COUNT(o.order_id) > 5;
```

**Use SQL when:**
- Data has many relationships
- Complex joins are frequent
- Referential integrity is critical
- Normalized data model is desired

---

#### Flexible/Weak Relationships (NoSQL Advantage)

When relationships are minimal or data is self-contained:

```json
// Document database - embedded relationships
{
  "_id": "customer_12345",
  "name": "John Doe",
  "email": "john@example.com",
  "orders": [
    {
      "order_id": "67890",
      "date": "2024-01-15",
      "total": 999.99,
      "items": [
        {
          "product_id": "prod_001",
          "name": "Laptop",
          "quantity": 1
        }
      ]
    }
  ]
}
```

**Use NoSQL when:**
- Data is self-contained or denormalized
- Relationships are simple (1-to-few)
- Document-centric access patterns
- Embedding related data improves performance

---

### Schema Flexibility

#### Schema-on-Write (SQL)

**Characteristics:**
- Define structure before inserting data
- Ensures data consistency
- Changes require migrations
- Type safety enforced

**Pros:**
- Data integrity guaranteed
- Clear data contract
- Prevents invalid data
- Query optimization easier

**Cons:**
- Rigid structure
- Migrations can be complex
- Slower to adapt to changes
- All fields must be known upfront

```sql
-- Adding a new field requires migration
ALTER TABLE customers
ADD COLUMN phone_number VARCHAR(20);

-- This will fail if column doesn't exist
SELECT first_name, last_name, phone_number FROM customers;
```

---

#### Schema-on-Read (NoSQL)

**Characteristics:**
- No predefined schema required
- Structure interpreted when read
- Easy to add/remove fields
- Dynamic typing

**Pros:**
- Rapid iteration
- Heterogeneous data supported
- No downtime for schema changes
- Flexibility for evolving requirements

**Cons:**
- Application must handle variations
- Potential data inconsistency
- Type safety at application level
- Query optimization more complex

```javascript
// MongoDB - flexible schema
db.customers.insertOne({
  name: "John Doe",
  email: "john@example.com"
});

db.customers.insertOne({
  name: "Jane Smith",
  email: "jane@example.com",
  phone: "+1-555-0123",    // New field
  preferences: {           // Nested document
    newsletter: true
  }
});

// Query works even with different fields
db.customers.find({ email: { $exists: true } });
```

### Decision Matrix: Data Model to Database

| Data Characteristic | SQL (Relational) | NoSQL (Document) | NoSQL (Key-Value) | NoSQL (Graph) |
|---------------------|------------------|------------------|-------------------|---------------|
| Structured data | ✅ Excellent | ⚠️ Possible | ❌ Not suitable | ❌ Not suitable |
| Semi-structured | ⚠️ JSON columns | ✅ Excellent | ❌ Not suitable | ⚠️ Properties |
| Complex relationships | ✅ Excellent | ⚠️ Denormalize | ❌ Not suitable | ✅ Excellent |
| Flexible schema | ❌ Migrations needed | ✅ Excellent | ✅ Excellent | ✅ Excellent |
| Referential integrity | ✅ Built-in | ⚠️ Application | ❌ Application | ⚠️ Application |
| Hierarchical data | ⚠️ Recursive queries | ✅ Excellent | ❌ Not suitable | ✅ Excellent |
| Simple key lookups | ⚠️ Indexed | ✅ Good | ✅ Excellent | ⚠️ Possible |

## Real-World Examples

### E-commerce Platform

**Product Catalog:** Document database (MongoDB)
- Products have varying attributes by category
- Flexible schema for different product types
- Embedded reviews and ratings

```json
{
  "product_id": "laptop_001",
  "name": "Gaming Laptop",
  "category": "Electronics",
  "specs": {
    "cpu": "Intel i9",
    "ram": "32GB",
    "storage": "1TB SSD"
  },
  "reviews": [...]
}
```

**Order Management:** Relational database (PostgreSQL)
- Strong consistency for transactions
- Complex queries for reporting
- Referential integrity for orders/customers

```sql
SELECT * FROM orders
WHERE order_date >= '2024-01-01'
AND status = 'shipped';
```

---

### Social Network

**User Relationships:** Graph database (Neo4j)
- Model friend connections
- Discover mutual friends
- Recommendation algorithms

**User Posts:** Document database (MongoDB)
- Flexible content types (text, images, videos)
- Embedded comments and reactions
- Rapid evolution of features

---

### Financial System

**Transactions:** Relational database (SQL)
- ACID compliance required
- Strong consistency
- Audit trails
- Complex reporting

**Audit Logs:** Document database or Time-Series
- High write volume
- Flexible log formats
- Time-based queries

## Best Practices

1. **Start with Data Analysis:**
   - Map your domain entities
   - Identify relationships
   - Understand access patterns
   - Anticipate schema evolution

2. **Consider Hybrid Approaches:**
   - Use multiple databases for different parts
   - SQL for transactions, NoSQL for catalog
   - Leverage strengths of each technology

3. **Plan for Change:**
   - Assume requirements will evolve
   - Choose flexibility vs rigidity intentionally
   - Consider migration complexity

4. **Match Data to Technology:**
   - Structured + relationships → SQL
   - Semi-structured + flexible → Document NoSQL
   - Simple lookups → Key-Value NoSQL
   - Complex relationships → Graph NoSQL
