## Key Concepts Summary

### Vertical vs Horizontal Scaling

#### Vertical Scaling (Scale-Up)

**Definition:** Adding more power to existing server (CPU, RAM, storage).

**Characteristics:**
```
Single Server → Bigger Server
16GB RAM      → 128GB RAM
4 CPU cores   → 32 CPU cores
1TB storage   → 10TB storage
```

**Advantages:**
- ✅ Simple to implement (just upgrade hardware)
- ✅ No application changes needed
- ✅ ACID transactions work seamlessly
- ✅ Consistent performance
- ✅ No data distribution complexity

**Disadvantages:**
- ❌ Hardware limits (finite maximum)
- ❌ Single point of failure
- ❌ Expensive (exponential cost increase)
- ❌ Downtime during upgrades
- ❌ Limited by physics

**Best For:**
- Traditional SQL databases
- Applications with manageable data growth
- When simplicity is prioritized
- Strong consistency requirements

```csharp
// Vertical scaling example - same code, bigger machine
public class OrderService
{
    private readonly SqlConnection _connection;
    
    public async Task<Order> GetOrderAsync(int orderId)
    {
        // Works on 16GB server and 128GB server identically
        return await _connection.QueryFirstOrDefaultAsync<Order>(
            "SELECT * FROM orders WHERE order_id = @OrderId",
            new { OrderId = orderId }
        );
    }
}
```

---

#### Horizontal Scaling (Scale-Out)

**Definition:** Adding more servers to distribute load.

**Characteristics:**
```
Single Server → Multiple Servers
Server 1      → Server 1, Server 2, Server 3, ... Server N
```

**Advantages:**
- ✅ Nearly infinite scalability
- ✅ No hardware ceiling
- ✅ Better fault tolerance (redundancy)
- ✅ Linear cost growth
- ✅ Geographic distribution possible
- ✅ Rolling updates without downtime

**Disadvantages:**
- ❌ Complex data distribution
- ❌ Potential consistency issues
- ❌ More complex operations
- ❌ Network latency between nodes
- ❌ Application must be distribution-aware

**Best For:**
- NoSQL databases (Cassandra, MongoDB, DynamoDB)
- Distributed SQL (CockroachDB, YugabyteDB)
- Large-scale applications
- Global distribution requirements

```csharp
// Horizontal scaling example - data distributed across nodes
public class ProductService
{
    private readonly IMongoCollection<Product> _products;
    
    public async Task<Product> GetProductAsync(string productId)
    {
        // MongoDB automatically routes to correct shard
        // based on shard key
        return await _products.Find(p => p.Id == productId)
            .FirstOrDefaultAsync();
    }
    
    public async Task<List<Product>> GetProductsByCategoryAsync(string category)
    {
        // Query may hit multiple shards and aggregate results
        return await _products.Find(p => p.Category == category)
            .ToListAsync();
    }
}
```

### Sharding (Horizontal Partitioning)

**Definition:** Splitting a dataset across multiple servers, where each shard contains a subset of data.

#### Why Shard?

1. **Break Through Size Limits:**
   - Single server: 1TB limit
   - 10 shards: 10TB capacity

2. **Increase Throughput:**
   - Single server: 1000 req/sec
   - 10 shards: 10,000 req/sec (parallelized)

3. **Reduce Query Time:**
   - Query subset of data on each shard
   - Parallel execution

4. **Geographic Distribution:**
   - Data closer to users
   - Lower latency

---

### Sharding Strategies

#### 1. Range-Based Sharding

**Concept:** Distribute data based on ranges of shard key values.

```
Users 1-1000     → Shard 1
Users 1001-2000  → Shard 2
Users 2001-3000  → Shard 3
```

**Advantages:**
- ✅ Simple to implement
- ✅ Efficient range queries
- ✅ Easy to add new ranges

**Disadvantages:**
- ❌ Can create hotspots (uneven distribution)
- ❌ Requires choosing good boundaries

```javascript
// MongoDB range sharding example
sh.shardCollection("users.profiles", { user_id: 1 });

// Add shard ranges
sh.addShardRange(
  "users.profiles",
  { user_id: MinKey },
  { user_id: 1000 },
  "shard1"
);
sh.addShardRange(
  "users.profiles",
  { user_id: 1000 },
  { user_id: 2000 },
  "shard2"
);
```

---

#### 2. Hash-Based Sharding

**Concept:** Hash the shard key and distribute based on hash value.

```
Hash(user_id=1234) % 3 = 1  → Shard 2
Hash(user_id=5678) % 3 = 2  → Shard 3
Hash(user_id=9012) % 3 = 0  → Shard 1
```

**Advantages:**
- ✅ Even data distribution
- ✅ No hotspots (usually)
- ✅ Simple algorithm

**Disadvantages:**
- ❌ Range queries hit all shards
- ❌ Difficult to add/remove shards

```javascript
// MongoDB hashed sharding
sh.shardCollection("products.catalog", { product_id: "hashed" });

// Automatic distribution based on hash
db.products.insertOne({
  product_id: "prod_12345",
  name: "Laptop",
  price: 999
});
// MongoDB calculates hash and routes to appropriate shard
```

---

#### 3. Geographic/Location-Based Sharding

**Concept:** Distribute data by geographic location.

```
US users      → US datacenter
EU users      → EU datacenter
Asia users    → Asia datacenter
```

**Advantages:**
- ✅ Data locality (lower latency)
- ✅ Compliance (data residency)
- ✅ Disaster recovery (regional isolation)

**Disadvantages:**
- ❌ Uneven distribution possible
- ❌ Cross-region queries expensive

```javascript
// MongoDB zone sharding example
sh.addShardTag("shard_us", "NA");
sh.addShardTag("shard_eu", "EU");
sh.addShardTag("shard_asia", "ASIA");

sh.addTagRange(
  "users.profiles",
  { region: "NA", user_id: MinKey },
  { region: "NA", user_id: MaxKey },
  "NA"
);
```

---

#### 4. Directory-Based Sharding

**Concept:** Maintain a lookup service that knows which shard contains which data.

```
Lookup Service:
  user_1 → Shard 1
  user_2 → Shard 3
  user_3 → Shard 1
```

**Advantages:**
- ✅ Flexible distribution
- ✅ Easy rebalancing
- ✅ Custom logic possible

**Disadvantages:**
- ❌ Lookup service is bottleneck
- ❌ Additional infrastructure
- ❌ Single point of failure

### Read vs Write Performance

#### Read-Heavy Workloads

**Characteristics:**
- 90%+ reads, <10% writes
- Examples: Product catalogs, content sites, dashboards

**Optimization Strategies:**
1. **Read Replicas (SQL)**
```csharp
// Primary for writes
await using var writeConnection = new SqlConnection(primaryConnectionString);
await writeConnection.ExecuteAsync("INSERT INTO products ...");

// Replica for reads
await using var readConnection = new SqlConnection(replicaConnectionString);
var products = await readConnection.QueryAsync<Product>("SELECT * FROM products");
```

2. **Caching Layer (Redis)**
```csharp
var cacheKey = $"product:{productId}";
var cached = await _cache.GetStringAsync(cacheKey);

if (cached != null)
    return JsonSerializer.Deserialize<Product>(cached);

// Cache miss - read from database
var product = await _db.Products.FindAsync(productId);
await _cache.SetStringAsync(cacheKey, JsonSerializer.Serialize(product));
return product;
```

3. **NoSQL Read Replicas**
```csharp
// MongoDB secondary reads
var options = new FindOptions
{
    ReadPreference = ReadPreference.SecondaryPreferred
};
var products = await _products.Find(_ => true, options).ToListAsync();
```

**Best Database Choices:**
- SQL with read replicas
- Document databases (MongoDB)
- Search engines (Elasticsearch)

---

#### Write-Heavy Workloads

**Characteristics:**
- High write throughput
- Examples: Logging, IoT sensors, analytics events

**Optimization Strategies:**
1. **Batch Writes**
```csharp
// Bad - individual writes
foreach (var log in logs)
{
    await _db.ExecuteAsync("INSERT INTO logs ...", log);
}

// Good - batch write
await _db.ExecuteAsync("INSERT INTO logs ...", logs);
```

2. **Write-Optimized NoSQL**
```csharp
// Cassandra - optimized for writes
var statement = new SimpleStatement(
    "INSERT INTO sensor_data (sensor_id, timestamp, value) VALUES (?, ?, ?)",
    sensorId, DateTime.UtcNow, value
);
await session.ExecuteAsync(statement);
```

3. **Time-Series Databases**
```csharp
// InfluxDB - purpose-built for time-series writes
var point = PointData
    .Measurement("temperature")
    .Tag("sensor", "sensor1")
    .Field("value", 22.5)
    .Timestamp(DateTime.UtcNow, WritePrecision.Ns);

await _writeApi.WritePointAsync(point);
```

**Best Database Choices:**
- Cassandra (distributed writes)
- Time-series (InfluxDB, TimescaleDB)
- Log stores (Elasticsearch, Loki)

### Performance Metrics

#### Latency

**SQL (Single Node):**
- Read: 1-10ms (indexed)
- Write: 1-10ms (single transaction)

**NoSQL (Distributed):**
- Read: 1-5ms (key lookup)
- Write: 5-50ms (replication to multiple nodes)

**Factors:**
- Network latency between nodes
- Replication factor
- Consistency level

```csharp
// Measure latency
var sw = Stopwatch.StartNew();
var result = await _db.QueryAsync("SELECT ...");
sw.Stop();
_logger.LogInformation("Query took {Ms}ms", sw.ElapsedMilliseconds);
```

---

#### Throughput

**SQL (Single Node):**
- Reads: 1K-10K queries/sec
- Writes: 500-5K queries/sec

**NoSQL (Distributed):**
- Reads: 10K-1M+ queries/sec (linear with nodes)
- Writes: 10K-500K+ queries/sec (linear with nodes)

**Scaling:**
```
SQL: Limited by single server capacity
NoSQL: Scales with number of nodes
  - 3 nodes: 30K qps
  - 6 nodes: 60K qps
  - 10 nodes: 100K qps
```

## Scalability Patterns

### 1. Read Scaling with Replicas

```
Primary (Writes) ──┬──► Replica 1 (Reads)
                   ├──► Replica 2 (Reads)
                   └──► Replica 3 (Reads)
```

**Use When:** Read-heavy workload (10:1 read:write ratio)

---

### 2. Write Scaling with Sharding

```
Application ──┬──► Shard 1 (users 1-1000)
              ├──► Shard 2 (users 1001-2000)
              └──► Shard 3 (users 2001-3000)
```

**Use When:** Write throughput exceeds single server capacity

---

### 3. Hybrid: Shards + Replicas

```
Shard 1 ──┬──► Replica 1A
          └──► Replica 1B

Shard 2 ──┬──► Replica 2A
          └──► Replica 2B
```

**Use When:** Both read and write scaling needed

## Real-World Examples

### Twitter
- **Problem:** Billions of tweets, high read/write
- **Solution:** Custom sharding across thousands of nodes
- **Approach:** Tweet IDs encode shard information

### Netflix
- **Problem:** Global streaming, millions of concurrent users
- **Solution:** Cassandra for distributed writes across regions
- **Benefit:** Linear scalability, no single point of failure

### Uber
- **Problem:** Real-time location updates, global scale
- **Solution:** PostgreSQL with sharding (initially), migrating to purpose-built solutions
- **Learning:** Started simple, scaled when needed

## Decision Framework

### When to Use Vertical Scaling (SQL)

✅ **Choose vertical scaling when:**
- Data size < 1TB
- Throughput < 10K requests/sec
- Strong consistency required
- Complex transactions needed
- Team familiar with SQL

**Example:** Small to medium business applications

---

### When to Use Horizontal Scaling (NoSQL)

✅ **Choose horizontal scaling when:**
- Data size > 1TB (or growing rapidly)
- Throughput > 10K requests/sec
- Global distribution needed
- Eventual consistency acceptable
- Write-heavy workload

**Example:** Social networks, IoT platforms, analytics

---

## Best Practices

1. **Start Simple:**
   - Begin with vertical scaling
   - Scale horizontally when needed
   - Don't over-engineer early

2. **Plan for Growth:**
   - Estimate growth trajectory
   - Choose databases that can scale
   - Monitor usage patterns

3. **Choose Right Shard Key:**
   - High cardinality
   - Even distribution
   - Matches query patterns

4. **Monitor Performance:**
   - Track latency percentiles (p50, p95, p99)
   - Measure throughput
   - Watch for hotspots

5. **Test at Scale:**
   - Load testing
   - Chaos engineering
   - Failover drills
