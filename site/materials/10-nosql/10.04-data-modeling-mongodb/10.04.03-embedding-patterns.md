# Lesson 3: Embedding Patterns

## Learning Objectives

By the end of this lesson, you will be able to:
- Apply the subset pattern to optimize working set size
- Use the extended reference pattern to avoid excessive joins
- Understand when to denormalize data through embedding
- Balance performance benefits against data duplication risks

---

## Introduction

Embedding is MongoDB's most powerful feature for optimizing read performance. However, naive embedding can lead to massive documents, duplicated data, and complex update logic. This lesson explores sophisticated embedding patterns that help you get the benefits of denormalization while managing its complexity: the subset pattern handles large arrays, and the extended reference pattern optimizes frequently-joined data.

## Key Concepts Summary

### The Subset Pattern

**Problem:** Documents contain large arrays that cause the working set to exceed RAM, leading to disk access and poor performance.

**Solution:** Split data into frequently accessed and rarely accessed subsets.

**Example: E-commerce Product Reviews**

```javascript
// Product document with ONLY most recent reviews embedded
{
  _id: "product123",
  name: "Ultra Widget",
  price: 29.99,
  recent_reviews: [  // Only last 10 reviews
    {
      rating: 5,
      comment: "Great product!",
      reviewer: "Alice",
      date: ISODate("2026-01-25")
    },
    {
      rating: 4,
      comment: "Good value",
      reviewer: "Bob",
      date: ISODate("2026-01-20")
    }
    // ... 8 more recent reviews
  ],
  total_reviews: 2847,
  average_rating: 4.3
}

// Separate Reviews collection has ALL reviews
{
  _id: "review001",
  product_id: "product123",
  rating: 5,
  comment: "Great product!",
  reviewer: "Alice",
  date: ISODate("2026-01-25")
}
```

**Benefits:**
- Keeps main document size manageable
- Frequently viewed data (recent reviews) loads quickly
- Full data available when needed via separate query
- Working set stays in RAM

**When to use:**
- Large arrays (hundreds or thousands of items)
- Only a small subset accessed in typical queries
- Clear criteria for what belongs in subset (e.g., most recent, top-rated)

### The Extended Reference Pattern

**Problem:** Referencing requires joins (lookups) which hurt performance, but full embedding causes massive duplication.

**Solution:** Embed only the frequently accessed fields; keep the full document separate.

**Example: Order with Customer Information**

```javascript
// Order document with extended customer reference
{
  _id: "order789",
  order_number: "ORD-2026-0127",
  order_date: ISODate("2026-01-27"),
  status: "shipped",
  
  // Extended reference: embed key customer fields
  customer: {
    customer_id: "cust456",
    name: "Jane Doe",
    email: "jane@example.com",
    shipping_address: {
      street: "123 Main St",
      city: "Springfield",
      state: "IL",
      zip: "62701"
    }
  },
  
  line_items: [
    { product: "Widget", quantity: 2, price: 29.99 },
    { product: "Gadget", quantity: 1, price: 49.99 }
  ],
  total: 109.97
}

// Full Customer document (separate collection)
{
  _id: "cust456",
  name: "Jane Doe",
  email: "jane@example.com",
  phone: "555-1234",
  addresses: [
    {
      type: "shipping",
      street: "123 Main St",
      city: "Springfield",
      state: "IL",
      zip: "62701"
    },
    {
      type: "billing",
      street: "456 Oak Ave",
      city: "Capital City",
      state: "IL",
      zip: "62702"
    }
  ],
  payment_methods: [...],
  order_history: [...],
  preferences: {...}
}
```

**Benefits:**
- Avoids expensive lookups for common queries (e.g., "show order details")
- No need to fetch customer document just to display order
- Captures historical state (customer's address at order time)
- Full customer data available when needed

**Considerations:**
- Duplicated data (customer name, email, address)
- Must decide: sync updates or keep historical snapshot?
  - Historical: Keep order's customer info unchanged (common for orders)
  - Synced: Update when customer info changes (requires careful logic)

**When to use:**
- Frequent joins between collections
- Only a few fields needed in most queries
- Trade-off between duplication and performance is favorable
- Often want historical snapshot rather than current data

### Decision Matrix

| Scenario | Pattern | Rationale |
|----------|---------|-----------|
| Product with 10,000 reviews; display shows 10 most recent | Subset | Keep working set small, most users only see recent |
| Movie with 50 actors; always show all actor names | Full Embed | Small, bounded data accessed together |
| Order needs customer name/address | Extended Reference | Avoid lookup, capture historical state |
| Blog post with 5 comments | Full Embed | Small, accessed together, bounded |
| User profile with 1M activity logs | Reference Only | Unbounded, rarely need all logs with profile |

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Design schemas for these scenarios using appropriate embedding patterns:

1. **Movie Database:**
   - Movies have 5-200 actors
   - Users browse movies and see cast list
   - Clicking an actor shows their full biography and filmography
   - Should you embed actors in movies? Fully, subset, or extended reference?

2. **Social Media Feed:**
   - Posts can have 0-10,000 comments
   - Feed shows post with first 3 comments
   - Users can click "see all comments"
   - How would you model this?

3. **Order Management:**
   - Orders reference products
   - Order display needs product name, image, and price
   - Product has 50+ other fields (dimensions, weight, manufacturer, etc.)
   - What pattern optimizes order queries?
