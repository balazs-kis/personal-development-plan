# Lesson 4: Reference Patterns (Subset and Extended Reference)

## Learning Objectives

By the end of this lesson, you will be able to:
- Apply the subset pattern to handle large embedded arrays
- Implement the extended reference pattern to reduce lookups
- Identify scenarios where these patterns provide significant performance benefits
- Understand the trade-offs of denormalization in these patterns

---

## Introduction

The subset and extended reference patterns are two of the most powerful tools in MongoDB schema design. They represent sophisticated approaches to the embedding vs. referencing decision: instead of choosing one or the other, these patterns strategically combine both approaches. The subset pattern keeps documents small by embedding only frequently accessed data, while the extended reference pattern avoids expensive lookups by duplicating key fields.

## Key Concepts Summary

### Subset Pattern Deep Dive

**When to Apply:**
- Working set exceeds available RAM
- Large arrays in documents (hundreds to thousands of items)
- Most queries only need a small portion of the array
- Clear criteria for subset selection (recent, top-rated, etc.)

**Implementation Strategies:**

**1. Time-Based Subset (Most Common):**
```javascript
// Blog post with recent comments only
{
  _id: "post123",
  title: "MongoDB Design Patterns",
  content: "...",
  recent_comments: [  // Last 25 comments
    {
      author: "Alice",
      text: "Great article!",
      date: ISODate("2026-01-27T10:30:00Z")
    }
    // ... 24 more
  ],
  comment_count: 847,
  oldest_comment_date: ISODate("2024-03-15T08:00:00Z")
}

// All comments in separate collection
{
  _id: "comment001",
  post_id: "post123",
  author: "Alice",
  text: "Great article!",
  date: ISODate("2026-01-27T10:30:00Z")
}
```

**2. Popularity-Based Subset:**
```javascript
// Movie with top actors only
{
  _id: "movie456",
  title: "Epic Film",
  top_actors: [  // Top 5 billed actors
    {
      actor_id: "actor789",
      name: "Famous Actor",
      character: "Main Hero",
      billing_order: 1
    }
    // ... 4 more
  ],
  total_cast: 237
}

// Full cast in separate collection
{
  _id: "cast001",
  movie_id: "movie456",
  actor_id: "actor789",
  name: "Famous Actor",
  character: "Main Hero",
  billing_order: 1
}
```

**Maintenance Considerations:**
- How to keep subset updated when new items are added?
- Background job vs. real-time update?
- Use `$push` with `$slice` for automatic subset maintenance:

```javascript
// Add new comment and automatically keep only last 25
db.posts.updateOne(
  { _id: "post123" },
  {
    $push: {
      recent_comments: {
        $each: [newComment],
        $slice: -25,  // Keep last 25
        $sort: { date: -1 }
      }
    },
    $inc: { comment_count: 1 }
  }
)
```

### Extended Reference Pattern Deep Dive

**When to Apply:**
- Frequently joining two collections
- Only a few fields needed in most queries
- Performance gain outweighs duplication cost
- Capturing historical state is valuable

**Implementation Strategies:**

**1. Historical Snapshot (No Sync Required):**
```javascript
// Invoice with customer data at invoice time
{
  _id: "invoice2026-001",
  invoice_number: "INV-2026-001",
  invoice_date: ISODate("2026-01-27"),
  
  // Extended reference: customer at time of invoice
  customer: {
    customer_id: "cust456",
    name: "Jane Doe",
    billing_address: {
      street: "123 Main St",
      city: "Springfield",
      state: "IL",
      zip: "62701"
    },
    tax_id: "12-3456789"
  },
  
  line_items: [...],
  subtotal: 1000.00,
  tax: 80.00,
  total: 1080.00
}
```

**Benefits:**
- Legal/compliance: invoice shows data as it was
- No sync problems: embedded data never changes
- Complete invoice display without lookup

**2. Synced Denormalization (Requires Update Logic):**
```javascript
// Social media post with author info
{
  _id: "post789",
  content: "Check out my new profile picture!",
  timestamp: ISODate("2026-01-27T15:30:00Z"),
  
  // Extended reference: synced with author
  author: {
    user_id: "user123",
    username: "jane_doe",
    display_name: "Jane Doe",
    avatar_url: "https://cdn.example.com/avatars/jane.jpg"
  },
  
  likes: 42,
  comments: [...]
}
```

**Update Strategy:**
When user changes display name or avatar:
```javascript
// 1. Update the User document
db.users.updateOne(
  { _id: "user123" },
  { $set: { display_name: "Jane Smith", avatar_url: "new_url" } }
)

// 2. Update all posts by this user
db.posts.updateMany(
  { "author.user_id": "user123" },
  {
    $set: {
      "author.display_name": "Jane Smith",
      "author.avatar_url": "new_url"
    }
  }
)
```

**Important:** Use a background job for large updates to avoid locking issues.

### Choosing Fields for Extended Reference

**Include fields that are:**
- Frequently displayed with the parent document
- Relatively stable (don't change often)
- Small in size
- Needed for filtering or display

**Exclude fields that are:**
- Rarely accessed
- Large (images, long descriptions)
- Frequently updated
- Sensitive/private

**Example Decision Matrix for Order → Customer:**

| Field | Include? | Reason |
|-------|----------|--------|
| customer_id | ✅ Yes | Always needed for reference |
| name | ✅ Yes | Displayed on order, rarely changes |
| email | ✅ Yes | Needed for communication |
| shipping_address | ✅ Yes | Essential for fulfillment |
| phone | ✅ Maybe | Useful but not always displayed |
| date_of_birth | ❌ No | Rarely needed for orders |
| password_hash | ❌ No | Never needed in orders, security risk |
| order_history | ❌ No | Large, not needed here |
| preferences | ❌ No | Not relevant to order display |

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

Design schemas for the following scenarios:

1. **News Website:**
   - Articles have 0-5,000 comments
   - Article page shows 50 most recent comments
   - Comments include author name, avatar, and comment text
   - Should author details be embedded or referenced?
   - How would you handle comment pagination?

2. **E-commerce Order System:**
   - Orders reference products
   - Product catalog has 50 fields per product
   - Order display needs: product name, SKU, image, and price
   - Product details change (e.g., price updates)
   - Should order capture historical price or current price?
   - What fields belong in extended reference?

3. **Social Network:**
   - Users have 1-10,000 posts
   - Profile page shows 20 most recent posts
   - Feed shows posts with author info (name, avatar)
   - Design the User → Posts relationship
   - Design the Feed → Post → User relationship

For each scenario, specify:
- Which pattern (subset, extended reference, or both)
- What fields to include
- How to handle updates
- Query patterns this design optimizes
