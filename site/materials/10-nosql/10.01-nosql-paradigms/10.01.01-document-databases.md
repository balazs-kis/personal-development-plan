---

## Introduction

Document databases store data as documents (typically JSON, BSON, or XML), where each document can have a different structure. Unlike relational databases with fixed schemas, document databases offer flexibility that aligns well with modern application development, especially when dealing with evolving data models or hierarchical data structures.

## Key Concepts Summary

### What is a Document Database?

Document databases store data as self-contained documents (usually JSON or BSON format). Each document contains key-value pairs where values can be:
- Simple types (strings, numbers, booleans)
- Nested documents (objects)
- Arrays
- Any combination of the above

```json
{
  "_id": "user_123",
  "name": "Alice Johnson",
  "email": "alice@example.com",
  "address": {
    "street": "123 Main St",
    "city": "Springfield",
    "state": "IL"
  },
  "orders": [
    {"orderId": "ord_001", "total": 99.99, "date": "2026-01-15"},
    {"orderId": "ord_002", "total": 149.50, "date": "2026-01-20"}
  ]
}
```

### Key Characteristics

**Flexible Schema:** Each document can have different fields. Adding new fields doesn't require schema migrations.

**Hierarchical Data:** Documents naturally represent nested and hierarchical data structures without joins.

**Atomic Operations:** Operations on a single document are atomic, providing consistency guarantees at the document level.

**Indexing:** Most document databases support indexing on any field, including nested fields and array elements.

### Popular Document Databases

**MongoDB**
- Most popular document database
- BSON format (binary JSON)
- Rich query language with aggregation framework
- Horizontal scalability through sharding

**Azure Cosmos DB for NoSQL**
- Fully managed, globally distributed
- Multi-model with document as primary model
- 99.999% availability SLA
- Automatic indexing

**CouchDB**
- HTTP/REST API
- Multi-master replication
- MVCC (Multi-Version Concurrency Control)
- Conflict resolution for distributed scenarios

### When to Use Document Databases

**Ideal Use Cases:**
- Content management systems and catalogs
- User profiles and personalization
- Real-time analytics and event logging
- E-commerce product catalogs with varying attributes
- Mobile and web applications with evolving data models

**Not Ideal For:**
- Complex transactions across multiple entities
- Queries requiring many joins across documents
- Applications requiring strict normalization
- Financial systems needing ACID guarantees across operations

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Design a document schema for a simple blog application that includes:
- Blog posts with title, content, author, tags, and publication date
- Comments on posts (nested within the post or referenced?)
- Author information

Consider:
1. Should comments be embedded in the post document or stored separately?
2. Should author information be embedded or referenced?
3. What are the trade-offs of each approach?

Sketch out the JSON structure for your chosen approach.
