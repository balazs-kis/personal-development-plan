## Introduction

Key-value stores are the simplest type of NoSQL database. They store data as a collection of key-value pairs where the key is a unique identifier and the value is an opaque blob of data. The database doesn't interpret or index the value's contents—it only knows how to retrieve it by its key. This simplicity enables exceptional performance for lookup operations.

## Key Concepts Summary

### What is a Key-Value Store?

Key-value stores are the simplest NoSQL model: they map unique keys to values. The database treats values as opaque—it doesn't understand or index their internal structure.

```
Key: "user:123:name" → Value: "Alice Johnson"
Key: "user:123:email" → Value: "alice@example.com"
Key: "session:abc-def-ghi" → Value: "{userId: 123, loginTime: 1706371200}"
Key: "counter:page_views" → Value: "42573"
```

### Key Characteristics

**Simple Data Model:** Just keys and values—no complex queries, joins, or secondary indexes.

**High Performance:** Optimized for fast reads and writes by key. Typically O(1) lookup time.

**Opaque Values:** The database doesn't interpret value contents. This provides flexibility but limits query capabilities.

**Atomic Operations:** Support for atomic operations like increment, decrement, compare-and-swap.

### Redis: The Swiss Army Knife of Key-Value Stores

Redis goes beyond simple key-value storage by supporting rich data structures:

**Data Structures:**
- **Strings:** Simple text or binary values
- **Lists:** Ordered collections (queues, stacks)
- **Sets:** Unordered collections of unique values
- **Sorted Sets:** Sets ordered by score
- **Hashes:** Maps of field-value pairs (mini objects)
- **Bitmaps, HyperLogLogs:** Specialized structures for specific use cases

**Additional Features:**
- In-memory storage with optional persistence
- Pub/Sub messaging
- Key expiration (TTL)
- Transactions
- Lua scripting

```redis
# String operations
SET user:123:name "Alice Johnson"
GET user:123:name

# Increment counter
INCR counter:page_views

# Hash (object-like)
HSET user:123 name "Alice" email "alice@example.com"
HGET user:123 name

# List (queue)
LPUSH queue:jobs "job1"
RPOP queue:jobs

# Set key expiration (30 minutes)
SETEX session:abc-def 1800 "{userId: 123}"
```

### etcd: Configuration and Coordination

While Redis is general-purpose, **etcd** is a distributed key-value store designed for:
- Service discovery and configuration management
- Distributed coordination and leader election
- Strong consistency guarantees (uses Raft consensus)
- Used extensively in Kubernetes

### When to Use Key-Value Stores

**Ideal Use Cases:**
- Session storage and management
- Caching frequently accessed data
- Feature flags and configuration
- Real-time leaderboards and counters
- Shopping cart data
- Rate limiting
- Simple task queues

**Not Ideal For:**
- Complex queries across multiple keys
- Relationships between entities
- Ad-hoc queries where you don't know the key
- Data that requires searching by value

### Key-Value vs. Document Databases

| Aspect | Key-Value | Document |
|--------|-----------|----------|
| **Data Transparency** | Opaque values | Structured, queryable documents |
| **Query Capability** | Key lookup only | Rich queries on fields |
| **Performance** | Faster for simple operations | Slightly slower but more flexible |
| **Use Case** | Caching, sessions | Complex data models |
