## Introduction

Graph databases are designed to store and navigate relationships between data. Unlike other databases where relationships are expensive to query (through joins or lookups), graph databases treat relationships as first-class citizens, making it natural and efficient to model and query interconnected data like social networks, recommendation engines, and fraud detection systems.

## Key Concepts Summary

### What is a Graph Database?

Graph databases store data as **nodes** (entities), **relationships** (connections), and **properties** (attributes). They're designed to efficiently traverse relationships, making them ideal for interconnected data.

**Graph Model:**
```
(Alice:Person {name: "Alice", age: 30})
   -[:FRIENDS_WITH {since: 2020}]->
(Bob:Person {name: "Bob", age: 28})
   -[:WORKS_AT]->
(Company:Organization {name: "TechCorp"})
   <-[:WORKS_AT]-
(Alice)
```

Visual representation:
```
   ┌─────────┐
   │  Alice  │
   │ Person  │
   └────┬────┘
        │ FRIENDS_WITH
        │ (since: 2020)
        ↓
   ┌────────┐        WORKS_AT
   │  Bob   │──────────────────┐
   │ Person │                  │
   └────────┘                  ↓
        ↑                 ┌──────────┐
        │                 │ TechCorp │
        │   WORKS_AT      │   Org    │
   ┌────────┐             └──────────┘
   │ Alice  │─────────────────────────┘
   └────────┘
```

### Core Components

**Nodes (Vertices):**
- Represent entities (people, products, locations)
- Can have one or more labels (types)
- Contain properties (key-value pairs)

**Relationships (Edges):**
- Connect two nodes with a direction
- Have exactly one type (e.g., FRIENDS_WITH, PURCHASED, LOCATED_IN)
- Can contain properties
- Are always stored as first-class citizens (not computed)

**Properties:**
- Key-value pairs attached to nodes or relationships
- Can be strings, numbers, booleans, dates, etc.

### Neo4j: The Leading Graph Database

**Key Features:**
- ACID-compliant transactions
- Native graph storage and processing
- Cypher query language (declarative, SQL-like)
- Index-free adjacency (relationships stored with nodes)
- Visualization tools (Neo4j Browser, Bloom)

**Cypher Query Language:**

Cypher uses ASCII-art syntax that resembles the graph structure:

```cypher
// Create nodes and relationships
CREATE (alice:Person {name: "Alice", age: 30})
CREATE (bob:Person {name: "Bob", age: 28})
CREATE (alice)-[:FRIENDS_WITH {since: 2020}]->(bob)

// Find all friends of Alice
MATCH (alice:Person {name: "Alice"})-[:FRIENDS_WITH]->(friend)
RETURN friend.name

// Find friends of friends (2 hops)
MATCH (alice:Person {name: "Alice"})-[:FRIENDS_WITH*2]->(foaf)
RETURN DISTINCT foaf.name

// Shortest path
MATCH path = shortestPath(
  (alice:Person {name: "Alice"})-[*]-(target:Person {name: "Charlie"})
)
RETURN path

// Recommendation: Friends who bought similar products
MATCH (user:Person {name: "Alice"})-[:PURCHASED]->(product:Product)
      <-[:PURCHASED]-(other:Person)
MATCH (other)-[:PURCHASED]->(recommendation:Product)
WHERE NOT (user)-[:PURCHASED]->(recommendation)
RETURN recommendation.name, COUNT(*) as score
ORDER BY score DESC
LIMIT 5
```

**Naming Conventions:**
- **Node labels:** CamelCase (e.g., `Person`, `ProductCategory`)
- **Relationship types:** ALL_CAPS_WITH_UNDERSCORES (e.g., `FRIENDS_WITH`, `PURCHASED`)
- **Property keys:** camelCase (e.g., `firstName`, `createdAt`)

### When to Use Graph Databases

**Ideal Use Cases:**
- Social networks (friends, followers, connections)
- Recommendation engines (products, content, connections)
- Fraud detection (identifying suspicious patterns)
- Network and IT operations (topology, dependencies)
- Knowledge graphs (entities and relationships)
- Access control and permissions (who can access what)
- Supply chain and logistics (tracking relationships)
- Master data management (connecting entities across systems)

**Characteristics that Favor Graphs:**
- Data is highly interconnected
- Queries traverse relationships (3+ hops)
- Relationships are as important as the data
- Need to find patterns or paths
- Schema evolves frequently

**Not Ideal For:**
- Simple key-value lookups
- Large-scale analytics on flat data
- Document storage with no relationships
- When relationships are rarely queried

### Graph vs. Other NoSQL Types

| Aspect | Graph | Document | Relational |
|--------|-------|----------|-----------|
| **Relationship Queries** | Extremely fast | Slow (manual resolution) | Slow (many joins) |
| **Schema Flexibility** | Very flexible | Very flexible | Rigid |
| **Best For** | Connected data | Hierarchical data | Tabular data |
| **Query Depth** | Efficient at any depth | Degrades with depth | Degrades with depth |

### Real-World Example: Social Network

```cypher
// Data model
(:User)-[:FOLLOWS]->(:User)
(:User)-[:POSTS]->(:Post)
(:User)-[:LIKES]->(:Post)
(:Post)-[:HAS_TAG]->(:Tag)

// Query: Recommend posts from friends' activity
MATCH (me:User {username: "alice"})-[:FOLLOWS]->(friend)
MATCH (friend)-[:LIKES]->(post:Post)
WHERE NOT (me)-[:LIKES]->(post)
RETURN post.title, COUNT(DISTINCT friend) as friendsWhoLiked
ORDER BY friendsWhoLiked DESC
LIMIT 10

// Query: Find mutual friends
MATCH (me:User {username: "alice"})-[:FOLLOWS]->(friend)
      <-[:FOLLOWS]-(other:User)
WHERE NOT (me)-[:FOLLOWS]->(other) AND me <> other
RETURN other.username, COUNT(DISTINCT friend) as mutualFriends
ORDER BY mutualFriends DESC
```

After completing the materials, try this exercise (do not spend more than 15 minutes):

Design a graph model for a simple project management system:

**Entities:**
- Users (developers, managers)
- Projects
- Tasks
- Skills

**Relationships to consider:**
- Users work on projects
- Projects contain tasks
- Tasks are assigned to users
- Tasks may depend on other tasks
- Users have skills
- Tasks require skills

Sketch out:
1. Node labels and their key properties
2. Relationship types
3. A Cypher query to find: "All users who have the required skills for unassigned tasks in a project"
