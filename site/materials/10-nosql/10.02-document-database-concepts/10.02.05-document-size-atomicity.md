- Apply strategies to work within size constraints

---

## Introduction

Document databases provide strong atomicity guarantees at the document level, meaning all changes to a single document either succeed or fail together. However, documents have size limitations (16MB in MongoDB) that influence how you model data. This lesson explores these constraints and the consistency guarantees provided by document databases.

## Key Concepts Summary

### The 16MB Document Size Limit

**MongoDB's Hard Limit:**
- Maximum BSON document size: **16 mebibytes (16,777,216 bytes)**
- This limit applies to the entire document including all nested documents and arrays
- Enforced to ensure reasonable performance and efficient use of memory

```javascript
// This document's size is the sum of:
// - All field names and values
// - All nested objects
// - All array elements
// - BSON metadata
{
  _id: ObjectId("..."),        // 12 bytes
  name: "Alice Johnson",       // Field name + string value
  address: {                   // Nested object
    street: "123 Main St",
    city: "Springfield"
  },
  orders: [                    // Array
    { orderId: "123", total: 99.99 },
    // ... potentially thousands of orders
  ]
}
```

**Why 16MB?**
- Prevents excessive memory usage
- Ensures efficient network transfer
- Enables reasonable query performance
- Encourages proper data modeling
- Limits impact of large document operations

### Implications of the Size Limit

**What Fits in 16MB?**

Rough estimates:
- **Plain text:** ~8-16 million characters
- **JSON documents:** ~500,000 to 1 million small objects
- **Small images:** A few high-resolution images (but shouldn't store in docs)
- **Typical application data:** Thousands of typical business records

**Real-World Example:**
```javascript
// This user document is approximately:
{
  _id: ObjectId("..."),           // ~12 bytes
  username: "alice123",           // ~20 bytes (field name + value)
  email: "alice@example.com",     // ~30 bytes
  profile: {                      // ~200 bytes
    name: "Alice Johnson",
    bio: "Software developer...",
    avatar: "url"
  },
  preferences: { ... },           // ~100 bytes
  loginHistory: [                 // ~50 bytes per entry
    { date: ISODate("..."), ip: "..." },
    // ... 1000 entries = ~50KB
  ]
}
// Total: ~50KB (well under 16MB)
```

**What Doesn't Fit:**
```javascript
// PROBLEMS:

// 1. Unbounded arrays that grow indefinitely
{
  userId: "user123",
  allActivityLogs: [  // Could eventually exceed 16MB
    // 10 years of activity logs...
  ]
}

// 2. Large binary data embedded
{
  productId: "prod123",
  productImage: "base64 encoded 20MB image"  // TOO LARGE!
}

// 3. Complete datasets embedded
{
  reportId: "report123",
  allUserData: [  // Thousands of users
    // ... millions of records
  ]
}
```

### Working Within Size Constraints

**Strategy 1: Use References Instead of Embedding**
```javascript
// DON'T: Embed all orders in user document
{
  _id: "user123",
  orders: [/* thousands of orders */]  // Could grow > 16MB
}

// DO: Reference orders in separate collection
{
  _id: "user123",
  name: "Alice"
}

// Orders collection
{ _id: "order456", userId: "user123", total: 99.99 }
```

**Strategy 2: Bucketing Pattern**
```javascript
// DON'T: Store all sensor readings in one document
{
  sensorId: "sensor_ABC",
  readings: [/* millions of readings */]
}

// DO: Bucket by time period
{
  _id: "sensor_ABC_2026-01-27",
  sensorId: "sensor_ABC",
  date: ISODate("2026-01-27"),
  readings: [
    { time: "00:00:15", temp: 72 },
    { time: "00:01:15", temp: 73 },
    // ... one day's worth (~8640 readings at 10s intervals)
  ]
}
```

**Strategy 3: GridFS for Large Files**
```javascript
// For files > 16MB, use GridFS
// GridFS chunks files into 255KB pieces

// Store file metadata
{
  _id: ObjectId("..."),
  filename: "video.mp4",
  length: 50000000,  // 50MB
  chunkSize: 261120,
  uploadDate: ISODate("...")
}

// Chunks stored separately
{ files_id: ObjectId("..."), n: 0, data: Binary("...") }
{ files_id: ObjectId("..."), n: 1, data: Binary("...") }
// ... many chunks
```

**Strategy 4: Subset Pattern**
```javascript
// Store summary in main document, details in separate collection
{
  _id: "user123",
  name: "Alice",
  orderSummary: {
    totalOrders: 523,
    totalSpent: 15234.50,
    lastOrderDate: ISODate("2026-01-20")
  }
}

// Full order details in separate collection
// orders collection with userId reference
```

### Atomicity at the Document Level

**Single Document Atomicity:**

MongoDB guarantees that operations on a single document are atomic:

```javascript
// This entire update is atomic
db.accounts.updateOne(
  { _id: "account123" },
  {
    $set: { lastModified: new Date() },
    $inc: { balance: -100 },
    $push: { transactions: {
      type: "withdrawal",
      amount: 100,
      date: new Date()
    }}
  }
)
// All changes succeed together or all fail together
```

**What Atomicity Guarantees:**
- All modifications to a document occur together
- No partial updates are visible to other operations
- Concurrent operations see consistent document state
- Document is never in an inconsistent state

**Example: Transfer Money**
```javascript
// ATOMIC: Update account balance and log transaction
db.accounts.updateOne(
  { _id: "account123" },
  {
    $inc: { balance: -100 },
    $push: {
      transactions: {
        type: "transfer",
        amount: -100,
        to: "account456",
        timestamp: new Date()
      }
    }
  }
)
```

### Multi-Document Atomicity (Transactions)

**Without Transactions (No Atomicity Across Documents):**
```javascript
// PROBLEM: Not atomic across documents
// If second operation fails, first is already committed

// Deduct from account 1
await db.accounts.updateOne(
  { _id: "account123" },
  { $inc: { balance: -100 } }
)

// Add to account 2
await db.accounts.updateOne(
  { _id: "account456" },
  { $inc: { balance: 100 } }
)
// If this fails, money is lost!
```

**With Transactions (ACID Across Documents):**
```javascript
// SOLUTION: Use multi-document transactions
const session = client.startSession();

try {
  await session.withTransaction(async () => {
    // Both operations succeed or both fail
    await db.accounts.updateOne(
      { _id: "account123" },
      { $inc: { balance: -100 } },
      { session }
    );
    
    await db.accounts.updateOne(
      { _id: "account456" },
      { $inc: { balance: 100 } },
      { session }
    );
  });
  
  console.log("Transfer successful");
} catch (error) {
  console.log("Transfer failed, rolled back");
} finally {
  await session.endSession();
}
```

**When to Use Transactions:**
- Financial operations (transfers, payments)
- Multi-step workflows that must complete together
- Operations affecting multiple documents that must stay consistent
- When you need rollback capability

**When NOT to Use Transactions:**
- Single document operations (already atomic)
- Read-only operations
- Operations that can tolerate eventual consistency
- High-throughput write scenarios (transactions have overhead)

### Atomicity Best Practices

**1. Design Documents for Atomicity:**
```javascript
// GOOD: Related data in one document
{
  _id: "order123",
  items: [
    { product: "Widget", quantity: 2, price: 9.99 }
  ],
  subtotal: 19.98,
  tax: 1.60,
  total: 21.58,
  status: "pending"
}
// All fields updated atomically
```

**2. Use $set, $inc, $push Atomically:**
```javascript
// Multiple operations in one update
db.products.updateOne(
  { _id: "prod123" },
  {
    $inc: { quantity: -1, sold: 1 },
    $push: { purchases: { date: new Date(), buyer: "user123" } },
    $set: { lastSoldDate: new Date() }
  }
)
```

**3. Avoid Multi-Document Transactions When Possible:**
```javascript
// Instead of transaction across 2 docs:
// Document 1: User balance
// Document 2: Transaction log

// BETTER: Embed transaction log in user doc
{
  _id: "user123",
  balance: 500,
  recentTransactions: [
    { date: ISODate("..."), amount: -100, type: "withdrawal" }
  ]
}
```

**4. Use Transactions Only When Necessary:**
```javascript
// Transactions have performance cost
// Use for critical consistency requirements only

// NEED transaction: Money transfer
// DON'T NEED transaction: Updating user preferences
```

### Checking Document Size

```javascript
// Check document size
const doc = db.users.findOne({ _id: "user123" });
const size = Object.bsonsize(doc);
console.log(`Document size: ${size} bytes (${(size/1024/1024).toFixed(2)} MB)`);

// Find large documents
db.collection.find({
  $where: "Object.bsonsize(this) > 10000000"  // > 10MB
})
```

### Performance Implications

**Small Documents (< 1KB):**
- Fast reads and writes
- Efficient memory usage
- Good cache utilization
- May require more references

**Medium Documents (1KB - 100KB):**
- Good balance for most use cases
- Reasonable performance
- Optimal for embedding related data

**Large Documents (100KB - 16MB):**
- Slower reads and writes
- Higher memory consumption
- Network transfer overhead
- May impact working set size
- Consider breaking into smaller documents
