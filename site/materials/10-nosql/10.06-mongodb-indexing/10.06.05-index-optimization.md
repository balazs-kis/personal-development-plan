## Learning Objectives

By the end of this lesson, you will be able to:
- Identify and remove redundant or unused indexes
- Balance index benefits against write performance costs
- Use MongoDB Atlas Performance Advisor
- Apply best practices for index maintenance
- Optimize indexes for production workloads

---

## Introduction

Creating too many indexes or the wrong indexes can harm performance as much as having too few. Each index adds storage overhead and slows down writes. Unused indexes waste resources. Over time, application query patterns change, making some indexes obsolete. This lesson teaches you to maintain a lean, effective index strategy: identifying redundant indexes, monitoring index usage, balancing read and write performance, and using tools like Performance Advisor to continuously optimize your database.

## Key Concepts Summary

### Index Usage Statistics

**Monitoring with $indexStats:**

```javascript
db.orders.aggregate([{ $indexStats: {} }])
```

**Output:**
```javascript
[
  {
    name: "_id_",
    key: { _id: 1 },
    host: "server1:27017",
    accesses: {
      ops: 125000,              // Operations using this index
      since: ISODate("2026-01-01")
    }
  },
  {
    name: "customerId_1_orderDate_-1",
    key: { customerId: 1, orderDate: -1 },
    accesses: {
      ops: 98500,
      since: ISODate("2026-01-01")
    }
  },
  {
    name: "status_1",
    key: { status: 1 },
    accesses: {
      ops: 0,                   // ❌ Never used!
      since: ISODate("2026-01-01")
    }
  }
]
```

**Finding Unused Indexes:**
```javascript
db.orders.aggregate([
  { $indexStats: {} },
  { $match: { "accesses.ops": 0 } },
  { $project: { name: 1, key: 1 } }
])

// Output shows indexes with zero operations
```

### Identifying Redundant Indexes

**Redundancy Types:**

**1. Prefix Redundancy:**
```javascript
// Redundant
db.collection.createIndex({ a: 1 })         // ❌ Redundant
db.collection.createIndex({ a: 1, b: 1 })   // ✅ Keep this

// Explanation: {a:1,b:1} supports queries on {a:1}
// The single-field index is unnecessary
```

**2. Reverse Redundancy:**
```javascript
// Redundant
db.collection.createIndex({ date: 1 })      // ❌ Redundant
db.collection.createIndex({ date: -1 })     // ✅ Keep one

// MongoDB can use either direction efficiently for single-field
```

**3. Overlapping Compound Indexes:**
```javascript
// Potentially redundant
db.orders.createIndex({ customerId: 1, orderDate: -1 })
db.orders.createIndex({ customerId: 1, status: 1 })

// Both support queries on {customerId}
// Evaluate if both are needed based on query patterns
```

### Write Performance Impact

**How Indexes Affect Writes:**

Each index must be updated for every write operation:

```javascript
// Collection with 5 indexes
db.orders.insertOne({ ... })

// Behind the scenes:
// 1. Insert document
// 2. Update _id index
// 3. Update index 1
// 4. Update index 2
// 5. Update index 3
// 6. Update index 4
// Total: 1 document write + 5 index writes
```

**Measuring Impact:**

**Before removing index:**
```javascript
// Run write workload
for (let i = 0; i < 1000; i++) {
  db.orders.insertOne({ customerId: "cust" + i, total: 100 })
}
// Time: 2.5 seconds
```

**After removing unused index:**
```javascript
db.orders.dropIndex("unused_index_1")

// Run same workload
for (let i = 0; i < 1000; i++) {
  db.orders.insertOne({ customerId: "cust" + i, total: 100 })
}
// Time: 2.1 seconds (16% faster)
```

### Atlas Performance Advisor

MongoDB Atlas automatically monitors slow queries and suggests indexes.

**How It Works:**
1. Monitors queries > 100ms
2. Analyzes query shapes and patterns
3. Suggests indexes ranked by impact
4. Shows which indexes to drop

**Accessing Performance Advisor:**
- MongoDB Atlas Dashboard
- Navigate to cluster
- Click "Performance Advisor" tab

**Index Ranking Criteria:**

Performance Advisor ranks suggestions by:
1. **Execution time** - Slower queries prioritized
2. **Frequency** - Often-run queries prioritized
3. **Documents examined** - High scan-to-return ratios prioritized
4. **Impact score** - Estimated improvement

**Example Recommendation:**
```javascript
{
  index: { customerId: 1, orderDate: -1 },
  impact: "High",
  collections: ["orders"],
  queryPattern: {
    filter: { customerId: <string> },
    sort: { orderDate: -1 }
  },
  avgExecutionTime: "1250ms",
  frequency: "245 queries/hour",
  recommendedAction: "Create Index"
}
```

### Index Build Strategies

**Foreground Build (Default):**
```javascript
db.collection.createIndex({ field: 1 })
```
- Faster build
- Blocks all operations on collection
- Use for small collections or during maintenance windows

**Background Build:**
```javascript
db.collection.createIndex({ field: 1 }, { background: true })
```
- ⚠️ Deprecated in MongoDB 4.2+
- Now all builds use "hybrid" approach
- Non-blocking on primaries

**Building on Secondary:**
```javascript
// Connect to secondary
mongo --host secondary.example.com

// Build index on secondary
db.collection.createIndex({ field: 1 })

// Repeat for each secondary, then primary
```
- Minimizes impact on production reads/writes
- Time-consuming but safest for large indexes

### Index Maintenance Best Practices

**1. Review Indexes Quarterly:**
```javascript
// Schedule regular index audits
// - Check $indexStats for unused indexes
// - Review query patterns
// - Remove redundant indexes
```

**2. Monitor Index Size:**
```javascript
db.orders.stats().indexSizes
```

**Output:**
```javascript
{
  "_id_": 10485760,              // 10 MB
  "customerId_1": 52428800,      // 50 MB
  "status_1": 5242880,           // 5 MB
  "orderDate_-1": 31457280       // 30 MB
}
// Total index size: 95 MB
```

**Index size considerations:**
- Indexes compete for RAM with working set
- Large indexes may not fit in memory
- Prioritize indexes for critical queries

**3. Test Index Changes in Staging:**
```javascript
// Never drop indexes in production without testing
// 1. Drop index in staging
// 2. Run query workload
// 3. Verify performance acceptable
// 4. Then drop in production
```

**4. Use Hidden Indexes (MongoDB 4.4+):**
```javascript
// Hide index instead of dropping
db.collection.hideIndex("index_name")

// MongoDB won't use it, but it stays up-to-date
// If performance degrades, unhide quickly
db.collection.unhideIndex("index_name")

// After verifying, drop permanently
db.collection.dropIndex("index_name")
```

### Balancing Read and Write Performance

**Scenarios:**

**Read-Heavy Application:**
- More indexes acceptable
- Optimize for query performance
- Index even moderately-used queries

**Write-Heavy Application:**
- Minimize indexes
- Only index critical queries
- Consider batching writes

**Balanced Workload:**
- Index high-frequency queries
- Remove indexes with low usage
- Monitor write latency impact

**Example Decision Framework:**

```javascript
// Query: Find recent orders by customer
db.orders.find({ customerId: "cust123" }).sort({ orderDate: -1 })

// Query frequency: 1000 queries/hour
// Write frequency: 100 inserts/hour
// Ratio: 10:1 (read-heavy)

// Decision: ✅ Create index
db.orders.createIndex({ customerId: 1, orderDate: -1 })
```

```javascript
// Query: Find orders by status
db.orders.find({ status: "pending" })

// Query frequency: 50 queries/hour
// Write frequency: 1000 inserts/hour
// Ratio: 1:20 (write-heavy)
// Status has low cardinality (3 values)

// Decision: ❌ Don't index
// Writes > reads, and status is not selective
```

### Optimization Checklist

**Before Going to Production:**

- [ ] Run explain() on all critical queries
- [ ] Verify indexes exist for common filters
- [ ] Check for compound indexes supporting sorts
- [ ] Identify and implement covered queries
- [ ] Remove redundant indexes
- [ ] Test write performance with full index set
- [ ] Document index strategy and rationale

**Ongoing Maintenance:**

- [ ] Monitor slow queries (> 100ms)
- [ ] Review $indexStats monthly
- [ ] Check Performance Advisor recommendations
- [ ] Audit indexes quarterly
- [ ] Drop unused indexes
- [ ] Update indexes when query patterns change

### Common Optimization Patterns

**Pattern 1: Convert to Covered Query**

**Before:**
```javascript
db.users.find({ country: "USA" }, { email: 1 })
// Uses: { country: 1 }
// Stage: IXSCAN → FETCH
```

**After:**
```javascript
db.users.createIndex({ country: 1, email: 1 })
db.users.find({ country: "USA" }, { _id: 0, email: 1 })
// Uses: { country: 1, email: 1 }
// Stage: PROJECTION_COVERED (no FETCH)
```

**Pattern 2: Avoid In-Memory Sort**

**Before:**
```javascript
db.orders.find({ status: "shipped" }).sort({ orderDate: -1 })
// Uses: { status: 1 }
// Stage: IXSCAN → FETCH → SORT (in-memory)
```

**After:**
```javascript
db.orders.createIndex({ status: 1, orderDate: -1 })
// Uses: { status: 1, orderDate: -1 }
// Stage: IXSCAN → FETCH (no sort needed)
```

**Pattern 3: Reduce Index Count**

**Before:**
```javascript
// 3 separate indexes
db.products.createIndex({ category: 1 })
db.products.createIndex({ price: 1 })
db.products.createIndex({ brand: 1 })

// Query patterns:
// - { category: "Electronics" }
// - { category: "Electronics", price: { $gt: 100 } }
// - { category: "Electronics", brand: "Samsung" }
```

**After:**
```javascript
// 1 compound index supports all
db.products.createIndex({ category: 1, price: 1, brand: 1 })

// Supports all three query patterns via prefixes
// Reduces write overhead by 67%
```
