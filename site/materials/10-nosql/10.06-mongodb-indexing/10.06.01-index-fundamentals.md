# Lesson 1: Index Fundamentals and Types

## Learning Objectives

- Understand how indexes improve query performance
- Identify different MongoDB index types and their use cases
- Create single-field and basic compound indexes
- Recognize the trade-offs of using indexes

---

## Introduction

Without indexes, MongoDB must perform collection scans—examining every document to find matches. This becomes prohibitively slow as collections grow. Indexes are specialized data structures (B-trees) that store a small portion of the collection's data in an easily traversable form. By creating indexes on frequently queried fields, you can reduce query execution time from seconds to milliseconds. However, indexes aren't free: they consume storage space and slow down write operations. Understanding index fundamentals helps you make informed decisions about which fields to index.

## Key Concepts Summary

### What Are Indexes?

Indexes are data structures that optimize data retrieval by maintaining an ordered representation of field values with pointers to documents:

**Without Index:**
```javascript
// MongoDB scans all documents
db.users.find({ email: "alice@example.com" })
// Examines: 1,000,000 documents
// Time: 2.5 seconds
```

**With Index:**
```javascript
// Create index
db.users.createIndex({ email: 1 })

// Same query now uses index
db.users.find({ email: "alice@example.com" })
// Examines: 1 document
// Time: 5 milliseconds
```

### How Indexes Work

**B-Tree Structure:**
MongoDB uses B-tree indexes that:
- Store field values in sorted order
- Maintain pointers to document locations
- Allow efficient lookups, range queries, and sorts
- Support prefix matching for compound indexes

**Index Entry Example:**
```
Index on { email: 1 }:
"alice@example.com" → DocumentID: 12345
"bob@example.com"   → DocumentID: 12346
"charlie@example.com" → DocumentID: 12347
```

### Creating Indexes

**Basic Syntax:**
```javascript
db.collection.createIndex(
  { <field>: <type> },
  { <options> }
)
```

**Type values:**
- `1` - Ascending order
- `-1` - Descending order
- `"text"` - Text index
- `"2dsphere"` - Geospatial index
- `"hashed"` - Hashed index

**Examples:**

**1. Single-field index (ascending):**
```javascript
db.products.createIndex({ price: 1 })
```

**2. Single-field index (descending):**
```javascript
db.orders.createIndex({ orderDate: -1 })
```

**3. Index with name:**
```javascript
db.users.createIndex(
  { email: 1 },
  { name: "email_index" }
)
```

**4. Unique index:**
```javascript
db.users.createIndex(
  { username: 1 },
  { unique: true }
)
```

### MongoDB Index Types

**1. Single-Field Index**

Index on one field:
```javascript
db.products.createIndex({ name: 1 })

// Supports queries like:
db.products.find({ name: "Laptop" })
db.products.find({ name: { $in: ["Laptop", "Desktop"] } })
db.products.find({ name: /^Lap/ })  // Prefix match
```

**2. Compound Index**

Index on multiple fields:
```javascript
db.orders.createIndex({ customerId: 1, orderDate: -1 })

// Supports queries on:
// - customerId alone
// - customerId + orderDate
// Does NOT support: orderDate alone
```

**3. Multikey Index**

Automatically created when indexing array fields:
```javascript
// Document with array field
{
  _id: 1,
  tags: ["mongodb", "database", "nosql"]
}

// Create index
db.posts.createIndex({ tags: 1 })

// Query
db.posts.find({ tags: "mongodb" })
// Index creates entries: "mongodb" → doc1, "database" → doc1, "nosql" → doc1
```

**4. Text Index**

For full-text search:
```javascript
db.articles.createIndex({ content: "text" })

// Query
db.articles.find({ $text: { $search: "mongodb indexing" } })
```

**5. Hashed Index**

For sharding and hash-based distribution:
```javascript
db.users.createIndex({ _id: "hashed" })
```

**6. Geospatial Index**

For location queries:
```javascript
db.places.createIndex({ location: "2dsphere" })

// Query places near coordinates
db.places.find({
  location: {
    $near: {
      $geometry: { type: "Point", coordinates: [-73.9667, 40.78] },
      $maxDistance: 1000  // meters
    }
  }
})
```

### Default _id Index

Every collection automatically has an index on `_id`:
```javascript
// Automatically created
{ _id: 1 }

// Cannot be dropped
// Ensures uniqueness
// Supports efficient _id queries
```

### Index Direction (1 vs -1)

**For single-field indexes:** Direction doesn't matter for queries, but affects sort performance:

```javascript
// Index
db.products.createIndex({ price: 1 })

// Both queries use the index efficiently
db.products.find({ price: { $gt: 100 } })  // Ascending
db.products.find({ price: { $gt: 100 } }).sort({ price: -1 })  // Descending
```

**For compound indexes:** Direction matters more (covered in next lesson).

### Viewing Indexes

**List all indexes:**
```javascript
db.collection.getIndexes()
```

**Output:**
```javascript
[
  {
    v: 2,
    key: { _id: 1 },
    name: "_id_"
  },
  {
    v: 2,
    key: { email: 1 },
    name: "email_1",
    unique: true
  }
]
```

### Dropping Indexes

**Drop specific index:**
```javascript
// By name
db.collection.dropIndex("email_1")

// By key
db.collection.dropIndex({ email: 1 })
```

**Drop all indexes (except _id):**
```javascript
db.collection.dropIndexes()
```

### Index Trade-offs

**Benefits:**
- ✅ Dramatically faster queries
- ✅ Efficient sorting
- ✅ Support for unique constraints
- ✅ Enable covered queries

**Costs:**
- ❌ Storage overhead (each index copies field data)
- ❌ Slower write operations (inserts, updates, deletes)
- ❌ Memory usage (indexes compete for RAM with working set)

**Guidelines:**
- Maximum 64 indexes per collection
- Each index adds 5-10% write overhead
- Index only fields you actively query
- Remove unused indexes

### When to Create Indexes

**Create indexes when:**
- Queries filter on specific fields frequently
- Queries sort on specific fields
- Queries need unique values enforced
- Query performance is critical

**Avoid indexes when:**
- Field has high write-to-read ratio
- Collection is small (< 1000 documents)
- Queries already run fast enough
- Field has low cardinality (few unique values)

**Example: Low cardinality (bad for indexing):**
```javascript
// Status field has only 3 values
db.orders.distinct("status")
// ["pending", "shipped", "delivered"]

// Index doesn't help much
db.orders.createIndex({ status: 1 })  // ❌ Usually not beneficial

// Each index scan returns ~33% of documents anyway
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Given a `customers` collection with documents like:
```javascript
{
  _id: ObjectId("..."),
  email: "alice@example.com",
  firstName: "Alice",
  lastName: "Johnson",
  accountCreated: ISODate("2025-05-15"),
  status: "active",
  purchases: 12,
  totalSpent: 1547.50
}
```

Your application has these query patterns:

1. **Find customer by email** (very frequent)
2. **Find customers by status** (frequent)
3. **List recent customers sorted by accountCreated** (frequent)
4. **Find high-value customers (totalSpent > $1000)** (occasional)

**Tasks:**
1. Which fields should definitely have indexes?
2. What type of index for each?
3. Would you index `status` despite low cardinality? Why or why not?
4. Write the `createIndex()` commands
5. How would you check if indexes are being used?
