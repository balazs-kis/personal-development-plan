## Introduction

The Just-In-Time (JIT) compiler is at the heart of .NET runtime performance. Modern .NET uses sophisticated techniques like tiered compilation and Dynamic PGO to balance startup time with steady-state performance. Understanding how the JIT works helps you write better code and make informed decisions about deployment strategies.

## Key Concepts Summary

### How JIT Compilation Works

The .NET Just-In-Time compiler translates Intermediate Language (IL) code to native machine code at runtime:

```
IL Code → JIT Compiler → Native Machine Code → Execution
```

**Traditional JIT Approach:**
- Method is compiled on first call
- Single compilation with full optimizations
- Trade-off: slower startup OR slower steady-state performance

### Tiered Compilation

Tiered compilation allows methods to be compiled multiple times with different optimization levels and hot-swapped at runtime:

```
Tier 0 (Quick JIT):
├─ Minimal optimizations
├─ Fast compilation time
└─ Prioritizes startup performance

       ↓ (Method becomes hot)

Tier 1 (Optimized JIT):
├─ Full optimizations
├─ Slower compilation time
└─ Prioritizes steady-state performance
```

**Benefits:**
- **Fast startup** - Quick JIT gets your application running quickly
- **Fast steady-state** - Optimized JIT replaces hot methods with better code
- **No compromise** - You get both fast startup AND fast runtime

### The Compilation Tiers

#### Tier 0: Quick JIT or ReadyToRun (R2R)

**Quick JIT:**
- Generates code quickly with minimal optimizations
- Used when method is first called
- Lower memory usage for rarely-called methods

**ReadyToRun (R2R):**
- Pre-compiled native code included in the assembly
- Loads even faster than Quick JIT
- May be less optimized than full JIT
- Can fall back to JIT if needed

#### Tier 1: Optimized JIT

**Characteristics:**
- Full optimization pipeline
- Inlining, loop optimizations, register allocation
- Uses profiling data when available (PGO)
- Compiled in background thread

**Promotion Criteria:**
- Method called frequently (hot method)
- Method contains loops that run many times
- Configurable thresholds

### Profile Guided Optimization (PGO)

PGO uses runtime behavior data to guide optimization decisions:

#### Static PGO (Traditional)
```
1. Training Run → Collect Profile Data
2. Optimized Build → Use Profile Data for Compilation
```

**Best for:**
- Libraries and frameworks
- Startup performance optimization
- Testable, predictable scenarios

#### Dynamic PGO (Modern .NET)
```
Runtime Behavior → Continuous Profiling → JIT Optimization
```

**Best for:**
- Current application behavior
- Real production workloads
- Adapting to runtime patterns

**Enabled by default in .NET 8+** when tiered compilation is on.

### Configuration Options

#### Enable/Disable Tiered Compilation

**Via Environment Variable:**
```bash
# Enable (default in .NET Core 3.0+)
DOTNET_TieredCompilation=1

# Disable
DOTNET_TieredCompilation=0
```

**Via runtimeconfig.json:**
```json
{
  "runtimeOptions": {
    "configProperties": {
      "System.Runtime.TieredCompilation": true
    }
  }
}
```

**Via MSBuild:**
```xml
<PropertyGroup>
  <TieredCompilation>true</TieredCompilation>
</PropertyGroup>
```

#### Quick JIT Configuration

**Enable/Disable Quick JIT:**
```bash
# Enable Quick JIT (default)
DOTNET_TC_QuickJit=1

# Disable Quick JIT (use only R2R or full JIT)
DOTNET_TC_QuickJit=0
```

**Trade-offs:**
- Disabling Quick JIT improves steady-state performance
- But increases startup time and memory usage

#### Dynamic PGO Configuration

```bash
# Enable Dynamic PGO (default in .NET 8+)
DOTNET_TieredPGO=1

# Disable Dynamic PGO
DOTNET_TieredPGO=0
```

### When Code Gets Optimized

**Promotion Triggers:**
1. **Call count threshold** - Method called ~30 times (configurable)
2. **Loop iteration threshold** - Loop runs many times in a single call
3. **On-Stack Replacement (OSR)** - Hot loops replaced while still running

**OSR Example:**
```csharp
// Method starts in Tier 0
for (int i = 0; i < 1_000_000; i++)
{
    // After many iterations, JIT compiles optimized version
    // and replaces the running code mid-loop (OSR)
    DoWork();
}
```

### ReadyToRun (R2R) Integration

ReadyToRun works alongside tiered compilation:

**R2R as Tier 0:**
- Pre-compiled code serves as Tier 0
- Faster than Quick JIT (no compilation needed)
- Can still be replaced by optimized JIT

**Publishing with R2R:**
```bash
dotnet publish -c Release -r win-x64 /p:PublishReadyToRun=true
```

**Benefits:**
- Faster startup (no Tier 0 compilation)
- Smaller JIT memory footprint
- Better for AOT-constrained environments

### Performance Characteristics

| Tier | Compilation Speed | Code Quality | Memory Usage | When Used |
|------|------------------|--------------|--------------|-----------|
| **R2R** | Pre-compiled | Good | Low | Startup (if available) |
| **Tier 0 (Quick)** | Very Fast | Basic | Low | First call |
| **Tier 1 (Optimized)** | Slow | Excellent | Higher | Hot methods |
| **Tier 1 + PGO** | Slow | Best | Higher | Hot methods with profiling |

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

**Experiment with Tiered Compilation Settings**

1. Create a simple console application with a computational method:

```csharp
public class Program
{
    static void Main()
    {
        for (int i = 0; i < 1000; i++)
        {
            ComputeSum();
        }
    }

    static long ComputeSum()
    {
        long sum = 0;
        for (int i = 0; i < 100_000; i++)
        {
            sum += i;
        }
        return sum;
    }
}
```

2. Run it with different settings and observe behavior:

```bash
# Default (tiered compilation enabled)
dotnet run -c Release

# Disable tiered compilation
$env:DOTNET_TieredCompilation=0
dotnet run -c Release

# Disable Quick JIT only
$env:DOTNET_TieredCompilation=1
$env:DOTNET_TC_QuickJit=0
dotnet run -c Release
```

3. Consider: How might the performance characteristics differ? Which setting would you use for a long-running server vs. a short-lived CLI tool?
