## Introduction

Assembly loading is fundamental to how .NET applications discover and load code. Modern .NET (.NET Core and later) introduced AssemblyLoadContext as a replacement for AppDomain's isolation capabilities, enabling powerful scenarios like plugin systems, version isolation, and dynamic code loading. Understanding AssemblyLoadContext is essential for building extensible applications.

## Key Concepts Summary

### Assembly Loading in Modern .NET

**.NET Framework Approach (Legacy):**
```
AppDomain → Assembly Loading → Limited Unloading
├─ Multiple AppDomains per process
├─ Security boundaries
└─ Heavy-weight isolation
```

**.NET Core/.NET 5+ Approach:**
```
AssemblyLoadContext → Assembly Loading → Dynamic Unloading
├─ Lightweight isolation
├─ No security boundaries
└─ Designed for plugin scenarios
```

### What is AssemblyLoadContext?

AssemblyLoadContext (ALC) is the runtime's provider for locating, loading, and caching managed assemblies.

**Core Responsibilities:**
- Locate assemblies based on assembly names
- Load assemblies from disk or memory
- Cache loaded assemblies
- Resolve dependencies
- Support unloading of assemblies

**Key Difference from AppDomain:**
| Feature | AppDomain (.NET Framework) | AssemblyLoadContext (.NET Core+) |
|---------|---------------------------|----------------------------------|
| **Security** | Security boundary | No security features |
| **Weight** | Heavy (process-like) | Lightweight |
| **Unloading** | Full domain unload | Cooperative unload |
| **Isolation** | Full isolation | Assembly-level isolation |
| **Use Case** | Security + Isolation | Versioning + Plugins |

### The Default AssemblyLoadContext

Every .NET application has a default AssemblyLoadContext:

```csharp
// The default ALC that loads your application
AssemblyLoadContext.Default
```

**Characteristics:**
- Loads the application's main assemblies
- **Cannot be unloaded** (lifetime = application lifetime)
- **One version per assembly** - cannot load multiple versions of the same assembly
- Automatically resolves dependencies

**Version Conflict Problem:**
```csharp
// Both plugins need different versions of Newtonsoft.Json
// Default ALC can only hold ONE version
Plugin A → Newtonsoft.Json 12.0.0  ❌ Conflict!
Plugin B → Newtonsoft.Json 13.0.0  ❌
```

### Creating Custom AssemblyLoadContexts

Custom ALCs solve version conflicts and enable isolation:

```csharp
// Basic custom AssemblyLoadContext
public class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath) 
        : base(isCollectible: true)  // Allow unloading
    {
        _resolver = new AssemblyDependencyResolver(pluginPath);
    }

    protected override Assembly? Load(AssemblyName assemblyName)
    {
        // Resolve the assembly path
        string? assemblyPath = _resolver.ResolveAssemblyToPath(assemblyName);
        
        if (assemblyPath != null)
        {
            return LoadFromAssemblyPath(assemblyPath);
        }

        // Fall back to default context
        return null;
    }

    protected override IntPtr LoadUnmanagedDll(string unmanagedDllName)
    {
        // Resolve native dependencies
        string? libraryPath = _resolver.ResolveUnmanagedDllToPath(unmanagedDllName);
        
        if (libraryPath != null)
        {
            return LoadUnmanagedDllFromPath(libraryPath);
        }

        return IntPtr.Zero;
    }
}
```

### Using AssemblyDependencyResolver

AssemblyDependencyResolver reads `.deps.json` files to resolve dependencies correctly:

```csharp
// Create resolver for a plugin
var resolver = new AssemblyDependencyResolver(pluginPath);

// Resolves managed assemblies
string? assemblyPath = resolver.ResolveAssemblyToPath(assemblyName);

// Resolves native libraries
string? nativePath = resolver.ResolveUnmanagedDllToPath(dllName);
```

**Why It's Important:**
- Reads the plugin's dependency graph from `.deps.json`
- Respects the plugin's dependencies (not host's)
- Handles platform-specific native libraries
- Understands NuGet package structure

### Loading Assemblies into Custom Contexts

```csharp
// Create custom context
var context = new PluginLoadContext(pluginPath);

// Load the plugin assembly
Assembly pluginAssembly = context.LoadFromAssemblyPath(pluginPath);

// Get types and create instances
Type pluginType = pluginAssembly.GetType("MyPlugin.PluginClass");
IPlugin plugin = (IPlugin)Activator.CreateInstance(pluginType);

// Use the plugin
plugin.Execute();
```

### Assembly Isolation and Shared Dependencies

**Critical Limitation:** Static state is **NOT automatically isolated**

```csharp
// Problem: Shared dependency in Default ALC
Default ALC:     Logger v2.0.0 (static state shared!)
Plugin A ALC:    Logger v2.0.0 (references Default ALC version)
Plugin B ALC:    Logger v2.0.0 (references Default ALC version)
```

**Solution: Explicit Isolation**
```csharp
// Load ALL dependencies into plugin ALC
Plugin A ALC:    Logger v2.0.0 (isolated static state)
Plugin B ALC:    Logger v2.0.0 (isolated static state)
```

**Implementation Pattern:**
```csharp
protected override Assembly? Load(AssemblyName assemblyName)
{
    // Always try to load from plugin path first
    string? assemblyPath = _resolver.ResolveAssemblyToPath(assemblyName);
    
    if (assemblyPath != null)
    {
        // Load in THIS context (isolated)
        return LoadFromAssemblyPath(assemblyPath);
    }

    // Only fall back to default for framework assemblies
    if (IsFrameworkAssembly(assemblyName))
    {
        return null; // Let default ALC handle it
    }

    // Don't share third-party dependencies
    return null;
}
```

### Unloading AssemblyLoadContexts

Unloading allows releasing memory and resources:

```csharp
// Create collectible context
var context = new PluginLoadContext(pluginPath);

// Load and use assemblies
Assembly assembly = context.LoadFromAssemblyPath(pluginPath);
// ... use the assembly ...

// Unload the context
context.Unload();

// Trigger garbage collection to free memory
GC.Collect();
GC.WaitForPendingFinalizers();
```

**Important Considerations:**
1. **Cooperative unloading** - unlike AppDomain, not forced
2. **All references must be released** - any live references prevent unloading
3. **WeakReferences** - use to detect when unload completes
4. **Assembly.Load() location matters** - where you load affects which ALC owns it

**Debugging Unload Issues:**
```csharp
WeakReference alcWeakRef = new WeakReference(context);

context.Unload();
context = null;

// Try to collect
for (int i = 0; alcWeakRef.IsAlive && i < 10; i++)
{
    GC.Collect();
    GC.WaitForPendingFinalizers();
}

if (alcWeakRef.IsAlive)
{
    Console.WriteLine("Context still alive - there are lingering references!");
}
```

### Common Plugin Architecture Patterns

#### Pattern 1: Simple Plugin Interface

```csharp
// Shared contract (in host and plugins)
public interface IPlugin
{
    string Name { get; }
    void Execute();
}

// Host loads plugins
foreach (string pluginPath in pluginPaths)
{
    var context = new PluginLoadContext(pluginPath);
    Assembly assembly = context.LoadFromAssemblyPath(pluginPath);
    
    foreach (Type type in assembly.GetTypes())
    {
        if (typeof(IPlugin).IsAssignableFrom(type))
        {
            IPlugin plugin = (IPlugin)Activator.CreateInstance(type);
            plugin.Execute();
        }
    }
}
```

#### Pattern 2: Bridge Module (Isolation Boundary)

```
Root Module (loaded in separate ALC)
    ↓
Bridge Layer (minimal interface)
    ↓
Dependency Logic (isolated in ALC)
```

**Benefits:**
- Prevents dependency leakage
- Clear API boundary
- Dependencies never escape to default ALC

#### Pattern 3: Engine Project (Resolver + ALC)

```
PowerShell/Host Module
    ↓
Engine Project (custom ALC + resolver)
    ↓
Dependencies (loaded in engine's ALC)
```

**Benefits:**
- Most robust isolation
- Complete control over loading
- Handles complex dependency graphs

### Security Considerations

**Important:** AssemblyLoadContext does **NOT** provide security boundaries.

```
❌ Do NOT use ALC for:
   - Running untrusted code
   - Security isolation
   - Sandboxing

✅ Use ALC for:
   - Version isolation
   - Plugin architectures
   - Dynamic code loading/unloading
   - Dependency management
```

**For untrusted code, use:**
- Separate processes
- Containers (Docker)
- Virtual machines
- OS-level security features

### Debugging and Diagnostics

**Viewing Loaded Assemblies:**
```csharp
// Get all AssemblyLoadContexts
foreach (var alc in AssemblyLoadContext.All)
{
    Console.WriteLine($"ALC: {alc.Name}");
    
    foreach (var assembly in alc.Assemblies)
    {
        Console.WriteLine($"  - {assembly.FullName}");
    }
}
```

**Finding Which ALC Loaded an Assembly:**
```csharp
Assembly assembly = typeof(MyType).Assembly;
AssemblyLoadContext alc = AssemblyLoadContext.GetLoadContext(assembly);
Console.WriteLine($"Loaded in: {alc.Name}");
```
