## Introduction

Understanding how the .NET runtime manages memory under the hood is crucial for writing high-performance applications. While the garbage collector handles memory automatically, knowing how the managed heap works, how objects are allocated, and how the generational system optimizes collection helps you write code that works with the GC rather than against it.

## Key Concepts Summary

### The Managed Heap Structure

The .NET runtime manages memory through a managed heap within each process's virtual address space:

```
Process Virtual Memory
├─ Stack (value types, references, method frames)
└─ Managed Heap
   ├─ Small Object Heap (SOH)
   │  ├─ Generation 0 (youngest objects)
   │  ├─ Generation 1 (buffer between Gen 0 and Gen 2)
   │  └─ Generation 2 (long-lived objects)
   └─ Large Object Heap (LOH)
      └─ Objects ≥ 85,000 bytes
```

**Key Characteristics:**
- Memory allocation is extremely fast (nearly as fast as stack allocation)
- Newly allocated objects are stored contiguously
- Improves CPU cache locality and access patterns

### How Memory Allocation Works

**Allocation Process:**
```csharp
// When you create a new object
var person = new Person();

// Runtime does this (simplified):
1. Check available space in Generation 0
2. If enough space:
   - Allocate at next available address
   - Move pointer forward
   - Zero out memory
3. If not enough space:
   - Trigger Generation 0 collection
   - Retry allocation
```

**Why It's Fast:**
```
Traditional allocator (C/C++):
├─ Search free list
├─ Find suitable block
├─ Split block
├─ Update metadata
└─ Return pointer

.NET managed heap:
├─ Add size to pointer (one instruction)
└─ Return pointer
```

The managed heap maintains a simple pointer to the next available location. Allocating is just incrementing a pointer!

### The Generational Garbage Collection System

The GC uses a **three-generation hypothesis**: most objects die young.

```
Generation 0: Nursery for new objects
├─ Collected most frequently
├─ Most objects die here (90%+)
├─ Fast collection (small size)
└─ Survivors promoted to Gen 1

Generation 1: Buffer generation
├─ Objects that survived one collection
├─ Collected less frequently than Gen 0
├─ Still relatively small and fast
└─ Survivors promoted to Gen 2

Generation 2: Tenured/long-lived objects
├─ Objects that survived multiple collections
├─ Collected infrequently (expensive)
├─ Large size, slow collection
└─ Includes LOH (logically part of Gen 2)
```

### Generation Collection Behavior

**Collection Triggers:**
```
Gen 0 Collection:
├─ Happens when Gen 0 fills up
├─ Very frequent (milliseconds)
├─ Fast (< 1ms typically)
└─ Collects only Gen 0

Gen 1 Collection:
├─ Triggered when Gen 1 fills or by Gen 0 collection
├─ Collects Gen 0 + Gen 1
├─ Moderate frequency
└─ Fast (< 5ms typically)

Gen 2 Collection (Full GC):
├─ Triggered when Gen 2 fills or by explicit request
├─ Collects Gen 0 + Gen 1 + Gen 2
├─ Infrequent (seconds to minutes)
└─ Expensive (10-100ms+)
```

**Promotion Criteria:**
```csharp
// Object lifecycle
var obj = new MyClass();  // Born in Gen 0

// After Gen 0 collection
if (obj is still referenced)
{
    // Promoted to Gen 1
}

// After Gen 1 collection
if (obj is still referenced)
{
    // Promoted to Gen 2 (stays here)
}
```

### The Large Object Heap (LOH)

Objects larger than a threshold are allocated on a separate heap:

```
Small Object Heap (SOH):
├─ Objects < 85,000 bytes
├─ Compacted during collection (objects moved)
└─ Contiguous memory layout

Large Object Heap (LOH):
├─ Objects ≥ 85,000 bytes
├─ NOT compacted by default (expensive)
├─ Fragmentation possible
└─ Logically part of Generation 2
```

**Why 85,000 bytes?**
- Compacting large objects is expensive (copying memory)
- Moving large objects would cause significant GC pause times
- Trade-off: accept fragmentation to avoid compaction cost

**LOH Characteristics:**

| Aspect | Small Object Heap | Large Object Heap |
|--------|------------------|-------------------|
| **Size Threshold** | < 85KB | ≥ 85KB |
| **Compaction** | Yes (default) | No (default) |
| **Generation** | 0, 1, 2 | Always Gen 2 |
| **Collection** | Frequent (Gen 0/1) | Infrequent (Gen 2 only) |
| **Fragmentation** | None (compacted) | Possible |
| **Allocation Speed** | Very fast | Fast |

**Enabling LOH Compaction:**
```csharp
// Force LOH compaction (use sparingly)
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect();
```

### GC Collection Phases

When a collection happens, the GC goes through these phases:

```
1. Mark Phase
   ├─ Identify all reachable objects from roots
   ├─ Roots: stack variables, static fields, CPU registers
   └─ Mark objects as "alive"

2. Plan Phase (for compacting generations)
   ├─ Decide which objects to move
   ├─ Calculate new addresses
   └─ Determine gaps and relocation targets

3. Sweep Phase (for non-compacting areas like LOH)
   ├─ Free memory from unmarked objects
   └─ Add freed blocks to free list

4. Compact Phase (SOH only)
   ├─ Move live objects together
   ├─ Update all references
   └─ Eliminate fragmentation
```

### Memory Allocation Performance Patterns

**Good Patterns (GC-Friendly):**

```csharp
✅ Short-lived allocations (Gen 0)
// Allocate, use, and discard quickly
void ProcessRequest()
{
    var buffer = new byte[4096];  // Dies in Gen 0
    // ... process ...
} // buffer goes out of scope

✅ Long-lived allocations (Gen 2)
// Allocate once, keep forever
private static readonly Cache = new ConcurrentDictionary<string, Data>();

✅ Pooling (reuse instead of allocate)
// Use ArrayPool to avoid allocations
var buffer = ArrayPool<byte>.Shared.Rent(4096);
try
{
    // ... use buffer ...
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

**Bad Patterns (GC-Unfriendly):**

```csharp
❌ Mid-life objects (promoted but short-lived)
// Object survives Gen 0 but isn't truly long-lived
private List<TempData> cache;

void ProcessBatch()
{
    cache = new List<TempData>();
    // ... process ...
    // cache survives Gen 0, gets promoted to Gen 1
    // But then dies shortly after
} // Promoted to Gen 2, wasting memory

❌ Large temporary allocations
// Creates LOH pressure and Gen 2 collections
void ProcessLargeData()
{
    var hugeBuffer = new byte[100_000];  // LOH allocation!
    // ... use once and discard ...
} // Triggers Gen 2 collections

❌ Resurrection (finalizers keeping objects alive)
class BadResource
{
    ~BadResource()
    {
        // Finalizer causes object to survive one extra collection
        SomeStaticField = this;  // Resurrection!
    }
}
```

### Workstation vs Server GC

.NET provides two GC modes with different characteristics:

**Workstation GC (Default for apps):**
```
Characteristics:
├─ Lower memory usage
├─ Optimized for responsiveness
├─ Runs on same thread as application
└─ Better for client apps (desktop, mobile)

Pause times: Shorter, more frequent
Throughput: Lower
Memory: Conservative
```

**Server GC (Default for ASP.NET Core):**
```
Characteristics:
├─ Higher memory usage
├─ Optimized for throughput
├─ Dedicated thread per CPU core
└─ Better for server applications

Pause times: Longer, less frequent  
Throughput: Higher
Memory: Aggressive
```

**Configuration:**
```xml
<PropertyGroup>
  <!-- Enable Server GC -->
  <ServerGarbageCollection>true</ServerGarbageCollection>
  
  <!-- Enable Concurrent GC (background collection) -->
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
```

### Memory Pressure and GC Triggers

The GC tracks memory pressure to decide when to collect:

```csharp
// Inform GC about native memory allocations
GC.AddMemoryPressure(byteCount);  // Before allocating native memory
// ... use native memory ...
GC.RemoveMemoryPressure(byteCount);  // After freeing native memory
```

**Why This Matters:**
- GC only tracks managed memory
- If you allocate 1GB of native memory, GC doesn't know
- Without pressure hints, GC might not collect when it should

### Object Pinning and GC Handles

Sometimes you need to prevent the GC from moving objects:

```csharp
// Pinning (prevents compaction)
byte[] buffer = new byte[1024];
GCHandle handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
try
{
    IntPtr ptr = handle.AddrOfPinnedObject();
    // Pass ptr to native code
}
finally
{
    handle.Free();  // Unpin
}
```

**Trade-offs:**
- **Benefit:** Native code can safely access managed memory
- **Cost:** Pinned objects can't be moved, causing fragmentation
- **Best Practice:** Pin only when necessary, unpin as soon as possible

### Analyzing GC Behavior

**GC Notification Events:**
```csharp
// Monitor GC collections
GC.RegisterForFullGCNotification(10, 10);

while (true)
{
    GCNotificationStatus status = GC.WaitForFullGCApproach();
    if (status == GCNotificationStatus.Succeeded)
    {
        // Full GC is approaching
        Console.WriteLine("Full GC approaching - reduce load");
    }
    
    status = GC.WaitForFullGCComplete();
    if (status == GCNotificationStatus.Succeeded)
    {
        // Full GC completed
        Console.WriteLine("Full GC completed");
    }
}
```

**GC Statistics:**
```csharp
// Get collection counts
int gen0 = GC.CollectionCount(0);
int gen1 = GC.CollectionCount(1);
int gen2 = GC.CollectionCount(2);

Console.WriteLine($"Gen 0: {gen0}, Gen 1: {gen1}, Gen 2: {gen2}");

// Get total memory
long totalMemory = GC.GetTotalMemory(forceFullCollection: false);
Console.WriteLine($"Total managed memory: {totalMemory:N0} bytes");

// Get generation of an object
int generation = GC.GetGeneration(myObject);
Console.WriteLine($"Object is in generation: {generation}");
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

**Analyze GC Behavior of Different Allocation Patterns**

1. Create a console application that demonstrates different allocation patterns:

```csharp
using System;
using System.Diagnostics;

class Program
{
    static void Main()
    {
        Console.WriteLine("=== Short-lived allocations ===");
        MeasureGC(() => ShortLivedAllocations());
        
        Console.WriteLine("\n=== Mid-life allocations ===");
        MeasureGC(() => MidLifeAllocations());
        
        Console.WriteLine("\n=== Large allocations ===");
        MeasureGC(() => LargeAllocations());
    }
    
    static void MeasureGC(Action action)
    {
        int gen0Before = GC.CollectionCount(0);
        int gen1Before = GC.CollectionCount(1);
        int gen2Before = GC.CollectionCount(2);
        long memBefore = GC.GetTotalMemory(false);
        
        action();
        
        int gen0After = GC.CollectionCount(0);
        int gen1After = GC.CollectionCount(1);
        int gen2After = GC.CollectionCount(2);
        long memAfter = GC.GetTotalMemory(false);
        
        Console.WriteLine($"Gen 0 collections: {gen0After - gen0Before}");
        Console.WriteLine($"Gen 1 collections: {gen1After - gen1Before}");
        Console.WriteLine($"Gen 2 collections: {gen2After - gen2Before}");
        Console.WriteLine($"Memory delta: {(memAfter - memBefore):N0} bytes");
    }
    
    static void ShortLivedAllocations()
    {
        for (int i = 0; i < 100_000; i++)
        {
            var obj = new byte[1000];
        }
    }
    
    static void MidLifeAllocations()
    {
        var list = new List<byte[]>();
        for (int i = 0; i < 10_000; i++)
        {
            list.Add(new byte[1000]);
            if (i % 1000 == 0)
            {
                list.Clear(); // Causes promotion then death
            }
        }
    }
    
    static void LargeAllocations()
    {
        for (int i = 0; i < 100; i++)
        {
            var large = new byte[100_000]; // LOH
        }
    }
}
```

2. Run the program and observe:
   - Which pattern triggers the most Gen 0 collections?
   - Which pattern triggers Gen 2 collections?
   - How does memory usage differ between patterns?

3. Consider: How would using ArrayPool change these patterns?
