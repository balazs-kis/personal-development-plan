# Lesson 3: Native AOT Compilation

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand what Native AOT (Ahead-of-Time) compilation is and how it differs from JIT
- Recognize the benefits and trade-offs of Native AOT deployment
- Identify scenarios where Native AOT is advantageous
- Understand the limitations of Native AOT (reflection, dynamic code, trimming)
- Configure and publish .NET applications using Native AOT
- Make libraries AOT-compatible

---

## Introduction

Native AOT represents a fundamental shift in how .NET applications can be deployed. Instead of shipping IL (Intermediate Language) that gets JIT-compiled at runtime, Native AOT compiles your entire application to native machine code ahead of time. This enables scenarios like minimal container images, fast-starting serverless functions, and running on platforms where JIT isn't allowed—but it comes with important constraints you need to understand.

## Key Concepts Summary

### What is Native AOT?

Native AOT (Ahead-of-Time) compilation is a deployment model where your .NET application is compiled to native machine code **during publish** rather than at runtime.

**Traditional .NET Deployment:**
```
C# Source → IL (Intermediate Language) → [Deploy] → JIT → Native Code → Run
                                           ↓
                                     Requires .NET Runtime
```

**Native AOT Deployment:**
```
C# Source → IL → [AOT Compiler] → Native Code → [Deploy] → Run
                      ↓
                Platform-Specific Native Executable
                No Runtime Required
```

### Key Benefits of Native AOT

#### 1. Faster Startup Time
```
Traditional .NET: Load Runtime + Load IL + JIT Compile → Start
Native AOT:       Load Native Code → Start

Improvement: 3-10x faster startup
```

**Why it's faster:**
- No runtime initialization
- No JIT compilation time
- Code is immediately executable

#### 2. Smaller Memory Footprint
```
Traditional .NET:
├─ .NET Runtime (~50-100MB)
├─ JIT Compiler
├─ IL Code
└─ Generated Native Code

Native AOT:
└─ Native Code Only (~10-30MB)

Improvement: 50-90% smaller memory usage
```

#### 3. Self-Contained Executable
```
Native AOT Output:
└─ myapp.exe (no dependencies)

Traditional:
├─ myapp.dll
├─ System.*.dll (dozens of files)
└─ .NET Runtime
```

**Benefits:**
- No .NET runtime installation required
- Single-file deployment
- Simplified distribution

#### 4. Runs in Restricted Environments
- iOS and some game consoles prohibit JIT
- Security-sensitive environments that forbid runtime code generation
- Embedded systems with limited resources

### When to Use Native AOT

**✅ Excellent Use Cases:**
```
1. Cloud Infrastructure & Serverless
   - AWS Lambda, Azure Functions
   - Kubernetes pods
   - Fast startup = lower cold start costs

2. Command-Line Tools
   - Fast startup critical for CLI UX
   - Single-file distribution
   - No runtime dependency

3. Microservices
   - Minimal container images
   - Lower memory = more instances
   - Fast scaling

4. IoT and Edge Devices
   - Limited resources
   - No runtime installation
   - Smaller footprint
```

**❌ Not Recommended For:**
```
1. Applications Using Heavy Reflection
   - Dynamic serializers (e.g., old JSON libraries)
   - ORM frameworks relying on reflection
   - Plugin architectures with dynamic loading

2. Applications Needing Runtime Code Generation
   - Roslyn compilation
   - Expression trees
   - Dynamic proxies

3. Large Monolithic Applications
   - Build time increases significantly
   - Harder to debug
   - Less benefit from startup improvements
```

### Major Limitations and Trade-offs

#### 1. No Dynamic Assembly Loading

```csharp
❌ Not Supported:
Assembly.LoadFrom("plugin.dll")
Assembly.LoadFile(path)

Reason: All code must be known at build time
```

**Alternative:** Use source generators instead of runtime code generation.

#### 2. Limited Reflection

**The Core Problem:**
The AOT compiler must decide at build time what code to include. Unconstrained reflection makes this impossible.

```csharp
❌ Problematic Reflection:
// Compiler can't know what type T is at build time
Type t = Type.GetType(userInput);
var instance = Activator.CreateInstance(t);

✅ AOT-Compatible Reflection:
// Compiler sees the type directly
var instance = new MyKnownType();
```

**Workarounds:**

**Option 1: Eliminate Reflection**
```csharp
// Instead of reflection-based serializer
❌ JsonConvert.DeserializeObject<T>(json);  // Newtonsoft.Json

// Use source-generated serializer
✅ JsonSerializer.Deserialize<T>(json);      // System.Text.Json
```

**Option 2: Use Attributes for Known Types**
```csharp
public class MyService
{
    // Tell AOT compiler to preserve this type and its properties
    [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicProperties)]
    public void ProcessType(Type type)
    {
        // Reflection on properties is now safe
        var properties = type.GetProperties();
    }
}
```

**Option 3: Mark Code as Incompatible**
```csharp
[RequiresUnreferencedCode("This method uses reflection that may not work in AOT")]
public void DynamicMethod(string typeName)
{
    Type t = Type.GetType(typeName);
    // ... reflection code ...
}
```

#### 3. Code Trimming Required

Native AOT aggressively removes unused code to keep size small:

```
Full .NET Framework: ~200MB
Trimmed .NET:        ~50MB
Native AOT:          ~10MB
```

**Trimming Incompatibilities:**
- Reflection-based serializers (use source generators)
- `System.Reflection.Emit` (runtime code generation)
- Dynamic proxy generation
- Some WPF/Windows Forms features

**Checking Trim Compatibility:**
```xml
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <EnableTrimAnalyzer>true</EnableTrimAnalyzer>
</PropertyGroup>
```

Build warnings will identify trim-incompatible code.

#### 4. Platform-Specific Builds

Native AOT compiles to specific platforms:

```bash
# Must specify runtime identifier
dotnet publish -r win-x64
dotnet publish -r linux-x64
dotnet publish -r osx-arm64
```

**Cannot:** Compile once, run anywhere (like traditional .NET)
**Must:** Build for each target platform separately

### Configuring Native AOT

#### Enable Native AOT in Project File

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    
    <!-- Enable Native AOT -->
    <PublishAot>true</PublishAot>
  </PropertyGroup>
</Project>
```

#### Publishing with Native AOT

```bash
# Publish for Windows
dotnet publish -c Release -r win-x64

# Publish for Linux
dotnet publish -r linux-x64 -c Release

# Publish for macOS ARM
dotnet publish -r osx-arm64 -c Release
```

**Output:** Native executable in `bin/Release/net8.0/{rid}/publish/`

**Windows:**

**macOS:**

### ASP.NET Core with Native AOT

ASP.NET Core supports Native AOT starting in .NET 8:

```csharp
var builder = WebApplication.CreateSlimBuilder(args);

// Configure JSON serialization for AOT
builder.Services.ConfigureHttpJsonOptions(options =>
{
    options.SerializerOptions.TypeInfoResolverChain.Insert(0, 
        AppJsonSerializerContext.Default);
});

var app = builder.Build();

// Minimal API endpoint
app.MapGet("/", () => new Person("John", 30));

app.Run();

// Source-generated JSON context
[JsonSerializable(typeof(Person))]
internal partial class AppJsonSerializerContext : JsonSerializerContext { }

record Person(string Name, int Age);
```

**Key Differences:**
- Use `WebApplication.CreateSlimBuilder()` instead of `CreateBuilder()`
- Must use source-generated JSON serialization
- Limited middleware support (check compatibility)
- Some features not available (e.g., Razor Pages)

### Making Libraries AOT-Compatible

#### Design Considerations for Library Authors

**1. Avoid Reflection Where Possible**
```csharp
❌ Reflection-based API:
public void Configure(Type handlerType)
{
    var handler = Activator.CreateInstance(handlerType);
}

✅ Generic API:
public void Configure<THandler>() where THandler : new()
{
    var handler = new THandler();
}
```

**2. Use Source Generators Instead of Runtime Reflection**
```csharp
// Instead of reflection-based mapping
❌ Mapper.Map<TSource, TDest>(source);

// Provide source-generated alternative
✅ [GeneratedMapper]
   partial class MyMapper { }
```

**3. Annotate Reflection Usage**
```csharp
public class ConfigManager
{
    // Tell AOT what members you need
    public void Load<[DynamicallyAccessedMembers(
        DynamicallyAccessedMemberTypes.PublicProperties
    )] TConfig>()
    {
        // Property reflection is safe here
    }
}
```

**4. Provide AOT Analysis**
```xml
<PropertyGroup>
  <IsAotCompatible>true</IsAotCompatible>
  <EnableTrimAnalyzer>true</EnableTrimAnalyzer>
</PropertyGroup>
```

Consumers get warnings if they use your library incorrectly.

### Debugging and Diagnostics

#### AOT Warnings

Native AOT generates warnings for incompatible patterns:

```
warning IL2026: Method 'MyMethod' uses reflection in a way that 
                may not work with trimming/AOT
```

**Common Warnings:**
- `IL2026`: Requires unreferenced code
- `IL2070`: Reflection accessing unpreserved members
- `IL2075`: Type passed to reflection doesn't have required members preserved

#### Runtime Behavior

```csharp
// Check if running in AOT mode
if (!RuntimeFeature.IsDynamicCodeSupported)
{
    // Running in Native AOT
    // Use AOT-compatible code paths
}
else
{
    // Running with JIT
    // Can use reflection freely
}
```

#### Size Analysis

```bash
# Publish and check output size
dotnet publish -c Release -r linux-x64

# Typical sizes:
# Self-contained (with runtime): ~60-80 MB
# Native AOT:                    ~10-15 MB
```

### Performance Characteristics

| Metric | Traditional .NET | Native AOT | Improvement |
|--------|-----------------|------------|-------------|
| **Startup Time** | 300-500ms | 30-50ms | 10x faster |
| **Memory (idle)** | 50-100 MB | 8-15 MB | 5-10x smaller |
| **Build Time** | Fast | Slow | 5-10x slower |
| **Steady-State Performance** | Excellent (JIT optimized) | Very Good (no PGO) | ~5-10% slower |
| **Package Size** | Large | Small | 5-8x smaller |

**Trade-off:** Slower builds for faster deployments and runtime.

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 20 minutes):

**Create and Publish a Native AOT Console App**

1. Create a new console application:
```bash
dotnet new console -n AotDemo
cd AotDemo
```

2. Enable Native AOT in the `.csproj`:
```xml
<PropertyGroup>
  <PublishAot>true</PublishAot>
</PropertyGroup>
```

3. Write a simple program:
```csharp
var start = DateTime.UtcNow;
Console.WriteLine($"Hello from Native AOT!");
Console.WriteLine($"Startup took: {(DateTime.UtcNow - start).TotalMilliseconds}ms");
```

4. Publish with Native AOT:
```bash
dotnet publish -c Release -r win-x64
```

5. Compare the output:
   - Check the file size
   - Run the executable and note startup time
   - Try without AOT (remove `<PublishAot>`) and compare

6. **Challenge:** Try using reflection (e.g., `Type.GetType()`) and see what warnings you get.
