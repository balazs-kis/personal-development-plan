## Introduction

While benchmarking tells you *how fast* your code runs, profiling tells you *why* it runs that way. Profiling tools help you identify CPU hotspots, memory leaks, excessive garbage collection, and other performance issues in real applications. Understanding how to profile effectively is essential for optimizing production systems and understanding application behavior under load.

## Key Concepts Summary

### Why Profile?

Profiling reveals the actual behavior of your application:

```
Benchmarking: How fast is this method?
Profiling:    Why is my application slow?

Benchmark → Measures specific code in isolation
Profile   → Analyzes entire application behavior
```

**What Profiling Reveals:**
- CPU hotspots (which methods use the most CPU time)
- Memory allocation patterns
- Garbage collection pressure
- I/O bottlenecks
- Thread contention
- Call hierarchies

## CPU Profiling

### Visual Studio CPU Profiling

#### Starting a CPU Profile

**Method 1: Performance Profiler (Alt+F2)**
1. Open Performance Profiler: **Debug → Performance Profiler** or **Alt+F2**
2. Select **CPU Usage**
3. Click **Start**
4. Run your scenario
5. Click **Stop Collection**

**Method 2: Integrated with Debugger**
1. Set breakpoints at start and end of code to analyze
2. Start debugging (F5)
3. Open **Diagnostic Tools** window: **Debug → Windows → Show Diagnostic Tools**
4. Enable **CPU Usage**
5. Run between breakpoints
6. View results in **CPU Usage** tab

#### Understanding the CPU Usage Report

```
[Hot Path] → Top Path View → Functions View → Caller/Callee
```

**Top Functions:**
```
Function Name                | Total CPU | Self CPU
---------------------------|-----------|----------
Program.ProcessData()      | 1,234ms   | 45ms
  ├─ JsonSerializer.Parse() | 789ms     | 789ms
  ├─ Database.Query()       | 345ms     | 100ms
  │  └─ SqlConnection.Open()| 245ms     | 245ms
  └─ ComputeHash()          | 55ms      | 55ms
```

- **Total CPU** - Time spent in function + all functions it calls
- **Self CPU** - Time spent only in this function (excludes called functions)

**Hot Path:**
The execution path that consumed the most CPU time:
```
Main → ProcessRequests → HandleRequest → ParseJson → ...
  ↑
  Shows most expensive code path
```

#### Flame Graph View

Visual representation of call stacks:

```
[Main                                                    ]
[ProcessRequests                                         ]
[HandleRequest                            ][Other...    ]
[ParseJson        ][QueryDB    ][Hash  ]
[Deserialize     ]
```

**Width** = CPU time consumed
**Height** = Call stack depth

**How to Read:**
- Wide boxes = CPU hotspots
- Look for unexpectedly wide boxes
- Hover for details (CPU time, percentage)

#### Caller/Callee View

Shows what calls a function (callers) and what it calls (callees):

```
Callers of ProcessData():
  Main()              → 100% (always calls it)
  BackgroundWorker()  → 25% (sometimes)

ProcessData():
  Total: 1,234ms

Callees from ProcessData():
  JsonSerializer.Parse() → 789ms (64%)
  Database.Query()       → 345ms (28%)
  ComputeHash()          → 55ms  (4%)
```

### Command-Line CPU Profiling

#### Using dotnet-trace

```bash
# Install dotnet-trace
dotnet tool install --global dotnet-trace

# List running processes
dotnet-trace ps

# Collect a trace (run for 10 seconds)
dotnet-trace collect --process-id <PID> --duration 00:00:10

# Collect specific provider
dotnet-trace collect --process-id <PID> --providers Microsoft-Windows-DotNETRuntime

# View in Visual Studio or PerfView
# File: trace.nettrace
```

**Advantages:**
- Cross-platform (Windows, Linux, macOS)
- No Visual Studio required
- Can profile production servers
- Lower overhead than full profiling

#### Using dotnet-counters

```bash
# Install dotnet-counters
dotnet tool install --global dotnet-counters

# Monitor real-time metrics
dotnet-counters monitor --process-id <PID>

# Monitor specific counters
dotnet-counters monitor --process-id <PID> \
  --counters System.Runtime[cpu-usage,working-set]
```

**Output:**
```
Press p to pause, r to resume, q to quit.
  Status: Running

[System.Runtime]
    CPU Usage (%)                                   45
    GC Heap Size (MB)                              234
    Gen 0 GC Count / 1 sec                          12
    Gen 1 GC Count / 1 sec                           2
    Gen 2 GC Count / 1 sec                           0
    Working Set (MB)                               456
```

## Memory Profiling

### Understanding Memory Issues

**Common Memory Problems:**

**1. Memory Leaks**
```
Memory usage grows over time and never decreases
↓
Application eventually crashes with OutOfMemoryException
```

**2. High Allocation Rate**
```
Frequent object allocations
↓
Frequent garbage collections
↓
Performance degradation
```

**3. Large Object Heap Fragmentation**
```
Large objects (>85KB) allocated/deallocated
↓
LOH fragmentation
↓
Memory inefficiency
```

### Visual Studio Memory Profiling

#### .NET Object Allocation Tool

**Steps:**
1. Open Performance Profiler (Alt+F2)
2. Select **.NET Object Allocation Tracking**
3. Click **Start**
4. Run your scenario
5. Stop collection

**What It Shows:**
- Which types are allocated most frequently
- Allocation call stacks
- Size of allocations
- Object lifetimes

**Example Output:**
```
Type                    | Count   | Size      | Avg Size
------------------------|---------|-----------|----------
System.String           | 45,678  | 12.3 MB   | 278 B
byte[]                  | 12,345  | 89.1 MB   | 7.4 KB
MyApp.Customer          | 8,901   | 4.2 MB    | 485 B
System.Int32[]          | 5,432   | 21.7 MB   | 4.1 KB
```

#### Memory Usage Tool (Snapshots)

**Steps:**
1. Open Performance Profiler (Alt+F2)
2. Select **Memory Usage**
3. Click **Start**
4. Take snapshot (baseline)
5. Run scenario that might leak
6. Take another snapshot
7. Compare snapshots

**Snapshot Comparison:**
```
Snapshot 1 → Snapshot 2
Total Memory: 45 MB → 234 MB (+189 MB)

Objects with increased count:
  Customer: 1,000 → 45,000 (+44,000) ← Memory leak candidate!
  byte[]:   500 → 501 (+1)
  string:   10,000 → 12,000 (+2,000)
```

**Finding the Leak:**
```
1. Find object type with unexpected growth
2. Click on type to see instances
3. View "Paths to Root" for each instance
4. Identify what's holding references
```

### Detecting Memory Leaks with dotnet-trace

```bash
# Monitor GC stats
dotnet-counters monitor --process-id <PID> \
  --counters System.Runtime[gc-heap-size,gen-0-gc-count]

# If heap size keeps growing, suspect a leak

# Collect memory trace
dotnet-trace collect --process-id <PID> \
  --providers Microsoft-Windows-DotNETRuntime:0x1:4

# Analyze in PerfView or Visual Studio
```

### Using dotnet-dump

```bash
# Install dotnet-dump
dotnet tool install --global dotnet-dump

# Capture a dump
dotnet-dump collect --process-id <PID>

# Analyze the dump
dotnet-dump analyze dump_20240101_123456.dmp

# In the analyzer:
> dumpheap -stat         # Object statistics
> dumpheap -type Customer # Instances of Customer
> gcroot <address>        # What's keeping object alive
```

**Example Session:**
```
> dumpheap -stat
Statistics:
      MT    Count    TotalSize Class Name
00007ff8  1000      24000     System.Int32[]
00007ff9  45000     1080000   MyApp.Customer  ← Suspicious!
...

> dumpheap -type MyApp.Customer
Address       MT            Size
00001234...   00007ff9...   24
00001235...   00007ff9...   24
...

> gcroot 00001234...
HandleTable:
    0000abcd... (strong handle)
      -> 0000def0... MyApp.CustomerCache
        -> 0000fghi... System.Collections.Generic.List<MyApp.Customer>
          -> 00001234... MyApp.Customer
```

**Root Cause:** CustomerCache is holding references!

## Analyzing Garbage Collection

### GC Metrics

**Key Metrics:**
- **Gen 0/1/2 Collections** - Frequency of collections
- **GC Heap Size** - Total managed memory
- **% Time in GC** - Time spent in garbage collection
- **Allocation Rate** - MB/sec allocated

**Good vs. Bad:**
```
✅ Good GC Behavior:
   - Mostly Gen 0 collections
   - Gen 2 collections are rare
   - < 5% time in GC
   - Stable heap size

❌ Bad GC Behavior:
   - Frequent Gen 2 collections
   - > 20% time in GC
   - Growing heap size
   - High allocation rate
```

### Viewing GC Events

**In Visual Studio:**
1. Collect CPU or Memory trace
2. Open **GC Events** view
3. Analyze:
   - GC frequency
   - GC duration
   - GC reasons (induced, allocation threshold, etc.)

**Using dotnet-trace:**
```bash
dotnet-trace collect --process-id <PID> \
  --providers Microsoft-Windows-DotNETRuntime:0x1:4 \
  --clrevents gc

# View in PerfView: GCStats report
```

### Reducing GC Pressure

```csharp
❌ Bad: High allocation rate
public string ProcessData(string[] items)
{
    string result = "";
    foreach (var item in items)
    {
        result += item + ",";  // Allocates new string each time!
    }
    return result;
}

✅ Good: Reduced allocations
public string ProcessData(string[] items)
{
    return string.Join(",", items);  // Single allocation
}

✅ Better: Zero allocations with Span
public void ProcessData(ReadOnlySpan<char> input, Span<char> output)
{
    // Work with stack-allocated spans
}
```

## PerfView

PerfView is Microsoft's powerful performance analysis tool:

**Key Features:**
- CPU sampling and tracing
- GC and memory analysis
- Event tracing (ETW/EventPipe)
- Cross-platform (.nettrace support)
- Advanced filtering and grouping

**Download:**
```
https://github.com/microsoft/perfview/releases
```

**Basic Usage:**
```bash
# Collect trace
PerfView.exe collect MyApp.exe
```

**When to Use PerfView:**
- Advanced CPU analysis
- Deep GC investigation
- Event correlation
- Production server analysis (ETW)
- Custom EventSource analysis

## Best Practices

### 1. Profile in Release Configuration

```bash
❌ Don't profile Debug builds
dotnet run

✅ Do profile Release builds
dotnet run -c Release
```

### 2. Profile Representative Scenarios

```
✅ Profile:
   - Typical user workflows
   - Peak load scenarios
   - Long-running operations
   - Real data volumes

❌ Avoid:
   - Trivial operations
   - Unrealistic data
   - Short-duration runs
```

### 3. Focus on Hot Paths

```
80/20 Rule: 80% of time spent in 20% of code

1. Find hottest functions (most CPU time)
2. Optimize those first
3. Re-profile to verify improvement
4. Repeat
```

### 4. Correlate Multiple Metrics

```
High CPU + Low Memory = CPU-bound computation
Low CPU + High Memory = Memory leak or excessive allocations
High CPU + High GC = Allocation-induced GC pressure
```

### 5. Use Multiple Tools

```
dotnet-counters → Quick health check (real-time)
dotnet-trace    → Detailed analysis (post-mortem)
Visual Studio   → Rich visualization
PerfView        → Advanced deep-dive
```

### 6. Profile in Production-Like Environments

```
Development: May have different:
  - Hardware (CPU, RAM)
  - Load (concurrent users)
  - Data volume
  - Network latency

Always validate performance in production-like staging environment
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

**Profile and Optimize a Sample Application**

1. **Create a sample app with performance issues:**

```csharp
public class PerformanceDemo
{
    private List<string> _cache = new List<string>();

    public void ProcessRequests()
    {
        for (int i = 0; i < 10000; i++)
        {
            ProcessRequest(i);
        }
    }

    private void ProcessRequest(int id)
    {
        // Memory leak: never cleared
        _cache.Add($"Request-{id}: {DateTime.Now}");

        // Inefficient string concatenation
        string data = "";
        for (int i = 0; i < 100; i++)
        {
            data += "x";
        }

        // Unnecessary allocations
        var bytes = new byte[1024];
        Array.Fill(bytes, (byte)id);
    }
}
```

2. **Profile the application:**
   - Use CPU profiling to find hot paths
   - Use memory profiling to detect the leak
   - Monitor GC pressure

3. **Identify issues:**
   - String concatenation hotspot
   - Memory leak in cache
   - Excessive allocations

4. **Optimize and re-profile:**
   - Fix string concatenation (use StringBuilder)
   - Clear cache or use bounded collection
   - Reduce allocations (use ArrayPool)
