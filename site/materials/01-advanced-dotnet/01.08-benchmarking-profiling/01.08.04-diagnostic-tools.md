# Lesson 4: .NET Diagnostic Tools

## Learning Objectives

By the end of this lesson, you will be able to:
- Use dotnet-counters to monitor real-time performance metrics
- Collect traces with dotnet-trace for detailed performance analysis
- Analyze memory dumps with dotnet-dump
- Investigate garbage collection with dotnet-gcdump
- Use dotnet-monitor for production diagnostics
- Understand EventPipe and EventCounter APIs
- Collect and analyze diagnostics from containerized applications
- Apply diagnostic tools to troubleshoot production issues

---

## Introduction

.NET provides a comprehensive suite of command-line diagnostic tools that work across Windows, Linux, and macOS. Unlike profilers that require IDE integration, these tools can diagnose running applications in any environment—including production containers and cloud deployments. Understanding these tools is essential for troubleshooting performance issues, memory leaks, and other runtime problems in real-world scenarios.

## Key Concepts Summary

### .NET Diagnostic Tools Ecosystem

```
Diagnostic Tools:
┌─────────────────────────────────────────────────────┐
│ dotnet-counters  → Real-time metrics monitoring     │
│ dotnet-trace     → Performance trace collection     │
│ dotnet-dump      → Process memory dumps             │
│ dotnet-gcdump    → GC heap snapshots                │
│ dotnet-monitor   → HTTP API for all diagnostics     │
└─────────────────────────────────────────────────────┘

EventPipe:
┌─────────────────────────────────────────────────────┐
│ Cross-platform tracing infrastructure               │
│ Collects events from runtime and custom sources     │
│ Powers all diagnostic tools                         │
└─────────────────────────────────────────────────────┘
```

### When to Use Each Tool

| Tool | Use When | Output |
|------|----------|--------|
| **dotnet-counters** | Need real-time metrics | Live console display |
| **dotnet-trace** | Investigate performance issues | .nettrace file |
| **dotnet-dump** | Analyze crash or state | Memory dump file |
| **dotnet-gcdump** | Investigate memory leaks | GC heap snapshot |
| **dotnet-monitor** | Production monitoring | HTTP API responses |

## dotnet-counters: Real-Time Monitoring

### Installation

```bash
# Install as global tool
dotnet tool install --global dotnet-counters

# Or update existing installation
dotnet tool update --global dotnet-counters
```

### Listing Running .NET Processes

```bash
# List all .NET processes
dotnet-counters ps

# Output:
# 12345 MyWebApi     C:\Apps\MyWebApi.dll
# 67890 MyWorker     C:\Apps\MyWorker.dll
```

### Monitoring Performance Counters

```bash
# Monitor default counters for process
dotnet-counters monitor --process-id 12345

# Monitor specific counters
dotnet-counters monitor \
    --process-id 12345 \
    --counters System.Runtime,Microsoft.AspNetCore.Hosting

# Monitor with custom refresh rate (1 second)
dotnet-counters monitor \
    --process-id 12345 \
    --refresh-interval 1
```

```bash

    --process-id 12345 \

dotnet-counters collect \
    --process-id 12345 \
    --format json \
    --output counters.json \
    --duration 60
```

### Custom EventCounters

Create your own performance counters:

```csharp
using System.Diagnostics.Tracing;

[EventSource(Name = "MyApp.Metrics")]
public sealed class AppMetrics : EventSource
{
    public static readonly AppMetrics Instance = new();

    private EventCounter _requestCounter;
    private EventCounter _errorCounter;
    private PollingCounter _queueSizeCounter;

    private AppMetrics()
    {
        _requestCounter = new EventCounter("requests", this);
        _errorCounter = new EventCounter("errors", this);
        _queueSizeCounter = new PollingCounter(
            "queue-size",
            this,
            () => MessageQueue.CurrentSize)
        {
            DisplayName = "Message Queue Size"
        };
    }

    public void RecordRequest() => _requestCounter.WriteMetric(1);
    public void RecordError() => _errorCounter.WriteMetric(1);

    protected override void Dispose(bool disposing)
    {
        _requestCounter?.Dispose();
        _errorCounter?.Dispose();
        _queueSizeCounter?.Dispose();
        base.Dispose(disposing);
    }
}

// Usage
AppMetrics.Instance.RecordRequest();
AppMetrics.Instance.RecordError();

// Monitor
// dotnet-counters monitor --process-id 12345 --counters MyApp.Metrics
```

## dotnet-trace: Performance Tracing

### Installation

```bash
# Install
dotnet tool install --global dotnet-trace

# Update
dotnet tool update --global dotnet-trace
```

### Collecting Traces

```bash
# Collect trace from running process
dotnet-trace collect --process-id 12345

# Collect specific providers
dotnet-trace collect \
    --process-id 12345 \
    --providers Microsoft-Windows-DotNETRuntime

# Collect for specific duration (30 seconds)
dotnet-trace collect \
    --process-id 12345 \
    --duration 00:00:30 \
    --output my-trace.nettrace
```

### Common Trace Profiles

```bash
# CPU sampling (default)
dotnet-trace collect --process-id 12345 --profile cpu-sampling

# Garbage collection
dotnet-trace collect --process-id 12345 --profile gc-collect

# GC with heap collection
dotnet-trace collect --process-id 12345 --profile gc-verbose
```

**Available Profiles:**
- `cpu-sampling` - CPU usage investigation
- `gc-collect` - GC collection and allocations
- `gc-verbose` - Detailed GC information
- `http` - HTTP request tracking

### Analyzing Traces

Traces can be analyzed in:

1. **Visual Studio** (Windows)
   - Open .nettrace file directly
   - View flame graphs and call trees
   - Filter and search events

2. **PerfView** (Windows)
   - Free Microsoft tool
   - Advanced analysis features
   - CPU stacks, GC analysis

3. **Speedscope** (Web-based)
   - Upload .nettrace (converted to speedscope format)
   - Interactive flame graphs
   - Cross-platform

### Converting Traces

```bash
# Convert to speedscope format
dotnet-trace convert my-trace.nettrace --format speedscope

# Convert to Chromium format (for Chrome DevTools)
dotnet-trace convert my-trace.nettrace --format chromium
```

## dotnet-dump: Memory Dump Analysis

### Installation

```bash
# Install
dotnet tool install --global dotnet-dump

# Update
dotnet tool update --global dotnet-dump
```

### Collecting Dumps

```bash
# Collect full memory dump
dotnet-dump collect --process-id 12345

# Collect with specific type
dotnet-dump collect \
    --process-id 12345 \
    --type Full \
    --output my-dump.dmp
```

**Dump Types:**
- `Full` - Complete process memory
- `Heap` - GC heap only (smaller)
- `Mini` - Minimal information
- `WithHeap` - Mini + GC heap

### Analyzing Dumps

```bash
# Analyze dump interactively
dotnet-dump analyze my-dump.dmp

# Commands available in analyzer:
```

**Common Analysis Commands:**

```
# Show CLR status
> clrstack

# Show managed threads
> threads

# Show GC heap statistics
> dumpheap -stat

# Show specific object type
> dumpheap -type System.String

# Show object references
> gcroot <address>

# Show exception information
> printexception

# Show finalization queue
> finalizequeue

# Show memory usage
> eeheap -gc
```

**Example Session:**


## dotnet-gcdump: GC Heap Analysis

### Installation

```bash
# Install
dotnet tool install --global dotnet-gcdump

# Update
dotnet tool update --global dotnet-gcdump
```

### Collecting GC Dumps

```bash
# Collect GC heap snapshot
dotnet-gcdump collect --process-id 12345

# Output: process_12345_20260203_123456.gcdump
```

**Advantages over Full Dumps:**
- Much smaller file size
- Lower performance impact
- Faster collection
- Easier to share/transfer

### Analyzing with Visual Studio

1. Open `.gcdump` file in Visual Studio
2. View **Summary** tab:
   - Total heap size
   - Object count by type
   - Largest objects

3. View **Paths to Root** tab:
   - Why objects are kept alive
   - Reference chains

4. View **Types** tab:
   - Object count per type
   - Total size per type
   - Average size

### Finding Memory Leaks

**Compare Two Snapshots:**

```bash
# Collect snapshot 1
dotnet-gcdump collect --process-id 12345 --output snapshot1.gcdump

# Wait and let app run
sleep 300

# Collect snapshot 2
dotnet-gcdump collect --process-id 12345 --output snapshot2.gcdump
```

**In Visual Studio:**
1. Open snapshot2.gcdump
2. Click "Compare to" → select snapshot1.gcdump
3. Look for types with growing object counts
4. Investigate paths to root for leaked objects

## dotnet-monitor: Production Diagnostics HTTP API

### Installation

```bash
# Install as global tool
dotnet tool install --global dotnet-monitor

# Run dotnet-monitor
dotnet monitor collect --urls "http://localhost:52323"
```

### Key Features

**HTTP API for diagnostics without SSH/RDP:**
- Collect traces via HTTP POST
- Get live metrics via HTTP GET
- Trigger process dumps
- Collect GC dumps
- View logs

### Configuration

```json
// appsettings.json
{
  "DefaultProcess": {
    "Filters": [{
      "Key": "ProcessName",
      "Value": "MyWebApi"
    }]
  },
  "DiagnosticPort": {
    "ConnectionMode": "Listen",
    "EndpointName": "/tmp/dotnet-monitor.sock"
  },
  "Metrics": {
    "Enabled": true,
    "UpdateIntervalSeconds": 5
  }
}
```

### API Endpoints

```bash
# Get process information
curl http://localhost:52323/processes

# Get live metrics
curl http://localhost:52323/metrics

# Collect trace (30 seconds)
curl -X POST http://localhost:52323/trace \
    -o trace.nettrace \
    -d '{
      "profile": "Cpu",
      "duration": "00:00:30"
    }'

# Collect GC dump
curl -X POST http://localhost:52323/gcdump \
    -o heap.gcdump

# Get logs
curl http://localhost:52323/logs?level=Warning
```

### Docker Integration

```dockerfile
# Dockerfile with dotnet-monitor
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 80
EXPOSE 52323

# Install dotnet-monitor
RUN dotnet tool install --global dotnet-monitor

FROM base AS final
COPY --from=publish /app .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

```yaml
# docker-compose.yml
version: '3.8'
services:
  webapp:
    build: .
    ports:
      - "5000:80"
      - "52323:52323"  # dotnet-monitor
    environment:
      - ASPNETCORE_URLS=http://+:80
      - DOTNETMONITOR_DiagnosticPort__ConnectionMode=Listen
```

## EventPipe and EventCounter

### Understanding EventPipe

EventPipe is .NET's cross-platform tracing infrastructure:

```
Application → EventSource → EventPipe → Diagnostic Tools
              ↓
         Custom Events
         Runtime Events
         Provider Events
```

**Key Benefits:**
- Cross-platform (Windows, Linux, macOS)
- Low overhead
- No admin/root required
- Works in containers

### Creating Custom EventSource

```csharp
using System.Diagnostics.Tracing;

[EventSource(Name = "MyApp-Performance")]
public sealed class PerformanceEventSource : EventSource
{
    public static readonly PerformanceEventSource Log = new();

    [Event(1, Level = EventLevel.Informational)]
    public void RequestStarted(string url)
    {
        WriteEvent(1, url);
    }

    [Event(2, Level = EventLevel.Informational)]
    public void RequestCompleted(string url, long durationMs)
    {
        WriteEvent(2, url, durationMs);
    }

    [Event(3, Level = EventLevel.Warning)]
    public void SlowRequest(string url, long durationMs)
    {
        WriteEvent(3, url, durationMs);
    }
}

// Usage
PerformanceEventSource.Log.RequestStarted("/api/users");
// ... process request ...
PerformanceEventSource.Log.RequestCompleted("/api/users", 123);
```

### Consuming Custom Events

```bash
# Collect custom events
dotnet-trace collect \
    --process-id 12345 \
    --providers MyApp-Performance
```

## Real-World Diagnostic Scenarios

### Scenario 1: High CPU Usage

```bash
# 1. Identify high CPU process
dotnet-counters ps

# 2. Monitor CPU in real-time
dotnet-counters monitor --process-id 12345

# 3. If CPU is high, collect CPU trace
dotnet-trace collect \
    --process-id 12345 \
    --profile cpu-sampling \
    --duration 00:00:30

# 4. Analyze in Visual Studio or PerfView
# Look for hot paths and expensive methods
```

### Scenario 2: Memory Leak

```bash
# 1. Collect baseline GC dump
dotnet-gcdump collect --process-id 12345 --output baseline.gcdump

# 2. Let app run under load for 10 minutes

# 3. Collect second GC dump
dotnet-gcdump collect --process-id 12345 --output after.gcdump

# 4. Compare in Visual Studio
# Identify types with growing object counts
# Trace paths to root to find what's holding references
```

### Scenario 3: Slow Requests

```bash
# 1. Collect HTTP trace
dotnet-trace collect \
    --process-id 12345 \
    --profile http \
    --duration 00:01:00

# 2. Analyze trace
# Look for long-running HTTP requests
# Identify database queries or external API calls
# Check for async/await issues
```

### Scenario 4: Production Issue

```bash
# Use dotnet-monitor for remote diagnostics

# 1. Get process info
curl http://myapp:52323/processes

# 2. Check live metrics
curl http://myapp:52323/metrics

# 3. If needed, collect trace
curl -X POST http://myapp:52323/trace \
    -o production-trace.nettrace \
    -d '{"profile": "Cpu", "duration": "00:00:30"}'

# 4. Download and analyze offline
```

## Best Practices

### 1. Use Appropriate Tool for the Job

```bash
✅ Real-time monitoring: dotnet-counters
✅ Performance investigation: dotnet-trace
✅ Memory leaks: dotnet-gcdump
✅ Crash analysis: dotnet-dump
✅ Production: dotnet-monitor
```

### 2. Limit Trace Duration

```bash
✅ Good: 30-60 second traces
dotnet-trace collect --duration 00:00:30

❌ Bad: Unbounded collection
dotnet-trace collect  # Can create huge files
```

### 3. Use Specific Providers

```bash
✅ Good: Only collect what you need
dotnet-trace collect --providers Microsoft-Windows-DotNETRuntime:0x1F:5

❌ Bad: Collect everything
dotnet-trace collect --providers *
```

### 4. Monitor in Production Safely

```bash
✅ dotnet-counters: Very low overhead
✅ dotnet-gcdump: Low overhead, safe
⚠️  dotnet-trace: Moderate overhead, limit duration
⚠️  dotnet-dump: Can pause app briefly
```
