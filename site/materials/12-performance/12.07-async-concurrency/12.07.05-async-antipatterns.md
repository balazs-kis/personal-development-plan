# Lesson 5: Avoiding Async Anti-Patterns

## Learning Objectives

By the end of this lesson, you will be able to:
- Recognize and avoid sync-over-async anti-patterns
- Understand why blocking on async code causes deadlocks
- Use async/await correctly throughout the call stack
- Avoid async void methods (except event handlers)
- Handle cancellation tokens properly

---

## Introduction

While async/await makes asynchronous programming easier, it's easy to fall into anti-patterns that cause deadlocks, poor performance, or hidden bugs. The most dangerous anti-pattern is "sync-over-async"—blocking on async code using `.Result`, `.Wait()`, or `.GetAwaiter().GetResult()`. Understanding these anti-patterns and how to avoid them is crucial for building reliable asynchronous applications.

## Key Concepts Summary

### Anti-Pattern #1: Sync-Over-Async (Blocking)

**The Problem:**
```csharp
// ❌ VERY BAD: Blocking on async code
public void GetData()
{
    var result = GetDataAsync().Result; // Deadlock risk!
    // Or:
    // GetDataAsync().Wait();
    // GetDataAsync().GetAwaiter().GetResult();
}

private async Task<string> GetDataAsync()
{
    return await _httpClient.GetStringAsync("https://api.example.com");
}
```

**Why It Causes Deadlocks:**
```
1. Main thread calls GetData()
2. GetData() calls GetDataAsync().Result
   - Blocks main thread waiting for task
3. GetDataAsync() starts, hits await
   - Captures current synchronization context
   - Returns to caller
4. When HTTP completes, continuation tries to resume on context
5. BUT context (main thread) is blocked by .Result
6. Deadlock! Neither can proceed

This happens in:
- UI applications (WPF, WinForms)
- Legacy ASP.NET (not Core)
- Any code with SynchronizationContext
```

**Real Deadlock Example:**
```csharp
// UI Application (WPF)
private void Button_Click(object sender, EventArgs e)
{
    // ❌ This WILL deadlock
    var data = FetchDataAsync().Result;
    textBox.Text = data;
}

private async Task<string> FetchDataAsync()
{
    // Captures UI context
    var result = await _httpClient.GetStringAsync(url);
    // Tries to resume on UI context
    // BUT UI thread is blocked by .Result above
    // DEADLOCK!
    return result;
}
```

**The Fix:**
```csharp
// ✅ GOOD: Async all the way
private async void Button_Click(object sender, EventArgs e)
{
    var data = await FetchDataAsync();
    textBox.Text = data;
}

private async Task<string> FetchDataAsync()
{
    return await _httpClient.GetStringAsync(url);
}

// No blocking, no deadlock!
```

### Anti-Pattern #2: Async Void

**The Problem:**
```csharp
// ❌ BAD: Async void (except for event handlers)
public async void ProcessDataAsync()
{
    await Task.Delay(100);
    throw new Exception("Oops!"); // Exception swallowed!
}

// Caller has no way to:
// - Await completion
// - Catch exceptions
// - Know when it finishes
```

**Why It's Dangerous:**
```
1. Can't await async void methods
2. Exceptions crash the app (unhandled)
3. Can't return results
4. Fire-and-forget with no tracking
5. Hard to test

Exception in async void:
- Goes to thread pool
- Triggers UnhandledException
- Usually crashes application
```

**The Fix:**
```csharp
// ✅ GOOD: Async Task
public async Task ProcessDataAsync()
{
    await Task.Delay(100);
    throw new Exception("Handled!"); // Exception can be caught
}

// Caller can await and handle
try
{
    await ProcessDataAsync();
}
catch (Exception ex)
{
    // Handle exception properly
}
```

**When Async Void Is OK:**
```csharp
// ✅ ONLY exception: Event handlers
private async void Button_Click(object sender, EventArgs e)
{
    try
    {
        await ProcessDataAsync();
    }
    catch (Exception ex)
    {
        // Must handle exceptions here
        MessageBox.Show($"Error: {ex.Message}");
    }
}

// Event handlers must be void
// Framework doesn't await them
// So async void is required
```

### Anti-Pattern #3: Forgotten Await

**The Problem:**
```csharp
// ❌ BAD: Forgot to await
public async Task ProcessAsync()
{
    SaveDataAsync(); // Forgot await!
    // Method returns immediately
    // SaveDataAsync continues in background
    // Might not complete before method returns
    
    return; // SaveDataAsync might still be running!
}
```

**Consequences:**
```
- Method returns before work completes
- No exception handling
- Timing bugs (race conditions)
- Hard to debug
```

**The Fix:**
```csharp
// ✅ GOOD: Await the task
public async Task ProcessAsync()
{
    await SaveDataAsync(); // Wait for completion
    // Now we know it's done
}

// Or if fire-and-forget is intentional:
public async Task ProcessAsync()
{
    _ = SaveDataAsync(); // Explicit fire-and-forget
    // Or:
    // SaveDataAsync().Forget(); // Custom extension
}
```

### Anti-Pattern #4: Mixing Sync and Async

**The Problem:**
```csharp
// ❌ BAD: Mixing blocking and async
public async Task<Data> GetDataAsync()
{
    var id = GetIdFromDatabase(); // Synchronous call
    return await FetchDataAsync(id); // Async call
}

private int GetIdFromDatabase()
{
    // Blocks thread
    using var connection = new SqlConnection(connectionString);
    connection.Open();
    var command = new SqlCommand("SELECT Id FROM Table", connection);
    return (int)command.ExecuteScalar();
}
```

**Why It's Bad:**
```
- Blocks thread unnecessarily
- Defeats purpose of async
- Under load, causes thread pool starvation
- Mixed async/sync is confusing
```

**The Fix:**
```csharp
// ✅ GOOD: Async all the way
public async Task<Data> GetDataAsync()
{
    var id = await GetIdFromDatabaseAsync();
    return await FetchDataAsync(id);
}

private async Task<int> GetIdFromDatabaseAsync()
{
    await using var connection = new SqlConnection(connectionString);
    await connection.OpenAsync();
    await using var command = new SqlCommand("SELECT Id FROM Table", connection);
    return (int)await command.ExecuteScalarAsync();
}
```

### Anti-Pattern #5: Async Lazy Loading

**The Problem:**
```csharp
public class Product
{
    private Data? _cachedData;
    
    // ❌ BAD: Can't make property getter async
    public Data Data
    {
        get
        {
            if (_cachedData == null)
            {
                // Force sync over async
                _cachedData = LoadDataAsync().Result; // Deadlock!
            }
            return _cachedData;
        }
    }
}
```

**The Fix:**
```csharp
public class Product
{
    private Data? _cachedData;
    
    // ✅ GOOD: Async method
    public async Task<Data> GetDataAsync()
    {
        if (_cachedData == null)
        {
            _cachedData = await LoadDataAsync();
        }
        return _cachedData;
    }
}

// Or use AsyncLazy pattern
public class Product
{
    private readonly AsyncLazy<Data> _data;
    
    public Product()
    {
        _data = new AsyncLazy<Data>(LoadDataAsync);
    }
    
    public Task<Data> GetDataAsync() => _data.GetValueAsync();
}
```

### Anti-Pattern #6: Not Using CancellationToken

**The Problem:**
```csharp
// ❌ BAD: No cancellation support
public async Task<List<Product>> GetProductsAsync()
{
    var products = new List<Product>();
    
    // Can't cancel even if client disconnects
    foreach (var id in productIds)
    {
        var product = await _repository.GetAsync(id);
        products.Add(product);
    }
    
    return products;
}
```

**The Fix:**
```csharp
// ✅ GOOD: Support cancellation
public async Task<List<Product>> GetProductsAsync(
    CancellationToken cancellationToken = default)
{
    var products = new List<Product>();
    
    foreach (var id in productIds)
    {
        cancellationToken.ThrowIfCancellationRequested();
        
        var product = await _repository.GetAsync(id, cancellationToken);
        products.Add(product);
    }
    
    return products;
}

// ASP.NET Core automatically provides token
[HttpGet]
public async Task<IActionResult> Get(CancellationToken ct)
{
    var products = await _service.GetProductsAsync(ct);
    return Ok(products);
}
```

### Anti-Pattern #7: Using Task.Run in ASP.NET Core

**The Problem:**
```csharp
// ❌ BAD: Task.Run in API
[HttpGet]
public async Task<IActionResult> GetData()
{
    // Wastes thread!
    var result = await Task.Run(() => ProcessData());
    return Ok(result);
}
```

**Why It's Bad:**
```
Task.Run:
- Takes thread from thread pool
- Does work on that thread
- Original thread waits

Result:
- Uses TWO threads where one would do
- Thread pool stress
- No benefit

Task.Run is for:
- Desktop apps (offload CPU work from UI thread)
- NOT for ASP.NET Core
```

**The Fix:**
```csharp
// ✅ GOOD: Just call the method
[HttpGet]
public async Task<IActionResult> GetData()
{
    var result = await ProcessDataAsync();
    return Ok(result);
}

// Or if truly CPU-bound:
[HttpGet]
public IActionResult GetData()
{
    var result = ProcessData(); // Synchronous
    return Ok(result);
}
```

### Best Practices Summary

**✅ DO:**
```csharp
// 1. Async all the way
public async Task<Result> DoWorkAsync()
{
    var data = await FetchAsync();
    var processed = await ProcessAsync(data);
    await SaveAsync(processed);
    return new Result(processed);
}

// 2. Use Task, not async void
public async Task ProcessAsync() { }

// 3. Pass CancellationToken
public async Task DoWorkAsync(CancellationToken ct = default) { }

// 4. ConfigureAwait(false) in libraries
await DoWorkAsync().ConfigureAwait(false);

// 5. Return Task directly when no await needed
public Task<Data> GetDataAsync()
{
    return _repository.GetAsync(id); // No async keyword
}
```

**❌ DON'T:**
```csharp
// 1. Block on async
var result = DoWorkAsync().Result; // NO!

// 2. Use async void (except event handlers)
public async void ProcessAsync() { } // NO!

// 3. Forget await
DoWorkAsync(); // Forgot await - NO!

// 4. Mix sync and async
var data = SyncMethod();
await AsyncMethod(data); // Inefficient

// 5. Use Task.Run in ASP.NET Core
await Task.Run(() => DoWork()); // Waste of thread

// 6. Ignore cancellation
public async Task Work() // Should take CancellationToken
```

### Detecting Anti-Patterns

**Static Analysis:**
```xml
<!-- Enable analyzers in .csproj -->
<PropertyGroup>
  <AnalysisMode>All</AnalysisMode>
  <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
</PropertyGroup>

<!-- Add async analyzer -->
<ItemGroup>
  <PackageReference Include="Microsoft.VisualStudio.Threading.Analyzers" 
                    Version="17.8.14" />
</ItemGroup>
```

**Common Warnings:**
```
VSTHRD002: Avoid problematic synchronous waits
VSTHRD003: Avoid awaiting foreign Tasks
VSTHRD100: Avoid async void methods
VSTHRD103: Call async methods when in an async method
VSTHRD110: Observe result of async calls
```
