# Lesson 4: Load Balancing and Auto-Scaling

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand load balancing algorithms and when to use each
- Implement health checks for load balancers
- Configure auto-scaling policies based on metrics
- Design systems that scale automatically with demand
- Choose appropriate load balancer types for different scenarios
- Apply best practices for zero-downtime deployments

---

## Introduction

Load balancers and auto-scaling work together to distribute traffic efficiently and adjust capacity dynamically. Load balancers ensure requests are distributed across healthy instances, while auto-scaling adds or removes instances based on demand. Together, they enable elastic architectures that handle variable load while minimizing costs.

## Key Concepts Summary

### Load Balancing Fundamentals

**Purpose:** Distribute incoming requests across multiple servers to:
- Prevent any single server from being overwhelmed
- Maximize throughput and minimize latency
- Provide redundancy and high availability
- Enable zero-downtime deployments

**Architecture:**
```
Client Requests
      │
      ▼
┌────────────┐
│   Load     │
│  Balancer  │
└────────────┘
      │
  ┌───┴───┬───────┐
  │       │       │
  ▼       ▼       ▼
┌───┐   ┌───┐   ┌───┐
│S1 │   │S2 │   │S3 │
└───┘   └───┘   └───┘
```

### Load Balancing Algorithms

#### 1. Round Robin

**How it works:** Distribute requests sequentially to each server in rotation.

```
Request 1 → Server 1
Request 2 → Server 2
Request 3 → Server 3
Request 4 → Server 1
Request 5 → Server 2
...
```

**Pros:**
✅ Simple and fair distribution
✅ Works well with homogeneous servers
✅ Low overhead

**Cons:**
❌ Doesn't account for server load
❌ Assumes all requests take same time
❌ No consideration for server capacity

**Use when:**
- All servers have similar capacity
- Requests have similar processing time
- Simple configuration needed

#### 2. Weighted Round Robin

**How it works:** Like round robin, but some servers receive more requests based on weight.

```
Server 1 (weight: 3)
Server 2 (weight: 2)
Server 3 (weight: 1)

Request 1 → Server 1
Request 2 → Server 1
Request 3 → Server 1
Request 4 → Server 2
Request 5 → Server 2
Request 6 → Server 3
Repeat...
```

**Use when:**
- Servers have different capacities
- Some servers are more powerful
- Want to gradually roll out new version (canary)

#### 3. Least Connections

**How it works:** Route to server with fewest active connections.

```
Server 1: 5 connections
Server 2: 3 connections ← Route here
Server 3: 7 connections

Next request goes to Server 2
```

**Pros:**
✅ Accounts for current load
✅ Works well with long-running requests
✅ Better for WebSockets/streaming

**Cons:**
❌ Slightly more overhead
❌ Needs connection tracking

**Use when:**
- Requests have varying duration
- Long-lived connections (WebSockets)
- Better load distribution needed

#### 4. Least Response Time

**How it works:** Route to server with lowest latency and fewest connections.

```
Server 1: 50ms avg, 5 connections
Server 2: 30ms avg, 3 connections ← Route here
Server 3: 70ms avg, 2 connections

Combines latency and load
```

**Use when:**
- Want optimal user experience
- Servers have varying performance
- Latency-sensitive applications

#### 5. IP Hash (Sticky Sessions)

**How it works:** Hash client IP to consistently route to same server.

```
Hash(Client IP) % Server Count = Server Index

Client 192.168.1.10 → Server 2 (always)
Client 192.168.1.20 → Server 1 (always)
```

**Pros:**
✅ Session affinity without shared storage
✅ Useful for stateful applications
✅ Simple implementation

**Cons:**
❌ Prevents true statelessness
❌ Uneven distribution if client IPs clustered
❌ Server failure breaks sessions

**Use when:**
- Legacy applications require session affinity
- Temporary solution during migration to stateless
- Cannot use distributed session storage

**Better alternative:**
Use distributed session storage (Redis) instead:

```csharp
// Instead of sticky sessions
services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = "redis:6379";
});
services.AddSession();
```

### Load Balancer Types

#### Layer 4 (Transport Layer) Load Balancer

**Operates at:** TCP/UDP level

**Decision based on:** IP address and port

**Example: Network Load Balancer (NLB)**

```
Client → NLB → Servers

NLB sees:
- Source IP: 192.168.1.10
- Dest IP: 10.0.1.5
- Port: 80
- Protocol: TCP

Routes based on TCP/UDP, no HTTP awareness
```

**Characteristics:**
✅ Very fast (minimal processing)
✅ High throughput (millions req/sec)
✅ Low latency
✅ Protocol agnostic

❌ No HTTP-level routing
❌ No SSL termination (typically)
❌ Limited health checks

**Use for:**
- Extreme performance requirements
- Non-HTTP protocols (gRPC, databases)
- When you need max throughput

#### Layer 7 (Application Layer) Load Balancer

**Operates at:** HTTP/HTTPS level

**Decision based on:** URL path, headers, cookies, etc.

**Example: Application Load Balancer (ALB)**

```
Client → ALB → Servers

ALB sees:
- HTTP method: GET
- Path: /api/users
- Headers: Authorization, Content-Type
- Cookies: session_id

Can route based on:
/api/users → UserService
/api/orders → OrderService
/admin/* → AdminService
```

**Characteristics:**
✅ Path-based routing
✅ Host-based routing
✅ SSL termination
✅ HTTP/2 and WebSocket support
✅ Advanced health checks

❌ Higher latency than L4
❌ More expensive (typically)

**Use for:**
- Microservices (different routes to different services)
- SSL termination
- Content-based routing
- Most web applications

### Health Checks

Load balancers need to know which servers are healthy:

**Types of Health Checks:**

#### 1. TCP Health Check

```
Load Balancer attempts to open TCP connection
✅ Connection successful → Healthy
❌ Connection refused → Unhealthy
```

Simple but doesn't verify application health.

#### 2. HTTP Health Check

```
GET /health HTTP/1.1

200 OK → Healthy
503 Service Unavailable → Unhealthy
Timeout → Unhealthy
```

Better - verifies application responds.

#### 3. Application Health Check

```
GET /health/detailed

{
    "status": "healthy",
    "database": "connected",
    "redis": "connected",
    "diskSpace": "sufficient"
}
```

Best - verifies dependencies too.

**Implementing Health Checks in ASP.NET Core:**

```csharp
public class Startup
{
    public void ConfigureServices(IServiceCollection services)
    {
        services.AddHealthChecks()
            .AddCheck("self", () => HealthCheckResult.Healthy())
            .AddDbContextCheck<ApplicationDbContext>()
            .AddRedis(Configuration["Redis:ConnectionString"])
            .AddCheck<CustomHealthCheck>("custom");
    }
    
    public void Configure(IApplicationBuilder app)
    {
        // Basic health endpoint for load balancer
        app.UseHealthChecks("/health", new HealthCheckOptions
        {
            Predicate = _ => true,
            ResponseWriter = async (context, report) =>
            {
                context.Response.ContentType = "application/json";
                var result = JsonSerializer.Serialize(new
                {
                    status = report.Status.ToString(),
                    checks = report.Entries.Select(e => new
                    {
                        name = e.Key,
                        status = e.Value.Status.ToString(),
                        description = e.Value.Description
                    })
                });
                await context.Response.WriteAsync(result);
            }
        });
        
        // Detailed health for monitoring
        app.UseHealthChecks("/health/detailed", new HealthCheckOptions
        {
            Predicate = _ => true,
            ResponseWriter = UIResponseWriter.WriteHealthCheckUIResponse
        });
    }
}

public class CustomHealthCheck : IHealthCheck
{
    private readonly IConfiguration _config;
    
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context,
        CancellationToken cancellationToken = default)
    {
        try
        {
            // Check something custom
            var isHealthy = await CheckExternalServiceAsync();
            
            return isHealthy
                ? HealthCheckResult.Healthy("All systems operational")
                : HealthCheckResult.Unhealthy("External service down");
        }
        catch (Exception ex)
        {
            return HealthCheckResult.Unhealthy("Health check failed", ex);
        }
    }
}
```

**Health Check Configuration:**

```json
{
  "HealthCheck": {
    "Interval": 30,     // Check every 30 seconds
    "Timeout": 5,       // Fail if no response in 5 seconds
    "UnhealthyThreshold": 2,  // Mark unhealthy after 2 failures
    "HealthyThreshold": 2     // Mark healthy after 2 successes
  }
}
```

### Auto-Scaling

**Purpose:** Automatically adjust the number of running instances based on demand.

**Benefits:**
- Handle traffic spikes without manual intervention
- Reduce costs during low traffic
- Maintain performance under load
- Improve availability

#### Scaling Dimensions

**1. Horizontal Scaling (Instance Count)**

```
Low Load:
[Instance 1]

Medium Load:
[Instance 1] [Instance 2]

High Load:
[Instance 1] [Instance 2] [Instance 3] [Instance 4]
```

**2. Vertical Scaling (Instance Size)**

```
Low Load:
[Small Instance]

High Load:
[Large Instance]
```

Most auto-scaling focuses on horizontal scaling.

### Auto-Scaling Metrics

#### CPU-Based Scaling

```yaml
# Scale when CPU > 70%
autoscaling:
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70
```

**Pros:** Simple, universally applicable
**Cons:** May not reflect actual load (I/O-bound apps)

#### Memory-Based Scaling

```yaml
autoscaling:
  minReplicas: 2
  maxReplicas: 10
  targetMemoryUtilizationPercentage: 80
```

**Pros:** Good for memory-intensive apps
**Cons:** Memory doesn't always correlate with load

#### Request-Based Scaling

```yaml
# Scale to maintain 1000 requests per instance
autoscaling:
  minReplicas: 2
  maxReplicas: 10
  targetRequestsPerSecond: 1000
```

**Pros:** Directly measures load
**Cons:** Requires load balancer integration

#### Custom Metrics

```yaml
# Scale based on queue length
autoscaling:
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: External
    external:
      metricName: queue_depth
      targetValue: 100
```

**Use when:** Standard metrics don't capture your bottleneck

### Auto-Scaling in Kubernetes (HPA)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-deployment
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # Wait 5min before scaling down
      policies:
      - type: Percent
        value: 50  # Scale down max 50% at a time
        periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0  # Scale up immediately
      policies:
      - type: Percent
        value: 100  # Can double instances
        periodSeconds: 60
```

### Auto-Scaling in Azure App Service

```csharp
// Using Azure SDK
var autoscaleSettings = new AutoscaleSettingResource
{
    Profiles = new[]
    {
        new AutoscaleProfile
        {
            Name = "Default",
            Capacity = new ScaleCapacity
            {
                Minimum = "2",
                Maximum = "10",
                Default = "2"
            },
            Rules = new[]
            {
                // Scale up rule
                new ScaleRule
                {
                    MetricTrigger = new MetricTrigger
                    {
                        MetricName = "CpuPercentage",
                        Threshold = 70,
                        Operator = ComparisonOperationType.GreaterThan,
                        TimeAggregation = TimeAggregationType.Average,
                        TimeWindow = TimeSpan.FromMinutes(5)
                    },
                    ScaleAction = new ScaleAction
                    {
                        Direction = ScaleDirection.Increase,
                        Value = "1",  // Add 1 instance
                        Cooldown = TimeSpan.FromMinutes(5)
                    }
                },
                // Scale down rule
                new ScaleRule
                {
                    MetricTrigger = new MetricTrigger
                    {
                        MetricName = "CpuPercentage",
                        Threshold = 30,
                        Operator = ComparisonOperationType.LessThan,
                        TimeAggregation = TimeAggregationType.Average,
                        TimeWindow = TimeSpan.FromMinutes(10)
                    },
                    ScaleAction = new ScaleAction
                    {
                        Direction = ScaleDirection.Decrease,
                        Value = "1",  // Remove 1 instance
                        Cooldown = TimeSpan.FromMinutes(10)
                    }
                }
            }
        }
    }
};
```

### Scaling Policies Best Practices

#### 1. Set Minimum Instances >= 2

Always run at least 2 instances for high availability:

```yaml
minReplicas: 2  # Never go below 2
maxReplicas: 20
```

#### 2. Scale Up Quickly, Scale Down Slowly

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0      # Immediate
    policies:
    - value: 100%                       # Double capacity
  scaleDown:
    stabilizationWindowSeconds: 300    # Wait 5 minutes
    policies:
    - value: 25%                        # Only 25% at a time
```

**Why?** Better to have excess capacity briefly than insufficient capacity.

#### 3. Set Appropriate Cooldown Periods

```yaml
scaleUp:
  cooldown: 60s    # Fast response to load
scaleDown:
  cooldown: 300s   # Avoid flapping
```

#### 4. Use Multiple Metrics

```yaml
metrics:
- cpu: 70%
- memory: 80%
- requestsPerSecond: 1000
# Scale if ANY metric exceeds threshold
```

#### 5. Set Realistic Max Replicas

```yaml
maxReplicas: 20  # Based on:
# - Cost budget
# - Database connection limit
# - External service rate limits
```

### Zero-Downtime Deployments

**Problem:** How to deploy new version without downtime?

**Solution:** Rolling updates with health checks

#### Rolling Update Strategy

```
Initial State (v1):
[v1] [v1] [v1] [v1]

Step 1: Deploy v2 to 1 instance
[v1] [v1] [v1] [v2] ← Wait for health check

Step 2: Health check passes, continue
[v1] [v1] [v2] [v2]

Step 3: Continue rolling out
[v1] [v2] [v2] [v2]

Step 4: Complete
[v2] [v2] [v2] [v2]
```

**Kubernetes Rolling Update:**

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Max 1 extra instance during update
      maxUnavailable: 0  # Never reduce capacity below desired
  template:
    spec:
      containers:
      - name: api
        image: api:v2
        readinessProbe:
          httpGet:
            path: /health
            port: 80
          initialDelaySeconds: 10
          periodSeconds: 5
        livenessProbe:
          httpGet:
            path: /health
            port: 80
          initialDelaySeconds: 30
          periodSeconds: 10
```

#### Blue-Green Deployment

```
Blue (v1) - Currently serving traffic
[Blue] [Blue] [Blue]
          ↑
    Load Balancer

Deploy Green (v2)
[Blue] [Blue] [Blue]  [Green] [Green] [Green]

Switch traffic after health checks
[Blue] [Blue] [Blue]  [Green] [Green] [Green]
                              ↑
                        Load Balancer

Remove old version
[Green] [Green] [Green]
         ↑
   Load Balancer
```

**Benefits:**
✅ Instant rollback (switch back to Blue)
✅ Zero downtime
✅ Test in production before switch

**Drawbacks:**
❌ Double resources during deployment
❌ Database migrations complex

#### Canary Deployment

```
v1 (95% traffic)
[v1] [v1] [v1] [v1] [v1] [v1] [v1] [v1] [v1] [v1-canary]
                                                    ↑
                                                  5% traffic

Monitor metrics, errors, performance

If healthy, increase canary traffic:
75% v1, 25% v2
50% v1, 50% v2
0% v1, 100% v2
```

**Implementation in Kubernetes (Flagger):**

```yaml
apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: api-canary
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  service:
    port: 80
  analysis:
    interval: 1m
    threshold: 5
    maxWeight: 50
    stepWeight: 10
    metrics:
    - name: request-success-rate
      thresholdRange:
        min: 99
    - name: request-duration
      thresholdRange:
        max: 500
```

## Complete Example: Scalable .NET API

```csharp
// Program.cs
var builder = WebApplication.CreateBuilder(args);

// Health checks for load balancer
builder.Services.AddHealthChecks()
    .AddDbContextCheck<ApplicationDbContext>()
    .AddRedis(builder.Configuration["Redis:ConnectionString"]);

// Distributed session for scalability
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = builder.Configuration["Redis:ConnectionString"];
});

// Configure for running behind load balancer
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | 
                              ForwardedHeaders.XForwardedProto;
    options.KnownNetworks.Clear();
    options.KnownProxies.Clear();
});

var app = builder.Build();

// Forward headers from load balancer
app.UseForwardedHeaders();

// Health endpoints
app.MapHealthChecks("/health");
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

// Graceful shutdown
var lifetime = app.Services.GetRequiredService<IHostApplicationLifetime>();
lifetime.ApplicationStopping.Register(() =>
{
    // Give load balancer time to remove from rotation
    Thread.Sleep(10000); // 10 seconds
});

app.Run();
```

## Key Takeaways

- **Load balancers distribute traffic** across multiple servers for availability and performance
- **Choose algorithm based on workload** - round robin for uniform, least connections for variable
- **Layer 7 (ALB) for HTTP routing** - Layer 4 (NLB) for max performance
- **Health checks ensure traffic only goes to healthy instances**
- **Auto-scaling adjusts capacity dynamically** based on metrics
- **Scale up fast, scale down slow** - avoid capacity shortfalls
- **Use rolling updates for zero-downtime deployments**
- **Implement graceful shutdown** - finish requests before terminating
