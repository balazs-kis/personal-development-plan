## Learning Objectives

By the end of this lesson, you will be able to:

- Set realistic performance targets based on business needs
- Create measurable service level objectives

## Introduction

Before optimizing anything, you need to know what success looks like. Performance engineering starts with defining clear, measurable goals. Service Level Agreements (SLAs), Service Level Objectives (SLOs), and Service Level Indicators (SLIs) provide the framework for setting and tracking performance expectations.

Without clear performance requirements, teams waste time optimizing the wrong things or over-engineering solutions that don't deliver business value.

## Key Concepts Summary

### The Performance Hierarchy

**Service Level Indicators (SLIs)** are quantitative measurements of service performance:
- Request latency (time to respond)
- Error rate (percentage of failed requests)
- Throughput (requests per second)
- Availability (percentage of successful health checks)

**Service Level Objectives (SLOs)** are specific, measurable targets for your SLIs:
- "95% of requests complete in under 200ms"
- "99.9% of requests succeed (error rate < 0.1%)"
- "99.95% uptime per month"

**Service Level Agreements (SLAs)** are formal contracts with customers that define:
- SLO commitments
- Consequences for violations (refunds, credits)
- Measurement methodology
- Exclusions (planned maintenance, force majeure)

**The relationship:**
```
SLA ≥ SLO > SLI (current performance)

Example:
SLA: 99.9% uptime promise to customers
SLO: 99.95% internal target (buffer for safety)
SLI: 99.97% actual measured uptime
```

### Why This Matters

**Business Alignment:** Performance goals must map to business needs, not arbitrary technical targets.

**Focus:** Clear SLOs help prioritize work. If you're already meeting your SLO, invest time elsewhere.

**Error Budgets:** SLOs define acceptable failure rates, enabling calculated risk-taking for feature velocity.

**Customer Trust:** SLAs set clear expectations with customers about what they can depend on.

### Defining Good SLIs

**Choose user-centric metrics:**
```
❌ Bad SLI: Database query time
✅ Good SLI: Time to load user's dashboard

❌ Bad SLI: Server CPU usage
✅ Good SLI: API response latency

❌ Bad SLI: Number of errors logged
✅ Good SLI: Percentage of requests that succeed
```

**Characteristics of good SLIs:**
- Directly correlate with user experience
- Measurable from the user's perspective
- Simple to understand
- Cover critical user journeys

### Setting Realistic SLOs

**Start with current performance:**
```csharp
// Analyze historical data
var p95Latency = GetPercentile(historicalData, 95);
var errorRate = CalculateErrorRate(historicalData);

// Set SLO with buffer for improvement
var targetLatency = p95Latency * 0.9;  // 10% improvement
var targetErrorRate = Math.Max(errorRate * 0.8, 0.001);  // 20% improvement or 0.1% minimum
```

**The 95th percentile from the past 7-15 days is a good baseline for latency SLOs.**

**Use tiered SLOs for different criticality:**
```
Critical Path (checkout):
- SLO: 99.99% success rate
- SLO: p95 latency < 100ms

Important (search):
- SLO: 99.9% success rate
- SLO: p95 latency < 300ms

Nice-to-have (recommendations):
- SLO: 99.5% success rate
- SLO: p95 latency < 1000ms
```

## The Five-Step SLO Process

Google recommends this practical approach:

### Step 1: List Critical User Journeys

Identify and prioritize user flows by business impact:

**E-commerce example:**
1. Checkout (highest impact - revenue)
2. Add to cart
3. Product search
4. Browse products
5. View recommendations

**SaaS application example:**
1. User authentication
2. Core feature usage (depends on product)
3. Data export
4. Settings management

### Step 2: Determine SLI Metrics

For each journey, define metrics that track user experience:

**Checkout journey:**
```json
{
  "journey": "checkout",
  "slis": [
    {
      "name": "checkout_success_rate",
      "description": "Percentage of checkout attempts that complete successfully",
      "type": "success_rate"
    },
    {
      "name": "checkout_latency",
      "description": "Time from checkout initiation to confirmation page",
      "type": "latency",
      "aggregation": "p95"
    }
  ]
}
```

### Step 3: Set SLO Target Goals

Define specific targets and measurement periods:

```csharp
public class ServiceLevelObjective
{
    public string Name { get; set; }
    public string SliName { get; set; }
    public decimal Target { get; set; }
    public TimeSpan MeasurementWindow { get; set; }
    public string Unit { get; set; }
}

// Example SLOs
var checkoutSuccessSlo = new ServiceLevelObjective
{
    Name = "Checkout Success Rate",
    SliName = "checkout_success_rate",
    Target = 99.9m,  // 99.9%
    MeasurementWindow = TimeSpan.FromDays(30),
    Unit = "percentage"
};

var checkoutLatencySlo = new ServiceLevelObjective
{
    Name = "Checkout Latency",
    SliName = "checkout_latency",
    Target = 200,  // 200ms
    MeasurementWindow = TimeSpan.FromDays(30),
    Unit = "milliseconds"
};
```

### Step 4: Create SLI and SLO Dashboards

Visualize your SLIs and track SLO compliance:

**Dashboard elements:**
- Current SLI values
- SLO targets (with visual indicators)
- Trend over time
- Error budget remaining
- Recent incidents/violations

**Example metrics to track:**
```csharp
public class SloStatus
{
    public string SloName { get; set; }
    public decimal CurrentValue { get; set; }
    public decimal Target { get; set; }
    public bool IsCompliant => CurrentValue >= Target;
    public decimal ErrorBudgetRemaining { get; set; }
    public List<Incident> RecentViolations { get; set; }
}
```

### Step 5: Create SLO Alerts

Alert only when SLOs are at risk:

```csharp
// Alert when error budget is nearly exhausted
public class ErrorBudgetAlert
{
    public string SloName { get; set; }
    public decimal ErrorBudgetRemaining { get; set; }
    
    public bool ShouldAlert()
    {
        // Alert when 80% of error budget is consumed
        return ErrorBudgetRemaining < 0.20m;
    }
    
    public AlertSeverity GetSeverity()
    {
        return ErrorBudgetRemaining switch
        {
            < 0.05m => AlertSeverity.Critical,
            < 0.20m => AlertSeverity.Warning,
            _ => AlertSeverity.Info
        };
    }
}
```

## Error Budgets

Error budgets make the SLA/SLO concept practical.

**Definition:** The acceptable amount of downtime or errors before you violate your SLO.

**Calculation:**
```csharp
public class ErrorBudget
{
    public decimal SloTarget { get; set; }  // e.g., 99.9%
    public TimeSpan MeasurementWindow { get; set; }
    
    public TimeSpan TotalAllowedDowntime
    {
        get
        {
            var uptimePercentage = SloTarget / 100m;
            var allowedDowntimePercentage = 1m - uptimePercentage;
            return TimeSpan.FromTicks(
                (long)(MeasurementWindow.Ticks * allowedDowntimePercentage)
            );
        }
    }
}

// Example: 99.9% SLO over 30 days
var budget = new ErrorBudget
{
    SloTarget = 99.9m,
    MeasurementWindow = TimeSpan.FromDays(30)
};

Console.WriteLine($"Allowed downtime: {budget.TotalAllowedDowntime.TotalMinutes:F2} minutes");
// Output: Allowed downtime: 43.20 minutes
```

**Monthly error budgets by SLO:**
```
99%     = 7 hours 18 minutes
99.5%   = 3 hours 39 minutes
99.9%   = 43 minutes
99.95%  = 21 minutes
99.99%  = 4 minutes
99.999% = 26 seconds
```

**Using error budgets:**
- **Budget remaining:** Launch that risky feature!
- **Budget exhausted:** Freeze features, focus on reliability.
- **Balancing act:** Trade reliability for velocity within budget constraints.

## Common Mistakes

### 1. Setting Unrealistic SLOs

```
❌ "99.999% uptime for a new startup with limited resources"
✅ "99.9% uptime initially, increase as the system matures"

❌ "p95 latency < 10ms for complex aggregation queries"
✅ "p95 latency < 500ms, optimize over time"
```

**Start achievable, improve incrementally.**

### 2. Too Many SLOs

```
❌ Tracking 50 different metrics
✅ Focus on 3-5 critical user journeys
```

**More SLOs = diluted focus and alert fatigue.**

### 3. Internal Metrics as SLIs

```
❌ "Database connection pool size"
❌ "Redis cache hit rate"
✅ "API endpoint latency"
✅ "User request success rate"
```

**Choose user-facing metrics, not internal implementation details.**

### 4. No Error Budget Policy

Define clear rules:
```
Error Budget > 50%: Normal feature velocity
Error Budget 20-50%: Careful with risky changes
Error Budget < 20%: Feature freeze, reliability focus
Error Budget = 0%: All hands on reliability
```

### 5. SLOs Without Dashboards

If you can't see your SLOs in real-time, they're just documentation.

## Example: E-commerce Checkout SLOs

```csharp
public class CheckoutSlos
{
    public static readonly List<ServiceLevelObjective> Objectives = new()
    {
        new ServiceLevelObjective
        {
            Name = "Checkout Availability",
            Description = "Percentage of time checkout is available",
            Target = 99.95m,
            MeasurementWindow = TimeSpan.FromDays(30),
            Sli = new Sli
            {
                Name = "checkout_uptime",
                Query = "sum(rate(checkout_success[5m])) / sum(rate(checkout_attempts[5m]))"
            }
        },
        new ServiceLevelObjective
        {
            Name = "Checkout Latency",
            Description = "95th percentile checkout completion time",
            Target = 200,  // milliseconds
            MeasurementWindow = TimeSpan.FromDays(30),
            Sli = new Sli
            {
                Name = "checkout_latency_p95",
                Query = "histogram_quantile(0.95, checkout_duration_seconds)"
            }
        },
        new ServiceLevelObjective
        {
            Name = "Payment Processing Success",
            Description = "Percentage of payment attempts that succeed",
            Target = 99.5m,
            MeasurementWindow = TimeSpan.FromDays(30),
            Sli = new Sli
            {
                Name = "payment_success_rate",
                Query = "sum(rate(payment_success[5m])) / sum(rate(payment_attempts[5m]))"
            }
        }
    };
}
```

## Practice Exercise

Define SLOs for a hypothetical API service:

1. **Identify 3 critical user journeys** (e.g., user authentication, data retrieval, data update)
2. **For each journey, define:**
   - 1-2 SLIs (success rate, latency)

   - Measurement window

Journey: User Authentication
- SLI: auth_success_rate

Journey: Data Retrieval
- SLI: retrieval_latency_p95

## Summary

Performance engineering starts with clear goals. SLIs measure what users experience, SLOs set targets for those measurements, and SLAs formalize commitments to customers. Error budgets enable teams to balance reliability with feature velocity. Start with a few critical user journeys, set achievable SLOs based on current performance, and iterate as your system matures.
