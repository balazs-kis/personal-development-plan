# Lesson 2: Large Object Heap (LOH)

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand what objects go on the Large Object Heap
- Explain why LOH objects aren't compacted by default
- Identify performance implications of LOH allocations
- Optimize code to avoid LOH-related issues
- Use techniques to reduce LOH pressure

---

## Introduction

The Large Object Heap (LOH) is a special part of the managed heap for objects ≥85,000 bytes. Understanding LOH behavior is critical because it's not compacted by default, leading to fragmentation, and it's only collected during expensive Gen 2 GCs.

## Key Concepts Summary

### What Goes on the LOH?

**Size Threshold: 85,000 bytes**

```csharp
// Small object (< 85,000 bytes) → Small Object Heap (SOH)
var small = new byte[84999];  // 84,999 bytes
Console.WriteLine($"Generation: {GC.GetGeneration(small)}");  // Gen 0

// Large object (≥ 85,000 bytes) → Large Object Heap (LOH)
var large = new byte[85000];  // 85,000 bytes
Console.WriteLine($"Generation: {GC.GetGeneration(large)}");  // Gen 2 (LOH)
```

**Why 85,000 bytes?**
- Performance tuning determined this threshold
- Compacting large objects is expensive (memory copying cost)
- Most large objects are arrays

### LOH is Generation 3 (Logically Gen 2)

```csharp
// LOH is sometimes called "Generation 3"
// But it's logically part of Generation 2

public void UnderstandLOH()
{
    var largeArray = new byte[100_000];
    
    // Reports as Gen 2, but lives on LOH
    Console.WriteLine(GC.GetGeneration(largeArray));  // Output: 2
    
    // LOH collected during Gen 2 GC only
    GC.Collect(2);  // Collects both Gen 2 and LOH
}
```

### No Compaction by Default

**Problem: Fragmentation**

```
Before LOH GC:
┌──────────────────────────────────────┐
│ [Large Obj A][Large Obj B][Large Obj C] │  All 100 KB each
└──────────────────────────────────────┘

After LOH GC (Obj B becomes garbage):
┌──────────────────────────────────────┐
│ [Large Obj A][   FREE   ][Large Obj C] │
│    100 KB       100 KB       100 KB   │
└──────────────────────────────────────┘

Try to allocate 150 KB object:
❌ Fails! Even though we have 100 KB free
```

**Code Example:**

```csharp
public class FragmentationDemo
{
    public void DemonstrateFragmentation()
    {
        var objects = new List<byte[]>();
        
        // Allocate 10 large objects
        for (int i = 0; i < 10; i++)
        {
            objects.Add(new byte[100_000]);
        }
        
        // Remove every other object
        for (int i = 1; i < objects.Count; i += 2)
        {
            objects[i] = null;
        }
        
        // Force GC
        GC.Collect(2);
        GC.WaitForPendingFinalizers();
        
        // LOH now has holes (fragmentation)
        // Free space exists but may not be contiguous
    }
}
```

### LOH Collection Behavior

**Only Collected in Gen 2 GC:**

```csharp
public void LOHCollectionTiming()
{
    // Create large object
    var large = new byte[100_000];
    
    // Gen 0 GC: LOH not collected
    GC.Collect(0);
    Console.WriteLine($"After Gen 0: {GC.GetGeneration(large)}");  // Still 2
    
    // Gen 1 GC: LOH not collected
    GC.Collect(1);
    Console.WriteLine($"After Gen 1: {GC.GetGeneration(large)}");  // Still 2
    
    // Gen 2 GC: LOH collected
    large = null;
    GC.Collect(2);
    // Now large object can be collected
}
```

**Allocation Cost:**


**Collection Cost:**

```csharp
public void CollectionCost()
{
    // Create many temporary large objects
    for (int i = 0; i < 100; i++)
    {
        var temp = new byte[100_000];
        // Becomes garbage immediately
    }
    
    // Triggers Gen 2 GC (expensive!)
    // All of Gen 0, Gen 1, Gen 2, and LOH collected
    GC.Collect(2);
}
```

**Fragmentation Cost:**

```csharp
public class FragmentationPerformance
{
    public void DemonstratePerformanceProblem()
    {
        var keep = new List<byte[]>();
        var temp = new List<byte[]>();
        
        // Create pattern of kept and temporary objects
        for (int i = 0; i < 10; i++)
        {
            keep.Add(new byte[200_000]);
            temp.Add(new byte[200_000]);
        }
        
        // Release temporary objects
        temp.Clear();
        GC.Collect(2);
        
        // LOH now fragmented
        // Future allocations may fail or trigger more GCs
        
        try
        {
            // May fail if no contiguous space
            var huge = new byte[5_000_000];
        }
        catch (OutOfMemoryException)
        {
            Console.WriteLine("Fragmentation caused OOM!");
        }
    }
}
```

### Enabling LOH Compaction

**.NET Core and .NET Framework 4.5.1+**

```csharp
public void CompactLOH()
{
    // Option 1: On-demand compaction
    GCSettings.LargeObjectHeapCompactionMode = 
        GCLargeObjectHeapCompactionMode.CompactOnce;
    
    GC.Collect(2, GCCollectionMode.Forced, blocking: true, compacting: true);
    
    // LOH compacted during this GC
    // Returns to default (no compaction) after
}

public void AutomaticCompaction()
{
    // Option 2: Automatic compaction (certain conditions)
    // - Container memory limit set
    // - GCHeapHardLimit or GCHeapHardLimitPercent configured
    
    // LOH automatically compacted when hard limit approached
}
```

**When to Compact:**

```csharp
public class CompactionStrategy
{
    public void DecideWhenToCompact()
    {
        // ✅ Good scenarios for compaction:
        // - After processing large batch
        // - Before long-running operation
        // - When fragmentation detected
        
        ProcessLargeBatch();
        
        // Compact after batch
        GCSettings.LargeObjectHeapCompactionMode = 
            GCLargeObjectHeapCompactionMode.CompactOnce;
        GC.Collect(2);
        
        // ❌ Don't compact:
        // - During latency-sensitive operations
        // - Frequently (adds overhead)
        // - When LOH not fragmented
    }
}
```

### Common LOH Issues

**Issue 1: Temporary Large Arrays**

```csharp
// ❌ Problem: Temporary large allocations cause Gen 2 GCs
public byte[] ProcessData(Stream input)
{
    var buffer = new byte[500_000];  // LOH allocation
    input.Read(buffer, 0, buffer.Length);
    
    // Process...
    
    return result;  // buffer becomes garbage → Gen 2 GC needed
}

// ✅ Solution: Use ArrayPool
public byte[] ProcessData(Stream input)
{
    var buffer = ArrayPool<byte>.Shared.Rent(500_000);
    try
    {
        input.Read(buffer, 0, 500_000);
        // Process...
        return result;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer);  // Reused, not GC'd
    }
}
```

**Issue 2: Large String Allocations**

```csharp
// ❌ Problem: Large strings on LOH
public string GenerateLargeReport()
{
    var sb = new StringBuilder();
    for (int i = 0; i < 100_000; i++)
    {
        sb.AppendLine($"Line {i}");
    }
    
    return sb.ToString();  // String ≥85,000 bytes → LOH
}

// ✅ Solution: Stream or chunked processing
public void GenerateLargeReport(Stream output)
{
    using var writer = new StreamWriter(output);
    for (int i = 0; i < 100_000; i++)
    {
        writer.WriteLine($"Line {i}");  // Written directly, no LOH
    }
}
```

**Issue 3: Large Collection Allocations**

```csharp
// ❌ Problem: Large List backing array on LOH
public class DataProcessor
{
    // List<T> backing array can grow onto LOH
    private List<int> _data = new();
    
    public void AddMillionItems()
    {
        for (int i = 0; i < 1_000_000; i++)
        {
            _data.Add(i);  // Backing array may exceed 85KB → LOH
        }
    }
}

// ✅ Solution: Pre-size or use alternative
public class BetterDataProcessor
{
    // Option 1: Pre-size if count known
    private List<int> _data = new(capacity: 1_000_000);
    
    // Option 2: Use arrays for large fixed-size collections
    private int[] _dataArray = new int[1_000_000];
    
    // Option 3: Segment into smaller chunks
    private List<int[]> _segments = new();
    private const int SegmentSize = 10_000;
}
```

### LOH Performance Monitoring

```csharp
public class LOHMonitor
{
    public void MonitorLOH()
    {
        var info = GC.GetGCMemoryInfo();
        
        Console.WriteLine($"Heap size: {info.HeapSizeBytes:N0} bytes");
        Console.WriteLine($"Total available: {info.TotalAvailableMemoryBytes:N0}");
        Console.WriteLine($"Fragmented bytes: {info.FragmentedBytes:N0}");
        
        // Gen 2 includes LOH
        Console.WriteLine($"Gen 2 collections: {GC.CollectionCount(2)}");
        
        // High Gen 2 collection rate may indicate LOH pressure
    }
    
    public void TrackLOHAllocations()
    {
        long memBefore = GC.GetTotalAllocatedBytes();
        int gen2Before = GC.CollectionCount(2);
        
        // Do work that might allocate large objects
        DoWork();
        
        long memAfter = GC.GetTotalAllocatedBytes();
        int gen2After = GC.CollectionCount(2);
        
        Console.WriteLine($"Allocated: {memAfter - memBefore:N0} bytes");
        Console.WriteLine($"Gen 2 GCs: {gen2After - gen2Before}");
        
        if (gen2After > gen2Before)
        {
            Console.WriteLine("⚠️ Gen 2 GC occurred - check for LOH allocations");
        }
    }
    
    private void DoWork() { /* ... */ }
}
```

### Best Practices for LOH

**1. Avoid Temporary Large Objects**

```csharp
// ❌ Bad: Temporary large allocation
public void ProcessFile(string path)
{
    var data = File.ReadAllBytes(path);  // May be > 85KB
    Process(data);
    // data becomes garbage
}

// ✅ Good: Stream processing
public void ProcessFile(string path)
{
    using var stream = File.OpenRead(path);
    ProcessStream(stream);  // No large allocation
}
```

**2. Use Object Pooling**

```csharp
// ✅ Pool large objects for reuse
public class LargeObjectPool
{
    private readonly ConcurrentBag<byte[]> _pool = new();
    private const int BufferSize = 500_000;
    
    public byte[] Rent()
    {
        return _pool.TryTake(out var buffer) 
            ? buffer 
            : new byte[BufferSize];
    }
    
    public void Return(byte[] buffer)
    {
        _pool.Add(buffer);
    }
}
```

**3. Break Large Objects into Chunks**

```csharp
// ❌ Single large array
var bigArray = new int[50_000];  // > 85KB on LOH

// ✅ Multiple smaller arrays
var chunks = new int[10][];
for (int i = 0; i < 10; i++)
{
    chunks[i] = new int[5_000];  // Each < 85KB, stays off LOH
}
```

**4. Monitor and Profile**

```csharp
// Use BenchmarkDotNet with MemoryDiagnoser
[MemoryDiagnoser]
public class LOHBenchmarks
{
    [Benchmark]
    public void AllocateLarge()
    {

```

## Summary

The Large Object Heap (LOH) holds objects ≥85,000 bytes and is logically part of Gen 2. Unlike the Small Object Heap, LOH isn't compacted by default, leading to fragmentation. LOH objects are only collected during Gen 2 GCs, making temporary large allocations expensive. Optimize by using ArrayPool for temporary large buffers, streaming data instead of loading entirely, chunking large collections, and enabling compaction when needed. Monitor Gen 2 collection frequency to identify LOH pressure.
