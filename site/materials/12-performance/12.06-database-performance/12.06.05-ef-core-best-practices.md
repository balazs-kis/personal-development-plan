## Key Concepts Summary

### AsNoTracking for Read-Only Queries

**Default Tracking Behavior:**
```csharp
// By default, EF Core tracks ALL queried entities
var products = await _context.Products.ToListAsync();

// EF Core creates change tracking proxies:
// - Monitors property changes
// - Maintains relationship fixup
// - Enables SaveChanges() to detect modifications
// Cost: Memory overhead + CPU for change detection
```

**AsNoTracking for Read-Only:**
```csharp
// ✅ Use AsNoTracking when you don't need to update entities
var products = await _context.Products
    .AsNoTracking()
    .ToListAsync();

// Benefits:
// - 5x faster query execution
// - 78% less memory allocation
// - No change tracking overhead
```

**Performance Comparison (10,000 records):**
```
With Tracking:
- Time: 31.1 ms
- Memory: 13.18 MB
- Change tracking proxies created

With AsNoTracking:
- Time: 6.2 ms (5x faster)
- Memory: 2.91 MB (78% less)
- No tracking overhead
```

**Global Configuration:**
```csharp
// Set default for entire context
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options)
        : base(options)
    {
        ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;
    }
}

// Override for specific queries that need tracking
var products = await _context.Products
    .AsTracking()
    .ToListAsync();
```

**When to Use Each:**
```
✅ AsNoTracking:
- Read-only queries (GET endpoints)
- Reporting and analytics
- Data export operations
- Display-only views

✅ With Tracking:
- Queries where entities will be updated
- Need relationship fixup
- Using SaveChanges() on queried entities
```

### Projection for Minimal Data Transfer

**Problem: Loading Entire Entities:**
```csharp
// ❌ Loads ALL columns even if you only need a few
var products = await _context.Products
    .Where(p => p.Category == "Electronics")
    .ToListAsync();

// SQL generated:
// SELECT Id, Name, Description, Price, Category, ImageUrl, 
//        CreatedAt, UpdatedAt, Stock, Supplier, ... 
// FROM Products WHERE Category = 'Electronics'

// Returns to client - used properties
foreach (var product in products)
{
    Console.WriteLine($"{product.Name}: ${product.Price}");
    // Only using 2 properties but loaded 15+!
}
```

**Solution: Project to DTOs:**
```csharp
// ✅ Load only needed columns
var products = await _context.Products
    .Where(p => p.Category == "Electronics")
    .Select(p => new ProductSummaryDto
    {
        Name = p.Name,
        Price = p.Price
    })
    .ToListAsync();

// SQL generated:
// SELECT Name, Price
// FROM Products WHERE Category = 'Electronics'

// Benefits:
// - Less data transferred over network
// - Faster deserialization
// - Lower memory usage
// - Automatically AsNoTracking (DTOs aren't tracked)
```

**Complex Projections:**
```csharp
// Projection with aggregations and related data
var customerStats = await _context.Customers
    .Select(c => new CustomerStatsDto
    {
        CustomerId = c.Id,
        Name = c.Name,
        TotalOrders = c.Orders.Count,
        TotalSpent = c.Orders.Sum(o => o.Total),
        AverageOrderValue = c.Orders.Average(o => o.Total),
        LastOrderDate = c.Orders.Max(o => o.OrderDate),
        TopProducts = c.Orders
            .SelectMany(o => o.OrderItems)
            .GroupBy(i => i.Product.Name)
            .OrderByDescending(g => g.Sum(i => i.Quantity))
            .Take(3)
            .Select(g => new ProductSummary
            {
                Name = g.Key,
                Quantity = g.Sum(i => i.Quantity)
            })
            .ToList()
    })
    .ToListAsync();

// Single efficient SQL query with JOINs and aggregations!
// Much better than loading full entities and calculating in memory
```

### Compiled Queries

**Problem: Query Translation Overhead:**
```csharp
// Every time this executes, EF Core:
// 1. Parses the LINQ expression tree
// 2. Translates to SQL
// 3. Caches the translation
// But steps 1-2 have overhead (~1-5ms per query)

public async Task<Product> GetProductAsync(int id)
{
    return await _context.Products
        .Where(p => p.Id == id)
        .FirstOrDefaultAsync();
}
```

**Solution: Compiled Query:**
```csharp
// Compile once, reuse many times
private static readonly Func<AppDbContext, int, Task<Product?>> _getProductQuery =
    EF.CompileAsyncQuery(
        (AppDbContext context, int id) =>
            context.Products
                .Where(p => p.Id == id)
                .FirstOrDefault());

public async Task<Product?> GetProductAsync(int id)
{
    return await _getProductQuery(_context, id);
    // Skips LINQ parsing and translation - uses cached SQL directly
}

// Performance gain: 10-30% for frequently executed queries
```

**More Compiled Query Examples:**
```csharp
// Query with multiple parameters
private static readonly Func<AppDbContext, string, DateTime, IAsyncEnumerable<Order>> 
    _getOrdersByStatusAndDate = EF.CompileAsyncQuery(
        (AppDbContext context, string status, DateTime date) =>
            context.Orders
                .Where(o => o.Status == status && o.OrderDate >= date)
                .OrderBy(o => o.OrderDate));

// Query with complex projection
private static readonly Func<AppDbContext, int, Task<CustomerDto?>> 
    _getCustomerWithStats = EF.CompileAsyncQuery(
        (AppDbContext context, int customerId) =>
            context.Customers
                .Where(c => c.Id == customerId)
                .Select(c => new CustomerDto
                {
                    Id = c.Id,
                    Name = c.Name,
                    OrderCount = c.Orders.Count,
                    TotalSpent = c.Orders.Sum(o => o.Total)
                })
                .FirstOrDefault());
```

### Avoiding Client Evaluation

**Problem: Client-Side Evaluation:**
```csharp
// ❌ BAD: Method can't be translated to SQL
public async Task<List<Product>> GetDiscountedProductsAsync()
{
    return await _context.Products
        .Where(p => IsEligibleForDiscount(p)) // Evaluated on client!
        .ToListAsync();
}

private bool IsEligibleForDiscount(Product product)
{
    return product.Stock > 10 && product.Price > 50;
}

// What actually happens:
// 1. EF Core loads ALL products into memory
// 2. Filters in application code using IsEligibleForDiscount()
// Result: Entire table loaded - terrible performance!
```

**Solution: Use Translatable Expressions:**
```csharp
// ✅ GOOD: Everything translates to SQL
public async Task<List<Product>> GetDiscountedProductsAsync()
{
    return await _context.Products
        .Where(p => p.Stock > 10 && p.Price > 50)
        .ToListAsync();
}

// SQL generated:
// SELECT * FROM Products WHERE Stock > 10 AND Price > 50
// Filtering happens in database - efficient!
```

**EF Core 3.0+ Behavior:**
```
Prior to EF Core 3.0:
- Client evaluation was allowed
- Silently loaded data and filtered in memory
- Major performance trap

EF Core 3.0+:
- Client evaluation throws exception by default
- Forces you to make explicit choice:
  - Use AsEnumerable() to intentionally evaluate client-side
  - Rewrite query to be translatable
```

### Select N+1 Prevention Patterns

**Pattern: Always Include Related Data:**
```csharp
// ❌ BAD: Lazy loading causes N+1
var orders = await _context.Orders.ToListAsync();
foreach (var order in orders)
{
    Console.WriteLine($"Customer: {order.Customer.Name}"); // N+1!
}

// ✅ GOOD: Eager load
var orders = await _context.Orders
    .Include(o => o.Customer)
    .ToListAsync();

// ✅ BETTER: Project only needed data
var orders = await _context.Orders
    .Select(o => new OrderDto
    {
        OrderId = o.Id,
        CustomerName = o.Customer.Name
    })
    .ToListAsync();
```

### Pagination Best Practices

**Efficient Pagination:**
```csharp
// ✅ GOOD: Skip/Take with ordering
public async Task<List<Product>> GetProductsPageAsync(int page, int pageSize)
{
    return await _context.Products
        .OrderBy(p => p.Id) // Required for consistent pagination
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .AsNoTracking()
        .ToListAsync();
}

// ❌ BAD: Loading all and paginating in memory
var allProducts = await _context.Products.ToListAsync(); // Loads everything!
var page = allProducts.Skip(90).Take(10).ToList();
```

**Keyset Pagination (Better for Large Datasets):**
```csharp
// Instead of Skip/Take (which gets slower with higher page numbers)
public async Task<List<Product>> GetProductsAfterAsync(int lastId, int pageSize)
{
    return await _context.Products
        .Where(p => p.Id > lastId)
        .OrderBy(p => p.Id)
        .Take(pageSize)
        .AsNoTracking()
        .ToListAsync();
}

// Benefits:
// - Consistent performance regardless of page number
// - Database can use index efficiently
// - No need to skip rows
```

### Performance Checklist

```csharp
// ✅ Performance Best Practices Checklist

// 1. Read-only queries
var products = await _context.Products
    .AsNoTracking()              // ✅ No tracking for read-only
    .Where(p => p.Category == "Electronics")
    .Select(p => new ProductDto  // ✅ Project to DTO
    {
        Id = p.Id,
        Name = p.Name,
        Price = p.Price
    })
    .ToListAsync();              // ✅ Async operation

// 2. Queries with relations
var orders = await _context.Orders
    .Include(o => o.Customer)    // ✅ Eager load to prevent N+1
    .Include(o => o.OrderItems)
    .Where(o => o.Status == "Pending")
    .AsNoTracking()
    .ToListAsync();

// 3. Pagination
var page = await _context.Products
    .OrderBy(p => p.Id)          // ✅ Always order for pagination
    .Skip((pageNumber - 1) * pageSize)
    .Take(pageSize)
    .AsNoTracking()
    .ToListAsync();

// 4. Bulk operations
_context.Orders.AddRange(orders); // ✅ AddRange, not Add in loop
await _context.SaveChangesAsync();

// 5. Bulk updates
await _context.Orders              // ✅ ExecuteUpdate for bulk updates
    .Where(o => o.Status == "Pending")
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, "Cancelled"));
```
