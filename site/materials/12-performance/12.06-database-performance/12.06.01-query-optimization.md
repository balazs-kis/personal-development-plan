## Introduction

Query optimization begins with understanding how databases execute queries and how indexes can dramatically improve performance. An execution plan shows the operations a database performs to retrieve data, revealing bottlenecks and inefficiencies. Proper indexing is the single most effective technique for improving query performance, but poorly designed indexes can actually hurt performance. This lesson covers the fundamentals of query optimization and indexing strategies.

## Key Concepts Summary

### How Indexes Work

**B-Tree Structure:**
```
Indexes use a balanced tree (B-Tree) structure:
- Root node at the top
- Branch nodes in the middle
- Leaf nodes at the bottom (contain actual data or pointers)

Each node contains:
- Key values (indexed column values)
- Pointers to child nodes or data rows

This structure allows O(log n) lookups instead of O(n) table scans.
```

**Index Types:**
```csharp
// Clustered index - defines physical order of data
// Table can have only ONE clustered index
CREATE CLUSTERED INDEX IX_Orders_OrderDate ON Orders(OrderDate);

// Non-clustered index - separate structure with pointers
// Table can have MULTIPLE non-clustered indexes
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId ON Orders(CustomerId);

// Composite index - multiple columns
CREATE INDEX IX_Orders_Customer_Date ON Orders(CustomerId, OrderDate);
```

### Reading Execution Plans

**Viewing Plans in SQL Server:**
```sql
-- Estimated execution plan (Ctrl+L in SSMS)
-- Shows plan without executing query

-- Actual execution plan (Ctrl+M in SSMS)
SET STATISTICS TIME ON;
SET STATISTICS IO ON;

SELECT * FROM Orders WHERE CustomerId = 123;
```

**Key Operators to Look For:**
```
✅ Index Seek - Good! Uses index efficiently
❌ Index Scan / Table Scan - Bad! Reads entire table/index
⚠️ Key Lookup - Can be expensive with many rows
⚠️ Hash Match / Nested Loops - Join operations
❌ Sort - Expensive, especially on large datasets
```

**Cost Percentages:**
```
Execution plans show relative cost of each operation:
- Look for operations consuming >20% of total cost
- These are optimization candidates
- Sometimes the most expensive operation is unavoidable
```

### Indexing Strategies

**When to Add Indexes:**
```sql
-- ✅ Columns in WHERE clauses
CREATE INDEX IX_Orders_Status ON Orders(Status);
SELECT * FROM Orders WHERE Status = 'Pending';

-- ✅ Columns in JOIN conditions
CREATE INDEX IX_OrderDetails_OrderId ON OrderDetails(OrderId);
SELECT * FROM Orders o
INNER JOIN OrderDetails od ON o.Id = od.OrderId;

-- ✅ Columns in ORDER BY
CREATE INDEX IX_Orders_OrderDate ON Orders(OrderDate);
SELECT * FROM Orders ORDER BY OrderDate DESC;

-- ✅ Foreign key columns
CREATE INDEX IX_Orders_CustomerId ON Orders(CustomerId);
```

**Composite Index Column Order:**
```sql
-- Rule: Most selective column first, then order by query frequency

-- Good: CustomerId is more selective than Status
CREATE INDEX IX_Orders_Customer_Status ON Orders(CustomerId, Status);

-- This query uses the index efficiently
SELECT * FROM Orders WHERE CustomerId = 123 AND Status = 'Pending';

-- This query uses only the first column (still helpful)
SELECT * FROM Orders WHERE CustomerId = 123;

-- This query CANNOT use the index (Status is second column)
SELECT * FROM Orders WHERE Status = 'Pending';
```

**Include Columns (Covering Indexes):**
```sql
-- Add non-key columns to avoid key lookups
CREATE INDEX IX_Orders_CustomerId 
ON Orders(CustomerId)
INCLUDE (OrderDate, TotalAmount, Status);

-- This query is now "covered" - no key lookups needed
SELECT OrderDate, TotalAmount, Status
FROM Orders
WHERE CustomerId = 123;
```

### When Indexes Hurt Performance

**❌ Too Many Indexes:**
```
Every index:
- Slows down INSERT, UPDATE, DELETE operations
- Consumes disk space
- Requires maintenance

Guideline: Keep indexes < 5-7 per table unless specific need
```

**❌ Low Selectivity:**
```sql
-- Bad: Boolean columns have low selectivity
CREATE INDEX IX_Orders_IsDeleted ON Orders(IsDeleted);
-- Only 2 possible values - index may not be used

-- Good: High cardinality columns
CREATE INDEX IX_Orders_OrderNumber ON Orders(OrderNumber);
-- Each value is unique - very selective
```

**❌ Functions on Indexed Columns:**
```sql
-- This CANNOT use the index on EmailAddress
SELECT * FROM Users WHERE LOWER(EmailAddress) = 'user@example.com';

-- Solution: Store lowercased value or use computed column with index
ALTER TABLE Users ADD EmailLower AS LOWER(EmailAddress) PERSISTED;
CREATE INDEX IX_Users_EmailLower ON Users(EmailLower);
```

### EF Core and Indexes

**Defining Indexes in EF Core:**
```csharp
public class Order
{
    public int Id { get; set; }
    public int CustomerId { get; set; }
    public string Status { get; set; }
    public DateTime OrderDate { get; set; }
}

// In DbContext configuration
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Order>()
        .HasIndex(o => o.CustomerId)
        .HasDatabaseName("IX_Orders_CustomerId");
    
    // Composite index
    modelBuilder.Entity<Order>()
        .HasIndex(o => new { o.CustomerId, o.Status })
        .HasDatabaseName("IX_Orders_Customer_Status");
    
    // Unique index
    modelBuilder.Entity<Order>()
        .HasIndex(o => o.OrderNumber)
        .IsUnique();
    
    // Include columns (SQL Server only)
    modelBuilder.Entity<Order>()
        .HasIndex(o => o.CustomerId)
        .IncludeProperties(o => new { o.OrderDate, o.TotalAmount });
}
```


```
   - High CPU queries
   - Queries with many reads
```
