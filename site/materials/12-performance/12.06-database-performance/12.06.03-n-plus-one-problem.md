## Introduction

The N+1 query problem is one of the most common and costly ORM performance issues. It occurs when you load a collection of entities (1 query) and then execute additional queries for each entity's related data (N queries), resulting in N+1 total database roundtrips. For a collection of 100 items, this means 101 queries instead of 1 or 2. This lesson teaches you to identify, prevent, and fix N+1 query problems in Entity Framework Core applications.

## Key Concepts Summary

### Understanding the N+1 Problem

**The Problem:**
```csharp
// This code causes N+1 queries!
var customers = await _context.Customers.ToListAsync(); // 1 query

foreach (var customer in customers) // N queries (one per customer)
{
    Console.WriteLine($"{customer.Name}: {customer.Orders.Count} orders");
    // Accessing Orders triggers a separate query for EACH customer
}

// Result: If you have 100 customers, this executes 101 queries!
```

**SQL Generated:**
```sql
-- Query 1: Load all customers
SELECT * FROM Customers;

-- Query 2: Load orders for customer 1
SELECT * FROM Orders WHERE CustomerId = 1;

-- Query 3: Load orders for customer 2
SELECT * FROM Orders WHERE CustomerId = 2;

-- ... (98 more queries)

-- Query 101: Load orders for customer 100
SELECT * FROM Orders WHERE CustomerId = 100;
```

**Performance Impact:**
```
Example scenario:
- 100 customers in database
- Each query takes 10ms (network + execution)

N+1 problem: 101 queries × 10ms = 1,010ms (1 second)
Optimized: 1 query × 15ms = 15ms

Result: 67x performance improvement!

With larger datasets:
- 1,000 records = 10+ seconds vs 20ms
- 10,000 records = 100+ seconds vs 50ms
```

### Solution 1: Eager Loading with Include()

**Basic Include:**
```csharp
// ✅ GOOD: Load customers and their orders in one query
var customers = await _context.Customers
    .Include(c => c.Orders)
    .ToListAsync();

// SQL Generated:
// SELECT * FROM Customers c
// LEFT JOIN Orders o ON c.Id = o.CustomerId

foreach (var customer in customers)
{
    Console.WriteLine($"{customer.Name}: {customer.Orders.Count} orders");
    // No additional queries - data already loaded!
}
```

**Multiple Includes:**
```csharp
// Load multiple related entities
var customers = await _context.Customers
    .Include(c => c.Orders)
    .Include(c => c.Address)
    .ToListAsync();
```

**Nested Includes (ThenInclude):**
```csharp
// Load customers, their orders, and order items
var customers = await _context.Customers
    .Include(c => c.Orders)
        .ThenInclude(o => o.OrderItems)
    .Include(c => c.Address)
    .ToListAsync();

// Or with multiple navigation paths
var orders = await _context.Orders
    .Include(o => o.Customer)
        .ThenInclude(c => c.Address)
    .Include(o => o.OrderItems)
        .ThenInclude(i => i.Product)
    .ToListAsync();
```

**Filtered Include (EF Core 5.0+):**
```csharp
// Include only specific related entities
var customers = await _context.Customers
    .Include(c => c.Orders.Where(o => o.Status == "Pending"))
    .ToListAsync();

// Include with ordering
var customers = await _context.Customers
    .Include(c => c.Orders.OrderByDescending(o => o.OrderDate).Take(5))
    .ToListAsync();
```

### Solution 2: Projection Queries (Select)

**Projection Instead of Include:**
```csharp
// Often more efficient than Include - loads only needed data
var customerSummaries = await _context.Customers
    .Select(c => new CustomerSummaryDto
    {
        Id = c.Id,
        Name = c.Name,
        OrderCount = c.Orders.Count,
        TotalSpent = c.Orders.Sum(o => o.Total),
        RecentOrders = c.Orders
            .OrderByDescending(o => o.OrderDate)
            .Take(5)
            .Select(o => new OrderDto
            {
                Id = o.Id,
                OrderDate = o.OrderDate,
                Total = o.Total
            })
            .ToList()
    })
    .ToListAsync();

// Single query with all data - no N+1 problem!
// Loads only the columns you actually need
```

**Benefits of Projection:**
```
✅ No tracking overhead (data loaded as DTOs)
✅ Reduced data transfer (only selected columns)
✅ Single SQL query (JOIN handled by database)
✅ Better performance than Include for complex scenarios
❌ More verbose code
❌ Manual mapping to DTOs
```

### Solution 3: Explicit Loading

**Load Related Data After Initial Query:**
```csharp
// Load customer first
var customer = await _context.Customers.FindAsync(customerId);

// Explicitly load related data when needed
await _context.Entry(customer)
    .Collection(c => c.Orders)
    .LoadAsync();

// Or load specific items
await _context.Entry(customer)
    .Collection(c => c.Orders)
    .Query()
    .Where(o => o.Status == "Pending")
    .LoadAsync();
```

**When to Use:**
```
✅ Conditional loading based on business logic
✅ Loading related data only for specific entities
✅ Deferred loading in long-running processes
❌ Not suitable for most collection scenarios (creates N+1)
```

### Single Query vs Split Query

**Cartesian Explosion Problem:**
```csharp
// ⚠️ Warning: Multiple collection includes can cause cartesian explosion
var customers = await _context.Customers
    .Include(c => c.Orders)      // Collection 1
    .Include(c => c.Addresses)   // Collection 2
    .ToListAsync();

// If customer has 10 orders and 3 addresses:
// Database returns 10 × 3 = 30 rows (duplicated data!)
// EF Core filters this to correct entities, but wastes bandwidth
```

**Solution: Split Query:**
```csharp
// Use split query for multiple collections
var customers = await _context.Customers
    .Include(c => c.Orders)
    .Include(c => c.Addresses)
    .AsSplitQuery() // Separate query for each Include
    .ToListAsync();

// Generates 3 queries:
// 1. SELECT * FROM Customers
// 2. SELECT * FROM Orders WHERE CustomerId IN (...)
// 3. SELECT * FROM Addresses WHERE CustomerId IN (...)
```

**Global Configuration:**
```csharp
// Make split query the default
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString)
        .UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));
```

**When to Use Each:**
```
Single Query (default):
✅ One collection include
✅ Need transactional consistency
✅ Small result sets

Split Query:
✅ Multiple collection includes
✅ Large result sets with cartesian explosion
✅ Don't need transaction across queries
```

### Detecting N+1 Problems

**Enable SQL Logging:**
```csharp
// appsettings.Development.json
{
  "Logging": {
    "LogLevel": {
      "Microsoft.EntityFrameworkCore.Database.Command": "Information"
    }
  }
}

// Program.cs
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString)
        .LogTo(Console.WriteLine, LogLevel.Information)
        .EnableSensitiveDataLogging()); // Development only!
```

**Look for Patterns in Logs:**
```
❌ RED FLAG: Multiple similar queries in sequence
[2024-01-30 10:15:01] SELECT * FROM Orders WHERE CustomerId = 1
[2024-01-30 10:15:01] SELECT * FROM Orders WHERE CustomerId = 2
[2024-01-30 10:15:01] SELECT * FROM Orders WHERE CustomerId = 3
// ... many more similar queries = N+1 problem!

✅ GOOD: Single JOIN query
[2024-01-30 10:15:01] SELECT c.*, o.* 
FROM Customers c 
LEFT JOIN Orders o ON c.Id = o.CustomerId
```

**Integration Tests with Query Counting:**
```csharp
[Fact]
public async Task GetCustomersWithOrders_ShouldNotHaveNPlusOneProblem()
{
    // Arrange
    var queryCount = 0;
    _context.Database.Log = (query) => queryCount++;
    
    // Act
    var customers = await _repository.GetCustomersWithOrdersAsync();
    
    // Assert
    Assert.InRange(queryCount, 1, 2); // Max 2 queries acceptable
    Assert.True(customers.All(c => c.Orders.Any()));
}
```
