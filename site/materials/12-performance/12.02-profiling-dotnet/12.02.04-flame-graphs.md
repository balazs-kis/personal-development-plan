## Introduction

Flame graphs and call trees visualize profiling data, making it easy to spot performance bottlenecks at a glance. Instead of sifting through tables of numbers, these visualizations show you exactly where time is spent in your code, with wider bars representing more time. They're essential for understanding the big picture of performance issues.

## Key Concepts Summary

### What is a Flame Graph?

A flame graph is a visualization where:
- **X-axis** represents alphabetical order or time
- **Y-axis** represents call stack depth (bottom = root, top = leaf)
- **Width** represents time or sample count
- **Color** is typically random (for visual distinction)

**Key principle:** The wider the bar, the more time spent in that function.

### Flame Graph vs Icicle Chart

**Flame Graph (Root at bottom):**
```
┌─────────────────────────────────────┐
│        LeafFunction (narrow)        │ ← Top: Deepest calls
├────────────────────────────┬────────┤
│    ChildFunction1          │ Child2 │
├────────────────────────────┴────────┤
│         ParentFunction              │
├─────────────────────────────────────┤
│            Main (wide)              │ ← Bottom: Root
└─────────────────────────────────────┘
```

**Icicle Chart (Root at top):**
```
┌─────────────────────────────────────┐
│            Main (wide)              │ ← Top: Root
├─────────────────────────────────────┤
│         ParentFunction              │
├────────────────────────────┬────────┤
│    ChildFunction1          │ Child2 │
├────────────────────────────┴────────┤
│        LeafFunction (narrow)        │ ← Bottom: Deepest calls
└─────────────────────────────────────┘
```

Visual Studio uses **icicle chart** format by default but can be flipped to flame graph format.

## Using Flame Graphs in Visual Studio

### Accessing Flame Graph View

```
1. Start CPU profiling session
2. Collect data
3. In CPU Usage details view, select "Flame Graph" from dropdown
4. Or use keyboard: Ctrl+E, F
```

### Reading the Visualization

**Example flame graph:**
```
[Main]                                    100% (1000ms)
├─[ProcessRequests]                        90% (900ms)
│ ├─[ValidateRequest]                      10% (100ms)
│ └─[ProcessData]                          80% (800ms) ← WIDE = HOT
│   ├─[ParseJson]                          20% (200ms)
│   └─[TransformData]                      60% (600ms) ← WIDEST = HOTTEST
│     ├─[ApplyRules]                       40% (400ms)
│     └─[FormatOutput]                     20% (200ms)
└─[Cleanup]                                10% (100ms)
```

**Analysis:**
- `TransformData` is the widest bar → biggest optimization opportunity
- 60% of total time spent in `TransformData`
- Focus optimization efforts here first

### Interactive Features

- Click any function to zoom into its subtree
- See only that function and its callees

**Flip View:**
- Toggle between flame graph and icicle chart
- Some find one easier to read than the other

**Search:**
- Find specific functions quickly
- Highlights matching nodes

**Details Panel:**
- Shows exact percentages

## Call Tree Analysis

### Call Tree View

Shows hierarchical execution flow with metrics:
```
Function Name                    | Total CPU | Self CPU | Count
---------------------------------|-----------|----------|-------
Main                             | 100.0%    |  0.5%    | 1
└─ ProcessRequests               |  90.0%    |  1.0%    | 1
   ├─ ValidateRequest            |  10.0%    | 10.0%    | 1,000
   └─ ProcessData                |  79.0%    |  5.0%    | 1,000
      ├─ ParseJson               |  20.0%    | 20.0%    | 1,000
      └─ TransformData           |  54.0%    |  4.0%    | 1,000
         ├─ ApplyRules           |  40.0%    | 40.0%    | 10,000  ← High count!
         └─ FormatOutput         |  10.0%    | 10.0%    | 1,000
```

**Key insights:**
- `ApplyRules`: 40% self CPU, called 10,000 times → reduce call frequency
- `ValidateRequest`: 10% self CPU, called 1,000 times → batch validation?
- `TransformData`: Low self CPU (4%) but high total (54%) → delegates to children

### Caller-Callee View

Shows both callers and callees of a function:
```
Selected: TransformData (54% Total CPU)

Callers (Who calls TransformData):
- ProcessData: 1,000 calls (54% of TransformData time)

Callees (What TransformData calls):
- ApplyRules: 10,000 calls (40% of TransformData time)  ← Most expensive
- FormatOutput: 1,000 calls (10% of TransformData time)
- Other: 4% (TransformData's own work)
```

**Use case:** Understand why a function is called and what it spends time on.

## Spotting Performance Patterns

### Pattern 1: Deep Call Stacks

```
Deep, narrow stacks = Recursive or deeply nested calls

[Main]
└─[RecursiveFunction] ← Narrow bar
  └─[RecursiveFunction]
    └─[RecursiveFunction]
      └─[RecursiveFunction]
        └─[RecursiveFunction]
          └─[RecursiveFunction]
            └─[BaseCase]
```

**Problem:** Overhead from function call stack frames.

**Solution:** Consider iterative approach or tail recursion optimization.

### Pattern 2: Wide Plateaus

```
Wide, flat regions = CPU-intensive work

[Main]
└─[ProcessData]
  └─[ComplexCalculation] ← VERY WIDE = CPU-intensive
    └─[ComputeHash]
```

**Problem:** Expensive operation dominating execution.

**Solution:** Optimize algorithm, cache results, or parallelize.

### Pattern 3: Many Thin Slices

```
Many thin bars = Death by a thousand cuts

[Main]
└─[ProcessItems]
  ├─[Helper1] (thin)
  ├─[Helper2] (thin)
  ├─[Helper3] (thin)
  ├─[Helper4] (thin)
  ... (repeated 1000x)
```

**Problem:** Small operations repeated many times.

**Solution:** Batch operations, reduce call overhead, inline hot functions.

### Pattern 4: Unexpected Functions

```
Surprise functions in hot path:

[Main]
└─[BusinessLogic]
  └─[Logging] ← 30% of time spent logging?!
    └─[StringFormat]
      └─[StringBuilder]
```

**Problem:** Debug/logging code left in hot path.

**Solution:** Conditional logging, reduce verbosity, use structured logging efficiently.

## Example: Real-World Analysis

### Scenario: Slow API Endpoint

**Initial flame graph:**
```
[HTTP Request Handler]                     100% (500ms)
├─[Authentication]                          10% (50ms)
└─[GetProducts]                             90% (450ms)
  ├─[QueryDatabase]                         20% (100ms)
  └─[MapToDto]                              70% (350ms) ← HOT!
    ├─[AutoMapper.Map]                      60% (300ms)
    │ └─[GetProductCategory]                50% (250ms) ← N+1!
    │   └─[DatabaseQuery]                   50% (250ms)
    └─[FormatPrices]                        10% (50ms)
```

**Analysis:**
1. `MapToDto` takes 70% of time
2. `AutoMapper.Map` responsible for 60%
3. `GetProductCategory` called repeatedly → N+1 query problem
4. Each call queries database → 250ms total in database calls

**Solution:**
```csharp
// Before: N+1 queries
public List<ProductDto> GetProducts()
{
    var products = _db.Products.ToList();
    
    return products.Select(p => new ProductDto
    {
        Name = p.Name,
        // N+1: Queries for each product!
        Category = _db.Categories.Find(p.CategoryId).Name
    }).ToList();
}

// After: Eager loading
public List<ProductDto> GetProducts()
{
    var products = _db.Products
        .Include(p => p.Category)  // Single query with join
        .ToList();
    
    return products.Select(p => new ProductDto
    {
        Name = p.Name,
        Category = p.Category.Name  // No database call
    }).ToList();
}
```

**After optimization flame graph:**
```
[HTTP Request Handler]                     100% (100ms) ← 80% improvement!
├─[Authentication]                          10% (10ms)
└─[GetProducts]                             90% (90ms)
  ├─[QueryDatabase]                         80% (80ms)
  └─[MapToDto]                              10% (10ms)
    ├─[AutoMapper.Map]                       8% (8ms)
    └─[FormatPrices]                         2% (2ms)
```

## Using dotnet-trace and SpeedScope

### Collecting Traces with dotnet-trace

```bash
# Install dotnet-trace
dotnet tool install -g dotnet-trace

# Find process
dotnet-trace ps

# Collect trace
dotnet-trace collect -p <process-id> --format speedscope

# Or with specific duration
dotnet-trace collect -p <process-id> --format speedscope --duration 00:00:30
```

### Viewing in SpeedScope

```bash
# SpeedScope is web-based
# Visit: https://www.speedscope.app/

# Drag and drop the .speedscope.json file
# Or use local SpeedScope:
npx speedscope <trace-file>.speedscope.json
```

**SpeedScope features:**
- **Time Order View:** See execution over time
- **Left Heavy View:** Standard flame graph (hot paths at left)
- **Sandwich View:** Both callers and callees

### Example SpeedScope Analysis

```
Left Heavy View (hottest functions on left):

[ApplyBusinessRules] (40% of time) ← Widest, leftmost = hottest
[ValidateData] (25%)
[TransformModel] (20%)
[SerializeResponse] (10%)
[Other] (5%)

Conclusion: ApplyBusinessRules is the primary optimization target
```

## PerfView Call Tree

### Navigating PerfView

**Opening CPU Stacks:**
```
1. Open .etl file in PerfView
2. Double-click "CPU Stacks"
3. Wait for symbols to load
4. Select grouping: "By Name" or "Call Tree"
```

**Call Tree View:**
```
Name                                    | Exc%  | Inc%  | Count
----------------------------------------|-------|-------|-------
+MyApp.dll!Main                         |  0.1% |100.0% | 1
  +MyApp.dll!ProcessRequests            |  1.0% | 99.9% | 1
    +MyApp.dll!ProcessData              |  5.0% | 89.0% | 1,000
      +MyApp.dll!TransformData          |  4.0% | 84.0% | 1,000
        +MyApp.dll!ApplyRules           | 40.0% | 40.0% | 10,000
        +MyApp.dll!FormatOutput         | 10.0% | 10.0% | 1,000
```

**Reading the metrics:**
- **Exc% (Exclusive):** Time in function itself
- **Inc% (Inclusive):** Time in function + children
- **Count:** Number of times called

### Filtering and Searching

**Find specific functions:**
```
1. Set "Find" text box: "MyApp"
2. Select "Inc" filter
3. Sort by Exc% to find hot functions
```

**Exclude framework code:**
```
1. Right-click → "Fold Item"
2. Folds selected subtree (e.g., System.*, Microsoft.*)
3. Focus on application code
```

## Best Practices

### 1. Start with the Widest Bars

```
✅ Optimize widest bars first (biggest impact)
❌ Don't optimize thin bars (minimal impact)

Example:
[Function A] 60% wide → Optimize first
[Function B] 30% wide → Optimize second  
[Function C]  2% wide → Probably not worth it
```

### 2. Correlate with Other Data

```csharp
// Flame graph shows: DatabaseQuery is 50% of time
// Also check:
// - Query execution plan (is query optimized?)
// - Network latency (is database remote?)
// - Connection pool (running out of connections?)
```

### 3. Compare Before/After

```
Before optimization:
[Main] 100% (1000ms)
└─[SlowFunction] 90% (900ms)

After optimization:
[Main] 100% (200ms)  ← 80% improvement
└─[OptimizedFunction] 50% (100ms)
```

### 4. Use Multiple Views

```
1. Flame Graph: Quick visual identification
2. Call Tree: Detailed metrics and counts
3. Caller-Callee: Understand relationships
4. Timeline: See performance over time
```

## Practice Exercise

1. **Create a sample application** with nested function calls:

```csharp
public class ProfileExample
{
    public void Main()
    {
        for (int i = 0; i < 1000; i++)
        {
            ProcessRequest();
        }
    }

    private void ProcessRequest()
    {
        ValidateInput();
        var data = LoadData();
        var result = TransformData(data);
        SaveResult(result);
    }

    private void ValidateInput() 
    { 
        Thread.Sleep(1);  // Simulate work
    }

    private string LoadData() 
    { 
        Thread.Sleep(5);  // Simulate slow DB
        return "data"; 
    }

    private string TransformData(string data)
    {
        ApplyRule1(data);
        ApplyRule2(data);
        ApplyRule3(data);  // This is slowest
        return data;
    }

    private void ApplyRule1(string data) { Thread.Sleep(2); }
    private void ApplyRule2(string data) { Thread.Sleep(3); }
    private void ApplyRule3(string data) { Thread.Sleep(10); }  // Hot path!

    private void SaveResult(string result) 
    { 
        Thread.Sleep(2);
    }
}
```

2. **Profile with Visual Studio**:
   - View flame graph
   - Identify widest bar (`ApplyRule3`)
   - Confirm it's 10ms × 1000 calls = 10 seconds

3. **Optimize the hot path**:
   - Reduce work in `ApplyRule3`
   - Profile again
   - Compare flame graphs

4. **Try with dotnet-trace + SpeedScope**:
   - Collect trace in Speedscope format
   - View in SpeedScope
   - Compare different visualization modes

## Summary

Flame graphs and call trees visualize profiling data, making performance bottlenecks immediately obvious through width. Visual Studio provides integrated flame graph and call tree views, while dotnet-trace with SpeedScope offers cross-platform visualization. Start optimization with the widest bars (most time spent), use multiple views for comprehensive understanding, and always compare before/after visualizations to verify improvements.
