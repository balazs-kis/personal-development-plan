## Key Concepts Summary

### What is CPU Profiling?

CPU profiling measures:
- **Where time is spent** (which methods consume the most CPU)
- **Call stacks** (how execution reached those methods)
- **Hot paths** (execution paths that run most frequently)
- **CPU utilization** (percentage of CPU time used)

### When to Use CPU Profiling

**Symptoms requiring CPU profiling:**
- High CPU usage (>80% sustained)
- Slow response times
- Application feels sluggish
- Scalability problems under load

**Questions CPU profiling answers:**
- Which methods are slowest?
- What's calling those slow methods?
- Are there any unexpected operations in hot paths?
- Is CPU time spent on actual work or overhead?

## Visual Studio CPU Profiler

### Starting a CPU Profiling Session

**Method 1: Debug Menu**
```
1. Open your project in Visual Studio
2. Set configuration to Release (not Debug!)
3. Debug → Performance Profiler (Alt+F2)
4. Check "CPU Usage"
5. Click "Start"
6. Exercise the application (reproduce slow scenario)
7. Click "Stop Collection"
```

**Method 2: Diagnostic Tools While Debugging**
```csharp
// While debugging, the Diagnostic Tools window shows live CPU usage
// Debug → Windows → Show Diagnostic Tools (Ctrl+Alt+F2)

public async Task<List<Product>> GetProducts()
{
    // Set breakpoint here
    var products = await _db.Products.ToListAsync();
    
    // CPU usage tracked automatically during debugging
    return products;
}
```

### Interpreting CPU Usage Results

**Hot Path View:**
```
The hot path shows the call stack consuming the most CPU time:

MyApp.Controllers.ProductController.GetProducts (1,245 ms)
  └─ EntityFramework.Core.DbSet.ToListAsync (1,200 ms)
      └─ System.Linq.Enumerable.Select (1,150 ms)
          └─ MyApp.Models.Product.CalculateDiscount (1,100 ms)  ← HOT PATH!
```

**Key metrics:**
- **Self CPU (%):** Time spent in this function itself (excluding called functions)
- **Total CPU (%):** Time spent in this function and all functions it calls
- **Module:** Which DLL/assembly the code belongs to

### Example: Identifying a Bottleneck

```csharp
// Before profiling - suspected slow code
public class ProductService
{
    public List<ProductDto> GetProductsWithPricing(List<Product> products)
    {
        var result = new List<ProductDto>();
        
        foreach (var product in products)
        {
            var dto = new ProductDto
            {
                Id = product.Id,
                Name = product.Name,
                Price = CalculatePrice(product),  // CPU profiler shows this is slow!
                Discount = CalculateDiscount(product)
            };
            result.Add(dto);
        }
        
        return result;
    }

    private decimal CalculatePrice(Product product)
    {
        // Profiler reveals: Complex pricing logic called in a loop
        // 500ms of 600ms total time spent here
        Thread.Sleep(1); // Simulating expensive calculation
        
        return product.BasePrice * GetMultiplier() * GetTax();
    }
}

// After profiling - optimized
public class ProductService
{
    public List<ProductDto> GetProductsWithPricing(List<Product> products)
    {
        // Pre-calculate values used for all products
        var multiplier = GetMultiplier();
        var tax = GetTax();
        
        var result = new List<ProductDto>(products.Count); // Pre-size list
        
        foreach (var product in products)
        {
            var dto = new ProductDto
            {
                Id = product.Id,
                Name = product.Name,
                Price = product.BasePrice * multiplier * tax, // Inlined and optimized
                Discount = CalculateDiscount(product)
            };
            result.Add(dto);
        }
        
        return result;
    }
}
```

## PerfView: Advanced CPU Profiling

### Why Use PerfView?

**PerfView advantages:**
- Free, open-source from Microsoft
- Very low overhead (suitable for production)
- Captures kernel events (complete picture)
- Works without Visual Studio
- Supports ETW (Event Tracing for Windows)
- Single executable, no installation required

**Use PerfView when:**
- Profiling in production environments
- Analyzing third-party libraries (no source code)
- Investigating system-level bottlenecks
- Visual Studio profiler isn't available

### Installing and Running PerfView

```bash
# Download
# Visit: https://github.com/microsoft/perfview/releases
# Download: PerfView.exe

# Run (requires Administrator privileges for full ETW)
# Right-click PerfView.exe → Run as Administrator

# Basic collection
PerfView.exe collect -MaxCollectSec:30 MyApp.exe

# Collect for running process
PerfView.exe collect -MaxCollectSec:30

# In PerfView UI:
# 1. Collect → Run
# 2. Enter command: MyApp.exe
# 3. Work with the app
# 4. Click "Stop Collection"
```

### Analyzing PerfView Traces

**Opening CPU Stacks:**
```
1. Open .etl.zip file in PerfView
2. Double-click "CPU Stacks"
3. Wait for symbols to load
4. Analyze in one of these views:
   - By Name (grouped by method)
   - Caller-Callee (who calls whom)
   - Call Tree (hierarchical view)
```

**Example Analysis:**
```
CPU Stacks View:

Name                                          | Inc %  | Exc %  | Count
----------------------------------------------|--------|--------|-------
MyApp.exe!ProductService.GetProducts          | 45.2%  |  2.1%  | 12,450
  └─ MyApp.exe!ProductService.CalculatePrice  | 43.1%  | 43.1%  | 12,450  ← 43% self time!
  
Interpretation:
- GetProducts spends 45.2% of total CPU (inclusive)
- CalculatePrice spends 43.1% of total CPU (exclusive)
- CalculatePrice is called 12,450 times
- Clear optimization target!
```

### Reading Flame Graphs in PerfView

```
Flame Graph (Bottom-up visualization):

[Main]                                    100%
├─ [HTTP Request Handler]                  85%
│  ├─ [ProductController.GetProducts]      70%
│  │  └─ [CalculatePrice] ←── WIDE BAR = HOT PATH (50%)
│  └─ [Authentication]                     15%
└─ [Background Tasks]                      15%

Wider bars = More time spent
Focus optimization on the widest bars
```

## Common CPU Performance Issues

### Issue 1: Synchronous Blocking

```csharp
// ❌ CPU profiler shows thread blocked
public ActionResult GetData()
{
    var result = _httpClient.GetAsync("https://api.example.com/data")
        .Result;  // Blocks thread pool thread
    
    return Json(result);
}

// ✅ Profiler shows no blocking
public async Task<ActionResult> GetData()
{
    var result = await _httpClient.GetAsync("https://api.example.com/data");
    return Json(result);
}
```

### Issue 2: N+1 Queries

```csharp
// ❌ Profiler shows many database round-trips
public List<OrderDto> GetOrders()
{
    var orders = _db.Orders.ToList();
    
    return orders.Select(o => new OrderDto
    {
        Id = o.Id,
        // Each call hits database - shows up in profiler!
        CustomerName = _db.Customers.Find(o.CustomerId).Name  
    }).ToList();
}

// ✅ Profiler shows single query
public List<OrderDto> GetOrders()
{
    var orders = _db.Orders
        .Include(o => o.Customer)  // Eager loading
        .ToList();
    
    return orders.Select(o => new OrderDto
    {
        Id = o.Id,
        CustomerName = o.Customer.Name
    }).ToList();
}
```

### Issue 3: Inefficient Algorithms

```csharp
// ❌ O(n²) algorithm - profiler shows this method dominating CPU
public List<int> FindDuplicates(List<int> numbers)
{
    var duplicates = new List<int>();
    
    for (int i = 0; i < numbers.Count; i++)
    {
        for (int j = i + 1; j < numbers.Count; j++)
        {
            if (numbers[i] == numbers[j])
                duplicates.Add(numbers[i]);
        }
    }
    
    return duplicates;
}

// ✅ O(n) algorithm - profiler shows dramatic improvement
public List<int> FindDuplicates(List<int> numbers)
{
    var seen = new HashSet<int>();
    var duplicates = new HashSet<int>();
    
    foreach (var num in numbers)
    {
        if (!seen.Add(num))
            duplicates.Add(num);
    }
    
    return duplicates.ToList();
}
```

### Issue 4: Excessive String Concatenation

```csharp
// ❌ Profiler shows many string allocations
public string BuildReport(List<Item> items)
{
    string report = "";
    
    foreach (var item in items)
    {
        report += $"{item.Name}: {item.Value}\n";  // New string each iteration!
    }
    
    return report;
}

// ✅ Profiler shows minimal allocations
public string BuildReport(List<Item> items)
{
    var sb = new StringBuilder(items.Count * 50);  // Pre-size
    
    foreach (var item in items)
    {
        sb.AppendLine($"{item.Name}: {item.Value}");
    }
    
    return sb.ToString();
}
```

## Profiling Workflow

### Step 1: Reproduce the Issue

```csharp
// Create a reproducible scenario
public class PerformanceTest
{
    [Fact]
    public void SlowOperation_ShouldBeProfiled()
    {
        // Start profiler before this test
        var service = new ProductService();
        
        // Reproduce slow scenario
        var products = GenerateTestProducts(10000);
        var result = service.GetProductsWithPricing(products);
        
        // Stop profiler
        // Analyze results
    }
}
```

### Step 2: Collect Profile Data

**Visual Studio:**
1. Set Release configuration
2. Performance Profiler → CPU Usage
3. Start
4. Run scenario
5. Stop

**PerfView:**
```bash
# Collect 30 seconds of data
PerfView collect -MaxCollectSec:30 -ThreadTime

# Or attach to running process
PerfView collect -MaxCollectSec:30 -ThreadTime -ProcessId:12345
```

### Step 3: Analyze Results

**Look for:**
- Methods with high **Exclusive (Self) CPU %**
- Unexpected methods in hot paths
- Long call chains
- Frequent small operations (death by a thousand cuts)

### Step 4: Optimize and Re-Profile

```csharp
// Optimization cycle
public class OptimizationWorkflow
{
    public void OptimizationCycle()
    {
        // 1. Profile baseline
        var baselineMetrics = ProfileOperation();
        // Result: 500ms, CalculatePrice is hot path
        
        // 2. Optimize
        OptimizeCalculatePrice();
        
        // 3. Profile again
        var optimizedMetrics = ProfileOperation();
        // Result: 150ms, 70% improvement!
        
        // 4. Verify improvement
        Assert.That(optimizedMetrics.Duration, 
            Is.LessThan(baselineMetrics.Duration * 0.5));
    }
}
```

## Best Practices

### 1. Profile in Release Mode

```
❌ Profiling in Debug mode gives misleading results
   - JIT optimizations disabled
   - Additional checks and assertions
   - Different code generation

✅ Always profile in Release mode
   - Matches production behavior
   - JIT optimizations enabled
   - Realistic performance characteristics
```

### 2. Profile Realistic Scenarios

```csharp
// ❌ Bad profiling scenario
var product = new Product { Id = 1, Name = "Test" };
var result = service.ProcessProduct(product);

// ✅ Good profiling scenario
var products = LoadProductionDataSample(count: 10000);
var stopwatch = Stopwatch.StartNew();

foreach (var product in products)
{
    service.ProcessProduct(product);
}

stopwatch.Stop();
Console.WriteLine($"Processed {products.Count} products in {stopwatch.ElapsedMilliseconds}ms");
```

### 3. Focus on Hot Paths

```
Pareto Principle: 80% of time spent in 20% of code

Don't optimize everything - optimize hot paths:
✅ Method with 40% CPU usage
✅ Tight loop called millions of times
❌ Method with 0.1% CPU usage
❌ Initialization code run once
```

### 4. Measure Before and After

```csharp
public class PerformanceComparison
{
    [Benchmark(Baseline = true)]
    public void Original()
    {
        // Original implementation
        // Baseline: 500ms
    }

    [Benchmark]
    public void Optimized()
    {
        // Optimized implementation
        // Should measure: <250ms (50% improvement)
    }
}
```

### 5. Use Symbol Servers

```
For meaningful profiling results, load symbols:

Visual Studio:
- Tools → Options → Debugging → Symbols
- Add Microsoft Symbol Servers

PerfView:
- Loads symbols automatically
- Set _NT_SYMBOL_PATH environment variable for offline symbols
```

## Practice Exercise

1. **Create a simple console application** with intentional CPU bottlenecks:

```csharp
public class PerformanceTestApp
{
    public static void Main()
    {
        var app = new PerformanceTestApp();
        
        // This should take 2-3 seconds
        app.SlowOperation();
        
        Console.WriteLine("Press any key to exit...");
        Console.ReadKey();
    }

    public void SlowOperation()
    {
        var numbers = Enumerable.Range(1, 10000).ToList();
        
        // Intentionally slow: O(n²)
        for (int i = 0; i < numbers.Count; i++)
        {
            for (int j = 0; j < numbers.Count; j++)
            {
                var sum = numbers[i] + numbers[j];
            }
        }
    }
}
```

2. **Profile the application**:
   - Use Visual Studio CPU Profiler
   - Identify the hot path (nested loop)
   - Note the CPU percentage and time

3. **Optimize the code**:
   - Remove unnecessary nested loop
   - Profile again
   - Measure improvement

4. **Try with PerfView**:
   - Download PerfView
   - Collect a trace of your application
   - Analyze CPU Stacks
   - Compare results with Visual Studio

## Summary

CPU profiling reveals where your application spends processor time, enabling data-driven optimization. Visual Studio provides an integrated profiler suitable for most scenarios, while PerfView offers advanced capabilities for production environments and system-level analysis. Always profile in Release mode, focus on hot paths with high CPU usage, and measure before and after optimizations to verify improvements.
