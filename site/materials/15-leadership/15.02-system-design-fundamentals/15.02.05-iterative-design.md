# Lesson 5: Iterative Design and Refinement

## Learning Objectives

By the end of this lesson, you will be able to:
- Apply a structured iterative approach to system design
- Identify and address bottlenecks in initial designs
- Refine designs based on feedback and constraints
- Use prototyping to validate assumptions

---

## Introduction

System design is never a one-shot process. You start with a simple design, identify problems, refine the solution, and repeat. This iterative approach prevents over-engineering while ensuring you address real constraints. This lesson covers the methodology for continuous design improvement.

## Key Concepts Summary

### The Iterative Design Process

System design follows a cyclical process, not a linear one:

```
1. Clarify Requirements
        ↓
2. Create Initial Design
        ↓
3. Identify Bottlenecks
        ↓
4. Refine Design
        ↓
5. Validate with Prototyping
        ↓
6. Gather Feedback
        ↓
   (Loop back to step 3 or 4)
```

### Step 1: Clarify Requirements (Already Covered)

```
Quick Recap:
- Functional requirements (what features?)
- Non-functional requirements (how well?)
- Scale requirements (how many users?)
- Constraints (budget, timeline, tech stack?)

Time: 5-10 minutes in an interview, longer in real projects
```

### Step 2: Create Initial High-Level Design

Start simple—don't try to solve everything at once.

#### Initial Design Template

```
Version 1.0 (Simplest Possible Design):

Client
  ↓
Single Server (Business Logic)
  ↓
Single Database

This handles:
- Basic functionality
- Small scale (hundreds of users)
- Helps identify what needs scaling
```

#### Example: URL Shortener v1.0

```
Client (Browser)
  ↓
API Server
  ↓
PostgreSQL Database

Tables:
- urls: {id, short_code, long_url, created_at}

Problems This Will Have:
- Single point of failure
- Won't scale beyond ~10K requests/second
- No caching for hot URLs
- Database becomes bottleneck

But That's OK! We'll refine next.
```

### Step 3: Identify Bottlenecks

Walk through your design and ask critical questions:

#### Bottleneck Identification Questions

**Performance Bottlenecks:**
```
- Where is the slowest operation?
- What happens under peak load?
- Which component will max out first?
- Are there network calls that could be cached?
```

**Scalability Bottlenecks:**
```
- What happens if traffic doubles? 10x?
- Can we add more servers? Or is DB the limit?
- Are there single points of failure?
- What's the read:write ratio?
```

**Reliability Bottlenecks:**
```
- What if the database goes down?
- What if a server crashes?
- How do we handle network partitions?
- Where could we lose data?
```

#### Example: URL Shortener Bottlenecks

```
Bottleneck Analysis:

1. Database Overload:
   - 100K reads/second → Database can't handle
   - Problem: Reading from disk is slow

2. Single Point of Failure:
   - If server dies, entire service down
   - If database dies, service down

3. No Geographic Distribution:
   - Users in Asia experience high latency
   - Problem: Server in US, round-trip time ~200ms

Priority: Fix #1 first (biggest impact)
```

### Step 4: Refine Design to Address Bottlenecks

For each bottleneck, apply a solution:

#### Common Refinement Patterns

**Pattern 1: Add Caching**
```
Problem: Database overloaded with reads

Before:
Client → Server → Database

After:
Client → Server → Cache (Redis) → Database
                     ↑
                   (90% hits)

Impact:
- 90% of reads served from cache
- Database load reduced 10x
- Response time: 200ms → 10ms
```

**Pattern 2: Add Load Balancer**
```
Problem: Single server can't handle traffic

Before:
Client → Single Server → Database

After:
Client → Load Balancer → [Server 1, Server 2, Server 3] → Database

Impact:
- Capacity tripled
- No single point of failure
- Can scale horizontally
```

**Pattern 3: Database Replication**
```
Problem: Database read bottleneck

Before:
Servers → Single Database

After:
Servers → [Master DB, Replica 1, Replica 2]
           (writes)   (reads)    (reads)

Impact:
- Read capacity tripled
- Write capacity unchanged
- Eventual consistency on reads
```

**Pattern 4: Database Sharding**
```
Problem: Database write bottleneck or data too large

Before:
Servers → Single Database (1B records)

After:
Servers → Router → [Shard 1, Shard 2, Shard 3]
                    (A-H)    (I-P)     (Q-Z)

Impact:
- Write capacity tripled
- Read capacity tripled
- Complexity increased
```

**Pattern 5: Add CDN**
```
Problem: High latency for global users

Before:
Global Clients → Server (US) → Database

After:
Global Clients → CDN (Edge Locations) → Server (US) → Database

Impact:
- Latency reduced 10x for static content
- Server load reduced
- Better user experience
```

#### Example: URL Shortener v2.0 (Refined)

```
Client
  ↓
CDN (for static assets)
  ↓
Load Balancer
  ↓
[API Server 1, API Server 2, API Server 3]
  ↓
Redis Cache (Hot URLs) ← 90% cache hit rate
  ↓ (on cache miss)
PostgreSQL (Master) → [Replica 1, Replica 2]
(writes)               (reads)

Improvements:
✓ Cache reduces DB load by 90%
✓ Load balancer enables horizontal scaling
✓ Database replicas handle read traffic
✓ No single point of failure

Remaining Issues:
- Master database still single point of failure for writes
- No geographic distribution (all in one region)
- Cache invalidation complexity
```

### Step 5: Validate with Prototyping

Don't just theorize—validate your assumptions:

#### Prototyping Strategies

**1. Paper Prototypes (Architecture Diagrams)**
```
Purpose: Visualize component interactions
Time: 30 minutes
Value: Catch logical errors early

Process:
- Draw component diagram
- Walk through user flows
- Identify missing pieces
```

**2. Proof of Concept (Minimal Implementation)**
```
Purpose: Validate critical technical assumptions
Time: 1-3 days
Value: Identify implementation challenges

Example:
- Build simple cache + database integration
- Test cache hit rates with realistic data
- Measure actual latency improvements
```

**3. Load Testing (Benchmarking)**
```
Purpose: Validate capacity estimates
Time: 1-2 days
Value: Real performance numbers vs. estimates

Example:
- Set up 1 server + 1 database
- Simulate 1000 concurrent users
- Measure: RPS, latency, error rate
- Extrapolate to production scale
```

**4. Pilot / Beta Testing**
```
Purpose: Validate with real users
Time: 2-4 weeks
Value: Real-world usage patterns

Example:
- Deploy to 1% of users
- Monitor metrics: latency, errors, usage
- Gather feedback
- Iterate before full rollout
```

### Step 6: Gather Feedback and Iterate

Collect feedback from multiple sources:

#### Feedback Sources

**Technical Feedback:**
```
- Code reviews from peers
- Architecture reviews from senior engineers
- Performance testing results
- Monitoring data from production
```

**Stakeholder Feedback:**
```
- Product managers: Feature priority
- Business: Cost constraints
- Users: UX and performance
- Operations: Maintainability
```

**Metrics to Monitor:**
```
- Response time (P50, P95, P99)
- Error rate
- Throughput (requests/second)
- Resource utilization (CPU, memory)
- Cost per request
```

### The Full Iterative Cycle: Example

#### Iteration 1: Twitter-like Feed (Naive)

```
Initial Design:
Client → Server → Database

Generate feed by:
- Query all followees' posts
- Sort by timestamp
- Return top 100

Problem Identified:
- User with 10K followees: Query takes 5 seconds
- Database overloaded with complex queries
```

#### Iteration 2: Add Caching

```
Refined Design:
Client → Server → Cache → Database

Pre-compute feeds:
- Worker generates feeds offline
- Store in cache (Redis)
- Serve from cache

Problem Identified:
- Celebrity tweets (10M followers) → 10M feed updates
- Worker can't keep up with writes
```

#### Iteration 3: Fanout on Write + Read

```
Further Refined:
Normal users: Fanout on write (pre-compute feeds)
Celebrities: Fanout on read (compute on demand)

Hybrid approach:
- Regular users: Pre-computed feeds in cache
- Celebrity posts: Fetch on-demand when user loads feed

Result:
- Feed generation: 5 seconds → 50ms
- Scales to millions of users
- Handles celebrity use case
```

### Iterative Design Principles

#### Principle 1: Start Simple

```
Don't design for 1 billion users on day 1.

Start: Handle current scale (10K users)
Then: Add components to reach next milestone (100K)
Finally: Reach target scale (1M+)

Why: Over-engineering wastes time and adds complexity
```

#### Principle 2: Measure, Don't Assume

```
Bad: "I think caching will help"
Good: "Cache hit rate is 85%, reducing DB load by 85%"

Always:
- Measure before optimizing
- Benchmark solutions
- Monitor production
```

#### Principle 3: Solve Real Bottlenecks

```
Optimize based on:
- Monitoring data
- User feedback
- Load testing

Don't optimize based on:
- Gut feeling
- What's trendy
- Premature optimization
```

#### Principle 4: Know When to Stop

```
Don't iterate forever.

Stop when:
- Requirements are met
- Bottlenecks are addressed
- Design is "good enough"

"Perfect is the enemy of good."
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 30 minutes):

**Iterative Design: Photo Sharing App**

**Requirements:**
- 10M daily active users
- Users upload 50M photos per day
- Users view 500M photos per day (10:1 read:write ratio)
- Photos average 2 MB each
- Need low latency globally

**Tasks:**

1. **Draw Initial Design (v1.0):**
   - Simplest possible architecture
   - Identify 3 bottlenecks

2. **Refine to v2.0:**
   - Address the most critical bottleneck
   - Show updated architecture

3. **Refine to v3.0:**
   - Address the second bottleneck
   - Show final architecture

4. **Validation Plan:**
   - How would you validate this design before building?
   - What metrics would you monitor?
