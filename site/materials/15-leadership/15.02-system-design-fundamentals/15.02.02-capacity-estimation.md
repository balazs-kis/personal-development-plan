# Lesson 2: Back-of-Envelope Capacity Estimation

## Learning Objectives

By the end of this lesson, you will be able to:
- Perform back-of-envelope calculations to estimate system capacity
- Use standard latency and throughput numbers as reference points
- Calculate storage, bandwidth, and server requirements
- Validate design feasibility before detailed planning

---

## Introduction

Back-of-envelope calculations are quick, rough estimates that help you determine if a design is feasible. They prevent spending weeks on designs that are fundamentally unworkable and help identify potential bottlenecks early. The goal isn't precision—it's catching order-of-magnitude problems.

## Key Concepts Summary

### Numbers Every Engineer Should Know

Memorize these reference points for quick calculations:

#### Powers of Two (Essential for Conversions)
```
2^10 ≈ 1 Thousand (1 KB)
2^20 ≈ 1 Million (1 MB)
2^30 ≈ 1 Billion (1 GB)
2^40 ≈ 1 Trillion (1 TB)
2^50 ≈ 1 Quadrillion (1 PB)
```

#### Latency Reference (From Fastest to Slowest)
```
L1 cache reference:                     0.5 ns
L2 cache reference:                     7 ns
Main memory (RAM) reference:            100 ns
Read 1 MB sequentially from memory:     250 μs (250,000 ns)
SSD random read:                        150 μs
Disk seek (HDD):                        10 ms
Read 1 MB sequentially from SSD:        1 ms
Read 1 MB sequentially from disk:       30 ms
Send packet CA → Netherlands → CA:      150 ms
```

**Key Takeaways:**
- Memory is ~100x faster than SSD
- SSD is ~100x faster than HDD
- Network across continents: ~150ms

#### Time Conversions
```
1 second = 1,000 milliseconds (ms)
1 millisecond = 1,000 microseconds (μs)
1 microsecond = 1,000 nanoseconds (ns)

Useful approximations:
- Seconds per day: ~86,400 (round to 90,000 or 100,000)
- Seconds per month: ~2.6M (round to 2.5M or 3M)
- Seconds per year: ~31.5M (round to 30M)
```

#### Throughput Benchmarks
```
Database (PostgreSQL):        ~10,000 queries per second (QPS)
Application Server:           ~1,000 requests per second (RPS)
Redis (in-memory cache):      ~100,000 operations per second
SSD:                          ~100,000 IOPS
HDD:                          ~100-200 IOPS
```

### The Four-Step Estimation Process

#### Step 1: Clarify Scale with Explicit Assumptions

Start by defining the scale:

```
Example: Twitter-like Service

Users:
- Total users: 1 billion
- Daily active users (DAU): 200 million
- Posts per user per day: 0.5
- Reads per user per day: 20

Data:
- Average post size: 140 characters ≈ 280 bytes (UTF-16)
- With metadata (user ID, timestamp, etc.): ~500 bytes
- Average photo size: 200 KB
- 10% of posts include photos
```

**Write down ALL assumptions!** These show your thinking process.

#### Step 2: Calculate Core Metrics

Break down into traffic, storage, and bandwidth:

**Traffic Estimation:**
```
Write Traffic (Tweets):
- 200M DAU × 0.5 tweets/day = 100M tweets/day
- 100M tweets/day ÷ 86,400 seconds ≈ 1,160 tweets/second
- Peak traffic (3x average): ~3,500 writes/second

Read Traffic:
- 200M DAU × 20 reads/day = 4B reads/day
- 4B reads/day ÷ 86,400 ≈ 46,000 reads/second
- Peak: ~140,000 reads/second

Read:Write Ratio = 40:1
```

**Storage Estimation:**
```
Daily Storage:
Text: 100M tweets × 500 bytes = 50 GB/day
Photos: 10M photos × 200 KB = 2 TB/day
Total: ~2 TB/day

5-year projection:
2 TB/day × 365 days × 5 years = 3.65 PB
With replication (3x): ~11 PB
```

**Bandwidth Estimation:**
```
Write Bandwidth:
2 TB/day ÷ 86,400 seconds ≈ 23 MB/second

Read Bandwidth (40x writes):
23 MB/s × 40 = 920 MB/second ≈ 1 GB/second
```

#### Step 3: Apply Component Benchmarks

Estimate infrastructure needs:

```
Database Servers:
- Need to handle: 3,500 writes/s + 140,000 reads/s
- Database capacity: ~10,000 QPS
- Number of DB servers: 140,000 / 10,000 ≈ 14 servers
- With redundancy: ~20-25 servers

Application Servers:
- Total requests: ~140,000 RPS (mostly reads)
- App server capacity: ~1,000 RPS
- Number of app servers: 140,000 / 1,000 = 140 servers
- With redundancy and buffer: ~200 servers

Cache Servers (Redis):
- Assuming 80% of reads served from cache
- Cache requests: 140,000 × 0.8 = 112,000 RPS
- Redis capacity: ~100,000 ops/sec
- Number of cache servers: 2-3 servers
```

#### Step 4: Sanity Check

Validate your estimates:

```
Sanity Checks:
✓ Does 2 TB/day for 200M users seem reasonable?
  → 2 TB ÷ 200M users = 10 KB per user per day
  → That's ~20 posts per user (500 bytes each) ✓

✓ Is 11 PB of storage over 5 years realistic?
  → YouTube stores ~500 hours of video per minute
  → That's massive scale, Twitter is smaller ✓

✓ Can 200 app servers handle 200M users?
  → 200M / 200 = 1M users per server
  → Sounds high, but users aren't active simultaneously ✓

⚠️ If off by 1 order of magnitude (10x): Acceptable
❌ If off by 3+ orders of magnitude (1000x): Revisit assumptions
```

### Common Calculation Patterns

#### Pattern 1: Daily Active Users → Requests Per Second
```
Formula: DAU × actions_per_user_per_day ÷ 86,400

Example: 
10M DAU × 50 actions/day ÷ 86,400 = ~5,800 RPS average
Peak (3x): ~17,400 RPS
```

#### Pattern 2: Storage Growth Over Time
```
Formula: daily_data × days × replication_factor

Example:
5 TB/day × 365 days/year × 3 years × 3 replicas = 16.4 PB
```

#### Pattern 3: Bandwidth from Data Volume
```
Formula: total_data_per_day ÷ 86,400

Example:
100 TB/day ÷ 86,400 = ~1.16 GB/second
```

#### Pattern 4: Server Count from RPS
```
Formula: total_RPS ÷ capacity_per_server × buffer_factor

Example:
50,000 RPS ÷ 1,000 RPS per server × 1.5 buffer = 75 servers
```

### Real-World Example: YouTube Storage Estimation

Let's walk through a complete example:

```
Assumptions:
- 1 billion active users
- 1 in 1,000 users uploads video daily = 1M videos/day
- Average video length: 10 minutes
- Average video size: 1 GB (after compression)
- Retention: 3 years

Calculation:
Raw Storage per Day:
1M videos × 1 GB = 1 PB/day

Encoding Formats (480p, 360p, 240p, 144p):
Each format is ~1/2 the size of the previous
Total encoded: 1 PB + 0.5 PB + 0.25 PB + 0.125 PB ≈ 2 PB

Replication (3x for redundancy):
2 PB × 3 = 6 PB

Total Daily Storage: 6 PB (encoded) + 3 PB (raw) = 9 PB

Caching (frequently watched videos):
Top 20% of videos = 0.2 PB/day
Over 30 days: 6 PB in cache

3-Year Storage:
9 PB/day × 365 × 3 = ~10,000 PB = 10 Exabytes

Cost Estimate:
$25 per TB per year × 10M TB = $250M/year storage cost
```

### Tips for Accurate Estimates

#### 1. Round Aggressively
```
Bad:  86,400 seconds per day
Good: 90,000 or 100,000 (easier mental math)

Bad:  367.25 days per year
Good: 365 days
```

#### 2. Use Scientific Notation
```
Instead of: 5,000,000,000
Write:      5 × 10^9 or 5B
```

#### 3. Work in Orders of Magnitude
```
Focus on:
- Thousands (K) vs Millions (M)
- Gigabytes (GB) vs Terabytes (TB)
- Being off by 10x is okay
- Being off by 1000x suggests a problem
```

#### 4. State Assumptions Clearly
```
Write:
"Assuming 100M DAU, 10 actions per user per day,
peak traffic is 3x average"

Don't assume the interviewer knows your assumptions!
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 25 minutes):

**Estimate Capacity for Instagram-like Service**

Given:
- 1 billion users
- 200 million daily active users
- Each user uploads 2 photos per day
- Each user views 50 photos per day
- Average photo size: 2 MB (original)
- System stores 3 versions: original (2 MB), medium (500 KB), thumbnail (100 KB)

Calculate:
1. **Write traffic:** Photos uploaded per second (average and peak)
2. **Read traffic:** Photos viewed per second (average and peak)
3. **Storage per day:** Total storage needed daily
4. **Storage for 5 years:** Total storage with replication (3x)
5. **Bandwidth:** Write and read bandwidth in MB/second
6. **Server estimates:** Number of app servers needed (assume 1,000 RPS per server)

Show your work and assumptions!
