# Lesson 4: Balancing Speed and Thoroughness

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the relationship between review speed and team velocity
- Apply strategies to maintain fast turnaround without sacrificing quality
- Prioritize review feedback by impact and urgency
- Establish team SLAs for code review response times

---

## Introduction

One of the most challenging aspects of code review is balancing thoroughness with speed. Reviews that are too slow create bottlenecks, frustrate developers, and reduce team velocity. Reviews that are too fast miss critical issues and degrade code quality. The key insight is that speed and quality are not mutually exclusive—in fact, fast response times and thorough reviews reinforce each other. This lesson explores how to review code quickly without compromising on quality.

## Key Concepts Summary

### The Core Tension

**Individual vs Team Velocity:**

```markdown
❌ Wrong optimization:
"I need to stay in flow, so I'll review PRs at the end
of the day when I'm done coding."

Result: Authors wait hours/days, lose context, 
team velocity drops.

✅ Right optimization:
"Fast PR reviews keep the whole team moving. I'll review
at natural break points throughout the day."

Result: Authors stay in context, team velocity high,
overall output increased.

Google's Principle:
"Team velocity is more important than individual velocity."
```

**The Cost of Slow Reviews:**

```markdown
Slow reviews (multi-day turnaround):
❌ Developer loses context (re-learning code)
❌ Merge conflicts accumulate
❌ Feature releases delayed
❌ Frustration and disengagement
❌ Work-in-progress inventory builds up
❌ Team output decreases

Fast reviews (same-day turnaround):
✅ Developer stays in context
✅ Quick iteration on feedback
✅ Features ship faster
✅ High team morale
✅ Smooth workflow
✅ Team output increases
```

### Speed Benchmarks and Goals

**Industry Benchmarks (2025 Data):**

```markdown
📊 Median cycle time: 3 hours
   - Small PRs (< 100 lines): 2 hours
   - Medium PRs (100-400 lines): 4 hours
   - Large PRs (> 400 lines): 8+ hours

⚠️ Concerning trend:
   - 71% of PRs are self-merged (no peer review)
   - 90% of large PRs (1000+ lines) ship without review
   - Suggests teams sacrificing quality for speed

🎯 Optimal balance:
   - 100% of PRs reviewed
   - Response within 1 business day
   - Complete review within same day when possible
```

**Google's SLA:**

```markdown
Response time targets:

✅ One business day maximum
   "You should respond to a code review request shortly
   after it arrives, ideally within one business day."

✅ Same day when possible
   "If you are not in the middle of a focused task, you
   should do the code review shortly after it comes in."

✅ Interrupt guidelines:
   ❌ Don't interrupt focused coding work
   ✅ Review at natural break points:
      - Between tasks
      - After lunch
      - When returning from meetings
      - During compilation/deployment
```

### Strategies for Fast, Thorough Reviews

**1. Prioritize by Impact**

```markdown
Categorize feedback by priority:

🔴 BLOCKER (must fix before merge):
   - Security vulnerabilities
   - Data loss risks
   - Broken functionality
   - Production-breaking changes
   - Architectural violations

🟡 IMPORTANT (should fix):
   - Code quality issues
   - Missing tests for core paths
   - Performance concerns
   - Maintainability problems

🟢 NICE-TO-HAVE (optional):
   - Style improvements (if not automated)
   - Minor optimizations
   - Naming suggestions
   - Future enhancements

Example:
"[BLOCKER] SQL injection vulnerability on line 42
[IMPORTANT] Missing tests for error handling
[NIT] Consider more descriptive variable name"

This allows:
✅ Author knows what's critical
✅ Can merge with only blockers fixed
✅ Can defer nice-to-haves to future PRs
✅ Fast approval while maintaining quality
```

**2. Quick Initial Response**

```markdown
Even if you can't do full review immediately:

✅ Quick acknowledgment (< 30 minutes):
"Thanks! I'll review this before end of day."
"Got it. Will review after my 2pm meeting."
"On it. Should have feedback within 2 hours."

Benefits:
- Author knows PR is on your radar
- Sets expectations
- Prevents frustration
- Shows respect for their time
```

**3. Efficient Review Workflow**

```markdown
Staff engineer's workflow (10 minutes):

1. Read PR description (1 min)
   - Understand what and why
   - Check if approach makes sense
   - Note testing mentioned

2. Skim code changes (2 min)
   - Get overall structure
   - Identify areas needing deep focus
   - Check diff size and scope

3. Deep review of critical areas (5 min)
   - Business logic correctness
   - Security implications
   - Error handling
   - Test coverage

4. Quick scan of the rest (1 min)
   - Style issues (should be automated)
   - Obvious bugs
   - Naming clarity

5. Write feedback (1 min)
   - Prioritize blockers first
   - Group related comments
   - Be concise but clear

Total: ~10 minutes for typical PR
```

**4. Right-Size Pull Requests**

```markdown
❌ Large PRs (> 400 lines):
- Take too long to review
- Get superficial review
- Higher defect escape rate
- Multiple concepts mixed
- Merge conflicts likely

✅ Small PRs (< 200 lines):
- Quick to review thoroughly
- Focused on one thing
- Easy to spot issues
- Fast iteration
- Less risky to merge

Guidelines for authors:
✅ One logical change per PR
✅ Split large features into sequential PRs
✅ Extract refactoring to separate PR
✅ Aim for < 400 lines (including tests)

Exception: Generated code, data migrations
```

**5. Leverage Automation**

```markdown
Automate what slows human review:

✅ Pre-commit hooks:
   - Linting (ESLint, ReSharper, etc.)
   - Formatting (Prettier, Black, gofmt)
   - Basic security scans

✅ CI/CD pipeline:
   - Automated tests must pass
   - Code coverage thresholds
   - Static analysis (SonarQube)
   - Security scanning (Snyk, Dependabot)
   - Performance regression tests

✅ Branch protection rules:
   - Required checks before merge
   - Required approvals
   - Up-to-date with base branch

Result: Human reviewers focus on:
- Business logic
- Architecture decisions
- Design patterns
- Test quality
- Edge cases

Not on:
- Formatting
- Style violations
- Import ordering
- Simple security issues
```

### When to Interrupt Your Work

**Context Switching is Expensive:**

```markdown
❌ Don't interrupt when:
- Deep in complex problem solving
- Writing critical algorithm
- In a debugging flow
- Just started a task (< 15 min)

The cost: 15-30 minutes to regain context

✅ Do interrupt at natural breaks:
- Finished a task
- Waiting for build/deploy
- Between meetings
- After lunch/breaks
- Context switch already happening

The cost: Minimal
```

**Emergency Exception:**

```markdown
Immediate review justified when:
🚨 Production is down
🚨 Security vulnerability
🚨 Blocking other developers
🚨 Time-sensitive release

For emergencies:
✅ Explicitly mark PR as urgent
✅ Tag reviewer directly
✅ Explain urgency in description
✅ Keep PR minimal
```

### Quality Isn't Sacrificed

**Research Shows:**

```markdown
Code review catches 60-90% of defects before production.

Fast reviews maintain quality because:

1. **Author stays in context**
   - Remembers design decisions
   - Can quickly address feedback
   - Less re-learning needed

2. **Shorter feedback loops**
   - More iterations possible
   - Incremental improvements
   - Learning accelerates

3. **Clearer communication**
   - Questions answered quickly
   - Misunderstandings resolved
   - Alignment maintained

4. **Better morale**
   - Less frustration
   - Positive team culture
   - Quality becomes natural

Slow reviews actually harm quality:
❌ Stale knowledge
❌ Rushed approvals to unblock
❌ Batch reviews (less thorough)
❌ Reviewers become bottleneck
```

### Establishing Team SLAs

**Define Clear Expectations:**

```markdown
Example team agreement:

📋 Code Review SLA

Response Time:
- Acknowledge within 4 hours
- Complete review within 1 business day
- Emergency reviews within 1 hour

PR Size Guidelines:
- Target: < 200 lines
- Maximum: 400 lines (excluding generated code)
- Large PRs (> 400): Requires justification

Review Depth:
- 100% of lines changed read
- Blockers identified immediately
- Nice-to-haves optional

Reviewer Assignment:
- 2 reviewers for critical changes
- 1 reviewer for routine changes
- Rotate reviewers for knowledge sharing

Availability:
- Mark yourself unavailable if can't review
- Reassign if no capacity
- Track pending reviews in standups

Escalation:
- If no response in 1 day, ping again
- If still blocked, escalate to lead
- Critical PRs go to staff/principal engineer
```

**Monitor and Adjust:**

```markdown
Track metrics:
📊 Average time to first review
📊 Average time to merge
📊 Number of pending reviews
📊 Review load per person
📊 Defects found in review vs production

Review in retrospectives:
- What's working well?
- Where are bottlenecks?
- Who's overloaded?
- How can we improve?

Adjust SLAs based on reality.
```

### Practical Time Management

**For Reviewers:**

```markdown
✅ Block review time on calendar:
   - 30 min morning
   - 30 min after lunch
   - 15 min end of day

✅ Batch small reviews:
   - Review 3-4 small PRs in one sitting
   - More efficient than context switching

✅ Deep review time for complex PRs:
   - Schedule dedicated 30-60 min block
   - No interruptions
   - Full focus

✅ Use PR size to estimate:
   - < 100 lines: 5-10 minutes
   - 100-400 lines: 15-30 minutes
   - > 400 lines: 30-60 minutes (or request split)
```

**For Authors:**

```markdown
✅ Make reviewer's job easier:
   - Clear PR description
   - Link to context (tickets, docs)
   - Self-review first
   - Note areas needing extra attention
   - Add test plan

✅ Choose reviewers strategically:
   - Expert for critical changes
   - Team member for knowledge sharing
   - Check their availability
   - Rotate to distribute load

✅ Time your PRs:
   - Avoid end-of-day submissions
   - Consider time zones
   - Don't submit Friday afternoon
   - Split if approaching size limit
```

## Practice Exercise

After completing the materials (15-20 minutes):

1. **Time Yourself:**
   - Find a public PR to review
   - Time how long it takes
   - Use the efficient workflow: description → skim → deep areas → feedback
   - Target: < 15 minutes

2. **Prioritize Feedback:**
   - Take a PR with multiple issues
   - Categorize each as BLOCKER / IMPORTANT / NIT
   - Practice: Would you approve with only blockers fixed?

3. **Calculate Team Impact:**
   - Current average review time: ___ hours
   - Number of PRs per week: ___
   - If reduced by 50%, time saved: ___ hours/week
   - What could the team accomplish with that time?

4. **Draft Team SLA:**
   - Write a 1-page code review SLA for your team
   - Include: response times, PR sizes, review depth
   - Make it realistic and measurable
