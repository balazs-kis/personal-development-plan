## Introduction

Code review is a cornerstone of software engineering quality and team learning. At its core, code review is the process where someone other than the code author examines code changes before they're merged. However, effective code review goes far beyond bug detection—it's a tool for knowledge sharing, maintaining standards, and building team culture. Understanding the fundamentals sets the foundation for using code review as a leadership tool.

## Key Concepts Summary

### Why Code Review Matters

**Primary Goals:**

```markdown
1. **Improve Code Quality**
   - Catch bugs before production
   - Ensure consistent coding standards
   - Identify design issues early

2. **Share Knowledge**
   - Spread understanding of the codebase
   - Learn new techniques and patterns
   - Build shared ownership

3. **Maintain Standards**
   - Enforce architectural decisions
   - Apply security best practices
   - Keep technical debt manageable

4. **Build Team Culture**
   - Foster collaboration
   - Develop communication skills
   - Create psychological safety
```

**Research-Backed Benefits:**

```markdown
✅ Catches 60-90% of defects before production
✅ Reduces cost of fixing bugs by 10-100x
✅ Accelerates onboarding for new team members
✅ Distributes system knowledge across the team
✅ Improves code maintainability over time
```

### The Golden Rule: Improve Overall Code Health

**Google's Core Principle:**

> "In doing a code review, you should make sure that the code health is improving over time. Reviewers should approve a change once it definitely improves the overall code health, even if the change isn't perfect."

```markdown
❌ Wrong mindset:
"This code must be perfect before I approve it."
"I would have written this differently, so I'll request changes."

✅ Right mindset:
"Does this code make the system better than before?"
"Is this good enough to improve health while allowing progress?"

Key insight: Favor continuous improvement over perfection.
```

**Balancing Quality and Progress:**

```markdown
Approve code that:
✅ Improves overall system health
✅ Is maintainable by the team
✅ Follows agreed-upon standards
✅ Doesn't introduce significant new problems

Request changes when:
❌ Code will degrade system health
❌ Introduces security vulnerabilities
❌ Breaks critical functionality
❌ Violates architectural principles
❌ Adds significant technical debt
```

### What to Look For in Code Review

**Priority Order:**

```markdown
1. **Design** (Highest Priority)
   - Is the code well-designed?
   - Does it fit appropriately into the system?
   - Is this the right time to add this functionality?
   - Does it integrate well with the rest of the system?

2. **Functionality**
   - Does the code do what the author intended?
   - Will it behave correctly for end users?
   - Are edge cases handled?
   - Does it handle errors gracefully?

3. **Complexity**
   - Is the code more complex than necessary?
   - Could another developer quickly understand it?
   - Is it over-engineered for the current requirements?

4. **Tests**
   - Are there appropriate automated tests?
   - Are tests correct and useful?
   - Do they actually test the code?
   - Are edge cases covered?

5. **Naming**
   - Are variable, function, and class names clear?
   - Are they descriptive enough?
   - Do they follow team conventions?

6. **Comments**
   - Are comments clear and useful?
   - Do they explain *why* rather than *what*?
   - Is there unnecessary commented-out code?

7. **Style**
   - Does the code follow style guides?
   - Is formatting consistent?
   - Should be mostly automated!

8. **Documentation**
   - Are relevant docs updated?
   - Are public APIs documented?
   - Is the README accurate?
```

**What NOT to Focus On:**

```markdown
❌ Personal preferences (if style guide doesn't specify)
❌ Micro-optimizations without profiling data
❌ Refactoring unrelated code (out of scope)
❌ Perfect naming (good enough is fine)
❌ Style issues that can be automated
```

### Code Review Workflows

**1. Pull Request / Merge Request (Most Common)**

```markdown
Developer:
1. Creates feature branch
2. Makes changes and commits
3. Opens pull request with description
4. Addresses reviewer feedback
5. Gets approval and merges

Reviewer:
1. Receives notification
2. Reviews changes
3. Leaves comments (approve/request changes/comment)
4. Re-reviews after updates
```

**2. Pair Programming (Real-time Review)**

```markdown
✅ Pros:
- Immediate feedback
- Real-time knowledge transfer
- Faster resolution of questions

❌ Cons:
- Requires synchronous time
- Doesn't scale well
- Less time for deep thinking
```

**3. Over-the-Shoulder (Informal)**

```markdown
✅ Good for:
- Quick sanity checks
- Emergency fixes
- Trivial changes

❌ Not good for:
- Complex changes
- Learning opportunities
- Audit trail
```

### Common Code Review Anti-Patterns

**1. The Nitpicker**

```markdown
❌ Problem:
Every review has 30+ comments about minor style issues,
variable naming, whitespace, and personal preferences.

✅ Solution:
- Use automated linters and formatters
- Distinguish blocking issues from suggestions
- Use "Nit:" prefix for non-critical feedback
- Ask: "Will this matter in 6 months?"
```

**2. The Approval Stamp**

```markdown
❌ Problem:
Reviewer approves everything immediately without 
actually reading the code.

✅ Solution:
- Set team expectations for review depth
- Track defects that made it through review
- Make review part of developer accountability
- Rotate reviewers to maintain standards
```

**3. The Blocker**

```markdown
❌ Problem:
Reviewer blocks every PR for days/weeks,
demanding perfection and rewriting everything.

✅ Solution:
- Remember: "Better" not "perfect"
- Distinguish critical from nice-to-have
- Set SLAs for review response time
- Escalate if reviews consistently slow team
```

**4. The Ghost**

```markdown
❌ Problem:
Reviewer never responds to review requests,
leaving PRs in limbo indefinitely.

✅ Solution:
- Set team SLA (e.g., 1 business day response)
- Track pending reviews in standups
- Reassign if reviewer unavailable
- Build review into sprint capacity
```

**5. The Ego Battle**

```markdown
❌ Problem:
Reviews become arguments about personal preferences,
with neither side willing to compromise.

✅ Solution:
- Defer to style guides as authority
- Use data to resolve performance debates
- Escalate to team lead if needed
- Focus on code health, not being right
```

### Practical Guidelines

**For Authors:**

```markdown
✅ Write clear PR descriptions
   - What changed and why
   - Testing performed
   - Related tickets/issues

✅ Keep PRs small (< 400 lines ideal)
   - Easier to review thoroughly
   - Faster to get approved
   - Less risk in changes

✅ Self-review before requesting review
   - Catch obvious issues
   - Clean up debug code
   - Update tests and docs

✅ Respond to all comments
   - Address or acknowledge each one
   - Explain reasoning if not making change
   - Mark resolved when fixed
```

**For Reviewers:**

```markdown
✅ Respond quickly (within 1 business day)
   - Even if just: "I'll review this tomorrow"
   - Keeps author in context
   - Maintains team velocity

✅ Read every line that changed
   - Don't skim complex logic
   - Understand the context
   - Check related files too

✅ Be thorough but pragmatic
   - Focus on what matters
   - Allow room for iteration
   - Trust the author's expertise

✅ Take breaks between reviews
   - Context switching is expensive
   - Wait for natural break points
   - Don't review while frustrated
```

### Review Checklist Example

```markdown
## Code Review Checklist

### Functionality
- [ ] Code does what the PR description says
- [ ] Edge cases are handled
- [ ] Error handling is appropriate
- [ ] No security vulnerabilities

### Design
- [ ] Fits well into existing architecture
- [ ] Uses appropriate design patterns
- [ ] No over-engineering
- [ ] Separates concerns properly

### Tests
- [ ] New code has tests
- [ ] Tests are meaningful (not just for coverage)
- [ ] Edge cases are tested
- [ ] Tests pass locally

### Readability
- [ ] Code is easy to understand
- [ ] Names are clear and descriptive
- [ ] Comments explain "why" not "what"
- [ ] No unnecessary complexity

### Best Practices
- [ ] No duplicated code
- [ ] No hard-coded values (use config)
- [ ] Follows language idioms
- [ ] No obvious performance issues

### Documentation
- [ ] README updated if needed
- [ ] API docs updated if needed
- [ ] Comments for complex logic
```

## Practice Exercise

After completing the materials (15-20 minutes):

1. **Review Analysis:**
   - Find a public pull request (GitHub, GitLab)
   - Review it using Google's checklist
   - Identify: What would you approve? What would you question?
   - Note: Was there anything the reviewer missed?

2. **Anti-Pattern Identification:**
   - Think about code reviews you've experienced
   - Identify which anti-patterns you've seen
   - Brainstorm: How could they have been prevented?

3. **Team Standards:**
   - Draft a 1-page code review guideline for a team
   - Include: What to review, SLAs, how to give feedback
   - Make it specific enough to be useful
