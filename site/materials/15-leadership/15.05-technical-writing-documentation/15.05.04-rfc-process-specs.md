## Introduction

RFCs (Requests for Comments) are structured technical proposals that force systematic thinking and drive collaborative decisions before implementation begins. The real value lies not just in the document itself, but in the process of achieving clarity and alignment across teams. RFCs are used at many tech companies (Google, Amazon, Stripe) and in open standards organizations (IETF) to make better technical decisions.

## Key Concepts Summary

### What RFCs Solve

RFCs aren't primarily about documentation—they're about forcing systematic thinking and driving collaborative decisions before implementation begins.

**Key Problems RFCs Address:**

```markdown
1. **Stakeholder Alignment**
   Problem: Teams build different interpretations of requirements
   Solution: Single source of truth everyone reviews and approves

2. **Decision Archaeology**
   Problem: "Why did we choose Redis over Memcached?" - lost in Slack
   Solution: Documented reasoning for future reference

3. **Scope Creep Defense**
   Problem: Requirements expand during implementation
   Solution: Clear boundaries; defer features as "v2" without losing momentum

4. **Cross-Team Communication**
   Problem: Dependent teams unaware of changes
   Solution: RFC serves as coordination vehicle

5. **Early Issue Detection**
   Problem: Design flaws found during implementation
   Solution: Multiple reviewers catch issues before coding
```

### Key Principles for Effective RFCs

**1. Focus on Buy-In, Not Completeness:**

```markdown
❌ Wrong focus:
"I need to document every implementation detail"

✅ Right focus:
"I need reviewers to understand and approve the design implications"

Include details with material impact on acceptability.
Omit implementation minutiae that don't affect decisions.
```

**2. Spell Out Design Implications:**

```markdown
❌ Unclear implications:
"We'll use event-driven architecture."

✅ Clear implications:
"We'll use event-driven architecture. This means:
- Payment team must publish order.created events
- Inventory team must consume these events within 5 seconds
- Both teams need Kafka access and monitoring
- We'll have eventual consistency (order appears before inventory reserved)"
```

**3. Be Honest About Trade-offs:**

```markdown
Every design choice has pros and cons. Document both:

## Trade-offs: Microservices vs Monolith

### Microservices (Proposed)
✅ Independent deployment and scaling
✅ Technology flexibility per service
✅ Fault isolation
❌ Distributed system complexity
❌ Network latency between services
❌ Harder to debug and trace
❌ Operational overhead (more things to deploy/monitor)

### Monolith (Current)
✅ Simple deployment and debugging
✅ No network overhead
✅ Easy transactions
❌ All-or-nothing scaling
❌ Tight coupling
❌ Single failure point
```

**4. Pre-Review Feedback:**

```markdown
Before formal submission:
1. Discuss with key stakeholders informally
2. Socialize the idea in team meetings
3. Address major concerns early
4. Build consensus before formal review

This makes formal review smoother and faster.
```

**5. Clarify Status Throughout:**

```markdown
Distinguish commitments from examples:

❌ Ambiguous:
"The API will look like this: POST /orders {...}"
(Is this final or just an example?)

✅ Clear:
"The API will use REST POST for order creation.
Here's an illustrative example: POST /orders {...}
Final schema will be reviewed separately."
```

### The RFC Review Process

**Typical Flow:**

```markdown
1. **Draft** (Author)
   - Write initial RFC
   - Self-review for clarity
   - Duration: 2-5 days

2. **Internal Review** (Team)
   - Share with immediate team
   - Gather feedback
   - Iterate on major points
   - Duration: 1 week

3. **Stakeholder Review** (Wider Audience)
   - Share with affected teams
   - Collect comments
   - Address concerns
   - Duration: 1-2 weeks

4. **Architecture Review** (Architects/Staff+)
   - Present at review meeting
   - Answer questions
   - Get approval or iterate
   - Duration: 1 meeting + follow-ups

5. **Final Approval** (Decision Maker)
   - Get sign-off
   - Set status to Approved
   - Begin implementation

6. **Updates During Implementation**
   - Document significant changes
   - Amend RFC if design evolves
   - Keep it accurate
```

**Review Best Practices:**

```markdown
As an RFC Author:
✅ Welcome criticism—it makes the design better
✅ Respond to all comments (even if "acknowledged, not changing")
✅ Summarize decisions made during review
✅ Update RFC based on feedback
✅ Don't take feedback personally

As an RFC Reviewer:
✅ Read the entire RFC before commenting
✅ Focus on design implications, not style
✅ Suggest alternatives, don't just criticize
✅ Distinguish blocking concerns from nice-to-haves
✅ Review within agreed timeframe (don't block progress)
```

### Common RFC Pitfalls

**1. Too Much Detail:**
```markdown
❌ Don't include:
- Complete pseudo-code
- Variable naming decisions
- UI mockup pixel perfection

✅ Do include:
- API contracts
- Data schemas that other teams depend on
- Performance requirements
- Security boundaries
```

**2. Too Little Detail:**
```markdown
❌ "We'll use a database for persistence."

✅ "We'll use PostgreSQL for transactional data because:
- We need ACID guarantees for payment consistency
- Queries are primarily key-value lookups
- Expected scale: 10K writes/sec, 100K reads/sec
- Estimated data size: 500GB over 2 years"
```

**3. Ignoring Alternatives:**
```markdown
❌ Only presenting one solution

✅ Presenting 2-3 alternatives with honest trade-offs
Shows you did the analysis and builds trust
```

**4. Missing the "Why":**
```markdown
❌ "We'll use Redis."

✅ "We'll use Redis because our cache hit ratio is 95% and 
sub-millisecond latency is critical for user experience. 
We evaluated Memcached but chose Redis for persistence 
during restarts and data structure support for the 
leaderboard feature."
```

## Practice Exercise

After completing the materials (30-45 minutes):

1. **RFC Template Setup:**
   - Create an RFC template for your team/organization
   - Include all essential sections from this lesson
   - Add team-specific sections if needed

2. **Mini RFC Writing:**
   Write a 2-3 page RFC for a technical decision from your past work:
   - Choose a real architectural decision
   - Follow the RFC structure
   - Include problem, solution, alternatives, and trade-offs
   - Have a colleague review it

3. **RFC Review Practice:**
   Find a public RFC (Rust, Python, Fuchsia, or your company)
   - Read it as a reviewer
   - Identify: What questions would you ask?
   - Note: What was clear? What was confusing?

4. **Trade-off Analysis:**
   Take a technology choice (e.g., "REST vs GraphQL")
   - List 3 pros and 3 cons for each
   - Write a "Why we chose X" rationale
