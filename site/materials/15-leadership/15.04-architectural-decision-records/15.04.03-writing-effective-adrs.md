# Lesson 3: Writing Effective ADRs

## Learning Objectives

By the end of this lesson, you will be able to:
- Write clear, concise context sections that explain the "why"
- Document trade-offs and alternatives considered
- Focus on reasoning rather than implementation details
- Write consequences that are honest and comprehensive
- Avoid common ADR writing pitfalls
- Make ADRs scannable and actionable

---

## Introduction

A well-written ADR is concise yet complete, focusing on the reasoning behind decisions rather than implementation details. This lesson covers best practices for writing ADRs that your team will actually read and that future developers will find invaluable.

## Key Concepts Summary

### The Golden Rules of ADR Writing

```
1. Focus on WHY, not HOW
2. Document trade-offs, not just benefits
3. Be honest about negatives
4. Keep it concise (1-2 pages max)
5. Write for future readers
```

---

## Writing the Context Section

### What Makes Good Context?

**Good context answers:**
- What problem are we solving?
- Why does this problem exist?
- What constraints do we face?
- What requirements must we meet?
- Why is this decision needed now?

### Context Writing Pattern

```markdown
## Context

[Problem Statement]
We currently have X, which causes Y problem.

[Evidence]
Data shows: Z metric, measurements, load tests, user feedback.

[Constraints]
We must work within these limitations: budget, time, skills, etc.

[Requirements]
The solution must: list specific requirements.

[Trigger]
We need to decide this now because: upcoming deadline, scaling issue, etc.
```

### Example: Good vs Bad Context

❌ **Bad Context (too vague):**
```markdown
## Context
Our current database is slow and we need something better.
```

✅ **Good Context (specific and evidence-based):**
```markdown
## Context

Our PostgreSQL database handles 50k daily active users well, but 
we're planning to scale to 500k within 6 months as we launch in 
3 new markets.

Current performance metrics:
- P95 query latency: 300ms
- Database CPU: 70% during peak hours
- Database connection pool exhaustion during traffic spikes

Load testing at 200k concurrent users shows:
- Latency increases to 2000ms (P95)
- Database CPU hits 95%
- Connection timeouts cause 5% error rate

Constraints:
- $10k/month infrastructure budget
- 3-month implementation timeline
- Team has PostgreSQL expertise, limited NoSQL experience

Requirements:
- Support 500k daily active users
- Maintain sub-100ms P95 query latency
- 99.9% availability
- Geographic distribution (US, EU, APAC)
```

### Context Anti-Patterns

❌ **Solution in context:**
```markdown
## Context
We need to use microservices because they're better.
```
(This is a decision, not context)

❌ **Too much history:**
```markdown
## Context
In 2015 we chose PHP. In 2017 we added MySQL. In 2019 we 
refactored the auth system. In 2020...
[5 paragraphs of history]
```
(Only relevant history matters)

❌ **Implementation details:**
```markdown
## Context
We need to configure Redis with AOF persistence, RDB snapshots
every 60 seconds, maxmemory-policy allkeys-lru...
```
(This belongs in documentation, not context)

## Writing the Decision Section

### Decision Writing Pattern

```markdown
## Decision

[Clear statement]
We will use {technology/pattern} for {purpose}.

[Scope]
Specifically:
- {Specific aspect 1}
- {Specific aspect 2}
- {Specific aspect 3}

[What we're NOT doing]
Explicitly:
- We are NOT doing X (common misconception)
- This does NOT apply to Y (scope boundary)
```

### Example: Good vs Bad Decisions

❌ **Bad Decision (vague):**
```markdown
## Decision
We'll use the best database for our needs.
```

❌ **Bad Decision (too broad):**
```markdown
## Decision
We'll rewrite everything in microservices using Kubernetes,
switch to GraphQL APIs, adopt event sourcing, implement CQRS,
and use React for the frontend.
```
(This should be 5+ separate ADRs)

✅ **Good Decision (clear and specific):**
```markdown
## Decision

We will implement database read replicas using PostgreSQL 
streaming replication.

Specifically:
- 1 primary database for writes (us-east-1)
- 3 read replicas for read traffic:
  - 1 replica in us-east-1 (primary region)
  - 1 replica in eu-west-1 (Europe)
  - 1 replica in ap-southeast-1 (APAC)
- Application routes reads to nearest replica
- Writes always go to primary
- Use pgBouncer for connection pooling

Explicitly NOT in scope:
- Database sharding (different ADR if needed)
- Multi-primary writes (too complex for current needs)
- Migrating to NoSQL (PostgreSQL meets our requirements)
```

### Active Voice vs Passive Voice

✅ **Active voice (clear):**
```markdown
We will deploy Redis Cluster for session storage.
```

❌ **Passive voice (weak):**
```markdown
Redis Cluster will be deployed for session storage.
```

**Why it matters:** Active voice creates clear ownership and is more direct.

## Writing the Consequences Section

### The Honesty Principle

```
ADRs without negative consequences are:
├─ Incomplete
├─ Untrustworthy
└─ Useless for future decision-making
```

**Every decision has trade-offs. Document them honestly.**

### Consequences Structure

```markdown
## Consequences

### Positive
- {Benefit 1 with specific metric/outcome}
- {Benefit 2 with specific metric/outcome}
- {Benefit 3 with specific metric/outcome}

### Negative
- {Cost/downside 1 with specific impact}
- {Cost/downside 2 with specific impact}
- {Cost/downside 3 with specific impact}

### Risks
- {Risk 1}: {mitigation strategy}
- {Risk 2}: {mitigation strategy}

### Technical Debt
- {Known limitations and future work needed}
```

### Example: Honest Consequences

```markdown
## Consequences

### Positive
- Query latency reduced from 300ms to 50ms (P95)
- Can scale read traffic to 1M req/sec by adding replicas
- Geographic distribution reduces latency for EU users by 200ms
- No application code changes required (transparent)
- PostgreSQL team expertise applies directly

### Negative
- Replication lag introduces eventual consistency (typically 100-500ms)
- Increased operational complexity (4 databases to monitor vs 1)
- Higher infrastructure cost: $2k/month additional (3 replicas)
- Need to implement read-write splitting in application layer
- Some queries may read stale data during lag spikes

### Risks
- Replication lag can spike during high write volume
  - Mitigation: Monitor replication lag, alert at >1 second
- Primary database failure requires replica promotion
  - Mitigation: Automated failover with 30-second timeout
- Split-brain scenario if network partition occurs
  - Mitigation: Use connection pooler with health checks

### Technical Debt
- Application doesn't handle replication lag intelligently
  - Future: Implement "read-your-writes" consistency
- No automated failover testing
  - Future: Monthly chaos engineering exercises
- Replica promotion is manual process
  - Future: Implement automated promotion
```

### Consequences Anti-Patterns

❌ **Only positives:**
```markdown
## Consequences
- Everything is better
- No downsides
- Perfect solution
```
(Unrealistic - every decision has trade-offs)

❌ **Vague negatives:**
```markdown
## Consequences
- Some additional complexity
- Might cost a bit more
- Could be harder to maintain
```
(Not actionable - be specific)

❌ **Defensive language:**
```markdown
## Consequences
- The negative consequences aren't really that bad when you 
  think about it, and besides, the alternatives were worse...
```
(Be honest and direct)

## Documenting Alternatives

### Why Document Alternatives?

```
Future Developer: "Why didn't we use MongoDB?"

Without alternatives documented:
"🤷 No idea."

With alternatives documented:
"Read ADR-015, section 'Considered Options'. MongoDB was 
evaluated but rejected because..."
```

### Alternatives Pattern

```markdown
## Considered Options

### Option 1: {Name}
- **Pros:** {benefits}
- **Cons:** {downsides}
- **Cost:** {rough estimate}
- **Why rejected:** {specific reason}

### Option 2: {Name}
- **Pros:** {benefits}
- **Cons:** {downsides}
- **Cost:** {rough estimate}
- **Why chosen:** {specific reason}
```

### Example: Documenting Alternatives

```markdown
## Considered Options

### Option 1: Database Sharding
**Approach:** Split database into multiple shards by user ID

**Pros:**
- Scales both reads and writes
- No replication lag issues
- Each shard is independent

**Cons:**
- High complexity (application must route queries)
- Cross-shard queries are expensive
- Rebalancing shards is difficult
- Requires significant application changes

**Cost:** 3-6 months development time, $5k/month infrastructure

**Why rejected:** Complexity not justified for read-heavy workload

### Option 2: Read Replicas (CHOSEN)
**Approach:** Primary for writes, replicas for reads

**Pros:**
- Simpler than sharding
- Transparent to most application code
- Scales read traffic easily
- Team has expertise

**Cons:**
- Doesn't scale writes
- Replication lag (eventual consistency)

**Cost:** 2 weeks development time, $2k/month infrastructure

**Why chosen:** Solves immediate read scalability problem with 
minimal complexity

### Option 3: NoSQL Database (MongoDB)
**Approach:** Migrate to MongoDB for horizontal scalability

**Pros:**
- Horizontal scalability built-in
- No schema migrations needed
- Good for document-oriented data

**Cons:**
- Major rewrite required (2-3 months)
- Team lacks MongoDB expertise
- Lose ACID guarantees for some operations
- Migration risk

**Cost:** 3 months development time, $3k/month infrastructure

**Why rejected:** Migration risk and timeline unacceptable, 
PostgreSQL meets requirements
```

## Writing for Different Audiences

### Different readers, different needs:

```
Future You (6 months later):
├─ Why did we do this?
└─ What were we thinking?

New Team Member:
├─ How do things work here?
└─ What are the architectural principles?

Technical Lead (different team):
├─ Should we adopt this pattern?
└─ What are the trade-offs?

Executive/Stakeholder:
├─ What's the business impact?
└─ What does this cost?
```

### Multi-Audience Writing Pattern

```markdown
## Decision
[1 paragraph: clear statement for everyone]

We will use Redis Cluster for session storage.

## Context
[Technical detail for engineers]

Current session storage in PostgreSQL causes latency issues...

## Business Impact
[For non-technical stakeholders]

This change will:
- Improve user experience (page loads 40% faster)
- Support 10x user growth without infrastructure redesign
- Cost an additional $500/month
- Take 2 weeks to implement

## Consequences
[Honest assessment for future decision-makers]
...
```

## Keep It Concise

### The 1-2 Page Rule

```
ADR Length Guidelines:
├─ Simple decision: 1 page
├─ Complex decision: 2 pages
└─ If >3 pages: split into multiple ADRs
```

### Conciseness Techniques

**1. Use bullet points:**
```markdown
❌ Long paragraph:
The system must support high availability and we need to ensure
that if one component fails the others continue working and we
should have automatic failover...

✅ Bullet points:
Requirements:
- High availability (99.9% uptime)
- Automatic failover
- Graceful degradation
```

**2. Use tables for comparisons:**
```markdown
| Option | Latency | Cost | Complexity |
|--------|---------|------|------------|
| Redis | 5ms | $500 | Medium |
| Memcached | 3ms | $300 | Low |
| Database | 50ms | $200 | Low |
```

**3. Link to detailed docs:**
```markdown
## Implementation Details
See [Redis Cluster Setup Guide](../guides/redis-setup.md) for:
- Installation steps
- Configuration parameters
- Monitoring setup
```

**4. Use summaries:**
```markdown
## Context (TL;DR)
Current database is slow. Need to scale reads to 1M req/sec.

## Detailed Context
[Full explanation if reader needs it]
```

## Common Writing Pitfalls

### Pitfall 1: Implementation Details

❌ **Too much implementation:**
```markdown
## Decision
Configure Redis with these settings:
redis.conf:
  maxmemory 4gb
  maxmemory-policy allkeys-lru
  save 900 1
  save 300 10
[50 lines of configuration]
```

✅ **Right level for ADR:**
```markdown
## Decision
Use Redis Cluster with LRU eviction policy and persistence enabled.

Configuration details: See [Redis Setup Guide](../guides/redis.md)
```

### Pitfall 2: Justifying the Decision

❌ **Defensive:**
```markdown
## Decision
We chose PostgreSQL, which is the RIGHT choice despite what 
some people think. MongoDB would have been a DISASTER and 
anyone who suggests it clearly doesn't understand databases...
```

✅ **Objective:**
```markdown
## Decision
We chose PostgreSQL over MongoDB because:
1. Team expertise (3 years PostgreSQL, no MongoDB)
2. ACID requirements for financial transactions
3. Existing tooling and monitoring

MongoDB was evaluated but not chosen (see Considered Options).
```

### Pitfall 3: Future Predictions

❌ **Speculative:**
```markdown
## Consequences
This will solve all our scaling problems forever and we'll 
never need to revisit this decision.
```

✅ **Realistic:**
```markdown
## Consequences
This solves current scaling needs (0-500k users). At 1M+ users,
we may need to consider sharding (see ADR-XXX for future options).
```

### Pitfall 4: No Evidence

❌ **Opinion-based:**
```markdown
## Context
The database is slow and everyone complains about it.
```

✅ **Evidence-based:**
```markdown
## Context
Database metrics show:
- P95 latency: 300ms (SLA is 100ms)
- User satisfaction score: 6.2/10 (down from 8.5/10)
- Support tickets about "slow loading": 40/week
```

## ADR Review Checklist

Before publishing an ADR, check:

- [ ] **Title:** Clear, concise, uses action verb?
- [ ] **Status:** Appropriate status (Proposed, Accepted, etc.)?
- [ ] **Context:** Explains WHY decision is needed?
- [ ] **Evidence:** Includes data, metrics, or concrete examples?
- [ ] **Decision:** Clear and specific?
- [ ] **Alternatives:** At least 2 options considered?
- [ ] **Consequences:** Both positive AND negative listed?
- [ ] **Honesty:** Negative consequences are realistic, not sugar-coated?
- [ ] **Length:** 1-2 pages maximum?
- [ ] **Audience:** Readable by future developers?
- [ ] **Links:** Cross-references to related ADRs and docs?

## Real-World Example: Before and After

### Before (Poor ADR)

```markdown
# Use Microservices

## Status
Accepted

## Context
Monoliths are bad.

## Decision
We'll use microservices.

## Consequences
Everything will be better.
```

### After (Good ADR)

```markdown
# ADR-023: Split User Service from Monolith

## Status
Accepted (2024-01-15)

## Context

Our monolithic application has grown to 500k lines of code with
deployment taking 45 minutes. The User Service team (5 engineers)
is blocked by other teams during deploys.

Current pain points:
- Deploy frequency: 1x per week (teams coordinate)
- Deploy duration: 45 minutes with 15-minute freeze
- Incident recovery: Must redeploy entire app
- User Service changes: 40% of all commits but can't deploy 
  independently

Requirements:
- User Service must deploy independently
- Other services remain in monolith (gradual extraction)
- Maintain existing APIs (backward compatibility)

Timeline: Must complete before Q2 when User Service team doubles.

## Decision

Extract User Service as independent microservice, leaving other
services in monolith.

Specifically:
- User Service handles: auth, profile, preferences
- New service in separate repo with own CI/CD
- Communicates via gRPC with monolith
- Shares database initially (extract DB later in ADR-024)
- API Gateway routes /api/users/* to new service

NOT in scope:
- Other services stay in monolith
- Database not separated (phase 2)
- No infrastructure changes beyond new service

## Considered Options

### Option 1: Extract User Service (CHOSEN)
- Pros: Solves immediate deploy independence, low risk
- Cons: Database still coupled, not full microservices
- Timeline: 3 weeks
- Why chosen: Minimal risk, solves pain point

### Option 2: Split Entire Monolith
- Pros: Full microservices architecture
- Cons: 6-month project, high risk, blocks feature work
- Timeline: 6 months
- Why rejected: Too risky, timeline unacceptable

### Option 3: Keep Monolith, Improve CI/CD
- Pros: No architecture changes
- Cons: Doesn't solve team independence
- Timeline: 2 weeks
- Why rejected: Doesn't address root problem

## Consequences

### Positive
- User Service deploys independently (40+ deploys/month possible)
- Faster deploys: 5 minutes vs 45 minutes
- Incidents isolated (User Service issues don't affect others)
- User Service team unblocked from other teams

### Negative
- Increased operational complexity (2 services vs 1)
- Distributed tracing needed (adds monitoring overhead)
- Network latency between services (~5ms added)
- Team must learn gRPC and microservices patterns
- Database still coupled (technical debt)

### Risks
- gRPC integration bugs
  - Mitigation: 2-week gradual rollout with feature flag
- Increased infrastructure cost ($800/month)
  - Mitigation: Budget approved, cost monitoring set up
- Database transaction boundaries now distributed
  - Mitigation: Keep User Service transactions simple

### Technical Debt
- Database not separated (phase 2 in ADR-024)
- API Gateway becomes single point of failure
  - Address when we extract 3+ services
- No circuit breakers yet
  - Implement when we extract payment service

## References
- Architecture diagram: [link]
- Deployment metrics: [link]
- gRPC vs REST analysis: [link]
```
