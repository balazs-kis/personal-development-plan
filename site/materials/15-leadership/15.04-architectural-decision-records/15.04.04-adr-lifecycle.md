# Lesson 4: ADR Lifecycle and Status Management

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the complete ADR lifecycle from proposal to superseded/deprecated
- Manage ADR status transitions appropriately
- Handle evolving decisions and superseded ADRs
- Implement ADR review and acceptance processes
- Know when to update vs create new ADRs
- Archive and maintain ADR history effectively

---

## Introduction

ADRs aren't static documents—they evolve through a lifecycle as decisions are proposed, reviewed, accepted, and eventually superseded. Understanding this lifecycle is crucial for maintaining a useful decision log that reflects the evolution of your architecture over time.

## Key Concepts Summary

### The ADR Lifecycle

```
    Idea/Draft
         ↓
      Proposed
         ↓
     In Review ←→ Revisions Needed
         ↓
    Accepted/Final
         ↓
    ┌────┴────┐
    ↓         ↓
Superseded  Deprecated
```

---

## ADR Status States

### 1. Idea (Pre-Draft)

**When:** Informal discussion stage, not yet formally tracked

**Characteristics:**
- Rough concept or proposal
- No formal ADR document yet
- Gathering initial feedback

**Example:**
```markdown
# Slack Discussion

Alice: "Should we consider Redis for sessions?"
Bob: "Maybe. What's the problem with current approach?"
Alice: "Database is slow. Let me draft an ADR."
```

**Action:** Move to Draft once there's concrete proposal

### 2. Draft

**When:** First formal stage of ADR development

**Characteristics:**
- Author is actively working on the ADR
- Content is incomplete or being revised
- Not yet ready for team review

**Example:**
```markdown
# ADR-015: Use Redis for Session Storage

## Status
Draft

Author: Alice Johnson
Created: 2024-01-10
Last Updated: 2024-01-12

## Context
[Being written...]

## Decision
[To be completed...]
```

**Typical Duration:** Few days to 1 week

**Actions:**
- Author completes sections
- Gathers evidence and data
- Documents alternatives
- When ready: move to Proposed

### 3. Proposed

**When:** Ready for team review and discussion

**Characteristics:**
- Complete enough for review
- Awaiting team feedback
- May be discussed in meetings
- Open for comments and revisions

**Example:**
```markdown
# ADR-015: Use Redis for Session Storage

## Status
Proposed

Author: Alice Johnson
Proposed Date: 2024-01-15
Review By: 2024-01-22
Reviewers: @bob, @charlie, @david
```

**Typical Duration:** 1-2 weeks

**Review Process:**
```
1. Author publishes ADR as PR
2. Team members review and comment
3. Discussion in architecture review meeting
4. Revisions based on feedback
5. Final approval or rejection
```

### 4. In Review / Last Call

**When:** Final review before acceptance

**Characteristics:**
- All major concerns addressed
- Final opportunity for objections
- Time-boxed review period

**Example:**
```markdown
## Status
Last Call

Review Period: 2024-01-20 to 2024-01-27
Comments Due: 2024-01-27 EOD

Reviewers who must approve:
- [x] Bob Smith (Tech Lead)
- [x] Charlie Brown (DevOps)
- [ ] David Lee (Security)
```

**Typical Duration:** Few days to 1 week

### 5. Accepted / Final

**When:** Approved and actively in use

**Characteristics:**
- Immutable (no more changes)
- Represents official architectural decision
- Team commits to following the decision

**Example:**
```markdown
## Status
Accepted

Accepted Date: 2024-01-28
Approvers: Bob Smith, Charlie Brown, David Lee
```

**What "Accepted" means:**
- The decision is official
- Implementation may begin
- New code should follow this decision
- Changes require a new ADR

### 6. Superseded

**When:** Replaced by a newer ADR

**Characteristics:**
- Was accepted, but no longer current
- Historical record preserved
- Links to superseding ADR

**Example:**
```markdown
## Status
Superseded by [ADR-042: Use Redis Cluster with Geo-Replication](0042-redis-cluster.md)

Original Accept Date: 2024-01-28
Superseded Date: 2024-06-15
Reason: Need geographic distribution for global users
```

**Why Supersede, Not Update:**
- Preserves history
- Shows evolution of thinking
- Future readers understand the journey

### 7. Deprecated

**When:** No longer recommended, but may still exist in code

**Characteristics:**
- Was implemented and accepted
- Now considered outdated
- Migration may be in progress

**Example:**
```markdown
## Status
Deprecated

Original Accept Date: 2024-01-28
Deprecated Date: 2025-01-15
Reason: Redis 7.0 provides better native features
Migration Plan: See [ADR-087: Redis 7.0 Migration](0087-redis-7-migration.md)
Expected Removal: Q2 2025
```

**Use Cases:**
- Technology EOL (end-of-life)
- Better alternatives available
- Architectural shift
- Security concerns

### 8. Rejected / Withdrawn

**When:** Proposed but not accepted

**Characteristics:**
- Never implemented
- Valuable as historical record (why NOT to do something)

**Example:**
```markdown
## Status
Rejected

Proposed Date: 2024-01-15
Rejected Date: 2024-01-28
Reason: Cost analysis showed $10k/month infrastructure cost 
exceeds budget. Team lacks expertise for 6-month learning curve.

Revisit If:
- Budget increases to $15k/month
- Team gains NoSQL expertise
- Requirements change significantly
```

**Why Keep Rejected ADRs:**
- Prevents rehashing same debate
- Documents why alternative wasn't chosen
- Shows options that were considered

### 9. Stagnant

**When:** Inactive for extended period (typically >6 months)

**Characteristics:**
- In Draft, Proposed, or Review
- No activity or progress
- Likely abandoned

**Example:**
```markdown
## Status
Stagnant

Last Activity: 2024-01-15
Marked Stagnant: 2024-07-15
Reason: Author left company, no one picked up

Action Needed:
- Find new owner, OR
- Move to Withdrawn
```

**Cleanup Strategy:**
- Quarterly review of stagnant ADRs
- Assign new owner or close

### 10. Living

**When:** Continuously updated document (rare)

**Characteristics:**
- Never reaches "Final" status
- Designed to evolve
- Not typical for ADRs (use sparingly)

**Example:**
```markdown
## Status
Living Document

Created: 2024-01-15
Last Updated: 2024-09-20

Purpose: Maintain list of approved libraries and frameworks.
This ADR is continuously updated as new libraries are approved.
```

**Warning:** Overuse defeats purpose of immutable history. Use for catalogs or evolving standards only.

## Status Transition Rules

### Valid Transitions

```
Draft → Proposed → In Review → Accepted → Superseded
                               ↓
                           Deprecated
Draft → Proposed → Rejected
Draft → Withdrawn
Proposed → Stagnant
```

### Invalid Transitions

❌ **Can't skip states:**
```
Draft → Accepted (should go through Proposed/Review)
```

❌ **Can't revert Accepted:**
```
Accepted → Draft (create new ADR instead)
```

❌ **Can't supersede Rejected:**
```
Rejected → Superseded (never was accepted)
```

## When to Update vs Create New ADR

### Update Existing ADR (while still Draft/Proposed)

```markdown
Scenario: ADR is Draft, reviewer suggests changes

✅ Update existing ADR:
- Fix typos
- Add more context
- Address reviewer feedback
- Refine decision
```

### Create New ADR (once Accepted)

```markdown
Scenario: Need to change an Accepted decision

❌ Don't edit ADR-015
✅ Create ADR-042 that supersedes ADR-015

Why:
- Preserves history
- Shows evolution of thinking
- Explains why change was needed
```

### Example: Evolution Through Multiple ADRs

```markdown
# ADR-015: Use Redis for Session Storage
Status: Superseded by ADR-042

Decision: Use single Redis instance for sessions
Context: Support 100k users
Date: 2024-01-28

---

# ADR-042: Use Redis Cluster with Geo-Replication
Status: Superseded by ADR-087

Decision: Migrate to Redis Cluster across 3 regions
Context: Now at 500k users, need geographic distribution
Date: 2024-06-15
Supersedes: ADR-015

---

# ADR-087: Migrate to Redis 7.0 with Active-Active
Status: Accepted

Decision: Upgrade to Redis 7.0 with active-active replication
Context: Redis 7.0 provides better geo-replication features
Date: 2025-01-15
Supersedes: ADR-042
```

**Value:** Clear progression shows why each change was made.

## ADR Review Process

### Typical Review Workflow

```
1. Author creates ADR as Draft
        ↓
2. Author completes ADR, moves to Proposed
        ↓
3. Opens Pull Request to docs/adr/
        ↓
4. Team members review (async comments)
        ↓
5. Discussion in architecture review meeting
        ↓
6. Author addresses feedback, revises ADR
        ↓
7. Final approval (Last Call period)
        ↓
8. Merge PR, ADR status → Accepted
```

### Review Meeting Agenda

```markdown
# Architecture Review Meeting - 2024-01-22

## ADRs for Review

### ADR-015: Use Redis for Session Storage (Proposed)
- Presenter: Alice Johnson (5 min)
- Discussion (15 min)
- Decision: Approve / Revisions Needed / Reject

### ADR-016: Adopt GraphQL for Public API (Draft)
- Early feedback round (10 min)
- Not yet ready for decision
```

### Review Cadence Best Practices

```
Weekly/Bi-weekly Architecture Review:
- Review Proposed ADRs
- Discuss Draft ADRs (early feedback)
- Track Stagnant ADRs

Quarterly ADR Health Check:
- Review all Stagnant ADRs
- Identify Deprecated candidates
- Update cross-references
```

## Managing ADR History

### Don't Delete ADRs

```
❌ Bad:
git rm docs/adr/0015-redis-sessions.md

✅ Good:
Update ADR-015 status to "Superseded"
Link to ADR-042 that replaces it
Keep ADR-015 in repository
```

**Why preserve history:**
- Understand evolution of architecture
- Learn from past decisions
- Avoid repeating mistakes
- Onboard new team members

### Git History for ADRs

```bash
# Good: One ADR per commit
git commit -m "Add ADR-015: Use Redis for Session Storage"

# Good: Status updates are explicit
git commit -m "Supersede ADR-015 with ADR-042"

# Bad: Editing accepted ADR
git commit -m "Update ADR-015 to use Redis Cluster"
# (Should create ADR-042 instead)
```

### ADR Numbering and History

```
Keep sequential numbering:
ADR-001 (Accepted)
ADR-002 (Rejected)
ADR-003 (Superseded)
ADR-004 (Accepted)
...

Don't reuse numbers:
❌ Delete ADR-002, reuse number
✅ Keep ADR-002 as Rejected, continue sequence
```

## Handling Special Cases

### Case 1: Urgent Decision

```markdown
# ADR-023: Emergency DDoS Mitigation

## Status
Accepted (Fast-tracked)

Decision Date: 2024-06-15 (same day)
Rationale: Active DDoS attack required immediate response
Review: Shortened to 2 hours (emergency exception)
Approved By: CTO, Tech Lead, Security Lead

## Note
This ADR was fast-tracked due to production emergency.
Retrospective review scheduled for 2024-06-20.
```

**When to fast-track:**
- Production emergencies
- Security incidents
- Regulatory deadlines

**Requirements:**
- Document why fast-tracked
- Schedule retrospective review
- Higher-level approval needed

### Case 2: Retroactive ADR

```markdown
# ADR-008: Document Existing PostgreSQL Usage

## Status
Accepted (Retroactive)

Original Decision: ~2020 (before ADR process)
Documented: 2024-01-15
Purpose: Document existing architecture for completeness

## Note
This ADR documents a decision made before we adopted ADRs.
It represents our best understanding of the original context.
```

**Use for:**
- Brownfield projects starting ADRs
- Documenting historical decisions
- Completing decision log

### Case 3: Temporary/Experimental Decision

```markdown
# ADR-031: Temporary Monolithic Deployment

## Status
Accepted (Temporary)

Implementation: Q1 2024
Planned Replacement: Q3 2024 (see ADR-042)
Reason: Limited DevOps resources, need fast time-to-market

## Note
This is an intentional temporary decision.
ADR-042 (microservices migration) is already planned.
```

**Use for:**
- Intentional technical debt
- Time-boxed experiments
- Phased migrations

## ADR Maintenance

### Regular Maintenance Tasks

**Weekly:**
- Review new ADR proposals
- Update statuses (Proposed → Accepted)
- Respond to ADR comments

**Monthly:**
- Check for outdated "Proposed" ADRs (move to Stagnant?)
- Update cross-references
- Verify links still work

**Quarterly:**
- Review all Stagnant ADRs (close or reassign)
- Identify candidates for Deprecated status
- Update ADR index/table of contents
- Archive old Superseded ADRs (move to archive folder)

### ADR Health Metrics

```markdown
Track:
- Number of ADRs by status
- Average time in Proposed state
- Number of Stagnant ADRs
- ADR creation rate

Good signs:
- Regular new ADRs (shows active architecture discussion)
- Few Stagnant ADRs (good ownership)
- Healthy Accepted → Superseded lifecycle

Warning signs:
- No new ADRs in 3+ months (decisions not documented?)
- Many Stagnant ADRs (abandoned proposals)
- ADRs never superseded (architecture not evolving?)
```

```markdown
![Status: Accepted](https://img.shields.io/badge/status-accepted-green)

## Status
Accepted (2024-01-28)
```

```yaml

        run: |
          # Ensure superseded ADRs link to replacement
          # [validation script]
```
