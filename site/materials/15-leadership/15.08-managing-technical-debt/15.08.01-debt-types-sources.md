# Lesson 1: Technical Debt Types and Sources

## Learning Objectives

By the end of this lesson, you will be able to:
- Define technical debt and understand its economic metaphor
- Identify different types and categories of technical debt
- Distinguish between deliberate and inadvertent debt
- Recognize the sources and causes of technical debt accumulation
- Understand when technical debt is strategic vs. problematic

---

## Introduction

Not all technical debt is created equal. Some debt is deliberate and strategic—a conscious trade-off to ship faster or test market assumptions. Other debt is inadvertent, accumulating through lack of knowledge or changing requirements. Understanding the types and sources of technical debt is the first step toward managing it effectively.

The metaphor of "debt" is powerful: like financial debt, technical debt has principal (the work not done) and interest (the ongoing cost of working around it). Also like financial debt, some is good leverage, while too much becomes crushing.

## Key Concepts Summary

### The Technical Debt Metaphor

**Definition:** Technical debt represents the implied cost of rework caused by choosing a limited solution now instead of a better approach that would take longer.

**The Economic Analogy:**
- **Principal:** The work that needs to be done to fix the debt
- **Interest:** The ongoing cost of working around the debt (slower development, more bugs, harder maintenance)
- **Interest rate:** How much the debt costs you over time
- **Default:** When debt becomes so crushing that development grinds to a halt

Like financial debt, technical debt isn't inherently bad—it's a tool. Strategic debt can accelerate time-to-market. Unmanaged debt can bankrupt your development velocity.

### Fowler's Technical Debt Quadrant

Martin Fowler proposed a 2x2 matrix that categorizes debt by two dimensions:

#### Deliberate vs. Inadvertent

**Deliberate:** You know you're taking on debt
- "We don't have time to do this right; we'll ship it and fix it later"
- Conscious decision to trade quality for speed

**Inadvertent:** You don't realize you're accumulating debt
- "We didn't know there was a better way to do this"
- Discovered after the fact through learning or changing requirements

#### Reckless vs. Prudent

**Reckless:** No consideration of consequences
- Ignoring known best practices
- Not planning for repayment
- "We'll deal with it later" (but never do)

**Prudent:** Thoughtful trade-offs
- Understanding the costs and benefits
- Planning for repayment
- "This is a strategic shortcut with acceptable consequences"

#### The Four Quadrants

| | Deliberate | Inadvertent |
|---|---|---|
| **Reckless** | "We don't have time for design" | "What's layering?" |
| **Prudent** | "We must ship now and deal with consequences" | "Now we know how we should have done it" |

**Examples:**

1. **Reckless & Deliberate:** Skipping automated tests to hit a deadline, with no plan to add them later
2. **Prudent & Deliberate:** Building an MVP with hardcoded configuration to test market fit, planning to make it configurable if successful
3. **Reckless & Inadvertent:** Junior team doesn't know about SOLID principles and creates tightly coupled code
4. **Prudent & Inadvertent:** After gaining domain knowledge, team realizes a better architecture exists (evolutionary learning)

**Key Insight:** Only the bottom-right quadrant (Prudent & Inadvertent) is truly unavoidable. The others are choices.

### 13 Types of Technical Debt

The Software Engineering Institute identifies 13 types of technical debt:

#### Technology-Based Debt

1. **Architecture Debt**
   - Circular dependencies between components
   - Monolithic structures that should be modular
   - Tight coupling preventing independent scaling
   - Example: Microservice that depends on 15 other services to function

2. **Code Debt**
   - Violating DRY (Don't Repeat Yourself) principle
   - Violating KISS (Keep It Simple, Stupid) principle
   - Poor naming, complex logic, lack of abstractions
   - Example: Copy-pasted business logic across 10 controllers

3. **Design Debt**
   - Poor UX decisions that require workarounds
   - Inconsistent interfaces or APIs
   - Example: API that returns different data structures for similar operations

4. **Build Debt**
   - Lack of CI/CD pipelines
   - Manual deployment processes
   - Slow build times
   - Example: 45-minute build process that could be 5 minutes

5. **Test Debt**
   - Missing test coverage
   - Flaky tests
   - No test automation
   - Example: Critical payment flow with no automated tests

6. **Test Automation Debt**
   - Manual testing for everything
   - Tests that don't run in CI
   - Example: QA team spending 2 days manually testing every release

7. **Defect Debt**
   - Known bugs not fixed
   - Bug backlog growing faster than resolution
   - Example: 500 open bugs, 50 critical, all triaged as "someday"

8. **Documentation Debt**
   - Outdated or missing documentation
   - Undocumented APIs or systems
   - Example: Critical service with no runbook for on-call engineers

9. **Data Debt**
   - Outdated data models
   - Poor data quality
   - Inefficient data structures
   - Example: Denormalized data requiring complex joins and causing performance issues

#### Organization-Based Debt

10. **Infrastructure Debt**
    - Outdated hardware or licenses
    - Unsupported software versions
    - Example: Running databases on unsupported PostgreSQL 9.6 (EOL 2021)

11. **Service Debt**
    - Services structured around organizational boundaries instead of business domains
    - Conway's Law anti-patterns
    - Example: "User Service" that mirrors the org chart instead of domain boundaries

12. **Requirement Debt**
    - Faulty backlog management
    - Requirements that contradict each other
    - Example: Feature backlog with 500 items, many obsolete or contradictory

13. **Process Debt**
    - Inefficient workflows
    - Manual processes that should be automated
    - Example: 8-step manual approval process for every small config change

### Common Sources of Technical Debt

**Business Pressure:** Deadlines that force shortcuts

**Lack of Knowledge:** Team doesn't know better approaches

**Changing Requirements:** What was right yesterday is wrong today

**Lack of Testing:** Bugs and regression accumulate

**Deferred Refactoring:** "We'll clean it up later" (but don't)

**Poor Collaboration:** Siloed teams building conflicting solutions

**Technology Obsolescence:** Frameworks and tools become outdated

**Success:** System outgrows original design assumptions (not always a failure!)

### When Debt Is Strategic vs. Problematic

#### Strategic Debt (Good Leverage)

**Characteristics:**
- Deliberate and time-bound
- Has a payoff plan
- Enables learning or market testing
- Cost is understood and acceptable

**Examples:**
- Building an MVP with manual processes to test product-market fit
- Hardcoding configuration for initial launch, planning to make it dynamic later
- Skipping edge cases for v1 to ship faster

#### Problematic Debt (Crushing Burden)

**Characteristics:**
- No plan to address it
- Accumulating faster than resolution
- Slowing down all development
- Causing frequent production issues

**Examples:**
- System so fragile that every change risks breakage
- Codebase so complex that only 2 people understand it
- Infrastructure so outdated that security patches can't be applied

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Think of a system you've worked on. Identify 5 pieces of technical debt:

1. For each piece, categorize it using Fowler's Quadrant (Reckless/Prudent, Deliberate/Inadvertent)
2. Identify which type of debt it is (Architecture, Code, Design, Test, etc.)
3. Was this debt strategic or problematic?
4. What was the source of this debt?

Write your answers down. This will help you recognize patterns in how debt accumulates.
