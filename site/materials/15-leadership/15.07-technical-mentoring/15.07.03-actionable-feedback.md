# Lesson 3: Giving Actionable Feedback

## Learning Objectives

By the end of this lesson, you will be able to:
- Provide specific, constructive feedback that drives improvement
- Structure feedback conversations effectively
- Balance directiveness with learning opportunities
- Avoid common feedback pitfalls
- Adapt feedback style to different contexts and individuals

---

## Introduction

Feedback is one of the most powerful tools mentors have, yet it's often done poorly: too vague, too harsh, mistimed, or focused on the person rather than the work. Actionable feedback is specific, timely, balanced, and clearly explains the "why" behind suggestions.

Great technical mentors master the art of feedback that helps engineers grow without crushing confidence or creating dependence.

## Key Concepts Summary

### The Three Questions Before Giving Feedback

Before giving any feedback, ask yourself:

1. **Does this need to be said?** Is this feedback truly valuable, or am I just stating a preference?
2. **Does this need to be said by me?** Am I the right person to give this feedback?
3. **Does this need to be said right now?** Is this the right time and context?

If the answer isn't "yes" to all three, skip the feedback.

### Core Principles of Effective Feedback

#### 1. Be Specific and Concrete

**Bad:** "This code is hard to read."

**Good:** "The `calculateInterest` function is hard to read because it's doing three different things: validation, calculation, and formatting. Try splitting it into smaller functions with clear names like `validateInput`, `computeInterest`, and `formatResult`."

**Why:** Specific feedback gives clear direction for improvement.

#### 2. Comment on Code, Not the Person

**Bad:** "Why did you use threads here when there's obviously no benefit?"

**Good:** "The concurrency model here is adding complexity (additional error handling, synchronization) without clear performance benefit. What problem is the threading solving?"

**Why:** Personal attacks shut down learning; focusing on the work keeps it constructive.

#### 3. Explain Your Reasoning

**Bad:** "Don't use `var` here, use explicit types."

**Good:** "Using explicit types here (`Dictionary<string, UserProfile>` instead of `var`) makes the data structure immediately clear to readers and catches type errors earlier. When the type isn't obvious from the right-hand side, explicit typing improves maintainability."

**Why:** Explaining "why" helps engineers understand principles, not just follow rules.

#### 4. Label Comment Severity

Use labels to help prioritize:
- **Nit:** Minor suggestion, non-blocking
- **Optional:** Worth considering but not required
- **FYI:** Informational, no action needed
- **Blocking:** Must be addressed before merging
- *(No label)* Implies "should be addressed"

**Example:**
```
Nit: Consider extracting this magic number to a named constant for clarity.
```

**Why:** Helps mentees prioritize and reduces anxiety about "must I do everything?"

#### 5. Balance Direction with Learning

**The Spectrum:**

| Too Directive | Balanced | Too Hands-Off |
|--------------|----------|---------------|
| "Change line 47 to `x++`" | "What happens if count is negative here?" | "Something's wrong somewhere" |
| No learning | Guides toward discovery | No actionable path |

**When to be more directive:**
- Critical bugs or security issues
- Established patterns the engineer doesn't know yet
- Time-sensitive situations

**When to guide with questions:**
- Problem-solving skills you want to develop
- Trade-offs with multiple valid solutions
- Debugging and troubleshooting

#### 6. Use the Sandwich Method (Carefully)

**Structure:**
1. Start with something positive (genuine, not contrived)
2. Address what needs improvement
3. End with encouragement and growth potential

**Example:**
"Your implementation of the caching layer is solid—the invalidation logic is particularly well thought out. The error handling could be more robust; right now uncaught exceptions could crash the cache. Consider wrapping cache operations in try-catch and logging failures. Overall, this is good work, and improving the error handling will make it production-ready."

**Caution:** Don't overuse or make it formulaic. Engineers see through fake positives.

### Timing and Context

#### When to Give Feedback

**Good Timing:**
- Soon after the work is completed (while fresh)
- In private (one-on-one settings, not public channels)
- When the person is receptive (not burned out or defensive)
- In dedicated review/pairing time (expected context)

**Bad Timing:**
- In team meetings or public channels
- When someone is overwhelmed or stressed
- Long after the work is done (context lost)
- As an "oh, by the way" in unrelated meetings

#### Format Matters

**Code Reviews:** Best for technical feedback on specific code.

**1-on-1s:** Best for broader patterns, career growth, and sensitive topics.

**Pairing Sessions:** Best for real-time guidance and teaching.

**Written (Slack/email):** Best for non-urgent, informational feedback. Careful with tone.

### Common Feedback Pitfalls

#### 1. The Vague Critique
"This needs to be better" ➔ Better how? What specifically?

#### 2. The Overwhelming List
15 comments on a 20-line change ➔ Focus on the most important 2-3 points.

#### 3. The Preference Disguised as Principle
"Never use ternary operators" ➔ Stating preferences as universal rules stifles learning.

#### 4. The Delayed Bomb
Waiting months to address a recurring issue ➔ Small, timely corrections prevent big confrontations.

#### 5. The Missing "Why"
"Do it this way" ➔ Without explanation, engineers don't learn transferable principles.

### The SBI Framework (Situation-Behavior-Impact)

A structured approach for sensitive or performance-related feedback:

1. **Situation:** Describe the context ("In the architecture review meeting yesterday...")
2. **Behavior:** Describe the specific observable behavior ("...you interrupted Sarah three times...")
3. **Impact:** Explain the effect ("...which made it hard for her to fully explain her design and may have discouraged her from contributing.")

**Example:**
"During yesterday's sprint planning, you committed to three large features for a two-week sprint. This is more than the team's historical velocity suggests is realistic, which could lead to missed commitments and pressure on the team. Let's talk about how to estimate more conservatively."

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Imagine you're reviewing code from a junior engineer. The code works but has several issues:
- A 200-line function that does multiple things
- No error handling
- Variable names like `data1`, `temp`, `result`
- Copy-pasted code in three places

Write 3-4 pieces of feedback that:
1. Prioritize the most important issues
2. Explain the "why" behind your suggestions
3. Are specific and actionable
4. Balance directiveness with learning

Compare your feedback against the principles in this lesson.
