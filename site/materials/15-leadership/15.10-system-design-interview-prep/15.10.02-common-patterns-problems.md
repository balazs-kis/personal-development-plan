## Introduction

System design interviews often ask similar types of questions across companies. While each problem has unique aspects, recognizing common patterns helps you approach any question systematically. Understanding these patterns—and when to apply them—demonstrates engineering maturity and real-world experience.

This lesson covers the most frequently asked questions and the architectural patterns that solve them.

### Core Architectural Patterns

**1. Caching**
- **When to use:** Reduce database load, improve read latency, serve repeated requests
- **Common strategies:** Write-through, write-back, write-around
- **Cache levels:** Browser, CDN, application, database
- **Trade-offs:** Complexity, consistency challenges, memory cost

**2. Sharding and Partitioning**
- **When to use:** Scale databases beyond single machine capacity
- **Sharding strategies:** Range-based, hash-based, geographic, entity-based
- **Consistent hashing:** Minimize data movement when nodes change
- **Trade-offs:** Join complexity, rebalancing cost, potential hotspots

**3. Load Balancing**
- **When to use:** Distribute traffic across multiple servers
- **Algorithms:** Round-robin, least connections, consistent hashing, weighted
- **Layers:** DNS, L4 (transport), L7 (application)
- **Trade-offs:** Additional latency, single point of failure (without redundancy)

**4. Message Queues**
- **When to use:** Decouple components, handle traffic spikes, async processing
- **Patterns:** Pub/sub, point-to-point, priority queues
- **Examples:** Kafka, RabbitMQ, SQS
- **Trade-offs:** Eventual consistency, complexity, ordering guarantees

**5. Database Scaling Patterns**
- **Read replicas:** Scale read operations
- **Write scaling:** Sharding, partitioning
- **SQL vs. NoSQL:** Structured vs. flexible schema, ACID vs. BASE
- **Trade-offs:** Consistency vs. availability (CAP theorem)

**6. Content Delivery Networks (CDNs)**
- **When to use:** Static content, global user base, reduce latency
- **How they work:** Edge caching, geographic distribution
- **Trade-offs:** Cost, cache invalidation complexity, stale data

**7. Rate Limiting**
- **When to use:** Prevent abuse, ensure fair usage, protect resources
- **Algorithms:** Token bucket, leaky bucket, fixed window, sliding window
- **Granularity:** Per-user, per-IP, per-API-key, global
- **Trade-offs:** False positives, implementation complexity

**8. Database Indexing**
- **When to use:** Speed up read queries
- **Types:** B-tree, hash, full-text, composite
- **Trade-offs:** Write performance penalty, storage overhead

### The CAP Theorem

**Fundamental trade-off in distributed systems:**
- **Consistency:** All nodes see the same data at the same time
- **Availability:** Every request receives a response (success or failure)
- **Partition Tolerance:** System continues operating despite network partitions

**Key insight:** You can only guarantee 2 of 3 during network partitions.

**Practical choices:**
- **CP systems:** Sacrifice availability for consistency (traditional RDBMS, HBase)
- **AP systems:** Sacrifice consistency for availability (Cassandra, DynamoDB)
- **Most systems:** Choose based on business requirements

### Scaling Strategies

**Horizontal Scaling (Scale Out):**
- Add more machines
- Better fault tolerance
- More complex to implement
- No single-machine limit

**Vertical Scaling (Scale Up):**
- Add more resources to existing machine
- Simpler to implement
- Limited by hardware ceiling
- Single point of failure

**When to use each:**
- Start vertical, go horizontal when needed
- Consider operational complexity vs. scaling needs
- Hybrid approaches are common in practice

### Pattern Selection Framework

**Questions to ask:**
1. What's the read/write ratio?
2. What consistency guarantees are needed?
3. What's the expected scale (users, requests, data)?
4. What latency requirements exist?
5. What failure modes must be handled?
6. What's the budget for complexity?

**Pattern matching examples:**
- High read/write ratio → Add caching
- Global user base + static content → Use CDN
- Need to handle traffic spikes → Add message queues
- Database becoming bottleneck → Add read replicas or shard
- Too many requests → Implement rate limiting

## Key Takeaways

- Common interview questions fall into categories: storage, social media, real-time services, infrastructure, and collaborative systems
- Core patterns recur across problems: caching, sharding, load balancing, message queues, CDNs, rate limiting
- Understanding why patterns exist is more valuable than memorizing their names
- Engineering maturity means knowing when NOT to use complex patterns
- Pattern selection depends on read/write ratio, consistency needs, scale, latency requirements, and failure modes
- CAP theorem governs fundamental trade-offs in distributed systems
- Most real-world systems use hybrid approaches combining multiple patterns
- Strong candidates explain trade-offs and downsides, not just benefits
