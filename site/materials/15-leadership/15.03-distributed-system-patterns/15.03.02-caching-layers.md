## Introduction

Caching is one of the most effective ways to improve system performance. By storing frequently accessed data in faster storage layers, we can dramatically reduce latency, database load, and infrastructure costs. Understanding when and how to cache is essential for building scalable systems.

## Key Concepts Summary

### The Caching Hierarchy

```
User Request
     ↓
1. Browser Cache (fastest, smallest)
     ↓
2. CDN Cache (edge locations)
     ↓
3. Application Cache (Redis, Memcached)
     ↓
4. Database Cache (query cache)
     ↓
5. Database (slowest, largest)
```

Each layer serves a specific purpose and trades off speed, size, and scope.

## Caching Layers

### 1. Browser Cache

```http
HTTP/1.1 200 OK
Cache-Control: max-age=3600, public
ETag: "v1.2.3"
Last-Modified: Mon, 01 Jan 2024 00:00:00 GMT
```

**What it caches:** Static assets (CSS, JS, images), API responses (with cache headers)

**Pros:**
- Zero latency (local to user)
- Reduces server load
- Works offline

**Cons:**
- User-specific (not shared)
- Limited control (user can clear)
- Size limitations

**Use for:** Static assets, rarely-changing resources

### 2. CDN (Content Delivery Network)

```
User in Tokyo → Tokyo Edge Server (cached)
User in NYC → NYC Edge Server (cached)
User in London → London Edge Server (cached)
     ↓ (if not cached)
Origin Server (your application)
```

**What it caches:** Static files, images, videos, API responses

**Pros:**
- Geographic distribution (lower latency)
- Reduces origin server load
- DDoS protection
- Handles traffic spikes

**Cons:**
- Cost for bandwidth
- Cache invalidation complexity
- Not suitable for personalized content

**Popular CDNs:** CloudFlare, Akamai, AWS CloudFront, Azure CDN

**Pattern:**
```csharp
// Push CDN: You upload assets
cdn.Upload("styles.css", content);

// Pull CDN: CDN fetches on first request
// Request: cdn.example.com/styles.css
// CDN checks cache → miss → fetches from origin → caches
```

### 3. Application Cache (In-Memory)

```csharp
// Using Redis as application cache
public class UserService
{
    private readonly IDistributedCache _cache;
    private readonly IUserRepository _repository;
    
    public async Task<User> GetUserAsync(int userId)
    {
        string cacheKey = $"user:{userId}";
        
        // Try cache first
        var cached = await _cache.GetStringAsync(cacheKey);
        if (cached != null)
        {
            return JsonSerializer.Deserialize<User>(cached);
        }
        
        // Cache miss - get from database
        var user = await _repository.GetByIdAsync(userId);
        
        // Store in cache for 1 hour
        await _cache.SetStringAsync(
            cacheKey,
            JsonSerializer.Serialize(user),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1)
            }
        );
        
        return user;
    }
}
```

**Technologies:**
- **Redis:** Feature-rich, persistence, pub/sub, data structures
- **Memcached:** Simple, fast, pure key-value
- **Hazelcast:** Distributed data structures, compute capabilities

**Pros:**
- Very fast (in-memory)
- Shared across application instances
- Rich data structures (Redis)

**Cons:**
- Volatile (data lost on restart, unless persistence enabled)
- Memory cost
- Complexity of distributed coordination

### 4. Database Cache

```sql
-- Query cache (MySQL - deprecated in 8.0)
SELECT SQL_CACHE * FROM users WHERE id = 123;

-- Modern approach: Use materialized views or application cache
CREATE MATERIALIZED VIEW user_summary AS
SELECT user_id, COUNT(*) as order_count
FROM orders
GROUP BY user_id;
```

**What it caches:** Query results, indexes in memory

**Pros:**
- Transparent to application
- No additional infrastructure

**Cons:**
- Limited control
- Cache invalidation complexities
- Deprecated in modern databases (use application cache instead)

## Caching Strategies (Patterns)

### 1. Cache-Aside (Lazy Loading)

```csharp
public async Task<Data> GetData(string key)
{
    // 1. Check cache
    var cached = await cache.GetAsync(key);
    if (cached != null) return cached;
    
    // 2. Cache miss - load from database
    var data = await database.GetAsync(key);
    
    // 3. Update cache
    await cache.SetAsync(key, data, ttl: TimeSpan.FromHours(1));
    
    return data;
}
```

**Pros:**
- Only cache what's actually used
- Resilient (cache failure doesn't break reads)

**Cons:**
- Cache miss penalty (3 operations: check cache, query DB, update cache)
- Initial requests slower (cache warming needed)
- Stale data possible

**Best for:** Read-heavy workloads, expensive queries

### 2. Read-Through Cache

```csharp
// Cache layer handles loading automatically
public async Task<Data> GetData(string key)
{
    // Cache checks itself and loads from DB if needed
    return await cache.GetOrLoadAsync(key, 
        async k => await database.GetAsync(k),
        ttl: TimeSpan.FromHours(1)
    );
}
```

**Pros:**
- Simpler application code
- Consistent pattern

**Cons:**
- Tight coupling to cache
- Cache must know about data source

**Best for:** When cache library supports it, uniform data access patterns

### 3. Write-Through Cache

```csharp
public async Task UpdateData(string key, Data data)
{
    // 1. Write to cache
    await cache.SetAsync(key, data);
    
    // 2. Write to database (synchronous)
    await database.UpdateAsync(key, data);
}
```

**Pros:**
- Cache always consistent with database
- No stale reads

**Cons:**
- Higher write latency (two writes)
- Cache may store data never read
- Wasted writes if data changes frequently

**Best for:** Data that's read immediately after write, consistency critical

### 4. Write-Around Cache

```csharp
public async Task UpdateData(string key, Data data)
{
    // 1. Write to database only
    await database.UpdateAsync(key, data);
    
    // 2. Invalidate cache
    await cache.RemoveAsync(key);
    
    // Next read will cache the new value
}
```

**Pros:**
- Reduces cache churn
- Good for write-heavy, read-once data

**Cons:**
- Cache miss on next read
- Recent writes not cached

**Best for:** Write-heavy workloads, data not read frequently after write

### 5. Write-Back (Write-Behind) Cache

```csharp
public async Task UpdateData(string key, Data data)
{
    // 1. Write to cache only
    await cache.SetAsync(key, data);
    
    // 2. Queue for async database write
    backgroundQueue.Enqueue(new WriteOperation(key, data));
    
    // Database write happens later
}
```

**Pros:**
- Lowest write latency
- Can batch writes to database
- Handles write bursts

**Cons:**
- Risk of data loss (cache failure before DB write)
- Complexity
- Eventual consistency

**Best for:** Write-heavy workloads, can tolerate eventual consistency

## Cache Eviction Policies

When the cache is full, which items should be removed?

### 1. Time-To-Live (TTL)

```csharp
await cache.SetAsync("user:123", user, TimeSpan.FromMinutes(30));
// Automatically deleted after 30 minutes
```

**Pros:** Simple, prevents memory leaks, predictable

**Cons:** Arbitrary expiration time, may evict still-useful data

**Use for:** Time-sensitive data (sessions, rate limits)

### 2. Least Recently Used (LRU)

```
Cache: [A, B, C] (max size = 3)
Access B → [A, C, B]
Access A → [C, B, A]
Add D → evict C → [B, A, D]
```

**Pros:** Intuitive, works well in practice

**Cons:** Overhead of tracking access time

**Use for:** General-purpose caching

### 3. Least Frequently Used (LFU)

```
Cache: [A(10), B(5), C(3)]
Add D → evict C (lowest frequency) → [A(10), B(5), D(1)]
```

**Pros:** Keeps popular items

**Cons:** Difficult to implement, requires tracking access count, cold start problem

**Use for:** Clear access patterns, stable popularity

### 4. First-In-First-Out (FIFO)

```
Cache: [A, B, C] (max size = 3)
Add D → evict A (oldest) → [B, C, D]
```

**Pros:** Simple to implement

**Cons:** Ignores access patterns

**Use for:** Simple caching needs, predictable patterns

## Distributed Caching

### Challenge: Consistent Hashing

```
Without consistent hashing:
- 3 cache servers, key "user:123"
- Hash("user:123") % 3 = Server 1
- Add 4th server → Hash("user:123") % 4 = Server 2 (different!)
- Cache miss for all keys

With consistent hashing:
- Add/remove servers → only ~1/n keys need remapping
```

### Redis Cluster Example

```csharp
// Configure Redis cluster
services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = "server1:6379,server2:6379,server3:6379";
    options.InstanceName = "MyApp_";
});

// Usage is transparent - library handles sharding
await cache.SetStringAsync("key", "value");
```

### Replication and High Availability

```
Master (writes)
  ↓ replicate
  ├─ Replica 1 (reads)
  ├─ Replica 2 (reads)
  └─ Replica 3 (reads)

If master fails → promote a replica
```

## Cache Invalidation Challenges

> "There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton

### Strategies:

**1. TTL (Time-based)**
```csharp
// Simple but may serve stale data or evict fresh data
cache.Set("user:123", user, TimeSpan.FromMinutes(5));
```

**2. Event-based Invalidation**
```csharp
public async Task UpdateUser(User user)
{
    await database.UpdateAsync(user);
    
    // Invalidate cache
    await cache.RemoveAsync($"user:{user.Id}");
    
    // Publish invalidation event (for other app instances)
    await bus.PublishAsync(new UserUpdatedEvent(user.Id));
}
```

**3. Versioning**
```csharp
// Include version in key
var cacheKey = $"user:{userId}:v{userVersion}";
// Old versions automatically age out via TTL
```

**4. Read Repair**
```csharp
var cached = await cache.GetAsync(key);
if (cached != null && IsStale(cached))
{
    cached = await database.GetAsync(key);
    await cache.SetAsync(key, cached);
}
return cached;
```
