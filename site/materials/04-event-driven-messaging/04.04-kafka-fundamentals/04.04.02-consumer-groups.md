## Introduction

In Kafka, **consumer groups** are the mechanism for achieving parallel, scalable consumption of event streams. Unlike traditional message queues where each message is delivered to one consumer, Kafka allows multiple consumer groups to independently read from the same topic, with each group maintaining its own consumption state.

Within a consumer group, Kafka automatically distributes partitions among available consumers, enabling horizontal scalability. Understanding how partition assignment and rebalancing work is crucial for building resilient, high-throughput consumer applications.

## Key Concepts Summary

### Consumer Groups: Independent Stream Readers

A **consumer group** is a set of consumers that cooperate to consume data from a topic. Each group:
- Has a unique `group.id` identifier
- Maintains its own offsets (consumption progress) for each partition
- Enables multiple applications to independently read from the same topic

```
Topic "orders" (3 partitions)
    ↓
Consumer Group "order-processor"
    → Consumer A: reads Partition 0
    → Consumer B: reads Partition 1
    → Consumer C: reads Partition 2

Consumer Group "analytics-service"
    → Consumer X: reads Partitions 0, 1, 2

Consumer Group "audit-logger"
    → Consumer Y: reads Partitions 0, 1
    → Consumer Z: reads Partition 2
```

**Key characteristics:**
- Each partition is consumed by exactly one consumer within a group
- Multiple consumer groups can read from the same topic independently
- Each group tracks its own offsets (consumption position)

### Partition Assignment and Load Balancing

Kafka automatically distributes partitions among consumers in a group. This process is called **partition assignment**:

**Rule:** `Each partition is assigned to exactly ONE consumer in a group`

**Example scenarios:**

```
Topic: 4 partitions, Consumer Group: 2 consumers
├─ Consumer 1: Partitions 0, 1
└─ Consumer 2: Partitions 2, 3

Topic: 4 partitions, Consumer Group: 4 consumers
├─ Consumer 1: Partition 0
├─ Consumer 2: Partition 1
├─ Consumer 3: Partition 2
└─ Consumer 4: Partition 3

Topic: 4 partitions, Consumer Group: 6 consumers
├─ Consumer 1: Partition 0
├─ Consumer 2: Partition 1
├─ Consumer 3: Partition 2
├─ Consumer 4: Partition 3
├─ Consumer 5: (idle - no partitions)
└─ Consumer 6: (idle - no partitions)
```

**Important implications:**
- Maximum parallelism within a group = number of partitions
- Adding more consumers than partitions = idle consumers
- Removing consumers = remaining consumers take over partitions

### Assignment Strategies

Kafka supports several strategies for assigning partitions to consumers:

#### 1. Range Assignor (default)
Assigns contiguous ranges of partitions to consumers:

```
Topic A (4 partitions), Topic B (2 partitions), 2 consumers

Consumer 1:
  - Topic A: Partitions 0, 1
  - Topic B: Partition 0

Consumer 2:
  - Topic A: Partitions 2, 3
  - Topic B: Partition 1
```

**Characteristics:**
- Simple and predictable
- Can lead to unbalanced assignments when subscribing to multiple topics

#### 2. Round-Robin Assignor
Distributes partitions evenly across consumers:

```
Topic A (4 partitions), Topic B (2 partitions), 2 consumers

Consumer 1:
  - Topic A: Partitions 0, 2
  - Topic B: Partition 1

Consumer 2:
  - Topic A: Partitions 1, 3
  - Topic B: Partition 0
```

**Characteristics:**
- Better balance across multiple topics
- May change assignments more dramatically during rebalancing

#### 3. Sticky Assignor
Minimizes partition movement during rebalancing:

**Characteristics:**
- Preserves as many existing assignments as possible
- Reduces rebalancing overhead
- Better for stateful processing

#### 4. Cooperative Sticky Assignor (recommended)
Incremental rebalancing that doesn't stop all consumers:

**Characteristics:**
- Rebalances only affected partitions
- Reduces downtime during consumer group changes
- Default in newer Kafka versions

```csharp
// .NET Kafka consumer configuration
var config = new ConsumerConfig
{
    GroupId = "order-processing-group",
    BootstrapServers = "localhost:9092",
    PartitionAssignmentStrategy = PartitionAssignmentStrategy.CooperativeSticky,
    EnableAutoCommit = false
};
```

### Consumer Group Rebalancing

**Rebalancing** is the process of reassigning partitions when:
- A new consumer joins the group
- An existing consumer leaves the group (gracefully or crashes)
- A consumer fails to send heartbeats within the timeout period
- Partition count changes (topic reconfiguration)

**Rebalancing phases:**

1. **Trigger**: Consumer joins/leaves or heartbeat timeout
2. **Partition revocation**: Consumers stop processing and commit offsets
3. **Partition assignment**: Kafka broker reassigns partitions using the assignment strategy
4. **Partition acquisition**: Consumers receive new assignments and resume processing

```
Initial state (3 consumers, 6 partitions):
Consumer A: [P0, P1]
Consumer B: [P2, P3]
Consumer C: [P4, P5]

Consumer B crashes → Rebalancing triggered

New state (2 consumers, 6 partitions):
Consumer A: [P0, P1, P2]
Consumer C: [P3, P4, P5]
```

**Rebalancing considerations:**
- During rebalancing, the entire consumer group stops processing (eager rebalancing)
- Cooperative rebalancing minimizes this disruption
- Frequent rebalancing impacts throughput
- Configure `session.timeout.ms` and `heartbeat.interval.ms` appropriately

### Scaling Consumer Groups

**Horizontal scaling patterns:**

```csharp
// Producer: Publishing to topic with 12 partitions
var producerConfig = new ProducerConfig { BootstrapServers = "localhost:9092" };
var producer = new ProducerBuilder<string, Order>(producerConfig).Build();

await producer.ProduceAsync("orders", new Message<string, Order>
{
    Key = order.CustomerId,
    Value = order
});

// Consumer Group: Start with 3 consumers
// Each consumer handles 4 partitions (12 / 3 = 4)
```

**Scaling up:**
- Add more consumer instances to the group
- Kafka automatically rebalances
- Processing throughput increases (up to partition count limit)

**Scaling down:**
- Remove consumer instances
- Kafka reassigns their partitions to remaining consumers
- Throughput decreases but system remains available

**Design considerations:**
- Plan partition count based on maximum expected parallelism
- Over-partitioning: `partitions >= expected_max_consumers`
- Monitor consumer lag to identify when scaling is needed
- Use consumer group lag as a scaling metric

```csharp
// Example: Scalable consumer with proper configuration
var config = new ConsumerConfig
{
    GroupId = "order-processor",
    BootstrapServers = "localhost:9092",
    AutoOffsetReset = AutoOffsetReset.Earliest,
    EnableAutoCommit = false,
    
    // Rebalancing configuration
    SessionTimeoutMs = 45000,          // 45 seconds
    HeartbeatIntervalMs = 3000,        // 3 seconds
    MaxPollIntervalMs = 300000,        // 5 minutes
    
    // Assignment strategy
    PartitionAssignmentStrategy = PartitionAssignmentStrategy.CooperativeSticky
};

using var consumer = new ConsumerBuilder<string, Order>(config).Build();
consumer.Subscribe("orders");

while (true)
{
    var consumeResult = consumer.Consume(cancellationToken);
    
    try
    {
        await ProcessOrder(consumeResult.Message.Value);
        consumer.Commit(consumeResult);
    }
    catch (Exception ex)
    {
        // Handle error, potentially reprocess
        logger.LogError(ex, "Failed to process order");
    }
}
```

### Consumer Group Coordination Protocol

**How consumers join a group:**

```
1. Consumer sends JoinGroup request to Group Coordinator
   ↓
2. Coordinator waits for all members (or timeout)
   ↓
3. Coordinator selects a consumer as Group Leader
   ↓
4. Leader receives member list and performs assignment
   ↓
5. Leader sends assignment back to Coordinator
   ↓
6. Coordinator distributes assignments to all members
   ↓
7. Consumers start consuming from assigned partitions
```

**Group Coordinator:**
- Special Kafka broker managing consumer group state
- One coordinator per consumer group
- Stores group metadata and offsets
- Detects consumer failures via heartbeats

```csharp
// Consumer automatically handles coordination
var consumer = new ConsumerBuilder<string, Order>(config)
    .SetPartitionsAssignedHandler((c, partitions) =>
    {
        _logger.LogInformation(
            "Partitions assigned: {Partitions}",
            string.Join(", ", partitions.Select(p => p.Partition)));
    })
    .SetPartitionsRevokedHandler((c, partitions) =>
    {
        _logger.LogInformation(
            "Partitions revoked: {Partitions}",
            string.Join(", ", partitions.Select(p => p.Partition)));
    })
    .Build();
```

### Rebalancing Deep Dive

**Eager Rebalancing (Legacy):**

```
Time T0: Consumer A [P0, P1], Consumer B [P2, P3]
         ↓
Time T1: Consumer C joins
         ↓
Time T2: ALL consumers stop consuming (stop-the-world)
         ↓
Time T3: Rebalancing in progress
         ↓
Time T4: New assignment: A [P0], B [P1, P2], C [P3]
         ↓
Time T5: ALL consumers resume (including A and B who didn't need changes)
```

**Cooperative Rebalancing (Modern):**

```
Time T0: Consumer A [P0, P1], Consumer B [P2, P3]
         ↓
Time T1: Consumer C joins
         ↓
Time T2: Only affected partitions stop (P1, P3)
         ↓
Time T3: Incremental rebalancing
         ↓
Time T4: P1 → C, P3 stays with B
         ↓
Time T5: Only affected consumers resume
```

**Configuration:**

```csharp
var config = new ConsumerConfig
{
    GroupId = "my-group",
    BootstrapServers = "localhost:9092",
    
    // Use cooperative rebalancing
    PartitionAssignmentStrategy = PartitionAssignmentStrategy.CooperativeSticky,
    
    // Heartbeat configuration
    SessionTimeoutMs = 45000,      // Max time without heartbeat before considered dead
    HeartbeatIntervalMs = 3000,    // Send heartbeat every 3 seconds
    
    // Processing timeout
    MaxPollIntervalMs = 300000     // Max time between poll() calls (5 minutes)
};
```

**Preventing unnecessary rebalances:**

```csharp
public class OptimizedConsumer
{
    public async Task ConsumeAsync(CancellationToken ct)
    {
        using var consumer = new ConsumerBuilder<string, Order>(config).Build();
        consumer.Subscribe("orders");
        
        while (!ct.IsCancellationRequested)
        {
            try
            {
                // Poll frequently to send heartbeats
                var result = consumer.Consume(TimeSpan.FromSeconds(1));
                
                if (result != null)
                {
                    // Process quickly to avoid MaxPollInterval timeout
                    await ProcessWithTimeout(result.Message.Value, 
                        TimeSpan.FromMinutes(4));
                    
                    consumer.Commit(result);
                }
            }
            catch (ConsumeException ex)
            {
                _logger.LogError(ex, "Consume error");
            }
        }
    }
    
    private async Task ProcessWithTimeout(Order order, TimeSpan timeout)
    {
        using var cts = new CancellationTokenSource(timeout);
        
        try
        {
            await ProcessOrder(order, cts.Token);
        }
        catch (OperationCanceledException)
        {
            _logger.LogWarning("Processing timeout, consumer may rebalance");
            throw;
        }
    }
}
```

### Static Group Membership

**Problem:** Frequent rebalances when consumers restart

**Solution:** Static membership (Kafka 2.3+)

```csharp
var config = new ConsumerConfig
{
    GroupId = "order-processor",
    BootstrapServers = "localhost:9092",
    
    // Static member ID
    GroupInstanceId = "consumer-1",  // Unique, stable identifier
    
    SessionTimeoutMs = 45000
};

// Benefits:
// - Consumer keeps same partitions after restart
// - No rebalancing if restart happens within session timeout
// - Faster recovery
```

**Use cases:**
- Stateful processing (local caches, state stores)
- Containerized deployments with stable IDs
- Minimizing rebalancing disruption

### Multi-Topic Consumption

```csharp
public class MultiTopicConsumer
{
    public void ConsumeMultipleTopics()
    {
        var consumer = new ConsumerBuilder<string, string>(config).Build();
        
        // Subscribe to multiple topics
        consumer.Subscribe(new[] { "orders", "payments", "shipments" });
        
        while (true)
        {
            var result = consumer.Consume();
            
            // Route by topic
            switch (result.Topic)
            {
                case "orders":
                    await ProcessOrder(result.Message);
                    break;
                case "payments":
                    await ProcessPayment(result.Message);
                    break;
                case "shipments":
                    await ProcessShipment(result.Message);
                    break;
            }
            
            consumer.Commit(result);
        }
    }
    
    public void ConsumeWithPattern()
    {
        var consumer = new ConsumerBuilder<string, string>(config).Build();
        
        // Subscribe to all topics matching pattern
        consumer.Subscribe("^order-.*");  // order-us, order-eu, order-asia
        
        while (true)
        {
            var result = consumer.Consume();
            ProcessOrder(result.Topic, result.Message);
            consumer.Commit(result);
        }
    }
}
```

### Monitoring Consumer Groups

```csharp
public class ConsumerGroupMonitoring
{
    public async Task MonitorLag()
    {
        var adminClient = new AdminClientBuilder(config).Build();
        
        // Get consumer group description
        var groupDesc = await adminClient.DescribeConsumerGroupsAsync(
            new[] { "order-processor" });
        
        foreach (var group in groupDesc)
        {
            _logger.LogInformation($"Group: {group.GroupId}");
            _logger.LogInformation($"State: {group.State}");
            _logger.LogInformation($"Members: {group.Members.Count}");
            
            foreach (var member in group.Members)
            {
                _logger.LogInformation(
                    $"  Member {member.MemberId}: " +
                    $"{member.Assignment.Partitions.Count} partitions");
            }
        }
        
        // Check lag for each partition
        var consumer = new ConsumerBuilder<string, Order>(config).Build();
        consumer.Subscribe("orders");
        
        // Trigger assignment
        consumer.Consume(TimeSpan.FromSeconds(1));
        
        var assignment = consumer.Assignment;
        foreach (var partition in assignment)
        {
            var committed = consumer.Committed(new[] { partition }, TimeSpan.FromSeconds(10));
            var watermark = consumer.GetWatermarkOffsets(partition);
            
            var committedOffset = committed[0].Offset.Value;
            var highWatermark = watermark.High.Value;
            var lag = highWatermark - committedOffset;
            
            _logger.LogInformation(
                $"Partition {partition.Partition}: Lag = {lag} messages");
            
            if (lag > 10000)
            {
                _logger.LogWarning($"High lag detected: {lag} messages");
            }
        }
    }
}
```
