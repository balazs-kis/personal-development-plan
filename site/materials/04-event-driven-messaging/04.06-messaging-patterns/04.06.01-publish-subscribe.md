## Introduction

The **Publish-Subscribe (Pub/Sub) pattern** is one of the most fundamental messaging patterns in distributed systems. It enables one-to-many communication where a publisher sends a message once, and multiple independent subscribers receive a copy. This pattern is the foundation of event-driven architectures, enabling loose coupling, parallel processing, and system scalability.

Unlike point-to-point messaging where each message is consumed by exactly one consumer, pub/sub broadcasts messages to all interested subscribers. Each subscriber maintains its own subscription and can process messages independently, at its own pace, without affecting other subscribers. This independence is crucial for building resilient, scalable systems where components can be added, removed, or updated without disrupting the overall architecture.

The pattern shines in scenarios where a single event needs to trigger multiple independent actions. For example, when a customer places an order, you might need to reserve inventory, process payment, send confirmation emails, update analytics, and notify a fulfillment center—all in response to a single "OrderPlaced" event.

## Key Concepts Summary

### What is Publish-Subscribe?

**Definition:** Publishers send messages to a topic/channel without knowledge of subscribers. Multiple subscribers can independently receive copies of each message.

```
Publisher → [Topic/Channel] → Subscriber A
                           → Subscriber B
                           → Subscriber C
```

**Key characteristics:**
- **One-to-many:** One message, multiple recipients
- **Loose coupling:** Publishers and subscribers don't know about each other
- **Independent consumption:** Each subscriber processes at its own pace
- **Message copies:** Each subscriber gets its own copy of the message

### Pub/Sub vs Point-to-Point

| Aspect | Point-to-Point | Publish-Subscribe |
|--------|----------------|-------------------|
| Message recipients | One consumer | Multiple subscribers |
| Message consumption | Consumed once | Copied to all subscribers |
| Coupling | Producer knows queue | Producer knows only topic |
| Use case | Task distribution | Event broadcasting |
| Example | Order processing queue | Order created event |

### Pub/Sub in RabbitMQ: Fanout Exchange

RabbitMQ implements pub/sub using **fanout exchanges** that broadcast to all bound queues:

```csharp
// Publisher: Sends order created event
public class OrderEventPublisher
{
    private readonly IConnection _connection;
    private readonly IModel _channel;
    
    public OrderEventPublisher(string hostname)
    {
        var factory = new ConnectionFactory { HostName = hostname };
        _connection = factory.CreateConnection();
        _channel = _connection.CreateModel();
        
        // Declare fanout exchange (pub/sub)
        _channel.ExchangeDeclare(
            exchange: "order-events",
            type: ExchangeType.Fanout,  // Fanout = broadcast to all
            durable: true,
            autoDelete: false
        );
    }
    
    public void PublishOrderCreated(Order order)
    {
        var message = new OrderCreatedEvent
        {
            OrderId = order.Id,
            CustomerId = order.CustomerId,
            TotalAmount = order.TotalAmount,
            CreatedAt = DateTime.UtcNow
        };
        
        var body = Encoding.UTF8.GetBytes(JsonSerializer.Serialize(message));
        
        var properties = _channel.CreateBasicProperties();
        properties.Persistent = true;
        properties.ContentType = "application/json";
        properties.Type = nameof(OrderCreatedEvent);
        
        // Publish to fanout exchange (no routing key needed)
        _channel.BasicPublish(
            exchange: "order-events",
            routingKey: "",  // Ignored for fanout exchanges
            basicProperties: properties,
            body: body
        );
        
        Console.WriteLine($"Published OrderCreated event for order {order.Id}");
    }
}
```

**Subscriber 1: Inventory Service**

```csharp
public class InventorySubscriber
{
    private readonly IConnection _connection;
    private readonly IModel _channel;
    
    public InventorySubscriber(string hostname)
    {
        var factory = new ConnectionFactory { HostName = hostname };
        _connection = factory.CreateConnection();
        _channel = _connection.CreateModel();
        
        // Declare same fanout exchange
        _channel.ExchangeDeclare(
            exchange: "order-events",
            type: ExchangeType.Fanout,
            durable: true
        );
        
        // Create exclusive queue for this subscriber
        var queueName = _channel.QueueDeclare(
            queue: "inventory-service-orders",  // Named queue
            durable: true,
            exclusive: false,
            autoDelete: false
        ).QueueName;
        
        // Bind queue to exchange
        _channel.QueueBind(
            queue: queueName,
            exchange: "order-events",
            routingKey: ""  // No routing key for fanout
        );
        
        Console.WriteLine($"Inventory service listening on queue: {queueName}");
    }
    
    public void Start()
    {
        var consumer = new EventingBasicConsumer(_channel);
        
        consumer.Received += (model, ea) =>
        {
            var body = ea.Body.ToArray();
            var message = Encoding.UTF8.GetString(body);
            var evt = JsonSerializer.Deserialize<OrderCreatedEvent>(message);
            
            // Process event
            Console.WriteLine($"[Inventory] Received OrderCreated: {evt.OrderId}");
            ReserveInventory(evt);
            
            _channel.BasicAck(ea.DeliveryTag, false);
        };
        
        _channel.BasicConsume(
            queue: "inventory-service-orders",
            autoAck: false,
            consumer: consumer
        );
    }
    
    private void ReserveInventory(OrderCreatedEvent evt)
    {
        // Business logic: reserve inventory for order
        Console.WriteLine($"[Inventory] Reserved inventory for order {evt.OrderId}");
    }
}
```

**Key points:**

### Pub/Sub in Kafka: Multiple Consumer Groups

Kafka implements pub/sub using **multiple consumer groups** reading from the same topic:

```csharp
// Producer: Publishes to topic
public class OrderEventProducer
{
    private readonly IProducer<string, OrderCreatedEvent> _producer;
    
    public OrderEventProducer(string bootstrapServers)
    {
        var config = new ProducerConfig
        {
            BootstrapServers = bootstrapServers,
            Acks = Acks.All
        };
        
        _producer = new ProducerBuilder<string, OrderCreatedEvent>(config)
            .SetValueSerializer(new JsonSerializer<OrderCreatedEvent>())
            .Build();
    }
    
    public async Task PublishOrderCreated(Order order)
    {
        var evt = new OrderCreatedEvent
        {
            OrderId = order.Id,
            CustomerId = order.CustomerId,
            TotalAmount = order.TotalAmount,
            CreatedAt = DateTime.UtcNow
        };
        
        var result = await _producer.ProduceAsync(
            "order-events",  // Topic
            new Message<string, OrderCreatedEvent>
            {
                Key = order.Id,
                Value = evt,
                Headers = new Headers
                {
                    { "event-type", Encoding.UTF8.GetBytes(nameof(OrderCreatedEvent)) }
                }
            }
        );
        
        Console.WriteLine($"Published OrderCreated to partition {result.Partition} at offset {result.Offset}");
    }
}
```

**Subscriber 1: Inventory Service (Consumer Group A)**

```csharp
public class InventoryConsumer
{
    private readonly IConsumer<string, OrderCreatedEvent> _consumer;
    
    public InventoryConsumer(string bootstrapServers)
    {
        var config = new ConsumerConfig
        {
            BootstrapServers = bootstrapServers,
            GroupId = "inventory-service",  // Unique consumer group
            AutoOffsetReset = AutoOffsetReset.Earliest,
            EnableAutoCommit = false
        };
        
        _consumer = new ConsumerBuilder<string, OrderCreatedEvent>(config)
            .SetValueDeserializer(new JsonDeserializer<OrderCreatedEvent>())
            .Build();
        
        _consumer.Subscribe("order-events");
    }
    
    public void Start(CancellationToken cancellationToken)
    {
        while (!cancellationToken.IsCancellationRequested)
        {
            var result = _consumer.Consume(cancellationToken);
            
            Console.WriteLine($"[Inventory] Received OrderCreated: {result.Message.Value.OrderId}");
            ReserveInventory(result.Message.Value);
            
            _consumer.Commit(result);
        }
    }
    
    private void ReserveInventory(OrderCreatedEvent evt)
    {
        Console.WriteLine($"[Inventory] Reserved inventory for order {evt.OrderId}");
    }
}
```

**Key points:**
- Each service uses a different `GroupId` (consumer group)

- Groups can consume at different rates

### Use Cases for Pub/Sub

**1. Event Notification**
```
Order placed → [OrderCreated event] → Inventory service (reserve stock)
                                    → Email service (send confirmation)
                                    → Analytics service (track metrics)
                                    → Loyalty service (award points)
```

**2. Cache Invalidation**
```
Product updated → [ProductChanged event] → API Gateway (clear cache)
                                         → Search service (reindex)
                                         → Recommendation engine (update model)
```

**3. System Integration**
```
User registered → [UserCreated event] → CRM system (create contact)
                                      → Email service (welcome email)
                                      → Analytics (track signup)
                                      → Compliance (start KYC)
```

### Handling Subscriber Failures

**Scenario: Subscriber is temporarily down**

RabbitMQ approach:
- Messages accumulate in the subscriber's queue
- Queue holds messages until subscriber reconnects
- Configure queue length limits to prevent overflow

```csharp
// Declare queue with max length
var arguments = new Dictionary<string, object>
{
    { "x-max-length", 10000 },  // Max 10,000 messages
    { "x-overflow", "reject-publish" }  // Or "drop-head"
};

_channel.QueueDeclare(
    queue: "email-service-orders",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: arguments
);
```

Kafka approach:
- Messages retained in topic (up to retention limit)
- Consumer lag increases
- Consumer catches up when it reconnects

```csharp
// Monitor consumer lag
var watermarkOffsets = _consumer.GetWatermarkOffsets(
    new TopicPartition("order-events", 0)
);
var currentOffset = _consumer.Position(new TopicPartition("order-events", 0));
var lag = watermarkOffsets.High.Value - currentOffset;

Console.WriteLine($"Consumer lag: {lag} messages");
```

### Design Considerations

**When to use pub/sub:**
- ✅ Multiple systems need the same information
- ✅ Loose coupling between services is required
- ✅ Systems can be added/removed dynamically
- ✅ Each subscriber has independent processing logic
- ✅ Event notification and system integration scenarios
- ✅ Broadcasting state changes to multiple interested parties

**When NOT to use pub/sub:**
- ❌ Only one consumer needs each message (use point-to-point)
- ❌ Subscribers must process in specific order (use choreography with dependencies)
- ❌ Response is needed from subscribers (use request-reply)
- ❌ Tight coupling and immediate consistency required

### Comparing RabbitMQ and Kafka Pub/Sub

| Aspect | RabbitMQ (Fanout Exchange) | Kafka (Consumer Groups) |
|--------|---------------------------|-------------------------|
| Routing | Broker routes to queues | Consumers pull from topic |
| Message retention | Deleted after consumption | Retained by time/size |
| Replay capability | No | Yes (rewind offset) |
| New subscriber behavior | Receives only new messages | Can read from beginning |
| Dynamic subscription | Easy (new queue binding) | Easy (new consumer group) |
| Ordering | Per queue | Per partition |
| Performance overhead | Higher per message | Lower (batch processing) |

**Message durability:**

RabbitMQ approach:
- Messages persist in individual queues
- Each subscriber queue holds a copy
- Messages deleted after acknowledgment
- Storage grows linearly with subscribers

Kafka approach:
- Single copy in topic (log)
- All consumer groups read same data
- Retention based on time/size policy
- Storage independent of subscriber count

### Advanced Pub/Sub Patterns

**Pattern 1: Selective Broadcasting with Filtering**

Sometimes you want pub/sub behavior but with selective delivery:

```csharp
// RabbitMQ with topic exchange (selective pub/sub)
_channel.ExchangeDeclare("events", ExchangeType.Topic, durable: true);

// Publisher categorizes events
_channel.BasicPublish("events", "order.us.created", null, body);
_channel.BasicPublish("events", "order.eu.cancelled", null, body);

// Subscriber 1: All US orders
_channel.QueueBind(queue, "events", "order.us.*");

// Subscriber 2: All cancelled orders
_channel.QueueBind(queue, "events", "order.*.cancelled");

// Subscriber 3: All orders
_channel.QueueBind(queue, "events", "order.#");
```

**Pattern 2: Late Subscriber (Kafka Advantage)**

```csharp
// New analytics service added 1 month after system launch
var config = new ConsumerConfig
{
    GroupId = "analytics-service-new",
    AutoOffsetReset = AutoOffsetReset.Earliest  // Read from beginning
};

// Can process all historical events!
```

**Pattern 3: Fan-out with Aggregation**

```csharp
// Multiple services process event and contribute to response
public class OrderOrchestrator
{
    private readonly Dictionary<string, OrderProcessingState> _pendingOrders = new();
    
    public async Task PublishOrderCreated(Order order)
    {
        var state = new OrderProcessingState
        {
            OrderId = order.Id,
            PendingResponses = new HashSet<string> 
            { 
                "inventory", "payment", "shipping" 
            }
        };
        _pendingOrders[order.Id] = state;
        
        // Broadcast to all services
        await _producer.ProduceAsync("order-events", new OrderCreatedEvent(order));
    }
    
    public void OnServiceCompleted(string orderId, string serviceName)
    {
        if (_pendingOrders.TryGetValue(orderId, out var state))
        {
            state.PendingResponses.Remove(serviceName);
            
            if (state.PendingResponses.Count == 0)
            {
                // All services completed
                CompleteOrder(orderId);
            }
        }
    }
}
```

### Error Handling and Recovery

**Handling poison messages in subscribers:**

```csharp
// RabbitMQ subscriber with retry logic
public class ResilientSubscriber
{
    private readonly IModel _channel;
    private const int MaxRetries = 3;
    
    public void Start()
    {
        var consumer = new EventingBasicConsumer(_channel);
        
        consumer.Received += async (model, ea) =>
        {
            var retryCount = GetRetryCount(ea.BasicProperties);
            
            try
            {
                await ProcessMessage(ea.Body);
                _channel.BasicAck(ea.DeliveryTag, false);
            }
            catch (Exception ex) when (retryCount < MaxRetries)
            {
                // Requeue with incremented retry count
                var properties = _channel.CreateBasicProperties();
                properties.Headers = new Dictionary<string, object>
                {
                    { "retry-count", retryCount + 1 }
                };
                
                _channel.BasicPublish("", ea.RoutingKey, properties, ea.Body);
                _channel.BasicAck(ea.DeliveryTag, false);
                
                _logger.LogWarning($"Retry {retryCount + 1}/{MaxRetries} for message");
            }
            catch
            {
                // Max retries exceeded - send to DLX
                _channel.BasicNack(ea.DeliveryTag, false, false);
                _logger.LogError("Message failed after max retries");
            }
        };
        
        _channel.BasicConsume(queue, false, consumer);
    }
    
    private int GetRetryCount(IBasicProperties properties)
    {
        if (properties?.Headers?.TryGetValue("retry-count", out var value) == true)
        {
            return Convert.ToInt32(value);
        }
        return 0;
    }
}
```

**Kafka subscriber with error handling:**

```csharp
public class ResilientKafkaConsumer
{
    private readonly IConsumer<string, OrderEvent> _consumer;
    private readonly IProducer<string, FailedMessage> _dlqProducer;
    
    public void Start(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            try
            {
                var result = _consumer.Consume(ct);
                
                try
                {
                    ProcessMessage(result.Message.Value);
                    _consumer.Commit(result);
                }
                catch (TransientException ex)
                {
                    // Don't commit - will be retried after rebalance
                    _logger.LogWarning($"Transient failure: {ex.Message}");
                    await Task.Delay(TimeSpan.FromSeconds(5), ct);
                }
                catch (Exception ex)
                {
                    // Permanent failure - send to DLQ and commit
                    await SendToDLQ(result, ex);
                    _consumer.Commit(result);
                }
            }
            catch (ConsumeException ex)
            {
                _logger.LogError($"Consume error: {ex.Error.Reason}");
            }
        }
    }
    
    private async Task SendToDLQ(ConsumeResult<string, OrderEvent> result, Exception ex)
    {
        await _dlqProducer.ProduceAsync("failed-order-events", new Message<string, FailedMessage>
        {
            Key = result.Message.Key,
            Value = new FailedMessage
            {
                OriginalTopic = result.Topic,
                OriginalPartition = result.Partition.Value,
                OriginalOffset = result.Offset.Value,
                Payload = result.Message.Value,
                Error = ex.Message,
                FailedAt = DateTime.UtcNow
            }
        });
    }
}
```

### Monitoring and Observability

**Tracking pub/sub health:**

```csharp
public class PubSubMetrics
{
    private readonly Counter _published;
    private readonly Counter _received;
    private readonly Histogram _publishLatency;
    private readonly Gauge _subscriberLag;
    
    public void RecordPublish(string topic, TimeSpan elapsed)
    {
        _published.Add(1, new("topic", topic));
        _publishLatency.Record(elapsed.TotalMilliseconds, new("topic", topic));
    }
    
    public void RecordConsume(string topic, string subscriber)
    {
        _received.Add(1, new("topic", topic), new("subscriber", subscriber));
    }
    
    public async Task UpdateLagMetrics(IConsumer<string, string> consumer)
    {
        var assignment = consumer.Assignment;
        
        foreach (var partition in assignment)
        {
            var watermark = consumer.GetWatermarkOffsets(partition);
            var position = consumer.Position(partition);
            var lag = watermark.High.Value - position.Value;
            
            _subscriberLag.Record(lag, 
                new("topic", partition.Topic),
                new("partition", partition.Partition.Value.ToString()));
        }
    }
}
```
