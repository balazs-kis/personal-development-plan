## Learning Objectives

By the end of this lesson, you will be able to:
- Understand how different message brokers persist messages

- Design systems that leverage persistent messaging appropriately

## Introduction

Message persistence and replay capability are critical differentiators between message brokers. While traditional message queues delete messages after delivery, event streaming platforms retain them for replay. Understanding these differences helps you choose the right broker and design more robust, audit-friendly systems.

## Key Concepts Summary

### Message Queue Persistence (RabbitMQ)

**Temporary by Design:**
- Messages deleted after acknowledgment
- Persistence for reliability, not replay
- Durable queues survive broker restart
- Messages on disk for crash recovery

**Example:**
```csharp
// Durable queue - survives broker restart
channel.QueueDeclare(
    queue: "orders",
    durable: true,      // Queue survives restart
    exclusive: false,
    autoDelete: false
);

// Persistent message
var properties = channel.CreateBasicProperties();
properties.Persistent = true;  // Message written to disk

channel.BasicPublish(
    exchange: "",
    routingKey: "orders",
    basicProperties: properties,
    body: message
);

// After consumer acknowledges, message is DELETED
channel.BasicAck(deliveryTag, multiple: false);
```

### Event Stream Persistence (Kafka)

**Retention-Based:**
- Events retained for configured period
- Time-based or size-based retention
- Consumers can replay historical events
- Log compaction for stateful streams

**Retention Policies:**
```csharp
// Time-based retention (7 days)
var config = new AdminClientConfig
{
    BootstrapServers = "localhost:9092"
};

var topicConfig = new Dictionary<string, string>
{
    { "retention.ms", "604800000" },  // 7 days in milliseconds
    { "retention.bytes", "-1" }        // Unlimited size
};

// Size-based retention (1GB per partition)
topicConfig["retention.bytes"] = "1073741824";

// Log compaction (keep latest value per key)
topicConfig["cleanup.policy"] = "compact";
```

**Replay Capability:**
```csharp
// Consumer can replay from any point
public class ReplayableConsumer
{
    public void ConsumeFromBeginning()
    {
        // Start from earliest message
        var offset = new TopicPartitionOffset("orders", 0, Offset.Beginning);
        _consumer.Assign(new[] { offset });
        
        while (true)
        {
            var result = _consumer.Consume();
            ProcessMessage(result.Message);
        }
    }
    
    public void ConsumeFromTimestamp(DateTime timestamp)
    {
        // Start from specific time
        var timestampOffset = new Timestamp(timestamp);
        var partitions = _consumer.OffsetsForTimes(
            new[] { new TopicPartitionTimestamp("orders", 0, timestampOffset) },
            TimeSpan.FromSeconds(10)
        );
        
        _consumer.Assign(partitions.Select(p => new TopicPartitionOffset(
            p.TopicPartition, p.Offset
        )));
    }
}
```

### Use Cases for Replay

**1. Reprocessing After Bug Fixes:**
```csharp
// Bug fixed, reprocess last 24 hours
public async Task ReprocessAfterBugFixAsync()
{
    var yesterday = DateTime.UtcNow.AddDays(-1);
    
    // Reset offset to 24 hours ago
    var offset = GetOffsetForTimestamp(yesterday);
    _consumer.Seek(offset);
    
    // Reprocess all events
    while (true)
    {
        var result = _consumer.Consume();
        if (result.Message.Timestamp.UtcDateTime > DateTime.UtcNow)
            break;
        
        await ProcessWithFixedLogicAsync(result.Message);
    }
}
```

**5. Time Travel Debugging:**
```csharp
// Reproduce a bug that occurred at specific time
public class TimeTravelDebugger
{
    public async Task ReproduceBugAsync(DateTime bugOccurredAt)
    {
        // Go back to just before the bug
        var startTime = bugOccurredAt.AddHours(-1);
        var offset = GetOffsetForTimestamp(startTime);
        
        _consumer.Seek(offset);
        
        // Step through events leading to bug
        while (true)
        {
            var result = _consumer.Consume();
            
            if (result.Message.Timestamp.UtcDateTime < bugOccurredAt)
            {
                // Process events normally
                await ProcessAsync(result.Message);
            }
            else
            {
                // We've reached the bug timeframe - enable detailed logging
                _logger.SetLevel(LogLevel.Trace);
                await ProcessWithDetailedLoggingAsync(result.Message);
            }
            
            if (result.Message.Timestamp.UtcDateTime > bugOccurredAt.AddMinutes(10))
                break;
        }
    }
}
```

**Size-Based Retention:**

**Log Compaction for State Streams:**
```csharp
// Compaction keeps only latest value per key
public class CompactedStateStream
{
    public void ConfigureCompaction()
    {
        var topicConfig = new Dictionary<string, string>
        {
            { "cleanup.policy", "compact" },
            
            // Min time before log is eligible for compaction
            { "min.compaction.lag.ms", "3600000" }, // 1 hour
            
            // Max time a delete marker is retained
            { "delete.retention.ms", "86400000" }, // 1 day
            
            // Ratio of dirty/total entries that triggers compaction
            { "min.cleanable.dirty.ratio", "0.5" }
        };
    }
    
    // Example: User profile stream
    public async Task UpdateUserProfileAsync(UserProfile profile)
    {
        // Key is user ID - compaction keeps latest profile
        await _producer.ProduceAsync("user-profiles", new Message<string, string>
        {
            Key = profile.UserId,
            Value = JsonSerializer.Serialize(profile)
        });
        
        // Old profiles for this user will be removed during compaction
    }
    
    // Consumer can rebuild current state from compacted log
    public async Task<Dictionary<string, UserProfile>> RebuildStateAsync()
    {
        var state = new Dictionary<string, UserProfile>();
        
        _consumer.Assign(new[] {
            new TopicPartitionOffset("user-profiles", 0, Offset.Beginning)
        });
        
        // Read compacted log - only latest values
        while (true)
        {
            var result = _consumer.Consume(TimeSpan.FromSeconds(1));
            if (result == null) break;
            
            var profile = JsonSerializer.Deserialize<UserProfile>(result.Message.Value);
            state[result.Message.Key] = profile;
        }
        
        return state;
    }
}
```

### RabbitMQ Persistence Best Practices

**Durability vs Performance Trade-offs:**
```csharp
public class RabbitMQPersistenceConfig
{
    // Full durability (slowest)
    public void ConfigureFullDurability()
    {
        // Durable queue
        channel.QueueDeclare(
            queue: "critical-orders",
            durable: true,
            exclusive: false,
            autoDelete: false
        );
        
        // Persistent messages
        var properties = channel.CreateBasicProperties();
        properties.Persistent = true;
        properties.DeliveryMode = 2; // Persistent
        
        // Publisher confirms
        channel.ConfirmSelect();
        
        channel.BasicPublish("", "critical-orders", properties, message);
        channel.WaitForConfirmsOrDie(); // Wait for disk write
    }
    
    // Balanced approach
    public void ConfigureBalanced()
    {
        // Durable queue
        channel.QueueDeclare("orders", durable: true);
        
        // Persistent messages
        var properties = channel.CreateBasicProperties();
        properties.Persistent = true;
        
        // Async confirms
        channel.ConfirmSelect();
        channel.BasicPublish("", "orders", properties, message);
        
        // Don't wait - continue publishing
        // Check confirms asynchronously
    }
    
    // Performance-optimized (transient)
    public void ConfigureTransient()
    {
        // Non-durable queue (in-memory only)
        channel.QueueDeclare(
            queue: "notifications",
            durable: false,
            exclusive: false,
            autoDelete: true
        );
        
        // Non-persistent messages
        var properties = channel.CreateBasicProperties();
        properties.Persistent = false;
        
        // No confirms
        channel.BasicPublish("", "notifications", properties, message);
        
        // Fastest, but messages lost on broker restart
    }
}
```

### Comparison

| Aspect | RabbitMQ | Kafka |
|--------|----------|-------|
| **Purpose of Persistence** | Reliability | Replay & retention |
| **After Consumption** | Deleted | Retained |
| **Retention** | Until acknowledged | Time/size-based |
| **Replay** | Not possible | Fully supported |
| **Audit Trail** | External required | Built-in |
| **Storage Cost** | Low (temporary) | Higher (retention period) |
| **Use Case** | Task queues | Event streaming, analytics |

```csharp

{
```

```csharp
    {
        // Non-durable queue for transient jobs
        channel.QueueDeclare(
            queue: "background-jobs",
            durable: false,      // Don't need to survive restart
            exclusive: false,
            autoDelete: true,    // Delete when no consumers
            arguments: new Dictionary<string, object>
            {
                // TTL - jobs expire after 1 hour
                { "x-message-ttl", 3600000 },
                
                // Max length - drop old jobs if queue fills
                { "x-max-length", 10000 }
            }
        );
        
        // Non-persistent messages
        var properties = channel.CreateBasicProperties();
        properties.Persistent = false;
        properties.Expiration = "3600000"; // 1 hour
    }
}

// Jobs processed once and deleted
public class JobProcessor
{
    public void ProcessJobs()
    {
        var consumer = new EventingBasicConsumer(channel);
        consumer.Received += async (model, ea) =>
        {
            var job = Deserialize<BackgroundJob>(ea.Body.ToArray());
            
            await ProcessJobAsync(job);
```

**Replay needed:** No  
**Cost:** Very low (minimal retention)

## Self-Check Questions

1. What's the main purpose of persistence in RabbitMQ vs Kafka?
   - **Answer:** RabbitMQ persists messages for reliability (crash recovery), deleting them after acknowledgment. Kafka persists for replay and historical analysis, retaining events for a configured period.

2. How does replay capability enable time-travel debugging?
   - **Answer:** By seeking to a specific timestamp or offset, you can replay events that occurred before a bug, processing them with detailed logging or fixed logic to understand and reproduce the issue.

3. What is log compaction and when would you use it?
   - **Answer:** Log compaction keeps only the latest value per key, removing intermediate updates. Use it for state streams (user profiles, configuration) where you need current state plus ability to rebuild history, but don't need every intermediate change.

4. Why might you choose different retention policies for different topics?
   - **Answer:** Different data has different value over time. High-volume transient data (clicks) needs short retention, while audit logs need years. Balance storage costs against replay and compliance needs.

5. Can you rebuild application state from a Kafka topic?
   - **Answer:** Yes! By consuming from Offset.Beginning, you can replay all events to reconstruct current state. This is fundamental to event sourcing and enables building new read models from historical events.

**Additional Questions:**

6. What are the storage implications of using Kafka vs RabbitMQ?
   - **Answer:** Kafka requires significantly more storage (GBs to TBs) since it retains all events for the retention period. RabbitMQ only stores unacknowledged messages temporarily (MBs to low GBs), deleting after acknowledgment.

7. How does RabbitMQ ensure messages aren't lost on broker restart?
   - **Answer:** By using durable queues and persistent messages (deliveryMode=2), messages are written to disk. However, they're still deleted after acknowledgment—persistence is for reliability, not replay.

8. What's the trade-off between retention period and storage cost?
   - **Answer:** Longer retention enables more replay scenarios and historical analysis but increases storage costs linearly. Use compression, compaction, and tiered storage to balance cost vs value.

## Key Takeaways

- **Message queues** persist for reliability, delete after consumption
- **Event streams** retain for replay and historical analysis
- **Kafka** enables time-travel debugging and new consumer onboarding
- **Retention policies** balance storage cost vs replay value
- **Log compaction** provides efficient storage for state streams
- Choose based on audit requirements, reprocessing needs, and storage budget
- Different topics can have different retention strategies based on data value
