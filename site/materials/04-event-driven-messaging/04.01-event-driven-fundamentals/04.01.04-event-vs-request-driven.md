# Lesson 4: Event-Driven vs Request-Driven Architecture

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the fundamental differences between event-driven and request-driven architectures
- Recognize when to use each architectural style
- Evaluate trade-offs between the two approaches
- Design hybrid systems that combine both patterns effectively

---

## Introduction

Most developers are familiar with request-driven (synchronous) architectures—the traditional client-server model where requests flow in one direction and responses flow back. Event-driven architecture represents a paradigm shift where services communicate through events asynchronously. Understanding both approaches and their trade-offs is essential for making informed architectural decisions.

## Key Concepts Summary

### Request-Driven Architecture

**Definition:** A request-driven (synchronous) architecture is one where services communicate through direct request-response calls. The client sends a request and waits for a response before continuing.

**Characteristics:**
- Synchronous communication
- Direct service-to-service calls
- Request-response pattern
- Tight coupling between services
- Immediate consistency
- Blocking operations

**Example:**
```csharp
// Request-Driven: Synchronous calls
public class OrderService
{
    private readonly IInventoryService _inventoryService;
    private readonly IPaymentService _paymentService;
    private readonly INotificationService _notificationService;
    
    public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
    {
        // Step 1: Check inventory (BLOCKS)
        var inventoryResult = await _inventoryService.CheckAvailabilityAsync(request.Items);
        if (!inventoryResult.IsAvailable)
            throw new InsufficientInventoryException();
        
        // Step 2: Process payment (BLOCKS)
        var paymentResult = await _paymentService.ProcessPaymentAsync(request.Payment);
        if (!paymentResult.Success)
            throw new PaymentFailedException();
        
        // Step 3: Create order
        var order = await _orderRepository.CreateAsync(request);
        
        // Step 4: Send notification (BLOCKS)
        await _notificationService.SendConfirmationAsync(order.Id);
        
        return new OrderResult { OrderId = order.Id };
    }
}
```

**Pros:**
- ✅ Simple to understand and implement
- ✅ Immediate feedback and error handling
- ✅ Strong consistency guarantees
- ✅ Easier debugging and tracing
- ✅ Familiar pattern for most developers

**Cons:**
- ❌ Tight coupling between services
- ❌ All services must be available simultaneously
- ❌ Cascading failures
- ❌ Difficult to scale independently
- ❌ Higher latency (sum of all service calls)

### Event-Driven Architecture

**Definition:** An event-driven architecture is one where services communicate through events asynchronously. Services publish events when something happens, and other services subscribe to events they care about.

**Characteristics:**
- Asynchronous communication
- Event-based messaging
- Loose coupling between services
- Eventual consistency
- Non-blocking operations
- Independent service operation

**Example:**
```csharp
// Event-Driven: Asynchronous events
public class OrderService
{
    private readonly IEventBus _eventBus;
    
    public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
    {
        // Create order immediately
        var order = await _orderRepository.CreateAsync(request);
        
        // Publish event (non-blocking)
        await _eventBus.PublishAsync(new OrderCreatedEvent
        {
            OrderId = order.Id,
            Items = request.Items,
            PaymentInfo = request.Payment,
            CustomerId = request.CustomerId,
            CreatedAt = DateTime.UtcNow
        });
        
        // Return immediately - don't wait for downstream processing
        return new OrderResult { OrderId = order.Id };
    }
}

// Downstream services handle events independently
public class InventoryService
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Process when ready, retry if needed
        await ReserveInventoryAsync(evt.OrderId, evt.Items);
    }
}

public class PaymentService
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Process independently
        var result = await ProcessPaymentAsync(evt.OrderId, evt.PaymentInfo);
        
        // Publish result as new event
        await _eventBus.PublishAsync(new PaymentProcessedEvent
        {
            OrderId = evt.OrderId,
            Success = result.Success,
            ProcessedAt = DateTime.UtcNow
        });
    }
}

public class NotificationService
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Send notification asynchronously
        await SendOrderConfirmationAsync(evt.OrderId);
    }
}
```

**Pros:**
- ✅ Loose coupling between services
- ✅ Services can be unavailable without blocking others
- ✅ Better scalability and independent scaling
- ✅ Resilient to failures
- ✅ Flexible and extensible (easy to add new consumers)
- ✅ Better throughput

**Cons:**
- ❌ More complex to understand and implement
- ❌ Eventual consistency (not immediate)
- ❌ Harder to debug and trace
- ❌ Requires message broker infrastructure
- ❌ More moving parts to manage

### Comparison Table

| Aspect | Request-Driven | Event-Driven |
|--------|----------------|--------------|
| **Communication** | Synchronous | Asynchronous |
| **Coupling** | Tight | Loose |
| **Consistency** | Immediate | Eventual |
| **Availability** | All services must be up | Services can be down |
| **Scalability** | Scale together | Scale independently |
| **Latency** | Sum of all calls | Single operation |
| **Complexity** | Lower | Higher |
| **Debugging** | Easier (linear flow) | Harder (distributed) |
| **Error Handling** | Immediate | Delayed/async |
| **Use Case** | Simple workflows, immediate response | Complex workflows, high throughput |

### When to Use Request-Driven Architecture

**Use request-driven when:**
- ✅ You need immediate response and feedback
- ✅ Strong consistency is required
- ✅ Simple, linear workflows
- ✅ Low complexity is preferred
- ✅ Synchronous operations are acceptable
- ✅ All services are reliable and always available

**Examples:**
- User authentication (need immediate success/failure)
- Real-time data queries (need current state)
- Simple CRUD operations
- API gateways routing requests

### When to Use Event-Driven Architecture

**Use event-driven when:**
- ✅ You can tolerate eventual consistency
- ✅ High throughput is required
- ✅ Services need to scale independently
- ✅ Loose coupling is important
- ✅ Complex workflows with multiple steps
- ✅ Services might be temporarily unavailable

**Examples:**
- Order processing (multiple steps, can be async)
- User registration (welcome email, profile setup can be async)
- Analytics and reporting (can process later)
- Inventory updates (eventual consistency acceptable)
- Notification systems (fire-and-forget)

### Hybrid Architecture

Most real-world systems combine both patterns:

```csharp
// Hybrid: Use request-driven for critical path, event-driven for background
public class OrderService
{
    private readonly IInventoryService _inventoryService;
    private readonly IPaymentService _paymentService;
    private readonly IEventBus _eventBus;
    
    public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
    {
        // Critical path: Synchronous checks
        var inventoryResult = await _inventoryService.CheckAvailabilityAsync(request.Items);
        if (!inventoryResult.IsAvailable)
            throw new InsufficientInventoryException();
        
        // Create order
        var order = await _orderRepository.CreateAsync(request);
        
        // Critical: Process payment synchronously (need immediate result)
        var paymentResult = await _paymentService.ProcessPaymentAsync(request.Payment);
        if (!paymentResult.Success)
        {
            await _orderRepository.CancelAsync(order.Id);
            throw new PaymentFailedException();
        }
        
        // Background: Publish events for non-critical operations
        await _eventBus.PublishAsync(new OrderCreatedEvent
        {
            OrderId = order.Id,
            Items = request.Items,
            CustomerId = request.CustomerId
        });
        
        // Return immediately (notification will be sent via event)
        return new OrderResult { OrderId = order.Id };
    }
}

// Background processing via events
public class NotificationService
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Non-critical: Send email asynchronously
        await SendOrderConfirmationEmailAsync(evt.OrderId);
    }
}

public class AnalyticsService
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Background: Track analytics
        await TrackOrderCreatedAsync(evt);
    }
}
```

### Migration Strategy: Request-Driven to Event-Driven

**Step 1: Identify candidates for async processing**
- Operations that don't need immediate response
- Background tasks
- Non-critical workflows

**Step 2: Start with non-critical paths**
- Keep critical path synchronous
- Move background operations to events

**Step 3: Gradually expand**
- Move more operations to events
- Add event handlers for new features
- Eventually move critical path if appropriate

**Example Migration:**
```csharp
// Before: All synchronous
public async Task RegisterUserAsync(UserRegistrationRequest request)
{
    var user = await _userService.CreateAsync(request);
    await _emailService.SendWelcomeAsync(user.Id);      // Can be async
    await _profileService.CreateAsync(user.Id);          // Can be async
    await _preferencesService.InitializeAsync(user.Id);  // Can be async
    return new UserResult { UserId = user.Id };
}

// After: Hybrid approach
public async Task RegisterUserAsync(UserRegistrationRequest request)
{
    // Critical: Create user synchronously (need user ID)
    var user = await _userService.CreateAsync(request);
    
    // Background: Publish event for async processing
    await _eventBus.PublishAsync(new UserRegisteredEvent
    {
        UserId = user.Id,
        Email = request.Email,
        RegistrationDate = DateTime.UtcNow
    });
    
    // Return immediately
    return new UserResult { UserId = user.Id };
}

// Background handlers process asynchronously
public class EmailServiceHandler
{
    public async Task HandleAsync(UserRegisteredEvent evt)
    {
        await _emailService.SendWelcomeAsync(evt.UserId);
    }
}
```

### Real-World Patterns

#### Strangler Fig Pattern
Gradually replace request-driven with event-driven:

```csharp
// Phase 1: Dual write - both old and new
public class OrderService
{
    public async Task CreateOrderAsync(OrderRequest request)
    {
        // Old path - synchronous
        var order = await _legacyOrderService.CreateAsync(request);
        
        // New path - also publish event (dual write)
        await _eventBus.PublishAsync(new OrderCreatedEvent
        {
            OrderId = order.Id,
            // ... event data
        });
        
        return order;
    }
}

// Phase 2: Switch consumers to event-based
public class NewOrderNotificationService
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // New consumers use events instead of direct calls
        await SendNotificationAsync(evt);
    }
}

// Phase 3: Remove old synchronous calls
public class OrderService
{
    public async Task CreateOrderAsync(OrderRequest request)
    {
        // Only event-based now
        var order = await _orderRepository.CreateAsync(request);
        
        await _eventBus.PublishAsync(new OrderCreatedEvent
        {
            OrderId = order.Id,
            // ... event data
        });
        
        return order;
    }
}
```

#### Event-Driven with Synchronous Validation
```csharp
// Critical validation remains synchronous
public class OrderService
{
    public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
    {
        // Synchronous validations
        var customer = await _customerService.GetByIdAsync(request.CustomerId);
        if (customer == null)
            throw new CustomerNotFoundException();
        
        var inventory = await _inventoryService.CheckAvailabilityAsync(request.Items);
        if (!inventory.AllAvailable)
            throw new InsufficientInventoryException();
        
        var creditCheck = await _creditService.CheckLimitAsync(customer.Id, request.TotalAmount);
        if (!creditCheck.Approved)
            throw new CreditLimitExceededException();
        
        // Create order
        var order = await _orderRepository.CreateAsync(request);
        
        // Everything else is event-driven
        await _eventBus.PublishAsync(new OrderCreatedEvent
        {
            OrderId = order.Id,
            CustomerId = request.CustomerId,
            Items = request.Items,
            TotalAmount = request.TotalAmount
        });
        
        return new OrderResult { OrderId = order.Id };
    }
}
```

### Monitoring and Observability

**Request-Driven Monitoring:**
```csharp
public class OrderService
{
    public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
    {
        using var activity = _tracer.StartActivity("CreateOrder");
        
        try
        {
            // Spans show direct call chain
            var inventory = await _inventoryService.CheckAsync(request.Items);
            var payment = await _paymentService.ProcessAsync(request.Payment);
            var order = await _orderRepository.CreateAsync(request);
            
            return new OrderResult { OrderId = order.Id };
        }
        catch (Exception ex)
        {
            activity?.SetStatus(ActivityStatusCode.Error);
            throw;
        }
    }
}
```

**Event-Driven Monitoring:**
```csharp
// Producer
public class OrderService
{
    public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
    {
        using var activity = _tracer.StartActivity("CreateOrder");
        
        var order = await _orderRepository.CreateAsync(request);
        
        var evt = new OrderCreatedEvent
        {
            OrderId = order.Id,
            CorrelationId = Activity.Current?.Id // Pass trace context
        };
        
        await _eventBus.PublishAsync(evt);
        
        return new OrderResult { OrderId = order.Id };
    }
}

// Consumer
public class InventoryService
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        // Restore trace context from event
        using var activity = _tracer.StartActivity(
            "HandleOrderCreated",
            ActivityKind.Consumer,
            evt.CorrelationId
        );
        
        activity?.SetTag("order.id", evt.OrderId);
        
        await ReserveInventoryAsync(evt.Items);
    }
}

// Distributed trace shows async flow
// CreateOrder -> OrderCreatedEvent -> HandleOrderCreated (InventoryService)
//                                  -> HandleOrderCreated (PaymentService)
//                                  -> HandleOrderCreated (NotificationService)
```

### Error Handling Comparison

**Request-Driven:**
```csharp
public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
{
    try
    {
        var inventory = await _inventoryService.ReserveAsync(request.Items);
        var payment = await _paymentService.ProcessAsync(request.Payment);
        var order = await _orderRepository.CreateAsync(request);
        
        return OrderResult.Success(order.Id);
    }
    catch (InsufficientInventoryException ex)
    {
        // Immediate error to user
        return OrderResult.Failure("Out of stock");
    }
    catch (PaymentDeclinedException ex)
    {
        // Rollback inventory
        await _inventoryService.ReleaseAsync(request.Items);
        return OrderResult.Failure("Payment declined");
    }
}
```

**Event-Driven:**
```csharp
// Producer
public async Task<OrderResult> CreateOrderAsync(OrderRequest request)
{
    var order = await _orderRepository.CreateAsync(request);
    
    await _eventBus.PublishAsync(new OrderCreatedEvent
    {
        OrderId = order.Id,
        Items = request.Items
    });
    
    // Return immediately - errors handled async
    return OrderResult.Pending(order.Id, "Processing");
}

// Consumer with error handling
public class InventoryReservationHandler
{
    public async Task HandleAsync(OrderCreatedEvent evt)
    {
        try
        {
            await _inventoryService.ReserveAsync(evt.Items);
            
            await _eventBus.PublishAsync(new InventoryReservedEvent
            {
                OrderId = evt.OrderId
            });
        }
        catch (InsufficientInventoryException ex)
        {
            // Publish failure event
            await _eventBus.PublishAsync(new InventoryReservationFailedEvent
            {
                OrderId = evt.OrderId,
                Reason = "Out of stock"
            });
        }
    }
}

// Saga handles failures
public class OrderSaga
{
    public async Task HandleAsync(InventoryReservationFailedEvent evt)
    {
        // Cancel order
        await _orderRepository.CancelAsync(evt.OrderId);
        
        // Notify customer
        await _eventBus.PublishAsync(new OrderCancelledEvent
        {
            OrderId = evt.OrderId,
            Reason = evt.Reason
        });
    }
}
```

## Self-Check Questions

1. What's the fundamental difference between request-driven and event-driven architectures?
   - **Answer:** Request-driven uses synchronous, direct service-to-service calls with tight coupling and immediate responses. Event-driven uses asynchronous event-based communication with loose coupling and eventual consistency.

2. When would you choose request-driven over event-driven architecture?
   - **Answer:** When you need immediate response/feedback, strong consistency is required, workflows are simple and linear, low complexity is preferred, or all services are reliable and always available.

3. What are the main trade-offs between immediate and eventual consistency?
   - **Answer:** Immediate consistency provides simpler reasoning and guarantees but requires tight coupling and synchronous operations. Eventual consistency enables better scalability and availability but introduces complexity in handling stale data and race conditions.

4. How can you combine both patterns in a hybrid architecture?
   - **Answer:** Use synchronous calls for critical path operations that need immediate validation/response, and use events for background processing, notifications, and non-critical operations. This balances user experience with system scalability.

5. What challenges arise when migrating from request-driven to event-driven?
   - **Answer:** Handling eventual consistency, managing distributed transactions, tracing across async boundaries, training teams on new patterns, refactoring error handling, and maintaining backward compatibility during migration.

**Additional Questions:**

6. How do you handle distributed transactions in event-driven architecture?
   - **Answer:** Use the Saga pattern to orchestrate or choreograph long-running transactions across services, with compensating actions to roll back on failure. Avoid distributed transactions; instead design for eventual consistency.

7. What's the impact on latency when moving from request-driven to event-driven?
   - **Answer:** User-facing latency typically decreases (faster response) since background work is deferred, but total end-to-end latency may increase since processing happens asynchronously. Trade-off between user experience and total processing time.

8. How do you maintain data consistency across services in event-driven systems?
   - **Answer:** Use event sourcing to maintain consistency, implement idempotent event handlers to handle duplicates, use versioning to detect conflicts, and design for eventual consistency rather than strong consistency.

---

## Key Takeaways

- **Request-driven** architecture uses synchronous request-response patterns
- **Event-driven** architecture uses asynchronous event-based communication
- Request-driven provides immediate consistency but tighter coupling
- Event-driven enables loose coupling but eventual consistency
- Most real-world systems use a **hybrid approach** combining both patterns
- Choose based on consistency requirements, coupling tolerance, and scalability needs
- Migrate gradually, starting with non-critical operations
