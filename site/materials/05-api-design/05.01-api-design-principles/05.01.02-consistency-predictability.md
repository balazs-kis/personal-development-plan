# Lesson 2: Consistency and Predictability

## Learning Objectives

By the end of this lesson, you will be able to:
- Design consistent naming conventions across APIs
- Establish predictable patterns for resources and operations
- Create consistency in error handling and responses
- Apply consistent data formats and structures
- Build style guides for API consistency

---

## Introduction

**Consistency** is one of the most important principles in API design. When APIs are consistent, developers can predict how they work based on patterns they've already learned. This dramatically reduces cognitive load and time-to-productivity.

Inconsistency forces developers to constantly refer to documentation, increases errors, and leads to frustration.

## Key Concepts Summary

### Naming Consistency

```csharp
// Good: Consistent naming
GET    /api/products
GET    /api/products/{id}
POST   /api/products
PUT    /api/products/{id}
DELETE /api/products/{id}

GET    /api/orders
GET    /api/orders/{id}
POST   /api/orders
PUT    /api/orders/{id}
DELETE /api/orders/{id}

// Bad: Inconsistent naming
GET /api/products          // Plural
GET /api/product/{id}      // Singular (inconsistent!)
POST /api/create-product   // Verb in URL
PUT /api/products/update   // Different pattern
DELETE /api/remove-product // Yet another pattern
```

### Response Structure Consistency

```csharp
// Consistent success response
public class ApiResponse<T>
{
    public bool Success { get; set; } = true;
    public T Data { get; set; }
    public Meta Meta { get; set; }
}

// Consistent error response
public class ApiError
{
    public bool Success { get; set; } = false;
    public string ErrorCode { get; set; }
    public string Message { get; set; }
    public Dictionary<string, string[]> ValidationErrors { get; set; }
}

// All endpoints return same structure
[HttpGet("products/{id}")]
public ApiResponse<Product> GetProduct(int id) =>  new() { Data = _products.Find(id) };

[HttpPost("products")]
public ApiResponse<Product> CreateProduct(CreateProductDto dto) => new() { Data = _products.Create(dto) };
```

### Date/Time Consistency

```csharp
// Good: Always use ISO 8601

    public DateTime CreatedAt { get; set; }  // Serialized as: "2024-01-15T14:30:00Z"
    public DateTime UpdatedAt { get; set; }  // Serialized as: "2024-01-15T15:45:00Z"

    .AddJsonOptions(options =>
```

### Error Handling Consistency

```csharp
// Consistent error codes
public static class ErrorCodes
{
    // 400 errors
    public const string InvalidInput = "INVALID_INPUT";
    public const string ValidationFailed = "VALIDATION_FAILED";
    public const string MissingRequiredField = "MISSING_REQUIRED_FIELD";
    
    // 404 errors
    public const string ResourceNotFound = "RESOURCE_NOT_FOUND";
    
    // 409 errors
    public const string ResourceAlreadyExists = "RESOURCE_ALREADY_EXISTS";
    public const string ConcurrencyConflict = "CONCURRENCY_CONFLICT";
    
    // 500 errors
    public const string InternalServerError = "INTERNAL_SERVER_ERROR";
}

// Exception filter for consistent errors
public class ApiExceptionFilter : IExceptionFilter
{
    public void OnException(ExceptionContext context)
    {
        var error = context.Exception switch
        {
            ValidationException ex => new ApiError
            {
                ErrorCode = ErrorCodes.ValidationFailed,
                Message = "Validation failed",
                ValidationErrors = ex.Errors.ToDictionary(e => e.PropertyName, e => new[] { e.ErrorMessage })
            },
            NotFoundException ex => new ApiError
            {
                ErrorCode = ErrorCodes.ResourceNotFound,
                Message = ex.Message
            },
            _ => new ApiError
            {
                ErrorCode = ErrorCodes.InternalServerError,
                Message = "An unexpected error occurred"
            }
        };
        
        context.Result = new ObjectResult(error)
        {
            StatusCode = GetStatusCode(context.Exception)
        };
    }
}
```

### HTTP Header Consistency

```csharp
// Consistent custom headers
public static class CustomHeaders
{
    // Request headers
    public const string ApiVersion = "X-API-Version";
    public const string RequestId = "X-Request-ID";
    public const string CorrelationId = "X-Correlation-ID";
    
    // Response headers
    public const string RateLimit = "X-RateLimit-Limit";
    public const string RateLimitRemaining = "X-RateLimit-Remaining";
    public const string RateLimitReset = "X-RateLimit-Reset";
    public const string Deprecation = "Deprecation";
    public const string Sunset = "Sunset";
}

// Middleware adds consistent headers
public class ApiHeaderMiddleware
{
    private readonly RequestDelegate _next;
    
    public async Task InvokeAsync(HttpContext context)
    {
        // Add request ID to all responses
        var requestId = Guid.NewGuid().ToString();
        context.Response.Headers[CustomHeaders.RequestId] = requestId;
        
        // Add rate limit headers
        context.Response.Headers[CustomHeaders.RateLimit] = "1000";
        context.Response.Headers[CustomHeaders.RateLimitRemaining] = "995";
        
        await _next(context);
    }
}
```

### Null Handling Consistency

```csharp
// Consistent null handling strategy
public class NullHandlingOptions
{
    // Option 1: Always include null fields
    public class Product
    {
        public int Id { get; set; }
        public string Name { get; set; }
        public string? Description { get; set; }  // Can be null
    }
    // Response: { "id": 1, "name": "Product", "description": null }
    
    // Option 2: Omit null fields (configure globally)
    services.AddControllers()
        .AddJsonOptions(options =>
        {
            options.JsonSerializerOptions.DefaultIgnoreCondition = 
                JsonIgnoreCondition.WhenWritingNull;
        });
    // Response: { "id": 1, "name": "Product" }  // description omitted
}

// Pick ONE approach and use it everywhere
```

### Bulk Operation Consistency

```csharp
// Consistent bulk operations
[HttpPost("products/bulk")]
public async Task<BulkOperationResult<Product>> BulkCreateProducts(
    [FromBody] List<CreateProductDto> products)
{
    var results = new BulkOperationResult<Product>();
    
    foreach (var dto in products)
    {
        try
        {
            var product = await _service.CreateAsync(dto);
            results.Succeeded.Add(product);
        }
        catch (Exception ex)
        {
            results.Failed.Add(new FailedOperation<CreateProductDto>
            {
                Item = dto,
                Error = ex.Message
            });
        }
    }
    
    return results;
}

public class BulkOperationResult<T>
{
    public List<T> Succeeded { get; set; } = new();
    public List<FailedOperation<object>> Failed { get; set; } = new();
    public int TotalProcessed => Succeeded.Count + Failed.Count;
}

// Same pattern for all bulk operations: /products/bulk, /orders/bulk, etc.
```

```csharp
public class ApiStyleGuide
```

### Status Code Consistency

```csharp
// Consistent status code usage across all endpoints
public class ApiStatusCodes
{
    // 2xx Success
    public const int OK = 200;              // GET success
    public const int Created = 201;         // POST success (resource created)
    public const int Accepted = 202;        // Async operation started
    public const int NoContent = 204;       // DELETE/PUT success (no body)
    
    // 4xx Client errors
    public const int BadRequest = 400;      // Validation failed
    public const int Unauthorized = 401;    // Authentication required
    public const int Forbidden = 403;       // Authenticated but not authorized
    public const int NotFound = 404;        // Resource doesn't exist
    public const int Conflict = 409;        // Duplicate, version conflict
    public const int UnprocessableEntity = 422;  // Semantic validation failed
    public const int TooManyRequests = 429; // Rate limit exceeded
    
    // 5xx Server errors
    public const int InternalServerError = 500;  // Unexpected error
    public const int ServiceUnavailable = 503;   // Temporary unavailability
}

// Consistent usage
[HttpGet("products/{id}")]
public IActionResult GetProduct(int id)
{
    var product = _repo.Find(id);
    return product == null 
        ? NotFound()        // Always 404 for missing resources
        : Ok(product);      // Always 200 for successful retrieval
}

[HttpPost("products")]
public IActionResult CreateProduct(CreateProductDto dto)
{
    var product = _service.Create(dto);
    return CreatedAtAction(    // Always 201 for creation
        nameof(GetProduct),
        new { id = product.Id },
        product);
}

[HttpDelete("products/{id}")]
public IActionResult DeleteProduct(int id)
{
    _repo.Delete(id);
    return NoContent();   // Always 204 for successful deletion
}
```

### Validation Error Consistency

```csharp
// Consistent validation error format
public class ValidationErrorResponse
{
    public bool Success { get; set; } = false;
    public string ErrorCode { get; set; } = "VALIDATION_FAILED";
    public string Message { get; set; } = "One or more validation errors occurred";
    public Dictionary<string, List<string>> Errors { get; set; }
}

// Example response
{
  "success": false,
  "errorCode": "VALIDATION_FAILED",
  "message": "One or more validation errors occurred",
  "errors": {
    "email": [
      "Email is required",
      "Email format is invalid"
    ],
    "age": [
      "Age must be between 18 and 120"
    ]
  }
}

// Consistent across all endpoints
[HttpPost("users")]
public IActionResult CreateUser(CreateUserDto dto)
{
    var validator = new CreateUserValidator();
    var result = validator.Validate(dto);
    
    if (!result.IsValid)
    {
        return BadRequest(new ValidationErrorResponse
        {
            Errors = result.Errors
                .GroupBy(e => e.PropertyName)
                .ToDictionary(
                    g => g.Key,
                    g => g.Select(e => e.ErrorMessage).ToList())
        });
    }
    
    // ...
}
```

## Self-Check Questions

1. Why is consistency more important than perfection in API design?
   - **Answer:** Developers can predict behavior based on learned patterns. Consistent "good enough" is better than inconsistent "perfect." Predictability reduces cognitive load and errors.

2. How do you handle inconsistencies in existing APIs?
   - **Answer:** Document them, add to style guide, fix in new major version, or create linting rules to prevent new violations. Use deprecation for gradual migration.

3. What are the benefits of a shared response envelope?
   - **Answer:** Consistent client code, easier error handling, ability to add metadata (pagination, links) without breaking changes, predictable structure for tooling.

4. How should dates and times be formatted?
   - **Answer:** ISO 8601 format (e.g., `2024-01-15T14:30:00Z`) for consistency, timezone clarity, and language-agnostic parsing.

5. What makes a good error code naming convention?
   - **Answer:** Descriptive, consistent prefix/format (e.g., `VALIDATION_FAILED`), not tied to HTTP status codes, stable over time, documented with examples.

6. How do you enforce consistency across a team?
   - **Answer:** Written style guide, automated linting (Spectral for OpenAPI), code reviews, shared libraries/base classes, design reviews, training.

7. When is it acceptable to break consistency?
   - **Answer:** When following a well-established industry standard (e.g., OAuth endpoints), or when consistency would make the API less intuitive. Document exceptions clearly.

8. How do you migrate from inconsistent to consistent API design?
   - **Answer:** Versioning (v1 keeps old patterns, v2 adopts new), deprecation warnings, migration guide, gradual rollout, maintain backward compatibility where possible.

## Key Takeaways

- **Consistency reduces cognitive load** and makes APIs predictable and easy to learn
- **Pick conventions and stick to them** across all endpoints and resources
- **Response envelopes** provide consistency and extensibility
- **Naming conventions** should cover resources, fields, booleans, timestamps, and IDs
- **Error handling** must be consistent in format, codes, and status codes
- **Query parameters** should follow the same patterns for filtering, sorting, and pagination
- **Date/time formats** should use ISO 8601 for unambiguous representation
- **Style guides** document decisions and enable enforcement through reviews and tooling
- **Automated validation** (linting, contract testing) catches inconsistencies early
- **Migration strategies** handle legacy inconsistencies without breaking existing clients
