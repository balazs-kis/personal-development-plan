# Lesson 1: Resource-Oriented Design

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand what resources are in REST and how they differ from RPC-style operations
- Model domains as resources with clear boundaries and relationships
- Identify collections vs individual resources and when to use each
- Design resource relationships and hierarchies that reflect your domain
- Apply resource naming patterns and conventions consistently
- Avoid exposing implementation details in your API design
- Handle edge cases like singleton resources and composite resources

---

## Introduction

REST (Representational State Transfer) is fundamentally about **resources**. A resource is any information that can be named—a document, an image, a temporal service, a collection of other resources, or a non-virtual object like a person. Resource-oriented design means thinking in terms of *nouns* (things) rather than *verbs* (actions).

This shift in thinking is crucial: instead of "getUserOrders()", you have "user's orders"—a resource that can be retrieved, updated, or deleted. This resource-centric approach enables uniform interfaces, predictable behavior, and better HTTP caching.

The power of resource-oriented design lies in its simplicity and consistency. Once you identify your resources, the HTTP methods (GET, POST, PUT, DELETE) provide a uniform interface for all operations. This consistency makes APIs intuitive and reduces the learning curve for API consumers.

## Key Concepts Summary

### What is a Resource?

```
Resource Examples:
- A user: /users/123
- A collection of users: /users
- A user's orders: /users/123/orders
- A specific order: /orders/456
- An image: /images/profile.jpg
- A search result: /search?q=laptop

NOT Resources (These are actions):
- /getUser
- /createOrder
- /deleteProduct
```

### Resource vs Collection

```csharp
// Collection resource (plural)
GET /api/products              // List all products
POST /api/products             // Create new product

// Individual resource (singular item from collection)
GET /api/products/{id}         // Get specific product
PUT /api/products/{id}         // Update specific product
DELETE /api/products/{id}      // Delete specific product

// Implementation
[ApiController]
[Route("api/products")]
public class ProductsController : ControllerBase
{
    // Collection endpoint
    [HttpGet]
    public ActionResult<List<Product>> GetProducts() => _products.ToList();
    
    // Individual resource endpoint
    [HttpGet("{id}")]
    public ActionResult<Product> GetProduct(int id)
    {
        var product = _products.Find(id);
        return product == null ? NotFound() : Ok(product);
    }
}
```

### Resource Relationships

```csharp
// Nested resources (parent-child relationship)
GET /api/customers/{customerId}/orders              // Customer's orders
GET /api/customers/{customerId}/orders/{orderId}   // Specific order for customer
GET /api/orders/{orderId}/items                     // Order's line items

// When to nest vs flatten
// Good: Clear ownership
GET /api/users/{userId}/posts                       // User owns posts

// Alternative: Independent access
GET /api/posts?userId={userId}                      // Posts can exist independently
GET /api/posts/{postId}                             // Direct access to post

// Bad: Too deep nesting
GET /api/users/{userId}/posts/{postId}/comments/{commentId}/likes/{likeId}
// Better: Flatten
GET /api/likes/{likeId}
GET /api/comments/{commentId}/likes
```

### Resource Modeling Example

```csharp
// Domain: E-commerce system
// Resources identified:
// - Customers
// - Products
// - Orders
// - Order Items (part of orders)
// - Reviews (belong to products)
// - Shopping Carts

// API design
public class ApiResources
{
    // Customers
    [HttpGet("api/customers")]
    [HttpPost("api/customers")]
    [HttpGet("api/customers/{id}")]
    [HttpPut("api/customers/{id}")]
    [HttpDelete("api/customers/{id}")]
    
    // Products
    [HttpGet("api/products")]
    [HttpPost("api/products")]
    [HttpGet("api/products/{id}")]
    [HttpPut("api/products/{id}")]
    [HttpDelete("api/products/{id}")]
    
    // Product reviews (nested)
    [HttpGet("api/products/{productId}/reviews")]
    [HttpPost("api/products/{productId}/reviews")]
    [HttpGet("api/products/{productId}/reviews/{reviewId}")]
    
    // Orders (can be independent or nested)
    [HttpGet("api/orders")]                           // All orders (admin)
    [HttpGet("api/customers/{customerId}/orders")]   // Customer's orders
    [HttpGet("api/orders/{orderId}")]
    [HttpPost("api/orders")]
    [HttpPut("api/orders/{orderId}")]
    
    // Order items (always nested under order)
    [HttpGet("api/orders/{orderId}/items")]
    [HttpPost("api/orders/{orderId}/items")]
    [HttpDelete("api/orders/{orderId}/items/{itemId}")]
    
    // Shopping cart (nested under customer)
    [HttpGet("api/customers/{customerId}/cart")]
    [HttpPut("api/customers/{customerId}/cart")]
}
```

### Singular vs Plural

```csharp
// Good: Consistent plural for collections
GET /api/users
GET /api/products
GET /api/orders

// Good: Singular for singleton resources
GET /api/customers/{customerId}/profile    // One profile per customer
GET /api/users/{userId}/settings           // One settings object

// Bad: Inconsistent
GET /api/user                // Should be /users
GET /api/products/{id}       // Good
GET /api/order/{id}          // Should be /orders/{id}
```

### Avoiding Implementation Details

```csharp
// Bad: Exposes database/implementation
GET /api/tbl_users                    // Table name leaked
GET /api/user_dto                     // DTO leaked
GET /api/getUserById?id=123          // RPC style, not resource
POST /api/saveOrder                   // Action leaked

// Good: Clean resource interface
GET /api/users
GET /api/users/{id}
POST /api/orders
PUT /api/orders/{id}

// Implementation stays hidden
public class UsersController : ControllerBase
{
    private readonly IUserRepository _repo;  // Could be EF, Dapper, anything
    
    [HttpGet("{id}")]
    public ActionResult<UserResponse> GetUser(int id)
    {
        // Fetch from database (hidden from API consumer)
        var user = _repo.GetById(id);
        
        // Map to API contract (not database entity)
        return Ok(new UserResponse
        {
            Id = user.Id,
            Name = user.FullName,  // Different from DB column names
            Email = user.EmailAddress
        });
    }
}
```

### Resource Granularity

```csharp
// Too fine-grained (chatty)
GET /api/users/{id}/firstName
GET /api/users/{id}/lastName
GET /api/users/{id}/email
GET /api/users/{id}/phone
// Requires 4 requests for one user!

// Better: Appropriate granularity
GET /api/users/{id}
// Returns complete user resource
{
  "id": 123,
  "firstName": "John",
  "lastName": "Doe",
  "email": "john@example.com",
  "phone": "+1234567890"
}

// Optional: Support field selection for optimization
GET /api/users/{id}?fields=firstName,email
// Returns subset when needed
```

### Resource Lifecycle

```csharp
// Complete resource lifecycle
public class OrderLifecycle
{
    // Creation
    POST /api/orders
    Body: { "customerId": 123, "items": [...] }
    Response: 201 Created, Location: /api/orders/456
    
    // Reading
    GET /api/orders/456
    Response: 200 OK, { "id": 456, "status": "pending", ... }
    
    // Updating
    PUT /api/orders/456
    Body: { "id": 456, "status": "confirmed", ... }
    Response: 200 OK or 204 No Content
    
    // Partial update
    PATCH /api/orders/456
    Body: { "status": "shipped" }
    Response: 200 OK
    
    // Deletion
    DELETE /api/orders/456
    Response: 204 No Content
    
    // Check if exists
    HEAD /api/orders/456
    Response: 200 OK (with headers, no body) or 404 Not Found
}
```

### Singleton Resources

```csharp
// Singleton resources: only one instance per parent
[ApiController]
[Route("api/users/{userId}")]
public class UserSingletonController : ControllerBase
{
    // User profile (one per user)
    [HttpGet("profile")]
    public ActionResult<UserProfile> GetProfile(int userId)
    {
        // GET /api/users/123/profile
        // Note: singular "profile", not "profiles"
        var profile = _profileService.GetByUserId(userId);
        
        if (profile == null)
            return NotFound();
        
        return Ok(profile);
    }
    
    [HttpPut("profile")]
    public ActionResult UpdateProfile(int userId, [FromBody] UserProfile profile)
    {
        // PUT /api/users/123/profile
        // Update or create (upsert pattern)
        _profileService.Upsert(userId, profile);
        return NoContent();
    }
    
    // User settings (one per user)
    [HttpGet("settings")]
    public ActionResult<UserSettings> GetSettings(int userId)
    {
        // GET /api/users/123/settings
        var settings = _settingsService.GetByUserId(userId);
        return Ok(settings ?? UserSettings.Default);
    }
    
    [HttpPut("settings")]
    public ActionResult UpdateSettings(int userId, [FromBody] UserSettings settings)
    {
        // PUT /api/users/123/settings
        _settingsService.Update(userId, settings);
        return NoContent();
    }
}

// Singleton vs Collection
// Singleton:  /api/users/123/profile    (one profile per user)
// Collection: /api/users/123/addresses  (multiple addresses per user)
```

### Composite Resources

```csharp
// Composite resources: aggregates of multiple resources
[ApiController]
[Route("api/dashboards")]
public class DashboardController : ControllerBase
{
    // Dashboard aggregates data from multiple resources
    [HttpGet("user/{userId}")]
    public async Task<ActionResult<UserDashboard>> GetUserDashboard(int userId)
    {
        // GET /api/dashboards/user/123
        // Composite resource that combines:
        // - User profile
        // - Recent orders
        // - Notifications
        // - Preferences
        
        var user = await _userService.GetById(userId);
        var orders = await _orderService.GetRecentByUserId(userId, limit: 5);
        var notifications = await _notificationService.GetUnreadByUserId(userId);
        var preferences = await _preferenceService.GetByUserId(userId);
        
        var dashboard = new UserDashboard
        {
            User = user,
            RecentOrders = orders,
            UnreadNotifications = notifications,
            Preferences = preferences
        };
        
        return Ok(dashboard);
    }
}

// Summary resource: statistics or aggregated data
[ApiController]
[Route("api/reports")]
public class ReportController : ControllerBase
{
    [HttpGet("sales/summary")]
    public ActionResult<SalesSummary> GetSalesSummary(
        [FromQuery] DateTime startDate,
        [FromQuery] DateTime endDate)
    {
        // GET /api/reports/sales/summary?startDate=2024-01-01&endDate=2024-12-31
        // Composite resource with aggregated data
        
        var summary = new SalesSummary
        {
            TotalRevenue = _salesService.GetTotalRevenue(startDate, endDate),
            OrderCount = _orderService.GetCount(startDate, endDate),
            AverageOrderValue = _salesService.GetAverageOrderValue(startDate, endDate),
            TopProducts = _productService.GetTopSelling(startDate, endDate, limit: 10)
        };
        
        return Ok(summary);
    }
}
```

### Cross-Cutting Resources

```csharp
// Resources that span multiple domains
[ApiController]
[Route("api")]
public class CrossCuttingController : ControllerBase
{
    // Search across multiple resource types
    [HttpGet("search")]
    public ActionResult<SearchResults> Search([FromQuery] string q)
    {
        // GET /api/search?q=laptop
        
        var results = new SearchResults
        {
            Products = _productService.Search(q, limit: 5),
            Articles = _articleService.Search(q, limit: 5),
            Users = _userService.Search(q, limit: 5)
        };
        
        return Ok(results);
    }
    
    // Activity feed across resources
    [HttpGet("activities")]
    public ActionResult<List<Activity>> GetActivities(
        [FromQuery] int page = 1,
        [FromQuery] int pageSize = 20)
    {
        // GET /api/activities?page=1&pageSize=20
        // Returns activities from orders, comments, reviews, etc.
        
        var activities = _activityService.GetRecent(page, pageSize);
        return Ok(activities);
    }
    
    // Notifications across all resource types
    [HttpGet("users/{userId}/notifications")]
    public ActionResult<List<Notification>> GetNotifications(int userId)
    {
        // GET /api/users/123/notifications
        // Aggregates notifications from orders, messages, comments, etc.
        
        var notifications = _notificationService.GetByUserId(userId);
        return Ok(notifications);
    }
}
```

### Resource Boundaries and Domain Context

```csharp
// Identifying resource boundaries
// Good boundaries:
// - Resources have clear identity
// - Resources can be independently managed
// - Resources have meaningful lifecycle
// - Resources align with domain concepts

// Example: E-commerce domain
public class EcommerceDomainResources
{
    // Clear resource boundaries:
    // /api/products          - Product catalog (inventory management context)
    // /api/customers         - Customer management (CRM context)
    // /api/orders            - Order processing (order management context)
    // /api/carts             - Shopping carts (shopping context)
    // /api/payments          - Payment processing (payment context)
    
    // Each resource has its own:
    // - Lifecycle
    // - Operations
    // - Relationships
    // - Access patterns
}

// Avoid blurred boundaries
// Bad example: mixing concerns
[Route("api/customer-order-data")]  // ❌ Unclear what this represents
public class BadController : ControllerBase { }

// Good example: clear separation
[Route("api/customers")]
public class CustomersController : ControllerBase 
{
    [HttpGet("{id}/orders")]  // ✅ Clear: customer's orders
    public ActionResult GetCustomerOrders(int id) { }
}

[Route("api/orders")]
public class OrdersController : ControllerBase 
{
    [HttpGet("{id}")]  // ✅ Clear: specific order
    public ActionResult GetOrder(int id) { }
}
```

### Resource Anti-Patterns to Avoid

```csharp
// Anti-pattern 1: Mixing verbs into resource URLs
// ❌ Bad
[HttpGet("api/calculateOrderTotal/{orderId}")]
[HttpPost("api/sendEmailToCustomer/{customerId}")]
[HttpGet("api/validateProduct/{productId}")]

// ✅ Good: Resources with appropriate HTTP methods
[HttpGet("api/orders/{orderId}")]  // Get order (includes total)
[HttpPost("api/customers/{customerId}/notifications")]  // Send notification
[HttpGet("api/products/{productId}")]  // Get product (includes validation status)

// Anti-pattern 2: Over-nesting
// ❌ Bad: Too deep
[HttpGet("api/countries/{countryId}/states/{stateId}/cities/{cityId}/streets/{streetId}/buildings/{buildingId}")]

// ✅ Good: Flatten and use query parameters
[HttpGet("api/buildings/{buildingId}")]
[HttpGet("api/buildings?cityId={cityId}")]

// Anti-pattern 3: Exposing database schema
// ❌ Bad
[HttpGet("api/tbl_users")]
[HttpGet("api/user_entity")]
[HttpPost("api/insert_order")]

// ✅ Good: Clean domain resources
[HttpGet("api/users")]
[HttpPost("api/orders")]

// Anti-pattern 4: Inconsistent naming
// ❌ Bad
[HttpGet("api/user")]      // Singular
[HttpGet("api/products")]  // Plural
[HttpGet("api/Orders")]    // Capital

// ✅ Good: Consistent plural, lowercase
[HttpGet("api/users")]
[HttpGet("api/products")]
[HttpGet("api/orders")]

// Anti-pattern 5: Action-based instead of resource-based
// ❌ Bad
[HttpPost("api/createUser")]
[HttpPost("api/updateProduct")]
[HttpPost("api/deleteOrder")]

// ✅ Good: Resource-based with HTTP methods
[HttpPost("api/users")]
[HttpPut("api/products/{id}")]
[HttpDelete("api/orders/{id}")]
```

## Practice Exercise

Design resources for a library system:

1. **Identify resources**:
   - Books, Authors, Members, Loans, Reservations, Genres, Publishers
   - Think about which are independent and which are nested

2. **Model relationships**:
   - One-to-many: Authors have many books, Members have many loans
   - Many-to-many: Books have many authors, Books have many genres
   - Parent-child: Loans have line items (for multi-book loans)
   - Draw resource hierarchy

3. **Design URLs**:
   - Collections and individual resources
   ```
   GET    /api/books
   GET    /api/books/{id}
   POST   /api/books
   PUT    /api/books/{id}
   DELETE /api/books/{id}
   
   GET    /api/books/{bookId}/reviews
   POST   /api/books/{bookId}/reviews
   
   GET    /api/members/{memberId}/loans
   GET    /api/loans/{loanId}
   POST   /api/loans
   
   GET    /api/authors/{authorId}/books
   GET    /api/books?genre=fiction&available=true
   ```

4. **Avoid anti-patterns**:
   - No verbs in URLs (❌ `/api/borrowBook`, ✅ `POST /api/loans`)
   - No implementation details (❌ `/api/tbl_books`, ✅ `/api/books`)
   - Consistent naming (all lowercase, plural collections)

5. **Consider edge cases**:
   - How do you handle book reservations?
   - How do you model overdue books?
   - How do you handle returning a book (state transition)?
   - Where does search fit in your resource model?

## Self-Check Questions

1. **What is the difference between a resource and a collection?**
   - A resource is a single entity (e.g., `/api/books/123`)
   - A collection is a group of resources (e.g., `/api/books`)

2. **When should you nest resources vs keep them flat?**
   - Nest when: child can't exist without parent, accessed through parent, adds clarity
   - Flatten when: nesting too deep (>2-3 levels), child is independent, multiple access paths

3. **Why should URLs use nouns instead of verbs?**
   - HTTP methods (GET, POST, PUT, DELETE) are the verbs
   - Nouns represent resources, enabling uniform interface
   - Consistent pattern across all operations

4. **How do you decide resource granularity?**
   - Balance between chattiness and efficiency
   - Group related data that changes together
   - Consider client needs and common access patterns
   - Use field selection for optimization if needed

5. **What implementation details should never appear in URLs?**
   - Database table names (`tbl_users`)
   - Data transfer objects (`user_dto`)
   - Technology stack (`/dotnet/api/users`)
   - Internal structure (`/database/entities/users`)

6. **When should you use singular vs plural nouns?**
   - Plural for collections: `/api/products`
   - Singular for singleton resources: `/api/users/123/profile`
   - Be consistent throughout your API

7. **How do you handle resources that span multiple domains?**
   - Create aggregate endpoints for common queries
   - Use search endpoints for cross-domain queries
   - Consider creating view resources or composite resources
   - Document cross-references between resource types
