## Introduction

Ansible is an open-source automation tool that simplifies configuration management, application deployment, and task automation. Unlike other configuration management tools, Ansible is agentless—it doesn't require any software to be installed on managed nodes. This lesson covers Ansible's architecture, core concepts, and when to use it.

## Key Concepts Summary

### Ansible Architecture

**Agentless Design:**
- No agents required on managed nodes
- Uses SSH (Linux) or WinRM (Windows)
- Lightweight and easy to set up
- Minimal overhead on managed systems

**Core Components:**

```
┌─────────────────────┐
│   Control Node      │ ← Where Ansible is installed
│   (Your Machine)    │   and commands are executed
└──────────┬──────────┘
           │
           │ SSH/WinRM
           │
    ┌──────┴───────┬───────────┬────────────┐
    │              │           │            │
┌───▼────┐   ┌────▼───┐  ┌────▼───┐  ┌────▼───┐
│ Node 1 │   │ Node 2 │  │ Node 3 │  │ Node 4 │
│  (VM)  │   │ (VM)   │  │ (VM)   │  │  (VM)  │
└────────┘   └────────┘  └────────┘  └────────┘
  Managed Nodes (no agent required)
```

### Three Main Components

**1. Control Node:**
- The machine where Ansible is installed
- Runs playbooks and ad-hoc commands
- Manages inventory and configuration
- Must be Linux/Unix (Python required)

**2. Managed Nodes:**
- Remote systems Ansible manages
- No Ansible agent required
- Only need SSH access and Python
- Can be Linux, Windows, network devices, cloud resources

**3. Inventory:**
- List of managed nodes
- Organized into groups
- Can be static (INI/YAML files) or dynamic
- Defines which hosts Ansible targets

## How Ansible Works

### Execution Flow

```
1. User runs ansible command/playbook
        ↓
2. Control node reads inventory (which hosts?)
        ↓
3. Control node connects via SSH/WinRM
        ↓
4. Ansible copies module code to managed node
        ↓
5. Module executes on managed node
        ↓
6. Module returns results
        ↓
7. Ansible removes temporary files
        ↓
8. Results displayed to user
```

### Ansible Modules

Modules are small programs that perform specific tasks:

**Common Modules:**
- `apt`/`yum` - Package management
- `copy` - Copy files
- `template` - Deploy templates
- `service` - Manage services
- `user` - Manage users
- `file` - Manage files/directories
- `shell`/`command` - Execute commands
- `git` - Git repository management

**Module Execution:**

```bash
# Ad-hoc command example
ansible webservers -m ping

# Install nginx on all webservers
ansible webservers -m apt -a "name=nginx state=present" --become
```

### Key Features

**1. Declarative Language:**
```yaml
# You declare desired state, not steps
- name: Ensure nginx is installed
  apt:
    name: nginx
    state: present
```

**2. Idempotency:**
- Safe to run multiple times
- Only makes changes when needed
- Checks current state before acting

**3. Human-Readable:**
```yaml
# YAML syntax is clear and easy to understand
- name: Copy nginx configuration
  copy:
    src: nginx.conf
    dest: /etc/nginx/nginx.conf
  notify: Restart nginx
```

## Ansible vs Other Tools

| Feature | Ansible | Puppet | Chef |
|---------|---------|--------|------|
| **Architecture** | Agentless (SSH) | Agent-based | Agent-based |
| **Language** | YAML | Puppet DSL | Ruby DSL |
| **Learning Curve** | Easy | Moderate | Steep |
| **Configuration** | Push | Pull | Pull |
| **Setup** | Minimal | Complex | Complex |
| **Best For** | Quick setup, cloud | Enterprise | Complex workflows |

**When to Use Ansible:**
- ✅ Need quick setup without agents
- ✅ Manage cloud resources
- ✅ Simple, readable automation
- ✅ Ad-hoc tasks and orchestration
- ✅ Multi-platform environments

**When to Consider Alternatives:**
- ❌ Need pull-based configuration (Puppet/Chef)
- ❌ Complex compliance requirements (Chef)
- ❌ Large-scale enterprise with existing agent infrastructure

## Installation and Setup

### Installing Ansible (Control Node)

**On Ubuntu/Debian:**
```bash
sudo apt update
sudo apt install ansible -y
```

**On RHEL/CentOS:**
```bash
sudo yum install epel-release -y
sudo yum install ansible -y
```

**On macOS:**
```bash
brew install ansible
```

**Using pip:**
```bash
pip install ansible
```

**Verify Installation:**
```bash
ansible --version
```

### Preparing Managed Nodes

**Requirements:**
1. SSH access from control node
2. Python installed (usually present by default)
3. User account with sudo privileges

**Setup SSH Keys:**
```bash
# Generate SSH key on control node
ssh-keygen -t rsa -b 4096

# Copy to managed nodes
ssh-copy-id user@managed-node-ip
```

**Test Connection:**
```bash
# Test SSH connection
ssh user@managed-node-ip

# Test Ansible connection
ansible managed-node-ip -m ping
```

## Basic Ansible Commands

### Ad-Hoc Commands

**Ping all hosts:**
```bash
ansible all -m ping
```

**Check disk space:**
```bash
ansible all -a "df -h"
```

**Install package:**
```bash
ansible webservers -m apt -a "name=nginx state=present" --become
```

**Restart service:**
```bash
ansible webservers -m service -a "name=nginx state=restarted" --become
```

**Copy file:**
```bash
ansible all -m copy -a "src=/local/file dest=/remote/file"
```

### Command Structure

```bash
ansible <host-pattern> -m <module> -a "<module-args>" [options]
```

**Common Options:**
- `-m` - Module name
- `-a` - Module arguments
- `--become` - Run with sudo
- `-i` - Specify inventory file
- `-u` - Remote user
- `-v` - Verbose output

## Simple Inventory Example

**Create inventory file: `hosts`**

```ini
# Web servers
[webservers]
web1.example.com
web2.example.com
web3.example.com

# Database servers
[dbservers]
db1.example.com
db2.example.com

# All production servers
[production:children]
webservers
dbservers
```

**Using the inventory:**

```bash
# Ping web servers only
ansible webservers -i hosts -m ping

# Ping all hosts
ansible all -i hosts -m ping

# Ping production group
ansible production -i hosts -m ping
```

## Configuration File

**Create `ansible.cfg`:**

```ini
[defaults]
inventory = ./hosts
remote_user = ansible
host_key_checking = False
retry_files_enabled = False

[privilege_escalation]
become = True
become_method = sudo
become_user = root
become_ask_pass = False
```

**Configuration Precedence:**
1. `ANSIBLE_CONFIG` environment variable
2. `ansible.cfg` in current directory
3. `~/.ansible.cfg` in home directory
4. `/etc/ansible/ansible.cfg` system-wide

## Practical Example

**Scenario:** Check system information on all servers

**1. Create inventory:**

```ini
# inventory.ini
[servers]
192.168.1.10
192.168.1.11
192.168.1.12
```

**2. Run ad-hoc commands:**

```bash
# Check if all servers are reachable
ansible servers -i inventory.ini -m ping

# Get hostname
ansible servers -i inventory.ini -a "hostname"

# Check uptime
ansible servers -i inventory.ini -a "uptime"

# Check memory
ansible servers -i inventory.ini -a "free -h"

# List running services
ansible servers -i inventory.ini -a "systemctl list-units --type=service --state=running"
```

## Ansible Use Cases

**1. Configuration Management:**
- Ensure servers have correct packages installed
- Manage configuration files
- Maintain consistent server state

**2. Application Deployment:**
- Deploy applications to multiple servers
- Update application versions
- Roll back deployments

**3. Provisioning:**
- Create cloud resources (EC2, Azure VMs, GCP instances)

**4. Orchestration:**
- Coordinate multi-tier deployments

- Complex workflows across many systems

- Apply security patches
- Enforce security policies

## Best Practices

**1. Use Version Control:**
```bash
# Keep all Ansible code in Git
git init
git add ansible.cfg hosts playbooks/
git commit -m "Initial Ansible setup"
```

**2. Start Simple:**
- Begin with ad-hoc commands
- Learn one module at a time
- Gradually build complexity

**3. Test in Development:**
- Never test directly in production
- Use separate inventories for dev/staging/prod
- Verify playbooks in safe environments

**4. Document Your Work:**
```yaml
- name: Install web server  # Clear task names
  apt:
    name: nginx
    state: present
  # Comments explain why, not what
```

**5. Use Dry Run:**
```bash
# Check what would change without applying
ansible-playbook playbook.yml --check
```

## Common Pitfalls to Avoid

**❌ Running as root unnecessarily:**
```bash
# Bad: Always using root
ansible all -u root -a "command"

# Good: Use regular user with sudo
ansible all -u ansible -a "command" --become
```

**❌ Not using idempotent modules:**
```yaml
# Bad: Using shell for package installation
- shell: apt-get install nginx

# Good: Using package module
- apt:
    name: nginx
    state: present
```

**❌ Hardcoding values:**
```yaml
# Bad
- copy:
    dest: /var/www/html/index.html
    content: "Server: web1"

# Good: Use variables
- copy:
    dest: /var/www/html/index.html
    content: "Server: {{ inventory_hostname }}"
```
