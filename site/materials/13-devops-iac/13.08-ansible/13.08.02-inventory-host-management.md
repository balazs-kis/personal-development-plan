## Learning Objectives

By the end of this lesson, you will be able to:
- Create and organize static inventory files
- Use inventory groups and group variables
- Implement dynamic inventory for cloud environments
- Manage host variables and connection settings

---

## Introduction

Ansible's inventory defines which systems Ansible manages and how to connect to them. A well-organized inventory makes it easy to target specific hosts or groups for automation tasks. This lesson covers static inventories, group organization, variables, and dynamic inventory patterns.

## Key Concepts Summary

### Static Inventory Basics

**INI Format:**

```ini
# Simple host list
mail.example.com
web1.example.com
web2.example.com

# Hosts with aliases
jumper ansible_host=192.168.1.50 ansible_user=admin

# Group definition
[webservers]
web1.example.com
web2.example.com
web3.example.com

[dbservers]
db1.example.com
db2.example.com

# Groups of groups
[production:children]
webservers
dbservers

# Group variables
[webservers:vars]
http_port=80
max_clients=200
```

**YAML Format:**

```yaml
all:
  hosts:
    mail.example.com:
  children:
    webservers:
      hosts:
        web1.example.com:
        web2.example.com:
        web3.example.com:
      vars:
        http_port: 80
        max_clients: 200
    dbservers:
      hosts:
        db1.example.com:
        db2.example.com:
    production:
      children:
        webservers:
        dbservers:
```

## Inventory Organization Patterns

### Pattern 1: By Function

```ini
[webservers]

web2.example.com

[appservers]
app1.example.com
app2.example.com

[dbservers]
db1.example.com
db2.example.com

[loadbalancers]
lb1.example.com
```

### Pattern 2: By Environment

```ini
[dev]
dev-web1.example.com
dev-db1.example.com

[staging]
stage-web1.example.com
stage-db1.example.com

[production]
prod-web1.example.com
prod-web2.example.com
prod-db1.example.com
prod-db2.example.com
```

### Pattern 3: Multi-Dimensional

```ini
# Function groups
[webservers]
dev-web1.example.com
prod-web1.example.com
prod-web2.example.com

[dbservers]
dev-db1.example.com

[development]

dev-db1.example.com

[production]

prod-web2.example.com
prod-db1.example.com

# Compound groups
```

## Host and Group Variables

### Inline Variables

```ini
[webservers]
web1.example.com ansible_host=192.168.1.10 ansible_port=2222
web2.example.com ansible_host=192.168.1.11 http_port=8080

[webservers:vars]
ansible_user=deploy
ansible_become=true
ansible_become_method=sudo
```

### Directory Structure for Variables

**Recommended layout:**

```
inventory/
├── production
├── staging
├── group_vars/
│   ├── all.yml
│   ├── webservers.yml
│   ├── dbservers.yml
│   └── production.yml
└── host_vars/
    ├── web1.example.com.yml
    ├── web2.example.com.yml
    └── db1.example.com.yml
```

**Example files:**

```yaml
# group_vars/all.yml
---
ansible_user: ansible
ansible_become: true
ntp_server: time.example.com
dns_servers:
  - 8.8.8.8
  - 8.8.4.4
```

```yaml
# group_vars/webservers.yml
---
http_port: 80
https_port: 443
max_clients: 200
document_root: /var/www/html
```

```yaml
# host_vars/web1.example.com.yml
---
ansible_host: 192.168.1.10
server_id: 1
is_primary: true
backup_schedule: "0 2 * * *"
```

## Connection Variables

**SSH Connection:**

```ini
[servers]
server1 ansible_host=192.168.1.10 ansible_user=admin ansible_port=22
server2 ansible_host=192.168.1.11 ansible_ssh_private_key_file=~/.ssh/server2.pem
```

**Common Connection Variables:**

| Variable | Description | Example |
|----------|-------------|---------|
| `ansible_host` | Target IP/hostname | `192.168.1.10` |
| `ansible_port` | SSH port | `22` |
| `ansible_user` | SSH user | `ubuntu` |
| `ansible_ssh_private_key_file` | SSH key path | `~/.ssh/id_rsa` |
| `ansible_become` | Enable privilege escalation | `true` |
| `ansible_become_user` | Become this user | `root` |
| `ansible_become_method` | Escalation method | `sudo` |
| `ansible_python_interpreter` | Python path | `/usr/bin/python3` |

**Windows Hosts:**

```ini
[windows]
win1.example.com ansible_host=192.168.1.20 ansible_connection=winrm ansible_user=Administrator ansible_password=SecretPassword

[windows:vars]
ansible_port=5986
ansible_connection=winrm
ansible_winrm_transport=ntlm
ansible_winrm_server_cert_validation=ignore
```

## Inventory Patterns and Targeting

**Target specific hosts:**

```bash
# Single host
ansible web1.example.com -m ping

# Multiple hosts
ansible web1.example.com,web2.example.com -m ping

# All hosts in a group
ansible webservers -m ping

# All hosts
ansible all -m ping
```

**Pattern matching:**

```bash
# Wildcards
ansible web* -m ping
ansible *.example.com -m ping

# Range
ansible web[1:3].example.com -m ping

# Exclusion
ansible webservers:!web1.example.com -m ping

# Intersection
ansible webservers:&production -m ping

# Union
ansible webservers:dbservers -m ping
```

**Complex patterns:**

```bash
# Production web servers except web1
ansible production:&webservers:!web1.example.com -m ping

# Development or staging
ansible 'development:staging' -m ping

# All except production
ansible 'all:!production' -m ping
```

## Dynamic Inventory

### Why Dynamic Inventory?

**Use cases:**
- Cloud environments where instances come and go
- Auto-scaling groups
- Multiple cloud providers
- Integration with CMDB systems
- Container orchestration platforms

### Inventory Plugins (Recommended)

**AWS EC2 Plugin:**

```yaml
# inventory_aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions:
  - us-east-1
  - us-west-2
filters:
  tag:Environment: production
  instance-state-name: running
keyed_groups:
  - key: tags.Application
    prefix: app
  - key: placement.availability_zone
    prefix: az
hostnames:
  - tag:Name
compose:
  ansible_host: public_ip_address
```

**Usage:**

```bash
# Test inventory
ansible-inventory -i inventory_aws_ec2.yml --list

# Use in playbooks
ansible-playbook -i inventory_aws_ec2.yml playbook.yml
```

**Azure Plugin:**

```yaml
# inventory_azure_rm.yml
plugin: azure.azcollection.azure_rm
auth_source: auto
include_vm_resource_groups:
  - myResourceGroup
keyed_groups:
  - prefix: tag
    key: tags
```

**GCP Plugin:**

```yaml
# inventory_gcp_compute.yml
plugin: google.cloud.gcp_compute
projects:
  - my-project-id
filters:
  - status = RUNNING
keyed_groups:
  - key: labels.environment
    prefix: env
  - key: zone
    prefix: zone
```

### Inventory Scripts (Legacy)

**Example Python script:**

```python
#!/usr/bin/env python3
import json
import subprocess

# Get EC2 instances
result = subprocess.run(
    ['aws', 'ec2', 'describe-instances', '--output', 'json'],
    capture_output=True, text=True
)
data = json.loads(result.stdout)

inventory = {
    '_meta': {
        'hostvars': {}
    },
    'webservers': {
        'hosts': []
    }
}

for reservation in data['Reservations']:
    for instance in reservation['Instances']:
        if instance['State']['Name'] == 'running':
            host = instance['PublicIpAddress']
            inventory['webservers']['hosts'].append(host)
            inventory['_meta']['hostvars'][host] = {
                'ansible_host': host,
                'instance_id': instance['InstanceId']
            }

print(json.dumps(inventory, indent=2))
```

**Make script executable and test:**

```bash
chmod +x inventory.py
./inventory.py --list
ansible -i inventory.py all -m ping
```

## Large-Scale Inventory Organization

**Multi-environment setup:**

```
ansible/
├── inventories/
│   ├── production/
│   │   ├── hosts
│   │   ├── group_vars/
│   │   │   ├── all.yml
│   │   │   ├── webservers.yml
│   │   │   └── dbservers.yml
│   │   └── host_vars/
│   │       └── web1.prod.com.yml
│   ├── staging/
│   │   ├── hosts
│   │   ├── group_vars/
│   │   └── host_vars/
│   └── development/
│       ├── hosts
│       ├── group_vars/
│       └── host_vars/
├── playbooks/
├── roles/
└── ansible.cfg
```

**Using environment-specific inventory:**

```bash
# Production
ansible-playbook -i inventories/production playbook.yml

# Staging
ansible-playbook -i inventories/staging playbook.yml

# Development
ansible-playbook -i inventories/development playbook.yml
```

## Best Practices

### 1. Use Meaningful Names

```ini
# ✅ Good: Clear, descriptive
[web_application_servers]
app-web-01.prod.example.com
app-web-02.prod.example.com

# ❌ Bad: Unclear
[group1]
server1
server2
```

### 2. Document Your Inventory

```ini
# Production inventory
# Last updated: 2026-02-02
# Contact: ops-team@example.com

# Web tier - nginx reverse proxies
[webservers]
web1.prod.example.com  # Primary, US-East
web2.prod.example.com  # Secondary, US-East
web3.prod.example.com  # US-West
```

### 3. Separate Secrets

```yaml
# group_vars/all.yml
database_host: db.example.com
database_port: 5432
# Don't store passwords here!

# Use Ansible Vault for secrets
# group_vars/all/vault.yml (encrypted)
database_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  ...encrypted content...
```

### 4. Limit Production Access

```ini
# inventories/production/hosts
[production]
prod-web-01.example.com
prod-web-02.example.com

[production:vars]
# Add safeguard
ansible_ask_become_pass=true
```

### 5. Test Inventory Before Use

```bash
# List all hosts
ansible-inventory -i inventory.ini --list

# Show specific host variables
ansible-inventory -i inventory.ini --host web1.example.com

# Graph inventory structure
ansible-inventory -i inventory.ini --graph
```

## Common Patterns

### Pattern: Blue/Green Deployment

```ini
[blue]
web1-blue.example.com
web2-blue.example.com

[green]
web1-green.example.com
web2-green.example.com

[active:children]
blue  # Switch to 'green' for deployment

[standby:children]
green  # Switch to 'blue' for deployment
```

### Pattern: Rolling Updates

```ini
[webservers]
web1.example.com
web2.example.com
web3.example.com
web4.example.com

[webservers:vars]
# Update in batches
serial=2  # Update 2 at a time
```

### Pattern: Disaster Recovery

```ini
[primary_datacenter]
web1-dc1.example.com
db1-dc1.example.com

[dr_datacenter]
web1-dr.example.com
db1-dr.example.com

[active_datacenter:children]
primary_datacenter

[backup_datacenter:children]
dr_datacenter
```
