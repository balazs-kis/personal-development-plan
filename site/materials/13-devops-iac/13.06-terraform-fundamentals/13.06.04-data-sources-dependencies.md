## Learning Objectives

By the end of this lesson, you will be able to:
- Use data sources to query existing infrastructure
- Fetch information from external systems
- Understand implicit vs explicit dependencies
- Manage resource dependencies correctly
- Use data sources for dynamic, region-agnostic configurations
- Reference remote state for cross-stack communication

---

## Introduction

Data sources allow Terraform to fetch information from APIs or other Terraform configurations without creating or modifying resources. Understanding dependencies—both implicit and explicit—is crucial for ensuring Terraform creates, updates, and destroys resources in the correct order.

## Key Concepts Summary

### Data Sources Overview

**Data sources** allow Terraform to fetch or compute data for use elsewhere in your configuration. Unlike resources, data sources are read-only and don't create infrastructure.

```hcl
data "<PROVIDER>_<TYPE>" "<NAME>" {
  # Filter/query arguments
}

# Reference: data.<TYPE>.<NAME>.<ATTRIBUTE>
```

---

## Basic Data Source Usage

### Example: AWS AMI Data Source

```hcl
# Query the latest Ubuntu AMI
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]  # Canonical
  
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-focal-20.04-amd64-server-*"]
  }
  
  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }
}

# Use the data source
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t2.micro"
  
  tags = {
    Name = "Web Server"
    AMI  = data.aws_ami.ubuntu.name
  }
}

# Output AMI information
output "ami_id" {
  description = "ID of the Ubuntu AMI"
  value       = data.aws_ami.ubuntu.id
}
```

### Example: Availability Zones

```hcl
# Get available availability zones
data "aws_availability_zones" "available" {
  state = "available"
}

# Create subnets in all available AZs
resource "aws_subnet" "public" {
  count             = length(data.aws_availability_zones.available.names)
  vpc_id            = aws_vpc.main.id
  availability_zone = data.aws_availability_zones.available.names[count.index]
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index)
  
  tags = {
    Name = "public-${data.aws_availability_zones.available.names[count.index]}"
  }
}
```

## Multi-Region Deployment with Data Sources

```hcl
# Get AZs dynamically for any region
data "aws_availability_zones" "available" {
  state = "available"
}

# Get the latest AMI for the current region
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]
  
  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*-x86_64-gp2"]
  }
}

# Region-agnostic subnet creation
resource "aws_subnet" "public" {
  count = min(3, length(data.aws_availability_zones.available.names))
  
  vpc_id            = aws_vpc.main.id
  availability_zone = data.aws_availability_zones.available.names[count.index]
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index)
}

# Use region-specific AMI
resource "aws_instance" "web" {
  ami               = data.aws_ami.amazon_linux.id
  instance_type     = "t2.micro"
  availability_zone = data.aws_availability_zones.available.names[0]
}
```

This configuration works in any AWS region without modification!

## Remote State Data Source

Access outputs from another Terraform configuration:

```hcl
# Reference remote state
data "terraform_remote_state" "networking" {
  backend = "s3"
  
  config = {
    bucket = "terraform-state-bucket"
    key    = "networking/terraform.tfstate"
    region = "us-west-2"
  }
}

# Use outputs from remote state
resource "aws_instance" "app" {
  subnet_id         = data.terraform_remote_state.networking.outputs.private_subnet_ids[0]
  security_groups   = [data.terraform_remote_state.networking.outputs.app_sg_id]
  instance_type     = "t2.micro"
  ami               = data.aws_ami.ubuntu.id
}

# Reference multiple remote states
data "terraform_remote_state" "vpc" {
  backend = "s3"
  config = {
    bucket = "terraform-state-bucket"
    key    = "vpc/terraform.tfstate"
    region = "us-west-2"
  }
}

data "terraform_remote_state" "security" {
  backend = "s3"
  config = {
    bucket = "terraform-state-bucket"
    key    = "security/terraform.tfstate"
    region = "us-west-2"
  }
}
```

## External Data Source

Run external programs to fetch data:

```hcl
data "external" "git_info" {
  program = ["bash", "${path.module}/scripts/git-info.sh"]
}

# scripts/git-info.sh
#!/bin/bash
set -e
echo "{\"commit\":\"$(git rev-parse HEAD)\",\"branch\":\"$(git rev-parse --abbrev-ref HEAD)\"}"

# Use the data
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t2.micro"
  
  tags = {
    GitCommit = data.external.git_info.result.commit
    GitBranch = data.external.git_info.result.branch
  }
}
```

## HTTP Data Source

```hcl
# Fetch data from HTTP endpoint
data "http" "my_ip" {
  url = "https://api.ipify.org?format=json"
  
  request_headers = {
    Accept = "application/json"
  }
}

locals {
  my_ip = jsondecode(data.http.my_ip.response_body).ip
}

# Allow access only from your IP
resource "aws_security_group_rule" "allow_my_ip" {
  type              = "ingress"
  from_port         = 22
  to_port           = 22
  protocol          = "tcp"
  cidr_blocks       = ["${local.my_ip}/32"]
  security_group_id = aws_security_group.example.id
}
```

## Implicit Dependencies

Terraform automatically creates dependencies when one resource references another.

```hcl
# VPC created first (no dependencies)
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

# Subnet depends on VPC (implicit)
resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id  # ← Implicit dependency
  cidr_block = "10.0.1.0/24"
}

# Instance depends on subnet (implicit)
resource "aws_instance" "web" {
  ami           = "ami-abc123"
  instance_type = "t2.micro"
  subnet_id     = aws_subnet.public.id  # ← Implicit dependency
}

# Security group rule depends on security group (implicit)
resource "aws_security_group_rule" "allow_http" {
  type              = "ingress"
  from_port         = 80
  to_port           = 80
  protocol          = "tcp"
  cidr_blocks       = ["0.0.0.0/0"]
  security_group_id = aws_security_group.web.id  # ← Implicit dependency
}
```

**Terraform will create in order:**
1. `aws_vpc.main`
2. `aws_subnet.public` (after VPC)
3. `aws_security_group.web` (after VPC)
4. `aws_instance.web` (after subnet)
5. `aws_security_group_rule.allow_http` (after security group)

## Explicit Dependencies

Use `depends_on` when Terraform can't automatically infer the dependency.

```hcl
# IAM role and policy
resource "aws_iam_role" "app" {
  name               = "app-role"
  assume_role_policy = data.aws_iam_policy_document.assume_role.json
}

resource "aws_iam_role_policy_attachment" "app" {
  role       = aws_iam_role.app.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess"
}

# Instance profile
resource "aws_iam_instance_profile" "app" {
  name = "app-profile"
  role = aws_iam_role.app.name
}

# Instance needs role to be fully configured
resource "aws_instance" "app" {
  ami                  = "ami-abc123"
  instance_type        = "t2.micro"
  iam_instance_profile = aws_iam_instance_profile.app.name
  
  # Explicit dependency: wait for policy attachment
  depends_on = [aws_iam_role_policy_attachment.app]
}
```

### When to Use `depends_on`

Use explicit dependencies when:
1. Resource depends on another's side effects (not attributes)
2. Resource needs another to be fully configured before creation
3. Order matters but there's no direct attribute reference

```hcl
# Example: S3 bucket notification requires permissions first
resource "aws_s3_bucket" "data" {
  bucket = "my-data-bucket"
}

resource "aws_lambda_permission" "allow_bucket" {
  statement_id  = "AllowS3Invoke"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.processor.function_name
  principal     = "s3.amazonaws.com"
  source_arn    = aws_s3_bucket.data.arn
}

resource "aws_s3_bucket_notification" "bucket_notification" {
  bucket = aws_s3_bucket.data.id
  
  lambda_function {
    lambda_function_arn = aws_lambda_function.processor.arn
    events              = ["s3:ObjectCreated:*"]
  }
  
  # Must wait for permission to be created
  depends_on = [aws_lambda_permission.allow_bucket]
}
```

## Best Practices for Dependencies

### 1. Favor Implicit Dependencies

```hcl
# Good: Implicit dependency
resource "aws_subnet" "public" {
  vpc_id = aws_vpc.main.id  # Clear relationship
}

# Avoid: Unnecessary explicit dependency
resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id
  depends_on = [aws_vpc.main]  # Redundant!
}
```

### 2. Use `depends_on` Sparingly

```hcl
# Only when truly needed
resource "aws_s3_bucket_notification" "example" {
  # ...
  depends_on = [aws_lambda_permission.allow_bucket]
}
```

### 3. Break Circular Dependencies

```hcl
# Bad: Circular dependency
resource "aws_security_group" "app" {
  # ...
  egress {
    security_groups = [aws_security_group.db.id]
  }
}

resource "aws_security_group" "db" {
  # ...
  ingress {
    security_groups = [aws_security_group.app.id]  # Circular!
  }
}

# Good: Use security group rules
resource "aws_security_group" "app" {
  name = "app-sg"
}

resource "aws_security_group" "db" {
  name = "db-sg"
}

resource "aws_security_group_rule" "app_to_db" {
  type                     = "egress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  source_security_group_id = aws_security_group.db.id
  security_group_id        = aws_security_group.app.id
}

resource "aws_security_group_rule" "db_from_app" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  source_security_group_id = aws_security_group.app.id
  security_group_id        = aws_security_group.db.id
}
```

## Data Source Lifecycle

Data sources are read during the plan phase, but may be deferred:

```hcl
# Read during plan
data "aws_ami" "ubuntu" {
  most_recent = true
  # All arguments are known at plan time
}

# May be deferred to apply
data "aws_subnet" "selected" {
  id = aws_subnet.public.id  # Not known until apply
}
```

## Common Mistakes to Avoid

| Mistake | Problem | Solution |
|---------|---------|----------|
| Overusing `depends_on` | Slower plans, less efficient | Use implicit dependencies |
| Not using data sources | Hardcoded values | Query existing infrastructure |
| Circular dependencies | Terraform can't proceed | Break into separate resources |
| Wrong dependency order | Creation failures | Check dependency graph |
| Ignoring data source filters | Wrong resource selected | Add specific filters |
| Not handling empty data sources | Errors when nothing found | Add error handling |
