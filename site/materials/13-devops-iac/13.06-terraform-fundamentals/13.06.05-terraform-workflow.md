# Lesson 5: Terraform Workflow: Init, Plan, Apply

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the complete Terraform workflow
- Initialize Terraform working directories
- Create and review execution plans
- Apply changes to infrastructure
- Destroy infrastructure safely
- Use Terraform commands effectively
- Follow workflow best practices

---

## Introduction

The Terraform workflow is the systematic process of managing infrastructure: Write → Plan → Apply. Understanding this workflow and the core commands (`init`, `plan`, `apply`, `destroy`) is essential for safe, predictable infrastructure management. This lesson covers the complete lifecycle of Terraform operations.

## Key Concepts Summary

### The Core Workflow

```
┌─────────────┐
│   Write     │  Author infrastructure as code
│  (Editor)   │  
└──────┬──────┘
       │
       ▼
┌─────────────┐
│    Init     │  terraform init
│   (Setup)   │  Download providers & modules
└──────┬──────┘
       │
       ▼
┌─────────────┐
│    Plan     │  terraform plan
│  (Preview)  │  Show what will change
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   Apply     │  terraform apply
│  (Execute)  │  Make the changes
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   Destroy   │  terraform destroy (optional)
│  (Cleanup)  │  Remove infrastructure
└─────────────┘
```

## Step 1: Write Configuration

Create your Terraform configuration files:

```hcl
# main.tf
terraform {
  required_version = ">= 1.6"
  
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support   = true
  
  tags = {
    Name        = "${var.project_name}-vpc"
    Environment = var.environment
  }
}

resource "aws_subnet" "public" {
  count = 2
  
  vpc_id                  = aws_vpc.main.id
  cidr_block              = cidrsubnet(var.vpc_cidr, 8, count.index)
  availability_zone       = data.aws_availability_zones.available.names[count.index]
  map_public_ip_on_launch = true
  
  tags = {
    Name = "${var.project_name}-public-${count.index + 1}"
  }
}
```

## Step 2: Initialize - `terraform init`

**Purpose:** Prepare your working directory for Terraform operations.

```bash
terraform init
```

### What `init` Does

1. **Downloads providers** specified in `required_providers`
2. **Downloads modules** referenced in configuration
3. **Initializes backend** for state storage
4. **Creates `.terraform` directory** with downloaded plugins
5. **Creates/updates `.terraform.lock.hcl`** lock file

### Init Output Example

```bash
$ terraform init

Initializing the backend...

Initializing provider plugins...
- Finding hashicorp/aws versions matching "~> 5.0"...
- Installing hashicorp/aws v5.31.0...
- Installed hashicorp/aws v5.31.0 (signed by HashiCorp)

Terraform has created a lock file .terraform.lock.hcl to record the provider
selections it made above. Include this file in your version control repository
so that Terraform can guarantee to make the same selections by default when
you run "terraform init" in the future.

Terraform has been successfully initialized!

You may now begin working with Terraform. Try running "terraform plan" to see
any changes that are required for your infrastructure. All Terraform commands
should now work.
```

### Init Options

```bash
# Basic init
terraform init

# Upgrade providers to latest within constraints
terraform init -upgrade

# Migrate state from one backend to another
terraform init -migrate-state

# Reconfigure backend
terraform init -reconfigure

# Only download providers, skip backend init
terraform init -backend=false

# Don't download plugins (use cached)
terraform init -plugin-dir=/path/to/plugins

# Don't copy any existing state
terraform init -force-copy=false
```

## Step 3: Validate - `terraform validate`

**Purpose:** Check configuration syntax and internal consistency.

```bash
terraform validate
```

### Validation Success

```bash
$ terraform validate
Success! The configuration is valid.
```

### Validation Failure

```bash
$ terraform validate

Error: Unsupported argument

  on main.tf line 12, in resource "aws_instance" "web":
  12:   instance_tipe = "t2.micro"

An argument named "instance_tipe" is not expected here.
Did you mean "instance_type"?
```

### Validate in CI/CD

```bash
# Check formatting
terraform fmt -check -recursive

# Validate syntax
terraform validate

# Exit with error if validation fails
if ! terraform validate; then
  echo "Terraform configuration is invalid"
  exit 1
fi
```

## Step 5: Plan - `terraform plan`

**Purpose:** Preview changes before applying them.

```bash
terraform plan
```

### Plan Output Symbols

```
+ create
- destroy
~ update in-place
-/+ destroy and recreate
<= read (data source)
```

### Example Plan Output

```bash
$ terraform plan

Terraform used the selected providers to generate the following execution plan.
Resource actions are indicated with the following symbols:
  + create

Terraform will perform the following actions:

  # aws_vpc.main will be created
  + resource "aws_vpc" "main" {
      + arn                  = (known after apply)
      + cidr_block           = "10.0.0.0/16"
      + enable_dns_hostnames = true
      + enable_dns_support   = true
      + id                   = (known after apply)
      + tags                 = {
          + "Environment" = "dev"
          + "Name"        = "my-app-vpc"
        }
    }

  # aws_subnet.public[0] will be created
  + resource "aws_subnet" "public" {
      + availability_zone       = "us-west-2a"
      + cidr_block              = "10.0.0.0/24"
      + id                      = (known after apply)
      + map_public_ip_on_launch = true
      + vpc_id                  = (known after apply)
      + tags                    = {
          + "Name" = "my-app-public-1"
        }
    }

Plan: 2 to add, 0 to change, 0 to destroy.
```

### Plan Options

```bash
# Save plan to file
terraform plan -out=tfplan

# Show plan in machine-readable format
terraform plan -json

# Target specific resources
terraform plan -target=aws_instance.web

# Specify variable values
terraform plan -var="environment=prod"

# Use variable file
terraform plan -var-file="production.tfvars"

# Don't refresh state before planning
terraform plan -refresh=false

# Show detailed exit code
terraform plan -detailed-exitcode
# Exit codes: 0 = no changes, 1 = error, 2 = changes pending
```

## Step 6: Apply - `terraform apply`

**Purpose:** Create, update, or delete infrastructure to match configuration.

```bash
terraform apply
```

### Interactive Apply

```bash
$ terraform apply

Terraform used the selected providers to generate the following execution plan.
Resource actions are indicated with the following symbols:
  + create

Terraform will perform the following actions:

  # aws_vpc.main will be created
  + resource "aws_vpc" "main" {
      ...
    }

Plan: 2 to add, 0 to change, 0 to destroy.

Do you want to perform these actions?
  Terraform will perform the actions described above.
  Only 'yes' will be accepted to approve.

  Enter a value: yes

aws_vpc.main: Creating...
aws_vpc.main: Creation complete after 2s [id=vpc-0123456789abcdef]
aws_subnet.public[0]: Creating...
aws_subnet.public[0]: Creation complete after 1s [id=subnet-0123456789abcdef]

Apply complete! Resources: 2 added, 0 changed, 0 destroyed.

Outputs:

vpc_id = "vpc-0123456789abcdef"
```

### Apply Options

```bash
# Auto-approve (no prompt)
terraform apply -auto-approve

# Apply saved plan
terraform apply tfplan

# Target specific resources
terraform apply -target=aws_instance.web

# Specify variables
terraform apply -var="environment=prod" -var-file="prod.tfvars"

# Replace specific resource (recreate)
terraform apply -replace=aws_instance.web

# Parallelism (default 10)
terraform apply -parallelism=20
```

## Step 8: Output - `terraform output`

**Purpose:** Extract output values from state.

```bash
# Show all outputs
terraform output

# Show specific output
terraform output vpc_id

# Output as JSON
terraform output -json

terraform output -raw vpc_id
```

## Step 9: Destroy - `terraform destroy`

**Purpose:** Remove all managed infrastructure.

```bash
terraform destroy
```

### Destroy Output

```bash
$ terraform destroy

Terraform used the selected providers to generate the following execution plan.
Resource actions are indicated with the following symbols:
  - destroy

Terraform will perform the following actions:

  # aws_subnet.public[0] will be destroyed
  - resource "aws_subnet" "public" {
      - id                      = "subnet-0123456789abcdef"
      - vpc_id                  = "vpc-0123456789abcdef"
      ...

      - id         = "vpc-0123456789abcdef"

aws_vpc.main: Destroying... [id=vpc-0123456789abcdef]
aws_vpc.main: Destruction complete after 1s
```

### Destroy Options

```bash
# Auto-approve
terraform destroy -auto-approve

# Target specific resources
terraform destroy -target=aws_instance.web

# With variables
terraform destroy -var="environment=dev"

# Dry run (show what would be destroyed)
terraform plan -destroy
```

## State Management Commands

### List Resources

```bash
# List all resources in state
terraform state list

# Example output:
# aws_vpc.main
# aws_subnet.public[0]
# aws_subnet.public[1]
```

### Show Resource Details

```bash
# Show specific resource
terraform state show aws_vpc.main
```

### Move Resources

```bash
# Rename resource
terraform state mv aws_instance.old_name aws_instance.new_name

# Move to module
terraform state mv aws_instance.web module.compute.aws_instance.web
```

### Remove from State

```bash
# Remove resource from state (doesn't destroy)
terraform state rm aws_instance.test
```

### Pull/Push State

```bash
# Pull state to stdout
terraform state pull > backup.tfstate

# Push state from file (dangerous!)
terraform state push backup.tfstate
```

## Workflow Best Practices

### 1. Always Run Plan Before Apply

```bash
# Good workflow
terraform plan
# Review changes carefully
terraform apply

# Or save and apply plan
terraform plan -out=tfplan
terraform apply tfplan
```

### 2. Use Version Control

```bash
# Commit changes before applying
git add .
git commit -m "Add VPC and subnets"
terraform apply
```

### 3. Use Remote State for Teams

```hcl
terraform {
  backend "s3" {
    bucket = "my-terraform-state"
    key    = "prod/terraform.tfstate"
    region = "us-west-2"
  }
}
```

### 4. Use Workspaces or Directories for Environments

```bash
# Option 1: Workspaces
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod

terraform workspace select prod
terraform apply

# Option 2: Separate directories
environments/
├── dev/
│   ├── main.tf
│   └── terraform.tfvars
├── staging/
│   ├── main.tf
│   └── terraform.tfvars
└── prod/
    ├── main.tf
    └── terraform.tfvars
```

### 5. Review Plans in Pull Requests

```yaml
# .github/workflows/terraform-pr.yml
name: Terraform Plan
on: [pull_request]

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: hashicorp/setup-terraform@v2
      
      - name: Terraform Init
        run: terraform init
      
      - name: Terraform Plan
        run: terraform plan -no-color
        continue-on-error: true
        id: plan
      
      - name: Comment PR
        uses: actions/github-script@v6
        with:
          script: |
            const output = `#### Terraform Plan
            \`\`\`
            ${{ steps.plan.outputs.stdout }}
            \`\`\``;
            
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: output
            });
```

### 6. Use State Locking

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "terraform.tfstate"
    region         = "us-west-2"
    dynamodb_table = "terraform-locks"  # Enables locking
  }
}
```

## Common Workflow Patterns

### Development Workflow

```bash
# 1. Make changes to configuration
vim main.tf

# 2. Format code
terraform fmt

# 3. Validate syntax
terraform validate

# 4. Plan changes
terraform plan -out=tfplan

# 5. Review plan
# ... review output ...

# 6. Apply plan
terraform apply tfplan

# 7. Verify
terraform show
```

### CI/CD Workflow

```bash
# 1. Validate and format check
terraform fmt -check -recursive
terraform validate

# 2. Plan
terraform plan -out=tfplan

# 3. (Optional) Require manual approval

# 4. Apply
terraform apply tfplan
```

### Emergency Changes

```bash
# For emergency fixes, still use workflow
# But target specific resources for speed

# 1. Plan targeted change
terraform plan -target=aws_security_group_rule.emergency_fix

# 2. Apply targeted change
terraform apply -target=aws_security_group_rule.emergency_fix -auto-approve

# 3. Document the change
# 4. Update configuration to match
# 5. Run full plan to verify everything matches
terraform plan
```

## Common Mistakes to Avoid

| Mistake | Problem | Solution |
|---------|---------|----------|
| Not running plan | Unexpected changes | Always plan before apply |
| Using `-auto-approve` carelessly | Destructive changes | Only in automated pipelines |
| Not using state locking | Concurrent modifications | Configure backend with locking |
| Applying without review | Mistakes go unnoticed | Review plan output carefully |
| Not using version control | Lost changes | Commit all Terraform files |
| Manual changes to infrastructure | State drift | All changes through Terraform |
| Not backing up state | Data loss | Use versioned remote backend |
