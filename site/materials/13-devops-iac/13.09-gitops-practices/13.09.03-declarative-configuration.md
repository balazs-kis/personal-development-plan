# Lesson 3: Declarative Configuration and State Management

## Learning Objectives

By the end of this lesson, you will be able to:
- Explain the difference between declarative and imperative configuration
- Understand how GitOps uses declarative configurations for state management
- Structure Git repositories for effective GitOps workflows
- Apply best practices for managing declarative configurations

---

## Introduction

At the heart of GitOps lies declarative configuration—the practice of describing your desired system state rather than the steps to achieve it. This lesson explores how declarative configurations enable GitOps workflows, how to organize them effectively, and the patterns that make GitOps scalable and maintainable.

## Key Concepts Summary

### Declarative vs Imperative Configuration

**Imperative (How to do it):**
```bash
# Imperative approach - specifies steps
kubectl create namespace production
kubectl create deployment my-app --image=myapp:v1.2.3
kubectl scale deployment my-app --replicas=3
kubectl expose deployment my-app --port=80
```

**Declarative (What you want):**
```yaml
# Declarative approach - specifies desired state
apiVersion: v1
kind: Namespace
metadata:
  name: production
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: myapp:v1.2.3
---
apiVersion: v1
kind: Service
metadata:
  name: my-app
  namespace: production
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 8080
```

**Why Declarative?**
- **Idempotent:** Applying the same configuration multiple times produces the same result
- **Version Controllable:** Full state can be stored in Git
- **Self-Documenting:** The configuration describes the entire system state
- **Reconcilable:** System can automatically detect and correct drift

### GitOps Repository Structuring

**Anti-Pattern: Branches per Environment**
```
❌ AVOID
├── main branch
├── staging branch
├── production branch
```
Problem: Environment promotion is rarely a simple merge. You'll need to cherry-pick changes, manage environment-specific configs, and handle divergence.

**Recommended: Folders per Environment**
```
✅ RECOMMENDED
├── apps/
│   ├── app1/
│   │   ├── base/
│   │   │   ├── deployment.yaml
│   │   │   └── service.yaml
│   │   ├── overlays/
│   │   │   ├── dev/
│   │   │   │   └── kustomization.yaml
│   │   │   ├── staging/
│   │   │   │   └── kustomization.yaml
│   │   │   └── production/
│   │   │       └── kustomization.yaml
│   └── app2/
├── infrastructure/
│   ├── namespaces/
│   ├── rbac/
│   └── networking/
└── shared-services/
    ├── ingress-controller/
    └── cert-manager/
```

### Three-Layer Architecture

Many successful GitOps implementations use a three-layer structure:

**Layer 1: Infrastructure**
- Namespaces
- RBAC (Roles, RoleBindings)
- Service Accounts
- Network Policies
- Resource Quotas

**Layer 2: Shared Services**
- Ingress Controllers
- Certificate Managers
- Monitoring Stack
- Logging Infrastructure
- Service Mesh

**Layer 3: Applications**
- Application deployments
- Application services
- Application configurations

Each layer depends on the previous layer, allowing for controlled bootstrap.

### Monorepo vs Multi-Repo

**Monorepo Approach:**
```
single-repo/
├── infrastructure/
├── shared-services/
└── apps/
    ├── team-a/
    ├── team-b/
    └── team-c/
```

**Advantages:**
- Simplified dependency management
- Easier to enforce consistency
- Single place to look for all configurations

**Disadvantages:**
- Access control is all-or-nothing (or requires complex CODEOWNERS)
- Can become large and unwieldy
- All teams see all changes

**Multi-Repo Approach:**
```
infrastructure-repo/
shared-services-repo/
team-a-apps-repo/
team-b-apps-repo/
team-c-apps-repo/
```

**Advantages:**
- Clear access control boundaries
- Teams work independently
- Smaller, focused repositories

**Disadvantages:**
- Cross-repo dependencies are harder to manage
- Requires coordination for cross-cutting changes
- More repositories to maintain

### Best Practices

**1. Separate Application Code from Configuration**
- Application source code: `app-code-repo`
- Kubernetes manifests: `app-config-repo`

This prevents triggering builds on config-only changes and vice versa.

**2. Use Kustomize or Helm for DRY Configurations**
```yaml
# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1  # Default

# overlays/production/kustomization.yaml
resources:
  - ../../base
patches:
  - target:
      kind: Deployment
      name: my-app
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 10
```

**3. Pin Versions, Not HEAD**
```yaml
# ❌ Bad - can change unexpectedly
image: myapp:latest

# ✅ Good - immutable
image: myapp:v1.2.3
# or
image: myapp@sha256:abc123...
```

**4. Store Secrets References, Not Secret Values**
```yaml
# ❌ NEVER COMMIT SECRETS
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
data:
  password: cGFzc3dvcmQxMjM=  # Bad!

# ✅ Use external secrets
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  secretStoreRef:
    name: vault-backend
  target:
    name: db-credentials
  data:
  - secretKey: password
    remoteRef:
      key: database/production/password
```

## Practice Exercise

After completing the materials, try this exercise (do not spend more than 15 minutes):

Design a repository structure for a hypothetical organization with:
- 3 environments (dev, staging, production)
- 2 teams (frontend, backend)
- 3 applications per team
- Shared infrastructure components (ingress, monitoring)

Draw the folder structure and explain your choices. Consider:
- How would teams get isolated access?
- How would you promote changes between environments?
- Where would environment-specific configurations go?
