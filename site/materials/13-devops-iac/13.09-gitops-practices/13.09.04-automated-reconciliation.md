# Lesson 4: Automated Reconciliation and Drift Detection

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand how automated reconciliation works in GitOps
- Explain configuration drift and its causes
- Implement drift detection and remediation strategies
- Configure reconciliation intervals and policies

---

## Introduction

Automated reconciliation is what makes GitOps truly powerful—it ensures that your actual system state continuously matches the desired state defined in Git. This lesson explores how GitOps tools detect drift, reconcile differences, and maintain system integrity without manual intervention.

## Key Concepts Summary

### What is Reconciliation?

Reconciliation is the continuous process of:
1. **Observing** the desired state (from Git)
2. **Comparing** it with the actual state (in the cluster)
3. **Applying** changes to eliminate differences
4. **Repeating** the process indefinitely

```
┌─────────────────────────────────────────┐
│      Reconciliation Loop                │
│                                         │
│  ┌──────────┐      ┌──────────┐       │
│  │   Git    │─────→│ GitOps   │       │
│  │  Repo    │      │ Operator │       │
│  └──────────┘      └─────┬────┘       │
│                          │             │
│                          ↓             │
│                    ┌───────────┐      │
│                    │  Compare  │      │
│                    └─────┬─────┘      │
│                          │             │
│                          ↓             │
│                    ┌───────────┐      │
│        ┌──────────→│   Apply   │      │
│        │           └─────┬─────┘      │
│        │                 │             │
│        │                 ↓             │
│  ┌─────┴─────┐    ┌───────────┐      │
│  │   Wait    │←───│  Cluster  │      │
│  │ Interval  │    │   State   │      │
│  └───────────┘    └───────────┘      │
└─────────────────────────────────────────┘
```

### Configuration Drift

**Configuration Drift** occurs when the actual state of a system diverges from its desired state.

**Common Causes:**
- Manual changes via `kubectl`
- Emergency hotfixes applied directly
- Auto-scaling or self-healing mechanisms
- External controllers modifying resources
- Resource deletion outside of GitOps

**Example:**
```yaml
# Desired State (Git)
spec:
  replicas: 3

# Actual State (Cluster - after manual kubectl scale)
spec:
  replicas: 5  # Drift detected!
```

**GitOps Response:**
The reconciliation loop detects the difference and automatically scales back to 3 replicas.

### Reconciliation Intervals

GitOps tools reconcile at regular intervals and on-demand.

**Flux Example:**
```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: my-app
  namespace: flux-system
spec:
  interval: 10m  # Check every 10 minutes
  retryInterval: 1m  # Retry every 1 minute on failure
  timeout: 2m  # Timeout for applying changes
  sourceRef:
    kind: GitRepository
    name: my-app-repo
  path: ./apps/production
  prune: true  # Delete resources removed from Git
  wait: true  # Wait for resources to be ready
```

**ArgoCD Example:**
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
spec:
  syncPolicy:
    automated:
      prune: true  # Delete resources not in Git
      selfHeal: true  # Auto-sync when drift detected
      allowEmpty: false
    syncOptions:
    - CreateNamespace=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
```

### Sync Policies

**Manual Sync:**
- Changes detected but not applied automatically
- Operator or user must approve sync
- Used for production environments requiring human oversight

```yaml
# ArgoCD - Manual sync
syncPolicy: {}  # No automated policy
```

**Automatic Sync:**
- Changes applied automatically when detected
- Reduces operational overhead
- Used for dev/staging or when full automation is desired

```yaml
# ArgoCD - Automatic sync
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

**Self-Healing:**
- Automatically corrects drift
- Reverts manual changes
- Ensures Git is always the source of truth

### Prune Policy

**Pruning** is the removal of resources that exist in the cluster but not in Git.

**Example Scenario:**
1. You deploy a ConfigMap via GitOps
2. Later, you remove the ConfigMap from Git
3. With `prune: true`, the ConfigMap is deleted from the cluster
4. With `prune: false`, the ConfigMap remains (orphaned)

**Recommendation:**
- Enable pruning in non-production environments
- Use cautiously in production (consider manual pruning)
- Always test prune behavior in lower environments

### Health Assessment

GitOps tools assess resource health to determine sync success.

**Health Statuses:**
- **Healthy:** Resource is running as expected
- **Progressing:** Resource is being created/updated
- **Degraded:** Resource exists but isn't healthy
- **Suspended:** Resource is intentionally paused
- **Unknown:** Health cannot be determined

**ArgoCD Health Assessment:**
```yaml
# Deployment is Healthy when:
# - Desired replicas == Available replicas
# - All pods are running
# - Rollout is complete

status:
  health:
    status: Healthy
  sync:
    status: Synced
```

### Webhook-Based Reconciliation

Instead of polling at intervals, some setups use webhooks for immediate reconciliation.

**Flux Webhook Receiver:**
```yaml
apiVersion: notification.toolkit.fluxcd.io/v1
kind: Receiver
metadata:
  name: my-app-receiver
spec:
  type: github
  events:
    - "ping"
    - "push"
  secretRef:
    name: webhook-token
  resources:
    - apiVersion: source.toolkit.fluxcd.io/v1
      kind: GitRepository
      name: my-app-repo
```

**Benefits:**
- Near-instant reconciliation after Git push
- Reduces load from frequent polling
- Better resource utilization

**Considerations:**
- Requires network access from Git to cluster
- Adds complexity to setup
- Fallback to polling still needed
