## Introduction

GitLab environments allow you to track where your code is deployed and provide deployment visibility, controls, and history. Protected environments restrict who can deploy to specific environments (like production), while environment-specific variables enable different configurations per environment.

## Key Concepts Summary

### Basic Environment Configuration

```yaml
stages:
  - build
  - test
  - deploy

deploy:staging:
  stage: deploy
  script:
    - echo "Deploying to staging server"
    - ./deploy.sh staging
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - develop
```

### Multiple Environments

```yaml
deploy:dev:
  stage: deploy
  script:
    - ./deploy.sh dev
  environment:
    name: development
    url: https://dev.example.com
  only:
    - develop

deploy:staging:
  stage: deploy
  script:
    - ./deploy.sh staging
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - main
  when: manual  # Require manual approval

deploy:production:
  stage: deploy
  script:
    - ./deploy.sh production
  environment:
    name: production
    url: https://example.com
  only:
    - main
  when: manual
```

### Dynamic Environments

```yaml
# Create environment per branch
deploy:review:
  stage: deploy
  script:
    - ./deploy-review-app.sh
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.review.example.com
    on_stop: stop:review  # Job to run when stopping environment
  only:
    - branches
  except:
    - main

# Stop review app
stop:review:
  stage: deploy
  script:
    - ./stop-review-app.sh
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
  when: manual
  only:
    - branches
  except:
    - main
```

### Environment Variables

```yaml
# Use different variables per environment
deploy:staging:
  stage: deploy
  variables:
    DATABASE_URL: $STAGING_DATABASE_URL
    API_KEY: $STAGING_API_KEY
  script:
    - echo "Deploying to $DATABASE_URL"
    - ./deploy.sh
  environment:
    name: staging

deploy:production:
  stage: deploy
  variables:
    DATABASE_URL: $PRODUCTION_DATABASE_URL
    API_KEY: $PRODUCTION_API_KEY
  script:
    - echo "Deploying to $DATABASE_URL"
    - ./deploy.sh
  environment:
    name: production
  when: manual
```

## Protected Environments

### Setting Up Protected Environments

Protected environments are configured in GitLab UI at:
**Settings → CI/CD → Protected Environments**

Access levels (Premium/Ultimate tiers):
- Maintainers only
- Maintainers + Developers
- Specific users/groups
- Required approvals

```yaml
# Jobs deploying to protected environments require permissions
deploy:production:
  stage: deploy
  script:
    - ./deploy.sh
  environment:
    name: production  # Protected environment
    url: https://example.com
  only:
    - main
  when: manual
```

### Deployment Approvals

```yaml
# Multiple approval gates
deploy:production:
  stage: deploy
  script:
    - ./deploy.sh
  environment:
    name: production
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual  # First gate: manual trigger
      # Second gate: Protected environment approval (configured in UI)
```

## Deployment Strategies

### Blue-Green Deployment

```yaml
variables:
  BLUE_URL: "https://blue.example.com"
  GREEN_URL: "https://green.example.com"

deploy:blue:
  stage: deploy
  script:
    - ./deploy.sh blue
  environment:
    name: production-blue
    url: $BLUE_URL
  when: manual

deploy:green:
  stage: deploy
  script:
    - ./deploy.sh green
  environment:
    name: production-green
    url: $GREEN_URL
  when: manual

switch:traffic:
  stage: deploy
  script:
    - ./switch-traffic.sh
  environment:
    name: production
    url: https://example.com
  when: manual
```

### Canary Deployment

```yaml
deploy:canary:
  stage: deploy
  script:
    - ./deploy-canary.sh 10  # 10% traffic
  environment:
    name: production-canary
  when: manual

deploy:production:
  stage: deploy
  script:
    - ./deploy-full.sh  # 100% traffic
  environment:
    name: production
  when: manual
```

### Rolling Deployment

```yaml
deploy:production:
  stage: deploy
  script:
    - |
      for server in server1 server2 server3; do
        echo "Deploying to $server"
        ssh $server "./deploy.sh"
        sleep 30  # Wait between servers
      done
  environment:
    name: production
```

## Complete Multi-Environment Pipeline

```yaml
image: mcr.microsoft.com/dotnet/sdk:8.0

variables:
  DOTNET_VERSION: "8.0"

stages:
  - build
  - test
  - deploy:dev
  - deploy:staging
  - deploy:prod

build:
  stage: build
  script:
    - dotnet restore
    - dotnet build -c Release
    - dotnet publish -c Release -o ./publish
  artifacts:
    paths:
      - publish/
    expire_in: 1 week

test:unit:
  stage: test
  script:
    - dotnet test --filter Category=Unit

test:integration:
  stage: test
  services:
    - postgres:15
  variables:
    POSTGRES_DB: testdb
    POSTGRES_USER: test
    POSTGRES_PASSWORD: test
  script:
    - dotnet test --filter Category=Integration

# Development - auto-deploy
deploy:development:
  stage: deploy:dev
  variables:
    APP_URL: $DEV_APP_URL
    DATABASE_URL: $DEV_DATABASE_URL
    API_KEY: $DEV_API_KEY
  script:
    - echo "Deploying to development"
    - ./deploy.sh development
  environment:
    name: development
    url: https://dev.example.com
    on_stop: stop:development
  only:
    - develop

stop:development:
  stage: deploy:dev
  variables:
    GIT_STRATEGY: none
  script:
    - ./stop.sh development
  environment:
    name: development
    action: stop
  when: manual
  only:
    - develop

# Staging - manual trigger
deploy:staging:
  stage: deploy:staging
  variables:
    APP_URL: $STAGING_APP_URL
    DATABASE_URL: $STAGING_DATABASE_URL
    API_KEY: $STAGING_API_KEY
  script:
    - echo "Deploying to staging"
    - ./deploy.sh staging
    - ./run-smoke-tests.sh
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - main
  when: manual

# Production - manual + protected
deploy:production:
  stage: deploy:prod
  variables:
    APP_URL: $PROD_APP_URL
    DATABASE_URL: $PROD_DATABASE_URL
    API_KEY: $PROD_API_KEY
  script:
    - echo "Deploying to production"
    - ./deploy.sh production
  environment:
    name: production
    url: https://example.com
  only:
    - main
  when: manual
```

## Review Apps (Dynamic Environments)

```yaml
# Create review app for each merge request
deploy:review:
  stage: deploy
  script:
    - export REVIEW_APP_URL="https://$CI_COMMIT_REF_SLUG.review.example.com"
    - ./deploy-review-app.sh $CI_COMMIT_REF_SLUG
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.review.example.com
    on_stop: stop:review
    auto_stop_in: 1 week
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

# Automatically stop review app
stop:review:
  stage: deploy
  script:
    - ./stop-review-app.sh $CI_COMMIT_REF_SLUG
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: manual
```

## Kubernetes Deployments

```yaml
deploy:k8s:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    - kubectl config set-cluster k8s --server="$KUBE_URL"
    - kubectl config set-credentials deployer --token="$KUBE_TOKEN"
    - kubectl config set-context default --cluster=k8s --user=deployer
    - kubectl config use-context default
    - |
      cat <<EOF | kubectl apply -f -
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: myapp
      spec:
        replicas: 3
        selector:
          matchLabels:
            app: myapp
        template:
          metadata:
            labels:
              app: myapp
          spec:
            containers:
            - name: myapp
              image: registry.example.com/myapp:$CI_COMMIT_SHA
              ports:
              - containerPort: 8080
      EOF
  environment:
    name: production
    url: https://example.com
  when: manual
```

## Environment-Specific Configuration

### Using CI/CD Variables

```yaml
# Define in GitLab UI:
# Settings → CI/CD → Variables

# Scope variables to environments:
# - Variable: DATABASE_URL
#   Environment scope: production
#   Value: postgres://prod-db:5432/app

# - Variable: DATABASE_URL
#   Environment scope: staging
#   Value: postgres://staging-db:5432/app

deploy:
  script:
    - echo "Database: $DATABASE_URL"
    - ./deploy.sh
  environment:
    name: $CI_ENVIRONMENT_NAME
```

### Configuration Files

```yaml
deploy:
  script:
    # Select config file based on environment
    - cp config/$CI_ENVIRONMENT_NAME.json config.json
    - ./deploy.sh
  environment:
    name: production

# Project structure:
# config/
#   development.json
#   staging.json
#   production.json
```

## Deployment Monitoring

### Deployment Status

```yaml
deploy:production:
  stage: deploy
  script:
    - ./deploy.sh
    - ./health-check.sh || exit 1
  environment:
    name: production
    url: https://example.com
  after_script:
    # Send deployment notification
    - |
      curl -X POST $SLACK_WEBHOOK \
        -d "{\"text\":\"Deployment $CI_ENVIRONMENT_NAME: $CI_JOB_STATUS\"}"
```

### Rollback Configuration

```yaml
# GitLab tracks deployment history
# Rollback via UI or API:
# POST /projects/:id/environments/:environment_id/deployments/:deployment_id/rollback

deploy:production:
  stage: deploy
  script:
    - ./deploy.sh $CI_COMMIT_SHA
  environment:
    name: production
    deployment_tier: production  # Track tier for metrics
```

## Best Practices

### Environment Naming

```yaml
# ✅ GOOD: Clear, consistent naming
environment:
  name: production

# ✅ GOOD: Descriptive dynamic names
environment:
  name: review/$CI_COMMIT_REF_SLUG

# ❌ BAD: Unclear names
environment:
  name: env1
```

### Deployment Safety

```yaml
# ✅ GOOD: Multiple safety gates for production
deploy:production:
  stage: deploy
  script:
    - ./pre-deploy-checks.sh || exit 1  # Validation
    - ./deploy.sh
    - ./post-deploy-checks.sh || exit 1  # Verification
  environment:
    name: production
  only:
    - main
  when: manual  # Manual trigger
  # + Protected environment (UI config)
  # + Approval rules (UI config)

# ✅ GOOD: Automatic dev, manual prod
deploy:dev:
  environment:
    name: development
  only:
    - develop

deploy:prod:
  environment:
    name: production
  when: manual
  only:
    - main
```

### Environment Variables

```yaml
# ✅ GOOD: Scoped variables per environment
# Define in GitLab UI with environment scope

deploy:
  script:
    - echo "API Key: ${API_KEY:0:5}..."  # Don't log full secrets
  environment:
    name: $TARGET_ENV

# ❌ BAD: Hardcoding environment-specific values
deploy:
  script:
    - export API_KEY="abc123"  # Never hardcode secrets
```

## When to Use What

| Scenario | Solution |
|----------|----------|
| Track deployments | Use `environment:` keyword |
| Restrict production deploys | Protected environments |
| Per-branch preview | Dynamic environments |
| Manual production gates | `when: manual` |
| Environment-specific config | CI/CD variables with scope |
| Blue-green deployment | Multiple environments + traffic switch |
| Rollback capability | Environment deployment history |
| Approval requirements | Protected environments + approval rules |
