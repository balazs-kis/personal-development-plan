## Introduction

GitLab CI/CD uses a YAML file named `.gitlab-ci.yml` placed in the repository root to define your pipeline. This file specifies jobs that run scripts, the order they execute in, and the conditions under which they run. Understanding the basic configuration syntax is essential for building effective CI/CD pipelines in GitLab.

## Key Concepts Summary

### Basic Pipeline Structure

```yaml
# .gitlab-ci.yml
# Define the stages that jobs will run in
stages:
  - build
  - test
  - deploy

# Job 1: Build the application
build-job:
  stage: build
  script:
    - echo "Compiling the code..."
    - echo "Compile complete."

# Job 2: Run unit tests
unit-test-job:
  stage: test
  script:
    - echo "Running unit tests..."
    - echo "Tests passed."

# Job 3: Deploy to production
deploy-prod:
  stage: deploy
  script:
    - echo "Deploying application..."
    - echo "Application deployed."
```

### Docker Image Configuration

```yaml
# Global image for all jobs
image: node:20

stages:
  - build
  - test

build:
  stage: build
  script:
    - npm install
    - npm run build

# Override with job-specific image
test:
  stage: test
  image: node:18  # Different version for testing
  script:
    - npm test
```

### Variables

```yaml
# Global variables available to all jobs
variables:
  DEPLOY_SITE: "https://example.com"
  BUILD_CONFIGURATION: "Release"

stages:
  - build
  - deploy

build-app:
  stage: build
  # Job-specific variables
  variables:
    OUTPUT_DIR: "./dist"
  script:
    - echo "Building in $BUILD_CONFIGURATION mode"
    - echo "Output directory: $OUTPUT_DIR"

deploy-app:
  stage: deploy
  script:
    - echo "Deploying to $DEPLOY_SITE"
  # Predefined CI/CD variables
  only:
    - main
```

### Predefined Variables

```yaml
job:
  script:
    - echo "Pipeline ID: $CI_PIPELINE_ID"
    - echo "Job ID: $CI_JOB_ID"
    - echo "Commit SHA: $CI_COMMIT_SHA"
    - echo "Branch: $CI_COMMIT_REF_NAME"
    - echo "Project: $CI_PROJECT_NAME"
    - echo "Runner: $GITLAB_USER_LOGIN"
```

### Before Script and After Script

```yaml
# Global before_script runs before every job
default:
  before_script:
    - echo "Setting up environment..."
    - export PATH=$PATH:/custom/path

stages:
  - test

test-job:
  stage: test
  before_script:
    - echo "Job-specific setup"
    - npm install
  script:
    - npm test
  after_script:
    - echo "Cleanup after test"
    - rm -rf node_modules
```

### Job Control Keywords

```yaml
stages:
  - build
  - test

build:
  stage: build
  script:
    - dotnet build
  # Only run on specific branches
  only:
    - main
    - develop

test:
  stage: test
  script:
    - dotnet test
  # Run on all branches except
  except:
    - tags

lint:
  stage: test
  script:
    - dotnet format --verify-no-changes
  # Allow failure without failing pipeline
  allow_failure: true
```

### Rules for Advanced Control

```yaml
# Modern approach using rules instead of only/except
deploy-staging:
  stage: deploy
  script:
    - echo "Deploying to staging"
  rules:
    - if: $CI_COMMIT_BRANCH == "develop"
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

deploy-production:
  stage: deploy
  script:
    - echo "Deploying to production"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual  # Require manual trigger
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/  # Version tags

test-changes:
  stage: test
  script:
    - npm test
  rules:
    - changes:
        - "src/**/*.ts"    # Only run if TypeScript files changed
        - "tests/**/*.ts"
```

### Working with Services

```yaml
# Start service containers alongside job
test-with-database:
  stage: test
  image: node:20
  services:
    - postgres:15
    - redis:7-alpine
  variables:
    POSTGRES_DB: testdb
    POSTGRES_USER: testuser
    POSTGRES_PASSWORD: testpass
    POSTGRES_HOST_AUTH_METHOD: trust
  script:
    - npm install
    - npm test
```

### Workflow Configuration

```yaml
# Control when entire pipeline runs
workflow:
  rules:
    # Don't create pipeline for branch pushes if MR exists
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"
    - if: $CI_COMMIT_BRANCH =~ /^feature\//

stages:
  - build
  - test
```

## Complete .NET Example

```yaml
image: mcr.microsoft.com/dotnet/sdk:8.0

variables:
  SOLUTION: "MySolution.sln"
  BUILD_CONFIGURATION: "Release"

stages:
  - restore
  - build
  - test
  - deploy

# Global setup
default:
  before_script:
    - dotnet --version

restore-dependencies:
  stage: restore
  script:
    - dotnet restore $SOLUTION
  artifacts:
    paths:
      - "**/obj/"
    expire_in: 1 hour

build-app:
  stage: build
  script:
    - dotnet build $SOLUTION --configuration $BUILD_CONFIGURATION --no-restore
  artifacts:
    paths:
      - "**/bin/"
    expire_in: 1 day

unit-tests:
  stage: test
  script:
    - dotnet test $SOLUTION --configuration $BUILD_CONFIGURATION --no-build --logger "trx"
  artifacts:
    when: always
    reports:
      junit:
        - "**/*TestResults.trx"

deploy-staging:
  stage: deploy
  script:
    - dotnet publish --configuration $BUILD_CONFIGURATION --output ./publish
    - echo "Deploying to staging..."
  only:
    - develop
  environment:
    name: staging
    url: https://staging.example.com

deploy-production:
  stage: deploy
  script:
    - dotnet publish --configuration $BUILD_CONFIGURATION --output ./publish
    - echo "Deploying to production..."
  only:
    - main
  when: manual
  environment:
    name: production
    url: https://example.com
```

## Configuration Best Practices

### Organizing Jobs

```yaml
# Use descriptive job names
stages:
  - build
  - test
  - deploy

build:frontend:
  stage: build
  script:
    - cd frontend && npm run build

build:backend:
  stage: build
  script:
    - cd backend && dotnet build

test:unit:
  stage: test
  script:
    - npm run test:unit

test:integration:
  stage: test
  script:
    - npm run test:integration
```

### Using Anchors and Extends

```yaml
# Define reusable configuration with anchors
.deploy-template:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache curl
  script:
    - ./deploy.sh $ENVIRONMENT

# Extend the template
deploy-staging:
  extends: .deploy-template
  variables:
    ENVIRONMENT: staging
  environment:
    name: staging

deploy-production:
  extends: .deploy-template
  variables:
    ENVIRONMENT: production
  environment:
    name: production
  when: manual
```

### Include External Configuration

```yaml
# Include templates from other files
include:
  - local: '/templates/build-template.yml'
  - remote: 'https://example.com/shared-config.yml'
  - project: 'group/shared-templates'
    file: '/templates/security.yml'
  - template: 'Security/SAST.gitlab-ci.yml'  # GitLab templates

stages:
  - build
  - test
  - security
```

## Pipeline Validation and Troubleshooting

### CI Lint Tool

```yaml
# Validate your configuration at:
# https://gitlab.com/your-project/-/ci/lint

# Or use GitLab CLI
# gitlab-ci-lint < .gitlab-ci.yml
```

### Debugging Tips

```yaml
debug-job:
  stage: test
  script:
    # Print all environment variables
    - export
    # Show current directory and files
    - pwd
    - ls -la
    # Show Git info
    - git log -1
    - git branch -a
    # Test commands before full execution
    - echo "Would run: dotnet build"
```

### Common Errors

```yaml
# ❌ BAD: Missing stages definition
build:
  script:
    - echo "Building"

# ✅ GOOD: Explicitly define stages
stages:
  - build

build:
  stage: build
  script:
    - echo "Building"

# ❌ BAD: Invalid YAML indentation
test:
script:  # Wrong indentation
  - npm test

# ✅ GOOD: Correct indentation
test:
  script:
    - npm test
```

## Pipeline Execution Model

### How GitLab Runs Your Pipeline

1. **Trigger**: Push, merge request, schedule, or API call triggers pipeline
2. **Parse**: GitLab parses `.gitlab-ci.yml` and validates syntax
3. **Create**: Pipeline is created with jobs assigned to stages
4. **Queue**: Jobs are queued waiting for available runners
5. **Execute**: Runners pick up jobs and execute scripts
6. **Report**: Results are sent back to GitLab and displayed in UI

### Runner Selection

```yaml
# Use tags to select specific runners
build:
  stage: build
  tags:
    - docker
    - linux
  script:
    - make build

deploy:
  stage: deploy
  tags:
    - production
    - shell
  script:
    - ./deploy.sh
```

## When to Use What

| Use Case | Configuration |
|----------|---------------|
| Simple sequential pipeline | Define stages, one job per stage |
| Conditional execution | Use `rules` or `only`/`except` |
| Reusable configuration | Use `extends` or anchors |
| Environment-specific settings | Use variables per job |
| Manual approval gates | Use `when: manual` |
| External templates | Use `include` |
| Service dependencies | Use `services` keyword |
