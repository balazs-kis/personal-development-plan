## Learning Objectives

By the end of this lesson, you will be able to:
- Organize pipelines using stages for sequential execution
- Create complex job dependencies using the `needs` keyword
- Implement Directed Acyclic Graph (DAG) pipelines for parallel execution
- Use job artifacts to pass data between jobs
- Configure job dependencies and execution order
- Optimize pipeline performance with parallel execution

---

## Introduction

GitLab CI/CD organizes work into jobs that belong to stages. By default, jobs in each stage run in parallel, and stages execute sequentially. However, you can create more sophisticated execution patterns using the `needs` keyword to build Directed Acyclic Graph (DAG) pipelines where jobs run as soon as their dependencies complete.

## Key Concepts Summary

### Stage-Based Execution (Default)

```yaml
# Default behavior: stages run sequentially
stages:
  - build
  - test
  - deploy

# All build jobs run in parallel
build:frontend:
  stage: build
  script:
    - npm run build

build:backend:
  stage: build
  script:
    - dotnet build

# Test jobs wait for ALL build jobs to complete
test:frontend:
  stage: test
  script:
    - npm test

test:backend:
  stage: test
  script:
    - dotnet test

# Deploy waits for ALL test jobs
deploy:
  stage: deploy
  script:
    - echo "Deploying..."
```

### Job Dependencies with `needs`

```yaml
stages:
  - build
  - test
  - deploy

build:frontend:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/

build:backend:
  stage: build
  script:
    - dotnet build
  artifacts:
    paths:
      - bin/

# Start as soon as frontend build completes
test:frontend:
  stage: test
  needs: [build:frontend]  # Don't wait for backend build
  script:
    - npm test

# Start as soon as backend build completes
test:backend:
  stage: test
  needs: [build:backend]  # Don't wait for frontend build
  script:
    - dotnet test

# Wait for both test jobs
deploy:
  stage: deploy
  needs:
    - test:frontend
    - test:backend
  script:
    - echo "Deploying..."
```

### DAG Pipeline Example

```yaml
# No stages defined - pure DAG
build:app:
  script:
    - dotnet build
  artifacts:
    paths:
      - bin/

build:docker:
  needs: [build:app]
  script:
    - docker build -t myapp .

test:unit:
  needs: [build:app]
  script:
    - dotnet test

test:integration:
  needs: [build:app]
  script:
    - dotnet test --filter Integration

security:scan:
  needs: [build:app]
  script:
    - trivy scan bin/

deploy:staging:
  needs:
    - build:docker
    - test:unit
    - test:integration
    - security:scan
  script:
    - kubectl apply -f staging/
```

### Needs with Artifacts

```yaml
build:
  stage: build
  script:
    - dotnet build -o ./output
  artifacts:
    paths:
      - output/

# Download artifacts from build job
test:
  stage: test
  needs:
    - job: build
      artifacts: true  # Default behavior
  script:
    - dotnet test output/MyApp.dll

# Don't download artifacts (faster if not needed)
lint:
  stage: test
  needs:
    - job: build
      artifacts: false
  script:
    - dotnet format --verify-no-changes
```

### Optional Dependencies

```yaml
build:
  stage: build
  script:
    - make build

# Continue even if build fails
test:optional:
  stage: test
  needs:
    - job: build
      optional: true
  script:
    - echo "Running optional tests"
```

### Cross-Project Dependencies

```yaml
# Trigger pipeline in another project
trigger:downstream:
  trigger:
    project: group/downstream-project
    branch: main

# Wait for triggered pipeline
deploy:
  needs:
    - trigger:downstream
  script:
    - echo "Deploying after downstream pipeline"
```

## Parallel Execution Patterns

### Fan-Out (Parallel Tests)

```yaml
build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/

# Multiple test jobs run in parallel after build
test:unit:
  stage: test
  needs: [build]
  script:
    - npm run test:unit

test:integration:
  stage: test
  needs: [build]
  script:
    - npm run test:integration

test:e2e:
  stage: test
  needs: [build]
  script:
    - npm run test:e2e
```

### Fan-In (Aggregate Results)

```yaml
test:chrome:
  stage: test
  script:
    - npm run test -- --browser=chrome

test:firefox:
  stage: test
  script:
    - npm run test -- --browser=firefox

test:safari:
  stage: test
  script:
    - npm run test -- --browser=safari

# Wait for all browser tests to complete
report:
  stage: report
  needs:
    - test:chrome
    - test:firefox
    - test:safari
  script:
    - node generate-report.js
```

### Diamond Pattern

```yaml
#       build
#       /   \
#    test  lint
#       \   /
#      deploy

build:
  script:
    - make build

test:
  needs: [build]
  script:
    - make test

lint:
  needs: [build]
  script:
    - make lint

deploy:
  needs:
    - test
    - lint
  script:
    - make deploy
```

## Advanced Job Control

### Parallel Matrix with Needs

```yaml
build:
  script:
    - dotnet build
  artifacts:
    paths:
      - bin/

test:
  needs: [build]
  parallel:
    matrix:
      - PLATFORM: [linux, windows, macos]
        DOTNET_VERSION: ['6.0', '7.0', '8.0']
  script:
    - dotnet test --framework net$DOTNET_VERSION
```

### Job Dependencies Across Stages

```yaml
stages:
  - build
  - test
  - security
  - deploy

build:app:
  stage: build
  script:
    - make build

# Test starts immediately after build
test:unit:
  stage: test
  needs: [build:app]
  script:
    - make test

# Security scan runs parallel to tests
security:sast:
  stage: security
  needs: [build:app]
  script:
    - semgrep scan

# Deploy waits for both test and security
deploy:prod:
  stage: deploy
  needs:
    - test:unit
    - security:sast
  script:
    - make deploy
```

### Conditional Needs

```yaml
build:
  script:
    - make build

test:
  needs: [build]
  script:
    - make test

# Only depend on test if running on main branch
deploy:
  script:
    - make deploy
  needs:
    - job: test
      optional: true
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      needs: [test]  # Must pass tests on main
    - if: $CI_COMMIT_BRANCH != "main"
      needs: []      # No dependencies on feature branches
```

## Performance Optimization

### Minimize Critical Path

```yaml
# BAD: Sequential execution
stages:
  - build
  - test-unit
  - test-integration
  - test-e2e
  - deploy

# GOOD: Parallel execution
stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - make build

# All tests run in parallel
test:unit:
  stage: test
  needs: [build]
  script:
    - make test-unit

test:integration:
  stage: test
  needs: [build]
  script:
    - make test-integration

test:e2e:
  stage: test
  needs: [build]
  script:
    - make test-e2e

deploy:
  stage: deploy
  needs:
    - test:unit
    - test:integration
    - test:e2e
  script:
    - make deploy
```

### Job Interruptibility

```yaml
# Allow newer pipelines to cancel running jobs
build:
  interruptible: true
  script:
    - make build

# Never interrupt deployment jobs
deploy:
  interruptible: false
  script:
    - make deploy
```

## Complete Example: Microservices Pipeline

```yaml
stages:
  - build
  - test
  - package
  - deploy

# Build services in parallel
build:api:
  stage: build
  script:
    - cd services/api && dotnet build
  artifacts:
    paths:
      - services/api/bin/

build:worker:
  stage: build
  script:
    - cd services/worker && dotnet build
  artifacts:
    paths:
      - services/worker/bin/

build:frontend:
  stage: build
  script:
    - cd frontend && npm run build
  artifacts:
    paths:
      - frontend/dist/

# Tests run as soon as their service builds
test:api:
  stage: test
  needs: [build:api]
  script:
    - cd services/api && dotnet test

test:worker:
  stage: test
  needs: [build:worker]
  script:
    - cd services/worker && dotnet test

test:frontend:
  stage: test
  needs: [build:frontend]
  script:
    - cd frontend && npm test

# Integration tests need all services
test:integration:
  stage: test
  needs:
    - build:api
    - build:worker
    - build:frontend
  services:
    - postgres:15
    - redis:7
  script:
    - npm run test:integration

# Package each service independently
package:api:
  stage: package
  needs:
    - build:api
    - test:api
    - test:integration
  script:
    - docker build -t api:$CI_COMMIT_SHA services/api

package:worker:
  stage: package
  needs:
    - build:worker
    - test:worker
    - test:integration
  script:
    - docker build -t worker:$CI_COMMIT_SHA services/worker

package:frontend:
  stage: package
  needs:
    - build:frontend
    - test:frontend
  script:
    - docker build -t frontend:$CI_COMMIT_SHA frontend

# Deploy when all packages are ready
deploy:staging:
  stage: deploy
  needs:
    - package:api
    - package:worker
    - package:frontend
  environment:
    name: staging
  script:
    - helm upgrade --install myapp ./charts/myapp
```

## Best Practices

### Use Needs for Independent Jobs

```yaml
# ✅ GOOD: Jobs run as soon as dependencies complete
test:unit:
  needs: [build]
  script:
    - npm test

# ❌ BAD: Job waits unnecessarily for unrelated jobs
test:unit:
  stage: test  # Waits for ALL jobs in previous stage
  script:
    - npm test
```

### Limit Needs References

```yaml
# ✅ GOOD: Limited, clear dependencies
deploy:
  needs:
    - test:unit
    - test:integration
  script:
    - make deploy

# ❌ BAD: Too many dependencies makes graph complex
deploy:
  needs:
    - job1
    - job2
    - job3
    - job4
    - job5
    - job6
    - job7
  script:
    - make deploy
```

### Balance Parallelism and Resources

```yaml
# Consider runner capacity
stages:
  - build
  - test

# If you have 4 runners, this is optimal
test:1:
  needs: [build]
  script:
    - make test-part-1

test:2:
  needs: [build]
  script:
    - make test-part-2

test:3:
  needs: [build]
  script:
    - make test-part-3

test:4:
  needs: [build]
  script:
    - make test-part-4
```

## When to Use Stages vs Needs

| Use Case | Solution |
|----------|----------|
| Simple linear pipeline | Use stages only |
| Independent parallel jobs | Use `needs` for faster execution |
| Complex dependencies | Use `needs` to create DAG |
| Fan-out testing | Use `needs` + `parallel` |
| Microservices | Use `needs` per service |
| Traditional stages work well | Don't over-complicate with `needs` |
