## Learning Objectives

By the end of this lesson, you will be able to:
- Design effective environment promotion strategies

- Apply best practices for safe production deployments

---

## Introduction

Environment promotion is the structured process of moving code and configuration from development through staging to production. Done right, it provides confidence that production deployments will succeed. Done wrong, it becomes a bottleneck that slows delivery. This lesson explores strategies for safe, efficient environment promotion with appropriate gates and checks at each stage.

## Key Concepts Summary

### Environment Promotion Fundamentals

**What is Environment Promotion?**
The process of moving applications and their configurations through a series of environments with increasing maturity and stability requirements.

**Typical Flow:**
```
Developer → Commit → CI Build → Dev Deploy → Staging Deploy → Production Deploy
                        ↓            ↓              ↓                ↓
                     Unit Tests  Integration  Performance     Live Traffic
                                   Tests         Tests
```

**Why It Matters:**
- Validates that deployments work before reaching production
- Provides opportunities to test in production-like environments
- Enables rollback strategies
- Creates checkpoints for approval and validation

### Environment Characteristics

**Development Environment:**
- **Purpose:** Rapid iteration and testing
- **Characteristics:**
  - Deployed frequently (every commit or multiple times per day)
  - May be unstable
  - Can run feature branches
  - Relaxed security controls
  - Mock or test data
  - Developers have full access
- **Promotion Gate:** Automated tests pass

**Staging/Pre-Production:**
- **Purpose:** Final validation before production
- **Characteristics:**
  - Mirrors production environment
  - Runs only main branch code
  - Production-like data (anonymized)
  - Production-equivalent infrastructure
  - Strict access controls
  - Full monitoring and observability
- **Promotion Gate:** Manual approval + automated tests

**Production:**
- **Purpose:** Serve end users
- **Characteristics:**
  - Highest stability requirements
  - Rigorous change control
  - Real user data
  - Maximum redundancy and reliability
  - Complete audit trail
  - 24/7 monitoring
- **Promotion Gate:** Manual approval + automated validation + smoke tests

### Deployment Pipeline Stages

**Stage 1: Build**
```yaml
stage: build
  jobs:
  - job: compile
    steps:
    - checkout: self
    - run: npm install
    - run: npm run build
    - run: npm test
    - publish: artifacts
```

**Stage 2: Deploy to Dev**
```yaml
stage: deploy_dev
  dependsOn: build
  jobs:
  - deployment: dev
    environment: development
    strategy:
      runOnce:
        deploy:
          steps:
          - download: current
            artifact: build
          - run: kubectl apply -f k8s/dev/
          - run: ./smoke-tests.sh dev
```

**Stage 3: Deploy to Staging**
```yaml
stage: deploy_staging
  dependsOn: deploy_dev
  condition: succeeded()
  jobs:
  - deployment: staging
    environment: staging
    strategy:
      runOnce:
        deploy:
          steps:
          - download: current
            artifact: build
          - run: kubectl apply -f k8s/staging/
          - run: ./integration-tests.sh staging
```

**Stage 4: Deploy to Production**
```yaml
stage: deploy_production
  dependsOn: deploy_staging
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: production
    environment: production
    strategy:
      runOnce:
        preDeploy:
          steps:
          - run: ./pre-deployment-checks.sh
        deploy:
          steps:
          - download: current
            artifact: build
          - run: kubectl apply -f k8s/production/
        postDeploy:
          steps:
          - run: ./smoke-tests.sh production
          - run: ./notify-team.sh
```

### Deployment Gates and Approvals

**Types of Gates:**

**1. Automated Quality Gates**
```yaml
quality_gate:
  conditions:
    - unit_tests: passed
    - code_coverage: >= 80%
    - security_scan: no_critical_issues
    - performance_tests: baseline_met
    - integration_tests: passed
```

**2. Manual Approval Gates**
```yaml
approval:
  type: manual
  approvers:
    - team: platform-team
      min_approvers: 2
    - team: security-team
      min_approvers: 1
  timeout: 24h
```

**3. Time-Based Gates**
```yaml
soak_period:
  type: delay
  duration: 2h
  description: "Allow metrics to stabilize in staging"
```

**4. External System Gates**
```yaml
external_gate:
  type: api_check
  endpoint: https://monitoring.example.com/api/health
  expected_status: 200
  retry_attempts: 3
```

### GitHub Actions Multi-Environment Pipeline

```yaml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Build
        run: |
          npm install
          npm run build
          npm test
      - name: Upload artifact
        uses: actions/upload-artifact@v3
        with:
          name: app-build
          path: dist/

  deploy-dev:
    needs: build
    runs-on: ubuntu-latest
    environment: development
    steps:
      - uses: actions/download-artifact@v3
        with:
          name: app-build
      - name: Deploy to dev
        run: |
          kubectl config use-context dev
          kubectl apply -f k8s/dev/

  deploy-staging:
    needs: deploy-dev
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/download-artifact@v3
        with:
          name: app-build
      - name: Deploy to staging
        run: |
          kubectl config use-context staging
          kubectl apply -f k8s/staging/
      - name: Run smoke tests
        run: ./smoke-tests.sh staging

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://app.example.com
    steps:
      - uses: actions/download-artifact@v3
        with:
          name: app-build
      - name: Deploy to production
        run: |
          kubectl config use-context production
          kubectl apply -f k8s/production/
      - name: Run smoke tests
        run: ./smoke-tests.sh production
```

**GitHub Environment Protection Rules:**
- Required reviewers (1-6 people)
- Wait timer (delay before deployment)
- Deployment branches (restrict which branches can deploy)

### GitOps-Based Promotion

**Directory Structure:**
```
gitops-repo/
├── apps/
│   └── myapp/
│       ├── base/
│       │   └── deployment.yaml
│       ├── dev/
│       │   ├── kustomization.yaml
│       │   └── version.yaml  # image: myapp:dev-abc123
│       ├── staging/
│       │   ├── kustomization.yaml
│       │   └── version.yaml  # image: myapp:v1.2.3
│       └── production/
│           ├── kustomization.yaml
│           └── version.yaml  # image: myapp:v1.2.2
```

**Promotion Process:**
1. CI builds image `myapp:v1.2.3`
2. Automated commit updates `dev/version.yaml`
3. ArgoCD/Flux syncs to dev cluster
4. Manual approval promotes to staging: copy image tag to `staging/version.yaml`
5. Validation in staging
6. Manual approval promotes to production: copy image tag to `production/version.yaml`

### Deployment Strategies

**1. Recreate (Downtime)**
```yaml
strategy:
  type: Recreate
```
- Stop all old instances
- Deploy new instances
- **Use case:** Development, database migrations

**2. Rolling Update (No Downtime)**
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```
- Gradually replace old instances with new
- **Use case:** Most production deployments

**3. Blue-Green (Zero Downtime)**
```yaml
# Deploy green
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-green
spec:
  replicas: 10
  template:
    metadata:
      labels:
        version: green

# Switch service
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    version: green  # Changed from blue
```
- **Use case:** High-stakes releases, instant rollback needed

**4. Canary (Progressive)**
```yaml
# 10% canary
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-canary
spec:
  replicas: 1  # 10% of 10 total instances
  template:
    metadata:
      labels:
        version: v2

# Stable version
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-stable
spec:
  replicas: 9  # 90%
  template:
    metadata:
      labels:
        version: v1
```
- **Use case:** High-risk changes, want to limit blast radius

### Rollback Strategies

**1. Git Revert (GitOps)**
```bash
# Revert to previous version
git revert HEAD
git push
# ArgoCD/Flux automatically rolls back
```

**2. Manual Kubectl Rollback**
```bash
# Rollback to previous revision
kubectl rollout undo deployment/myapp

# Rollback to specific revision
kubectl rollout undo deployment/myapp --to-revision=3
```

**3. Blue-Green Switch Back**
```bash
# Switch service back to blue
kubectl patch service myapp -p '{"spec":{"selector":{"version":"blue"}}}'
```

**4. Pipeline Re-run**
```bash
# Re-run successful previous pipeline
gh workflow run deploy.yml --ref v1.2.2
```

### Best Practices

1. **Automate dev/staging, gate production**
2. **Deploy to staging from main branch only**
3. **Use same artifact across environments** (don't rebuild)
4. **Implement smoke tests after each deployment**
5. **Monitor metrics before promoting**
6. **Document rollback procedures**
7. **Use deployment strategies appropriate to risk**
8. **Keep deployment windows predictable**
9. **Implement deployment locks for critical times**
10. **Practice deployments and rollbacks regularly**
