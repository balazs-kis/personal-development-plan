## Introduction

Secrets—API keys, database passwords, encryption keys—are the keys to your kingdom. A single leaked secret can compromise your entire system. Yet many teams still commit secrets to Git, pass them in plaintext, or store them insecurely. This lesson covers enterprise-grade secrets management strategies that keep your credentials safe while remaining practical for daily development.

## Key Concepts Summary

### The Secrets Management Problem

**What are secrets?**
- Database credentials
- API keys and tokens
- Encryption keys
- TLS certificates
- OAuth client secrets
- SSH keys

**Common mistakes:**
```bash
# ❌ NEVER DO THIS: Secrets in code
const API_KEY = "sk-prod-abc123xyz";

# ❌ NEVER DO THIS: Secrets in version control
# .env (committed to git)
DATABASE_PASSWORD=SuperSecret123

# ❌ NEVER DO THIS: Secrets in Docker images
# Dockerfile
ENV API_KEY=sk-prod-abc123xyz

# ❌ NEVER DO THIS: Secrets in plain ConfigMaps
apiVersion: v1
kind: ConfigMap
data:
  database-password: SuperSecret123  # ConfigMaps are not encrypted!
```

**Why this is dangerous:**
- Git history is permanent—secrets can be extracted even after "deletion"
- Anyone with repo access has all secrets
- No audit trail of who accessed what
- No rotation mechanism
- Secrets spread across environment

### Secrets Management Requirements

A proper secrets management solution provides:

1. **Encryption at rest:** Secrets stored encrypted
2. **Encryption in transit:** Secrets transmitted over TLS
3. **Access control:** Role-based access to secrets
4. **Audit logging:** Who accessed which secrets when
5. **Secret rotation:** Ability to rotate credentials
6. **Secret versioning:** Track changes to secrets over time
7. **Dynamic secrets:** Generate credentials on-demand
8. **Lease management:** Automatic expiration and renewal

### Secrets Management Hierarchy

**Level 1: Basic (Don't do this in production)**
```yaml
# Kubernetes Secret (base64 encoded, NOT encrypted)
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  password: U3VwZXJTZWNyZXQxMjM=  # Just base64, not encrypted!
```

**Problems:**
- Base64 is encoding, not encryption
- Anyone with cluster access can decode
- Must be managed manually
- No rotation or audit trail

**Level 2: Encrypted Secrets**
```yaml
# Sealed Secrets (encrypted in Git)
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: db-secret
spec:
  encryptedData:
    password: AgBh3+...encrypted...
```

**Better, but:**
- Still static secrets
- Manual rotation required
- Limited audit capabilities

**Level 3: External Secrets (Recommended)**
```yaml
# External Secret referencing Vault
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-secret
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: db-secret
  data:
  - secretKey: password
    remoteRef:
      key: database/production/password
```

**Benefits:**
- Secrets stored in dedicated secret manager
- Automatic rotation support
- Full audit trail
- Access control in secret manager

### Vault Integration Methods

**1. Vault Secrets Operator (VSO) - Recommended**

Synchronizes secrets from Vault to native Kubernetes Secrets:

```yaml
# VaultStaticSecret resource
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultStaticSecret
metadata:
  name: db-credentials
spec:
  type: kv-v2
  mount: secret
  path: database/production
  refreshAfter: 1h
  destination:
    name: db-secret
    create: true
```

**Benefits:**
- Secrets automatically synced from Vault
- Applications use standard Kubernetes Secrets
- Supports rotation with TTL
- Multiple auth methods (Kubernetes SA, AppRole, AWS, GCP)

**2. Vault Agent Injector**

Injects Vault Agent sidecar into pods:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "myapp"
        vault.hashicorp.com/agent-inject-secret-db: "database/creds/myapp"
        vault.hashicorp.com/agent-inject-template-db: |
          {{- with secret "database/creds/myapp" -}}
          export DB_USER="{{ .Data.username }}"
          export DB_PASSWORD="{{ .Data.password }}"
          {{- end }}
    spec:
      containers:
      - name: app
        image: myapp:1.0
```

**Benefits:**
- No code changes required
- Secrets rendered to files
- Automatic renewal before expiration

**3. CSI Secret Store Driver**

Mounts secrets as volumes using CSI:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp
spec:
  containers:
  - name: app
    volumeMounts:
    - name: secrets
      mountPath: "/mnt/secrets"
      readOnly: true
  volumes:
  - name: secrets
    csi:
      driver: secrets-store.csi.k8s.io
      readOnly: true
      volumeAttributes:
        secretProviderClass: "vault-provider"
```

### Dynamic Secrets

Vault can generate credentials on-demand:

**Static Secrets (Traditional):**
```
1. Admin creates database user
2. Admin stores password in Vault
3. App retrieves password
4. Manual rotation required
```

**Dynamic Secrets (Vault):**
```
1. Vault is configured with database admin credentials
2. App requests database credentials
3. Vault generates unique username/password
4. App uses credentials (valid for lease duration)
5. Vault automatically revokes after lease expires
```

**Example: Database Dynamic Secrets**
```hcl
# Configure database backend in Vault
path "database/creds/myapp" {
  capabilities = ["read"]
}

# Vault creates role with this SQL
CREATE ROLE "{{name}}" WITH
  LOGIN PASSWORD '{{password}}'
  VALID UNTIL '{{expiration}}'
  INHERIT IN ROLE app_user;
```

**Benefits:**
- Unique credentials per application/instance
- Automatic expiration
- Automatic rotation
- Instant revocation
- Reduced blast radius if compromised

### Secrets in CI/CD Pipelines

**GitHub Actions:**
```yaml
name: Deploy
on: [push]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    
    - name: Get secrets from Vault
      uses: hashicorp/vault-action@v2
      with:
        url: https://vault.example.com
        method: jwt
        role: github-actions
        secrets: |
          secret/data/production/db password | DB_PASSWORD
          
    - name: Deploy
      env:
        DB_PASSWORD: ${{ steps.vault.outputs.DB_PASSWORD }}
      run: ./deploy.sh
```

**GitLab CI:**
```yaml
deploy:
  stage: deploy
  secrets:
    DATABASE_PASSWORD:
      vault: production/database/password@secret
      file: false
  script:
    - echo "Deploying with DB password from Vault"
    - ./deploy.sh
```

### Secret Rotation Strategy

**Manual Rotation (Legacy):**
1. Generate new secret
2. Update secret in all locations
3. Update applications
4. Monitor for failures
5. Remove old secret

**Automated Rotation (Modern):**
```yaml
# Vault policy for auto-rotation
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultStaticSecret
metadata:
  name: db-credentials
spec:
  mount: secret
  path: database/production
  refreshAfter: 24h  # Check for updates every 24 hours
  rolloutRestartTargets:
  - kind: Deployment
    name: myapp  # Restart deployment on secret change
```

**Best Practices:**
- Rotate secrets regularly (30-90 days)
- Use dynamic secrets when possible
- Test rotation in non-prod first
- Monitor applications after rotation
- Keep old secrets for grace period

### Access Control and Audit

**Vault Policies (ACL):**
```hcl
# Development team policy
path "secret/data/development/*" {
  capabilities = ["read", "list"]
}

# Production admin policy
path "secret/data/production/*" {
  capabilities = ["create", "read", "update", "delete", "list"]
}

# App policy (most restrictive)
path "secret/data/production/myapp" {
  capabilities = ["read"]
}
```

**Audit Logging:**
```json
{
  "time": "2026-01-15T10:30:00Z",
  "type": "request",
  "auth": {
    "display_name": "myapp-pod",
    "policies": ["myapp-prod"]
  },
  "request": {
    "operation": "read",
    "path": "secret/data/production/database"
  }
}
```

**Vault Path Structure:**
```
secret/
├── development/
│   ├── database/
│   │   ├── username: "dev_user"
│   │   └── password: "dev_pass"
│   └── api/
│       └── key: "dev_key"
├── staging/
│   ├── database/
│   │   ├── username: "staging_user"
│   │   └── password: "staging_pass"
│   └── api/
│       └── key: "staging_key"
└── production/
    ├── database/
    │   ├── username: "prod_user"
    │   └── password: "prod_pass"
    └── api/
        └── key: "prod_key"
```
