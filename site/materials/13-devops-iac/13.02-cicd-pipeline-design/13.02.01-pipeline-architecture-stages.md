## Introduction

A well-designed CI/CD pipeline is the backbone of modern software delivery. Pipelines automate the journey from code commit to production deployment, providing fast feedback, consistent builds, and reliable releases. Understanding pipeline architecture—how to organize stages, implement gates, and design for speed and safety—is essential for effective DevOps practices.

This lesson explores the fundamental architecture of CI/CD pipelines, the stages that compose them, and the gates that ensure quality at each step.

## Key Concepts Summary

### What is a CI/CD Pipeline?

A CI/CD pipeline automates the software delivery process from code commit to production deployment.

```
Code Commit → Build → Test → Deploy → Monitor
     ↓          ↓       ↓       ↓         ↓
   Trigger   Compile  Verify  Release  Observe
```

**Three related concepts:**

1. **Continuous Integration (CI):** Code changes are frequently merged into the main branch with automated build and test processes
2. **Continuous Delivery (CD):** Code passing CI is automatically published to production-like environments, ready for manual deployment
3. **Continuous Deployment:** Changes automatically deploy to production after passing all stages

```csharp
// Example: Triggering a pipeline on commit
// .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]  # Trigger on every commit to main
  pull_request:
    branches: [main]  # And on pull requests

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v3
        
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: '8.0'
          
      - name: Build
        run: dotnet build --configuration Release
        
      - name: Test
        run: dotnet test --no-build --configuration Release
```

### Pipeline Stages

Stages organize the pipeline into logical phases, executed sequentially or in parallel.

#### Common Pipeline Stages

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   Source    │ →   │    Build    │ →   │    Test     │ →   │   Deploy    │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
      ↓                    ↓                    ↓                    ↓
  Checkout           Compile            Unit Tests          Staging
  Dependencies       Package            Integration         Production
                     Artifacts          Security
```

#### Stage 1: Source

**Purpose:** Retrieve code and dependencies

**Activities:**
- Checkout code from version control
- Fetch dependencies and libraries
- Set up build environment

```yaml
# Example: Source stage
source:
  stage: source
  script:
    - git clone https://github.com/org/repo.git
    - cd repo
    - git checkout $CI_COMMIT_SHA
```

#### Stage 2: Build

**Purpose:** Compile code and create artifacts

**Activities:**
- Compile source code
- Run static analysis
- Create build artifacts (binaries, containers)
- Version artifacts

```csharp
// Build stage produces artifacts
public class BuildStage
{
    public async Task<BuildArtifact> ExecuteAsync()
    {
        // Compile code
        await _compiler.CompileAsync("src/");
        
        // Run static analysis
        var analysisResults = await _analyzer.AnalyzeAsync();
        if (analysisResults.HasCriticalIssues)
        {
            throw new BuildFailedException("Critical issues found");
        }
        
        // Package artifact
        var version = GenerateVersion();
        var artifact = await _packager.CreateArtifactAsync(version);
        
        // Upload to artifact repository
        await _repository.UploadAsync(artifact);
        
        return artifact;
    }
}
```

#### Stage 3: Test

**Purpose:** Verify code quality and functionality

**Activities:**
- Run unit tests
- Run integration tests
- Execute security scans
- Perform performance tests

```yaml
# Example: Test stage with parallel jobs
test:
  stage: test
  parallel:
    matrix:
      - TEST_TYPE: [unit, integration, security]
  script:
    - |
      case $TEST_TYPE in
        unit)
          dotnet test --filter Category=Unit
          ;;
        integration)
          dotnet test --filter Category=Integration
          ;;
        security)
          dotnet list package --vulnerable
          ;;
      esac
```

#### Stage 4: Deploy

**Purpose:** Release artifacts to target environments

**Activities:**
- Deploy to staging
- Run smoke tests
- Deploy to production (manual or automatic)
- Verify health

```csharp
// Example: Deployment stage with health checks
public class DeploymentStage
{
    public async Task ExecuteAsync(BuildArtifact artifact, Environment env)
    {
        // Deploy artifact
        await _deployer.DeployAsync(artifact, env);
        
        // Wait for application to start
        await Task.Delay(TimeSpan.FromSeconds(30));
        
        // Run health checks
        var healthy = await _healthChecker.IsHealthyAsync(env);
        if (!healthy)
        {
            // Rollback on failure
            await _deployer.RollbackAsync(env);
            throw new DeploymentFailedException("Health checks failed");
        }
        
        // Run smoke tests
        await _smokeTests.RunAsync(env);
    }
}
```

### Quality Gates and Approval Gates

**Gates** are checkpoints that control progression between stages.

#### Quality Gates (Automated)

Automated checks that must pass before proceeding:

```
Build Stage → [Quality Gate] → Test Stage
                    ↓
              Check if:
              - Build succeeded
              - No compilation errors
              - Code coverage > 80%
              - No critical security issues
```

**Implementation example:**

```csharp
// Quality gate implementation
public class QualityGate
{
    public async Task<bool> EvaluateAsync(BuildResult result)
    {
        var checks = new List<QualityCheck>
        {
            new CodeCoverageCheck(minimumCoverage: 0.80),
            new SecurityVulnerabilityCheck(allowCritical: false),
            new CodeComplexityCheck(maximumComplexity: 15),
            new DuplicationCheck(maximumDuplication: 0.05)
        };
        
        foreach (var check in checks)
        {
            if (!await check.PassesAsync(result))
            {
                _logger.LogError("Quality gate failed: {CheckName}", check.Name);
                return false;
            }
        }
        
        return true;
    }
}
```

**Common quality gate criteria:**
- **Code coverage:** Minimum percentage of code tested
- **Test results:** All tests must pass
- **Security scan:** No critical vulnerabilities
- **Code quality:** Complexity and duplication thresholds
- **Performance:** Response time benchmarks

#### Approval Gates (Manual)

Manual checkpoints requiring human authorization:

```
Staging Deploy → [Approval Gate] → Production Deploy
                       ↓
                 Required:
                 - QA approval
                 - Product owner sign-off
                 - Compliance review
```

**When to use manual approvals:**
- Production deployments (especially early in DevOps journey)
- Compliance-regulated changes
- High-risk deployments
- Major version releases

```yaml
# Example: Manual approval gate
deploy-production:
  stage: deploy
  environment:
    name: production
    approval: required  # Manual approval needed
  script:
    - ./deploy.sh production
  only:
    - main
```

### Pipeline Design Best Practices

#### 1. Fail Fast

**Principle:** Put fastest, most likely to fail stages first

```
Source (30s) → Build (2m) → Unit Tests (3m) → Integration Tests (10m) → Deploy (15m)
                                ↑
                          Fail here most often
                          Saves 25 minutes if test fails
```

#### 2. Parallelize When Possible

**Principle:** Run independent tasks concurrently

```
                    ┌──→ Unit Tests ──┐
Build ──→ Artifact  │                 │──→ Package
                    └──→ Lint/SAST ───┘
```

```yaml
# Example: Parallel execution
test:
  stage: test
  needs: [build]  # Run after build completes
  parallel:
    matrix:
      - TEST_SUITE: [unit, integration, e2e]
  script:
    - npm run test:$TEST_SUITE
```

#### 3. Keep Pipelines Fast

**Goal:** Provide feedback in < 10 minutes for CI pipeline

**Strategies:**
- Cache dependencies
- Use incremental builds
- Parallelize tests
- Optimize Docker layers
- Use appropriate instance sizes

```csharp
// Example: Caching for speed
public class BuildOptimizer
{
    public async Task<BuildResult> BuildWithCacheAsync()
    {
        // Check cache first
        var cacheKey = GenerateCacheKey();
        var cached = await _cache.GetAsync(cacheKey);
        
        if (cached != null)
        {
            _logger.LogInformation("Using cached build");
            return cached;
        }
        
        // Build and cache
        var result = await _builder.BuildAsync();
        await _cache.SetAsync(cacheKey, result, TimeSpan.FromHours(24));
        
        return result;
    }
}
```

#### 4. Make Pipelines Idempotent

**Principle:** Running the same pipeline multiple times produces the same result

```csharp
// Bad: Pipeline depends on external state
public async Task DeployAsync()
{
    var version = await _api.GetLatestVersionAsync();  // Changes over time!
    await _deployer.DeployAsync(version);
}

// Good: Pipeline is deterministic
public async Task DeployAsync(string commitSha)
{
    var artifact = await _repository.GetArtifactAsync(commitSha);
    await _deployer.DeployAsync(artifact);
}
```

#### 5. Provide Clear Feedback

**Principle:** Failures should be immediately obvious with actionable information

```csharp
// Example: Clear failure messages
public class TestResultReporter
{
    public void ReportFailure(TestResult result)
    {
        var message = $@"
❌ Tests Failed in {result.Stage}

Failed Tests: {result.FailedCount}/{result.TotalCount}

Top Failures:
{string.Join("\n", result.FailedTests.Take(5).Select(t => $"  • {t.Name}: {t.Error}"))}

View full report: {result.ReportUrl}
Commit: {result.CommitSha}
Branch: {result.Branch}
";
        
        _notifier.NotifyTeam(message);
    }
}
```

#### 6. Separate Build and Deploy

**Principle:** Build once, deploy many times

```
Build Artifact → Deploy to Dev → Deploy to Staging → Deploy to Production
      ↓             ↓                  ↓                      ↓
   app:1.2.3    app:1.2.3          app:1.2.3           app:1.2.3
               (same artifact)    (same artifact)     (same artifact)
```

This ensures what you test is exactly what you deploy.

## Common Pipeline Patterns

### Pattern 1: Simple CI Pipeline

```yaml
stages:
  - build
  - test

build:
  stage: build
  script:
    - dotnet build

test:
  stage: test
  script:
    - dotnet test
```

**Use case:** Small projects, proof of concepts

### Pattern 2: Multi-Environment CD Pipeline

```yaml
stages:
  - build
  - test
  - deploy-staging
  - deploy-production

build:
  stage: build
  script:
    - dotnet publish -o ./artifacts

test:
  stage: test
  script:
    - dotnet test

deploy-staging:
  stage: deploy-staging
  script:
    - ./deploy.sh staging
  environment: staging

deploy-production:
  stage: deploy-production
  script:
    - ./deploy.sh production
  environment: production
  when: manual  # Require approval
```

**Use case:** Production applications with staging environment

### Pattern 3: Trunk-Based with Feature Flags

```yaml
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Build
        run: dotnet build
      - name: Test
        run: dotnet test
      - name: Deploy to Production
        run: ./deploy.sh production
        # New features hidden behind feature flags
        # No need for long-lived branches
```

**Use case:** High-velocity teams practicing continuous deployment

## Key Takeaways

1. **CI/CD pipelines automate the delivery process**—from code commit through testing to deployment, providing fast feedback and consistent releases.

2. **Stages organize pipelines logically**—source, build, test, and deploy stages each serve specific purposes and run sequentially or in parallel.

3. **Quality gates ensure code quality**—automated checks enforce standards before code progresses, while approval gates add manual controls for high-risk stages.

4. **Design for speed and reliability**—fail fast, parallelize tasks, cache dependencies, and provide clear feedback to developers.

5. **Build once, deploy many**—create artifacts once and deploy the same artifact across all environments to ensure consistency.
