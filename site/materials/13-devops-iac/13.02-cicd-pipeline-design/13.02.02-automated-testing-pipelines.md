## Introduction

Automated testing is the cornerstone of effective CI/CD pipelines. Tests provide fast, reliable feedback about code quality, catching bugs before they reach production. A well-designed testing strategy balances comprehensive coverage with execution speed, enabling teams to deploy confidently and frequently.

This lesson explores the types of automated tests, how to organize them in pipelines, and best practices for test automation that enables rapid, safe delivery.

## Key Concepts Summary

### The Testing Pyramid

The testing pyramid guides test distribution in CI/CD pipelines:

```
                    ▲
                   ╱ ╲
                  ╱ E2E╲          ← Few, slow, expensive
                 ╱───────╲           (UI/acceptance tests)
                ╱         ╲
               ╱Integration╲      ← Some, medium speed
              ╱─────────────╲       (API/service tests)
             ╱               ╲
            ╱      Unit       ╲   ← Many, fast, cheap
           ╱___________________╲    (function/class tests)
```

**Principle:** More tests at the bottom (fast, isolated), fewer at the top (slow, integrated)

**Why this matters:**
- **Unit tests** (70%): Fast feedback (seconds), pinpoint failures
- **Integration tests** (20%): Medium feedback (minutes), verify component interaction
- **E2E tests** (10%): Slow feedback (minutes to hours), validate user workflows

```csharp
// Example: Testing pyramid in practice
namespace MyApp.Tests
{
    // Unit tests: Fast, isolated, many
    public class OrderCalculatorTests
    {
        [Fact]
        public void CalculateTotal_WithValidItems_ReturnsCorrectSum()
        {
            // Arrange
            var calculator = new OrderCalculator();
            var items = new[] { 10.0m, 20.0m, 30.0m };
            
            // Act
            var total = calculator.CalculateTotal(items);
            
            // Assert
            Assert.Equal(60.0m, total);
        }
        // Runs in milliseconds
    }
    
    // Integration tests: Medium speed, few external dependencies
    public class OrderServiceIntegrationTests
    {
        [Fact]
        public async Task CreateOrder_WithValidData_SavesToDatabase()
        {
            // Arrange
            var service = CreateServiceWithTestDatabase();
            var order = new Order { CustomerId = 1, Items = CreateTestItems() };
            
            // Act
            var result = await service.CreateOrderAsync(order);
            
            // Assert
            Assert.NotNull(result.Id);
            var saved = await service.GetOrderAsync(result.Id);
            Assert.Equal(order.CustomerId, saved.CustomerId);
        }
        // Runs in seconds
    }
    
    // E2E tests: Slow, full system validation
    public class CheckoutE2ETests
    {
        [Fact]
        public async Task CompleteCheckout_AsNewCustomer_CreatesOrderAndSendsEmail()
        {
            // Arrange
            var browser = await LaunchBrowserAsync();
            
            // Act
            await browser.GoToAsync("https://app.example.com");
            await browser.ClickAsync("#add-to-cart");
            await browser.FillAsync("#email", "test@example.com");
            await browser.ClickAsync("#checkout");
            
            // Assert
            await browser.ExpectAsync("Order confirmed");
            var email = await GetLastEmailAsync("test@example.com");
            Assert.Contains("Order confirmation", email.Subject);
        }
        // Runs in minutes
    }
}
```

### Types of Tests in CI/CD Pipelines

#### 1. Unit Tests

**Purpose:** Verify individual components in isolation

**Characteristics:**
- Fast execution (milliseconds to seconds)
- No external dependencies (mock/stub them)
- High code coverage target (70-90%)
- Run on every commit

```csharp
// Example: Unit test with mocked dependencies
public class PaymentServiceTests
{
    [Fact]
    public async Task ProcessPayment_WithValidCard_ReturnsSuccess()
    {
        // Arrange
        var mockGateway = new Mock<IPaymentGateway>();
        mockGateway
            .Setup(g => g.ChargeAsync(It.IsAny<Payment>()))
            .ReturnsAsync(new PaymentResult { Success = true });
        
        var service = new PaymentService(mockGateway.Object);
        var payment = new Payment { Amount = 100.0m, CardNumber = "4111111111111111" };
        
        // Act
        var result = await service.ProcessPaymentAsync(payment);
        
        // Assert
        Assert.True(result.Success);
        mockGateway.Verify(g => g.ChargeAsync(payment), Times.Once);
    }
}
```

**Pipeline integration:**
```yaml
unit-tests:
  stage: test
  script:
    - dotnet test --filter Category=Unit --logger "console;verbosity=detailed"
  artifacts:
    reports:
      junit: test-results/unit-tests.xml
```

#### 2. Integration Tests

**Purpose:** Verify that components work together correctly

**Characteristics:**
- Medium execution time (seconds to minutes)
- Use real dependencies (databases, APIs) in test environment
- Test API contracts and data flows
- Run after unit tests pass

```csharp
// Example: Integration test with real database
[Collection("Database")]
public class OrderRepositoryIntegrationTests : IAsyncLifetime
{
    private readonly IDbConnection _connection;
    
    public async Task InitializeAsync()
    {
        // Set up test database
        await _connection.ExecuteAsync("DELETE FROM Orders");
    }
    
    [Fact]
    public async Task SaveOrder_WithValidData_PersistsToDatabase()
    {
        // Arrange
        var repository = new OrderRepository(_connection);
        var order = new Order
        {
            CustomerId = 123,
            Total = 99.99m,
            CreatedAt = DateTime.UtcNow
        };
        
        // Act
        await repository.SaveAsync(order);
        
        // Assert
        var saved = await repository.GetByIdAsync(order.Id);
        Assert.NotNull(saved);
        Assert.Equal(order.CustomerId, saved.CustomerId);
        Assert.Equal(order.Total, saved.Total);
    }
    
    public async Task DisposeAsync()
    {
        // Clean up
        await _connection.ExecuteAsync("DELETE FROM Orders");
    }
}
```

**Pipeline integration:**
```yaml
integration-tests:
  stage: test
  services:
    - postgres:15  # Spin up test database
  variables:
    DATABASE_URL: "postgres://test:test@postgres/testdb"
  script:
    - dotnet test --filter Category=Integration
  dependencies:
    - unit-tests  # Run after unit tests
```

#### 3. Security Tests

**Purpose:** Identify vulnerabilities and security issues

**Types:**
- **SAST (Static Application Security Testing):** Analyze source code
- **DAST (Dynamic Application Security Testing):** Test running application
- **Dependency scanning:** Check for vulnerable packages

```yaml
# Example: Security scanning in pipeline
security-scan:
  stage: test
  parallel:
    matrix:
      - SCAN_TYPE: [sast, dependency, secret]
  script:
    - |
      case $SCAN_TYPE in
        sast)
          # Static analysis
          dotnet tool run security-scan analyze
          ;;
        dependency)
          # Check for vulnerable packages
          dotnet list package --vulnerable --include-transitive
          ;;
        secret)
          # Scan for secrets in code
          trufflehog git file://. --json
          ;;
      esac
  allow_failure: false  # Block pipeline if vulnerabilities found
```

```csharp
// Example: Security test
public class SecurityTests
{
    [Fact]
    public void Configuration_DoesNotContainSecrets()
    {
        // Arrange
        var config = LoadConfiguration();
        
        // Act & Assert
        Assert.DoesNotContain("password=", config.ConnectionString);
        Assert.DoesNotContain("secret", config.ApiKey.ToLower());
        Assert.True(config.UseEncryption, "Encryption must be enabled");
    }
    
    [Fact]
    public async Task Api_RequiresAuthentication()
    {
        // Arrange
        var client = new HttpClient();
        
        // Act
        var response = await client.GetAsync("https://api.example.com/orders");
        
        // Assert
        Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
    }
}
```

#### 4. Performance Tests

**Purpose:** Ensure application meets performance requirements

**Characteristics:**
- Measure response times, throughput, resource usage
- Run against production-like environment
- May run less frequently (nightly, weekly)

```csharp
// Example: Performance test
public class PerformanceTests
{
    [Fact]
    public async Task GetOrders_Under100Concurrent_RespondsWithin500ms()
    {
        // Arrange
        var client = CreateTestClient();
        var concurrentRequests = 100;
        
        // Act
        var stopwatch = Stopwatch.StartNew();
        var tasks = Enumerable.Range(0, concurrentRequests)
            .Select(_ => client.GetAsync("/api/orders"))
            .ToList();
        
        var results = await Task.WhenAll(tasks);
        stopwatch.Stop();
        
        // Assert
        Assert.All(results, r => Assert.True(r.IsSuccessStatusCode));
        var avgResponseTime = stopwatch.ElapsedMilliseconds / concurrentRequests;
        Assert.True(avgResponseTime < 500, 
            $"Average response time {avgResponseTime}ms exceeds 500ms threshold");
    }
}
```

#### 5. Acceptance/E2E Tests

**Purpose:** Validate complete user workflows from UI

**Characteristics:**
- Slowest execution (minutes per test)
- Test through browser or API
- Focus on critical user journeys
- Run fewer tests (5-10 key flows)

```csharp
// Example: E2E test with Playwright
public class CheckoutE2ETests
{
    private IBrowser _browser;
    private IPage _page;
    
    [Fact]
    public async Task CompleteCheckoutFlow_AsRegisteredUser_SuccessfullyCreatesOrder()
    {
        // Arrange
        await _page.GotoAsync("https://staging.example.com");
        
        // Act - Login
        await _page.ClickAsync("text=Login");
        await _page.FillAsync("#email", "test@example.com");
        await _page.FillAsync("#password", "TestPassword123!");
        await _page.ClickAsync("button[type=submit]");
        
        // Act - Add to cart
        await _page.ClickAsync("text=Shop");
        await _page.ClickAsync(".product-card:first-child >> text=Add to Cart");
        
        // Act - Checkout
        await _page.ClickAsync("text=Cart");
        await _page.ClickAsync("text=Checkout");
        await _page.FillAsync("#card-number", "4111111111111111");
        await _page.FillAsync("#cvv", "123");
        await _page.ClickAsync("text=Place Order");
        
        // Assert
        await _page.WaitForSelectorAsync("text=Order Confirmed");
        var orderNumber = await _page.TextContentAsync(".order-number");
        Assert.Matches(@"ORD-\d{6}", orderNumber);
    }
}
```

### Test Organization in Pipelines

#### Sequential Execution (Fail Fast)

```yaml
stages:
  - test:unit        # Fast: 2 minutes
  - test:integration # Medium: 5 minutes
  - test:e2e         # Slow: 15 minutes

# If unit tests fail, stop immediately (save 20 minutes)
```

#### Parallel Execution (Speed)

```yaml
test:
  stage: test
  parallel:
    matrix:
      - TEST_TYPE: [unit, integration, security]
      - PLATFORM: [linux, windows]
  script:
    - run-tests-$TEST_TYPE-$PLATFORM
    
# Run all combinations in parallel: 6 jobs simultaneously
```

#### Conditional Execution (Optimize)

```yaml
unit-tests:
  stage: test
  script:
    - dotnet test --filter Category=Unit
  # Always run

integration-tests:
  stage: test
  script:
    - dotnet test --filter Category=Integration
  only:
    - main
    - merge_requests
  # Only on important branches

e2e-tests:
  stage: test
  script:
    - npm run test:e2e
  only:
    - main
  when: manual  # Manual trigger or scheduled
```

### Quality Gates with Test Results

```csharp
// Example: Enforcing quality gates based on test results
public class QualityGateEvaluator
{
    public async Task<GateResult> EvaluateTestResultsAsync(TestRun testRun)
    {
        var gates = new List<IGate>
        {
            new TestPassRateGate(minimumPassRate: 1.0),      // 100% tests must pass
            new CodeCoverageGate(minimumCoverage: 0.80),      // 80% coverage required
            new SecurityVulnerabilityGate(allowCritical: false), // No critical vulnerabilities
            new PerformanceGate(maxResponseTime: 500)         // < 500ms response time
        };
        
        var results = new List<GateEvaluation>();
        
        foreach (var gate in gates)
        {
            var result = await gate.EvaluateAsync(testRun);
            results.Add(result);
            
            if (!result.Passed)
            {
                _logger.LogError("Quality gate failed: {Gate}", gate.Name);
            }
        }
        
        var allPassed = results.All(r => r.Passed);
        
        return new GateResult
        {
            Passed = allPassed,
            Evaluations = results,
            Message = allPassed 
                ? "All quality gates passed" 
                : $"{results.Count(r => !r.Passed)} quality gate(s) failed"
        };
    }
}
```

### Best Practices for Test Automation

#### 1. Keep Tests Fast

```csharp
// Bad: Slow test with unnecessary delays
[Fact]
public async Task SlowTest()
{
    await Task.Delay(5000);  // Don't do this!
    var result = await _service.DoSomethingAsync();
    Assert.True(result);
}

// Good: Fast test with proper async patterns
[Fact]
public async Task FastTest()
{
    var result = await _service.DoSomethingAsync();
    Assert.True(result);
}
```

#### 2. Make Tests Reliable (No Flaky Tests)

```csharp
// Bad: Flaky test with race conditions
[Fact]
public async Task FlakyTest()
{
    _service.StartBackgroundJob();
    await Task.Delay(1000);  // Hope job finishes in 1 second
    var result = _service.GetResult();
    Assert.NotNull(result);  // Sometimes fails!
}

// Good: Deterministic test
[Fact]
public async Task ReliableTest()
{
    var completion = _service.StartBackgroundJob();
    await completion;  // Wait for actual completion
    var result = _service.GetResult();
    Assert.NotNull(result);  // Always passes or fails consistently
}
```

#### 3. Isolate Tests

```csharp
// Bad: Tests depend on each other
public class OrderTests
{
    private static Order _sharedOrder;  // Don't do this!
    
    [Fact]
    public void Test1_CreateOrder()
    {
        _sharedOrder = new Order { Id = 1 };
    }
    
    [Fact]
    public void Test2_UpdateOrder()  // Depends on Test1
    {
        _sharedOrder.Status = OrderStatus.Shipped;
    }
}

// Good: Independent tests
public class OrderTests
{
    [Fact]
    public void CreateOrder_WithValidData_ReturnsOrder()
    {
        var order = new Order { Id = 1 };
        Assert.NotNull(order);
    }
    
    [Fact]
    public void UpdateOrder_ToShipped_ChangesStatus()
    {
        var order = new Order { Id = 1, Status = OrderStatus.Pending };
        order.Status = OrderStatus.Shipped;
        Assert.Equal(OrderStatus.Shipped, order.Status);
    }
}
```

#### 4. Use Test Data Builders

```csharp
// Example: Test data builder pattern
public class OrderBuilder
{
    private int _customerId = 1;
    private List<OrderItem> _items = new();
    private decimal _total = 0;
    
    public OrderBuilder WithCustomer(int customerId)
    {
        _customerId = customerId;
        return this;
    }
    
    public OrderBuilder WithItem(string name, decimal price)
    {
        _items.Add(new OrderItem { Name = name, Price = price });
        _total += price;
        return this;
    }
    
    public Order Build()
    {
        return new Order
        {
            CustomerId = _customerId,
            Items = _items,
            Total = _total
        };
    }
}

// Usage in tests
[Fact]
public void Test_WithMultipleItems()
{
    var order = new OrderBuilder()
        .WithCustomer(123)
        .WithItem("Widget", 10.99m)
        .WithItem("Gadget", 24.99m)
        .Build();
    
    Assert.Equal(35.98m, order.Total);
}
```

## Key Takeaways

1. **Follow the testing pyramid**—many fast unit tests, fewer integration tests, minimal E2E tests for optimal feedback speed.

2. **Different test types serve different purposes**—unit tests catch logic errors, integration tests verify component interaction, E2E tests validate user workflows.

3. **Organize tests to fail fast**—run fastest tests first, parallelize when possible, and use conditional execution for expensive tests.

4. **Quality gates enforce standards**—use test results to automatically block bad code from progressing through the pipeline.

5. **Keep tests fast, reliable, and isolated**—slow or flaky tests undermine confidence and slow down delivery.
