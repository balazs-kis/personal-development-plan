## Introduction

Pipeline-as-Code treats CI/CD pipelines as source code—version controlled, reviewed, and tested just like application code. Combined with effective branching strategies, this approach enables teams to iterate on their delivery process while maintaining high-quality standards.

This lesson explores how to define pipelines declaratively, organize pipeline code effectively, and implement branching strategies that support continuous integration and deployment.

## Key Concepts Summary

### Pipeline-as-Code

**Definition:** Defining CI/CD pipelines in version-controlled configuration files rather than through UI clicks.

**Benefits:**
- **Version controlled:** Track changes, review history
- **Reviewable:** Code review pipeline changes
- **Portable:** Move pipelines between projects
- **Testable:** Validate pipeline syntax
- **Documentable:** Pipeline is self-documenting

```yaml
# Example: Simple pipeline-as-code in YAML
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  DOTNET_VERSION: '8.0'
  APP_NAME: 'my-application'

jobs:
  build:
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v3
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
      
      - name: Restore dependencies
        run: dotnet restore
      
      - name: Build
        run: dotnet build --configuration Release --no-restore
      
      - name: Test
        run: dotnet test --configuration Release --no-build --verbosity normal
      
      - name: Publish artifacts
        run: dotnet publish --configuration Release --output ./publish
      
      - name: Upload artifacts
        uses: actions/upload-artifact@v3
        with:
          name: ${{ env.APP_NAME }}-${{ github.sha }}
          path: ./publish
```

### Declarative vs Imperative Pipelines

**Declarative (What):** Describe the desired state

```yaml
# Declarative: What should happen
deploy:
  stage: deploy
  image: alpine:latest
  environment:
    name: production
    url: https://app.example.com
  script:
    - apk add --no-cache curl
    - curl -X POST $DEPLOY_WEBHOOK
```

**Imperative (How):** Specify exact steps

```bash
# Imperative: How to do it
#!/bin/bash
set -e

# Install dependencies
apk add --no-cache curl openssh-client

# Configure SSH
mkdir -p ~/.ssh
echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
chmod 600 ~/.ssh/id_rsa

# Copy files
scp -r ./dist/* user@server:/app

# Restart service
ssh user@server "systemctl restart myapp"
```

**Best practice:** Use declarative when possible; imperative for complex logic.

### Pipeline Organization Patterns

#### Pattern 1: Modular Jobs

```yaml
# Reusable job definitions
.build-template: &build-template
  stage: build
  image: mcr.microsoft.com/dotnet/sdk:8.0
  script:
    - dotnet build --configuration Release
  artifacts:
    paths:
      - ./bin/Release/

# Use template
build-api:
  <<: *build-template
  variables:
    PROJECT: "Api"

build-worker:
  <<: *build-template
  variables:
    PROJECT: "Worker"
```

#### Pattern 2: Reusable Workflows

```yaml
# .github/workflows/reusable-deploy.yml
name: Reusable Deploy

on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
      version:
        required: true
        type: string
    secrets:
      DEPLOY_TOKEN:
        required: true

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    
    steps:
      - name: Deploy version ${{ inputs.version }}
        run: |
          echo "Deploying to ${{ inputs.environment }}"
          ./deploy.sh ${{ inputs.environment }} ${{ inputs.version }}
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```

```yaml
# .github/workflows/main.yml
name: Main Pipeline

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: dotnet build
  
  deploy-staging:
    needs: build
    uses: ./.github/workflows/reusable-deploy.yml
    with:
      environment: staging
      version: ${{ github.sha }}
    secrets:
      DEPLOY_TOKEN: ${{ secrets.STAGING_DEPLOY_TOKEN }}
  
  deploy-production:
    needs: deploy-staging
    uses: ./.github/workflows/reusable-deploy.yml
    with:
      environment: production
      version: ${{ github.sha }}
    secrets:
      DEPLOY_TOKEN: ${{ secrets.PROD_DEPLOY_TOKEN }}
```

#### Pattern 3: Matrix Builds

```yaml
# Test across multiple configurations
test:
  strategy:
    matrix:
      os: [ubuntu-latest, windows-latest, macos-latest]
      dotnet-version: ['6.0', '7.0', '8.0']
      
  runs-on: ${{ matrix.os }}
  
  steps:
    - uses: actions/checkout@v3
    
    - name: Setup .NET ${{ matrix.dotnet-version }}
      uses: actions/setup-dotnet@v3
      with:
        dotnet-version: ${{ matrix.dotnet-version }}
    
    - name: Test
      run: dotnet test
```

### Trunk-Based Development

**Core principle:** Developers collaborate on code in a single branch ("trunk" or "main"), avoiding long-lived development branches.

```
Traditional Gitflow:
main ─────────────────────────────────────────
     ↘                                      ↗
      develop ──────────────────────────────
               ↘                  ↗
                feature-branch ───
                
Result: Merge conflicts, integration delays


Trunk-Based Development:
main ─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─
      ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓
   Frequent small commits directly to main
   OR short-lived feature branches (<1 day)

Result: Continuous integration, always releasable
```

---

### Trunk-Based Development Practices

#### For Small Teams (<10 developers)

**Commit directly to trunk:**

```bash
# Developer workflow
git checkout main
git pull origin main

# Make small change
# ... edit code ...

# Run tests locally
dotnet test

# Commit directly to main
git add .
git commit -m "feat: add order validation"
git push origin main

# CI/CD runs automatically
# - Build
# - Test
# - Deploy to dev
# - Deploy to staging (if tests pass)
# - Deploy to production (if approved)
```

**Key practices:**
- Commit at least once per day
- Run full build locally before pushing
- Keep changes small
- Use feature flags for incomplete features

```csharp
// Example: Feature flag for incomplete feature
public class OrderService
{
    public async Task<Order> CreateOrderAsync(OrderRequest request)
    {
        // New feature still in development
        if (await _featureFlags.IsEnabledAsync("express-checkout"))
        {
            // New code path (work in progress)
            return await CreateExpressOrderAsync(request);
        }
        
        // Existing code path (stable)
        return await CreateStandardOrderAsync(request);
    }
}
```

#### For Larger Teams (>10 developers)

**Short-lived feature branches for code review:**

```bash
# Developer workflow
git checkout main
git pull origin main

# Create short-lived branch
git checkout -b feature/add-payment-validation

# Make changes
# ... edit code ...

# Push for review
git push origin feature/add-payment-validation

# Create PR
gh pr create --title "Add payment validation" \
  --body "Adds validation for credit card payments"

# After approval (same day):
# - Merge to main
# - Delete branch immediately
```

**Rules for feature branches:**
- **Lifespan:** < 1 day (merge before end of workday)
- **Scope:** Small, focused changes
- **Integration:** Merge to main daily
- **Purpose:** Code review only (not long-term development)

```yaml
# Pipeline for feature branches
on:
  pull_request:
    branches: [main]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      # Run full CI checks
      - name: Build
        run: dotnet build
      
      - name: Test
        run: dotnet test
      
      - name: Code quality
        run: dotnet tool run sonarscanner
      
      # Require checks to pass before merge
```

### Branching Strategies Comparison

#### 1. Trunk-Based Development

```
✅ Best for: Continuous integration/deployment
✅ Team maturity: High (requires discipline)
✅ Release frequency: Daily or more
✅ CI/CD integration: Excellent
```

**Characteristics:**
- Single main branch
- Frequent small commits
- Feature flags for incomplete work
- Always releasable

#### 2. GitFlow

```
⚠️ Best for: Scheduled releases
⚠️ Team maturity: Medium
⚠️ Release frequency: Weekly to monthly
❌ CI/CD integration: Poor
```

**Characteristics:**
- Multiple long-lived branches (main, develop, release, hotfix)
- Complex merging process
- Environments often out of sync
- **Considered legacy for modern CI/CD**

```
main ────v1.0────────────────v1.1──────────
          ↘                    ↗
develop ────────────────────────────────────
             ↘          ↗
feature ──────────────
```

**Why GitFlow is problematic for CI/CD:**
- Long-lived branches cause merge conflicts
- Delayed integration
- Environments fall out of sync
- Requires hotfix branches (shouldn't be needed with CD)

#### 3. GitHub Flow

```
✅ Best for: Web applications, continuous deployment
✅ Team maturity: Medium to high
✅ Release frequency: Multiple times per day
✅ CI/CD integration: Excellent
```

**Characteristics:**
- Main branch + short-lived feature branches
- Everything in main is deployable
- Deploy from main frequently

```
main ─────┬───┬───┬───┬───┬───────
          ↓   ↓   ↓   ↓   ↓
       feature branches (short-lived)
```

### Pipeline Configuration Best Practices

#### 1. Keep Pipeline Files Simple

```yaml
# Good: Clear, readable pipeline
name: CI Pipeline

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: npm install
      - run: npm test

# Bad: Overly complex inline scripts
name: CI Pipeline

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: |
          if [ "$GITHUB_REF" == "refs/heads/main" ]; then
            npm install --production
            npm run build:prod
            # ... 50 more lines ...
          else
            npm install
            npm test
          fi
```

**Better approach:** Extract complex logic to scripts:

```yaml
# Pipeline file stays clean
name: CI Pipeline

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: ./scripts/ci-test.sh
```

#### 2. Use Environment Variables

```yaml
# Define once, use everywhere
env:
  DOTNET_VERSION: '8.0'
  NODE_VERSION: '20'
  CONTAINER_REGISTRY: 'ghcr.io'

jobs:
  build-backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/setup-dotnet@v3
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
  
  build-frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/setup-node@v3
        with:
          node-version: ${{ env.NODE_VERSION }}
```

#### 3. Fail Fast

```yaml
# Run fast tests first
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: npm run lint  # Fast: 30 seconds
  
  unit-test:
    needs: lint  # Only after lint passes
    runs-on: ubuntu-latest
    steps:
      - run: npm test  # Medium: 2 minutes
  
  integration-test:
    needs: unit-test  # Only after unit tests pass
    runs-on: ubuntu-latest
    steps:
      - run: npm run test:integration  # Slow: 10 minutes
```

#### 4. Cache Dependencies

```yaml
# Cache npm modules
- uses: actions/cache@v3
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-

# Cache NuGet packages
- uses: actions/cache@v3
  with:
    path: ~/.nuget/packages
    key: ${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}
    restore-keys: |
      ${{ runner.os }}-nuget-
```

#### 5. Use Conditional Execution

```yaml
# Only deploy from main branch
deploy:
  if: github.ref == 'refs/heads/main'
  runs-on: ubuntu-latest
  steps:
    - run: ./deploy.sh

# Only run expensive tests on main and PRs
expensive-tests:
  if: github.event_name == 'pull_request' || github.ref == 'refs/heads/main'
  runs-on: ubuntu-latest
  steps:
    - run: npm run test:e2e
```

### Real-World Example: Complete Pipeline-as-Code

```yaml
# .github/workflows/complete-pipeline.yml
name: Complete CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  DOTNET_VERSION: '8.0'
  APP_NAME: 'my-api'

jobs:
  # Stage 1: Build and Unit Test
  build-and-test:
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v3
        with:
          fetch-depth: 0
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
      
      - name: Cache NuGet packages
        uses: actions/cache@v3
        with:
          path: ~/.nuget/packages
          key: ${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}
      
      - name: Restore dependencies
        run: dotnet restore
      
      - name: Build
        run: dotnet build --configuration Release --no-restore
      
      - name: Run unit tests
        run: dotnet test --filter Category=Unit --no-build --configuration Release
      
      - name: Publish application
        run: dotnet publish --configuration Release --output ./publish
      
      - name: Upload artifacts
        uses: actions/upload-artifact@v3
        with:
          name: ${{ env.APP_NAME }}-${{ github.sha }}
          path: ./publish
          retention-days: 30
  
  # Stage 2: Integration Tests (only on PRs and main)
  integration-test:
    needs: build-and-test
    if: github.event_name == 'pull_request' || github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
    
    steps:
      - uses: actions/checkout@v3
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
      
      - name: Run integration tests
        run: dotnet test --filter Category=Integration
        env:
          DATABASE_URL: postgresql://postgres:test@postgres/testdb
  
  # Stage 3: Security Scan
  security-scan:
    needs: build-and-test
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v3
      
      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'fs'
          scan-ref: '.'
          severity: 'CRITICAL,HIGH'
  
  # Stage 4: Deploy to Staging (only from main)
  deploy-staging:
    needs: [build-and-test, integration-test, security-scan]
    if: github.ref == 'refs/heads/main'
    uses: ./.github/workflows/deploy.yml
    with:
      environment: staging
      version: ${{ github.sha }}
    secrets: inherit
  
  # Stage 5: Deploy to Production (manual approval)
  deploy-production:
    needs: deploy-staging
    uses: ./.github/workflows/deploy.yml
    with:
      environment: production
      version: ${{ github.sha }}
    secrets: inherit
```

## Key Takeaways

1. **Pipeline-as-Code enables version control and review**—treat pipeline configuration as source code for better collaboration and tracking.

2. **Trunk-based development supports continuous integration**—frequent small commits to main avoid merge conflicts and integration delays.

3. **GitFlow is legacy for modern CI/CD**—long-lived branches create environment sync issues and slow down delivery.

4. **Feature flags enable trunk-based development**—deploy incomplete features behind flags to keep main always releasable.

5. **Organize pipeline code for reusability**—use modular jobs, reusable workflows, and matrix builds to avoid duplication.
