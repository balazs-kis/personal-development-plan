- Persist data across container restarts
- Share data between containers

---

## Introduction

Containers are ephemeral by design—when you delete a container, its data is gone. Docker volumes provide a way to persist data outside the container lifecycle, enable data sharing between containers, and improve I/O performance. Understanding storage options is crucial for stateful applications like databases, file uploads, and development environments.

## Key Concepts Summary

### Docker Storage Options

```
┌──────────────────────────────────────────────┐
│         Docker Storage Options                │
├──────────────┬──────────────┬────────────────┤
│   Volumes    │ Bind Mounts  │    tmpfs       │
│ (Managed by  │ (Host path)  │  (Memory)      │
│   Docker)    │              │                │
└──────────────┴──────────────┴────────────────┘
```

| Feature | Volumes | Bind Mounts | tmpfs |
|---------|---------|-------------|-------|
| **Managed by** | Docker | User | Docker |
| **Host location** | `/var/lib/docker/volumes/` | User-specified | Memory |
| **Persistence** | Yes | Yes | No (RAM) |
| **Best for** | Production data | Development | Secrets, temp data |
| **Performance** | Good | Good | Excellent |
| **Cross-platform** | Yes | Limited | Linux only |

### 1. Volumes (Recommended)

**Volumes** are Docker-managed storage outside containers.

**Create a volume:**
```bash
docker volume create my-volume
```

**Use the volume:**
```bash
docker run -d \
  --name myapp \
  -v my-volume:/app/data \
  myapp:latest
```

**Why volumes are best:**
- ✅ Managed by Docker
- ✅ Easy to backup and migrate
- ✅ Work on all platforms
- ✅ Can be shared between containers
- ✅ Drivers for cloud storage
- ✅ Can be pre-populated

**Volume Commands:**
```bash
# List volumes
docker volume ls

# Inspect volume
docker volume inspect my-volume

# Remove volume
docker volume rm my-volume

# Remove unused volumes
docker volume prune

# Create volume with options
docker volume create \
  --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.1,rw \
  --opt device=:/path/to/dir \
  my-nfs-volume
```

### 2. Bind Mounts

**Bind mounts** map a host directory to a container directory.

```bash
docker run -d \
  --name dev-app \
  -v /path/on/host:/app \
  myapp:latest
```

**Use cases:**
- Development (live code reloading)
- Configuration files
- Sharing files between host and container

**Development Example:**
```bash
# Mount source code directory
docker run -d \
  --name dev-server \
  -v $(pwd)/src:/app/src \
  -v $(pwd)/package.json:/app/package.json \
  -p 3000:3000 \
  node:18 \
  npm run dev
```

**Read-only bind mount:**
```bash
docker run -v /host/config:/app/config:ro myapp
```

### 3. tmpfs Mounts

**tmpfs** stores data in host memory, never written to disk.

```bash
docker run -d \
  --name temp-app \
  --tmpfs /app/temp:rw,noexec,nosuid,size=100m \
  myapp:latest
```

**Use cases:**
- Sensitive data (passwords, keys)
- Temporary processing
- Build caches

### Volume vs Bind Mount Syntax

```bash
# Named volume
docker run -v my-volume:/app/data myapp

# Bind mount (absolute path)
docker run -v /host/path:/container/path myapp

# Bind mount (relative path with ${PWD})
docker run -v ${PWD}/data:/app/data myapp

# Tmpfs
docker run --tmpfs /app/temp myapp
```

### Dockerfile VOLUME Instruction

```dockerfile
FROM nginx:alpine
# Declare volume mount point
VOLUME /usr/share/nginx/html
VOLUME /var/log/nginx
```

**What it does:**
- Documents that the path contains important data
- Docker creates anonymous volume if none specified
- Helps users understand data persistence points

### Sharing Data Between Containers

**Approach 1: Named Volume**
```bash
# Create volume
docker volume create shared-data

# Container 1 writes
docker run -d --name writer \
  -v shared-data:/data \
  alpine sh -c "while true; do date >> /data/log.txt; sleep 5; done"

# Container 2 reads
docker run -it --rm \
  -v shared-data:/data \
  alpine tail -f /data/log.txt
```

**Approach 2: Volumes-from (Legacy)**
```bash
# Data container
docker run -v /data --name data-container alpine true

# Use data from another container
docker run --volumes-from data-container myapp
```

### Persistent Database Example

**PostgreSQL with volume:**
```bash
# Create volume for database data
docker volume create postgres-data

# Run PostgreSQL
docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=secret \
  -v postgres-data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:15

# Data persists even after container removal
docker rm -f postgres

# Restart with same volume
docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=secret \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:15
# Data is still there!
```

### Development Workflow Example

```bash
# Project structure
myapp/
├── src/
│   ├── index.js
│   └── routes/
├── package.json
└── Dockerfile

# Run with live reload
docker run -d \
  --name dev \
  -v $(pwd)/src:/app/src \
  -v $(pwd)/package.json:/app/package.json \
  -v /app/node_modules \
  -p 3000:3000 \
  myapp:latest \
  npm run dev
```

**Key pattern:**
- Mount source code for live updates
- Mount `package.json` for dependency changes
- **Don't** mount `node_modules` (use anonymous volume)

### Volume Backup and Restore

**Backup a volume:**
```bash
# Run temporary container to backup
docker run --rm \
  -v my-volume:/data \
  -v $(pwd):/backup \
  alpine \
  tar czf /backup/backup.tar.gz -C /data .
```

**Restore a volume:**
```bash
# Create new volume
docker volume create restored-volume

# Restore from backup
docker run --rm \
  -v restored-volume:/data \
  -v $(pwd):/backup \
  alpine \
  tar xzf /backup/backup.tar.gz -C /data
```

### Volume Drivers

Docker supports pluggable volume drivers:

**Local driver (default):**
```bash
docker volume create --driver local my-volume
```

**NFS driver:**
```bash
docker volume create \
  --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.100,rw \
  --opt device=:/path/to/share \
  nfs-volume
```

**Cloud drivers (AWS EBS, Azure Disk, etc.):**
```bash
docker volume create \
  --driver rexray/ebs \
  --opt size=10 \
  aws-volume
```

### Best Practices

**1. Use named volumes for production:**
```bash
# ✅ Good: named, manageable
docker run -v postgres-data:/var/lib/postgresql/data postgres

# ❌ Bad: anonymous volume
docker run -v /var/lib/postgresql/data postgres
```

**2. Use bind mounts for development:**
```bash
# ✅ Development: live code updates
docker run -v $(pwd)/src:/app/src myapp

# ❌ Production: don't use bind mounts
```

**3. Document volumes in Dockerfile:**
```dockerfile
# Declare important data directories
VOLUME ["/var/lib/mysql", "/etc/mysql/conf.d"]
```

**4. Don't mount sensitive paths:**
```bash
# ❌ Dangerous: entire root filesystem
docker run -v /:/host alpine

# ❌ Dangerous: Docker socket
docker run -v /var/run/docker.sock:/var/run/docker.sock alpine
```

**5. Use read-only mounts when possible:**
```bash
docker run -v /config:/app/config:ro myapp
```

**6. Clean up unused volumes:**
```bash
# List dangling volumes
docker volume ls -f dangling=true

# Remove unused volumes
docker volume prune
```

### Common Patterns

**Pattern 1: Application + Database**
```bash
# Create volumes
docker volume create app-data
docker volume create db-data

# Run database
docker run -d \
  --name db \
  -v db-data:/var/lib/postgresql/data \
  postgres:15

# Run app
docker run -d \
  --name app \
  -v app-data:/app/uploads \
  --link db:db \
  myapp:latest
```

**Pattern 2: Log Aggregation**
```bash
# Shared log volume
docker volume create logs

# App writes logs
docker run -d \
  -v logs:/var/log/app \
  myapp

# Log collector reads logs
docker run -d \
  -v logs:/logs:ro \
  fluentd
```

**Pattern 3: Configuration Management**
```bash
# Read-only config
docker run -d \
  -v $(pwd)/config.yml:/app/config.yml:ro \
  myapp
```

### Troubleshooting

**Check what volumes a container uses:**
```bash
docker inspect myapp --format='{{json .Mounts}}' | jq
```

**Find which container uses a volume:**
```bash
docker ps -a --filter volume=my-volume
```

**Volume permission issues:**
```bash
# Set ownership in Dockerfile
RUN chown -R appuser:appuser /app/data
VOLUME /app/data

# Or fix in entrypoint script
#!/bin/sh
chown -R appuser:appuser /app/data
exec su-exec appuser "$@"
```

**Mount disappeared data:**
```bash
# Check if volume exists
docker volume ls | grep my-volume

# Inspect volume
docker volume inspect my-volume

# Verify mount in container
docker exec myapp ls -la /app/data
```

## Key Takeaways

✅ **Volumes persist data beyond container lifecycle**
- Managed by Docker
- Stored in /var/lib/docker/volumes
- Survive container removal

✅ **Choose the right storage type**
- Volumes: Production data, managed by Docker
- Bind mounts: Development, need host access
- tmpfs: Temporary data, memory-backed

✅ **Named volumes are better than anonymous**
- Easy to reference and manage
- Clear purpose and ownership
- Easier backup and restore

✅ **Security and permissions matter**
- Use read-only mounts when appropriate
- Mind uid/gid mismatches
- Careful with host bind mounts

✅ **Backup and restore workflows**
- Use temporary containers for access
- Archive with tar
- Restore from backups reliably
