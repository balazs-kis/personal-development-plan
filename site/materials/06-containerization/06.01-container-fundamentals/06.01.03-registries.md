They are to containers what package repositories (npm, NuGet, Maven) are to software packages. Understanding registries is essential for any containerized workflow, from development to production deployment.

## Key Concepts Summary

### What is a Container Registry?

A container registry is a **storage and distribution system** for container images. It's the central hub of the container ecosystem, analogous to:
- **npm registry** for JavaScript packages
- **NuGet** for .NET packages
- **Maven Central** for Java libraries
- **PyPI** for Python packages

**Core Functions:**

1. **Storage**: Securely store container images and their layers
2. **Distribution**: Efficiently distribute images to deployment targets
3. **Versioning**: Manage multiple versions through tags
4. **Access Control**: Authenticate and authorize users/services
5. **Security**: Scan for vulnerabilities, enforce policies
6. **Content Trust**: Verify image integrity and authenticity

**What Registries Provide:**
- **Centralized storage** for images across teams
- **Version control** through tags and digests
- **Access control** and authentication (public/private repos)
- **Content trust** and image signing
- **Vulnerability scanning** for security
- **Distribution** to various environments (dev, staging, prod)
- **Webhooks** for CI/CD integration
- **Geo-replication** for global availability
- **Garbage collection** to manage storage costs

### Registry Hierarchy and Terminology

```
Registry (e.g., Docker Hub, ACR, ECR, GCR)
    └── Repository (e.g., mycompany/myapp)
            ├── Image:tag1 (e.g., myapp:1.0.0)
            ├── Image:tag2 (e.g., myapp:1.1.0)
            ├── Image:tag3 (e.g., myapp:latest)
            └── Image:tag4 (e.g., myapp:dev)
```

**Key Terms:**

- **Registry:** The service/platform hosting images
  - Examples: docker.io, azurecr.io, gcr.io
  - Can be public or private
  - Provides API for push/pull operations

- **Repository:** A collection of related images (same application)
  - Named: `nginx`, `mycompany/myapp`, `project/service`
  - Can have multiple tags
  - Separate repositories even within same registry

- **Tag:** A version label for a specific image
  - Examples: `1.0`, `latest`, `v2.1.3-alpine`, `dev`, `prod`
  - Mutable: can be moved to point to different image
  - User-friendly labels

- **Digest:** Immutable content hash (SHA-256)
  - Example: `sha256:abc123def456...`
  - Never changes
  - Guarantees exact image version

- **Manifest:** JSON document describing image contents
  - References to all layers
  - Configuration
  - Architecture/OS information

### Image Naming Convention

Full image name format (Fully Qualified Image Name):

```
[registry-host[:port]]/[namespace/][repository][:tag][@digest]
```

**Component Breakdown:**

```
myregistry.azurecr.io/myteam/myapp:v1.2.3
│                     │      │      │
│                     │      │      └─ Tag (version)
│                     │      └──────── Repository (app name)
│                     └────────────── Namespace (team/project)
└──────────────────────────────────── Registry host
```

**Examples with Explanations:**

```bash
# Docker Hub (default registry, library namespace)
nginx:latest
# Full: docker.io/library/nginx:latest

# Docker Hub (user namespace)
myusername/myapp:1.0
# Full: docker.io/myusername/myapp:1.0

# Azure Container Registry
myregistry.azurecr.io/myapp:prod
myregistry.azurecr.io/team-a/service-x:v2.1.0

# Amazon ECR
123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:v2.0
123456789012.dkr.ecr.us-west-2.amazonaws.com/frontend:latest

# Google Container Registry / Artifact Registry
gcr.io/my-project/myapp:staging
us-docker.pkg.dev/my-project/my-repo/myapp:v1.0

# GitHub Container Registry
ghcr.io/myorganization/myapp:main

# Custom private registry
registry.company.com:5000/department/app:1.0.0
```

**Default Behavior:**
- No registry specified → defaults to `docker.io`
- No tag specified → defaults to `:latest`
- No namespace specified → defaults to `library` (Docker Hub official images)

```bash
# These are equivalent:
docker pull nginx
docker pull docker.io/library/nginx:latest
```

### Public vs Private Registries

#### Public Registries

Public registries host images accessible to anyone. They're ideal for open-source projects and sharing images publicly.

**Docker Hub (docker.io)**
- **Largest public registry** (millions of images)
- **Official images:** Curated by Docker (nginx, postgres, redis, mysql, node, python, etc.)
- **Verified publishers:** Images from trusted organizations
- **Community images:** User-contributed images
- **Free tier:** Unlimited public repos, limited private repos
- **Rate limiting:** 100 pulls/6 hours for anonymous, 200 for authenticated free users
- **Web UI:** Browse, search, documentation

**Usage:**
```bash
# Pull official image
docker pull nginx

# Pull community image
docker pull username/custom-app

# Search for images
docker search postgres
```

**GitHub Container Registry (ghcr.io)**
- **Integrated with GitHub:** Tight CI/CD integration
- **Free for public images:** No rate limits
- **GitHub Actions integration:** Easy automated builds
- **Package linking:** Associate with repositories
- **Fine-grained permissions:** GitHub-based access control

**Usage:**
```bash
# Pull from GHCR
docker pull ghcr.io/owner/repo/image:tag

# Login with GitHub token
echo $CR_PAT | docker login ghcr.io -u USERNAME --password-stdin
```

**Quay.io**
- **Red Hat's registry** (now part of Red Hat)
- **Security scanning:** Built-in vulnerability detection
- **Both public and private:** Flexible options
- **Container security:** Advanced security features
- **Build triggers:** Automated builds on git push

**Other Public Registries:**
- **DockerHub alternatives:** GitLab Container Registry, Canister.io
- **Language-specific:** Some ecosystems have specialized registries

**Characteristics of Public Registries:**
| Aspect | Details |
|--------|---------|
| ✅ **Advantages** | Free for public images, easy sharing, large community |
| ✅ **Discovery** | Search functionality, browse popular images |
| ✅ **Open Source** | Perfect for OSS projects |
| ❌ **Security** | Anyone can publish (verify sources!) |
| ❌ **Rate Limits** | Pull limits on free tiers |
| ❌ **Privacy** | Images visible to everyone |

#### Private Registries

Private registries require authentication and provide enterprise features for secure, controlled image distribution.

**Cloud Provider Registries:**

**Azure Container Registry (ACR)**
- **Fully managed:** Microsoft Azure service
- **Geo-replication:** Global distribution
- **Security:** Azure AD integration, network isolation
- **Vulnerability scanning:** With Azure Defender
- **Tiers:** Basic, Standard, Premium (different features/performance)
- **Tasks:** Build images in the cloud (ACR Tasks)

**Features:**
```bash
# Login to ACR
az acr login --name myregistry

# Push image
docker tag myapp:1.0 myregistry.azurecr.io/myapp:1.0
docker push myregistry.azurecr.io/myapp:1.0

# Import images between registries
az acr import --name myregistry --source sourceregistry.azurecr.io/myapp:1.0
```

**Amazon Elastic Container Registry (ECR)**
- **AWS-native:** Integrated with ECS, EKS, Lambda
- **IAM integration:** AWS Identity and Access Management
- **Image scanning:** Automated vulnerability scanning
- **Lifecycle policies:** Automatic cleanup
- **Encryption:** At rest and in transit

```bash
# Login
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456789012.dkr.ecr.us-east-1.amazonaws.com

# Push
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
```

**Google Artifact Registry / Container Registry**
- **Google Cloud:** Integrated with GKE, Cloud Run
- **Multi-format:** Docker, Maven, npm (Artifact Registry)
- **Vulnerability scanning:** Automatic
- **IAM:** Google Cloud IAM

```bash
# Login
gcloud auth configure-docker
gcloud auth configure-docker us-docker.pkg.dev

# Push
docker push gcr.io/my-project/myapp:1.0
docker push us-docker.pkg.dev/my-project/my-repo/myapp:1.0
```

**Self-Hosted Options:**

**Harbor** - CNCF graduated project with enterprise features
- RBAC, replication, quotas, vulnerability scanning (Trivy)
- Content trust (image signing), webhook support, multi-tenancy
- Also serves Helm charts

**Docker Registry (Open Source)** - Official, minimal implementation
- Lightweight, OCI-compliant, basic auth, storage drivers (S3, Azure, GCS)
- No UI (add frontend separately)

**GitLab Container Registry** - Integrated with GitLab CI/CD
- Project-level registry, GitLab credentials, free tier included

**JFrog Artifactory** - Universal registry (Docker + many formats)
- Enterprise features, HA, replication, commercial product

**Characteristics of Private Registries:**
| Aspect | Details |
|--------|---------|
| ✅ **Security** | Authentication required, fine-grained access control |
| ✅ **Compliance** | Meet regulatory requirements |
| ✅ **No rate limits** | (self-managed) unlimited pulls |
| ✅ **Control** | Full control over images and policies |
| ✅ **CI/CD integration** | Service principals, API keys |
| ❌ **Cost** | Paid service or infrastructure to maintain |
| ❌ **Maintenance** | Self-hosted requires ops overhead |

### Working with Registries

#### Authentication

Different registries have different auth mechanisms:

```bash
# Docker Hub
docker login
# Prompts for username/password

# Docker Hub with token
docker login -u username -p <access-token>

# Azure Container Registry (using Azure CLI)
az acr login --name myregistry
# OR with admin credentials
docker login myregistry.azurecr.io -u <username> -p <password>

# Amazon ECR (requires AWS CLI)
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456789012.dkr.ecr.us-east-1.amazonaws.com

# Google Container Registry / Artifact Registry
gcloud auth configure-docker
gcloud auth configure-docker us-docker.pkg.dev

# GitHub Container Registry (with PAT)
echo $GITHUB_TOKEN | docker login ghcr.io -u USERNAME --password-stdin

# Custom registry
docker login registry.company.com -u username -p password

# Logout
docker logout myregistry.azurecr.io
```

**Authentication Storage:**
Credentials stored in `~/.docker/config.json` (or Windows equivalent):
```json
{
  "auths": {
    "https://index.docker.io/v1/": {
      "auth": "base64encodedcredentials"
    },
    "myregistry.azurecr.io": {
      "auth": "base64encodedcredentials"
    }
  }
}
```

**Security Best Practices:**
- ✅ Use tokens/service principals, not passwords
- ✅ Rotate credentials regularly
- ✅ Use credential helpers (keychain integration)
- ✅ Never commit credentials to source control
- ✅ Use CI/CD secrets management

#### Pushing Images

Complete workflow for pushing images to a registry:

```bash
# Step 1: Build image with registry name in tag
docker build -t myregistry.azurecr.io/myapp:1.0 .

# OR Step 1: Build locally, then tag for registry
docker build -t myapp:1.0 .
docker tag myapp:1.0 myregistry.azurecr.io/myapp:1.0

# Step 2: Authenticate to registry (if not already)
az acr login --name myregistry

# Step 3: Push image to registry
docker push myregistry.azurecr.io/myapp:1.0

# Optional: Push multiple tags
docker tag myapp:1.0 myregistry.azurecr.io/myapp:latest
docker push myregistry.azurecr.io/myapp:latest

# Push all tags of an image
docker push --all-tags myregistry.azurecr.io/myapp
```

**Multi-Platform Push:**
```bash
# Build and push multi-platform image
docker buildx build --platform linux/amd64,linux/arm64 \
  -t myregistry.azurecr.io/myapp:1.0 \
  --push .
```

**What Happens During Push:**
1. Docker checks authentication
2. Uploads layers that don't exist in registry (skips existing ones)
3. Uploads image manifest
4. Creates/updates tag

**Efficiency:**
- Only new/changed layers uploaded
- Existing layers skipped (huge bandwidth savings)
- Parallel uploads for multiple layers

#### Pulling Images

```bash
# Pull from Docker Hub (default)
docker pull nginx:latest

# Pull from private registry
docker pull myregistry.azurecr.io/myapp:1.0

# Pull by digest (immutable)
docker pull nginx@sha256:abc123def456...

# Pull all tags (not recommended, use sparingly)
docker pull --all-tags myregistry.azurecr.io/myapp

# Pull and verify signature (Docker Content Trust)
export DOCKER_CONTENT_TRUST=1
docker pull myregistry.azurecr.io/myapp:1.0
```

**Pull Behavior:**
1. Docker checks if image exists locally
2. Compares local manifest with remote
3. Downloads missing layers
4. Verifies layer integrity (checksums)
5. Assembles image locally

**Layer Reuse:**
If base layers already exist locally (from other images), only new layers are downloaded.

### Registry Security Features

#### Image Vulnerability Scanning

Modern registries scan images for known security vulnerabilities (CVEs).

**How It Works:**
1. Image pushed → automatic scan initiated
2. Layers analyzed against vulnerability databases
3. Report generated: Critical / High / Medium / Low / Negligible
4. Policies can block deployment of vulnerable images

**Azure Container Registry:**
```bash
# View scan results
az acr show-vulnerabilities --name myregistry --repository myapp --tag 1.0
```

**Amazon ECR:**
```bash
# Enable scanning on push
aws ecr put-image-scanning-configuration \
  --repository-name myapp \
  --image-scanning-configuration scanOnPush=true
```

**Best Practices:**
- Enable automatic scanning on push
- Set up alerts for critical vulnerabilities
- Regularly rescan (new CVEs discovered daily)
- Keep base images updated

#### Content Trust and Image Signing

Ensures images haven't been tampered with.

**Docker Content Trust (DCT):**
```bash
# Enable DCT
export DOCKER_CONTENT_TRUST=1

# Push signed image
docker push myregistry.azurecr.io/myapp:1.0

# Pull verifies signature (fails if invalid)
docker pull myregistry.azurecr.io/myapp:1.0
```

**Cosign (Sigstore):**
```bash
# Sign image
cosign sign myregistry.azurecr.io/myapp:1.0

# Verify signature
cosign verify myregistry.azurecr.io/myapp:1.0
```

#### Access Control

**Role-Based Access Control (RBAC):**

**Azure Container Registry:**
```bash
# Assign roles (AcrPull, AcrPush, AcrDelete, Owner)
az role assignment create \
  --assignee user@company.com \
  --role AcrPush \
  --scope /subscriptions/.../registries/myregistry
```

**Amazon ECR:** Uses IAM policies for granular control

**Service Principals / Service Accounts:**

For CI/CD, use dedicated service accounts:

```bash
# Azure: Create service principal
az ad sp create-for-rbac --name myapp-ci --role AcrPush

# Use in CI/CD
docker login myregistry.azurecr.io -u <appId> -p <password>
```

**IP Filtering and Network Isolation:**

```bash
# Azure: Restrict by IP
az acr network-rule add --name myregistry --ip-address 203.0.113.0/24

# Azure: Private endpoints (VNet)
az acr private-endpoint-connection create ...
```

### Registry Best Practices

#### 1. Use Private Registries for Production

**Why:**
- Better security and control
- No rate limiting issues
- Compliance requirements
- Audit trails
- Fine-grained access control

**Implementation:**
```bash
# Bad: Pull from public registry in production
docker pull nginx:latest

# Good: Use internal registry with verified images
docker pull registry.company.com/verified/nginx:1.21.0
```

#### 2. Implement Image Scanning

**Policy Example:**
```
- Scan all images on push
- Block deployment if Critical vulnerabilities found
- Allow deployment with High vulnerabilities (with approval)
- Rescan images daily (new CVEs discovered)
- Alert security team on Critical findings
```

**Implementation:**
```bash
# Azure: Enable Defender scanning
az security auto-provisioning-setting update --auto-provision "On" --name "default"

# Amazon ECR: Enable scan on push
aws ecr put-image-scanning-configuration \
  --repository-name myapp \
  --image-scanning-configuration scanOnPush=true

# Harbor: Configure vulnerability policies
# UI: Administration → Vulnerability → Create Policy
```

#### 3. Use Specific Tags, Not `latest`

**Why `latest` is Problematic:**
- **Unpredictable:** Changes without warning
- **Not immutable:** Same tag, different image
- **Breaks reproducibility:** Can't recreate exact deployment
- **Hidden updates:** May pull breaking changes

**Best Practices:**

```dockerfile
# ❌ Bad: Unpredictable, changes over time
FROM node:latest

# ⚠️ Better: Major version, but still updates
FROM node:18

# ✅ Good: Specific version
FROM node:18.19.0

# ✅ Best: Specific version + Alpine variant
FROM node:18.19.0-alpine

# ✅ Production: Immutable digest
FROM node:18.19.0-alpine@sha256:abc123def456...
```

**Tag Strategy:**
```bash
# Development: Use descriptive tags
myapp:dev-abc1234           # dev branch + commit
myapp:feature-auth-xyz789   # feature branch

# Staging: Use semantic versioning
myapp:1.2.3-rc1             # Release candidate
myapp:1.2.3-beta            # Beta version

# Production: Immutable tags
myapp:1.2.3                 # Semantic version
myapp:1.2.3@sha256:...      # With digest for extra safety
```

#### 4. Implement Lifecycle Policies

Automatically remove old/unused images to manage costs and storage.

**Azure Container Registry:**
```bash
# Create retention policy (keep last 30 days)
az acr retention create --name myregistry --days 30 --status enabled

# Remove untagged manifests older than 7 days
az acr run --registry myregistry \
  --cmd "acr purge --filter 'myapp:.*' --ago 7d --untagged" \
  /dev/null
```

**Amazon ECR:**
```json
{
  "rules": [{
    "rulePriority": 1,
    "description": "Keep last 10 images",
    "selection": {
      "tagStatus": "any",
      "countType": "imageCountMoreThan",
      "countNumber": 10
    },
    "action": {
      "type": "expire"
    }
  }]
}
```

```bash
# Apply policy
aws ecr put-lifecycle-policy \
  --repository-name myapp \
  --lifecycle-policy-text file://policy.json
```

**Harbor:**
```yaml
# Tag retention rules in UI
# Keep: last 10 images
# Keep: images from last 30 days
# Keep: images matching pattern prod-*
```

#### 5. Use Multi-Stage Builds

**Why:**
- Push only final, production-ready image
- Keep build artifacts out of registry
- Smaller images = faster pulls
- Better security (fewer dependencies)

**Example:**
```dockerfile
# Build stage (not pushed)
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app

# Runtime stage (pushed to registry)
FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

**Result:**
- Build stage: ~1.5 GB (SDK, build tools)
- Runtime stage: ~200 MB (runtime only)
- Registry only stores 200 MB image

#### 6. Implement Geo-Replication

For global deployments, replicate images to multiple regions.

**Azure Container Registry (Premium):**
```bash
# Enable geo-replication
az acr replication create --name myregistry --location westeurope
az acr replication create --name myregistry --location eastasia
```

**Benefits:** Faster pulls, reduced latency, lower costs

#### 7. Use Immutable Tags (Production)

Prevent tags from being overwritten.

**Azure:**
```bash
az acr config content-trust update --registry myregistry --status enabled
```

**Harbor:** Project settings → Immutability Rules

**Why:** Prevents overwrites, ensures reproducibility, audit compliance

#### 8. Integrate with CI/CD

**GitHub Actions Example:**
```yaml
name: Build and Push
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Login to ACR
        uses: docker/login-action@v2
        with:
          registry: myregistry.azurecr.io
          username: ${{ secrets.ACR_USERNAME }}
          password: ${{ secrets.ACR_PASSWORD }}
      
      - name: Build and Push
        uses: docker/build-push-action@v4
        with:
          push: true
          tags: |
            myregistry.azurecr.io/myapp:${{ github.sha }}
            myregistry.azurecr.io/myapp:latest
```

**Azure Pipelines Example:**
```yaml
- task: Docker@2
  inputs:
    containerRegistry: 'myregistry'
    repository: 'myapp'
    command: 'buildAndPush'
    Dockerfile: '**/Dockerfile'
    tags: |
      $(Build.BuildId)
      latest
```

#### 9. Monitor Registry Metrics

Track usage, performance, and potential issues:
- Pull/push operations per minute
- Storage used, bandwidth consumed
- Failed authentication attempts
- Scan results (vulnerabilities found)

#### 10. Implement Webhook Notifications

Trigger actions when images are pushed:
- Notify team on new image
- Trigger deployment pipeline
- Start security scans

## Key Takeaways

✅ **Registries are central to container workflows**
- Store, distribute, and manage container images
- Essential for CI/CD and deployment pipelines
- Public vs private based on needs

✅ **Public registries great for open source**
- Docker Hub: largest, most popular
- GitHub Container Registry: tight integration
- Free for public images, rate limits apply

✅ **Private registries essential for production**
- ACR, ECR, GCR: cloud-native options
- Harbor: self-hosted with enterprise features
- Security, compliance, control

✅ **Security features protect your images**
- Vulnerability scanning finds CVEs
- Content trust ensures integrity
- RBAC controls access
- Network isolation adds defense-in-depth

✅ **Best practices optimize efficiency and security**
- Use specific tags, not `latest`
- Implement lifecycle policies
- Enable geo-replication for global apps
- Integrate scanning and signing
- Monitor usage and metrics

✅ **Layer sharing reduces storage and bandwidth**
- Common base layers stored once
- Only changed layers transferred
- Massive efficiency gains
