## Introduction

Container images are the blueprint from which containers are created. Understanding their layered architecture is fundamental to building efficient, maintainable containerized applications. The layered filesystem is one of the most important innovations in containerization, enabling features like efficient storage, fast distribution, and build caching.

This lesson explores how images are constructed, stored, optimized, and how to leverage layers effectively in your containerization workflow.

## Key Concepts Summary

### What is a Container Image?

A container image is a **read-only template** containing everything needed to run an application:
- **Application code** and assets
- **Runtime environment** (e.g., Node.js, Python, .NET)
- **System tools and libraries** (required dependencies)
- **Configuration files** (default configs)
- **Environment settings** (environment variables, working directory)
- **Metadata** (labels, exposed ports, entrypoint)

**Key Characteristics:**
- **Immutable**: Once built, an image doesn't change
- **Portable**: Runs consistently across different environments
- **Versioned**: Tagged with versions (e.g., `myapp:1.0`, `myapp:latest`)
- **Distributable**: Stored in registries and pulled as needed

Images are built from instructions in a `Dockerfile` and stored in registries for distribution.

### The Layered Filesystem

Container images use a **layered filesystem** where each layer represents a change to the filesystem. This is fundamental to container efficiency.

**Detailed Layer Structure:**

```
┌──────────────────────────────────────────┐
│  Container Layer (Read/Write)             │  ← Writable, ephemeral
│  - Runtime changes                        │
│  - Log files                              │
│  - Temporary data                         │
├──────────────────────────────────────────┤
│  Layer 5: ENTRYPOINT ["dotnet", "app"]   │  ← Application config
├──────────────────────────────────────────┤
│  Layer 4: COPY ./bin/Release /app        │  ← Application binaries
├──────────────────────────────────────────┤
│  Layer 3: RUN dotnet restore             │  ← Installed dependencies
├──────────────────────────────────────────┤
│  Layer 2: COPY *.csproj /app/            │  ← Project files
├──────────────────────────────────────────┤
│  Layer 1: WORKDIR /app                   │  ← Working directory
├──────────────────────────────────────────┤
│  Layer 0: FROM mcr.microsoft.com/dotnet  │  ← Base image (multiple layers)
│           /aspnet:8.0                     │
└──────────────────────────────────────────┘
```

**Key Principles:**

1. **Immutability**: Image layers are read-only and never change
2. **Stacking**: Layers stack on top of each other
3. **Sharing**: Multiple images can share common base layers
4. **Efficiency**: Only changed layers need to be downloaded/stored
5. **Copy-on-Write**: Runtime changes go to the container layer only

### Layer Creation in Dockerfiles

Each instruction in a Dockerfile that modifies the filesystem creates a new layer:

**Layer-Creating Instructions:**
- `FROM` - Base image (may contain multiple layers itself)
- `RUN` - Execute commands (install packages, compile code)
- `COPY` - Copy files from build context
- `ADD` - Copy files with additional features (URL fetch, tar extraction)

**Non-Layer Instructions:**
- `ENV` - Set environment variables (metadata only)
- `EXPOSE` - Document ports (metadata only)
- `LABEL` - Add metadata
- `ENTRYPOINT` - Set default command (metadata only)
- `CMD` - Set default arguments (metadata only)
- `WORKDIR` - Change working directory (may create layer if directory doesn't exist)

### Example Dockerfile with Layer Analysis

```dockerfile
# Layer 1: Base image (contains many layers itself)
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app                            # May create layer if /app doesn't exist
EXPOSE 80                               # Metadata only, no layer
EXPOSE 443                              # Metadata only, no layer

# Build stage
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src                            # Layer 2: Create /src directory

# Layer 3: Copy project file
COPY ["MyApp.csproj", "./"]             

# Layer 4: Restore dependencies
RUN dotnet restore "MyApp.csproj"       

# Layer 5: Copy source code
COPY . .                                

# Layer 6: Build application
RUN dotnet build "MyApp.csproj" -c Release -o /app/build

# Publish stage
FROM build AS publish
# Layer 7: Publish application
RUN dotnet publish "MyApp.csproj" -c Release -o /app/publish

# Final stage
FROM base AS final
WORKDIR /app
# Layer 8: Copy published output
COPY --from=publish /app/publish .      
ENTRYPOINT ["dotnet", "MyApp.dll"]      # Metadata only, no layer
```

**Layer Count:**
- Base image layers: ~8-10 layers (from Microsoft's base image)
- Build layers: ~7 layers created during build
- Final image layers: ~2-3 layers (base + published app)
- **Total final image layers:** ~10-13 layers

Multi-stage builds reduce final image size by only including necessary layers in the final stage.

### Layer Sharing and Storage Efficiency

**How Layer Sharing Works:**

When multiple images use the same base image, that base is stored only once:

```
App A Image (250 MB)     App B Image (300 MB)     App C Image (275 MB)
┌────────────────┐       ┌────────────────┐       ┌────────────────┐
│ App A (50 MB)  │       │ App B (100 MB) │       │ App C (75 MB)  │
├────────────────┤       ├────────────────┤       ├────────────────┤
│ node:18        │◄──────┤ node:18        │◄──────┤ node:18        │
│ (200 MB)       │ Same! │ (200 MB)       │ Same! │ (200 MB)       │
└────────────────┘       └────────────────┘       └────────────────┘

Disk usage WITHOUT sharing: 250 + 300 + 275 = 825 MB
Disk usage WITH sharing:    200 + 50 + 100 + 75 = 425 MB
Savings: 400 MB (48% reduction)
```

**Benefits:**
- **Reduced storage:** Base layers shared across images
- **Faster pulls:** Only download new/changed layers
- **Efficient distribution:** Registries only store unique layers
- **Lower bandwidth:** Don't re-download unchanged layers

**Layer Identification:**
Each layer is identified by its **SHA-256 content hash**:
```
sha256:abc123... (layer 1)
sha256:def456... (layer 2)
sha256:ghi789... (layer 3)
```

If two layers have the same hash, they're identical and stored once.

### Image Layer Caching

Docker caches layers during builds to speed up subsequent builds:

**Cache Behavior:**

```dockerfile
FROM node:18                    # Layer cached if base image unchanged
WORKDIR /app                    # Layer cached if instruction unchanged
COPY package*.json ./           # Layer cached if package.json unchanged
RUN npm install                 # ← CACHED if previous layer cached
COPY . .                        # ← Cache INVALIDATED if source code changed
RUN npm run build               # ← Must rebuild (previous layer changed)
```

**Cache Invalidation Rules:**

1. **Layer changed:** If instruction or its inputs change, cache invalidated
2. **Previous layer changed:** All subsequent layers must be rebuilt
3. **Base image updated:** All layers must be rebuilt
4. **Build context changed:** Only affects layers that use changed files

**Optimization Strategy:**

```dockerfile
# ❌ Bad: Frequent cache invalidation
FROM node:18
WORKDIR /app
COPY . .                  # Copies everything, invalidates cache often
RUN npm install           # Reinstalls deps every time code changes
RUN npm run build

# ✅ Good: Maximize cache hits
FROM node:18
WORKDIR /app
COPY package*.json ./     # Copy deps definition first
RUN npm install           # Only re-runs if package.json changes
COPY . .                  # Copy source code last
RUN npm run build         # Only re-runs if source code changes
```

**Benefits of Good Caching:**
- **Faster builds:** Seconds instead of minutes
- **Lower CI costs:** Less CPU/time for builds
- **Quicker iterations:** Faster developer feedback loop

### Union Filesystem and Copy-on-Write

Container images use a **union filesystem** to create a unified view of all layers:

**How Union Filesystems Work:**

```
View from Container:
/app/
  index.js      ← From Layer 3
  package.json  ← From Layer 2
  node_modules/ ← From Layer 2 (npm install)
  config.json   ← From Container Layer (runtime change)

Physical Storage:
Layer 3: /var/lib/docker/overlay2/xyz123.../diff/app/index.js
Layer 2: /var/lib/docker/overlay2/abc456.../diff/app/package.json
Layer 2: /var/lib/docker/overlay2/abc456.../diff/app/node_modules/
Container Layer: /var/lib/docker/overlay2/def789.../diff/app/config.json

Union Mount creates unified view at runtime
```

**Copy-on-Write (CoW) Behavior:**

When a running container modifies a file from a lower read-only layer:

```
1. File exists in Layer 2 (read-only)
2. Container tries to modify it
3. CoW mechanism copies file to Container Layer (read-write)
4. Modification applied to copy in Container Layer
5. Original in Layer 2 remains unchanged
6. Union filesystem shows modified version from Container Layer

Result: Original layer preserved, changes isolated to container
```

**Implications:**
- ✅ Image layers never modified (immutable, shareable)
- ✅ Multiple containers can share same image layers safely
- ❌ Large file modifications expensive (entire file copied)
- ❌ Database files in container layer = poor performance

**Best Practice:** Use volumes for frequently modified data (logs, databases, uploads).

### Image Tags and Digests

Images are identified in multiple ways:

**1. Repository Name:**
```
nginx
mycompany/myapp
gcr.io/my-project/service
```

**2. Tags (Mutable):**
```
nginx:latest           # Can change over time
nginx:1.21            # Specific version
nginx:1.21-alpine     # Version + variant
myapp:v1.2.3          # Semantic versioning
myapp:main-abc123     # Branch + commit
myapp:pr-456          # Pull request builds
```

**3. Digests (Immutable):**
```
nginx@sha256:abc123def456...   # Content-based hash, never changes
myapp@sha256:789ghi012jkl...   # Guaranteed specific image version
```

**Tag vs Digest:**

| Aspect | Tags | Digests |
|--------|------|---------|
| **Mutability** | Can be moved to different image | Immutable, fixed forever |
| **Readability** | Human-friendly (`v1.2.3`) | Machine hash (64-char hex) |
| **Reproducibility** | Not guaranteed | Guaranteed |
| **Use Case** | Development, readability | Production, security, compliance |

**Best Practices:**

```dockerfile
# ❌ Development only: mutable, unpredictable
FROM node:latest

# ✅ Better: specific version
FROM node:18.19

# ✅ Best for production: immutable digest
FROM node:18.19@sha256:abc123def456...
```

**Pulling by Tag vs Digest:**

```bash
# Pull by tag (may get different image over time)
docker pull nginx:latest

# Pull by digest (always exact same image)
docker pull nginx@sha256:abc123def456789...

# Pull by tag and verify digest
docker pull nginx:1.21
docker inspect nginx:1.21 | grep -i digest
```

### Layer Size Optimization

**Layer Size Best Practices:**

```dockerfile
# ❌ Bad: Multiple RUN instructions create multiple layers
FROM ubuntu:22.04
RUN apt-get update                    # Layer 1: 50 MB
RUN apt-get install -y python3        # Layer 2: 100 MB
RUN apt-get install -y python3-pip    # Layer 3: 80 MB
RUN apt-get clean                     # Layer 4: doesn't reduce previous layers!
# Total: 230 MB (clean has no effect on size!)

# ✅ Good: Combine into single RUN, clean in same layer
FROM ubuntu:22.04
RUN apt-get update && \
    apt-get install -y python3 python3-pip && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*
# Total: 150 MB (cleanup in same layer reduces size)
```

**Why This Matters:**
- Each layer is immutable
- Deleting files in a later layer doesn't reduce size
- Files must be removed in the same layer they're created

**Additional Optimization Techniques:**

1. **Use smaller base images:**
```dockerfile
FROM ubuntu:22.04          # ~78 MB
FROM alpine:3.18           # ~7 MB (much smaller!)
FROM mcr.microsoft.com/dotnet/aspnet:8.0-alpine  # Alpine variant
```

2. **Multi-stage builds** (covered later):
```dockerfile
# Build stage: includes SDK, build tools (large)
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
# ... build process ...

# Runtime stage: only runtime, no SDK (small)
FROM mcr.microsoft.com/dotnet/aspnet:8.0
COPY --from=build /app/publish .
```

3. **Remove unnecessary files in same layer:**
```dockerfile
RUN wget https://example.com/large-file.tar.gz && \
    tar -xzf large-file.tar.gz && \
    mv extracted-file /app/ && \
    rm large-file.tar.gz           # Remove in same layer!
```

### Inspecting Image Layers

**Using Docker CLI:**

```bash
# View image layers and their sizes
docker history nginx:latest

# Output example:
IMAGE          CREATED       CREATED BY                                      SIZE
abc123def456   2 weeks ago   /bin/sh -c #(nop)  CMD ["nginx" "-g" "daemon…   0B
def456ghi789   2 weeks ago   /bin/sh -c #(nop)  EXPOSE 80                    0B
ghi789jkl012   2 weeks ago   /bin/sh -c apt-get update && apt-get install…   54.3MB
jkl012mno345   3 weeks ago   /bin/sh -c #(nop)  FROM ubuntu:22.04            77.8MB

# Detailed image inspection
docker inspect nginx:latest

# View specific layer information
docker image inspect nginx:latest --format='{{.RootFS.Layers}}'
```

**Analyzing Layer Impact:**

```bash
# Build and see layer sizes
docker build -t myapp:test .

# Check final image size
docker images myapp:test

# See history with sizes
docker history myapp:test
```

## Key Takeaways

✅ **Container images use layered filesystems**
- Each layer is immutable and stacked
- Only top container layer is writable
- Layers identified by content hash (SHA-256)

✅ **Layer sharing provides massive efficiency gains**
- Shared base layers stored once
- Reduces storage by 50-90% typically
- Faster pulls (only download new layers)

✅ **Build cache significantly speeds up development**
- Order matters: stable instructions first
- Invalidation cascades down
- Good ordering = seconds vs minutes for rebuilds

✅ **Tags are mutable, digests are immutable**
- Use tags for convenience and readability
- Use digests for production and reproducibility
- Never rely on `latest` in production

✅ **Layer optimization reduces image size**
- Combine commands to minimize layers
- Clean up in same layer where files created
- Use smaller base images (Alpine variants)
- Multi-stage builds for production images

✅ **Union filesystem creates unified view**
- Copy-on-write for modifications
- Original layers never modified
- Use volumes for frequently modified data
