# Lesson 5: Cluster Architecture Patterns

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand single-master vs multi-master cluster architectures
- Design highly available Kubernetes clusters
- Understand different deployment topologies
- Choose appropriate architectures for different use cases

## Introduction

Kubernetes clusters can be architected in various ways depending on requirements for availability, scale, and use case. This lesson covers common architecture patterns, from simple single-node clusters for development to highly available production clusters spanning multiple data centers.

## Key Concepts Summary

### Cluster Architecture Spectrum

```
Development → Testing → Staging → Production → Multi-Region
    ↓          ↓          ↓          ↓            ↓
  1 node   1 master    1 master   3 masters   Multi-cluster
            3 workers   5 workers  10+ workers  Federated
```

### 1. Single-Node Cluster (Development)

**Use Case:** Local development, learning, testing

**Architecture:**
```
┌─────────────────────────────────────┐
│         Single Node                  │
│                                      │
│  ┌────────────────────────────────┐ │
│  │   Control Plane Components     │ │
│  │   (API, etcd, scheduler, etc.) │ │
│  └────────────────────────────────┘ │
│  ┌────────────────────────────────┐ │
│  │   Worker Components            │ │
│  │   (kubelet, kube-proxy, pods)  │ │
│  └────────────────────────────────┘ │
└─────────────────────────────────────┘
```

**Tools:**
- **minikube** - Full Kubernetes in a VM
- **kind** - Kubernetes in Docker
- **k3s** - Lightweight Kubernetes
- **Docker Desktop** - Built-in Kubernetes

**Example (minikube):**
```bash
# Start single-node cluster
minikube start

# Deploy application
kubectl create deployment nginx --image=nginx

# Access service
minikube service nginx
```

**Pros:**
- Easy to set up
- Minimal resources
- Fast iteration

**Cons:**
- No HA
- Not production-ready
- Limited scale

### 2. Single-Master Cluster

**Use Case:** Development, testing, small production workloads

**Architecture:**
```
┌─────────────────────────────────────┐
│        Master Node                   │
│  ┌────────────────────────────────┐ │
│  │   API Server                   │ │
│  │   etcd                         │ │
│  │   Scheduler                    │ │
│  │   Controller Manager           │ │
│  └────────────────────────────────┘ │
└──────────────┬──────────────────────┘
               ↓
    ┌──────────┴──────────┐
    ↓                      ↓
┌─────────┐          ┌─────────┐
│ Worker  │          │ Worker  │
│  Node 1 │          │  Node 2 │
└─────────┘          └─────────┘
```

**Pros:**
- Simple to manage
- Lower cost
- Suitable for non-critical workloads

**Cons:**
- Single point of failure
- Limited control plane capacity
- Not recommended for production

### 3. High Availability (HA) Cluster

**Use Case:** Production workloads, mission-critical applications

**Stacked etcd topology:**
```
┌──────────────────────────────────────────────────────┐
│                  Load Balancer                        │
│             (HAProxy / cloud LB)                      │
└───┬─────────────────┬─────────────────┬──────────────┘
    ↓                 ↓                 ↓
┌─────────┐      ┌─────────┐      ┌─────────┐
│ Master1 │      │ Master2 │      │ Master3 │
│ ┌─────┐ │      │ ┌─────┐ │      │ ┌─────┐ │
│ │ API │ │      │ │ API │ │      │ │ API │ │
│ └─────┘ │      │ └─────┘ │      │ └─────┘ │
│ ┌─────┐ │      │ ┌─────┐ │      │ ┌─────┐ │
│ │etcd │←┼──────┼→│etcd │←┼──────┼→│etcd │ │
│ └─────┘ │      │ └─────┘ │      │ └─────┘ │
│ Sched   │      │ Sched   │      │ Sched   │
│ CtrlMgr │      │ CtrlMgr │      │ CtrlMgr │
└─────────┘      └─────────┘      └─────────┘
      ↓                ↓                ↓
   ┌──────────────────┴─────────────────┐
   ↓                                     ↓
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│Worker 1 │  │Worker 2 │  │Worker 3 │  │Worker N │
└─────────┘  └─────────┘  └─────────┘  └─────────┘
```

**External etcd topology:**
```
┌──────────────────────────────────────────────────────┐
│                  Load Balancer                        │
└───┬─────────────────┬─────────────────┬──────────────┘
    ↓                 ↓                 ↓
┌─────────┐      ┌─────────┐      ┌─────────┐
│ Master1 │      │ Master2 │      │ Master3 │
│ ┌─────┐ │      │ ┌─────┐ │      │ ┌─────┐ │
│ │ API │ │      │ │ API │ │      │ │ API │ │
│ └──┬──┘ │      │ └──┬──┘ │      │ └──┬──┘ │
│ Sched   │      │ Sched   │      │ Sched   │
│ CtrlMgr │      │ CtrlMgr │      │ CtrlMgr │
└────┼────┘      └────┼────┘      └────┼────┘
     └────────────────┼────────────────┘
                      ↓
         ┌────────────┴────────────┐
         ↓                          ↓
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │  etcd1  │←→│  etcd2  │←→│  etcd3  │
    └─────────┘  └─────────┘  └─────────┘
         (Separate etcd cluster)
```

**Comparison:**

| Aspect | Stacked etcd | External etcd |
|--------|--------------|---------------|
| Setup | Simpler | More complex |
| Nodes | Fewer required | More required |
| Failure domain | Coupled | Decoupled |
| Recommended for | Most cases | Large clusters |

**HA Components:**

**API Server:**
- All instances active (active-active)
- Load balancer distributes requests
- Stateless, horizontally scalable

**etcd:**
- Requires quorum (majority)
- 3 nodes = tolerates 1 failure
- 5 nodes = tolerates 2 failures
- Always use odd numbers

**Scheduler & Controller Manager:**
- Leader election (active-passive)
- Only one active at a time
- Automatic failover

### 4. Node Pools and Taints

**Separate workload types:**
```
┌──────────────────────────────────────────────┐
│              Control Plane                    │
└──────────────────┬───────────────────────────┘
                   ↓
    ┌──────────────┼──────────────┐
    ↓              ↓              ↓
┌─────────┐  ┌─────────┐  ┌─────────┐
│General  │  │ Memory  │  │   GPU   │
│Purpose  │  │Optimized│  │  Nodes  │
│  Pool   │  │  Pool   │  │  Pool   │
│         │  │         │  │         │
│ Web     │  │Database │  │  ML     │
│ APIs    │  │ Cache   │  │Training │
└─────────┘  └─────────┘  └─────────┘
```

**Taint nodes:**
```bash
# Taint GPU nodes
kubectl taint nodes gpu-node-1 gpu=true:NoSchedule

# Taint memory-optimized nodes
kubectl taint nodes mem-node-1 workload=memory-intensive:NoSchedule
```

**Schedule with tolerations:**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ml-training
spec:
  tolerations:
  - key: "gpu"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
  nodeSelector:
    gpu: "nvidia-tesla"
  containers:
  - name: training
    image: ml-model:latest
    resources:
      limits:
        nvidia.com/gpu: 1
```

### 5. Multi-Zone Cluster

**Use Case:** High availability within a region

**Architecture:**
```
┌─────────────────────────────────────────────────────┐
│                 Cloud Region                         │
│                                                       │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐ │
│  │   Zone A    │  │   Zone B    │  │   Zone C    │ │
│  │             │  │             │  │             │ │
│  │ Master1     │  │ Master2     │  │ Master3     │ │
│  │ etcd1       │  │ etcd2       │  │ etcd3       │ │
│  │             │  │             │  │             │ │
│  │ Worker1     │  │ Worker2     │  │ Worker3     │ │
│  │ Worker4     │  │ Worker5     │  │ Worker6     │ │
│  └─────────────┘  └─────────────┘  └─────────────┘ │
└─────────────────────────────────────────────────────┘
```

**Benefits:**
- Survives zone failure
- Low latency between zones
- Automatic pod redistribution

**Example (AWS):**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 6
  template:
    spec:
      # Spread across zones
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: web
```

### 6. Multi-Region / Multi-Cluster

**Use Case:** Disaster recovery, geo-distribution, compliance

**Architecture:**
```
┌─────────────────────────────────────────────────────┐
│                 Global Load Balancer                 │
│              (Traffic Director / Route53)            │
└──────────────┬─────────────────┬────────────────────┘
               ↓                 ↓
    ┌──────────────────┐  ┌──────────────────┐
    │  Region: US-East │  │  Region: EU-West │
    │                  │  │                  │
    │  ┌────────────┐  │  │  ┌────────────┐  │
    │  │ Cluster 1  │  │  │  │ Cluster 2  │  │
    │  │            │  │  │  │            │  │
    │  │ 3 Masters  │  │  │  │ 3 Masters  │  │
    │  │ 10 Workers │  │  │  │ 10 Workers │  │
    │  └────────────┘  │  │  └────────────┘  │
    └──────────────────┘  └──────────────────┘
```

**Strategies:**

**Active-Passive:**
- Primary cluster serves traffic
- Secondary cluster on standby
- Failover on primary failure

**Active-Active:**
- Both clusters serve traffic
- Geographic routing
- Requires data replication

**Tools:**
- **Kubefed** - Kubernetes Federation
- **Istio Multi-Cluster** - Service mesh across clusters
- **External DNS** - DNS management
- **Velero** - Backup and restore

### Cluster Sizing Guidelines

**Small cluster:**
```
Use case: Dev/Test, small apps
- 1 master (or 3 for HA)
- 3-10 workers
- Resources: 2 CPU, 4GB RAM per node
```

**Medium cluster:**
```
Use case: Production, moderate scale
- 3 masters
- 10-50 workers
- Resources: 4 CPU, 16GB RAM per node
```

**Large cluster:**
```
Use case: Enterprise production
- 3-5 masters
- 50-500 workers
- Resources: 8+ CPU, 32+ GB RAM per node
```

**Considerations:**
- Maximum 5000 nodes per cluster
- Maximum 150,000 pods per cluster
- Maximum 300,000 containers per cluster
- Maximum 100 pods per node

### Control Plane Scaling

**API Server:**
```bash
# Run multiple instances
# Behind load balancer
# Scale based on:
# - Number of nodes
# - API request rate
# - Watch connections
```

**etcd:**
```bash
# 3 nodes: up to 100 worker nodes
# 5 nodes: up to 500 worker nodes
# More than 5 not recommended
```

**Scheduler & Controller Manager:**
```bash
# Use leader election
# Run 3-5 instances for HA
# Only one active, rest on standby
```

### Disaster Recovery

**Backup Strategy:**
```bash
# 1. Backup etcd regularly
ETCDCTL_API=3 etcdctl snapshot save backup.db

# 2. Store backups off-cluster
aws s3 cp backup.db s3://k8s-backups/

# 3. Backup application data
velero backup create full-backup --include-namespaces production

# 4. Store cluster configuration in Git
git push origin main
```

**Recovery Plan:**
```
1. Restore etcd from backup
2. Restore cluster from configuration (GitOps)
3. Restore application data (Velero)
4. Validate cluster health
5. Resume traffic
```

### Cost Optimization

**Node Efficiency:**
```bash
# Use node autoscaling
# Enable cluster autoscaler
kubectl apply -f https://github.com/kubernetes/autoscaler/releases/download/cluster-autoscaler-1.27.0/cluster-autoscaler-autodiscover.yaml

# Configure:
# - Min/max nodes per pool
# - Scale-down delay
# - Utilization thresholds
```

**Workload Optimization:**
```yaml
# Set appropriate resource requests/limits
apiVersion: v1
kind: Pod
metadata:
  name: optimized-pod
spec:
  containers:
  - name: app
    image: myapp:latest
    resources:
      requests:
        memory: "128Mi"
        cpu: "100m"
      limits:
        memory: "256Mi"
        cpu: "200m"
```

**Spot/Preemptible Instances:**
```yaml
# Use spot instances for fault-tolerant workloads
apiVersion: v1
kind: Node
metadata:
  labels:
    node.kubernetes.io/instance-type: spot
spec:
  taints:
  - key: spot
    value: "true"
    effect: NoSchedule
```

**Resource Bin Packing:**
```yaml
# Configure scheduler for efficiency
apiVersion: v1
kind: ConfigMap
metadata:
  name: scheduler-config
  namespace: kube-system
data:
  scheduler-config.yaml: |
    apiVersion: kubescheduler.config.k8s.io/v1
    kind: KubeSchedulerConfiguration
    profiles:
    - schedulerName: default-scheduler
      plugins:
        score:
          enabled:
          - name: NodeResourcesFit
            weight: 1
```

### Capacity Planning

**Growth Metrics:**
```
Track over time:
- Pod count growth rate
- Node resource utilization
- Network throughput
- Storage consumption
- API server request rate
```

**Planning Guidelines:**
```
Small cluster (< 100 pods):
- 1-3 control plane nodes
- 3-10 worker nodes
- CPU: 2-4 cores per node
- Memory: 8-16 GB per node

Medium cluster (100-1000 pods):
- 3 control plane nodes
- 10-50 worker nodes
- CPU: 4-8 cores per node
- Memory: 16-32 GB per node

Large cluster (1000+ pods):
- 3-5 control plane nodes
- 50-500 worker nodes
- CPU: 8-16 cores per node
- Memory: 32-64 GB per node
- Separate etcd cluster
```

**Scaling Limits:**
```
Kubernetes limits (v1.27):
- 5,000 nodes per cluster
- 150,000 total pods
- 300,000 total containers
- 100 pods per node
```

### Multi-Tenancy Patterns

**Namespace Isolation:**
```yaml
# Create tenant namespace
apiVersion: v1
kind: Namespace
metadata:
  name: tenant-a
  labels:
    tenant: tenant-a

---
# Resource quota per tenant
apiVersion: v1
kind: ResourceQuota
metadata:
  name: tenant-a-quota
  namespace: tenant-a
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    persistentvolumeclaims: "10"
    services.loadbalancers: "2"

---
# Limit range
apiVersion: v1
kind: LimitRange
metadata:
  name: tenant-a-limits
  namespace: tenant-a
spec:
  limits:
  - max:
      cpu: "2"
      memory: 4Gi
    min:
      cpu: "100m"
      memory: 128Mi
    default:
      cpu: "500m"
      memory: 512Mi
    defaultRequest:
      cpu: "200m"
      memory: 256Mi
    type: Container
```

**Network Policies per Tenant:**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: tenant-a-isolation
  namespace: tenant-a
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          tenant: tenant-a
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          tenant: tenant-a
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
```

### Hybrid Cloud Patterns

**Multi-Cluster Management:**
```
┌─────────────────────────────────────────────┐
│         Cluster Management Plane            │
│  (Fleet Manager / Rancher / Anthos)        │
└──────┬────────────┬────────────┬───────────┘
       ↓            ↓            ↓
┌──────────┐  ┌──────────┐  ┌──────────┐
│  AWS     │  │  Azure   │  │ On-Prem  │
│ Cluster  │  │ Cluster  │  │ Cluster  │
└──────────┘  └──────────┘  └──────────┘
```

**Workload Distribution:**
```yaml
# Use affinity to prefer specific clusters
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/region
                operator: In
                values:
                - us-west-2
```

## Practice Exercise

After completing the materials (20 minutes max):

1. **Analyze your cluster architecture:**
```bash
# Check number of masters
kubectl get nodes -l node-role.kubernetes.io/control-plane

# Check worker nodes
kubectl get nodes -l '!node-role.kubernetes.io/control-plane'

# View resource capacity
kubectl top nodes
```

2. **Check HA setup:**
```bash
# Check etcd members
kubectl exec -n kube-system etcd-master-1 -- etcdctl member list

# Check API server endpoints
kubectl config view | grep server:
```

3. **Review node distribution:**
```bash
# Check zones (cloud clusters)
kubectl get nodes -L topology.kubernetes.io/zone

# Check pod distribution
kubectl get pods -o wide --all-namespaces
```

4. **Plan a backup strategy:**
```bash
# Install Velero (example)
velero install --provider aws --bucket k8s-backups

# Create backup
velero backup create my-backup

# Schedule recurring backups
velero schedule create daily --schedule="0 2 * * *"
```
