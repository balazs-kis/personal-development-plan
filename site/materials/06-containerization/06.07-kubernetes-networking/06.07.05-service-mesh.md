## Introduction

A service mesh is a dedicated infrastructure layer that adds capabilities like observability, traffic management, and security to service-to-service communication without requiring code changes. Service meshes use sidecar proxies (or ambient mode) to intercept and manage all network traffic between microservices, providing advanced features that are difficult to implement at the application level.

## Key Concepts Summary

### What is a Service Mesh?

```
Without Service Mesh:
Service A → Service B
  ↓
Each service implements:
- Retries
- Timeouts  
- Metrics
- Logging
- Security
Code in every service!

With Service Mesh:
Service A → Proxy → Proxy → Service B
              ↓       ↓
         All features handled by mesh
         No code changes needed!
```

**Service mesh provides:**
- **Observability:** Metrics, logs, traces
- **Traffic management:** Routing, retries, timeouts, circuit breaking
- **Security:** mTLS, authentication, authorization
- **Resilience:** Fault injection, load balancing

### Architecture Patterns

**Sidecar Mode (traditional):**
```
┌─────────────────────────┐
│         Pod             │
│  ┌─────────┐ ┌────────┐│
│  │  App    │ │ Proxy  ││
│  │Container│←│(Envoy) ││
│  └─────────┘ └────────┘│
└─────────────────────────┘

One proxy per pod
```

**Ambient Mode (Istio):**
```
┌─────────────────────────┐
│         Node            │
│  ┌────────┐ ┌────────┐ │
│  │ App 1  │ │ App 2  │ │
│  └───┬────┘ └────┬───┘ │
│      └──────┬────┘      │
│     ┌───────▼──────┐    │
│     │ Layer 4 Proxy│    │
│     └──────────────┘    │
└─────────────────────────┘

Shared per-node proxy
```

### Istio

**Architecture:**
```
┌──────────────────────────────────────┐
│          Control Plane               │
│  ┌────────┐  ┌────────┐  ┌────────┐│
│  │ Pilot  │  │Citadel │  │Galley  ││
│  └────────┘  └────────┘  └────────┘│
└─────────┬────────────────────────────┘
          ↓ (config)
┌──────────────────────────────────────┐
│          Data Plane                  │
│  ┌──────────────┐  ┌──────────────┐│
│  │Pod + Envoy   │  │Pod + Envoy   ││
│  │Sidecar       │  │Sidecar       ││
│  └──────────────┘  └──────────────┘│
└──────────────────────────────────────┘
```

**Key Features:**
- Automatic mTLS between services
- Advanced traffic routing (canary, A/B)
- Fault injection for testing
- Comprehensive observability
- Multiple deployment modes (sidecar/ambient)

**Install Istio:**
```bash
# Download istioctl
curl -L https://istio.io/downloadIstio | sh -
cd istio-1.20.0
export PATH=$PWD/bin:$PATH

# Install
istioctl install --set profile=demo -y

# Enable sidecar injection
kubectl label namespace default istio-injection=enabled
```

**Example: Traffic Routing**
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: web
spec:
  hosts:
  - web
  http:
  - match:
    - headers:
        version:
          exact: v2
    route:
    - destination:
        host: web
        subset: v2
  - route:
    - destination:
        host: web
        subset: v1
      weight: 90
    - destination:
        host: web
        subset: v2
      weight: 10
```

### Linkerd

**Architecture:**
```
┌──────────────────────────────────────┐
│          Control Plane               │
│  ┌────────────────────────────────┐ │
│  │  Destination, Identity, Proxy  │ │
│  └────────────────────────────────┘ │
└─────────┬────────────────────────────┘
          ↓
┌──────────────────────────────────────┐
│          Data Plane                  │
│  ┌──────────────┐  ┌──────────────┐│
│  │Pod + Linkerd │  │Pod + Linkerd ││
│  │Proxy (Rust)  │  │Proxy (Rust)  ││
│  └──────────────┘  └──────────────┘│
└──────────────────────────────────────┘
```

**Key Features:**
- Lightweight (Rust-based micro-proxy)
- Security-first design
- Simple, opinionated approach
- Excellent performance
- CNCF graduated project

**Install Linkerd:**
```bash
# Install CLI
curl --proto '=https' --tlsv1.2 -sSfL https://run.linkerd.io/install | sh
export PATH=$PATH:$HOME/.linkerd2/bin

# Check requirements
linkerd check --pre

# Install control plane
linkerd install --crds | kubectl apply -f -
linkerd install | kubectl apply -f -

# Verify
linkerd check

# Add to namespace
kubectl annotate namespace default linkerd.io/inject=enabled
```

**Example: Retry Policy**
```yaml
apiVersion: policy.linkerd.io/v1beta2
kind: Retry
metadata:
  name: web-retry
  namespace: default
spec:
  selector:
    matchLabels:
      app: web
  httpRetries:
    maxRetries: 3
    backoff:
      minWait: 100ms
      maxWait: 1s
```

### Service Mesh Features

**1. Mutual TLS (mTLS):**
```
Service A → [encrypt] → Service B
          ← [encrypt] ←

Automatic encryption + authentication
No code changes needed
```

**2. Traffic Management:**
```yaml
# Canary deployment (10% v2)
- destination:
    host: api
    subset: v1
  weight: 90
- destination:
    host: api
    subset: v2
  weight: 10
```

**3. Observability:**
```
Automatic metrics:
- Request rate
- Error rate
- Latency (p50, p95, p99)
- Success rate

For every service!
```

**4. Resilience:**
```yaml
# Circuit breaking
connectionPool:
  tcp:
    maxConnections: 100
  http:
    http1MaxPendingRequests: 50
    maxRequestsPerConnection: 2

outlierDetection:
  consecutiveErrors: 5
  interval: 30s
  baseEjectionTime: 30s
```

### When to Use a Service Mesh

**Good Use Cases:**
- Microservices architecture (10+ services)
- Need end-to-end encryption (mTLS)
- Advanced traffic management (canary, A/B)
- Comprehensive observability
- Zero-trust security model

**Probably Overkill:**
- Monolithic application
- Small number of services (< 5)
- Simple architecture
- Tight resource constraints

### Istio vs Linkerd Comparison

| Feature | Istio | Linkerd |
|---------|-------|---------|
| **Complexity** | Higher | Lower |
| **Resource Usage** | More | Less |
| **Proxy** | Envoy (C++) | Custom (Rust) |
| **Performance** | Good | Excellent |
| **Features** | Extensive | Focused |
| **Maturity** | High | High (CNCF Graduated) |
| **Best For** | Large, complex deployments | Simplicity, performance |

**Istio strengths:**
- Extensive features
- Ecosystem integrations
- Multiple deployment modes
- Enterprise support

**Linkerd strengths:**
- Simpler, easier to use
- Better performance
- Smaller footprint
- Security-first design

### Service Mesh Alternatives

**Without a full service mesh:**

### Getting Started with Istio

**Installation options:**
```bash

export PATH=$PWD/bin:$PATH

# Profiles available:
# - minimal: Bare minimum (control plane only)
# - demo: Full features + addons (development)
# - production: Production-ready defaults
# - ambient: Ambient mesh mode

istioctl install --set profile=demo -y

# Option 2: Helm

helm install istio-base istio/base -n istio-system --create-namespace
helm install istiod istio/istiod -n istio-system
helm install istio-ingress istio/gateway -n istio-system
```

**Enable sidecar injection:**
```bash
# Automatic injection per namespace
kubectl label namespace default istio-injection=enabled

# Manual injection per deployment
kubectl get deploy web -o yaml | istioctl kube-inject -f - | kubectl apply -f -

# Verify injection
kubectl get pods
# Each pod should have 2 containers: app + istio-proxy
```

**Deploy sample application:**

### Advanced Istio Patterns

**Traffic splitting (canary deployment):**
```yaml
# Define service subsets
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api
spec:
  host: api
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2

---
# Traffic routing
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api
spec:
  hosts:
  - api
  http:
  - match:
    - headers:
        x-beta-user:
          exact: "true"
    route:
    - destination:
        host: api
        subset: v2
  - route:
    - destination:
        host: api
        subset: v1
      weight: 95
    - destination:
        host: api
        subset: v2
      weight: 5
```

**Circuit breaking and resilience:**
```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api-circuit-breaker
spec:
  host: api
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 50
        maxRequestsPerConnection: 2
    outlierDetection:
      consecutiveErrors: 5
      interval: 30s
      baseEjectionTime: 30s

---
# Request timeouts and retries
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api-resilience
spec:
  hosts:
  - api
  http:
  - route:
    - destination:
        host: api
    timeout: 10s
    retries:
      attempts: 3
      perTryTimeout: 3s
      retryOn: 5xx,connect-failure
```

**Fault injection (testing):**
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api-fault
spec:
  hosts:
  - api
  http:
  - fault:
      delay:
        percentage:
          value: 10
        fixedDelay: 5s
      abort:
        percentage:
          value: 5
        httpStatus: 500
    route:
    - destination:
        host: api
```

### Advanced Linkerd Patterns

**Traffic splits:**
```yaml
apiVersion: split.smi-spec.io/v1alpha2
kind: TrafficSplit
metadata:
  name: api-split
spec:
  service: api
  backends:
  - service: api-v1
    weight: 90
  - service: api-v2
    weight: 10
```

**Timeouts and retries:**
```yaml
apiVersion: policy.linkerd.io/v1beta2
kind: Retry
metadata:
  name: api-retry
spec:
  selector:
    matchLabels:
      app: api
  httpRetries:
    maxRetries: 3
    backoff:
      minWait: 100ms
      maxWait: 1s

---
apiVersion: policy.linkerd.io/v1beta2
kind: HTTPRoute
metadata:
  name: api-timeout
spec:
  parentRefs:
  - name: api
    kind: Service
  rules:
  - timeouts:
      request: 10s
```

### Service Mesh Security

**Istio mTLS:**
```yaml
# Strict mode: Only encrypted traffic
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: production
spec:
  mtls:
    mode: STRICT
```

**Authorization policies:**
```yaml
# Deny all by default
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: deny-all
spec:
  {}

---
# Allow specific communication
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-frontend-to-api
spec:
  selector:
    matchLabels:
      app: api
  action: ALLOW
  rules:
  - from:
    - source:
        principals:
        - cluster.local/ns/default/sa/frontend
    to:
    - operation:
        methods: ["GET", "POST"]
```

**Linkerd authorization:**
```yaml
apiVersion: policy.linkerd.io/v1alpha1
kind: Server
metadata:
  name: api-server
spec:
  podSelector:
    matchLabels:
      app: api
  port: 8080

---
apiVersion: policy.linkerd.io/v1alpha1
kind: ServerAuthorization
metadata:
  name: api-from-frontend
spec:
  server:
    name: api-server
  client:
    meshTLS:
      serviceAccounts:
      - name: frontend
```

### Migration Strategies

**Gradual adoption approach:**
```bash
# Phase 1: Install control plane
istioctl install --set profile=minimal -y

# Phase 2: Enable per-namespace
kubectl label namespace staging istio-injection=enabled

# Phase 3: Monitor and verify
istioctl analyze
kubectl get pods -n staging

# Phase 4: Expand incrementally
kubectl label namespace production istio-injection=enabled

# Phase 5: Enable features gradually
# - mTLS
# - Policies
# - Traffic management
```

**Zero-downtime migration:**
```yaml
# Run meshed and unmeshed versions
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-v1
spec:
  replicas: 3
  template:
    metadata:
      labels:
        version: v1
        # No mesh
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-v2
spec:
  replicas: 1
  template:
    metadata:
      labels:
        version: v2
      annotations:
        sidecar.istio.io/inject: "true"
```

### Troubleshooting

**Istio common issues:**

**Sidecar not injecting:**
```bash
# Check namespace label
kubectl get namespace default --show-labels

# Manually inject
kubectl get deploy app -o yaml | istioctl kube-inject -f - | kubectl apply -f -
```

**mTLS failures:**
```bash
# Check policies
kubectl get peerauthentication --all-namespaces
kubectl get destinationrule --all-namespaces

# Verify certificates
istioctl proxy-config secret <pod>
```

**Linkerd common issues:**

**Proxy not injecting:**
```bash
# Check annotation
kubectl get namespace production -o yaml | grep inject

# Reinject
kubectl get deploy app -o yaml | linkerd inject - | kubectl apply -f -
```

**Certificate errors:**
```bash
linkerd check --proxy
kubectl logs -n linkerd deploy/linkerd-identity
```
