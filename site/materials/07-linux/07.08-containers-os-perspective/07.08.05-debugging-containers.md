# Lesson 5: Debugging Containers from the Host

## Learning Objectives

By the end of this lesson, you will be able to:
- Debug containers using docker debug command
- Access container processes from the host
- Inspect container namespaces from the host
- Troubleshoot networking issues from the host
- Debug containers without exec access
- Use host tools to diagnose container problems
- Understand when to debug from host vs inside container

---

## Introduction

Debugging containers from the host is essential when containers lack debugging tools, are hardened for security, or have crashed. Understanding how to inspect processes, filesystems, and network from the host level allows you to troubleshoot issues that would be impossible to diagnose from within the container. This lesson teaches you host-level debugging techniques for production container environments.

## Key Concepts Summary

### Why Debug from Host?

**Use cases:**
```
1. Container lacks debugging tools
   - Slim/hardened images (Alpine, distroless)
   - Production security requirements
   - Minimal base images

2. Container is inaccessible
   - Crashed or restarting
   - No shell available
   - Exec disabled

3. Host-level issues
   - Network configuration
   - Storage problems
   - Resource limits
   - Kernel issues

4. Security investigation
   - Suspicious behavior
   - Post-breach analysis
   - Forensics
```

### Docker Debug Command

**What is docker debug?**
- Attaches debug shell to container
- Provides tool-rich environment
- Doesn't modify original container
- Ephemeral debug container

**Basic usage:**
```bash
# Debug running container
docker debug container_name

# Debug with specific image
docker debug --image ubuntu:22.04 container_name

# Debug even slim images
docker debug distroless-container
```

**How it works:**
```
1. Creates privileged debug container
2. Shares namespaces with target
3. Provides debugging tools
4. Mounts target filesystem
5. Cleanup when exit
```

**Available tools:**
```
Pre-installed in debug container:
- vim, nano     - Text editors
- curl, wget    - Network tools
- htop, ps      - Process monitoring
- strace        - System call tracing
- tcpdump       - Network capture
- And many more...
```

**Example:**
```bash
# Start hardened container
docker run -d --name app distroless/java:11

# Try to exec (fails - no shell)
docker exec app sh
# Error: executable file not found

# Debug instead
docker debug app

# Now have full shell with tools
# Can inspect processes, files, network
```

### Accessing Container Processes

**Find container processes:**
```bash
# Get container PID
docker inspect -f '{{.State.Pid}}' container_name

# Or
PID=$(docker inspect -f '{{.State.Pid}}' container_name)

# View process tree
ps -ef | grep $PID
pstree -p $PID

# View process details
ps aux -p $PID
cat /proc/$PID/status
```

**View all container processes:**
```bash
# Container's process namespace
ps -eo pid,ppid,cmd --forest | grep -A 20 "docker"

# Or use docker top
docker top container_name

# With custom format
docker top container_name aux
```

**Inspect process from host:**
```bash
PID=$(docker inspect -f '{{.State.Pid}}' container_name)

# Process environment
cat /proc/$PID/environ | tr '\0' '\n'

# Open files
lsof -p $PID

# Network connections
ss -p | grep $PID

# Memory maps
cat /proc/$PID/maps

# Current working directory
ls -la /proc/$PID/cwd
```

### Accessing Container Filesystem

**Container root filesystem:**
```bash
# Get container ID
CONTAINER_ID=$(docker inspect -f '{{.Id}}' container_name)

# Overlay merged directory
MERGED_DIR="/var/lib/docker/overlay2/${CONTAINER_ID}/merged"

# Access filesystem
sudo ls -la $MERGED_DIR

# Read files
sudo cat $MERGED_DIR/etc/nginx/nginx.conf

# View logs
sudo tail -f $MERGED_DIR/var/log/app.log
```

**Using nsenter:**
```bash
# Enter mount namespace
PID=$(docker inspect -f '{{.State.Pid}}' container_name)
nsenter -t $PID -m bash

# Now inside container's filesystem view
ls /
cat /etc/hostname
```

**Copy files:**
```bash
# Copy from container
docker cp container_name:/path/to/file /host/path

# Copy to container
docker cp /host/path container_name:/path/to/file

# Even works on stopped containers
```

### Debugging Networking

**View container network:**
```bash
# Container IP
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' container_name

# Network namespace
PID=$(docker inspect -f '{{.State.Pid}}' container_name)
readlink /proc/$PID/ns/net

# Enter network namespace
nsenter -t $PID -n bash

# Now can run network commands
ip addr show
ss -tulpn
netstat -an
```

**Capture network traffic:**
```bash
# From host (need interface name)
docker inspect -f '{{.NetworkSettings.SandboxKey}}' container_name

# Find veth pair
ip link | grep -A 1 docker

# Capture with tcpdump
tcpdump -i veth1234567 -w capture.pcap

# Or use docker debug
docker debug container_name
tcpdump -i eth0
```

**Test connectivity:**
```bash
# From host to container
CONTAINER_IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' container_name)
ping $CONTAINER_IP
curl http://$CONTAINER_IP:80

# Container to host
docker exec container_name ping host.docker.internal

# Container to container
docker exec container1 ping container2
```

### Using nsenter

**What is nsenter?**
- Enters Linux namespaces
- Accesses container resources
- Runs commands in namespace
- Powerful debugging tool

**Enter all namespaces:**
```bash
PID=$(docker inspect -f '{{.State.Pid}}' container_name)
nsenter --target $PID --all bash

# Equivalent to docker exec but works when exec doesn't
```

**Enter specific namespaces:**
```bash
# Mount namespace only
nsenter -t $PID -m bash

# Network namespace only
nsenter -t $PID -n bash

# PID namespace only
nsenter -t $PID -p bash

# Multiple namespaces
nsenter -t $PID -m -n bash
```

**Run single command:**
```bash
# Run command in namespace
nsenter -t $PID -m ls /app

# Check network config
nsenter -t $PID -n ip addr show

# View process tree
nsenter -t $PID -p ps aux
```

### Debugging Crashed Containers

**View container logs:**
```bash
# Last logs before crash
docker logs container_name

# Follow logs
docker logs -f container_name

# With timestamps
docker logs -t container_name

# Last 100 lines
docker logs --tail 100 container_name
```

**Inspect exit status:**
```bash
# Check exit code
docker inspect -f '{{.State.ExitCode}}' container_name

# Common exit codes:
# 0   - Success
# 1   - General error
# 125 - Docker daemon error
# 126 - Command cannot execute
# 127 - Command not found
# 137 - SIGKILL (OOM kill or manual)
# 143 - SIGTERM (graceful shutdown)
```

**Check for OOM kill:**
```bash
# OOM killed?
docker inspect -f '{{.State.OOMKilled}}' container_name

# System logs
dmesg | grep -i "oom"
journalctl -xe | grep -i "oom"

# Memory limit
docker inspect -f '{{.HostConfig.Memory}}' container_name
```

**Prevent restart to debug:**
```bash
# Update restart policy
docker update --restart=no container_name

# Container stays stopped after crash
# Can inspect filesystem, logs, etc.
```

### Debugging Daemon Issues

**Check daemon logs:**
```bash
# Systemd systems
journalctl -xu docker.service

# Recent logs
journalctl -xu docker.service -n 100

# Follow logs
journalctl -xu docker.service -f

# Or traditional logs
tail -f /var/log/syslog | grep docker
tail -f /var/log/messages | grep docker
```

**Daemon configuration:**
```bash
# View daemon config
cat /etc/docker/daemon.json

# Check running daemon
dockerd --version
docker info

# Restart daemon
sudo systemctl restart docker
```

### Using strace

**Trace system calls:**
```bash
# Get container PID
PID=$(docker inspect -f '{{.State.Pid}}' container_name)

# Trace system calls
strace -p $PID

# With timestamps
strace -t -p $PID

# Follow forks
strace -f -p $PID

# Filter specific calls
strace -e trace=open,read,write -p $PID

# Save to file
strace -o trace.log -p $PID
```

**Trace container startup:**
```bash
# Trace docker exec
strace docker exec container_name command

# Trace container start
strace docker start container_name
```

### Practical Debugging Workflows

**Workflow 1: Unresponsive container**
```bash
# 1. Check if running
docker ps | grep container_name

# 2. Check logs
docker logs --tail 50 container_name

# 3. Check resource usage
docker stats container_name --no-stream

# 4. Check processes
docker top container_name

# 5. Enter debug shell
docker debug container_name

# 6. Investigate inside
ps aux
netstat -tulpn
df -h
```

**Workflow 2: Network connectivity issue**
```bash
# 1. Get container IP
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' container_name

# 2. Test from host
ping $CONTAINER_IP
curl http://$CONTAINER_IP:80

# 3. Check port mappings
docker port container_name

# 4. Enter network namespace
PID=$(docker inspect -f '{{.State.Pid}}' container_name)
nsenter -t $PID -n bash

# 5. Debug network
ip addr
ip route
ss -tulpn
ping 8.8.8.8
```

**Workflow 3: File permission issue**
```bash
# 1. Check container user
docker exec container_name id

# 2. View file permissions
docker exec container_name ls -la /app

# 3. Access from host
CONTAINER_ID=$(docker inspect -f '{{.Id}}' container_name)
sudo ls -la /var/lib/docker/overlay2/${CONTAINER_ID}/merged/app

# 4. Fix permissions
docker exec container_name chown -R app:app /app
```

### Best Practices

**Security:**
```
- Use docker debug for minimal images
- Avoid privileged debug containers when possible
- Remove debug containers after use
- Don't leave debug tools in production images
- Log debugging sessions
- Follow least privilege principle
```

**Efficiency:**
```
- Start with logs and stats
- Use docker debug for interactive debugging
- Use nsenter for specific namespace access
- Save strace output for offline analysis
- Document debugging steps
- Automate common checks
```

**Production:**
```
- Enable appropriate logging
- Use monitoring tools
- Keep debug capabilities available
- Test debugging procedures
- Train team on debugging techniques
- Have runbooks for common issues
```
