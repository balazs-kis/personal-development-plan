## Introduction

Recording rules and alerting rules are essential features of Prometheus that improve performance and enable proactive monitoring. Recording rules precompute frequently-needed expressions and save results as new time series, while alerting rules define conditions that trigger notifications. Together, they form the foundation of production monitoring systems.

## Key Concepts Summary

### Recording Rules

**Recording rules** precompute frequently-needed or computationally expensive expressions and save their results as new time series.

**Why use recording rules:**
```
Benefits:
✓ Improve dashboard load times
✓ Reduce query latency for complex queries
✓ Simplify commonly used expressions
✓ Enable aggregation at lower cost
✓ Create derived metrics

Use cases:
→ Expensive aggregations used in multiple dashboards
→ Frequently queried percentiles
→ Multi-step calculations (rates of rates)
→ Level-based aggregations
```

#### Recording Rule Structure

**Basic format:**
```yaml
groups:
  - name: example-group
    interval: 30s  # How often to evaluate (optional)
    rules:
      - record: metric:aggregation:operation
        expr: <PromQL expression>
        labels:
          # Optional additional labels
```

**Complete example:**
```yaml
groups:
  - name: api-metrics
    interval: 30s
    rules:
      # Record request rate by job
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
      
      # Record error rate percentage
      - record: job:http_errors:rate5m_percent
        expr: |
          sum by (job) (rate(http_requests_total{status=~"5.."}[5m])) /
          sum by (job) (rate(http_requests_total[5m])) * 100
      
      # Record 95th percentile latency
      - record: job:http_request_duration:p95
        expr: |
          histogram_quantile(0.95,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m])))
```

#### Naming Convention

**Format: `level:metric:operations`**

```
level:       Aggregation level and labels retained
metric:      Base metric name (preserve original if possible)
operations:  List of operations applied (newest first)
```

**Examples:**
```yaml
# Good naming
✓ job:http_requests_total:rate5m
✓ instance:cpu:usage_percent
✓ job_method:http_requests:rate5m
✓ cluster:memory:available_bytes

# Bad naming
✗ http_rate                    # Lacks context
✗ http_requests_job_rate       # Wrong order
✗ rate5m_http_requests         # Operations should be last
```

**Breakdown:**
```
job:http_requests_total:rate5m
│   │                   │
│   │                   └─ Operation: rate over 5 minutes
│   └─ Metric: http_requests_total
└─ Level: aggregated by job
```

#### Multi-Level Aggregations

Build aggregations progressively:

```yaml
groups:
  - name: http-requests
    rules:
      # Level 1: Aggregate to instance level
      - record: instance:http_requests:rate5m
        expr: sum by (instance) (rate(http_requests_total[5m]))
      
      # Level 2: Aggregate to job level
      - record: job:http_requests:rate5m
        expr: sum by (job) (instance:http_requests:rate5m)
      
      # Level 3: Aggregate to cluster level
      - record: cluster:http_requests:rate5m
        expr: sum(job:http_requests:rate5m)
```

**Benefits:**
- Reuse lower-level aggregations
- Reduce computation cost
- Enable flexible querying at different levels

### Alerting Rules

**Alerting rules** define conditions that trigger notifications when met.

#### Alert Rule Structure

**Basic format:**
```yaml
groups:
  - name: alert-group
    interval: 30s
    rules:
      - alert: AlertName
        expr: <PromQL expression>
        for: <duration>
        labels:
          severity: critical
        annotations:
          summary: "Alert summary"
          description: "Alert description"
```

**Complete example:**
```yaml
groups:
  - name: instance-alerts
    rules:
      - alert: InstanceDown
        expr: up == 0
        for: 5m
        labels:
          severity: critical
          component: infrastructure
        annotations:
          summary: "Instance {{ $labels.instance }} is down"
          description: |
            Instance {{ $labels.instance }} of job {{ $labels.job }}
            has been down for more than 5 minutes.
          runbook_url: "https://wiki.example.com/runbooks/instance-down"
```

#### Alert States

Alerts go through three states:

```
Inactive → Pending → Firing
```

**State transitions:**
```
1. Inactive: Condition is false
   expr evaluates to false

2. Pending: Condition is true, waiting for 'for' duration
   expr == true, but not yet for full duration
   
3. Firing: Condition true for 'for' duration
   expr == true for entire 'for' period
   Alert sent to Alertmanager
```

**Example:**
```yaml
- alert: HighCPU
  expr: cpu_usage_percent > 80
  for: 10m  # Must be true for 10 minutes before firing
```

#### Alert Labels

**Labels** categorize and route alerts:

```yaml
labels:
  severity: critical       # critical, warning, info
  team: backend           # Routing to teams
  component: database     # System component
  environment: production # Environment
```

**Common severity levels:**
```
critical → Page on-call engineer immediately
warning  → Create ticket, notify during business hours
info     → Log for awareness, no immediate action
```

**Using labels for routing:**
```yaml
# Alertmanager routes based on labels
route:
  receiver: default
  routes:
    - match:
        severity: critical
      receiver: pagerduty
    
    - match:
        severity: warning
        team: backend
      receiver: backend-slack
```

#### Alert Annotations

**Annotations** provide context (not used for routing):

```yaml
annotations:
  summary: "Short description of alert"
  description: "Detailed description with context"
  runbook_url: "Link to runbook"
  dashboard_url: "Link to relevant dashboard"
```

**Using template variables:**
```yaml
annotations:
  summary: "High CPU on {{ $labels.instance }}"
  description: |
    CPU usage is {{ $value }}% on instance {{ $labels.instance }}
    in job {{ $labels.job }}.
  
  # Available variables:
  # {{ $labels.<labelname> }} - Label values
  # {{ $value }} - Expression result value
  # {{ $externalLabels }} - External labels
```

### Common Alerting Patterns

#### 1. Instance Down

```yaml
- alert: InstanceDown
  expr: up == 0
  for: 5m
  labels:
    severity: critical
  annotations:
    summary: "Instance {{ $labels.instance }} down"
    description: "{{ $labels.instance }} of job {{ $labels.job }} has been down for more than 5 minutes."
```

#### 2. High Error Rate

```yaml
- alert: HighErrorRate
  expr: |
    sum by (job) (rate(http_requests_total{status=~"5.."}[5m])) /
    sum by (job) (rate(http_requests_total[5m])) > 0.05
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "High error rate on {{ $labels.job }}"
    description: "Error rate is {{ $value | humanizePercentage }} on job {{ $labels.job }}."
```

#### 3. High Latency

```yaml
- alert: HighLatency
  expr: |
    histogram_quantile(0.95,
      sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))
    ) > 1.0
  for: 15m
  labels:
    severity: warning
  annotations:
    summary: "High latency on {{ $labels.job }}"
    description: "95th percentile latency is {{ $value }}s on job {{ $labels.job }}."
```

#### 4. Disk Space Low

```yaml
- alert: DiskSpaceLow
  expr: |
    (node_filesystem_avail_bytes{mountpoint="/"} /
     node_filesystem_size_bytes{mountpoint="/"}) < 0.10
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "Disk space low on {{ $labels.instance }}"
    description: "Disk space is below 10% on {{ $labels.instance }}."
```

#### 5. Predicted Disk Full

```yaml
- alert: DiskWillFillIn4Hours
  expr: |
    predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[1h], 4*3600) < 0
  for: 30m
  labels:
    severity: warning
  annotations:
    summary: "Disk will fill soon on {{ $labels.instance }}"
    description: "Filesystem is predicted to fill within 4 hours on {{ $labels.instance }}."
```

#### 6. Service Not Available

```yaml
- alert: ServiceUnavailable
  expr: absent(up{job="critical-service"})
  for: 5m
  labels:
    severity: critical
  annotations:
    summary: "Critical service not being scraped"
    description: "The critical-service job has no targets being scraped."
```

#### 7. Memory Pressure

```yaml
- alert: HighMemoryUsage
  expr: |
    (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) > 0.90
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "High memory usage on {{ $labels.instance }}"
    description: "Memory usage is {{ $value | humanizePercentage }} on {{ $labels.instance }}."
```

### Configuration and Validation

#### Loading Rules

**prometheus.yml:**
```yaml
# Prometheus configuration
global:
  evaluation_interval: 15s  # How often to evaluate rules

rule_files:
  - "rules/*.yml"           # Load all rule files
  - "alerts/alerts.yml"     # Specific file
```

#### Validating Rules

**Check syntax before deploying:**
```bash
# Validate rule file
promtool check rules /path/to/rules.yml

# Example output:
# Checking /path/to/rules.yml
#   SUCCESS: 5 rules found
```

**Check specific queries:**
```bash
# Test if query is valid
promtool check query 'up == 0'
```

#### Reloading Rules

```bash
# Hot reload without restart
kill -HUP <prometheus-pid>

# Or via HTTP
curl -X POST http://localhost:9090/-/reload
```

### Best Practices

**1. Use `for` clause to prevent flapping:**
```yaml
# Bad - fires immediately
- alert: HighCPU
  expr: cpu_usage > 80

# Good - waits 10 minutes
- alert: HighCPU
  expr: cpu_usage > 80
  for: 10m
```

**2. Add runbook links:**
```yaml
annotations:
  runbook_url: "https://wiki.example.com/runbooks/high-cpu"
```

**3. Make alerts actionable:**
```yaml
# Bad - vague
summary: "Something is wrong"

# Good - specific
summary: "High CPU usage ({{ $value }}%) on {{ $labels.instance }}"
description: |
  CPU has been above 80% for 10 minutes.
  Check processes: top -n 1
  Check load: uptime
```

**4. Use recording rules for complex alert expressions:**
```yaml
# Recording rule
- record: job:error_rate:rate5m
  expr: |
    sum by (job) (rate(errors_total[5m])) /
    sum by (job) (rate(requests_total[5m]))

# Alert uses recording rule
- alert: HighErrorRate
  expr: job:error_rate:rate5m > 0.05
  for: 10m
```

**5. Group related rules:**
```yaml
groups:
  - name: node-exporter-alerts
    rules:
      - alert: NodeDown
      - alert: NodeHighCPU
      - alert: NodeHighMemory
  
  - name: application-alerts
    rules:
      - alert: AppHighErrorRate
      - alert: AppHighLatency
```

**6. Use appropriate intervals:**
```yaml
# Fast-changing metrics: short interval
- name: request-rates
  interval: 15s
  
# Slow-changing metrics: longer interval
- name: capacity-planning
  interval: 5m
```

## Key Takeaways

- **Recording rules** precompute expensive queries for performance
- Use **`level:metric:operations`** naming convention
- **Alerting rules** define when to send notifications
- Use **`for`** clause to prevent alert flapping
- **Labels** are for routing; **annotations** are for context
- Always include **runbook URLs** in alerts
- **Validate rules** with `promtool` before deploying
- Make alerts **specific and actionable**
