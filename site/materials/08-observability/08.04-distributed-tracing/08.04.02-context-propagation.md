## Introduction

Context propagation is the mechanism that allows distributed tracing to work across service boundaries. When Service A calls Service B, the trace context (trace ID, span ID) must be passed along so that Service B's spans can be linked to the same trace. The W3C Trace Context standard defines how this information is serialized and transmitted.

## Key Concepts Summary

### What is Context Propagation?

**Context propagation** is the mechanism that moves trace information (trace ID, span ID, and metadata) between services and processes in a distributed system.

```
Without Context Propagation:
Service A: Trace ID = abc123
Service B: Trace ID = xyz789  ❌ New trace! Lost context!
Service C: Trace ID = def456  ❌ Another new trace!

With Context Propagation:
Service A: Trace ID = abc123
Service B: Trace ID = abc123  ✓ Same trace!
Service C: Trace ID = abc123  ✓ Same trace!
```

### How Context Propagation Works

Context propagation operates in four steps:

```
1. SERIALIZE: Convert trace context to string format
   ↓
2. INJECT: Add context to outgoing request (HTTP headers)
   ↓
3. EXTRACT: Read context from incoming request
   ↓
4. DESERIALIZE: Parse context back to trace objects
```

**Example flow:**

```
Service A                        Service B
---------                        ---------
1. Create span                   
   Trace ID: abc123
   Span ID: span1
                                 
2. Make HTTP call    ───────→    3. Receive request
   Headers:                         Headers:
   traceparent: 00-abc123-          traceparent: 00-abc123-
     span1-01                         span1-01
                                 
                                 4. Extract context
                                    Parent Trace: abc123
                                    Parent Span: span1
                                    
                                 5. Create child span
                                    Trace ID: abc123
                                    Span ID: span2
                                    Parent: span1
```

### W3C Trace Context Standard

The **W3C Trace Context** is the industry standard for propagating trace information. It defines two HTTP headers:

#### 1. traceparent Header

The `traceparent` header carries essential trace context:

```
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
             │  │                                │                │
             │  │                                │                └─ Trace flags
             │  │                                └─ Parent span ID (16 hex chars)
             │  └─ Trace ID (32 hex characters)
             └─ Version (00 = version 0)
```

**Field breakdown:**

1. **Version** (2 hex digits): Currently `00`
   - Indicates the format version
   - Allows for future changes to the format

2. **Trace ID** (32 hex digits): Unique identifier for the trace
   - 128-bit number represented as 32 hex characters
   - Example: `0af7651916cd43dd8448eb211c80319c`
   - Must be unique across all traces

3. **Parent Span ID** (16 hex digits): Identifier of the calling span
   - 64-bit number represented as 16 hex characters
   - Example: `b7ad6b7169203331`
   - Links child spans to their parent

4. **Trace Flags** (2 hex digits): Sampling and other flags
   - `01` = sampled (trace should be recorded)
   - `00` = not sampled (trace can be dropped)

#### 2. tracestate Header

The `tracestate` header carries vendor-specific context:

```
tracestate: vendor1=value1,vendor2=value2
```

**Purpose:**
- Allows vendors to add custom trace data
- Preserves information across different tracing systems
- Maintains compatibility between different backends

### Context Propagation in HTTP

**Outgoing request (Service A):**

```csharp
// OpenTelemetry automatically injects headers
var client = new HttpClient();
var response = await client.GetAsync("http://service-b/api/data");

// HTTP Headers automatically include:
// traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
```

**Incoming request (Service B):**

```csharp
// OpenTelemetry automatically extracts headers
[HttpGet("data")]
public IActionResult GetData()
{
    // Current Activity inherits trace context from headers
    var traceId = Activity.Current?.TraceId;  // 0af7651916cd43dd8448eb211c80319c
    var spanId = Activity.Current?.SpanId;    // (new span ID)
    var parentId = Activity.Current?.ParentSpanId; // b7ad6b7169203331
    
    // Your code here...
}
```

### Propagators

**Propagators** handle serialization and deserialization of context.

OpenTelemetry supports multiple propagation formats:

```csharp
// Configure propagation format
builder.Services.Configure<OpenTelemetryLoggerOptions>(logging => 
    logging.SetResourceBuilder(ResourceBuilder.CreateDefault()
        .AddService("my-service")));

// Common propagators:
// 1. W3C Trace Context (default, recommended)
// 2. B3 (Zipkin format)
// 3. Jaeger format
// 4. AWS X-Ray format
```

**W3C Trace Context is the default and recommended propagator** as it's the industry standard.

### Context Propagation Across Different Transports

#### HTTP/REST

```
GET /api/orders HTTP/1.1
Host: order-service.example.com
traceparent: 00-abc123...-span1-01
tracestate: vendor=xyz
```

#### gRPC

```csharp
// Context automatically propagated via metadata
var call = client.GetOrderAsync(
    new OrderRequest { OrderId = 123 });
```

#### Message Queues (RabbitMQ, Kafka)

```csharp
// Context propagated via message headers/properties
await producer.SendAsync(new Message
{
    Headers = 
    {
        ["traceparent"] = "00-abc123...-span1-01"
    },
    Body = payload
});
```

### Manual Context Propagation

Sometimes you need to manually propagate context:

```csharp
// Extract current context
var activity = Activity.Current;
var traceId = activity?.TraceId.ToString();
var spanId = activity?.SpanId.ToString();

// Inject into custom transport (e.g., background job)
await _queueService.EnqueueJob(new Job
{
    TraceId = traceId,
    ParentSpanId = spanId,
    Payload = data
});

// Later, restore context
var restoredActivity = new Activity("ProcessJob");
restoredActivity.SetParentId(
    ActivityTraceId.CreateFromString(job.TraceId),
    ActivitySpanId.CreateFromString(job.ParentSpanId));
restoredActivity.Start();

// Process job...

restoredActivity.Stop();
```

### Context Propagation Patterns

#### 1. Chain Pattern (Sequential)

```
Request → Service A → Service B → Service C

Trace:
├─ Service A span [parent]
   └─ Service B span
      └─ Service C span
```

#### 2. Fan-Out Pattern (Parallel)

```
              ┌─→ Service B
Request → A ──┼─→ Service C
              └─→ Service D

Trace:
├─ Service A span [parent]
   ├─ Service B span
   ├─ Service C span
   └─ Service D span
```

#### 3. Mixed Pattern

```
              ┌─→ Service B ─→ Service D
Request → A ──┤
              └─→ Service C ─→ Service E

Trace:
├─ Service A span
   ├─ Service B span
   │  └─ Service D span
   └─ Service C span
      └─ Service E span
```

### Common Issues and Troubleshooting

#### Problem: Broken Trace Chain

```
✗ Symptom: Spans appear as separate traces
✗ Cause: Context not propagated

Solution:
✓ Ensure automatic instrumentation is enabled
✓ Check that HTTP client is instrumented
✓ Verify propagator is configured correctly
```

#### Problem: Missing Parent-Child Relationship

```csharp
// Wrong: Creating spans without context
using var span = activitySource.StartActivity("Operation");
// This creates a root span, not a child!

// Right: OpenTelemetry automatically links to parent
using var span = activitySource.StartActivity("Operation");
// If Activity.Current exists, this becomes a child span
```

#### Problem: Context Lost in Async Operations

```csharp
// Potential issue: Task.Run may lose context
await Task.Run(() => 
{
    // Activity.Current might be null here!
});

// Better: Use await directly
await SomeAsyncOperation();
// Activity.Current flows automatically
```

### Best Practices

**1. Always Use Automatic Propagation:**
```csharp
// Let OpenTelemetry handle propagation
services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()); // ← Enables propagation
```

**2. Use W3C Trace Context:**
```csharp
// W3C is the standard and works everywhere
// (It's the default in OpenTelemetry)
```

**3. Preserve Context in Background Jobs:**
```csharp
// Capture context when queuing
var currentActivity = Activity.Current;
await _queue.Enqueue(new Job 
{ 
    TraceContext = currentActivity?.Id 
});
```

**4. Test Context Propagation:**
```csharp
// Verify trace IDs match across services
var traceId = Activity.Current?.TraceId;
_logger.LogInformation("Processing with trace: {TraceId}", traceId);
```

## Key Takeaways

- **Context propagation** enables distributed tracing across service boundaries
- The **W3C Trace Context standard** defines the `traceparent` header format
- **traceparent** contains: version, trace ID, parent span ID, and flags
- OpenTelemetry **automatically propagates** context for instrumented libraries
- Context flows through **four steps**: serialize → inject → extract → deserialize
- **Broken propagation** results in disconnected traces
- Always use **automatic propagation** when possible
