## Introduction

Distributed tracing allows you to follow a request's journey through multiple services in a distributed system. At its core are two fundamental concepts: **traces** (the complete path of a request) and **spans** (individual units of work). Understanding these building blocks is essential for implementing effective observability in microservices architectures.

## Key Concepts Summary

### What is a Trace?

A **trace** represents the complete path a request takes through your application or distributed system. It gives you the "big picture" of what happens when a request is made, whether your system is a monolith or a sophisticated mesh of microservices.

```
Trace Example: E-commerce Order Flow

Trace ID: 0af7651916cd43dd8448eb211c80319c
Duration: 450ms

[API Gateway] ─┬─> [Order Service] ─┬─> [Inventory Service]
               │                     └─> [Payment Service]
               └─> [User Service]
```

**Key characteristics:**
- Has a unique **trace ID** that ties all related operations together
- Represents end-to-end request flow
- Can span multiple services, processes, and machines
- Shows both successful operations and failures

### What is a Span?

A **span** represents a single unit of work within a trace. Each span captures:
- The operation name
- Start and end timestamps
- Metadata (attributes/tags)
- The parent-child relationship with other spans

```
Span Example: Database Query

Span ID: b7ad6b7169203331
Parent Span ID: a2fb4a1d1a96d312
Operation: SELECT * FROM orders WHERE user_id = ?
Duration: 50ms
Attributes:
  - db.system: postgresql
  - db.name: ecommerce
  - db.statement: SELECT * FROM orders WHERE user_id = $1
  - db.user: app_user
```

### Span Hierarchy

Spans form a tree structure within a trace, showing parent-child relationships:

```
Root Span: HTTP GET /api/orders
├─ Span: OrderService.GetOrders()
│  ├─ Span: Database Query - Get Orders
│  └─ Span: Cache Lookup
├─ Span: UserService.GetUserInfo()
│  └─ Span: Database Query - Get User
└─ Span: HTTP GET /inventory-service/check
   └─ Span: InventoryService.CheckStock()
      └─ Span: Redis GET inventory:*
```

**Parent-Child Relationships:**
- **Root span**: The first span in a trace (no parent)
- **Child span**: Nested operation within a parent
- **Sibling spans**: Spans at the same level (same parent)

### Key Span Attributes

#### 1. Trace ID
A unique 128-bit identifier shared by all spans in a single trace.

```
Trace ID: 0af7651916cd43dd8448eb211c80319c
```

**Purpose:** Links all related operations together, even across service boundaries.

#### 2. Span ID
A unique 64-bit identifier for each individual span.

```
Span ID: b7ad6b7169203331
```

**Purpose:** Uniquely identifies this operation within the trace.

#### 3. Parent Span ID
The span ID of the parent span, establishing the hierarchy.

```
Parent Span ID: a2fb4a1d1a96d312
```

**Purpose:** Shows which operation triggered this operation.

#### 4. Timestamps
Start and end times for the operation.

```
Start: 2026-01-27T10:15:30.123Z
End:   2026-01-27T10:15:30.173Z
Duration: 50ms
```

#### 5. Attributes (Tags)
Key-value pairs providing context about the operation.

```csharp
// Example attributes
span.SetAttribute("http.method", "GET");
span.SetAttribute("http.url", "/api/orders/123");
span.SetAttribute("http.status_code", 200);
span.SetAttribute("user.id", "user-456");
```

#### 6. Events
Timestamped logs within a span.

```csharp
span.AddEvent("Cache miss - fetching from database");
span.AddEvent("Order validated successfully");
```

#### 7. Status
Indicates whether the operation succeeded or failed.

```csharp
span.SetStatus(ActivityStatusCode.Ok);
// or
span.SetStatus(ActivityStatusCode.Error, "Payment failed");
```

### Span Types (Kind)

Spans can have different types based on their role:

```csharp
// Internal operation
ActivityKind.Internal

// Client making a call to another service
ActivityKind.Client

// Server receiving a request
ActivityKind.Server

// Message producer
ActivityKind.Producer

// Message consumer
ActivityKind.Consumer
```

### Why Distributed Tracing Matters

**Problem without tracing:**
```
User reports: "The app is slow!"

Where's the slowness?
- Frontend? Backend? Database?
- Which service is slow?
- Which operation is slow?
- Is it always slow or intermittent?

❌ No visibility = No answers
```

**Solution with tracing:**
```
Trace shows:
✓ Payment Service: 2000ms (Problem found!)
  └─ External API call: 1950ms (Root cause!)

✓ All other services: <50ms
✓ Database queries: <30ms
✓ Cache operations: <5ms

✅ Complete visibility = Fast diagnosis
```

### Real-World Example

**E-commerce checkout flow:**

```
Trace ID: abc123
Total Duration: 850ms

1. API Gateway receives request [5ms]
   └─ Validates JWT token

2. Order Service processes checkout [800ms]
   ├─ Inventory Service checks stock [50ms]
   │  └─ Database query [45ms]
   │
   ├─ Payment Service charges card [700ms] ⚠️ SLOW
   │  ├─ External payment API [680ms] ⚠️ ROOT CAUSE
   │  └─ Database transaction [15ms]
   │
   └─ Shipping Service creates shipment [30ms]
      └─ HTTP POST to warehouse API [25ms]

3. Order confirmation sent [15ms]

DIAGNOSIS: External payment API is slow (680ms)
ACTION: Implement timeout or switch providers
```

## Key Takeaways

- A **trace** is the complete journey of a request through your system
- A **span** is a single unit of work within that journey
- **Trace IDs** link all spans belonging to the same request
- **Parent span IDs** establish the hierarchy between operations
- Spans capture **timing, metadata, and status** for each operation
- Distributed tracing reveals **where time is spent** and **where errors occur**
- Without tracing, debugging distributed systems is nearly impossible
