# Lesson 1: Alert Design Principles

## Learning Objectives

By the end of this lesson, you will be able to:
- Design alerts that focus on business impact and actionability
- Apply principles to reduce alert fatigue
- Implement alert quality management practices
- Create alerts that are descriptive and include remediation guidance

---

## Introduction

Alert fatigue occurs when teams receive too many alerts or false alarms, causing responders to become desensitized and ignore critical issues. Effective alert design focuses on creating fewer, more valuable alerts that drive action and minimize noise.

## Key Concepts Summary

### Focus on Business Impact
Only create alerts for conditions that matter to your business and affect customers. If customers aren't impacted, avoid creating high-priority alerts. Ask yourself: "Does this require immediate human action?"

```yaml
# Good: Alerts on customer-facing impact
alert: HighErrorRate
expr: rate(http_requests_total{status=~"5.."}[5m]) > 0.05
annotations:
  summary: "High error rate affecting users"
  description: "{{ $value | humanizePercentage }} of requests are failing"
  impact: "Customers cannot complete purchases"
  
# Bad: Alerts on every infrastructure hiccup  
alert: HighCPUUsage
expr: cpu_usage > 70
# This may not affect users at all
```

### Actionability First
Every alert should answer three questions:
1. **What is wrong?** - Clear description of the problem
2. **Why does it matter?** - Business impact statement
3. **What should I do?** - Link to runbook or remediation steps

```yaml
annotations:
  summary: "API Gateway request latency is high"
  description: "P95 latency is {{ $value }}ms (threshold: 500ms)"
  impact: "Users experiencing slow page loads"
  runbook_url: "https://wiki.company.com/runbooks/api-gateway-latency"
```

### Alert Quality Management

Use these metrics to identify problematic alerts:
- **Alert Volume:** Total number of alerts over time
- **Mean Time to Resolve (MTTR):** How long alerts stay open
- **Alert Acknowledge Rate:** Percentage of alerts acknowledged
- **False Positive Rate:** Alerts that don't require action

### Reduce Alert Volume Through Aggregation

Rather than alerting on each individual instance failure, aggregate related failures:

```yaml
# Good: Aggregate by service
alert: ServiceDegraded
expr: |
  (count by (service) (up{job="api"} == 0) / 
   count by (service) (up{job="api"})) > 0.5
annotations:
  summary: "{{ $labels.service }} is degraded"
  description: "More than 50% of instances are down"

# Bad: Alert on each instance
alert: InstanceDown
expr: up{job="api"} == 0
# Creates alert storm during outages
```

### Make Alerts Descriptive

Include relevant context in alert titles and descriptions:
- Avoid generic messages like "Service is down"
- Include specific metrics and thresholds
- Add relevant labels (region, environment, service)

```yaml
# Good
alert: DatabaseConnectionPoolExhausted
annotations:
  summary: "Database connection pool exhausted in {{ $labels.region }}"
  description: |
    Connection pool usage: {{ $value | humanizePercentage }}
    Available connections: 0
    Environment: {{ $labels.environment }}

# Bad
alert: DatabaseIssue
annotations:
  summary: "Database problem"
```

1. Three alerts that might be creating noise (not actionable or low business impact)
