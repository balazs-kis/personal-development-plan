# Lesson 3: Alert Severity and Routing

## Learning Objectives

By the end of this lesson, you will be able to:
- Classify alerts by severity and priority
- Design alert routing and escalation policies
- Configure notification channels appropriately
- Implement alert grouping and deduplication
- Reduce alert noise through inhibition and silencing

---

## Introduction

Not all alerts require the same response. Alert severity classification and intelligent routing ensure the right people are notified about the right problems at the right time, preventing alert fatigue while maintaining rapid response for critical issues.

## Key Concepts Summary

### Alert Severity Levels

Classify alerts into clear priority levels:

**Critical (P1) - Immediate Response Required 24/7**
- Production-impacting failures
- Requires immediate human action
- Page on-call engineer via phone/SMS
- Example: Complete service outage, data loss

```yaml
alert: ServiceDown
labels:
  severity: critical
  priority: P1
annotations:
  summary: "Service {{ $labels.service }} is completely down"
  description: "0 healthy instances available"
  impact: "All users unable to access the service"
  paging: "true"
```

**High (P2) - Action Required Within Business Hours**
- Degraded service affecting some users
- Requires action within 24 hours
- Send to team channel/email
- Example: Elevated error rates, performance degradation

```yaml
alert: ErrorRateElevated
labels:
  severity: high
  priority: P2
annotations:
  summary: "Error rate above threshold"
  description: "{{ $value | humanizePercentage }} of requests failing"
  impact: "Some users experiencing intermittent failures"
```

**Warning (P3) - Action Needed Eventually**
- Potential future issues
- Requires action but not urgent
- Ticket/email notification
- Example: Resource trending toward limits

```yaml
alert: DiskSpaceLow
labels:
  severity: warning
  priority: P3
annotations:
  summary: "Disk space below 20% on {{ $labels.instance }}"
  description: "Current usage: {{ $value | humanizePercentage }}"
  action: "Review and clean up old files"
```

**Info - Informational Only**
- Status changes, deployments
- No action required
- Dashboard/log only
- Example: Deployment completed, backup finished

```yaml
alert: DeploymentCompleted
labels:
  severity: info
annotations:
  summary: "Deployment of {{ $labels.service }} v{{ $labels.version }} completed"
```

### Alert Content Standards

Every alert should include:

```yaml
annotations:
  # Concise, descriptive title (not generic)
  summary: "API Gateway latency exceeds SLO"
  
  # Specific metric and threshold
  description: "P95 latency: {{ $value }}s (SLO: 500ms)"
  
  # Clear impact statement
  impact: "Users experiencing slow checkout process"
  
  # Actionable remediation steps or runbook
  runbook_url: "https://wiki.company.com/runbooks/api-latency"
  
  # Additional context
  dashboard_url: "https://grafana.company.com/d/api-dashboard"
  service: "{{ $labels.service }}"
  environment: "{{ $labels.environment }}"
```

### Alert Routing and Escalation

Configure routing trees to direct alerts to appropriate teams:

```yaml
# Alertmanager configuration
route:
  # Default receiver for unmatched alerts
  receiver: default-team
  
  # Group alerts to reduce notification storms
  group_by: ['alertname', 'cluster', 'service']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  
  # Route specific alerts to specific teams
  routes:
    # Critical alerts to on-call
    - match:
        severity: critical
      receiver: pagerduty-oncall
      group_wait: 10s
      repeat_interval: 5m
      
    # Database alerts to database team
    - match_re:
        service: database.*
      receiver: database-team
      
    # Frontend alerts during business hours
    - match:
        team: frontend
      receiver: frontend-team
      active_time_intervals:
        - business-hours

# Time intervals
time_intervals:
  - name: business-hours
    time_intervals:
      - times:
        - start_time: '09:00'
          end_time: '17:00'
        weekdays: ['monday:friday']
```

### Escalation Policies

Define escalation chains when alerts aren't acknowledged:

```yaml
# Example escalation policy
escalation_policy:
  - level: 1
    notification: pager
    timeout: 5m
    recipients:
      - primary-oncall
      
  - level: 2
    notification: phone_call
    timeout: 10m
    recipients:
      - primary-oncall
      - backup-oncall
      
  - level: 3
    notification: phone_call
    timeout: 15m
    recipients:
      - team-lead
      - engineering-manager
```

### Alert Grouping

Group related alerts to prevent notification storms:

```yaml
route:
  # Group by cluster and alertname
  group_by: ['cluster', 'alertname']
  
  # Wait 30s for more alerts before sending
  group_wait: 30s
  
  # Send grouped alerts every 5 minutes
  group_interval: 5m

# Instead of 100 alerts:
# - PodCrashLooping for pod-1
# - PodCrashLooping for pod-2
# - PodCrashLooping for pod-3
# ... 97 more

# You receive 1 grouped alert:
# - PodCrashLooping affecting 100 pods in production cluster
```

### Alert Deduplication and Inhibition

Prevent duplicate notifications and suppress dependent alerts:

```yaml
# Inhibition rules
inhibit_rules:
  # If cluster is down, suppress all pod alerts
  - source_match:
      alertname: ClusterDown
      severity: critical
    target_match:
      alertname: PodDown
    equal: ['cluster']
    
  # If database is down, suppress connection pool alerts
  - source_match:
      alertname: DatabaseDown
    target_match:
      alertname: DatabaseConnectionPoolHigh
    equal: ['database']
    
  # If deployment in progress, suppress some alerts
  - source_match:
      alertname: DeploymentInProgress
    target_match_re:
      alertname: (PodRestarting|HighErrorRate)
    equal: ['service']
```

### Silences

Temporarily mute alerts during maintenance:

```bash
# Silence alerts using Alertmanager API
amtool silence add \
  alertname="PodDown" \
  cluster="production" \
  --duration=2h \
  --comment="Planned maintenance window" \
  --author="ops-team"

# Or via Alertmanager UI
# Silences can match on any label combination
# Useful for: maintenance, known issues, testing
```

### Notification Channels

Configure appropriate channels by severity:

| Severity | Channels | Response Time |
|----------|----------|---------------|
| Critical | PagerDuty, Phone, SMS | Immediate |
| High | Slack, Email, Ticket | Within 24h |
| Warning | Ticket, Email | Best effort |
| Info | Dashboard, Logs | None |

```yaml
receivers:
  # Critical alerts
  - name: pagerduty-oncall
    pagerduty_configs:
      - service_key: <key>
        severity: critical
        
  # High priority alerts
  - name: team-slack
    slack_configs:
      - api_url: <webhook>
        channel: '#alerts-prod'
        title: 'Alert: {{ .GroupLabels.alertname }}'
        text: '{{ range .Alerts }}{{ .Annotations.description }}{{ end }}'
        
  # Warnings
  - name: ticketing-system
    webhook_configs:
      - url: 'https://tickets.company.com/api/create'
```
