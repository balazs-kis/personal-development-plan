# Lesson 1: Structured vs Unstructured Logging

## Learning Objectives

By the end of this lesson, you will be able to:
- Distinguish between structured and unstructured logging
- Understand the benefits of structured logging
- Recognize when to use JSON format for logs
- Convert unstructured logs to structured format
- Query and filter structured logs effectively

---

## Introduction

Traditional logging writes plain text messages to files, making them difficult to parse, search, and analyze programmatically. Structured logging formats logs as JSON objects with named fields, transforming logs from human-readable text into machine-readable data. This enables powerful querying, filtering, and correlation with other observability signals. Understanding this distinction is fundamental to modern observability.

## Key Concepts Summary

### Unstructured Logging

**What is it?**
```
Plain text log messages
Human-readable format
No machine-parseable structure
Traditional approach
```

**Example:**
```
2026-01-27 10:00:00 User John Doe with ID 123 made a purchase of $200.00
2026-01-27 10:01:15 ERROR: Payment gateway timeout for user 456
2026-01-27 10:02:30 INFO Request to /api/products took 250ms
```

**Characteristics:**
```
Format:      Free-form text
Parsing:     Regex required
Querying:    Text search only
Filtering:   Limited
Aggregation: Difficult
Machine-readable: No
```

**Problems:**
```
✗ Can't filter by user ID without regex
✗ Can't calculate average purchase amount
✗ Can't group by error type
✗ Hard to correlate with traces
✗ Inconsistent format across logs
✗ Expensive to parse at scale
```

### Structured Logging

**What is it?**
```
JSON-formatted log objects
Named fields with values
Machine-parseable structure
Modern observability approach
```

**Example:**
```json
{
  "timestamp": "2026-01-27T10:00:00Z",
  "level": "INFO",
  "message": "Purchase completed",
  "userId": "123",
  "userName": "John Doe",
  "amount": 200.00,
  "currency": "USD",
  "traceId": "abc-123-def"
}

{
  "timestamp": "2026-01-27T10:01:15Z",
  "level": "ERROR",
  "message": "Payment gateway timeout",
  "userId": "456",
  "error": "TimeoutException",
  "gateway": "stripe",
  "traceId": "xyz-789-ghi"
}
```

**Characteristics:**
```
Format:      JSON objects
Parsing:     Not needed (already parsed)
Querying:    Field-level queries
Filtering:   By any field
Aggregation: Easy
Machine-readable: Yes
```

**Benefits:**
```
✓ Filter by userId = "123"
✓ Calculate sum(amount) by userId
✓ Group by error type
✓ Correlate via traceId
✓ Consistent structure
✓ Efficient at scale
```

### Comparison

**Storage:**
```
Unstructured:
"2026-01-27 10:00:00 User 123 purchased $200"
Size: ~50 bytes as text

Structured:
{
  "timestamp": "2026-01-27T10:00:00Z",
  "userId": "123",
  "amount": 200.00,
  "event": "purchase"
}
Size: ~100 bytes as JSON

Trade-off: More storage for better queryability
```

**Querying:**
```
Unstructured:
grep "User 123" logs.txt
grep -E "purchased \$[0-9]+" logs.txt
→ Slow, regex required, limited

Structured:
WHERE userId = "123"
WHERE amount > 100
WHERE event = "purchase" AND userId = "123"
→ Fast, SQL-like, powerful
```

**Analysis:**
```
Unstructured:
"Extract purchase amounts" → Complex parsing
"Average amount per user" → Nearly impossible
"Group by error type" → Manual categorization

Structured:
SELECT AVG(amount) FROM logs WHERE event="purchase"
SELECT error, COUNT(*) FROM logs GROUP BY error
SELECT userId, SUM(amount) FROM logs GROUP BY userId
→ Simple queries, powerful insights
```

### JSON Format

**Basic structure:**
```json
{
  "timestamp": "ISO 8601 timestamp",
  "level": "INFO|WARN|ERROR",
  "message": "Human-readable description",
  "field1": "value1",
  "field2": 123,
  "field3": true,
  "nested": {
    "subfield": "value"
  }
}
```

**Common fields:**
```
timestamp:    When event occurred (ISO 8601)
level:        Log severity (INFO, ERROR, etc.)
message:      Human-readable message
logger:       Logger name or source
thread:       Thread ID
exception:    Exception details (if error)
```

**Application fields:**
```
userId:       User identifier
sessionId:    Session identifier
requestId:    Request/correlation ID
traceId:      Distributed trace ID
spanId:       Trace span ID
endpoint:     API endpoint
method:       HTTP method
statusCode:   HTTP status
duration:     Operation duration (ms)
```

**Business fields:**
```
event:        Business event type
amount:       Transaction amount
quantity:     Item quantity
product:      Product identifier
action:       User action
```

### When to Use Structured Logging

**Always use in:**
```
✓ Production environments
✓ Microservices
✓ Distributed systems
✓ Cloud-native applications
✓ High-volume systems
✓ Systems with log aggregation
```

**Consider unstructured for:**
```
? Local development (for readability)
? Legacy systems (migration cost)
? Simple applications (low volume)
? Console debugging

But structured is still better!
```

### Migration Strategy

**Step 1: Identify log statements**
```csharp
// Before: Unstructured
logger.LogInformation($"User {userId} purchased {productName} for ${amount}");

// After: Structured
logger.LogInformation(
    "Purchase completed",
    userId,
    productName,
    amount);
```

**Step 2: Extract variables**
```csharp
// Before: String interpolation
logger.LogError($"Payment failed for order {orderId}: {ex.Message}");

// After: Named parameters
logger.LogError(
    ex,
    "Payment failed for order {OrderId}",
    orderId);
```

**Step 3: Add context**
```csharp
// Before: Minimal info
logger.LogInformation("Order processed");

// After: Rich context
logger.LogInformation(
    "Order processed: {OrderId} by user {UserId}, amount {Amount}, items {ItemCount}",
    orderId,
    userId,
    amount,
    itemCount);
```

### Real-World Example

**Unstructured debugging:**
```
Problem: Find all errors for user "user-123"

Logs:
2026-01-27 10:00:00 ERROR Payment failed user=user-123
2026-01-27 10:01:00 Error: timeout (user: user-123)
2026-01-27 10:02:00 ERR user-123 invalid card

Solution: 
grep -i "user-123" logs.txt | grep -i "error"

Issues:
- Different formats
- May miss some
- No aggregation
- Manual work
```

**Structured debugging:**
```
Problem: Find all errors for user "user-123"

Query:
SELECT * FROM logs
WHERE userId = "user-123"
AND level = "ERROR"
ORDER BY timestamp DESC

Also easy:
- Count errors per user
- Group by error type
- Calculate error rate
- Correlate with traces
```

### Best Practices

**Do:**
```
✓ Use JSON format
✓ Include timestamp
✓ Add correlation IDs
✓ Use consistent field names
✓ Log at appropriate levels
✓ Include error details
✓ Add business context
```

**Don't:**
```
✗ Mix structured and unstructured
✗ Stringify objects (use fields)
✗ Include sensitive data
✗ Use inconsistent names
✗ Nest too deeply
✗ Log passwords/tokens
```

### Performance Considerations

**Structured logging overhead:**
```
JSON serialization:     Minimal (microseconds)
Additional fields:      Tiny (bytes per field)
Storage:               Slightly more than text
Query performance:     Much faster

Trade-off: Worth it!
```

**Optimization tips:**
```
✓ Use async logging
✓ Batch writes
✓ Sample high-volume logs
✓ Configure appropriate levels
✓ Use efficient serializers
```

## Practice Exercise

After completing the materials, convert these unstructured logs (spend 10 minutes):

```
Exercise: Convert to structured format

Unstructured logs:
1. "2026-01-27 10:00:00 User john@example.com logged in from 192.168.1.1"
2. "2026-01-27 10:01:00 ERROR Database connection timeout after 30s"
3. "2026-01-27 10:02:00 API request to /api/users took 250ms and returned 200"

Structured version:
1. {
     "timestamp": "2026-01-27T10:00:00Z",
     "level": "INFO",
     "event": "user_login",
     "message": "User logged in",
     "userEmail": "john@example.com",
     "ipAddress": "192.168.1.1"
   }

2. {
     "timestamp": "2026-01-27T10:01:00Z",
     "level": "ERROR",
     "event": "database_error",
     "message": "Database connection timeout",
     "error": "TimeoutException",
     "timeout": 30,
     "timeoutUnit": "seconds"
   }

3. {
     "timestamp": "2026-01-27T10:02:00Z",
     "level": "INFO",
     "event": "api_request",
     "message": "API request completed",
     "endpoint": "/api/users",
     "method": "GET",
     "duration": 250,
     "durationUnit": "ms",
     "statusCode": 200
   }

Benefits:
- Can query: WHERE event = "user_login"
- Can filter: WHERE duration > 200
- Can group: GROUP BY statusCode
- Can correlate: Add traceId field
```
