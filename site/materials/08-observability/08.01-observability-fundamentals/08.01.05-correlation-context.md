## Introduction

Correlation is what transforms separate telemetry signals into a complete observability story. Without correlation, you have disconnected logs, isolated metrics, and standalone traces. With proper correlation, you can jump from an alert to relevant logs, find the trace that shows where time was spent, and understand the full context of any issue. This lesson teaches you to build systems where everything connects.

## Key Concepts Summary

### What is Correlation?

**Definition:**
```
Correlation = Connecting related telemetry
Linking logs, metrics, traces
Providing context across signals
Enabling navigation between data
```

**Why it matters:**
```
Without correlation:
- Logs isolated from traces
- Metrics disconnected from context
- Hard to investigate issues
- Manual correlation needed

With correlation:
- Jump from alert to logs
- Find trace for error
- Full context instantly
- Fast debugging
```

### Correlation Identifiers

**Common correlation IDs:**
```
Trace ID:        Unique per request
Span ID:         Unique per operation
Request ID:      Alternative to trace ID
Correlation ID:  Custom identifier
User ID:         Per-user tracking
Session ID:      Per-session tracking
Transaction ID:  Business transaction
```

**Trace and span IDs:**
```
Trace ID:  abc-123-def-456 (unique per request)
Span ID:   xyz-789 (unique per operation)

Trace contains multiple spans:
Trace abc-123
├─ Span xyz-789 (API Gateway)
├─ Span xyz-790 (Auth Service)
└─ Span xyz-791 (Database)

All share same trace ID
Each has unique span ID
```

### Context Propagation

**What is context propagation?**
```
Passing correlation IDs between services
Maintaining context across boundaries
Enabling end-to-end tracking
```

**W3C Trace Context standard:**
```
HTTP Header: traceparent
Format: version-trace_id-span_id-flags

Example:
traceparent: 00-abc123def456-xyz789-01

Components:
00:        Version
abc123...: Trace ID (32 hex chars)
xyz789:    Span ID (16 hex chars)
01:        Flags (sampled)
```

**Propagation in action:**
```
1. Client request
   → Generate trace ID
   → Add to header

2. Service A receives
   → Extract trace ID
   → Create span
   → Pass to Service B

3. Service B receives
   → Extract trace ID
   → Create child span
   → Pass to Database

4. Database operation
   → Create DB span
   → Same trace ID

Result: Complete request trace
All operations linked
```

### Correlating Logs and Traces

**Adding trace context to logs:**
```csharp
using var activity = Activity.Current;

_logger.LogInformation(
    "Processing order {OrderId} for user {UserId}",
    orderId,
    userId);

// OpenTelemetry automatically adds:
// - TraceId
// - SpanId
// - TraceFlags

// Log output:
{
    "timestamp": "2026-01-27T10:00:00Z",
    "level": "Information",
    "message": "Processing order...",
    "orderId": "order-123",
    "userId": "user-456",
    "traceId": "abc123def456",    // ← Correlation!
    "spanId": "xyz789",             // ← Correlation!
    "traceFlags": "01"
}
```

**Finding logs for a trace:**
```
1. User reports slow request
   → Get trace ID from UI

2. Query traces
   → Find trace: abc-123

3. Query logs
   → WHERE traceId = 'abc-123'
   → Get all related logs

4. See full context
   → Every log for that request
   → Chronological order
   → Complete story
```

### Correlating Metrics and Traces

**Exemplars:**
```
Metric: histogram of latencies
Exemplar: specific slow request

Example:
http_request_duration_seconds_bucket{le="1.0"} 1000
# {trace_id="abc123", span_id="xyz789"} 0.95 1611234567

Enables:
1. See high latency in metric
2. Click exemplar
3. Jump to specific trace
4. Investigate slow request
```

**Metric dimensions with trace info:**
```
Alert: High error rate
Metric: http_errors_total{endpoint="/api/checkout"} = 50

Investigation:
1. Query logs: WHERE endpoint = '/api/checkout' AND level = 'ERROR'
2. Get trace IDs from error logs
3. View traces for failed requests
4. Find root cause
```

### Correlating Across Services

**Distributed context:**
```
Request flow:
API Gateway → Auth → Product → Payment

Same trace ID throughout:
trace_id: abc-123

Each service logs with trace ID:
API Gateway:  [abc-123] Request received
Auth:         [abc-123] User authenticated
Product:      [abc-123] Product retrieved
Payment:      [abc-123] Payment processed

Query: Get all logs for trace abc-123
Result: Complete request flow across all services
```

**Cross-service debugging:**
```
Problem: Checkout failing

1. Check API logs
   → traceId: abc-123
   → Error in payment service

2. Check payment service logs
   → Filter by traceId: abc-123
   → Error: "Payment gateway timeout"

3. Check trace
   → Payment span: 30s duration
   → External API call: 29s

4. Check metrics
   → payment_gateway_latency: 30s (usually 1s)

Root cause: Payment gateway degradation
```

### Building Correlation

**Implementation checklist:**
```
✓ Generate trace ID at entry point
✓ Propagate through all services
✓ Include in all logs
✓ Add to spans
✓ Include in error responses
✓ Store with business events
✓ Make queryable everywhere
```

**Example middleware:**
```csharp
public class CorrelationMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<CorrelationMiddleware> _logger;

    public async Task InvokeAsync(HttpContext context)
    {
        // Extract or generate correlation ID
        var correlationId = ExtractCorrelationId(context);
        
        // Add to response headers
        context.Response.Headers["X-Correlation-ID"] = correlationId;
        
        // Add to Activity (trace)
        var activity = Activity.Current;
        activity?.SetTag("correlation.id", correlationId);
        
        // Add to logging scope
        using (_logger.BeginScope(new Dictionary<string, object>
        {
            ["CorrelationId"] = correlationId,
            ["TraceId"] = activity?.TraceId.ToString(),
            ["SpanId"] = activity?.SpanId.ToString()
        }))
        {
            _logger.LogInformation(
                "Request started for {Method} {Path}",
                context.Request.Method,
                context.Request.Path);
            
            await _next(context);
            
            _logger.LogInformation(
                "Request completed with status {StatusCode}",
                context.Response.StatusCode);
        }
    }
}
```

### Correlation Patterns

**Pattern 1: Trace-first debugging**
```
1. Start with trace
   → User reports slow request
   → Provide trace ID

2. View full trace
   → Identify slow span
   → Note span ID

3. Get logs for span
   → Query by trace ID and span ID
   → See detailed logs

4. Check related metrics
   → Use trace timestamp
   → Filter by service
```

**Pattern 2: Log-first debugging**
```
1. Start with error log
   → Error detected
   → Log contains trace ID

2. Get full trace
   → Query traces by ID
   → See complete flow

3. Find related logs
   → All logs for trace
   → Chronological order

4. Investigate metrics
   → Check service health
   → Look for patterns
```

**Pattern 3: Metric-first debugging**
```
1. Start with metric alert
   → High latency detected
   → Time window: last 5 min

2. Query traces in window
   → Get slow traces
   → Sort by duration

3. Examine slowest traces
   → Find bottlenecks
   → Note trace IDs

4. Get detailed logs
   → Filter by trace IDs
   → Find root cause
```

### Best Practices

**Practice 1: Always propagate context**
```
✓ HTTP headers
✓ Message queue metadata
✓ gRPC metadata
✓ Database comments
✓ Async operations
```

**Practice 2: Include rich context**
```
Minimum context:
- Trace ID
- Span ID
- Timestamp

Rich context:
- User ID
- Session ID
- Request ID
- Business transaction ID
- Environment
- Version
```

**Practice 3: Make IDs accessible**
```
✓ Return in API responses
✓ Show in error messages
✓ Log to stdout
✓ Include in UI
✓ Send to error tracking

User can provide ID for support
```

**Practice 4: Consistent format**
```
Use standard formats:
✓ W3C Trace Context
✓ OpenTelemetry conventions
✓ UUID format

Avoid:
✗ Custom formats
✗ Non-portable IDs
✗ Inconsistent naming
```

### Common Pitfalls

**Pitfall 1: Lost context**
```
Problem: Context not propagated
        New thread → no context
        Message queue → no context

Solution: Explicitly pass context
         Use async-local storage
         Include in message headers
```

**Pitfall 2: Non-unique IDs**
```
Problem: Reusing IDs
        Same ID for different requests

Solution: Generate unique IDs
         Use standard generators
         Validate uniqueness
```

**Pitfall 3: No correlation**
```
Problem: Logs without trace ID
        Metrics without context
        Traces without logs

Solution: Instrument consistently
         Validate correlation
         Test end-to-end
```
