---

## Introduction

Observability rests on three foundational pillars: logs, metrics, and traces. Each provides a different lens for understanding system behavior. Logs show what happened, metrics show how much and how fast, and traces show where time was spent. Together, they enable comprehensive system understanding. This lesson explores each pillar and how they work together.

## Key Concepts Summary

### Overview of Three Pillars

**The pillars:**
```
1. Metrics  - What and how much?
2. Logs     - What happened?
3. Traces   - Where did time go?

Together:   Complete system picture
Alone:      Incomplete understanding
```

**Why three pillars?**
```
Each answers different questions
Complementary, not redundant
Together provide full context
Essential for observability
```

### Pillar 1: Metrics

**What are metrics?**
```
Numeric measurements over time
Aggregated data points
Time-series data
Quantitative information
```

**Characteristics:**
```
Format:       Numbers
Storage:      Efficient (time-series DB)
Query:        Fast aggregations
Cardinality:  Low to medium
Cost:         Low
```

**Types of metrics:**
```
Counter:      Monotonically increasing (requests total)
Gauge:        Point-in-time value (CPU usage)
Histogram:    Distribution (request latency)
Summary:      Similar to histogram with percentiles
```

**What metrics tell you:**
```
✓ How many requests?
✓ What's the error rate?
✓ How fast is it?
✓ What's the CPU usage?
✓ How many items in queue?
```

**Example metrics:**
```
http_requests_total{method="GET", status="200"}
cpu_usage_percent{host="web-01"}
request_duration_seconds{endpoint="/api/users"}
database_connections_active
error_rate_percent{service="auth"}
```

**When to use metrics:**
```
✓ Performance trends
✓ Resource utilization
✓ Business KPIs
✓ Alerting
✓ Dashboards
✓ Capacity planning
```

**Advantages:**
```
+ Efficient storage
+ Fast queries
+ Good for alerting
+ Long-term trends
+ Low overhead
```

**Limitations:**
```
- No context
- Aggregated (lose detail)
- Hard to debug specific issues
- Need predefined
```

### Pillar 2: Logs

**What are logs?**
```
Detailed event records
Timestamped messages
Contextual information
Granular system activity
```

**Characteristics:**
```
Format:       Text or structured (JSON)
Storage:      Expensive (large volume)
Query:        Slower (full-text search)
Cardinality:  Very high
Cost:         High
```

**Log levels:**
```
TRACE:   Very detailed debugging
DEBUG:   Diagnostic information
INFO:    General information
WARN:    Warning messages
ERROR:   Error events
FATAL:   Critical failures
```

**What logs tell you:**
```
✓ What happened?
✓ When did it happen?
✓ What was the context?
✓ What was the error message?
✓ What was the request ID?
```

**Example logs:**
```json
{
  "timestamp": "2026-01-27T09:47:23Z",
  "level": "ERROR",
  "service": "payment-service",
  "traceId": "abc123",
  "message": "Payment failed",
  "error": "Insufficient funds",
  "userId": "user-456",
  "amount": 99.99
}
```

**When to use logs:**
```
✓ Debugging errors
✓ Audit trails
✓ Security investigations
✓ Understanding context
✓ Specific event details
✓ Compliance
```

**Advantages:**
```
+ Detailed context
+ Flexible structure
+ Rich information
+ Good for debugging
+ Captures everything
```

**Limitations:**
```
- Expensive storage
- High volume
- Slow queries
- Hard to aggregate
- Retention challenges
```

### Pillar 3: Traces

**What are traces?**
```
Request journey tracking
Spans across services
Distributed system view
Latency breakdown
```

**Characteristics:**
```
Format:       Structured spans
Storage:      Moderate (sampled)
Query:        Service graph, latency
Cardinality:  High
Cost:         Moderate
```

**Key concepts:**
```
Trace:       Complete request journey
Span:        Single operation
Parent span: Calling operation
Child span:  Called operation
Context:     Propagated metadata
```

**What traces tell you:**
```
✓ Where did time go?
✓ Which service is slow?
✓ What's the call path?
✓ Where did error occur?
✓ What's the dependency?
```

**Example trace:**
```
Trace ID: abc123
Total duration: 1200ms

├─ API Gateway (50ms)
│  └─ Auth Service (100ms)
│     └─ User DB query (80ms)
├─ Product Service (1000ms) ← slow!
│  └─ Product DB query (950ms)
└─ Payment Service (50ms)
```

**When to use traces:**
```
✓ Latency investigation
✓ Service dependencies
✓ Error propagation
✓ Performance optimization
✓ Understanding flow
✓ Distributed debugging
```

**Advantages:**
```
+ Shows call path
+ Latency breakdown
+ Distributed view
+ Error location
+ Dependencies
```

**Limitations:**
```
- Complex setup
- Sampling required
- Context propagation needed
- Limited historical data
```

### How the Pillars Work Together

**Complementary strengths:**
```
Metrics:  "Error rate increased"
Logs:     "Here's the error message"
Traces:   "Here's where it failed"

Together: Complete picture
```

**Example debugging flow:**
```
1. Metric alert:
   "Latency increased 2x"

2. Check traces:
   "Payment service slow"
   "Database queries taking 2s"

3. Check logs:
   Filter by slow trace IDs
   "Connection pool exhausted"
   "Max connections reached"

4. Check metrics:
   "DB connections = 100 (max)"
   "Spike in traffic"

Root cause: Need more DB connections
Fix: Increase pool size
```

**Correlation:**
```
Common identifiers:
- Trace ID in logs
- Request ID in metrics
- User ID across all
- Timestamp alignment

Enable:
✓ Jump from metric to logs
✓ Find traces for errors
✓ Correlate events
✓ Full context
```

### Practical Usage Patterns

**Pattern 1: Metrics-driven investigation**
```
1. Alert on metric
   → http_errors_total spiked

2. Filter logs by time
   → Find error messages

3. Get trace for error
   → See where it failed
```

**Pattern 2: Trace-driven debugging**
```
1. Slow request reported
   → Find trace by ID

2. Identify slow span
   → Database query 5s

3. Check logs for span
   → See query details

4. Check metrics
   → Database load high
```

**Pattern 3: Log-driven investigation**
```
1. Error in logs
   → Exception stack trace

2. Get trace ID from log
   → See full request path

3. Check related metrics
   → Resource utilization
```

### Data Volume and Cost

**Relative costs:**
```
Metrics:  Low
Traces:   Medium (sampled)
Logs:     High (large volume)

Total:    Manageable with strategy
```

**Optimization strategies:**
```
Metrics:
✓ Use aggregations
✓ Retention policies
✓ Downsample old data

Logs:
✓ Log levels (prod = INFO+)
✓ Sampling
✓ Structured logging
✓ Short retention

Traces:
✓ Sampling (1-10%)
✓ Head-based sampling
✓ Tail-based sampling
✓ Keep errors always
```

### The Emerging Fourth Pillar: Profiling

**What is profiling?**
```
Continuous performance profiling
CPU, memory, I/O breakdown
Code-level insights
```

**Why add profiling?**
```
Metrics:   "Service uses 80% CPU"
Traces:    "Request takes 500ms"
Profiling: "Function X uses 60% CPU"
          "Memory allocated in line 42"

Provides: Code-level optimization
```

**When to use profiling:**
```
✓ Performance optimization
✓ Memory leaks
✓ CPU hotspots
✓ Code efficiency
```

### Best Practices

**Instrumentation:**
```
Metrics:
- Define SLIs/SLOs
- Key business metrics
- Resource utilization
- Error rates

Logs:
- Structured format
- Appropriate levels
- Rich context
- Correlation IDs

Traces:
- Auto-instrumentation
- Custom spans for key operations
- Proper sampling
- Context propagation
```

**Querying:**
```
Metrics:
- Dashboards for trends
- Alerts for anomalies
- Quick health checks

Logs:
- Error investigation
- Specific event lookup
- Compliance/audit

Traces:
- Latency analysis
- Service dependencies
- Error root cause
```

**Retention:**
```
Metrics: Long (months to years)
Logs:   Short to medium (days to weeks)
Traces: Short (days)

Adjust based on:
- Compliance requirements
- Storage costs
- Query needs
```

## Practice Exercise

After completing the materials, analyze these scenarios (spend 10 minutes):

```
Scenario 1: "API is slow"

What to check:
1. Metrics: Which endpoint? Latency trend?
2. Traces: Where's the bottleneck? DB? External API?
3. Logs: Any errors? What's different?

Scenario 2: "Users can't login"

What to check:
1. Metrics: Error rate on /login endpoint?
2. Logs: What errors are occurring?
3. Traces: Where does auth fail?

Scenario 3: "Database queries slow"

What to check:
1. Traces: Which queries are slow?
2. Logs: Full query text? Lock timeouts?
3. Metrics: Connection pool full? CPU high?

Scenario 4: "Memory growing over time"

What to check:
1. Metrics: Memory trend over days?
2. Logs: Out of memory errors?
3. Profiling: Which objects consuming memory?
4. Traces: Memory-intensive operations?
```
