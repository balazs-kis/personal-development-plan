## Introduction

Observability-driven development means building systems with observability as a first-class concern, not an afterthought. Just as test-driven development changes how we write code, observability-driven development changes how we design systems. This lesson teaches you to build applications that are easy to understand, debug, and operate in production.

## Key Concepts Summary

### What is Observability-Driven Development?

**Definition:**
```
Building systems with built-in observability
Instrumentation from day one
Making systems interrogable
Designing for debuggability
```

**Key principle:**
```
"Make it observable, then make it work"

Not:  Build → Debug → Add logs
But:  Design → Instrument → Build → Operate
```

**Why it matters:**
```
✓ Easier debugging in production
✓ Faster incident resolution
✓ Better system understanding
✓ Proactive problem detection
✓ Lower operational costs
```

### Core Principles

**Principle 1: Instrument everything**
```
Every service:    Metrics, logs, traces
Every endpoint:   Latency, errors, throughput
Every dependency: External calls tracked
Every operation:  Key business events logged
```

**Principle 2: Emit rich context**
```
Not just: "Error occurred"
But:      "Error: Payment failed"
          "User: user-123"
          "Amount: $99.99"
          "Trace: abc-456"
          "Card type: Visa"
```

**Principle 3: Design for unknown unknowns**
```
Can't predict all failures
System must answer new questions
Flexible querying required
High-cardinality data needed
```

**Principle 4: Make it queryable**
```
Structured data
Consistent naming
Proper dimensions
Correlation IDs
```

**Principle 5: Observe behavior, not implementation**
```
Focus on:  What users experience
Not:       Internal implementation details

Measure:   Request latency
Not:       Function execution time (unless relevant)
```

### Instrumenting Code

**What to instrument:**
```
HTTP endpoints:
- Request rate
- Response time
- Error rate
- Status codes

Database calls:
- Query duration
- Connection pool usage
- Errors
- Query types

External APIs:
- Call duration
- Success/failure rate
- Timeouts
- Retries

Business events:
- User signup
- Order placed
- Payment processed
- Feature used
```

**Example: HTTP endpoint**
```csharp
[HttpGet("products/{id}")]
public async Task<Product> GetProduct(int id)
{
    // Start trace span
    using var activity = Activity.Current;
    activity?.SetTag("product.id", id);
    
    // Increment request counter
    _metrics.RequestCounter.Add(1, 
        new KeyValuePair<string, object>("endpoint", "GetProduct"));
    
    var stopwatch = Stopwatch.StartNew();
    
    try
    {
        // Log request
        _logger.LogInformation(
            "Fetching product {ProductId}",
            id);
        
        var product = await _repository.GetProductAsync(id);
        
        if (product == null)
        {
            // Log not found
            _logger.LogWarning(
                "Product {ProductId} not found",
                id);
            
            // Record metric
            _metrics.NotFoundCounter.Add(1);
            
            throw new NotFoundException();
        }
        
        // Record success metric
        _metrics.SuccessCounter.Add(1);
        
        // Record latency
        _metrics.RequestDuration.Record(
            stopwatch.ElapsedMilliseconds,
            new KeyValuePair<string, object>("endpoint", "GetProduct"),
            new KeyValuePair<string, object>("status", "success"));
        
        return product;
    }
    catch (Exception ex)
    {
        // Log error with context
        _logger.LogError(ex,
            "Error fetching product {ProductId}",
            id);
        
        // Record error metric
        _metrics.ErrorCounter.Add(1,
            new KeyValuePair<string, object>("endpoint", "GetProduct"),
            new KeyValuePair<string, object>("error_type", ex.GetType().Name));
        
        // Record latency
        _metrics.RequestDuration.Record(
            stopwatch.ElapsedMilliseconds,
            new KeyValuePair<string, object>("endpoint", "GetProduct"),
            new KeyValuePair<string, object>("status", "error"));
        
        // Add to trace
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        
        throw;
    }
}
```

### Key Metrics to Track

**RED metrics (Requests):**
```
Rate:      Requests per second
Errors:    Error rate percentage
Duration:  Response time (latency)

For: User-facing services
```

**USE metrics (Resources):**
```
Utilization: How busy (% of capacity)
Saturation:  How full (queue depth)
Errors:      Error count

For: Infrastructure, databases
```

**Business metrics:**
```
Signups per hour
Revenue per minute
Cart abandonment rate
Feature adoption rate
```

### Logging Best Practices

**Structured logging:**
```csharp
// Bad: Unstructured
_logger.LogInformation($"User {userId} placed order {orderId}");

// Good: Structured
_logger.LogInformation(
    "Order placed by user",
    userId,      // Indexed field
    orderId,     // Indexed field
    amount,      // Indexed field
    itemCount);  // Indexed field
```

**Log levels:**
```
TRACE:  Very verbose, only in dev
DEBUG:  Development and troubleshooting
INFO:   General operational info
WARN:   Concerning but not errors
ERROR:  Error that needs attention
FATAL:  System crash, immediate action
```

**What to log:**
```
✓ Important business events
✓ Errors with full context
✓ External API calls
✓ Security events
✓ State changes

✗ PII without masking
✗ Secrets/passwords
✗ Too verbose in production
✗ Redundant information
```

### Tracing Best Practices

**Creating spans:**
```csharp
// Auto-instrumentation handles most HTTP/DB calls
// Add custom spans for key operations

using var activity = _activitySource.StartActivity("ProcessPayment");
activity?.SetTag("payment.method", paymentMethod);
activity?.SetTag("payment.amount", amount);
activity?.SetTag("user.id", userId);

try
{
    var result = await _paymentService.ProcessAsync(payment);
    activity?.SetTag("payment.id", result.PaymentId);
    activity?.SetStatus(ActivityStatusCode.Ok);
    return result;
}
catch (Exception ex)
{
    activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
    activity?.RecordException(ex);
    throw;
}
```

**Span attributes:**
```
Add relevant context:
- Business identifiers (user ID, order ID)
- Request parameters
- Response status
- Error information
- Environmental data
```

### Correlation and Context

**Correlation IDs:**
```
Generate at entry point
Pass through all services
Include in logs, metrics, traces
Enable end-to-end tracking
```

**Example flow:**
```
1. API Gateway
   → Generate correlation ID
   → Add to headers

2. Service A
   → Extract correlation ID
   → Add to logs
   → Pass to Service B

3. Service B
   → Extract correlation ID
   → Add to logs
   → Include in traces

Result: Query all systems by single ID
```

**Implementation:**
```csharp
// Middleware to extract/generate correlation ID
public class CorrelationIdMiddleware
{
    private readonly RequestDelegate _next;

    public async Task InvokeAsync(HttpContext context)
    {
        var correlationId = context.Request.Headers["X-Correlation-ID"]
            .FirstOrDefault() ?? Guid.NewGuid().ToString();
        
        context.Response.Headers.Add("X-Correlation-ID", correlationId);
        
        using (_logger.BeginScope(
            new Dictionary<string, object>
            {
                ["CorrelationId"] = correlationId
            }))
        {
            await _next(context);
        }
    }
}

// All logs will include correlation ID
_logger.LogInformation("Processing request");
// Output: {"message": "Processing request", "correlationId": "abc-123"}
```

### Design Patterns

**Pattern 1: Structured events**
```csharp
public class OrderPlacedEvent
{
    public string OrderId { get; set; }
    public string UserId { get; set; }
    public decimal Amount { get; set; }
    public int ItemCount { get; set; }
    public string PaymentMethod { get; set; }
}

// Log structured event
_logger.LogInformation(
    "Order placed: {@OrderPlaced}",
    new OrderPlacedEvent
    {
        OrderId = order.Id,
        UserId = order.UserId,
        Amount = order.TotalAmount,
        ItemCount = order.Items.Count,
        PaymentMethod = order.PaymentMethod
    });
```

**Pattern 2: Observability facade**
```csharp
public interface IObservability
{
    void TrackRequest(string endpoint, double duration, bool success);
    void TrackError(string operation, Exception ex);
    void TrackBusinessEvent(string eventName, Dictionary<string, object> properties);
    IDisposable StartOperation(string operationName);
}

// Use consistent observability interface
_observability.TrackBusinessEvent("UserSignup", new Dictionary<string, object>
{
    ["UserId"] = userId,
    ["SignupMethod"] = "Email",
    ["TrialEnabled"] = true
});
```

**Pattern 3: Decorator for telemetry**
```csharp
public class ObservableRepository<T> : IRepository<T>
{
    private readonly IRepository<T> _inner;
    private readonly IObservability _observability;

    public async Task<T> GetByIdAsync(int id)
    {
        using var operation = _observability.StartOperation("Repository.GetById");
        
        try
        {
            var result = await _inner.GetByIdAsync(id);
            _observability.TrackRequest("GetById", operation.Duration, true);
            return result;
        }
        catch (Exception ex)
        {
            _observability.TrackError("GetById", ex);
            throw;
        }
    }
}
```

### Testing Observability

**Verify instrumentation:**
```csharp
[Fact]
public async Task GetProduct_EmitsMetrics()
{
    // Arrange
    var metricsCollector = new TestMetricsCollector();
    var controller = new ProductController(metricsCollector);

    // Act
    await controller.GetProduct(123);

    // Assert
    Assert.Contains(metricsCollector.Metrics, 
        m => m.Name == "http.server.request.duration");
    Assert.Contains(metricsCollector.Metrics,
        m => m.Name == "http.server.request.count");
}
```

### Common Pitfalls

**Pitfall 1: Too much logging**
```
Bad: Log every variable
Good: Log important state changes

Balance: Enough to debug, not overwhelming
```

**Pitfall 2: Not enough context**
```
Bad: "Error processing request"
Good: "Error processing payment for user user-123, order order-456, amount $99.99"
```

**Pitfall 3: Inconsistent naming**
```
Bad: "request_count", "RequestDuration", "http-errors"
Good: "http.server.request.count",
      "http.server.request.duration",
      "http.server.errors.count"
```

**Pitfall 4: Missing correlation**
```
Bad: Logs and traces separate, can't correlate
Good: Trace ID in every log, log events in spans
```

## Practice Exercise

After completing the materials, design observability for a simple API (spend 15 minutes):

```
Exercise: E-commerce Product API

Endpoints:
- GET /products
- GET /products/{id}
- POST /products
- PUT /products/{id}
- DELETE /products/{id}

Design:
1. What metrics to track?
   - Request count per endpoint
   - Response time per endpoint
   - Error rate per endpoint
   - Products created/updated/deleted count

2. What to log?
   - All requests (INFO)
   - Errors with stack traces (ERROR)
   - Product creation/updates (INFO with details)
   - Validation failures (WARN)

3. What to trace?
   - Each request as trace
   - Database queries as spans
   - External API calls as spans
   - Business logic as spans

4. What context to include?
   - Request ID (correlation)
   - User ID
   - Product ID
   - Endpoint name
   - HTTP method and status

5. How to correlate?
   - Generate request ID at entry
   - Include in all logs
   - Add to trace context
   - Return in response header
```
