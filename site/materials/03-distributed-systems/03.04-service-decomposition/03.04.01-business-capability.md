# Lesson 1: Decomposing by Business Capability

## Learning Objectives

By the end of this lesson, you will be able to:
- Define what a business capability is and why it's a good basis for service boundaries
- Identify business capabilities in a given domain
- Map capabilities to potential microservices
- Understand the relationship between business capabilities and team organization

---

## Introduction

One of the most effective strategies for decomposing a monolith is to organize services around **business capabilities** — what the business does to generate value. Unlike technical decomposition (splitting by layers like UI, business logic, data access), business capability decomposition creates services that represent complete business functions, from UI to data storage.

This approach aligns well with Conway's Law: organizations that design systems will produce designs that mirror their communication structure. By organizing services around capabilities, you can also organize teams around those same capabilities.

## Key Concepts

### What is a Business Capability?

A **business capability** is a particular ability or capacity that a business may possess or exchange to achieve a specific purpose or outcome. Capabilities answer the question: "What does the business do?"

Examples for an e-commerce company:
- **Product Catalog Management**: Maintain product information, pricing, descriptions
- **Order Management**: Process orders, track status, handle cancellations
- **Inventory Management**: Track stock levels, manage warehouses, handle replenishment
- **Customer Management**: Maintain customer profiles, preferences, purchase history
- **Payment Processing**: Handle payments, refunds, payment methods
- **Shipping & Fulfillment**: Coordinate shipping, track deliveries, manage carriers
- **Recommendations**: Generate product recommendations based on user behavior

### Characteristics of Good Business Capabilities

1. **Stable over time**: Capabilities change slowly compared to implementation details
2. **Business-focused**: Expressed in business language, not technical terms
3. **Cohesive**: Everything needed to deliver the capability is grouped together
4. **Independent**: Can be delivered by a team without constant coordination

### From Capabilities to Services

Not every capability becomes a service. Consider:

**Size**: Some capabilities are too small and should be combined:
```
❌ Too granular:
   - "Validate Address"
   - "Calculate Tax"
   - "Generate Invoice Number"

✅ Right size:
   - "Order Management" (includes all order-related operations)
```

**Dependencies**: Capabilities with high interdependence might stay together:
```
Example: In a banking system
- Account Management and Transaction Processing are tightly coupled
- Consider: Should they be one service or two?
- Depends on: Can they be developed/deployed independently? Do they change together?
```

### Capability Mapping Process

1. **Identify Capabilities**: Workshop with business stakeholders
   - Ask: "What does the business do?"
   - Look at organizational structure (but don't be constrained by it)
   - Review existing modules/features

2. **Group and Refine**: Organize into hierarchy
   ```
   Order Management (top-level capability)
   ├── Order Placement
   ├── Order Tracking
   ├── Order Modification
   └── Returns & Refunds
   ```

3. **Assess Boundaries**: For each capability, ask:
   - Can a team own this end-to-end?
   - Does it have clear inputs and outputs?
   - Can it change independently of other capabilities?
   - Is it a manageable size?

4. **Map to Services**: Decide which capabilities become services
   - Start with larger services (avoid premature decomposition)
   - You can always split later; merging is harder

## Detailed Capability Mapping Workflow

### Step 1: Capability Discovery Workshop

```csharp
// Structured approach to discovering business capabilities

public class CapabilityDiscoveryWorkshop
{
    // Preparation
    public class WorkshopPreparation
    {
        // Participants needed:
        // - Product owners
        // - Domain experts
        // - Architects
        // - Senior developers
        
        // Materials:
        // - Whiteboard / Miro board
        // - Post-it notes (physical or digital)
        // - Current system documentation
        // - User journey maps
    }
    
    // Activity 1: Brainstorm "What We Do"
    public List<string> BrainstormCapabilities()
    {
        // Ask: "What does our business/system do?"
        // Examples for e-commerce:
        return new List<string>
        {
            "Sell products",
            "Manage inventory",
            "Process payments",
            "Ship orders",
            "Support customers",
            "Market products",
            "Analyze data"
        };
        
        // Avoid "how" - focus on "what"
        // Avoid technical details
    }
    
    // Activity 2: Group Related Capabilities
    public Dictionary<string, List<string>> GroupCapabilities()
    {
        return new Dictionary<string, List<string>>
        {
            ["Order Management"] = new List<string>
            {
                "Create orders",
                "Track orders",
                "Cancel orders",
                "Process returns"
            },
            ["Product Catalog"] = new List<string>
            {
                "Browse products",
                "Search products",
                "View product details",
                "Manage product information"
            },
            ["Inventory Management"] = new List<string>
            {
                "Track stock levels",
                "Replenish inventory",
                "Reserve stock",
                "Release reservations"
            }
        };
    }
    
    // Activity 3: Identify Dependencies
    public class CapabilityDependency
    {
        public string Capability { get; set; }
        public List<string> DependsOn { get; set; }
        public DependencyType Type { get; set; }
    }
    
    public enum DependencyType
    {
        Strong,      // Must have for capability to work
        Weak,        // Nice to have, can work without
        Information  // Only needs data, not behavior
    }
}
```

### Step 2: Evaluate Capability Characteristics

```csharp
// Assess each capability for service suitability

public class CapabilityAssessment
{
    public string CapabilityName { get; set; }
    
    // Cohesion: Do these functions belong together?
    public int CohesionScore { get; set; } // 1-10
    
    // Size: Is this too big or too small?
    public enum SizeRating { TooSmall, Right, TooLarge }
    public SizeRating Size { get; set; }
    
    // Independence: Can it work alone?
    public int IndependenceScore { get; set; } // 1-10
    
    // Change frequency: How often does it change?
    public enum ChangeFrequency { Low, Medium, High }
    public ChangeFrequency Frequency { get; set; }
    
    // Team assignment: Can one team own it?
    public bool CanBeOwnedByOneTeam { get; set; }
    
    // Calculate service suitability
    public int CalculateSuitabilityScore()
    {
        var score = 0;
        score += CohesionScore;
        score += IndependenceScore;
        score += Size == SizeRating.Right ? 10 : 0;
        score += CanBeOwnedByOneTeam ? 10 : 0;
        
        return score; // Higher = better service candidate
    }
}

// Example assessment
public class ExampleAssessments
{
    public CapabilityAssessment OrderManagement = new()
    {
        CapabilityName = "Order Management",
        CohesionScore = 9,  // Order operations are highly cohesive
        Size = CapabilityAssessment.SizeRating.Right,
        IndependenceScore = 7,  // Needs product/inventory info
        Frequency = CapabilityAssessment.ChangeFrequency.Medium,
        CanBeOwnedByOneTeam = true
        // Suitability: High (good service candidate)
    };
    
    public CapabilityAssessment AddressValidation = new()
    {
        CapabilityName = "Address Validation",
        CohesionScore = 10,  // Single, focused purpose
        Size = CapabilityAssessment.SizeRating.TooSmall,  // Just validation
        IndependenceScore = 10,  // Completely independent
        Frequency = CapabilityAssessment.ChangeFrequency.Low,
        CanBeOwnedByOneTeam = false  // Too small for dedicated team
        // Suitability: Low (library or part of larger service)
    };
}
```

## Capability vs Technical Decomposition

### Visual Comparison

```csharp
// BEFORE: Technical decomposition (layered monolith)

public class TechnicalDecomposition
{
    // Presentation Layer Service
    public class UIService
    {
        // ALL user interfaces
        // - Order UI
        // - Product UI
        // - User UI
        // - Payment UI
    }
    
    // Business Logic Layer Service
    public class BusinessLogicService
    {
        // ALL business logic
        // - Order processing
        // - Product management
        // - User management
        // - Payment processing
    }
    
    // Data Access Layer Service
    public class DataAccessService
    {
        // ALL database access
        // - Order data
        // - Product data
        // - User data
        // - Payment data
    }
    
    // Problems:
    // ❌ Changes ripple across all layers
    // ❌ Can't scale layers independently (usually)
    // ❌ Team organization doesn't match structure
    // ❌ No clear ownership
}

// AFTER: Business capability decomposition

public class CapabilityDecomposition
{
    // Order Management Service (vertical slice)
    public class OrderService
    {
        // Order UI (API endpoints)
        public class OrderController { }
        
        // Order business logic
        public class OrderProcessor { }
        
        // Order data access
        public class OrderRepository { }
        
        // Order database
        // - Orders table
        // - OrderLines table
    }
    
    // Product Catalog Service (vertical slice)
    public class ProductService
    {
        // Product UI (API endpoints)
        public class ProductController { }
        
        // Product business logic
        public class ProductManager { }
        
        // Product data access
        public class ProductRepository { }
        
        // Product database
        // - Products table
        // - Categories table
    }
    
    // Benefits:
    // ✅ Each service is independently deployable
    // ✅ Clear ownership (one team per service)
    // ✅ Can scale services independently
    // ✅ Technology choice per service
}
```

## Advanced Considerations

### Handling Shared Capabilities

```csharp
// Problem: Some capabilities are used by everyone

public class SharedCapabilityStrategies
{
    // Strategy 1: Shared service (careful!)
    public class AuthenticationService
    {
        // All services need authentication
        // Centralize to avoid duplication
        
        // Risks:
        // - Single point of failure
        // - Potential bottleneck
        
        // Mitigations:
        // - High availability setup
        // - Caching in consuming services
        // - Lightweight, focused API
    }
    
    // Strategy 2: Sidecar pattern
    public class AuthenticationSidecar
    {
        // Deploy authentication logic alongside each service
        // - Local process, fast
        // - No network hop
        // - Still centrally managed (via config)
    }
    
    // Strategy 3: Library (for non-business logic)
    public class SharedUtilities
    {
        // OK for:
        // - Logging interfaces
        // - HTTP client helpers
        // - Configuration readers
        
        // NOT OK for:
        // - Business rules
        // - Domain logic
        // - Validation rules
    }
}
```

## Practice Exercise

**Scenario**: You're decomposing a **healthcare appointment system** monolith.

Current features include:
- Patient registration and profiles
- Doctor schedules and availability
- Appointment booking and reminders
- Medical records storage
- Billing and insurance claims
- Prescription management
- Lab test ordering and results

**Tasks** (30 minutes):

### Part 1: Capability Identification (10 min)
1. List 5-7 business capabilities
2. For each, identify 3-4 sub-capabilities
3. Rate each on cohesion (1-10) and independence (1-10)

### Part 2: Service Mapping (10 min)
1. Group capabilities into 4-6 proposed services
2. For each service:
   - Name it
   - List owned capabilities
   - Identify 3-5 key operations
   - Estimate team size needed

### Part 3: Dependency Analysis (10 min)
1. Draw a diagram showing service dependencies
2. Identify strong vs weak dependencies
3. For each dependency, decide:
   - Synchronous API call?
   - Asynchronous event?
   - Data duplication?

**Consider**:
- Which capabilities change together?
- Which could different teams own?
- What are natural transaction boundaries?
- Where is data highly coupled?

## Self-Check Questions

1. **What's the difference between technical decomposition and business capability decomposition?**
   - Technical: Split by layers (UI, business logic, data)
   - Business capability: Split by what the business does

2. **Why are business capabilities more stable than technical implementations?**
   - The business functions (what it does) change slowly
   - How it's implemented (technology) changes frequently

3. **How does capability-based decomposition relate to team organization?**
   - Enables teams to own complete capabilities end-to-end
   - Reduces coordination overhead between teams
   - Aligns with Conway's Law

4. **When might a capability be too small to be its own service?**
   - When it's called synchronously by only one other service
   - When it has no independent business value
   - When it would create excessive network overhead

---

## Key Takeaways

✅ **Business capabilities** provide stable, business-aligned service boundaries

✅ Start with **larger services**; you can split later if needed

✅ Each service should represent a complete capability: UI + logic + data

✅ **Team organization** should mirror service boundaries

✅ Avoid decomposing too fine-grained; balance autonomy with complexity
