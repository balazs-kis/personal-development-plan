# Lesson 4: Database Decomposition Strategies

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the "Database per Service" pattern and why it's important
- Apply strategies for decomposing a shared database across services
- Handle data consistency challenges during and after decomposition
- Choose appropriate patterns for data access across service boundaries

---

## Introduction

Database decomposition is often the hardest part of microservices migration. A shared database creates tight coupling between services — changes to the schema require coordination, and services can't be deployed independently. The **Database per Service** pattern solves this by giving each service its own database, but introduces new challenges around data consistency and cross-service queries.

## Key Concepts

### Why Database per Service?

**Problems with shared databases:**

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Service A  │     │  Service B  │     │  Service C  │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
       └───────────────────┼───────────────────┘
                           │
                    ┌──────▼──────┐
                    │   Shared    │
                    │   Database  │
                    └─────────────┘

Problems:
❌ Schema changes affect all services
❌ Can't deploy services independently
❌ Can't scale databases differently
❌ Can't choose different database technologies
❌ Difficult to understand which service owns what data
```

**Benefits of database per service:**

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Service A  │     │  Service B  │     │  Service C  │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
   ┌───▼───┐           ┌───▼───┐           ┌───▼───┐
   │  DB A │           │  DB B │           │  DB C │
   │(PostgreSQL)       │(MongoDB)          │(Redis)│
   └───────┘           └───────┘           └───────┘

Benefits:
✅ Services are loosely coupled
✅ Each service can choose its own database technology
✅ Independent scaling
✅ Clear data ownership
✅ Independent deployments
```

## Decomposition Strategies

### Strategy 1: Split by Tables (Simple Case)

**When applicable**: Tables have clear ownership and few foreign keys

```
Monolith Database:
  - Users
  - Orders
  - OrderLines
  - Products
  - Inventory
  - Reviews

Split to:

┌──────────────────┐
│  User Service    │
│   - Users        │
└──────────────────┘

┌──────────────────┐
│  Order Service   │
│   - Orders       │
│   - OrderLines   │
└──────────────────┘

┌──────────────────┐
│  Product Service │
│   - Products     │
│   - Reviews      │
└──────────────────┘

┌──────────────────┐
│ Inventory Service│
│   - Inventory    │
└──────────────────┘
```

**Handling Foreign Keys:**
```sql
-- Before (in monolith):
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    UserId INT FOREIGN KEY REFERENCES Users(UserId),
    ProductId INT FOREIGN KEY REFERENCES Products(ProductId)
);

-- After (in Order Service):
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    UserId INT,      -- Store ID only, no FK
    ProductId INT    -- Store ID only, no FK
);
```

Services must validate IDs via API calls instead of database constraints.

### Strategy 2: Move Reference Data

**Challenge**: What if multiple services need reference data (e.g., Country codes, Categories)?

**Options:**

**A. Duplicate Reference Data**
```
Each service has its own copy
├── Updates via events
└── Eventually consistent

Pros: Fast reads, no coupling
Cons: Data duplication, sync complexity
```

**B. Reference Data Service**
```
┌────────────────────┐
│ Reference Data Svc │
│  - Countries       │
│  - Categories      │
│  - Currencies      │
└────────────────────┘
         △
         │ (cached locally)
         │
    ┌────┴────┬────────┐
    │         │        │
Service A  Service B  Service C

Pros: Single source of truth
Cons: Dependency, potential bottleneck
```

**C. Embed in Services**
```
Small, rarely-changing data can be embedded:
  - Configuration files
  - Environment variables
  - Code constants

Pros: No dependencies, fast
Cons: Updates require redeployment
```

### Strategy 3: Data Ownership Transfer

**Scenario**: Product and Review tables are tightly coupled

**Before:**
```
Products Table
  - ProductId (PK)
  - Name
  - Description

Reviews Table
  - ReviewId (PK)
  - ProductId (FK to Products)
  - Rating
  - Comment
```

**Option A: Reviews belong to Product Service**
```
┌────────────────────────┐
│   Product Service      │
│   - Products           │
│   - Reviews            │
└────────────────────────┘
```

**Option B: Reviews are separate, hold Product ID reference**
```
┌──────────────────┐         ┌──────────────────┐
│ Product Service  │         │  Review Service  │
│  - Products      │         │  - Reviews       │
│                  │         │  - ProductId(ref)│
└──────────────────┘         └──────────────────┘
        │                            │
        └──── Events ────────────────┘
```

### Strategy 4: The Saga Pattern for Transactions

**Problem**: Transactions that span multiple services

**Before (monolithic transaction):**
```sql
BEGIN TRANSACTION;
  INSERT INTO Orders (...);
  UPDATE Inventory SET quantity = quantity - 1 WHERE ...;
  INSERT INTO Payments (...);
COMMIT;
```

**After (Saga Pattern):**

**Choreography-based**:
```
1. Order Service: Create Order → Publish "OrderCreated"
2. Inventory Service: Reserve Stock → Publish "StockReserved"
3. Payment Service: Process Payment → Publish "PaymentProcessed"
4. Order Service: Confirm Order → Publish "OrderConfirmed"

If payment fails:
  Payment Service → Publish "PaymentFailed"
  Inventory Service → Releases reserved stock
  Order Service → Marks order as failed
```

**Orchestration-based**:
```
Order Saga Coordinator:
  1. Call Order Service: CreateOrder
  2. Call Inventory Service: ReserveStock
  3. Call Payment Service: ProcessPayment
  4. Call Order Service: ConfirmOrder

  If any step fails:
    - Execute compensating transactions in reverse order
```

## Handling Cross-Service Queries

### Challenge: Queries that span services

**Example**: "Show me all orders for user X with product details"

Before (single database):
```sql
SELECT o.*, p.Name, p.Price
FROM Orders o
JOIN Products p ON o.ProductId = p.ProductId
WHERE o.UserId = @userId
```

After (separate databases): **Can't join across services!**

### Solution 1: API Composition

```
1. Order Service: Get orders for user
   → [{orderId: 1, productId: 101}, {orderId: 2, productId: 102}]

2. Product Service: Get products by IDs
   → [{productId: 101, name: "Book"}, {productId: 102, name: "Pen"}]

3. API Gateway: Merge results
   → [{orderId: 1, productId: 101, name: "Book"}, ...]
```

**Pros**: Simple, no data duplication  
**Cons**: Multiple network calls, slower, potential inconsistency

### Solution 2: CQRS with Read Models

```
Command Side (Writes):
  ┌──────────────┐         ┌──────────────┐
  │ Order Service│         │Product Service│
  │  - Orders DB │         │ -Products DB │
  └──────┬───────┘         └──────┬───────┘
         │ Events                 │ Events
         └────────┬───────────────┘
                  ▼
           ┌──────────────┐
           │  Event Bus   │
           └──────┬───────┘
                  ▼
Query Side (Reads):
         ┌─────────────────────┐
         │  Read Model Builder │
         └──────┬──────────────┘
                ▼
         ┌──────────────────────┐
         │ Materialized View DB │
         │ (Denormalized data)  │
         └──────────────────────┘
```

Events update a denormalized read model optimized for queries.

**Pros**: Fast queries, decoupled  
**Cons**: Eventual consistency, complexity

### Solution 3: Event-Carried State Transfer

```
When Order is created:
  OrderCreated Event contains:
  {
    orderId: 1,
    userId: 123,
    productId: 101,
    productName: "Book",      ← Include product details
    productPrice: 29.99,
    userName: "John Doe",     ← Include user details
    userEmail: "john@example.com"
  }
```

Services include related data in events so consumers don't need to make additional calls.

**Pros**: Self-contained events, no additional lookups  
**Cons**: Data duplication in events, larger message size

## Migration Approach

### Phase 1: Logical Separation (Still One Database)

```
┌─────────────────────────────────────────┐
│          Monolith Application           │
│  ┌──────┐  ┌──────┐  ┌────────┐        │
│  │Order │  │Product│  │Inventory│       │
│  │Module│  │Module│  │ Module  │        │
│  └───┬──┘  └───┬──┘  └────┬───┘        │
└──────┼─────────┼──────────┼────────────┘
       │         │          │
       └─────────┼──────────┘
                 │
          ┌──────▼──────┐
          │  Database   │
          │  (Schemas:  │
          │   orders,   │
          │   products, │
          │   inventory)│
          └─────────────┘

Use database schemas to logically separate data
Each module only accesses its own schema
```

### Phase 2: Separate Databases (Same Server)

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│Order Service │  │Product Service│  │Inventory Svc│
└──────┬───────┘  └──────┬───────┘  └──────┬──────┘
       │                 │                 │
┌──────▼──────┐   ┌──────▼──────┐   ┌─────▼───────┐
│Order DB     │   │Product DB   │   │Inventory DB │
│(Database 1) │   │(Database 2) │   │(Database 3) │
└─────────────┘   └─────────────┘   └─────────────┘
        All on same PostgreSQL server

Benefits: Separate but easy to query for debugging
```

### Phase 3: Physically Separate (Different Servers/Tech)

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│Order Service │  │Product Service│  │Inventory Svc │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
┌──────▼──────┐   ┌──────▼──────┐   ┌─────▼────────┐
│PostgreSQL   │   │MongoDB      │   │Redis         │
│(Orders)     │   │(Products)   │   │(Inventory)   │
└─────────────┘   └─────────────┘   └──────────────┘

Full independence: different technologies, scaling, locations
```

## Advanced Transaction Patterns

### Saga Orchestration vs Choreography

```csharp
// Detailed comparison with implementations

public class SagaPatterns
{
    // Orchestration: Central coordinator
    public class OrderSagaOrchestrator
    {
        private readonly IOrderService _orderService;
        private readonly IInventoryService _inventoryService;
        private readonly IPaymentService _paymentService;
        
        public async Task<SagaResult> ExecuteOrderSagaAsync(CreateOrderCommand cmd)
        {
            var saga = new OrderSaga { CorrelationId = Guid.NewGuid() };
            
            try
            {
                // Step 1: Create order
                saga.OrderId = await _orderService.CreateOrderAsync(cmd);
                saga.Steps.Add(new SagaStep { Name = "CreateOrder", Status = "Completed" });
                
                // Step 2: Reserve inventory
                await _inventoryService.ReserveStockAsync(saga.OrderId, cmd.Items);
                saga.Steps.Add(new SagaStep { Name = "ReserveStock", Status = "Completed" });
                
                // Step 3: Process payment
                await _paymentService.ProcessPaymentAsync(saga.OrderId, cmd.PaymentInfo);
                saga.Steps.Add(new SagaStep { Name = "ProcessPayment", Status = "Completed" });
                
                // Step 4: Confirm order
                await _orderService.ConfirmOrderAsync(saga.OrderId);
                
                return SagaResult.Success(saga);
            }
            catch (Exception ex)
            {
                // Compensate in reverse order
                await CompensateAsync(saga);
                return SagaResult.Failure(saga, ex);
            }
        }
        
        private async Task CompensateAsync(OrderSaga saga)
        {
            // Reverse order
            foreach (var step in saga.Steps.Reverse())
            {
                switch (step.Name)
                {
                    case "ProcessPayment":
                        await _paymentService.RefundAsync(saga.OrderId);
                        break;
                    case "ReserveStock":
                        await _inventoryService.ReleaseStockAsync(saga.OrderId);
                        break;
                    case "CreateOrder":
                        await _orderService.CancelOrderAsync(saga.OrderId);
                        break;
                }
            }
        }
        
        // Benefits:
        // ✓ Clear flow visibility
        // ✓ Easy to reason about
        // ✓ Centralized error handling
        
        // Drawbacks:
        // ⚠️ Single point of failure (coordinator)
        // ⚠️ Tight coupling to coordinator
    }
    
    // Choreography: Event-driven coordination
    public class ChoreographySaga
    {
        // Each service listens and reacts to events
        
        // Order Service
        public class OrderServiceEvents
        {
            public async Task CreateOrderAsync(CreateOrderCommand cmd)
            {
                var order = new Order { Id = Guid.NewGuid(), Status = "Pending" };
                await _repo.SaveAsync(order);
                
                // Publish event
                await _eventBus.PublishAsync(new OrderCreatedEvent
                {
                    OrderId = order.Id,
                    Items = cmd.Items,
                    PaymentInfo = cmd.PaymentInfo
                });
            }
        }
        
        // Inventory Service
        public class InventoryServiceEvents
        {
            public async Task HandleOrderCreatedAsync(OrderCreatedEvent evt)
            {
                try
                {
                    await ReserveStockAsync(evt.OrderId, evt.Items);
                    
                    // Publish success
                    await _eventBus.PublishAsync(new StockReservedEvent
                    {
                        OrderId = evt.OrderId
                    });
                }
                catch
                {
                    // Publish failure
                    await _eventBus.PublishAsync(new StockReservationFailedEvent
                    {
                        OrderId = evt.OrderId
                    });
                }
            }
        }
        
        // Payment Service
        public class PaymentServiceEvents
        {
            public async Task HandleStockReservedAsync(StockReservedEvent evt)
            {
                try
                {
                    await ProcessPaymentAsync(evt.OrderId);
                    
                    await _eventBus.PublishAsync(new PaymentProcessedEvent
                    {
                        OrderId = evt.OrderId
                    });
                }
                catch
                {
                    // Compensate inventory
                    await _eventBus.PublishAsync(new PaymentFailedEvent
                    {
                        OrderId = evt.OrderId
                    });
                }
            }
        }
        
        // Order Service compensation
        public class OrderServiceCompensation
        {
            public async Task HandlePaymentFailedAsync(PaymentFailedEvent evt)
            {
                await _orderService.CancelOrderAsync(evt.OrderId);
            }
        }
        
        // Benefits:
        // ✓ Decoupled services
        // ✓ No single point of failure
        // ✓ Services independently deployable
        
        // Drawbacks:
        // ⚠️ Harder to understand flow
        // ⚠️ Difficult to debug
        // ⚠️ Circular dependencies possible
    }
}
```

### Database Sharding Strategies

```csharp
// When databases get too large for single service

public class ShardingStrategies
{
    // Strategy 1: Hash-based sharding
    public class HashSharding
    {
        public int GetShard(string customerId, int totalShards)
        {
            // Use consistent hashing
            var hash = customerId.GetHashCode();
            return Math.Abs(hash % totalShards);
        }
        
        public async Task<Order> GetOrderAsync(string orderId, string customerId)
        {
            var shard = GetShard(customerId, totalShards: 10);
            var db = _shardedDatabases[shard];
            
            return await db.Orders.FindAsync(orderId);
        }
        
        // Benefits:
        // ✓ Even distribution
        // ✓ Simple logic
        
        // Drawbacks:
        // ⚠️ Can't easily query across shards
        // ⚠️ Rebalancing is complex
    }
    
    // Strategy 2: Range-based sharding
    public class RangeSharding
    {
        public int GetShard(string customerId)
        {
            // Customers A-H → Shard 0
            // Customers I-P → Shard 1
            // Customers Q-Z → Shard 2
            
            var firstChar = customerId[0];
            if (firstChar <= 'H') return 0;
            if (firstChar <= 'P') return 1;
            return 2;
        }
        
        // Benefits:
        // ✓ Range queries easier
        
        // Drawbacks:
        // ⚠️ Uneven distribution possible
    }
    
    // Strategy 3: Geographic sharding
    public class GeographicSharding
    {
        public int GetShard(string region)
        {
            return region switch
            {
                "US-East" => 0,
                "US-West" => 1,
                "EU" => 2,
                "Asia" => 3,
                _ => 0
            };
        }
        
        // Benefits:
        // ✓ Data locality (latency)
        // ✓ Regulatory compliance
        
        // Drawbacks:
        // ⚠️ Uneven load by region
    }
}
```

## CQRS in Practice

```csharp
// Command Query Responsibility Segregation

public class CQRSImplementation
{
    // Write side (Commands)
    public class CommandSide
    {
        [HttpPost("orders")]
        public async Task<IActionResult> CreateOrder(CreateOrderCommand cmd)
        {
            // Write to normalized database
            var order = new Order
            {
                Id = Guid.NewGuid(),
                CustomerId = cmd.CustomerId,
                Items = cmd.Items,
                Total = cmd.Items.Sum(i => i.Price * i.Quantity)
            };
            
            await _writeDb.Orders.AddAsync(order);
            await _writeDb.SaveChangesAsync();
            
            // Publish event for read side
            await _eventBus.PublishAsync(new OrderCreatedEvent
            {
                OrderId = order.Id,
                CustomerId = cmd.CustomerId,
                CustomerName = cmd.CustomerName,
                Items = cmd.Items.Select(i => new
                {
                    i.ProductId,
                    ProductName = i.ProductName,
                    i.Quantity,
                    i.Price
                }).ToList(),
                Total = order.Total,
                CreatedAt = DateTime.UtcNow
            });
            
            return Ok(new { orderId = order.Id });
        }
    }
    
    // Read side (Queries)
    public class QuerySide
    {
        [HttpGet("orders/{id}")]
        public async Task<OrderDetailView> GetOrderDetails(string id)
        {
            // Read from denormalized view
            var orderView = await _readDb.OrderViews
                .Include(o => o.Items)
                .Include(o => o.Customer)
                .FirstOrDefaultAsync(o => o.OrderId == id);
            
            return orderView;
            
            // Fast! No joins needed
            // All data pre-computed
        }
        
        // Read model builder (projection)
        public async Task HandleOrderCreatedAsync(OrderCreatedEvent evt)
        {
            // Build denormalized read model
            var orderView = new OrderDetailView
            {
                OrderId = evt.OrderId,
                CustomerName = evt.CustomerName,
                Items = evt.Items.Select(i => new OrderItemView
                {
                    ProductName = i.ProductName,
                    Quantity = i.Quantity,
                    Price = i.Price
                }).ToList(),
                Total = evt.Total,
                OrderDate = evt.CreatedAt
            };
            
            await _readDb.OrderViews.AddAsync(orderView);
            await _readDb.SaveChangesAsync();
        }
    }
    
    // Benefits:
    // ✓ Optimized reads and writes separately
    // ✓ Scale reads and writes independently
    // ✓ No complex joins on read
    
    // Drawbacks:
    // ⚠️ Eventual consistency
    // ⚠️ More complex architecture
}
```

## Self-Check Questions

1. **Why can't services share a database?**
   - Creates tight coupling
   - Prevents independent deployments
   - Can't scale or choose technology independently

2. **How do you handle foreign key relationships across services?**
   - Store IDs without database foreign keys
   - Validate via API calls or events
   - Accept eventual consistency

3. **What's the difference between saga choreography vs orchestration?**
   - Choreography: Services coordinate via events (decentralized)
   - Orchestration: Central coordinator manages flow (centralized)

4. **When should you use CQRS?**
   - When query patterns differ significantly from write patterns
   - When you need to join data from multiple services efficiently
   - When eventual consistency is acceptable for reads

## Key Takeaways

✅ **Database per Service** is essential for true microservices independence

✅ **Foreign keys** become references; validate via APIs or events

✅ Use **Saga pattern** for distributed transactions

✅ **Cross-service queries** require API composition, CQRS, or event-carried state

✅ **Migrate gradually**: Logical → separate databases → different tech

✅ Accept **eventual consistency** for many scenarios

✅ **Data duplication** is sometimes necessary and okay
