# Lesson 3: Strangler Fig Pattern for Migration

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the Strangler Fig pattern and why it's effective for monolith migration
- Design a phased migration strategy using the Strangler Fig approach
- Implement routing mechanisms to direct traffic between old and new systems
- Identify which functionality to extract first for maximum value and minimum risk

---

## Introduction

Rewriting a monolith from scratch is risky and often fails. The **Strangler Fig Pattern** offers a better way: incrementally replace functionality in a legacy system by routing requests to new services while gradually "strangling" the old system until it can be retired.

The pattern is named after strangler fig trees, which seed in the upper branches of existing trees and gradually grow downward, eventually encompassing and replacing the original tree.

## Key Concepts

### What is the Strangler Fig Pattern?

The Strangler Fig pattern involves:

1. **Identify**: Choose a piece of functionality to extract
2. **Build**: Create a new service that implements this functionality
3. **Route**: Add routing logic to direct some requests to the new service
4. **Monitor**: Verify the new service works correctly
5. **Expand**: Gradually route more traffic to the new service
6. **Remove**: Once all traffic is routed, remove the old code

### Why Strangler Fig Works

**Advantages:**
- ✅ **Lower Risk**: Migrate incrementally, not big bang
- ✅ **Continuous Delivery**: New features can go to new services
- ✅ **Rollback Capability**: Easy to route back to old system if problems arise
- ✅ **Business Continuity**: System remains operational throughout migration
- ✅ **Learning Opportunity**: Team learns microservices incrementally

**Challenges:**
- ⚠️ **Dual Maintenance**: Temporarily maintain both old and new systems
- ⚠️ **Data Synchronization**: Keep data consistent across systems
- ⚠️ **Routing Complexity**: Need infrastructure to route requests
- ⚠️ **Testing**: Must test both old and new code paths

### The Routing Layer

The key enabler is a **routing layer** (proxy, API gateway, or load balancer) that decides where to send each request:

```
┌─────────────┐
│   Clients   │
└──────┬──────┘
       │
       ▼
┌────────────────────┐
│  Routing Layer     │  ◀── Configuration determines routing
│  (API Gateway/Proxy│
└─────┬──────┬───────┘
      │      │
      │      └──────────────┐
      ▼                     ▼
┌──────────────┐    ┌──────────────────┐
│  Monolith    │    │  New Service(s)  │
│              │    │                  │
│  /orders     │    │  /orders ✓       │
│  /products   │    │                  │
│  /users      │    │                  │
└──────────────┘    └──────────────────┘
```

**Routing Strategies:**

1. **URL-based**: Route by path (e.g., `/api/v2/orders` → new service)
2. **Header-based**: Route by custom header (`X-Use-New-Service: true`)
3. **User-based**: Route specific users/customers to new service (canary)
4. **Feature flag**: Dynamically toggle routing via feature flags
5. **Percentage**: Route X% of traffic to new service

## Migration Strategy

### Phase 1: Preparation

**Set up infrastructure:**
```
1. Deploy routing layer (e.g., NGINX, Kong, Azure API Management)
2. Implement feature flags for routing decisions
3. Set up monitoring and logging for both old and new
4. Establish rollback procedures
```

### Phase 2: Choose First Service

**Prioritization criteria:**

**High Value, Low Risk** targets:
- ✅ Relatively independent functionality
- ✅ Clear boundaries
- ✅ High business value
- ✅ Doesn't require complex data migration
- ✅ Low number of dependencies

**Examples of good first services:**
- Notifications/Email service
- Reporting service
- Search functionality
- Recommendation engine

**Examples of poor first services:**
- Core business entities with many dependencies
- Functionality tightly coupled to database
- Services requiring complex transactions

### Phase 3: Extract and Route

```
Step 1: Build new service
  ├── Implement functionality
  ├── Deploy independently
  └── Verify it works in isolation

Step 2: Dual-write (if data is involved)
  ├── Monolith writes to both old and new datastores
  └── Synchronize existing data

Step 3: Route read traffic
  ├── Start with 1% of traffic
  ├── Monitor for errors
  ├── Gradually increase to 100%
  └── Compare responses (shadow mode)

Step 4: Route write traffic
  ├── Start with safe operations
  ├── Monitor data consistency
  └── Gradually increase

Step 5: Remove old code
  ├── Stop routing to monolith
  ├── Remove code from monolith
  └── Decommission old database tables
```

### Phase 4: Repeat

Once the first service is successfully extracted, repeat for the next service using lessons learned.

## Practical Example: E-Commerce Migration

### Starting Point: Monolith

```
E-Commerce Monolith
├── User Management
├── Product Catalog
├── Order Processing
├── Inventory Management
├── Payment Processing
├── Shipping
└── Notifications
```

### Migration Plan

**Iteration 1: Extract Notifications** (Low risk, high independence)

```
Before:
  Client → Monolith → [Sends Email]

After:
  Client → Monolith → Message Queue → Notification Service → [Sends Email]
```

**Why first?**
- Asynchronous, so less risky
- Clear boundary
- No complex data dependencies
- High value (can improve notification system independently)

**Iteration 2: Extract Product Catalog** (Medium risk, medium independence)

```
Routing rule:
  GET /api/products/* → Product Service
  Everything else → Monolith

Data migration:
  1. Export products from monolith DB
  2. Import to product service DB
  3. Keep in sync during transition
  4. Switch read traffic
  5. Eventually switch write traffic
```

**Iteration 3: Extract Order Processing** (Higher risk, more dependencies)

```
Challenges:
  - Orders reference products, users, inventory
  - Need distributed transactions or sagas
  - Critical business functionality

Approach:
  1. Build order service with Anti-Corruption Layer
  2. Order service calls product/user services
  3. Use Saga pattern for consistency
  4. Route create-order requests to new service
  5. Dual-read: new service + monolith for verification
```

## Handling Data Migration

### Strategy 1: Event-Driven Synchronization

```
Monolith                New Service
   │                         │
   │ Write to old DB         │
   ├──────────┐              │
   │          │              │
   │    Publish Event        │
   │          │              │
   │          └──────────────▶ Consume Event
   │                         │
   │                         │ Write to new DB
```

### Strategy 2: Dual-Write Pattern

```
Application Layer
   │
   ├──────────┬──────────────┐
   │          │              │
   ▼          ▼              ▼
Old DB    New DB    Message Queue
                         │
                         └──▶ Sync Service
```

**Note**: Dual-write has consistency risks. Consider using the Outbox pattern or Change Data Capture (CDC) instead.

### Strategy 3: Read from Old, Write to New

```
Phase 1: New service reads from monolith DB (via API)
Phase 2: Dual-write to both databases
Phase 3: New service reads from its own DB
Phase 4: Stop writing to monolith DB
```

## Monitoring and Validation

### What to Monitor

**During Migration:**
- ✓ Response times (old vs new)
- ✓ Error rates (old vs new)
- ✓ Data consistency (compare responses)
- ✓ Traffic distribution (% to old vs new)
- ✓ Resource usage (CPU, memory, database connections)

**Validation Techniques:**

1. **Shadow Mode**: Route to both, but only use old response
   ```
   Request → [Old System (use response)]
           → [New System (log & compare)]
   ```

2. **Dark Launch**: Deploy but don't route real traffic yet
   ```
   Internal testing with production data copies
   ```

3. **Canary Release**: Route small percentage of real traffic
   ```
   95% → Old System
   5%  → New System (monitor carefully)
   ```

## Advanced Migration Techniques

### Parallel Running (Shadow Mode)

```csharp
// Run new and old systems in parallel for validation

public class ShadowModeImplementation
{
    public async Task<IActionResult> HandleRequest(HttpRequest request)
    {
        // Primary: Route to old system (use this response)
        var oldResponse = await _monolithClient.ForwardAsync(request);
        
        // Shadow: Route to new service (compare, don't use)
        _ = Task.Run(async () =>
        {
            try
            {
                var newResponse = await _newServiceClient.ForwardAsync(request);
                
                // Compare responses
                await _comparisonService.CompareAsync(new Comparison
                {
                    Request = request,
                    OldResponse = oldResponse,
                    NewResponse = newResponse,
                    Timestamp = DateTime.UtcNow
                });
                
                // Log differences
                if (!_comparisonService.ResponsesMatch(oldResponse, newResponse))
                {
                    _logger.LogWarning(
                        "Response mismatch: {Path}, Old: {Old}, New: {New}",
                        request.Path, oldResponse, newResponse);
                }
            }
            catch (Exception ex)
            {
                // New service error doesn't affect users
                _logger.LogError(ex, "Shadow request failed");
            }
        });
        
        // Return old response (users unaffected by new service)
        return oldResponse;
    }
    
    // Benefits:
    // ✓ Zero risk to users
    // ✓ Real production data validation
    // ✓ Performance comparison
    // ✓ Identify edge cases
}
```

### Feature Toggle Strategy

```csharp
// Control migration with feature flags

public class FeatureToggleStranglerFig
{
    private readonly IFeatureManager _features;
    
    public async Task<IActionResult> HandleRequest(HttpRequest request)
    {
        // Check feature flags for routing decisions
        
        // 1. User-based rollout
        var userId = request.Headers["User-Id"];
        if (await _features.IsEnabledForUserAsync("UseNewService", userId))
        {
            return await _newServiceClient.ForwardAsync(request);
        }
        
        // 2. Percentage rollout
        if (await _features.IsEnabledForPercentageAsync("UseNewService", 10))
        {
            return await _newServiceClient.ForwardAsync(request);
        }
        
        // 3. Geography-based
        var region = request.Headers["Region"];
        if (region == "US-West" && await _features.IsEnabledAsync("UseNewService"))
        {
            return await _newServiceClient.ForwardAsync(request);
        }
        
        // Default: Old system
        return await _monolithClient.ForwardAsync(request);
    }
    
    // Feature flag configuration
    public class FeatureFlagConfig
    {
        public string Name { get; set; } = "UseNewService";
        public bool Enabled { get; set; } = false;
        public int Percentage { get; set; } = 0;
        public List<string> EnabledUsers { get; set; } = new();
        public List<string> EnabledRegions { get; set; } = new();
        
        // Can update without redeployment!
    }
}
```

### Data Synchronization Patterns

```csharp
// Keep data in sync during migration

public class DataSynchronizationStrategies
{
    // Pattern 1: Dual-Write (Application Level)
    public class DualWritePattern
    {
        public async Task CreateOrderAsync(Order order)
        {
            // Write to both old and new
            await _oldDb.Orders.AddAsync(order);
            await _newDb.Orders.AddAsync(order);
            
            // Commit both
            await _oldDb.SaveChangesAsync();
            await _newDb.SaveChangesAsync();
            
            // Risk: Not atomic! 
            // One could succeed, other fail
        }
    }
    
    // Pattern 2: Change Data Capture (Database Level)
    public class CDCPattern
    {
        // Use database CDC (e.g., Debezium)
        // Captures all changes in old database
        // Streams to new database
        
        // Setup:
        // 1. Enable CDC on old database tables
        // 2. Configure Debezium connector
        // 3. Stream changes to new service
        
        // Benefits:
        // ✓ No application code changes
        // ✓ Captures all changes (even direct SQL)
        // ✓ Reliable, proven technology
    }
    
    // Pattern 3: Event-Driven Sync
    public class EventDrivenSync
    {
        public async Task CreateOrderAsync(Order order)
        {
            // Write to old database
            await _oldDb.Orders.AddAsync(order);
            await _oldDb.SaveChangesAsync();
            
            // Publish event
            await _eventBus.PublishAsync(new OrderCreatedEvent
            {
                OrderId = order.Id,
                // ... order details
            });
        }
        
        // New service subscribes
        public class NewServiceEventHandler
        {
            public async Task HandleOrderCreatedAsync(OrderCreatedEvent evt)
            {
                // Write to new database
                await _newDb.Orders.AddAsync(MapToNewModel(evt));
                await _newDb.SaveChangesAsync();
            }
        }
        
        // Benefits:
        // ✓ Eventual consistency acceptable
        // ✓ Decoupled sync mechanism
        // ✓ Can replay events if needed
    }
    
    // Pattern 4: Read-Through Pattern
    public class ReadThroughPattern
    {
        // New service reads from old during transition
        
        public async Task<Order> GetOrderAsync(string orderId)
        {
            // Check new database first
            var order = await _newDb.Orders.FindAsync(orderId);
            
            if (order == null)
            {
                // Fall back to old database
                var oldOrder = await _oldDb.Orders.FindAsync(orderId);
                if (oldOrder != null)
                {
                    order = MapToNewModel(oldOrder);
                    
                    // Optional: Migrate on read
                    await _newDb.Orders.AddAsync(order);
                    await _newDb.SaveChangesAsync();
                }
            }
            
            return order;
        }
    }
}
```

### Routing Infrastructure Options

```csharp
// Different ways to implement routing layer

public class RoutingInfrastructureOptions
{
    // Option 1: API Gateway (AWS API Gateway, Azure API Management, Kong)
    public class APIGateway
    {
        // Configuration-based routing
        // No code deployment needed for route changes
        
        // Example: Azure API Management policy
        public string AzureAPIMPolicy = @"
        <policies>
            <inbound>
                <choose>
                    <when condition=""@(context.Request.Url.Path.StartsWith('/api/v2/orders'))"">
                        <set-backend-service base-url=""https://new-order-service.azurewebsites.net"" />
                    </when>
                    <otherwise>
                        <set-backend-service base-url=""https://monolith.azurewebsites.net"" />
                    </otherwise>
                </choose>
            </inbound>
        </policies>";
        
        // Benefits:
        // ✓ Managed service
        // ✓ Built-in features (auth, rate limiting, caching)
        // ✓ Easy to configure
    }
    
    // Option 2: Service Mesh (Istio, Linkerd)
    public class ServiceMesh
    {
        // Traffic routing via sidecar proxies
        
        // Example: Istio VirtualService
        public string IstioVirtualService = @"
        apiVersion: networking.istio.io/v1beta1
        kind: VirtualService
        metadata:
          name: order-service
        spec:
          hosts:
          - order-service
          http:
          - match:
            - headers:
                x-use-new-service:
                  exact: 'true'
            route:
            - destination:
                host: order-service-v2
                weight: 100
          - route:
            - destination:
                host: order-service-v1
                weight: 90
            - destination:
                host: order-service-v2
                weight: 10";
        
        // Benefits:
        // ✓ Advanced traffic management
        // ✓ Observability built-in
        // ✓ Gradual rollout easy
    }
    
    // Option 3: Reverse Proxy (NGINX, HAProxy)
    public class ReverseProxy
    {
        // Configuration-based routing
        
        // Example: NGINX config
        public string NginxConfig = @"
        upstream monolith {
            server monolith:8080;
        }
        
        upstream new-service {
            server new-service:8080;
        }
        
        server {
            listen 80;
            
            location /api/v2/orders {
                proxy_pass http://new-service;
            }
            
            location / {
                proxy_pass http://monolith;
            }
        }";
        
        // Benefits:
        // ✓ Simple, well-understood
        // ✓ High performance
        // ✓ Full control
    }
    
    // Option 4: Custom Application Gateway
    public class CustomGateway
    {
        [HttpGet("{*path}")]
        public async Task<IActionResult> RouteRequest(string path)
        {
            // Dynamic routing logic
            var route = await _routingService.GetRouteAsync(path);
            
            if (route.UseNewService)
            {
                return await _newServiceClient.ForwardAsync(path);
            }
            
            return await _monolithClient.ForwardAsync(path);
        }
        
        // Benefits:
        // ✓ Full flexibility
        // ✓ Complex routing logic
        // ✓ Dynamic configuration
        
        // Costs:
        // ⚠️ Must build and maintain
        // ⚠️ Potential bottleneck
    }
}
```

### Rollback Strategies

```csharp
// Plan for rollback before you need it

public class RollbackStrategies
{
    // Strategy 1: Instant Routing Rollback
    public async Task RollbackRoutingAsync(string serviceName)
    {
        // Switch routing back to old system
        await _routingService.UpdateRouteAsync(serviceName, new RouteConfig
        {
            UseNewService = false,
            Percentage = 0
        });
        
        // Immediate effect, no deployment needed
    }
    
    // Strategy 2: Database Rollback (if needed)
    public class DatabaseRollback
    {
        // If new service wrote bad data
        public async Task RollbackDataAsync()
        {
            // 1. Stop writes to new service
            await DisableNewServiceAsync();
            
            // 2. Restore from backup (if needed)
            await RestoreNewDatabaseFromBackupAsync();
            
            // 3. Re-sync from old database
            await ResyncFromOldDatabaseAsync();
        }
    }
    
    // Strategy 3: Feature Flag Rollback
    public async Task RollbackFeatureAsync(string featureKey)
    {
        // Instantly disable feature flag
        await _featureManager.DisableAsync(featureKey);
        
        // All users revert to old system
        // No deployment needed
    }
    
    // Monitoring triggers for automatic rollback
    public class AutoRollbackTriggers
    {
        public bool ShouldRollback(ServiceMetrics metrics)
        {
            // Automatic rollback conditions
            if (metrics.ErrorRate > 0.05) // 5% error rate
                return true;
            
            if (metrics.P95Latency > TimeSpan.FromSeconds(5))
                return true;
            
            if (metrics.SuccessRate < 0.95) // 95% success rate
                return true;
            
            return false;
        }
    }
}
```

## Real-World Case Study

```csharp
// Complete migration example: Extract product search from monolith

public class ProductSearchMigration
{
    // Step 1: Current state
    public class CurrentMonolith
    {
        // Monolith with embedded search
        [HttpGet("products/search")]
        public async Task<List<Product>> SearchAsync(string query)
        {
            return await _db.Products
                .Where(p => p.Name.Contains(query))
                .ToListAsync();
            
            // Problems:
            // - Slow (full table scan)
            // - Can't scale independently
            // - Blocks product catalog changes
        }
    }
    
    // Step 2: Build new search service
    public class NewSearchService
    {
        private readonly IElasticClient _elastic;
        
        [HttpGet("search")]
        public async Task<SearchResults> SearchAsync(string query)
        {
            var response = await _elastic.SearchAsync<ProductDocument>(s => s
                .Query(q => q.MultiMatch(m => m
                    .Query(query)
                    .Fields(f => f
                        .Field(p => p.Name, boost: 2)
                        .Field(p => p.Description)))));
            
            return MapToResults(response);
        }
    }
    
    // Step 3: Data synchronization
    public class DataSync
    {
        // Initial bulk load
        public async Task InitialLoadAsync()
        {
            var products = await _db.Products.ToListAsync();
            foreach (var product in products)
            {
                await _elastic.IndexDocumentAsync(new ProductDocument
                {
                    Id = product.Id,
                    Name = product.Name,
                    Description = product.Description,
                    // ... more fields
                });
            }
        }
        
        // Ongoing sync via events
        public async Task HandleProductUpdatedAsync(ProductUpdatedEvent evt)
        {
            await _elastic.UpdateAsync<ProductDocument>(evt.ProductId, u => u
                .Doc(new ProductDocument
                {
                    Name = evt.Name,
                    Description = evt.Description
                }));
        }
    }
    
    // Step 4: Routing migration
    public class RoutingMigration
    {
        // Week 1: Shadow mode (0% traffic)
        public async Task Week1_ShadowModeAsync(string query)
        {
            var monolithResults = await _monolith.SearchAsync(query);
            
            _ = Task.Run(async () =>
            {
                var newResults = await _newSearchService.SearchAsync(query);
                await CompareResultsAsync(monolithResults, newResults);
            });
            
            return monolithResults; // Use monolith
        }
        
        // Week 2: Canary (5% traffic)
        public async Task Week2_CanaryAsync(string query)
        {
            if (Random.Next(100) < 5)
            {
                return await _newSearchService.SearchAsync(query);
            }
            return await _monolith.SearchAsync(query);
        }
        
        // Week 3-4: Gradual rollout (25%, 50%, 75%, 100%)
        // Week 5: Monitor at 100%
        // Week 6: Remove old code
    }
    
    // Step 5: Cleanup
    public class Cleanup
    {
        public async Task RemoveOldCodeAsync()
        {
            // 1. Verify all traffic to new service
            // 2. Remove old search code from monolith
            // 3. Drop old search indexes
            // 4. Update documentation
            // 5. Celebrate! 🎉
        }
    }
}
```

   - Incremental migration allows testing and validation at each step
   - Easy rollback if problems occur
   - Business continues operating normally
   - Team learns gradually

2. **What role does the routing layer play?**
   - Directs traffic between old and new systems
   - Enables gradual migration
   - Provides traffic control for canary releases

   - Clear boundaries

## Key Takeaways

✅ **Strangler Fig** enables incremental, low-risk migration

✅ Start with **low-risk, high-value** functionality

✅ **Routing layer** is critical infrastructure

✅ Use **canary releases** and **shadow mode** for validation

✅ **Data migration** is often the hardest part — plan carefully

✅ **Monitor everything** during migration

✅ Be prepared to **rollback** if necessary
