# Lesson 2: Client-Side vs Server-Side Discovery

## Learning Objectives

By the end of this lesson, you will be able to:
- Distinguish between client-side and server-side discovery patterns
- Understand the trade-offs of each approach
- Implement client-side discovery with service registry integration
- Recognize when to use server-side discovery with load balancers
- Choose the appropriate pattern for different scenarios
- Implement hybrid approaches for complex architectures
- Handle failure scenarios in both patterns

---

## Introduction

In Lesson 1, we learned that service discovery helps services find each other. But *who* performs the discovery? Should the calling service (client) query the registry and choose an instance? Or should it call a load balancer that handles discovery and routing?

This choice—**client-side vs server-side discovery**—has significant implications for your architecture's complexity, performance, and operational characteristics. Neither is universally better; the right choice depends on your constraints, infrastructure, and team capabilities.

## Key Concepts Summary

### Client-Side Discovery Pattern

In client-side discovery, the client is responsible for:
1. Querying the service registry
2. Choosing which instance to call (load balancing)
3. Making the direct request to the chosen instance

```
┌──────────────┐
│  Client      │
│  Service     │
└──────┬───────┘
       │ 1. Query "inventory-service"
       ▼
┌──────────────────┐
│ Service Registry │
│  (Consul/Eureka) │
└──────────────────┘
       │ 2. Returns: [IP1, IP2, IP3]
       ▼
┌──────────────┐
│  Client      │
│  Service     │ 3. Choose IP2 (client-side load balancing)
└──────┬───────┘
       │ 4. HTTP GET http://IP2:8080/stock
       ▼
┌──────────────┐
│  Inventory   │
│  Service     │
│  (Instance 2)│
└──────────────┘
```

## Client-Side Discovery Implementation

### Basic Implementation

```csharp
public class ClientSideDiscoveryHttpClient
{
    private readonly IServiceRegistry _registry;
    private readonly HttpClient _httpClient;
    private readonly ILoadBalancer _loadBalancer;
    private readonly ILogger<ClientSideDiscoveryHttpClient> _logger;
    
    public async Task<HttpResponseMessage> GetAsync(string serviceName, string path)
    {
        // 1. Discover service instances
        var instances = await _registry.GetServiceInstancesAsync(serviceName);
        
        if (!instances.Any())
        {
            throw new ServiceNotFoundException($"No instances found for {serviceName}");
        }
        
        // 2. Client-side load balancing - choose an instance
        var selectedInstance = _loadBalancer.Choose(instances);
        
        _logger.LogDebug(
            "Selected instance {InstanceId} at {Host}:{Port} for {ServiceName}",
            selectedInstance.Id,
            selectedInstance.Host,
            selectedInstance.Port,
            serviceName);
        
        // 3. Make direct request to chosen instance
        var url = $"http://{selectedInstance.Host}:{selectedInstance.Port}{path}";
        
        try
        {
            return await _httpClient.GetAsync(url);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Request failed to instance {InstanceId}", selectedInstance.Id);
            throw;
        }
    }
}

// Usage
var response = await discoveryClient.GetAsync("inventory-service", "/api/stock/12345");
```

### Advanced Client-Side Discovery with Retry and Circuit Breaker

```csharp
public class ResilientClientSideDiscovery
{
    private readonly IServiceRegistry _registry;
    private readonly HttpClient _httpClient;
    private readonly ILoadBalancer _loadBalancer;
    private readonly Dictionary<string, ICircuitBreaker> _circuitBreakers = new();
    private readonly ILogger _logger;
    
    public async Task<HttpResponseMessage> GetAsync(
        string serviceName,
        string path,
        int maxRetries = 3)
    {
        Exception lastException = null;
        
        for (int attempt = 0; attempt < maxRetries; attempt++)
        {
            try
            {
                // Discover instances (with caching)
                var instances = await _registry.GetServiceInstancesAsync(serviceName);
                
                if (!instances.Any())
                {
                    throw new ServiceNotFoundException($"No instances found for {serviceName}");
                }
                
                // Filter out instances with open circuit breakers
                var availableInstances = instances
                    .Where(i => GetCircuitBreaker(i.Id).State != CircuitState.Open)
                    .ToList();
                
                if (!availableInstances.Any())
                {
                    _logger.LogWarning(
                        "All instances of {ServiceName} have open circuit breakers",
                        serviceName);
                    
                    // Wait a bit and retry
                    await Task.Delay(TimeSpan.FromSeconds(Math.Pow(2, attempt)));
                    continue;
                }
                
                // Choose instance
                var instance = _loadBalancer.Choose(availableInstances);
                var url = $"http://{instance.Host}:{instance.Port}{path}";
                
                // Execute through circuit breaker
                var breaker = GetCircuitBreaker(instance.Id);
                var response = await breaker.ExecuteAsync(async () =>
                {
                    return await _httpClient.GetAsync(url);
                });
                
                return response;
            }
            catch (Exception ex)
            {
                lastException = ex;
                _logger.LogWarning(
                    ex,
                    "Attempt {Attempt} failed for {ServiceName}",
                    attempt + 1,
                    serviceName);
                
                if (attempt < maxRetries - 1)
                {
                    await Task.Delay(TimeSpan.FromMilliseconds(100 * Math.Pow(2, attempt)));
                }
            }
        }
        
        throw new ServiceCallException(
            $"Failed to call {serviceName} after {maxRetries} attempts",
            lastException);
    }
    
    private ICircuitBreaker GetCircuitBreaker(string instanceId)
    {
        return _circuitBreakers.GetOrAdd(instanceId, id =>
            new CircuitBreaker(
                failureThreshold: 5,
                timeout: TimeSpan.FromSeconds(30)));
    }
}
```

### Client-Side Discovery with Caching

```csharp
public class CachingServiceRegistry : IServiceRegistry
{
    private readonly IServiceRegistry _inner;
    private readonly IMemoryCache _cache;
    private readonly ILogger _logger;
    
    public async Task<List<ServiceInstance>> GetServiceInstancesAsync(
        string serviceName,
        bool forceRefresh = false)
    {
        var cacheKey = $"service:{serviceName}";
        
        if (!forceRefresh && _cache.TryGetValue(cacheKey, out List<ServiceInstance> cached))
        {
            _logger.LogDebug("Cache hit for service {ServiceName}", serviceName);
            return cached;
        }
        
        try
        {
            var instances = await _inner.GetServiceInstancesAsync(serviceName);
            
            // Cache with sliding expiration
            _cache.Set(cacheKey, instances, new MemoryCacheEntryOptions
            {
                SlidingExpiration = TimeSpan.FromSeconds(30),
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            });
            
            _logger.LogInformation(
                "Cached {Count} instances of {ServiceName}",
                instances.Count,
                serviceName);
            
            return instances;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Failed to refresh service {ServiceName}", serviceName);
            
            // Return stale cache if available
            if (_cache.TryGetValue(cacheKey, out cached))
            {
                _logger.LogWarning(
                    "Returning stale cache for {ServiceName}",
                    serviceName);
                return cached;
            }
            
            throw;
        }
    }
}
```

**Pros of Client-Side Discovery:**
- ✅ **No single point of failure:** No load balancer to fail
- ✅ **Lower latency:** Direct connection, no intermediary hop
- ✅ **Flexible load balancing:** Client controls algorithm
- ✅ **Service-specific routing:** Different clients can use different strategies
- ✅ **Registry awareness:** Client knows all available instances

**Cons of Client-Side Discovery:**
- ❌ **Client complexity:** Every client must implement discovery and load balancing logic
- ❌ **Language coupling:** Discovery library must exist for each language
- ❌ **Client updates:** Load balancing logic changes require updating all clients
- ❌ **Registry dependency:** Clients directly depend on registry availability

## Server-Side Discovery Pattern

In server-side discovery, clients call a load balancer that:
1. Queries the service registry (or is notified of changes)
2. Chooses which instance to route the request to
3. Proxies the request to the chosen instance

```
┌──────────────┐
│  Client      │
│  Service     │
└──────┬───────┘
       │ 1. HTTP GET http://load-balancer/inventory-service/stock
       ▼
┌──────────────────┐           ┌──────────────────┐
│  Load Balancer   │───────────│ Service Registry │
│  (NGINX/HAProxy/ │ 2. Query  │  (Consul/K8s)    │
│   AWS ALB/ELB)   │ (or sync) │                  │
└──────┬───────────┘           └──────────────────┘
       │ 3. Choose Instance 2, proxy request
       ▼
┌──────────────┐
│  Inventory   │
│  Service     │
│  (Instance 2)│
└──────────────┘
```

## Server-Side Discovery Implementation

### Simple Client Code

```csharp
// Client code is simple - just call the load balancer
public class ServerSideDiscoveryHttpClient
{
    private readonly HttpClient _httpClient;
    private readonly string _loadBalancerUrl;
    
    public ServerSideDiscoveryHttpClient(string loadBalancerUrl)
    {
        _loadBalancerUrl = loadBalancerUrl;
        _httpClient = new HttpClient();
    }
    
    public async Task<HttpResponseMessage> GetAsync(string serviceName, string path)
    {
        // Simple! Load balancer handles discovery and routing
        var url = $"{_loadBalancerUrl}/{serviceName}{path}";
        return await _httpClient.GetAsync(url);
    }
}

// Usage - client doesn't know about service instances or registry
var response = await client.GetAsync("inventory-service", "/api/stock/12345");
```

### Kubernetes Service (Built-in Server-Side)

```yaml
# Kubernetes Service acts as built-in server-side load balancer
apiVersion: v1
kind: Service
metadata:
  name: inventory-service
  labels:
    app: inventory
spec:
  selector:
    app: inventory
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
  type: ClusterIP  # Load balances across pods automatically
  sessionAffinity: ClientIP  # Optional sticky sessions
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800
```

```csharp
// Client code - Kubernetes handles everything
public class KubernetesServiceClient
{
    private readonly HttpClient _httpClient;
    
    public async Task<T> CallServiceAsync<T>(string serviceName, string path)
    {
        // Kubernetes DNS resolves service name to ClusterIP
        // ClusterIP load-balances to healthy pods
        var url = $"http://{serviceName}{path}";
        
        var response = await _httpClient.GetAsync(url);
        response.EnsureSuccessStatusCode();
        
        return await response.Content.ReadFromJsonAsync<T>();
    }
}
```

### NGINX as Server-Side Load Balancer

```nginx
# nginx.conf
http {
    # Upstream defines backend instances
    upstream inventory-service {
        # Load balancing algorithm
        least_conn;
        
        # Service instances (updated via Consul template or similar)
        server 10.0.1.10:8080 weight=3 max_fails=3 fail_timeout=30s;
        server 10.0.1.11:8080 weight=2 max_fails=3 fail_timeout=30s;
        server 10.0.1.12:8080 weight=1 max_fails=3 fail_timeout=30s;
        
        # Health check
        check interval=10s rise=2 fall=3 timeout=5s;
    }
    
    server {
        listen 80;
        
        location /inventory-service/ {
            # Strip /inventory-service/ prefix
            rewrite ^/inventory-service/(.*) /$1 break;
            
            # Proxy to backend
            proxy_pass http://inventory-service;
            
            # Headers
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            
            # Timeouts
            proxy_connect_timeout 5s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;
        }
    }
}
```

**Pros of Server-Side Discovery:**
- ✅ **Simple clients:** No discovery or load balancing logic in clients
- ✅ **Language agnostic:** Any client can make standard HTTP calls
- ✅ **Centralized routing:** Load balancing logic in one place, easy to update
- ✅ **Built-in features:** Load balancers often provide SSL termination, rate limiting, logging
- ✅ **Operational maturity:** Battle-tested load balancers

**Cons of Server-Side Discovery:**
- ❌ **Extra hop:** Added latency from proxying through load balancer
- ❌ **Single point of failure:** Load balancer must be highly available
- ❌ **Limited flexibility:** All clients use the same load balancing algorithm
- ❌ **Operational overhead:** Additional component to deploy, monitor, and scale

## Comparison Matrix

| Aspect | Client-Side Discovery | Server-Side Discovery |
|--------|----------------------|----------------------|
| **Latency** | Lower (direct connection) | Slightly higher (extra hop) |
| **Client complexity** | High (discovery + LB logic) | Low (standard HTTP calls) |
| **Single point of failure** | No | Yes (load balancer) |
| **Language support** | Requires library per language | Universal (HTTP) |
| **Load balancing flexibility** | High (per-client customization) | Limited (centralized config) |
| **Operational complexity** | Lower (fewer components) | Higher (LB + HA setup) |
| **Caching strategy** | Client-controlled | LB-controlled |
| **Examples** | Netflix Ribbon, Consul Template | Kubernetes Services, AWS ALB, NGINX |

## Hybrid Approaches

### API Gateway with Service Discovery

```
Client → API Gateway → Service Registry → Backend Services
         (Server-Side)    ↓
                     Load Balance & Route
```

**Implementation with Ocelot (.NET):**
```json
{
  "Routes": [
    {
      "UpstreamPathTemplate": "/inventory/{everything}",
      "DownstreamPathTemplate": "/{everything}",
      "ServiceName": "inventory-service",
      "LoadBalancerOptions": {
        "Type": "RoundRobin"
      }
    }
  ],
  "GlobalConfiguration": {
    "ServiceDiscoveryProvider": {
      "Host": "consul",
      "Port": 8500,
      "Type": "Consul"
    }
  }
}
```

### Sidecar Proxy Pattern (Service Mesh)

```
Service A → Envoy Proxy → Service Registry → Envoy Proxy → Service B
         (Sidecar)                         (Sidecar)
```

**Istio VirtualService:**
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: inventory-service
spec:
  hosts:
  - inventory-service
  http:
  - route:
    - destination:
        host: inventory-service
        subset: v1
      weight: 90
    - destination:
        host: inventory-service
        subset: v2
      weight: 10
    timeout: 10s
    retries:
      attempts: 3
      perTryTimeout: 3s
```

## Decision Framework

### Choose Client-Side Discovery When:
- ✅ You have a homogeneous tech stack (all .NET, all Java, etc.)
- ✅ Performance is critical (can't afford extra hop)
- ✅ You need per-service custom load balancing
- ✅ Your team is comfortable with the complexity
- ✅ You want to avoid additional infrastructure components
- ✅ Example: Internal microservices with Netflix-style architecture

### Choose Server-Side Discovery When:
- ✅ You have polyglot services (multiple languages)
- ✅ You want to keep client code simple
- ✅ You're using Kubernetes (built-in server-side discovery)
- ✅ You need centralized traffic management
- ✅ You want to leverage existing load balancer features
- ✅ You need SSL termination, WAF, rate limiting at the edge
- ✅ Example: Kubernetes deployments, cloud-native apps

### Choose Service Mesh When:
- ✅ You need advanced traffic management (canary, blue-green)
- ✅ You want zero-trust security (mTLS between services)
- ✅ You need sophisticated observability (distributed tracing)
- ✅ You have many microservices (100+)
- ✅ Your team can handle the operational complexity
- ✅ Example: Large-scale production microservices

### Client-Side Discovery Metrics

```csharp
public class ObservableClientSideDiscovery
{
    private readonly Counter<long> _discoveryCounter;
    private readonly Histogram<double> _requestLatency;
    private readonly Gauge<int> _activeConnections;
    
    public ObservableClientSideDiscovery(IMeterFactory meterFactory)
    {
        var meter = meterFactory.Create("ClientDiscovery");
        
        _discoveryCounter = meter.CreateCounter<long>(
            "discovery.lookups",
            description: "Service discovery lookups");
        
        _requestLatency = meter.CreateHistogram<double>(
            "request.latency_ms",
            unit: "ms",
            description: "Request latency by service");
        
        _activeConnections = meter.CreateGauge<int>(
            "connections.active",
            description: "Active connections by instance");
    }
    
    public async Task<HttpResponseMessage> GetAsync(string serviceName, string path)
    {
        _discoveryCounter.Add(1, new KeyValuePair<string, object>("service", serviceName));
        
        var sw = Stopwatch.StartNew();
        try
        {
            var response = await ExecuteRequestAsync(serviceName, path);
            
            _requestLatency.Record(sw.Elapsed.TotalMilliseconds,
                new KeyValuePair<string, object>("service", serviceName),
                new KeyValuePair<string, object>("status", "success"));
            
            return response;
        }
        catch (Exception ex)
        {
            _requestLatency.Record(sw.Elapsed.TotalMilliseconds,
                new KeyValuePair<string, object>("service", serviceName),
                new KeyValuePair<string, object>("status", "failure"));
            throw;
        }
    }
}
```

## Key Takeaways

✅ Client-side discovery gives more control but adds client complexity

✅ Server-side discovery simplifies clients but requires load balancer infrastructure

✅ Kubernetes provides excellent built-in server-side discovery

✅ Service mesh combines benefits of both patterns with additional features

✅ Choose based on: team skills, infrastructure, polyglot needs, and scale

✅ Hybrid approaches (API Gateway, Service Mesh) often work best in practice
