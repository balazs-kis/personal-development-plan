# Lesson 5: Choosing the Right Consistency Model

## Learning Objectives

By the end of this lesson, you will be able to:
- Evaluate different consistency models for your application needs
- Make informed trade-offs between consistency, availability, and performance
- Apply different consistency models to different parts of the same system
- Configure consistency levels in popular databases (Cosmos DB, Cassandra)
- Recognize anti-patterns and common mistakes in consistency choices

---

## Introduction

There is no one-size-fits-all consistency model. The key to building successful distributed systems is choosing the right consistency model for each use case, understanding the trade-offs, and often using different models for different parts of your application. This lesson provides a framework for making these decisions and avoiding common pitfalls.

## Decision Framework

### The Consistency Spectrum

```
Strong              Causal              Eventual
Consistency         Consistency         Consistency
    ↓                   ↓                   ↓
Higher latency      Moderate latency     Lower latency
Lower availability  Good availability    Higher availability
Simpler code        Moderate complexity  More complex code
Fewer replicas      Regional replicas    Global replicas
```

### Key Questions to Ask

```csharp
public class ConsistencyDecisionHelper
{
    public ConsistencyModel RecommendConsistency(ApplicationRequirements requirements)
    {
        // 1. Can the system tolerate stale reads?
        if (requirements.CannotTolerateStaleReads)
        {
            return ConsistencyModel.Strong;
        }
        
        // 2. Are there causal dependencies that must be preserved?
        if (requirements.HasCausalDependencies)
        {
            return ConsistencyModel.Causal;
        }
        
        // 3. Do users need to see their own writes immediately?
        if (requirements.RequiresReadYourWrites)
        {
            return ConsistencyModel.Session;
        }
        
        // 4. Is availability more important than immediate consistency?
        if (requirements.AvailabilityOverConsistency)
        {
            return ConsistencyModel.Eventual;
        }
        
        // 5. Are there strict regulatory or financial requirements?
        if (requirements.RegulatoryCompliance)
        {
            return ConsistencyModel.Strong;
        }
        
        // Default: Session consistency (good balance)
        return ConsistencyModel.Session;
    }
}

public class ApplicationRequirements
{
    public bool CannotTolerateStaleReads { get; set; }
    public bool HasCausalDependencies { get; set; }
    public bool RequiresReadYourWrites { get; set; }
    public bool AvailabilityOverConsistency { get; set; }
    public bool RegulatoryCompliance { get; set; }
}
```

## Use Case Matrix

### Strong Consistency

**✅ Use When:**
- Financial transactions
- Inventory management
- Seat/room booking systems
- Auctions
- Unique constraints (usernames, emails)

```csharp
// Example: Bank transfer - MUST use strong consistency
public class BankTransferService
{
    public async Task<TransferResult> TransferAsync(
        string fromAccount,
        string toAccount,
        decimal amount)
    {
        // Use distributed transaction or consensus
        using var transaction = await _db.BeginTransactionAsync(
            IsolationLevel.Serializable);
        
        try
        {
            var from = await _db.GetAccountAsync(fromAccount);
            var to = await _db.GetAccountAsync(toAccount);
            
            if (from.Balance < amount)
            {
                throw new InsufficientFundsException();
            }
            
            from.Balance -= amount;
            to.Balance += amount;
            
            await _db.UpdateAccountsAsync(from, to);
            await transaction.CommitAsync();
            
            return TransferResult.Success();
        }
        catch
        {
            await transaction.RollbackAsync();
            throw;
        }
    }
}
```

**❌ Don't Use When:**
- High-volume reads
- Global distribution required
- Availability is critical
- Stale data is acceptable

### Causal Consistency

**✅ Use When:**
- Social media posts and comments
- Messaging systems
- Collaborative editing
- Activity feeds

```csharp
// Example: Social media comments
public class CommentService
{
    public async Task<Comment> PostReplyAsync(
        string postId,
        string parentCommentId,
        string content,
        VectorClock causalContext)
    {
        // Causal consistency ensures reply appears after parent
        var comment = new Comment
        {
            Id = Guid.NewGuid().ToString(),
            PostId = postId,
            ParentId = parentCommentId,
            Content = content
        };
        
        await _store.WriteAsync(comment, causalContext);
        return comment;
    }
}
```

**❌ Don't Use When:**
- No causal relationships exist
- Session guarantees are sufficient
- Strong consistency is required

### Session Consistency

**✅ Use When:**
- User profiles
- Shopping carts
- User preferences/settings
- Most user-facing features

```csharp
// Example: Shopping cart
public class CartService
{
    public async Task<Cart> AddItemAsync(
        string userId,
        CartItem item,
        string sessionToken)
    {
        var (cart, newToken) = await _store.ReadAsync<Cart>(
            $"cart:{userId}",
            sessionToken);
        
        cart.Items.Add(item);
        
        await _store.WriteAsync($"cart:{userId}", cart, newToken);
        
        return cart; // User immediately sees their addition
    }
}
```

**❌ Don't Use When:**
- Cross-session consistency needed
- Multiple users editing same data
- Strict ordering requirements

### Eventual Consistency

**✅ Use When:**
- Analytics/metrics
- Caching
- News feeds
- Product catalogs
- View counts, likes

```csharp
// Example: Like counter
public class LikeService
{
    public async Task LikePostAsync(string postId, string userId)
    {
        // Eventual consistency is fine - exact count not critical
        await _cache.IncrementAsync($"likes:{postId}");
        
        // Asynchronously persist to database
        _ = Task.Run(async () =>
        {
            await _db.RecordLikeAsync(postId, userId);
        });
    }
    
    public async Task<int> GetLikeCountAsync(string postId)
    {
        // May be slightly stale - that's OK
        return await _cache.GetAsync<int>($"likes:{postId}");
    }
}
```

**❌ Don't Use When:**
- Users need immediate feedback
- Causality must be preserved
- Data loss is unacceptable

## Mixed Consistency in One System

```csharp
public class ECommerceSystem
{
    // Different parts of the system use different consistency models
    
    // Strong consistency: Inventory
    public async Task<bool> ReserveInventoryAsync(string productId, int quantity)
    {
        // Cannot oversell - use strong consistency
        using var transaction = await _inventoryDb.BeginTransactionAsync(
            IsolationLevel.Serializable);
        
        var product = await _inventoryDb.GetProductAsync(productId);
        if (product.Available < quantity)
        {
            return false;
        }
        
        product.Available -= quantity;
        await _inventoryDb.UpdateProductAsync(product);
        await transaction.CommitAsync();
        
        return true;
    }
    
    // Session consistency: Shopping cart
    public async Task<Cart> AddToCartAsync(
        string userId,
        CartItem item,
        string sessionToken)
    {
        // User must see their own cart updates
        // Session consistency is sufficient
        return await _cartService.AddItemAsync(userId, item, sessionToken);
    }
    
    // Eventual consistency: Product recommendations
    public async Task<List<Product>> GetRecommendationsAsync(string userId)
    {
        // Stale recommendations are fine
        // Use cached, eventually consistent data
        return await _recommendationCache.GetAsync(userId);
    }
    
    // Eventual consistency: View counts
    public async Task IncrementViewCountAsync(string productId)
    {
        // Exact count not critical
        await _metricsService.IncrementAsync($"views:{productId}");
    }
}
```

## Common Anti-Patterns

### ❌ Anti-Pattern 1: Using Strong Consistency Everywhere

```csharp
// BAD: Everything uses strong consistency
public class OverlyConsistentSystem
{
    public async Task<User> GetUserProfileAsync(string userId)
    {
        // User profile doesn't need strong consistency!
        return await _db.ReadWithStrongConsistencyAsync<User>(userId);
        // Result: High latency, poor availability
    }
    
    public async Task<int> GetLikeCountAsync(string postId)
    {
        // Like count doesn't need strong consistency!
        return await _db.ReadWithStrongConsistencyAsync<int>($"likes:{postId}");
        // Result: Unnecessary coordination overhead
    }
}

// GOOD: Choose appropriate consistency per use case
public class WellDesignedSystem
{
    public async Task<User> GetUserProfileAsync(string userId, string sessionToken)
    {
        // Session consistency - user sees their own updates
        return await _db.ReadWithSessionAsync<User>(userId, sessionToken);
    }
    
    public async Task<int> GetLikeCountAsync(string postId)
    {
        // Eventual consistency from cache
        return await _cache.GetAsync<int>($"likes:{postId}");
    }
}
```

### ❌ Anti-Pattern 2: Ignoring Consistency Completely

```csharp
// BAD: No thought given to consistency
public class InconsistentSystem
{
    public async Task UpdateUserEmailAsync(string userId, string newEmail)
    {
        // Write to cache
        await _cache.SetAsync($"user:{userId}:email", newEmail);
        
        // Write to database (eventually)
        _ = Task.Run(() => _db.UpdateEmailAsync(userId, newEmail));
        
        // Problem: User might not see their own email change!
    }
}

// GOOD: Appropriate consistency guarantees
public class ConsistentSystem
{
    public async Task UpdateUserEmailAsync(
        string userId,
        string newEmail,
        string sessionToken)
    {
        // Write to database first
        var newToken = await _db.WriteWithSessionAsync(
            $"user:{userId}",
            new { Email = newEmail },
            sessionToken);
        
        // Invalidate cache
        await _cache.RemoveAsync($"user:{userId}");
        
        // User will see their update (Read-Your-Writes)
        return newToken;
    }
}
```

### ❌ Anti-Pattern 3: Mixing Consistency Models Incorrectly

```csharp
// BAD: Inconsistent consistency between related data
public class MixedIncorrectly
{
    public async Task PlaceOrderAsync(Order order)
    {
        // Strong consistency for inventory
        await _inventoryDb.ReserveItemsAsync(order.Items);
        
        // Eventual consistency for order record
        _ = Task.Run(() => _orderDb.CreateOrderAsync(order));
        
        // Problem: Inventory reserved but order might fail!
        // User charged but no order exists!
    }
}

// GOOD: Related operations use same consistency
public class MixedCorrectly
{
    public async Task PlaceOrderAsync(Order order)
    {
        // Both use strong consistency for atomicity
        using var transaction = await _db.BeginTransactionAsync();
        
        await _inventoryDb.ReserveItemsAsync(order.Items, transaction);
        await _orderDb.CreateOrderAsync(order, transaction);
        
        await transaction.CommitAsync();
    }
}
```

## Performance Implications

Understanding the performance characteristics of each consistency model helps make informed decisions.

```csharp
public class ConsistencyPerformanceDemo
{
    public async Task DemonstrateLatencyDifferencesAsync()
    {
        var stopwatch = Stopwatch.StartNew();
        
        // Strong consistency: ~100-500ms (cross-datacenter coordination)
        stopwatch.Restart();
        await _strongDb.ReadAsync("key");
        var strongLatency = stopwatch.ElapsedMilliseconds;
        
        // Session consistency: ~10-50ms (local replica with session token)
        stopwatch.Restart();
        await _sessionDb.ReadAsync("key", sessionToken);
        var sessionLatency = stopwatch.ElapsedMilliseconds;
        
        // Eventual consistency: ~5-20ms (nearest replica, no coordination)
        stopwatch.Restart();
        await _eventualDb.ReadAsync("key");
        var eventualLatency = stopwatch.ElapsedMilliseconds;
        
        _logger.LogInformation(
            "Latencies - Strong: {Strong}ms, Session: {Session}ms, Eventual: {Eventual}ms",
            strongLatency, sessionLatency, eventualLatency);
        
        // Typical results: Strong is 5-20x slower than eventual
    }
    
    public async Task DemonstrateThroughputDifferencesAsync()
    {
        // Strong consistency: Limited by coordinator throughput
        // ~1,000-10,000 writes/second (single leader)
        
        // Eventual consistency: Scales with replicas
        // ~100,000+ writes/second (multi-master)
        
        var tasks = new List<Task>();
        var writeCount = 10000;
        
        var sw = Stopwatch.StartNew();
        for (int i = 0; i < writeCount; i++)
        {
            tasks.Add(_eventualDb.WriteAsync($"key{i}", $"value{i}"));
        }
        await Task.WhenAll(tasks);
        sw.Stop();
        
        var throughput = writeCount / sw.Elapsed.TotalSeconds;
        _logger.LogInformation(
            "Eventual consistency throughput: {Throughput} writes/second",
            throughput);
    }
}
```

### Cost-Benefit Analysis

| Model | Latency | Throughput | Availability | Complexity | Best For |
|-------|---------|------------|--------------|------------|----------|
| **Strong** | High | Low | Lower | Low (simple) | Finance, inventory |
| **Causal** | Medium | Medium | Good | Medium | Social media, collab |
| **Session** | Low-Medium | High | High | Medium | User profiles, carts |
| **Eventual** | Low | Very High | Very High | High (conflicts) | Analytics, caching |

```csharp
public class CosmosDbConsistencyConfig
{
    // Account-level default
    public CosmosClient CreateClientWithDefaultConsistency()
    {
        return new CosmosClient(

            {
                // Account default (can be overridden per request)

        string partitionKey,
        ConsistencyLevel consistency)

        {
            ConsistencyLevel = consistency
        };

            new PartitionKey(partitionKey),
            requestOptions);
        
        return response.Resource;
    }
    
    // Different operations, different consistency
    public async Task ProcessOrderAsync(Order order)
    {
        // Strong consistency for payment
        await WritePaymentAsync(order, ConsistencyLevel.Strong);
        
        // Session consistency for user's order view
        await WriteOrderRecordAsync(order, ConsistencyLevel.Session);
        
        // Eventual consistency for analytics
        await WriteAnalyticsAsync(order, ConsistencyLevel.Eventual);
    }
```

### Cassandra Consistency Configuration

```csharp
public class CassandraConsistencyConfig
{
    private readonly ISession _session;
    
    // Writes
    public async Task WriteWithQuorumAsync(string key, string value)
    {
        var statement = new SimpleStatement(
            "INSERT INTO data (key, value) VALUES (?, ?)",
            key, value)
            .SetConsistencyLevel(ConsistencyLevel.Quorum); // Majority
        
        await _session.ExecuteAsync(statement);
    }
    
    public async Task WriteWithLocalQuorumAsync(string key, string value)
    {
        var statement = new SimpleStatement(
            "INSERT INTO data (key, value) VALUES (?, ?)",
            key, value)
            .SetConsistencyLevel(ConsistencyLevel.LocalQuorum); // Majority in DC
        
        await _session.ExecuteAsync(statement);
    }
    
    public async Task WriteEventuallyAsync(string key, string value)
    {
        var statement = new SimpleStatement(
            "INSERT INTO data (key, value) VALUES (?, ?)",
            key, value)
            .SetConsistencyLevel(ConsistencyLevel.One); // Fast, eventual
        
        await _session.ExecuteAsync(statement);
    }
    
    // Reads
    public async Task<string> ReadStrongAsync(string key)
    {
        var statement = new SimpleStatement(
            "SELECT value FROM data WHERE key = ?", key)
            .SetConsistencyLevel(ConsistencyLevel.All); // All replicas
        
        var result = await _session.ExecuteAsync(statement);
        return result.First().GetValue<string>("value");
    }
    
    public async Task<string> ReadEventualAsync(string key)
    {
        var statement = new SimpleStatement(
            "SELECT value FROM data WHERE key = ?", key)
            .SetConsistencyLevel(ConsistencyLevel.One); // Single replica
        
        var result = await _session.ExecuteAsync(statement);
        return result.First().GetValue<string>("value");
    }
}
```

## Migration Strategy

When changing consistency models, plan the migration carefully.

```csharp
public class ConsistencyMigrationStrategy
{
    // Phase 1: Add feature flag
    public async Task<User> GetUserAsync(string userId, string sessionToken)
    {
        if (_featureFlags.IsEnabled("strong_consistency_user_reads"))
        {
            return await _db.ReadStrongAsync<User>(userId);
        }
        else
        {
            return await _db.ReadSessionAsync<User>(userId, sessionToken);
        }
    }
    
    // Phase 2: Monitor metrics
    public async Task MonitorConsistencyMigrationAsync()
    {
        var strongReadLatency = await _metrics.GetP99LatencyAsync("user_read_strong");
        var sessionReadLatency = await _metrics.GetP99LatencyAsync("user_read_session");
        
        _logger.LogInformation(
            "Migration metrics - Strong: {StrongP99}ms, Session: {SessionP99}ms",
            strongReadLatency, sessionReadLatency);
        
        // Monitor error rates, user complaints, etc.
    }
    
    // Phase 3: Gradual rollout
    public async Task GradualRolloutAsync()
    {
        // 10% -> 50% -> 100% over days/weeks
        await _featureFlags.SetRolloutPercentageAsync(
            "strong_consistency_user_reads",
            percentage: 10);
        
        // Monitor for issues before increasing
    }
}
```

## Key Takeaways

- No single consistency model is right for all use cases
- Stronger consistency = higher latency, lower availability
- Weaker consistency = higher availability, more complex application logic
- Most systems use multiple consistency models for different features
- Start with session consistency (good default for user-facing features)
- Use strong consistency only when absolutely necessary
- Use eventual consistency for high-volume, non-critical data
- Consider the impact on user experience when choosing consistency
- Configure consistency per operation when your database supports it
- Test failure scenarios to validate your consistency choices
