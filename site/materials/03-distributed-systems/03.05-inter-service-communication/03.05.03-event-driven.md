## Introduction

Event-driven communication enables loose coupling between services. Instead of services calling each other directly, they publish events about what happened, and interested services subscribe to those events. This pattern is fundamental for building scalable, resilient microservices architectures.

## Key Concepts

### Events vs Commands

**Command**: "Do something"
```csharp
// Command - imperative, directed to specific service
public class ProcessPaymentCommand
{
    public Guid OrderId { get; set; }
    public decimal Amount { get; set; }
    public string PaymentMethod { get; set; }
}

// Sent to: Payment Service (specific recipient)
// Expectation: Payment will be processed
```

**Event**: "Something happened"
```csharp
// Event - past tense, broadcast to anyone interested
public class OrderPlacedEvent
{
    public Guid OrderId { get; set; }
    public Guid CustomerId { get; set; }
    public DateTime OrderDate { get; set; }
    public decimal Total { get; set; }
    public List<OrderItemDto> Items { get; set; }
}

// Published to: Anyone who subscribes
// Subscribers: Inventory, Shipping, Analytics, Notification services
```

### Publish-Subscribe Pattern

```
┌──────────────┐
│   Publisher  │
│ (Order Svc)  │
└──────┬───────┘
       │ Publishes: OrderPlaced
       ▼
┌──────────────┐
│ Message Broker│
│  (RabbitMQ/  │
│    Kafka)    │
└──┬─────┬──┬──┘
   │     │  │
   │     │  └────────────────────┐
   │     │                       │
   ▼     ▼                       ▼
┌─────┐ ┌──────────┐  ┌─────────────────┐
│Inven│ │Shipping  │  │Notification Svc │
│tory │ │Service   │  │                 │
└─────┘ └──────────┘  └─────────────────┘
```

**Implementation:**
```csharp
// Publisher
public class OrderService
{
    private readonly IEventBus _eventBus;

    public async Task<Order> CreateOrderAsync(CreateOrderDto dto)
    {
        var order = new Order(dto);
        await _repository.SaveAsync(order);

        // Publish event
        await _eventBus.PublishAsync(new OrderPlacedEvent
        {
            OrderId = order.Id,
            CustomerId = order.CustomerId,
            Total = order.Total,
            Items = order.Items.Select(i => new OrderItemDto
            {
                ProductId = i.ProductId,
                Quantity = i.Quantity
            }).ToList()
        });

        return order;
    }
}

// Subscriber
public class InventoryEventHandler : IEventHandler<OrderPlacedEvent>
{
    public async Task HandleAsync(OrderPlacedEvent @event)
    {
        foreach (var item in @event.Items)
        {
            await _inventoryService.ReserveStockAsync(
                item.ProductId, 
                item.Quantity);
        }
    }
}
```

## Event Design Principles

### 1. Event Naming

**Good names** (past tense, describes what happened):
- `OrderPlaced`
- `PaymentProcessed`
- `UserRegistered`
- `InventoryReserved`

**Poor names**:
- `PlaceOrder` (sounds like a command)
- `Order` (not descriptive)
- `OrderEvent` (too generic)

### 2. Event Content

**Thin Events** (just IDs):
```csharp
public class OrderPlacedEvent
{
    public Guid OrderId { get; set; }
}
```

**Pros**: Small messages, no coupling  
**Cons**: Consumers must query for details

**Fat Events** (full data):
```csharp
public class OrderPlacedEvent
{
    public Guid OrderId { get; set; }
    public Guid CustomerId { get; set; }
    public string CustomerName { get; set; }
    public string CustomerEmail { get; set; }
    public List<OrderItemDto> Items { get; set; }
    public decimal Total { get; set; }
    public AddressDto ShippingAddress { get; set; }
}
```

**Pros**: Self-contained, no queries needed  
**Cons**: Larger messages, some coupling

**Recommended**: Middle ground - include commonly needed data

### 3. Event Versioning

**Strategy 1: Additive Changes Only**
```csharp
// V1
public class OrderPlacedEvent
{
    public Guid OrderId { get; set; }
    public decimal Total { get; set; }
}

// V2 - add optional field
public class OrderPlacedEvent
{
    public Guid OrderId { get; set; }
    public decimal Total { get; set; }
    public string? CouponCode { get; set; } // New, optional
}
```

**Strategy 2: Separate Event Types**
```csharp
public class OrderPlacedEvent_V1 { ... }
public class OrderPlacedEvent_V2 { ... }
```

**Strategy 3: Schema Registry**
- Use tools like Confluent Schema Registry
- Version schemas centrally
- Enforce compatibility rules

## Choreography vs Orchestration

### Choreography (Decentralized)

**Pattern**: Services react to events independently

```
OrderService publishes OrderPlaced
    │
    ├──▶ InventoryService: reserves stock → publishes StockReserved
    │         │
    │         └──▶ ShippingService: creates shipment
    │
    ├──▶ PaymentService: processes payment → publishes PaymentProcessed
    │         │
    │         └──▶ OrderService: confirms order
    │
    └──▶ NotificationService: sends confirmation email
```

**Pros**:
- ✅ Loose coupling
- ✅ Easy to add new participants
- ✅ No single point of failure

**Cons**:
- ❌ Hard to understand overall flow
- ❌ Difficult to debug
- ❌ No central place to manage state

**Implementation Example:**
```csharp
// Order Service
public class OrderService
{
    public async Task PlaceOrderAsync(PlaceOrderCommand command)
    {
        var order = new Order(command);
        await _repository.SaveAsync(order);
        
        await _eventBus.PublishAsync(new OrderPlacedEvent
        {
            OrderId = order.Id,
            CustomerId = order.CustomerId,
            Items = order.Items,
            Total = order.Total
        });
    }
}

// Services react independently to OrderPlacedEvent
// Inventory, Payment, Notification services each have handlers

### Orchestration (Centralized)

**Pattern**: Central orchestrator coordinates workflow

```
┌──────────────────────────┐
│  Order Saga Orchestrator │
└────┬─────┬─────┬─────┬───┘
     │     │     │     │
     ▼     ▼     ▼     ▼
  Inventory  Payment  Shipping  Notification
  Service    Service  Service   Service
```

**Implementation:**
```csharp
public class OrderSaga
{
    public async Task ExecuteAsync(CreateOrderCommand cmd)
    {
        var sagaId = Guid.NewGuid();
        var state = new OrderSagaState { SagaId = sagaId, Command = cmd };
        
        try
        {
            var orderId = await _orderService.CreateOrderAsync(cmd);
            state.OrderId = orderId;
            
            await _inventoryService.ReserveStockAsync(cmd.Items);
            var paymentId = await _paymentService.ProcessPaymentAsync(cmd.CustomerId, cmd.Total);
            await _shippingService.CreateShipmentAsync(orderId);
            
            state.Status = SagaStatus.Completed;
            await _orderService.ConfirmOrderAsync(orderId);
        }
        catch (Exception ex)
        {
            await CompensateAsync(state);
            throw;
        }
    }
    
    private async Task CompensateAsync(OrderSagaState state)
    {
        if (state.OrderId != Guid.Empty)
        {
            await _inventoryService.ReleaseStockAsync(state.Command.Items);
            await _orderService.CancelOrderAsync(state.OrderId);
        }
    }
}
```

**Pros**:
- ✅ Clear workflow
- ✅ Easy to debug
- ✅ Central state management
- ✅ Explicit compensation logic

**Cons**:
- ❌ Orchestrator is a dependency
- ❌ Can become complex
- ❌ Single point of failure (mitigate with redundancy)

**Durable Orchestration:**
```csharp
[FunctionName("OrderSaga")]
public async Task<OrderResult> RunOrchestrator([OrchestrationTrigger] IDurableOrchestrationContext context)
{
    var cmd = context.GetInput<CreateOrderCommand>();
    
    try
    {
        var orderId = await context.CallActivityAsync<Guid>("CreateOrder", cmd);
        await context.CallActivityAsync("ReserveStock", cmd.Items);
        await context.CallActivityAsync("ProcessPayment", (cmd.CustomerId, cmd.Total));
        return new OrderResult { OrderId = orderId, Success = true };
    }
    catch
    {
        await context.CallActivityAsync("CompensateOrder", orderId);
        throw;
    }
}
```

### Choosing Between Choreography and Orchestration

**Use Choreography when:**
- Simple workflows (2-3 steps)
- Services should be highly decoupled
- Adding new participants frequently
- No complex business rules
- Failure handling is simple

**Use Orchestration when:**
- Complex workflows (4+ steps)
- Need visibility into workflow state
- Complex compensation logic
- Business rules span multiple services
- Need to audit complete workflow

**Hybrid Approach:**
```csharp
// High-level orchestration
public class OrderWorkflowOrchestrator
{
    public async Task ProcessOrderAsync(CreateOrderCommand cmd)
    {
        // Orchestrate critical path
        var orderId = await _orderService.CreateOrderAsync(cmd);
        await _inventoryService.ReserveStockAsync(cmd.Items);
        var paymentId = await _paymentService.ProcessPaymentAsync(cmd.CustomerId, cmd.Total);
        
        // Publish event for choreographed side effects
        await _eventBus.PublishAsync(new OrderConfirmedEvent
        {
            OrderId = orderId,
            PaymentId = paymentId,
            CustomerId = cmd.CustomerId
        });
        
        // These happen via choreography:
        // - Shipping service creates shipment
        // - Notification service sends emails
        // - Analytics service tracks metrics
        // - Loyalty service awards points
    }
}
```

## Message Delivery Semantics

### At-Most-Once
- Message delivered **zero or one time**
- May be lost
- **Use when**: Loss is acceptable (e.g., metrics, telemetry)

**Implementation:**
```csharp
// Fire and forget - no acknowledgment
await _messageBus.PublishAsync(message, deliveryMode: DeliveryMode.AtMostOnce);
// If publish fails, message is lost - no retry
```

**Example scenarios:**
- Real-time metrics (losing one data point is OK)
- Non-critical notifications
- Telemetry data
- Performance monitoring

### At-Least-Once
- Message delivered **one or more times**
- May be duplicated
- **Use when**: Duplicates can be handled (idempotent consumers)
- **Most common** in practice

**Implementation:**
```csharp
// Publish with retry
await _messageBus.PublishAsync(message, new PublishOptions
{
    DeliveryMode = DeliveryMode.Persistent,
    RetryAttempts = 3,
    RetryDelay = TimeSpan.FromSeconds(5)
});

// Consumer acknowledges after successful processing
public class OrderEventHandler : IEventHandler<OrderPlacedEvent>
{
    public async Task HandleAsync(OrderPlacedEvent @event)
    {
        await ProcessOrderAsync(@event);
        // Message broker only removes message after acknowledgment
    }
}
```

**Why duplicates occur:**
- Message processed but acknowledgment lost
- Network timeout during processing  
- Service crashes after processing, before ack

### Exactly-Once
- Message delivered **exactly one time**
- Very difficult to achieve in distributed systems
- Often "at-least-once + idempotency" instead

**Why it's hard:** Requires coordination between producer, broker, and consumer. High latency, complex infrastructure.

**Approximation with Kafka:**
```csharp
// Kafka transactions (closest to exactly-once)
var producer = new ProducerBuilder<string, string>(config)
    .SetTransactionalId("order-producer")
    .Build();

producer.InitTransactions();

try
{
    producer.BeginTransaction();
    await producer.ProduceAsync("orders", message);
    await UpdateDatabaseAsync();
    producer.CommitTransaction();
}
catch
{
    producer.AbortTransaction();
    throw;
}
```

**Implementing Idempotency**:
```csharp
public class PaymentEventHandler : IEventHandler<ProcessPaymentEvent>
{
    public async Task HandleAsync(ProcessPaymentEvent @event)
    {
        // Check if already processed using unique message ID
        if (await _repository.ExistsAsync(@event.MessageId))
        {
            _logger.LogInformation(
                "Payment {PaymentId} already processed (MessageId: {MessageId})", 
                @event.PaymentId,
                @event.MessageId);
            return; // Idempotent - safe to call multiple times
        }

        // Process payment
        await _paymentService.ProcessAsync(@event);
        
        // Store message ID to prevent reprocessing
        await _repository.MarkProcessedAsync(@event.MessageId, DateTime.UtcNow);
    }
}

// Message ID in event
public class ProcessPaymentEvent
{
    public Guid MessageId { get; set; } = Guid.NewGuid();  // Unique per publish
    public Guid PaymentId { get; set; }
    public decimal Amount { get; set; }
}

// Tracking table
public class ProcessedMessage
{
    public Guid MessageId { get; set; }
    public DateTime ProcessedAt { get; set; }
    public string Handler { get; set; }
}

// Cleanup old processed messages (after retention period)
public class ProcessedMessageCleanupService : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await _repository.DeleteProcessedBefore(DateTime.UtcNow.AddDays(-7));
            await Task.Delay(TimeSpan.FromHours(24), stoppingToken);
        }
    }
}
```

**Idempotency with Natural Keys:**
```csharp
// Use business keys instead of message IDs
public class InventoryEventHandler : IEventHandler<ReserveStockEvent>
{
    public async Task HandleAsync(ReserveStockEvent @event)
    {
        // Check using business keys
        var exists = await _repository.ReservationExistsAsync(@event.OrderId, @event.ProductId);
        if (exists) return; // Already done
        
        await _repository.CreateReservationAsync(new StockReservation
        {
            OrderId = @event.OrderId,
            ProductId = @event.ProductId,
            Quantity = @event.Quantity
        });
    }
}
```

**Database Transaction with Message (Outbox Pattern):**
```csharp
// Transactional outbox pattern (for exactly-once semantics)
public class OrderService
{
    public async Task PlaceOrderAsync(CreateOrderCommand command)
    {
        using var transaction = await _dbContext.Database.BeginTransactionAsync();
        
        // Save order and event to outbox in same transaction
        var order = new Order(command);
        await _dbContext.Orders.AddAsync(order);
        
        var outboxMessage = new OutboxMessage
        {
            EventType = nameof(OrderPlacedEvent),
            Payload = JsonSerializer.Serialize(new OrderPlacedEvent { ... })
        };
        await _dbContext.OutboxMessages.AddAsync(outboxMessage);
        
        await _dbContext.SaveChangesAsync();
        await transaction.CommitAsync();
    }
}

// Background service publishes from outbox
public class OutboxPublisher : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var messages = await _dbContext.OutboxMessages
                .Where(m => !m.Published)
                .Take(100)
                .ToListAsync();
            
            foreach (var message in messages)
            {
                await _messageBus.PublishAsync(message.EventType, message.Payload);
                message.Published = true;
            }
            
            await _dbContext.SaveChangesAsync();
            await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
        }
    }
}
```

2. **Choose Pattern**: Choreography or Orchestration? Why?

**Analysis:**
```
Choreography Approach:
✅ Pros:
  - Loose coupling between services
  - Easy to add new subscribers (e.g., Analytics, Loyalty)
  - No single point of failure
  - Services independently scalable
  
❌ Cons:
  - Hard to visualize complete workflow
  - Difficult to track order status across services
  - No central error handling
  - Complex debugging

Orchestration Approach:
✅ Pros:
  - Clear workflow definition
  - Central status tracking
  - Easy compensation logic
  - Better observability
  
❌ Cons:
  - Orchestrator becomes critical dependency
  - Services coupled to orchestrator
  - More complex to add new steps

Recommendation: Hybrid
  - Orchestrate critical path (Order → Inventory → Payment)
  - Choreograph side effects (Shipping, Notifications, Analytics)
  
Why: Critical business logic needs visibility and control,
     while side effects benefit from loose coupling
```

3. **Design Event Schema**: For `OrderPlacedEvent`, what data should it include?

**Schema Design:**
```csharp
public class OrderPlacedEvent
{
    // Correlation
    public Guid EventId { get; set; }        // Unique event identifier
    public Guid OrderId { get; set; }        // Order identifier
    public Guid CorrelationId { get; set; }  // Track related events
    public DateTime Timestamp { get; set; }   // When event occurred
    
    // Core Order Data (needed by most consumers)
    public Guid CustomerId { get; set; }
    public string CustomerEmail { get; set; }  // For notifications
    public decimal TotalAmount { get; set; }
    
    // Order Items (needed by inventory, shipping)
    public List<OrderItemDto> Items { get; set; }
    
    // Shipping Information (needed by shipping service)
    public AddressDto ShippingAddress { get; set; }
    
    // Payment Information (needed by payment service)
    public PaymentMethodDto PaymentMethod { get; set; }
    
    // Metadata
    public string OrderSource { get; set; }   // Web, Mobile, API
    public Dictionary<string, string> Metadata { get; set; }
}

public class OrderItemDto
{
    public Guid ProductId { get; set; }
    public string ProductName { get; set; }   // Snapshot for notifications
    public int Quantity { get; set; }
    public decimal UnitPrice { get; set; }     // Snapshot price at order time
    public decimal Subtotal { get; set; }
}

Rationale:
  - Include commonly needed data (avoid extra service calls)
  - Snapshot data that might change (prices, names)
  - Balance: Not too fat (avoid 10KB events), not too thin
  - Include correlation ID for tracing
```

4. **Handle Failures**: What if payment fails after inventory is reserved?

**Compensation Strategies:**
- Choreography: PaymentFailed event triggers inventory to release stock
- Orchestration: Saga explicitly releases stock in catch block
- State Machine: Transition to Cancelling state, publish compensation events

Each approach handles rollback differently but achieves same goal.

5. **Idempotency**: How do you ensure each service handles duplicate events?

**Implementation:**
- Message ID tracking: Store processed message IDs
- Natural key check: Use business keys (OrderId) to detect duplicates  
- Database constraints: Unique indexes prevent duplicate inserts
- Abstract base class for idempotent handlers simplifies implementation

## Self-Check Questions

1. **What's the difference between events and commands?**
   - Commands: Imperative, directed to specific recipient, expect action
     Example: "ProcessPayment" sent to Payment Service
   - Events: Past tense, broadcast to interested parties, describe what happened
     Example: "OrderPlaced" published for any service to consume
   - Commands: One receiver, Events: Zero or more receivers
   - Commands: Caller cares if it succeeds, Events: Publisher doesn't know who handles

2. **Why is idempotency important?**
   - At-least-once delivery can cause duplicates
   - Services must handle processing same message multiple times
   - Without idempotency: Double charges, duplicate shipments, incorrect inventory
   - Enables safe retries after failures
   - Required for reliable message processing

3. **When to use choreography vs orchestration?**
   - Choreography: Simple workflows (2-3 steps), prefer loose coupling, easy to extend
     Example: OrderPlaced → multiple independent reactions
   - Orchestration: Complex workflows (4+ steps), need visibility, complex compensation
     Example: Multi-step booking with interdependencies
   - Consider hybrid: Orchestrate critical path, choreograph side effects

4. **How do you version events?**
   - Additive changes only: Add optional fields, don't remove or rename
   - Separate event types: OrderPlacedEvent_V1, OrderPlacedEvent_V2
   - Schema registry: Centrally manage and enforce compatibility
   - Event upcasting: Convert old events to new format on read
   - Version field: Include version number in event for routing

5. **What is the outbox pattern?**
   - Stores events in database alongside business data in same transaction
   - Background process publishes from outbox to message broker
   - Ensures atomicity: Either both save or neither
   - Prevents lost events if message broker is unavailable
   - Achieves exactly-once delivery semantics

6. **How do you handle event ordering?**
   - Single partition per aggregate: All events for one order on same partition
   - Sequence numbers: Include ordering metadata in events
   - Event sourcing: Natural ordering via event stream
   - Caution: Ordering across different aggregates is hard
   - Often: Design to not require strict ordering

7. **What's the difference between pub/sub and message queue?**
   - Pub/Sub: One message, many subscribers (broadcast)
     Example: OrderPlaced → Inventory, Payment, Shipping all receive
   - Message Queue: One message, one consumer (load distribution)
     Example: Send email task → one worker processes
   - Pub/Sub: Topic-based, Message Queue: Queue-based
   - Both: Decouple producer from consumer

## Key Takeaways

✅ **Events** enable loose coupling between services - publishers don't know consumers

✅ **Pub/Sub** allows multiple consumers to react to events independently

✅ **Choreography** = decentralized (loose coupling), **Orchestration** = centralized (visibility)

✅ **Idempotency** is essential for at-least-once delivery - design handlers to be reentrant

✅ **Event design** matters: naming (past tense), content (fat vs thin), versioning (additive)

✅ **Message brokers** provide durability, routing, delivery guarantees

✅ **Outbox pattern** ensures atomicity between database and events

✅ **Correlation IDs** enable tracing events across distributed workflows

✅ **Compensating transactions** handle failures in event-driven systems

✅ **Schema evolution** must be carefully managed to avoid breaking consumers

## Common Pitfalls

**1. Making events too granular:**
```
❌ Don't: Publish separate events for every field change
   UserNameChanged, UserEmailChanged, UserPhoneChanged...
   
✅ Do: Publish meaningful business events
   UserProfileUpdated { changes: { name, email, phone } }
```

**2. Not handling duplicates:**
```
❌ Don't: Assume exactly-once delivery
   Decrement inventory without checking
   
✅ Do: Implement idempotent handlers
   Check if already processed, use unique keys
```

**3. Circular event dependencies:**
```
❌ Don't: Create event loops
   OrderService publishes OrderPlaced
   → InventoryService reserves stock, publishes StockReserved
   → OrderService handles StockReserved, publishes OrderPlaced
   [infinite loop!]
   
✅ Do: Design event flows as DAG (directed acyclic graph)
```

**4. Synchronous calls in event handlers:**
```
❌ Don't: Make blocking calls in handlers
   public async Task HandleAsync(OrderPlaced @event)
   {
       await _inventoryService.GetStock(@event.ProductId); // Sync call!
   }
   Defeats purpose of async messaging
   
✅ Do: Include needed data in events or query asynchronously
```

**5. No dead letter queue:**
```
❌ Don't: Retry failed messages infinitely
   Poison messages block queue
   
✅ Do: Move to dead-letter queue after N retries
   Monitor DLQ, investigate and replay
```

**6. Ignoring event ordering:**
```
❌ Don't: Assume events arrive in order across services
   
✅ Do: Use sequence numbers or timestamps
   Handle out-of-order events gracefully
```
