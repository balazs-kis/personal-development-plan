## Introduction

In distributed systems, failures are inevitable — network issues, service crashes, slow responses, and overloaded systems all happen regularly. The key to resilient microservices isn't preventing failures, but handling them gracefully. This lesson covers essential patterns for building fault-tolerant communication between services.

## Key Concepts

### 1. Timeout Pattern

**Problem**: Service calls hang indefinitely

**Solution**: Set maximum wait time

```csharp
// Without timeout - dangerous!
var response = await _httpClient.GetAsync("/api/orders");

// With timeout
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
try
{
    var response = await _httpClient.GetAsync("/api/orders", cts.Token);
}
catch (OperationCanceledException)
{
    _logger.LogWarning("Request timed out after 5 seconds");
    throw new TimeoutException("Orders service did not respond in time");
}
```

**Best Practices**:
- Always set timeouts on external calls
- Different timeouts for different operations (queries vs commands)
- Consider network latency + processing time
- Typical values: 1-10 seconds for synchronous calls

---

### 2. Retry Pattern

**Problem**: Transient failures (network blips, temporary overload)

**Solution**: Retry failed requests with backoff

**Types of Retries**:

**Fixed Delay**:
```csharp
// Retry 3 times with 1 second between attempts
var policy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(
        retryCount: 3,
        sleepDurationProvider: attempt => TimeSpan.FromSeconds(1));

await policy.ExecuteAsync(async () =>
{
    return await _httpClient.GetAsync("/api/orders");
});
```

**Exponential Backoff**:
```csharp
// Retry with increasing delays: 1s, 2s, 4s
var policy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(
        retryCount: 3,
        sleepDurationProvider: attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt)));
```

**Exponential Backoff with Jitter** (Recommended):
```csharp
var policy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(
        retryCount: 3,
        sleepDurationProvider: attempt => 
        {
            var baseDelay = TimeSpan.FromSeconds(Math.Pow(2, attempt));
            var jitter = TimeSpan.FromMilliseconds(Random.Shared.Next(0, 1000));
            return baseDelay + jitter;
        });
```

**Why Jitter?** Prevents "thundering herd" — many clients retrying simultaneously.

**What to Retry**:
- ✅ Network errors (timeouts, connection refused)
- ✅ HTTP 429 (Too Many Requests)
- ✅ HTTP 503 (Service Unavailable)
- ✅ HTTP 504 (Gateway Timeout)
- ❌ HTTP 400 (Bad Request) — will never succeed
- ❌ HTTP 401/403 (Auth errors) — need different handling
- ❌ HTTP 404 (Not Found) — retrying won't help

### 3. Circuit Breaker Pattern

**Problem**: Calling a failing service wastes resources and delays failure

**Solution**: "Break the circuit" after repeated failures

**States**:

```
        Success count reaches threshold
    ┌──────────────────────────────┐
    │                              │
    ▼                              │
┌────────┐  Failures exceed    ┌──────┐  Timeout expires  ┌─────────────┐
│ Closed │   threshold         │ Open │───────────────────▶│ Half-Open   │
└────────┘────────────────────▶└──────┘                   └─────────────┘
    ▲                              │                             │
    │                              │   All requests              │ Test request
    │                              │   fail fast                 │ succeeds
    │                              │                             │
    └──────────────────────────────┴─────────────────────────────┘
          Test request fails
```

**States Explained**:
- **Closed**: Normal operation, requests flow through
- **Open**: Too many failures, requests fail immediately
- **Half-Open**: Testing if service recovered

**Implementation with Polly**:
```csharp
var circuitBreaker = Policy
    .Handle<HttpRequestException>()
    .CircuitBreakerAsync(
        handledEventsAllowedBeforeBreaking: 5,  // Break after 5 failures
        durationOfBreak: TimeSpan.FromMinutes(1), // Stay open for 1 minute
        onBreak: (exception, duration) =>
        {
            _logger.LogWarning("Circuit breaker opened for {Duration}", duration);
        },
        onReset: () =>
        {
            _logger.LogInformation("Circuit breaker reset");
        },
        onHalfOpen: () =>
        {
            _logger.LogInformation("Circuit breaker half-open, testing...");
        });

try
{
    await circuitBreaker.ExecuteAsync(async () =>
    {
        return await _httpClient.GetAsync("/api/orders");
    });
}
catch (BrokenCircuitException)
{
    _logger.LogWarning("Circuit is open, failing fast");
    // Return cached data or fallback response
}
```

**Advanced: Sliding Window**:
```csharp
var advancedCircuitBreaker = Policy
    .Handle<HttpRequestException>()
    .AdvancedCircuitBreakerAsync(
        failureThreshold: 0.5,  // Break if 50% of requests fail
        samplingDuration: TimeSpan.FromSeconds(10),  // In a 10-second window
        minimumThroughput: 5,   // Need at least 5 requests to calculate
        durationOfBreak: TimeSpan.FromMinutes(1));
```

### 4. Fallback Pattern

**Problem**: What to do when calls fail?

**Solution**: Provide degraded but functional response

**Strategies**:

**1. Return Cached Data**:
```csharp
var fallbackPolicy = Policy<ProductDto>
    .Handle<HttpRequestException>()
    .FallbackAsync(
        fallbackValue: await _cache.GetAsync<ProductDto>(productId),
        onFallbackAsync: async (result, context) =>
        {
            _logger.LogWarning("Falling back to cached product data");
        });
```

**2. Return Default Value**:
```csharp
var fallbackPolicy = Policy<List<Review>>
    .Handle<HttpRequestException>()
    .FallbackAsync(
        fallbackValue: new List<Review>(),  // Empty list
        onFallbackAsync: async (result, context) =>
        {
            _logger.LogWarning("Reviews service unavailable, returning empty list");
        });
```

**3. Call Alternative Service**:
```csharp
var fallbackPolicy = Policy<WeatherForecast>
    .Handle<HttpRequestException>()
    .FallbackAsync(async (context, ct) =>
    {
        // Primary service failed, try backup
        return await _backupWeatherService.GetForecastAsync();
    });
```

### 5. Bulkhead Pattern

**Problem**: One slow dependency consumes all resources

**Solution**: Isolate resources per dependency

```csharp
// Limit concurrent calls to orders service
var bulkhead = Policy.BulkheadAsync<HttpResponseMessage>(
    maxParallelization: 10,  // Max 10 concurrent requests
    maxQueuingActions: 20);  // Max 20 waiting in queue

try
{
    await bulkhead.ExecuteAsync(async () =>
    {
        return await _httpClient.GetAsync("/api/orders");
    });
}
catch (BulkheadRejectedException)
{
    _logger.LogWarning("Bulkhead capacity exceeded");
    return StatusCode(503, "Service temporarily overloaded");
}
```

**Why It Matters**:
- Prevents one slow service from blocking all threads
- Maintains capacity for other operations
- Provides predictable behavior under load

## Combining Policies

**Policy Wrap** (Recommended approach):
```csharp
// Combine multiple policies
var retryPolicy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(3, attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt)));

var circuitBreakerPolicy = Policy
    .Handle<HttpRequestException>()
    .CircuitBreakerAsync(5, TimeSpan.FromMinutes(1));

var fallbackPolicy = Policy<HttpResponseMessage>
    .Handle<HttpRequestException>()
    .Or<BrokenCircuitException>()
    .FallbackAsync(new HttpResponseMessage(HttpStatusCode.OK)
    {
        Content = new StringContent("{\"cached\": true}")
    });

// Wrap policies (order matters!)
var policyWrap = Policy.WrapAsync(fallbackPolicy, circuitBreakerPolicy, retryPolicy);

// Execute with all policies
var response = await policyWrap.ExecuteAsync(async () =>
{
    return await _httpClient.GetAsync("/api/orders");
});
```

**Order Matters**:
```
Fallback (outermost)
  ↓
Circuit Breaker
  ↓
Retry (innermost)
  ↓
Actual Call
```

## Best Practices

### 1. Different Policies for Different Services

```csharp
// Fast, reliable service: aggressive retries
var userServicePolicy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(5, attempt => TimeSpan.FromMilliseconds(100 * attempt));

// Slow, flaky service: conservative retries + circuit breaker
var legacyServicePolicy = Policy.WrapAsync(
    Policy.Handle<HttpRequestException>()
        .CircuitBreakerAsync(3, TimeSpan.FromMinutes(5)),
    Policy.Handle<HttpRequestException>()
        .WaitAndRetryAsync(2, attempt => TimeSpan.FromSeconds(2 * attempt)));
```

### 2. Idempotency

**Critical**: Ensure operations can be retried safely

```csharp
// ❌ NOT idempotent
[HttpPost("inventory/decrement")]
public async Task DecrementStock(int productId)
{
    var product = await _db.Products.FindAsync(productId);
    product.Stock--;  // Dangerous if retried!
    await _db.SaveChangesAsync();
}

// ✅ Idempotent
[HttpPost("inventory/reserve")]
public async Task ReserveStock(ReserveStockCommand cmd)
{
    // Check if already processed
    if (await _db.Reservations.AnyAsync(r => r.RequestId == cmd.RequestId))
        return;  // Already done, safe to ignore

    var reservation = new Reservation
    {
        RequestId = cmd.RequestId,  // Unique ID from client
        ProductId = cmd.ProductId,
        Quantity = cmd.Quantity
    };
    await _db.Reservations.AddAsync(reservation);
    await _db.SaveChangesAsync();
}
```

### 3. Monitoring

**Track resilience metrics**:
```csharp
var policy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(3,
        attempt => TimeSpan.FromSeconds(attempt),
        onRetry: (exception, timespan, retryCount, context) =>
        {
            _metrics.IncrementCounter("retry_attempts", new[]
            {
                new KeyValuePair<string, object>("service", "orders"),
                new KeyValuePair<string, object>("attempt", retryCount)
            });
        });
```

    Policy
        .Handle<HttpRequestException>()

**Inventory Service (critical):**
```csharp
// Timeout: 5 seconds (critical path, allow more time)
// Retry: 3 attempts with longer backoff (2s, 4s, 8s)
// Circuit breaker: Open after 10 failures in 30s, stay open 1 minute
// Fallback: None - must succeed or fail explicitly

var inventoryPolicy = Policy.WrapAsync(
    // Circuit breaker (no fallback - inventory is critical)
    Policy
        .Handle<Exception>()
        .AdvancedCircuitBreakerAsync(
            failureThreshold: 0.7,           // 70% failure rate
            samplingDuration: TimeSpan.FromSeconds(30),
            minimumThroughput: 10,
            durationOfBreak: TimeSpan.FromMinutes(1),
            onBreak: (exception, duration) =>
            {
                _logger.LogError(
                    "Inventory circuit breaker opened for {Duration}",
                    duration);
                _metrics.IncrementCounterAsync("inventory.circuit_open");
            }),
    
    // Bulkhead (limit concurrent calls to inventory)
    Policy.BulkheadAsync<HttpResponseMessage>(
        maxParallelization: 20,
        maxQueuingActions: 50),
    
    // Retry
    Policy
        .Handle<HttpRequestException>()
        .Or<TimeoutException>()
        .WaitAndRetryAsync(
            retryCount: 3,
            sleepDurationProvider: attempt =>

                _logger.LogWarning(

                    retryCount, timespan.TotalMilliseconds, exception.Message);
            }),
    
    // Timeout
    Policy.TimeoutAsync(TimeSpan.FromSeconds(5))
);
```

## Self-Check Questions

1. **Why exponential backoff with jitter?**
   - Exponential backoff: Gives service time to recover (1s, 2s, 4s, 8s...)
   - Prevents immediate retry storms
   - Jitter (randomization): Spreads out retry attempts from multiple clients
   - Without jitter: Thundering herd - all clients retry at same time
   - With jitter: Requests spread over time window

2. **When should circuit breaker open?**
   - After repeated failures exceed threshold (e.g., 5 failures, or 50% failure rate)
   - To prevent wasting resources on failing service
   - Allows service time to recover without constant load
   - Fails fast: Returns immediate error instead of waiting
   - Moves to half-open after timeout to test recovery

3. **What operations are safe to retry?**
   - Idempotent operations: GET, PUT with same payload
   - Commands with unique ID: Can detect and skip duplicates
   - HTTP GET: Safe to retry (read-only)
   - HTTP PUT (with idempotency key): Safe to retry
   - HTTP POST: Dangerous without idempotency (creates duplicates)
   - HTTP DELETE: Usually safe (deleting already-deleted is OK)

4. **What's the purpose of bulkhead pattern?**
   - Isolates resources per dependency (separate thread pools, connections)
   - Prevents one slow dependency from consuming all capacity
   - Limits concurrent calls to each service
   - Maintains capacity for other operations
   - Example: Limit inventory calls to 20 concurrent, reviews to 10

5. **How do you test resilience policies?**
   - Inject faults: Simulate timeouts, errors, slow responses
   - Chaos engineering: Randomly fail services in production
   - Load testing: Verify behavior under realistic load
   - Measure: Latencies, error rates, circuit breaker states
   - Tools: Simmy (chaos engineering), k6 (load testing)

6. **What's the order for wrapping policies?**
   - Innermost: Timeout (fail fast)
   - Middle: Retry (handle transient failures)
   - Middle: Circuit breaker (stop calling failed service)
   - Outer: Bulkhead (limit concurrency)
   - Outermost: Fallback (graceful degradation)
   - Execution flows outward, then inward

7. **When should you NOT retry?**
   - 400 Bad Request: Client error, won't succeed
   - 401 Unauthorized: Need new token, not transient
   - 404 Not Found: Resource doesn't exist
   - 422 Unprocessable Entity: Validation error
   - Any client error (4xx): Fix the request, don't retry

## Key Takeaways

✅ **Always set timeouts** on external calls - never let calls hang indefinitely

✅ **Retry with exponential backoff + jitter** for transient failures - gives services time to recover

✅ **Circuit breaker** prevents cascading failures - fail fast when service is down

✅ **Fallback** provides degraded functionality - better than complete failure

✅ **Bulkhead** isolates resources per dependency - one slow service doesn't block everything

✅ **Combine policies** for comprehensive resilience - wrap timeout, retry, breaker, fallback

✅ **Monitor** all resilience metrics - circuit breaker state, retry counts, latencies

✅ **Test failure scenarios** - chaos engineering, fault injection, load testing

✅ **Idempotency** enables safe retries - design operations to be reentrant

✅ **Policy per dependency** - different services need different policies

## Advanced Patterns

### Adaptive Timeout

Adjust timeout based on observed latencies:

```csharp
public class AdaptiveTimeoutPolicy
{
    private readonly ConcurrentQueue<double> _recentLatencies = new();
    private readonly int _maxSamples = 100;
    
    public TimeSpan GetTimeout()
    {
        if (_recentLatencies.IsEmpty)
            return TimeSpan.FromSeconds(5);  // Default
        
        // P99 latency + buffer
        var p99 = _recentLatencies.OrderBy(x => x).ElementAt((int)(_recentLatencies.Count * 0.99));
        return TimeSpan.FromMilliseconds(p99 * 1.5);
    }
    
    public async Task<T> ExecuteAsync<T>(Func<Task<T>> action)
    {
        var sw = Stopwatch.StartNew();
        
        try
        {
            using var cts = new CancellationTokenSource(GetTimeout());
            return await action();
        }
        finally
        {
            sw.Stop();
            _recentLatencies.Enqueue(sw.Elapsed.TotalMilliseconds);
            if (_recentLatencies.Count > _maxSamples)
                _recentLatencies.TryDequeue(out _);
        }
    }
}
```

### Health-Based Circuit Breaker

Open circuit based on health endpoint:

```csharp
public class HealthBasedCircuitBreaker
{
    private CircuitState _state = CircuitState.Closed;
    private DateTime _lastHealthCheck = DateTime.MinValue;
    
    public async Task<T> ExecuteAsync<T>(Func<Task<T>> action)
    {
        // Check health every 30 seconds
        if ((DateTime.UtcNow - _lastHealthCheck).TotalSeconds > 30)
        {
            var isHealthy = await CheckHealthAsync();
            _state = isHealthy ? CircuitState.Closed : CircuitState.Open;
            _lastHealthCheck = DateTime.UtcNow;
        }
        
        if (_state == CircuitState.Open)
            throw new BrokenCircuitException("Circuit open based on health check");
        
        return await action();
    }
    
    private async Task<bool> CheckHealthAsync()
    {
        try
        {
            var response = await _httpClient.GetAsync("/health", 
                new CancellationTokenSource(TimeSpan.FromSeconds(2)).Token);
            return response.IsSuccessStatusCode;
        }
        catch
        {
            return false;
        }
    }
}
```

### Retry with Retry-After Header

Respect server's retry guidance:

```csharp
public class RetryAfterPolicy
{
    public async Task<HttpResponseMessage> ExecuteAsync(Func<Task<HttpResponseMessage>> action)
    {
        var maxRetries = 3;
        
        for (int i = 0; i < maxRetries; i++)
        {
            var response = await action();
            
            if (response.IsSuccessStatusCode)
                return response;
            
            if (response.StatusCode == HttpStatusCode.TooManyRequests)
            {
                // Check Retry-After header
                if (response.Headers.RetryAfter != null)
                {
                    var delay = response.Headers.RetryAfter.Delta ?? 
                               TimeSpan.FromSeconds(60);
                    
                    _logger.LogWarning("Rate limited, waiting {Delay}", delay);
                    await Task.Delay(delay);
                    continue;
                }
            }
            
            if (!IsTransientError(response.StatusCode))
                return response;  // Don't retry client errors
            
            await Task.Delay(TimeSpan.FromSeconds(Math.Pow(2, i)));
        }
        
        throw new MaxRetriesExceededException();
    }
}
```
