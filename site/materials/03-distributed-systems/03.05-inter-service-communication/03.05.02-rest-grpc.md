## Introduction

REST and gRPC are the two most popular protocols for synchronous service-to-service communication. REST uses HTTP with JSON and is widely understood, while gRPC uses HTTP/2 with Protocol Buffers for higher performance. Understanding the strengths and trade-offs of each helps you choose the right tool for each scenario.

## Key Concepts

### REST (Representational State Transfer)

**Characteristics:**
- HTTP methods: GET, POST, PUT, DELETE, PATCH
- JSON or XML payloads (usually JSON)
- Stateless
- Resource-oriented URLs
- Human-readable

**REST Example:**
```csharp
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<ActionResult<OrderDto>> GetOrder(int id)
    {
        var order = await _service.GetOrderAsync(id);
        if (order == null) return NotFound();
        return Ok(order);
    }

    [HttpPost]
    public async Task<ActionResult<OrderDto>> CreateOrder(CreateOrderDto dto)
    {
        var order = await _service.CreateOrderAsync(dto);
        return CreatedAtAction(nameof(GetOrder), new { id = order.Id }, order);
    }
}
```

**Best Practices:**
- Use nouns for resources: `/orders`, not `/getOrders`
- Use HTTP methods correctly (GET for reads, POST for creates)
- Return appropriate status codes (200, 201, 404, 400, 500)
- Version your APIs (`/api/v1/orders`)
- Use HATEOAS for discoverability (optional)

### gRPC (gRPC Remote Procedure Call)

**Characteristics:**
- HTTP/2 protocol
- Protocol Buffers (protobuf) for serialization
- Strongly typed contracts
- Supports streaming
- Binary format (not human-readable)

## REST vs gRPC Comparison

| Aspect | REST | gRPC |
|--------|------|------|
| **Protocol** | HTTP/1.1 | HTTP/2 |
| **Payload** | JSON (text) | Protocol Buffers (binary) |
| **Performance** | Slower (text parsing) | Faster (binary) |
| **Browser Support** | Native | Requires gRPC-Web |
| **Streaming** | Limited (SSE, WebSockets) | Built-in (bidirectional) |
| **Human Readable** | Yes | No |
| **Contract** | OpenAPI/Swagger | .proto files |
| **Tooling** | Excellent (Postman, etc.) | Good (gRPCurl, Bloom RPC) |
| **Learning Curve** | Low | Medium |
| **Best For** | Public APIs, web clients | Internal services, high performance |

### Performance Benchmarks

**Typical Results** (internal services):
- gRPC: ~30-50% faster than REST
- Payload size: 50-70% smaller with protobuf
- Latency: 20-40% lower

**When Performance Matters:**
```
Scenario: 1000 requests/second between services

REST:
  - Payload: ~2KB per request
  - Total: 2MB/s bandwidth
  - Latency: ~15ms average
  - CPU: High (JSON parsing)

gRPC:
  - Payload: ~600 bytes per request
  - Total: 600KB/s bandwidth
  - Latency: ~8ms average
  - CPU: Low (binary deserialization)

Savings: 70% bandwidth, 47% latency reduction
```

**Real-World Benchmark Example:**

```csharp
// Benchmark: 10,000 requests fetching order details

// REST Implementation: Mean 15.2ms, Payload 2.1KB, Total 152s, Bandwidth 21MB
// gRPC Implementation: Mean 8.7ms, Payload 0.7KB, Total 87s, Bandwidth 7MB
// Result: 43% faster, 67% smaller payloads
```

### HTTP/2 Benefits for gRPC

**Multiplexing:**
```
HTTP/1.1 (REST):
Request 1 ──▶ Response 1 ──▶ Request 2 ──▶ Response 2
(Sequential - head-of-line blocking)

HTTP/2 (gRPC):
Request 1 ──▶
Request 2 ──▶  (Parallel - multiplexed)
Request 3 ──▶
Responses can arrive out of order
```

**Header Compression (HPACK):**
- HTTP/1.1: ~450 bytes per request
- HTTP/2: ~450 bytes first request, ~25 bytes subsequent (compressed deltas)
- Savings: ~63% reduction in header overhead

**Server Push:**
```protobuf
// Server can proactively send related data
rpc GetOrder(GetOrderRequest) returns (OrderResponse);
// Server pushes: Order + OrderItems + Customer (in one round trip)
```

## When to Use Each

### Use REST When:

✅ **Public APIs**: External developers will use your API
✅ **Browser clients**: JavaScript needs to call your API
✅ **Simple CRUD**: Standard create/read/update/delete operations
✅ **Discoverability**: Clients explore API dynamically
✅ **Existing ecosystem**: Integrating with REST-based systems
✅ **Debugging**: Need to easily test with curl/Postman

**Example**: Public API for mobile app

### Use gRPC When:

✅ **Internal services**: Microservices talking to each other
✅ **High performance**: Latency and throughput are critical
✅ **Streaming**: Need real-time bidirectional communication
✅ **Polyglot**: Multiple languages, strong contracts needed
✅ **Large payloads**: Efficient binary serialization matters
✅ **.NET to .NET**: Can leverage code generation

**Example**: Order service calling inventory service

### Hybrid Approach

Many systems use both:
```
External clients (mobile/web)
        │
        │ REST/JSON
        ▼
┌────────────────┐
│  API Gateway   │
└────────┬───────┘
         │ gRPC
         ▼
Internal microservices
```

## gRPC Streaming Patterns

### Server Streaming

```protobuf
rpc WatchOrder (OrderRequest) returns (stream OrderUpdate);
```

**Use case**: Real-time updates (order status changes)

**Implementation:**
```csharp
// Server-side
public override async Task WatchOrder(
    OrderRequest request,
    IServerStreamWriter<OrderUpdate> responseStream,
    ServerCallContext context)
{
    var orderId = request.OrderId;
    
    // Subscribe to order updates (e.g., from message bus)
    await foreach (var update in _orderUpdateStream.SubscribeAsync(orderId))
    {
        // Check if client is still connected
        if (context.CancellationToken.IsCancellationRequested)
            break;
        
        // Stream update to client
        await responseStream.WriteAsync(new OrderUpdate
        {
            OrderId = update.OrderId,
            Status = update.Status,
            Timestamp = Timestamp.FromDateTime(update.Timestamp)
        });
    }
}

// Client-side
public async Task MonitorOrder(int orderId)
{
    using var call = _client.WatchOrder(new OrderRequest { OrderId = orderId });
    
    await foreach (var update in call.ResponseStream.ReadAllAsync())
    {
        Console.WriteLine($"Order {update.OrderId} status: {update.Status}");
        
        if (update.Status == OrderStatus.Delivered)
            break;
    }
}
```

**Real-world scenarios:**
- Stock price updates
- Order tracking
- Log streaming
- Progress notifications

### Client Streaming

```protobuf
rpc UploadOrderItems (stream OrderItem) returns (OrderSummary);
```

**Use case**: Uploading large datasets

**Implementation:**
```csharp
// Server-side
public override async Task<OrderSummary> UploadOrderItems(
    IAsyncStreamReader<OrderItem> requestStream,
    ServerCallContext context)
{
    var items = new List<OrderItem>();
    decimal total = 0;
    
    // Read streamed items
    await foreach (var item in requestStream.ReadAllAsync())
    {
        items.Add(item);
        total += item.Price * item.Quantity;
    }
    
    return new OrderSummary
    {
        ItemCount = items.Count,
        TotalAmount = total
    };
}

// Client-side
public async Task<OrderSummary> CreateLargeBulkOrder(List<OrderItem> items)
{
    using var call = _client.UploadOrderItems();
    
    // Stream items to server
    foreach (var item in items)
    {
        await call.RequestStream.WriteAsync(item);
    }
    
    // Signal completion
    await call.RequestStream.CompleteAsync();
    
    // Get summary response
    return await call.ResponseAsync;
}
```

**Real-world scenarios:**
- File uploads
- Batch data imports
- Metrics reporting
- Log aggregation

### Bidirectional Streaming

```protobuf
rpc Chat (stream ChatMessage) returns (stream ChatMessage);
```

**Use case**: Real-time chat, live updates

**Implementation:**
```csharp
// Server-side
public override async Task Chat(
    IAsyncStreamReader<ChatMessage> requestStream,
    IServerStreamWriter<ChatMessage> responseStream,
    ServerCallContext context)
{
    var userId = context.GetHttpContext().User.Identity.Name;
    
    // Handle incoming messages in background
    var readTask = Task.Run(async () =>
    {
        await foreach (var message in requestStream.ReadAllAsync())
        {
            // Broadcast to all connected clients
            await _chatHub.BroadcastMessageAsync(message);
        }
    });
    
    // Subscribe to chat updates
    await foreach (var message in _chatHub.SubscribeAsync(userId))
    {
        if (context.CancellationToken.IsCancellationRequested)
            break;
            
        await responseStream.WriteAsync(message);
    }
    
    await readTask;
}

// Client-side
public async Task ParticipateInChat()
{
    using var call = _client.Chat();
    
    // Background task to receive messages
    var receiveTask = Task.Run(async () =>
    {
        await foreach (var message in call.ResponseStream.ReadAllAsync())
        {
            Console.WriteLine($"{message.Username}: {message.Text}");
        }
    });
    
    // Send messages from user input
    string input;
    while ((input = Console.ReadLine()) != null)
    {
        await call.RequestStream.WriteAsync(new ChatMessage
        {
            Username = _username,
            Text = input,
            Timestamp = Timestamp.FromDateTime(DateTime.UtcNow)
        });
    }
    
    await call.RequestStream.CompleteAsync();
    await receiveTask;
}
```

**Real-world scenarios:**
- Real-time chat
- Collaborative editing
- Live gaming
- IoT device communication

### Stream Best Practices

**1. Handle Cancellation:**
```csharp
public override async Task StreamData(
    Request request,
    IServerStreamWriter<Response> responseStream,
    ServerCallContext context)
{
    try
    {
        while (!context.CancellationToken.IsCancellationRequested)
        {
            await responseStream.WriteAsync(await GetNextDataAsync());
        }
    }
    catch (OperationCanceledException)
    {
        _logger.LogInformation("Stream cancelled by client");
    }
}
```

**2. Implement Backpressure:** HTTP/2 flow control handles this automatically

**3. Set Deadlines:**
```csharp
var deadline = DateTime.UtcNow.AddMinutes(5);
using var call = _client.StreamData(new Request(), new CallOptions(deadline: deadline));
```

## REST API Versioning Strategies

### 1. URL Versioning (Most Common)
```
/api/v1/orders
/api/v2/orders
```

**Pros**: Clear, easy to route  
**Cons**: Can lead to URL explosion

**Implementation:**
```csharp
// V1 Controller
[ApiController]
[Route("api/v1/[controller]")]
public class OrdersV1Controller : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<ActionResult<OrderDtoV1>> GetOrder(int id)
    {
        var order = await _service.GetOrderAsync(id);
        return Ok(MapToV1(order));
    }
}

// V2 Controller (with additional fields)
[ApiController]
[Route("api/v2/[controller]")]
public class OrdersV2Controller : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<ActionResult<OrderDtoV2>> GetOrder(int id)
    {
        var order = await _service.GetOrderAsync(id);
        return Ok(MapToV2(order));  // Includes new fields
    }
}
```

### 2. Header Versioning
```
GET /api/orders
Accept: application/vnd.company.v1+json
```

**Pros**: Clean URLs  
**Cons**: Less visible

**Implementation:**
```csharp
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    [ApiVersion("1.0")]
    public async Task<ActionResult<OrderDtoV1>> GetOrderV1(int id)
    {
        var order = await _service.GetOrderAsync(id);
        return Ok(MapToV1(order));
    }

    [HttpGet("{id}")]
    [ApiVersion("2.0")]
    public async Task<ActionResult<OrderDtoV2>> GetOrderV2(int id)
    {
        var order = await _service.GetOrderAsync(id);
        return Ok(MapToV2(order));
    }
}

// Startup configuration
services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;
    options.ApiVersionReader = new HeaderApiVersionReader("api-version");
});
```

### 3. Query Parameter
```
/api/orders?version=1
```

**Pros**: Simple  
**Cons**: Optional parameter issues

### 4. Content Negotiation
```
GET /api/orders/123
Accept: application/vnd.orders.v2+json
```

Response includes version-specific fields based on Accept header.

### Versioning Best Practices

**Deprecation Strategy:**
```csharp
[ApiVersion("1.0", Deprecated = true)]
[HttpGet("{id}")]
public async Task<ActionResult<OrderDtoV1>> GetOrderV1(int id)
{
    Response.Headers.Add("X-API-Deprecated", "true");
    Response.Headers.Add("X-API-Sunset", "2024-12-31");
    return Ok(MapToV1(await _service.GetOrderAsync(id)));
}
```

**Sunset Header:** `Sunset: Sat, 31 Dec 2024 23:59:59 GMT`

### Managing Breaking Changes

**Breaking changes:** Removing fields, changing types, renaming, stricter validation
**Non-breaking:** Adding optional fields, new endpoints, relaxing validation

**Migration:** V1 and V2 coexist → V1 deprecated → Monitor usage → V1 removed after sunset

3. **Compare**: For a book search feature:
   - Design REST endpoint
   - Design gRPC method
   - Which is better and why?

**Comparison:**

```
REST Book Search:
  GET /api/v1/books/search?q=potter&limit=100
  
  Pros:
  - Simple to test (browser, curl, Postman)
  - Cacheable (HTTP caching headers)
  - Works from web browsers
  
  Cons:
  - JSON payload larger (~2KB per book × 100 = 200KB)
  - Must fetch all results at once or implement pagination
  - Higher latency for large result sets

gRPC Book Search:
  rpc SearchBooks (SearchBooksRequest) returns (stream Book);
  
  Pros:
  - Streaming results (show results as they arrive)
  - Smaller payloads (~600 bytes × 100 = 60KB)
  - Can cancel search early
  - Lower latency (binary format)
  
  Cons:
  - Not browser-accessible (needs gRPC-Web)
  - Harder to test (need gRPCurl or Bloom RPC)
  - Can't use HTTP caching

Recommendation:
  - Public API / Web frontend: REST (compatibility, ease of use)
  - Internal services / Mobile apps: gRPC (performance, streaming)
  - Hybrid: REST for public, gRPC for internal
```

## Self-Check Questions

1. **When would you choose REST over gRPC?**
   - Public API accessed by external developers
   - Browser clients (JavaScript web apps)
   - Simple CRUD operations with no performance concerns
   - Better tooling needed (Postman, Swagger UI)
   - Human-readable format required for debugging
   - Third-party integrations expecting REST
   - Caching via HTTP headers is important

2. **What are the main advantages of gRPC?**
   - Performance: 30-50% faster than REST due to binary serialization
   - Smaller payloads: 50-70% reduction in size
   - Streaming: Built-in bidirectional streaming
   - Strong contracts: .proto files enforce schema
   - Code generation: Type-safe client/server code
   - HTTP/2 benefits: Multiplexing, header compression
   - Lower latency: Binary format, no JSON parsing

3. **Why is HTTP/2 important for gRPC?**
   - Enables multiplexing: Multiple requests on single connection
   - Header compression (HPACK): Reduces overhead
   - Server push: Proactively send related data
   - Bidirectional streaming: Full-duplex communication
   - Binary framing: Efficient protocol overhead
   - Flow control: Better resource management

4. **Can you use gRPC from a browser?**
   - Not natively: Browsers don't fully support HTTP/2 primitives gRPC needs
   - Requires gRPC-Web: Proxy/translation layer
   - gRPC-Web limitations: No bidirectional streaming, reduced performance
   - Alternative: Use REST for browser, gRPC for backend

5. **How do you version gRPC services?**
   - Package versioning: `package library.v1;`, `package library.v2;`
   - Service versioning: `service BookServiceV1 {}`, `service BookServiceV2 {}`
   - Field numbering: Add new fields with new numbers, don't reuse old numbers
   - Backwards compatibility: Can add optional fields without breaking
   - Proto3 best practices: All fields are optional by default

6. **What's the trade-off with streaming?**
   - Pros: Real-time updates, lower memory footprint, better UX
   - Cons: More complex to implement, harder to debug, connection management
   - Not cacheable: Can't cache streaming responses
   - Connection persistence: Requires long-lived connections

7. **When is JSON preferable to Protobuf?**
   - Human readability needed
   - Schema flexibility required (dynamic fields)
   - JavaScript heavy environment
   - Quick prototyping
   - Debugging and logging
   - External integrations expecting JSON

✅ **Version APIs** from the start to allow evolution without breaking clients

✅ **Streaming** in gRPC is powerful for real-time scenarios and large datasets

✅ **Protobuf** is more efficient but less human-readable than JSON

✅ **Choose based on requirements**: Public access, performance needs, client capabilities

✅ **Migration strategy**: Can coexist during transition, migrate high-traffic first

## Common Pitfalls

**1. Using gRPC for public APIs:**
```
❌ Don't: Expose gRPC directly to web browsers
   Requires gRPC-Web, limited browser support

✅ Do: Use REST for public APIs, gRPC for internal
   API Gateway translates REST → gRPC
```

**2. Ignoring API versioning:**
```
❌ Don't: Change API without versioning
   Breaks existing clients

✅ Do: Version from day 1
   /api/v1/orders or Accept: application/vnd.api.v1+json
```

**3. Not handling streaming errors:**
```
❌ Don't: Assume streams never fail
   public async Task StreamData(IServerStreamWriter<Data> stream)
   {
       while (true)
           await stream.WriteAsync(GetData());
   }

✅ Do: Handle cancellation and errors
   try
   {
       while (!context.CancellationToken.IsCancellationRequested)
           await stream.WriteAsync(GetData());
   }
   catch (RpcException ex)
   {
       _logger.LogError(ex, "Stream failed");
   }
```

**4. Overusing gRPC streaming:**
```
❌ Don't: Use streaming for simple request-response
   rpc GetUser(UserId) returns (stream User);  // Overkill

✅ Do: Use unary for simple calls
   rpc GetUser(UserId) returns (User);  // Appropriate
```

**5. Not documenting REST APIs:**
```
❌ Don't: Build REST API without documentation

✅ Do: Use OpenAPI/Swagger
   services.AddSwaggerGen();
   // Auto-generated interactive documentation
```
