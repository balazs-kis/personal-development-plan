## Introduction

As microservices systems grow, managing cross-cutting concerns like authentication, routing, rate limiting, and observability becomes challenging. API gateways and service mesh are infrastructure patterns that solve these problems by providing a dedicated layer for communication management.

## Key Concepts

### API Gateway

**Definition**: Single entry point for clients to access backend microservices

```
┌─────────────┐
│   Clients   │
│  (Mobile/   │
│   Web/API)  │
└──────┬──────┘
       │
       ▼
┌─────────────────────┐
│   API Gateway       │
│  - Authentication   │
│  - Rate Limiting    │
│  - Routing          │
│  - Load Balancing   │
│  - Request/Response │
│    Transformation   │
└───┬──────┬─────┬────┘
    │      │     │
    ▼      ▼     ▼
┌───────┐ ┌───────┐ ┌───────┐
│Service│ │Service│ │Service│
│   A   │ │   B   │ │   C   │
└───────┘ └───────┘ └───────┘
```

**Responsibilities**:
- **Authentication & Authorization**: Verify tokens, enforce permissions
- **Routing**: Direct requests to appropriate services
- **Rate Limiting**: Protect services from overload
- **Request/Response Transformation**: Protocol translation, aggregation
- **SSL Termination**: Handle TLS at gateway
- **Caching**: Cache responses to reduce load
- **Logging & Monitoring**: Centralized observability

**Custom Middleware**:
```csharp
// Authentication middleware
app.Use(async (context, next) =>
{
    var token = context.Request.Headers["Authorization"].FirstOrDefault();
    if (string.IsNullOrEmpty(token))
    {
        context.Response.StatusCode = 401;
        return;
    }

    // Validate token
    var isValid = await _tokenValidator.ValidateAsync(token);
    if (!isValid)
    {
        context.Response.StatusCode = 403;
        return;
    }

    await next();
});

// Rate limiting
app.UseRateLimiter(new RateLimiterOptions
{
    GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(
        httpContext => RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: httpContext.User.Identity?.Name ?? "anonymous",
            factory: partition => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 100,
                Window = TimeSpan.FromMinutes(1)
            }))
});
```

## Gateway Patterns

### 1. Gateway Routing

Simple pass-through routing:
```
Client → Gateway → Route to Service A or B based on path
```

### Gateway Aggregation

Combine multiple service calls:
```csharp
[HttpGet("products/{id}/details")]
public async Task<ProductDetailsDto> GetProductDetails(int id)
{
    // Aggregate from multiple services in parallel
    var productTask = _productService.GetProductAsync(id);
    var reviewsTask = _reviewService.GetReviewsAsync(id);
    var inventoryTask = _inventoryService.GetStockAsync(id);

    await Task.WhenAll(productTask, reviewsTask, inventoryTask);

    return new ProductDetailsDto
    {
        Product = await productTask,
        Reviews = await reviewsTask,
        Stock = await inventoryTask
    };
}
```

**With Error Handling:**
```csharp
[HttpGet("products/{id}/details")]
public async Task<ProductDetailsDto> GetProductDetails(int id)
{
    var productTask = _productService.GetProductAsync(id);
    var reviewsTask = SafeGetReviewsAsync(id);      // Graceful degradation
    var inventoryTask = SafeGetStockAsync(id);       // Graceful degradation

    await Task.WhenAll(productTask, reviewsTask, inventoryTask);

    return new ProductDetailsDto
    {
        Product = await productTask,                  // Required
        Reviews = await reviewsTask,                  // Optional
        Stock = await inventoryTask                    // Optional
    };
}

private async Task<List<Review>> SafeGetReviewsAsync(int productId)
{
    try
    {
        return await _reviewService.GetReviewsAsync(productId);
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "Failed to fetch reviews for product {ProductId}", productId);
        return new List<Review>();  // Return empty on failure
    }
}

private async Task<StockInfo> SafeGetStockAsync(int productId)
{
    try
    {
        return await _inventoryService.GetStockAsync(productId);
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "Failed to fetch stock for product {ProductId}", productId);
        return new StockInfo { Available = false, Quantity = 0 };
    }
}
```

**Benefits:**
- Reduces client calls from N to 1
- Parallel execution reduces total latency
- Gateway owns aggregation logic
- Client gets single, optimized payload

**When to use:**
- Mobile clients (reduce round trips)
- Complex UIs needing data from many services
- Public APIs (hide internal service structure)

### 3. Backend for Frontend (BFF)

Different gateways for different clients:
```
┌──────────────┐         ┌──────────────┐
│ Mobile App   │────────▶│  Mobile BFF  │
└──────────────┘         └──────┬───────┘
                                │
┌──────────────┐         ┌──────▼───────┐
│  Web App     │────────▶│   Web BFF    │──────┐
└──────────────┘         └──────┬───────┘      │
                                │              │
                         Backend Services ◀────┘
```

Each BFF optimized for its client's needs.

**Implementation Example:**

```csharp
// Mobile BFF - optimized for bandwidth
[ApiController]
[Route("mobile/api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<MobileProductDto> GetProduct(int id)
    {
        var product = await _productService.GetProductAsync(id);
        
        // Minimal payload for mobile
        return new MobileProductDto
        {
            Id = product.Id,
            Name = product.Name,
            Price = product.Price,
            ImageUrl = product.ThumbnailUrl,  // Low-res thumbnail
            InStock = product.Stock > 0
        };
    }
}

// Web BFF - richer data
[ApiController]
[Route("web/api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<WebProductDto> GetProduct(int id)
    {
        // Aggregate more data for web
        var productTask = _productService.GetProductAsync(id);
        var reviewsTask = _reviewService.GetReviewsAsync(id, limit: 10);
        var recommendationsTask = _recommendationService.GetRecommendationsAsync(id);
        
        await Task.WhenAll(productTask, reviewsTask, recommendationsTask);
        
        return new WebProductDto
        {
            Id = product.Id,
            Name = product.Name,
            Description = product.FullDescription,  // Full description
            Price = product.Price,
            Images = product.AllImages,             // All high-res images
            Stock = product.Stock,
            Reviews = await reviewsTask,
            Recommendations = await recommendationsTask,
            Specifications = product.Specifications
        };
    }
}

// Admin BFF - management features
[ApiController]
[Route("admin/api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<AdminProductDto> GetProduct(int id)
    {
        var product = await _productService.GetProductAsync(id);
        var analytics = await _analyticsService.GetProductAnalyticsAsync(id);
        
        return new AdminProductDto
        {
            // All product data
            ...product,
            // Plus analytics
            Views = analytics.TotalViews,
            Conversions = analytics.ConversionRate,
            Revenue = analytics.TotalRevenue,
            // Plus audit info
            CreatedBy = product.CreatedBy,
            ModifiedAt = product.ModifiedAt
        };
    }
}
```

**Benefits:**
- Each BFF optimized for client capabilities
- Mobile: Smaller payloads, fewer calls
- Web: Richer data, more features
- Admin: Additional management/analytics data
- Can evolve independently per platform

**When to use:**
- Multiple client types with different needs
- Mobile apps needing optimized payloads
- Web apps needing rich data
- Admin interfaces needing extra data
- Different authentication per platform

## Service Mesh

**Definition**: Infrastructure layer handling service-to-service communication

```
┌─────────────────────────────────────────────────┐
│            Control Plane                        │
│  - Configuration                                │
│  - Policy Management                            │
│  - Certificate Authority                        │
└───────┬────────────────┬────────────────┬──────┘
        │                │                │
┌───────▼────────┐  ┌────▼───────┐  ┌────▼───────┐
│ Service A      │  │ Service B  │  │ Service C  │
│ ┌────────────┐ │  │┌──────────┐│  │┌──────────┐│
│ │  Sidecar   │ │  ││ Sidecar  ││  ││ Sidecar  ││
│ │  (Envoy)   │ │  ││ (Envoy)  ││  ││ (Envoy)  ││
│ └─────┬──────┘ │  │└────┬─────┘│  │└────┬─────┘│
│       │ App    │  │     │ App  │  │     │ App  │
└───────┴────────┘  └─────┴──────┘  └─────┴──────┘
         Data Plane
```

**Responsibilities**:
- **Traffic Management**: Load balancing, routing, retries
- **Security**: mTLS, authentication, authorization
- **Observability**: Metrics, logs, distributed tracing
- **Resilience**: Circuit breakers, timeouts, fault injection

### Service Mesh in Kubernetes (Istio Example)

**Virtual Service** (routing rules):
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: orders-service
spec:
  hosts:
  - orders-service
  http:
  - match:
    - headers:
        x-version:
          exact: "v2"
    route:
    - destination:
        host: orders-service
        subset: v2
  - route:
    - destination:
        host: orders-service
        subset: v1
```

**Destination Rule** (traffic policies):
```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: orders-service
spec:
  host: orders-service
  trafficPolicy:
    loadBalancer:
      simple: ROUND_ROBIN
    connectionPool:
      tcp:
        maxConnections: 100
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 30s
      baseEjectionTime: 30s
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
```

## API Gateway vs Service Mesh

| Aspect | API Gateway | Service Mesh |
|--------|-------------|--------------|
| **Layer** | Edge (north-south traffic) | Internal (east-west traffic) |
| **Clients** | External (mobile, web, APIs) | Service-to-service |
| **Focus** | Entry point, aggregation | Service communication |
| **Typical Features** | Rate limiting, API keys, transformation | mTLS, circuit breaker, observability |
| **Deployment** | Single/few instances | Sidecar per service |
| **Complexity** | Lower | Higher |
| **When to Use** | Always (for external access) | Large number of services |

### Using Both Together

```
External Clients
      │
      ▼
┌───────────────┐
│  API Gateway  │  ◀── North-South traffic
└───────┬───────┘
        │
        ▼
┌─────────────────────────────────┐
│      Service Mesh               │  ◀── East-West traffic
│  ┌─────────┐    ┌─────────┐    │
│  │Service A│───▶│Service B│    │
│  └─────────┘    └─────────┘    │
│       │              │          │
│       ▼              ▼          │
│  ┌─────────┐    ┌─────────┐    │
│  │Service C│    │Service D│    │
│  └─────────┘    └─────────┘    │
└─────────────────────────────────┘
```

3. **Aggregation**: Design a `/api/product-details/{id}` endpoint that aggregates:
   - Product info (Products Service)
   - Reviews (Reviews Service)
   - Stock (Inventory Service)

**Implementation:**
```csharp
[HttpGet("api/product-details/{id}")]
public async Task<ActionResult<ProductDetailsResponse>> GetProductDetails(int id)
{
    try
    {
        // Fetch required data (product) - fail if not available
        var product = await _productService.GetProductAsync(id);
        if (product == null)
            return NotFound();

        // Fetch optional data in parallel - degrade gracefully
        var reviewsTask = GetReviewsWithFallbackAsync(id);
        var stockTask = GetStockWithFallbackAsync(id);

        await Task.WhenAll(reviewsTask, stockTask);

        return Ok(new ProductDetailsResponse
        {
            Product = new ProductDto
            {
                Id = product.Id,
                Name = product.Name,
                Description = product.Description,
                Price = product.Price,
                Images = product.Images
            },
            Reviews = await reviewsTask,
            Stock = await stockTask,
            Metadata = new ResponseMetadata
            {
                ResponseTime = DateTime.UtcNow,
                Services = new ServiceStatus
                {
                    Product = "healthy",
                    Reviews = reviewsTask.IsCompletedSuccessfully ? "healthy" : "degraded",
                    Stock = stockTask.IsCompletedSuccessfully ? "healthy" : "degraded"
                }
            }
        });
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Failed to fetch product details for {ProductId}", id);
        return StatusCode(500, "Internal server error");
    }
}

private async Task<ReviewsDto> GetReviewsWithFallbackAsync(int productId)
{
    try
    {
        using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
        return await _reviewService.GetReviewsAsync(productId, cts.Token);
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "Reviews service unavailable for product {ProductId}", productId);
        return new ReviewsDto
        {
            Reviews = new List<Review>(),
            Count = 0,
            AverageRating = null,
            Note = "Reviews temporarily unavailable"
        };
    }
}

private async Task<StockDto> GetStockWithFallbackAsync(int productId)
{
    try
    {
        using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
        return await _inventoryService.GetStockAsync(productId, cts.Token);
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "Inventory service unavailable for product {ProductId}", productId);
        return new StockDto
        {
            Available = null,  // Unknown
            Quantity = null,
            Note = "Stock information temporarily unavailable"
        };
    }
}
```

4. **Service Mesh Decision**: Would you add a service mesh? Why or why not?

**Decision Framework:**
```
Factors to Consider:

Number of Services: 10 services
✓ Service mesh starts making sense at 10+ services

Service-to-Service Communication Complexity:
- Simple request-response: Probably don't need mesh
- Complex routing, retries, circuit breakers: Consider mesh

Team Size & Expertise:
- Small team: Mesh adds operational complexity
- Large team with k8s experience: Mesh is manageable

Requirements:
✓ mTLS between all services: Strong argument for mesh
✓ Advanced traffic management (canary, A/B): Mesh helps
✓ Distributed tracing: Mesh provides automatic instrumentation
- Simple needs: Library (Polly) may suffice

Decision: YES, add service mesh if:
  1. Running on Kubernetes
  2. Need mTLS for compliance
  3. Team has k8s expertise
  4. Want zero-code observability

Decision: NO, skip service mesh if:
  1. Simple architecture (< 10 services)
  2. Small team, limited k8s expertise
  3. Can achieve goals with libraries (Polly, Serilog)
  4. Don't need advanced traffic management

For this scenario (10 services, e-commerce):
Recommendation: Start without service mesh
  - Use API Gateway for north-south traffic
  - Use Polly for resilience
  - Use OpenTelemetry for tracing
  - Consider mesh later if complexity grows (20+ services)
```

5. **BFF Pattern**: Should mobile and web apps share the same gateway? Why?

**Recommendation: Separate BFFs**
- Mobile needs: Minimal bandwidth, smaller payloads (20KB vs 200KB for web)
- Web needs: Rich data, SEO metadata, full images
- Different access patterns: Mobile (frequent, small) vs Web (occasional, large)
- Platform-specific optimizations worth the maintenance overhead
- Share common code via libraries to avoid duplication

## Self-Check Questions

1. **What problems do API gateways solve?**
   - Single entry point for clients (simplifies client code)
   - Authentication & authorization (centralized security)
   - Rate limiting (protect backend services)
   - Request aggregation (reduce client round trips)
   - Protocol translation (REST to gRPC)
   - SSL termination (offload TLS handling)
   - Logging & monitoring (centralized observability)

2. **What is a sidecar proxy?**
   - Proxy deployed alongside each service instance (same pod in k8s)
   - Handles all network communication for the service
   - Provides observability, security, traffic management
   - Service code doesn't need resilience libraries
   - Examples: Envoy, Linkerd proxy

3. **When should you use a service mesh?**
   - Many services (10+, ideally 20+)
   - Need mTLS between all services
   - Complex traffic management (canary, blue-green)
   - Want automatic distributed tracing
   - Running on Kubernetes
   - Team has k8s/mesh expertise
   - Polyglot environment (many languages)

4. **What's the difference between north-south and east-west traffic?**
   - North-south: External clients → Internal services (API Gateway)
     Example: Mobile app → API Gateway → Order Service
   - East-west: Service → Service (internal) (Service Mesh)
     Example: Order Service → Inventory Service
   - North-south: Entry/exit points
   - East-west: Internal service communication

5. **What is the BFF pattern?**
   - Backend For Frontend: Separate gateway per client type
   - Mobile BFF: Optimized for mobile (minimal data, thumbnails)
   - Web BFF: Optimized for web (rich data, full content)
   - Each BFF aggregates and transforms appropriately
   - Allows independent evolution per platform

6. **How does an API gateway differ from a load balancer?**
   - Load balancer: Distributes traffic across instances (Layer 4/7)
   - API gateway: Application-level routing, transformation, aggregation (Layer 7)
   - Gateway: Authentication, rate limiting, caching
   - Load balancer: Health checks, failover
   - Often used together: LB in front of gateway

7. **What are gateway aggregation trade-offs?**
   - Pros: Fewer client calls, better mobile performance
   - Cons: Gateway becomes complex, potential bottleneck
   - Pros: Hide internal service structure
   - Cons: Gateway must know about all services
   - Consider: Service mesh for complex aggregation

## Key Takeaways

✅ **API Gateway**: Single entry point for external clients (north-south traffic)

✅ **Service Mesh**: Manages internal service-to-service communication (east-west traffic)

✅ **BFF Pattern**: Different gateways for different client types (mobile, web, admin)

✅ **Use both** for comprehensive communication management in large systems

✅ **Start simple**: Add service mesh only when complexity justifies operational overhead

✅ **Gateway aggregation** reduces client round trips but adds gateway complexity

✅ **Cross-cutting concerns** (auth, rate limiting, logging) belong in gateway layer

✅ **Service mesh** provides zero-code observability, security, and traffic management

✅ **Sidecar pattern** keeps application code simple, shifts concerns to infrastructure

✅ **Consider trade-offs**: Operational complexity vs developer productivity

## Common Pitfalls

**1. Overloading the API gateway:**
```
❌ Don't: Put all business logic in gateway
   Gateway validates, transforms, orchestrates...
   Becomes a distributed monolith
   
✅ Do: Gateway handles cross-cutting concerns only
   Auth, rate limiting, routing
   Business logic stays in services
```

**2. Not planning for gateway failures:**
```
❌ Don't: Single gateway instance (SPOF)
   
✅ Do: Multiple gateway instances behind load balancer
   Health checks, auto-scaling
   Graceful degradation if backend services fail
```

**3. Adding service mesh too early:**
```
❌ Don't: Add mesh with 3-5 services
   Operational complexity outweighs benefits
   
✅ Do: Start with libraries (Polly), add mesh at 20+ services
   When zero-code instrumentation is worth the complexity
```

**4. Not monitoring gateway performance:**
```
❌ Don't: Ignore gateway as bottleneck
   All traffic flows through it
   
✅ Do: Monitor latency, throughput, error rates
   Set up alerts for degradation
   Load test gateway under realistic conditions
```

**5. Tight coupling via gateway aggregation:**
```
❌ Don't: Gateway knows details of all services
   Changes in services require gateway updates
   
✅ Do: Keep aggregation logic generic
   Services provide consistent interfaces
   Consider GraphQL for flexible aggregation
```
