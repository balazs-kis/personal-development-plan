## Introduction

OAuth 2.0 is the industry-standard authorization framework that enables applications to obtain limited access to user resources without exposing credentials. Understanding OAuth 2.0 is essential for building modern, secure applications that integrate with third-party services or provide APIs.

**Key distinction:** OAuth 2.0 is an *authorization* framework, not an authentication protocol. It answers the question "what can this application access?" not "who is this user?" (that's where OpenID Connect comes in, which we'll cover later).

## Key Concepts Summary

### What is OAuth 2.0?

OAuth 2.0 solves a fundamental problem: **How can one application access your data from another application without giving away your password?**

Before OAuth, users would give their passwords to third-party apps to access their data. OAuth 2.0 provides a secure alternative through delegated authorization.

### OAuth 2.0 Roles

```
┌─────────────────┐
│ Resource Owner  │  (User who owns the data)
└────────┬────────┘
         │ 1. Authorizes
         ▼
┌─────────────────┐
│ Authorization   │  (Issues tokens after user authorizes)
│ Server          │
└────────┬────────┘
         │ 2. Issues Token
         ▼
┌─────────────────┐
│ Client          │  (Application requesting access)
└────────┬────────┘
         │ 3. Uses Token
         ▼
┌─────────────────┐
│ Resource Server │  (API hosting the protected data)
└─────────────────┘
```

### Main Grant Types

#### 1. Authorization Code Grant (✅ RECOMMENDED)

**Use for:** Web applications, mobile apps, SPAs (with PKCE)

**How it works:**
1. User clicks "Login with [Service]"
2. App redirects to authorization server
3. User authenticates and grants permission
4. Authorization server returns an authorization code
5. App exchanges code for access token (server-to-server)
6. App uses access token to call APIs

```
User → Client → Authorization Server → User Authenticates
                                     ↓
                              Authorization Code
                                     ↓
Client (Backend) → Exchange Code for Token → Access Token
                                              ↓
                                        Resource Server
```

**Security:** Most secure because tokens never pass through the browser.

#### 2. Client Credentials Grant (✅ RECOMMENDED)

**Use for:** Machine-to-machine authentication (no user involved)

**How it works:**
1. Service authenticates with client ID and secret
2. Authorization server returns access token
3. Service uses token to call APIs

```csharp
// Example: Service-to-service authentication
var tokenResponse = await httpClient.PostAsync(
    "https://auth.example.com/oauth/token",
    new FormUrlEncodedContent(new Dictionary<string, string>
    {
        ["grant_type"] = "client_credentials",
        ["client_id"] = "my-service",
        ["client_secret"] = "secret",
        ["scope"] = "api.read"
    }));
```

**Use cases:**
- Background services
- Cron jobs
- Microservice-to-microservice communication
- CLI tools

#### 3. Refresh Token Grant (✅ RECOMMENDED)

**Use for:** Obtaining new access tokens without re-authentication

**How it works:**
1. Access token expires
2. Client sends refresh token to authorization server
3. Server issues new access token (and optionally new refresh token)

```
Access Token Expires → Use Refresh Token → Get New Access Token
```

**Security:** Refresh tokens should be:
- Long-lived but rotatable
- Stored securely
- Bound to the client that requested them

#### 4. Device Code Grant (✅ RECOMMENDED)

**Use for:** Devices with limited input (smart TVs, IoT devices)

**How it works:**
1. Device shows a code and URL
2. User visits URL on another device and enters code
3. User authenticates and grants permission
4. Device receives access token

### Deprecated Grant Types (❌ AVOID)

#### Implicit Grant (❌ DEPRECATED)

**Why deprecated:** Tokens exposed directly in browser URL fragments, vulnerable to leakage.

**Replaced by:** Authorization Code Grant with PKCE

#### Resource Owner Password Credentials (❌ DEPRECATED)

**Why deprecated:** Requires sharing user credentials with the application, defeating the purpose of OAuth.

**Replaced by:** Authorization Code Grant

## OAuth 2.0 Terminology

| Term | Definition |
|------|------------|
| **Scope** | Defines what access the application is requesting (e.g., `read:profile`, `write:posts`) |
| **Authorization Code** | Temporary code exchanged for an access token |
| **Access Token** | Credential used to access protected resources |
| **Refresh Token** | Long-lived token used to obtain new access tokens |
| **Client ID** | Public identifier for the application |
| **Client Secret** | Private credential for confidential clients |
| **Redirect URI** | Where the authorization server sends the user after authorization |
| **State Parameter** | Random value for CSRF protection |

## Common Misunderstandings

### ❌ "OAuth is for authentication"
**Reality:** OAuth 2.0 is for *authorization*. For authentication, use OpenID Connect (built on OAuth 2.0).

### ❌ "I should use Implicit Flow for my SPA"
**Reality:** Implicit Flow is deprecated. Use Authorization Code Flow with PKCE for SPAs.

### ❌ "Access tokens should be long-lived"
**Reality:** Access tokens should be short-lived (minutes to hours). Use refresh tokens for long-term access.

### ❌ "I can trust data in an access token"
**Reality:** Always validate tokens. Never trust unverified data.
