## Introduction

Dynamic Application Security Testing (DAST) tests running applications from the outside, simulating how an attacker would interact with your system. Unlike SAST, which analyzes code, DAST sends requests to your application and analyzes responses to identify vulnerabilities like authentication bypasses, injection flaws, and configuration issues.

DAST is "black-box" testing—it doesn't need source code access. It discovers runtime vulnerabilities that SAST can't detect, such as authentication logic flaws, server misconfigurations, and issues in third-party components.

## Key Concepts Summary

### What is DAST?

DAST tools interact with running applications to discover vulnerabilities through:
- **Crawling:** Discovering all pages, forms, and endpoints
- **Scanning:** Testing inputs for common vulnerabilities
- **Fuzzing:** Sending malformed or unexpected data to trigger errors
- **Attack Simulation:** Attempting exploitation to confirm vulnerabilities

DAST finds issues like:
- SQL injection
- Cross-site scripting (XSS)
- Authentication and session management flaws
- Security misconfigurations
- Insecure direct object references
- Server-side request forgery (SSRF)
- XML external entity (XXE) attacks

### Why DAST Matters

**Runtime Detection:** Finds vulnerabilities that only appear when code runs, such as logic flaws, configuration issues, and environment-specific problems.

**No Source Code Required:** Tests compiled applications, third-party components, and legacy systems where source code isn't available.

**Realistic Testing:** Simulates real attacker behavior, providing confidence that identified issues are exploitable.

**Configuration Coverage:** Detects server misconfigurations, missing security headers, and TLS/SSL issues.

### SAST vs DAST Comparison

| Aspect | SAST | DAST |
|--------|------|------|
| **Testing Type** | White-box (code analysis) | Black-box (runtime testing) |
| **When to Run** | During development/build | During testing/staging |
| **What It Finds** | Code-level vulnerabilities | Runtime and configuration issues |
| **False Positives** | Higher | Lower (confirms exploitability) |
| **Code Access** | Required | Not required |
| **Speed** | Fast (no execution) | Slower (needs running app) |
| **Coverage** | All code paths | Only reachable functionality |

**Best Practice:** Use both SAST and DAST together for comprehensive coverage.

### DAST Testing Workflow

The typical DAST process follows three stages:

**1. Explore**
- Learn about the application structure
- Identify endpoints, forms, and APIs
- Map the attack surface
- Discover hidden content
- Identify technologies in use

**2. Attack**
- Test inputs for injection flaws
- Attempt authentication bypasses
- Fuzz parameters to trigger errors
- Test for XSS, CSRF, and other client-side issues
- Check security headers and configurations

**3. Report**
- Document discovered vulnerabilities
- Provide exploitation steps
- Assess severity and business impact
- Recommend remediation

## OWASP ZAP Setup and Usage

### Installation

**Docker (recommended):**
```bash
# Run ZAP in Docker
docker run -u zap -p 8080:8080 -p 8090:8090 \
  -i ghcr.io/zaproxy/zaproxy:stable zap-webswing.sh

# Access ZAP at http://localhost:8080/zap
```

**Local Installation:**
```bash
# Download from https://www.zaproxy.org/download/
# Or use package manager:

# Windows (Chocolatey)
choco install zap

# macOS (Homebrew)
brew install --cask owasp-zap

# Linux (snap)
snap install zaproxy --classic
```

### Basic Scanning

**Automated Scan:**
```bash
# Quick scan of a target
zap-cli quick-scan http://example.com

# Full scan (spider + active scan)
zap-cli spider http://example.com
zap-cli active-scan http://example.com

# Generate report
zap-cli report -o report.html -f html
```

**GUI Workflow:**
1. Launch OWASP ZAP
2. Enter target URL in "Quick Start" tab
3. Click "Automated Scan"
4. Review findings in "Alerts" tab
5. Investigate false positives
6. Export report (HTML, XML, JSON, Markdown)

### Manual Testing with Proxy

Configure your browser to proxy through ZAP (localhost:8080):

```javascript
// Firefox Proxy Settings
Preferences > Network Settings > Manual proxy configuration
HTTP Proxy: localhost
Port: 8080
✓ Also use this proxy for HTTPS
```

**Intercepting and Modifying Requests:**
1. Enable "Break" mode (green/red button)
2. Navigate to target application in browser
3. ZAP intercepts the request
4. Modify parameters, headers, or body
5. Forward or drop the request
6. Analyze the response

Example modification:
```http
Original Request:
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json

{"username": "user123", "role": "user"}

Modified Request (privilege escalation test):
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json

{"username": "user123", "role": "admin"}
```

### Active Scanning

Active scanning attempts to exploit vulnerabilities:

```bash
# Spider first to discover content
zap.spider.scan(url='http://example.com')

# Wait for spider to complete
while int(zap.spider.status()) < 100:
    time.sleep(1)

# Run active scan
zap.ascan.scan(url='http://example.com')

# Wait for scan to complete
while int(zap.ascan.status()) < 100:
    time.sleep(5)

# Get alerts
alerts = zap.core.alerts(baseurl='http://example.com')
```

**Scan Policies:**
- **Default Policy:** Balanced scan (medium speed, good coverage)
- **Quick Scan:** Fast, less thorough
- **Full Scan:** Comprehensive, time-intensive
- **Custom Policy:** Tune individual attack strengths

## Burp Suite for DAST

### Burp Suite Community vs Professional

| Feature | Community | Professional |
|---------|-----------|-------------|
| **Proxy** | ✓ | ✓ |
| **Repeater** | ✓ | ✓ |
| **Intruder** | Limited | Full |
| **Scanner** | ✗ | ✓ |
| **Extensions** | Limited | Full |
| **Price** | Free | Commercial |

### Basic Burp Suite Workflow

**1. Configure Proxy:**
```
Burp > Proxy > Options > Proxy Listeners
Binding: 127.0.0.1:8080
```

**2. Capture Traffic:**
- Configure browser to use Burp proxy
- Install Burp CA certificate for HTTPS
- Navigate to target application
- View requests in "Proxy > HTTP history"

**3. Test with Repeater:**
- Right-click request > "Send to Repeater"
- Modify request parameters
- Click "Send"
- Analyze response for vulnerabilities

**4. Automated Scanning (Professional):**
- Right-click target > "Scan"
- Configure scan settings
- Review findings in "Dashboard > Issues"

### Example: Testing for SQL Injection

**Manual Testing with Repeater:**
```http
Original Request:
GET /products?id=1 HTTP/1.1
Host: example.com

Test Payloads:
1. id=1' (syntax error test)
2. id=1 AND 1=1 (true condition)
3. id=1 AND 1=2 (false condition)
4. id=1 UNION SELECT NULL,NULL,NULL-- (union test)

Expected Behavior:
- Payload 1: Error message or different response
- Payloads 2 & 3: Different responses indicate SQL injection
- Payload 4: Successful union indicates exploitable SQLi
```

## CI/CD Integration

### OWASP ZAP in GitHub Actions

```yaml
name: DAST Scan

on:
  push:
    branches: [ main, develop ]
  schedule:
    - cron: '0 2 * * *'  # Daily at 2 AM

jobs:
  dast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Start Application
        run: |
          docker-compose up -d
          sleep 30  # Wait for app to be ready
      
      - name: ZAP Baseline Scan
        uses: zaproxy/action-baseline@v0.12.0
        with:
          target: 'http://localhost:8080'
          rules_file_name: '.zap/rules.tsv'
          cmd_options: '-a'
      
      - name: Upload ZAP Report
        uses: actions/upload-artifact@v3
        if: always()
        with:
          name: zap-report
          path: report_html.html
```

### ZAP Rules Configuration

Create `.zap/rules.tsv` to customize scan:
```tsv
10202	WARN	(Absence of Anti-CSRF Tokens)
10011	WARN	(Cookie Without Secure Flag)
10017	WARN	(Cross-Domain JavaScript Source File Inclusion)
10098	WARN	(Cross-Domain Misconfiguration)
10105	WARN	(Weak Authentication Method)
```

Columns: `ID`, `THRESHOLD` (IGNORE/INFO/WARN/FAIL), `NAME`

## Interpreting DAST Results

### Risk Levels

**Critical:** Immediate exploitation risk, requires urgent fix
- SQL Injection with data exposure
- Authentication bypass
- Remote code execution

**High:** Significant security impact
- Stored XSS
- Insecure direct object reference
- Missing authentication on sensitive endpoints

**Medium:** Moderate risk
- Reflected XSS with limited impact
- Information disclosure
- Missing security headers

**Low/Informational:** Best practice violations
- Verbose error messages
- Unnecessary HTTP methods enabled
- Version disclosure

### Example Finding

```
Alert: SQL Injection
Risk: CRITICAL
Confidence: MEDIUM
URL: http://example.com/products?id=1
Parameter: id
Attack: 1' OR '1'='1
Evidence: "You have an error in your SQL syntax"

Description:
SQL injection may be possible. The application appears to concatenate 
user input into SQL queries without proper sanitization.

Solution:
Use parameterized queries (prepared statements) or an ORM. Never 
concatenate user input into SQL queries.

Reference:
https://owasp.org/www-community/attacks/SQL_Injection
CWE-89: Improper Neutralization of Special Elements used in an SQL Command
```

## Best Practices

### 1. Test in Staging, Not Production
Run DAST scans against staging/test environments that mirror production but don't contain real user data.

### 2. Authenticated Scanning
Configure DAST tools with valid credentials to test authenticated functionality:

```yaml
# ZAP context configuration
authentication:
  method: "form"
  loginUrl: "http://example.com/login"
  parameters:
    username: "testuser"
    password: "testpass"
  indicators:
    loggedIn: "Welcome testuser"
    loggedOut: "Please log in"
```

### 3. Scope Configuration
Define scan scope to avoid testing out-of-scope systems:

```
In Scope:
- http://example.com/*
- https://api.example.com/*

Out of Scope:
- http://example.com/logout
- http://example.com/external-redirect
- https://third-party-service.com/*
```

### 4. Rate Limiting
Configure scan speed to avoid overwhelming the application:

```python
# ZAP scan policy
zap.ascan.set_option_max_scan_duration_in_mins(60)
zap.ascan.set_option_thread_per_host(5)
zap.ascan.set_option_delay_in_ms(100)
```

### 5. Regular Scanning
Schedule automated DAST scans:
- After each deployment
- Nightly regression scans
- Before major releases
- After security updates

### 6. Validate Findings
Not all alerts are vulnerabilities. Manually verify critical findings before remediation.

## Summary

DAST complements SAST by testing running applications from an attacker's perspective. It finds runtime vulnerabilities, configuration issues, and logic flaws that static analysis can't detect. While slower than SAST, DAST provides high confidence that identified issues are real and exploitable.
