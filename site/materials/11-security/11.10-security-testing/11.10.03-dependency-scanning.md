## Introduction

Modern applications rely on hundreds or thousands of third-party dependencies. Each dependency introduces potential security vulnerabilities. Dependency vulnerability scanning (Software Composition Analysis or SCA) identifies known vulnerabilities in your dependencies, helping you patch issues before attackers exploit them.

High-profile breaches like Log4Shell (CVE-2021-44228) demonstrate the critical importance of dependency scanning. A single vulnerable library can compromise an entire application.

## Key Concepts Summary

### What is Software Composition Analysis (SCA)?

SCA tools analyze your project's dependencies (direct and transitive) and compare them against vulnerability databases like:
- **National Vulnerability Database (NVD)** - NIST's database of CVEs
- **GitHub Advisory Database** - Security advisories for open-source projects
- **Snyk Vulnerability Database** - Curated vulnerability data with remediation advice
- **NPM Security Advisories** - npm-specific vulnerabilities

### Why Dependency Scanning Matters

**Scale of Risk:** The average application has 200+ dependencies. A single vulnerable dependency can compromise your entire application.

**Known Vulnerabilities:** Attackers actively exploit known CVEs. Public exploit code exists for many vulnerabilities.

**Supply Chain Attacks:** Dependencies can be compromised by attackers (e.g., event-stream incident, ua-parser-js backdoor).

**Transitive Dependencies:** You inherit vulnerabilities from dependencies of your dependencies.

**Compliance:** Many regulations require tracking and patching known vulnerabilities.

### Direct vs Transitive Dependencies

**Direct Dependencies:** Libraries you explicitly reference in your configuration.
```json
// package.json
{
  "dependencies": {
    "express": "^4.18.0",      // Direct
    "lodash": "^4.17.21"        // Direct
  }
}
```

**Transitive Dependencies:** Libraries your dependencies rely on.
```
Your App
 └─ express (direct)
     ├─ body-parser (transitive)
     ├─ cookie-parser (transitive)
     └─ debug (transitive)
         └─ ms (transitive)
```

Transitive vulnerabilities are harder to track but equally dangerous.

## npm Vulnerability Scanning

### Basic npm audit

```bash
# Scan dependencies for vulnerabilities
npm audit

# Example output:
# found 2 vulnerabilities (1 moderate, 1 high) in 1204 scanned packages
#   1 vulnerability requires manual review
```

**Severity Levels:**
- **Critical:** Immediate action required
- **High:** Urgent fix needed
- **Moderate:** Important to fix soon
- **Low:** Minor issue, fix when convenient

### Detailed Audit Report

```bash
# View detailed report
npm audit --json > audit-report.json

# View only production dependencies
npm audit --production

# View audit report in browser
npm audit --browser
```

Example finding:
```
┌───────────────┬──────────────────────────────────────────────────────────────┐
│ Moderate      │ Prototype Pollution in lodash                                │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Package       │ lodash                                                       │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Patched in    │ >=4.17.21                                                    │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Dependency of │ express                                                      │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Path          │ express > lodash                                             │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ More info     │ https://npmjs.com/advisories/1673                            │
└───────────────┴──────────────────────────────────────────────────────────────┘
```

### Fixing Vulnerabilities

```bash
# Automatically fix vulnerabilities
npm audit fix

# Fix with semver-compatible updates
npm audit fix --only=prod

# Force major version updates (may introduce breaking changes)
npm audit fix --force

# Dry run (see what would be updated)
npm audit fix --dry-run
```

**⚠️ Warning:** `npm audit fix --force` can introduce breaking changes. Test thoroughly after running.

### Yarn Alternative

```bash
# Scan with Yarn
yarn audit

# Fix vulnerabilities
yarn audit fix
```

## .NET Dependency Scanning

### Built-in dotnet CLI

```bash
# List all packages with known vulnerabilities
dotnet list package --vulnerable

# Include transitive dependencies
dotnet list package --vulnerable --include-transitive

# Filter by severity
dotnet list package --vulnerable --severity high

# Example output:
# Project `MyApp` has the following vulnerable packages
#    [net6.0]: 
#    Top-level Package      Requested   Resolved   Severity   Advisory URL
#    > Newtonsoft.Json      12.0.3      12.0.3     High       https://github.com/advisories/GHSA-5crp-9r3c-p9vr
```

**Severity Levels in .NET:**
- **Critical:** Immediate remediation required
- **High:** Fix as soon as possible
- **Moderate:** Plan remediation
- **Low:** Fix when convenient

### Understanding the Output

```
Top-level Package: Your direct dependency
Requested: Version you specified
Resolved: Actual version installed
Severity: Risk level
Advisory URL: Details about the vulnerability
```

### Fixing .NET Vulnerabilities

```bash
# Update specific package
dotnet add package Newtonsoft.Json --version 13.0.3

# Update all packages to latest
dotnet outdated  # Requires dotnet-outdated-tool

# Update packages in all projects
dotnet restore --force
dotnet build
```

## Snyk for Advanced Scanning

### Installation and Setup

```bash
# Install Snyk CLI
npm install -g snyk

# Authenticate
snyk auth

# Test project for vulnerabilities
snyk test

# Monitor project (continuous monitoring)
snyk monitor
```

### Snyk for .NET

```bash
# Navigate to project directory
cd MyApp/

# Test for vulnerabilities
snyk test --file=MyApp.csproj

# Test all projects in solution
snyk test --all-projects

# Monitor for ongoing vulnerability alerts
snyk monitor --file=MyApp.csproj
```

Snyk analyzes:
- **PackageReference projects:** Scans `obj/project.assets.json`
- **packages.config projects:** Scans `packages` directory

### Snyk for JavaScript/TypeScript

```bash
# Test npm project
snyk test

# Test and output JSON
snyk test --json > results.json

# Test specific severity
snyk test --severity-threshold=high

# Ignore dev dependencies
snyk test --prod
```

### Advanced Snyk Features

**Fix vulnerabilities automatically:**
```bash
# Open PRs to fix vulnerabilities
snyk fix

# Or generate patches
snyk wizard
```

**Container scanning:**
```bash
# Scan Docker images
snyk container test myapp:latest
```

**IaC scanning:**
```bash
# Scan infrastructure as code
snyk iac test terraform/
snyk iac test kubernetes/deployment.yaml
```

### Snyk Reports

```bash
# Generate HTML report
snyk test --json | snyk-to-html -o report.html

# Generate SARIF report for GitHub
snyk test --sarif-file-output=snyk.sarif
```

## GitHub Dependabot

### Enabling Dependabot

Create `.github/dependabot.yml`:
```yaml
version: 2
updates:
  # Enable npm dependency updates
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 10
    reviewers:
      - "security-team"
    labels:
      - "dependencies"
      - "security"
  
  # Enable .NET dependency updates
  - package-ecosystem: "nuget"
    directory: "/"
    schedule:
      interval: "daily"
    open-pull-requests-limit: 5
    commit-message:
      prefix: "chore"
      prefix-development: "chore"
```

### Dependabot Security Updates

Dependabot automatically:
1. Detects vulnerable dependencies
2. Opens pull requests with patches
3. Provides vulnerability details and remediation advice
4. Keeps PRs up-to-date with latest patches

**Example Dependabot PR:**
```markdown
Bumps lodash from 4.17.19 to 4.17.21

Security Updates:
- CVE-2021-23337: Prototype Pollution (High)

Dependabot will resolve any conflicts with this PR as long as you don't 
alter it yourself.
```

## CI/CD Integration

### GitHub Actions with npm audit

```yaml
name: Dependency Scan

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  schedule:
    - cron: '0 8 * * 1'  # Weekly on Monday

jobs:
  npm-audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'
      
      - name: Install dependencies
        run: npm ci
      
      - name: Run npm audit
        run: npm audit --audit-level=moderate
        continue-on-error: false  # Fail build on vulnerabilities
      
      - name: Generate audit report
        if: always()
        run: npm audit --json > npm-audit.json
      
      - name: Upload audit report
        if: always()
        uses: actions/upload-artifact@v3
        with:
          name: npm-audit-report
          path: npm-audit.json
```

### GitHub Actions with Snyk

```yaml
name: Snyk Security Scan

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  snyk:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Run Snyk to check for vulnerabilities
        uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          args: --severity-threshold=high --fail-on=upgradable
      
      - name: Upload result to GitHub Code Scanning
        uses: github/codeql-action/upload-sarif@v2
        with:
          sarif_file: snyk.sarif
```

### Azure DevOps with .NET

```yaml
trigger:
  - main

pool:
  vmImage: 'ubuntu-latest'

steps:
- task: UseDotNet@2
  inputs:
    version: '8.0.x'

- script: |
    dotnet restore
    dotnet list package --vulnerable --include-transitive 2>&1 | tee vulnerable-packages.txt
  displayName: 'Scan for vulnerable packages'

- script: |
    if grep -q "has the following vulnerable packages" vulnerable-packages.txt; then
      echo "##vso[task.logissue type=error]Vulnerable packages found!"
      exit 1
    fi
  displayName: 'Check for vulnerabilities'

- task: PublishBuildArtifacts@1
  condition: always()
  inputs:
    pathToPublish: 'vulnerable-packages.txt'
    artifactName: 'vulnerability-report'
```

## Prioritizing and Remediating Vulnerabilities

### Risk Assessment Matrix

| Factor | Questions |
|--------|-----------|
| **Severity** | Critical, High, Moderate, or Low? |
| **Exploitability** | Is there public exploit code? |
| **Exposure** | Is the vulnerable code path used? |
| **Attack Vector** | Remote or local? Authenticated or unauthenticated? |
| **Data Sensitivity** | Does it protect sensitive data? |
| **Fix Availability** | Is a patch available? |

### Remediation Strategies

**1. Update to Patched Version (Best)**
```bash
# npm
npm install package@latest

# .NET
dotnet add package PackageName --version 2.0.0
```

**2. Use Alternative Package**
If no patch is available, consider alternatives:
```json
// Replace vulnerable package
"dependencies": {
  "moment": "^2.29.4"  // Remove
  "date-fns": "^2.30.0"  // Use instead
}
```

**3. Apply Workarounds**
Sometimes you can mitigate without updating:
```csharp
// Example: Validate input before passing to vulnerable method
if (IsValidInput(userInput))
{
    ProcessWithVulnerableLibrary(userInput);
}
```

**4. Accept Risk (Last Resort)**
Document why you're accepting the risk:
```yaml
# .snyk policy file
vulnerabilities:
  'SNYK-JS-LODASH-590103':
    reason: 'Not exploitable in our use case'
    expires: '2026-06-01T00:00:00.000Z'
    created: '2026-01-30T00:00:00.000Z'
```

## Best Practices

### 1. Scan Regularly
- Every build (CI/CD)
- Daily scheduled scans
- Before releases
- After adding/updating dependencies

### 2. Prioritize Critical Issues
Focus on:
- Critical and High severity
- Exploitable vulnerabilities with public PoCs
- Dependencies in production code (not dev dependencies)

### 3. Keep Dependencies Up-to-Date
```bash
# Check for outdated packages
npm outdated
dotnet outdated  # Requires dotnet-outdated-tool

# Update regularly
npm update
dotnet restore
```

### 4. Minimize Dependencies
- Remove unused dependencies
- Prefer well-maintained packages
- Avoid packages with many transitive dependencies

### 5. Use Lock Files
```bash
# npm
npm ci  # Use package-lock.json for consistent installs

# .NET
# NuGet uses packages.lock.json automatically
dotnet restore --locked-mode
```

### 6. Monitor Continuously
Use tools like Snyk, Dependabot, or GitHub Advanced Security for ongoing monitoring.

## Practice Exercise

1. **npm Project:**
   - Run `npm audit` on an existing project
   - Identify at least one vulnerability
   - Fix it with `npm audit fix` or manual update
   - Verify the fix with another scan

2. **.NET Project:**
   - Run `dotnet list package --vulnerable --include-transitive`
   - Update a vulnerable package
   - Run the scan again to confirm the fix

3. **Snyk Integration:**
   - Create a Snyk account
   - Authenticate with `snyk auth`
   - Scan a project with `snyk test`
   - Review the report and fix one vulnerability

4. **CI/CD Integration:**
   - Add dependency scanning to your CI/CD pipeline
   - Configure it to fail the build on high/critical vulnerabilities
   - Test by introducing a vulnerable dependency

## Summary

Dependency vulnerability scanning is essential for modern application security. With hundreds of dependencies in typical projects, automated scanning finds known vulnerabilities before attackers exploit them. Use built-in tools (npm audit, dotnet CLI) for basic scanning, and advanced tools (Snyk, Dependabot) for comprehensive monitoring and automated remediation.
