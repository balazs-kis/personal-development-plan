# Lesson 1: JWT Structure and Anatomy

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the three components of a JWT: header, payload, and signature
- Decode and inspect JWT tokens
- Identify registered, public, and private claims
- Recognize the difference between encoded and encrypted data
- Understand Base64Url encoding in JWTs

---

## Introduction

JSON Web Tokens (JWT) are the most common format for tokens in modern authentication and authorization systems. Understanding JWT structure is fundamental to using them securely. A JWT is not encrypted—it's only encoded and signed. This means anyone can decode and read the contents, making it critical to understand what data belongs in a JWT and what doesn't.

**Key principle:** JWTs are signed for integrity, not encrypted for confidentiality. Never put secrets in a JWT payload.

## Key Concepts Summary

### JWT Format

A JWT consists of three parts separated by dots (`.`):

```
xxxxx.yyyyy.zzzzz
```

```
Header.Payload.Signature
```

**Example JWT:**
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

Each part is **Base64Url-encoded** (not encrypted).

---

## Part 1: Header

The header contains metadata about the token.

### Structure

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### Key Fields

**`alg` (Algorithm) - REQUIRED**
- Specifies the signing algorithm
- Common values: `HS256`, `RS256`, `ES256`, `none`
- Critical for security (we'll cover this in Lesson 2)

**`typ` (Type) - OPTIONAL**
- Usually set to `"JWT"`
- Declares that this is a JWT token

**`kid` (Key ID) - OPTIONAL**
- Identifies which key was used to sign the JWT
- Useful when the server has multiple signing keys

### Example Headers

```json
// HMAC with SHA-256
{
  "alg": "HS256",
  "typ": "JWT"
}

// RSA with SHA-256 and key ID
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2024-01-key"
}

// Elliptic Curve with SHA-256
{
  "alg": "ES256",
  "typ": "JWT"
}
```

## Part 2: Payload (Claims)

The payload contains claims—statements about an entity (typically the user) and additional data.

### Structure

```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "email": "john.doe@example.com",
  "role": "admin",
  "iat": 1516239022,
  "exp": 1516242622
}
```

### Types of Claims

#### 1. Registered Claims (Standardized)

Claims defined in the JWT specification (RFC 7519):

| Claim | Name | Description | Example |
|-------|------|-------------|---------|
| `iss` | Issuer | Who issued the token | `"https://auth.example.com"` |
| `sub` | Subject | User/entity identifier (unique ID) | `"248289761001"` |
| `aud` | Audience | Who the token is intended for | `"https://api.example.com"` |
| `exp` | Expiration | When the token expires (Unix timestamp) | `1516242622` |
| `nbf` | Not Before | Token not valid before this time | `1516239022` |
| `iat` | Issued At | When the token was issued | `1516239022` |
| `jti` | JWT ID | Unique identifier for this token | `"abc-123-xyz"` |

#### 2. Public Claims

Claims defined in the [IANA JWT Claims Registry](https://www.iana.org/assignments/jwt/jwt.xhtml) or defined by you with care to avoid collisions:

```json
{
  "name": "John Doe",
  "email": "john.doe@example.com",
  "email_verified": true,
  "picture": "https://example.com/john.jpg"
}
```

#### 3. Private Claims

Custom claims agreed upon between parties:

```json
{
  "user_id": "12345",
  "role": "admin",
  "permissions": ["read", "write", "delete"],
  "organization_id": "org-abc-123",
  "is_premium": true
}
```

### Example Payload

```json
{
  // Registered claims
  "iss": "https://auth.example.com",
  "sub": "248289761001",
  "aud": "https://api.example.com",
  "exp": 1641234567,
  "iat": 1641230967,
  
  // Public claims
  "name": "Jane Smith",
  "email": "jane.smith@example.com",
  "email_verified": true,
  
  // Private claims
  "role": "editor",
  "organization": "Acme Corp",
  "permissions": ["posts:read", "posts:write"]
}
```

## Part 3: Signature

The signature ensures the token hasn't been tampered with and verifies the sender's identity.

### How It's Created

```
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)
```

Or for RSA:

```
RSASHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  privateKey
)
```

### Purpose

The signature serves two critical functions:

1. **Integrity:** Verifies that the header and payload haven't been modified
2. **Authenticity:** Proves the token was issued by a trusted party

### Verification Process

```
┌─────────────────────────────────────────┐
│ Received JWT                            │
├─────────────────────────────────────────┤
│ Header: { "alg": "HS256", "typ": "JWT" }│
│ Payload: { "sub": "123", "name": "..." }│
│ Signature: "SflKxwRJSM..."              │
└─────────────────────────────────────────┘
              ↓
┌─────────────────────────────────────────┐
│ Server recomputes signature:            │
│ HMACSHA256(header + "." + payload, key) │
└─────────────────────────────────────────┘
              ↓
┌─────────────────────────────────────────┐
│ Compare signatures:                     │
│ Computed == Received?                   │
├─────────────────────────────────────────┤
│ ✓ Match → Token is valid               │
│ ✗ No match → Token tampered/invalid    │
└─────────────────────────────────────────┘
```

## Base64Url Encoding

JWTs use **Base64Url encoding** (not standard Base64).

### Differences from Standard Base64

| Character | Standard Base64 | Base64Url |
|-----------|-----------------|-----------|
| 62nd char | `+` | `-` |
| 63rd char | `/` | `_` |
| Padding | `=` | No padding |

**Why Base64Url?**
- URL-safe (no special characters that need escaping)
- Can be used in HTTP headers
- Can be used in URL query parameters

### Example

```javascript
// Original JSON
const header = { "alg": "HS256", "typ": "JWT" };

// JSON stringify
const headerJson = JSON.stringify(header);
// {"alg":"HS256","typ":"JWT"}

// Base64Url encode
const headerEncoded = base64UrlEncode(headerJson);
// eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
```

## Decoding JWTs

### Important: Decoding ≠ Validation

**Decoding** extracts the header and payload. Anyone can do this.

**Validation** verifies the signature and claims. Only those with the key can do this.

```javascript
// ❌ WRONG: Trusting decoded data without validation
const parts = jwt.split('.');
const payload = JSON.parse(atob(parts[1]));
const userId = payload.sub;  // DANGER: Unvalidated data!

// ✅ CORRECT: Validate first, then use
const validated = await validateJwt(jwt, secret);
if (validated.isValid) {
  const userId = validated.payload.sub;  // Safe to use
}
```

### Using jwt.io

Visit [jwt.io](https://jwt.io) to decode and inspect JWTs:

1. Paste your JWT in the "Encoded" section
2. View the decoded header and payload
3. **Warning:** Never paste real production tokens on public websites!

## Practical Examples

### Creating a JWT (C#)

```csharp
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using Microsoft.IdentityModel.Tokens;

public string CreateJwt(string userId, string userName)
{
    var key = new SymmetricSecurityKey(
        Encoding.UTF8.GetBytes("your-256-bit-secret-key-here"));
    
    var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    
    var claims = new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub, userId),
        new Claim(JwtRegisteredClaimNames.Name, userName),
        new Claim(JwtRegisteredClaimNames.Email, "user@example.com"),
        new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
        new Claim("role", "admin")  // Custom claim
    };
    
    var token = new JwtSecurityToken(
        issuer: "https://auth.example.com",
        audience: "https://api.example.com",
        claims: claims,
        notBefore: DateTime.UtcNow,
        expires: DateTime.UtcNow.AddHours(1),
        signingCredentials: credentials
    );
    
    return new JwtSecurityTokenHandler().WriteToken(token);
}
```

### Reading a JWT (C#)

```csharp
public void InspectJwt(string jwt)
{
    var handler = new JwtSecurityTokenHandler();
    
    // Decode (without validation)
    var token = handler.ReadJwtToken(jwt);
    
    Console.WriteLine($"Algorithm: {token.Header.Alg}");
    Console.WriteLine($"Type: {token.Header.Typ}");
    Console.WriteLine($"Issuer: {token.Issuer}");
    Console.WriteLine($"Subject: {token.Subject}");
    Console.WriteLine($"Valid From: {token.ValidFrom}");
    Console.WriteLine($"Valid To: {token.ValidTo}");
    
    Console.WriteLine("\nClaims:");
    foreach (var claim in token.Claims)
    {
        Console.WriteLine($"  {claim.Type}: {claim.Value}");
    }
}
```

### Creating a JWT (JavaScript/Node.js)

```javascript
const jwt = require('jsonwebtoken');

function createJwt(userId, userName) {
  const payload = {
    sub: userId,
    name: userName,
    email: 'user@example.com',
    role: 'admin'
  };
  
  const secret = 'your-256-bit-secret-key-here';
  
  const options = {
    issuer: 'https://auth.example.com',
    audience: 'https://api.example.com',
    expiresIn: '1h',
    algorithm: 'HS256'
  };
  
  return jwt.sign(payload, secret, options);
}
```

## Security Implications of JWT Structure

### ⚠️ The Payload is NOT Encrypted

```json
{
  "sub": "123",
  "name": "John Doe",
  "password": "secret123",  // ❌ NEVER DO THIS
  "ssn": "123-45-6789",     // ❌ NEVER DO THIS
  "credit_card": "1234..."   // ❌ NEVER DO THIS
}
```

**Anyone can decode the payload:**
```bash
# On Linux/Mac
echo "eyJzdWIiOiIxMjM..." | base64 -d

# In browser
atob("eyJzdWIiOiIxMjM...")
```

### ✅ What to Put in JWTs

- User ID (sub)
- User name
- Email (if not sensitive)
- Roles and permissions
- Token metadata (iat, exp, iss, aud)
- Non-sensitive user preferences

### ❌ What NOT to Put in JWTs

- Passwords or password hashes
- Social Security Numbers
- Credit card numbers
- Any PII (Personally Identifiable Information) that's sensitive
- API keys or secrets
- Session secrets

---

## JWT vs JWE (JSON Web Encryption)

If you need to encrypt the payload, use **JWE** (JSON Web Encryption), not JWT:

```
JWT  = Signed (integrity + authenticity)
JWE  = Encrypted (confidentiality + integrity + authenticity)
```

**Example JWE:**
```
eyJhbGciOiJSU0ExXzUi...  // Encrypted
```

For most use cases, JWT (signed) is sufficient. Use JWE only when you must include sensitive data.

## Common Misconceptions

### ❌ "JWTs are encrypted"
**Reality:** JWTs are encoded and signed, not encrypted. Anyone can decode and read them.

### ❌ "Base64 encoding provides security"
**Reality:** Base64 is encoding, not encryption. It's trivially reversible.

### ❌ "I can trust data in a decoded JWT"
**Reality:** Only trust data after signature validation. Decoding without validation is unsafe.

### ❌ "Longer JWTs are more secure"
**Reality:** Security comes from the signature and algorithm, not the size.
