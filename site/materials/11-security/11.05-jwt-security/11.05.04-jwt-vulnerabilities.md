## Introduction

JWTs are powerful but dangerous when misused. Many high-profile security breaches have resulted from JWT vulnerabilities. This lesson covers the most common attacks, how they work, and how to prevent them. Understanding these vulnerabilities is essential for building secure applications.

**Key principle:** Assume attackers will try every known JWT exploit. Your defenses must be comprehensive, not partial.

## 1. The "None" Algorithm Attack

### How It Works

The JWT specification allows an algorithm value of `"none"`, indicating an unsigned token.

**Attack flow:**
1. Attacker obtains a valid JWT
2. Attacker modifies the header to set `"alg": "none"`
3. Attacker modifies the payload (escalate privileges, change user ID)
4. Attacker removes or empties the signature
5. If server accepts "none", token is validated without checking signature

### Example Attack

**Original token:**
```
Header:
{
  "alg": "HS256",
  "typ": "JWT"
}

Payload:
{
  "sub": "user123",
  "role": "user"
}

Signature: (valid signature)
```

**Malicious token:**
```
Header:
{
  "alg": "none",     ← Changed
  "typ": "JWT"
}

Payload:
{
  "sub": "user123",
  "role": "admin"    ← Escalated privileges
}

Signature: (empty or removed)
```

### Vulnerable Code

```csharp
// ❌ VULNERABLE: Accepts any algorithm
var validationParameters = new TokenValidationParameters
{
    ValidateIssuerSigningKey = false,  // DANGER!
    IssuerSigningKey = key
};
```

### Defense

```csharp
// ✅ SECURE: Explicitly reject "none"
var validationParameters = new TokenValidationParameters
{
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = key,
    RequireSignedTokens = true,  // Reject unsigned tokens
    
    // Whitelist acceptable algorithms
    ValidAlgorithms = new[] { SecurityAlgorithms.RsaSha256 }
};

// Additional manual check
var token = handler.ReadJwtToken(jwt);
if (token.Header.Alg == SecurityAlgorithms.None || 
    token.Header.Alg.Equals("none", StringComparison.OrdinalIgnoreCase))
{
    throw new SecurityTokenException("Algorithm 'none' is not allowed");
}
```

## 2. Algorithm Confusion Attack

### How It Works

Exploits servers that accept multiple algorithms (RS256 and HS256) and don't properly validate which algorithm to use.

**Attack flow:**
1. Server uses RS256 (asymmetric) to sign tokens
2. Server's public key is available (as intended)
3. Attacker changes header from `"alg": "RS256"` to `"alg": "HS256"`
4. Attacker signs token with HS256 using the public key as the HMAC secret
5. Server validates token using the public key as an HMAC secret
6. Validation succeeds (WRONG!)

### Why It Works

```
RS256 Signing:
  signature = RSA_SIGN(message, privateKey)
  verify = RSA_VERIFY(message, signature, publicKey)

HS256 Signing:
  signature = HMAC(message, secret)
  verify = HMAC(message, secret) == signature

Attack:
  Server has: publicKey
  Attacker uses: signature = HMAC(message, publicKey)
  Server validates: HMAC(message, publicKey) == signature
  Result: VALID (but shouldn't be!)
```

### Vulnerable Code

```csharp
// ❌ VULNERABLE: Accepts multiple incompatible algorithms
var validationParameters = new TokenValidationParameters
{
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = rsaPublicKey,
    
    // Attacker can switch to HS256 and use public key as secret!
    ValidAlgorithms = new[] { "RS256", "HS256" }
};
```

### Defense

```csharp
// ✅ SECURE: Only accept ONE algorithm type
var validationParameters = new TokenValidationParameters
{
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = rsaPublicKey,
    
    // Only RS256, period
    ValidAlgorithms = new[] { SecurityAlgorithms.RsaSha256 }
};

// Or use separate endpoints/validators for different algorithms
// Never mix RS256 and HS256 in the same validator
```

## 3. Weak HMAC Secrets

### How It Works

If an HS256 secret is weak, attackers can brute-force it offline.

**Attack flow:**
1. Attacker obtains a valid JWT
2. Attacker tries millions of secret candidates
3. For each candidate, compute HMAC signature
4. If computed signature matches JWT signature, secret found
5. Attacker can now forge any token

### Vulnerable Secrets

```csharp
// ❌ VULNERABLE: Weak secrets
var secret = "password";
var secret = "secret";
var secret = "123456";
var secret = "myapp";

// ❌ VULNERABLE: Short secrets
var secret = "abc";  // Way too short

// ❌ VULNERABLE: Dictionary words
var secret = "administrator";
```

### Defense

```csharp
// ✅ SECURE: Strong, random secret (256+ bits for HS256)
using System.Security.Cryptography;

public static string GenerateSecureSecret()
{
    var bytes = new byte[32];  // 256 bits
    RandomNumberGenerator.Fill(bytes);
    return Convert.ToBase64String(bytes);
}

// Example result: "yQ3kF8xN2mL9pR1vT6wZ4jH7dB5sA0cY8gU3nE2qK1="

// Store in secure configuration, never in source code
var secret = configuration["Jwt:Secret"];
```

### Key Requirements

| Algorithm | Minimum Key Size | Recommended |
|-----------|------------------|-------------|
| HS256 | 256 bits (32 bytes) | 256 bits |
| HS384 | 384 bits (48 bytes) | 384 bits |
| HS512 | 512 bits (64 bytes) | 512 bits |

## 4. No Signature Verification

### How It Works

Some implementations decode JWTs without validating the signature.

### Vulnerable Code

```csharp
// ❌ VULNERABLE: Decoding without validation
var handler = new JwtSecurityTokenHandler();
var token = handler.ReadJwtToken(jwt);  // Only decodes, doesn't validate!

var userId = token.Claims.First(c => c.Type == "sub").Value;
var role = token.Claims.First(c => c.Type == "role").Value;

// Using unvalidated data - DANGER!
```

```javascript
// ❌ VULNERABLE: Manual decoding
function parseJwt(token) {
    const base64Url = token.split('.')[1];
    const base64 = base64Url.replace(/-/g, '+').replace(/_/g, '/');
    const jsonPayload = decodeURIComponent(atob(base64).split('').map(c => {
        return '%' + ('00' + c.charCodeAt(0).toString(16)).slice(-2);
    }).join(''));
    
    return JSON.parse(jsonPayload);
}

const payload = parseJwt(token);
const userId = payload.sub;  // UNVALIDATED - NEVER DO THIS
```

### Defense

```csharp
// ✅ SECURE: Always validate before trusting
var validationParameters = new TokenValidationParameters
{
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = key,
    ValidateIssuer = true,
    ValidIssuer = issuer,
    ValidateAudience = true,
    ValidAudience = audience,
    ValidateLifetime = true
};

try
{
    var principal = handler.ValidateToken(jwt, validationParameters, out _);
    
    // NOW it's safe to use the data
    var userId = principal.FindFirst("sub")?.Value;
    var role = principal.FindFirst("role")?.Value;
}
catch (SecurityTokenException)
{
    // Token invalid - reject
    throw;
}
```

## 5. Trusting Unvalidated Claims

### How It Works

Even with signature validation, trusting certain claims without additional checks can be dangerous.

### Vulnerable Patterns

```csharp
// ❌ VULNERABLE: Blindly trusting claims
var principal = ValidateToken(jwt);  // Signature validated
var userId = principal.FindFirst("sub")?.Value;

// But what if the token is:
// 1. Expired?
// 2. For a different audience?
// 3. From wrong issuer?
// 4. User was deleted/banned?

// Use userId directly without additional checks - DANGER!
var user = database.GetUser(userId);
```

### Defense

```csharp
// ✅ SECURE: Validate ALL claims, then verify business rules
var principal = ValidateToken(jwt);  // Validates: signature, exp, aud, iss

var userId = principal.FindFirst("sub")?.Value;

// Additional business logic checks
var user = await database.GetUser(userId);

if (user == null)
{
    throw new SecurityException("User not found");
}

if (user.IsBanned)
{
    throw new SecurityException("User is banned");
}

if (user.IsDeleted)
{
    throw new SecurityException("User is deleted");
}

// NOW it's safe to proceed
```

## 6. Missing Expiration Validation

### How It Works

Tokens without expiration or with validation disabled allow indefinite access.

### Vulnerable Code

```csharp
// ❌ VULNERABLE: No expiration in token
var token = new JwtSecurityToken(
    issuer: issuer,
    audience: audience,
    claims: claims
    // No expires parameter!
);

// ❌ VULNERABLE: Expiration validation disabled
var validationParameters = new TokenValidationParameters
{
    ValidateLifetime = false,  // DANGER!
    // ...
};
```

### Defense

```csharp
// ✅ SECURE: Always set expiration
var token = new JwtSecurityToken(
    issuer: issuer,
    audience: audience,
    claims: claims,
    expires: DateTime.UtcNow.AddHours(1),  // Short-lived
    signingCredentials: credentials
);

// ✅ SECURE: Always validate expiration
var validationParameters = new TokenValidationParameters
{
    ValidateLifetime = true,
    RequireExpirationTime = true,  // Require exp claim
    ClockSkew = TimeSpan.FromMinutes(5)
};
```

### Recommended Token Lifetimes

| Token Type | Recommended Lifetime |
|------------|---------------------|
| Access Token | 5-60 minutes |
| ID Token | 5-60 minutes |
| Refresh Token | Hours to days (with rotation) |

## 7. Header Parameter Injection

### JWK Injection Attack

JWTs can include a `jwk` header parameter containing the public key to verify the signature.

**Attack:**
1. Attacker generates their own key pair
2. Attacker includes their public key in JWT header (`jwk` parameter)
3. Attacker signs JWT with their private key
4. If server uses the `jwk` from header, validation succeeds!

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "jwk": {
    "kty": "RSA",
    "e": "AQAB",
    "n": "attacker's public key..."
  }
}
```

### JKU Injection Attack

Similar to JWK, but `jku` points to a URL where the key set is hosted.

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "jku": "https://attacker.com/keys.json"
}
```

### Defense

```csharp
// ✅ SECURE: Never trust keys from token header
var validationParameters = new TokenValidationParameters
{
    ValidateIssuerSigningKey = true,
    
    // Use ONLY keys you control or fetch from trusted sources
    IssuerSigningKey = trustedPublicKey,
    
    // OR fetch from trusted JWKS endpoint
    IssuerSigningKeyResolver = (token, securityToken, kid, parameters) =>
    {
        // Fetch from YOUR trusted authority only
        var keys = FetchKeysFromTrustedAuthority();
        return keys;
    }
};

// NEVER use jwk or jku from token header
```

## 8. Token Disclosure/Leakage

### Common Leakage Vectors

**1. Logging:**
```csharp
// ❌ VULNERABLE: Logging tokens
logger.LogInformation($"Received token: {jwt}");
logger.LogDebug($"Authorization header: {authHeader}");
```

**2. URL Parameters:**
```
// ❌ VULNERABLE: Token in URL
https://api.example.com/data?token=eyJhbGciOi...

// Token appears in:
// - Browser history
// - Server logs
// - Proxy logs
// - Referer headers
```

**3. Local Storage:**
```javascript
// ❌ VULNERABLE: Token in localStorage (XSS vulnerable)
localStorage.setItem('token', jwt);

// Any JavaScript can access it:
var stolenToken = localStorage.getItem('token');
```

**4. Insecure Transmission:**
```
// ❌ VULNERABLE: Token over HTTP (not HTTPS)
http://api.example.com/data
Authorization: Bearer eyJhbGciOi...

// Token can be intercepted by anyone on the network
```

### Defense

```csharp
// ✅ SECURE: Sanitize logs
logger.LogInformation("User authenticated");  // Don't log token

// If you must log for debugging, mask it
var maskedToken = jwt.Length > 20 ? jwt.Substring(0, 20) + "..." : "***";
logger.LogDebug($"Token prefix: {maskedToken}");

// ✅ SECURE: Use Authorization header, not URL
// POST /api/data
// Authorization: Bearer eyJhbGciOi...

// ✅ SECURE: HTTPS always
app.UseHttpsRedirection();
app.UseHsts();

// ✅ SECURE: HttpOnly cookies or memory storage (not localStorage)
// Backend for Frontend (BFF) pattern recommended for SPAs
```

## Security Checklist

### Token Creation
- ✓ Use strong algorithms (RS256, ES256)
- ✓ Set short expiration times
- ✓ Include all required claims (iss, aud, exp, sub)
- ✓ Use strong secrets (256+ bits for HMAC)
- ✓ Never include sensitive data in payload

### Token Validation
- ✓ Validate signature
- ✓ Validate algorithm (whitelist)
- ✓ Validate issuer
- ✓ Validate audience
- ✓ Validate expiration
- ✓ Validate not-before (if present)
- ✓ Reject "none" algorithm
- ✓ Use up-to-date libraries

### Token Storage & Transmission
- ✓ Use HTTPS exclusively
- ✓ Use Authorization header
- ✓ HttpOnly cookies for web
- ✓ Never log tokens
- ✓ Never store in localStorage
- ✓ Never pass in URL parameters

## Testing for Vulnerabilities

### Manual Testing

```bash
# Test 1: None algorithm attack
# Original token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.SflKx...

# Change header to {"alg":"none","typ":"JWT"}
# Base64Url encode: eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0
# New token: eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiIxMjM0NTY3ODkwIn0.

# Test 2: Algorithm confusion
# Change RS256 to HS256 in header
# Sign with public key as HMAC secret

# Test 3: Expired token
# Use token with exp in the past

# Test 4: Wrong audience
# Create token with different aud claim
```

### Automated Testing

```csharp
[Fact]
public void RejectToken_WithNoneAlgorithm()
{
    var noneToken = CreateTokenWithAlgorithm("none");
    
    Assert.Throws<SecurityTokenException>(() =>
        _validator.Validate(noneToken)
    );
}

[Fact]
public void RejectToken_WithAlgorithmMismatch()
{
    // Create HS256 token, validator expects RS256
    var hs256Token = CreateHS256Token();
    
    Assert.Throws<SecurityTokenInvalidAlgorithmException>(() =>
        _rsaValidator.Validate(hs256Token)
    );
}

[Fact]
public void RejectToken_WithWeakSecret()
{
    // This test checks if weak secrets can be brute-forced
    // Use a known weak secret and attempt to crack it
    var weakSecret = "password";
    var token = CreateToken(weakSecret);
    
    var crackedSecret = BruteForceSecret(token);
    
    Assert.Equal(weakSecret, crackedSecret);
    // If this passes, your secret is too weak!
}
```

## Real-World Examples

### Example 1: Critical Vulnerability (2015)

Auth0 discovered vulnerabilities in popular JWT libraries that accepted the "none" algorithm, allowing complete authentication bypass.

### Example 2: Algorithm Confusion (2016)

Many Node.js JWT libraries were vulnerable to algorithm confusion attacks, where RS256 tokens could be forged using the public key.

### Example 3: Weak Secrets (Ongoing)

Attackers regularly brute-force weak HMAC secrets from captured JWTs, especially when secrets are common words or short strings.
