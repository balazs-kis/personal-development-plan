# Lesson 2: JWT Signing Algorithms

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand the difference between symmetric and asymmetric signing algorithms
- Compare HS256, RS256, and ES256 algorithms
- Choose the appropriate algorithm for your use case
- Understand the security implications of each algorithm
- Recognize and prevent algorithm confusion attacks

---

## Introduction

The signing algorithm (`alg` in the JWT header) is one of the most critical security decisions you'll make when implementing JWTs. Choosing the wrong algorithm or misconfiguring it can completely undermine your application's security. This lesson covers the main JWT signing algorithms, their strengths and weaknesses, and when to use each.

**Key principle:** The algorithm determines how the signature is created and verified. It's not just about cryptography—it's about the trust model and key management of your system.

## Key Concepts Summary

### Algorithm Categories

JWT signing algorithms fall into two main categories:

```
┌─────────────────────────────────────────────────────┐
│ Symmetric (HMAC)                                    │
├─────────────────────────────────────────────────────┤
│ • Same secret key for signing AND verification      │
│ • HS256, HS384, HS512                              │
│ • Faster, simpler                                   │
│ • Both parties must have the secret                │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│ Asymmetric (RSA, ECDSA)                            │
├─────────────────────────────────────────────────────┤
│ • Private key for signing, public key for verify    │
│ • RS256, RS384, RS512 (RSA)                        │
│ • ES256, ES384, ES512 (ECDSA)                      │
│ • More secure key distribution                     │
│ • Only issuer needs the private key                │
└─────────────────────────────────────────────────────┘
```

## HS256 (HMAC with SHA-256)

### What It Is

**HMAC** = Hash-based Message Authentication Code

Uses a **symmetric secret key** to create and verify signatures.

```
Signature = HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)
```

### How It Works

```
┌──────────────┐                          ┌──────────────┐
│   Issuer     │                          │  Validator   │
│              │                          │              │
│ [Secret Key] │                          │ [Secret Key] │
└──────┬───────┘                          └──────┬───────┘
       │                                         │
       │ 1. Create signature                     │
       │    using secret                         │
       │                                         │
       │ ──────────────────────────────────────> │
       │         Send JWT                        │
       │                                         │
       │                           2. Verify     │
       │                              signature  │
       │                              using      │
       │                              secret     │
```

### Advantages

✅ **Fast:** HMAC operations are computationally efficient
✅ **Simple:** Easy to implement and understand
✅ **Small signatures:** Shorter than RSA signatures

### Disadvantages

❌ **Shared secret:** Both issuer and validator must have the same secret
❌ **Key distribution:** How do you securely share the secret?
❌ **Trust model:** Anyone with the secret can create and verify tokens

### When to Use HS256

Use HS256 when:
- Issuer and validator are the same system (monolith)
- You control both token creation and validation
- Performance is critical
- You have secure key management

**Example:** Single API server that issues and validates its own JWTs.

### Security Requirements

```csharp
// ✅ GOOD: Strong, random secret (256 bits minimum for HS256)
var secret = GenerateCryptographicRandomBytes(32); // 256 bits

// ❌ BAD: Weak, guessable secret
var secret = "password123";

// ❌ BAD: Short secret
var secret = "abc";
```

**Minimum key lengths:**
- HS256: 256 bits (32 bytes)
- HS384: 384 bits (48 bytes)
- HS512: 512 bits (64 bytes)

### Implementation Example (C#)

```csharp
using System.IdentityModel.Tokens.Jwt;
using Microsoft.IdentityModel.Tokens;

public class JwtService
{
    private readonly SymmetricSecurityKey _key;
    
    public JwtService(string secret)
    {
        // Secret must be at least 256 bits (32 bytes) for HS256
        _key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret));
    }
    
    public string CreateToken(string userId)
    {
        var credentials = new SigningCredentials(_key, SecurityAlgorithms.HmacSha256);
        
        var token = new JwtSecurityToken(
            issuer: "https://api.example.com",
            audience: "https://api.example.com",
            claims: new[] { new Claim("sub", userId) },
            expires: DateTime.UtcNow.AddHours(1),
            signingCredentials: credentials
        );
        
        return new JwtSecurityTokenHandler().WriteToken(token);
    }
    
    public ClaimsPrincipal ValidateToken(string jwt)
    {
        var validationParameters = new TokenValidationParameters
        {
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = _key,  // Same key used to validate
            
            ValidateIssuer = true,
            ValidIssuer = "https://api.example.com",
            
            ValidateAudience = true,
            ValidAudience = "https://api.example.com",
            
            ValidateLifetime = true,
            ClockSkew = TimeSpan.FromMinutes(5)
        };
        
        var handler = new JwtSecurityTokenHandler();
        return handler.ValidateToken(jwt, validationParameters, out _);
    }
}
```

## RS256 (RSA with SHA-256)

### What It Is

**RSA** = Rivest–Shamir–Adleman (asymmetric cryptography)

Uses a **public/private key pair**:
- **Private key:** Signs tokens (kept secret by issuer)
- **Public key:** Verifies tokens (can be publicly distributed)

```
Signature = RSASHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  privateKey
)
```

### How It Works

```
┌──────────────────┐                    ┌────────────────────┐
│     Issuer       │                    │    Validator       │
│                  │                    │                    │
│ [Private Key] 🔐 │                    │ [Public Key] 🔓   │
└────────┬─────────┘                    └────────┬───────────┘
         │                                       │
         │ 1. Sign with private key              │
         │                                       │
         │ ────────────────────────────────────> │
         │          Send JWT                     │
         │                                       │
         │                        2. Verify with │
         │                           public key  │
         │                                       │
         │ <──────────────────────────────────── │
         │     (Can share public key safely)     │
```

### Advantages

✅ **Secure key distribution:** Public key can be shared openly
✅ **Trust model:** Only the holder of the private key can create tokens
✅ **Multiple validators:** Many services can verify with the public key
✅ **No shared secrets:** Eliminates secret distribution problem

### Disadvantages

❌ **Slower:** RSA operations are more computationally expensive
❌ **Larger signatures:** RSA signatures are longer (typically 256-512 bytes)
❌ **Key management:** Must protect private key carefully

### When to Use RS256

Use RS256 when:
- Multiple services need to verify tokens
- Token issuer and validators are different systems
- You need to distribute verification capability without sharing secrets
- Security is more important than performance

**Example:** Authorization server issues tokens, multiple microservices validate them.

### Key Generation

```bash
# Generate private key (2048 bits minimum, 4096 recommended)
openssl genpkey -algorithm RSA -out private_key.pem -pkeyopt rsa_keygen_bits:2048

# Extract public key from private key
openssl rsa -pubout -in private_key.pem -out public_key.pem
```

### Implementation Example (C#)

```csharp
using System.IdentityModel.Tokens.Jwt;
using System.Security.Cryptography;
using Microsoft.IdentityModel.Tokens;

public class JwtService
{
    private readonly RsaSecurityKey _privateKey;
    private readonly RsaSecurityKey _publicKey;
    
    public JwtService()
    {
        var rsa = RSA.Create(2048);  // 2048-bit key
        _privateKey = new RsaSecurityKey(rsa);
        _publicKey = new RsaSecurityKey(rsa.ExportParameters(false));  // Public only
    }
    
    // Issuer side: Create token with private key
    public string CreateToken(string userId)
    {
        var credentials = new SigningCredentials(_privateKey, SecurityAlgorithms.RsaSha256);
        
        var token = new JwtSecurityToken(
            issuer: "https://auth.example.com",
            audience: "https://api.example.com",
            claims: new[] { new Claim("sub", userId) },
            expires: DateTime.UtcNow.AddHours(1),
            signingCredentials: credentials
        );
        
        return new JwtSecurityTokenHandler().WriteToken(token);
    }
    
    // Validator side: Validate token with public key
    public ClaimsPrincipal ValidateToken(string jwt)
    {
        var validationParameters = new TokenValidationParameters
        {
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = _publicKey,  // Only public key needed!
            
            ValidateIssuer = true,
            ValidIssuer = "https://auth.example.com",
            
            ValidateAudience = true,
            ValidAudience = "https://api.example.com",
            
            ValidateLifetime = true
        };
        
        var handler = new JwtSecurityTokenHandler();
        return handler.ValidateToken(jwt, validationParameters, out _);
    }
}
```

## ES256 (ECDSA with SHA-256)

### What It Is

**ECDSA** = Elliptic Curve Digital Signature Algorithm

Like RSA, uses **public/private key pair**, but based on elliptic curve cryptography.

### Advantages Over RSA

✅ **Smaller keys:** 256-bit ECDSA ≈ 3072-bit RSA security
✅ **Smaller signatures:** Much shorter than RSA signatures
✅ **Faster:** More efficient than RSA
✅ **Modern:** State-of-the-art cryptography

### When to Use ES256

Use ES256 when:
- You want asymmetric security with better performance
- Signature size matters (mobile, bandwidth-constrained)
- You're building a modern system from scratch

**Recommendation:** ES256 is generally preferred over RS256 for new systems.

### Implementation Example (C#)

```csharp
using System.Security.Cryptography;
using Microsoft.IdentityModel.Tokens;

public class JwtService
{
    private readonly ECDsaSecurityKey _privateKey;
    private readonly ECDsaSecurityKey _publicKey;
    
    public JwtService()
    {
        var ecdsa = ECDsa.Create(ECCurve.NamedCurves.nistP256);  // P-256 curve
        _privateKey = new ECDsaSecurityKey(ecdsa);
        
        var publicEcdsa = ECDsa.Create();
        publicEcdsa.ImportParameters(ecdsa.ExportParameters(false));
        _publicKey = new ECDsaSecurityKey(publicEcdsa);
    }
    
    public string CreateToken(string userId)
    {
        var credentials = new SigningCredentials(_privateKey, SecurityAlgorithms.EcdsaSha256);
        
        var token = new JwtSecurityToken(
            issuer: "https://auth.example.com",
            audience: "https://api.example.com",
            claims: new[] { new Claim("sub", userId) },
            expires: DateTime.UtcNow.AddHours(1),
            signingCredentials: credentials
        );
        
        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}
```

## Algorithm Comparison

| Feature | HS256 | RS256 | ES256 |
|---------|-------|-------|-------|
| **Type** | Symmetric | Asymmetric | Asymmetric |
| **Keys** | Shared secret | Public/Private | Public/Private |
| **Performance** | Fastest | Slowest | Fast |
| **Signature Size** | Small (32 bytes) | Large (256-512 bytes) | Small (64 bytes) |
| **Key Size** | 256 bits | 2048-4096 bits | 256 bits |
| **Security** | Depends on secret | Strong | Strongest |
| **Key Distribution** | Difficult | Easy | Easy |
| **Use Case** | Same system | Multiple systems | Modern systems |

## Algorithm Security Considerations

### The "none" Algorithm

```json
{
  "alg": "none",
  "typ": "JWT"
}
```

**NEVER accept tokens with `"alg": "none"`!**

This algorithm means "no signature." Attackers can forge tokens trivially.

```csharp
// ✅ GOOD: Explicitly reject "none"
var validationParameters = new TokenValidationParameters
{
    ValidAlgorithms = new[] { "RS256", "HS256" },  // Whitelist only
    RequireSignedTokens = true  // Reject unsigned tokens
};

// ❌ BAD: Accepting any algorithm
ValidateIssuerSigningKey = false
```

### Algorithm Confusion Attack

**Attack scenario:**
1. Server uses RS256 (asymmetric) with public/private keys
2. Server also accepts HS256 (symmetric)
3. Attacker gets the public key (it's public!)
4. Attacker changes `alg` from `RS256` to `HS256`
5. Attacker signs token with HS256 using the **public key as the HMAC secret**
6. Server validates using the public key as an HMAC secret
7. Attack succeeds!

**Prevention:**

```csharp
// ✅ GOOD: Whitelist expected algorithm
var validationParameters = new TokenValidationParameters
{
    ValidAlgorithms = new[] { "RS256" },  // Only RS256, period
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = publicKey  // RSA public key
};

// ❌ BAD: Accepting multiple incompatible algorithms
ValidAlgorithms = new[] { "RS256", "HS256" }  // Don't do this!
```

### Key Strength Requirements

| Algorithm | Minimum Key Size | Recommended |
|-----------|------------------|-------------|
| HS256 | 256 bits (32 bytes) | 256 bits |
| HS384 | 384 bits (48 bytes) | 384 bits |
| HS512 | 512 bits (64 bytes) | 512 bits |
| RS256 | 2048 bits | 2048-4096 bits |
| RS384 | 3072 bits | 3072-4096 bits |
| RS512 | 4096 bits | 4096 bits |
| ES256 | 256 bits (P-256 curve) | 256 bits |
| ES384 | 384 bits (P-384 curve) | 384 bits |
| ES512 | 521 bits (P-521 curve) | 521 bits |

## Decision Tree: Choosing an Algorithm

```
┌─────────────────────────────────────────┐
│ Do you control both issuer and          │
│ validator (same system)?                │
└────────┬────────────────────────────────┘
         │
    ┌────┴────┐
    │   YES   │ → HS256 (Simple, Fast)
    └─────────┘
         │
    ┌────┴────┐
    │   NO    │
    └────┬────┘
         │
┌────────┴─────────────────────────────────┐
│ Building a new system from scratch?      │
└────────┬─────────────────────────────────┘
         │
    ┌────┴────┐
    │   YES   │ → ES256 (Modern, Efficient)
    └─────────┘
         │
    ┌────┴────┐
    │   NO    │ → RS256 (Widely Supported)
    └─────────┘
```

## Practical Examples

### ASP.NET Core Configuration

```csharp
// Startup.cs / Program.cs

// For HS256 (symmetric)
services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        var secret = configuration["Jwt:Secret"];
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(secret)),
            
            ValidAlgorithms = new[] { SecurityAlgorithms.HmacSha256 },
            
            ValidateIssuer = true,
            ValidIssuer = configuration["Jwt:Issuer"],
            
            ValidateAudience = true,
            ValidAudience = configuration["Jwt:Audience"]
        };
    });

// For RS256 (asymmetric)
services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://auth.example.com";  // OIDC authority
        options.Audience = "https://api.example.com";
        
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidAlgorithms = new[] { SecurityAlgorithms.RsaSha256 },
            ValidateIssuerSigningKey = true
            // Public key fetched from JWKS endpoint automatically
        };
    });
```

## Common Mistakes

### Mistake 1: Using Weak HMAC Secrets

```csharp
// ❌ BAD: Weak secret
var secret = "password";
var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret));

// ✅ GOOD: Strong, random secret
var secret = Convert.ToBase64String(RandomNumberGenerator.GetBytes(32));
var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret));
```

### Mistake 2: Not Whitelisting Algorithms

```csharp
// ❌ BAD: Accepting any algorithm
var validationParameters = new TokenValidationParameters
{
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = key
    // No ValidAlgorithms specified!
};

// ✅ GOOD: Explicit algorithm whitelist
ValidAlgorithms = new[] { "HS256" }
```

### Mistake 3: Mixing Asymmetric and Symmetric

```csharp
// ❌ BAD: Accepting both
ValidAlgorithms = new[] { "RS256", "HS256" }  // Algorithm confusion risk!

// ✅ GOOD: One or the other
ValidAlgorithms = new[] { "RS256" }
```
