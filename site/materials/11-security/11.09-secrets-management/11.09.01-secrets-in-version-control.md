# Lesson 1: Secrets in Version Control: Why Not and How to Prevent

## Learning Objectives

By the end of this lesson, you will be able to:
- Understand why secrets should never be committed to version control
- Recognize common ways secrets accidentally leak into repositories
- Use .gitignore and git-secrets to prevent secret commits
- Respond appropriately when secrets are accidentally committed
- Implement secret scanning in your development workflow

---

## Introduction

One of the most common and dangerous security mistakes is committing secrets (API keys, passwords, tokens, certificates) to version control. Even if you delete them later, they remain in Git history forever and can be easily discovered by attackers. This lesson teaches you why this is critical and how to prevent it from happening.

**Key principle:** Once a secret hits version control, consider it compromised. Prevention is the only reliable defense.

## Key Concepts Summary

### Why Secrets in Git is Dangerous

```
The Problem:
1. Git history is permanent - deleting a file doesn't delete history
2. Repositories can be cloned by anyone with access
3. Public repositories are indexed by search engines
4. Bots scan GitHub constantly looking for leaked credentials
5. Former employees retain cloned copies

Real-World Impact:
- AWS keys leaked → $50,000+ in unauthorized charges within hours
- Database credentials leaked → entire customer database stolen
- API keys leaked → service abuse and rate limit exhaustion
- Private keys leaked → impersonation and unauthorized access
```

### Common Ways Secrets Leak

```csharp
// ❌ BAD: Hardcoded in source code
public class DatabaseConfig
{
    public const string ConnectionString = 
        "Server=prod-db.example.com;User=admin;Password=MyP@ssw0rd123";
}

// ❌ BAD: In appsettings.json (committed to Git)
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=...;Password=secret123"
  },
  "ApiKeys": {
    "Stripe": "sk_live_actual_key_here"
  }
}

// ❌ BAD: In environment-specific files that get committed
// appsettings.Production.json - should NOT be in Git!

// ❌ BAD: In comments
// TODO: Use password "TempPass123" until we fix the auth system

// ❌ BAD: In example or test files
// ExampleConfig.cs with real credentials "for testing"
```

### Using .gitignore Properly

```bash
# .gitignore - Always ignore these files

# Secret files
*.env
*.env.local
*.env.production
appsettings.Production.json
appsettings.Staging.json
secrets.json
*.pfx
*.pem
*.key

# User-specific files
*.user
*.suo
*.userprefs

# IDE folders
.vs/
.vscode/
.idea/

# Configuration files that may contain secrets
**/appsettings.*.json
!**/appsettings.json
!**/appsettings.Development.json

# Certificate files
*.cer
*.crt
*.p12

# AWS credentials
.aws/

# Azure credentials
.azure/
```

### Git Pre-Commit Hook

```bash
#!/bin/sh
# .git/hooks/pre-commit

# Check for common secret patterns
if git diff --cached --name-only | xargs grep -E '(password|secret|key|token).*=.*["\047][^"\047]+["\047]' ; then
    echo "⚠️  Possible secret detected in commit!"
    echo "Please review the above matches and remove any sensitive data."
    exit 1
fi

# Check for specific file patterns
if git diff --cached --name-only | grep -E '\.(pfx|p12|pem|key)$' ; then
    echo "⚠️  Certificate or key file detected in commit!"
    echo "These files should not be committed to version control."
    exit 1
fi

exit 0
```

### Using git-secrets Tool

```bash
# Install git-secrets (macOS)
brew install git-secrets

# Install git-secrets (Windows - via chocolatey)
choco install git-secrets

# Install git-secrets (Linux)
git clone https://github.com/awslabs/git-secrets.git
cd git-secrets
sudo make install

# Initialize git-secrets in repository
cd your-repo
git secrets --install

# Register AWS patterns
git secrets --register-aws

# Add custom patterns
git secrets --add 'password\s*=\s*.+'
git secrets --add 'sk_live_[0-9a-zA-Z]{24}'  # Stripe keys
git secrets --add 'api[_-]?key\s*[:=]\s*["\047][^\047"]+["\047]'

# Scan repository for secrets
git secrets --scan

# Scan entire history
git secrets --scan-history
```

### Secret Scanning in CI/CD

```yaml
# GitHub Actions - Secret scanning
name: Security Scan

on: [push, pull_request]

jobs:
  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
        with:
          fetch-depth: 0  # Full history for scanning
      
      - name: TruffleHog Secret Scan
        uses: trufflesecurity/trufflehog@main
        with:
          path: ./
          base: ${{ github.event.repository.default_branch }}
          head: HEAD
      
      - name: Gitleaks
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### When a Secret is Leaked

```bash
# Step 1: Consider it compromised immediately
# The moment a secret enters Git, assume it's exposed

# Step 2: Rotate the secret
# - Change the password
# - Revoke the API key and generate a new one
# - Regenerate the certificate
# - Update all services using the old secret

# Step 3: Check for unauthorized usage
# - Review access logs for the compromised credential
# - Check for unusual activity
# - Alert your security team

# Step 4: Remove from Git history (but still consider compromised!)
# Using git filter-repo (recommended)
git filter-repo --path-glob '**/secrets.json' --invert-paths

# Or using BFG Repo Cleaner
java -jar bfg.jar --delete-files secrets.json
git reflog expire --expire=now --all
git gc --prune=now --aggressive

# Step 5: Force push (requires coordination with team)
git push origin --force --all

# Step 6: Notify all developers
# Everyone must re-clone the repository
```

### Proper Alternatives

```csharp
// ✅ GOOD: Use environment variables
var connectionString = Environment.GetEnvironmentVariable("DATABASE_CONNECTION_STRING");
var apiKey = Environment.GetEnvironmentVariable("STRIPE_API_KEY");

// ✅ GOOD: Use User Secrets (development)
// Stored in: %APPDATA%\Microsoft\UserSecrets\<user_secrets_id>\secrets.json
// Initialize: dotnet user-secrets init
// Set: dotnet user-secrets set "Stripe:ApiKey" "sk_test_..."

// ✅ GOOD: Use Configuration (loads from multiple sources)
var apiKey = configuration["Stripe:ApiKey"];

// ✅ GOOD: Use Key Vault (production)
var keyVaultUrl = configuration["KeyVaultUrl"];
builder.Configuration.AddAzureKeyVault(new Uri(keyVaultUrl), new DefaultAzureCredential());

// ✅ GOOD: Template files with placeholders
// appsettings.template.json (committed)
{
  "ConnectionStrings": {
    "DefaultConnection": "<INSERT_CONNECTION_STRING>"
  },
  "ApiKeys": {
    "Stripe": "<INSERT_STRIPE_KEY>"
  }
}

// appsettings.Production.json (NOT committed, generated during deployment)
```

### GitHub Secret Scanning

```
GitHub automatically scans repositories for known secret patterns:
- AWS keys
- Azure tokens
- Google Cloud keys
- Stripe API keys
- GitHub tokens
- And 200+ other patterns

When detected:
1. Repository owner receives alert
2. Secret provider may be notified
3. Push protection can block the commit
4. Security advisories are created

Enable push protection:
Settings → Code security and analysis → Secret scanning → Push protection
```

### Documentation Best Practices

```markdown
# README.md - Document secrets without revealing them

## Configuration

This application requires the following environment variables:

- `DATABASE_CONNECTION_STRING`: PostgreSQL connection string
- `STRIPE_API_KEY`: Stripe API key (get from Stripe Dashboard)
- `JWT_SECRET`: Secret key for JWT signing (generate with: openssl rand -base64 32)
- `SENDGRID_API_KEY`: SendGrid API key for email delivery

### Local Development

Copy `.env.example` to `.env` and fill in your local values:

```bash
cp .env.example .env
```

Never commit your `.env` file!

### Production Deployment

Production secrets are managed in Azure Key Vault. See [deployment docs](./docs/deployment.md) for details.
```

### Example .env.example File

```bash
# .env.example - COMMITTED to Git (no real values!)
# Copy this to .env and fill in real values

DATABASE_CONNECTION_STRING=Server=localhost;Database=myapp;User=dev;Password=<your-password>
STRIPE_API_KEY=sk_test_<your-test-key>
JWT_SECRET=<generate-with-openssl-rand-base64-32>
SENDGRID_API_KEY=<your-sendgrid-key>

# Azure (production only)
# AZURE_KEY_VAULT_URL=https://<your-vault>.vault.azure.net/
```

### Security Audit Checklist

```
□ All secret-containing files are in .gitignore
□ git-secrets or similar tool is installed
□ Pre-commit hooks check for secrets
□ Secret scanning enabled in CI/CD
□ No secrets in code comments or documentation
□ Template files documented with placeholders
□ Team trained on secret management
□ Incident response plan for leaked secrets
□ Regular audits of repository history
□ Rotate secrets if anyone with access leaves team
```
